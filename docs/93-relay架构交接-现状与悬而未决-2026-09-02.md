## 4. 用户已明确的核心诉求（接手人第一优先遵守）

- **不要自创一套 / 不要绕开 kit**：kit 引擎有能力就复用，缺了才加。
- **不要一堆薄层**：要"深"——一个领域一个模块做透，职责单一，不要一件事几个人干、数据不清。
- **所有生成能力全部走 relay（经 kit）**（用户原话："Kit 当然走 relay 啦，所有的东西都要走 relay 啊"、"老生成链全部废弃"）：image / video / text / chat 等**一切能力都走 relay → kit 引擎**，**没有老链兜底**。`routes/protocolAdapters` / `requestModes` 的生成部分 / `system.ts` 的 proxy 生成转发 / 前端 pollTask 那套老链是废弃对象。
- **落盘不依赖 kit**（走既有 `saveRemoteUrl`/前端 `saveResultToTasks`）。
- **别再让他为"真机出图"花钱**：要写测试（mock kit/网络）验证，不要每次 curl 烧积分。

## 5. 悬而未决 / 接手人要做决定的点（我在这些地方反复打转，别再重蹈）

1. **relay 层到底收敛成什么样？** 用户嫌 4 个 relay-*.ts 平铺壳 + relay-engine "薄层多、职责散"。但 route(HTTP端点)/poll(DB句柄+恢复)/common(provider+参考图+落盘)/presets(9004协议) 每块又都是 kit 不提供的必要职责。**需要一个"深"的归置**（可能并入一个目录/文件，或明确职责单一），但**别再新造一层逻辑**（我建 relay/core.ts 又被否："又要自创一套"）。
2. **chat/文本怎么"走 relay"（已定全走 relay，但有关键实现卡点）**：90号早期"chat 走老 proxy"红线已作废——用户明确所有能力走 relay。卡点：kit 门面 `relay.generate.text` 目前是**硬编码 OpenAI 同步、不吐流**。要让 chat 也走 relay→kit，得走 kit **协议驱动逃生舱**（像 image 一样传 chat 协议，`executeModelProtocol`/`submitModelProtocol` 支持 sync 文本），或给 kit 补 chat 流式能力。接手人需决定 chat 在 relay 里的形态（同步文本 or 流式）。
3. **kit 门面 vs 逃生舱分工**：同步 `/api/relay` 用门面 `relay.generate.image`；异步 `/api/generate` 用逃生舱 `submitModelProtocol`/driver。用户要"直接接 kit 门面/核心"——需确认这两条是否都算"直接接 kit"，还是用户想只用门面（但门面是阻塞式，给不了可 attach 的 /api/generate）。
4. **relay-engine 重排是否值得保留**：重排后与上游 `cp -R` 升级冲突。若觉得不值，可考虑 git 还原 relay-engine（但要小心：M1 driver + generate/image 改动在未提交内容里，git checkout 会丢，需先提取）。
