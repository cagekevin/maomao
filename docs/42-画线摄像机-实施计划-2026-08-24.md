# 画线摄像机沿曲线运动：实施计划

> 日期：2026-08-24
> 配套方案：`docs/41-画线摄像机沿曲线运动-我们现状与实施方案-2026-08-24.md`
> ⚠️ **审计状态（执行者必读）**：本计划经代码级批判性审计，已堵死 5 个会误导实现的坑（见各节 ⚠️ 标记）：① `cameraPath` 必须挂 shot 而非全局 state；② bake 焦距直接取 `camera.focalLength`（本工程 `camera` 即当前镜头主相机，无需额外快照）；③ 拖曲线不自动改关键帧（需主动重新生成）；④ history 是本工程「防抖自动追踪」，只需让 `cameraPath` 走 shot → `setShots` 即自动入栈，**勿手动** `recordChange`（本代码库无此手动 API）；⑤ 欧拉甩头是已知数学限制（非偶发）。**严格按本文实现，勿自作主张改数据流。**
> 核心对齐原则：**曲线只是"一次性批量生成相机关键帧"的输入方式**。生成后，曲线退场成普通关键帧，后续完全走现有"视窗拖对象→打关键帧"的同一套管线。画线时只动曲线，调关键帧时只动关键帧，两者互不干扰、互不实时影响——和现有"调时装只调时装、调关键帧只调关键帧"完全一致。

## 0. 设计决策（已与用户确认，实施必须遵循）

1. **工具栏"编辑曲线"按钮**（参考上传背景图按钮）：点一下弹小下拉菜单，两项+一参数——
   - 时间范围：从__秒 到__秒（决定关键帧铺哪段帧，默认 0→15s）
   - 画点密度：疏/中/密（只影响曲线控制点数量/形状，不影响关键帧）
   - 关键帧数量：数字（如 20，决定生成几个关键帧）
   - 底部「开始绘制」→ 进入 `editMode='path'`
2. **拖出曲线**：按住地面拖动，松手按弧长采样成控制点（密度由"画点密度"），并**生成关键帧**（数量由"关键帧数量"，铺满时间范围）。
3. **曲线只在 `editMode='path'` 显示**，切其他工具隐藏。
4. **曲线 = 镜头的运动，改曲线自动更新运镜**：`cameraPath.points / 参数` 是摄像机这条"骨骼"的运动源，拖动控制点或改三参数后**松手自动重新生成关键帧**（替换 `sourceKeyframeFrames`）、运镜立即变，无需"重新生成"按钮、不做任何提示。仅在 Timeline 里手动改关键帧的速度/时间时，曲线保持原样（曲线与"手调时间点"互为独立，自动生成只覆盖自己生成的帧）。
5. **右键控制点菜单**：①删除点（保底 2 点）②删除整条曲线。
6. **一条曲线 = 一个镜头的摄像机运动**（一段视频）；一个镜头只有一条摄像机曲线、对应它自己的关键帧行，不存在第二条曲线去覆盖/衔接。不写段间过渡。
7. **不预览**；画完去 Timeline 播放看效果。
8. 颜色：曲线本体用轴色 `#d7675b`；**控制点复用骨骼关节 `MixamoJointMarker` 同款金色**（§4.3），适配深色背景。

## 1. 数据模型（最小侵入，**必须挂在 shot 上**）

> ⚠️ 关键：历史坑——`cameraPath` **必须作为 shot 的一等字段**，绝不能是全局 state（像 `keyframes` 那样）。因为切换 shot / 克隆 shot / 应用 shot 状态都走 `normalizeShot` + `projectData` 链路，全局 state 会导致"切镜头曲线不跟着切、克隆丢曲线"。

`project.js` 的 `normalizeShot`（320-351）返回值里加：

```js
// normalizeShot 返回对象内新增（与 keyframes 并列）：
cameraPath: normalizeCameraPath(shot?.cameraPath)  // 旧工程/无 → null
```

`normalizeCameraPath` 给默认值：
```js
cameraPath: {
  id: string,
  points: { id: string, position: [x,y,z] }[],
  closed: boolean,
  tension: number,
  startFrame: number,
  endFrame: number,
  keyframeCount: number,
  sourceKeyframeFrames: number[], // 本曲线生成的关键帧 frame 列表；首次为 []
} | null
```

- `PROJECT_VERSION` +1，`normalizeShot` 对旧工程给 `cameraPath: null`（已在上面处理）。
- `projectData` / `cloneProjectValue` / `addShot` / `duplicateShot` / `applyShotState` 因 cameraPath 是 shot 字段，**自动透传**，无需额外改。
- App.jsx 里 `cameraPath` 应来自 `activeShot`（与 `keyframes` 取 `shot.keyframes` 同路；归一化统一在 project.js 的 `normalizeShot`，App 侧恢复走 `applyProjectSnapshot`，显示走 `displayedShots`），编辑时经现有 shot 更新链路写回 activeShot（参考现有怎么改 shot.camera / shot.keyframes）。

**关键帧本身不加任何新字段**——bake 出的关键帧就是 `{frame, position, rotation, focalLength, interpolation}`，和 `addKeyframe`（App.jsx:809）产物完全一致。仅 `cameraPath.sourceKeyframeFrames` 记录"哪些 frame 是这条曲线生成的"，用于重新生成/删除时精准替换，不误伤用户手动关键帧。

## 2. 纯函数（移植 nomi 数学，无副作用）

`project.js` 新增：

```js
import * as THREE from 'three'

export function buildCameraPathCurve(path) {
  const pts = path.points.map(p => new THREE.Vector3(...p.position))
  if (pts.length < 2) return null
  const curve = new THREE.CatmullRomCurve3(pts, path.closed, 'catmullrom', path.tension)
  curve.updateArcLengths()
  return curve
}

// 生成 keyframeCount 个关键帧，铺满 [startFrame, endFrame]
export function bakePathToKeyframes(path, startFrame, endFrame, keyframeCount, focalLength) {
  const curve = buildCameraPathCurve(path)
  if (!curve) return []
  const span = Math.max(1, endFrame - startFrame)
  const N = Math.max(2, Math.round(keyframeCount)) // 恰好生成 N 个关键帧（修正 off-by-one）
  const keys = []
  for (let i = 0; i < N; i++) {
    const u = N > 1 ? i / (N - 1) : 0 // 覆盖 [startFrame, endFrame] 两端
    const pos = curve.getPointAt(u)
    const tan = curve.getTangentAt(u).normalize()
    const m = new THREE.Matrix4().lookAt(pos, pos.clone().add(tan), new THREE.Vector3(0, 1, 0))
    const e = new THREE.Euler().setFromRotationMatrix(m)
    keys.push({
      frame: Math.round(startFrame + u * span),
      position: [pos.x, pos.y, pos.z],
      rotation: [e.x, e.y, e.z],
      focalLength,
      interpolation: 'smooth',
    })
  }
  return keys
}
```

> 朝向用切线 `lookAt` 算（复用相机已有 `targetMode` 体系时，bake 关键帧里 rotation 已是最终朝向，播放时 `cameraAtFrame` 直接插值，无需运行时 lookAt）。

## 4. 视口曲线编辑（Viewport.jsx 新增 `<PathEditor>`，仅 path 模式挂载）

复用现有 `frameloop="demand"` + `invalidate()` 范式（Viewport.jsx 按符号 `frameloop`/`invalidate` 定位），性能零新增负担。

### 4.1 划线（体感 = PS 里用画笔拖一条线）
- **进工具 → 光标变画笔/十字**（参考 PS 画笔激活态），提示"按住拖动画一条运镜路径"。
- 监听地面 `onPointerDown/Move/Up`（参考 models.jsx 表面拖拽的 pointer capture 套路，按符号 `onSurfacePointerDown` 定位）。
- **按住拖动**：鼠标在屏幕上的轨迹实时投到 y=0 平面，连成一条空间曲线——跟 PS 画笔拖出笔触一样实时跟随光标。`pointermove` 按"画点密度"做最小间距去重（疏=阈值大、密=阈值小）收集控制点。
- 每条新点 → `invalidate()` 实时重绘曲线（`<Line>` 来自 drei，颜色 X 轴色 `#d7675b`）。
- **松手定型**：曲线固定，并自动带上**一串控制点**（= 你骨骼上的关节点），用户随后可拖/删/补。
- `pointerup` → 调 `bakePathToKeyframes` **自动生成关键帧**（替换 `sourceKeyframeFrames`）→ 写入 `keyframes`（见 §5），运镜立即生效、无需手动确认。

> 划线这一步的体感完全对标 PS 画笔：按住拖、实时出线、松手留线+自动锚点。唯一区别是线落在 3D 地面而非 2D 画布。

### 4.2 控制点编辑（与骨骼关节点同一范式，复用 models.jsx）

**控制点 = 摄像机这条"骨骼"的关节点**，交互完全照搬现有骨骼：
- **控制点小球** = 骨骼关节球（models.jsx `MixamoJointMarker` 的 `onPointerDown/Move/Up` + `setPointerCapture` 套路）。同样的 hover/选中视觉、同样的拖拽时 `invalidate()` 实时重绘（models.jsx 按符号 `onBeginDrag`/`invalidate` 定位）。
- **拖点** = 拖关节：射线投 xz 平面改 `point.position`（可离地做升降）。拖完改 `cameraPath.points`，松手即**自动重新生成关键帧**、运镜实时更新（替换 `sourceKeyframeFrames`）。
- **双击线段补点** = 骨骼里没有，但用透明 `TubeGeometry` 命中管 `onDoubleClick` 在弧长处 `splice` 插入控制点（参考 nomi `TrajectoryHitTube`），补点后自动生成。
- **右键控制点** = 弹上下文菜单（两项）。删除点：若 `points.length > 2` 才允许删（保底 2 点），删后自动生成。删除整条：清 `cameraPath` + 删 `sourceKeyframeFrames` 对应的关键帧。

> 和骨骼的唯一差异：骨骼拖完改的是"对象 transform"，曲线拖完改的是"cameraPath.points"；但两者最终都通过"生成/更新关键帧"落进同一套 `keyframes[]` 系统。所以控制点编辑直接复用 models.jsx 的拖拽骨架，不另造。

### 4.3 显示控制
- `<PathEditor>` 仅在 `editMode==='path'` 时由 `MainViewport` 挂载；其他工具 `return null` → 曲线不渲染、零开销。
- **控制点 = 曲线这条「摄像机骨骼」的关节点 → UI 直接复用骨骼关节标记 `MixamoJointMarker` 同款视觉**（models.jsx:90-118，金色系半透明悬浮球），不要另造颜色：
  - 默认：金色 `#bf9948`、`opacity 0.28`、`sphereGeometry [0.022, 12, 8]`、`meshBasicMaterial + depthTest={false}`、`scale 0.72`。
  - hover：略放大并提高透明度（沿用骨骼 hover 反馈，不抢眼）。
  - 选中：金色提亮 `#ffd469`、`opacity 0.98`、`scale 1.25`。
  - 与相机选中黄 `#eabf62` 同属金色系，但关节球是细小圆点、形态与相机模型差异大，不会误混——用户的心智是"这些点=骨骼关节点"。若实际区分度不足，备选方案用骨骼 IK 手柄的青色 `#55bca9`。
- 曲线本体 `<Line>` 仍用轴色 `#d7675b`（§0.8）强调"这是一条路径"，与金色关节球并存，分别承担"路径"与"关节点"两层视觉语言。

## 5. 生成/写回关键帧（对齐 addKeyframe 范式，App.jsx）

> ⚠️ 三个历史坑，下一个 AI 必看：
> 1. **focalLength 来源**：bake 直接取当前 `camera.focalLength`。本工程只有这一个 `camera` state 作为当前镜头主相机的唯一真源（`CAMERA_ID` 只是选中标记），path 模式不挪 `camera`，所以无需任何额外"快照"步骤。
> 2. **history 走现有「防抖自动追踪」，勿手动 recordChange**：本工程历史由 useEffect 监听 `currentProject`（其依赖已含 `shots`）+ 防抖后自动 `recordChange`（App.jsx 按符号定位，`HISTORY_DEBOUNCE_MS`）。只要让 `cameraPath` 作为 shot 字段经 `setShots` 更新 → `currentProject` 重组 → 自动入栈。**没有**手动 `recordHistoryChange(prev, cur)` 这类 API。连续拖拽会被防抖天然合并成一条撤销记录（与现有对象拖拽一致，是期望行为）。撤销/恢复走 `normalizeShot` 对 `cameraPath` 的归一化即可。
> 3. **sourceKeyframeFrames 首次为 `[]`**：首次生成时无可删旧帧，直接并入；重新生成时才先删旧 frame 再并入。

```js
// 在 App.jsx 中，bake 完成（首次或重新生成）后：
const baked = bakePathToKeyframes(cameraPath, startFrame, endFrame, keyframeCount, camera.focalLength)
// cameraPath.points 的修改必须经 setShots 写回 shot，使 currentProject 重组 → 历史防抖自动入栈
setShots(list => list.map(shot => shot.id === activeShotId ? { ...shot, cameraPath: { ...shot.cameraPath, sourceKeyframeFrames: baked.map(k => k.frame) } } : shot))
// keyframes 与 cameraPath 分开 set 即可，两条路都会让 currentProject 变化、由现有机制自动追踪，勿手动 recordChange
setKeyframes(list => {
  const oldFrames = cameraPath.sourceKeyframeFrames || []
  const withoutOld = oldFrames.length ? list.filter(k => !oldFrames.includes(k.frame)) : list
  return [...withoutOld, ...baked].sort((a, b) => a.frame - b.frame)
})
```

- Timeline（App.jsx:1195+）的 `keyframes` prop 已接收，bake 出的关键帧**自动出现在摄像机轨道**，拖拽改快慢（`onMoveKeyframe`/`moveKeyframe`）零改动即可用。
- 删除整条曲线：清 `cameraPath=null` + 删 `sourceKeyframeFrames` 对应的关键帧（经 `setShots` 与 `setKeyframes`，自动入栈）。
- 删除单点：`points.length>2` 才允许，改 `cameraPath.points` 后自动重新生成关键帧（经 `setShots` 自动入栈）。

## 6. 性能要点（用户重点强调）

1. **`frameloop="demand"`**：静止零渲染。画线/拖点全程 `invalidate()` 驱动，与现有骨骼拖拽同套路，无连续渲染。
2. **曲线只在 path 模式挂载**：其他工具不渲染 `<PathEditor>`，零常驻开销。
3. **bake 一次性**：松手/重新生成才跑一次 `bakePathToKeyframes`（生成 N 个关键帧，微秒级），播放/导出期**不调用任何曲线函数**——纯走现有 `cameraAtFrame` 插值。
4. **控制点/曲线几何固定**：`<Line>`/`getSpacedPoints(64)` 固定 64 段，顶点数不随控制点增长；`CatmullRomCurve3` 构建成本线性、微秒级。
5. **不引入运行时注册表/第二条渲染路径**：完全复用现有 `PreviewCameraController` + `cameraAtFrame`，导出/预览零分支。

### 6.1 已知限制（P0 不解决，但必须让执行者知道，不能假装"lookAt 就完事"）

- **欧拉甩头（R2）**：bake 用 `lookAt` 算关键帧 `rotation`（欧拉），但播放时 `cameraAtFrame`（project.js:469）对 rotation 用 `lerpAngle` 逐分量线性插值欧拉角。**当曲线跨越竖直方向（pitch ≈ ±90°，如从上看俯冲向下）时，相邻关键帧欧拉插值会跨越万向锁，镜头突然翻转甩头**。这是数学上确定的，不是偶发。P0 接受此限制（多数运镜不竖直），但：① 不要向用户宣称"绝对不甩头"；② P2 应升级为四元数 slerp（bake 存四元数，`cameraAtFrame` 用 slerp 替代 lerpAngle）。
- **改曲线即改运镜（自动生成）**：拖点/改参/删补点松手都会自动重新生成关键帧，这是用户心智（曲线=镜头参数），无需提示。唯一注意：自动生成会覆盖自己这一批 `sourceKeyframeFrames` 的帧，若用户在 Timeline 手调过这些帧的时间点会被覆盖（P2 解决手调保留，见 §8）。
- **一个镜头一条曲线**：曲线覆盖该镜头自身的时间范围，不做段间过渡、无多曲线协同（对应"一条曲线 = 一个镜头的运动"心智，非缺陷）。

## 9. 用户心智 / 易用性审计（产品视角补充）

### 9.1 心智模型：一条贯穿始终的隐喻（P0 必做）

让"点击编辑"和"画画"都服务同一句用户能在脑子里复述的话：

> **"我在地面上画一条线，等于给这段视频铺运镜关键帧；画完后我可以像捏骨骼关节一样去捏这条线的点。"**

- **曲线 = 路径，控制点 = 关节点** 的视觉分工已被 §4.3 落实（线用轴色、点用骨骼金色关节球）——这是整个功能最关键的"一看就懂"设计，务必死守。
- **补齐你强调的心智**：**一条曲线 = 一个镜头 = 摄像机这一行的运动（镜头参数）**。就像"一个物体 = 一条对象轨道 = 一套对象关键帧"一样，本功能里一个镜头只有**一条**摄像机曲线、对应它自己的 `keyframes` 行，**不存在第二条曲线去覆盖**。所以"两条曲线互占、互相覆盖"是伪命题——什么去重、冲突提示都不需要。

### 9.2 菜单三参数是必要的，保三个，全平铺（不折叠）

这三项都真实作用于结果，用户（你自己）需要直观可见，不做"高级"折叠、不做预提示：
- **时间范围**：决定关键帧铺在哪段帧（默认当期镜头 0→15s）。
- **画点密度**：决定这条线有多"贴"你手画的轮廓（见下方"画点密度 ≠ 关键帧数量"）。
- **关键帧数量**：决定把曲线切成多少个关键帧（运镜精度，默认 20）。

**画点密度 ≠ 关键帧数量（回答你在问的"它是不是跟线是两码事"）：**
- 可见的那条线（`CatmullRomCurve3`）是**穿过所有控制点的平滑曲线**，控制点就是它的"骨骼把手"，线完全由这些点决定——所以**点和线不是两码事**。
- 点越多，线越能保留你手画的细节（能跟得住急弯/抖动）；点越少，线越"顺滑平均"。所以**画点密度直接决定线条精细度**，是真实参数，必须保留。
- 但它们和关键帧数量是**两个独立维度**：密度管"线的空间形状"，关键帧数量管"把线采成几个点去播放（时间分辨率）"。控制点 ≠ bake 出的关键帧。

**交互顺序（解决你的疑虑：到底先选还是先画）：**
- 让**密度默认足够密**（画的时候高保真记录，别丢细节），「开始绘制」成为唯一主动作。**先画 → 自动生成关键帧 → 之后你想再调再改这三个参数重新生成**。这样既不用画之前纠结密度，又保证手画细节不丢；密度是画后可调的"精细度"，不是画前不可逆的承诺。

### 9.4 工具发现性（P1 建议）

- 「编辑曲线」作为工具栏一个按钮即可被发现；工具激活后光标变画笔/十字，落在绘制状态自然感知（不做多余提示）。

### 9.5 撤销体验（P1 建议）

- 依赖现有防抖自动追踪后，一次长拖 = 一条撤销记录，与对象拖拽一致——符合"Ctrl+Z 撤销这一步操作"的用户预期，**不必额外拆分**。
- 明确"一条曲线 = 这个镜头的摄像机轨道"的边界：删除曲线应连 `sourceKeyframeFrames` 对应的关键帧一起消失，且撤销一次即可整体还原。

### 9.7 控制点的密度原则

- 因为画点密度决定手画细节的保留程度，**默认往「密」取，先高保真**（呼应 §9.3 先画再调）；画完嫌点太多/线太碎，再用密度调低重新生成。控制点是否密集只影响编辑手感与观感，与关键帧数量无关，无需为"少而精"刻意压缩。
