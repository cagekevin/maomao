> 本文档记录「把 `tests/unit/` 纳入类型检查 + 渐进消化存量类型错误」这条线的**全部已确认决策、当前状态、拆解步骤与踩坑记录**，供后续接手（含新 AI）无缝续作。读完全文应能直接开始 M4。

## 1. 背景与目标

### 为什么会做这件事
`src/` 业务源码已全部 TS 化（`TS-migration-handoff-2026-08-31.md`）。但 `tests/unit/` 的测试此前是 `.js/.jsx`，是**类型黑盒**——不报错、但也不被检查。

我们先把测试**迁移成 `.ts/.tsx`**（提交 `fe13000`），再让它们**纳入 tsc 类型检查**，让测试也吃上类型红利。

### 核心目标（已确认）
- **目标 B**（不是全清 1039 个错）：**机制先立住 + 按优先级渐进消化**。
- 即：类型检查成为**持续约束**（新增测试走类型检查），存量错误**按 ROI 从高到低渐进消除**，不追求一次全清。
- **不退回改 TS 前**：测试已迁移成 `.ts/.tsx` 并提交，退回 `.js` 是逃避类型检查，不是"改正确"。

## 5. 关键陷阱（State 3，已确认）——下一步必须避开

1. **M3 收口会连锁改 src 业务侧**：`ToolDef.execute` 从 `unknown` 收窄成 `ToolResult`，所有用 `ToolDef` 的 src 代码可能报错。**收口前必须先量化会波及多少 src**，确保不把已绿的 `src` type-check 弄红（这比测试错更严重的回归）。
2. **M1 数据必须可靠且不污染工作区**：之前用"临时去全部 nocheck 跑 tsc"的方式，**弄丢过 172 个文件的 @ts-nocheck**（`status` 批量改文件恢复失败）。M1 必须用**不污染工作区**的只读方式。
3. **区分测试错 vs src 连带错**：跑 `tsc -p tests/tsconfig.json` 时 src 被连带检查，`import.meta.env` 等 src 错会混进来。M1 必须分开，否则 M2 分类失真。
4. **工具 M5 别再反客为主**：修 `status` 的 bug 已经绕了很久。M3（业务收口）**完全不需要脚本**。脚本是辅助，不阻塞主线。

## 6. 下一步执行方向（State 4 待最终确认，倾向如下）

按陷阱 1/2/3，**必须先做 M1（可靠、只读、区分测试/src 的错误基座）**，再谈 M3 收口。

候选 M1 实现方式（优先只读，不污染工作区）：
- **方案 A（推荐）**：用独立临时 tsconfig 对 `tests/unit` 做检查，但**不临时改文件**——利用"基线所有文件带 @ts-nocheck"的事实，改用一个**不含 tests 的临时检查**或**逐个文件单独统计**。
- 方案 B：接受"临时去 nocheck"，但必须**逐个文件处理 + 每文件 finally 恢复**（增量恢复），不批量。

> ⚠️ 已知 `ts-tests.mjs` 的 `status` 用"批量去掉全部文件 nocheck → tsc → 恢复"，**恢复不可靠**（实测弄丢 172 个文件）。**不要用 `status` 做 M1**，改用 `check`（单文件，可靠）或新的只读方案。

## 7. 踩坑记录（防止重犯）

1. **Windows 调 `npx` 必须 `spawnSync('npx', [...], { shell: true })`**，否则 npx.cmd 不执行。
2. **`check` 必须用 `try/finally` 恢复原文件**（去掉 @ts-nocheck → tsc → 恢复）。
3. **脚本写文件必须显式 UTF-8**（node `readFileSync`/`writeFileSync`），禁 shell 文本替换（会 GBK 乱码）。
4. **`@vitest-environment jsdom` 注解不能被破坏**——加/删 @ts-nocheck 都要避开它。
5. **`status` 的"批量改文件"设计在中断时不可靠**，曾有文件丢失 @ts-nocheck。生产工具应避免"临时改工作区"。
6. `tsc` 输出路径是**相对路径正斜杠**，`fileStats` 的 key 须用 `toLowerCase()` 对齐（盘符/大小写）。
7. **M3 收口别用判别联合**：`ToolResult` 若写成 `{ok:true;data} | {ok:false;error}` 判别联合，`strict:false` 项目里直接访问 `.data/.error` 的既有 src 会全部报错（useAgentChat 十几处）。**用宽松对象 `{ok:boolean; data?:any; error?:unknown}`** 才是信封语义，且不弄红 src。
8. **`vi.mock` 工厂里 `execute` 参数序与 `ToolDef` 签名相反是 latent 隐患**：`ToolDef.execute:(ctx,args)` vs 实际 `execute(args,ctx)`。本次收口返回类型时被迫 `args as Record<string,unknown>`。后续若要根治需统一参数序（风险高，先不动）。
9. **fetch mock 只需类型对齐**：`setup.mjs` 已把 `globalThis.fetch` 定义成共享 vi.fn，运行时就是 mock；TS 却当 `typeof fetch`。`const fetchMock = globalThis.fetch as unknown as ReturnType<typeof vi.fn>` 即可，**不要**在测试里 `vi.stubGlobal`（会静默失败）。
10. **`vi.mocked()` 是标准解法**：`vi.mock`'d 模块导入的具名函数，直接用 mock 方法会 TS2339，包 `vi.mocked(fn)` 即可（beforeEach 里的 mockReset 也适用）。
11. **canvas/event 等 DOM mock 用 `as unknown as X` 收尾**：`getContext` 返回/赋值、`fakeDataTransfer()`、事件对象、crypto stub，都因缺 DOM 类型字段报 TS2740/TS2739/TS2322，cast 成对应类型即可（测试 mock 本就只实现被测用到的字段）。
