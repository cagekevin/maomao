## 1. 需求语义

用户原话：每隔一段时间自动同步到云端；**云端比本地新 → 先弹警告等用户确认**；**每次查到和云端一样 → 不同步**。

经澄清，确认以下决策；其中 q0「无冲突才推」与 q1「云端更新弹三选一」曾存在语义张力，已按**行业通用最优解**融合为确定的最终语义（见第 9 节收敛说明）：

| 维度 | 最终决策（行业通用） |
|---|---|
| 触发频率 | 每 **30 分钟** 一轮（默认开启，保守后台静默） |
| 正常行为 | **无冲突才静默推**：本地有改动且云端不新 → 直接推、不打扰；本地无改动或已一致 → 零流量跳过 |
| 云端更新时 | **三选一**：`下载云端` / `上传覆盖` / `稍后`（冲突绝不全自动覆盖，交给用户） |
| 双向 | **只定时推，不自动拉**；拉取仍走手动按钮（TopNav） |
| 多标签页 | **单实例调度**：同浏览器多标签只有一个标签真正轮询，避免重复推（行业标配防抖） |
| 连续拒绝 | **当日退避**：用户连续 `稍后` 达阈值 → 当天不再弹，次日重置（防骚扰） |

**确定的融合语义**（消除 q0/q1 张力）：
- 轮询到时，若本地与云端一致或本地无改动 → 静默跳过（不弹、不发起请求、不增加 rev）。
- 本地有改动且云端不新 → 静默上传（等同手动"推送"无冲突分支，无需用户介入）。
- 云端更新（比本地新）→ **绝不全自动覆盖**，弹三选一交给用户；选`稍后`则本轮跳过、计入退避。

> 该语义与 OneDrive / Dropbox / iCloud 的自动同步行为一致：**自动同步只在无冲突时悄悄发生，一旦出现版本冲突就完全交还人工决策**，不会在用户不知情时覆盖任一方数据。

## 3. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│ App 根挂载：startAutoSync()  卸载：stopAutoSync()             │
└───────────────────────────┬─────────────────────────────────┘
                              │ setTimeout 递归（30min）
                              ▼
                   ┌──────────────────────┐
                   │  autoSync.runTick()   │  模块级纯控制器，不依赖 React
                   │  (守护前置检查)        │
                   └──────────┬───────────┘
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
  Ⅰ 单实例仲裁        Ⅱ 退避闸门          Ⅲ 同步/环境守护
  (BroadcastChannel)  (cancelCount≥阈值    (running / hidden /
  仅 Leader 标签轮询    → 当日跳过)         offline / 未启用未登录)
        └─────────────────────┼─────────────────────┘
                              ▼

                              │

              ▼               ▼                ▼
```

## 4. 新增模块 `src/components/base/store/autoSync.ts`

### 4.1 形态
模块级单例控制器（对齐 `confirmStore`/`cloudSync` 的"非 React、可被异步链路调用"范式），不在 React 组件内维护 timer。

### 4.2 状态
```ts
let timer: number | null = null;       // setTimeout 句柄
let running = false;                    // 防重入：本轮是否进行中（跨标签共享，见 4.4）
let started = false;                    // 是否已 start（避免重复挂）
let cancelCount = 0;                     // 连续「稍后」次数（退避闸门，见 4.5）
let backoffUntil = 0;                    // 当日退避截止时间戳（0 = 未退避）
```

### 4.3 配置读取（来自 appSettings，见第 7 节）
- `autoSyncEnabled: boolean`（默认 **true**——行业通用默认开启 + 有冲突保护不会误覆盖，安全）
- `autoSyncIntervalMin: number`（默认 30；枚举可选 5/10/15/30/60）

### 4.4 调度循环 + 单实例仲裁（行业标配：多标签只有一个 Leader 轮询）
同浏览器开多个标签时，若每个标签各自 30min 轮询会重复推、重复弹窗。行业通用做法是用 `BroadcastChannel`（或 `localStorage` 锁）选出一个 **Leader 标签** 负责轮询，其余标签只挂不轮询。

```ts
// 单实例选举：频道名 'maomao-autosync'；Leader 持锁、心跳续租
const chan = 'BroadcastChannel' in globalThis ? new BroadcastChannel('maomao-autosync') : null;
let isLeader = true;                     // 单标签环境天然 Leader
let leaderLease = 0;                     // Leader 租约过期时间
function claimLeadership() { /* 抢锁 + 30s 心跳续租；失联则 follower 顶上 */ }

function scheduleNext() {
  if (timer != null) clearTimeout(timer);
  const mins = getSetting('autoSyncIntervalMin') || 30;
  timer = setTimeout(() => { void runTick(); }, mins * 60_000);
}
```
> 单实例只解决"多标签重复推"，**不**改变冲突弹窗语义：Leader 标签弹出的三选一仍由该标签用户响应。

### 4.5 tick 守护（顺序敏感，缺一不可）
四道闸门：单实例 → 退避 → 同步/环境守护 → 真正上传。
```ts
async function runTick() {
  try {
    if (!isLeader) return;               // Ⅰ 单实例：仅 Leader 标签轮询
    if (backoffUntil > Date.now()) return;   // Ⅱ 退避：当日已被用户拒绝饱和，跳过
    if (running) return;                 // Ⅲ-① 防重入（跨标签经 CloudSyncEngine 串行，见第10节）
    if (document.hidden) return;         // Ⅲ-② 后台标签不弹、不推
    if (!navigator.onLine) return;       // Ⅲ-③ 离线跳过
    if (!isCloudSyncReady()) return;     // Ⅲ-④ 未启用/未登录 跳过
    running = true;
    const r = await uploadConfig(
      (m) => showToast(m, { type: 'info' }),
      { onAutoConflict: autoResolveConflict },  // 三态，见第 6 节
    );
    if (r.cancelled) {                   // 用户选「稍后」→ 累计退避
      cancelCount += 1;
      if (cancelCount >= 3) {            // 阈值：连续拒绝 3 次（≈90min）→ 当日不再打扰
        backoffUntil = startOfNextDay(); // 次日 00:00 重置；或简单 = Date.now()+24h
        cancelCount = 0;
      }
    } else {
      cancelCount = 0;                   // 任一次成功/下载即清零退避计数
    }
  } catch {
    /* 静默：自动同步失败绝不应阻塞 UI */
  } finally {
    running = false;
    scheduleNext();                      // 无论成败都排下一轮
  }
}
```

> `isCloudSyncReady()`：从云同步开关 + 登录态抽一个纯函数，供 `autoSync` 与 `useCloudSync`（TopNav 手动按钮）共用，避免判定逻辑两份分叉。
> 注：现有 `uploadConfig` **本身不**判 `enabled`/登录态，该判定发生在手动按钮处（`useCloudSync().enabled` + `getSigninState()`）。自动调度器必须在调用前自己判，否则未登录时会反复弹"读取云端失败"类错误。

### 4.6 启动与生命周期
```ts
export function startAutoSync() {
  if (started) return;
  started = true;
  claimLeadership();                     // 抢 Leader 租约
  // 首轮延迟 30s，避免一启动就弹确认框
  timer = setTimeout(() => { void runTick(); }, 30_000);
}
export function stopAutoSync() {
  if (timer != null) clearTimeout(timer);
  timer = null; started = false; running = false;
  releaseLeadership();                   // 释放租约，让其它标签可接管
}
export function restartAutoSync() {  // 用户改设置时调用
  stopAutoSync(); startAutoSync();
}
```

## 5. "静默跳过/无冲突才推"如何复用

`uploadConfig` 内部已做：
- 收集本地数据 → 算 `localHash` → 读云端 → `decideUpload`。
- `decideUpload` 返回 `none`（云端不新 + 本地无改动，或首次无基线）→ 不调用 `onConfirm`，直接走打包推送；但若本地无任何改动，推送一个等同内容也无副作用（仅 rev+1）。
- 若想"完全不推无改动数据"，可在 `autoResolveConflict` 外层判断：仅当 `localDirty` 才推。建议：**本地无改动（ledger.localHash 一致）时直接 return，不发起任何网络请求**，最省流量且避免 rev 无意义自增。

> 审计点：是否在 autoSync 层额外判 `localDirty` 以零流量跳过？当前 `uploadConfig` 无改动也会 push。建议 autoSync 在调用前先读 ledger 比对 `contentFingerprint(collectLocalData())`；若无改动直接 `scheduleNext()`。这一层短路不影响手动按钮行为。

## 6. 三选一冲突处理（核心审计点）

### 6.1 现状限制
- `uploadConfig` 的 `onConfirm: UploadConfirmHandler = (copy, decision) => Promise<boolean>`，返回 `false` → 中止上传（cancelled）。仅二态。
- `confirmStore.askConfirm` 返回 `Promise<boolean>`，`resolveConfirm(ok)` 二态，UI 只有"确认/取消"两按钮。

要实现"下载云端"，需要把冲突决策从二态扩成三态，且**不能破坏手动同步链路**。

### 6.2 改造方案（最小侵入、双链路并存）

**(a) 新增三态解析类型与可选回调**（`cloudSync.ts`）：
```ts
export type ConflictResolution = 'upload' | 'download' | 'cancel';
export type AutoConflictHandler = (
  copy: ConfirmCopy, decision: UploadDecision,
) => Promise<ConflictResolution>;
```
`uploadConfig` 签名扩展为：
```ts
export async function uploadConfig(
  onProgress,
  opts: { onConfirm?: UploadConfirmHandler; onAutoConflict?: AutoConflictHandler } = {},
)
```
- 传 `onConfirm`（手动按钮）→ 行为与现在完全一致（boolean），不破坏。
- 传 `onAutoConflict`（自动调度）→ 走三态。

**(b) `uploadConfig` 冲突分支改造**：
```ts
if (decision.kind !== 'none') {
  if (opts.onAutoConflict) {
    const r = await opts.onAutoConflict(describeUploadConflict(decision), decision);
    if (r === 'cancel')    return { ok:false, count:0, cancelled:true };
    if (r === 'download')  return { ok:false, count:0, action:'download-needed' };
    // r === 'upload' → 继续下面的 push
  } else if (opts.onConfirm) {
    if (!(await opts.onConfirm(...))) return { ok:false, count:0, cancelled:true };
  }
  // 无回调 → 旧行为直接上传（无头/测试）
}
```
返回新增 `action?: 'download-needed'`，让调度器据此拉取。

**(c) 调度器分支**：
```ts
const r = await uploadConfig(..., { onAutoConflict: autoResolveConflict });
if (r.action === 'download-needed') {
  await downloadConfig((m)=>showToast(m), { onConfirm: (c)=>askConfirm(c) });
}
```
`downloadConfig` 的覆盖确认仍走现有二态 `askConfirm`（用户可再次取消），不引入第四态。

### 6.3 弹窗 UI 改造（三按钮）

在 `confirmStore` 新增**专用三态方法**，不污染现有 `askConfirm` 的 boolean 契约：
```ts
export type ChoiceKey = 'confirm' | 'download' | 'cancel';
export function askChoice(opts: ConfirmOptions & { downloadText?: string }): Promise<ChoiceKey>
```
- `ConfirmOptions` 新增可选 `downloadText`（第三按钮文案，默认"下载云端"）。
- `ConfirmContainer` 渲染时若 `request.downloadText` 存在 → 画三按钮，第三按钮调 `resolveChoice('download')`。
- 现有 `askConfirm` 完全不动，手动同步链路零改动。

### 6.4 状态机闭环（审计重点）
```
          云端更新冲突
              │
              ▼
   ┌── askChoice 三选 ──┐
   │      │      │      │
 'download' 'upload' 'cancel'
   │        │        │
   ▼        ▼        ▼
download  uploadConfig 本周期跳过
Config    (push)     (scheduleNext)
   │        │
   ▼        ▼
 写回本地  记台账
 (记台账)
```
- `download` 分支：拉取后 `downloadConfig` 内部 `writeLedger` 把云端版记为新基线 → 下一轮本地 hash 与云端一致 → 不再误报冲突（且 `cancelCount` 清零）。
- `upload` 分支：推送后 `uploadConfig` 内部 `writeLedger` 记新基线（`cancelCount` 清零）。
- `cancel` 分支（已定稿，非可选）：不动任何数据，本轮跳过并 `cancelCount += 1`；**连续 `cancel` ≥ 3 次（约 90min）→ 设 `backoffUntil = 次日 00:00`，当天不再弹、不再轮询**（对应第 4.5 节退避闸门）。任一次 `upload`/`download` 成功即把 `cancelCount` 归零。

> 退避是行业通用防骚扰做法（OneDrive/Dropbox 在用户持续忽略冲突提示后，会停止反复打扰，转由用户在方便时手动处理）。阈值为默认 3，可后续做成设置项。

## 7. 配置项（写到 `appSettings` 注册表）

在 `src/components/base/store/settingRegistry.ts` 注册两项，UI 入口放在"云同步/账号"设置段（如 `AccountsSettings` 或新建 `CloudSyncSettings`）：

| key | 类型 | 默认 | 说明 |
|---|---|---|---|
| `autoSyncEnabled` | boolean | true | 是否启用自动同步（默认开启，见第 9 节收敛） |
| `autoSyncIntervalMin` | enum | 30 | 轮询间隔（分钟）：5/10/15/30/60 |

改这两项时调用 `restartAutoSync()` 使新间隔/开关立即生效（在 `setSetting` 的订阅或设置面板 onChange 里触发）。

> 这两项属"应用设置"，本身会进 `app_settings` 被云同步——即自动同步配置也会跨设备同步（合理：在一台机器开自动同步，其他机器也开）。

## 8. 接线点

- **启动**：`App.tsx` 顶层 `useEffect`（或 `Canvas` 挂载处）调用 `startAutoSync()`；卸载 `stopAutoSync()`。App 是根组件 → 等价于应用生命周期。
- **设置变更**：`autoSyncEnabled` / `autoSyncIntervalMin` 变化 → `restartAutoSync()`。
- **不接 TopNav 手动按钮**：手动"推送/拉取"按钮逻辑保持不变，自动调度是独立旁路。

## 10. 风险、边界与失败处理

| 风险 | 缓解 |
|---|---|
| 定时器在 React 严格模式双挂载下重复 | `started` 守卫去重；`stopAutoSync` 幂等 |
| 上一轮未结束就到下一轮 | `running` 防重入 + `setTimeout` 递归 |
| 后台标签反复弹确认 | 守护② `document.hidden` 跳过 |
| 离线/未登录时反复失败弹 toast | 守护③/④ 跳过 + `finally` 静默 |
| 三选一"下载"误覆盖本地新改动 | `downloadConfig` 内部 `diffWithLocal` 已会再次列覆盖清单二次确认 |
| 自动推送把本地脏数据推上去 | 同手动：`decideUpload` 已判云端新旧，云端更新时不静默推 |
| 多标签页同时自动同步 | 各标签独立 ledger；但 `CloudSyncEngine.isSyncing` 全局串行使推送不并发（fetch 层已挡） |
| 多标签重复轮询/弹窗 | **单实例 Leader 选举**（`BroadcastChannel` 租约+心跳续租）：仅 Leader 轮询，`running` 跨标签经 `CloudSyncEngine.isSyncing` 兜底串行 |
| 连续拒绝导致每轮弹窗 | 退避闸门：连续 `稍后` ≥ 3 → `backoffUntil=次日`，当天不再弹 |
| rev 无意义自增（无改动也推） | 见第 5 节 autoSync 层短路 `localDirty` 判断（建议实现） |
