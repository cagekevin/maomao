`speed` 的语义**只活在映射层**（`sourceTime.ts` + `timelineOps`）；预览 / 导出 / 混音 / UI

#### 3.2b ★预览取帧契约（2026-09-14 裁定 · 取证见 §十 F1）

前一稿只裁了「变换**求值**共用」，**没裁「预览的帧从哪来」**——而 M1 的播放走的是
`<video>/<audio>` **元素池**（`PlaybackSink.tsx:136-146` + `currentTime` 对齐），导出走 mediabunny
`VideoSample`（`composite.ts:108`）。这是 M-B 母体真正的另一半，不裁就等于「求值一条、取帧两条」：

**裁定：预览 = canvas 绘制，帧源 = 走带元素池（同一个 `<video>` 元素）。**

| 判据 | 说明 |
| --- | --- |
| **同一时间基** | 同一元素既出声又出画面 ⇒ 画面与声音天然同步，不需要两套 seek 对齐 |
| **可丢帧有机制** | `ctx.drawImage(videoEl, …)` 是**同步**的，rAF 驱动天然「画不完下一帧覆盖」——不需要 `await sink.getSample()` 的逐帧 await（原方案「实时、可丢帧」**没有任何机制落点**） |
| **文字必须走 canvas** | 预览用 DOM/CSS 渲染文字、导出用 canvas ⇒ 排版必然两份，**M-B 母体原样复活**。故预览与导出共用 `core/textLayout` 的布局盒 |
| **单例硬契约** | **元素池单例、宿主唯一**：工作台打开时**不得**出现第二份 `PlaybackSink`（否则双份解码 + **双份出声**） |
| **度量改口径** | 不再宣称「渲染路径 1 条」，改为「**求值 1 条 + 取帧适配器 2 个 + 落点 1 张画布**」 |
| **不许绕过导出唯一入口** | `refs` 实证：`export/composite.ts` **fan-in = 1（仅 `export/pipeline.ts` + 测试）** ⇒ 它是「导出唯一入口」的**内部实现**。监视器若直接 import 它，就把唯一入口变成 2 个；而 `dockContract` 的「禁直调导出实现」守卫**只扫 `dock/`**，管不到 `panels/workbench/`（清单必漏母体）。故预览**不走** `renderFrameAt` —— 它只服务导出 + 静帧校对 |

⇒ 取帧有两个**适配器**（`HTMLVideoElement` / `VideoSample`），而**求值只有一条**（`core/transformEval`）。
落地与守卫见 §四 R3 + 债 `TD-22-13`。

### 8.6 ★修正：`mixClip` 的改法不是最优（收口时暴露的真 bug）

**第一版改法**（等价改写）：
```ts
const timeInClip = timelineTimeAt(wrapped.timestamp, clip) - clip.timelineStart;  // 加回来
const startSample = Math.round((clip.timelineStart + timeInClip) * MIX_SAMPLE_RATE); // 又减掉
```
**两行互相抵消** = 纯噪音。**更严重的是它在变速下会算错**：
- `duration`（= `sourceEnd - sourceStart`）是**源侧**的量；
- `timestamp - sourceStart` 也是**源侧**的量；
- 但输出缓冲的样本位是**时间轴侧**的量。M1 两侧同刻度故无差别；**变速后差一个倍率** ⇒ 音频写错位置。

**修正**：整段走时间轴侧 —— `timelineTimeAt(ts)` 直接落样本位；越界判定也改为比较
`timelineTime >= clip.timelineStart + duration`（同一侧的量，变速后仍成立）。

> **教训（记入方法）**：收口的目标不是「让两处代码长得一样」，而是**「问这个消费方真正需要哪条映射」**。
> 我把「等价改写」当成了目标，于是写出 `- x + x` 这种自己被自己抵消、却在变速下失效的代码。
> 这正是 Step 3 说的「搬新家 ≠ 消灭复杂度」的一个变体：**形式归一了，语义没归一**。

| 17 | `export/composite.ts:140` | `track.kind !== 'video'` → skip | **需确认**：文字轨要渲染（它是画面层） | **高**：漏则文字不入成片 |

**结论（3 条高风险的共性）**：

> **#4 / #16 / #5 / #6 / #12 / #17 —— 全部是「二分判据」在第三种 kind 出现时的失效。**
> 它们现在写的是 `kind === 'audio' ? A : B` 或 `kind === 'video'`，
> **加第三种时，这些二分不会报错，只会静默走错分支**。

**⇒ 提出一条前置建议（P-3 产出，待你定）**：

**把二分判据改成「显式穷举」形态** ——
```ts
// 现在（加第三种静默失效）
return clipKind === 'audio' ? 'audio' : 'video';

// 改为（加第三种时 TS 报错，强制处理）
const ROUTE: Record<ClipKind, TrackKind> = { video: 'video', audio: 'audio', image: 'video' };
return ROUTE[clipKind];
```
- **收益**：`ClipKind` / `TrackKind` 加值那天，**编译器点名所有需要处理的点**（不再是静默错分支）；
- **代价**：`Record` 比三元略长；
- **判据**：与 §八 P-1 的「按层白名单」同款手法 —— **把「靠人记得」换成「靠类型兜」**。

### P-4 · `dockContract` 守卫改「按形态」的方案验证 ✅ 已完成
