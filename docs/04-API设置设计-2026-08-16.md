# 04 专题：API 设置设计（多供应商 · 不绑定单一 API）

> 日期：2026-08-16
> 本文讲前端「第三方 API 配置」这一功能的**现状设计**（已实现，非计划）。核心定位：**不绑定任何一个网站/API，后续可扩展接入更多供应商**。字段名、分层、扩展路径都按这个方向设计，并有代码注释佐证。

---

## 一、设计理念（为什么这样设计）

### 1.1 核心原则：Provider 是声明式对象，天然支持 N 个 API

- 前端设置面板管的是**一份「供应商数组」**，每个供应商是一个**纯声明式对象**：`{ id, name, base_url, protocol, ... }`。
- 一个数组装多个供应商（Lovart / OpenAI 兼容 / 未来任意站），**不是写死某一个 API**。
- 画布发请求时按「选中的 provider」分派，**换 API 只加一个 provider 对象**，前端逻辑不用为每个 API 写分支。

### 1.2 为什么用「正交枚举」而不是每个 API 一套字段

- 不同 API 的差异可以抽象成**几个正交维度**（详见 §三），而不是每个 API 造一套专有字段。
- 好处：新增 API 时复用同一套字段结构，只是枚举值不同 → **不用加翻译层、不增加复杂度**（这正是 `docs/api-接入/02-provider字段契约.md` 强调的"字段名永远照本表，绝不发明新名"）。

### 1.3 红线：UI 开放的协议 = 后端已实现的协议

- 前端设置面板**只开放后端真正能接通的协议**；未实现的一律不开放或标「即将支持」，**绝不开放让用户配了白配**（误导）。
- 这就是"不绑定单一 API"的正确落地：**每一步扩展都是「后端实现一个协议 → 前端开放该协议」配套进行**。

## 二、数据模型（Provider 对象）

### 2.1 前端 provider 对象字段（`providerStore.js` emptyProvider）

| 字段 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `id` | str | 自产 `p_xxx` | 唯一标识，路由键 |
| `name` | str | `新供应商` | 展示名 |
| `base_url` | str | `''` | API 基地址 |
| `protocol` | str | `openai` | 协议身份（怎么说话，§3.1） |
| `image_request_mode` | str | `openai` | 图片请求形态（怎么读结果，§3.2） |
| `image_mode` | str | `sync` | 生图同步/异步（怎么等结果，§3.3） |
| `enabled` | bool | true | 启用开关 |
| `isPrimary` | bool | false | 主供应商（全表最多 1 个 true） |
| `readonly` | bool | false | 内置 provider 只锁核心结构字段 |
| `image_models` | arr | [] | 生图模型清单 |
| `chat_models` | arr | [] | 聊天模型清单 |
| `video_models` | arr | [] | 视频模型清单 |
| `model_names` | obj | {} | 单模型显示名覆盖 |

> **模型项**（`ModelSection.jsx`）：每个模型 `{ id, label }`——`id` 必填（真正传给上游的值），`label` 可选（显示名，留空回退 id）。

### 2.2 Key 安全设计（不落明文）

- **key 只进后端 env，不回前端明文**（`providerStore.js` 头注释）：列表接口只返回 `has_key` / `key_preview`（掩码）。
- 编辑新 key：存 UI 态 `_apiKey`；清除：`_clearKey`；保存时：`_apiKey` 非空 → 传 `api_key`，`_clearKey` → 传 `clear_key`，否则不传（沿用旧值）。
- 这就是"多开账号"与"API key"分离的原因：key 是供应商凭据（env），cookie 是账号登录态（另一套，见 §五）。

### 2.3 配置持久化：双源文件（providers.json + api.config.json）

API 配置存在 **localTool 的两个文件**，职责不同、互为补充：

| 文件 | 位置 | 职责 | 谁读写 |
|---|---|---|---|
| `providers.json` | localTool 数据目录（`getDataDir()`） | **主数据源**，运行时读写的唯一真相 | `GET/PUT /api/providers`（`loadProviders()` / `saveProviders()`） |
| `api.config.json` | 项目根（`MAOMAO_CONFIG_FILE` 可覆盖） | **带注释骨架**，供 AI/人维护，含 `_meta` / `_comment` | 前端保存后 `PUT /api/config/base` 回写合并 |

**双源的原因**（代码注释 `providers.ts` line 515-518）：前端设置页改完 → `providers.json` 更新了、但 `api.config.json` 不变 → 双源漂移。所以前端 `save()` 成功后调 `PUT /api/config/base`，把脱敏视图**合并回写** `api.config.json`。

**回写时保留注释**（`syncConfigJson`，providers.ts line 521-556）：
- 保留顶层 `_meta` 和每个 provider 的 `_comment`（AI/人维护的注释骨架），**只更新字段，绝不抹掉注释**。
- 这是"配置给 AI/人看 + 前端可改"两全的设计。

**现状实证**：`api.config.json` 里已配 **2 个 provider**（`lovart` = apimart/async + `modelscope` 魔搭 = openai/sync），说明多 provider 已真实启用，不是只有单上游。

> **模型项在 config 里多两个字段**：`api.config.json` 的模型是 `{ id, label, streaming, promptOnly }`（localTool `ProviderModel`），比前端 UI 的 `{ id, label }` 多了 `streaming`（是否流式）/ `promptOnly`（是否仅提示词），前端保存不覆盖这两个字段。

## 三、三层抽象（正交维度）

这是「不绑定单一 API」的**核心抽象**：把 API 差异拆成三个互相独立的维度，任意组合。

### 3.1 protocol（协议身份）—— 怎么说话

接口风格（`ProviderForm.jsx` 文件头契约表 + 契约文档）。现 UI 已开放 2 种：
- `apimart`（Lovart 网关 / 异步任务 task_id 轮询形态）
- `openai`（OpenAI 兼容直连）

> **代码注释里的完整枚举（未来）**：`localTool/src/routes/providers.ts` line 24-25 明确写了"扩展点：将来可加 `gemini / volcengine / runninghub / CLI`，前端协议下拉与 test 探测随之扩展"。契约文档 `02-provider字段契约.md` §五给出 8 选 1 完整清单（openai/apimart/gemini/gemini-cli/volcengine/runninghub/jimeng/codex）。**这些是未来方向，本期前端只开放已实现的 2 种。**

### 3.2 image_request_mode（图片请求形态）—— 怎么读结果

同一 `openai` 协议下的**请求体形态**（4 选 1，`ProviderForm.jsx` 的 `REQUEST_MODES`）：
- `openai` / `openai-json` / `openai-video-proxy` / `openai-responses`

不同平台支持的请求格式不同（如有的站会被自动嗅探成 `openai-json`）。后端 `generate_ai_image` 按它决定发什么 body。**契约必填字段，UI 禁止删选项**（删了配对应平台时后端无法正确发请求）。

### 3.3 image_mode（同步/异步）—— 怎么等结果

生图请求方式（**本项目扩展字段，官方没有**，localTool 透传）：
- `sync`（同步）：URL 带 `?wait=1`，SSE 等待结果返回
- `async`（异步）：提交返回 task_id，前端轮询 `/v1/tasks/{id}`

前端 `imageApi.js` 按它决定走 SSE 等待还是 task_id 轮询。**注意：异步模式能配合任务恢复轮询（见 `03-任务ID全链路` §四），是"刷新后任务不断"的基础。**

### 3.4 设置驱动请求方式（前端怎么发，全看设置）

**核心：前端生图/请求的方式，完全由 API 设置里的 `image_mode` 决定，不写死。**

```
API 设置 image_mode = async  →  前端 generateAsync（提交拿 task_id → 轮询结果）
API 设置 image_mode = sync   →  前端 generateSync（URL 带 ?wait=1 → SSE 等结果）
```

- 实现：`imageApi.js` 的 `generateImage()` 读 `provider.image_mode`，`mode === 'async' ? generateAsync : generateSync`。`videoApi.js` 视频强制 async。
- 好处：**同一个前端逻辑，不写死协议，配不同 API 只需改设置**；前端不用为每个站写分支。
- **这也是"不绑定单一 API"的直接体现**：发请求的方式跟着设置走，而非跟着代码写死。

### 3.5 预留字段：为未来打基础

- 设置面板**已经留了多个字段**，当前某个平台/模式可能"没激活"，但字段在——这是**打地基**，将来接新平台直接复用，不用加翻译层：
  - `image_request_mode` 的 4 种形态（`openai` / `openai-json` / `openai-video-proxy` / `openai-responses`）：现在主要用 `openai`，**「兼容 OpenAI / OpenAI JS」这些是为后续平台预留**。
  - `protocol` 枚举已定义 8 种（当前开放 2 种）。
  - localTool `ProviderModel` 的 `streaming` / `promptOnly`：预留给流式/纯提示词模型。
- **铁律**（`ProviderForm.jsx` 文件头）：看似"当前没用到"的字段都只是某平台/模式暂时没激活，**不代表后端不需要**；一旦删掉，配别的平台时后端就不知道用哪种方式发请求。**预留字段禁止删。**

> 三层的正交关系：`protocol` 决定"用哪套协议说话"，`image_request_mode` 决定"openai 协议下怎么发图片请求"，`image_mode` 决定"同步等还是异步轮询"。三者独立组合，覆盖不同 API 的差异。

## 四、多 Provider 工作机制（节点式选模型）

### 4.1 节点式：每个节点可跨 provider 选模型

- 模型下拉聚合**所有 provider** 的模型（`providerModels.js` 头注释：现在有多个 API，希望节点式——两个节点可分别选不同 provider 的不同模型）。
- 模型 value 用 `{providerId}::{modelId}`（双冒号，兼容 modelId 含 `/` 如 `Qwen/Qwen3-14B`）。
- 生成时用 `resolveProviderModel` 解析回 `{ provider, modelId }`，再经 `/api/proxy` 转发到该 provider。

### 4.2 主供应商（primary）

- 全表最多 1 个 `isPrimary`。没有 provider 时可回退到主供应商 / 第一个。
- 保存后把主供应商写入 localTool KV `active_api_endpoint`（对齐官方 `active_api_endpoint`，供跨端读取当前生效 endpoint）。

### 4.3 测试连接 & 拉取模型

- **测试连接**（`test`）：发 `POST /api/providers/test-connection`，后端探测连通性 + **嗅探协议**（auto 时先探 openai `/v1/models`，失败再探 apimart `/v1/gateway/health`）。
- **拉取模型**（`fetchModels`）：`POST /api/providers/:id/fetch-models`，按关键词分类成 image/chat/video 三栏回填。

## 五、与「多开账号」的关系（accountsStore）

- **API key**（供应商凭据）→ 走 provider 设置，存 env。
- **多开账号**（登录态 cookie，如即梦/字节系）→ 走账号管理，存 `localStorage`（`yimao_accounts`）。
- 两套正交：API 设置管"怎么连上游 API"，账号管理管"某个网站的登录态"。Cookie 白名单（`LOGIN_COOKIE_WHITELIST`）针对特定站，**与 provider 无耦合**。

## 六、可扩展路径（接入新 API 要动哪几处）

按"后端实现一个协议 → 前端开放该协议"配套推进。以新增一个 `gemini` 协议为例：

1. **后端**：实现 `gemini` client（发请求/读结果）→ 在协议枚举 `SUPPORTED_PROVIDER_PROTOCOLS` 注册 → `resolveProviderTarget` 加对应 url 拼接/鉴权。
2. **前端**：`ProviderForm.jsx` 的 `PROTOCOLS` 下拉加 `gemini` 选项（**只加后端已实现的**）→ `test` 探测逻辑可能需扩展（对应 gemini 的 `/v1beta` 探测）。
3. **模型**：拉取模型分类逻辑覆盖 gemini 的返回格式；节点下拉自然出现该 provider 的模型（`buildAllModels` 已按 provider 聚合）。
4. **验证**：`npm run build` + `test:smoke` + `test:regression`；localTool 改动过则 `cd localTool && npm test`。

**铁律**：
- 字段名永远照 `02-provider字段契约.md`，绝不发明新名。
- key 永远只进 env，列表脱敏。
- primary 唯一化；id 不重复。
- **协议锁死**在 normalize 里强制（用户填错也会被纠正，如按 id/域名自动锁 protocol + request_mode）。

| 维度 | 已实现（本期） | 未来方向（未做） |

## 九、打基础清单（为接入更多 API 铺路）

按「现在就能做」和「等条件成熟再做」分类。**目的**：后续 AI 知道哪些地基已打、哪些还欠着，避免重复或误判。

### 9.1 已打好（本会话完成）

| # | 基础 | 落点 | 说明 |
|---|---|---|---|
| ① | **ProviderForm 按协议动态显隐字段** | `ProviderForm.jsx`（`HTTP_PROTOCOLS`/`CLI_PROTOCOLS`/`isHttpProtocol`） | 表单能力已具备：HTTP 类显示 base_url/key/请求形态，CLI 类自动隐藏。将来加 codex/jimeng/gemini-cli 只需把它们加入 `CLI_PROTOCOLS`。当前 apimart/openai 都是 HTTP，行为不变。 |
| ② | **测试连接探测按协议表驱动（可插拔）** | localTool `providers.ts`（`PROBE_PATHS`/`PROBE_ORDER`） | 探测逻辑从「堆 if」改成「表驱动」，将来加 gemini(/v1beta)/volcengine(/api/v3)/runninghub 只需补一条映射。纯重构、零行为变化（测试 81/81 通过）。 |

### 9.2 等条件成熟再做（先记着，别急）

| # | 基础 | 为什么现在不做 | 触发条件 |
|---|---|---|---|
| ③ | **协议可用性从后端拉 `supported_protocols`** | 需后端先明确「已实现哪些协议」，前端据此渲染下拉并禁用未实现的；目前只有 2 种且前端写死够用 | 后端实现第 3 个协议时配套 |
| ④ | **`streaming` 字段前端消费** | 前端 `chatApi` 是 `stream:false` 写死；config 里模型已有 `streaming`/`promptOnly` 但未读 | 确认网关 chat 流式链路支持后 |
| ⑤ | **`image_request_mode` 各形态前端请求体** | 4 种枚举已定义，但前端发送主要走 `openai`；`openai-json`/`responses`/`video-proxy` 需后端 `generate_ai_image` 先通 | 后端各形态分派实现后 |
| ⑥ | **协议扩展的单元测试骨架** | 只有 2 种协议，测试骨架价值低；等有第 3 个协议再建 | 接入新协议时 |

> **红线提醒**：③④⑤ 都遵循「后端实现 → 前端开放/配套」原则，前端单方面改会导致"配了接不上"。当前 UI 开放 apimart/openai 是安全边界。
