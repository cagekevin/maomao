## 〇、一句话结论

对方仓库**最值钱的是它的数据流设计，不是它的 UI**。

它的 UI 是 Tauri 桌面端一套（独立窗口 + 自绘标题栏 + i18n + fileService + IndexedDB），**整包搬过来 100% 编译不过**。
但它的四条数据流契约是**与平台无关的、已踩过坑的真理**：

1. **数据模型与渲染操作严格分离**（`types/videoEditor.ts` 纯数据 + `timelineOps.ts` 纯函数，零 React 依赖）；
2. **预览与导出共用同一条合成渲染路径**（`videoCompositor.renderFrameAt`，所见即所得，杜绝「预览对导出错」）；
3. **直通 vs 合成由 `needsCompositing(tracks)` 一个谓词决定**，且直通走关键帧对齐的无损搬运（`exportLosslessTrim`），绕开编码器；
4. **历史栈只快照轨道数组**，连续拖拽由调用方决定何时落一张（避免一次拖拽炸出几十张快照）。

本仓库要做的，是把这四条**原样继承**，只换「承载平台」：
- Tauri 独立窗口 → 本仓库 `base/editors` 同款的 **`FullscreenShell` portal 全屏层**（无 Tauri / 无独立 React 实例）；
- IndexedDB 仓储 → 本仓库 `contentStore` + `STORAGE_KEYS`（kv 后端）；
- `fileService` / `asset://` → 本仓库 `localTool /files/` 单一落盘通道；
- 窗口 `postMessage` 回传 → 直接回调（导出结果同步回写节点，无跨窗口协议）。

## 一、安置位置（先定边界，再定目录）

### 1.1 它是什么性质的东西

它是**业务域编辑器**，不是「通用地基」。`base/README.md` 红线原文：
**`base/` 是通用地基，业务域（nodes / panels / videoEditor 等）可依赖 `base/`，但 `base/` 不得反向依赖业务域**（`npm run check:arch` 拦截）。

> **约定**：本文所有 `base/...` 均指 `src/components/base/...`（如 `base/README.md` ≡ `src/components/base/README.md`、`base/editors/ImageEditor.tsx` ≡ `src/components/base/editors/ImageEditor.tsx`）。其中 `FullscreenShell` 位于 `base/panels/`（非 `base/editors/`）。

视频剪辑器作为业务域**依赖** `base/panels/FullscreenShell`、`base/core/contentStore`、`base/api/filesApi`、`base/canvas/deriveNodes` 是**合规方向**；
反之若在 `base/` 里加视频剪辑专属逻辑（合成器、时间轴纯函数等）则违规，必须落在 `src/components/videoEditor/`。

`ImageEditor` 虽在 `base/editors/`，但它被定为「内容编辑/查看器」（通用地基），且已先落地、有先例。
视频剪辑器体量远大于图片编辑器（核心 5 文件 + 纯逻辑 + 数据层 + 导出管线，约等于 `Director3DNode` 的量级），
**按性质应归入业务域，与 `src/components/nodes/` 同级**——就像 `VideoProcessNode`、`Director3DNode` 那样。

> **决策**：代码主目录落在 `src/components/videoEditor/`（业务域，归 `check:arch` 允许）；
> 挂载方式**复用** `base/panels/` 的 `FullscreenShell`（只 import 它的挂载壳，不把逻辑塞进 base/）。

## 二、数据编排（四层，自下而上）

```
┌─────────────────────────────────────────────────────────────┐
│  Layer 4  节点绑定（Editor ↔ Node）                          │
│   launch：节点 hover「剪辑」  →  export：VideoEditorExportResult │
├─────────────────────────────────────────────────────────────┤
│  Layer 3  导出管线（export/）                                │
│   needsCompositing → 直通(exportLosslessTrim/Concat) │ 合成   │
│   AbortController + 阶段事件 + 音频模式(encode/copy/pcm/none)  │
├─────────────────────────────────────────────────────────────┤
│  Layer 2  素材与探测（data/sourceResolver + hooks/useEditorSources）│
│   resolveClipUrl → /files/ + 画布节点 url + 素材库；探测去重缓存  │
├─────────────────────────────────────────────────────────────┤
│  Layer 1  工程数据（core/types + data/projectRepository）     │
│   tracks/clips/transitions/transforms → contentStore(kv)      │
│   + 纯函数 timelineOps（唯一改写入口）+ useEditorHistory       │
└─────────────────────────────────────────────────────────────┘
```

**铁律**：上层只依赖下层；Layer 1 纯函数**不 import 任何 React / 存储 / 网络**，
UI（`panels/`）只读 store、只通过 `timelineOps` 改 tracks。这与参考库 `multitrack-correctness` 计划的设计完全一致：
> 「把『按片段 ID 定位所属轨道并更新』的逻辑收口到 `timelineOps.ts` 纯函数，主轨更新后顺排，叠加轨保留自由时间位置。窗口组件只负责提交持久化与历史事务。」

## 三、数据流契约（本文核心交付物）

> 每条契约 = **「对方仓库的已验证设计」+「本仓库落地形态」+「禁止项」**。
> 这些契约是真相源，代码向它们对齐；改契约要先改本文。

### 契约 C1 · 工程数据模型（采纳，需瘦身）

**来源**：`types/videoEditor.ts`（参考库已把结构按多轨设计，一期只产单轨也无需迁移）。

**本仓库形态**：`core/types.ts` 照搬以下结构，**只删 Tauri 专属字段**：

| 参考库字段 | 处置 | 理由 |
| --- | --- | --- |
| `VideoEditorClip.filePath` | **删**（改走 `sourceUrl` = `/files/...` 或画布节点 url） | 本仓库无 `asset://` 本地路径体系（`113` ②） |
| `VideoEditorClip.assetId` | 保留（作为稳定资产身份，重定位用） | 与素材库 `ResourceItem.id` 对齐 |
| `VideoEditorClip.nodeId` | 保留（回溯来源画布节点） | 多源剪辑要回写正确节点 |
| `VideoEditorProjectRecord.projectId` | **必须有** | 本仓库按 `projectId` 隔离（见 `STORAGE_KEYS` 的 `canvas-state-v1-{projectId}`） |
| `VideoEditorProjectRecord.nodeId` | 必须有（工程锚点） | 导出结果回写锚点节点 |
| `schemaVersion` | 必须有 | 读到更高版本按「无工程」处理，不按缺字段渲染 |

**强制纯函数**（一并搬，已在参考库验证、可单测）：
`splitClipsAt` · `relayoutSequential` · `computeTimelineDuration` · `findClipAtTime` ·
`evaluateVolume`（包络线性插值）· `evaluateTransitionAlpha` · `hasMixedSources` · `needsCompositing`。

**规则 C1.1**：`Timeline`/`Inspector`/`Preview` **不得直接 mutaete `clip`/`track` 字段**，
一切改写经 `timelineOps` 纯函数生成新数组 → 交给 `editorStore` dispatch。
**规则 C1.2**：主视频轨是「磁吸」的（`!overlay` 的 `kind==='video'` 轨），任何增删后 `relayoutSequential` 压实；
叠加轨/音频轨保留自由时间位置与留空。

### 契约 C2 · 工程持久化（IndexedDB → contentStore）

**来源**：`services/indexedDb/videoEditorRepository.ts`（`videoEditorProjects` 表，主键 `projectId::nodeId`，schema 版本守卫）。

**本仓库形态**：`data/projectRepository.ts` 只经 `contentStore`（`contentGetAsync` / `contentSetAsync`），
键先登记进 `contracts.ts` 的 `STORAGE_KEYS`：

```ts
// contracts.ts STORAGE_KEYS 新增（遵循 CANVAS_STATE_PREFIX 同款动态模板风格）
'video-editor-project-{nodeId}': {
  domain: 'videoEditor',
  store: 'videoEditor/data/projectRepository.ts',
  backend: 'kv',                 // 跨端持久化，与 director3d-project-{nodeId} 同款
  pattern: true,
  note: '视频剪辑器工程：{tracks,selection,playhead}。按锚点 nodeId 隔离',
},
```

**映射对照**：

| 参考库 | 本仓库 |
| --- | --- |
| `buildVideoEditorProjectId(projectId,nodeId)` = `${projectId}::${nodeId}` | 键 `video-editor-project-{nodeId}`（projectId 已在内容里，`STORAGE_KEYS` 只按 nodeId 隔离即可，避免双写） |
| `getVideoEditorProject(id)`（IndexedDB `getAll`） | `contentGetAsync(KEY)`（kv 后端） |
| `schemaVersion` 高于当前 → 返回 null | 同语义：`getSnapshot().schemaVersion > VIDEO_EDITOR_SCHEMA_VERSION` → 视为无工程 |
| `saveVideoEditorProject`（事务写） | `contentSetAsync(KEY, record)`（contentStore 已带缓存+订阅+节流） |

**规则 C2.1（红线）**：禁止裸字符串键、禁止直调 `sGet/sSet/kvSet`；未登记的键在 `dev` 下 `contentStore.checkRegistered` 直接 throw（`113` 红线 2）。
**规则 C2.2**：写盘用 `createDebouncedPersist` 节流（参考 `contentStore` 原语）；**通知订阅即时、落盘节流**，UI 响应不受影响。
**规则 C2.3**：导出中/编辑中不阻塞持久化；工程记录与画布快照（`canvas-state-v1-{projectId}`）**是两条独立键**，禁止把 tracks 塞进画布快照（防双写漂移，同 `scriptBoxNode` 已注明的红线）。

**规则 C2.4（SSOT 唯一写者，红线）**：`video-editor-project-{nodeId}` 是 tracks 的**唯一真相源**，`editorStore` 经 `projectRepository` 是 tracks 的**唯一写者**；画布节点 `data` 仅作为**只读锚点**（存 `anchorNodeId`/`projectId`），由编辑器回写时**单向覆盖**锚点关系，节点侧**不得反向改写 tracks**。两处关系是"工程记录 → 节点锚点"的单向依赖，不存在第二写者，因此 D7 已结清（见 §九 D7 改写）。

### 契约 C3 · 素材 URL 唯一出口（消灭第二落盘通道）

**来源**：`useVideoEditorSources.ts` 的 `resolveClipUrl(clip)`——优先 `filePath` 经 `getConvertFileSrc()`，回落 `sourceUrl`。

**本仓库形态**：`data/sourceResolver.ts` 单一函数，三源归一：

```ts
function resolveClipUrl(clip: VideoEditorClip): string {
  // 1. 画布节点图源 / 本机导入落盘 url（uploadFileToLocal 返回的 /files/... 直接存为 sourceUrl）
  if (clip.sourceUrl) return clip.sourceUrl;
  // 2. 素材库资源（经素材库 resolve 函数，非裸路径）
  if (clip.assetId) return resolveAssetUrl(clip.assetId);
  return '';
}
```

**规则 C3.1（红线）**：剪辑器**不得自建第二落盘通道**。本机文件 / 素材库必须经 `localTool /files/`（见 `113` 红线 4）。
**规则 C3.2**：探测以「解析后 URL」为键做缓存（`useEditorSources` 的 `pruneVideoEditorSources` 同构），
分割产生的同源片段**不重复探测**（参考库实测结论：避免同一文件被探测 N 次）。
**规则 C3.3**：`sourceUrl` 持久化进工程记录；`filePath` 概念在本仓库不存在，落盘后一律是 `/files/` 绝对或相对 url。
**执行动作（G0）**：本机导入落盘统一调 `uploadFileToLocal(file, UPLOAD_DIRS.videoEditor, name)`（返回 `/files/canvas/video-editor/<name>` 并直接存为 `clip.sourceUrl`）；先在 `base/utils/uploadDirs.ts` 的 `UPLOAD_DIRS` 新增 `'videoEditor': 'canvas/video-editor'`（与 `canvas/video-process` 同级），禁止散写 `'canvas/video-editor'` 字面量（后端白名单未含会打爆落盘）。

### 契约 C4 · 编辑器 ↔ 节点边界（启动与产出）

**来源**：`videoEditorService.ts` 的 `openVideoEditorForNodes`（从画布节点建/复用工程，锚定第一个节点）
+ `videoEditorWindowService.ts` 的 `VideoEditorExportResult`（导出回传主窗口）。

**本仓库形态**：

**启动（对齐 `useImageHoverActions` 的「标记」同级）**：
- 视频/图片类节点的 hover 工具栏加「剪辑」按钮（与 `ImageEditor` 的「标记」同位）；
- 组件级 state 开 `VideoEditor`，传入 `{ projectId, anchorNodeId, sourceNodes }`；
- 打开前：`projectRepository` 取已有工程 → 有则复用（**增量追加**本次新选中源，保留已有裁剪/分割）；无则按 `relayoutSequential(usable.map(buildClip))` 建一条主视频轨。
  （参考库 `openVideoEditorForNodes` 的「多选追加而非重建」逻辑**必须继承**，否则用户多选了却只看到一个旧片段。）

**产出（三态，见 mockup 抬头 split button）**：

| 落点 | 动作 | 本仓库实现 |
| --- | --- | --- |
| **导出为新节点**（主链路） | 生成新视频节点回画布 | `deriveNodes.spawnAndCommit` / `buildSpawnNodes`（与 Director3DNode 导出同构），**右侧新建节点**，不覆盖源 |
| 导出到本地 | 落 `/files/` | `uploadFileToLocal(blob, UPLOAD_DIRS.videoEditor, name)`（返回 `/files/canvas/video-editor/<name>`）+ toast 路径 |
| 导出当前帧为图片 | 出图片节点 | `renderFrameAt` 抽当前帧 → `ImageNode` |

**规则 C4.1（破坏性操作不覆盖）**：导出结果**新建节点**而非覆盖源（参考库 `registerCanvasDerivation` 守卫的意图——剪辑是破坏性的，覆盖会让原始素材在画布上无从找回）。
**规则 C4.2（异步安全）**：导出是异步的，期间用户可能切项目/删源节点。回写前必须复核 `projectId`/`anchorNodeId` 仍有效（参考库 `assertCurrent?.()` 的意图），失效则丢弃结果并 toast。**复核的权威判定统一走 `deriveNodes` 的节点存活查询（或画布 store 查找），禁止各调用点各自实现「有效」语义**（统一出口，避免多份"有效"定义漂移）。
**规则 C4.3（如实告知音频去向）**：导出返回 `audioKept` 与 `audioDropReason`（参考库 `LosslessTrimResult`），界面据此提示，不让用户自己发现没声音。
**规则 C4.4（挂载上下文）**：`<VideoEditor>` 必须由画布 React Flow 提供树内渲染——节点 hover 触发的 state 直接 `editor && <VideoEditor/>` 条件挂载，对齐 `ImageEditor`（父层条件渲染 + `FullscreenShell open` 常量）。`FullscreenShell` 虽用 `createPortal` 挂到 `document.body`，但 **React 上下文随 React 树保留**，故挂载点必须在 `useReactFlow` / `deriveNodes.spawnAndCommit` 的 provider 子树内，否则无法回写节点。不可挂到 provider 之外。

**规则 C4.5（挂载硬断言，原 D9 提升）**：`<VideoEditor>` 挂载时即断言所在 React 树具备 `useReactFlow()` / `deriveNodes` 的 provider 上下文；**缺失直接 `throw`**，而非等"将来改独立窗口"才补。静默挂载到 provider 之外会导致回写失败且无任何报错，故该断言是启动期必过的硬门禁，不递延。

> 本仓库**不需要**参考库的 `postVideoEditorExported` 跨窗口 `postMessage` 协议——因为编辑器是同一 React 树里的 portal，导出结果直接经 `onExport(result)` 回调回写，省掉 `videoEditorWindowService.ts` 整个消息总线（含 `ALLOWED_*_MESSAGE_TYPES` 白名单）。

### 契约 C5 · 导出管线（直通 vs 合成，单一入口 + 可中断）

**来源**：`videoEditorMediaService.ts`（`exportLosslessTrim` / `exportLosslessConcat` / `exportComposite`）
+ `window.md` 设计决策 + `videoAudioMixer.resolveCompositeAudioMode`。

**本仓库形态**：`export/exportPipeline.ts` 单一入口，内部由 `needsCompositing(tracks)` 分流：

```
exportPipeline(tracks, opts) ─┬─ needsCompositing === false ─→ 无损直通
                              │     · 单片段  → exportLosslessTrim（关键帧对齐搬运，绕开编码器）
                              │     · 多片段  → exportLosslessConcat（各段解码参数一致才允许，否则报错而非产出坏文件）
                              └─ needsCompositing === true  ─→ 合成重编码
                                    · renderFrameAt 逐帧 + AudioBufferSource
                                    · 进度分「混音 20% / 画面 70% / 写音频 10%」三段（mockup 舞台 3「导出中」）
```

**关键继承点（都是踩坑结论，必须保留）**：

1. **直通必须绕开 `Conversion.trim`**。参考库已证实：当入点不在关键帧、`firstTimestamp < startTimestamp` 时，mediabunny 的 `Conversion.trim` 会**强制重编码**；而 WebView 上对 4K 调 `VideoEncoder.isConfigSupported` 会抛 `TypeError: Type error` 直接崩。
   → 本仓库用**分组无损搬运**实现直通（参考库 `exportLosslessTrim` 已验证，API 在 mediabunny 1.54 均存在）：

   ```ts
   const sink = new EncodedPacketSink(videoTrack);
   const startPacket = (await sink.getKeyPacket(start)) ?? (await sink.getFirstKeyPacket());
   const actualStart = startPacket.timestamp;            // 入点吸附到前关键帧
   const videoSource = new EncodedVideoPacketSource(videoCodec);
   output.addVideoTrack(videoSource);
   await output.start();
   // 音轨仅在容器支持该编码时原样搬，否则丢弃（总比整体失败好）
   for await (const p of sink.packets(startPacket, endPacket)) await videoSource.add(p); // 时间戳平移零点
   await output.finalize();
   ```

   音频轨仅在 `output.format.getSupportedAudioCodecs().includes(audioCodec)` 时以 `EncodedAudioPacketSource` 原样搬，否则**丢弃音轨**（参考库意图：编码不被 MP4 接受时直接丢音频，总比整个导出失败好）。
   代价：入点精度受关键帧间隔限制——**导出后如实提示 `actualStart`**，不假装精确。

2. **音频出口的目标只有一个：压缩后的 AAC**（用户预期、文件可控、兼容好）。
   mediabunny 的 `aac/opus/mp3/flac` 编码**全部委托给 WebCodecs `AudioEncoder`**（`encode.js:688`：
   `if (typeof AudioEncoder === 'undefined') return false`）；而 `pcm-*` 系列是"自己打包原始采样、不需要编码器"
   （`encode.js:685`：`PCM_AUDIO_CODECS.includes(codec) → return true`）。
   **结论：PCM 不碰 WebCodecs 不是设计选择，而是它无压缩、压根没有编码步骤——它产出的是未压缩原始音频，
   48kHz 立体声 ≈ 1.5 Mbps，一部片子可从几百 MB 暴涨到数 GB，且部分容器/播放器对 MP4 内的 PCM 支持差。
   所以 PCM 是「兜底里的兜底」，绝不能和 AAC 平起平坐当成能力。**

   **架构决策（作为架构师的选择：直面"必须产出压缩音轨"，不绕路）**：本仓库目标运行时是 **Chromium 内核**（Chrome 扩展 MV3 / Vite web / PWA），**不是** Tauri/WebKit。
   **决定性前提**：本仓库实际渲染引擎是 **Blink(Chromium)**，WebCodecs `AudioEncoder` 自 **Chrome 94（2021）** 起即稳定可用（AAC 编码常年被支持）。
   即目标平台**保证** `AudioEncoder` 存在且支持 AAC。因此：
   - **AAC 是唯一允许的压缩音轨出口**，不存在"编码器缺席就退化到未压缩 PCM"的绕路分支——那样是用更差的产物回避真问题（真问题是"必须产出压缩音轨"）。
   - 若运行时不支持 AAC（理论上不该发生在目标平台），**直接报错、明示用户**，而不是静默产出数 GB 的 PCM 文件让用户事后才发现。这正符合"一次性做对、不堆兜底/防卫"。

   > **参考库真相核验（并拒绝其懒政部分）**：我完整读了 `AI-Canvas-tauri-video-editor` 的音频链路，它**确实没"装上"编码器**，
   > 且在 `AudioEncoder` 缺席时退化到 `pcm-s16`（注释还写着过时的 `initPcmEncoder`）。
   > 它之所以在"成熟软件"里表现好，是因为**参考库自身**跑在已带 `AudioEncoder` 的 Tauri/WebKit 上、PCM 分支基本不触发（本仓库不跑 Tauri/WebKit，该前提不适用本仓库）；
   > 但 **PCM 退化本身是懒政绕路模式**——用未压缩产物回避"保证压缩编码"的真问题。我们**学它的正确部分（能力感知、copy 优先），拒绝它的懒政部分（静默 PCM 退化）**。

   音频出口判定（**只有两条正确路径，无绕路兜底**）：

   | 路径 | 条件 | 实现 |
   | --- | --- | --- |
   | **无损 copy** | 无需混音/不改音量/各段参数一致 | `EncodedAudioPacketSource` 原样搬已编码 AAC 分组（零 CPU、零损、首选——这是"不重编码"的正确做法，非兜底） |
   | **AAC via WebCodecs** | 需混音/调音量（常态） | `new AudioBufferSource({ codec: 'aac' })`（目标平台保证可用） |

   > **唯一异常出口（明错，不静默）**：导出前跑一次能力探针（C9）。若 `typeof AudioEncoder === 'undefined'` 或 AAC `isConfigSupported` 失败，
   > **直接 `throw` 明确错误并让 UI 红字提示"当前运行环境不支持音频编码，导出将不带音轨 / 请升级客户端"**——绝不允许落到未压缩 PCM。
   > 探针在启动期做一次（C9），结果随 UA/版本 memo 化，不必每次导出重复。
   > **明确不做（YAGNI，非"过度设计"修辞）**：① `registerEncoder` 注册 WASM AAC 编码器；② 把重编码挪到原生侧（若未来引入原生壳）。二者都是为"目标平台不会发生的场景"预付成本，违反"不堆过多防卫/兜底"。仅当未来产品**确要**支持无 `AudioEncoder` 的运行环境时，才作为独立任务启用，而非现在埋进导出管线。

3. **能力探针（启动期一次，非每次导出）**：直接用 mediabunny 自带的 `canEncodeAudio({codec:'aac'})` / `canEncodeVideo({codec:'avc'})`——其内部已做 `typeof` 守卫 + `isConfigSupported` 异常吞掉（不会因 WebKit 不识某枚举而崩），**本仓库不再自己包一层 `guardEncoderProbe` 去"试下一个候选"**（那是过度防卫）。
   探针在启动期跑一次，若结果显示 AAC/avc 不支持，**直接抛明确错误让 UI 红字提示**，而不是继续绕来绕去试候选。结果按 UA/版本号 memo 化，避免每次导出重复 `configure`。

4. **可中断**：全程 `AbortController` + `signal`；`finally` 清理临时 `Input`/解码器/落盘文件（mockup 舞台 3「取消必须真中断，否则第二次导出撞残留」）。
5. **源读取稳健性（治根，不在导出层堆内存兜底）**：mediabunny 经 `Input` 的 `Source` 抽象读字节（`InputOptions.source` 可传入自定义 `Source`）。导出对本地 `/files/`（localTool/18080）发起多段 Range 读取时，WebKit 并发压力下会让 `fetch` 直接失败（报 `TypeError: Type error`）。
   **正确做法（一次性做对）**：实现一个 `BoundedConcurrencySource`（自定义 `Source`，封装 `fetch` + `AbortSignal`），**限制并发 Range 请求数**（如 ≤4）并对单段失败退避重试一次——根因是并发过高，把并发压下来就读得稳。
   **禁止**参考库那种"失败就把整份文件塞进内存"的重型兜底：对 4K 源那会直接 OOM，是用内存兜底掩盖读取层缺陷的懒政。若退避重试后仍失败，导出**直接报错**（让用户重试 / 检查 localTool），不静默转全内存。

**规则 C5.1**：`needsCompositing` 是导出路径的**唯一判据**，UI 检查器明示当前走哪条（参考库设计：避免「加了个画中画就整条掉画质」悄悄发生）。
**规则 C5.2**：`export/mediaEngine.ts` 是导出管线对媒体引擎的**唯一封装层**，且必须**建立在已有 `base/utils/videoEngine.ts` 之上**（它已具备 `readVideoMetadata` / `processVideo` / `concatVideos` / `videoToGif` / `uploadResult`）。缺口（分组无损搬运、合成渲染、PCM 兜底）补进 `videoEngine.ts` 或在其之上的薄封装，**禁止新建平行 services**（同 `113` 风险「与 videoEngine 能力打架」）。

### 契约 C6 · 历史栈（只快照轨道数组）

**来源**：`useTimelineHistory.ts`（快照栈上限 50，`begin`/`commit`/`undo`/`redo`，连续交互只在 `begin` 落一张）。

**本仓库形态**：`hooks/useEditorHistory.ts` 同构。剪辑工程体量小（片段是元数据不含媒体），**整份 tracks 快照**比反向 diff 简单可靠。

**规则 C6.1**：连续拖拽/滑块 = `begin()` 在 pointerdown，`end()` 在 pointerup，**期间多次变更只产一张快照**（参考库 multitrack 计划 Task 3 的核心：一次连续交互只生成一个可撤销快照）。
**规则 C6.2**：单击按钮类操作（分割/删除/复制）各自 `commit()` 一张。
**规则 C6.3**：历史栈**独立于画布历史栈**（`historyStack.ts`）——编辑器是临时全屏层，其撤销不应污染画布节点操作，关闭即弃。
**规则 C6.4**：`MAX_HISTORY=50`，超限丢最旧，防止长时间编辑吃内存。

### 契约 C7 · 轨道状态闭环（lock/hide/mute 一致性）

**来源**：`track-state-behavior` 计划——锁定/隐藏/静音必须在时间轴、预览、属性编辑、导出**四处行为一致**，且不新增 schema 字段（状态已存在 `VideoEditorTrack.muted/locked/hidden`）。

**规则 C7.1**：轨道状态**只存在 `VideoEditorTrack`**，不新增持久化字段。
**规则 C7.2**：窗口层集中执行「锁定授权」——删除/复制/分割/属性修改/整轨删除/层级调整**统一拒绝锁定目标**（`isTrackLocked`/`isClipLocked` 纯函数判定）；混合选择删除时只删未锁定片段。
**规则 C7.3**：预览层按状态决定——主轨隐藏=走带但不绘制+强制静音；主轨静音=只关声不隐画面；叠加轨按轨道静音+阻止锁定轨拖拽；活动音频轨用 `<audio>` 跟随播放头，隐藏/静音轨不发声。
**规则 C7.4**：时间轴/检查器只做反馈与阻止入口（锁定片段禁用右键/变换/转场/音量输入），**不得出现「点了但导出结果没变」的假按钮**（mockup 舞台 3 审计结论）。

### 契约 C8 · 预览与合成共用渲染路径（WYSIWYG）

**来源**：`videoCompositor.ts` 的 `renderFrameAt(context, canvas, tracks, time, resolve)`——
**预览与导出走同一条渲染函数**，多轨叠加/画中画/转场所见即所得。

**本仓库形态**：`export/composite.ts` 为**新建文件**，移植参考库 `videoCompositor.renderFrameAt`（本仓库 `videoEngine.ts` 目前只有 trim/concat/metadata，尚无帧合成器）；`Preview.tsx` 两种预览策略：
- **主轨**：原生 `<video>` 吃系统解码器（比逐帧驱动 canvas 稳，参考库 + 本仓库 `videoEngine` 共识）；
- **叠加层**：图片用 `<img>`、视频叠加用独立 `<video>`（URL 经 C3 解析），按 `playhead - timelineStart + sourceIn` 同步 `currentTime`；CSS transform 叠位置（首发不做全合成实时预览，全量合成只在导出时做——见 `113` 风险「多轨实时预览卡顿」）。

**规则 C8.1**：`computeDrawRect`（contain + transform 求绘制矩形）、`evaluateTransitionAlpha`、`findDissolveUnderlay`（交叠淡入底图）**预览导出共用同一份**，杜绝「预览对导出错」。
**规则 C8.2**：`renderFrameAt` 是 `async`（视频帧经 `VideoSampleSink.getSample`），调用方负责 `sample.close()` 与 `Input.dispose()`，避免帧泄漏。

## 六、红线（落地即检查）

1. **存储键禁止裸字符串**：必须 `STORAGE_KEYS` 登记，`contentStore.checkRegistered` 在 dev 下 throw（`113` 红线 2）。
2. **事件名禁止裸字符串**：若编辑器与画布需通信（如「导出为新节点」），先登记 `EVENTS`（`113` 红线 3）。
3. **唯一落盘通道**：`localTool /files/`；剪辑器不得自建第二通道（`113` 红线 4）。
4. **单一媒体引擎**：`videoEngine`（mediabunny）是唯一实现，缺口补在它身上。
5. **画布与时间轴交互区必须 `nodrag`**，否则拖动被画布节点吞掉。
6. **全屏层必须走 `FullscreenShell`**（自动登记 modalLayer），禁止自挂 `window.addEventListener` 抢快捷键（参考 `115` 第三轮「全屏模态层未挡住 React Flow 删除键」事故）。
7. **不手改 `dist/`**；改完 `npm run build` 出包。
8. 每 Gate 收尾跑：`type-check → test:smoke → test:unit → build`（较大改动加 `check:health`）。

- 改一个片段变换 → 只有 `timelineOps` 产新数组、历史栈 +1（C1/C6）；
- 主轨 + 图片贴图导出 → 检查器明示「合成重编码」（C5.1）；
- 锁定轨道 → 时间轴/预览/检查器/导出四处一致拒绝（C7）；
- 导出中取消 → 真中断且无残留文件（C5.4）；
- 刷新重开 → 工程从 contentStore 恢复（C2）。

## 九、技术债清单（做完上述决策后的已知风险）

> 本节是**架构师视角的债务登记**：上述每个"最优/不过度设计"决策都附带 deferred cost。落地时应同步建护栏，否则会在后续迭代静默爆雷。

| # | 债务项 | 触发条件 | 后果 | 护栏 / 缓解 | 到期（需还债）条件 |
| --- | --- | --- | --- | --- | --- |
| D1 | **运行时假设债**：显式绑定 **Chromium(Blink) 内核**（有 `AudioEncoder`/`VideoEncoder`，Chrome 94+ 即稳定）。这是**有意为之的硬性前提**，非隐性绑定（本仓库实跑 runtime = Chrome 扩展 MV3 / Vite web / PWA，非 Tauri/WebKit） | 产品后续需支持 **非 Chromium 内核**（Firefox<某版 / Safari<26 / 其他 WebView） | 非目标平台用户导出时**直接收到"不支持音频/视频编码"的明确错误**（已是明错，不再静默退化） | 维护**平台能力矩阵** + 启动期 `canEncode*` 探针硬门；把 WASM/原生编码器列为已知递延项 | 任一"无 `AudioEncoder` 的运行环境"进入支持范围 |

**债务总览原则**：
- **D1/D2/D11 是同一笔债的三个面**——"依赖 Chromium(Blink) 内核的 `AudioEncoder`、不为不触发的路径过度设计"。它现在的收益是零包体增量、实现简单；代价是一旦支持范围扩大（非 Chromium 内核）就必须补编码器（见 D1/D2/D11）。本文已用"未来可选扩展"把还债路径留好，避免到时候推倒重来。
- **D4/D5/D8 是"依赖外部库 / 外部服务"的普遍债**，统一靠**适配层 + 契约测试**兜底，不侵入业务。
- **D7/D9 是"状态真理源 / 挂载边界"的架构债**，靠**单一写者 + 约束编码化**防止静默失效。
