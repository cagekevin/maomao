## 〇、一句话结论

对方仓库**最值钱的是它的数据流设计，不是它的 UI**。

它的 UI 是 Tauri 桌面端一套（独立窗口 + 自绘标题栏 + i18n + fileService + IndexedDB），**整包搬过来 100% 编译不过**。
但它的四条数据流契约是**与平台无关的、已踩过坑的真理**：

1. **数据模型与渲染操作严格分离**（`types/videoEditor.ts` 纯数据 + `timelineOps.ts` 纯函数，零 React 依赖）；
2. **预览与导出共用同一条合成渲染路径**（`videoCompositor.renderFrameAt`，所见即所得，杜绝「预览对导出错」）；
3. **直通 vs 合成由 `needsCompositing(tracks)` 一个谓词决定**，且直通走关键帧对齐的无损搬运（`exportLosslessTrim`），绕开编码器；
4. **历史栈只快照轨道数组**，连续拖拽由调用方决定何时落一张（避免一次拖拽炸出几十张快照）。

本仓库要做的，是把这四条**原样继承**，只换「承载平台」：
- Tauri 独立窗口 → **常驻底部层**（画布内容区内的普通子节点，与 AI 助手同构；无 Tauri / 无独立 React 实例）；M2 工作台才走 `FullscreenShell` portal；
- IndexedDB 仓储 → 本仓库 `contentStore` + `STORAGE_KEYS`（kv 后端）；
- `fileService` / `asset://` → 本仓库 `localTool /files/` 单一落盘通道；
- 窗口 `postMessage` 回传 → 直接回调（导出结果同步回写节点，无跨窗口协议）。

## 形态定稿（2026-09-13）：基座 + 可收起的上层

> **本节地位**：本节是 2026-09-13 讨论的**形态裁决**，是 §一（安置位置）、C4（入口与产出）、C6.3（历史栈生命周期）、D7/D9 的**上游依据**。
> 与本节冲突的旧表述一律以本节为准（那几节已按本节改写）。
> **范围切分**：本节只定 **M1 基座层**（素材装配 + 导出）的形态；**M2 工作台**（精剪：预览/检查器/转场/音量/变速）整体推迟，其 mockup 与契约不在本轮。

### 0.1 形态：三种状态，**没有「全屏模态态」，也没有「折叠但仍编辑」**

```
① 折叠（未激活）── 像 AI 助手收起一样，底部不留任何痕迹
     │  点顶栏按钮
     ▼
② 基座（激活 · 底部时间轴条）── 编辑态：接收素材 / 吃键盘 / 持有会话
     │  点「展开工作台」
     ▼
③ 工作台（M2）── 大预览 + 检查器 + 精剪
```

底层其实是 **一个「激活位」+ 两档展开程度**：

| | 折叠 | 基座 | 工作台 |
| --- | --- | --- | --- |
| 激活（是否在剪辑） | **否** | 是 | 是 |
| 接收画布选中素材（C11） | **否** | 是 | 是 |
| 键盘归属（C10） | 全归画布 | 只有 `Delete` / `⌘Z` / `⌘⇧Z` 归剪辑器 | 同基座 |
| 画布 | 满屏 | 被压缩、仍可操作 | 被覆盖 |

> **红线（最重要的形态红线）**：**折叠 = 未激活 = 不接受画布上的任何素材。**
> 不存在「编辑到一半最小化」这个中间态——**面板没展开，就是根本不在视频编辑状态**。
> 这一条一次消除两个隐患：① 折叠时的静默入池（用户点了素材什么都没发生、后台其实多了一条）；② 折叠态的「后台还存在感」。
> 入口两个，**都是纯入口、都不带状态暗示**：
> ① **页面最底部居中的半圆把手**（主入口，只在折叠态出现；半圆 + 向上箭头，无数值）——见 §0.3；
> ② **顶栏按钮**（次入口，与 AI 助手按钮同排同款）。

> **但有两件事不因折叠消失**：
> ① **工程不丢**——随改随存（§0.6），折叠只是离开编辑态，再次展开原样恢复；
> ② **在飞的导出不中断**——导出是后台任务，折叠 ≠ 取消；取消只有一个入口，就是导出进度上的「取消导出」。

**展开顺序由依赖方向决定**：tracks 是上游、预览是下游 → 先给时间轴、后给画面是唯一正确的顺序（反过来会先长出一屏没有数据支撑的画面）。M2 落地时这条顺序同样不得倒置。

### 0.3 状态清单

| 状态 | 触发 | 形态 | 是否激活 |
| --- | --- | --- | --- |
| **折叠** | 默认 / 点收起按钮收起 / 点把手展开 | **页面最底部居中的半圆把手**（纯入口：半圆 + 向上箭头，**无任何数值**） | 否 |
| **基座** | 点顶栏按钮 / 点底部半圆把手 | 底部时间轴条（工具带 / 轨道区），高度可拖 | 是 |
| **播放中**（基座子态） | 点播放 | 播放头走 + 出声（M1 无画面）；**任何编辑动作先自动暂停** | 是 |
| **工作台** | 点「展开工作台」 | M2，本轮不实现 | 是 |

> **修订（2026-09-13）**：折叠态**没有**「细状态条」之类的中间形态——旧设计已删。
> 既然折叠 = 未激活，就不该有任何「后台还有事」的暗示；那会让人以为剪辑器还在跑。

**折叠态的可见形态只有一个：页面最底部居中的「半圆把手」（半圆 + 向上箭头）。**（2026-09-13 定）

| 维度 | 定论 | 理由 |
| --- | --- | --- |
| 形状 | **半圆**（上圆下平，贴页面最底边）+ 中间一个**向上箭头** | 视觉上就是"抽屉拉手"，一眼知道"这里能拉起来" |
| 位置 | **页面最底部、水平居中** | 时间轴是主时间观入口，就该长在它要展开的地方 |
| **不放** | **不与 AI 助手并排在右上角** | 右上角是"工具/助手"区；把时间轴入口放进那一堆图标里，语义冲突且难找 |
| 内容 | **只有半圆 + 箭头，不显示任何数值** | 参考实现的把手带摘要（「时间轴 · 7 段 · 0:24」），我们**刻意不带**——带了就是状态暗示，违反"折叠 = 未激活" |
| 时机 | 只在**折叠态**出现；基座 / 工作台展开时消失 | 收起由基座工具带上的收起按钮负责，避免两个入口并存 |
| 范围 | 仅在画布视图（`view === 'canvas'`）出现 | 与画布专属覆盖层同一范围 |

> **参考实现的反证**：Nomi 的折叠把手曾挪到右下"避开中央编辑通道"（2026-08-06），随后**用户拍板挪回底部中间**（2026-08-08），理由是「时间轴是主时间观入口，应在底部中间」。我们直接采用底部居中，省掉这次来回。

> **红线（形态 · 键盘）**：**基座不是全屏模态层，不得登记 `modalLayer`。**
> 一旦登记，画布全局快捷键（⌘Z / Q/W/E / Delete / Tab）整体让位，而「**在画布上点选素材 → 入轨**」这条主入口**只在基座展开时才生效**，它依赖画布正常 → 用户会得到「剪辑器一开，画布就废了」。
> 键盘归属按 **激活位** 派生（**不做新基建**）：只有 `Delete` / `⌘Z` / `⌘⇧Z` 归剪辑器（防画布被误删 / 误撤销），其余画布照常；剪辑器自身的其余操作**全部按钮化**。见 C10。

### 0.4 动作归属（哪个动作在哪一层）

| 动作 | 归属 | 理由 |
| --- | --- | --- |
| 加入素材（**在画布上点选素材节点**） | **基座（仅激活时）** | 「往轨上放东西」本质是时序操作，不是看画面 |
| 拖序、调片段长度（粗档）、整段取舍、吸附 | **基座** | 粗排（assembly） |
| 导出 | **基座** | 不加工作台也能出片，导出不被扣为人质 |
| 替换素材、精剪（帧级切点 / 转场 / 画中画 / 字幕 / 音量包络 / 变速 / 调色） | **工作台（M2）** | 判断依据只能是画面本身 |

> **M1 的定位是「粗排」，不是「精剪」。** 粗排的判断依据是缩略图、时长、顺序，不需要逐帧看。
> 由此推出一条硬结论：**缩略图条 + 波形不是锦上添花，是 M1 能独立成立的前提。**
> 「改片段长度」是粗排里唯一需要画面的动作；音频在画布上没有任何可视形态，没有波形等于纯盲。
> 这**修正 §四 复用清单**里把 `VideoThumbnail` 当「可借的 UI 加分项」的旧表述——它是功能必需项。

### 0.5 精度分档（UI 分档，**数据不分档**）

- 基座只到**秒级 / 吸附到片段边界**；帧级精度归工作台；
- **红线（数据）**：分档只发生在 UI 层，`core/types.ts` **只有一套**数据模型（时间戳）。
  不得为「简单的基座」造第二套简化模型——那是「两个编辑器」的变种，必然出现「时间轴改了画面没变」。

### 0.6 「取消」这个动作消失（改为暂存制）

旧 mockup 抬头是「取消 / 导出」，那是全屏层语义（放弃并退出）。基座是常驻层，**没有「退出」这件事**：

| 旧语义 | 新语义 |
| --- | --- |
| 取消 = 放弃改动并关闭 | **不存在**。折叠只是离开编辑态，工程随改随存（C2），不丢 |
| — | 破坏性动作改为显式：**清空工程**，且需二次确认（**不设「移出全部素材」**——那是已删的池子时代话术；片段清理由普通删除 / 波纹删除承担，见 C15） |
| — | 折叠**不取消**在飞的导出（导出是后台任务；取消只有一个入口：进度条上的「取消导出」） |

### 0.7 视角：mockup 必须画「画布视角」

旧 `mockup/video-editor-mockup.html` 是**编辑器视角**（1280×900 全屏四段骨架），它是 **M2 工作台的参考图，保留不动**。
M1 的新 mockup 是 `mockup/video-editor-dock-mockup.html`，**画布视角**：背景是真实画布（节点 / 连线 / 左下工具栏），底部才是时间轴条。

理由：本方案合理性的根据就是「素材从画布来」。图画成编辑器全屏，看图的人无法验证这一点，形态也会自然长回旧样子。

## 一、安置位置（先定边界，再定目录）

### 1.1 它是什么性质的东西

它是**业务域编辑器**，不是「通用地基」。`base/README.md` 红线原文：
**`base/` 是通用地基，业务域（nodes / panels / videoEditor 等）可依赖 `base/`，但 `base/` 不得反向依赖业务域**（`npm run check:arch` 拦截）。

> **更新(2026-09-13 · 取证修正 · 本条对 videoEditor 原不成立)**：`scripts/check-arch.mjs` 的分层规则原用**手写域名清单** `BUSINESS_RE = /^src\/components\/(nodes|scriptbox|agent|panels)\//` —— 不含 `videoEditor`（也不含 `edges`），故「`check:arch` 拦截」对剪辑器域**当时并不成立**。
> 已由 `docs/123` G-1 改为**反向判据**：`base/` 不得 import `src/components/` 下**任何非 `base/` 目录**（一次改完，自动覆盖未来所有业务域）。
> 该判据上线即抓出 1 处真实越界 —— `base/ui/NodeShell.tsx → edges/CustomHandle.tsx`（旧名单从未拦过）→ 已修（`CustomHandle` 下沉 `base/ui/`）。

> **约定**：本文所有 `base/...` 均指 `src/components/base/...`（如 `base/README.md` ≡ `src/components/base/README.md`、`base/editors/ImageEditor.tsx` ≡ `src/components/base/editors/ImageEditor.tsx`）。其中 `FullscreenShell` 位于 `base/panels/`（非 `base/editors/`）。

视频剪辑器作为业务域**依赖** `base/core/contentStore`、`base/api/filesApi`、`base/canvas/deriveNodes`、`base/canvas/nodeMedia`（选中派生）是**合规方向**（M2 工作台再加 `base/panels/FullscreenShell`）；

`ImageEditor` 虽在 `base/editors/`，但它被定为「内容编辑/查看器」（通用地基），且已先落地、有先例。
视频剪辑器体量远大于图片编辑器（核心 5 文件 + 纯逻辑 + 数据层 + 导出管线，约等于 `Director3DNode` 的量级），
**按性质应归入业务域，与 `src/components/nodes/` 同级**——就像 `VideoProcessNode`、`Director3DNode` 那样。

> **决策**：代码主目录落在 `src/components/videoEditor/`（业务域，归 `check:arch` 允许）。
> **挂载方式见 §1.2 与 C10**：M1 基座层是**常驻底部层**（画布内容区内的普通子节点，非 portal、非模态，展开时压缩画布而非覆盖）；
> **M2 工作台**才复用 `base/panels/FullscreenShell`（只 import 挂载壳，不把逻辑塞进 base/）。
> **本节已推翻原方案的「M1 也走 FullscreenShell」**——全屏层是临时/关闭即弃的语义，与「长期存活、随时回来」的剪辑会话冲突（见形态定稿）。

| `schemaVersion` 高于当前 → 返回 null | 同语义：`getSnapshot().schemaVersion > VIDEO_EDITOR_SCHEMA_VERSION` → 视为无工程 |
| `saveVideoEditorProject`（事务写） | `contentSetAsync(KEY, record)`（contentStore 已带缓存+订阅+节流） |
| （无） | **素材池已删**（C11 重写）：入轨零中间站，工程记录里不再有 `pool` 字段 |

**规则 C2.1（红线）**：禁止裸字符串键、禁止直调 `sGet/sSet/kvSet`；未登记的键在 `dev` 下 `contentStore.checkRegistered` 直接 throw（`113` 红线 2）。

> **更新(2026-09-13 · 取证修正)**：`contentStore.checkRegistered` 是 `contentStore.ts:232` 的**内部函数、未导出** → **外部不可调用**，因此「外部靠它 throw」这条机制不成立。红线实际由两道承载：**编译期** `npm run check:keys`（裸键字面量静态拦截）+ **写入路径内部守卫**。

**规则 C2.2**：写盘用 `createDebouncedPersist` 节流（参考 `contentStore` 原语）；**通知订阅即时、落盘节流**，UI 响应不受影响。

> **更新(2026-09-13 · 实现修正)**：节流**不属于持久化原语层**。`docs/123` G2 的 `projectRepository.saveProject` 走 KV 严格族 CAS（`contentKvSetCas`），**必须能返回 409 冲突结果**；若在它之上套节流，`saveProject` 会变成「发射后不管」、冲突结果没有返回路径 → C2.7 的「不静默覆盖」当场失效。
> 故节流归**调用方**（`editorStore`），且**必须消费 conflict 结果**（可提示、可重载，不可吞）。
**规则 C2.3**：导出中/编辑中不阻塞持久化；工程记录与画布快照（`canvas-state-v1-{projectId}`）**是两条独立键**，禁止把 tracks 塞进画布快照（防双写漂移，同 `scriptBoxNode` 已注明的红线）。

**规则 C2.4（SSOT 唯一写者，红线）**：`video-editor-project-{projectId}` 是 **tracks 的唯一真相源**，
`editorStore` 经 `projectRepository` 是**唯一写者**。画布节点**不参与工程状态**——它只被**读**（选中派生素材，见 C11），不回写、也不被回写。
因此本方案**没有第二写者**，D7 维持结清（见 §九 D7）。

> **与旧稿的差别**：旧稿把 `anchorNodeId` 当作工程身份、并在节点 `data` 上存锚点（单向覆盖）。
> 形态定稿后入口是全局的，**「锚点」这个概念整个消失**——没有锚点，就没有「两处关系」可言，SSOT 反而更干净。

**规则 C2.5（体积红线）**：工程记录**只存元数据与 URL**，禁止内联 `base64`（缩略图 / 波形 / 素材本体一律不进工程记录）——同 `72-会话落盘base64体积降级` 的教训。
**规则 C2.6（多片子 = 多 project）**：工程**随项目走，一个 project 一份工程**（与 AI 助手会话同构：AI 会话也是跟 project 走）。
要剪第二条片子就**进新 project**；因此**导出后不清空工程**（可继续改、继续导出）。工程**不做「多序列」**。
**规则 C2.7（并发）**：工程记录与画布快照同属「同一项目的画布资产」→ **多窗口并发写同样受 `118` 的 CAS / 冲突可见约束**。
> 工程记录是另一条键，但语义相同：**不允许静默覆盖**（宁可让用户看到冲突，也不要悄悄丢掉对方的编辑）。

### 契约 C3 · 素材 URL 唯一出口（消灭第二落盘通道）

**来源**：`useVideoEditorSources.ts` 的 `resolveClipUrl(clip)`——优先 `filePath` 经 `getConvertFileSrc()`，回落 `sourceUrl`。

**本仓库形态**：`data/sourceResolver.ts` 单一函数，三源归一：

```ts
function resolveClipUrl(clip: VideoEditorClip): string {
  // 1. 画布节点图源 / 本机导入落盘 url（uploadFileToLocal 返回的 /files/... 直接存为 sourceUrl）
  if (clip.sourceUrl) return clip.sourceUrl;
  // 2. 素材库资源（经素材库 resolve 函数，非裸路径）
  if (clip.assetId) return resolveAssetUrl(clip.assetId);
  return '';
}
```

**规则 C3.1（红线）**：剪辑器**不得自建第二落盘通道**。本机文件 / 素材库必须经 `localTool /files/`（见 `113` 红线 4）。
**规则 C3.2**：探测以「解析后 URL」为键做缓存（`useEditorSources` 的 `pruneVideoEditorSources` 同构），
分割产生的同源片段**不重复探测**（参考库实测结论：避免同一文件被探测 N 次）。
**规则 C3.3**：`sourceUrl` 持久化进工程记录；`filePath` 概念在本仓库不存在，落盘后一律是 `/files/` 绝对或相对 url。

> **更新(2026-09-13 · 实现修正)**：
> ① 上面示例的「解析不出 → 返回 `''`」**不采用**：`docs/123` §二.7 P4 已裁定「**解析 URL」与「判是否断链」必须是同一个原语**，故实现为 `data/sourceResolver.ts::resolveClipSource`，返回**判别联合** `{status:'ok',url}` / `{status:'broken',reason}`；**探测失败也是断链的触发点**（传 `probe` 进来，同一个裁决点）。
> ② 解析**不得**走 `base/utils/assetUrl.ts::resolveAssetUrl(scope:'render')`：该出口会把**任何**本地文件 URL 改写成按需出图端点 `/files/thumbnail?url=…`（`assetUrl.ts:179`），而那端点由 Jimp 出图（白名单只认图片）→ **视频经它会静默拿错结果**。剪辑器一律取**原文件**地址（`toAbsoluteFileUrl`）。
> ③ 断链判定收口于上述同一原语，`{status:'broken'}` 是**持续状态**（片段红标），不是 toast。
**执行动作（G0）**：本机导入落盘统一调 `uploadFileToLocal(file, UPLOAD_DIRS.videoEditor, name)`（返回 `/files/canvas/video-editor/<name>` 并直接存为 `clip.sourceUrl`）；先在 `base/utils/uploadDirs.ts` 的 `UPLOAD_DIRS` 新增 `'videoEditor': 'canvas/video-editor'`（与 `canvas/video-process` 同级），禁止散写 `'canvas/video-editor'` 字面量（后端白名单未含会打爆落盘）。

+ `videoEditorWindowService.ts` 的 `VideoEditorExportResult`（导出回传主窗口）。

**规则 C4.3（如实告知音频去向）**：导出返回 `audioKept` 与 `audioDropReason`（参考库 `LosslessTrimResult`），界面据此提示，不让用户自己发现没声音。
**规则 C4.4（挂载上下文）**：基座常驻在画布内容区内（`useReactFlow` provider 子树内），**天然具备** `deriveNodes.spawnAndCommit` 上下文；M2 工作台虽走 `createPortal(document.body)`，但 **React 上下文随 React 树保留**，故其挂载点同样必须在 provider 子树内。
**规则 C4.5（挂载硬断言，原 D9 提升）**：`<VideoEditorDock>` 挂载时即断言所在 React 树具备 `useReactFlow()` / `deriveNodes` 的 provider 上下文；**缺失直接 `throw`**。常驻层一旦挂到 provider 之外，导出回写会静默失败且无任何报错，故该断言是启动期必过的硬门禁，不递延。
**规则 C4.6（跨轨拖拽拒绝，不静默改语义）**：把音频片段拖到视频轨（或反向）**直接拒绝并提示**，不得静默转换——静默转换会让「我拖过去它怎么变成了这样」成为不可解释行为。分轨判据只有 `routeClipToTrack(kind)`（C11）。
**规则 C4.7（带声音的视频不拆轨，红线）**：视频片段的音轨**随其所在视频片段内联**（`clip.hasAudio`），**不自动拆到音频轨**；只有「纯音频素材」才上音频轨。

### 契约 C5 · 导出管线（直通 vs 合成，单一入口 + 可中断）

**来源**：`videoEditorMediaService.ts`（`exportLosslessTrim` / `exportLosslessConcat` / `exportComposite`）
+ `window.md` 设计决策 + `videoAudioMixer.resolveCompositeAudioMode`。

**本仓库形态**：`export/exportPipeline.ts` 单一入口，内部由 `needsCompositing(tracks)` 分流：

```
exportPipeline(tracks, opts) ─┬─ needsCompositing === false ─→ 无损直通
                              │     · 单片段  → exportLosslessTrim（关键帧对齐搬运，绕开编码器）
                              │     · 多片段  → exportLosslessConcat（各段解码参数一致才允许，否则报错而非产出坏文件）
                              └─ needsCompositing === true  ─→ 合成重编码
                                    · renderFrameAt 逐帧 + AudioBufferSource
                                    · 进度分「混音 20% / 画面 70% / 写音频 10%」三段（mockup 舞台 3「导出中」）
```

**关键继承点（都是踩坑结论，必须保留）**：

1. **直通必须绕开 `Conversion.trim`**。参考库已证实：当入点不在关键帧、`firstTimestamp < startTimestamp` 时，mediabunny 的 `Conversion.trim` 会**强制重编码**；而 WebView 上对 4K 调 `VideoEncoder.isConfigSupported` 会抛 `TypeError: Type error` 直接崩。
   → 本仓库用**分组无损搬运**实现直通（参考库 `exportLosslessTrim` 已验证，API 在 mediabunny 1.54 均存在）：

   ```ts
   const sink = new EncodedPacketSink(videoTrack);
   const startPacket = (await sink.getKeyPacket(start)) ?? (await sink.getFirstKeyPacket());
   const actualStart = startPacket.timestamp;            // 入点吸附到前关键帧
   const videoSource = new EncodedVideoPacketSource(videoCodec);
   output.addVideoTrack(videoSource);
   await output.start();
   // 音轨仅在容器支持该编码时原样搬，否则丢弃（总比整体失败好）
   for await (const p of sink.packets(startPacket, endPacket)) await videoSource.add(p); // 时间戳平移零点
   await output.finalize();
   ```

   音频轨仅在 `output.format.getSupportedAudioCodecs().includes(audioCodec)` 时以 `EncodedAudioPacketSource` 原样搬，否则**丢弃音轨**（参考库意图：编码不被 MP4 接受时直接丢音频，总比整个导出失败好）。
   代价：入点精度受关键帧间隔限制——**导出后如实提示 `actualStart`**，不假装精确。

2. **音频出口的目标只有一个：压缩后的 AAC**（用户预期、文件可控、兼容好）。
   mediabunny 的 `aac/opus/mp3/flac` 编码**全部委托给 WebCodecs `AudioEncoder`**（`encode.js:688`：
   `if (typeof AudioEncoder === 'undefined') return false`）；而 `pcm-*` 系列是"自己打包原始采样、不需要编码器"
   （`encode.js:685`：`PCM_AUDIO_CODECS.includes(codec) → return true`）。
   **结论：PCM 不碰 WebCodecs 不是设计选择，而是它无压缩、压根没有编码步骤——它产出的是未压缩原始音频，
   48kHz 立体声 ≈ 1.5 Mbps，一部片子可从几百 MB 暴涨到数 GB，且部分容器/播放器对 MP4 内的 PCM 支持差。
   所以 PCM 是「兜底里的兜底」，绝不能和 AAC 平起平坐当成能力。**

   **架构决策（作为架构师的选择：直面"必须产出压缩音轨"，不绕路）**：本仓库目标运行时是 **Chromium 内核**（Chrome 扩展 MV3 / Vite web / PWA），**不是** Tauri/WebKit。
   **决定性前提**：本仓库实际渲染引擎是 **Blink(Chromium)**，WebCodecs `AudioEncoder` 自 **Chrome 94（2021）** 起即稳定可用（AAC 编码常年被支持）。
   即目标平台**保证** `AudioEncoder` 存在且支持 AAC。因此：
   - **AAC 是唯一允许的压缩音轨出口**，不存在"编码器缺席就退化到未压缩 PCM"的绕路分支——那样是用更差的产物回避真问题（真问题是"必须产出压缩音轨"）。
   - 若运行时不支持 AAC（理论上不该发生在目标平台），**直接报错、明示用户**，而不是静默产出数 GB 的 PCM 文件让用户事后才发现。这正符合"一次性做对、不堆兜底/防卫"。

   > **参考库真相核验（并拒绝其懒政部分）**：我完整读了 `AI-Canvas-tauri-video-editor` 的音频链路，它**确实没"装上"编码器**，
   > 且在 `AudioEncoder` 缺席时退化到 `pcm-s16`（注释还写着过时的 `initPcmEncoder`）。
   > 它之所以在"成熟软件"里表现好，是因为**参考库自身**跑在已带 `AudioEncoder` 的 Tauri/WebKit 上、PCM 分支基本不触发（本仓库不跑 Tauri/WebKit，该前提不适用本仓库）；
   > 但 **PCM 退化本身是懒政绕路模式**——用未压缩产物回避"保证压缩编码"的真问题。我们**学它的正确部分（能力感知、copy 优先），拒绝它的懒政部分（静默 PCM 退化）**。

   音频出口判定（**只有两条正确路径，无绕路兜底**）：

   | 路径 | 条件 | 实现 |
   | --- | --- | --- |
   | **无损 copy** | 无需混音/不改音量/各段参数一致 | `EncodedAudioPacketSource` 原样搬已编码 AAC 分组（零 CPU、零损、首选——这是"不重编码"的正确做法，非兜底） |
   | **AAC via WebCodecs** | 需混音/调音量（常态） | `new AudioBufferSource({ codec: 'aac' })`（目标平台保证可用） |

   > **唯一异常出口（明错，不静默）**：导出前跑一次能力探针（C9）。若 `typeof AudioEncoder === 'undefined'` 或 AAC `isConfigSupported` 失败，
   > **直接 `throw` 明确错误并让 UI 红字提示"当前运行环境不支持音频编码，导出将不带音轨 / 请升级客户端"**——绝不允许落到未压缩 PCM。
   > 探针在启动期做一次（C9），结果随 UA/版本 memo 化，不必每次导出重复。
   > **明确不做（YAGNI，非"过度设计"修辞）**：① `registerEncoder` 注册 WASM AAC 编码器；② 把重编码挪到原生侧（若未来引入原生壳）。二者都是为"目标平台不会发生的场景"预付成本，违反"不堆过多防卫/兜底"。仅当未来产品**确要**支持无 `AudioEncoder` 的运行环境时，才作为独立任务启用，而非现在埋进导出管线。

3. **能力探针（启动期一次，非每次导出）**：直接用 mediabunny 自带的 `canEncodeAudio({codec:'aac'})` / `canEncodeVideo({codec:'avc'})`——其内部已做 `typeof` 守卫 + `isConfigSupported` 异常吞掉（不会因 WebKit 不识某枚举而崩），**本仓库不再自己包一层 `guardEncoderProbe` 去"试下一个候选"**（那是过度防卫）。
   探针在启动期跑一次，若结果显示 AAC/avc 不支持，**直接抛明确错误让 UI 红字提示**，而不是继续绕来绕去试候选。结果按 UA/版本号 memo 化，避免每次导出重复 `configure`。

4. **可中断**：全程 `AbortController` + `signal`；`finally` 清理临时 `Input`/解码器/落盘文件（mockup 舞台 3「取消必须真中断，否则第二次导出撞残留」）。
5. **源读取稳健性（治根，不在导出层堆内存兜底）**：mediabunny 经 `Input` 的 `Source` 抽象读字节（`InputOptions.source` 可传入自定义 `Source`）。导出对本地 `/files/`（localTool/18080）发起多段 Range 读取时，WebKit 并发压力下会让 `fetch` 直接失败（报 `TypeError: Type error`）。
   **正确做法（一次性做对）**：实现一个 `BoundedConcurrencySource`（自定义 `Source`，封装 `fetch` + `AbortSignal`），**限制并发 Range 请求数**（如 ≤4）并对单段失败退避重试一次——根因是并发过高，把并发压下来就读得稳。
   **禁止**参考库那种"失败就把整份文件塞进内存"的重型兜底：对 4K 源那会直接 OOM，是用内存兜底掩盖读取层缺陷的懒政。若退避重试后仍失败，导出**直接报错**（让用户重试 / 检查 localTool），不静默转全内存。

   > **更新(2026-09-13 · 裁定 · 本条已改判为「不做」)**：`BoundedConcurrencySource` **本仓库不实现**（`docs/123` §二.10 **方案 A**）。
   > 理由：该兜底自述的根因是 **WebKit** 并发压力，而本文 C5 已自证本仓运行时是 **Blink(Chromium)** → **根因不适用于目标平台**；为不存在的场景预付成本违反铁律 5（不虚构），且会多出一条常驻维护面。
   > 做法：**先按浏览器原生并发直接读**；真复现 fetch 失败时，再从「提高并发上限 / 流式 / 临时落盘」三种**根因解**里选（本条自己也说正确解不是内存兜底）。
   > 失败形态不变：**明确报错**（本就该报错，不静默、不重试到"可能成功"）。

**规则 C5.1**：`needsCompositing` 是导出路径的**唯一判据**，UI 检查器明示当前走哪条（参考库设计：避免「加了个画中画就整条掉画质」悄悄发生）。
**规则 C5.2**：`export/mediaEngine.ts` 是导出管线对媒体引擎的**唯一封装层**，且必须**建立在已有 `base/utils/videoEngine.ts` 之上**（它已具备 `readVideoMetadata` / `processVideo` / `concatVideos` / `videoToGif` / `uploadResult`）。缺口（分组无损搬运、合成渲染、PCM 兜底）补进 `videoEngine.ts` 或在其之上的薄封装，**禁止新建平行 services**（同 `113` 风险「与 videoEngine 能力打架」）。

> **更新(2026-09-13 · 复杂度定位修正)**：`export/mediaEngine.ts` **不建**（已删）—— 它只有 1 种实现（纯转发 `videoEngine`），是**假接缝**（`docs/123` §二.7 P1 / 铁律 5：只有一种实现的接缝禁抽象）。
> 现行形态：缺口**直接补进 `base/utils/videoEngine.ts`**（`:176 readVideoMetadata` / `:206 processVideo` / `:312 concatVideos` / `:519 videoToGif` / `:597 uploadResult` 已有），导出管线在其之上薄组合，**不设中间封装层**。「禁止新建平行 services」继续有效。
**规则 C5.6（导出前信息常驻，而不是拦一次）**（2026-09-13 简化）：
① 走哪条路径（直通 / 合成重编码）② 工程参数（比例 / 帧率 / 音频出口 / 是否含音轨）③ 是否会有黑边 —— 这三件事**常驻在工具带上**
（导出按钮旁一行小字，放不下就 hover 展开），**点导出直接开始**，不弹预检窗。
> 只有**真的需要决策**时才拦一次：**存在断链片段**（C13）→ 弹「跳过这些片段继续导出 / 取消」。
> 依据：参考实现就是这么做的 —— 工具带上方一条常驻提示（「有 2 个片段分辨率不一致，无法无损直通，导出将归一到 1920×1080 合成（重编码）」），用户提前就知道，不需要被拦一次。明细可展开、可一键复制（同 C9.1）。

### 契约 C7 · 轨道状态闭环（lock/hide/mute 一致性）

**来源**：`track-state-behavior` 计划——锁定/隐藏/静音必须在时间轴、预览、属性编辑、导出**四处行为一致**，且不新增 schema 字段（状态已存在 `VideoEditorTrack.muted/locked/hidden`）。

**规则 C7.1（三条状态都要：锁定 · 隐藏 · 静音 · 独奏不要）**（2026-09-13 依用户圈定）

| 状态 | 字段 | 作用 | 视觉 |
| --- | --- | --- | --- |
| **锁定** | `locked` | 该轨片段拒绝删除 / 复制 / 分割 / 裁切 / 定格 / 拖动 | 锁图标转 accent 色 + 轨道加锁描边 |
| **隐藏** | `hidden` | 该轨不参与预览与导出渲染（走带照走，只是不画） | 眼睛图标转 accent 色（带斜线）+ 片段降饱和 |
| **静音** | `muted` | 视频轨 = **关掉内联原声**（C4.7 配套）· 音频轨 = 关配乐 | 喇叭图标转 accent 色（带斜线）+ 片段降饱和 |

> **明确不做：「独奏 Solo」** —— 用户 2026-09-13 圈定不要。
> 轨道状态**只存在 `VideoEditorTrack`**（`locked / hidden / muted`），**不新增 schema 字段**。

**规则 C7.2（禁止假按钮）**：三条状态都必须有**即时视觉反馈** + **真实作用**（导出里真的不出声 / 真的不渲染 / 真的拒绝编辑）。
**不得出现「点了但结果没变」的假按钮**（旧 mockup 舞台 3 的审计结论）。
**规则 C7.3（锁定授权收口在一处）**：删除 · 复制 · 分割 · 裁左 · 裁右 · 定格 · 拖动 —— **统一在一处判 `isTrackLocked / isClipLocked`**，禁止每个动作各写一遍。混合多选含锁定片段时，只处理未锁定的部分。

**规则 C7.4（轨道头 = 固定列图标网格，无文字）**（2026-09-13 依剪映定）
轨道头**不写中文标签**，改为**固定列位的图标网格**：`[类型图标] [锁] [眼] [喇叭]`，缺的列**留空占位**（保证跨轨列位对齐）。

- **状态靠颜色**：正常 = 白 / 次级灰；**开启（已锁定 / 已隐藏 / 已静音）= accent 色**（剪映用青色，我们用 `--accent`）。
- 类型图标：视频轨 = 方框内播放三角 · 音频轨 = 圆圈内音符（音频轨**没有"眼"这一列**，留空）。

> **收益两条**：① 省宽度——轨道头从 132px 收到 ~72px，宽度还给轨道；② 列位对齐后**扫一眼就能读出所有轨的全部状态**，不靠读字。

**规则 C7.5（轨道高度可调，缩略图 / 波形同步缩放）**（2026-09-13 依用户指定）
轨道行高可拖拽调整；**行高一变，片段里的缩略图胶片条与波形同步缩放**（不是拉伸变形，是按新高度重新切片 / 重绘）。
> 这意味着胶片条**不能是"固定像素的贴图"**：缩略图切片的尺寸必须**由行高派生**（`background-size` 按行高算，或按行高重新请求切片）。
> 波形同理：峰值的绘制高度按行高算，**不能预渲染成一张固定高度的图**。

### 契约 C8 · 预览与合成共用渲染路径（WYSIWYG）

**来源**：`videoCompositor.ts` 的 `renderFrameAt(context, canvas, tracks, time, resolve)`——
**预览与导出走同一条渲染函数**，多轨叠加/画中画/转场所见即所得。

**本仓库形态**：`export/composite.ts` 为**新建文件**，移植参考库 `videoCompositor.renderFrameAt`（本仓库 `videoEngine.ts` 目前只有 trim/concat/metadata，尚无帧合成器）；`Preview.tsx` 两种预览策略：
- **主轨**：原生 `<video>` 吃系统解码器（比逐帧驱动 canvas 稳，参考库 + 本仓库 `videoEngine` 共识）；
- **叠加层**：图片用 `<img>`、视频叠加用独立 `<video>`（URL 经 C3 解析），按 `playhead - timelineStart + sourceIn` 同步 `currentTime`；CSS transform 叠位置（首发不做全合成实时预览，全量合成只在导出时做——见 `113` 风险「多轨实时预览卡顿」）。

**规则 C8.1**：`computeDrawRect`（contain + transform 求绘制矩形）、`evaluateTransitionAlpha`、`findDissolveUnderlay`（交叠淡入底图）**预览导出共用同一份**，杜绝「预览对导出错」。
**规则 C8.2**：`renderFrameAt` 是 `async`（视频帧经 `VideoSampleSink.getSample`），调用方负责 `sample.close()` 与 `Input.dispose()`，避免帧泄漏。
**规则 C8.3（播放态与编辑互斥，剪映同款口径）**：**任何触达工程的编辑动作（拖片段 / 调长度 / 删除 / 加入素材）→ 先自动暂停，再执行。**
播放态是**只读态**，不存在「边播边改」。
> 不做成「播放中禁止点击」——那会变成「点了没反应」；**自动暂停**才是用户的预期。

**M1 走带的口径（2026-09-13 决定）**：M1 **不设监视器**。走带 = **播放头走 + 出声**，画面参照是**片段上的缩略图条**。
> 这条划定了 M1 的边界：**M1 是「装配与试听」，不是「看片」**。所有需要「看着画面下刀」的操作（帧级切点、贴图/字幕落位、转场审核）整个归 M2。

### 契约 C10 · 基座层的键盘归属（**不做新基建**）

**为什么要有这条**：基座是**常驻非模态层**，不能登记 `modalLayer`（登记一次画布快捷键全废、主入口「画布选中 → 入池」直接死掉）。
但完全不管键盘也不行——**画布已有的全局键会在剪辑态下误伤**。

**关键区分（本契约的全部要点）**：

| 键 | 算不算「给剪辑器加快捷键」 | 结论 |
| --- | --- | --- |
| 空格 / ←→ / S / I-O / Home-End / ⌘滚轮 / ⌘C / ⌘V | **是** | **M1 一律不绑，全部靠按钮**（用户更擅长按钮；剪映级舒适按钮 > 快捷键） |
| **⌘Z / ⌘⇧Z** | **否**——这是「画布不要在剪辑器里被静默误撤销」 | **必须让位**，顺带由基座接手（成本为零） |
| **Delete / Backspace** | **否**——这是「画布不要在剪辑器里被静默误删节点」 | **必须让位**，由基座接手（删选中片段） |

> **最要紧的一条**：在基座里拖错一个片段、按 ⌘Z，若没人处理，事件会漏到画布 → **撤掉的是画布上的节点操作**。
> 这与 `modalLayer.ts` 文件头记录的那起事故同源。所以 ⌘Z 的让位**与「剪辑器要不要快捷键」完全无关**，它是防误伤。
> Delete 同理：用户很可能刚从画布点选素材进来、画布上还留着选中节点，此时按 Delete 若漏给 React Flow → **删掉的是画布节点**。

**本仓库形态（零新基建）**：归属判据就是**激活位**（§0.1）——不需要焦点作用域，也不需要新订阅机制：

| 位置 | 改法 | 成本 |
| --- | --- | --- |
| `useCanvasShortcuts` 守卫（⌘Z / ⌘⇧Z 等） | 现为**查询式** `if (hasModalLayer()) return;` → 加一项「或 基座激活」 | 一行 |
| React Flow 的 `deleteKeyCode` | App 已订阅 `useAppSettings()`，故 `deleteKeyCode={modalLayerOpen || videoEditorOpen ? null : DELETE_KEY_CODE}` | 一行，**无需新订阅** |
| 基座自己接的键 | 只有 `Delete`/`Backspace`（删选中片段）与 `⌘Z`/`⌘⇧Z`（工程撤销/重做），且带 `isEditableTarget` 守卫（时间码输入框内不劫键） | 一个 keydown 处理 |

**规则 C10.1（红线）**：基座**不得**使用 `FullscreenShell` / `useFullscreenEditorKeys` / `registerLayer`。登记一次，画布快捷键即全废。
**规则 C10.2**：基座**不吃 Esc**。常驻层没有「退出」语义（§0.6），Esc 保持给输入框 / 下拉。
**规则 C10.3**：**键盘归属由激活位派生，不由焦点派生**——「基座展开 = 剪辑态」，这三个键就归剪辑器；折叠即全部还原。用户不需要先点进某个区域才能用 Delete。
**规则 C10.4（配置纪律）**：除 `Delete` / `⌘Z` / `⌘⇧Z` 外，基座**不得再绑任何键**。要加键先用按钮验证它真的高频；禁止先绑键、后补按钮（那会造出「没反应也没按钮」的隐形功能）。
**规则 C10.5**：折叠态**不持有任何键盘归属**（未激活，天然不吃键），画布快捷键完整恢复。
**规则 C10.6（交互基线）**：**按钮优先**——走带、分割、删除、吸附、缩放全部有按钮，且按钮要有舒适的热区与即时反馈（对齐剪映级手感）。**快捷键是锦上添花，不是可用性的前提。**

### 契约 C11 · 素材入轨与分轨（2026-09-13 重写：删掉「待加入区」；同日修订：入轨改为「点选即落轨」）

**来源**：用户口径「**点素材 → 它直接出现在时间轴上**」（2026-09-13 修订：入轨 = 在画布上点选素材节点，选中即落轨尾；不设节点按钮、不设拖拽）。

**为什么不设「待加入区」（2026-09-13 决策 · 净删除）**
最初方案照搬了 AI 助手的「待引用区」，但**这个类比在关键处不成立**：

| | AI 助手待引用区 | 剪辑器上轨 |
| --- | --- | --- |
| 终点的成本 | 发消息 = 调模型、花钱、**不可轻改** | 落轨 = **可撤销、零成本** |
| 因此需要「先攒再确认」吗 | 需要 | **不需要**（按错了 ⌘Z 就回去） |

池子带来的连带复杂度（现已全部删除）：池子两态 · 「加入即消费」· chip 这个 UI 概念 · `pool` 持久化（C2）· 幂等 ·
**入池触发点短路**（旧 C11.13 那条红线）· 框选批量入池的**顺序歧义**。

**本仓库形态：入轨只有一个入口 —— 在画布上点选素材节点，零中间站。**

| 唯一入口 | 行为 | 说明 |
| --- | --- | --- |
| **在画布上点选一个素材节点** | 该素材**立即追加到对应类型轨的轨尾** | 顺序 = 点选先后（C11.3）；**仅在基座激活（展开）时生效**（C11.5）；**不设节点按钮、不设拖拽** |

> **与参考实现的差异（2026-09-13 修订）**：他们用「节点上的『加入时间轴』按钮（点击贴尾 · 拖拽自选位置）」双通道；
> 本仓库**更简化**——**点选即入轨**，一个入口、零按钮、零拖拽。
> 依据：素材本来就长在画布上，**"在画布上选中它"本身就是最自然的"我要用它"表达**，再加一层按钮 / 拖拽是多余的中转。
> **连带净删除**：节点 hover 按钮、拖拽入轨，以及随之而来的「拖中显示落位时间码」「位置冲突滑入最近合法位」（C14.3 已同步收窄）。

**规则 C11.1（分轨唯一判据）**：`core/routeClip.ts` 的 `routeClipToTrack(kind)` —— 视频/图片 → 视频轨，音频 → 音频轨。UI 不得内联 `kind === 'audio' ? … : …`。
**规则 C11.2（一次入轨 = 一次可撤销操作）**：每次入轨进历史栈一次（C6.2）；入轨后**立即落轨、立即可见**，不需要用户再确认一步。
**规则 C11.3（顺序 = 入轨先后，红线）**：片段在轨上的先后**就是用户入轨的先后**（先点先进）；主轨磁吸压实只合并空隙，**不改变相对顺序**。
**禁止**任何"按名称 / 按时长 / 按生成时间"的自动排序 —— 顺序是用户的编排结果，不是可推导的属性。
**规则 C11.4（"同一素材用两次" = 再点一次那个节点，红线）**：不需要任何特殊机制 —— **点选是显式动作，点几次就上几条**。
> **（2026-09-13 修订）** 旧稿这里写"短路问题存在的前提是「入池由选中派生驱动」，现在这个前提没有了"——**该判断已随入轨方式改回"选中驱动"而作废**。
> 现在的入轨就是由「在画布上点选」驱动，因此**必须守住"不设幂等 / 不去重 / 不设已入轨态"**：点选一次 = 入轨一次；再点一次（先取消选中，再点它）= 再得一条。
> 另一条路是**右键 → 复制片段**（C15.2），它的价值不在"重复入轨"，而在**复用一段已经修剪过的物料**（"再点一次"只会拿到完整素材）。
**规则 C11.5（激活门，红线）**：入轨**只在基座展开（激活）时生效** —— 折叠态下**在画布上点选素材节点不产生任何动作**（不入轨、不入池、不留痕）。
> 见 §0.1 红线：折叠 = 未激活 = 不接受任何素材。**点选是唯一入口，所以这道激活门就是「禁止静默副作用」的最终防线** ——
> 少了它，折叠态下用户在画布上随便点两下，就会往后台塞进片段而毫无反馈。
**规则 C11.6（基座只到粗档）**：入轨不承载「入点 / 出点」这类精细参数（那是工作台的事）；落轨用源素材整段 + 默认时长（图片素材用 `defaultImageDuration`）。
**规则 C11.7（M1 走带必须真出声）**：M1 的走带可以没有大预览，但**必须能播放并出声** —— 否则「调音频长度」是纯盲操作。
> 走查结论（§七 F4）：这是 M1 唯一一处「画面可以不看、但声音必须能听」的地方。
**规则 C11.7b（音频片段 = 真实波形，M1 必做）**（2026-09-13 **反转**）
音频片段画 **真实波形**（从音频解码后的峰值数组绘制），配深蓝底 + 顶部名字条。
**波形是音频在时间轴上唯一的信息载体** —— 粗排也靠它判断"这段有没有声音、说话从哪里开始、拖到哪了"。
> **反转原因**：上一稿把波形降为 P1、改用"秒格"，理由是"粗排不需要精听"。**判断错了**：
> ① 波形不是"精听"，它同时承担**定位**（拖到哪了）与**有无内容**（哪里是静音）两种粗排刚需；
> ② 剪映把波形做成了整个音频轨的视觉主体 —— 这是最不该省的东西。
> **实现要点**：解码 → 降采样成**固定列数的峰值数组** → 按行高（C7.5）绘制。峰值数组可缓存，**不要每帧重算**。
> **禁止**用固定图案冒充波形（会被读成真实音量，属于撒谎）—— 要做就做真的。
**规则 C11.8（多选只服务片段操作）**：片段支持多选 —— `Shift 点选` 与**框选空白处**，用于**批量删除**等片段操作。
> **框选 / `Shift` 多选不参与入轨**（入轨只有 C11 的**单选点选**）—— 这顺带消掉了旧稿"框选批量的顺序歧义"。
> 红线：基座内的框选**不得**被画布的 `panOnDrag` 抢走 —— `nodrag` 只挡拖拽起点，框选是另一套鼠标事件，要单独隔离。
**规则 C11.9（不设最少片段数）**：剪辑器**不限制片段数量**，一个片段也能剪（把长片裁短是合理诉求）。
> 这修正 `113` §五 的口诀：更准确的表述是「**单素材的转码 / 抽帧 / GIF 走节点；涉及时间轴编排的（哪怕只有一个片段）走剪辑器**」。
**规则 C11.10（胶片条的正确实现，性能红线）**：片段缩略图**禁止"每个片段各挂一个真 `<video>`"**。
> 参考实现的实测坑（其时间轴性能审计发现 #2）：每个 video clip 挂 `<video preload="metadata">` 拉首帧，10~30 个片段就出现解码线程争用、滚动卡顿、内存上涨；且 `<img loading="lazy">` 对「横向 overflow 容器里 absolute 定位的离屏片段」基本不触发。
> 正确做法（也是他们改后的方案）：**一次抽帧拼成一条横向胶片 jpg**，落盘 + 会话内缓存，片段用 `background` 按 `frameCount / offset` 映射显示 —— **裁剪即所见**。
> 附带一条坑：缩略图用 `object-cover` 会把关键内容裁掉（他们的走查记录「缩略图一眼认不出是哪一镜」）；胶片条用等高切片、不做 cover 裁切。
**规则 C11.10b（片段名条独立在片段顶部）**（2026-09-13 依剪映定）
素材名**不压在缩略图上**，而是**片段顶部一条独立的窄条**，名字写在条里：

- **视频片段** = 顶部名字条（accent 系底）+ 缩略图胶片条 + 底部细边
- **音频片段** = 顶部名字条（深蓝底）+ 波形区（C11.7b）
- **名字用素材名，不带序号**（`开场镜头_v3.mp4`，不是 `1. 开场镜头_v3.mp4`）
  > 理由：分割之后序号会变成 `1. 1. 1.`，反而误导。**顺序感由片段在轨上的位置本身表达**，不需要数字。
**规则 C11.10c（片段高度随轨道行高同步，红线）**：名条高度固定（约 16px），**胶片条 / 波形占剩余高度并随之缩放**（C7.5）。
> 缩略图切片与波形峰值都**由行高派生**，禁止写死像素。

> **明确不做（YAGNI）· 不抄「一键全部加入」**：参考实现有「有 N 个镜头可拼成初稿 → 一键拼成初稿」的批量入口，我们**不抄** ——
> 逐个点没有负担，且**一键会抹掉"入轨顺序的显式性"**（顺序本身就是用户在编排）。

### 契约 C12 · 工程参数（尺寸 / 帧率 / 音频）—— 导出的唯一基准

**为什么必须有**：素材从画布随手抓 → **横竖屏混剪、24/30/60fps 混剪必然发生**。没有工程参数，「合成归一」就没有目标值，导出结果不可预期。

**本仓库形态**：工程记录里存一组 `settings`（**工程参数**，随工程持久化；不是 UI 偏好）：

| 参数 | 默认 | 来源规则 | 可见性 |
| --- | --- | --- | --- |
| 比例（画布尺寸） | 首个入轨**视频/图片**片段的尺寸 | 首个入轨片段决定初值；**之后用户可随时改**（见 C12.2） | 工具带常显（`16:9 · 30fps ▾`） |
| 帧率 | 30 | 首个入轨**视频**片段的帧率（图片不参与）；混帧率统一到工程帧率 | 与尺寸同一处 |
| 音频采样率 / 码率 | 48 kHz / AAC 128 kbps | 固定（M1 不暴露） | 导出对话框显示 |

**规则 C12.1（红线）**：工程参数是**导出的唯一基准**。片段一律按「contain 到工程尺寸」归一；
`needsCompositing(tracks)` 的判据**必须包含「存在片段尺寸 ≠ 工程尺寸」**——否则会出现「尺寸不一致却走了直通」。
**规则 C12.2（可随时改；黑边归 M2）**（2026-09-13 修正）：比例 / 帧率**随时可改** —— 空工程时显示「跟随首个片段」，有片段后用户随时可改并固定。
改比例**会产生黑边**（片段按 contain 归一）。**黑边由 M2 解决**：M2 的画面缩放 / 填充（fit 模式：拉伸 / 裁满）能把黑边吃掉。
> **M1 只做"如实显示"**：导出预检里说明最终比例与"是否会有黑边"，**不假装能消掉**，也不因此禁止用户改。
**规则 C12.3（改了不重排）**：改比例 / 帧率**不移动任何片段的时间位置**，只影响渲染归一与导出参数 —— 它是「画框」，不是「内容」。
**规则 C12.4（不碰数据模型）**：帧率只影响导出与吸附档位，**不改变数据模型的时间戳单位**（§0.5：数据模型只有一套）。

### 契约 C13 · 素材断链与引用完整性

**为什么必须有**：工程的素材来自画布节点与本机落盘，两者都会消失（节点被删、文件被清）。

**判定（两个来源，严重度不同）**：

| 来源 | 判定 | 严重度 |
| --- | --- | --- |
| 源节点被删 | 工程记录的 `nodeId` 在画布上已不存在 | **提示级**——节点删了，文件可能还在（见 C13.3） |
| 资源不可读 | `resolveClipUrl(clip)` 为空，或探测 / 读取失败 | **致命级**——渲染与导出真的拿不到数据 |

**表现（已定）**：

- 时间轴上的该片段**变红**（`--danger` 描边 + 红底 + 「素材已失效」角标）；
- 片段**仍留在轨上，不清除**（用户可能只是临时离线、或把节点挪走了）；
- 导出前**预检**列出所有断链片段，让用户选择「跳过这些片段继续导出」或「取消」；
- 跳过时**如实告知跳过了哪个片段**，不静默产黑帧、不静默改时长——同 C4.3 对音频的处理原则。

**规则 C13.1（红线 · 引用登记）**：工程记录里的每个 `sourceUrl` / `assetId` **必须被文件生命周期层视为「被引用」**。
> 否则单一引用感知 GC（`13-文件生命周期`）或素材库清理（`122`）会把素材清掉 → 剪辑器凭空断链，且用户无从理解。
> 本契约只登记**需求**，实现归属那两层；但两侧都必须有「剪辑器工程引用」这个来源。
**规则 C13.2**：断链**只影响渲染与导出**，不动工程数据（不自动删片段、不自动改时长）——保证用户修好素材后自动恢复。
**规则 C13.3（源节点被删 = 只标红，不自动删、也不加专门动作）**：节点消失只标红提示；**清理就用普通删除片段**（C15）—— 不另设「清理失效片段」这个专门动作（不留第二入口）。只有资源真的读不到才红，避免误报（节点删了但 `/files/` 还在是常态）。
> **与参考实现（Nomi）的差异 —— 需要留意**：他们选择「删画布节点 → 单向通知时间轴，移除全部引用该节点的 clip」，理由是 clip 的 url 是**创建时冻结的快照**，留着重导会「渲染已删节点的旧帧」。
> 我们**不自动删**：导出预检（C5.6）已经挡住「静默产坏片」这个真正的风险，而自动删会**静默改用户数据**；且画布删节点常常只是整理画布。
> 若上线后用户实际更想要"删了就一起删"，再改成自动（届时必须保留撤销）。
**规则 C13.4（节点重生成 → 回填新产物，不是断链）**：源节点仍在、但产物被**重新生成**（URL 变了）时，引用它的所有片段**自动回填新产物**：`startFrame` 不动、`trim` 越界夹取、URL 换新。
> 这是 C13 的**另一半**，也是本稿初版**漏掉的一向**（参考实现把它与"删除对账"对称实现）。
> 只做"标红"不做"回填"，会出现最坏的一种情况：**用户重生成了一张更好的图，时间轴上却还播着旧的**——而且它不红（旧 URL 仍可读），是静默不一致。
**规则 C13.5（对账不得影响画布操作，红线）**：节点 → 工程的同步必须是**单向通知 + no-op 安全**：无引用时早退、异常不得冒泡、**绝不允许反过来影响画布删除本身**。
> 参考实现的纪律值得照抄：跨 store 只在 action 运行时取 `getState()`（live binding），不在模块初始化期触碰，避免 `workbenchStore ↔ canvasStore ↔ canvasActions` 循环初始化。
**规则 C13.6（对账后必须收口派生状态）**：片段被移除 / 替换后，**同时收口**：① 选区（不残留指向已删片段的幽灵选中）；② 播放（停止播放）；③ **历史栈不记录对账**（它不是用户操作，不该污染撤销栈）。

### 契约 C14 · 无变化不落盘 / id 唯一性 / 不静默失败（三条来自参考实现的真实事故）

> 来源：`~/Downloads/Nomi-main` 调研（2026-09-13）。三条都在他们有测试或事故记录兜底，属"必然会被踩"的类别。

**规则 C14.1（无变化不落盘）**：所有工程改写必须先判「是否真的变了」——**引用未变就原样返回同一个 state，不自增持久化修订号**。
> 参考实现：`persistRevision` 只在 `changed` 时 +1，且 `if (nextTimeline === state.timeline) return state`，并有专门测试断言「删的节点在时间轴上没有片段时 → 不动时间轴、修订号不自增」。
> 为什么重要：自动保存由「修订号」驱动 → **任何"空转改写"都会变成一次落盘 + 一次跨窗口广播**。我们画布侧已有同类教训（`106` 的"无变化不 setState"）。

**规则 C14.2（id 唯一性，红线）**：**禁止用"每次加载归零的自增序列"生成持久化 id**（`text-1` / `clip-1`…）。
> 参考实现的真实事故：字幕 id 用归零自增序列 → 新会话又生成 `text-1`，与落盘旧片段**撞 id** → 编辑一条把另一条一起改了（React key 也重复）；修法是 `crypto.randomUUID()` + 加载时对重复 id 重铸。
> 落在我们身上：`clip` / `track` 的 id 一律走既有 `generateId`（`base/core/idGen.ts`），并在工程加载时做一次重复检测。

**规则 C14.3（不静默失败）**：轨上片段的**移动类操作永远不能"静默什么都没发生"**——期望位被占就**滑入最近合法空位**，类型不符就**拒绝并说明期望**。
> 参考实现原文：「与移动同一碰撞模型：期望位被占则滑入最近合法空位，**插入永不静默失败**」；拖错轨时返回 `{ status:'reject', expectedTrack }` 让 UI 提示。
> 细化到我们：**"拒绝"只用于语义冲突（音频片段拖到视频轨，C4.6），位置冲突一律"滑入"**——后者若也拒绝，用户只会觉得"拖不动"。
> **（2026-09-13 修订）** 画布 → 轨道的「拖入 / 插入」入口已删（C11 改为**点选即落轨尾**，不存在"位置被占"这一情景），本规则现只覆盖**轨上片段之间的移动**。

### 契约 C15 · 片段操作面（以播放头为轴的编辑动作 · 删除二态 · 复制 · 右键集）

**一、以播放头为轴的三个动作**（2026-09-13 依用户圈定新增 · 全部进 M1 工具带）

| 动作 | 语义 | 结果 |
| --- | --- | --- |
| **分割** | 在播放头处切开 | 一段变两段，**总长不变** |
| **裁掉左侧** | 保留播放头**右边**的部分 | 片段入点前移到播放头；**总长变短** |
| **裁掉右侧** | 保留播放头**左边**的部分 | 片段出点前移到播放头；**总长变短** |

> **共同前提**：播放头必须**压在某个片段上**；否则三个按钮整体**置灰** + tooltip「把播放头移到片段上」（工具带表的"禁用 = 置灰，不是隐藏"）。
> **为什么"裁"要单独两个按钮**：粗排里最高频的动作就是"砍头去尾"。没有它们，用户得走「分割 → 选中那段 → 删除 → 闭合空隙」四步。
> **边界**：裁到长度为 0（播放头正好在片段头 / 尾）→ **置灰并提示**，**不静默把整段删掉**。
> **跨轨**：三个动作都对**播放头下的全部未锁定片段**生效（多轨同时切），这是剪辑器的惯例；锁定的轨跳过（C7.3）。

**二、定格**（2026-09-13 依用户圈定新增 · 进 M1）

| 动作 | 语义 | 结果 |
| --- | --- | --- |
| **定格** | 抽出**播放头所在的那一帧**，插成一段静止片段 | 原片段在播放头处被切开，中间插入 `默认 3s` 的静止片段 |

> 产物是**图片片段**（复用 `renderFrameAt` 抽帧 → 落盘 → `ImageClip`），因此**不需要为它新增 clip 类型**。
> 抽帧是**异步**的（C8.2）→ 期间按钮显示"处理中"；失败**如实报错**（C9.1），**不静默跳过**。

**三、删除（两种位置语义）**

| 语义 | 行为 | 备注 |
| --- | --- | --- |
| **留洞删除**（lift） | 片段移除，**位置留空**，后续片段不动 | 默认；配合「闭合空隙」补洞 —— **更新(2026-09-13)**：「闭合空隙」**不另立原语**，其**语义入口就是 `relayoutSequential`**（`docs/123` §一.4 自述；另立 `closeGaps` 别名＝两名指一物，已否决） |
| **波纹删除**（ripple） | 片段移除，**后续片段前移填空** | 影响范围更大 → 必须可撤销 |

**入口（M1 全部要有）**：

| # | 入口 | 映射 |
| --- | --- | --- |
| 1 | 工具带「删除 ▾」 | 主项 = **留洞**；下拉内 = **波纹**（C10.6 按钮优先） |
| 2 | 键盘 `Delete` / `Backspace` | **只绑留洞**；波纹**不绑键**（防 ⇧ 误按导致整条后移） |
| 3 | **片段右键菜单** | 两项都在，且写明差异 |
| 4 | 多选后批量（C11.8） | 按同一语义对多选集合执行 |

**另一种"删除类"动作，不是删片段，不许混进同一菜单**：

| 动作 | 对象 | 入口 |
| --- | --- | --- |
| 清空工程 | 整份工程（§0.6 破坏性动作） | 显式动作 + 二次确认 |

> **已删除两种**（2026-09-13 简化）：①「移出 chip」—— 待加入区整个删了（C11）；②「清理失效片段」—— 断链片段用**普通删除**处理，不留第二入口。

**M1 的右键集（就此定，不做更多）**：

| 目标 | 菜单项 |
| --- | --- |
| **片段** | 分割（播放头处）· 裁掉左侧 · 裁掉右侧 · 定格 · —— · 复制片段 · —— · 删除（留洞）· 波纹删除（后续前移） |
| **轨道头** | 锁定 · 隐藏 · 静音（与图标按钮同源） |
| **轨道空白** | **M1 不给右键菜单** |

> **分割 / 裁左 / 裁右：工具带 + 右键，两处同源**（2026-09-13 **修正**）：上一轮把分割移出工具带是**判断错误** ——
> 它的语义是**在播放头处分割**，播放头是**全局位置、与选中无关**，而且用户执行它时手正在走带那边（不在片段上）。
> 反证：剪映把这几个放在工具带最左的编辑工具簇里（`▐[` `╎[` `]╎`）。C15.1 要求两处调用同一个动作函数。

**规则 C15.1（右键与按钮同源，红线）**：右键菜单项**必须调用与工具带按钮 / 轨道头图标同一个动作函数**，禁止另写一份——否则很快出现"按钮能删、右键删不动"这类不一致。
**规则 C15.2（复制片段 = 复用「已修剪的片段」）**：复制在**轨上**进行（副本紧随其后，可再拖走），进历史栈一次。
> 它的价值是：**复用一段已经修剪 / 已调好位置的物料**——重新从画布选一次只会拿到完整素材（干净入出点），而复制保留 trim 与当前时长。
**规则 C15.3（破坏性动作的可见性）**：删除 · 波纹删除 · 裁左 · 裁右 · 定格 · 清空工程 —— 执行后**必须可撤销**；波纹删除与"裁"还要在**执行前**让用户知道"它会动到总长"（hover 预览或执行后 toast 说明移动了几段 / 缩短了多少）。

## 六、红线（落地即检查）

1. **存储键禁止裸字符串**：必须 `STORAGE_KEYS` 登记，`contentStore.checkRegistered` 在 dev 下 throw（`113` 红线 2）。
2. **事件名禁止裸字符串**：若编辑器与画布需通信（如「导出为新节点」），先登记 `EVENTS`（`113` 红线 3）。
3. **唯一落盘通道**：`localTool /files/`；剪辑器不得自建第二通道（`113` 红线 4）。
4. **单一媒体引擎**：`videoEngine`（mediabunny）是唯一实现，缺口补在它身上。
5. **画布与基座交互区必须 `nodrag`**，否则拖动被画布节点吞掉。
6. **基座不得走 `FullscreenShell` / 不得登记 `modalLayer`**（C10.1）：登记一次，画布快捷键全废，「画布选中 → 入池」这条主入口直接死掉。
   **M2 工作台则相反——必须走 `FullscreenShell`**（自动登记 modalLayer），禁止自挂 `window.addEventListener` 抢快捷键（参考 `115` 第三轮「全屏模态层未挡住 React Flow 删除键」事故）。
7. **键盘归属由激活位派生**（C10）：基座激活时只有 `Delete` / `⌘Z` / `⌘⇧Z` 归剪辑器（防画布被误删 / 误撤销），其余画布照常；**除这三个键外基座不得再绑任何键**（C10.4）。
8. **数据模型只有一套**（§0.5）：精度分档只发生在 UI 层，`core/types.ts` 不得为基座造第二套简化模型。
9. **折叠态不接收素材**（§0.1 红线 / C11.5）：折叠 = 未激活 —— **在画布上点选素材节点不产生任何动作**（不入轨）。
10. **入轨 = 在画布上点选素材节点**（C11）：点选即追加到对应轨尾，零中间站；**不设节点按钮、不设拖拽**。
11. **带声音的视频不拆轨**（C4.7）：音轨随视频片段内联，不自动拆到音频轨。
12. **不手改 `dist/`**；改完 `npm run build` 出包。
13. 每 Gate 收尾跑：`type-check → test:smoke → test:unit → build`（较大改动加 `check:health`）。
14. **工程参数是导出唯一基准**（C12.1）：`needsCompositing` 判据必须包含「存在片段尺寸 ≠ 工程尺寸」。
15. **工程记录禁止内联 base64**（C2.5）：只存元数据与 URL。
16. **工程引用必须计入文件生命周期**（C13.1）：否则 GC 会把素材清掉，剪辑器凭空断链，用户无从理解。
17. **id 禁止用"归零自增序列"生成**（C14.2）：必须 `generateId`，加载时对重复 id 重铸。参考实现为此出过「编辑一条字幕、另一条也被改了」的事故。
18. **放置类操作不得静默失败**（C14.3）：位置冲突 → 滑入最近合法位；类型冲突 → 拒绝并说明期望。
19. **右键集与工具带同源**（C15.1）：右键菜单项必须调用同一个动作函数，禁止另写一份。
20. **键盘删除只绑留洞**（C15）：波纹删除必须走按钮 / 右键，防 ⇧ 误按让后面整条前移。
21. **入轨顺序 = 用户入轨先后**（C11.3）：禁止任何自动排序；主轨磁吸只合空隙、不改相对顺序。
22. **入轨只有点选一个入口**（C11）：在画布上点选素材节点 → 追加到对应轨尾。**不设中间站 / 缓冲队列**；**框选 / 多选不参与入轨**（防顺序歧义）；**不设幂等 / 去重**（再点一次即再得一条，C11.4）。
23. **音频轨必须画真实波形**（C11.7b）：波形是音频在时间轴上唯一的信息载体，M1 必做；**禁止用固定图案冒充波形**。
24. **三条轨道状态都要有**（C7.1）：锁定 · 隐藏 · 静音（两轨都给）；**独奏不做**。少了静音，C4.7 的内联音轨就是不可控的。
25. **轨道头无文字，只留固定列图标网格**（C7.4）；**状态靠颜色**（accent = 已开启）。
26. **轨道行高可调，缩略图 / 波形由行高派生**（C7.5 / C11.10c）：禁止写死像素。

| F13 | 把已在轨的源节点**重新生成**一次（换了产物 URL） | 时间轴上该片段**自动换成新产物**，位置不变、trim 夹取，且**不标红** | 节点重生成 = 回填，不是断链（C13.4）；只标红不回填会静默播旧的 |

| F15 | 依次入轨 A → B → C 三个素材 | 轨上顺序即 A → B → C（先点先进），主轨磁吸只合空隙、不改相对顺序 | 入轨顺序 = 用户入轨先后（C11.3）；**没有**任何"一键全部加入"或自动排序 |

**架构层验收（人工）**：

- 基座展开时**画布仍可用**：能点选节点、能拖节点、`Q/W/E` 仍生效（证明没登记 modalLayer，C10.1）；
- 基座展开时：选中一个片段按 `Delete` → **删的是片段，不是画布节点**；按 `⌘Z` → **撤的是剪辑，不是画布**；折叠后两者完整还原给画布（C10）；
- 改一个片段变换 → 只有 `timelineOps` 产新数组、历史栈 +1（C1/C6）；
- 锁定轨道 → 时间轴 / 预览 / 检查器 / 导出四处一致拒绝（C7）；
- 导出中取消 → 真中断且无残留文件（C5.4）；
- 刷新重开 → 工程从 contentStore 恢复（C2）。

**债务总览原则**：
- **D1/D2/D11 是同一笔债的三个面**——"依赖 Chromium(Blink) 内核的 `AudioEncoder`、不为不触发的路径过度设计"。它现在的收益是零包体增量、实现简单；代价是一旦支持范围扩大（非 Chromium 内核）就必须补编码器（见 D1/D2/D11）。本文已用"未来可选扩展"把还债路径留好，避免到时候推倒重来。
- **D4/D5/D8 是"依赖外部库 / 外部服务"的普遍债**，统一靠**适配层 + 契约测试**兜底，不侵入业务。

- **D12–D16 是形态定稿与 2026-09-13 决策新长出来的债**：D12 已结清（键盘基建作废）、D13 已大幅缩小（折叠 = 未激活）；剩下的是「工程参数 / 断链 / 并发 / schema」四类，统一靠 **`schemaVersion` 守卫 + 导出预检 + 复用 `118` 的 CAS** 兜底。
