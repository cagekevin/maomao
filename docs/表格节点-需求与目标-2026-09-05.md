## 一、一句话需求（已过时）

> 一个**可编辑的表格节点**：把外部表格**粘贴进来原样保留行列**，能**自由编辑**，选中某行时把它（**文字** 与 **图片**）**喂给下游消费**。

分镜规模小：**一个剧本 20~40 行**（非几千行），所以**不需要虚拟滚动/性能优化**，普通渲染足够快。性能不是约束，**编辑的顺手程度**才是。

---

## 二、核心诉求与决策要点

| # | 诉求 | 关键结论 |
|---|------|---------|
| 1 | **粘贴外部表格原样进来** | 粘贴进来是什么列就是什么列，**不预设字段**（不要写死"镜头号/景别/台词"模板）。 |
| 2 | **能编辑** | 不能只读。要能改格、增删行、调顺序（分镜最常改顺序）。 |
| 3 | **图片不是必备，但要能"选图/引用图"喂下游** | 粘贴**全文字、不带图**。图片是后续**手动**加到**图片列**的（列类型化：把某列标成 image）。选图入口 = **点图片列单元格**（弹画布/素材图，选中存引用），**不用 @**。 |
| 4 | **每行输出给下游** | 每行一个明确可见的输出端口。下游连上某行端口，拿 `该行文字(文本列) + 该行图片(图片列)` 两样，**文字图片天然分流、一起给**。 |
| 5 | **轻量、易编辑** | 相比剧本盒子（重：三步引擎 + AI 生成 + 多端口），表格节点应轻：只做"数据表 + 行编辑 + 每行输出"。 |
| 6 | **全局定义（整表共享上下文）** | **一段文字、不分块不放图**，放**设置按钮**里编辑，不占表格行；任意行输出时并入该行内容。 |
| 7 | **画布角色** | **纯上游产出节点，只连下游、不连上游**（不需 input，只把行+全局喂下游）。 |
| 8 | **单行 AI 优化** | 行内容打包 JSON 交 AI → AI **只改文字** → JSON 回填该行文字；**图只读参考**（发出去给 AI 看，不带回、不改）。 |

## 三、产品形态构想

### 3.1 数据形态：列类型化二维表（最终模型，2026-09-05）✅

> **用户决策：粘贴进来**全**是纯文字，没有图片**。图片是后续**手动**加到少数"图片列"的。图片与文本在结构上**分层**（文本是格内字符串，图片是"图片列"单元格的引用），不混在同一格。

```
data.columns = [ { key, name, kind: 'text' | 'image' }, ... ]   // 列定义；kind 默认 text，可手动改成 image
data.rows    = [ { id, cells: [v1, v2, ...] }, ... ]             // 文本列 cells 存字符串；图片列 cells 存图引用
data.activeRowId  // （供将来"选中某行"语义用；现已改为每行独立端口，见 §3.3）
```

- **列名、列数、列内容**全来自粘贴进来的外部表格；列类型（kind）**默认全 text**，用户后续可把某一列标记成 image。
- **列类型化 ≠ 预设分镜模板**：列名/列数仍全自由（由粘贴决定），`kind` 只是列的附加类型属性。用户想在某列放图，才把该列标成 image。
- 文本列单元格 = 纯字符串；图片列单元格 = **图片引用**（点该格弹选择 → 存 `{id,url,label}` → 格内显示缩略图 + 替换/清空）。图片列才渲染重控件，文本列极轻。

### 3.1b 粘贴走"专门入口"（决策，2026-09-05）✅

> **决策：粘贴不是一个常用功能，在表格节点内做一个显式"粘贴入口"，用户点开入口后再粘贴。**
> 好处：① 安全——不抢画布全局 `paste` 事件，不跟现有"画布级粘贴压纯文本/建节点"冲突；② 只在用户主动进入粘贴态时才拦截剪贴板，平时表格照常编辑。

- 形态设想：表格节点空态或工具栏一个"粘贴表格"按钮/占位区 → 点击后进入"等待粘贴"态（内部焦点 + 拦截该容器 `paste`）→ 用户 `Ctrl/Cmd+V` 把外部表格粘进来 → 解析成 `columns + rows` → 退出粘贴态进入正常编辑。
- 解析只读 `text/plain` 的 Tab/换行（TSV）与 `text/html` 的 `<table>`（保留行列结构），**不复用**会压平 Tab 的 `sanitizePastedText`（见 §4.1 冲突）。
- 可追加选项：入口也支持**从文件粘贴/导入**（如拖入 `.csv`），非必需。
- 粘贴后的列 kind 默认全 text（用户自己把需要的列标成 image）。

### 3.2 编辑：增删行/格 & 把列标成"图片列"

- **每行 `id`** 用于端口/增删/排序。
- **编辑 = 点哪格改哪格**：文本列是原生输入框/textarea；图片列单元格是图片位。
- **行操作**：加行/删行/上移/下移/复制（分镜最常调顺序）。
- **列操作**：改列名；把某列标记为 image（该列变图片列）；列级增删（可选，够用再加）。
- **把列标成图片列的入口**：列头菜单/悬停一个"设为图片列"动作（具体 UI 做时定）。一旦某列是 image，该列单元格不再当文本输入，而是图片引用位。
- **选图来源（点选，非 @ 弹层）**：点图片列单元格 → 弹图片选择（画布节点图 / 素材库，来源待 §五 定）→ 选中存引用。**不用 @**（@ 适合文本流夹带；结构化图片列用点选/按钮更清晰）。
- **为什么用引用不是存副本**：图来自画布其它节点/素材，原节点更新表格也跟着新；表格 data 只存小引用，轻。

### 3.3 每行一个明确的可见输出端口（决策，2026-09-05）✅

> **决策：表格节点每一行都应有一个自己的输出端口，且是「明确可见」的**（不是剧本盒那种隐藏端口/锚点），用户能看到这一行有个口能拉出去连。用户原话："每一行都应该有个输出端口"、"剧本盒是隐藏端口，我们要一个明确的端口，跟它不一样。"
> 澄清：剧本盒的每分镜口是**样式隐藏、只作锚点、连线视觉从节点右侧整体出**；表格要的是**每行行内右侧一个真实可见的小圆点口**，跟着这一行走。

- **形态**：每一行在**它自己那行的右侧**内嵌一个**可见的 source 口**（`row-${rowId}`）。用户看到第 N 行右侧有个口 → 从它拖出去连下游。端口**跟随该行**（行随内容撑开，口就贴在哪行高度上），天然对齐。
  - 参考先例：**GridSplitNode 的 `cell-${i}` 口**（在内容区内每个 cell 卡片渲染可见小圆点 `<Handle>`，`!w-1.5 !h-1.5 !bg-blue-500 !rounded-full`，hover 才现/常显由样式决定）——这是"内容区内、每子项一个可见明确端口"的现成形态，比剧本盒隐藏口更贴近需求。
  - 也参考 `CustomHandle`（可见环样式，但它是按 NodeShell 外框定位的单个口）；表格行多且高度动态，更适合**行内嵌 Handle**（同 GridSplit），不是外框 CustomHandle。
- **产出语义**：下游连某一行端口，就从表格里拿**那一行**的输出（该行所有文本列文字 + 该行所有图片列里的图）。多行可分别连到不同下游（生图/文本），互不干扰。
- **接入点**：`NODE_OUTPUTS` 加声明，按 sourceHandle 反查对应行 → 输出该行文字/图（复用剧本盒"按端口反查分镜 → collectAssets"的解析范式；id 成对 `rowHandleId`/`parseRowHandle` 照抄 contracts 的 `shotHandleId`/`parseShotHandle` 写法，前缀 `row-`）。
- ✅ **输出内容已定（2026-09-05）**：**每行一个端口，下游连上就「一起」拿该行全部文本列文字 + 该行图片列里的图**，不拆文字口/图口。文字走 texts 通道、图走 images 通道，同时给下游。用户原话："肯定是一起输给下游，难道还要分开吗？肯定不用分开。"

### 3.4 节点尺寸自适应（高度 + 宽度）

> **决策：表格节点宽高都要自适应内容**，学剧本盒子的自适应。用户原话："宽高肯定需要自适应，学剧本盒子的高度自适应，还要再加个宽度也自适应。"
> ✅ 剧本盒现成机制 `useContentHeightSync` **已支持高度 + 宽度同步**（传 `syncWidth: true`），表格节点直接复用它，无需新造。

- **机制**（见 §4.8）：`useContentHeightSync(contentRef, id, { minHeight, fallbackWidth, syncWidth: true, wrapperRef })` 监听内容尺寸 → rAF 写回 `node.height`（+ `node.width`）→ 外框贴合内容，无限画布不滚动不溢出。
- **要点**：去掉固定 height/width（只留 minHeight/minWidth）；`wrapperRef` 传 NodeShell 根 div（含标题栏），否则写回偏矮。

### 3.5 全局定义（整表共享上下文）→ 放"设置按钮"里（决策，2026-09-05）✅

> **用户决策：表格节点有一个"全局定义"——整表共享的一段上下文，会固定合并进下面所有行的输出。** 例如某镜头行被连到下游，其输出 = 该行自身内容 + 这个全局定义。
> **形态**：全局定义**不放表格行里**（否则破坏表格整齐/第一行永远是全局不好看），而是放在节点**设置按钮（齿轮）**里编辑，作为独立配置。参考剧本盒的 GearSettings 弹窗。
> 用户原话："第一行永远是全局，可能只有一行，设计不好看，可以放到设置按钮里写。"

- 表格主体 = 纯数据行（每行一个镜头），干净整齐。
- **全局定义 = 一段文字（无图、不分块）**：经设置弹窗编辑一段全局文本（如整体风格/主角外观等），存 `data.global`。用户原话："它只有一个全局定义，里面不需要图，只是一段文字而已。"
- **输出合并规则**：任意数据行被连到下游时，产出 = **该行自身内容 + 全局定义**（全局文本并入该行，作共享上下文。合并的具体位置/结构实现时定，但形态就是"一段文本并入"，不拆块不放图）。
- **为何这样设计**：分镜策划里每行的提示词都需要共享"整体风格/主角外观"等上下文，重复填在每行太累且易不一致；提为全局定义，一处维护、自动并入每行输出。

### 3.6 画布角色：纯上游产出节点，不连上游（决策，2026-09-05）✅

> **用户决策：表格节点只需要连下游（作为数据源被下游消费），不需要连上游**。用户原话："表格不需要连上游，连上游没用，只需要连下游。"
> 含义：表格是**纯产出节点**（source），不做消费端，不接 input handle。它不能从别处接收图/文字，只把行+全局喂给下游。实现时连上游的复杂度（`useConnectedInputs` 消费、input handle）直接不做。

### 3.7 单行 AI 优化：行 ↔ JSON 双向（决策，2026-09-05）✅

> **用户需求：既能自己改，又能让 AI 优化其中一行。** 人工改走直接编辑（§3.2）；AI 优化走"把该行交给 AI"。
> **方案：该行内容打包成 JSON 给 AI → AI 只改文字 → 按 JSON 回填该行。** 用户原话："发出去时把行转成 JSON 让 AI 改，改完再用 JSON 改回来，就能刚好改完这一行。"
> **图只读参考**：行图片**发出去时作为参考图给 AI 看，AI 不改图、不带图回来**，图引用原样保留。用户原话："图不需要带回来，只需要发出去，只能改文字，图只是参考。"

- **数据模型天然支持**：表格是列类型化二维数组（`columns + rows`），每行可序列化为**带 key 的对象**（`{ 列名A: v, 列名B: v, ... }`），AI 改的是结构化字段，能精确定位回填到每个 cell。
- **JSON 打包内容（发给 AI）**：
  - 该行的**文字 cells**（AI 可改）。
  - 该行的**图引用** → 作为**参考图附件**（AI 看，不可改）。
  - **全局定义** → 作为**上下文文本**（AI 看，只读，不该被单行改动）。
  - 附带用户指令（如"优化画面描述，更有电影感"）。
- **回填（AI → 表格）**：AI 返回优化后的**文字 JSON** → 解析 → 覆盖回该行**文字 cells**。图引用、行 id、列结构**一律不动**（AI 无权改，回填只认文字字段）。
- **schema 边界**：JSON 需区分**可改字段（文字 cells）vs 只读字段（图引用、全局定义、行 id、列名）**，防止 AI 优化完把图引用弄丢 / 改坏结构。
- **复用现有链路**：发图给 AI 走 AgentPanel 附件机制（`selectedImageNodes`/附件）；文字指令走 AI 助手对话框。表格行内放一个"交给 AI 优化"的入口（如行内按钮），把该行打包进对话框。
- ✅ **回填流程已定（2026-09-05）**：AI 返回文字 JSON → **UI 预览 diff → 用户确认 → 替换该行**（半自动，可反悔，高度自定义）。

## 四、调研：代码里已有的能力（浅层，2026-09-05 现状）

> 说明：以下只做浅层核对，确认"哪些能复用、哪些要新写、哪些有冲突"。

### 4.1 表格能力：无现成，且有一个冲突点 ⚠️

- **整个 src/ 没有**"表格/单元格编辑/粘贴外部表格成二维"的实现。
- **冲突**：`src/components/base/utils/clipboard.ts` 的 `sanitizePastedText` **会把 Tab 分隔压成空格**（历史用户决策：粘贴表格/富文本必须压成纯文本，见 `useAssetDropPaste.ts` 文件头注释）。
  - **方案已定（2026-09-05）**：表格粘贴走**专门入口**（§3.1b），不进全局 `paste`、不碰 `sanitizePastedText`。在表格内部做独立解析（`text/plain` TSV / `text/html` table），与画布级粘贴（压纯文本/建 textNode）**彻底分流**，全局行为零污染，冲突消除。

### 4.2 节点注册：有唯一目录，登记即接入 ✅

- 唯一目录：`src/components/base/canvas/NodePalette.ts` 的 `paletteNodes`。
- 每项结构：`{ type, label, icon, cat, component, data, builtin }`。
- 新增节点**登记即自动出现**在右键菜单 + 节点面板，并由 `buildNodeTypeComponents()` 派生进 App nodeTypes（**不用手写平行表**）。
- 现有节点 type 清单：imageNode / imageBoxNode / gridSplitNode / gridMergeNode / panoramaNode / director3dNode / faceMosaicNode / loopNode / videoExtractNode / videoProcessNode / group / scriptBoxNode /（顶部隐藏）textNode / promptNode / discountVideoNode。

### 4.3 节点产出管线：有统一契约 NODE_OUTPUTS ✅（表格"喂下游"接入点）

- 权威文件：`src/hooks/useConnectedInputs.ts`。
- **核心机制**：下游节点用 `useConnectedInputs(nodeId)`，**实时读取"直接连到自己"的上游产出**（不复制、引用最新）。
- 产出类型 = **四通道** `NodeOutputGroup { images, texts, videos, audios }`，每项 `NodeOutputItem { id, url, label, text, sourceNodeId, kind }`。
- **有产出的上游节点**必须在 `NODE_OUTPUTS` 表声明如何解析自己的 data → 四通道（现登记：scriptBoxNode/imageBoxNode/videoExtractNode/gridSplitNode/gridMergeNode）。
  - 已有 `arrayImages(list, prefix, labelFn)` 工具，把字符串数组 URL 归一成 `images` 产出。
  - 剧本盒示范了**多端口产出**：每个分镜注册一个 `shot-${id}` 隐藏 source handle，下游连哪个 handle 就拿哪个镜头的图（`collectAssets` 用 `@资产名` 匹配）。
- **表格节点的接入方向**：表格作为**上游产出节点**时，需在 `NODE_OUTPUTS` 加声明，把"选中行"解析成输出（文字 → texts；引用图 → images）。具体产出形态待定。

### 4.4 下游消费节点怎么做（生图/文本怎么拿上游）

- 消费端（如 PromptNode/DiscountVideoNode 等）用 `useConnectedInputs` 拿到上游 `images/texts/...`，作为参考图/参考文本。
- 画布已有**完整的图/文字可被下游消费**的闭环。表格节点只要能**产出**，就能接进这条线。

### 4.5 "@ 选图 / 素材候选"机制：有纯函数与弹层范式 ✅（表格可借鉴/复用逻辑）

- **触发判定**：`src/components/base/prompt/promptMention.ts` 的 `detectMentionQuery(before)` —— 纯函数，判断该不该弹（光标前最近 `@`）。可单测。
- **弹层定位**：`computeMentionPlacement` 同文件。
- **@名 → 芯片**：`src/components/base/prompt/promptChips.ts` 的 `autoLinkAssetsByName`（`@名` → `@{id:label|thumb}`）。
- **候选数据形态**：`{ id, label, url?, kind:'image'|'text' }`（来自 PromptInput 的 refImages/refTexts）。
- **注意**：PromptInput 是整段富文本 contentEditable，**不能直接搬进"逐行表格"**。但 `detectMentionQuery` 的判定 + 候选弹层 UI 范式可参考，表格行内做轻量实现。
- **素材来源候选**：`AssetLibrary.tsx`（`src/components/base/panels/`）从 localTool `/api/resources` 拉素材（migrated/人物、场景等分类，分页加载），是"画布里图片"之外的又一个可引来源。

### 4.6 图片节点 / 素材：输出形态与 hover 能力

- `ImageNode`：单图节点，产出走 genericOutput（data.imageUrl → images）。
- `ImageBoxNode`：多图容器，`NODE_OUTPUTS` 已声明：读 `data.images`（对象数组 `{id,url,label}`）全部产出。
- 图片类 hover（裁剪/标记/压缩）共享 `useImageHoverActions`（在 nodes/），非表格必需。
- **"画布内所有图片"的全量枚举**：现有 `useConnectedInputs` 只解决"某节点的直接上游"，**没有现成的"遍历全画布取所有图片产出"的统一清单**。@ 弹层要列"画布里所有图片"，需新做一层聚合（遍历 nodes 取各图片类产出 + 可选素材库），这是待定设计点。
- **取图核心纯函数已有**：`src/components/agent/canvas/useCanvasAgentTools.ts` 的 `getNodeImageUrl(node)`（导出自 `agent/index.ts`）——从**任意节点提取主图 URL**，覆盖 `data.imageUrl`/`data.url`（字符串）与 `data.images`/`data.imageUrls`（数组，兼容字符串/对象 `{url}`/`{imageUrl}`），无图返回空串。"@ 弹画布里所有图片"的逐节点取图能力，可基于它聚合，不必新写解析。

### 4.7 AI 助手"选中画布节点 → 出现在对话框"（补充线索，可复用）

> 用户补充（2026-09-05）：AI 助手里，选中画布上的节点它会出现在对话框。这个机制可能可复用。

- **入口**：`src/components/panels/AgentPanel.tsx` 接收 prop `selectedImageNodes`，类型 `Array<{ url, label?, nodeId?, nodeType?, x?, y? }>`。
- **App 侧构造**：`src/App.tsx` 的 `onSelectionChange`（约 L1051-1062）——遍历"当前选中节点"，用 `getNodeImageUrl(n)` 取主图，组装 `{nodeId, nodeType, label, url, x, y}`，过滤掉无 url 的，`setSelectedImageNodes(selImg)`。
- **AgentPanel 消费**：`selectedImageNodes` → 存进 `pendingImageNodes`（"待引用"状态，防误触，对齐大雄 ghost 语义），用户点输入框/发送时 `confirmPendingImages()` 并入正式附件，作为参考图发 AI。
- **为什么对表格节点重要**：这正是"**从画布节点取图、给某个消费方引用**"的**现成闭环**，和表格行想"选画布图片作为行的引用图"是**同一类问题**。
  - 可直接复用的底座：`getNodeImageUrl`（取图纯函数）+ 画布选中→提取图列表（App 的范例逻辑）+ AgentPanel 的"待确认引用→附件"交互范式。
  - 差异点：AgentPanel 的触发源是"节点选中"；表格节点想要的是"**行内的选图入口**"（点按钮 / 输入 `@`）。两者底层取图能力可共享，触发 UI 不同（表格行内做轻量选图，不走整节点选中）。
  - 反向提示：若表格节点本身也可被"画布选中"，它也会自然出现在 AI 助手待引用里（取决于 `getNodeImageUrl` 能否从表格 data 提取到图，与表格 data 形态设计相关）。

### 4.8 每行端口 + 宽高自适应（剧本盒 & GridSplit 的参照）

> 表格要"每行一个明确可见的输出端口 + 宽高自适应"。两个参照：① 剧本盒（`ScriptBoxNode.tsx`）给出**每行一个 source handle 的注册/解析范式 + 宽高自适应**；② GridSplit（`GridSplitNode.tsx`）给出**内容区内每子项一个「可见明确端口」**的先例。**两者结合**：端口形态学 GridSplit（可见、跟行走），注册与解析 + 自适应学剧本盒。

- **可见端口先例（GridSplit cell- 口，L641-645/747-752）**：在内容区每个 cell 卡片里内嵌原生 `<Handle type="source" position={Position.Right} id={`cell-${i}`} className="!w-1.5 !h-1.5 !bg-blue-500 !border-[1px] !border-white !rounded-full ..." />`——**可见小圆点、跟随所在子项**。表格每行右侧就照这个做（可见口，非隐藏）。hover 显示 or 常显由样式决定。
- **注册/解析范式（剧本盒，ScriptBoxNode L220-229）**：每行注册一个 source handle。写侧 id 用 contracts 的 `shotHandleId`/`shot-` 前缀；读侧 `parseShotHandle` 反解析（按前缀长度截取）。表格照此新增成对 `rowHandleId`/`parseRowHandle`（前缀 `row-`），禁止裸拼字符串。
  - 关键坑：**增删行后需 `updateNodeInternals` 强制重测**（用"行 id 列表 key"触发，非整个数组），否则新 handle 进不了 handleBounds、连边报 code-008。
  - 读侧消费（useConnectedInputs NODE_OUTPUTS）：`scriptBoxNode` 声明按 `parseShotHandle(sourceHandle)` 反查分镜 → `collectAssets(shot, assets)`。**表格同范式**：端口 `row-${rowId}` → NODE_OUTPUTS 按 handle 反查行 → 输出该行文字/图。
- **宽高自适应**（剧本盒，ScriptBoxNode L128-129）：
  - `useContentHeightSync(contentRef, id, { minHeight, fallbackWidth, syncWidth: true, wrapperRef })` —— 来自 `base/core/uiHooks.ts` L299，**已支持高度 + 宽度同步**（`syncWidth:true`）。表格节点直接复用即可实现"高度 + 宽度自适应"。
  - `contentRef` = 主内容区；`wrapperRef` = NodeShell 根 div（含标题栏）作测量基准，否则写回偏矮。
  - NodeShell 层：`minWidth/minHeight`、去掉固定宽高（否则内容溢出框外）；`aspectRatio={null}`。
  - 机制细节：ResizeObserver 监听 → rAF 写回 node.height/width（防抖 4px 阈值 + 断开重连破 ResizeObserver 循环告警）。

## 五、关键待定问题（落地前需用户确认）

1. **表格节点的画布角色**：✅ **已决策（2026-09-05）**——**纯上游产出节点，只连下游、不连上游**（见 §3.6）。连上游的复杂度不做。
2. **每行端口输出什么（改自"选中行文字形态"）**：某行被下游连上时，该行产出 = ① 该行所有**文本列**文字 ② 该行所有**图片列**里的图 ③ 若配了全局定义（§3.5），再并入全局定义。两条通道。要确认：
   - 文字是否整行拼成一段给下游？（还是让下游能按列挑 / 给全部 text cells 让消费方自己取）
   - 图片是否就是该行**图片列 cells**里的图引用？（"长得像图片 URL 的文本格"不自动识别——图片只来自被标成 image 的列。这点建议直接定为"只取图片列"最干净。）
3. **每行端口是"恒定的行口"还是"行内还分文字/图口"**：✅ **已决策（2026-09-05）**——**一行一个口，下游连上同时拿该行文字+图，不拆文字口/图口**。不再待确认。
4. **图片列选图的数据源（"点选/按钮"弹什么候选）**：点图片列单元格选图时，弹"画布里所有图片"，是从"遍历画布所有节点 + `getNodeImageUrl` 取图"来，还是从"素材库 /api/resources"来，还是两者合并？（前者可直接复用 `getNodeImageUrl`，无需新解析；候选范围 = 能取到图的节点，label 用节点名。触发方式已定为**点选/按钮**，不用 @ 弹层。）
5. **粘贴解析策略**：✅ **已决策（2026-09-05）**——粘贴走**表格内专门入口**（§3.1b），独立解析 TSV/HTML，**不进全局 paste、不复用 `sanitizePastedText`**，与现有"粘贴压纯文本"彻底分流，无冲突。不再待确认。
6. **宽高自适应**：✅ **已决策（2026-09-05）**——复用剧本盒 `useContentHeightSync`（`syncWidth:true` 同时自适应高度+宽度），见 §3.4 / §4.8。不再待确认。
7. **和剧本盒子的关系**：表格节点成熟后**替换**剧本盒，还是**并存**？是否删除剧本盒（及它占用的多端口产出/引擎逻辑）？
8. **全局定义（§3.5）的形态与合并细节**：✅ **已决策（2026-09-05）**——全局定义 = **一段文字，不分块、不放图**，经齿轮设置编辑存 `data.global`，输出时并入该行。具体拼接位置/结构实现时定。不再待确认。
9. **单行 AI 优化（§3.7）的回填方式**：✅ **已决策（2026-09-05）**——**AI 返回文字 JSON → 先在 UI 预览 diff → 用户确认 → 才替换该行**（半自动，高度自定义、可反悔）。不再待确认。

## 六、明确不做 / 边界

- **不做几千行规模的虚拟滚动/懒加载优化**（分镜只有几十行）。
- **不做"每个格都能变图"的复合单元格**——图片只在被标成 image 的**列**的单元格里以引用/缩略图出现（图片列单元格），**文本列单元格永远是纯文本**，图不嵌进文本格。
- **不预设分镜字段模板**（镜头号/景别/台词……都不是写死的，由粘贴内容决定；列类型 kind 只是列的属性，不影响列名/列数自由）。
- **暂时不深改剧本盒子**（它是重节点，不主动收口；仅作对比参考）。
