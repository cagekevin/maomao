# 前端「发请求统一」可执行步骤（改前端 → 再并后端 relay/API）

> 目标顺序（用户确认）：**先把前端发请求数据统一** → 后端 relay/API 合并成一个（后者另做）。
> 本文件是可执行步骤：具体到文件/新增什么/验证什么，每步可编译、可回退、不破坏现状。
> 原则：**新增统一门面（默认走老通道，行为不变）**，节点逐步切；不删老通道直到后端合并完成。

---

## 背景（已核实，勿重查）

- 前端 5 类入口：文本(TextNode=chat) / promote(PromptNode=image) / 视频(DiscountVideoNode=video) /
  剧本盒子(scriptBoxEngine=chat+image) / AI 助手(contextCompression=chat)。
- 全部收敛到 3 门面：`imageApi.generateImage` / `videoApi.generateVideo` / `chatApi.chatCompletions`（无旁路）。
- 模型 value = `providerId::modelId`（providerModels.ts），节点用 `resolveProviderModel(providers, selectedModel, primary)` 解出 `{ provider, modelId }`，把**整个 provider 富对象**塞给门面。
- 门面底层走 proxyGenerate → `/api/proxy`（出站细节依赖 provider 富对象：base_url/protocol/image_request_mode/refFormat...）。
- 后端 `/api/generate`(image/video 后端驱动) 与 `/api/relay`(chat) **已就绪并真机验通**，收 GenIntent 形态（providerId/capability/model/prompt/messages/size/images/taskId）。
- 后端 config/providers/<id>.json（96 号）已建：providerId = 平台 id。

## 统一目标形态

5 类入口不再塞 provider 富对象，改传统一 `GenIntent`（providerId + model + 模态参数 + taskId）。
门面内部按需把 providerId 查回 provider（走老通道时）或直接发 GenIntent（走新通道时）。

## 可执行步骤

### Step 1 · 建统一类型 `GenIntent` + 门面统一入口（新增文件，不碰现有）
- 文件：`src/components/base/api/genIntent.ts`
- 内容：
  - `export interface GenIntent`（capability/providerId/model/taskId/prompt/messages/size/images —— 见 docs/100 §2）
  - `export interface GenOutput`（= GenerationResult：ok/url/content/error/aborted，复用）
  - 一个**语义入口** `genRequest(intent, extra)`：内部按 `RELAY_ASYNC_SUBMIT`/通道开关分派：
    - 老通道：`providers.find(providerId)` 查回 provider 富对象 → 调 imageProxy/videoProxy/chatProxy（现状逻辑）
    - 新通道(relay)：组装 POST /api/generate 或 /api/relay
  - 默认走老通道（`RELAY_ASYNC_SUBMIT=false`），行为与现状逐字节等价。
- 验证：`npx tsc --noEmit` 过；无运行时行为变化。

### Step 2 · 门面函数接受 GenIntent（改 imageApi/videoApi/chatApi）
- `generateImage(opts)`：opts 改收 `{ providerId, model, prompt, size, n, aspectRatio, quality, images, taskId }`（provider 字段移除），内部把"参考图归一/尺寸查表"保留，最终走 `genRequest(intent)`。
- `generateVideo(opts)` / `chatCompletions(opts)` 同理：providerId 替换 provider。
- `resolveProviderModel` 仍解出 provider，但**只取 `provider.id` 填 providerId**，不再传整个对象。
- 验证：tsc 过；TS 报错会逼出所有仍传 provider 的调用点 → 逐个改。

### Step 3 · 逐类入口切到新签名（每类改完 tsc + 手测）
顺序（每类独立提交）：
1. **promote 节点 (PromptNode.tsx:284)** image
2. **文本节点 (TextNode.tsx:207)** chat
3. **视频节点 (DiscountVideoNode.tsx:230)** video
4. **剧本盒子 (scriptBoxEngine.ts 全部调用点)** chat + image
5. **AI 助手 (contextCompression.ts:134)** chat
- 每类改动点：把 `generateImage({ provider: useProvider, ... })` → `generateImage({ providerId: useProvider?.id, model: modelId, ... })`。
- 验证：tsc；本地起后端 + 起前端点一次该节点出结果（能力零退化：进度/取消/参考图/错误）。

### Step 4 · 后端合并 relay/API（前端稳定后另做，不并入本清单执行）
- 此时前端已稳定发 GenIntent(providerId)。后端再把 /api/relay 与 /api/generate 合并成单一统一 API（对前端只暴露一套端点语义），
  把 providerId → config/providers + preset 的翻译收口。→ 见 docs/98/99（后端合并设计）。

## 红线
- **Step 1-3 不删老通道**：proxyGenerate / /api/proxy 保留到后端合并完成后再退役。
- **能力零退化**：每步必须保证进度条/取消/参考图/错误中文/刷新恢复不坏；改完真机点一次。
- **providerId 是主键**：前端不再传 base_url/protocol/refFormat 等出站细节给后端（老通道内部查回 provider 仅用于兼容期拼 target）。
- 每步 `tsc --noEmit` 通过再进下一步；改前 `git stash`/分支，可随时回退。

## 现状结论
本清单的 Step 1-2 是"新增+归一"（安全、可编译、行为不变）；Step 3 需前端运行环境手测（无法在本环境真机验证，需你在本地跑前端点一次）。
