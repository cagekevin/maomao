1. **先挑高价值低风险的**：`VideoExtractNode`（明确刷新丢结果）最值得先收口。
2. **豁免的保持豁免**：VideoProcess/GridSplit/Loop 等特定功能模块，**不主动收口**，除非有明确 bug。
3. **更新 CONTEXT 待办状态**：逐节点标注已完成/豁免/待收口。

**✅ 执行结果（2026-08-22，逐节点审计）**：

## R3 · official 权益层接管决策（P2，中风险）

**现状**：`official.ts` 权益转发层（`/api/user/info`、`model-entitlements`、`vip-check`、`invalidate`）已实现"带缓存降级的透传"，但**前端三处权益接口 base 默认直连官方、不经本层**（official.ts:316-339，"就绪未接管"态）。

**决策点**：
1. **让前端改走本层**：可获得本地缓存降级（5xx→stale、KV 防回环），但失去官方实时权益。
2. **维持直连官方**：更简单、实时，但无降级保护（官方接口抖动时前端会报错）。

**建议**：若官方权益接口**稳定性是痛点**，启用本层；否则维持现状。**属业务决策，非纯技术**。

## R5 · check-api 校验增强（P3，低风险）

**现状**：`check-api-contract.cjs` 只校验"登记的条目 ↔ 后端路由"镜像，**不校验"登记的 fn 是否真的存在于前端代码"**——本次发现 platform 幽灵 ACTIVE 就是因此漏检。

**收口目标**：校验脚本增加"fn 存在性"检查：
- ACTIVE 条目的 fn（如 `localToolApi.fetchTasks`）应能在对应模块找到导出/定义
- 找不到 → warn（可能是幽灵登记）

**建议**：低成本高价值，能防"登记了 ACTIVE 但前端没实现"的幽灵条目再次出现。

## R7 · 错误重试/降级统一收敛（P2，中风险）

**现状**：CONTEXT §六.C 已知待办"节点级 catch 大多只 setState 不收敛"。本次 API 收口已统一了**后端错误信封**（`{error:{code,message}}`）和**前端 `extractErrorDetail`**，但**节点级 catch 的错误处理**仍散落。

**收口目标**：把节点级错误降级/重试收敛到一个统一 hook（类似 `useNodeGeneration`），复用 `classifyError` + `GEN_ERRORS`。

**建议**：中高价值但中风险（跨节点），需谨慎。可作为**独立后续任务**，不并入 API 中转层。

**✅ 执行结果（2026-08-22，修订：不新造 hook，错误出口补统一分类记录）**：
- 审计发现：已接入 `useNodeGeneration` 的 4 节点错误出口已统一（setError+toast），无散落；真正散落的是未接入的本地处理节点。且 R2 后这些节点**不接入 useNodeGeneration**（本地处理），故不抽 `useNodeErrorHandling` hook（避免过度设计），改为在错误出口复用 `classifyError` 补分类记录。
- 4 处改动：`useNodeGeneration` 失败路径（run 抛异常 + `{ok:false}` 契约失败）、`VideoExtractNode`/`VideoProcessNode` catch、`FaceMosaicNode` 单张失败。均带 `errType`/`retryable` 进 logger，message 原样透传（错误透传铁律）。
- 重试判定对齐：network/timeout（retryable）供「再来一次」入口，business/http 不自动重试；`reportDegrade` 仅降级场景（本期错误出口无降级路径，不涉及）。
- 测试：useNodeGeneration 补 2 断言（network 可重试 / business 不可重试），VideoExtractNode 补分类记录断言；全量 1590 单测绿。
