# AI 助手状态管理：完整数据流与职责重设计

> **核心目标**：让架构更清晰、更易懂，不混、不乱。
> **方法**：重新设计完整数据流与职责划分——**每个模块只干自己的事、状态只有一个来源、数据流清晰单向**。不做局部补丁、不堆砌补丁式的守卫。
> **落地原则**：
>   1. **职责单一**：UI 只渲染，数据层只读写，工具层只操作画布，谁都不越界。
>   2. **单一数据源**：对话状态收敛到 conversationStore，不搞三套状态互相同步。
>   3. **写盘收敛**：落盘集中在数据层一处，不散落在各处手动 capture。
>   4. **按需修复**：必修的排前，可修/不修的排后或标注（用户一次就懂的，不做过度设计）。

## 〇、本方案是「追平既有范式」，不是新造轮子

核对画布其他核心 store，项目**已普遍采用**一套统一的 store 范式：

| Store | 模式 | 自动落盘 |
|-------|------|----------|
| `taskStore.js` | `useSyncExternalStore` + 模块级单例 + listeners | ✅ 变更即 persist 后端 |
| `projectStore.js` | `useSyncExternalStore` + 模块级单例 | ✅ 变更即双写 localStorage+后端 |
| `providerStore.js` | `useSyncExternalStore` + 模块级单例 | ✅ setState 即 notify |
| **`conversationStore.js`（AI 助手）** | **手动 `current`+`cache`+`capture`** | **❌ 手动落盘、三套状态** |

**结论**：本方案让 conversationStore 从项目里唯一落后的「手动同步」模式，**对齐到 taskStore/projectStore/providerStore 已用对的标准模式**。是「追平既有范式」而非创新——重构后 AI 助手 store 与画布其他 store 结构一致，架构更清晰、更易懂、不混不乱。

> **参照范例**：实施 conversationStore 订阅化时，直接照抄 `taskStore.js`/`providerStore.js` 的 `useSyncExternalStore + 模块级单例 + setState→notify` 骨架即可，保持全项目一致。

## 〇·二、已定位的根本缺陷

通过运行时诊断（Console 追踪 `save/load` 调用栈）确认了**刷新丢记录的直接根因**，以及背后的架构缺陷：

### 直接根因（已实证）
`AgentPanel.jsx` 在挂载时有两个 `useEffect`（`activeSkills` 依赖、`attachments` 依赖），各自调用 `captureActiveConversation()`：

```js
useEffect(() => {            // AgentPanel.jsx
  setCurrentSnapshot({ skills: activeSkills })
  try { captureActiveConversation() } catch {}   // ← 用空 current 覆盖 localStorage
}, [activeSkills])
useEffect(() => {
  setCurrentSnapshot({ attachments })
  try { captureActiveConversation() } catch {}   // ← 同样问题
}, [attachments])
```

**时序缺陷**：挂载时 `conversationStore.current` 还是初始空数组，`useAgentChat` 的初始化 effect（`applyConversation` 恢复消息）与这两个 effect 的执行顺序不受控。若这两个 effect 先跑，就会把**空消息写回 localStorage，覆盖掉真实历史**。诊断日志证实：刷新后 `load` 读到 2 条消息，随后 `save` 被 `AgentPanel.jsx` 的 `captureActiveConversation` 覆盖成 0 条。

### 架构缺陷（根因背后的系统性原因）
1. **三套状态无单一来源**：React `useState`（useAgentChat）+ 内存镜像 `current`（conversationStore）+ localStorage（持久化），靠各处手动同步。
2. **落盘时机靠手动 `captureActiveConversation`**，散落在 `useAgentChat`/`AgentPanel`，漏调或时序错就丢/覆盖。
3. **模块级临时态**（`pendingGenerations`/`aiUndoStack`）不持久化、跨对话串话。
4. **职责混乱**：`AgentPanel` 的 UI effect 混入了"持久化"职责，与 `conversationStore` 的职责边界不清。

## 一、重设计目标

1. **单一数据源**：所有对话状态收敛到 `conversationStore`，它是唯一真相源（source of truth）。
2. **自动落盘**：状态变更即写 localStorage，**消除所有手动 `captureActiveConversation` 调用**。
3. **职责分离**：UI 组件只管渲染与用户交互，**不做持久化**；数据层统一负责读、写、落盘。
4. **per-conversation 彻底隔离**：`pendingGenerations`/`aiUndoStack`/`awaitingConfirm` 下沉到对话级。
5. **时序安全**：挂载恢复（hydration）与写盘不会互相覆盖。

## 二、完整数据流设计

### 2.1 单一数据源：conversationStore（可订阅 + 自动落盘）

```
┌────────────────────────────────────────────────────────────┐
│  conversationStore（唯一真相源，useSyncExternalStore）       │
│                                                            │
│  state = {                                                 │
│    conversations: [ { id, title, ts, updatedAt,            │
│                      messages, skills, attachments, draft, │
│                      workflow, pending, memory,            │
│                      pendingGenerations, aiUndoStack,      │
│                      awaitingConfirm } ],                  │
│    activeId,                                               │
│  }                                                         │
│                                                            │
│  写入口（唯一）：_commit(nextState)                         │
│    → 更新 state + 通知订阅者 + 自动 JSON 落盘 localStorage  │
│  读入口：useConversationStore() / getActiveSnapshot()      │
└────────────────────────────────────────────────────────────┘
```

**核心：一切写操作都走 `_commit`，内部自动落盘。** 不再有"手动 save/capture"。

### 2.2 各模块职责（谁管什么）

| 模块 | 职责 | 写盘动作 |
|------|------|----------|
| **conversationStore** | 唯一数据源；读/写/落盘/恢复 | 所有 `_commit` 自动落盘 |
| **useAgentChat** | 对话引擎：发消息、工具循环、恢复 | 消息变更 → `_commit(updateActiveMessages)`；不再手动 capture |
| **AgentPanel** | 纯 UI：渲染消息、输入、模式、Skill | **不做持久化**；改 skills/attachments 只调 `setActiveSnapshot` 由 store 落盘 |
| **useCanvasAgentTools** | 画布工具层：读写画布 + 暂存策划/撤销 | `pendingGenerations`/`aiUndoStack` 经 store 读写 |
| **inputStateMachine** | 运行态（瞬时，不持久化） | 不落盘 |

### 2.3 写盘时机（消除手动 capture）

**原则：状态变更即 `_commit`，store 内部落盘。** 具体：

- **消息变更**：`useAgentChat` 每次 `setMessages` 后，同步调 `store.updateActiveMessages(msgs)`（内部 `_commit` + 200~300ms 节流落盘）。
- **skills/attachments 变更**：`AgentPanel` 调 `store.setActiveSkills()` / `store.setActiveAttachments()`（内部 `_commit` 落盘），**不再调 capture**。
- **切换/新建/删除对话**：store 内部先 `_commit` 当前对话，再切目标。
- **策划/撤销栈**：经 store 的 `setActivePendingGenerations()` / `pushActiveUndo()`（内部 `_commit` 落盘）。

**删除**：`captureActiveConversation` 从对外 API 移除（或改为 `_commit` 的内部实现），杜绝"UI 层漏调/错调导致覆盖"。

### 2.4 挂载恢复（hydration）时序安全

**问题**：挂载早期 `current` 为空，UI effect 若写盘会覆盖。

**重设计解决**：
1. store 内部维护 `hydrated` 标志，`applyActiveConversation()`（恢复）完成后置 true。
2. **只有 `_commit` 在 `hydrated=true` 时才落盘**；未恢复前的写操作只更新内存，不落盘。
3. **UI effect 不再直接持久化**——既然 AgentPanel 不再调 capture，天然避免覆盖。
4. `useAgentChat` 的初始化 effect 是**唯一**负责 `applyActiveConversation` 的地方，恢复完成后才允许后续写盘。

> 注：`hydrated` 在此是**数据层内部**的落盘守卫（区分"恢复中"与"已就绪"），不是业务补丁——它保证了"加载完成前绝不覆盖已存数据"，是单一数据源设计的必要组成部分。

## 五、验收标准

1. 聊天后**刷新 → 完整历史保留**（含最近一条），不出现"回到初始界面"。
2. 挂载时**不会**用空数据覆盖已有记录。
3. 多对话切换 → 消息/草稿/Skill/策划/撤销栈互不串话。
4. Skill 三阶段：`present_plan` 后 `awaitingConfirm` 为 true，`execute_plan` 未确认被拒；刷新后仍处于待确认态。
5. `undo_ai` 只撤当前对话的 AI 操作。
6. 原有画布工具、生图、Skill 批量出图回归通过。

## 六、风险与注意

- **useSyncExternalStore 的 getSnapshot 必须返回稳定引用**（否则死循环渲染），`_commit` 一律生成新对象。
- **自动落盘节流**：消息流式落盘需 200~300ms 节流；`workflow`/`pending` 等瞬时态落盘与消息共用同一节流器，避免每轮状态翻转频繁写盘。
- **localStorage 容量**：每对话消息上限 `AGENT_MSG_MAX=60`，加上策划/撤销栈字段，需评估总量。
- **多窗口**：chrome.storage 环境跨窗口同步；localStorage 需 `storage` 事件监听（可选增强）。
