## 结论先行

**扩图可以用原生方案做，而且比裁剪更适合原生方案。**

- **扩图**：输入是**参数**（目标比例 / 外扩量 / 偏移），**没有"选区"**，因此不需要"屏幕选区 → 原图像素"的坐标映射 → 天然规避了裁剪那一类 bug。且核心数学已是**带单测的纯函数**（`computeOutpaintTarget` / `computeOutpaintDrawPos`）。
- **裁剪**：难点全在选区映射，但**已由「就地裁剪 `InlineImageCropper`」跑通**（用户实测可成功保存）→ 不必重写，直接**复用 / 收口到它**即可。
- **全屏 `ImageEditor` 的裁剪**：实测保存无效，且**未定位到确定根因** → 建议**不再投入**，其裁剪入口退役，仅保留已验证可用的「标记/涂鸦」。

## 一、现状证据（实测，非推测）

| 场景 | 实现 | 保存是否生效 | 说明 |
|---|---|---|---|
| 节点内【就地裁剪】 | `InlineImageCropper` | ✅ 生效 | 用户实测成功 |
| 全屏编辑器【标记/涂鸦】 | `ImageEditor` pencil | ✅ 生效 | 用户实测成功 |
| 全屏编辑器【裁剪】 | `ImageEditor.applyCrop` | ❌ 无效 | 用户实测失败 |
| 全屏编辑器【扩图】 | `ImageEditor.applyOutpaint` | ❌ 同链路，预期同样不可靠 | 与裁剪共用同一套画布写回 |

### 为什么「标记行、裁剪不行」——两条实现的关键差异

**能用的（原生管线，`InlineImageCropper.handleSave`）**：

```
compressImage(url, {keepOriginalFormat:true})   → 同源 dataURL（canvas 永不污染）
  → loadImageWithTimeout(dataUrl)               → 干净 Image
  → document.createElement('canvas')            → 【新建游离 canvas】
  → ctx.drawImage(...)                          → toDataURL
```

特征：**不碰 React 绑定的 canvas、不用 `getImageData`**；一次性新建游离画布，画完即导出。

**不行的（`ImageEditor.applyCrop`）**：

```
canvasRef.current（React 渲染的活画布）
  → ctx.getImageData(sx,sy,sw,sh)     ← 读像素
  → canvas.width = sw; canvas.height = sh   ← 就地改活画布尺寸（会清空画布）
  → ctx.putImageData(data,0,0)        ← 写回
  → commitCanvasToImgRef()            → toDataURL('image/png') 再异步回填 imgRef
  → setImgSize / setTool / setCrop    → 触发 React 重渲染
```

特征：**就地改活画布 + `getImageData/putImageData` + 尺寸变更 + 异步回填底图 + 紧随重渲染**，可变环节多。

### 已排除的原因

- ❌ **不是跨域污染（tainted canvas）**。若被污染，`toDataURL` 本身就会抛 `SecurityError`，那么「标记保存」同样会失败；但它实测正常。且原生管线用 dataURL 绘制源，本就不会污染。
- ❌ **不是 React 重渲染冲掉画布**。`<canvas>` 的 JSX 只绑了 `style.width/height`，未绑 `width`/`height` 属性，重渲染不会重置画布像素。

### 未定位到的部分（诚实标注）

`applyCrop` 的像素映射为 `scaleX = canvas.width / canvas.offsetWidth`（显示尺寸 → 原图像素）。该映射依赖布局尺寸，在**缩放 `zoom`、滚动容器、`object-contain` 留白**等组合下易失准；jsdom 单测（mock canvas）无法复现真实布局时序，故 `tests/unit/ImageEditor.cropSave.test.tsx` 全绿但真机失败。
**结论：不再在 `ImageEditor` 里追这个根因**——投入产出比低，且已有可用替代路径。

## 二、关键判断：扩图比裁剪更适合原生方案

| 维度 | 裁剪 | 扩图 |
|---|---|---|
| 用户输入 | **屏幕选区矩形** | **参数**（比例 / 外扩量 / 偏移） |
| 是否需要坐标映射 | ✅ 需要（显示 px → 原图 px，且要处理 `object-contain` 留白偏移） | ❌ **完全不需要** |
| 数学是否已有 | 就地裁剪内已实现（`cropRectFromSelection`） | ✅ `computeOutpaintTarget` / `computeOutpaintDrawPos`，**纯函数 + 已有单测** |
| 失败风险 | 中高（映射失准即失败） | 低（纯计算 + 一次 `drawImage`） |
| 原生方案难度 | ★★★☆☆（但已跑通，可复用） | ★☆☆☆☆ |

> 一句话：**扩图的输入本来就是自然像素/比例空间的参数，不需要从 UI 反解坐标**——这恰好绕开了裁剪的全部风险点。

## State 1：定契约（输入 / 输出 / 边界）

### 输入
- 图片 URL（`data:` / `blob:` / `http(s)` / `/files/` 相对路径均可）。
- 扩图参数：
  - `ratioKey`：`OUTPAINT_RATIOS` 之一（`1:1 / 4:3 / 3:4 / 16:9 / 9:16`），不传 = 保持原比例。
  - `amount`：外扩量 `0~1`（`toOutpaintZoom(amount)`；`0` = 无白边、原图铺满，默认 `0`）。
  - `offset`：`{x, y}`，归一化 `[-0.5, 0.5]`（-0.5 贴左/上，+0.5 贴右/下，0 居中）。

### 输出
- `{ dataUrl, width, height }`，其中 `width/height` = 扩图目标画布真实像素（`tw × th`）。
- 沿用既有落点：`onImageReplaced(dataUrl, dims)` → `fitByRatio(w,h)` 节点框自动跟随（见 `78` 号文档，已通）。

### 边界 / 失败拦截
- 透明图（PNG/WebP）→ 输出 PNG、**透明底不填充**；JPEG → 白底填充后输出 JPEG（沿用 `InlineImageCropper` 的格式纪律，避免透明变黑底）。
- 加载/跨域失败 → 抛明确错误 + `toastError` 透传真实原因，**不静默吞错**。
- 外扩后画布可能很大（如 `amount=1` 时面积约 4 倍）→ `toDataURL` 出图体积显著增大；注意会话落盘 base64 体积（参见 `72-会话落盘base64体积降级`）。建议 `amount` 上限保持现有 `OUTPAINT_ZOOM_MIN/MAX` 钳制。

### 收口检索（复用，不新增重复实现）
| 能力 | 既有件 | 动作 |
|---|---|---|
| 干净绘制源 | `compressImage(url,{keepOriginalFormat:true})` | 复用 |
| 图片加载 + 超时 | `loadImageWithTimeout` | 复用 |
| 扩图数学 | `computeOutpaintTarget` / `computeOutpaintDrawPos` / `toOutpaintZoom` / `OUTPAINT_RATIOS` | 复用（纯函数，已有单测） |
| 节点比例跟随 | `useFitNodeRatio.fitByRatio` | 复用（`78` 已接） |
| 写回入口 | `useImageHoverActions.onImageReplaced` | 复用 |
| 就地裁剪 | `InlineImageCropper` | **保持不动**，作为裁剪唯一实现 |

## State 2：定数据流（链路 / 唯一入口）

### 2.1 抽出共享「原生导出管线」（新增 1 个小工具文件）

裁剪与扩图共用同一条**已验证可用**的管线，彻底摆脱 `getImageData` + 就地改活画布模式：

```ts
// src/components/base/utils/canvasExport.ts
import { compressImage } from './imageCompress.ts';
import { loadImageWithTimeout } from './asyncGuard.ts';

/**
 * 原生导出管线（由「就地裁剪」验证可用）。
 * 不碰 React 绑定的 canvas、不用 getImageData：
 *   compressImage → 同源 dataURL → loadImageWithTimeout → 新建游离 canvas → draw → toDataURL
 */
export async function exportCanvas(
  url: string,
  size: { w: number; h: number },
  draw: (ctx: CanvasRenderingContext2D, img: HTMLImageElement) => void,
): Promise<{ dataUrl: string; width: number; height: number }> {
  const clean = await compressImage(url, { keepOriginalFormat: true });
  const img = await loadImageWithTimeout(clean.dataUrl);
  const canvas = document.createElement('canvas');
  canvas.width = size.w;
  canvas.height = size.h;
  const ctx = canvas.getContext('2d');
  if (!ctx) throw new Error('无法创建画布');
  draw(ctx, img);
  const m = /^data:([^;,]+)/.exec(clean.dataUrl);
  const outFormat = m?.[1] === 'image/jpeg' ? 'image/jpeg' : 'image/png';
  return { dataUrl: canvas.toDataURL(outFormat, 0.9), width: size.w, height: size.h };
}
```

### 2.2 扩图链路

```
[直接操作] 拖边缘手柄 / 点预设比例  →  得到 ratioKey（amount 恒为 0，即无白边以外的额外放大）
   ↓
computeOutpaintTarget(srcW, srcH, ratio, toOutpaintZoom(amount)) → { tw, th, maxOffX, maxOffY }
computeOutpaintDrawPos(offset, maxOffX, maxOffY)                 → { dx, dy }   ← offset 来自「拖动原图定位」
   ↓
exportCanvas(url, { w: tw, h: th }, (ctx, img) => {
   非透明 → ctx.fillStyle='#fff'; ctx.fillRect(0,0,tw,th)
   ctx.drawImage(img, dx, dy)            ← 原图按 1:1 自然像素贴入，不做缩放
})
   ↓
{ dataUrl, width: tw, height: th }
   ↓
onImageReplaced(dataUrl, {width,height}) → fitByRatio → 节点框跟随
```

**唯一入口判定**
- **画布写回唯一方式**：`exportCanvas`（新建游离 canvas + `drawImage`）。禁止再出现"就地改 `canvasRef` 尺寸 + `putImageData`"。
- **数学唯一来源**：`computeOutpaintTarget` / `computeOutpaintDrawPos`（纯函数）。
- **节点自适应唯一函数**：`fitByRatio`。

### 2.3 缩放机制：扩图的前提条件（★ 当前实现缺失的环节）

**结论：是的，扩图必须先缩小图片在视口中的显示比例，否则白边根本看不见、也拖不动。**

视口（`viewportRef`）尺寸固定，而"扩图"的本质是**画布变大**。画布显示尺寸 = `imgSize × zoom`，若 `zoom` 不变，画布一变大就撑出视口 —— 用户只能看到局部，白边全在视口外，**无从下手**。

**当前实现的缺陷（已确认）**：`renderOutpaint` 在 `setImgSize({ w: t.tw, h: t.th })` 后**从未重算 `zoom`**，而 `fitZoom`（第 275 行，基于 `viewportRef` + `imgSize`）是现成的却没被调用。这正是「拖动原图定位」难用的根因 —— 不是交互设计问题，是**看不全**。

**做法**：任何导致目标画布尺寸变化的操作（进入扩图 / 拖边缘 / 切预设 / 改外扩量）之后，**必须重新 `fitZoom()`**，把目标画布完整缩放进视口（留 padding）：

```ts
setImgSize({ w: t.tw, h: t.th });  // 画布变大
// ↓ 紧接着：让缩放跟上，保证用户始终看到完整画布与四周白边
fitZoom();
```

规律：**目标画布越大 → zoom 越小 → 原图在画面里显示得越小**，四周白边随之可见。这就是用户直觉里"先缩小图片，才能往外扩"的机制来源。

> 注意区分两个"缩放"：
> - **显示 zoom**：随画幅变化自动 fit，只影响预览观感，不影响出图。
> - **原图像素**：`computeOutpaintTarget` 返回的 `sw/sh` **恒等于原图原始尺寸**，原图永远 1:1 贴入、不缩放不拉伸（保证画质不劣化）。变的只有画布尺寸和原图在其中的位置。

### 2.4 UI 交互（聚焦：定画幅 → 摆原图 → 出图）

```
      ┌─ ── ── ── ── ── ── ──┐
      │  斜线纹 = 留给 AI 的白区  │
      │    ┌───────────┐      │
   ◄──┤    │  原图可拖动  │      ├─►   四边/四角手柄：按住往外拖
      │    └───────────┘      │
      │              1920×1080 │   拖动时实时显示目标尺寸
      └─ ── ── ── ── ── ── ──┘
```

| 元素 | 做法 | 为什么 |
|---|---|---|
| 画幅 | 4 边 + 4 角拖拽手柄 | 直接操作，大厂感来源 |
| 预设 | `1:1 / 4:3 / 16:9 / 9:16 / 原比例` 胶囊 | 比拖更准，一键切 |
| 尺寸反馈 | 拖动中实时显示 `1920×1080` | 用户关心实际像素 |
| 原图定位 | 白区内自由拖；**居中吸附 + 三分线** | ★ 决定 AI 往哪延伸（主体靠左→右边留空间），是核心功能不是补偿操作 |
| 白区视觉 | 斜线纹 / 浅灰底 | 明确"这里是给 AI 填的"，避免误认成品 |
| 缩放 | 画幅一变即 `fitZoom()` | 见 2.3，保证始终看到全貌 |

**砍掉（不做）**：扩展滑块（拖边缘已替代）、生成中 shimmer、A/B 对比、重新生成。
理由：本工具的产出只是"四周留白的图"，**填充由下一步大模型完成**；生成态与结果对比属于下一环节，不在此处。

**关键约束**：白边保持**纯白 `#ffffff`**（`OUTPAINT_FILL` 已对）。下一步大模型依赖白色识别待填区，灰度或 JPEG 压缩噪点都会干扰 —— 故输出走 PNG 无损，不用现有 `toDataURL('image/jpeg', 0.9)`。

### 2.5 落点与回写

- **落点**：双击放大（大图）场景中加「扩图」入口。扩图需要比例/预设与拖动手柄，**节点内小空间放不下**，不做成 `InlineImageCropper` 那样的节点内浮层。
- **是否替换原节点图片**：**是**。与裁剪一致，走 `onImageReplaced(dataUrl, {width,height})` 覆盖节点当前图，节点框由 `fitByRatio` 跟随新比例。
- 入口传入 `imageUrl`，输出 `{ dataUrl, width: tw, height: th }`。

## State 3：构思测试（断言，实现一变必红）

1. **纯函数（已有 `ImageEditor.outpaint.test.ts`，继续沿用）**
   - 原图 800×600，`ratio=1:1`、`amount=0` → 目标画布 **800×800**（zoom=1 无白边）。
   - 原图 800×600，`amount=0.5` → 目标画布按比例放大，且 `maxOffX/maxOffY > 0`（四周留白）。
   - `offset={x:-0.5,y:0}` → `dx=0`（贴左）；`offset={x:0.5}` → `dx=tw-sw`（贴右）。

2. **导出管线（新增）**
   - 给定 url 与目标尺寸 → 断言返回 `width/height` 等于传入尺寸（**不依赖缩略图端点还原**）。
   - 断言绘制源为 **dataURL**（同源），即 `loadImageWithTimeout` 收到的是 `data:` 开头（防跨域污染回归）。
   - 断言**未调用** `getImageData`（mock ctx 记录），确保不回退到旧模式。

3. **白边约束（扩图专属）**
   - 输出白边为**纯白 `#ffffff`**（`OUTPAINT_FILL`），不得是灰度或半透明 —— 下一步大模型靠白色识别待填区。
   - 输出格式走 **PNG 无损**，不得用 `toDataURL('image/jpeg', 0.9)`（压缩噪点会干扰 AI 判断白区边界）。

4. **缩放机制（★ 新增，对应 2.3）**
   - 目标画布变化后，`tw × zoom ≤ 视口宽` 且 `th × zoom ≤ 视口高`（**画布完整可见**，用户能看到四周白边）。
   - 目标画布变大 → `zoom` 变小（单调性），即"原图在画面里显示得更小"。
   - **原图不被缩放**：`sw === srcW && sh === srcH`（恒为原始像素），变的只有画布尺寸与原图位置 —— 防画质劣化回归。

5. **节点跟随（复用 `78` 的断言）**
   - 保存后 `fitByRatio(tw, th)` 被调用，节点框比例 = `tw/th`。

### 可变性纪律
- `exportCanvas` 每次新建游离 canvas，**不复用、不缓存**；无全局可变状态。
- 画幅拖动 / 原图定位只更新**预览态**（不落盘、不入撤销栈），点确认才导出写回。
- `zoom` 是**派生显示态**：只随画幅 fit 变化，不参与出图计算，避免与 `imgSize` 双写不同步。

### 防返工锚点
后续加「旋转 / 翻转 / 加水印」等纯变换动作，只需往 `exportCanvas` 传不同的 `draw` 回调即可，**不必再碰画布生命周期**——加一个函数，不重写链路。

## 风险与遗留

1. **`ImageEditor` 裁剪根因未定位**：本方案选择绕开而非修复。若日后要恢复全屏裁剪，须先解决"在 React 活画布上就地 `getImageData` + 改尺寸 + 异步回填"的时序问题；在此之前**不删**其代码，但也不再投入。
2. **出图体积 vs 白边保真**：扩图面积放大后 base64 明显变大，会话落盘（见 `72` 号文档）压力上升。但**白边必须 PNG 无损**（JPEG 噪点会干扰下一步 AI 识别），故不能以换 JPEG 来省体积；改为**限制扩图上/下限**（沿用 `OUTPAINT_ZOOM_MIN/MAX` 钳制）来控制体积。
3. **两套裁剪实现并存期**：`ImageEditor`（失效）与 `InlineImageCropper`（可用）短期内共存——**必须先切换入口指向 `InlineImageCropper`**，避免用户仍点到失效的那条。
