# 09-日志系统统一收口规范-2026-08-17

> 目标：梳理当前日志逻辑的现状、指出「乱/不规范」的根因，给出统一收口方案与落地动作清单。
> 范围：仅日志系统。与业务存储（KV / chrome.storage / localStorage）的关系只说明边界，不改动业务存储。

---

## 1. 现状梳理（理清「谁在记日志、记到哪」）

当前日志其实只有**一条真正的物理落盘链路**，但入口分散、概念混淆，容易被误认为有多套日志存储。

### 1.1 链路总览

```
[前端] logger.js  log(category, action, detail, level)
        │  ① console.log/warn/error（浏览器控制台）
        │  ② POST /api/logs （fire-and-forget 上报）
        ▼
[后端] routes/logs.ts  格式化为 [frontend][level][category] action ts #taskId #nodeId detail
        │   打 console → 被 logWriter 接管
        ▼
[后端] utils/logWriter.ts  按天轮转写文件
        ▼
localTool/logs/localtool_18080_YYYY-MM-DD.log   ← 唯一物理落盘点
```

### 1.2 各「存储」与日志的真实关系（澄清误解）

| 名称 | 实现位置 | 真实用途 | 是否存日志 |
|------|----------|----------|-----------|
| Chrome 插件存储 | `storageAdapter.js`（`chrome.storage.local`） | 业务配置 / 非画布类 key 持久化 | ❌ 不是日志 |
| 本地存储 | `storageAdapter.js`（`localStorage`） | 非插件环境的兜底业务存储 | ❌ 不是日志 |
| KV 存储 | `kvStore.js` → `/api/kv/*` → SQLite | 画布快照等跨端共享业务数据 | ❌ 不是日志 |
| 后端 loctool 落盘 | `logWriter.ts` | **唯一真正的日志落盘** | ✅ 就是它 |

> 结论：所谓「4 种日志存储」其实只有 1 种（后端文件落盘）。其余 3 种是业务数据存储，和日志无关。它们仅在 `kvStore.js` 写入失败时，由 `logger.warn(...)` 记一条日志，而那行日志最终也汇入上面唯一的日志文件。

### 1.3 当前行为要点

- **前端 `logger.js`**
  - 输出：浏览器 console + 上报 `/api/logs`。
  - 去重：同一 `(category+action+detail)` 200ms 内合并（`REPORT_MIN_GAP = 200`）。
  - 职责边界：只记高价值不可还原日志——生成 start/success/fail、异常错误、项目切换/新建/删除。**不记**节点增删、连线、改属性等结构操作（可从快照 + undo 还原）。
  - 自动从 `detail` 提取 `taskId` / `nodeId`（兼容 `task_id` / `node_id`），便于按任务/节点 grep。
- **后端 `routes/logs.ts`**：只做**格式化 + console.log**，**不落库、不单独写文件**——寄生在 console 上。
- **后端 `logWriter.ts`**：进程启动时 `initLogWriter()` 接管 `console.log/info/warn/error`，按天轮转写 `localtool_18080_YYYY-MM-DD.log`，保留 `LOG_KEEP_DAYS`（默认 7）天，同时同步输出到原 console（前台可见）。
- **前端实际输出格式**（`logger.js`）：`[log] HH:MM:SS | <category> | <action> | <detail>`
- **后端落盘格式**（`logs.ts`）：`[frontend][<level>][<category>] <action> <iso-timestamp> #<taskId> <nodeId> <detail>`

## 2. 「乱 / 不规范」的根因

1. **命名与概念混淆**：把业务存储（KV / chrome.storage / localStorage）和日志存储混为一谈，容易让人误以为有多套日志落库。实际上它们零关系。
2. **入口分散**：前端直接 `console.log` 散落在各组件、又在 `logger.js` 统一上报，两套输出格式不一致，grep 时噪声大。
3. **上报是 fire-and-forget**：`POST /api/logs` 失败被静默吞掉，日志一旦上报失败即丢失，且无重试/缓冲。
4. **后端日志不落库**：`/api/logs` 只打 console，无法按 `taskId` / 时间窗结构化检索，只能靠文件 grep。
5. **格式未强约束**：`detail` 里 `taskId/nodeId` 靠手动塞字段提取，漏记则无法关联。
6. **无统一 level 规范**：warn / error 使用随意，业务降级 warn 与真错误混在一起。

## 3. 统一收口方案

### 3.1 概念收口（一句话规则）

> **日志只走一条路：前端 `logger.js` → 后端 `/api/logs` → `logWriter` 文件落盘。**
> 业务数据（KV / chrome.storage / localStorage）**禁止**写入日志文件，日志**禁止**写入 SQLite。

### 3.2 入口收口

- 全仓日志统一走 `logger.log(category, action, detail, level)`，禁止在业务组件里直接 `console.log` 记「业务日志」（调试临时 console 除外，但带 `// TODO-debug` 注释，PR 前清掉）。
- `logger` 提供语义化封装（推荐新增，不强求）：
  - `logger.info / warn / error`
  - `logger.gen(taskId, 'start'|'success'|'fail', detail)` —— 生成类统一前缀
  - `logger.project(action, detail)` —— 项目切换/新建/删除统一 `category='project'`

### 3.3 格式收口（强制）

统一单行格式，后端 `logs.ts` 已落实现，前端须保证字段完整：

```
[frontend][<level>][<category>] <action> <iso-timestamp> #taskId=<id> #nodeId=<id> <detail>
```

- `level` ∈ `info | warn | error`（默认 `info`）。
- `taskId` / `nodeId` 必须从 `detail.taskId` / `detail.nodeId` 自动提取；调用方**必须**把这两个字段放进 `detail`，漏记视为不规范。
- `category` 取自枚举白名单（见 3.5），不允许自由字符串。

### 3.4 上报可靠性收口

- `POST /api/logs` 改为**带本地内存缓冲 + 失败重试**（最多 2 次，间隔 1s）；连续失败降级为仅 console，避免阻塞主流程。
- 上报失败不再静默吞：本地 console 一定输出，确保「至少浏览器侧有记录」。

### 3.5 分类枚举（白名单，逐步迁移）

| category | 含义 | 典型 action |
|----------|------|------------|
| `gen` | 节点生成 | start / success / fail |
| `project` | 项目生命周期 | switch / create / delete |
| `error` | 全局异常 | uncaught / unhandledrejection |
| `storage` | 存储降级告警 | kv-fallback |
| `shortcut` | 快捷键 | bind / trigger |
| `system` | 系统/启动 | init / ready |

> 新增 category 需在此文档登记，避免碎片化。

### 3.6 落盘与留存收口

- 保持「按天轮转 + `LOG_KEEP_DAYS` 默认 7 天」不变。
- **暂不落 SQLite**：日志量不可控，落库会撑大业务 SQLite（与 `kv.ts` 防 base64 撑库同一考量）。如确需结构化检索，后续单独开 `logs` 表 + 索引，不在本期。

## 5. 查询约定（最终用户怎么查日志）

- 一个任务的生命周期：在 `localTool/logs/localtool_18080_YYYY-MM-DD.log` 中 grep `#taskId=<id>`。
- 后端原生日志：`[log] / [warn] / [error]`。
- 前端上报日志：`[frontend][level][category] ... #taskId #nodeId`。
- 按天文件天然支持时间窗切片；跨天检索用 `#taskId` 跨文件 grep。

## 6. 审计结果（对照规范的实际偏差 · 2026-08-17）

对当前代码逐文件审计，结论如下。

### 6.1 已符合规范的部分 ✅

- 日志物理落盘唯一性正确：`logger.js` → `POST /api/logs` → `logWriter.ts` 文件落盘，无第二条落库路径。
- 业务存储（KV / chrome.storage / localStorage）确实不写日志文件，日志也不写 SQLite。
- `logger` 已提供 `info/warn/error` 语义封装，且 `taskId/nodeId` 自动提取已实现。
- 高价值日志已接 `logger`：`useNodeGeneration.js`（生成 start/success/fail）、`ErrorBoundary.jsx`、`App.jsx`（项目切换/新建）、`kvStore.js`（KV 降级）。
