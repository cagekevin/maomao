[2] send(text, attachments)                     useAgentChat:406
     · 忙判定：isAgentBusy() → 忙则进 steerQueue（:414）
     · 附件归一化：blob→data / 相对→绝对 / 只认base64的provider转base64（:433-434）
     · 参考图编号目录：refCatalog + setCurrentReferenceImages（:436-449）
[3] buildRequestMessages() 构造 LLM 消息             agentCore.js:227
     · fresh-task 只发本轮（agentCore.js:291）

[4] 双链路：provider → /api/proxy ；否则 → /api/agent/{key}/chat

## 2. 多条发送路径（5 条）

### A · 文本发送 `send`（主流，useAgentChat:406）
```
send(text, attachments)
 ├─ 忙 → 入 steerQueue（不打断）→ return
 ├─ Demo 模式（VITE_AGENT_DEMO='1'）→ runDemoMode()（本地规则引擎，不走真实 LLM）
 └─ 真实模式 → 多轮工具循环（≤ MAX_TOOL_ROUNDS）
      · planning 置位 → roundTrip()（agentRuntime.js:50）→ 工具循环 → 无工具调用结束
```

**关键细节（改这里最容易错）**：
- `MAX_TOOL_ROUNDS` 上限：走满仍不收敛时，`assistant` 被提升到循环外访问（`:470`），否则 `ReferenceError`。
- **finally 是三态落盘**（`:531`）：`!ok ? (aborted?'stopped':'failed') : 'completed'`。`AbortError`→stopped，其他异常→failed。
- **三阶段门禁**：`pausedForConfirm`（`:534`）时 workflow 置 `awaiting_confirm`，**保留 pending**（不清空），等用户确认后 `send('已确认，请按策划执行')` 重建。
- steer 队列续跑在 finally 尾部（`:550-556`），状态置 `planning` 继续。

### A' · 非流式 JSON（`roundTrip` 的 `isNonStream` 分支）
- 触发：`streamMode === 'non-stream'`。
- 请求 `stream:false`，响应完整 JSON，`res.json()` 解析 `choices[0].message.content`。
- 默认不开工具（`ENABLE_TOOLS_ON_NON_STREAM=false`）。
- ⚠️ **历史 bug**：localTool 曾把非流式完整 JSON 误当 SSE 逐行过滤 → 回复截断。已修（`system.ts` 尊重前端 `stream:false` + SSE 剥壳）。改此处必看 `system.ts` 的 `requestStream` 变量。

### B · 图像模式 `sendImageMode`（不经 LLM）
- 提示词 + 参考图 → 构造单个 generation 步骤 → 复用 `execute_plan`（canvasPlanExecutor）直连画布生图。
- 参考图按 `provider.refFormat === 'base64'` 决定是否转 base64。

### C · steer 队列续跑（`sendRef` + `workflow.steerQueue`）
- 任务进行中再发送 → 排入当前对话 `workflow.steerQueue`（per-conversation，切对话不串台）。
- 队列消息标记 `steer: true`、`statusLabel: '已排队'`（`:417`）。
- 任务结束后 finally 自动取队列下一条执行。

### D · Skill 三阶段（`runToolCalls` + 门禁）
- `show_plan_for_confirm`（策划）→ 按 `runMode` → `execute_plan`（执行）。
- **runMode 分级**（`:471-476`）：
  - `auto`（默认）：`show_plan_for_confirm` 仍输出规划/generations，但**不进入 awaiting 确认态**，LLM 直接 `execute_plan`（不弹确认）。
  - `semi`：进入 awaiting 确认态，展示确认门禁，用户确认后才 `execute_plan`。

## 3. 协议层细节（改消息构造必看）

`buildRequestMessages`（agentCore.js:227-362）是最容易踩雷的协议层，4 个隐藏不变量：

### 3.1 fresh-task：历史轮次不进上下文（⚠️ 2026-08-18 新增过渡参数 historyTurns）
- **默认（historyTurns=0）**：历史 user/assistant 消息**一律不进 LLM 上下文**，只发「本轮」user + 同轮工具循环的 assistant/tool（agentCore.js `buildRequestMessages`）。
- **跨轮记忆靠 memory 注入**（摘要/统一风格/已确认信息/备注/最近策划），**跨轮改图靠执行层回退**（`execute_plan` 的 `getLastUserReferenceImages`）。
- **为什么**：彻底消除「跨轮真图堆积 + refCatalog 每轮从 1 重编撞号」→「反推图一却全反推」的 bug。
- **【过渡方案·2026-08-18 决策】**：`buildRequestMessages` 新增第 7 参 `historyTurns`（默认 0 维持原行为，但 useAgentChat 实际会传**设置里配置的值**）。`historyTurns` 由 **AI 助手设置面板可配置**（`AgentChatSettings.jsx`「历史回传轮数」输入框，存 `agent_history_turns`，经 `loadAgentHistoryTurns()/saveAgentHistoryTurns()` 读写，见 `agentModelStore.js`），每次 `send` 的 `buildRequestMessages` 调用时**实时读取**（不缓存，改设置立即生效）。取值：
  - `0` = 不回传历史文字（严格 fresh-task）；
  - `1` = 只回传上一轮文字；
  - `N`（任意非负整数） = 回传最近 N 轮 user/assistant 纯文字；**N 大（如 1000000）时回溯到最早 → 约等于不限**（受 `AGENT_MSG_MAX=60` 消息上限兜底）。
  - 默认值 `6`（`AGENT_HISTORY_TURNS_DEFAULT`）。解决「纯文字对话失忆」（如"反推这张图提示词"→"把提示词优化一下"，第二轮必须知道第一轮反推的文本）。
  - **安全边界（不可破坏）**：`historyTurns>0` 只回传【文字】。历史轮次所有【图片附件绝不内联进上下文】，图仍走 `imageCatalog`「图N」编号 + 执行层 `direct_refs` 反查（`agentCore.js` 历史 user 分支只 `content` 纯文字，无 `image_url`）——否则复发「反推图一却全反推」。
  - **历史 system 一律不回传**：`historyTurns>0` 提前 startIdx 后，循环内显式 `if (m.role==='system') continue` 跳过，system 只认前置注入（准则/systemPrompt/Skill/memory/imageCatalog），避免旧 system 覆盖新准则。
  - **为什么是过渡**：它放宽了 fresh-task「连文字也砍」的副作用，但没治本。真正治本是补齐 memory 自动摘要——`summary` 已由 `maybeCompressSummary`→`compressToSummary` 自动沉淀（见 §5.1），`facts` 仍靠显式「记住」类交互写入。当前 `historyTurns` 默认 6 仍作为过渡并存，待 summary 质量稳定后可回退为 0 走纯 fresh-task + 更强 memory。
  - **改这里会踩什么雷**：改 `buildRequestMessages` 的回传范围必须保住 ① tool 消息配对（assistant 声明 tool_calls 登记 id、tool 命中才保留）② 本轮带图分支（`i===lastUserIdx` 才内联本轮图 + refCatalog）③ 历史图永不内联。单测守护见 `tests/unit/agentLogic.test.js`（5 个过渡方案用例）+ `tests/unit/agentModelStore.test.js`（7 个历史轮数配置边界用例）。

### 3.2 tool 消息配对（agentCore.js:326-355）
- OpenAI 协议要求 `role:'tool'` 消息**必须紧跟带 `tool_calls` 的 assistant 消息**，且 `tool_call_id` 能匹配。
- 实现：维护 `pendingToolIds` 集合。assistant 声明 tool_calls → 登记 id；tool 消息**需命中才保留，否则丢弃**（孤儿消息触发后端报错）。
- **改这里必看**：删消息时若破坏配对，后端会报 `messages with role "tool" must be a response to a preceeding message with "tool_calls"`。

### 3.3 empty tool_calls 过滤（agentCore.js:333-336）
- 空数组 `[]` 是 truthy，若不过滤会原样发给 LLM → 后端报 `Empty tool_calls is not supported in message`。
- 只发「非空」的 tool_calls。

### 3.4 图片目录机制（两种编号并存，容易混）
| 编号 | 位置 | 用途 |
|---|---|---|
| `图N` | imageCatalog 注入 system（agentCore.js:280-290） | 跨轮引用历史图/上一轮生成图，配 `direct_refs` |
| `参考图N` | refCatalog（useAgentChat:441-446）+ `attachment_indices`（0-based） | 本轮参考图精确引用，`attachment_indices` 指向编号 |

- **图本体不进 LLM 上下文**，执行层按编号反查原图（`setCurrentReferenceImages`）。
- 参考图附件带画布坐标 `x/y`，以文本附给 LLM 感知位置（agentCore.js:310-318）。

## 4. 工具调用层（useCanvasAgentTools）

### 4.1 runToolCalls 的 async 逐个 await（agentRuntime.js:198-257）
```js
for (const tc of toolCalls) {                 // 真实是 for...of，不是下标 for
  const r = await callTool(tc.function.name, parseArgs(tc.function.arguments))
  // 结果回填 role:'tool' 消息（按 tc.id 配对）
  // 特殊分支：show_plan_for_confirm / execute_plan 会额外 appendMsg 策划/执行摘要
}
```
- **必须逐个 `await`**：若用同步 `forEach`，`callTool` 异步返回的 `undefined` 会被当"调用失败"误判，触发重试 → **死循环重复建节点**（历史 bug，TASK-006 修复）。
- **两个特殊分支不能漏**（真实代码 `agentRuntime.js:198-249` 内有）：
  - `show_plan_for_confirm` → 走门禁（§12.1），可能 `setAwaitingConfirm` 暂停循环，并 append 策划摘要消息。
  - `execute_plan` → 执行器建节点 + 带参考图生图，append 执行摘要消息（`execution_summary`）。
  - 若照"纯 for 循环回填"重写会丢掉这两条摘要渲染，用户看不到策划/执行进度。
- 改这里**禁止**改回同步循环。

### 4.2 工具分组（~30 个）
读（list_nodes/read_canvas/get_node_details）｜建（create_node/batch_create_nodes）｜改（update_node/update_node_any_field）｜连（connect_nodes/batch_connect_nodes/delete_edge）｜执行（generate_node/execute_plan/show_plan_for_confirm）｜视图（fit_view/zoom_in/zoom_out/focus_node）｜管理（lock_node/group_nodes/undo_ai/move_node）。

- `AGENT_TOOLS` 数组**顺序 = 模型选择优先级**（常用在前）——**这是给模型看的能力清单顺序，不是随机排序**：越靠前模型越倾向先选。加新工具要放在语义合理且模型易触达的位置，放太后基本选不到。
- 工具写画布走 `setNodes`/`setEdges`/`deriveNodes`，并压入 **AI 撤销栈**（`undo_ai`）。

### 4.2.1 工具轴注册表（2026-08-21，阶段2）：加一个工具只需 `registerTool` 一条
> 原静态 `AGENT_TOOLS` 数组已升级为**工具注册表**（`toolRegistry.js`：`registerTool`/`getTools`/`resetTools`）。`AGENT_TOOLS` 现为 `getTools()` 的兼容别名；`buildCanvasAgentToolSchemas`/`buildCanvasAgentTools`/`CANVAS_AGENT_TOOL_NAMES` 全部读注册表。

**加一个画布工具的最小 SOP**：
```js
// 1) 在 useCanvasAgentTools.js 模块内定义工具对象（复用现有工具同构）
const myTool = {
  name: 'my_tool',             // snake_case，AI 会按名调用
  description: '……',            // 越具体 AI 越会用
  parameters: { type:'object', properties:{...}, required:[...] },
  execute: (args, ctx) => ({ ok:true, data:{...} }), // 返回值=LLM 的"眼睛"，写清楚
  // mutating 可选；若写画布需入 undo_ai 撤销栈 → 在注册时标记
}
// 2) 把 myTool 加入模块底部注册块 dep 列表（defs 数组）→ registerTool({...myTool, mutating: ...})
//    之后它自动进入：schema（LLM 能力清单）+ buildCanvasAgentTools 执行 Map + CANVAS_AGENT_TOOL_NAMES。
```
> drawsContract：**写画布工具**的 `mutating` 若为 true，`buildCanvasAgentTools` 会在执行前统一压 AI 撤销栈（可被 `undo_ai` 整体撤回）。mutating 由注册时从 `MUTATING_TOOLS` 派生入条目。
> **⚠️ 时序雷**：注册（`registerTool`）必须先于任何 `getTools()`/`buildCanvasAgentToolSchemas()` 调用，否则工具全消失、AI 无能力。推荐做法：工具定义与注册同在 `useCanvasAgentTools.js` 模块顶部，模块加载时同步注册，顺序天然正确。`resetTools()` 仅供 isolated 测试（清空后需重新注册，**勿在与工具加载共存的测试里调用**）。

### 4.3 callTool 分发（工具名 → 执行函数）
`callTool(name, args, ctx)` 是工具层的**总入口分发器**：
- 拿 `name` 在工具注册表（`getTools()`，原 `AGENT_TOOLS` 别名）里查执行函数；找不到 → 返回"未知工具"错误回填 tool 消息（不抛异常，保证 `runToolCalls` 循环不被打断）。
- 每个工具签名统一收 `args` + `ctx`（`ctx` 带当前 projectId / canvas API / memory / pending 等运行时依赖，由 agentRuntime 注入）。
- 执行结果（无论成功/失败）都序列化成字符串回填 `role:'tool'` 消息，供下一轮 LLM 续跑——**工具的返回值就是 LLM 的"眼睛"**，返回写清楚（比如"已建节点 id=N，含图片 M 张"）模型才能继续决策。
- 写画布类工具内部统一调 `deriveNodes` 建节点，并在同一原子操作里把**整张画布快照**压入 AI 撤销栈。

### 4.4 AI 撤销栈与 undo_ai（撤销镜像于用户 Ctrl+Z，但栈独立且持久化）
- `undo_ai` 本身也是个工具（`useCanvasAgentTools.js:982-995`）：模型说"撤销刚才的操作"时，从 AI 撤销栈弹栈（`popActiveAiUndo`），把快照 `{nodes,edges}` 经 `apply` 回滚到画布。**注意它不调 `useCanvasHistory.undo()`**——`useCanvasHistory` 是用户 Ctrl+Z 的栈，两者刻意隔离（见 `useCanvasAgentTools.js:211-212` 头部注释）。
- **栈在哪**：per-conversation，存在 `conversationAiState.js` 的 `aiUndoStack`（经 `conversationStore` 聚合 re-export，随会话落盘）。**这跟用户 Ctrl+Z 的 `useCanvasHistory` 栈完全分离**——AI 的撤销不污染用户手动操作历史，反之亦然。（2026-08-21 随 conversationStore 拆分，实现从原 `conversationStore.js` 迁至 `conversationAiState.js`；旧行号 `:185`/`:477-499` 已失效，grep `pushActiveAiUndo` 定位。）
- **什么时候压栈**：`wrap`（写工具统一包装，`useCanvasAgentTools.js` 的 wrap 入口）在**每个写画布工具执行前**捕获 `{nodes,edges}` 快照 push 进 `aiUndoStack`（集中于 wrap 一处，不散落到各工具内部）。模型连续建 3 个节点，栈里就有 3 个快照，`undo_ai` 一次回滚一个。
- **为什么原子**：配合 `deriveNodes` 的"建子节点 + 连线"在同一操作内完成（见 §8），wrap 在 wrap 入口整张画布拍快照 → 撤销时节点和连线一起回滚，不会只撤节点漏撤边。
- **边界（已按 `conversationAiState.js` 核实）**：
  - **持久化**：`aiUndoStack` 随 `conversation` 会话落盘，刷新网页 / 重开项目**快照仍在**（不会清空）。
  - **上限 20**：`pushActiveAiUndo` `if (stack.length > 20) stack.shift()`——压满 20 后最旧快照被丢。**测试守护**：`conversationStore.test.js` 实测 push 25 次 → 栈长 20、pop 后 19，回归勿破。
  - **读返回副本**：`getActiveAiUndoStack` `return [...]` 副本，外部改不影响内部栈。

### 5.1 memory 机制（跨轮记忆靠它，不靠原始消息）
`conversationSnapshot.js` 的快照里有个独立的 `memory` 字段（经 `conversationStore.getCurrentMemory`/`setCurrentMemory` 读写），**per-conversation**，结构固定（`conversationState.emptyMemory`）：
```js
{
  summary: '',        // 当前会话的精简摘要（多轮后 LLM 看不到早期消息时靠它回忆）——【已自动沉淀，见下】
  facts: [],          // 用户明确陈述的持久事实（如风格偏好、项目背景）
  lastPlan: null,     // 最近一次策划（show_plan_for_confirm/execute_plan 写入）
  lastSharedStyle: '',// 最近一次共享的画风/样式，供图生图默认延续
  notes: [],          // 零散备注
  global_contract: null,  // 全局契约（canvasPlanExecutor 双保险用，见 §13.5）
  artifacts: null,    // 最近产物引用（节点/任务 id 等，供后续工具反查）
}
```
- **谁写**：
  - `show_plan_for_confirm`（策划落 confirmed 之前）和 `execute_plan`（执行时）都会写 `lastPlan`。
  - 图生图/共享样式类工具写 `lastSharedStyle`、`artifacts`（见 conversationAiState `setCurrentGlobalContract` 同时映射 `lastSharedStyle`）。
  - `setCurrentMemory(m)` 是统一写入口，做 normalize 后落内存 + notify（不单独落盘，随 `setCurrentSnapshot` 落）。
- **【✅ 2026-08-21 后已治本：自动摘要已落地】**：`summary` 字段**不再是空**——`useAgentChat.send` 收尾触发 `maybeCompressSummary()`（`useAgentChat.js`，门槛 `RECENT_KEEP_COUNT=8` 条消息且 60s 节流，fire-and-forget），调用 `contextCompression.compressToSummary` 用 LLM 把历史压成带区段（目标/约束/已定/未完成/节点与图编号/失败）的摘要，写回 `memory.summary`。**只影响发给模型的上下文，不删不改原始消息**。失败/超时只记日志、保留旧摘要，绝不阻塞主流程。这补齐了原 §3.1 `historyTurns` 过渡方案的「治本」方向：纯文字对话（不经 `execute_plan`）现在也能跨轮回忆，但 `historyTurns` 默认 6 仍作为过渡并存（可逐步回退到 0 + 更强 summary）。
- **「学」（promptLearning，已落地）**：`buildRequestMessages` 第 8 参 `learnedContext` 由 `promptLearning.buildLearnedContext(memory, text)` 预生成——从本对话 `memory.lastPlan.generations`（已执行策划的步骤 prompt）提样、脱敏、按相似度+近因挑 top-4，拼成「不可信只读创作数据」注入块（agentCore.js:264-266, 334-336）。空串=不注入。让 LLM 学本项目用户长话表达习惯，不靠全量读画布。
- **「记」项目长期记忆（projectMemoryStore + memoryRetrieval，2026-08-21 已接通全链路）**：
  - `projectMemoryStore` 实现对**项目级**长期记忆的持久化（KV `agent_project_memory_v1_${agentKey}`，按 kind=preference/fact/constraint/decision 分类、脱敏、并发写锁、模块缓存）。
  - `memoryRetrieval` 实现 `rankProjectMemories`（相关度+类别权重+近因 MMR 挑 top-K）+ `buildProjectMemoryBlock` + `buildProjectMemoryContextFromStore`（同步按 query 取注入块，**读源：当前项目已落库记忆，非暂存**）。
  - **写入闭环（已接通）**：`useCanvasAgentTools.memorySuggestTool`（`memory_suggest` 工具，已注册）做校验/脱敏 → `setActivePendingMemorySuggest` 暂存 + `setAwaitingConfirm(true)` 复用确认门禁 → 用户确认后 `useAgentChat.confirmPendingMemorySuggest`（:690）读暂存 → `projectMemoryStore.saveProjectMemory` 落库 + 清暂存。
  - **读取注入（即读即注入，但门槛为空串）**：`send` 每轮经 `buildRequestMessages` 第 9 参调 `buildProjectMemoryContextFromStore(agentKey, '', text)`。⚠️ 注意第二参 `projectId` 恒传 `''`（该函数注释已声明"项目记忆不分项目，参数已弃用"），即按 agentKey 全局取；若 store 无已确认记忆则返回空串，不注入。此读取通路已实装，但**属于软增强**：无记忆时零开销、有记忆时补上下文，不阻塞主流程。
- **谁读**：`buildRequestMessages`（agentCore）构造发给 LLM 的 messages 时，把 `memory`（summary/lastSharedStyle/facts/notes/lastPlan/全局契约）+ `learnedContext` 序列化进 **system 或固定前缀消息**，作为"长期记忆"注入。这样即使 fresh-task 把早期原始消息砍了（§3.1），模型仍能从注入块回忆上下文。
- **为什么不能只靠原始消息**：fresh-task 机制下，每轮只发「system + 本轮 user/tool」，历史轮次的 user/assistant 文本被裁掉。若没有 `memory.summary`/`facts`，模型第 5 轮就忘了第 1 轮用户说的"用国潮风"——所以**持久偏好必须进 memory.facts（或项目记忆），不是藏在历史消息里**。
- **normalizeMemory**：读回时兜底（缺字段补默认、数组非数组纠正，`conversationState.normalizeMemory`），防止旧 localStorage 数据缺字段导致 `memory.xxx` undefined 报错。
- **跨项目隔离**：memory 跟着 `agentKey`（= 项目）走，切项目自动切 memory。

### Provider 数据来源（决定走哪条链路的根因）

- **主供应商**：`providerStore.js` 的 `isPrimary`（`:70`）。`useCanvasAgentTools` 从主供应商读 `provider`。
- **模型分类**：provider 模型分三类 `image_models / chat_models / video_models`（localTool providers.ts:10）。**AI 助手聊天用 `chat_models`**，生图用 `image_models`。
- **KV 同步**：改主供应商时 `providerStore.js:179` 会同步写 localTool KV 的 `active_api_endpoint`（跨端读当前生效 endpoint）。
- **判定规则**：roundTrip（agentRuntime.js:50）里「provider 存在」= 主供应商存在且启用；存在 → proxy 链路，否则 → agent 链路。

### 6.1 roundTrip 双模式（流式 / 非流式）
`roundTrip(ctx, requestMessages, signal, onStream)` 是 LLM 通信的唯一出口。**分流由 `streamMode`（`agentModelStore` 的聊天模型配置）决定**，不是 `body.stream` 字段：
- `roundTrip` 内部 `const streamMode = loadAgentChatModel()?.streamMode || 'stream'`（`agentRuntime.js:53`），`isNonStream = streamMode === 'non-stream'`（`54`），再 `llmBody.stream = !isNonStream`（`60`）。
- 改非流式行为要看 **`agentModelStore.streamMode`**，不是去改 `llmBody.stream`。

**(1) 流式模式（streamMode 为 'stream'，默认）**
- `fetch` 拿 `ReadableStream`，用 `reader.read()` 逐块读 `Uint8Array` → `TextDecoder` 解码成文本片段（`agentRuntime.js:125-127`）。
- **SSE 增量解析**：累积 buffer，按 `\n\n` 切 event，逐行剥 `data:` 前缀；`[DONE]` 结束。每个增量 delta 经 `parseSSEChunk` 抽出 `content` 增量 + `tool_calls` 增量（注意 tool_calls 是分片到达的，要逐片拼接 id/index/function.name/arguments）。
- **50ms 节流 flush**：增量不是每片都 setState，而是攒进 pending 缓冲，每 50ms（`setInterval`/时间判断）flush 一次到 UI → 打字机流畅且不高频重渲染（历史 bug：每片 setState 导致大回复卡死）。
- 流式终止：后端 `[DONE]` 或 `AbortController.abort()`（用户点停止）。
- 前端 `Accept: text/event-stream`，system.ts 收到 SSE 走 `requestStream` 流式 pipe 分支（`system.ts:434`）。

**(2) 非流式模式（streamMode === 'non-stream'，isNonStream 分支）**
- **触发**：AI 助手设置里把聊天模型标为「非流式」（`streamMode==='non-stream'`），**前端主动把 `llmBody.stream` 置 false、Accept 改 `application/json`**（`agentRuntime.js` 的 `stream = !isNonStream` 与 `accept = isNonStream ? 'application/json' : 'text/event-stream'`）。
- **前端容错解析（非 `res.json()`）**：`roundTrip` 非流式分支先 `await res.text()` 整段读出，再经 `safeParseNonStreamJSON`（`agentRuntime.js` 内，三级兜底：①直接 parse ②去 ```json 围栏 ③抽首个完整 `{…}` 对象，全失败返回 null）解析。**绝不**用旧的 `await res.json().catch(()=>({}))`——该写法会把网关/代理缓冲断流截断的非法 JSON 静默吞成 `{}` → content 全丢且无提示（历史 bug，已修）。解析失败时把原始文本当 content 保留（渲染层 `extractImageSpans` 仍能抽 URL 出图），并打 ERROR 日志，不静默丢内容。整体回填一条 assistant 消息。
- **proxy 链路经 httpRequest**：provider 存在时 `/api/proxy` 走 `base/httpClient.httpRequest`（SSE 模式 + `timeoutMs:0` 不掐断 + `parseJson:false` 返回原始 Response），回炉的是 HTTP 语义，SSE 行协议豁免；直连官方 `/api/agent/...` 分支保留原生 `fetch`。两条链路最终都进上述 `safeParseNonStreamJSON`。
- **system.ts 侧强一致（localTool 侧，仍成立）**：`requestStream = p.stream !== false`（`system.ts:378`）——前端 `stream:false` → `requestStream=false`，此时**即使上游返回 `Content-Type: text/event-stream`，也强制走完整 `arrayBuffer` 非流式分支（`system.ts:479` 起），不进 SSE pipe 分支**，避免"流式壳包着非流式内容"被逐行过滤丢字。这是 localTool 侧的第一道保险；前端 `safeParseNonStreamJSON` 是针对"已到前端但仍被截断"的第二道保险，二者互补。
- ⚠️ **非流式与"上游代理缓冲 SSE"是两回事**：非流式时根本不走 SSE 分支，谈不上"退化"；见 (3) 的精确边界。

**(3) 上游 SSE 被缓冲的退化（仅限流式子场景）**
- 仅当 `streamMode==='stream'`（前端要流、system.ts `requestStream=true`）时：agent 链路走 `fetchWithProxy`，本机代理可能把 SSE 缓冲成一次性大块返回（`Accept-Encoding: identity` 主动规避 gzip 也只是减少缓冲，不保证逐行）。此时仍进 `system.ts:434` 流式 pipe 分支，前端 `parseSSEChunk` 按 `\n\n` 切整个 buffer（不依赖"边收边解"）**功能正确**，只是打字机退化成"整段到达"。**这是已知 trade-off，不是 bug。**
- 若 `streamMode==='non-stream'`，本条**不适用**（走 (2) 的完整 JSON 分支）。

### 6.2 localTool system.ts 的 stream 尊重与 SSE 剥壳
- **`requestStream` 符号确实存在**（`system.ts:371` 声明、`378` 赋值、`434` 判定）——改非流式相关逻辑 grep `requestStream` 即可定位。
- **尊重前端 stream 意图**：`requestStream=false`（前端 `stream:false`）时，无论上游 content-type 是否 SSE，一律走完整 `arrayBuffer` 分支（`:479`），不剥壳、不逐行。
- **SSE 剥壳（仅 `requestStream=true` 且上游真 SSE）**：`:434` 分支剥 `data:` 前缀、拼接 `data:` 行、遇 `[DONE]` 收尾，经 `createSSEParserTransform` 还原纯 JSON 后逐块 pipe 给前端解析器。
- **信封翻译**：上游常包 `{code, data}` 信封，system.ts 剥掉，前端直接拿 `data`（`agentChat.ts`/`chatApi.ts` 统一处理）。
- **4xx 错误不走流式 pipe**：`:411` 起直接读 raw body 透传真实错误 JSON，避免前端只看到状态码看不到原因（历史 bug：400 被当 SSE 过滤只剩状态码）。

### 6.3 ENABLE_TOOLS_ON_NON_STREAM（非流式也允许工具）
- 默认非流式分支**不传 tools**（`withTools = !isNonStream || ENABLE_TOOLS_ON_NON_STREAM`，`agentRuntime.js:56`），历史上为了简单只回文本。
- `ENABLE_TOOLS_ON_NON_STREAM` 开关打开后，非流式也传 `tools`（`stream:false` + `tools` 同时发），且响应里 `message.tool_calls` 会被解析回填（`agentRuntime.js:113-118`），走 `runToolCalls` 续跑 → "非流式 provider"也能完整用上策划/执行链路（半自动/全自动都不受影响，只是首响不是打字机）。
- 改这里要确认：非流式 JSON 的 `tool_calls.arguments` 是**完整字符串**（不是分片），解析走 `:113-118` 的整段 map，别复用流式的"增量 append"。

## 8. 建子节点统一契约（deriveNodes）

- `buildSpawnNodes` / `applySpawnSnapshot` / `makeChildId`。
- 收敛 9 处「建子节点 + 连线」为统一快照构造，配合 `CanvasEdgesContext.record` **原子进 undo 栈**。
- **为什么原子**：`useCanvasHistory.record` 注释明确"先 setNodes 再 record 必须显式传快照"，否则 undo 丢新增节点。
- 子节点 data 构造保留在各节点（每处业务不同），统一工具只管骨架（位置/edge id/原子快照）。

## 9. 状态机（InputStateMachine）

`idle → planning → running → (awaiting_confirm | failed) → idle`

- **awaiting_confirm 不是死态**：它等用户点「已确认」→ `handleConfirmPlan`（`:309`）翻 `awaitingConfirm=false` 并**重发"请按策划执行"** → 新一轮 `send` → `planning → running → completed`，不是自动回到 running。状态机图里 `awaiting_confirm → idle` 表示"用户取消/清空"路径；"确认后执行"是经"重发消息"重新进入 `planning`（见 §12.3 阶段3）。
- 发送锁：`sendingRef.current = true`（`send` 开头，`:423`），finally 释放（`:548`）。
- 忙判定：`isAgentBusy()` = 发送锁 + 状态机 running（复合判定，防并发双发）。图像模式用同一把锁（`sendImageMode:577` 也查 `isAgentBusy()`）。
- 停止：`AbortController.abort()` → catch `AbortError` → `setStatus('idle')` + `stripStreaming()`（`:515-526`）。
- **stripStreaming 清所有 streaming 残留占位**（循环中途出错可能残留多轮，不只最后一个）。

## 12. 半自动 / 全自动、图像 / 智能模式、Skill 的实现

### 12.1 半自动（semi） vs 全自动（auto）——执行分级

**为什么需要分级**：早期所有任务都让 LLM 调 `show_plan_for_confirm` 并强制 `awaiting` 确认，导致"发个简单信息也要确认"。大雄是有分级的，已对齐（见 `useAgentChat.js:115-126` 头部注释）。

**状态存储**：`runMode` 存 `conversationStore`（per-conversation，默认 `'auto'`），由 `getCurrentRunMode / setCurrentRunMode` 读写（`conversationStore.js:340-356`）。**不随 `send` 传参**，而是执行工具时现场读。

**决策点**：在 `useCanvasAgentTools.js` 的 `presentPlanTool`（即工具 `show_plan_for_confirm`，`:676-729`）内：

```js
// useCanvasAgentTools.js:717-723
const hasSkillNow = Array.isArray(getCurrentSnapshot()?.skills) && getCurrentSnapshot().skills.length > 0
const needConfirm = hasSkillNow || getCurrentRunMode() === 'semi'   // 有 Skill 必确认；无 Skill 看 runMode
setAwaitingConfirm(needConfirm)
```

| 场景 | `needConfirm` | 行为 |
|---|---|---|
| 无 Skill + `auto`（默认） | `false` | `show_plan_for_confirm` 照常展示规划/步骤卡片，但**不弹确认按钮**，LLM 继续 `execute_plan` 直接执行 |
| 无 Skill + `semi` | `true` | 进入 `awaiting_confirm` 门禁，展示确认按钮，用户确认后才 `execute_plan` |
| 有 Skill（无论 runMode） | `true` | 始终走三阶段，必须确认策划 |

**门禁硬约束**：`execute_plan` 执行时若 `getAwaitingConfirm()` 为真直接拒绝（`:793-795`），防止 LLM 在用户未确认前出图。只有确认按钮 `handleConfirmPlan`（`:309`）翻转 `awaitingConfirm=false` 后重发，才会真正执行。

**循环暂停**：`send` 的 `finally` 检测 `pausedForConfirm`（由 `getAwaitingConfirm()` 在循环内 `:506` 设置）→ `workflow.status='awaiting_confirm'` + 状态机 `awaiting_confirm`，`return` 不再自动跑 steer 队列（`useAgentChat.js:534-542`）。

### 12.2 智能模式（agent）vs 图像模式（image）

**切换**：`setInputModeAndPersist`（`AgentPanel.jsx:178`），UI 两个按钮「智能 / 图像」（`AgentPanel.jsx:605-616`）。`inputMode==='image'` 时 `handleSend` 改走 `sendImageMode`（`:287-295`），否则走 `send`（`:305`）。

**智能模式 = 经 LLM**（`send`，`useAgentChat.js:407`）：
- 走完整「理解→规划→执行」工具循环（§2-A），`buildRequestMessages` 组装 LLM 上下文，`roundTrip` 调模型，`runToolCalls` 执行画布工具。
- 受 `runMode`（§12.1）与 Skill（§12.3）影响。

**图像模式 = 直连生图，不经 LLM**（`sendImageMode`，`useAgentChat.js:573-641`）：
- 提示词 + 参考图 → 构造单个（或拆分多个）`generation` 步骤 → 直接 `callTool('execute_plan', { generations, auto_run:true })` 在画布生图（`:616`），**完全绕过 LLM 与工具循环**。
- 不进入 `awaiting` 门禁（无 `show_plan_for_confirm` 调用）；`runMode` 按钮在图像模式下禁用（`:768`）。
- **多参考图「分别改图」拆分（TASK-008）**：`imageModeLooksLikePerReferenceEdit(prompt, refCount)`（`agentCore.js:461`）判断语义（"分别/各自/每张/各改…"），命中且参考图 ≥2 张 → `buildPerReferenceGenerations`（`agentCore.js:481`）拆成 N 个独立 generation，每步 `attachment_indices:[i]` 只挂自己那张；否则整批塞单 generation（`:601-612`）。参考图先 `setCurrentReferenceImages` 写入 `refPool`（`:600`），`execute_plan` 才能按编号取到。
- 参考图按 `provider.refFormat === 'base64'` 决定是否转 base64（`:587`）。

### 12.3 Skill 三阶段实现

**Skill 是什么**：用户从设置页或面板启用的「批量生图剧本」（如"5主图+8详情"），原文无损注入 system，约束 LLM 的生图规则（角色/结构/文案不可覆盖）。

**启用链路（仅智能模式 send 路径）**：
1. `applySkill`（`:139`）把 Skill 加入 `activeSkills` → `useEffect` `:136` 写 `conversationStore.setCurrentSnapshot({ skills })`。
2. `useAgentChat({ skills: activeSkills })`（`:166`）→ `skillsRef`（`:212`）→ `send` 内 `buildRequestMessages(..., skillsRef.current, ...)`（`useAgentChat.js:484`）。
3. `buildRequestMessages` 把每个 Skill 原文包成 `===== Skill 文档开始/结束 =====` 注入 system，并追加 `SKILL_EXECUTION_RULES`（`agentCore.js:242-247`）。

⚠️ **图像模式（sendImageMode）不走这条链路**：`sendImageMode`（`useAgentChat.js:573-644`）构造 user 消息时显式 `skills: []` 置空，且直接调 `callTool('execute_plan', ...)` 绕过 LLM / `runToolCalls` / `buildRequestMessages`，所以**图像模式不注入 Skill 原文**，也不会触发 Skill 三阶段门禁（链路 B 见 §13.2）。改 Skill 注入逻辑只需动智能模式 `send` 路径，无需碰 `sendImageMode`。

**`SKILL_EXECUTION_RULES`**（`agentCore.js:84-99`）规定三阶段：
- **阶段1 策划**：LLM 在回复正文用 json 代码块输出完整 `generations` 数组，并调 `show_plan_for_confirm`（只传 `plan_text`），**不直接 `execute_plan`**；前端从正文解析并 `setActivePendingGenerations` 暂存（`useAgentChat.js:493-496`）。
- **阶段2 等待确认**：`show_plan_for_confirm` 内 `needConfirm=true`（有 Skill 必确认，§12.1）→ `setAwaitingConfirm(true)` → 循环暂停等用户确认。
- **阶段3 执行**：用户点「已确认」→ `handleConfirmPlan`（`:309`）翻 `awaitingConfirm=false` 并重发"请按策划执行" → LLM 调 `execute_plan`，执行器自动从阶段1 暂存的 `pendingGenerations` 读 generations（`:798-800`），**无需 LLM 再传超大 JSON**。

**统一风格契约**：阶段1 须给 `global_contract` 三字段（visual_positioning / unified_style_prompt / unified_negative_prompt），`show_plan_for_confirm` 收到后 `setCurrentGlobalContract`（`:713`），后续每步 prompt 头部原样携带，保证整批风格统一。

**不变量**：Skill 与 `runMode` 相互独立——选 Skill 不会自动切 `runMode`，且 Skill 三阶段始终需确认（`:719`、`AgentPanel.jsx:764` 注释）。

- **A 与 B 的分叉点**：`AgentPanel.handleSend`（`:287-305`）按 `inputMode` 选 `sendImageMode` 还是 `send`。**改发送逻辑必须两条都看**。

### 13.5 链路 A/B 的共同终点：canvasPlanExecutor 深度（必读）

链路 A、B 最终都汇聚到 `execute_plan → canvasPlanExecutor.executePlan`（`canvasPlanExecutor.js`）。它不是简单建节点，而是**多步编排执行器**，对齐大雄 canvas-agent 的 plan-executor。改"出图行为/前序依赖/参考图"全在这里：

- **Wave1 / Wave2 分批**：`depends_on_previous` / `use_previous_results` / `depends_on_steps` 任一为真 → 进**依赖批(Wave2)**，否则**独立批(Wave1)**（`:143-148, 232-233`）。Wave1 先串行建节点（防 `addNodes` 竞态）再 `Promise.all` 并行跑图（`:321-345`）；Wave2 仅当 Wave1 全部成功才执行，否则跳过并写明"前置未全部成功"（`:347-450, 425-429`）。
- **前序依赖靠"连线"而非运行时注入**（`:10-12`）：Wave2 把成功的前序节点 `addEdges` 连到本步，下游 `useConnectedInputs` 自动读上游 `data.imageUrl` 当参考图，**无需改下游节点代码**。
- **全局单飞锁**（`:19-26, 214-224, 464-466`）：`executingPlan` 模块级布尔，同一时刻只许一套批量生成在跑，防"用户手动点 + AI 触发"或"两个入口同时 execute_plan"导致重复建节点/重复计费；带 `EXECUTING_PLAN_TIMEOUT=120s` 超时兜底，正常由 `finally` 释放。
- **global_contract 双保险锁**（`:259-264`）：执行层把 `visual_positioning / unified_style_prompt / unified_negative_prompt` 三字段**逐字拼到每步 prompt 头部**（前缀 `[统一风格锁定]`），即使规划层漏带，执行层也补——这是整批风格统一的最终兜底。
- **依赖批 prompt 改写（不是只连线）**（`:28-140, 380-393`）：`dependency_mode` 为 `fusion` → `buildFusionPrompt`（挂全部前序成功图 + 融合提示词）；`product_reference` → `buildProductReferencePrompt`（只挂产品定稿、禁止叠用户上传图，防"用户图+产品定稿"两张混喂）；这是 6 个平移自大雄 L10055-10172 的纯函数。
- **兜底自动识别（TASK-012 缺口）**（`:348-363, 369-393`）：用户要"融合"但 LLM 没给 fusion 步 → 自动追加融合步；对话含"详情页套图/系列"但 LLM 漏标 `dependency_mode` → 强制 `product_reference`。**下个 AI 别删这些兜底**，否则回归"漏标就不融合/不套图"。
- **artifact 跨步资产注入**（`:394-409`）：依赖步声明 `input_artifact_ids` → 从 `artifacts` 表取 url 写进 `data.images`（与连线并存双保险）；声明了但资产表无 url → 明确报失败，**不要口头猜依赖**。

**图生图参考图解析优先级（最易踩坑，见 `useCanvasAgentTools.js:737-766` 注释）**：
1. `direct_refs`（优先，仅独立步骤）：引用历史图/上一轮生成图 url，执行层 `getCurrentImageMap()` 反查成"图N"，prompt 里"图N"→"第X张参考图"。

3. 无参考图：`use_attachments=false`，**不挂任何图**。
⚠️ **跨轮生成结果图（lastResults）彻底关闭**（`use_last_outputs=false`）：绝不自动挂历史生成图，只有 `direct_refs` 明确引用时才用。
**历史 bug 根因**（"反推图一却全反推"反复改不对）：① `direct_refs` 与 `attachment_indices` 优先级曾搞反；② `attachment_indices` 未严格按 `use_attachments` 语义（无附件应清空）；③ 曾考虑自动挂历史生成图，违反大雄原则。改参考图逻辑时严格按 ①②③，别重蹈。

### 13.6 三处易错的实现细节

- **genParams 模块级单例**（非 props 贯穿）：`AgentPanel` 生图参数区 → `setGenParams()`（`useCanvasAgentTools.js:44`）写入模块变量 → `execute_plan` 读取传给 `canvasPlanExecutor`。原因：工具层非组件树，props 贯穿链路过长；复用 `taskStore.currentTaskId` 既有模式（`:21-30`）。注意它**不走 React 状态**，改参数区后若 `execute_plan` 读不到，先查 `getGenParams()` 而非找 props。
- **proxy 双链路判定（roundTrip）**：`provider` 存在（主供应商启用）→ 走 `localTool /api/proxy`（`:64-86`），body 里 `url` 按 `protocol==='openai'` 拼 `openai://chat/completions`（伪协议，localTool 拼 base+key）或原样透传 `base_url + /v1/chat/completions`；否则直连 `endpoint`（即 `/api/agent/:key/chat`）。**加新供应商只动 D 链路（/api/proxy + providers.ts），别动 roundTrip 的 agent 分支**。
- **pendingGenerations 暂存（避免超大 JSON 走 tool 参数）**：阶段1 LLM 在回复正文输出 generations JSON（对齐大雄），`useAgentChat` 解析后 `setActivePendingGenerations`；`show_plan_for_confirm` 也 `setPendingGenerations` 兜底（`:716`）。`execute_plan` 优先读暂存，参数里 `generations` 仅兜底、`required: []`（`:785-787`）。⚠️ 不要把 generations 强制塞进 tool_calls.arguments——长 prompt 会让 SSE 解析失败（这是当初拆正文通道的原因）。

### 13.7 链路 D 下半段：出图后发生了什么（节点→任务中心→落盘）

链路 A/B/C 经 `execute_plan → canvasPlanExecutor` 建节点并 `runNodeGeneration`，真正的"出图"在 `imageApi.js` / `videoApi.js` / `chatApi.js`（均经 `localTool:18080 /api/proxy`）。这后半段最容易出 bug 且文档一直空白：

- **runNodeGeneration 的并发地基**（`taskStore.js:306`）：`genActive >= MAX_CONCURRENT_GEN` 则**返回 false（未触发）**，节点保持待生成态、用户可手动点——不是报错。执行器 `await runNodeGeneration(id)` 拿 `start()` 返回的 `{ok, resultUrl}`（新版 `useNodeGeneration` 契约），供前序依赖/多图编排。
- **执行器为何要"轮询等待节点注册"**（`taskStore.js:268-275` + `canvasPlanExecutor.js` 的 `ensureNodeReady`）：执行器用 `ctx.addNodes` 直接建节点，React **异步渲染**后 `PromptNode` 才在 `useNodeGeneration` 的 effect 里 `registerTaskRetry`。若执行器在注册前就 `runNodeGeneration`，会因找不到回调返回 false。故执行器 `addNodes` 后**轮询 `hasRegisteredTaskRetry(nodeId)` 确认注册完成再跑**。⚠️ 改节点建链/渲染时序时，这层等待不能省。
- **X-Task-Id 贯穿（前端 task_id ↔ 网关 thread_id 断链修复）**（`taskStore.js:25-31`）：前端自造 `task_id` 是主键却从不传给 localTool/网关，导致和 Lovart `thread_id` 断链、无法关联查询。`setCurrentTaskId(id)` 暂存当前生成 id，`imageApi/videoApi` 的 `proxyRequest` 读它加 `X-Task-Id` header 贯穿（`imageApi.js:38`），localTool/网关据此把 `task_id ↔ thread_id` 关联落库。**改生图请求头/任务流时别丢这个 header**。
- **刷新丢图坑（已规避，别回归）**（`taskStore.js:190-193`）：节点 `data.imageUrl` 若只存"上游原始 URL"，刷新后该 URL 可能失效/是临时地址 → **画布丢图，而任务中心读的是已落盘的 `/files/tasks/` URL → 任务中心有图、画布没图的错位**。解法：任务完成时 `saveResultToTasks` 落盘镜像 URL，并经 `eventBus.publish('agent:task-completed', {resultUrl: 已落盘URL})` 广播，节点监听后回写 `data.imageUrl` 为落盘地址（`promptNodeIntegration` 集成点）。⚠️ 任何改"节点存哪张图"的逻辑都要走落盘 URL，不要直接存上游 URL。

### 13.8 异步恢复与刷新不丢图（pollTask.js）

- **为什么只轮询异步任务**（`pollTask.js:1-23`）：前端刷新网页 ≠ 网关重启。异步任务（生图 async 模式/视频）提交后网关继续跑，前端只丢了"等结果"的请求。靠已落库的 `pollTaskId`（网关返回的 `task_id`，`taskStore.setTaskPollId`）经 `localTool /api/v1/gateway/task/{id}` 重查补回状态。文本/生图 sync 是同步阻塞、无 `task_id` 可查 → **天然跳过**（对齐官方只恢复视频任务）。
- **轮询节流**：`POLL_INTERVAL=5000` + `MAX_PER_ROUND=5`（一次刷新几十个任务不炸网关），`2s` 检查 `5s` 节流（`pollTask.js:29-33,114-122`）。
- **结果 URL 提取差异**：图片 `result.images[0].url`（网关包成 `[url]` 需取 `[0]`）；视频 `video_url` 顶层映射（`pollTask.js:37-58, 166`）。
- **网络抖动不误判失败**：查询异常时 `return false` 保持 running，下轮再试，避免刷新后误报 failed（`pollTask.js:67-69`）。
- **完成广播**：`pollOneTask` 完成也 `publish('agent:task-completed', …)`（`pollTask.js:80-82`），与同步路径共用同一回写通道——这是"刷新后任务继续跑直到返回"的闭环关键。
