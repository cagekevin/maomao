# 72 · 会话落盘 base64 体积降级 — 根因与修复代价分析

> 日期：2026-08-29
> 触发现象：`installHook.js:1 [warn] ... 会话落盘触发体积降级 | {"key":"agent_conversations_...","rawBytes":5465693,"budget":2097152}`
> 背景：用户把画布上的图发给 AI 助手后，会话体积飙到 ~5.2MB，超过 2MB 落盘预算，触发 `volumePolicy` 降级。

---

## 一、现象本质（结论先行）

这条 warn **不是 bug，是"安全网"的正常告知**：
- 它说明"为了不撑爆 localStorage 配额（避免 `QuotaExceededError` 弹失败 Toast），系统已把落盘快照裁剪/压缩到 2MB 内"。
- 降级作用在**投影副本**（`applyConversationBudget` 只对 `normalized` 副本裁剪），**内存态不动**，当前对话无损。
- 影响的只是**刷新后从存储恢复的旧上下文变短**（较早文字 / `memory.summary` 可能被截断）。

---

## 二、根因链路（为什么带图就爆）

### 2.1 画布上的图是什么形态
`src/components/nodes/ImageNode.jsx`（上传/替换）：
- 优先 `uploadFileToLocal` → 拿到 `/files/xxx` 持久路径（刷新不丢）；
- **仅当上传失败**才回退 `fileToDataUrl` 变 base64。
- 正常情况：画布图节点 `data.url` = `/files/xxx`，**本身不占存储**。

### 2.2 但发给 AI 时被强制转 base64
用户点"把画布图发给 AI"，附件 url 来自 `n.url`（即 `/files/` 路径），进 `normalizeImageUrlForSend` 后走本地图分支：
```javascript
// src/components/base/imageUrl.js
// 本地图（/files/）：压缩到≤1920 保持原格式 → base64
const { dataUrl } = await compressImage(compressable, { maxSize: MAX_SEND_DIM, keepOriginalFormat: true })
if (dataUrl) return dataUrl
```
→ 返回 `data:image/...;base64,...`。

**设计两难**：AI 网关（apimart-gateway）是独立服务，读不到你本机 `/files/` 路径，所以发送出口必须"打包"图片——唯一通用办法是 base64 内联进 HTTP body，让网关能看见图。这是 `preferBase64` 注释所述的「联邦网关 / 远程 provider 自包含」。

### 2.3 但 base64 也跟着进了存储（真正的设计疏漏）
`useAgentChat.js` 构造 `userMsg` 时：
```javascript
userMsg.attachments = await normalizeAttachmentsForSend(attachments, { preferBase64: ... })
// ...
setHistory([...getCurrentSnapshot().messages, userMsg])   // 进内存态
```
`userMsg.attachments[].url` 此时已是 **base64**。随后 `setCurrentSnapshot` → `commit` → `persistDebounced` → `applyConversationBudget` → 落盘 localStorage。

结果：**同一份含 base64 的消息既用于发送，又被原样存进会话快照**。base64 比原图大 ~33%，多张图叠加 → 整包 5.2MB > 2MB → 降级。

## 三、关键事实：存储里的 base64 是"死重"

`src/components/agent/runtime/agentCore.js` 343-345 行（`buildRequestMessages`）：
```javascript
// 历史 user 消息（含 historyTurns 回溯范围内的）：图一律不进上下文，仅保留纯文字
// （不含 refCatalog/坐标，避免撞号干扰；也无 image_url，杜绝历史真图堆积）。
out.push({ role: 'user', content: m.content || '' })
```

即：AI 回看历史时**只取 `m.content`（文字），从不读取 `m.attachments[].url` 的图**。
历史带图经 `normalizeAttachmentsForSend` 生成的 base64，**在回复旧消息时根本不会被重新使用**。

→ 存储里那些 base64 纯粹是占体积的死数据。

---

## 四、修复方案 A′（最终推荐）：保留 originalUrl，落盘时换回 /files/

> ### ⚠️ 前两轮结论作废声明（重新审计已纠正）
> 本文档前版曾给出"剥离 base64、置空 url"的方案，基于两个**错误结论**，现予推翻：
> 1. ❌ 误判"UI 不渲染历史消息图"——搜索范围错误（只搜 `src/components/agent/**/*.jsx` 得 0 命中）。
>    ✅ **实际**：`AgentPanel.jsx` 的渲染组件 `src/components/panels/AgentMessage.jsx` 247-254 行**明确渲染** user 消息附件缩略图：
>    ```jsx
>    {message.attachments && message.attachments.length > 0 && (
>      <div className="flex flex-wrap gap-1 justify-end">
>        {message.attachments.map((a, i) => (
>          <button ... onClick={() => openZoom(a.url)} title="点击查看大图">
>            <LazyImage src={a.url} alt="" className="w-full h-full" />
>    ```
>    `LazyImage` 对空 src 显示"图片加载失败"占位（62-66 行）→ **置空 url 会让刷新后历史图全变破图**。
> 2. ❌ 误判"base64 无法反解成 /files/ 文件名，故只能剥离"。
>    ✅ **实际**：**根本不需要反解**。原始 `/files/` 路径在 `normalizeAttachmentsForSend` 转换**之前**就存在于入参 `a.url` 里，只要在该函数展开时保留为 `originalUrl` 字段即可（见 §4.1）。

### 4.1 核心思路（同步、无 async、不新建文件）

**改动点 1（发送侧，保留原始路径）**——`agentAttachments.js` 34 行：
```javascript
// 现状
attachments.map(async (a) => ({ ...a, url: await normalizeImageUrlForSend(a?.url, { preferBase64 }) }))
// 改为：保留原始 url 供落盘回显（仅多一个字段，发送行为不变）
attachments.map(async (a) => ({ ...a, originalUrl: a?.url, url: await normalizeImageUrlForSend(a?.url, { preferBase64 }) }))
```

**改动点 2（落盘侧，投影副本换回 /files/）**——`conversationState.js` 的 `persistConversation`，在 `applyConversationBudget` **之前**：
```javascript
// 伪代码（示意，不落地）：同步纯函数，仅作用于 normalized 副本
function restoreOriginalUrls(messages) {
  return messages.map((m) => {
    if (!Array.isArray(m.attachments)) return m
    return {
      ...m,
      attachments: m.attachments.map((a) => {
        // 仅当「当前 url 是内联 base64」且「originalUrl 是可落盘的安全地址」时换回
        const isInline = typeof a.url === 'string' && a.url.startsWith('data:')
        const safe = typeof a.originalUrl === 'string' && a.originalUrl &&
                     (a.originalUrl.startsWith('/files/') || /^https?:/i.test(a.originalUrl))
        return isInline && safe ? { ...a, url: a.originalUrl } : a
      }),
    }
  })
}
```

**为什么这样是对的**：
- 内存态 `url` 仍是 base64 → **发送照常**（网关需要自包含 base64）；
- 落盘副本 `url` 换回 `/files/xxx`（约 100 字节）→ **体积从 MB 级暴降到 KB 级**；
- 刷新后 `LazyImage src="/files/xxx"` → 经 `useRenderImageResolver` 补全为绝对地址 → **图正常显示**（且是原始分辨率，比压缩后的 1920 更好）；
- **不新建任何文件**（引用的是画布节点已有的 `/files/`），故不引入 GC / 去重 / 异步竞态问题。

### 4.2 为什么这个方案零副作用（逐条已验证）

| 验证点 | 证据 | 结论 |
|--------|------|------|
| AI 回看历史不读图 | `agentCore.js` 343-345：`out.push({ role:'user', content: m.content \|\| '' })`，历史 user 只取 `content` 文字 | 落盘 url 换成 `/files/` 不影响 AI 上下文 |
| 当前轮发送 | 内存态 `url` 保持 base64；`referenceImages`/`imageCatalog` 走模块级变量（不落盘） | 发送链路零改动、零影响 |
| 刷新后 UI 回显 | `AgentMessage.jsx` 247-254 渲染 `a.url`；换成 `/files/xxx` 后 `LazyImage` 正常加载 | **图不丢，反而更清晰**（原图而非压缩图） |
| pending 恢复重发 | `useAgentChat.js` 491：`setCurrentPending(makePendingRef({..., attachments}))` 存**原始** attachments；恢复重走 `send`→`normalizeAttachmentsForSend` | 落盘换 url 不影响 pending 重发 |
| tool 消息是否藏 base64 | `agentRuntime.js` 395：tool content = `JSON.stringify({ok:true, ...result.data})`，生图结果经 `saveResultToTasks` 落盘为 `/files/tasks/xxx` | **主路径 tool 消息不含 base64**，无需处理 |
| GC 风险 | 本方案**不新建文件**，仅引用画布节点已有的 `/files/` | 不引入新 GC 风险（与画布节点 `data.url` 同性质） |

### 4.3 落盘体积来源确认（★ 重大修正：爆点是【两个】，不是一处）

`estimateConversationsBytes` = `JSON.stringify(conversations).length`（`volumePolicy.js` 83-86），**整包全字段计入**。

`downgradeConversation` 投影时 `dropPending:true`（124 行）→ pending 被剥离，不计入预算。

**base64 在 conversation 里存了两份**（此前只识别出第一份）：

| 爆点 | 位置 | 写入处 | 体量 |
|------|------|--------|------|
| **① 累积爆点** | `conv.messages[].attachments[].url` | `useAgentChat.js` 488 `setHistory(userMsg)` | **所有历史轮**带图 base64 累加 |
| **② 本轮爆点** | `conv.referenceImages`（per-conversation 字段） | `useAgentChat.js` 486 `setCurrentReferenceImages(...)` → `conversationAiState.js` 135 `setCurrentRefImages` → `commit` 到 conv | **本轮**参考图 base64（覆盖写） |

**② 的证据链**（此前误判为"模块级变量不落盘"，实为错判）：
```javascript
// conversationAiState.js 130-142
export function getCurrentRefImages() { return getActiveConv()?.referenceImages || [] }
export function setCurrentRefImages(urls = []) {
  commit({ ...getState(), conversations: getState().conversations.map(
    (c) => (c.id === conv.id ? { ...c, referenceImages: next, updatedAt: Date.now() } : c)) })
}
// conversationState.js 372（normalizeConversation 里确认为 conv 正式字段）
if (!Array.isArray(c.referenceImages)) c.referenceImages = []
```

**这解释了本次 5.2MB 的构成**：用户发了一轮带图（3 张）→
- ② `conv.referenceImages` = 这 3 张的 base64 ≈ **2.6MB**
- ① `messages[].attachments` = 同一批 3 张的 base64 ≈ **2.6MB**
- 合计 ≈ **5.2MB**（与日志 `rawBytes:5465693` 吻合，即同一批图存了两遍）

### 4.3.1 ★★ 最终审计的认知修正：真正危害不是"存储被撑爆"，而是"前端误触发降级"

上述分析默认"base64 真的进了存储、把库撑大"。**经最终审计，这个前提是错的**——项目里**已经有一半的治理机制**：

**已有机制：入库外置（`localTool/src/utils/base64Externalize.ts`）**
```typescript
// localTool/src/routes/kv.ts:33
const finalValue = externalizeBase64InValue(value);   // 入库前调用
```
- 在 `handleKvSet` **入库前**深度遍历 value，把所有 `data:image/video/audio;base64` 解码落盘成 `uploads/` 文件，用 `/files/` URL 替换；
- **sha1 幂等去重**（文件名 = sha1 前 16 位，同图不重复落盘）；
- 逐字段 try/catch，**失败保留原 base64**，不破坏 `{ok:true}` 契约；
- 设计初衷正是治理"base64 撑爆 KV 库致全量写盘卡死"（docs/41 第 2 节）。

**⇒ 会话数据经 `/api/kv/set` 入库时，base64 已被自动外置成 `/files/` URL。实际磁盘上的库体积是小的。**

**那 warn 为什么还在？——因为「算体积」和「外置」不在同一个环节：**

| 环节 | 执行者 | 数据形态 | 体积 |
|------|--------|---------|------|
| ① 前端算体积 + 降级裁剪 | **前端** `applyConversationBudget`（在 `contentSet` **之前**） | 前端内存里仍是 **base64** | **5.2MB → 触发 warn + 裁剪** |
| ② 前端发送入库 | 前端 `contentSet` | base64 | — |
| ③ 后端外置入库 | **localTool** `handleKvSet` | base64 → **`/files/`** | 小 ✅ |

**⇒ 真正的危害是：前端拿着"尚未外置的 base64"算出 5.2MB，误判为超预算，从而【错误地裁剪了用户的历史上下文和 memory.summary】。存储本身其实没被撑爆（后端会外置）。**

**这条修正改变了方案的评价标准**：任何一个"只在后端外置/只在落盘时清洗"的方案都不能消除 warn——**必须让前端从一开始就不持有 base64**，前端算出的体积才是真实值，才不会误触发降级。这直接导向方案 E（§4.9）。

### ⚠️ 由此得出的关键结论：方案 A′ 是不完整的"半解"

A′ 只把 ①（`messages`）换回 `/files/` → 体积从 5.2MB 降到 **≈2.6MB**，**仍然超过 2MB 预算 → 降级 warn 依旧触发**。

**A′ 无法消除告警。** 必须同时治理 ②（`conv.referenceImages`）才有效。这直接导向方案 D（见 §4.8）。

### 4.4 翻车点（重新审计后，逐条给对策）

**翻车点 1：置空方案会毁掉刷新后回显（已作废方案的致命伤，A′ 已规避）**
- A′ 换回 `/files/` 而非置空 → 回显正常。**这是选 A′ 而非旧方案的决定性理由**。

**翻车点 2：并非所有 originalUrl 都可安全落盘（边界情况，必须处理）**
- `/files/` 或 `http(s)` → 安全，换回（主路径：画布图、公网图）✅
- `blob:`（视频抽帧/剪辑临时地址）→ 刷新后失效，**不能换回**（换回等于存坏链）→ 保持 base64 或置空
- `data:`（上传失败回退的图）→ originalUrl 本身就是 base64，换了等于没换 → 保持原样
- **对策**：按 §4.1 伪代码的 `safe` 判定，仅 `/files/` 与 `http(s)` 才换回；其余走降级（保留 base64，体积问题下次惰性处理）。边界情况占比极小。

**翻车点 3：浅拷贝污染内存态**
- `normalized` 是 `.map(normalizeConversation)` 产生的**浅拷贝**，内层 message 对象仍与 `states` 共享引用。若清洗函数直接 `m.attachments[i].url = x` **会改到内存态** → 正在聊的图变 `/files/`（不影响 AI，但影响本轮 `openZoom` 显示原图，属行为漂移）。
- **对策**：必须返回**新对象**（`{...a, url}` / `{...m, attachments}`），绝不 mutate。§4.1 伪代码已用 map + 展开保证。

**翻车点 4：清洗位置必须在 `applyConversationBudget` 之前**
- 否则 `estimateConversationsBytes` 算的仍是 base64 体积 → 降级 warn 照打，白改。
- **对策**：清洗插在 `persistConversation` 内、`applyConversationBudget(normalized, ...)` 调用**之前**（conversationState.js 76-77 行之间）。

**翻车点 5：存量历史会话（已落 base64、无 originalUrl）不会自动受益**
- 旧数据没有 `originalUrl` 字段，清洗函数判定 `safe=false` → 保持 base64 → 体积不降。
- **对策**：接受存量不回洗（新会话不再增长即可）；如需彻底清理，可加一次性惰性迁移（读取时若 url 是 base64 且无 originalUrl，异步 `saveInlineToLocal` 落盘再替换）。**不作为首发范围**。

**翻车点 6：`originalUrl` 字段会略微增大内存/落盘体积（可忽略）**
- 每条附件多存一个 `/files/xxx` 短字符串（~100 字节），相比省下的 MB 级 base64 可忽略不计。

**翻车点 7：图像模式（runDirectBranch，670-674 行）同样走 `normalizeAttachmentsForSend`**
- 该分支也会 base64 化附件，且同样经 `setHistory` 落盘 → **同属爆点**。
- **对策**：改动点 1 在 `normalizeAttachmentsForSend` 内（共用函数），**自动覆盖两个分支**，无需额外处理。

### 4.5 改动清单（最小面）

| # | 文件 | 改动 |
|---|------|------|
| 1 | `src/components/agent/runtime/agentAttachments.js` 34 行 | `{...a, originalUrl: a?.url, url: await normalize(...)}` |
| 2 | `src/components/agent/conversation/conversationState.js` 76-77 行之间 | 插入同步纯函数 `restoreOriginalUrls(normalized.messages)`，仅作用于副本 |
| 3 | **（A′ 遗漏，但必需）** `conv.referenceImages` 治理 | 见 §4.3 —— 不做此项则体积仍 ≈2.6MB，warn 依旧 |

不改 `send`、不改 `agentCore`、不改 `LazyImage`、不改 `volumePolicy`、不碰发送/请求链路。

### 4.6 代价汇总

| 维度 | 影响 |
|------|------|
| AI 对话行为（当前/历史） | **零影响**（历史只取 content；发送仍用内存态 base64） |
| 当前对话 / 流式 | 零影响（内存态不动） |
| **刷新后历史图回显** | **正常显示，且为原始分辨率**（旧"置空"方案会毁掉此项） |
| pending 恢复重发 | 零影响（pending 自带原始 attachments） |
| 体积收益 | 带图会话 **MB 级 → KB 级**，2MB 降级 warn 消除 |
| 改动面 | 极小：2 处、1 个同步纯函数 |
| 是否新建文件 / GC / async 竞态 | **均无**（仅引用已有 `/files/`） |
| 存量迁移 | 存量不自动受益，新会话即时生效（可接受） |
| 风险等级 | **低**（同步、纯投影、可回退） |

### 4.7 被否决的方案

- **旧"剥离置空"方案**：会毁掉刷新后历史图回显（`AgentMessage.jsx` 渲染 + `LazyImage` 破图占位）→ **已作废**。
- **异步落盘成新 /files/（`saveInlineToLocal`）**：需 async（落盘 writer 是同步的，有竞态）、新建文件（GC/去重问题）、存的是压缩图。**A′ 用已有 originalUrl 同步解决，严格更优**，仅作为存量惰性迁移的可选手段。
- **IndexedDB 拆分**：改动面大，偏离现有 KV 架构，不必要。
- **A′（保留 originalUrl）**：**不完整半解** —— 只治 ①（messages），漏了 ②（`conv.referenceImages`），体积仍 ≈2.6MB 超预算，**warn 不消失**。可作为 D 的过渡，但不能作为终解。

## 四·八、方案 D（终解 · 彻底解耦）：会话只存 /files/，base64 只在出站两条边现场生成

### 4.8.1 核心契约（一句话）

> **`/files/` 是会话内的唯一真值（source of truth），可落盘、可累积、体积极小；
> base64 只是"出站编码"，只在【LLM 看图】和【生图网关参考图】两条边上现场生成，永不落盘、永不进 conversation。**

#### 为什么 base64 只在出站：通用性论证（用户已确认「必须 base64，因为最通用」）

| 形态 | 本质 | 谁能读 | 适用 |
|------|------|--------|------|
| `/files/xxx` | 指向**本地磁盘**的地址 | **仅本机** localTool | 本机落盘 / 本机渲染 |
| `data:;base64,...` | 像素**内联在 HTTP body** | **任何接收方**（自包含，不受 URL 可达性 / CORS / 内网限制） | 一切「出本机」的传输 |

**判据：只要数据要"出本机"，就必须 base64。**

| 场景 | 出本机？ | 形态 |
|------|---------|------|
| 落盘到本地会话存储 | ❌ 本机读写 | **`/files/`**（不需要通用性） |
| 聊天缩略图 `LazyImage`（`AgentMessage.jsx` 251） | ❌ 本机渲染 | **`/files/`**（且是原图，优于压缩图） |
| LLM 看图（发到网关） | ✅ | **base64**（边1 现场转） |
| 生图网关参考图 | ✅ | **base64**（边2 现场转） |

⇒ **base64 属于「出站传输层」，不属于「存储层」。** 存储是本机事务，无需通用性——这是把 base64 从会话剥离的理论依据。

⚠️ **该论证同时坐实 D-1 为确定高危项**：既然出站必须 base64，则 execute_plan 漏转 = 网关收到 `/files/` = 读不到 = **参考图静默丢失（图生图退化成文生图，无报错）**。故边2 转码必须先于消息侧解耦落地并手测验证。

#### 边2 转码的天然解：幂等（降低 D-2 / D-7 风险）

`canvasPlanExecutor.js` 295 行当前用 `toAbsoluteFileUrl(u)` 处理参考图 → 说明 url 是 **`/files/` 与 `data:` 混存**。而 `normalizeImageUrlForSend` 对两种输入天然幂等：

```javascript
// imageUrl.js 218
if (u.startsWith('data:')) return u     // 已是 base64 → 原样返回，不二次压缩
// /files/ → 压缩（≤1920）+ 转 base64
```

⇒ 边2 直接复用它，即可同时吃两种输入；**存量 base64 不会被二次压缩**，D-2（重复转码）与 D-7（存量兼容）风险随之降低。

### 4.8.3 关键设计：为什么 `buildRequestMessages` 签名可以不变（保住单测）

`buildRequestMessages` 是同步纯函数、被大量单测覆盖，**不能改成 async、不宜加参数**。

**解法：在 `send` 层造"临时副本"注入，而非改函数签名**：
```javascript
// 伪代码（示意）
const base64Urls = await normalizeAttachmentsForSend(currentAttachments, { preferBase64 })  // 本轮 base64
const msgsForLLM = injectCurrentRoundBase64(messages, base64Urls)   // 仅替换【最后一个 user】的 attachments.url
const contextMessages = buildRequestMessages(msgsForLLM, ...)        // 签名不变、单测不变
```
- `injectCurrentRoundBase64` 只改**临时副本**的最后一个 user 消息（即"当前轮"，与 `agentCore.js` 328 行 `i === lastUserIdx` 判定一致）；
- 历史轮保持原样（本就不进图）；
- 临时副本用完即弃，**绝不落盘**。

⇒ `buildRequestMessages` / `agentCore.js` **零改动，单测全绿**。

### 4.8.6 翻车点（D 特有，逐条给对策）

**D-1：生图参考图必须是 base64，若漏转则图生图静默失效（最高危）**
- 现象：`execute_plan` 的 refPool 从 base64 变 `/files/`，若未转码直接传网关 → 网关读不到本地 127.0.0.1 → **参考图丢失、图生图变文生图**（静默，无报错）。
- 对策：边2 转码是**强制项**，且转码失败必须 `logger.error` + 让该步显式失败（绝不静默降级为无参考图）。**必须在图生图回路上手测验证**。

**D-2：execute_plan 内重复转码性能问题**
- 现象：多个 generation（如 13 张套图）引用同一张参考图 → 若逐步转会重复压缩 13 次（每次 canvas 解码 ~100ms+）。
- 对策：**url → base64 的 Map 缓存**（同 url 只压缩一次），工具执行期内有效。

**D-3：`injectCurrentRoundBase64` 必须精准命中"当前轮"**
- 现象：若误改历史轮消息的 url → 历史图被塞进 LLM 上下文 → 复发"反推图一却全反推"（项目记录在案的历史 bug，见 `agentCore.js` 196 行）。
- 对策：只在**最后一个 user 消息**（`lastUserIdx`）上注入，与 `agentCore.js` 328 行 `i === lastUserIdx` 判定严格对齐；临时副本用完即弃。

**D-4：normalizeAttachmentsForSend 对 /files/ 会压缩+转码，边1/边2 语义是否一致？**
- 现象：边1（LLM 看图）与边2（生图参考图）都调同一函数，结果一致 → 缓存可共用，行为一致。
- 对策：保持不变（两边本就同源，现状亦如此）。

**D-5：图像模式（direct）分支的 `referenceImages` 参数**
- 现象：`runDirectBranch` 710 行 `callTool('execute_plan', { referenceImages })` 直接传 url 数组。
- 对策：若边2 统一在 execute_plan 内转码，则该参数传 /files/ 即可（execute_plan 内部转）；需确认 `globalRefs`（955 行 `args.referenceImages`）也走同一转码路径，**不能漏**。

**D-6：pending 的 attachments 原本就是原始 /files/**
- 现象：`setCurrentPending(makePendingRef({..., attachments}))` 存的是原始 attachments（491 行）。
- 对策：D 下 messages 也存 /files/ → 二者一致，恢复重发行为不变 ✅（且更一致）。

**D-7：存量旧会话（已落 base64）**
- 现象：存量 messages/referenceImages 里是 base64，D 的新逻辑读到 base64 时如何处理？
- 对策：转码函数 **幂等**（`normalizeImageUrlForSend` 对已是 `data:` 的输入原样返回，见 `imageUrl.js` 218 行 `if (u.startsWith('data:')) return u`）→ 存量 base64 照常工作，只是体积不降。**存量惰性迁移可选**，不阻塞首发。

### 4.9.6 E 的翻车点

**E-1：`/api/proxy` 是通用透传，不能无差别改写 body**
- 现象：`/api/proxy` 转发到任意外部 provider，body 语义由 provider 决定。若 blanket 替换所有 `/files/` → 可能破坏非图片字段语义。
- 对策：只识别**已知图片字段形态**（如 `image_url.url`、`images[].url`、`referenceImages[]`），且仅当值以 `/files/` 开头才替换；其余原样透传。

**E-2：大模型/多图请求的转换耗时与内存**
- 现象：服务端一次性读多个文件转 base64 → 请求延迟增加、内存峰值上升（尤其 13 张套图）。
- 对策：**sha1 持久化缓存**（`/files/` 路径本身就是内容哈希，天然去重）；转换失败显式报错，不静默丢弃。

**E-3：`/api/agent/:id/chat` 当前是"无状态透传"，加转换需保持 SSE 时序**
- 现象：`agentChat.ts` 147 行 `const msgs = [...messages]`、180 行 `messages: msgs` 直接透传。
- 对策：转换在 `JSON.stringify(msgs)` **之前**同步完成（或 await 后），再发起上游请求；不改变 SSE 透传逻辑（192-217 行）。

**E-4：外部直连场景（不经 localTool）是否残留？**
- 现象：若 `VITE_API_BASE` 指向**远程** localTool，则 `/files/` 是远程机器的路径 → 远程 localTool 也能读自己的 uploads（同机部署则一致）；若两者分离会失效。
- 对策：确认部署形态。生产"页面部署到 localTool 18080 同源访问"（`config.js` 17 行）→ **同机，无此问题** ✅

**E-5：存量与外置机制的交互**
- 现象：存量会话里若仍是 base64（外置失败保留的），E 下前端直接把它当 url 传给 localTool。
- 对策：`resolveLocalImageUrls` **幂等**（已是 `data:` 的原样透传，是 `/files/` 才读盘转换）→ 天然兼容两种形态 ✅

**E-6：文件被 GC 回收后，出站转换失败**
- 现象：孤儿文件 GC 若回收了会话仍引用的 `/files/` → 读盘失败 → 图丢失。
- 对策：转换失败必须 `logger.error` + 显式失败（对齐 E-2），**绝不静默丢弃参考图**（这正是 D-1 的教训）。需确认 GC 不会回收会话引用的文件。

| 维度 | 影响 |
|------|------|
| 落盘体积 | **两个爆点全治理** → 5.2MB → **KB 级** |
| **前端误判降级** | ✅ **根除**（前端不再持有 base64，算出的体积即真实值） |
| 前端代码 | **净减少**（删 compressImage / FileReader / async 转码 / 缓存） |
| 刷新后历史图 | ✅ 原图渲染（优于压缩图） |
| LLM 看图 / 图生图 | ✅ 功能不变（服务端转码），需手测验证 |
| 改动面 | 前端删 3 处 + 后端加 2 处（跨端，但每处都简单） |
| 风险等级 | **中低**（前端风险大幅下降；后端新增需手测，但有幂等 + 显式失败兜底） |
| 与已有架构 | ✅ 与 `base64Externalize` 天然闭环，符合"localTool 为本机可信服务"的既有定位 |

### 4.9.8 结论

**E 是终解**：它不只是"减小体积"，而是把 base64 归还给"出站传输层"（§4.8.1 论证），前端彻底不持有，与项目已有的"入库外置"机制形成闭环，且**前端是删代码**。

实施顺序建议（隔离最高危项）：
1. **先做后端 E-4/E-5**（localTool 出站回读 + 幂等 + 显式失败 + sha1 缓存），此时前端仍传 base64 → 幂等透传，**零风险灰度**；
2. **再切前端**（删 `normalizeAttachmentsForSend` 调用，改传 `/files/`）→ 体积问题消失；
3. **手测图生图 + 跨轮回退**，确认参考图不丢。

## 五、决策建议

**采用方案 E（§4.9 前端全程持 /files/，转换下移 localTool）—— A′ 与 D 均已降级**

**为什么是 E（用户提出，经审计验证为最优）**：
- 两条出站链路（LLM 聊天 + 生图）**全部经过 localTool**（`API_BASE` = 127.0.0.1:18080），而 localTool 是本机服务、本就能读自己的 `uploads/` → **把"读文件→转 base64"放在这一跳天然成立**；
- 与项目已有的 **`base64Externalize`（入库外置 base64 → /files/）** 形成完整闭环（用户所说"存俩名"即 `/files/` URL 与 `uploads/<sha1>` 磁盘文件的映射，机制已存在）；
- **前端是"删代码"**（去掉 compressImage / FileReader / async 转码 / 缓存），后端加 2 处转换；
- 前端不再持有 base64 → **前端算出的体积即真实值 → 根除"误判降级裁剪历史上下文"这一真正危害**（见 §4.3.1）；
- 相对 D：前端零转换、零 async、零缓存管理，D-1/D-2 风险大幅下降。

**为什么不是 A′**：A′ 只治理了爆点 ①（`messages`），遗漏了爆点 ②（`conv.referenceImages`，本轮参考图 base64 覆盖写、会落盘）。两者体量相当（本次 5.2MB ≈ ①2.6MB + ②2.6MB），**只修 ① 体积仍 ≈2.6MB，超 2MB 预算，降级 warn 依旧触发 → A′ 无法达成目标**。

**D 的要点**：
- 契约：`/files/` 是会话唯一真值；base64 只在【LLM 看图】【生图网关参考图】两条出站边现场生成，永不落盘；
- 关键设计：`buildRequestMessages` **零改动**（在 send 层用"当前轮临时副本"注入 base64），单测全绿；
- 一次治理两个爆点 → 落盘 KB 级，warn 彻底消失；
- 代价：5 处改动，含 `execute_plan`（核心执行层）与 `send` 请求构造，**风险中**。

**最高危验证项**：E-6 / E-2 —— 出站转换失败时必须**显式失败 + logger.error**，绝不静默丢弃参考图（图生图变文生图，无报错）。必须手测图生图回路。

**实施顺序（灰度，隔离风险）**：
1. 先做后端出站回读（幂等：已是 `data:` 原样透传，`/files/` 才读盘转换）+ sha1 缓存 + 显式失败 → 此时前端仍传 base64，属于**零风险灰度**；
2. 再切前端（删 `normalizeAttachmentsForSend` 调用，改传 `/files/`）→ 体积与误判降级问题消失；
3. 手测生图参考图 + 跨轮回退，确认参考图不丢。

**首发范围**：新会话即时生效；存量旧会话不自动回洗，但转码函数对 base64 输入**幂等**（`imageUrl.js` 218 行原样返回），故存量功能不受影响，仅体积不降。

## 六、验证方法（落地后）

1. 带 3 张画布图发给 AI，观察日志：不再出现 `会话落盘触发体积降级`；
2. 检查 `agent_conversations_*` 存储项体积（DevTools → Application → Local Storage）：应从 MB 级降到 KB 级；
