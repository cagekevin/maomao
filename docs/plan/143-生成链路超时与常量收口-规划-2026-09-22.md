### 2.2 真相归后端，前端只是消费者

**用户裁定**：「前端是消费者，就算统一也轮不到他」。
预算是「**这个任务该等多久**」这个业务判据，而「豆包视频实测 8 分钟」这类知识**只有后端有**。
前端硬编码 `VIDEO_TIMEOUT` = **消费者替生产者定真相**（三铁律③）。

**两个产物必须分开**（各管自己那段）：

| 产物 | 归属 |
| --- | --- |
| 「**上游该等多久**」 | **后端真相** |
| 「**前端自己处理响应体/解析/落盘要多久**」 | **前端真相**（`CHAT_TOTAL_TIMEOUT` 里的 `+60000` 宽限） |

**正确形态**：

```
后端持有默认真相 budgetMsFor(provider, capability)
   ↓ 在接口响应里【告知】调用方（生产者给全）
前端读它，不再自己硬编码
   ↓ 可选：调用方显式覆盖（"我这次只等 N 秒"）
后端默认用【自己的】真源；被覆盖时才用覆盖值
```

**关键**：调用方**可以**表达耐心（可选覆盖），但**不许**作为默认真相。

### 2.3 与 TD-01-24 的关系：**方向按「任务是否脱离调用方存活」分**（2026-09-22 用户裁定修正）

`config.ts:141-151`（TD-01-24）诊断对了症状（前端先放弃 ⇒ 上游白跑 ⇒ 重复消耗）。
**但「方向反了」这个判词只对 image/video 成立** —— 见下面的分层判据。

**★ 判据：谁等，谁就是生产者**（决定预算是「谁的事」）

| capability | 任务的存活方式 | **谁是生产者** | 预算真相归谁 |
| --- | --- | --- | --- |
| **image / video** | **异步句柄**：后端持有任务、脱离前端仍存活并续跑到终态 | **后端** | ✅ **后端持真相**，前端读响应里的 `budgetMs` |
| **chat** | **同步调用**：无句柄、不建任务行，任务**就是这一次请求**，响应即终态 | ✅ **前端**（它在等，它决定等多久） | ✅ **前端声明**（`body.timeoutMs`），后端作 **override 原样用** |

⇒ **两个判据，两种形态，不许互相「收口」**（`ADR-0031`：判据不同不合并）：

| | 做法 | 判定 |
| --- | --- | --- |
| image/video：TD-01-24 现状（前端写请求体） | 前端 → 请求体 → 后端原样用 | ❌ **消费者越权**（后端才是生产者） |
| image/video：**本规划** | 后端 → 响应告知 → 前端读 `budgetMs` | ✅ 生产者给全 |
| **chat：TD-01-24 原方向** | 前端 → 请求体 → 后端原样用 | ✅ **正确**（前端就是生产者；同步链没有「响应告知」的窗口） |
| chat：本规划曾提的「预取端点」 | 前端先 GET 一次预算再 POST | ❌ **撤回** —— 多一次往返去问一个**本来就该自己定**的数 |

**为什么同步链上「预取端点」是错解**：chat 没有句柄、响应即终态 ⇒ 不存在「先拿响应再设定时器」的窗口；
而「这次等多久」本来就是**发起方自己的耐心**。让后端持有它 = 让执行者替发起者决定耐心。
⇒ **chat 保持前端声明 + 后端 override 原样用，不改**（用户裁定 2026-09-22）。

⇒ 本规划**修订 TD-01-24 的方向仅限 image/video**；chat 侧只做**语义修正**（原把「等上游响应」**段值** 120s
当总预算传给后端 ⇒ 已改为总预算 `CHAT_TOTAL_TIMEOUT` · S5′），并按 A7 回改其注释与**账本解法注**（§5 S5′/S12′）。

## 3. `upstreamStartedAt` 必须保留（原 §3「合并分段预算」已撤销）

**原判断有误，已撤**（见 §7 撤销记录）：`relay-poll.ts:603-628` 的段①（`:611`）与段②（`:621`）**用的是同一个 `timeoutMs` 变量**，注释 `:608` 原文即「两段的界都沿用同一个 `timeoutMs` —— 不新造数字」⇒ **不存在"两份预算"可合并**，原 §3 的"净收益"为 0、S6′ 无可施工。

```
尚未交出 task_id（可能已部分出站）→ 必须 unknown（宁 unknown 不 failed）
已交出                              → 才能判 failed
```

守的是**「重复计费」红线**（TD-08-24）。**结论：它本来就是"一个预算 + 一个事实"，不需要也不应该改。**

### 4.1 同名不同义，**不得"统一"**

`GEN_POLL_INTERVAL`（前端，3000）≠ `DEFAULT_POLL_INTERVAL_MS`（后端，3000）：

- 前端那个 = 多久问**后端**一次
- 后端那个 = 多久问**上游平台**一次

数值相同是巧合。命名相似不是重复。

**第二例（审计补，值也不同，更危险）**：`MAX_CONSECUTIVE_POLL_ERRORS`

| 载体 | 值 | 数的是什么 |
| --- | --- | --- |
| 前端 `relayProxy.ts:33` | **5** | 前端**连续 attach 失败**次数 |
| 后端 `relay-poll.ts:138` | **30** | 后端**连续上游 poll 异常**次数 |

同名、同字面语义（"连续轮询异常阈值"）、**值差 6 倍**，但载体不同 ⇒ 与上例同理**不得"统一"**。
登记在此，防下一位按名合并（若合并，前端 5 次就停 = 把后端 30 次的设计意图压掉）。

## 5. 施工图

### 5.0 前置设计

**接口契约「后端告知预算」**：

```
POST /api/generate     →  { code:0, data:{ taskId, budgetMs } }
GET  /api/generate/:id →  { code:0, data:{ status, progress?, url?, error?, budgetMs? } }
```

| 决定 | 取值 | 理由 |
| --- | --- | --- |
| 字段名 | **`budgetMs`** | 入参 `timeoutMs` 是"调用方覆盖"、出参是"后端定的预算"，同名会混成假统一 |
| 入参 `timeoutMs` | 保留为**可选覆盖** | 不是默认真相 |
| **fail-fast 判据（拆分）** | **POST = fail-fast**（未出站，违约即拒）；**GET attach = 不得 fail-fast** | 按 ADR-0048「按后果选 fail-soft/fail-fast」：attach 时任务**已在跑、钱已花**，判"契约违约"失败 ⇒ 撞重复计费红线与 §2.2「停止等待 ≠ 失败」 |
| **chat 的预算获取** | ✅ **已定（2026-09-22 用户裁定）：前端声明（前端就是生产者）→ 后端作 override 原样用。不改。** ~~三条路径（预取端点 / 不设上限 / 会话缓存）~~ **全部撤回** —— 它们是按「后端持真源」这个**只适用于异步链**的判据推出来的，对同步链是错解（见 §2.3 分层判据） | 后端 `budgetMsFor('chat')` 的默认值保留，用于**前端未声明**时（如其它调用方）；前端声明时它只当 override |
| **结构粒度** | ✅ **D4 已取证，粒度已定**：仓内无重复可复用（任务书 §1.3）⇒ `override ?? DEFAULT_BUDGET[capability]`，**只建 3 条、不预建 provider 空层** | A14 后半句已过；ADR-0053 ① 禁止为设想的消费方铺路 |
| **既有缺陷须一并处理** | ⚠️ `GET /api/generate/:id` 对**不存在的任务返 404**（`routes/generate.ts:145`），而前端 `relayProxy.ts:138-139` 把**非 2xx 一律折成 `running`** ⇒ 后端丢句柄时前端**空等到自己的预算耗尽** | 这正是本表「attach 不得 fail-fast ⇒ 保持 `running`」的**同一失败形态**：fail-soft 本身没错，但**没人区分"后端在跑"与"后端说没有"** ⇒ 该形态会被固化。不处理它，「保持 running」就变成"把不可诊断当默认" |

**预算真源形态**（粒度已定，见上表末行）：

```
budgetMsFor(capability, override?) = override ?? DEFAULT_BUDGET[capability]
DEFAULT_BUDGET = { chat: 180_000, image: 300_000, video: 600_000 }   // 只建这 3 条
```

**前端拿不到 `budgetMs`**：
- **POST 缺** ⇒ **fail-fast** 报错（`budgetMs` 是必给字段，编一个数 = 默认值兜底，形态④）
- **GET attach 缺** ⇒ **不得 fail-fast**；保持 `running`，靠后端写终态（同 TD-08-24 语义）
- **GET attach 404（任务不存在）** ⇒ 现行为是**折成 `running` 空等到超时**（见上表末行）。**必须与 S3′ 同批定死**：404 是"后端明确说没有这个任务"（生产者给全的事实），不该被消费者折成"还在跑"。三种可选取法：①前端把 404 折成终态 `unknown`（与 TD-08-24 的第三终态对齐）；②后端对"句柄已丢"返 `status:'unknown'` 而非 404；③保留 404 但前端**立即停止等待**并给可诊断文案。**选哪条属架构判断，S3′ 内定死并给探针。**
