## 一 · 需求口径（一句话）

> **模型与运行时都由后端（localTool）持有，前端只按 URL 调用。**

深度视频是**唯一示范**，抠图**照它来**。这条原则**高于**"Image 系列接哪些资源"的类比 ——
因为 Image 系列（mediapipe）用的是**框架自带运行时**，而 SAM-HQ **没有框架可依附**，
其运行时**本就在模型目录里**（`matting/static/ort/`），**正是"后端持有"的形态**。

### 1.1 事实核对：抠图与深度视频的形态对应

| 段 | 深度视频 | **抠图（本方案）** | 是否同形态 |
|---|---|---|---|
| 模型落点 | `runtime-models/depth-video/models/` | `runtime-models/matting/static/models/` | ✅ 后端持有 |
| 运行时落点 | `runtime-models/depth-video/vendor/onnxruntime/` | `runtime-models/matting/static/ort/` | ✅ 后端持有 |
| 宿主 | `/models/depth-video/*`（别名 `/depth-video/*`）| `/models/matting/*` | ✅ 同一宿主 |
| 前端取件 | `RUNTIME_MODELS` 拼前缀 | `runtimeModelUrl('matting', …)` | ✅ 唯一出口 |
| 前端调用 | `import(URL)` → `pipeline()` | `import(URL)` → `InferenceSession.create()` | ⚠️ **API 不同**（见 §1.2）|
| `package.json` | **不动** | **不动** | ✅ 零依赖变更 |

### 1.2 唯一无法消除的差异（诚实声明）

深度视频的运行时（transformers.js）**是 JS 库**，有 `pipeline()` 这种高层 API；
抠图是**裸 ONNX**，只能用 `InferenceSession` + 手喂张量。

> **但差异只在"调用什么 API"，不在"资源归谁"。** 资源归属与取件口径**完全一致** —— 这正是用户原则的射程。

**为什么不能也走 transformers.js 的 `SamModel`（实测已查，结论确定）**：

| 查证 | 结果 |
|---|---|
| 库有没有 SAM 支持 | ✅ **有**：`SamModel` + `AutoProcessor`（`models/sam/modeling_sam.d.ts`）|
| 库认标准 SAM 吗 | ✅ 认（官方示例 `Xenova/sam-vit-base`）|
| **库认我们的模型吗** | ❌ **不认** —— 实测解码：我们的 decoder 要 `interm_embeddings [1,160,64,64]`（**SAM-HQ 特有的 var-token 通路**），而库的 `SamModel` 只认 `image_embeddings` + `image_positional_embeddings`（标准 SAM 的 PE）。**结构对不上** |
| 能否重新导出成库兼容形态 | ❌ **不能** —— `scripts/export-onnx.py`（README 声称的导出脚本）**全盘不存在**，模型无法在本机重现 |

⇒ **不是"没想到用库"，是"库的 SAM 覆盖不到 SAM-HQ 这个变体"**。故只能直接操作 ORT —— **这是模型选型决定的，不是方案偏好**。

## 四 · 方案

### 4.1 资源层 —— 后端出，前端调（**照抄深度视频**）

```ts
// 取件唯一出口（禁拼字面量）—— 与 depthVideo 的 RUNTIME_MODELS 同角色
runtimeModelUrl('matting', 'static/models/sam_hq_vit_t_encoder.onnx')
runtimeModelUrl('matting', 'static/models/sam_hq_vit_t_decoder.onnx')
runtimeModelUrl('matting', 'static/ort/ort.bundle.min.mjs')      // ← 运行时也从后端取
// wasmPaths → runtimeModelUrl('matting', 'static/ort/')
```

| 决策 | 结论 | 理由 |
|---|---|---|
| ORT 来源 | **`static/ort/`**（后端托管，前端按 URL 取）| 与 `depth-video/vendor/onnxruntime/` **同形态**；**不动 `package.json`** |
| 为何不用主项目 ORT | **否** | 它是 `@huggingface/transformers` 的**间接依赖**（不在 `package.json`），让业务代码直接依赖"别人的间接依赖"= 声明不实；且违背"运行时由后端出" |
| 目录是否拉平成 `vendor/` | **不改** | 当前结构宿主可直接服务；depth-video 的 `vendor/`+`models/` 是它自己的历史结构，**非体系强制**（`runtime-models/README.md`：目录名"随便起"）。改动要动演示页 + 重算清单，收益仅"看起来像"（`ADR-0053` 第 0 关：答不出降哪一项就不改）|

### 4.2 代码层 —— 四分离深模块（`ADR-0042` D5，depthVideo 是范本）

```
src/components/image/lib/matting/          （4 件 ≥3 ⇒ 子域成立，ADR-0044 D2）
  mattingConfig.ts   ← 单源：模型 id · 预处理常量 · 取件 URL 派生（对齐 depthUrls 单源）
  mattingEngine.ts   ← 纯逻辑：预处理/坐标变换/mask 后处理（无 DOM/无 ORT，可单测）
  mattingLoader.ts   ← 装载：动态 import 运行时 + session 单例 + 释放（对齐 depthVideo/loader）
  index.ts           ← 能力片门面（按用例）
```

| 文件 | 导出（按用例） | 对齐 depthVideo |
|---|---|---|
| `mattingConfig.ts` | `MATTING_MODEL_ID` · `MATTING_INPUT_SIZE` · `MATTING_MEAN`/`MATTING_STD` · `mattingModelUrl(rel)` · `MATTING_ORT_DIR` | ↔ `depthUrls.ts`（路径单源）|
| `mattingEngine.ts` | `scaleForSize(w,h)` · `toModelCoords(pt,scale)` · `decodeMask(logits,w,h)` | ↔ `engine.ts`（纯函数，可测）|
| `mattingLoader.ts` | `loadMattingSessions()` · `encodeImage()` · `predictMask()` · `disposeMatting()` | ↔ `loader.ts`（装载 + G3 释放）|
| `index.ts` | 门面：只露 UI 真实需要的符号 | ↔ `video/index.ts`（只露 2 个符号）|

**三道闸门（照抄 depthVideo 的 G1/G2/G3）**：

| 闸 | 抠图落实 |
|---|---|
| **G1 代码按需** | ORT 运行时**不在首屏**——只由 `mattingLoader` 内 `import(/* @vite-ignore */ URL)` 动态加载（照抄 `DepthVideoModal.tsx:375`）|
| **G2 时机按需** | 仅在**用户打开抠图编辑器**时加载 session；点选才 `predictMask`；fast 路径不存在（抠图无 fast 档）|
| **G3 释放** | 关编辑器 → `disposeMatting()` + revoke objectURL |

#### 4.2.1 失败契约：判别联合（**V2 §1.2 🔴红线 · 修正 §5 的"抛原错"**）

> **⚠️ 修正**：§五 初稿写「`mattingLoader` 抛原错，不返回 null」—— 按 V2 §1.2 + `ADR-0002/0003`，
> **"预期会失败"的分支必须返回判别联合，不是 throw**。`throw` 只保留给"不该发生"的编程错误。

```ts
// mattingLoader.ts —— 边界 ACL（外部/浏览器 API 的 throw 在此洗脱）
export type MattingErrorCode = 'ModelMissing' | 'EngineLoadFailed' | 'EncodeFailed' | 'PredictFailed';

export type MattingResult<T> =
  | { ok: true; data: T }
  | { ok: false; code: MattingErrorCode; message: string };   // ✅ message（❌ 禁 msg）

export async function loadMattingSessions(): Promise<MattingResult<MattingSessions>>;
export async function encodeImage(...):          Promise<MattingResult<MattingEmbedding>>;
export async function predictMask(...):          Promise<MattingResult<MaskLogits>>;
```

| 失败 | 返回 | 防线级（`ADR-0052`）|
|---|---|---|
| 模型/运行时文件缺失 | `{ok:false, code:'ModelMissing', message}` | **3**（`loadMattingSessions` 唯一入口）|
| 动态 import 失败 | `{ok:false, code:'EngineLoadFailed', message}` | **3** |
| 预处理/编码失败 | `{ok:false, code:'EncodeFailed', message}` | **3** |
| decoder 推理失败 | `{ok:false, code:'PredictFailed', message}` | **3** |

**`throw` 仅用于**：ORT 返回的张量形状与 `mattingConfig` 断言不符（= 模型换了、代码该改，**不该发生**）。

#### 4.2.2 不变量下沉（**V2 §0.5 第一原则** —— 判据不停在文档层）

> V2 §0.5：「规则写在文档里 = 没有强制力」。把抠图的关键约束**下沉到能报错的那一层**：

| 约束 | 下沉到 | 手段 |
|---|---|---|
| 模型 id / 预处理常量 / 张量形状 | **L1 类型层** | `as const` + 具名类型；`MattingSessions` 的形状字段类型化 ⇒ 写错**编译报错** |
| 取件 URL | **L2 唯一入口** | 只经 `mattingModelUrl()`（内部调 `runtimeModelUrl`）⇒ 外部拿不到拼接能力 |
| 运行时加载 | **L2 唯一入口** | ORT 只在 `mattingLoader` 内 import ⇒ 别处想用也拿不到 |
| 失败必须可见 | **L1** | 判别联合（§4.2.1）⇒ 不处理 `ok:false` 就取不到 `data`（`tsc` 逼） |

#### 4.2.3 接线：谁必须调它（**V2 Step 1.5 —— 建了原语 ≠ 完成**）

> 「只列一条 = 假接线」。每个新原语的**消费者必须穷尽列出**：

| 原语 | 谁必须调它（穷尽） | 生产消费验收 |
|---|---|---|
| `loadMattingSessions` | `MattingEditor`（打开时）；`disposeMatting` 在关闭时 | `grep -rn "loadMattingSessions" src` 去掉定义处与 `*.test.*` 后 **>0** |
| `encodeImage` | `MattingEditor`（图片就绪后，**一次**）| 同上 |
| `predictMask` | `MattingEditor`（点选防抖后）| 同上 |
| `disposeMatting` | `MattingEditor`（卸载 cleanup）| 同上 |
| `mattingModelUrl` | 仅 `mattingLoader`（**不对外**）| 门面不导出它 ⇒ 无外部消费是**正确**的（L2 收口）|

#### 4.2.4 生命周期 / 并发 / 取消（**V2 Step 3.4**）

| 项 | 落实 |
|---|---|
| **取消** | 编辑器关闭时（`useEffect` cleanup）置 `cancelled` 标志 ⇒ 晚到的 `predictMask` 结果**不写已卸载组件** |
| **超时** | 模型加载与推理均经 `withTimeout`（`base/utils/net/asyncGuard.ts:92`）—— 45 MB 模型首载 + 1024 encoder 推理都可能卡死 |
| **退订** | 入参 `assetUrl` 变化的 effect 走 `cancelled` 模式（照抄 `FaceMosaicEditor.tsx:96-130`）|
| **节流** | 点选已内置 200ms 防抖（演示页既有）；**不额外加**节流层 |
| **并发论证** | 推理中锁输入（`running` 标志）⇒ **同一时刻只有一次推理**。**本仓无通用锁原语**，故用"编辑器是唯一调用方 + UI 锁"论证，**不口头假设** |

### 4.3 运行时初始化（照抄演示页 + 适配取件 URL）

```ts
// mattingLoader.ts 内
const ort: any = await import(/* @vite-ignore */ mattingModelUrl('static/ort/ort.bundle.min.mjs'));
ort.env.wasm.wasmPaths = mattingModelUrl('static/ort/');   // 根相对，与页面同源
ort.env.wasm.numThreads = 1;   // ← 见下
```

**单线程降级（实测驱动的决定）**：全仓无 `COOP/COEP` ⇒ `SharedArrayBuffer` 不可用 ⇒
**多线程 wasm 起不来**。故显式 `numThreads = 1`，并**如实声明代价**（推理变慢，具体秒数落账时实测）。
> **不选"给主应用加 COOP/COEP"** —— 那是**全站级**改动（影响所有第三方资源加载），
> 而抠图是**单功能**；改全局为局部让路，代价面远大于收益。**这是 `ADR-0048` 的 fail-soft 选择**。

## 九点五 · 门面重构：从「转发废物」到「用例编排」（2026-09-24 · 用户裁定）

> **用户原话**：「我们的门面怎么是一个只会转发的废物？我最讨厌这种门面了，一点儿营养都没有。
> 你起码是个编排层，还有点实际意义。」

### 首版错在哪（留痕）

首版 `index.ts` 是**纯转发**（`export … from` 清单）—— 它还自我标榜"门面按用例定义（`ADR-0044` §8）"，
**实际做的正是 `ADR-0044` §3-b 点名批判的「纯中转门面」**（该条实证过"白删"形态）。

**代价是可量化的**：编辑器为了跑一次抠图，被迫消费 **14 个符号**，并自己编排 6 步：

```ts
const loaded = await loadMattingSessions();          // ③ 内部时序
if (!loaded.ok) return;                              // ④ 三次失败判定散在 UI
const encoded = await encodeImage(loaded.data, src);
if (!encoded.ok) return;
const pred = await predictMask(loaded.data, encoded.data, pts, w, h);
if (!pred.ok) return;
```

⇒ 换成第二个消费者（批量抠图 / 换图重算）**这 6 步得再抄一遍**；且 `MattingSessions`/`MattingEmbedding`
这类**内部概念被迫外露**（消费者得知道"有两段 ONNX"）。

### 改成编排层（现状）

门面暴露**两个用例**，内部三段时序全部收编：

```ts
// 编辑器现在只说这两句
const session = await createMattingSession(src);   // 用例①：装载 + 编码（一次）
const alpha = await session.cutout(points);        // 用例②：每次点选（复用 embedding）
```

| 收编了什么 | 依据 |
|---|---|
| `MattingSessions` / `MattingEmbedding` | 内部概念，消费者不需知道两段 ONNX |
| `loadSessions`/`encode`/`predict` 三段时序 | 编排进 `createMattingSession` |
| 模型空间坐标换算 | 消费者只说**原图像素坐标**，换算由门面做 |
| logits → alpha（阈值 0）| 消费者拿到的是可直接用的 alpha |
| `drawParamsFor` / `toPromptPoint` | 不再是公开 API |

**为什么拆「会话 + 抠图」而不是一个 `runMatting(image, points)`**：
encoder 编码要数秒（1024×1024 推理），而用户会**反复点**微调 mask。
若每次点选都完整跑一遍 ⇒ 交互不可用。⇒ 会话持有编码结果，`cutout` 只跑 decoder。
**这不是泄漏内部细节，它正是用户可感知的交互契约**（"点一下要立刻响应"）。

| 编辑器接触内部三段时序 | 有（6 处）| **0 处**（`grep` 实证）|
| `tsc` / 全量单测 / build / `check:arch` | — | 全绿（3334/3334）|

| **③** | `MANIFEST.json` 8 条里含 `index.html`/`index.js`/`package.json`，读者会误以为**演示页是模型的一部分** | README 把文件表**拆成两栏**（「推理必需」/「演示件（非推理必需）」），并点明 MANIFEST 按目录扫描故一并记录 | 清单按目录扫描是**既有正确行为**（同目录文件都记），不该为"少 3 条"改扫描逻辑 |

**凭证**：`node localTool/scripts/runtime-model.mjs doctor matting` → **8/8 仍绿**（README/MANIFEST 不在资产清单内，改动不影响完整性校验）。

### 顺带修的一处**真错**（初稿声称、实测证伪）

初稿 README 写「encoder/decoder 为本机 `scripts/export-onnx.py` 导出」—— 实测**该脚本全盘不存在**（`find . -name "export-onnx.py"` 零命中）。
⇒ 已在 README 标注「**已不存在** ⇒ 本模型当前**无法在本机重新导出**」，并说明这是**为什么不能改走 `transformers.js` 的 `SamModel`** 的关键前提（§1.2 第 4 行）。
**这条不留痕的后果**：后续 AI 会以为"重跑导出脚本即可兼容库"，撞墙后才重新发现 —— 属 `ADR-0001` 意义上"引用了答不出'凭什么成立'的既有约定"。

## 十二 · faceMosaic 能力片重组（2026-09-25 · 用户裁定）

### 结论：按「能力」聚，不按「形态」切

用户提问「脸部打码是不是放错位置了」→ 全面调查 → **方向对，但错因不同**。

**实测（`refs` 消费矩阵）**：

| 编辑器 | 真实消费者 | 宿主数 | `editors/` 是否合理 |
|---|---|---|---|
| `ImageEditor` | `ImageGenerate` + `useImageHoverActions` | **2+** | ✅ 共享 |
| `InlineImageCropper` | 同上 | **2+** | ✅ 共享 |
| `CameraStudioPanel` | `AssetNode` + `ImageGenerate` | **2** | ✅ 共享 |
| `FaceMosaicEditor` | **仅 `FaceMosaicNode`** | **1** | ❌ 单宿主 |

⇒ **不是"只有 FaceMosaic 错"** —— 有 3 件单宿主。

**但"单宿主"本身不构成搬移理由**（`ADR-0044` §3-b 明确：那是"按谁在用判"，与 §8 冲突）。
真正的判据是 `ADR-0042` D6：**深构对象 = 域内一个个「能力」，不是按"节点/编辑器"这种「形态」切。**
⇒ 「人像打码」是一个能力（节点态 + 编辑器态 + 算法），却被按形态拆到 3 个目录 ⇒ **该聚。**

**范本**：`video/depthVideo/`（编辑器 + engine + loader + spawn + depthUrls **同居**）。

### 做了什么

```
src/components/image/faceMosaic/          ← 新能力片（平铺，对齐 depthVideo）
  FaceMosaicNode.tsx     （原 image/nodes/）
  FaceMosaicEditor.tsx   （原 image/editors/）
  faceMosaic.ts          （原 image/lib/，算法）
  README.md              （说明"为什么不建 index.ts"）
```

- 内部 import 一律 `./`（同目录，不用 `@/` 别名、不用跨目录 `../`）
- `FaceMosaicNode` 直连 `./FaceMosaicEditor`（不再绕 `../editors` 门面）
- `editors/index.ts` **删除该导出** + 头注写明「本子域语义 = 多宿主共享的编辑器」
- **不建 `faceMosaic/index.ts`**：唯一域外消费者 `NodePalette` 要的是具体符号（无具名用例）⇒
  按 `ADR-0044` §9②「无用例可承载 ⇒ 消费者直连能力片」

### ⚠️ 过程失误留痕：用全量单测当定位工具（**用户当场指出**）

**我在查上述失败用例时，连续跑了 3 次全量单测**（每次 ~20s × 277 文件）。
用户指出「**这不是坑人吗**」—— 对，而且这是明令禁止的滑法
（`架构师改码7步法`「严禁四种滑法：**改一版试一次**、猜环境、在错误位置深度优化、靠探针反复猜谜」）。

| ❌ 错误做法（我做的） | ✅ 正确做法 |
|---|---|
| 跑全量 → grep → 输出被终端回显污染 → **再跑同一条** | ① **按已改动文件跑最小射程**（改的是 faceMosaic 三件 ⇒ 先跑 `FaceMosaicNode.test.tsx` / `faceMosaic.test.ts` / `nodeDefaults.test.ts`）|
| 拿全量单测当**定位工具** | 全量单测是**验收工具**；定位用 `--bail=1` 或按文件跑 |
| 输出被污染后**重复同一命令** | 换手段：重定向到文件 / `--reporter=json` / **缩小射程** |

**根因**：没先想清"哪个测试可能受影响"，就用了最大射程。
**判据**：**跑测试的射程应与「改动影响面」匹配**，而不是"反正全量最保险"——
后者把 20s 变成 60s+，且**掩盖了真正的问题：我对影响面的判断缺失**
（本该先想清楚"搬了哪三个文件、哪些测试引用它们"，那一步能同时得出
①最小测试射程 ②搬迁工具盲区 两个答案）。

**正确的最小命令**（下次直接用）：
```bash
npx vitest run tests/unit/FaceMosaicNode.test.tsx tests/unit/faceMosaic.test.ts tests/unit/nodeDefaults.test.ts
```
