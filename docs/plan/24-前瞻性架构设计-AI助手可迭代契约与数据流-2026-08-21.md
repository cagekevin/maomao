# 24 - 前瞻性架构设计：AI 助手的可迭代契约与数据流

> **状态：🔵 前瞻性设计（v2，待评审，非本次立即实施）**
> **日期**：2026-08-21
> **性质**：面向未来的架构设计。目标不是修 bug，而是**把 AI 助手设计成"每个维度都可独立迭代、增改不牵动全局"**。
> **v2 变更**：从"四轴"升级为"**五轴**"——补上遗漏的**工具轴**（AI 对画布的能力集合，最独立、最常增长）。工具轴放哪是本次设计的核心命题。

---

## 0. 问题本质：为什么"改起来特别麻烦"

### 0.1 当前现状（已实测确认）

当前 AI 助手的状态/能力被**平铺**在两层：
- **状态层**：`conversationState` 的会话对象平铺所有字段（messages/skills/attachments/draft/workflow/pending/memory/runMode/undoStack/pendingGenerations/awaitingConfirm/referenceImages）。
- **执行层**：`useAgentChat`（hook 编排）+ `useCanvasAgentTools`（工具层，~30 工具）+ `agentRuntime`（LLM 通信）+ `agentCore`（纯函数）。

### 0.2 根因（改起来麻烦的三个病灶）

| 病灶 | 表现 | 后果 |
|---|---|---|
| **无维度边界** | 状态字段平铺、能力散落各文件 | 增改一处，认知负担全量 |
| **工具层与状态层双向纠缠** | `useCanvasAgentTools` 依赖 conversationStore（编排/参考图），又被 useAgentChat 依赖（callTool）；工具是 hook，无法被纯 store 调用 | 加一个工具要理清与编排/消息的耦合 |
| **消息双源 + 动作穿透式** | messages 双源；send/stop/clear 直接读写任意字段 | 手动同步，改必崩 |

## 1. 前瞻性设计总纲：五轴正交 + 分层契约

> **核心理念**：AI 助手不是"一个会话对象"，而是**多个可独立演化的维度**。把每个维度建模为**独立的契约单元**，维度之间**正交**，数据流**单向**。

### 1.1 五轴模型（可变维度的第一级分类）

```
┌────────────────────────────────────────────────────────────────┐
│                    AI 助手五轴模型（正交）                        │
│                                                                │
│  轴1 会话轴 (Conversation)   —— 对话的"容器"                    │
│      · 会话 CRUD / 切换 / 隔离 / 标题 / 时间戳                   │
│                                                                │
│  轴2 消息轴 (Message)        —— 对话的"内容"                    │
│      · messages 增删改 / streaming / 消息类型 / 附件 / 图        │
│                                                                │
│  轴3 编排轴 (Orchestration)  —— AI 怎么"跑"                     │
│      · workflow(状态机) / steerQueue / pending / runMode        │
│      · Skill 门禁 / 确认态 / 撤销栈 / 参考图 / 记忆              │
│                                                                │
│  轴4 工具轴 (Tool)           —— AI 能对画布"做什么"（★新增）    │
│      · ~30 工具定义 / callTool 分发 / ctx 注入 / 参数 / 契约     │
│                                                                │
│  轴5 展示轴 (Presentation)   —— UI 怎么"看"                     │
│      · 纯 UI 态（error/model/stateAction/sending），不持久      │
└────────────────────────────────────────────────────────────────┘
```

### 1.2 为什么必须加"工具轴"（前瞻性依据）

工具是 AI 助手**最独立、最常增长、最该正交**的维度：
- **独立性**：一个工具 = 名字 + 签名(schema) + 执行函数(ctx)。加一个画布工具，逻辑上**完全不该碰**消息/会话/编排。
- **高频增长**：画布能力会持续扩张（新节点类型、新操作、新参数），工具数会从 30 往上涨。
- **契约明确**：工具是"给 LLM 看的能力清单"（`AGENT_TOOLS` 顺序 = 模型选择优先级，docs/12 §4.2），有统一签名，天然适合独立成轴。

> **核心承诺**：以后加一个"画布工具"，只动工具轴；加一个"消息类型"，只动消息轴；加一个"AI 编排能力"，只动编排轴。**五轴互不牵动。**

## 2. 契约字段设计（按轴重组）

### 2.1 会话轴（容器）—— 精简，只放"容器"属性

```
conversation = {
  id, title, ts, updatedAt,   // 容器元数据
}
```
**外移**：messages→消息轴；workflow/pending/runMode/undoStack/pendingGenerations/awaitingConfirm/referenceImages/memory→编排轴。

### 2.2 消息轴（内容）—— 独立存储 + 独立增改

```
messages: Message[]
Message = {
  id, role,           // user/assistant/tool/system
  content, type,      // type: 'text'|'image'|'tool_card'|'skill_summary'|...（扩展点）
  attachments?, streaming?, tool_calls?, lastResults?,
  meta?,              // 扩展元数据（新字段放这，不破坏结构）
}
```
**前瞻设计**：`type` + `meta` 扩展点——加新消息类型只加分支，不改基础结构。独立订阅 `useMessages(agentKey)`，读写唯一入口 `messageActions`。

### 2.3 编排轴（AI 怎么跑）—— 按"能力子域"分组

```
orchestration = {
  workflow: { status, nodeIds, steerQueue, startedAt, updatedAt },  // 执行流
  pending: { conversationId, text, attachments },                    // 刷新恢复
  runMode: 'auto'|'semi',                                           // 分级门禁
  skill: { pendingGenerations, awaitingConfirm },                    // Skill 三阶段
  undo: { aiUndoStack },                                             // 撤销
  refImages: { referenceImages },                                    // 参考图
  memory: { summary, facts, lastPlan, lastSharedStyle, notes, global_contract, artifacts }, // 记忆
}
```
**前瞻设计**：每个能力子域独立；新增能力=新增子域。编排轴**驱动**消息轴（单向：编排→消息）。

### 2.4 工具轴（AI 能做什么）★ —— 独立能力注册表

> **工具轴是本设计的核心新维度。** 它解决"加一个工具要理清所有耦合"的问题。

```
工具轴 = 工具注册表 + 分发器 + ctx 注入
Tool = {
  name,                 // 工具名（LLM 调用名）
  schema,               // 参数 JSON Schema（给 LLM 看）
  description,          // 能力说明（进 AGENT_TOOLS 顺序）
  run(ctx, args) => result,   // 执行函数
  category,             // 分组：read/build/update/connect/execute/view/manage
  writesCanvas: bool,   // 是否写画布（决定是否压撤销栈）
}
```

**前瞻设计要点**：
1. **工具轴独立注册**：`toolRegistry = { [name]: Tool }`，`registerTool(Tool)` 追加能力。**加工具 = 新增一条注册，不碰其他轴。**
2. **callTool 是唯一执行入口**：`callTool(name, args, ctx)` 从注册表查工具执行，找不到返回"未知工具"（不抛，保证 runToolCalls 循环不打断，docs/12 §4.3）。
3. **ctx 注入显式化**：工具需要的运行时依赖（projectId/画布 API/编排状态/撤销栈）统一由 ctx 注入，**工具不直接 import conversationStore**——依赖单向：工具轴 →(只读 ctx)← 编排轴。
4. **写画布工具统一包装**：`writesCanvas` 标记 + 统一 wrap（压 AI 撤销栈），新工具声明即可，不散落。
5. **AGENT_TOOLS 顺序**：注册表按 category + 插入顺序生成，新工具自动进入 LLM 能力清单（docs/12 §4.2 顺序=选择优先级，放语义合理位置）。

### 2.5 展示轴（UI 态）—— 纯前端，不持久

```
presentation = { sending, error, stateAction, model }
```
仅存在于 UI 层（useAgentChat 薄壳），不进持久层；由"组件不卸载"（docs/23 Step3）保证切页存活。

## 3. 数据流设计（单向 + 按轴订阅）

### 3.1 五轴单向数据流总图

```
                    ┌─────────── 编排轴（AI 怎么跑）───────────┐
                    │  workflow/runMode/skill/undo/memory      │
                    └──────┬───────────────┬───────────────┘
                           │驱动(编排→消息) │ 调用(编排→工具)
                           ▼               ▼
                    ┌─────────── 消息轴 ───────────┐   ┌──── 工具轴（AI 能做什么）────┐
                    │  messages（唯一存储）          │   │  toolRegistry + callTool      │
                    └──────┬───────────────────┘   │  · 只经 ctx 读状态，不直接 import │
                           │订阅                     │  · 写画布统一压撤销栈            │
                           ▼                         └──────▲───────────────────────┘
                    ┌─────────── 展示轴 ───────────┐        │
                    │  AgentPanel 只订阅 3 轴        │────────┘ 工具结果 → 回填消息轴
                    │  UI 动作 → 编排/工具动作       │
                    └──────────────────────────────┘
```

### 3.2 关键数据流原则

1. **单向**：UI → 动作 → 状态；状态 → 订阅 → UI。UI 永不直接写状态。
2. **按轴订阅**：AgentPanel 分别订阅消息/编排/展示轴，不订阅整个会话对象。
3. **编排 → 消息**（单向）：编排产出内容写消息轴；不反向依赖消息决定编排。
4. **编排 → 工具**（单向）：编排（runToolCalls）调工具；工具结果回填消息轴。
5. **工具轴只读 ctx**：工具不直接 import conversationStore，所有状态经 ctx 注入。**这是工具轴独立的关键**——工具层不再与状态层双向纠缠。
6. **动作收敛**：状态变更经轴级 action；工具执行经 callTool。

## 4. 未来迭代路径示例（验证五轴可迭代性）

| 未来需求 | 按此设计改哪里 | 不牵动 |
|---|---|---|
| **新增"画布工具"**（如"一键排版"） | 工具轴：`registerTool({...})` 加一条 | 会话/消息/编排/展示轴全不动 |
| **新增"视频消息"类型** | 消息轴：加 `type:'video'` 分支 + meta | 其余四轴不动 |
| **新增"AI 编排能力"**（如"分镜生成"） | 编排轴：新增一个子域 + 动作 | 其余四轴不动 |
| **新增"新按钮"**（如"重新生成"） | 展示轴 + 编排轴加一个 action | 消息/会话/工具轴不动 |
| **新增"跨轮记忆提炼"** | 编排轴 memory 子域 | 其余不动 |
| **新增"第三个执行分级"** | 编排轴 runMode 扩值 + 门禁 | 其余不动 |
| **工具改造参数**（如生图加 ratio） | 工具轴：工具 schema + ctx 加参 | 其余不动 |

> **每次迭代只动一个轴的一个子域**——这就是"每块可独立操作、不至于改起来特别麻烦"的落地形态。

## 5. 五轴正交性验证

| 轴 | 它依赖谁 | 谁依赖它 | 是否单向 |
|---|---|---|---|
| 会话轴 | 无（最底层容器） | 消息/编排/展示 | ✅ |
| 消息轴 | 会话轴 | 展示（订阅）、编排（驱动） | ✅ |
| 编排轴 | 会话轴 | 展示（订阅）、工具（被调用） | ✅ |
| 工具轴 | **只经 ctx**（不直接依赖状态层） | 编排（调用） | ✅ |
| 展示轴 | 消息/编排（订阅） | 无（最上层） | ✅ |

**关键**：工具轴通过 **ctx 注入**而非直接 import，把"工具层 ↔ 状态层"的**双向纠缠**改成**单向（编排→工具→结果回填）**。这是工具轴独立、且五轴真正正交的**设计基石**。

## 6. 与当前代码的差距与迁移路径

> 现状已具备：conversationState（单源+订阅+落盘）、拆分文件、agentRuntime（依赖注入，无 React）。**缺的是"按轴建模" + "工具轴独立"**。

| 当前 | 目标（本设计） | 迁移步骤 |
|---|---|---|
| conv 平铺字段 | 五轴分离 | ① 消息独立成轴（docs/23 Step1）② 编排字段按子域分组 ③ 工具独立成轴 |
| useCanvasAgentTools 双向纠缠 | 工具轴只经 ctx | ① 抽出 `toolRegistry` ② 工具改经 ctx 读状态 ③ callTool 查注册表 |
| messages 双源 | 消息轴唯一存储 | docs/23 Step1 |
| 订阅整个会话 | 按轴订阅 | 新增 useMessages/useOrchestration/useTools hooks |
| 动作穿透式 | 轴级 action + callTool | 逐轴收敛 |

**迁移原则**：**分轴渐进**，每轴独立落地 + 独立测试 + 独立 docs 同步，不追求一步到位。建议顺序：会话/消息（docs/23）→ 编排 → 工具轴 → 展示。

## 7. 决策记录

- ✅ **五轴正交**（会话/消息/编排/工具/展示）作为第一级可变维度分类。
- ✅ **工具轴独立**：工具经 ctx 读状态（不直接 import），callTool 查注册表，加工具=注册一条。**这是本次 v2 的核心修正。**
- ✅ **消息轴 `type`+`meta` 扩展点**、**编排轴按能力子域**、**数据流单向+按轴订阅**。
- ✅ 复用现有 conversationState 底座，不新建第四套 store。
- ⚠️ 本文档是**前瞻性设计**；实施并入 docs/23 分步迁移，作为其"目标形态"的进阶版。
