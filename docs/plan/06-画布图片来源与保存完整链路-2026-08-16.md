# 06 - 画布上图片的来源与保存完整链路

> 本文梳理画布上所有图片的「来源 → 谁保存 → 保存什么 → 保存到哪里」的完整链路。
> 涉及模块：拖入/粘贴导入、素材库上传、AI 节点生成，以及画布快照持久化（KV + base64 外置）。
> 关联文档：`02-前端图片URL统一机制`、`05-KV存储设计`、`01-项目与画布存储链路`。

---

## 0. 全局心智模型

画布上的图片有 **三种来源** 和 **三层存储**：

| 来源 | 入口 | 是否落盘文件 | 是否进画布快照 |
|---|---|---|---|
| ① 拖入 / 粘贴 | `useAssetDropPaste` | ✅ 优先上传 `/files/` | ✅（存 URL 或 dataURL） |
| ② 素材库上传 | `AssetLibrary` | ✅ 上传当前目录 | ❌（只进素材库，拖到画布才进快照） |
| ③ AI 节点生成 | `useNodeGeneration` + `PromptNode` 等 | ✅ 落 `tasks/` 目录 | ✅（存生成结果 URL） |

**三层存储**：
1. **画布快照 KV**（key=`canvas-state-v1-<projectId>`）：存节点引用（URL 或 dataURL），是「画布能不能恢复出来」的权威源。
2. **localTool 磁盘文件**（`uploads/<subfolder>/...`）：图片本体，被 URL 引用。KV 入库前会把 dataURL 外置到这里（`base64Externalize`）。
3. **SQLite 业务表**（tasks / resources / projects）：任务记录、素材库元数据、项目元数据，供面板检索展示，不存图片本体。

图片 URL 有 4 种形态，渲染/发送/存储统一经 `imageUrl.js` 归一化（详见 `02-前端图片URL统一机制`）：
`绝对 http(s)` / `data: base64` / `blob:`(临时) / `相对 /files/`。

## 0.5 架构真相源与 nodeId 关联契约（核心断言）

> 本节是本文的「宪法」。所有链路、双写、恢复逻辑都建立在下面三条断言之上。
> 违反其中任意一条，就会重现「刷新丢图 / 任务中心多垃圾任务」这类 bug。

### 断言 1：双真相源，各管一摊，互不为对方备份

| 真相源 | 物理位置 | 负责的数据 | 不负责的数据 |
|---|---|---|---|
| **任务中心（SQLite `tasks` 表）** | localTool SQLite | 生图/生成任务的「结果真相」：`resultUrl`、状态、模型、prompt、时间戳 | 画布拓扑、节点位置 |
| **画布快照（SQLite `kv` 表，key=`canvas-state-v1-<projectId>`）** | localTool SQLite | 画布拓扑真相：节点、连线、位置、以及节点上的图片**引用**（URL 或 dataURL） | 生成任务记录、素材库元数据 |

- 图片**本体**只存在于 `uploads/` 磁盘，被以上两处的 URL 共同引用，两者都不持有本体。
- 因此：**图片/生图结果以任务中心为准，画布拓扑以画布快照为准**。任何一方都是「唯一真相」，不是另一方的缓存或副本。
- 画布节点上的 `data.imageUrl` 只是任务中心 `resultUrl` 的一个**引用视图**——它能丢（快照没写进去），但任务中心记录不能丢。这正是一条关键推论（见断言 3）。

### 断言 2：nodeId 是两套真相源之间唯一的关联键（含三类生成来源）

- 任务中心的每一行**必须**带 `nodeId`，且要能对应到画布快照里的某个节点 `id`。
- **标准生成节点（PromptNode / TextNode / DiscountVideoNode 等）与任务行是 1:1 对应**：一个生成节点 → 一条任务记录。
- **三类生成来源都受本契约约束**（不是只有手动点 PromptNode）：
  1. **手动点节点生成**：直接走 `useNodeGeneration` 契约，天然带 `nodeId`。
  2. **AI 助手（Agent）驱动生成**：`trigger_generation` 工具 → `runNodeGeneration(nodeId)`（`useCanvasAgentTools.js`）→ 复用目标节点已注册的 `useNodeGeneration` 契约。**本质还是"节点生成"，`nodeId` 来自工具入参，契约不变。**
  3. **剧本盒子生成**：分两种子模式，关联方式不同——
     - **(a) 出图即建下游节点**：剧本盒子"生成分镜出图"会 `addNodes` 建真正的 `promptNode`（`id = script-prompt-<shotId>-<base>`，见 `scriptBoxEngine.js:443`）并连线。这些下游节点**回到标准 1:1 契约**，走任务中心、带 `nodeId`。
     - **(b) 资产图 / 分镜图直接写回剧本盒子 data**：`assets[].imageUrl`、`shots[].imageUrl` 是剧本盒子节点的**内部子资源**，不建独立画布节点，因此**不适用 1:1 tasks 行关联**。它们的真相源仍是任务中心（落盘 `uploads/tasks/`），但恢复时不靠"画布节点 `nodeId` → tasks 行"，而是靠**剧本盒子节点自身 data 内的 `imageUrl` 引用**——即：剧本盒子节点 `id` 是其子资源的归属键，子资源 URL 内联在 `data` 里随画布快照持久化。刷新后由剧本盒子节点自行读 `data` 恢复，不依赖 tasks 行回填。
- 断裂后果（历史真实 bug）：
  - 任务行 `nodeId = null` → 这条任务和任何节点都对不上 → 在任务中心里**凭空多出来一条垃圾任务**（正是"刷新后多一个任务"的根因）。
  - 标准生成节点 `data.imageUrl` 为空、但任务中心有对应 `completed` 记录 → 刷新后画布**丢图**。
- 所以：**`nodeId` 非空且正确，是这个架构的命脉（对子模式 (a) 与手动/Agent 生成）。** 任何写任务的逻辑都必须保证 `nodeId` 被带上；子模式 (b) 则不写独立 tasks 行，靠剧本盒子 data 内联引用持久化。

### 断言 3：恢复方向只能从「任务中心」补「画布」，不能反过来

- 因为任务中心是结果的唯一真相，画布引用可能丢失，所以刷新/挂载时的恢复逻辑必须是：
  **画布节点 `data.imageUrl` 缺失 → 按 `nodeId` 去任务中心查 `status='completed'` 且 `resultUrl` 存在的记录 → 回填节点并写回快照。**
  （实现见 `PromptNode.jsx` 挂载 `useEffect` 恢复逻辑。）
- 反向不成立：不能指望画布快照去「修复」任务中心，因为快照本就不持有结果真相。
- 这条断言直接治死了「刷新丢图」——只要任务中心有图，画布永远能找回。

### 断言 4：防御分两层（根因修复 + 兜底过滤）

- **根因层**：写入侧必须保证不产生 `nodeId=null` 的任务行（如 `persistThreadId` 改为只为前端 `frontTaskId` 补 `thread_id`，不再为网关 `taskId` 建空行）。
- **兜底层**：读取侧（`taskStore.getSnapshot`）过滤掉 `nodeId` 为空的任务，即使未来某处误建空行，UI 也不显示。
- 两层叠加 = 既治本又不留显示漏洞。

## 1. 来源①：拖入 / 粘贴（用户主动导入）

### 入口
- `src/components/base/useAssetDropPaste.js`
  - `onDrop`：文件拖入、素材库拖入、URL 文本拖入
  - `onPaste`：剪贴板图片/视频/音频文件、内部 `mutiwindow-images`、普通文本
  - 全局粘贴监听：`useGlobalPaste`（挂 `window.paste`）

### 谁保存
- 文件直接经 `uploadFileToLocal(file, 'canvas/drop')`（`filesApi.js`）上传，**不经过素材库**。
- 上传失败时 fallback：`FileReader.readAsDataURL` → 把 dataURL 直接写进节点 `data.imageUrl`。

### 保存什么 / 保存到哪里
| 情况 | 保存内容 | 保存位置 |
|---|---|---|
| 上传成功 | 节点 `data = { imageUrl: 'http://127.0.0.1:18080/files/canvas/drop/xxx.png', label }` | 画布快照 KV + `uploads/canvas/drop/` |
| 上传失败 | 节点 `data = { imageUrl: 'data:image/png;base64,...', label }` | 画布快照 KV（内联） |
| 文本文件 | `textNode`，`data = { text }` | 画布快照 KV |
| 拖入素材库素材 | 复用素材已有 `url` 建 `imageNode` | 画布快照 KV |
| 拖入图片 URL 文本 | `imageNode`，`data = { imageUrl: 文本URL }` | 画布快照 KV |
| 粘贴 `mutiwindow-images` | 多张 `imageNode` 网格 | 画布快照 KV |

### 关键代码
```js
// useAssetDropPaste.js:72 优先上传，失败回退 dataURL
const url = await uploadFileToLocal(file, 'canvas/drop')
if (url) { addNode('imageNode', pos, { imageUrl: url, label: file.name }); return }
// fallback: FileReader.readAsDataURL → addNode('imageNode', ... dataURL)
```

## 2. 来源②：素材库上传（素材池 / 人物 / 场景 / 道具）

### 入口
- `src/components/base/AssetLibrary.jsx`
  - `handleFiles`（上传按钮 + 拖入到素材库面板）
  - 目录 pill：`migrated`(全部) / `migrated/人物` / `migrated/场景` / `migrated/道具` / `materials`(素材池)

### 谁保存
- 前端直接 `POST /api/files/upload`（`API_BASE + /api/files/upload`，body=`FormData{subfolder, file}`）。
- 落盘后调用 `reset(true)` → `rescanResources()` 触发后端扫描磁盘，把文件收录进 **resources SQLite 表**。
- 注意：素材库上传**不写画布快照**。只有当素材被拖到画布（`onDrop` 的 `application/x-yimao-asset`）建节点后，才进入画布快照。

### 保存什么 / 保存到哪里
| 内容 | 保存位置 |
|---|---|
| 文件本体 | `uploads/<folder>/`（如 `uploads/materials/`、`uploads/migrated/人物/`） |
| 素材元数据 | SQLite `resources` 表（id, folder, type, url, name, size…），经 rescan 同步 |

> 前端 `assetStore.js` 是**原型期的 localStorage 模拟实现**（key=`yimao_asset_library`，含 seed 演示素材 + `addAssets` 写 localStorage）。接真系统后 UI 不变，数据源切到 `/api/resources`。当前真实运行路径以 `AssetLibrary.jsx` + `resourcesApi.js` 为准。

### 关键代码
```js
// AssetLibrary.jsx:166-186 上传到当前目录并 rescan
```

## 3. 来源③：AI 节点生成（PromptNode / TextNode / DiscountVideoNode 等）

### 入口
- `src/components/base/useNodeGeneration.js`：统一「提交 → 进度 → 成功双写(taskStore + node.data) / 失败 / retry」契约。
- `PromptNode.jsx`：`onSuccess` / `onRecover` 把结果写回节点。
- 其它生成节点（`TextNode`、`DiscountVideoNode`、`ImageBoxNode`、`Director3DNode` 等）复用同一契约。

### 保存链路（双写 + 落盘）

**第 1 步：写任务中心（taskStore → SQLite tasks 表）**
```js
// useNodeGeneration.js:78 成功后
taskCtl.done(rawUrl)  // → taskStore.reportGenerate 内 persist → saveTask 落 SQLite
```
- 保存内容：`{ id, nodeId, type, prompt, modelName, status:'completed', resultUrl, ... }`
- 保存位置：localTool SQLite `tasks` 表（`tasksApi.js` → `/api/tasks`）。

**第 2 步：回写节点 data（内存 + 画布快照）**
```js
// PromptNode.jsx:166 onSuccess → 173 调 saveResultToTasks（节点侧）
setImageUrl(r.url)
patchData({ imageUrl: r.url })   // 写回 node.data → 最终随画布快照进 KV
```

**第 3 步：生成结果本体落盘 tasks 目录（关键，防丢图）**
```js
// PromptNode.jsx:173（节点侧 saveResultToTasks） + taskStore.js:171-187（taskStore.done 内落盘）
saveResultToTasks(r.url, 'image').then((persistedUrl) => {
  // 落盘成功 → 用 /files/tasks/ URL 覆盖 taskStore.resultUrl 与 node.data.imageUrl
  // 并广播 mutiwindow-task-completed → onRecover 再次写回节点（刷新后恢复）
})
```
- `saveResultToTasks`（`filesApi.js:136`）：
  - `data:` → 转 Blob 上传 `POST /api/files/upload`（subfolder=`tasks`，文件名 `generated_<时间戳>.png`，见 `safeName('generated', ext)`）。**注意：此处是时间戳唯一化，不是 sha1 去重**。
  - `http(s)` → `POST /api/files/upload` 带 `{ fileUrl }`，幂等下载落盘。
  - `blob:` → 直接返回 null（临时地址不落盘）。
  - 补充：`sha1 去重`（`hash.ext` 文件名）只存在于 `saveInlineToLocal`（`filesApi.js:50-51`），不要与本函数混淆。
- 保存内容：**图片本体**。保存位置：`uploads/tasks/<name>.png`。

### 为什么生成结果要落盘两次（taskStore + node.data）
上游生图网关可能返回外链 / 临时地址，刷新后会失效，导致：
- 「任务中心有图（已落盘），画布没图（仍用失效 URL）」错位。
- 解决：节点侧 `PromptNode` 调 `saveResultToTasks` 把持久 URL 覆盖写回 `node.data.imageUrl`；
  `taskStore.done` 内部也会落盘并发 `mutiwindow-task-completed` 广播，节点 `onRecover` 再兜底写回。刷新后画布读 KV 快照里的持久 URL，不破图。

### 关键代码
```js
// taskStore.js:171-196 done 内落盘 + 广播
if (safeUrl && !safeUrl.startsWith('blob:')) {
  saveResultToTasks(resultUrl, task.type).then((persistedUrl) => {
    if (persistedUrl) {
      // 覆盖任务结果 + 广播给节点 onRecover 写回 data.imageUrl
      window.dispatchEvent(new CustomEvent('mutiwindow-task-completed', {
        detail: { taskId: task.id, nodeId: task.nodeId, resultUrl: persistedUrl, status: 'completed' }
      }))
    }
  })
}
```

## 4. 画布快照持久化（所有图片最终如何「留下来」）

### 入口
- `src/components/base/projectStore.js`：`saveCanvasState(projectId, nodes, edges)`
- 触发：App 自动保存（防抖）→ `storageSet('canvas-state-v1-<projectId>', { nodes, edges })`

### 谁保存 / 保存什么
- 保存经 `kvStore.js`：前缀 `canvas-state-v1-` 的 key 自动分流到 **localTool KV**（`/api/kv/set` → SQLite `kv` 表）。
- 保存内容：节点白名单字段 `['id','type','position','data','width','height']`，其中 `data.imageUrl`（或 `data.images` 数组）就是图片引用。
- **不保存** 运行时 UI 态（selected/dragging/measured/handles）。

### 保存到哪里
- 关系型元信息：`SQLite kv` 表，key=`canvas-state-v1-<projectId>`。
- 图片本体：不在 KV，在 `uploads/` 磁盘（被 URL 引用）或内联为 dataURL（在 KV value 内）。

### base64 外置（KV 入库前的去重落盘）
- `localTool/src/routes/kv.ts:33`：`handleKvSet` 入库前调用 `externalizeBase64InValue(value)`。
- `localTool/src/utils/base64Externalize.ts`：
  - 深度遍历快照 JSON，所有 `data:image/video/audio;base64` 字段解码落盘到 `uploads/canvas/<sha1前16位>.<ext>`（幂等去重）。
  - 用绝对 `/files/` URL 替换原 base64 后入库 → KV 库不再被 base64 撑大（解决 docs/41 所述卡死问题）。
  - 单字段外置失败 → 保留原 base64，不拖垮整条 value。
- 文件名 = `sha1(base64内容)` 前 16 位 → 同一张图永远映射同一文件，重复不重复落盘。

### 手动「清理缓存」入口
- `App.jsx:602 handleClearCache`：把画布内联 base64（含 ImageBox 的 `images` 数组、`imageUrl/videoUrl/thumbnailUrl/poster` 等）逐个经 `saveInlineToLocal` 落盘为 `/files/` URL，**绝不删图**，localTool 离线时保留原图并提示。

### 关键代码
```js
// projectStore.js:146-164
await storageSet(key, { nodes: sanitizeNodes(nodes), edges: sanitizeEdges(edges) })
await kvSet(`${key}_version`, version)  // 版本冲突检测，防旧数据冲新数据
```
```ts
// kv.ts:33 入库前外置 base64
const finalValue = externalizeBase64InValue(value)
```

## 5. 完整链路图（以「一张图」为例）

### 路径 A：用户拖入图片
```
[拖入文件]
   → useAssetDropPaste.onDrop
   → uploadFileToLocal('canvas/drop')        uploads/canvas/drop/xxx.png
   → addNode('imageNode', { imageUrl: '/files/...' })
   → 自动保存 → saveCanvasState
   → kvSet('canvas-state-v1-<pid>')           SQLite kv（存 URL 引用）
   → handleKvSet 外置（已是 URL，原样入库）
刷新后：KV URL → <img> 正常显示 ✅
```

### 路径 B：素材库上传 → 拖到画布
```
[素材库上传]
   → AssetLibrary.handleFiles → POST /api/files/upload (subfolder='materials')
   → uploads/materials/xxx.png + rescan → SQLite resources 表
[拖素材到画布]
   → onDrop 读 application/x-yimao-asset.url → addNode('imageNode', { imageUrl })
   → 自动保存 → KV 存 URL 引用
```

### 路径 C：AI 生成图片
```
[PromptNode 生成]
   → useNodeGeneration.start
   → reportGenerate → taskStore → saveTask     SQLite tasks 表
   → imageApi 调网关 → 返回 resultUrl
   → onSuccess: patchData({ imageUrl: resultUrl })   写回节点（进画布快照）
   → taskCtl.done → saveResultToTasks(resultUrl)      uploads/tasks/xxx.png
   → 持久 URL 覆盖 taskStore + 广播 mutiwindow-task-completed
   → PromptNode.onRecover → patchData({ imageUrl: 持久URL })   防刷新丢图
   → 自动保存 → KV 存持久 URL 引用
刷新后：KV 持久 URL → <img> 正常显示 ✅（与任务中心一致）
```

### 路径 D：上传失败 / localTool 离线（兜底）
```
[拖入图片但上传失败]
   → FileReader.readAsDataURL → addNode('imageNode', { imageUrl: 'data:...' })
   → 自动保存 → KV 内联 base64
   → handleKvSet → externalizeBase64InValue 尽力外置；外置失败则保留 base64
刷新后：KV 内联 base64 → <img> 仍可显示 ✅（体积大但图不丢）
```

## 6. 存储位置速查表

| 数据 | 物理位置 | 写入者 | 说明 |
|---|---|---|---|
| 画布快照（含图片 URL 引用） | SQLite `kv` 表，key=`canvas-state-v1-<pid>` | `projectStore.saveCanvasState` → `kvSet` | 跨端共享，版本冲突检测 |
| 拖入图片本体 | `uploads/canvas/drop/` | `filesApi.uploadFileToLocal` | URL 形态持久 |
| 生成图片本体 | `uploads/tasks/` | `filesApi.saveResultToTasks` | 任务中心 + 画布共用 |
| 素材库文件本体 | `uploads/<folder>/`(materials/migrated/人物…) | `AssetLibrary.handleFiles` | 与 resources 表对应 |
| 打码/处理中间图 | `uploads/canvas/face_mosaic/` | `FaceMosaicNode` | 节点内局部使用 |
| 任务记录 | SQLite `tasks` 表 | `taskStore` → `tasksApi` | 任务中心展示 |
| 素材元数据 | SQLite `resources` 表 | rescan / `resourcesApi` | 素材库面板展示 |
| 项目元数据 | SQLite `projects` 表 + localStorage 兜底 | `projectStore` | 当前项目定位 |
| 内联 base64（兜底） | 直接内嵌在 KV value 内 | `useAssetDropPaste` fallback / `base64Externalize` 失败保留 | 体积大，丢失风险低 |

## 7. 设计要点与易错点

1. **双真相源，各管一摊（详见 §0.5）**：图片/生成结果以**任务中心（tasks 表）**为唯一真相，画布拓扑以**画布快照（kv 表）**为唯一真相，二者靠 `nodeId` 绑死。画布节点上的 `imageUrl` 只是任务中心 `resultUrl` 的引用视图，可丢但任务中心不可丢。
2. **`nodeId` 是关联命脉（铁律，覆盖三类生成来源）**：手动点节点、**AI 助手 `trigger_generation`**、**剧本盒子出图建下游节点** 这三类都走 `useNodeGeneration` 统一契约 → 任务中心行**必须**带非空 `nodeId`。剧本盒子的"资产图/分镜图直接写回 data"（子模式 b）例外：不写独立 tasks 行，靠剧本盒子节点 data 内联 `imageUrl` 随画布快照持久化。写入任务的逻辑（如 `persistThreadId`）不得为网关 `taskId` 建 `nodeId=null` 的空行，否则任务中心凭空多一条垃圾任务（历史 bug）。
3. **恢复方向单向（从任务中心补画布）**：刷新/挂载时若节点 `data.imageUrl` 为空，按 `nodeId` 去任务中心查 `completed` 记录回填——这是治本逻辑，反向不成立（画布快照不持有结果真相）。
4. **生成图片必须落盘 `tasks/` 并回写节点**。否则上游外链失效 → 画布丢图、任务中心有图，两者错位（历史 bug，已通过双写 + 广播修复）。双写链路：`useNodeGeneration.start` → `taskCtl.done` 落盘 tasks 目录 + 广播 `mutiwindow-task-completed` → 节点 `onRecover`/`onSuccess` 回写 `data.imageUrl`。
5. **KV 入库前统一 base64 外置**。`localTool/src/routes/kv.ts:33` 调 `externalizeBase64InValue`，任何内联 dataURL 进 KV 都会被转成磁盘文件 URL（`uploads/canvas/<sha1前16位>.<ext>`，幂等去重），避免 SQLite 被撑爆卡死；单字段外置失败则保留原 base64。
6. **素材库上传 ≠ 进画布**。素材只在被拖到画布建节点后才进入画布快照 KV。
7. **失败永不删图**。`saveInlineToLocal` / `uploadFileToLocal` / `externalizeBase64InValue` 任一环节失败，都保留原 base64，保证图不丢（localTool 离线时 `useAssetDropPaste` 走 `FileReader.readAsDataURL` 兜底）。
8. **URL 形态统一收敛**。`imageUrl.js` 的 `normalizeImageUrl`（渲染）/`normalizeImageUrlForSend`（发送）是唯一出口，避免相对路径在 localhost/chrome-extension 下破图。

## 8. 全部入口清单（无遗漏）

> 三类入口：**粘贴（Paste）**、**拖拽（Drag/Drop）**、**生成（Generate）**。
> 以下按「入口位置 → 处理函数 → 落点」逐条列出，覆盖画布空白区、右键菜单、各节点、素材面板、Agent 面板、Agent 工具。

## 9. 入口审查发现的待修点（Bug / 隐患）

1. **`ImageNode` 上传按钮失效（D8）【✅ 已修复】**：`fileRef` input（`ImageNode.jsx:174-180`）原先只有 `ref` + 隐藏样式、**没有 `onChange` 读取文件**，点击只触发 `fileRef.current?.click()`，选完文件后无任何处理——「上传/替换」与空态点击不生效。**已修复**：新增 `handleFileSelect` 挂到 `onChange`，图片/视频/音频优先 `uploadFileToLocal(f, 'canvas/drop')` 落盘 `/files/` 持久 URL（刷新不丢），失败回退 dataURL 内联；文本文件 `FileReader` 读文本写回 `data.text` 切文本态。
2. **视频/结果节点用 `blob:` 临时地址未落盘（D9/D10/G6/G7/G8）**：`VideoProcessNode` 与 `VideoExtractNode` 的**源视频**（`onUpload` 写入 `data.sourceVideoUrl` / `data.videoUrl`）用 `URL.createObjectURL` 暂存；`VideoExtractNode` 抽帧结果（`extractedImages`）是 JPEG base64 dataURL 存组件 state；`GridMergeNode`/`GridSplitNode` 结果用 `URL.createObjectURL` 或 canvas dataURL 直接写 `data`。刷新后 blob 失效、state 清空，dataURL 虽可显示但撑大 KV。
   - **已修复（视频处理产物）**：`videoEngine.uploadResult` 原先被注释误导成「已落盘」，实为 `URL.createObjectURL` 临时地址（`videoEngine.js:449-452`），导致 `VideoProcessNode` 所有处理输出（拼接/裁剪/GIF/音频）刷新即丢。已改为真正落盘 `uploadFileToLocal(blob, 'canvas/video-process')` 返回持久 `/files/` URL，失败才降级临时 blob URL（不阻塞主流程）。
   - **仍未修（源视频 / 抽帧 / 网格）**：`VideoProcessNode.onUpload`、`VideoExtractNode` 源视频 + 抽帧结果、`GridMergeNode`/`GridSplitNode` 结果仍是 blob/dataURL。建议统一 `saveInlineToLocal`/`uploadFileToLocal` 落盘换 URL。
3. **`AgentPanel` 参考图用 dataURL（G14）**：附件以 dataURL 内联，未上传 localTool；对话历史若持久化会撑大存储（与 §3 base64 外置思路一致，建议接入时统一外置）。
