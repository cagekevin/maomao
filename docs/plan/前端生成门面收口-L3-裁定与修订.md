## 3. 逐条裁定与依据

### 3.1 修正 1 → **选 A：统一抛** **`AbortError`**

**为什么不是 B**（审计给的零风险选项）：B 把错误语义继续藏进返回值，而调用方 `useNodeGeneration` **早已实现 throw 分支**——

```275:282:src/hooks/useNodeGeneration.ts
    } catch (e) {
      if (e?.name === 'AbortError') {
        // 用户停止：不报错，返回取消标记，由调用方处理
        ...
        return { ok: false, error: '已停止', aborted: true }
```

即：**现有 catch 分支是死代码**（因为 `imageApi` 把 AbortError 吃掉了）。选 A 是让实现回归设计意图，B 是给错误设计打补丁。

**实际影响面（我逐点核过，≈0）**：

| 读 `r.aborted` 的位置                                                                      | 调用对象                             | 受 A 影响？                                               |
| -------------------------------------------------------------------------------------- | -------------------------------- | ----------------------------------------------------- |
| `scriptBoxEngine:298`                                                                  | `chatCompletions`                | ❌ chat 语义不变（`relayProxy.ts:289` 返信封）                  |
| `scriptBoxEngine:455/456`                                                              | `generateImage`                  | ❌ `:409` 注释「用户要求停止不做——**不传 AbortSignal**」→ 永不触发 abort |
| `scriptBoxEngine:581/698/699/700/747/1042`                                             | `chatCompletions`                | ❌ 同上                                                  |
| **`scriptBoxEngine:1134-1148`（第 3 位传** **`undefined, signal`）+ 结果处理** **`:1166-1176`** | `generateImage`                  | ✅ **受影响，但方向正确** —— 这是选 A **唯一的实质收益点**，见下方专项说明         |
| `PromptNode:284` / `TemplateNode:262` / `DiscountVideoNode:230`                        | 传给 `useNodeGeneration` 的 run 执行器 | ❌ 异常由 `:276` catch 兜                                  |

**专项说明 ——** **`scriptBoxEngine:1134-1148`** **是唯一走 A 路径的** **`generateImage`** **调用点**（其余 `generateImage` 均不传 signal）。它**确实传了 signal**：

```1142:1148:src/components/scriptbox/scriptBoxEngine.ts
          // 中止信号必须落在第 3 位：generateImage(opts, onProgress?, signal?)。
          // 【已修历史 bug】曾误传在第 2 位 onProgress 位 → imageProxy/pollUntilDone 首句
          // onProgress?.(10,…) 对 AbortSignal 对象发起调用 → TypeError（AbortSignal 非 nullish，
          // ?.() 不短路）→ 被 catch 后 classifyError 以 `e instanceof TypeError` 判为 network →
          // fail('onProgress is not a function')。三条分支（responses/async 轮询/同步 SSE）首句均如此，
          // 请求在发出前就已失败，综合图从未成功过。回归断言见 scriptBoxEngine.deep.test.js。
        }, undefined, signal)
```

行为对比（尾帧变体「综合图」中止时）：

| <br /> | 现状（B：返信封）                                                                    | 选 A 后（抛 `AbortError`）                                            |
| ------ | ---------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 走到哪    | `:1166` else 分支                                                              | `runAbortable:234` catch                                         |
| 结果     | `errorMsg='已停止'` + `tailFrameVariantsError='已停止，可重试'` —— **误导用户以为失败、还提示可重试** | `logger.warn('·已中止')` + `onReset?.()` 复位 loading —— **不弹 toast** |

即：选 A 让 `:1167-1169` 那行注释（「图像链路中止一律 AbortError 上抛，由 runAbortable 的 catch 兜底」）**从谎言重新变成事实**——它在旧时代是对的，随 `proxyGenerate` 退役而失效，选 A 即回归设计意图。这进一步支持 A 而非 B。

**收益**（两处）：

1. 修掉 `useNodeGeneration:263-266` 的现存 bug——用户停止生图时走 else 分支，弹红色错误 toast「已停止」。
2. 修掉 `scriptBoxEngine:1166-1176` 的误导文案——尾帧变体中止不再显示「已停止，可重试」。

**必须同步做**（否则 A 不成立）：

1. 删 `scriptBoxEngine.ts:1167-1169` 过期注释（本次误判源头）。
2. §9 风险表新增一行：**abort 语义变更**（这是行为变更，不是保持现状）。
3. 人工验收加一条：生图进行中点停止 → 确认**不弹红 toast**，且任务中心状态为「已停止」。
4. `generate.ts` 中止时**原样透传** `relayGenerate` 抛出的 error（message 恒为 `'Aborted'`），**禁止**新建中文 message 的 AbortError —— 见 §4.2.1 铁律。

### 4.2.1 abort message 铁律（选 A 的**隐含约束**，不遵守必踩坑）

> **【L3c 更新】本节的** **`/abort/i`** **message 判定**已失效——`scriptBoxEngine:234` 已改走统一 `classifyError`（看 `e.name`，不再依赖 message 文案）。下述「防中文 message」的坑已自动消除，铁律表述更新为：**`generate.ts`** **中止仍须原样透传 relayGenerate 的 AbortError（name 恒为 'AbortError'）**，因为 classifyError 判据是 `name === 'AbortError' || err.aborted`；若自行 `new Error('已停止')` 且不设 name，仍会被判 business 误弹红 toast。

选 A 后有一个极易踩的坑：`scriptBoxEngine` 的 `runAbortable` 判定中止**不是**看 `e.name`，而是**匹配 message 里的 "abort" 字样**：

```232:239:src/components/scriptbox/scriptBoxEngine.ts
    } catch (e) {
      onReset?.()
      if (classifyError(e).type === 'abort') {   // 【已由 L3c 统一判定，原 /abort/i 已移除】
        logger.warn('scriptBox', `${info.logLabel}·已中止`, info.ctx)
      } else {
        toast(e?.message || info.toastFail)
        logger.error('scriptBox', `${info.logLabel}·异常`, { ...info.ctx, error: e?.message })
      }
    }
```

> 【L3c】下表的 `/abort/i` 列不再适用——判定不再看 message，两个自然抛出点（`relayProxy:195-197` / `httpClient:161-163`）都因 `name==='AbortError'` 命中 abort。业务错 message 恰含 "abort" 但 name 非 AbortError 的场景，原会被误判 warn，现正确判 business → toast（该路径近乎不可达，仅纪律修正）。

链路上的两个自然抛出点都合规：

| 抛出点                     | message                         | `classifyError`（L3c 后判据）                    |
| ----------------------- | ------------------------------- | ------------------------------------------- |
| `relayProxy.ts:195-197` | `'Aborted'`                     | name===`AbortError` → abort → warn，不弹 toast |
| `httpClient.ts:161-163` | `'The user aborted a request.'` | name===`AbortError` → abort → warn，不弹 toast |

**但**若施工者按 `imageApi.ts:95` 的既有习惯写 `throw new Error('已停止')`（哪怕设了 `name = 'AbortError'`），message 是中文「已停止」→ `/abort/i` 为 **false** → **弹 toast「已停止」**，比现状（设置 `errorMsg`）**更糟**。

> **铁律**：`generate.ts` 中止时**必须原样透传** `relayGenerate` 抛出的 error（name 恒为 `'AbortError'`、message 恒为 `'Aborted'`），
> **禁止**新建中文 message 的 AbortError。
> 【L3c】测试 #4 断言对象已由「`/abort/i.test(err.message)`」改为「`err.name === 'AbortError'`」（判定统一走 classifyError 的 name）。
