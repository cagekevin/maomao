## 2. 错误类型解剖（「具体是什么类型」）

> 每条都给出：**编译器看到什么类型 → 为什么现在才报 → 真实根因 → 根治写法 → 禁止写法**。
> 这一节是施工时的判据表，遇到报错先对号入座，不要凭手感改。

### 2.1 TS4111 · `noPropertyAccessFromIndexSignature`

**报错原文**：`Property 'type' comes from an index signature, so it must be accessed with ['type']`。

**类型链**：目标类型带 `[key: string]: T`（或 `Record<string, T>`）⇒ `obj.foo` 的类型是 `T`，
但 TS 认为「用点访问等于断言这个键一定存在」，要求显式 `obj['foo']`。

**两类根因，处理方式完全不同**：

| 类别 | 判据 | 典型现场 | 根治写法 |
|---|---|---|---|
| **A. 真字典**（键由运行时/外部输入决定） | 键名不是源码里的固定字面量集合 | LLM 工具入参 `args: Record<string, unknown>`；JSON 校验中间态 `isRecord(value)`；`node.data` 宽对象 | ① 访问改 `['key']`（这是**正确写法**，不是掩盖）；② 取值前先做边界校验，让 `unknown` 变成具体类型 |
| **B. 假字典**（键其实固定，用索引签名偷懒） | 键名全是代码里写死的业务字段 | `ScriptBoxData` 的 `[key: string]: unknown`；`promptHubStore`；`canvasSnapshotSchema` | 把字段**显式登记进 interface**，删掉索引签名；确实需要扩展位的，收成 `extra?: Record<string, unknown>` 单一字段 |

**实证 1（B 类）**：`src/components/scriptbox/scriptBoxSchema.ts:76`

```ts
export interface ScriptBoxData extends ScriptBoxTop {
  shots: ScriptBoxShot[];
  assets: ScriptBoxAsset[];
  [key: string]: unknown;   // ← 根因：textModel / selectedModel / assetModelSettings / upstreamImages
}                           //    全部退化成 unknown，字段名拼错也能过
```

`scriptBoxEngine.ts:193` 的 `d.textModel` 因此报 TS4111；即使改成 `d['textModel']`，
类型仍是 `unknown`，`String(d['textModel'] || ...)` 照样能过 —— **只改语法不解决类型漏洞**。
根治：把这 4 个字段登记进 `ScriptBoxTop` / `ScriptBoxData`，索引签名只保留真正的外部扩展位。

**实证 2（A 类）**：`src/components/agent/canvas/useCanvasAgentTools.ts:396`

```ts
function buildCreateNode(args: Record<string, unknown>, ...) {
  const type = str(args.type);   // TS4111；且 str() 之前 args.type 是 unknown
```

这是 LLM 传进来的不可信 JSON ⇒ 属于 A 类。根治不是 `args.type!`，而是
**边界读取函数**：`const type = readString(args, 'type')`（内部 `typeof v === 'string'`），
返回 `string | undefined`；后续所有分支都在具体类型上跑。

**实证 3（A 类 · 后端）**：`localTool/src/ai-relay/protocol/validation.ts:38`

```ts
if (!isRecord(value)) { ... }
if (!['bearer','header','query','none'].includes(String(value.type))) { ... }  // TS4111 ×151
```

根治：`parseAuthentication(value): AuthConfig | null`，把「校验 + 取值 + 归一化」合成一个函数，
下游拿 `AuthConfig`（`type: 'bearer' | 'header' | 'query' | 'none'`、`prefix?: string`、`name?: string`），
而不是继续在 `Record<string, unknown>` 上点来点去。

**禁止**：`as Record<string, any>`、`// @ts-expect-error`、把 interface 改成 `Record<string, any>` 消错。

### 2.2 TS2375 / TS2379 / TS2412 · `exactOptionalPropertyTypes`

**含义**：`foo?: string` 的语义从「`string | undefined`」收紧为「**要么没有这个键，要么是 string**」。
显式写 `{ foo: undefined }` 不再等价于省略 `foo`。

三个码是同一根因的三种位置：

| 码 | 场景 | 例 |
|---|---|---|
| TS2375 | 对象字面量赋给带可选属性的类型 | `{ stepId: s.id }` → `PlanEntry`，`s.id: string \| undefined` |
| TS2379 | 实参传给带可选属性的参数 | `lockNodeSettings(nodeId, { m: model \| undefined, ... })` |
| TS2412 | 直接给可选属性赋 `undefined` | `this.memory = maybeMemory` |

**实证**：`canvasPlanExecutor.ts:78` + `:633`

```ts
interface PlanEntry {
  stepId?: string;        // 语义：键可缺省
  // ...
}
const entry = { stepId: s.id /* string | undefined */ };  // TS2375
```

**两条根治路线，按「消费方是否区分键是否存在」裁定**：

| 路线 | 何时用 | 写法 |
|---|---|---|
| **A. 承认 undefined 等价于缺省** | 消费方只读值（`entry.stepId ?? ''`）、不 `'stepId' in entry`、不做 JSON 差异 | 接口改 `stepId?: string \| undefined`，一处改、全链路通 |
| **B. 必须不写这个键** | 序列化 / KV 写入 / JSON patch / `Object.keys` 遍历 / 协议字段 | 调用侧条件展开：`...(s.id !== undefined ? { stepId: s.id } : {})` |

**判定流程（每处 30 秒）**：
1. `grep` 该字段名，看有没有 `'foo' in obj`、`Object.keys(obj)`、`JSON.stringify` 后做键比对、`delete obj.foo`；
2. 有 → 路线 B；没有 → 路线 A；
3. 路线 A 只改**声明**，不改调用点；路线 B 只改**调用点**，不改声明。**不要两头都改**（会制造第二份语义）。

**React / r3f 特例**：库的 props 类型不能改（`MeshStandardMaterial` 的 `color?: string`）。
`primitives.tsx:45` 的 `<meshStandardMaterial color={color} />`（`color?: string`）必须走路线 B：

```tsx
<meshStandardMaterial {...whiteMaterial} {...(color !== undefined ? { color } : {})} />
```

**禁止**：`color={color!}`、`color={color as string}` —— 运行时该是 `undefined` 仍是 `undefined`，
断言只让编译器闭嘴，没改变任何行为。

### 2.3 TS2532 / TS18048 / TS2722 / TS2538 / TS2488 · `noUncheckedIndexedAccess`

**含义**：`arr[i]` / `obj[key]` 的结果类型统一加 `| undefined` —— 因为越界/缺键在运行时**确实**是 `undefined`。
这是全套开关里**最直接暴露真实运行时风险**的一项，也是工作量最大的一项。

| 码 | 编译器在说什么 | 典型现场 |
|---|---|---|
| TS18048 | `'x' is possibly 'undefined'`：变量来自索引访问，随后被使用 | `const row = rows[i]; row.cells` |
| TS2532 | `Object is possibly 'undefined'`：直接对索引结果取属性 | `sb.columns[ci].label` |
| TS2722 | 索引取出的函数可能不存在，却被直接调用 | `handlers[name](args)` |
| TS2538 | `undefined` 不能作索引 | `map[maybeKey]` |
| TS2488 | 索引结果不可迭代 | `for (const x of matrix[i])` |

**四种根因，四种根治写法**（这是本期最重要的模板库）：

| 根因 | 反例 | 根治 |
|---|---|---|
| **① 循环索引**（边界由 `i < arr.length` 保证，TS 不认） | `for (let i=0;i<arr.length;i++) arr[i].label` | `for (const [i, item] of arr.entries())` / `for (const item of arr)` —— 把「索引存在」变成语言保证 |
| **② 已判长度后索引** | `if (arr.length > 2) use(arr[2])` | 局部常量 + 显式守卫：`const third = arr[2]; if (third === undefined) return;` |
| **③ 真可能缺**（查表 / 正则组 / `split()[0]`） | `const v = map[key]; v.trim()` | 按业务选：展示层 `?? ''`；数据层早返回；不该缺则 `throw new Error(...)`（fail-loud） |
| **④ 测试里的下标取值** | `expect(rows[0].cells[0]).toBe('x')` | 测试辅助 `at(rows, 0)`（内部断言非空并返回 `T`），或 `const row = rows[0]; expect(row).toBeDefined(); if (!row) throw ...` |

**实证 1（①）**：`src/components/agent/assistantTable/assistantTable.ts:405`

```ts
for (let ci = 0; ci < sb.columns.length; ci++) {
  obj[sb.columns[ci].label] = row.cells[ci] ?? '';   // TS2532 ×N
}
```

根治：

```ts
for (const [ci, col] of sb.columns.entries()) {
  obj[col.label] = row.cells[ci] ?? '';              // col 是 Column，不是 Column | undefined
}
```

**实证 2（③）**：`src/components/videoEditor/engine/lib/gradients/canvas.ts:516`

```ts
const chosen = palette[i];        // GradientStop | undefined
ctx.fillStyle = chosen.color;     // TS18048 ×2
```

必须先回答「`i` 越界时业务上怎么办」：调色板是固定表 ⇒ 越界是编程错误 ⇒ 早抛
`if (!chosen) throw new Error('palette index out of range')`，**不要** `chosen!`。

**实证 3（④）**：`tests/unit/assistantTable.test.ts:79`

```ts
expect(rowToText(table, rows[0])).toBe('...');   // TS2345: TableRow | undefined
```

测试侧建议先落一个共享辅助（新建 `tests/helpers/at.ts`）：`at(arr, i)` 内部 `if (!v) throw`，
这样 1232 处测试错误里的大部分能按同一模板收敛，且失败信息比 `!` 明确。

**禁止**：批量 `arr[i]!`。`!` 会让「越界」从编译期错误变成运行时 `TypeError`，
而这正是这个开关要抓的东西。

### 2.4 TS4114 · `noImplicitOverride`

**含义**：子类覆盖基类成员必须写 `override`，防止「基类改名后子类方法悄悄变成新方法」。

**现场**：React class 组件（`ErrorBoundary` 的 `state` / `componentDidCatch` / `render`）覆盖
`React.Component`；`videoEditor/engine/commands/*` 的命令类覆盖基类 `execute` / `undo`。
40 个文件里 35 个只有 1 处，35 个集中在 `videoEditor`。

**修法**：加 `override`。若加上后报「没有可覆盖的成员」，说明基类早已没有该方法 ⇒
这是**死方法**，删掉（不要为了消错把基类补一个空方法）。

### 2.5 TS1484 · `verbatimModuleSyntax`

**含义**：只用于类型的 import 必须写 `import type`，否则编译产物会保留该 import，
运行时可能加载一个「本该只存在于类型层」的模块。

**修法**：`import { type X, Y } from './m'` 或独立 `import type { X } from './m'`。
18 处 / 11 文件，纯机械。注意：这是**模块语义**开关，不是类型检查严格度，但它属于「最严格」清单，且成本极低。

### 2.6 TS2345 / TS2322 / TS2769 —— 级联错误，**不要单独修**

这三类在 nua/eop 下的绝大多数是「上游变成 `T | undefined` 后，下游参数/赋值对不上」。
修上游自动消失。判据：若某处 TS2322 的参数类型里出现 `| undefined`，先去修那个 `| undefined` 的来源；
只有「来源本身就该是 `T | undefined`」时，才改下游签名。

> **统一机制**：开发期用 CLI 开关跑 `npx tsc --noEmit --<flag>`（主配置保持 0 错、门禁常绿）；
> 期尾把开关写进 `tsconfig.json` 并复验 0 错，再合并。**禁止在期初就把开关写进主配置**——
> 那会让 `check:push` / CI 在整个工期里都是红的，等于关掉了门禁。

## 4. 单文件施工 SOP（每处报错都走这 7 步）

1. **取清单**（只取目标文件，避免被 2000 行日志淹没）：
   ```powershell
   npx tsc --noEmit --noUncheckedIndexedAccess 2>&1 |
     Select-String '^src/components/agent/assistantTable/assistantTable.ts\('
   ```
2. **读类型定义**：跳到报错表达式涉及的 `interface` / `type` / 函数签名。
   问一句：**这个值在类型上为什么可能是 `undefined`？**（数组越界 / 缺键 / 可选属性 / 外部输入）
3. **对号入座**：按 §2 的表判定根因类别（①循环 ②判长 ③真缺 ④测试 / A 真字典 B 假字典 / A 承认 B 不写键）。
4. **写根因，不写断言**：按对应模板改；**禁止** `!`、`as any` / `as unknown as`、`@ts-expect-error`。
5. **单文件复验**：
   ```powershell
   npx tsc --noEmit --noUncheckedIndexedAccess 2>&1 |
     Select-String '^src/.../目标文件\('   # 期望 0 行
   ```
   同时看**全量计数不上升**（改 A 文件时不能把错挤到 B 文件）。
6. **跑相关单测**：`npx vitest run tests/unit/<stem>.test.ts`（按影响面最小射程，禁止全量）。
7. **提交**：一个文件或一组同构文件一个 commit，message 带开关与错误码，例：
   `types(strict): nua assistantTable 收口 28 处（TS2532/TS18048）`。
   本批若登记了债，message 末尾带 TD 号，并按 §5.4 记账。

**节奏**：每 10 个文件更新 §7 进度看板 + 跑一次全量计数；每完成一个模块跑一次相关单测集合。

## 4.6 工具脚本：边做边沉淀（给下一个 AI 复用）

> **原则**：脚本是**给下一个 AI 用的基础设施**，不是一次性命令。
> 遇到重复操作就把「怎么做」固化成 `scripts/` 下的只读工具，让后来者一条命令拿到同样口径的数字；
> 但边界不变：**只做查漏补缺与机械任务，不替人做语义判断**（§4.5.3）。

### 4.6.1 什么时候该写脚本（触发条件，满足任一）

- 同一查询/统计动作本批做了 **≥3 次**（按文件过滤错误、按错误码分组、按属性名聚类）；
- 每次都要手写 **>3 行**管道命令，且参数容易写错（tsc 开关组合、路径过滤、引号转义）；
- 需要「改前/改后」对比，但手工记账**不可复算**（净减口径）；
- 需要**防回退**（本批 diff 里新增 `!` / `as any` / `@ts-expect-error` 就报红）；
- 某个机械任务要重复处理 **>20 处**，且属于 §4.5.3 允许的两类（`import type`、`override`）。

**不写**：
- 只用一次、不涉及批量/对比的查询；
- 需要人判断语义的修复（TS4111 的 A/B、TS2375 的 A/B、TS2532 的缺值策略）——脚本最多出「候选清单」，不能自动改；
- 会写源码且无法原子还原的脚本（除非走 `probe.mjs` 的 journal 机制）。

### 4.6.2 脚本验收标准（缺一不可）

1. **默认只读；改写类默认 dry-run**：不写 `src/` / `tests/` / `localTool/`。确需写盘时，
   **`--dry` 是默认且唯一的安全模式**；应用必须显式 `--write`，且先跑 `--dry` 把完整 diff 交人审阅。
   **没有 `--dry` 的改写脚本禁止使用。**
2. **自检**：扫到 0 个文件 / 解析到 0 条错误时 **fail-loud**（防「假绿」）；tsc 输出必须校验
   「含 `error TS` 的行数 == 成功解析条数」。
3. **口径稳定**：同一输入跑两次输出完全一致（排序稳定）；所有数字可由命令复算，禁止手抄。
4. **可过滤**：至少支持按文件片段、错误码、属性名/变量名过滤。
5. **可对比**：支持 `--json <path>` 落快照、`--diff <path>` 算净减（照 `m1-count.mjs` 的口径）。
6. **登记**：写进 `scripts/README.md`（用途 + 命令 + 是否手动）；脚本头 JSDoc 写清
   「为什么存在 / 口径定义 / 边界」。
7. **不挂 CI**：度量/查漏工具不是闸；只有真正的判据才建闸（本仓 ADR-0016）。
8. **坏样本自证**：先用当前 3658 错里的一个文件验证它**抓得到**，再用 0 错文件验证它**不误报**。

| `test-affected.cjs` | 按暂存改动反查测试（已有） | 复用 | 全程 |

> 台账只增不删；脚本退役时标「已退役 + 原因」，不要直接删行——后来者需要知道为什么不用它。
> 每批收尾（§4 SOP 第 7 步）必须回答一句：**本批有没有重复劳动？该不该沉淀成脚本？**
> 有就当场建/改，并更新本台账 + `scripts/README.md`；没有就写「无」。

### 4.6.4 禁止

- 一次性脚本改名后留在 `scripts/` 冒充工具（无头注释、无自检、无 README 登记）。
- 脚本自动插入 `!` / `as any` / `@ts-expect-error` 来「修」类型错误。
- 脚本直接改源码且没有 `--dry` / 原子还原。
- 脚本输出「0 错」但没有自检（比不扫更危险）。

### 4.6.5 机械改写脚本的三道闸（硬规则）

> 用户裁定（2026-10-19）：**机械改写很危险，必须 `--dry`，否则禁止使用该脚本。**
> 这不是「建议」，是使用许可：没有 dry-run 的改写脚本，一律不许跑。

1. **默认 dry-run**：不带 `--write` 时**只打印 unified diff**（文件、行号、删除行/新增行），
   不写任何文件。`--dry` 是默认模式，不需要额外传；`--write` 才是显式第二道。
2. **写前审阅 + 小批量**：先跑 dry-run，人审 diff；一次 `--write` **≤20 个文件**。
   写前把原文存 journal（同 `probe.mjs`），写后立刻 `npx tsc --noEmit` 全量复验；
   **任何新增错误 → 自动回滚全部改动并 exit 2**。
3. **diff 红线**：候选 diff 里出现 `!` / `as any` / `@ts-ignore` / `@ts-expect-error` → 直接拒绝该脚本；
   `override` 必须落在声明起始（`override async render` ✅，`async override render` ❌ TS1029）。

**已实证的坑（2026-10-19 P1 试跑）**：
- 47 处 TS4114 里有 7 处是 `async render(...)`，`override` 必须写在 `async` **前面**；
  插到 `async` 后面会引入 TS1029 —— 这正是「机械改写必须先 dry-run 看 diff」的证据。
- **更隐蔽的一点（2026-10-19 实测）**：TS 对 `async render` 报的是**名字列**（`render` 的 `r`，第 9 列），
  不是 `async` 的 `a`（第 3 列）。按报错列直接插会生成 `async override render`；脚本必须把插入点
  前移到 `async` 前。`ts-strict-override.mjs` 已按此实现，47/47 候选、0 人工。
- `NetworkError.cause` 覆盖的是 `Error.cause`，`override cause?: unknown;` 合法；
  但若按「删掉冗余字段」处理，会改变 `'cause' in err` 的运行时结果（`useDefineForClassFields`），
  属于**不能机械做**的判断。

## 5. 红线（根治 vs 掩盖）

### 5.1 绝对禁止

| 写法 | 为什么禁止 |
|---|---|
| `arr[i]!` / `obj.foo!` | 把「可能缺」改成编译器闭嘴；运行时越界仍是 `TypeError` |
| `as any` / `as never` | 已有 `scripts/check-any-honesty.mjs`（`npm run check:any`）拦截 |
| `as unknown as X` | 连「两个类型有没有关系」都放弃了 |
| `@ts-expect-error` / `@ts-ignore` | 把报错藏进注释；后续真正的错误也会被一起吞掉 |
| `@ts-nocheck` | 整文件失守（当前全仓 0，必须保持） |
| 把 interface 改成 `Record<string, any>` | TS4111 立刻归零，但类型信息全丢，等于关掉开关 |
| 在子配置里 `strict: false` 覆盖 | 制造「看起来开了、实际没开」的假绿 |
| 使用没有 `--dry` 的机械改写脚本 | 改写不可预览 = 不可审阅；批量写错无法逐行发现 |
| 未经 diff 审阅直接 `--write` | 同上；`async override` 顺序错会引入 TS1029 |

### 5.2 允许的收窄手段（白名单）

`typeof` / `in` 守卫、类型谓词函数（`x is T`）、`??` 默认值、早返回、`throw`（fail-loud）、
`Array.prototype.entries()` / `for...of`、`Map.get` + 守卫、`Object.entries`、条件展开、
`satisfies`、`as const`（仅字面量）、`Array.prototype.at` + 守卫。

### 5.3 「默认值」与「抛错」怎么选

- **展示层 / UI 文案**：`?? ''` / `?? 0` 可接受（缺了也要能渲染）。
- **数据层 / 协议层 / 持久化**：缺了就是数据损坏，**必须抛错或返回错误信封**，不能用默认值掩盖。
  判据：这个字段缺失时，用户看到的是「空白」还是「错误」？后者必须 fail-loud。

### 5.4 收窄时发现 bug：先判定，再登记

> **一句话**：债登记的是「**正确修法还没做**」，不是「这个类型错误不存在」。
> 每批结束时 `tsc` 必须是绿的 —— 所以每条 bug 要么当场修，要么**先加诚实守卫**再登记。
> **禁止第四种**：「登记债 + 保留 `!` / `as`」——那不是"先记着"，是"假装没有"。

#### 5.4.1 先分三类（决定要不要登记）

| 类别 | 判据 | 处置 | 登记债？ |
|---|---|---|---|
| **类型表达债** | 运行时不可能缺（长度/构造/上游校验保证），只是类型没表达出来 | 改 `for...of` / `entries()` / 局部常量 / 类型谓词；**0 行为变化** | 否 |
| **真 bug · 可当场修** | 运行时确实可能缺，缺失会崩/静默错；改动局限在当前文件/同一根因，约 <30 行 | 加守卫或修逻辑 + 单测 + `probe.mjs` 行为探针 | 否（修完即结） |
| **真 bug · 本批不修** | 同上，但需产品决策 / 跨模块重构 / 改动面大 | **先加诚实守卫**（fail-loud 或显式降级 + 日志），再登记 TD，代码注释引用债号 | 是 |
| **真 bug · 不想修** | 修它收益低 / 要产品决策 / 不属于本期范围 | **先登记债**（摘要里写明「为什么不修」），再加诚实守卫；不许留 `!`/`as` | 是 |

> **「先登记」的含义**：遇到 bug 先 `debt.mjs add` 拿真实号，**再决定修不修**；
> 不是先改代码、后补账。债号先落，后续谁接手都能顺着锚点找到证据。

**不属于以上四类的做法一律禁止**：
- 只登记、让 `tsc` 红着 → 门禁不允许，且下一批会被迫用更脏的手段消错。
- 登记完用 `!`/`as` 消错 → 债成了遮羞布。
- 把真 bug 登记成"类型债"降级 → 利息率错档，永远不会被还。

#### 5.4.2 三个问题（每处 30 秒）

1. **运行时真的可能缺吗？**（读调用方、数据来源、不变量）
   - 不可能 → 类型表达债，直接修。
   - 可能 → 第 2 问。
2. **缺了会怎样？**
   - 崩 / 写坏数据 / 静默错 → 真 bug。
   - 展示层空白可接受 → 显式默认值 + 注释；若默认值会掩盖数据损坏 → 升级为真 bug。
3. **本批能修完吗？**
   - 能 → 当场修（守卫 + 单测）。
   - 不能 → 加诚实守卫 + 登记债。
   - **不想修**（收益低 / 要产品决策）→ **先登记债**（摘要写「为什么不修」）+ 加诚实守卫。

#### 5.4.3 登记命令与字段（先拿号，再写注释）

```powershell
# ⓪ 先建本批区域日志（锚点必须是已存在的文件；跨区用 <触发区NN>-跨区-<主题>-<日期>.md）
#    例：daily/架构日志/18-跨区-类型最严格收口-2026-10-19.md

# ① 拿真实债号（禁止先写注释、后补号）
node scripts/debt.mjs add --area 22 --summary "gradients/canvas.ts:516 调色板越界直接取 chosen.color 会 TypeError；本批只加 fail-loud 守卫，空表兜底待还" --class 增债 --rate 高 --anchor 18-跨区-类型最严格收口-2026-10-19.md

# ② 把真实号写进代码注释
# // TD-22-xx：palette 为空属数据错误，此处 fail-loud；空表兜底待还

# ③ 批次收尾体检锚点（断链巡检，不是闸）
node scripts/debt.mjs audit
```

**字段规则**（`scripts/debt.mjs` 写入口会校验）：
- `--area`：按**缺陷所在模块**归区（不新开"类型区"）；跨区只写 `@见 TD-xx`，不搬运明细。
- `--summary`：**≤120 字、禁竖线 `|`／`｜`**；必须含 **文件:行 + 触发条件 + 后果**；解法只写一句话方向，不展开。
- `--class`：`还债` / `持平` / `增债`。修类型表达 → 还债；新增兜底或新缺口 → 增债。
- `--rate`：会崩/主链路/数据损坏 = `高`；边界路径可降级 = `中`；不可达/仅注释漂移 = `低`。
- `--anchor`：本批区域日志（明细真源），**不是**本计划文件。

#### 5.4.4 什么债会阻塞翻开关？

| 利息率 | 允许只登记吗 | 翻开关前的最低要求 |
|---|---|---|
| 高（会崩/主链路/数据损坏） | ❌ 不允许 | 必须先有 fail-loud 守卫或当场修；债只记"正确修法未做" |
| 中（边界路径/可降级） | ✅ 可以 | 显式降级 + 日志留痕 + 债 |
| 低（不可达/仅类型表达） | ✅ 可以 | `tsc` 必须绿（用真实类型消错，不是 `!`） |

**判据**：翻开关那一刻，代码里不能存在「编译器认为安全、运行时可能崩」的路径。
「不想修」**不改变利息率**：高息 bug 即使不想修，也必须先有 fail-loud 守卫才能翻开关。

#### 5.4.5 批次记账模板

```
[strict] <flag> <模块>：N → 0
- 根因簇：<源头类型/interface>（一处改，联动 M 处）
- 真 bug：<文件:行> → 当场修 / 加 fail-loud 守卫 + TD-xx-yy（高息）
- 工具：新增/改进 <script>（或无）；§4.6.3 台账 + scripts/README.md 已更新
- 验证：tsc --noEmit --<flag> = 0；vitest <相关> = N passed；check:any = 0
- 债：新增 TD-xx-yy ×K；debt.mjs audit 通过
```

> 注意：**测试 mock 形状不对不算产品 bug**，直接改测试对齐真实行为；若测试暴露出 src 真 bug，按缺陷所在模块归区登记。
