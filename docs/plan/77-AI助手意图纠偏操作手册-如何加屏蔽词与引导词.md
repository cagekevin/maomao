# AI 助手意图纠偏操作手册：怎么加屏蔽词与引导词

> **什么时候读这篇**：AI 又做了不该做的事——调错工具、绕圈子推理、该做的不做。
> **先读 §0 决策表**，它直接告诉你该改哪一层、改哪个文件。
>
> 行号取自 2026-09-01 的代码状态，**会漂移**——以符号名为准（搜名字比信行号可靠）。

---

## 0. 三十秒决策表

| 症状 | 失灵的层 | 去哪加 | 一句话做法 |
|---|---|---|---|
| **某个具体工具被反复误调** | 工具描述没说清能力边界 | **层②** `useCanvasAgentTools.ts` 该工具的 `description` | 加一句「⚠️ 只返回…，不含…；要…不要调用本工具」 |
| **一类任务在分流表里找不到位置**（模型在两档间摇摆） | 分流表缺档位 | **层①** `agentConfig.ts` 分流表 + 铁律 | 表格加一行 + 铁律加一条 |
| **模型推理很久、反复自我推翻** | 缺确定性引导 | **层③** `agentCore.ts` 正则 + `INTENT_HINT` | 加正则 + 加提示文案 + **必须加单测** |
| **该调的工具没调** | 通常是描述太弱或提示说过头 | 先看层②，再回头检查层①措辞 | 见 §6 红线 4（"禁止"式措辞会让它不敢用） |

**优先级**：能改层② 就别改层①，能改层① 就别改层③。层② 最精准（只影响一个工具），层③ 风险最高（误判会带偏整轮）。

## 1. 三层在哪生效（一条消息的一生）

```text
用户输入
   ↓
【发请求前】组装 system 消息
   ├─ ① CANVAS_RULES 分流表 —— 每轮都在（通用规则）
   └─ ③ 意图预判提示 —— 本地规则命中时才追加（本轮结论）
   ↓
LLM 推理：这轮要干什么？要不要调工具？调哪个？
   ↓
【选工具那一刻】读 tools[].description
   └─ ② 工具能力声明 —— function calling 时唯一必读的位置
   ↓
调用工具 → 执行
```

**① 和 ③ 都在推理前**，区别是：① 是通用规则（要模型自己套用），③ 是本轮结论（不用它推理）。
**② 在最靠近决策点的地方**——模型伸手拿工具时正好读到，所以最有效。

三层互相兜底：① 没挡住，② 在它拿工具时提醒；② 没读进去，③ 开头就说了该干什么。

## 2. 各层怎么加

### 2.1 层② 工具 description（优先用这层）⭐

**位置**：`src/components/agent/canvas/useCanvasAgentTools.ts`，搜工具名找到它的 `description` 字段。

**现成范例**（就是本次改的两处）：

```690:690:src/components/agent/canvas/useCanvasAgentTools.ts
  description: '读取指定节点完整 data（提示词/模型/尺寸/结果 URL 等）。⚠️ 只返回结构化数据，不含图像/视频的画面内容：要分析图片（反推提示词、描述图片、识别图中文字等）请直接看用户消息里的图，不要调用本工具。',
```

```703:703:src/components/agent/canvas/useCanvasAgentTools.ts
  description: '一次读取画布全貌（所有节点+连线，含各节点提示词、文本内容与生成结果）。⚠️ 只返回结构化数据，不含图像/视频的画面内容；分析图片内容（反推提示词、描述图片、识别图中文字等）不要用本工具，直接看用户消息里的图。',
```

**模板**：

```
'<原描述>。⚠️ <这个工具给不了什么>：<正确做法>，不要调用本工具。'
```

三个要素缺一不可：

1. **给不了什么** —— 说清能力边界（"只返回结构化数据，不含画面内容"）
2. **正确做法** —— 告诉它该干什么（"直接看用户消息里的图"），不让它悬着
3. **明确否定** —— "不要调用本工具"

**为什么有效**：模型选工具时必须读 description，这是 100% 会被读到的位置，比 system prompt 里的通用规则更局部、更及时。

**改动后**：跑 `npm run type-check` + `npm run build` 即可（纯字符串，无需加测试）。

### 2.2 层① 分流表（一类任务缺档位时）

**位置**：`src/components/agent/agentConfig.ts` 的 `CANVAS_RULES`（`AGENT_PROMPTS.CANVAS_RULES`）。

两处一起改：

**① 表格加一行**（`:69` 附近）：

```markdown
| **内容理解/产出文字**（反推/写提示词、描述图片内容、提取图上文字、翻译/润色/起标题/起名字、问「这张图里有什么/什么风格」） | 【终止·文字产出】 | **直接用文字给出结果**，不调用任何画布工具；只有用户接着说「照这个生成/出图」才转入【修改与生成】 |
```

**② 铁律加一条**（`:82-83` 附近）：

```markdown
- **「产出文字」≠「生成图片」**：用户要的是提示词/描述/文案这类**文字结果**时，属于【内容理解/产出文字】，不调 create_node / generate_node / get_node_details / list_nodes；只有用户明确说「生成/出图/画一张」才走【修改与生成】。
```

**写档位的要点**：

- 括号里的示例**必须用用户的真实说法**（"反推""起个名字"），不要写抽象概念
- 动作列要给出**判定边界**（什么情况才算这档、什么时候转走）
- 别写"禁止 XX"式措辞——见 §6 红线 4

**注意**：`tests/unit/agentLogic.test.ts` 只断言 `toContain('你是猫猫画布助手')`，改表格内容不会破坏测试。

### 2.3 层③ 本地预判（模型摇摆时用，风险最高）

**位置**：`src/components/agent/runtime/agentCore.ts` 末尾「意图本地判定」段落。

**三处要一起改**：

| 改什么 | 位置 | 说明 |
|---|---|---|
| 正则 | `:669` `GENERATE_RE` / `:671` `CONTENT_RE` / `:673` `CHAT_RE` | 按判定顺序从前到后，越靠前优先级越高 |
| 提示文案 | `:658` `INTENT_HINT` | 注入给模型看的那句话 |
| 判定函数 | `:682` `classifyLocalIntent` | 加新 intent 时要在函数里加分支 |

**模板（以加一个新意图为例）**：

```ts
// 1) 加正则
const XXX_RE = /(关键词1|关键词2|关键词3)/i

// 2) 类型加值
export type LocalIntent = 'chat' | 'content' | 'generate' | 'xxx'

// 3) 加提示文案
export const INTENT_HINT: Record<LocalIntent, string> = {
  ...
  xxx: '<这类任务该怎么做的说明>',
}

// 4) 判定函数加分支（注意顺序！）
if (XXX_RE.test(t)) return { intent: 'xxx', confidence: 0.85, rule: 'xxx' }
```

**四条硬规则**：

1. **宁可漏判，不可误判**。判不出返回 `null` → 不注入 → 行为完全同现状，零风险；误判会把整轮引导到错的方向。
2. **生成类动词必须排在前面**。「反推提示词并生成一张图」必须判 generate，否则会把真实出图需求引导成"不用工具"。
3. **单字动词要慎重**。「画」没进 `GENERATE_RE`，因为会误伤「画风」这类描述词——宁可让"画一只猫"漏判（交 LLM 正常出图）。
4. **改了就必须加单测**，见 §3。

## 3. 层③ 的单测要求（强制）

改了正则或判定函数，**必须**在 `tests/unit/localIntent.test.ts` 补用例，三类都要有：

```ts
const cases: [string, string][] = [
  // ① 正向：新加的关键词要命中
  ['新关键词的例句', 'xxx'],
  // ② 反向：不能被新正则误伤的（尤其是生成类）
  ['反推提示词并生成一张图', 'generate'],
  // ③ 无关：完全不相关的输入必须仍是 null
  ['帮我把这些节点连起来', 'null'],
]
```

再补一条 `buildIntentHint` 断言（验证注入文案真的变了）：

```ts
it('xxx 命中时注入对应提示', () => {
  expect(buildIntentHint('新关键词的例句')).toContain('<INTENT_HINT 里的关键词>')
})
```

现有 27 个用例就是这么组织的，照抄结构即可。

## 4. 完整案例：本次「反推图像提示词」故障

**症状**：用户发图 +「反推图像提示词」→ 模型在【查看画布】与【生成/改图】间摇摆 6 轮 → 误调 `get_node_details`。

**定位**：

- `get_node_details` 只返回节点结构化 data，**读不到画面内容** → 纯属无效调用
- 根因是分流表 8 档里没有"内容理解/产出文字"的位置，模型只能二选一

**三层各加了什么**：

| 层 | 加了什么 | 解决什么 |
|---|---|---|
| ① | 分流表补「内容理解/产出文字」档 + 「产出文字≠生成图片」「工具能力边界」两条铁律 | 摇摆：给档位 |
| ② | `get_node_details`、`read_canvas` 的 description 加"只返回结构化数据，不含画面内容" | 误调：选工具时提醒 |
| ③ | `CONTENT_RE` 收反推/描述/提取/翻译润色/起标题等词 + `INTENT_HINT.content` | 摇摆：直接给结论 |

**顺带修的**：`read_canvas` 原描述写着「要了解全局时**优先**用它」——这句在**主动引导**误调，已改。

**验证**：type-check 通过 + 2226 用例全过（新增 27 条）+ build 成功。手工验三条：发图反推提示词不调工具 / 「你好」纯文字 / 「列出画布节点」照常工作。

## 6. 红线（别踩）

1. **同一句话别在三处都加**。层① 已说过"工具读不到画面内容"，层② 再写一遍是噪音——层② 的价值在于**局部于那个工具**，措辞要针对该工具。
2. **不要改请求结构做硬拦**（比如"禁工具意图 → 请求体不传 tools 字段"）。已评估否决：误调只读工具只慢一轮，误判却让 AI 整轮无法操作画布，**代价不对称**。
3. **正则宁漏不误**（层③ 专属，见 §2.3 硬规则 1）。
4. **别用"禁止/绝对不许/永远不要"式措辞**。会让模型僵化——该用工具时也不敢用。写"When not to use"而不是"Never use"。
5. **不要为了保险给所有工具都加**。只改**实际被误调**的那个（本次只改了 2 个读工具，`list_nodes` 没动，因为它的描述已有"改画布前"的语境限定）。
6. **改 `localTool/` 还要另跑** `cd localTool && npm test`（本次没碰后端）。

## 7. 什么时候说明三层都不够

**观察信号**：同一类误调在加了层② 之后仍反复出现（说明文字引导对该模型无效）。

那时才考虑架构级方案：

- **L3 执行期白名单** —— 在 `agentRuntime.ts` 的 `runToolCalls` 里，按意图校验 `toolName ∈ INTENT_TOOLS[intent]`，不在则拒绝并回一条提示。
- 这是**架构改动**（涉及 `agentCore` / `useAgentChat` / `agentRuntime` / `agentConfig` 四处），要走 `spec/CONTEXT.md` 的重型重构 SOP，**别自己直接上**。
