## 1. 旧方案审计结论（7 项）

### 🔴 A-1 致命：无改动也推 → 双机 rev 空转 → 无限假冲突弹窗

- 现象：`uploadConfig` 只要 `decideUpload` 返回 `none` 就**必定 push**（`cloudSync.ts:589-591`），不管本地有没有改动。每轮 rev +1。
- 后果（可复现）：A 机空转推到 rev 6 → B 机台账还是 rev 5 → `cloudRev > ledgerRev` → **弹「云端内容比你本地新」**，但内容其实一模一样。B 选「上传」→ rev 7 → A 下一轮又弹……**每 30 分钟弹一次，永不收敛**，且用户看不到任何实际差异。
- 旧方案把它当成「rev 无意义自增（优化项，建议实现）」，实为**正确性缺陷**。
- **修法**：判定加「内容维度」——云端内容指纹 == 本地内容指纹 → 一律跳过（不推、不弹）。见 §4.1。这是本方案的地基，缺了它整个自动同步不可用。

### 🔴 A-2 严重：新机器无台账 + 云端有数据 → 静默覆盖云端

- 现状：`decideUpload` 中 `!input.ledger` 直接返回 `none`（`cloudSync.ts:290`），即「无基线无从判断 → 静默上传」。手动点一次问题不大；**自动同步无人值守时，等于一台新机器把云端真实数据用本地默认值覆盖掉**。
- **修法**：拆成两条——云端为空 → `none`（首次上传，安全）；云端有数据但无台账 → `cloud-newer`（必须问一次）。见 §4.1。
- ⚠️ **契约变更**：`tests/unit/cloudSync.test.ts:303` 的用例「无台账 → none」需同步改为「无台账 + 云端有数据 → cloud-newer」，并补「无台账 + 云端为空 → none」。

### 🟠 A-3 引用了不存在的 API（照抄会直接编译失败）

旧稿 §2/§4.5 声称「现有 `useCloudSync().enabled` + `getSigninState()`」。**全库 0 匹配，两者都不存在**。本项目云同步是 GAS URL 直连（`config.ts:151` CLOUD_SYNC_GAS_URL），**没有登录态、没有 enabled 开关**（手动按钮是无条件可点的）。
- **修法**：新增 `isCloudSyncReady()`（判定＝GAS URL 有效 且 当前无同步在跑），放在 `cloudSync.ts`，自动与手动共用。见 §4.4。

### 🟠 A-4 `running` 重入标志：多余且有害

- 多余：调度用**递归 `setTimeout`**（在 `finally` 里排下一轮），单标签内天然不可能重入。
- 有害：`askConfirm` 的 Promise **没有超时**，用户不点就永不 settle。若弹窗挂起，`running` 永远 true → **自动同步永久死亡直到刷新**。
- **修法**：删除 `running`。跨标签并发由 `CloudSyncEngine.isSyncing`（`cloudSync.ts:39/44`，fetch 层 throws）兜底。

### 🟠 A-5 过度设计：BroadcastChannel Leader 选举（约 60 行状态机）可以不要

旧稿称其为「行业标配」。但本项目同浏览器多标签**共享 localStorage**（台账、数据全是同一份），配合 A-1 的「内容一致即跳过」：
- 两标签同时 tick → 都 pull → 都发现内容一致 → 都跳过，**零副作用**；
- 最坏情况（恰好都判定该推）→ 多推一次、rev +2 → 下一轮内容一致 → 跳过，**用户零感知**。
- 而 Leader 选举还引入新故障模式：**Leader 标签在后台（hidden）→ 全天不轮询，同步彻底停摆**。
- **修法**：整块删除（`-60` 行，少一个频道、一个心跳定时器、一套重选举状态机）。

### 🟡 A-6 后台标签 `document.hidden` 一刀切 → 全天不推

旧稿在 tick 开头 `if (document.hidden) return`，`runTick` 直接结束。用户挂着标签切到别处 → **一整天没同步过**。
- **修法**：只在「需要弹窗」时让路：静默推送照常跑；把 `document.hidden` 判断挪进冲突处理器，命中即按「稍后」处理且**不计入退避计数**（用户没看见，不该算他拒绝）。见 §4.5。

### 🟡 A-7 杂项

| # | 问题 | 修法 |
|---|---|---|
| a | tick 里传 `showToast` 当 `onProgress` → 每 30 分钟弹「正在同步至云端」toast，与「静默」自相矛盾 | 自动链路不传 `onProgress`；只在「下载完成 / 失败」弹一次 |
| b | 冲突文案沿用手动版「仍要上传覆盖」（红色危险按钮），自动场景主按钮语义错 | `describeUploadConflict(d, mode)`，`auto` 模式出三态文案 |
| c | `cloud-unknown`（GAS 抽风）每 30 分钟弹「无法确认云端是否有更新」 | 自动链路静默跳过，不计退避 |
| d | 自动下载后照抄手动链路 `window.location.reload()` → **正在画的画布被冲掉** | 自动链路**绝不 reload**，只 toast「部分设置刷新后生效」 |
| e | `restartAutoSync()` 需额外接到「设置变更」，漏接就是 bug | 开关每轮现读 `getSetting('autoSyncEnabled')`，**不需要任何重启接线**；`restartAutoSync` 整个删除 |
| f | 间隔做成 `appSettings` number 项 → 需扩 `settingRegistry` 的 `SettingDef` 联合（现只有 `boolean` / `string[]`）+ 自定义 UI | v1 **固定 30 分钟常量**，间隔可调留二期 |

## 2. 最终语义（唯一权威状态机）

每轮 tick = **1 次只读探测（pull_data）**；只有判定「本地有改动且云端不新」才再发 1 次 push。真正的「拉」只在用户点「下载云端」时发生（满足「只定时推，不自动拉」）。

| 云端可读 | 本地脏 | cloudRev > ledgerRev | 内容一致 | 行为 |
|---|---|---|---|---|
| ✓ | ✗ | ✗ | ✓ | **跳过**（0 次写请求） |
| ✓ | ✗ | ✓ | ✓ | **跳过**（rev 空转，内容相同 → 不打扰） |
| ✓ | ✗ | ✗ | ✗ | 静默推（无基线，云端为空/首次） |
| ✓ | ✓ | ✗ | ✗ | **静默推**（无冲突，不打扰） |
| ✓ | ✗ | ✓ | ✗ | 弹三选一 · 标题「云端有更新」 |
| ✓ | ✓ | ✓ | ✗ | 弹三选一 · 标题「双方都有更新」 |
| ✓ | — | — | — | 无台账 + 云端有数据 → 弹三选一（A-2） |
| ✗ | — | — | — | **静默跳过**（网络抖动，不打扰、不计退避） |

三选一：`下载云端` / `上传本地` / `稍后`。
- 选「下载云端」→ `downloadConfig` → 写回本地 + 记台账 → 下一轮内容一致 → 收敛。
- 选「上传本地」→ 继续 push → 记台账 → 收敛。
- 选「稍后」→ 本轮不动任何数据，`cancelCount+1`；**连续 3 次 → 退避到次日 00:00**，当天不再弹。任一次「下载/上传」成功即清零。

## 3. 目标架构

```
App.tsx useEffect  → startAutoSync() / 卸载 stopAutoSync()
                          │ 递归 setTimeout（首轮 30s，之后 30min）
                          ▼
              autoSync.ts（模块级单例，不依赖 React）
        ┌─────────────────┼─────────────────┐
   每轮读开关         跳过/退避/离线/GAS未就绪     冲突时
   getSetting        isCloudSyncReady()      askChoice 三选一
        └─────────────────┼─────────────────┘
                          ▼
        uploadConfig(undefined, { onAutoConflict })
                          │
        ┌─────────────────┼──────────────────┐
     skipped           ok(true)          action:'download-needed'
      （跳过）         （静默推送完成）      → downloadConfig(onConfirm: askConfirm)
```

数据流单向：`autoSync → cloudSync → CloudSyncEngine`，autoSync 不反向依赖 UI；弹窗经 `confirmStore` 中转。

**(2) `decideUpload` 加 `cloudHash` 入参 + 两条新规则**（约 270-297 行）
```ts
export function decideUpload(input: {
  cloudReadable: boolean;
  cloudExists: boolean;
  cloudRev: number;
  cloudUpdatedAt: number;
  ledger: SyncLedger | null;
  localHash: string;
  /** 云端内容指纹（'' = 云端空/读不到）。与 localHash 同由 contentFingerprint(纯数据) 产出，可直接比 */
  cloudHash?: string;
}): UploadDecision {
  const localDirty = !input.ledger || input.ledger.localHash !== input.localHash;
  const inSync = !!input.cloudHash && input.cloudHash === input.localHash;
  const base: UploadDecision = {
    kind: 'none', cloudRev: input.cloudRev, cloudUpdatedAt: input.cloudUpdatedAt,
    ledgerRev: input.ledger?.rev ?? null, localDirty, inSync,
  };
  if (!input.cloudReadable) return { ...base, kind: 'cloud-unknown' };
  // 【A-1】内容完全一致 → 无论 rev 谁大都不打扰、不推（否则双机 rev 空转会无限弹假冲突）
  if (inSync) return base;
  // 云端为空 → 首次上传，静默
  if (!input.cloudExists) return base;
  // 【A-2】云端有数据但本机无台账 → 关系未知，必须问一次，不可盲推覆盖
  if (!input.ledger) return { ...base, kind: 'cloud-newer' };
  if (input.cloudRev > input.ledger.rev) {
    return { ...base, kind: localDirty ? 'both-changed' : 'cloud-newer' };
  }
  return base;
}
```
> `cloudHash` 可选 → 老调用方（含现有单测）行为不变，增量安全。

**(3) 新增三态类型 + `uploadConfig` 扩 `onAutoConflict` / 返回 `action`/`skipped`**（约 536-616 行）
```ts
export type ConflictResolution = 'upload' | 'download' | 'cancel';
export type AutoConflictHandler = (
  copy: ConfirmCopy, decision: UploadDecision,
) => Promise<ConflictResolution>;

export async function uploadConfig(
  onProgress?,
  opts: { onConfirm?: UploadConfirmHandler; onAutoConflict?: AutoConflictHandler } = {},
) {
  // ...collectLocalData / pull 不变...
  const cloudHash = cloud ? contentFingerprint(cloud.data) : '';
  const decision = decideUpload({ cloudReadable, cloudExists: !!cloud, cloudRev: cloud?.rev ?? 0,
    cloudUpdatedAt: cloud?.updatedAt ?? 0, ledger, localHash, cloudHash });

  if (decision.kind !== 'none') {
    if (opts.onAutoConflict) {
      const r = await opts.onAutoConflict(describeUploadConflict(decision, 'auto'), decision);
      if (r === 'cancel')   return { ok: false, count: 0, cancelled: true };
      if (r === 'download') return { ok: false, count: 0, action: 'download-needed' as const };
      // 'upload' → 落到下面 push
    } else if (opts.onConfirm) {
      if (!(await opts.onConfirm(describeUploadConflict(decision, 'manual'), decision)))
        return { ok: false, count: 0, cancelled: true };
    } else {
      logger.warn('同步', '[上传] 有冲突但未提供确认回调，按旧行为直接上传', { kind: decision.kind });
    }
  } else if (decision.inSync) {
    // 【A-1】内容一致 → 零副作用跳过（不 push、不 +rev、不弹窗）
    logger.debug('同步', '[上传] 内容一致，跳过', {}, { module: 'project' });
    return { ok: true, count: 0, skipped: true };
  }
  // 3) 打包推送（不变）
}
```

### 4.2 `src/components/base/core/confirmStore.ts`（二态→三态，**净简化**）

不要并出两套机制。把内部 resolver 泛化为 `ChoiceKey`，`askConfirm` 降级为门面：

```ts
export type ChoiceKey = 'confirm' | 'download' | 'cancel';

let pending: { request: ConfirmRequest; resolve: (c: ChoiceKey) => void } | null = null;

/** 三态确认（含可选第三按钮）。有旧弹窗未决 → 旧请求按 cancel 结算，保证每个 Promise 都 settle。 */
export function askChoice(opts: ConfirmOptions & { downloadText?: string }): Promise<ChoiceKey> {
  if (pending) settle(pending, 'cancel');
  return new Promise((resolve) => {
    const request: ConfirmRequest = { ...opts, id: ++seq,
      confirmText: opts.confirmText || DEFAULT_CONFIRM_TEXT,
      cancelText: opts.cancelText || DEFAULT_CANCEL_TEXT,
      danger: !!opts.danger };
    pending = { request, resolve };
    emit();
  });
}

/** 二态门面：confirm=true / 其余=false。手动同步链路零改动。 */
export function askConfirm(opts: ConfirmOptions): Promise<boolean> {
  return askChoice(opts).then((c) => c === 'confirm');
}

export function resolveConfirm(ok: boolean): void { resolveChoice(ok ? 'confirm' : 'cancel'); }
export function resolveChoice(c: ChoiceKey): void { if (pending) settle(pending, c); }
```
- `ConfirmRequest` 加 `downloadText?: string`。
- `settle` 签名改 `(item, c: ChoiceKey)`。**文件头 JSDoc 同步更新**（这是全局唯一确认入口的机制变更，必须留痕）。

### 4.5 新增 `src/components/base/store/autoSync.ts`（约 90 行）

文件头 JSDoc 必须写清：为什么没有 `running` 标志、为什么没有 Leader 选举、为什么 `inSync` 短路是地基（CLAUDE.md §决策记录铁律：单文件局部机制记文件头）。

```ts
import { getSetting } from './appSettings.ts';
import {
  uploadConfig, downloadConfig, isCloudSyncReady,
  type AutoConflictHandler, type ConflictResolution,
} from './cloudSync.ts';
import { askChoice, askConfirm } from '../core/confirmStore.ts';
import { showToast } from '../core/toastStore.ts';
import { logger } from '../core/logger.ts';

const INTERVAL_MS = 30 * 60_000;
const FIRST_DELAY_MS = 30_000;
const CANCEL_BACKOFF_THRESHOLD = 3;

let timer: ReturnType<typeof setTimeout> | null = null;
let started = false;
let cancelCount = 0;
let backoffUntil = 0;

/** 排下一轮（递归 setTimeout：单标签内天然串行，无需 running 重入标志 —— 见 A-4） */
function scheduleNext(delay = INTERVAL_MS): void {
  if (timer != null) clearTimeout(timer);
  timer = setTimeout(() => { void runTick(); }, delay);
}

async function runTick(): Promise<void> {
  try {
    if (!getSetting('autoSyncEnabled')) return;   // 每轮现读 → 改开关无需重启调度器（A-7e）
    if (Date.now() < backoffUntil) return;        // 当日退避：用户连续「稍后」3 次
    if (!navigator.onLine) return;
    if (!isCloudSyncReady()) return;              // GAS 未配置 / 正有同步在跑

    // 不传 onProgress：自动同步全程静默，只在「下载完成/失败」弹一次 toast（A-7a）
    const r = await uploadConfig(undefined, { onAutoConflict: autoResolveConflict });

    if (r.action === 'download-needed') {
      const d = await downloadConfig(undefined, { onConfirm: (copy) => askConfirm(copy) });
      cancelCount = 0;
      // 绝不 reload：自动下载若照抄手动链路的 window.location.reload() 会冲掉正在画的画布（A-7d）
      if (d.ok) showToast(`已下载云端配置（${d.count} 项），部分设置刷新后生效`, { type: 'success' });
      else if (!d.cancelled) showToast(d.error || '下载云端配置失败', { type: 'error' });
    } else if (!r.cancelled) {
      cancelCount = 0;
    }
  } catch (e) {
    logger.warn('自动同步', '本轮异常（静默，不阻塞 UI）', { error: (e as Error)?.message || '未知' });
  } finally {
    scheduleNext();
  }
}

/** 冲突三选一。返回 cancel 时区分「用户真的点了稍后」与「不该打扰」，后者不计退避。 */
const autoResolveConflict: AutoConflictHandler = async (copy, decision) => {
  if (document.hidden) return 'cancel';            // A-6：后台不弹，下轮再说（不计退避）
  if (decision.kind === 'cloud-unknown') return 'cancel'; // A-7c：网络抖动不打扰（不计退避）
  const c = await askChoice({ ...copy, cancelText: '稍后', downloadText: '下载云端' });
  if (c === 'download') return 'download';
  if (c === 'confirm') return 'upload';
  cancelCount += 1;
  if (cancelCount >= CANCEL_BACKOFF_THRESHOLD) {
    const t = new Date(); t.setHours(24, 0, 0, 0); // 次日 00:00 重置
    backoffUntil = t.getTime();
    cancelCount = 0;
  }
  return 'cancel';
};

export function startAutoSync(): void {
  if (started) return;
  started = true;
  scheduleNext(FIRST_DELAY_MS);
}
export function stopAutoSync(): void {
  if (timer != null) clearTimeout(timer);
  timer = null;
  started = false;
}
```

## 7. 验收（手动，约 15 分钟）

1. 静置 30 分钟无任何改动 → F12 Network 每 30min **仅 1 个 `pull_data`**，无 `push_data`，无 toast，无弹窗。
2. 改一个设置（如关「显示缩略图」）→ 30min 内自动 `push_data` 一次，rev +1，无 toast。
3. 另一台机器/浏览器改数据并推送 → 本机下一轮弹三选一；点「下载云端」→ 本地生效 + toast，**页面不刷新**；再等一轮 → 无弹窗（收敛）。
4. 连点 3 次「稍后」→ 当天不再弹；手动点 TopNav「从云端拉取」仍可用。
5. 切到别的标签让页面 hidden 30min → 无弹窗；切回来下一轮正常。
6. 关掉「自动同步到云端」开关 → 不再有任何云请求（无需重启）。

## 8. 已知边界（不修，记录在案）

- **跨设备 `providers` 天然不同**：`collectLocalData`（`cloudSync.ts:422`）从本机 localTool 读 API 供应商配置，两台机器配置不同 → 内容指纹恒不相等 → 会持续判定为真冲突。用户点一次「下载云端」或「上传本地」后即收敛（下载后本地=云端，指纹一致）。localTool 未启动时 `providers` 缺失，同理。
- **退避状态只存内存**：刷新即清零（下次启动重新给 3 次机会），符合预期，不落盘。
- **间隔不可调**：v1 固定 30 分钟（`autoSync.ts` 常量）。要做成设置项需扩 `settingRegistry` 的 `SettingDef` 联合加 `'number'` 类型 + 自定义 select UI，约 +40 行，留二期。
