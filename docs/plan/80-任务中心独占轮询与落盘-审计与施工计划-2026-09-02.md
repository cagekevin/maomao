## 一、审计对象：一次生图到底发了多少次请求

样本时间线（18:12:38 提交 → 18:13:29 完成）：

| 请求 | 次数 | 说明 |
|---|---|---|
| `GET /v1/tasks/{id}`（生图轮询） | 13 | 间隔 3s，`proxyGenerate.pollUntilDone` |
| `GET /api/v1/gateway/task/{id}`（恢复轮询） | 8 | 间隔 5s，`pollTask.runRound` |
| `POST /api/files/upload` | **2（并发）** | 同一 URL、同一秒各发一次 |
| `POST /api/tasks/save`（saveTask） | 30+ | 每轮轮询各回写一次 |
| `GET/POST kvGet/kvSet`（项目快照） | 若干 | 无关，不展开 |

**两条轮询查的是同一个 `taskId`，且查的是同一件事。** 这是本文的中心事实。

## 二、现状：三个「双」

### 2.1 双轮询者

| 轮询者 | 传输 | 单次超时 | 重试 | 位置 |
|---|---|---|---|---|
| 生图流程 | `/api/proxy` → 网关 | **`timeoutMs: 0`（无超时）** | 0 | `src/components/base/api/proxyGenerate.ts` 的 `pollUntilDone` |
| 恢复轮询 | `/api/v1/gateway/task/{id}` | 默认 `HTTP_DEFAULT_TIMEOUT`=15000 | **3（继承默认）** | `src/components/base/api/pollTask.ts` 的 `pollOneTask` |

两个主人、两套传输、两套超时策略，查同一个任务；任务中心只是它们共同回写的数据库。

**为什么恢复轮询会介入"根本没刷新"的任务**（这是"好多恢复轮询"的直接原因）：

`pollTask.runRound` 的候选条件是 `status ∈ {running, pending} && pollTaskId`。而 async 提交成功瞬间 `proxyGenerate` 就调 `setTaskPollId` 写回 `pollTaskId` → 该任务**立即成为候选**。互斥锁 `nodeRunning`（`taskStore.ts`，按 nodeId）只防"同一节点重复 start"，**不防查询**。

放大项（三个叠加，缺一不可）：

1. `pollOneTask` 未传 `timeoutMs`/`retries` → 继承 httpClient 默认 15s × 3 次 ≈ 单任务最坏占用 **约 48s**；
2. `POLL_INTERVAL = 5000`，且 `initTaskRecovery` 的 `setInterval` 回调里 `runRound()` **未 await**；
3. 模块内只有 `lastRun`/`timer` 两个变量，**没有 in-flight 集合**。

→ 上一轮没跑完，5s 后新一轮照扫同一批，查询必然重叠。

附带隐患：`pollUntilDone` 的轮询请求用 `timeoutMs: 0`。网关挂起时单次轮询可挂到 `GEN_TIMEOUT`（300s），配合 `GEN_MAX_CONCURRENT = 6` 即 6 个悬挂请求。

### 2.2 双落盘出口

一次生成对同一个远程 URL 发了**两个并发** `POST /api/files/upload`。两个调用点：

- `src/hooks/useNodeGeneration.ts` —— 主落盘，`await saveResultToTasks(...)`
- `src/components/nodes/PromptNode.tsx` 的 `onSuccess` —— 再落一次

**这不是谁手滑多写了一遍，是被上游的写入顺序逼出来的补丁**：

`useNodeGeneration` 在落盘**之前**先把原始外链写进 `node.data[resultKey]`（乐观回填，供即时显示）。`onSuccess` 拿到的是原始外链，为了把节点上的地址修正成持久 URL，只好自己再落一次盘。

后端的幂等在并发下失效：

`localTool/src/routes/files.ts` 的 `saveRemoteUrl` 用 `fs.existsSync(savedPath)` 判重，但判定发生在**下载完成之后**（URL 带扩展名时）或下载后定名时——两个并发请求到达时双方都判 `false` → **都真下载一遍**。文件头注释宣称的"重复调用不重复落盘"在并发场景不成立。

### 2.3 双完成出口

`agent:task-completed` 有两个发布点，载荷语义不同：

| 发布点 | `resultUrl` 内容 |
|---|---|
| `taskStore.done` | 已落盘的持久 URL（`/files/tasks/...`） |
| `pollTask.pollOneTask` | **上游原始外链**（`https://a.lovart.ai/...`） |

恢复轮询先判 completed 时，会经 `useNodeGeneration` 的完成监听 → 节点 `onRecover` → 把**已落盘的持久 URL 覆盖成会过期外链** → 刷新后丢图。

## 三、根因

| 编号 | 根因 | 表现 |
|---|---|---|
| **A** | 轮询权不在任务中心：两个模块各自轮询同一 taskId | 请求翻倍、恢复轮询"刷屏"、两套超时策略、`timeoutMs:0` 悬挂 |
| **B** | 落盘权不在任务中心：落盘前先写原始外链，逼出第二处落盘 | 下载翻倍、30s 预算被摊薄 → **下载超时** |
| **C** | 完成出口不在任务中心：两个 publish 点、载荷不一致 | 外链污染节点、刷新丢图 |

> **A 是 B 的间接放大器**：轮询与下载打的是**同一个 localTool 进程（18080）**。轮询自我堆积成并发重叠 → 挤压事件循环/连接 → 下载的 30s 预算被吃穿。

## 四、目标架构：任务中心独占

**核心判断：`pollTaskId`「有主与否」是运行时属性，不是任务属性。**

刷新后进程内状态天然为空，所有在跑任务自动变"无主"。因此——

> **「恢复」不再是独立机制**，它等于「启动时给所有 `running/pending` 且 `pollTaskId` 的任务重新挂轮询器」，调用的是与生成流程**同一个 `ensurePolling(taskId)`**。

### 4.1 轮询器注册表（运行时，不持久化）

`src/components/base/taskStore.ts` 内新增：

```
const pollers = new Map<string, PollerHandle>()   // taskId -> 句柄
```

- `ensurePolling(taskId, opts)` —— 唯一轮询入口。已有 entry 则直接返回其 promise；**一个 taskId 在 Map 里只可能有一个 entry → 双重轮询在构造上不可能**，不需要任何去重/互斥判断。
- `awaitTask(taskId, { timeoutMs, signal })` —— 等待终态，返回 `{ status, payload, error }`。
- `stopPolling(taskId)` —— 终态/中止时清理。

轮询参数从散落三处收敛到一处：

| 项 | 现状 | 收敛后 |
|---|---|---|
| 传输 | `/api/proxy` 与 `/api/v1/gateway/task` 两套 | **统一 `/api/v1/gateway/task/{id}`**（provider 无关——换 API 前端无感，沿用 `pollTask.ts` 文件头既有取舍） |
| 单次超时 | `0` / 默认 15s×3 | **20s，`retries: 0`**（轮询本身有下一轮，http 层重试是错配） |
| 间隔 | 3s / 5s 各写各的 | 按 type：`GEN_POLL_INTERVAL` / `VIDEO_POLL_INTERVAL` |
| 总超时 | 300s / 600s | 按 type：`GEN_TIMEOUT` / `VIDEO_TIMEOUT` |

调用方只有两处，同一实现：
1. 生成流程拿到 `pollTaskId` 后（替代 `pollUntilDone` 的 while 循环）
2. 启动扫描（替代 `initTaskRecovery`，`src/App.tsx` 挂载后调用）

### 4.2 落盘回归任务中心（**撤销 P0-C 契约**）

现状契约（`taskStore.ts` 的 `done` 注释）：「resultUrl 应为已持久 URL；**调用方先落盘再 done**」。

改为：`done(rawUrl)` → 任务中心落盘 → 广播持久 URL。

- 删 `useNodeGeneration.ts` 主落盘处的 `saveResultToTasks`
- 删 `PromptNode.tsx` `onSuccess` 里的 `saveResultToTasks`
- 一次生成 = **一次下载**（构造保证，不靠去重）

节点显示不受影响：`node.data` 的乐观写入保留作即时反馈，完成事件携带持久 URL 由既有完成监听覆盖回写。节点零下载。

### 4.3 完成出口唯一

`publishTaskCompleted`（`src/components/base/taskCompletionBus.ts`）只在任务中心的终态函数里调一次。`taskStore.done` 与 `pollTask` 两处收进来，载荷天然一致。

### 4.4 下载并发闸门（可选，P2）

现状 6 个生图并发 = 6 个 30s 预算下载同时抢带宽。任务中心加下载并发上限（2~3），排队而非并发。

⚠️ 与 `spec/CONTEXT.md §三`「并发治理：仅生图需要治理」冲突。本条是**同一原则的延伸**（落盘并发由落盘所有者治理），不是新增防御；若认为过度设计，可砍掉本条，仅保留 `saveResultToTasks` 的进程内 URL→Promise 去重。

## 八、本方案不覆盖（诚实边界）

- **真实网络延迟**：若 `a.lovart.ai` 经代理确实慢，根治后下载该慢还是慢。根治消除的是**自伤**（双倍下载、轮询风暴、300s 悬挂）。剩余问题看后端 `[download] FAIL` 日志（`localTool` 控制台）判断是代理层还是 CDN 层。
- **视频超时预算**：`config.ts` 虽有 `VIDEO_DOWNLOAD_TIMEOUT = 60000`，但 `saveResultToTasks` 统一用 `UPLOAD_TIMEOUT = 30000`，视频下载极易超时。**按 type 选超时**未纳入本计划的正文（属单点修复，可随手改）。
- **sync 生图无 `pollTaskId`**：不在本方案范围，仍走既有 `data.imageUrl` 副本恢复路径（见 `spec/CONTEXT.md §五` 数据一致性风险红线 ③）。

### 9.3 现状数据流

```
前端
├─ proxyGenerate.pollUntilDone ── while(3s) ──► /api/proxy ──► 9004 /v1/tasks/{id}
│        └─ setTaskPollId() 写回 ──┐
├─ pollTask.runRound ── 每 5s 扫 ──► /api/v1/gateway/task/{id} ──► 9004
│        └─ patchTask() ───────────┤
│                                  ▼
│                          taskStore（被动存储）
│                                  ├─ patchTask → saveTask（每个轮询者各 1 次）
│                                  └─ publishTaskCompleted（2 个发布点）
├─ useNodeGeneration ──► saveResultToTasks ──► /api/files/upload ──► 下载 CDN
└─ PromptNode.onSuccess ─► saveResultToTasks ─► /api/files/upload ──► 下载同一 CDN
                                                     │
                                                     ▼
                                        localTool（18080，单进程承担以上全部）
```

**关键**：轮询与下载打的是**同一个 localTool 进程**。前端轮询自我堆积 → 挤压该进程 → 下载的 30s 预算被吃穿。这是"下载超时"的传导路径。

### 9.5 已否决的替代方案（审计者常问，附否决理由）

| 方案 | 否决理由 |
|---|---|
| **前端加个 in-flight Map 去重** | 治标。两条链路仍共存，只是不打架；配置仍两套；`timeoutMs:0` 仍在。且要引入"谁优先"的额外裁决逻辑 |
| **把超时 30s 调到 120s** | 纯挪阈值。下载慢的根因（双倍下载 + 带宽争抢 + 进程被轮询挤压）一个没解决；还让失败暴露得更晚 |
| **`saveResultToTasks` 加并发去重** | 必要但不够。它防住重复下载，却防不住"双轮询"和"外链污染节点"，且掩盖了真正的结构问题 |
| **用网关 `?wait=1` SSE 同步**（`README.md:76` 已支持） | 长连接悬挂 5 分钟；**刷新即断且无法重新接上**——这正是 sync 模式无 `pollTaskId`、恢复全靠 `data.imageUrl` 副本的原因（CONTEXT §五 风险红线③）。把全量生成压到 SSE 会把该缺陷放大到所有节点 |
| **走网关 webhook 回调**（`README.md:78` 已支持） | 可行但复杂：需幂等入库、进程重启丢回调、回调地址与端口耦合、本地调试链路变长。而 localTool 轮询目标是本机 9004，单次查询 ~350ms，成本极低，不值得引入回调契约 |

### 9.6 风险与回滚

| 风险 | 说明 | 回滚 |
|---|---|---|
| §五.1 撤销 P0-C 改 `done()` 契约 | 影响所有 `done()` 调用方 | 每阶段独立 commit，`git revert` 单阶段 |
| `timeoutMs:0` 改成 20s | 极端慢的上游可能被提前判死 | 常量在 `config.ts`，改数不改结构 |
| 轮询主体搬迁 | `imageApi`/`videoApi` 行为对齐验证 | P0-1 为纯新增，可先落地观察再切 |

## 十、Debug 日志噪音治理（排查体验）

> **⚠️ 先钉死问题边界（用户确认，2026-09-02）**：
> - 本审计样本是**开启 debug 后**的浏览器控制台导出（行首 `index-DB9dMobB.js:4` 为打包产物定位）。
> - **不开 debug 时日志非常干净**——生产态与后端落盘的 `localtool_18080.log` **均无此问题**。
>
> 因此本节目标是 **debug 排查体验**（开 debug 时能否一眼看出问题），**不是**日志文件体积、上报成本或生产噪音。
> 治理项据此调整：不再以"减少上报/落盘"为理由，而以"让 debug 输出可读"为唯一标准。

| 类别 | 行数 | 占比 | 性质 |
|---|---|---|---|
| `http \| [请求] 发出/成功` | 148 | **70%** | 噪音 |
| `saveTask`（任务回写） | 50 | 24% | 噪音（成功不该记） |
| `恢复轮询` 三连（本轮/查询/进行中） | 24 | 11% | 噪音（状态未变也记） |
| `kvGet`/`kvSet` + 保存快照 | 42 | 20% | 半噪音（写放大，见下） |
| **`生成` start/success/落盘** | **7** | **3.3%** | **有效信号** |

> 有交叉计数（同一行命中多类），合计 >100%。

**信噪比 ≈ 1 : 29。** 有效信号被淹没，这正是"看起来好多恢复轮询、但看不出为什么"的直接原因。

**为什么生产态是干净的（机制上成立，非巧合）**：

`logger.debug` **只在模块位开启时 console 输出，且不上报后端**（`logger.ts:116-117` 明确"属排查噪音，不污染日志文件"）。所以：

- 未开 debug → `logger.debug` 整类静默，console 与 `localtool_18080.log` 只有 `info/warn/error + [frontend]` → **干净**
- 开 debug → 噪音**全部集中在浏览器控制台**，后端日志文件仍不收

**结论**：现有分层设计本身是对的，无需为了"减少上报"去改任何东西。**唯一要治的是 debug 开启时的可读性**——排查恰恰只能在 debug 开启时进行，而此时有效信号被淹没，等于排查工具在最需要它的时候失效。

### 10.2 治理项（按收益排序）

**共同前提**：以下均为 `logger.debug` 埋点，**只影响 debug 输出，不动 info/warn/error**，故对生产与后端日志零影响；改动不触碰 `contracts.ts` 登记的端点与事件，`check:api`/`check:events` 不敏感。

| # | 动作 | 位置 | 预估降噪 |
|---|---|---|---|
| 1 | **http 层合并同键请求**：同一 `(method+url)` 在采样窗口内只记首末 + 计数，形如 `[请求] ×13 累计 4.6s 末次 200` | `base/api/httpClient.ts` 的 `[请求] 发出/成功` | 148 → ~15 行 |
| 2 | **轮询日志只在状态变化时记**：`恢复轮询 进行中` 的 `progress` 与上轮相同则跳过（样本里 7 次 `progress:30` 全冗余） | `pollTask.ts`（或方案四的 `ensurePolling`） | 24 → ~3 行 |
| 3 | **`saveTask` 成功不记，只记失败**——对齐 `logger.ts:12-19` 既有铁律「只记录高价值、不可还原的」；写成功完全可还原 | `httpClient.ts` / `localToolApi.ts` | 50 → 0 行（失败时 1 行） |
| 4 | **项目快照写放大**：18:12:32~34 三秒内连续 4 次快照、每次 3 个 KV 请求。属真实性能问题不止噪音，应提高防抖窗口或按内容哈希去重 | `projectStore` / `contentStore` | 42 → ~10 行 |
| 5 | **debug 支持按任务过滤**：现按 module 分（`asset`/`agent`/`image`/`text`），加按 `taskId`/`nodeId` 过滤，排查单任务时只看它 | `config.ts DEBUG_MODULES` + `logger.ts` | 排查效率 |
| 6 | **生成链路只留 3 条 info**：`start`(含 nodeId/type) / `落盘`(含持久 url) / `success|fail`。中间 `[节点] start`、`run返回`、`[异步] 提交` 降为 debug 且合并 | `useNodeGeneration.ts` | 有效信号更聚焦 |

### 10.3 一条命令看有效信号（当前噪音下也能用）

```bash
grep -E "生成 \| (start|success|fail)|落盘|\[download\] (OK|FAIL)" <日志>
```

样本里这条只输出 5 行，却能完整判断"这次生图成功与否、落盘到哪、下载有没有失败"。

## 十一、最优解（推荐）：localTool 独占轮询

> **§四（任务中心独占轮询）是前端侧的结构收敛；本節是把轮询权继续下沉到 localTool，是终态。**
> 两者不是竞争方案：**§四 是正确的中间态，§十一 是终点**。若一次做到位，直接上 §十一，§四 的注册表可作为其前端适配层。

### 11.1 为什么 localTool 轮询是最优

核心差异不在"谁来跑循环"，而在**轮询句柄的归属与生命周期**：

| | 前端轮询（现状 / §四） | **localTool 轮询（本节）** |
|---|---|---|
| 句柄归属 | 浏览器标签页 | **localTool 进程** |
| 刷新页面 | 句柄丢失 → 需"恢复轮询"重新起循环 | **句柄存活**，前端一次 GET 即可重新 attach |
| 多标签页 | 每个标签页各起一份轮询 | **共享同一份** |
| 前端请求数（单次生图） | 21 次查询 + 2 次下载 | **1 次提交 + N 次轻量进度查询（可选）** |
| 下载位置 | 浏览器 → localTool → CDN（受 30s 前端预算） | **localTool → CDN**（后端预算，可 120s） |
| 落盘次数 | 2（并发穿透幂等） | **1** |
| "恢复"机制 | 需要（轮询循环重挂） | **退化为一次查询，不再需要"轮询恢复"** |

**最关键的一句**：localTool 轮询后，**"刷新后恢复"从"重新起一个轮询循环"退化为"发一次 GET 问结果"**——`pollTask.ts` 整个模块可以删除，"恢复轮询"这个概念不再存在。

### 11.2 设计

**新增端点**（登记进 `contracts.ts apiRegistry`，走 `npm run check:api`）：

| 端点 | 作用 |
|---|---|
| `POST /api/generate` | 提交。localTool 内部：转发网关 → 拿 `task_id` → **进程内起轮询** → 终态后 `saveRemoteUrl` 落盘 → 一次性返回 `{ code:0, data:{ url: '/files/tasks/...', status } }` |
| `GET /api/generate/:frontTaskId` | 查进度 / 取结果。**可重复调用**（attach 到同一 in-flight 句柄）。进程重启则单次回源查网关，不重建循环 |

**轮询参数放在 localTool**（`config` 或 env）：

- 间隔：生图 3s / 视频 5s
- 单次查询超时 20s、`retries: 0`
- 总超时：生图 300s / 视频 600s
- **句柄注册表**：`Map<frontTaskId, { pollTaskId, status, timer, subscribers }>`，终态后保留结果 5 分钟供迟到的前端取

**落盘在 localTool 内完成**：复用 `localTool/src/routes/files.ts` 的 `saveRemoteUrl`（已有 sha1 幂等 + `fetchWithProxy` 走代理 + `[download]` 留痕）。前端拿到的**直接是 `/files/tasks/...`，永不接触 `a.lovart.ai` 外链**。

**前端改动**：

- 删 `src/components/base/api/pollTask.ts`（整模块）
- `proxyGenerate.pollUntilDone` 删 while 循环 → 改为一次 `POST /api/generate`
- `useNodeGeneration` 删 `saveResultToTasks`；`PromptNode.onSuccess` 删 `saveResultToTasks`
- `agent:task-completed` 保留（仍由任务中心发布），但 resultUrl 来源唯一

### 11.3 三处根因的最终状态

| 根因 | §四（前端收口） | **§十一（localTool 轮询）** |
|---|---|---|
| A 双轮询 | 前端只有一个轮询者（仍 21 次查询） | **前端 0 次轮询**，后端 1 个句柄 |
| B 双落盘 | 前端只落 1 次（仍在浏览器侧，仍受 30s） | **落盘在后端 1 次，前端 0 次**；30s 预算彻底消失 |
| C 双完成出口 | 单 publish 点 | 单 publish 点 + **结果 URL 只有一种形态（`/files/`）** |

### 11.4 代价与新增风险（诚实列出）

| 代价 | 说明 | 缓解 |
|---|---|---|
| **后端改动 + 新增端点** | 需动 `localTool`，并跑 `cd localTool && npm test` | 新增路由独立文件，不动既有 `/api/proxy` |
| **localTool 成单点** | 进程崩溃 → 在跑任务句柄丢失 | 句柄落库（`tasks` 表已有 `task_id`/`thread_id`）；重启后单次回源查网关即可恢复，不重建循环 |
| **长连接占用** | 前端提交请求需保持到终态（≤5min） | 已有先例：`/api/proxy` 的 `PROXY_TIMEOUT_MS = 300000`（`system.ts:32`）与 SSE 流式分支 |
| **进度回传** | 一次 POST 拿不到中间进度 | 两条可选：① SSE 推 progress（localTool 已有 SSE 透传能力）；② 前端低频 `GET /api/generate/:id` 拉。建议先用 ②，够用且不引入流 |
| **`image_mode` 开关语义变化** | 现有 sync/async 由 `provider.image_mode` 决定（`imageApi.ts:7-9`） | 保留开关：async 走新端点；sync 走既有 `?wait=1` SSE，两条并存不冲突 |

### 11.5 建议路径

```
阶段 1（P0，~1h）  §十 日志治理 #1#2#3        —— 先让 debug 日志能看，成本极低（不影响生产）
阶段 2（P0）        §四 P0-1~P0-3 前端轮询收口   —— 不动后端，纯前端重构，立刻消除双轮询
阶段 3（P1）        §四 P1-1~P1-2 落盘/完成收口   —— 需确认 §五.1 撤销 P0-C
阶段 4（P1）        §十一 localTool 轮询端点      —— 后端改动，前端退化，删 pollTask.ts
```

阶段 2 与阶段 3 可独立上线并各自验证；阶段 4 是终态，做完即删掉阶段 2 引入的注册表。

> **若只做一件事**：阶段 4。它一次性消除 A/B/C，且阶段 1~3 的收益全部包含在内。
> **若后端暂不能动**：阶段 1 + 2 + 3，能在不改后端的前提下消除双击、双下载与外链污染。
