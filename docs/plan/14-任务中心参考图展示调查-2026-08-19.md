# 调查文档：任务中心展示「发任务时的参考图 + 发送方式」

> 日期：2026-08-19 · 状态：**仅调查，未改任何代码**
> 结论先行：需求可实现（方案 A），但落地需打通「参考图从节点层 → task 对象 → 任务中心 UI」三层，
> 且库里 `request_data.urls` 与真正发给网关的 `genBody.image_urls` 是**两套数据**，不能混为一谈。

---

## 一、用户需求（精确）

在任务中心卡片上：
1. 能看到「这次生图任务发出时附带的参考图」缩略图；
2. 能看出「这张参考图是以什么方式发出去的」（base64 内联 / URL 引用 / blob 转 base64）。
> 硬性约束（用户）：**不新增 `isBase64` 之类的标记字段**。发送方式由前端直接判断 `src.startsWith('data:')` 得出，base64 肉眼可辨，加字段是废物。

---

## 二、参考图数据流全链路（实测，逐层）

### 第 0 层：参考图从哪来（节点 UI 侧）
以 `PromptNode.jsx` 为样本（生图标准节点）：

```
refImages = [...(connected.images || []), ...(data.images?.length ? data.images : [])]   // PromptNode:59
refTexts  = [...(connected.texts  || []), ...(data.texts?.length  ? data.texts  : [])]
```
- `connected.images`：`useConnectedInputs(id)` 拉取的「连线上游节点产出」（任意上游图节点 → 本节点）。
- `data.images`：剧本盒子（StepAssets）用 `collectAssets` 按 `@资产名` 匹配后塞进本节点 data 的**资产参考图**（更精准）。
- 合并顺序：连线上游优先，再补剧本盒子资产。两者皆空 → 素材区隐藏，绝不显示假图。
- **每张参考图对象是 `{ url, sourceNodeId? , ... }`，关键是 `.url`**（PromptNode:192 `refUrls = refImages.map(img => img.url)`）。

视频节点 `DiscountVideoNode.jsx:157` 同构：`refUrls = connected.images.map(img => img.url)`，无 `data.images` 合并。

### 第 1 层：参考图怎么组装进请求（业务参数层）
`generateImage()`（`imageApi.js:61`）：
```js
const refImages = await normalizeImageUrlsForSend(images, { preferBase64: provider?.refFormat === 'base64' })
if (refImages.length > 0) genBody.image_urls = refImages   // ← 真正发给网关的字段叫 image_urls
```
- 调用处：`PromptNode.jsx:194` 的 `run` 把 `refUrls` 传给 `generateImage({ images: refUrls, ... })`。
- **关键**：发给网关的字段是 `genBody.image_urls`，**不是** `request_data.urls`。

### 第 2 层：URL 形式归一化（发送端，决定「发送方式」）
`normalizeImageUrlsForSend`（`imageUrl.js:119`）→ 逐个 `normalizeImageUrlForSend`（`imageUrl.js:102`）：

| 输入 URL 形式 | preferBase64=false（默认，走网关） | preferBase64=true（provider.refFormat='base64'） |
|---|---|---|
| `data:image/...;base64,` | 原样 | 原样（已是 base64） |
| `http(s)://` | 原样 | 拉取转 base64 |
| `/files/...`（本地磁盘） | 补全绝对 `API_BASE+/files/...` | 拉取转 base64 |
| `blob:`（浏览器临时） | 转 data: base64（网关访问不到） | 转 data: base64 |
| 裸 base64 | 原样 | 原样 |

- **`preferBase64` 由 `provider.refFormat` 决定**（`imageApi.js:71`），即发送方式本质上由「该 provider 的配置」决定，不是前端写死。
- 因此「以什么方式发出去」的真正答案是：**该任务所用 provider 的 `refFormat` 是 `'base64'` 还是默认 URL**。前端展示时只要看 `src.startsWith('data:')` 即判为 base64 内联，否则为 URL 引用（其中 `/files/` 补全的绝对 URL 属「本地文件 URL 引用」）。

### 第 3 层：请求是否经 localTool 落库（DB 侧）
- `imageProxy`（`proxyGenerate.js`）把 `genBody` 发往 `localTool:18080/api/proxy`，再由网关转发供应商。
- 任务落库在 `taskStore.reportGenerate`，`request_data` 列来自 `taskToRow` 的 `JSON_FIELDS` 白名单（`tasks.ts:26` 含 `requestData`）。
- **已实测**：库里 `request_data` 结构为 `{ model, prompt, aspectRatio, urls }`，其中 `urls` 是 **base64 数组**（单条 ~1.3–1.9MB）。
- ⚠️ **重要歧义待确认**：节点 `type` 对象是 `{ type:'image', prompt, modelName }`（`PromptNode.jsx:186`），**不含 `urls`**；但 DB 里 `request_data.urls` 有 base64。说明 `urls` 是**另一处（taskStore 落库层或 proxyGenerate 回写）**塞进 `request_data` 的，与第 1 层的 `genBody.image_urls` 不是同一个字段、同一份值。需进一步 grep `taskStore`/`proxyGenerate` 确认 `request_data.urls` 的来源，才能决定方案 A 该读哪份数据。

## 三、任务中心为什么现在看不到参考图（实测）

`TaskCenter.jsx` 渲染链路：
- 卡片读取 task 字段：`id / nodeId / status / type / modelName / channelName / prompt / createdAt / resultUrl / progress / stageLabel / errorMsg`。**无参考图字段**。
- 「请求/响应数据」展开块（`TaskCenter.jsx:346-348`）只 `JSON.stringify` 上述 7 个文本字段，**没包含 `request_data` / `urls` / `image_urls`**。
- `taskStore.reportGenerate` 返回的 task 对象（`taskStore.js:179` 段）字段也不含参考图。
- → 结论：**参考图数据在库（或节点）里存在，但从未被带进 task 对象、也未被 UI 渲染**，所以任务中心完全看不到。

## 五、方案 A 落地设计（最小改动，不动落库逻辑）

目标：任务中心能看到参考图 + 发送方式，不新增标记字段，不改 `request_data` 落库。

### 5.1 数据怎么来（二选一，各有取舍）

**A1：从节点层把参考图带进 task 对象（推荐，数据最准）**
- 在 `useNodeGeneration` 的 `type` 对象里增加 `referenceImages` 字段，由各节点 `run` 执行前把 `refUrls` 附上：
  - `PromptNode.jsx:186` `type` 改为 `{ type:'image', prompt, modelName, referenceImages: refUrls }`。
  - `DiscountVideoNode.jsx:151` 同理 `type` 增加 `referenceImages: refUrls`。
  - `taskStore.reportGenerate` 把 `referenceImages` 写进 task 对象（与现有 `prompt` 同层落库，落 `extra_fields` 或顶层字段）。
- 优点：参考图 = 用户实际发出的图，与发送方式一一对应；前端 `TaskCenter` 直接读 task.referenceImages 渲染。
- 缺点：需改 2 个节点 + taskStore，且**存量 84 条历史任务无 `referenceImages`**（前端渲染时需 `task.referenceImages?.length` 兜底，无则隐藏该区，不影响旧任务）。

**A2：任务中心直接读库里现成的 `request_data.urls`**
- `TaskCenter` 拉单条任务详情（经 `localToolApi.getTask(id)` / `/api/tasks/:id`）取 `request_data.urls`。
- 优点：零改节点、零改落库，存量 43 条立即有图。
- 缺点：① `request_data.urls` 与真正发出的 `genBody.image_urls` 是否一致**尚需确认（见二.3 歧义）**；② base64 直接塞 `<img src>` 渲染 1.9MB 图性能尚可但占内存；③ 发送方式展示仍以 `src.startsWith('data:')` 判断，与 A1 一致。

> 建议：A1 为正解（数据语义正确），A2 可作兜底兼容存量。两者可并存：渲染优先级 `task.referenceImages ?? request_data.urls`。

### 5.2 UI 渲染（`TaskCenter.jsx`）
- 在 prompt 文本下方新增「参考图」区：横向缩略图组，每个 `<img src={normalizeImageUrl(url)} />`（走 `imageUrl.js:35` 的渲染归一化，保证 `/files/` 补全、data: 原样）。
- 每张图下方标注发送方式：`url.startsWith('data:') ? 'base64 内联' : (url.startsWith('/files/') || url.startsWith(API_BASE) ? '本地文件 URL' : '远程 URL 引用')`。**无任何额外标记字段**。
- 无参考图（`task.referenceImages?.length` 且 `request_data.urls?.length` 皆空）→ 该区不渲染。

### 5.3 启动/重启
- 纯前端改动，改完 `npm run dev` 重启前端即可；DB 不动、无需迁移。
- 若走 A1 改了 `taskStore` 落库字段，属新增字段，向下兼容旧任务（旧任务该字段 undefined）。

## 六、待确认项（动手前必须厘清）

1. **`request_data.urls` 的来源**：节点 `type` 不带 `urls`，DB 却有。需 grep `proxyGenerate.js` / `taskStore.js` 确认 `urls` 是 proxy 回写还是 taskStore 另塞，才能拍板 A1/A2 数据一致性。
2. **存量任务**：84 条中仅 43 条有 `request_data.urls`，且 A1 新字段对旧任务为空 → UI 需兜底。
3. **视频节点是否要同样展示**：用户需求聚焦「发任务时的参考图」，视频节点也有 `refUrls`，建议一并带上保持一致。
4. **base64 大图渲染性能**：单条 `request_data.urls` 可达 1.9MB，若 A2 直渲多个 base64，任务中心列表可能卡。A1 同样问题（节点侧 `refUrls` 可能已是 base64）。可考虑缩略图用 `object-fit` 小尺寸 + 点击放大，降低首屏开销。

---

## 七、一句话总结
参考图确实进了库（`request_data.urls` 是 base64），但任务中心既不读也不渲染。方案 A 只需在节点层把 `refUrls` 带进 task、并在 `TaskCenter` 渲染缩略图 + 用 `startsWith('data:')` 判发送方式，即可满足需求；存量任务用 `request_data.urls` 兜底。动手前先 grep 确认 `request_data.urls` 的真实来源。
