# 66 · AI 助手 Config 收集与收口方案

> 日期：2026-08-28
> 范围：一毛AI画布「AI 助手（Agent）」的所有配置项
> 目标：把散落在前端 config.js / agent 各模块常量 / localStorage 持久化 / 后端 localTool.env 里的 AI 助手配置，集中到一个地方管理（收口），形成「改一处知全貌、单一真源」的形态。
> 本文档仅为盘点 + 方案，**不含代码改动**；落地步骤见 §5 分步计划，确认后再施工。

---

## 0. 一句话结论

AI 助手配置目前散在 **4 个层面、6+ 处**：前端编译期 env（config.js）、前端运行时常量（agentCore.js / agentRuntime.js）、前端用户持久化偏好（agentModelStore.js / runModeRegistry.js）、后端出站 env（localTool/.env）。其中有 **3 处已经收口成功**（env 读取、存储键登记、三态工作模式），但 **运行时常量、内置 system prompt、超时/温度等数值仍无统一去处**，并存在 **2 处前后端重复实现（CANVAS_AGENT_RULES 双份、temperature 双份）**。

收口方案：新建 `src/components/agent/agentConfig.js` 作为 **AI 助手前端配置单一真源**，运行时常量与内置 prompt 常量全部迁入；backend env 因进程隔离无法并入前端模块，改为「映射表 + 双份规则消除」。详见 §4。

## 2. Config 消费数据流（谁读谁、往哪儿出站）

```
┌───────────────────────── 前端（浏览器） ─────────────────────────┐
│  settingRegistry.js (布尔开关, agentOpen)                          │
│  agentModelStore.js   agent_chat_model / agent_history_turns       │
│  runModeRegistry.js   agent_work_mode → workMode systemPrompt      │
│        │                                                            │
│        ▼                                                            │
│  AgentPanel.jsx  defaultAgentModel / agentProvider                  │
│        │                                                            │
│        ▼                                                            │
│  useAgentChat.js  组装 endpoint = CHAT_BASE_URL 或                  │
│       │                  `${API_BASE}/api/agent/{agentKey}/chat`    │
│       ▼                                                            │
│  agentCore.buildRequestMessages 注入 system：                      │
│    CANVAS_AGENT_RULES + systemPrompt + SKILL_EXECUTION_RULES       │
│    + WORK_MODE systemPrompt + memory + imageCatalog + 学/记         │
│       ▼                                                            │
│  agentRuntime.roundTrip 构造 body：model / messages / tools        │
│    + temperature(0.6) / stream（非流式不传 tools）                  │
│       │                                                            │
│       ├── 有 provider → POST /api/proxy → localTool → 外部 LLM     │
│       └── 无 provider → POST /api/agent/:key/chat → agentChat.ts   │
│                                            │                        │
└────────────────────────────────────────────┴──────────────────────┘
                                             ▼
                                     ┌─ 后端 localTool（出站）─┐
                                     │ agentChat.ts getConfig() │
                                     │ 读 LLM_CHAT_* / AI_CANVAS_* │
                                     │ + 兜底注入后端 CANVAS_AGENT_RULES │
                                     └──────────┬───────────────┘
                                                ▼
                                  外部 OpenAI 兼容 LLM（DeepSeek/魔搭等）
```

三条路径要点：
1. **有 provider**（正常）→ 前端 `agentRuntime` 直连 `/api/proxy`，后端 agentChat.ts **不参与** → 前端注入的 system 是唯一生效源。
2. **无 provider** → 前端直连 `/api/agent/:key/chat` → agentChat.ts 读取后端 env 出站，并 兜底 注入后端 rules。
3. 前端 `AGENT_DEMO_MODE=true` → 走 `demoPlan` 规则引擎，完全不出站。

## 3. 问题诊断（当前分散的风险）

### 问题① 内置 system prompt 双份 · 必改
`CANVAS_AGENT_RULES` 前后端各一份且**内容已不同步**（前端是诊断增强版带意图分流表，后端是旧版）。由于默认走 proxy 路径、后端不参与，前端版才是生效源，**后端 agentChat.ts:75-102 是死代码**，但在「无 provider」兜底场景会注入旧版，两方行为不一致。→ 应删后端重复常量，明确「前端是唯一注入源」。

### 问题② temperature 双份
`0.6` 硬编码在前端 agentRuntime.js:91（`/v1/chat/completions` 分支）与后端 agentChat.ts:207（`temperature:...||0.6`）。改温度需两处同步，易漏。→ 归一为配置项。

### 问题③ 运行时常量无统一去处
`MAX_TOOL_ROUNDS` / `ENABLE_TOOLS_ON_NON_STREAM` 在 agentCore.js，`temperature` 在 agentRuntime.js，`上下文预算` 在 config.js——同属「AI 助手运行参数」，却分处 3 个文件，新增一个 AI 开关不知道该放哪。→ 统一迁入 agentConfig.js。

### 问题④ 前后端 LLM_* 同名不同用途
`LLM_CHAT_BASE_URL/API_KEY/MODEL` 前端（VITE_ 前缀，client 侧校验用）与后端（process.env，出站真源）同名，仅靠 `VITE_` 前缀区分，排障时极易改错层。→ 需要映射表 + 明确边界。

### 问题⑤ 内置 prompt 三处分离
`CANVAS_AGENT_RULES`（agentCore）、`SKILL_EXECUTION_RULES`（agentCore）、`WORK_MODE_DEFS`（runModeRegistry）都是「注入 LLM 的 system 片段」，管理分散。→ 归拢到 agentConfig 的 prompts 命名空间（但 WORK_MODE_DEFS 与三态强耦合，可保留原位、仅登记）。

### 问题⑥ 魔法数值无关键
超时/上下水/温度/轮数 缺乏单点与文档，新人排查时靠搜数字。→ 全部提为命名常量进表单。

## 4. 收口目标态设计

> 原则（对齐既有规范：config.js 是 env 单一来源、contracts.js 是存储键单一来源、settingRegistry 是布尔开关单一来源）：
> - **已有成功收口的不推翻**（1.1 env、1.3 持久化、契约登记），只做补充登记。
> - 新增一个「AI 助手配置单一真源」`agentConfig.js`，横向收起 **1.2 运行时常量 + 内置 prompt**，并 **重新导出 1.1 的 env**、**聚合导出 1.3 的偏好读取**，形成「改 AI 配置只看一个文件」的体验。

### 4.1 新建 `src/components/agent/agentConfig.js`  ✅ 位置已选定（用户确认）

> 最终收口位置：`src/components/agent/agentConfig.js`，并经 `agent/index.js` 聚合导出。
> 不采用「并入 base/config.js」（会把 env 单一来源文件变杂烩、且 base 反向依赖 agent）与「后端全量下发」（前端编译期常量不适配）。

职责：AI 助手前端配置的**唯一入口 + 真源**。结构分层：

```js
// agentConfig.js —— AI 助手配置单一真源
//（新改动：改 AI 配置只看本文件；外部一律从本文件 import，勿绕深层路径）

// ── A. 运行时常量（由 agentCore.js / agentRuntime.js 迁入）────────────────
export const MAX_TOOL_ROUNDS = 8
export const ENABLE_TOOLS_ON_NON_STREAM = false
export const AGENT_TEMPERATURE = 0.6          // 取代 agentRuntime.js:91 硬编码
export const NON_STREAM_TIMEOUT_MS = ...      //（如需，由 CHAT_TIMEOUT 派生）

// ── B. 内置 system prompt（由 agentCore.js 迁入）──────────────────────────
export const AGENT_PROMPTS = {
  CANVAS_RULES,          // 原 CANVAS_AGENT_RULES
  SKILL_EXECUTION_RULES, // 原 SKILL_EXECUTION_RULES
  // WORK_MODE 片段保持在 runModeRegistry（与三态强耦合），此处仅登记引用
}

// ── C. env 重新导出（来自 config.js，避免双源）────────────────────────────
export { LLM_CHAT_BASE_URL, LLM_CHAT_API_KEY, LLM_CHAT_MODEL,
         AGENT_DEMO_MODE, AGENT_MODELS,
         AGENT_CONTEXT_WINDOW_DEFAULT, AGENT_CONTEXT_OUTPUT_BUDGET_RATIO } from '../base/config.js'

// ── D. 用户偏好读取聚合（来自 agentModelStore / runModeRegistry）────────────
export { loadAgentChatModel, loadAgentHistoryTurns } from '../base/settings/agentModelStore.js'
export { getWorkMode, RUN_MODE_IDS } from './runtime/runModeRegistry.js'
```

### 4.2 后端边界（不并入前端模块）

后端 `localTool` 是独立 Node 进程，无法 import 前端模块。收口方式是：
1. **删后端重复 `CANVAS_AGENT_RULES`**（agentChat.ts:75-102）——改为「前端已注入，后端仅在 `AI_CANVAS_ENHANCE` 且消息无 system 时兜底一个最小占位/或引用外部文件」，消除双份失同步。
2. **temperature 归一**——后端 `agentChat.ts:207` 的 `||0.6` 改为读取 `LLM_CHAT_TEMPERATURE` env（默认 0.6），与前端 `AGENT_TEMPERATURE` 通过映射表单对齐。
3. 保留 localTool/.env.example 单点说明 + 本节「前后端映射表」，作为第二套真源的对照索引。

### 4.3 前后端 LLM 配置映射表（防改错层）

| 语义 | 前端（VITE_/前缀 config.js） | 后端（localTool/.env，出站真源） |
|---|---|---|
| 端点 | `VITE_LLM_CHAT_BASE_URL`（未配 provider 直连校验） | `LLM_CHAT_BASE_URL`（真正出站，必配） |
| 密钥 | `VITE_LLM_CHAT_API_KEY` | `LLM_CHAT_API_KEY`（必填） |
| 模型 | `VITE_LLM_CHAT_MODEL`（默认 gpt-4o-mini） | `LLM_CHAT_MODEL`（覆盖前端 defaultModel） |
| 超时 | `CHAT_TIMEOUT`（120000，前端 loading 重置） | `LLM_CHAT_TIMEOUT_MS`（120000，后端流透传） |
| 温度 | `AGENT_TEMPERATURE`（0.6，前端发 body） | `LLM_CHAT_TEMPERATURE`（0.6，后端兜底） |
| 准则 | `CANVAS_AGENT_RULES`（前端注入，唯一生效） | `AI_CANVAS_ENHANCE` / `AI_CANVAS_SYSTEM_PROMPT_FILE`（兜底/覆盖） |

## 7. 风险与不变量（改配置绝不破坏）

1. **不变量：前端是 system 注入唯一生效源**（proxy 路径后端不参与）。任何「改系统提示词」都必须落前端 agentConfig，后端仅兜底。
2. **不变量：fresh-task + 图片编号化安全底线**（历史图片不内联、refCatalog 不每轮重编撞号）不受本收口影响——收口只动常量位置，不碰 buildRequestMessages 逻辑。
3. **re-export 保测试契约**：agentCore/agentRuntime 迁常量后用 `export { X } from './agentConfig.js'` 保持既有单测 import 路径不破坏（同 agentCore 文件头既有「测试契约」做法）。
4. **不引入行为变更**：每个 P 阶段先迁常量→跑单测→build，确认零行为差异再进下一阶段。
5. **后端 .env 密不绝入 repo**：localTool/.env 已 gitignore，新增 `LLM_CHAT_TEMPERATURE` 仅写进 .env.example 模板。
6. 运行数据/状态（会话、记忆、技能、gen 参数、credit 等）非「配置」，不并入 agentConfig，仅在 contracts.js 已登记。
