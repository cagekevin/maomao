## 1. 可选深化项（按性价比排序，挑着做）

### A. 收口测试里的 `as any` 临时标记（顺手、低风险）
白天消化时为绕过类型错误，部分测试用了 `(window as any)` / `(h.X as any)` / `as unknown as X` 等收口。可针对**本批 11 个文件**逐个回看，把"纯粹因为测试 mock 形状"的 `any` 收敛成精确类型：

- `tests/unit/TaskCenter.test.tsx`、`PromptNode.imgMenu.test.tsx`、`useScriptBoxEngine.test.ts`：`vi.mock` 工厂里 `(...a: any[])` 与 `(vi.fn as any)(...a)` → 若对应 src 已导出精确签名，可改为直接透传 `(...a) => useProvidersList(...a)`。
- `tests/unit/useCanvasShortcuts.test.tsx`、`useContextMenu.test.ts`：`(window as any).getSelection` / `(global as any).IntersectionObserver` → 用 `@types/jsdom` 或本地 `declare global` 补类型，去掉 `as any`。
- `tests/unit/useFitNodeRatio.test.ts`：`as unknown as React.SyntheticEvent<...>` → 若 src 的 handler 签名已精确，可去掉 cast。

> 工具：`node scripts/ts-tests.mjs check <file>` 先看是否还报错；改完 `verify <file>` 固化。

### B. 用 `strict` 局部扫描 `any` 泄漏（中风险、治本）
当前 `tests/tsconfig.json` 可能未全开 `strict`。可选：
1. 复制一份 `tsconfig.strict.probe.json`，`"strict": true` + `"noImplicitAny": true`，只对 `tests/` 跑一次，列出真实类型隐患点（非 `@ts-nocheck` 掩盖，是 `as any` 之外的）。
2. 挑 2~3 个低风险文件把 `any` 换成具体类型，**不动 src**，仅提升测试自身强度。

> 注意：这只是探针，不要把 `strict` 直接写回正式 `tsconfig`，以免破坏门禁（除非白天 handoff 已规划 M3 开 strict）。

### C. src 业务类型纵深（原预判"M3 深化"，现已自然消解）
handoff 曾预判 `useAgentChat.hook` / `canvasAgentTools` 需 src 收口。实测：
- 这两个测试文件**已无 `@ts-nocheck`**，`tsc` 检查 0 错；
- 全工程 `tsc` 0 错，说明 src 侧该路径已干净。

→ **C 项今晚不必做**。若想进一步，可改为：在 `src/` 里全局搜 `: any` / `as any`，挑 **纯业务模块**（非第三方适配层）做类型补全，作为长期债务清理，但属完全可选。

### D. 门禁加固（一次性、高价值）
- 确认 `husky` 的 `pre-push` 已稳定跑 `test:unit` + 两份 `tsc`；若还没把 `type-check:tests` 加进 `pre-commit`，可补上，让后续误加 `@ts-nocheck` 被即时拦下。
- 跑一次 `npm run build`（或项目等价构建）确认类型门禁与产物构建一致。
