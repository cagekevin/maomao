> 涉及文件：`src/components/panels/AgentPanel.jsx`、`src/components/agent/canvas/useCanvasAgentTools.js`、`src/components/agent/runtime/useAgentChat.js`、设置持久化（`creditSwitch` 新增）

## 0. 一句话结论

把 AI 助手当前「智能/图像 × 全自动/半自动」两个正交维度（叠加一条隐藏的“有 Skill 强制半自动”规则）收敛为一个**三态选择器**，从**用户付出的精力**切分：`直接生图` / `分步确认` / `完全自主`。另在面板顶部加一个**高消耗积分确认开关（独立、默认开）**，作为**通用积分闸**：凡是真正生成图/视频（烧积分）那一下，不管在哪个模式，都要先确认。

一句话心智模型：**建节点不花积分，随便 AI 建；只有“真去生成”那一下烧积分，受积分开关约束——且这个闸对所有模式一视同仁（含直接生图、分步确认）。**

---

## 1. 背景与问题

### 1.1 现状：模式入口多且正交

| 维度 | 取值 |
|---|---|
| 能力类型 | 智能（LLM+规划+工具）/ 图像（直连生图） |
| 自动化程度 | 全自动 `auto` / 半自动 `semi` |
| 隐藏规则 | `needConfirm = hasSkillNow \|\| runMode==='semi'`（有 Skill 强制半自动） |

用户实际面对的状态超过 3 种，且两维语义彼此独立，难以一句话说清「这次交互到底会不会自动改画布」。

### 1.2 用户核心焦虑：积分被偷烧

用户最担心的是**积分消耗**（生图/生视频要付费），而非“AI 改布局”。现有「半自动/全自动」按“是否确认策划”切分，**没有**对“是否烧积分”做任何保护——完全自主模式下一旦规划落地就直出，积分说烧就烧。

### 1.3 关键事实（代码层，设计的地基）

`execute_plan` 工具（`useCanvasAgentTools.js`）的 `auto_run` 参数：
- `auto_run=false` → **只建节点，不执行生成** → **不消耗积分**
- `auto_run=true`（默认）→ 建节点 + **立即真生图/生视频** → **消耗积分**

> 结论：真正的“省钱/烧钱”分水岭不是「建节点」，也不是「规划」，而是**真执行生成那一下（发送）**。确认与保护都应收敛到这一处。

---

## 2. 目标 / 非目标

### 2.1 目标
1. 模式入口收敛为**一个三态选择器**，语义从用户精力出发、一眼可懂。
2. “完全自主”也能被积分安全网约束：**烧积分前先确认**。
3. 保持现有引擎（`send` / `sendImageMode` / `execute_plan`）尽量不动，收敛判定到一处。

### 2.2 非目标
- 不做按操作类型（effect）的复杂策略引擎（参考仓库路线，暂不引入）。
- 不做媒体生成的真·画布 ghost 生命周期回收（超出本次范围）。
- 不改「改画布/改布局」这类零成本操作的确认策略（它由三按钮决定，不归积分开关管）。

## 3. 设计方案

### 3.1 模式入口：三钮选择器

**从用户精力 / AI 自主程度切分，能力词退出顶层按钮。**

| 按钮 | 用户理解 | 底层驱动 | 建节点 | 真生图（烧积分那下）|
|---|---|---|---|---|
| **直接生图** | 一输就出，简单模式 | `inputMode='image'` → `sendImageMode`（不经 LLM 编排）| 直接建 | 受**通用积分闸**（开则确认）|
| **分步确认** | 每一步都问我 | `inputMode='agent'` + `runMode='semi'` | 看了才建 | 每步确认（叠加通用积分闸）|
| **完全自主** | AI 全包 | `inputMode='agent'` + `runMode='auto'` | 自动建 | 受**通用积分闸**（开则确认）|

> 命名说明：舍弃原「智能/图像」「半自动/全自动」——「半自动/全自动」对非技术用户不够直觉；「智能图像」是能力词，与另外两个不同维。改用「直接生图 / 分步确认 / 完全自主」。

### 3.2 顶部高消耗积分确认开关（**通用总闸**）

**独立开关，默认“开”，常驻摆面板顶部。管住所有模式的媒体生成那一下。**

> 用户原话口径：开了 = 要确认；关了 = 不用确认、直接跑（不需要找我确认，AI 也不去自动点“生成”按钮，由引擎间接触发运行）。

| 开关 | 效果（任一模式下，凡真生成图/视频前）|
|---|---|
| **开（默认，安全）** | 真生成**前弹一次确认**，用户点头才烧积分 |
| **关** | 直接跑，不弹确认（风险自担）|

作用范围：**不区分模式，所有情况一视同仁**——只要下一步是真执行 image/video 生成（烧积分那下），开关开就必须先确认。
- 「直接生图」：现在本来就是 auto_run 直出，开关开时同样拦一下再烧积分（不再“直接点生成图片”）。
- 「分步确认」：虽然每步都做策划确认，但真正烧积分那下仍叠加总闸。
- 「完全自主」：真生成那下也受总闸约束。
- 开关开时，`auto_run` 执行被悬挂为“待确认”，确认后才真正烧积分；开关关时，`auto_run` 直接放行。

> 语义解释与次序无关紧要，后续若发现理解偏差由用户一键翻正（开关就是“高消耗积分确认”：开=确认，关=不确认）。

### 3.3 三按钮 → 底层存量映射

```
直接生图  → inputMode='image'                          （sendImageMode，不经 LLM）
分步确认  → inputMode='agent' + runMode='semi'
完全自主  → inputMode='agent' + runMode='auto'
```
- `inputMode`：全局持久化（`agent_input_mode`，content）——已有。
- `runMode`：per-conversation（`conv.runMode`）——已有。

### 3.4 高消耗积分开关持久化

- `creditSwitch`：全局设置项，默认 `true`（安全）。
- 落点：设置层（与 AI 助手配置同区），面板顶部开关与其联动。

### 3.5 AI 系统提示词补充（防“干等”）

当积分总闸把生成挂起、等用户确认时，LLM 可能误以为「任务没生成完/生成失败」，反复等待或重复触发。需在系统准则里补一条，明确「**节点/工作表建好那一下，本任务即视为完成**」。

- **改**：系统准则 `CANVAS_AGENT_RULES`（`src/components/agent/runtime/agentCore.js`，已含 L89「generate_node 提交成功即算完成」）**追加**积分确认门禁语义：
  > 当本任务包含图像/视频生成，且系统要求先确认（高消耗积分确认开启）导致生成暂挂起时：**你把节点/工作表建好、生成已提交并等待确认，本轮任务即视为完成**。不要再等待、不要反复调用 `execute_plan` / `generate_node`、不要在没有结果时声称“已生成”；应如实说明「节点已建好，生成待确认，确认后自动生成」。
- **不动**：已有「生成即完成」规则保持，与新条款统一“提交即完成”心智。

## 4. 完整链路（数据流）

### 4.1 核心判定（收敛到工具层一处，替换旧 `hasSkillNow`）

```
needConfirm = (runMode==='semi')                        // 分步确认：每一步（策划/画布/媒体）都问
           || (本次含媒体生成 && creditSwitch)          // 通用积分闸：任一模式，真生成图/视频前都确认
```

- 删除旧的 `hasSkillNow` 强制项 →「完全自主」连 Skill 策划也不再强制确认，但仍受**通用积分闸**约束（有媒体就确认）。
- `needConfirm` 决定「真执行媒体生成前」是否悬挂确认。直接生图走 `runMode==='semi'` 之外的分支，但第二项仍命中（含媒体生成 && 开关开）。

### 4.2 三条主流程

**A. 直接生图（direct）**
```
输出提示词+参考图 → handleSend 命中 inputMode==='image' → sendImageMode()
→ 构造 generation → execute_plan 入口
→ 若 creditSwitch=开：建节点（免费）→ 弹「将生成 N 张图/视频，消耗积分，确认开始？」
                    → 用户确认 → auto_run 才真正烧积分
→ 若 creditSwitch=关：直接 auto_run 建节点+执行烧积分，不弹
```

**B. 分步确认（semi）—— 继承现状 + 叠加积分闸**
```
send() → roundTrip → LLM → show_plan_for_confirm（needConfirm=true → awaitingConfirm=true，展示策划）
→ 用户点确认 → handleConfirmPlan → 翻转 awaitingConfirm=false → 重发
→ execute_plan：getAwaitingConfirm() 校验放行 → 建节点；媒体生成那下若开关开，仍先确认再烧积分
```

**C. 完全自主（auto）—— 关键变化，受通用积分闸**
```
send() → roundTrip → LLM → show_plan_for_confirm（规划照常展示，needConfirm 按 4.1 判定）
→ execute_plan：
     若本次会生成媒体 且 creditSwitch=开：
        AI 先建好节点 / 规划（免费，不弹）
        → 弹「将生成 N 张图/视频，消耗积分，确认开始？」
        → 用户确认 → 才 auto_run 真正烧积分
     若 creditSwitch=关：直接建节点 + 执行烧积分，不弹
```

### 4.3 积分门禁落点（**通用闸**）

- **建节点 / 改布局**：`auto_run=false` 阶段，本身不烧积分 → **不拦**。
- **真执行媒体生成**：`auto_run=true` 那一下 → 只要 `creditSwitch` 开，无论哪个模式都插一次确认（含消费预估）再放行。
- 三模式（直接生图 / 分步确认 / 完全自主）在「烧积分那下」受同一把闸约束，一视同仁。

## 5. 已定的边界决策

1. **待生成节点不删、不做回收**：建节点免费，`execute_plan` 建了就是建了（与现有画布上“生图节点”一致）。用户可自行选择是否生成，也可**自己改提示词后再生成**，节点天然支持。**不设计取消/丢弃逻辑**（用户裁定：建就建，无影响）。
2. **积分门禁粒度：整批一次确认**，多步合成「共 N 张图/视频」确认一次（最省事），不做逐步。
3. **删掉 Skill 强制确认**（`hasSkillNow`）；「完全自主」连 Skill 策划也不强制确认，但 Skill 触发媒体生成仍受**通用积分闸**约束。
4. **直接生图不再直接 auto_run 直出**：开关开时，也会在烧积分前拦一下确认（用户明确要求“不让它直接点生成图片”）。
5. 积分开关是**独立控件**，**通用**作用于所有模式，不与三按钮正交打架。

> 本节把现状**从代码里核对**的契约、数据流，以及实现本 PRD 时会踩到的**真问题**写清楚。施工前由实施与评审过一遍，再拍板 P 项的解法。

### 10.1 现状契约（代码核对）

| 位置 | 现状行为 |
|---|---|
| `show_plan_for_confirm`（useCanvasAgentTools.js:805）| `needConfirm = hasSkillNow \|\| runMode==='semi'`；`setAwaitingConfirm(needConfirm)`；返回 `awaiting_confirm` |
| `execute_plan`（useCanvasAgentTools.js:866）| 入口 `if (getAwaitingConfirm()) 拒绝`（:890）；`autoRun = args.auto_run!==false`（:913）；把 `autoRun` 传入执行器（:997）|
| `executePlan`（canvasPlanExecutor.js:214）| `autoRun=false` → 建全部节点（Wave1 独立批 + Wave2 依赖批），每步 `status='ready'`，**不触发生成、不耗积分**；`autoRun=true` → 建节点 + 逐个 `runNode`（真正烧积分）|
| 执行器幂等性 | **无**：`executePlan` 每次 `appendNode`（执行器 :298），同一份 generations 重跑会**重复建节点** |
| `send` 工具循环（useAgentChat.js:490-559）| 循环停止点**只有** `if(getAwaitingConfirm()) break`（:555）；当前无任何“积分待确认”停点 |
| `sendImageMode`（useAgentChat.js:621-664）| 纯直连：`callTool('execute_plan',{generations, auto_run:true, ...})`（:664），**不经 agent 工具循环、不设 awaitingConfirm**；成功即回“已在画布生图” |
| `executePlanDirect`（useAgentChat.js:790-795）| **prompts 逐条确认后**的第二个直连入口：`callTool('execute_plan',{generations, auto_run:true})`（:792），不经 LLM、不设 awaitingConfirm。→ 代码里共有 **2 个**「不经过 agent 循环的 auto_run:true 直跑点」（sendImageMode 与 executePlanDirect）都需要被 credit 门禁覆盖 |

### 10.2 发现的问题（P 项，施工前必须拍板）

**P1 · 两条门禁时序不同，不能共用一个状态。**
- 分步确认的门禁在 **show_plan**（`awaitingConfirm`）；完全自主+开关的门禁在 **execute_plan 真生成时**（新 `creditPending`）。两者是不同状态、不同 UI。
- 因此 PRD 3/4 里 `needConfirm = semi || (含媒体 && creditSwitch)` **应拆为两条独立路径**，它不是同一个 needConfirm：
  - 分步确认 → `awaitingConfirm`（show_plan 设，保持现状）
  - 完全自主 + 开关开 → `creditPending`（executePlanTool 设）
- 分步确认下**不再叠加** `creditPending`（plan 确认已覆盖媒体），避免让用户确认两次。

**P2 · 现有 execute_plan 门禁是“整单入口一票否决”，满足不了“建节点放行、只拦烧积分”。**
- :890 的 `getAwaitingConfirm()` 拦的是**整个 execute_plan**（分步/技能用）。
- 完全自主+开关要的是：建节点免费放行、只在真正烧积分那下拦。**不能复用 awaitingConfirm**。
- 必须在 `executePlanTool` 内加 credit 判定：命中（非分步确认 && 开关开）→ **强制 `autoRun=false`**（建节点不跑），每个 entry `status='ready'`，并置 `creditPending`。**绝不能让 LLM 的 `auto_run:true` 直接跑**。

**P3 · 确认后“补跑”绝不能重呼 execute_plan（会重复建节点）。**
- 执行器每次 `appendNode`。用同一 generations 再 execute_plan = 建重复节点。
- → credit 确认后的“真正生成”必须对**已建的 ready 节点**做**生成触发**（trigger_generation 语义），而不是重跑 execute_plan。**这是本次最大的实现风险点**，见 P4。

**P4 · 目前没有任何“对已建 ready 节点按 DAG 批量触发生成”的复用入口。**
- `triggerGenerationTool` 是**单节点**触发；执行器只在 `executePlan` 内部 `runNode`。
- 两条候选路线对比 → **已拍板路线①**（评审确认）：
  - **路线①（选中）**：给 `executePlan` 加 `runExisting` 模式——跳过建节点，仅对已建节点按 DAG（依赖边已在 Wave2 连线里）触发生成。**调度逻辑只有一份**，正常跑与补跑行为天然一致（单飞锁/超时/日志/entries 一并复用）。
  - 路线②（否）：逐个 `trigger_generation` + 自管 DAG。不动执行器但需**复制一份 Wave1/Wave2 前序等待调度**（prevOk/resolved/realIdToIdx 那套），两套调度易漂移、多步依赖合成易漏连线。违背“统一机制优于打补丁”。
- 路线①前置条件（详见 10.4）：creditPending 时**必然在 `execute_plan` 同一次调用里拿到执行器返回的 `entries`（含每步 `nodeId`）**，把 `steps↔nodeId` 映射随 per-conversation 状态持久化，补跑据此对号，不重定位。
- 该决定同时敲定 P6：sendImageMode / executePlanDirect 两个直跑点的补跑，与 agent 循环共用同一个 `runExisting` 补跑入口。

**P5 · send 工具循环只有 `awaitingConfirm` 一个停点。**
- auto+credit 命中 `creditPending` 后，若不新增停点，LLM 会进下一轮：或再调 execute_plan（→P3 重复节点）、或自言自语。
- → `send` 循环（:555）需改为 `getAwaitingConfirm() || getCreditPending()` 才 break；配合系统提示词（3.5）让 LLM 别在“待确认”态继续触发。

**P6 · 直连生图有 2 个不经 agent 循环的 auto_run:true 直跑点，都要拦。**
- `sendImageMode`（:664）与 `executePlanDirect`（:792，prompts 逐条确认通道）都是纯直连，无 awaitingConfirm，也**不经 `send` 工具循环**。
- credit 门禁要管住它们：命中断言 → `executePlanTool` 内强制 `autoRun=false` + 置 `creditPending`（**两个直跑点都走同一个 executePlanTool 判定**，不各写一遍）。
- `sendImageMode`/`executePlanDirect` 的成功判定需兼容“返回 ready/待确认”而非“已生成”。
- 直接生图的 creditPending → 确认 UI → 补跑触发，需与 agent 循环**共用同一套机制**（见 P4 路线定夺）。

**P7 · 开关范围：只作用于“非分步确认”路径。**
- 分步确认已由 `awaitingConfirm` 天然“先确认”，**不设** `creditPending`，否则确认两次。
- `creditPending` 仅在 `runMode!=='semi' && creditSwitch` 时触发（覆盖完全自主 + 直接生图）。

**P8 · creditPending 需 per-conversation 持久化、刷新可恢复。**
- 现状刷新恢复逻辑盯着 `awaitingConfirm`/`pending`。`creditPending` 要同样入 per-conv 状态，刷新后保持“待确认”，避免丢单。

**P9 · “含媒体”判定在 execute_plan 内恒成立（可能要改成“无条件”）。**
- `executePlan` 只建 `promptNode`（generations 即图/视频步骤）；非媒体画布改动走其它工具。→ execute_plan 路径下“含媒体”基本恒真，credit 判定实际可简化为 `runMode!=='semi' && creditSwitch`。
- ⚠️ 视频：当前 `executePlan` 未见建视频节点的落点，只在对话里提“image/video”。需核实视频生成是否另有工具/节点类型，再定“媒体”识别口径（施工前置项）。

### 10.4 P4 定稿：补跑路线①`runExisting` 的数据流、文件归属、契约（拍板即施工依据）

> 本节把「文件怎么放、数据怎么流、契约怎么定」想清楚，评审据此放行后进入 State1 施工。

#### 10.4.1 数据流（credit 门禁 → 待确认 → 补跑）

```
发起（三路汇聚到 execute_plan 唯一入口）：
  A) agent 循环 execute_plan      B) sendImageMode(:664)   C) executePlanDirect(:792)
  └─▶ executePlanTool(execute_plan.execute, useCanvasAgentTools.js:886)
       │  判定：runMode!=='semi' && creditSwitch
       │  · 命中 → 强制 autoRun=false（不烧积分），执行 executePlan 只建节点
       │          每个 entry status='ready'；返回 { ok:true, awaited:'credit' }
       │  · 未命中 → 原逻辑 autoRun 放行（烧积分）
       存 per-conv：creditPending=true + creditGenerationState={gens, map: (stepId→nodeId)}（entries 回传）
       └─▶ send 工具循环（:555）在 getCreditPending() 处 break（防 LLM 再触发）
           · sendImageMode/executePlanDirect 兼容返回「准备就绪/待确认」
用户点击「确认生成」→ 唯一补跑入口 runExistingPlanTool()
       └─▶ executePlan({ generations: st.map.suis, autoRun:true, mode:'runExisting', nodeMappings: st.map })
           · 跳过 appendNode；依赖边已在 Wave2 期建好（画布上），只触发 runNode
           · 既有单飞锁/超时/entries 聚合复用 → 真正烧积分
       ├─▶ 清 per-conv creditPending + creditGenerationState
       └─▶ workflow：running → completed/failed（对齐现链路）
```

- 关键不变式：**`steps↔nodeId` 映射只在 `execute_plan` 同一次调用里取（entries 回传），补跑不再重定位节点**——这是路线①能成立的前提，也是防重复建节点的根。
- `creditPending` 挂起期间 AI 不再碰 execute_plan（§P5 + 系统提示词 §3.5），只有用户确认这一条路触发补跑。

#### 10.4.2 文件归属（不新增文件，全部并入既有）

| 职责 | 落点（既有文件） | 说明 |
|---|---|---|
| credit 判定 + 强制 autoRun（**唯一入口**） | `useCanvasAgentTools.js` → `execute_plan` 的 `execute()`（:886） | 三路（agent 循环 / sendImageMode / executePlanDirect）统收敛到此处，不各写判定 |
| 补跑唯一入口 | `useCanvasAgentTools.js` 新增 `runExistingPlanTool` | 仅供（a)AgentPanel 确认按钮 与 (b)sendImageMode/executePlanDirect 确认回调 共用；内部调执行器 `runExisting` 模式 |
| `runExisting` 模式（建节点/触发解耦） | `canvasPlanExecutor.js` → `executePlan` 加 `mode:'normal'\|'runExisting'` | 不开新文件；runExisting 跳过 appendNode，仅按 DAG 触发 |
| `creditPending` + `creditGenerationState`（per-conv） | `conversationSkillState.js`（照 awaitingConfirm/pendingGenerations 同模式） | 新增读写 + `conversationState.js` 归一化补默认 |
| `creditSwitch`（全局） | 设置层（与 `agent_input_mode` 主常量同注册源） | 面板顶部开关 <→> 设置联动 |
| 系统提示词 | `agentCore.js` → `CANVAS_AGENT_RULES` 追加 §3.5 | 防“干等” |

**不新建任何文件**：状态、执行器、工具、设置四处职责均有现成归置目录，并入即可，避免职责散落（State1「文件该不该存在」判定）。

#### 10.4.3 契约点名（State1 施工必查，防二份/裸量）

- **契约常量先查登记**：`creditSwitch` 存储键、conversation 新增字段（`creditPending`/`creditGenerationState`）、credit 确认事件名，一律进 `contracts.js` 登记后引用，**禁裸字面量**。
- **唯一入口建结构**：补跑一律走 `runExistingPlanTool` → `executePlan(mode:'runExisting')`，禁止在 AgentPanel 或 sendImageMode 里手写 `setNodes`/逐节点触发拼装（防绕唯一入口、漏单飞锁/漏持久化）。
- **幂等/去重**：执行器已有全局单飞锁（canvasPlanExecutor `executingPlan`）。补跑入口再加「前置校验」：`creditGenerationState` 缺失或 `creditPending!==true` → 直接拒绝（防重复计费/防无据触发）。确认按钮连点只生效一次。
- **统一解析**：补跑复用执行器返回的 `entries` 作 `steps↔nodeId` 映射的唯一来源，不另写解析。
- **跨模块引用**：`creditPending`/映射读写走 `conversationSkillState` 既有导出，不循环 import。
- **异步总超时**：触发沿用 `runNodeGeneration` 带超时 + 全局单飞锁超时兜底（EXECUTING_PLAN_TIMEOUT）；补跑不引入新的无限轮询。
- **失败可见**：补跑返回 `entries` 的逐步 `status` 与错误原样透传；`creditPending` 置位与清除必须成对（成功清、失败保留待重试），不得静默吞。

#### 10.4.4 施工拆分（顺序，避免回归）

1. **契约登记**：contracts.js 增 creditSwitch 存储键 + conversation 新字段 + 事件（P-登记）。
2. **执行器** `runExisting` 模式：先无 credit 逻辑，仅抽「建节点与触发解耦」，供手动改动后验证不回归。
3. **运行态** `creditPending` + `creditGenerationState` per-conv（P8）落库与归一。
4. **入口收敛** `executePlanTool` credit 判定 + 强制 autoRun=false + 存映射。
5. **补跑入口 + 工具循环停点**（P5） + sendImageMode/executePlanDirect 兼容。
6. **UI**：credit 确认弹窗接补跑入口；顶部开关联动设置。
7. **提示词** 3.5 追加。
