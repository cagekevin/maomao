## 2. 调查实证（已核实，可直接验）

### E1 · `agentRuntime` 的 `else` 不是历史残留，是「零配置回退」产品决策

- `AgentPanel.tsx:78-86`：`agentProvider` 计算链末段为
  `return providers?.find((p) => p.id === 'modelscope') || primary || null`
  → **为空的唯一条件 = `providers` 列表为空**（用户未配任何 provider 或尚未加载完成）。
- `AgentPanel.tsx:187`：`useAgentChat({ provider: agentProvider })`；`useAgentChat.ts:314` 形参默认 `provider = null`。
- `agentRuntime.ts:105`：`const useProxy = !!provider` —— else 分支即"未配 provider"路径。

### E3 · responses 形态**从未真正生效**（活 bug，非冗余）

```335:335:localTool/src/generateEngine.ts
    const url = `${(baseUrl || '').replace(/\/+$/, '')}/chat/completions`;
```

`relayChatStream` **硬编码 `/chat/completions`**，从不支持 responses。而前端：

- `agentRuntime.ts:88-103`：`llmBody = isResponsesChat ? buildResponsesChatBody(...) : {...}`
- `agentRuntime.ts:134-145`：`relayBody` 用的是 **`requestMessages`**（原始 messages），**不是 `llmBody`**
- `agentRuntime.ts:159`：`useProxy` 分支发的是 `JSON.stringify(relayBody)` → **`llmBody` 算出来即丢弃**
- `agentRuntime.ts:184`：`else` 分支才发 `JSON.stringify(llmBody)`，而终点 `/api/agent`（`agentChat.ts:187` 硬编码 `stream: true`）透传给 OpenAI 兼容端点，该端点**不认 responses 的 `input` 数组**
- `agentRuntime.ts:340/353`：`isResponsesChat` 却仍决定用 `parseResponsesSSEChunk` 还是 `parseSSEChunk`

→ **两条链路下 responses 都不成立**：useProxy 分支发了 messages 却用 responses 解析器解 SSE；else 分支发了 responses body 给只认 messages 的端点。provider 配成 responses 模式的用户会拿到空回复。

**【判断】** 前端 responses 相关代码应整体删除；responses 支持若需要，应由后端 ai-relay 引擎负责（后端已有 `localTool/src/routes/requestModes.ts` 镜像层）。

**输入源**（4 类，诉求不同）

| 来源 | 调用 | 诉求 |

**输出目标**
- `{ok:true, url}`（image / video）
- `{ok:true, content}`（chat 同步）
- chunk 流（chat 流式）

**副作用边界**（门面层只负责前两条）

| 副作用 | 归属 |
|---|---|
| 出站 HTTP | 门面（`httpClient` 唯一出口） |
| `onProgress(percent, message)` | 门面透传 |

| 结果落盘 | ❌ relay 后归后端 `saveRemoteUrl`；前端 `saveResultToTasks` 归 `useNodeGeneration.ts:245`（幂等兜底，不动） |
| 前端轮询 | ❌ 已收口在 `relayProxy.relayAttachUntilDone` |

**边缘情况（已裁定）**

1. **chat 同步 vs 流式** → 一个通道 + `stream` option（后端 `generate.ts:46` 已按 `stream || hasTools` 分流，前端只需透传标志）。
2. **SSE 解析归谁** → **留在 `agentRuntime`**。打字机 + tool_calls delta 累积是 UI 层职责；门面只负责出站 + 吐原始 chunk。
3. **timeout** → 由 capability 查表（`GEN_TIMEOUT` / `VIDEO_TIMEOUT` / `CHAT_TIMEOUT`），调用方不传。
4. **abort 语义** → image/video **抛** `AbortError`；chat 同步保留 `aborted:true` 信封（16 处调用点依赖，不统一）。

**用户已裁定**：不需要零配置回退（→ 删 `else`）；其余按架构师建议（→ 上述 4 条按此执行）。

### 5.4 异步总超时（铁律）

`agentRuntime` 现用 `timeoutMs: 0`（`agentRuntime.ts:161`）禁 15s 掐点——**但 0 = 无总超时，违反"异步必须带总超时"铁律**（流式挂起会永久等待）。

**本批补**：`chatStream` 由调用方 `agentRuntime` 传入 `AbortController`，配 `CHAT_TIMEOUT + 60_000` 宽限总闸（对齐 `SCRIPT_TEXT_TIMEOUT` 思路，`config.ts:137`）。超时即 abort 并清理悬挂 reader。
