## 一、结论（先说答案）

**性能模式不是「缩放到多少」的分级，而是一个开关：开 = 关掉持续消耗 + 隐藏连线；关 = 完全不降级。**

三句话：

1. **判据换轴**：从 `zoom ≤ 0.5/0.3/0.2` 换成一个问题 —— **「这个行为在用户什么都不做时，还在不持续烧？」**（该判据只筛"持续消耗"，**不筛"交互态动画"** —— 见 §4.2）
2. **`LOD 2/3` 删掉**：它们降的是「静止零成本」的对象（静态 `img`／输入控件），却额外付出 8 个节点重渲（负收益）。
3. **降级下发下沉到 CSS**：降级规则活在 `index.css` 里 ⇒ **新组件只要渲染在 `.react-flow` 内就自动被降级**，结构上不可能漏。今天的 `useAssetDegrade`（8 个节点 JS 分支）是"每加一个节点就要记得加一次"的必漏结构。
   - ⚠️ 该不变式的**前提**：组件用 class 表达动画。对内联 `style={{animation:…}}` 的组件（`GeneratingOverlay`）必须先加 class，否则 CSS 盖不住（见 §6.2）。

**状态机（2026-09-30 收敛为 1 个 class）**：

| class | 触发（真相源） | 降级范围 |
|---|---|---|
| `perf-on` | 性能模式开关开（`appSettings.performanceMode`） | **全部降级**：粒子、辉光、无限动画、**连线本体**、视频解码 |

- **无阈值、无第二档、无缩放判据**（原 `view-far` 作废，见 §4.3）。

## 二、现状判据：为什么 LOD 2/3 没有意义

### 2.1 它们降的是「静止零成本」的对象

`src/index.css:673-706` 的降级清单：`video` / `img` / `iframe` / `textarea` / `input` / `button`。

| 对象 | 静止时成本 | 结论 |
|---|---|---|
| 静态 `<img>` | 解码一次即纹理，**不重绘就不烧** | 降它≈0 收益 |
| `input`/`textarea`/`button` | `visibility:hidden` 不减 DOM 不减布局 | 只省"少画一次" |
| 节点 `opacity: 0.8`（`:703-706`） | **opacity < 1 反而创建合成层** | 可能负收益 |

### 2.2 它们放过了真正「每帧持续烧」的东西

| 持续消耗项 | 实证位置 | 在 lod 降级清单里？ |
|---|---|---|
| 17×`animateMotion repeatCount="indefinite"`（每条激活边 = 16 拖尾 + 1 头部） | `edges/CometParticles.tsx:52,68` | ❌ |
| `filter: blur(3px)` 辉光 | `index.css:625` | ❌ |
| `npbSpin`/`npbGlow`/`npbShimmer` 生成中动画（**内联 style，无容器 class**） | keyframes `index.css:302-326`；消费方 `parts/GeneratingOverlay.tsx` | ❌ |

> 原表列过「`animation: … 1.6s linear infinite` 跑马灯（`index.css:604`）」—— **2026-09-30 取证后已移出**：
> 它的选择器是 `index.css:580` 的 `.react-flow__node:has(.react-flow__handle.connectingto)::before`，
> **只在用户拖拽连线时存在**，不满足 §4.2 的"静止时仍烧"判据。

### 2.3 lod-2 是「降级引发重渲」

- `useAssetDegrade` 消费端 **8 个节点**（`ImageGenerate.tsx:124` · `ImageBoxNode.tsx:84` · `GridSplitNode.tsx:215` · `AssetNode.tsx:102` · `VideoProcessNode.tsx:316` · `VideoGenerate.tsx:96` · `VideoExtractNode.tsx:85` · `TemplateNode.tsx:165`），做的是**条件渲染**（卸载 `<img>` DOM）。
  > 更正（2026-09-30）：原文写"10 个"。`GridMergeNode.tsx:136` 与 `FaceMosaicNode.tsx:80-82` 早已删掉该调用，代码注释写明"旧的 … 已删：本节点未消费（死调用）"。
- 跨 0.3 阈值 → `lodLevel` 变 → 8 个节点 + 全部 `useLod` 消费者**同时重渲**（`docs/plan/106` §P1 已警告）。
- 而 4 档 = 缩到 0.2 要跨 **3 次**阈值 = 3 次全量重渲抖动。
- ⇒ **为省「静止零成本」的绘制，付出一次全量重渲。动机与结果相反。**

### 2.4 附带实证：`zoomed-out-lod` 是死 class

`lod.tsx:64/75/80` 写入，`index.css` **零规则消费**，全仓无其他消费者（`scripts/1mao-scripts/` 下的官方原型快照除外）。
🔍 `node --version` 无关，用内置搜索：`zoomed-out-lod` → 仅 `lod.tsx` 与 `scripts/1mao-scripts/`。
⇒ 随 §8.2 与 `lod.tsx` 整体退役一并删除。

> **展示类**（生成结果）可降；**工作区与交互反馈**（处理节点预览、拖拽线）**不可降**（降了用户就没法干活）。

> **选中态例外（2026-09-30 二次修，用户报障）**：隐藏连线**只隐藏未选中的** ——
> ① `cust-edge-hit`（22px 透明命中层）**永不隐藏**：隐藏后边**彻底点不中**（删边 / 选边都做不了）= 能力受损；

> 代价：看不见的线仍可点中（命中层保留）—— 可接受；反过来"看不见也点不中"才是真丢能力。

> **接线前提（2026-09-30 施工中定）**：`settingRegistry.performanceMode` 的默认值由 `true` 改 **`false`**。

## 四、Step 1 · 定真相与边界

### 4.1 SSOT（🔴 红线）

- **降级态的唯一真相 = `.react-flow` 上的 `perf-on`**，由 `App.tsx` 的 `className` **声明式产出**。
- **JS 侧零降级态消费者**：不许 `useState` / `useContext` / `useStore` 持有一份"当前是否降级"的副本再往下转发。
  - 依据：`setState` → 消费者重渲 → **降级动作本身成为成本**。这正是现状 4 档跨阈值抖动的成因（`docs/plan/106` §P1）。
  - 唯一例外：**视频解码需要 `pause()`**（`display:none` 是否停解码待实测，§十）。该例外形态为"直读 `appSettings.performanceMode`"（低频、开关驱动），**不是**从 DOM / 缩放派生 —— 见 §6.3。
- **验收**：`grep -rn "useLod\|LodContext" src` → **0 命中**（`lod.tsx` 退役后）。
- **🔍 怎么发现**：`grep -rn "classList\.\(add\|remove\)" src | grep -i "react-flow\|perf-"` → **0 命中**（无命令式写入者）。
  > ⚠️ 不许用裸 `grep "classList.add\|remove" src` 当判据 —— 现状就有 4 个**无关**文件命中（`promptChips.ts:173` · `useTabDragSort.ts` · `useColumnResize.ts` · 以及本次要退役的 `lod.tsx`），照原文那样写会假红。

### 4.2 「该不该降级」的唯一判据（🔴 红线）

> **判据：这个行为在用户什么都不做时，还在不持续烧？**
> ⚠️ 本表有**两类纳入依据**，不许混：① **持续消耗**（上句判据）；② **用户明示需求**（特例，全表仅「连线本体」一项）。

| 对象 | 持续消耗？ | 处置 |
|---|---|---|
| `animateMotion` 粒子 | ✅ 每帧 | **降** |
| `filter: blur()` 辉光 | ✅ 每帧栅格化 | **降** |
| `infinite` CSS 动画 —— **生成中**（`npbSpin`/`npbGlow`/`npbShimmer`） | ✅ 每帧 | **降**（只暂停**视觉**，进度与错误必须仍可见） |
| `<video>` 解码播放 | ✅ 每帧解码 | **降**（归 `perf-on`） |
| **连线本体**（`.cust-edge-base` / `.cust-edge-hit`） | ❌ 静止零成本 | **降** —— 依据是**用户明示需求**（2026-09-30 裁定），**不是**"它在烧" |
| 静态 `<img>` | ❌ 一次性 | **不降** |
| `input`/`textarea`/`button` | ❌ 静止零成本 | **不降** |
| **交互态动画**：拖拽连线跑马灯（`index.css:580` `.react-flow__node:has(.connectingto)::before`）· 黄条 `animate-pulse`（`App.tsx:1744`） | ✅ 每帧，但**只在用户正在操作/闸提醒时存在** | **不降** —— 不满足"用户什么都不做时还在烧"（判据本意） |

- **🔍 怎么发现**：新增任何降级规则前，先搜被降对象的 CSS/JS，确认它含 `animation` / `filter` / `animateMotion` / 解码。**答不出"它持续烧在哪" ⇒ 不许加这条降级**（唯一的例外是"用户明示需求"，须在落账写明是谁的裁定）。

### 4.3 状态机（**1 个 class**，与规模、缩放都无关）

| class | 触发（真相源） | 降级范围 |
|---|---|---|
| `perf-on` | 性能模式开关开（用户偏好，`appSettings.performanceMode`） | **全部降级**：粒子流、辉光、无限动画、**连线本体**、视频解码 |

- **开关关 ⇒ 一个 class 都不加 ⇒ 完全不降级**（红线 6）。
- **无阈值、无第二档**（原 `view-far` 的 `zoom ≤ 阈值` 整档删除）。

> **为什么"隐藏连线本体"归 `perf-on`（2026-09-30 用户裁定，推翻本文 2026-09-20 的"归 `view-far`"）**：
> 原设计的理由是"边是结构信息，正常缩放下隐藏 = 信息丢失；鸟瞰时边密集成团才'降得无所失'"。
> 该理由不成立：① 用户要的就是"开关一开就清爽"，把它拆给缩放 = 等于没给；② "鸟瞰档"在同类产品中无先例，且要额外实测拍阈值（原 §十 第 1 项）= 引入不确定性。
