## 一、结论（先说答案）

**性能模式不是「缩放到多少」的分级，而是「谁在持续消耗」的开关。**

三句话：

1. **判据换轴**：从 `zoom ≤ 0.5/0.3/0.2` 换成一个问题 —— **「这个行为在用户什么都不做时，还在不持续烧？」**
2. **`LOD 2/3 删掉**：它们降的是「静止零成本」的对象（静态 `img`／输入控件），却额外付出 10 个节点重渲（负收益）。
3. **降级下发下沉到 CSS**：降级规则活在 `index.css` 里 ⇒ **新组件只要渲染在 `.react-flow` 内就自动被降级**，结构上不可能漏。今天的 `useAssetDegrade`（10 个节点 JS 分支）是"每加一个节点就要记得加一次"的必漏结构。

## 二、现状判据：为什么 LOD 2/3 没有意义

### 2.1 它们降的是「静止零成本」的对象

`src/index.css:674-707` 的降级清单：`video` / `img` / `iframe` / `textarea` / `input` / `button`。

| 对象 | 静止时成本 | 结论 |
|---|---|---|
| 静态 `<img>` | 解码一次即纹理，**不重绘就不烧** | 降它≈0 收益 |
| `input`/`textarea`/`button` | `visibility:hidden` 不减 DOM 不减布局 | 只省"少画一次" |
| 节点 `opacity: 0.8`（`:704-707`） | **opacity < 1 反而创建合成层** | 可能负收益 |

### 2.2 它们放过了真正「每帧持续烧」的东西

| 持续消耗项 | 实证位置 | 在 lod 降级清单里？ |
|---|---|---|
| 16×`animateMotion indefinite`（每条激活边） | `edges/CometParticles.tsx:52` | ❌ |
| `filter: blur(3px)` 辉光 | `index.css:626` | ❌ |
| `animation: … 1.6s linear infinite` 跑马灯 | `index.css:604` | ❌ |
| `npbSpin`/`npbGlow`/`npbShimmer` 生成中动画 | `index.css:303-326` | ❌ |

### 2.3 lod-2 是「降级引发重渲」

- `useAssetDegrade` 消费端 **10 个节点**（`ImageGenerate.tsx:114` · `ImageBoxNode.tsx:84` · `AssetNode.tsx:102` · `TemplateNode.tsx:164` · `GridSplitNode.tsx:215` …），做的是**条件渲染**（卸载 `<img>` DOM）。
- 跨 0.3 阈值 → `lodLevel` 变 → 10 个节点 + 全部 `useLod` 消费者**同时重渲**（`docs/plan/106` §P1 已警告）。
- 而 4 档 = 缩到 0.2 要跨 **3 次**阈值 = 3 次全量重渲抖动。
- ⇒ **为省「静止零成本」的绘制，付出一次全量重渲。动机与结果相反。**

### 2.4 附带实证：`zoomed-out-lod` 是死 class

`lod.tsx:64/75/80` 写入，`index.css` **零规则消费**，全仓无其他消费者（`scripts/1mao-scripts/` 下的官方原型快照除外）。
🔍 `node --version` 无关，用内置搜索：`zoomed-out-lod` → 仅 `lod.tsx` 与 `scripts/1mao-scripts/`。

## 四、Step 1 · 定真相与边界

### 4.1 SSOT（🔴 红线）

- **降级态的唯一物理真相 = `.react-flow` 上的 class**。
- **JS 不持有降级态副本**：不许 `const [isMoving, setMoving] = useState()` 再转发。
  - 依据：`setState` → 消费者重渲 → **降级动作本身成为成本**。这正是现状 4 档跨阈值抖动的成因（`docs/plan/106` §P1）。
- **验收**：`grep -n "useState" src/components/canvas/shell/lod.tsx` → 不得出现与降级态相关的 state（`lastRef` 型防重复 ref 除外）。
- **🔍 怎么发现**：`grep -rn "classList.add\|classList.remove" src` → **命中必须只有 1 个文件**（`lod.tsx`）；≥2 处 = 出现第二个写入者。

### 4.2 「该不该降级」的唯一判据（🔴 红线）

> **判据：这个行为在用户什么都不做时，还在不持续烧？**

| 对象 | 持续消耗？ | 处置 |
|---|---|---|
| `animateMotion` 粒子 | ✅ 每帧 | **降** |
| `filter: blur()` 辉光 | ✅ 每帧栅格化 | **降** |
| `infinite` CSS 动画（跑马灯／生成中） | ✅ 每帧 | **降**（生成中只暂停**视觉**，进度必须仍可见） |
| `<video>` 解码播放 | ✅ 每帧解码 | **降**（归视图意图层，见 4.3） |
| 静态 `<img>` | ❌ 一次性 | **不降** |
| `input`/`textarea`/`button` | ❌ 静止零成本 | **不降** |
| 静态边 path（未激活） | ❌ 静止零成本 | **不降**（只在视图意图层降，见 4.3） |

- **🔍 怎么发现**：新增任何降级规则前，先搜被降对象的 CSS/JS，确认它含 `animation` / `filter` / `animateMotion` / 解码。**答不出"它持续烧在哪" ⇒ 不许加这条降级。**

### 4.3 状态机（**2 个 class + 1 个阈值**，与规模无关）

| class | 触发（真相源） | 归谁 | 降级范围 |
|---|---|---|---|
| `perf-on` | 性能模式开关开（用户偏好，`appSettings.performanceMode`） | 用户意图 | **所有「每帧持续消耗」**：粒子、辉光、无限动画 |
| `view-far` | `zoom ≤ 阈值`（视图意图） | 视图 | **解码类 + 结构性内容**：停下视频解码、隐藏边、简化节点静态内容 |

**两者正交**：性能模式关 ⇒ 只可能被 `view-far` 影响；性能模式开 ⇒ 两层叠加。

> **为什么"隐藏边"归 `view-far` 而不归 `perf-on`**：边是**结构信息**。用户在正常缩放下隐藏边会"看不见连线"，属信息丢失；而 zoom 极小（鸟瞰）时边密集成团、无信息量 —— 此时降级才是"降得无所失"。
> ⇒ **用户原始需求「性能模式开就隐藏连线」需要拆开**：连线上的**特效**归 `perf-on`（符合预期），连线**本身**归 `view-far`（有依据）。（见 §十 待拍板）

### 4.4 YAGNI 红线（防复刻 TD-04-22）

- **不许预留字段/档位**：不得新增 `edgeFxLimit` / `perfLevel: 0|1|2|3` / `viewportMoving` 之类"以后可能要用"的声明。
- 依据：`TD-04-22`（2026-09-13 用户裁定"没用的就删"）—— 正是这一类假字段被删；`lod.tsx:19` 留话「要做请**新写实现并同时接上消费端**」。
- **验收**：每个新增字段/class，**必须同时有消费端**（CSS 规则或 JS 读取），并在落账写清"谁消费"。
- **🔍 怎么发现**：`grep -rn "<新 class 名>" src/index.css` → **0 命中即幽灵预留**（`zoomed-out-lod` 就是这么躺了很久）。

### 4.5 接线穷尽（谁必须调它）

新原语 `applyPerfClass()` 的**调用点必须穷尽**（缺一个 = 假接线）：

| 触发源 | 落点 | 现状 |
|---|---|---|
| 性能模式开关变化 | `App.tsx`（`<LodProvider enablePerformanceMode>` 已是唯一注入口） | ✅ 已有 |
| zoom 变化 → `view-far` | `lod.tsx` 内 `useStore(s => s.transform[2])` | ✅ 已有（改造阈值逻辑） |
| （若 §十 实测要求）交互中 | `ReactFlow` 的 `onMoveStart` | ❌ **当前没有** |

- **验收**：`grep -rn "applyPerfClass" src` → 命中数 = 上表实际需要的调用点数，且**含生产调用**（只有测试命中 = 没接）。
- **🔍 怎么发现**：`grep -rn "onMoveStart" src` → 现状 0 命中（`onMoveEnd` 只用于落盘，`App.tsx:525`）。

## 五、Step 2 · 契约

1. **class 名即契约**，写成字面量联合类型（L1，编译期逼迫）：

```ts
/** 降级态 → .react-flow 的 class。**只这两个**，不许加档位。 */
type PerfClass = 'perf-on' | 'view-far';
```

2. **失败契约**：本模块无 I/O、无失败分支 —— 若施工中发现需要 `try/catch`，**说明设计放错了层**（回 §4.2）。
3. **禁默认值兜底**：`container?.classList` 的 `?.` 是"容器可能不存在"的 ACL 边界，**保持现状**；不许为它加 `if (!container) return` 之外的任何"兜底 class"。
4. **🔍 怎么发现**：`grep -nE "catch|throw" src/components/canvas/shell/lod.tsx` → 施工后仍应为 **0**。

## 六、Step 3 · 组装与投影

### 6.1 唯一写入口

```
applyPerfClass({ perfOn: boolean, viewFar: boolean })   // lod.tsx 内，非导出或窄导出
  → 计算目标 class 集合 → 与当前 diff → classList.add/remove
```

### 6.2 CSS 承接全部降级（消费端零 JS）

| 降级项 | 目标选择器 | 状态 |
|---|---|---|
| 粒子流光 | `.cust-edge-comet` | ✅ 类名已实证（`CustomEdge.tsx:68`） |

| 拖拽连线 | `.cust-conn-*`（ConnectionLine 用同套类） | ✅ 已实证（`ConnectionLine.tsx:31-34`） |
| 跑马灯 | **待取证**（`index.css:604` 的 `cust-marquee-rotate` 消费方） | ⚠️ 见 §十 |
| 生成中动画 | **待取证**（`npbSpin/npbGlow/npbShimmer` 容器类名） | ⚠️ 见 §十 |

**CSS 形态要求**：
- 用 `display: none`，**不用 `visibility: hidden`** —— 后者不停 SMIL `animateMotion`（需 §十 实测确认）。
- 🔍 怎么发现：`grep -nE "visibility: hidden" src/index.css` → 本次改造后，与 lod 相关的 `visibility:hidden` 规则应全部消失。

### 6.3 必须 JS 的例外（只有一类）

- **视频解码**：`display:none` 一般**不止停解码**（待实测），需 `pause()` ⇒ 归"必须 JS"。
- 形态：`useViewFar()`（**窄 hook，只吐一个 boolean**），仅视频类节点消费（现有 `useVideoPoster` 的节点）。
- **消费者必须收窄**：从 11 个 → 仅视频类（目标 ≤3），否则 §4.1 的"重渲即成本"回归。
- 🔍 怎么发现：`grep -rn "useLod\|useViewFar" src` → 命中数即消费者数；**超过视频类节点数即违规**。

### 6.4 生命周期 / 并发

- `useStore` 订阅由 React Flow 托管，无需手工退订；`rAF` 必须在 cleanup 里 `cancelAnimationFrame`（现状 `lod.tsx:73` 已有，保持）。
- 🔍 怎么发现：`grep -n "useEffect" src/components/canvas/shell/lod.tsx` → 每个 effect 必须有 cleanup 分支。

| 1 | **`view-far` 阈值取多少** | 0.5 激进（边常被隐藏，可能困惑）／0.3 保守（接近删档前的收益） | 在 0.5 / 0.4 / 0.3 各停一次，看"边是否还提供信息" |
| 2 | `display:none` 是否真停 SMIL `animateMotion` | spec 上"不渲染"，但动画时间轴是否仍在推进无定论 | DevTools 隐藏前后对比 CPU |
| 3 | `display:none` 的 `<video>` 是否继续解码 | 若会继续，则 §6.3 的 JS `pause()` 必需 | 隐藏前后看解码器占用 |
| 4 | **pan/zoom 是否为合成层平移** | 若**是**，则**不需要**"交互中"这一档（设计更简）；若**否**，需补 `perf-moving`（§4.5 预留了 `onMoveStart`） | Performance 录制 pan，看有无 Layout/Paint |
| 5 | 跑马灯 / 生成中动画的**消费类名** | 现仅有 `@keyframes` 定义，容器类名未取证 | `grep -rn "cust-marquee\|npbSpin" src` |
| 6 | **「性能模式开即隐藏连线」是否也要** | 属用户可见行为变化，且与 §4.3 的归位相反 | 见下 |

**关于第 6 项（用户原始需求）**：本设计把「连线本身」归 `view-far`（缩放驱动），「连线上特效」归 `perf-on`（开关驱动）。
若你确实要**开关一开就隐藏连线**（不看缩放），说一声 —— 那是 `perf-on` 下追加一条 CSS 规则的事，但它会让"性能模式"从"降开销"变成"降信息"。

## 十一、弯路留痕（强制）

**弯路 1（本轮，需修正）**：我曾推断「pan 时 React Flow 每帧重算全部边的 `d`」→ 据此设计"交互中隐藏边"。
- **错在哪**：pan/zoom 走 `.react-flow__viewport` 的 `transform`，**节点相对坐标不变 ⇒ 边 `d` 不重算**；只有**拖节点**才重算。真正的每帧成本在**重绘/栅格化**（尤其带 `blur` 的元素）。
- **已回退**：设计改为"关持续消耗"而非"隐藏边"，并把"是否需要交互中档"降级为 §十 第 4 项待实测。
- **教训**：`pan 时重算 path` 是典型的"看起来很对"的推断 —— 属于"凡能查的一律不许靠推理"。

**弯路 2（上一轮）**：我曾提出"按关联边数 N 降级"（规模判据）→ **被用户裁定否决**（"不需要考虑画面上有几个节点"）。
- **错在哪**：规模是变量，拿它当判据会让行为随画布大小漂移，且需要实测定 N（引入不确定性）。
- **已回退**：全部规模判据已从设计移除。
