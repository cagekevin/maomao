# 26-API中转层连接优化-PRD-2026-08-21

> 范围限定：仅聚焦「前端 API 聚合层 ↔ localTool 后端 API 聚合层」这一对 API 中转站之间的连接优化。
> 不含画布、节点、生图等业务逻辑扩散。只谈「各个中转站」的契约与配合。

---

## 1. 项目定位

猫猫AI画布的「**API 中转层**」优化。前端一组聚合薄壳把请求收敛后打到 `localTool` 网关（18080），网关按路由表分发。

- **给谁用**：前端开发者、localTool 维护者、最终用户（所有画布异步请求经此链）。
- **核心价值**：让前后端 API 契约边界「更完美、更和谐」——契约对称、错误语义一致、新增端点零摩擦、可观测、无重复样板与歧义路径。

---

## 2. 模块拆分（互不重叠，仅 API 中转范畴）

1. **前端 API 出口底座**（`httpClient.js` + `config.js`）
   —— 所有 fetch 的唯一出入口；超时/取消/错误分类/重试；`API_BASE` 地址单一真相源。
2. **前端业务聚合薄壳**（`localToolApi.js` / `filesApi.js` / `chatApi.js` / `imageApi.js` / `videoApi.js` + 深模块 `proxyGenerate.js` / `genErrors.js`）
   —— 各业务域 URL 契约 + 样板收口，是前端侧「API 中转站集群」。注：`taskStore.js`/`assetStore.js` 经 `localToolApi.js` 间接调端点，本身非登记簿（详见 §2.1 模块 2 注）。
3. **后端路由表与分发**（`localTool/src/router.ts` + `index.ts` 主分发）
   —— 声明式路由表（顺序即优先级）、具名路由优先、catch-all 透传兜底。
4. **后端路由处理器集群**（`localTool/src/routes/*.ts`：files/kv/tasks/projects/resources/providers/admin/agentChat/official/passthrough/system/platform/logs 等）
   —— 每个 API 终点，是后端侧「API 中转站集群」。
5. **契约对齐与可观测**（横跨前后端）
   —— 命名/信封/错误码/日志一致性约定与链路观测点。

**依赖与重叠检查**
- M1 是被 M2 依赖的底层底座（M2 全部经 M1 发请求），无重叠。
- M2 与 M4 是一对一/一对多的「契约镜像」：每个前端聚合函数对应一个后端路由处理器，是本次优化的核心耦合面。
- M3 是 M4 的索引与顺序仲裁者（具名路由优先于 catch-all），M3 与 M4 强绑定、不重叠。
- M5 横切 M1–M4，本身不持有传输逻辑，仅定义规范，不与任何模块功能重叠。

## 2.1 模块细化（第 2 层五步法结论）

> 每模块含「现状扫描」+「细化约束」。现状来自实际代码读取，约束对应第 1 层 C1–C4。

### 模块 1 · 前端 API 出口底座（`httpClient.js` + `config.js`）
**现状**
- `httpRequest` 已统一超时(15s)/取消/错误分类(`NetworkError`/`HttpError`/`TimeoutError`/`AbortError`)/受限重试(仅网络/超时重试，业务错不重试)。
- `httpPost`/`httpRequestLogged` 为助手；错误解析第 95 行优先级 `error|detail|message`。
- `config.js` 已是地址单一真源（`API_BASE`/`LOCAL_TOOL_PORT`），多档超时已备。
- **缺口**：`proxyGenerate.js`(4处)/`agentRuntime.js`(1处) 裸 `fetch` 绕过出口；`promptHubStore`/`logger`/`cloudSync` 也有裸 fetch（多为跨域第三方/旁路，可白名单）。
**细化约束**
- **M1-a 唯一出口**：指向 localTool 的请求全走 `httpClient`；裸 fetch 仅限白名单：①跨域第三方源（promptHub 外部源）；②异步 fire-and-forget 旁路（logger/cloudSync）；③**AI 助手 `useProxy=false` 时直连官方 LLM**（`agentRuntime.js:139` 的 `endpoint` 来自 `LLM_CHAT_BASE_URL`，docs/11 全量接管前的历史合法路径，非 localTool）。其余（含 `proxyGenerate`/`agentRuntime` 走 `/api/proxy` 分支）必须回炉 `httpClient`。
- **M1-b 错误抽取单一函数**：抽 `extractErrorDetail(data)` 纯函数，统一 `typeof data.error==='string' ? {code:'UNKNOWN',message:data.error} : (data.error||{code:'UNKNOWN',message:data.detail||data.message})`。**关键**：`HttpError.message` 只承载业务 message，不再拼 `HTTP 500:` 前缀（现状第96-97行会拼 `HTTP ${status}: ${detail}`，导致 status 与 message 双重携带）；状态码由 `HttpError.status` 单独暴露给调用方（→ C2）。
- **M1-c 超时档位**：一律取自 `config.js`，禁止调用处硬写数字。
- **M1-d 取消语义**：统一经 `signal` 入参，绕行点回炉后自动对齐。

### 模块 2 · 前端业务聚合薄壳（`localToolApi.js`/`filesApi.js`/`chatApi`/`imageApi`/`videoApi` + `proxyGenerate.js`/`genErrors.js`）
> 注：`taskStore.js` **不是**端点登记簿——它只调 `localToolApi.js` 的函数，端点登记责任在 `localToolApi.js`；`assetStore.js` 的 `18080` 是返回 URL 字符串拼接（非配置裸写），归 URL 契约形态问题。本模块成员修正为上述列表。

**现状**
- `localToolApi.js` 已高度收口（tasks/projects/resources/providers/kv/files，注释「新增端点只加 1 函数」）；`filesApi.js` 落盘深模块走 `/api/files/upload`+`UPLOAD_TIMEOUT`。
- `chatApi`/`imageApi`/`videoApi` 只做「业务参数→body」，真实请求委托 `proxyGenerate.js`（SSE 豁免红线已固化，不走 httpClient）。
- **错误分类已部分收口**：`genErrors.js` 的 `classifyError`（依赖 `contracts.js` 的 `GEN_ERRORS` 类型登记 `abort|timeout|network|http|business`）统一「错误→类型」决策（CONTEXT §三铁律）；但**错误 message 字段提取未收口**——`proxyGenerate` 内散写点**实为四处**（非三处）：①`__proxyFetch`（第68行 `error.message|message|detail`，裸 fetch 抛错分支）；②`chatProxy.parseNestedError`（第249行 `error.message||message||detail`，**永不抛错分支，HTTP 非 2xx 视为业务错误**）；③`imageProxy`/`videoProxy` 经 `__proxyFetch` 复用①；④`classifyError` 只取 `e.message` 不解析嵌套 `error` 对象。注意 `chatProxy` 因「信封永不抛错」语义**显式不走 `__proxyFetch`**（第208行注释：避免给业务错误误加网络前缀），故 `extractErrorDetail` 收口时须同时覆盖「抛错分支(`__proxyFetch`)」与「不抛错分支(`chatProxy` 返回 `{ok,error}`)」两种消费形态，`classifyError` 当前完全未覆盖 SSE 域（chatProxy/imageProxy/videoProxy）的错误分类。
- **缺口**：①20+ 端点无结构化登记表（人肉对齐后端→白实现风险）；②`proxyGenerate` 的 message 提取优先级与 httpClient（第95行 `error|detail|message`）分歧；③返回形态混用 `{ok:true}`/`{deleted:n}`/`{items}`/`{ok,url,error}`；④`label` 词根 `fetchTasks` 与后端 `tasks` 不统一；⑤**组件层直拼 `httpRequest(API_BASE+...)` 绕过薄壳**：`GeneratedView.jsx:232`(`/api/files/mkdir`)、`AssetLibrary.jsx:209/283`(`/api/files/upload`/`mkdir`)、`pollTask.js:66`(`/api/v1/gateway/task/{id}`) 直接拼 URL，不在 `localToolApi`/`filesApi` 收口内；注意 `pollTask` 的 `gateway/task` 是 localTool 跨进程代理到 apimart(18090) 的统一查询端点（system.ts handleGatewayTask），虽已走 `httpRequest` 符合 M1 唯一出口，但仍散写 `data.error?.message||data.error`（pollTask.js:84）应收口到 `extractErrorDetail`（M2-b）；⑥`genErrors.js`/`contracts.js` 已存在却被初稿漏提（重造轮子风险）。
**细化约束**
- **M2-a 中央端点登记表（在 BACKEND_ROUTES 基础上新建结构化表，非简单升级）**：`src/components/base/contracts.js` 的 `BACKEND_ROUTES`（contracts.js:426-431）当前**仅是字符串占位常量**——`ACTIVE`/`RESERVED` 的值是描述性文本（如 `'localTool routes/* 中 frontend 实际使用集合'`），**无可程序化提取的 route pattern**；`API_ENDPOINTS`（:394-399）**仅含 `fileThumbnail` 一个字段**，远非「20+ 端点登记表」。故 M2-a 实为**新建结构化表**（保留 P0-4 的「ACTIVE/RESERVED 死路由分类」思路作为字段，但数据须从零填充），而非「升级既有数据结构」。结构化表形态：`{ fn, route, method, envelope, root, status }`（status: active/standby/official-standby），覆盖 `localToolApi`/`filesApi`/`proxyGenerate`/`pollTask`/`GeneratedView`/`AssetLibrary` 全部调用点；借鉴 docs/08 方法（→ C1）。**注意**：前端 `BACKEND_ROUTES` 无可提取结构，M5-c 的静态校验**仅后端 `router.ts` 的 `routes` 表可正则提取**，前端侧须手写填充并与后端互检（→ M5-c）。
- **M2-b 错误 message 提取收口（区分抛错/不抛错两分支）**：抽 `httpClient.extractErrorDetail(data)` 纯函数，`proxyGenerate` 的 message 提取统一复用——**抛错分支**（`__proxyFetch` 的 `error.message|message|detail`）与**不抛错分支**（`chatProxy` 的 `parseNestedError` 返回的 `{ok,error}` 信封，`error` 为字符串）都收口到同一纯函数；`chatProxy` 的 `{ok:false,error:"msg"}` 信封**是 SSE 域的刻意设计（CONTEXT 铁律：chat 业务错误不抛、不归网络错）**，收口时保留「`chatProxy` 返回 `{ok,error}` 而非 throw」语义，仅把 `parseNestedError` 内部提取逻辑替换为 `extractErrorDetail` 的 message 部分（→ M1-b/C2/M5-e）。**类型归类继续用 `classifyError`（genErrors.js）不重复造**，但须扩展 `classifyError` 覆盖 SSE 域错误（chatProxy 返回 `{ok:false}` 时应归类为 `business` 而非漏归）（→ M5-b）。
- **M2-c 信封收敛**：成功统一 `{code:0,data}` 或至少 `ok`+`data`；失败统一 `error.code`（→ C2）。**前端 storage 层例外**：`kvStore.storageSet` 在 KV 失败降级 localStorage 时返 `{ok:true,degraded:true}`（kvStore.js:53），这是**前端专有成功标记**，后端 `/api/kv/set` 仅返 `{ok:true}`（kv.ts:40）；信封收敛仅约束「前端↔后端传输层」，前端内部 storage 抽象可保留 `degraded` 等前端态标记，不与后端信封混淆（→ C2）。
- **M2-d 新增零摩擦**：「加函数 + 登记 1 行」双动作，防漏登记。
- **M2-e label 对齐**：`label` 词根对齐后端 route 日志前缀（→ C4）。

### 模块 3 · 后端路由表与分发（`router.ts` + `index.ts`）
**现状**
- `router.ts` 已是声明式路由表 `routes: Route[]`（精确/正则/catchAll 三类），`matchRoute` 顺序匹配，catch-all 恒命中且须表末。
- `index.ts` 阶段 2 具名→阶段 3 前端托管→阶段 4 catch-all→阶段 5 404；`SILENT_LOG_PATHS` 静默高频轮询；日志 `[METHOD] pathname`。
- **缺口**：前端登记↔后端 route 仅靠人肉；日志三套词根未统一（`[GET] /api/tasks` / `[taskToRow:dropped]` / `[passthrough]` / `[official]`）；顺序铁律靠注释红线；catch-all 的 `isLocalOnlyPath` 判定无契约文档；`official.ts` 权益转发层（带缓存降级、KV 自指过滤）属「前端未接管」态，其 route 与前端权益调用无映射（前端直连官方），登记表互检时会「后端有前端无」而 info 待补，须 M5-c 标注 `passthrough/official-standby`。
**细化约束**
- **M3-a 双向映射单一真源**：`routes` 表为权威清单；与前端 `apiRegistry` 程序化互检，缺失告警（→ C1）。
- **M3-b 日志词根对齐**：后端 `[METHOD] pathname` 词根与前端 `label` 统一词根表（→ C4）。
- **M3-c 顺序不变式**：`matchRoute` 校验 catch-all 必表末，否则启动抛错（替代注释红线）。
- **M3-d 本地优先可见**：导出「本地接管/透传」路径清单，前端 `apiRegistry` 标注每个端点 `local|passthrough`。

### 模块 4 · 后端路由处理器集群（`routes/*.ts`）
**现状**
- CRUD handler 统一 `json`/`sendError`；成功混用 `{ok:true}`/`{deleted:n}`/`{items}`；`sendError` 仅 `{error:message}`（无 code）。
- `passthrough.ts` 原样回传官方（status/headers/body 不改写，仅自身错用 `sendError` 504/502）；与 `official.ts` 共享 `readOfficialBase`。
- **`official.ts` 权益转发层是「带缓存降级的透传」，比 passthrough 更复杂（M3/M4 初稿零覆盖）**：`forwardGet` 对官方 5xx→返 stale 缓存（official.ts:197-207）、网络错/超时→502/504（:251-255）、**成功/官方 4xx/401/403 原样透传不包 502**（:229-234 注释「错误透传官方原始状态码与 body，不包成 502」）、进程内 Map 缓存按 token hash 隔离（:50）、KV `active_api_endpoint` 自指过滤防回环（:85-110）。`handleOfficialInvalidate` 返 `{ok:true,removed}`（:313）。属 M4-c「原样不改写」的增强版（加缓存降级），但**前端三处权益接口 base 默认直连官方、不经本层**（official.ts:316-339 注释），本层是「就绪未接管」态。
- **缺口**：错误信封无 `code`；成功形态比初稿更碎——除 `{ok:true}`/`{deleted:n}`/`{items}` 外，还有 `platform.ts` 的 **`{success:true,data}`**（自研替换官方平台接口用 `success` 而非 `ok`/`code`，第三种成功形态，初稿漏列）、`files.ts` 的 `{url,path,thumbnailUrl}`/`{files,folders}`/`{path}`（upload/list/open 三形态，**且 `read`/`thumbnail` 直返二进制流不包 JSON**）、`admin.ts` 的 `{kv,tasks,resources,disk}`/`{keys:rows}`/`{ok:true,deleted,count}`/`{ok:true,counts}`/`{scanned,deleted,referenced,deletedFiles}`（**`handleAdminCleanup` 无 `ok` 外包裹**）、`official.ts` 的 `{ok:true,removed}`、`resources.ts` 的 `{ok:true,count,scanned,added,skipped,orphanDeleted}`/`{ok:true,id,url,name}`；**`tasks.ts`/`resources.ts` 分页包裹**：`handleTasksGet`/`handleResourcesGet` 均返 `{items,total,page,pageSize}`（非裸 `{items}`，初稿漏列）；`detail` vs `message` 字段名分歧；透传层原生形状 vs 具名层改写形状不收敛；**二进制流端点（files read/thumbnail）彻底不走 JSON 信封**（见 M4-f）。**本轮补 3 个已登记域的实际形态（初稿零覆盖）**：①`projects.ts` 的 `handleProjectsGet` 返 **`{projects:[{id,name,createdAt,isLastOpened}], lastOpened}`**（含 `null` key 回退链，`projects.ts:23-35`），`handleProjectsSave` 返 `{ok:true}`（:81）；②`kv.ts` 的 `handleKvGet` 返 **`null`（key 不存在）或解析后的值**（:17-20，**非 `{ok}` 包裹、也非 `{data}`**），`handleKvSet`/`handleKvDelete` 返 `{ok:true}`（:40/50），且 `handleKvSet` 内含 base64 外置降级（失败字段回退保留原 base64，不破坏 `{ok:true}` 契约，kv.ts:33）；③`logs.ts` 的 `handleLogsPost` 返 `{ok:true}`（:50，前端上报失败静默忽略，不影响主链路）。三域均在 `router.ts` 登记（:119/122-124/145-146）、前端经 `localToolApi`/`projectStore`/`kvStore` 收口消费，属「已登记已覆盖但 PRD 漏列」，须纳入 M4-b 完整形态清单。
**细化约束**
- **M4-a 错误信封升级（渐进兼容）**：`sendError(res, code, message, status)` → `{error:{code,message}}` 全 handler 统一；前端 `extractErrorDetail` 单一读取，**且须兼容旧形态**——后端 `sendError` 现状全是 `{error:"msg"}`（字符串），升级时旧客户端/未升级 handler 仍可能返字符串，`extractErrorDetail` 需 `typeof error==='string' ? {code:'UNKNOWN',message:error} : error` 兜底（→ C2/C3）。
- **M4-b 成功信封收敛（破坏性变更，需前端同步）**：现状成功形态比初稿更碎——`files.ts` 的 `{url,path,thumbnailUrl}`/`{files,folders}`/`{path}`、`admin.ts` 的 `{kv,tasks,resources,disk}`/`{keys:rows}`/`{ok:true,deleted,count}`/`{ok:true,counts}`/`{scanned,deleted,referenced,deletedFiles}`（无 `ok` 外包裹）、`official.ts` 的 `{ok:true,removed}`（invalidate 变体）、`resources.ts` 的 `{ok:true,count,scanned,added,skipped,orphanDeleted}`/`{ok:true,id,url,name}`、**`tasks.ts`/`resources.ts` 的分页包裹 `{items,total,page,pageSize}`（handleTasksGet/handleResourcesGet）+ tasks 同文件 `{ok:true}`/`{deleted:n}`/`{deleted:changes}` 三形态并存**、**`projects.ts` 的 `{projects:[{id,name,createdAt,isLastOpened}], lastOpened}`（handleProjectsGet，含 `null`/`'default'` 回退）/ `{ok:true}`（handleProjectsSave）**、**`kv.ts` 的 `null` 或解析值（handleKvGet，key 不存在返裸 `null` 非 `{ok}`/非 `{data}`）/ `{ok:true}`（handleKvSet/handleKvDelete，set 内含 base64 外置降级不破坏契约）**、**`logs.ts` 的 `{ok:true}`（handleLogsPost，前端上报失败静默忽略）**。统一为 `{code:0,data}` 是** breaking change**：所有按 `res.ok`/`res.deleted`/`res.items`/`res.total`/`res.page`/`res.url`/`res.path` 直接读字段的前端代码（`localToolApi`/`filesApi`/`taskStore`/`kvStore`/各 store）须同步改为 `res.data.xxx`。建议**分批迁移**：先加 `code` 字段保持旧字段兼容，下个版本再去旧字段（→ C2）。**隐藏依赖**：`tasks.ts` 的 `rowToTask` 特意为前端 `httpClient.diffAndPersistTasks` 的 `e.id` 去重键回填 `id===taskId`（tasks.ts:36-41 注释），收敛信封时**不得移除该 `id` 回填**，否则前端任务中心 reload 后去重键 miss、历史记录重复累加（见 daily/11 报告）；`{items,total,page,pageSize}` 收敛为 `{code:0,data:{items,...}}` 时须保留 `total/page/pageSize` 在 data 内。**豁免域**：二进制流端点（`files.ts` 的 `handleRead`/`handleThumbnail` 直返文件流，files.ts:166-208/246-300）与 SSE 流式域（M5-e）**不适用 JSON 信封收敛**，见 M4-f。
- **M4-c 透传适配（有意识，非随意改写）**：`passthrough.ts` 维持原样回传；但 `system.ts` 的 `/api/proxy` 链路已实现**有意识的协议翻译**——对「包裹型上游」（Lovart 等返回 `{code,data}`）主动**剥壳为 `data`** 直返前端（system.ts:561-583 注释「协议翻译：剥 `{code,data}` 信封，前端直接拿到 data」），对原生型上游（如官方 chat 返回纯 JSON/choices）保持原样。属**收敛信封的半步已落地**，但前端 `proxyGenerate` 解析时**无法预知后端是否已剥壳**（同一上游可能被剥/未被剥），须与 M2-b 的 `extractErrorDetail` 协同：错误侧仍按 `error.code||error.message||error` 兜底，成功侧须兼容「裸 data / `{code,data}` / `{ok}` / `{success,data}`」四种可能。严禁把上游 `{error:{...}}` 改写成 `{error:"..."}`（→ C3）。
- **M4-c3 official 权益转发层（缓存降级透传，M4-c 增强版）**：`official.ts` 的 `forwardGet` 在「原样透传」之上加**进程内缓存降级**——官方 5xx→返 stale 缓存（official.ts:197-207）、网络错/超时→502/504、官方 4xx/401/403 **原样透传不包 502**（:229-234）、KV `active_api_endpoint` 自指过滤防回环（:85-110）。与 M4-c 同属「不重写官方语义」，但**多一层缓存降级契约**，前端若未来改道 18080 接管权益，须理解「响应可能来自 stale 缓存 + `x-cache: hit-stale` 头」而非实时官方；当前前端权益接口 base 默认直连官方（official.ts:316-339），本层为「就绪未接管」，M5-c 登记表须标 `official-standby` 避免误判白实现（→ C3）。
- **M4-c2 成功形态全集（补 platform.ts）**：统一 `{code:0,data}` 时须纳入 `platform.ts` 的 `{success:true,data}` 作为第四种待收敛形态（与 M4-b 的 ok/deleted/items/path 并列），前端 `platform` 调用点（`fetchBuiltin`/`Xi` 等）同步改 `res.data.xxx`（见 §5.4 缺口⑥扩展）。**本轮修正**：`platform.ts` 实际有**两套**成功形态——①`handleBuiltin`/`handleModels`/`handleWorkflowAppsByProject` 用 `{success:true,data}`（platform.ts:37/84/92，自研替换官方 1mao 平台接口）；②`handlePluginManifest` 用 **`{version,hasUpdate}`（无 success 包裹，非 `{success,data}` 形态）**（platform.ts:20-23，本地模式返回当前版本）。M4-b 收敛 `{code:0,data}` 时两套都须覆盖，`{version,hasUpdate}` 是 platform 域第五种待收敛形态，前端 `fetchPluginManifest` 调用点同步改 `res.data.xxx`。
- **M4-e SSE/流式域信封例外（结构性，非缺陷）**：`agentChat.ts` 的 SSE 透传把错误包成 **`data: {"error":"..."}` 字符串行**（agentChat.ts:131/261），非 SSE 分支把上游 JSON 原样塞 `data:` 行（:256）；`providers.ts` 的 `handleProviderTest` 用**平铺** `{ok:false,error:"..."}`（providers.ts:634）而非嵌套 `{error:{code,message}}`，成功用 `{ok,status,protocol,...}`（:603/620）或 `{providers:[]}`（:450）。这些**是 SSE/探测域的既有契约，与 M4-a 的 `{error:{code,message}}` 冲突但不可简单统一**：SSE 行协议只能承载字符串/扁平 JSON，无法塞 `code` 嵌套对象。收敛策略见 M5-e（流式域信封边界），M4-a 的 `sendError` 升级**仅限非 SSE 的具名 CRUD handler**，不强行改造 SSE 透传层。
- **M4-f 二进制流端点豁免 JSON 信封（结构性，非缺陷）**：`files.ts` 的 `handleRead`（files.ts:166-208）与 `handleThumbnail`（:246-300）直接 `res.writeHead(200,...)` + `fs.createReadStream(...).pipe(res)` 返**二进制文件流**，`<img src>`/前端直接消费流，无 JSON 解析；仅错误（404/400/502）才走 `sendError`。此类端点**彻底不适用 M4-a/M4-b 的 JSON 信封收敛**——强行包 `{code:0,data}` 会破坏 `<img src>` 直链消费。M4-a 的 `sendError` 升级与 M4-b 的成功信封统一**明确排除二进制流端点**；校验脚本（M5-c）须将 `/api/files/read`、`/api/files/thumbnail` 标 `stream` 类型豁免信封检查。与 M5-e（SSE 流式例外）并列，构成「JSON 信封统一仅限非流非 SSE 的具名 CRUD handler」完整边界。
- **M4-d 本地优先声明**：具名 handler 显式注释「本地处理，不 deleg 透传」。

## 3. 翻车点（最容易出问题的 3 处）

1. **契约漂移 / 镜像错位**：前端聚合函数（`localToolApi.js` 等）与后端路由处理器（`routes/*.ts`）是手写双份、人工对齐的「镜像」。新增端点时任一端漏改或拼写不一致（路径前缀 `/api/`、方法 GET/POST/PUT、query vs body），都会静默落到 catch-all 透传，把本该本地处理的能力「白实现」。
2. **错误语义不对称**：前端 `httpClient.js` 把非 2xx 分类为 `HttpError(status,data)`，但后端透传层对上游 4xx/5xx 原样回传不改写，而具名路由处理器可能各写各的错误形状。非 SSE 域内前端聚合薄壳若假设统一信封，遇到形态不一致会解析错位或吞错；流式域（chatProxy 的 `{ok,error}` / agentChat 的 `data:{"error":"..."}` / providers 的平铺 `{ok,error}`）本就保留例外，须由 M5-e 划清边界、仅对齐 message 文本抽取（不强行统一嵌套 code）。
3. **重复样板与多出口**：前端已有 `httpClient` 统一出口，但仍有 `chatApi/imageApi/videoApi/proxyGenerate` 等多种聚合形态，部分绕开约定直拼；后端路由乱序也会让「本地优先」失效。两端约定（超时档位、重试策略、地址来源）各说各话，调参时互相甩锅、定位困难。

## 4. 约束清单

### 4.1 模块约束
- **M1**：唯一 fetch 入口；`API_BASE` 单一真相源，禁止裸写 18080。
- **M2**：每函数对应唯一后端端点；返回形状单一约定。
- **M3**：具名路由严格优先于 catch-all；顺序即优先级不可随意插队。
- **M4**：本地处理能力不可被透传覆盖；**非 SSE 具名 CRUD handler 错误信封统一**（SSE/探测域保留例外，见 M4-e/M5-e）。
- **M5**：端点命名/信封/错误码/日志前缀跨前后端一致。

### 4.2 跨模块约束
- **C1 单一契约真源**：每个 API 端点必须有「前端函数名 ↔ 后端 route 模式」的双向可查映射；新增端点必须两端同时登记（杜绝隐形透传白实现）。
- **C2 信封对称**：请求（method/Content-Type/body 形态）与响应（成功 `{code,data}` 或 `{ok}`、失败 `{error:{code,message}}`）前后端强制同一套约定；**适用范围：仅非 SSE 的具名 CRUD handler**（见 M5-e）——SSE 透传层/探测域因行协议限制保留 `data:{"error":"..."}`/平铺 `{ok,error}` 例外，但其 message 文本抽取优先级须与 `extractErrorDetail` 一致，确保文案前后端统一。
- **C3 错误不吞不重写**：非 2xx 由 `httpClient` 统一分类透传；后端具名处理器失败统一用 `sendError`/约定形状，严禁前端聚合层改写 message（CONTEXT 铁律）。
- **C4 可观测对齐**：前端 `label` 与后端 `console.log([passthrough]/[proxy]/路径)` 共用同一端点语义命名，便于跨跳追链路。

## 5. docs 罗盘基线（既有契约，细化时须复用，不重造轮子）

本次优化前先盘清 `docs/` 里与 API 中转站强相关的既有规范，作为不可冲突的基线。

### 5.1 docs/11 路由表重构方案（后端路由表已定型）
- 后端分发已是声明式路由表（`router.ts`）：顺序即优先级、具名路由严格优先 catch-all、带 `middleware` 预留钩子、Handler 第三参不约束（闭包自行提取 id）。
- 红线：阶段顺序 具名→前端托管→catch-all→404；catch-all 不得无脑 return；OPTIONS/CORS 在路由匹配前。
- **关系**：模块 3/4 边界已被 docs/11 锁死，本次细化只需在其上对齐「前端函数↔后端 route 双向映射」，不重做路由表。

### 5.2 docs/04 API 设置设计（前端出口已有「设置驱动」范式）
- 前端发请求方式完全由 `image_mode`（sync/async）等设置决定，不写死协议；`imageApi/videoApi/chatApi` 是这套范式的产物。
- 铁律：字段名照契约、key 只进 env、预留字段禁止删、「后端实现→前端开放」配套。
- **关系**：模块 2 薄壳承载「协议/模式分派」，本次优化要尊重这套分派，而非把它们压平。

### 5.3 docs/08 存储键集中登记（收口方法论范本）
- 解决「散落字符串/双登记/同名常量」问题，与本次「前端聚合函数↔后端路由镜像错位」（翻车点①）同源不同域。
- 范式可直接迁移：建一张**中央端点登记表**（前端函数名 ↔ 后端 route pattern ↔ method ↔ 信封形状），新端点必须先登记（对应 C1）。
- **关系**：模块 5（契约对齐）的最佳实现形态，即借鉴 docs/08 的「中央登记表 + 强制登记 + 动态工厂」方法。

### 5.4 既有 docs 尚未覆盖的缺口（本次优化要补）
1. 前端聚合薄壳**尚无中央端点登记表**（docs/08 管存储键，不是 API 端点），端点镜像靠人肉对齐 → 翻车点①。
2. 前后端**错误信封尚未统一约定**（docs 多处提到 `sendError`/`{ok}`/`HttpError`，但无一份「API 错误码/形状契约」文档）→ 翻车点②。
