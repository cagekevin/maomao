# 图片「显示 vs 发送」策略评判与收口设计

- 编号：18
- 日期：2026-08-21
- 状态：🟢 P0/P1/P2（webp 调整为「不引入」）均已落地
- 关联：docs/17-WebP整站图片策略-2026-08-20.md
- 触发：画布图片多时拖拽卡顿

---

## 一、结论先行（TL;DR）

1. **同分辨率 WebP（docs/17 的核心主张）解决了不拖拽卡顿** —— 拖拽成本在"解码后的像素数"，不在文件体积。2000×2000 的 jpg 与 webp 解码后都是 2000×2000 位图。WebP 唯一真正的价值是"**发送端省体积、同清晰**"。
2. **真正治拖拽卡的唯一杠杆是"显示按需尺寸解码"**：画布小框显示 2K/4K 原图是最大开销源，改成显示 `maxDim` 级（够小框清晰）小图，解码位图像素降一个数量级。
3. docs/17 的两个关键前提，**在现有代码里查无实据**：
   - "唯一闸门 normalizeImageUrl"：全 src 除其自身文件外无人引用，实际显示出口是 `toAbsoluteFileUrl`（24 文件混用）。
   - "发送用 256 缩略图会糊 → 需禁"：发送链路（`normalizeImageUrlForSend`）用的是**原图**，不是 thumbnail。`compressImage` 也只在 ImageNode 手动"压缩"里（quality 0.8、不缩分辨率）。
4. **收口结论**：不新造第二个图片出口。把"显示"与"发送"绑到**同一个统一出口**，由 scope 区分策略；后端复用 `resizeImage`（已支持按扩展名编码，可出 webp），把按需出图端点补齐 `format` 即可。显示瘦身、发送保真，互不干扰，一处呼吸。

## 二、现状实证（源码核对）

### 2.1 前端图片出口现状（多头，无真正唯一闸门）

| 出口 | 文件 / 位置 | 用途 | 现状 |
|---|---|---|---|
| `normalizeImageUrl` | imageUrl.js#L35 | 渲染端归一化 | ⚠️ **除自身外 0 处调用**，未接入组件 |
| `toAbsoluteFileUrl` | imageUrl.js#L22 | 相对 /files/ 补全 | 实际显示出口，被 ~24 个文件使用 |
| `normalizeImageUrlForSend` | imageUrl.js#L102 | 发送归一化（blob→data、补全） | 发送链路在用，发送的就是**原图** |
| `compressImage` | imageCompress.js / 仅 ImageNode#L104 | 手动"压缩"（quality 0.8） | 无 maxSize、不缩分辨率；**非发送路径** |
| 画布节点显示 | ImageNode.jsx#L240 | `<img src={原图}>` + CSS 缩放 | **全分辨率解码 → 拖拽卡顿主因** |

结论：docs/17 §3.2「normalizeImageUrl 是唯一出口」不成立；真正显示走 `toAbsoluteFileUrl` 且大量组件直接 `<img src=原图>`，是**多出口、无闸门**。

### 2.2 后端出图现状（已基本就绪）

- `resizeImage(src, dst, {maxDim, quality})`（fileStore.ts#L86）：`scale=min(1, maxDim/长边)`，`maxDim≥长边` 时 `scale=1` 仅压缩不放大；按 `dst` **扩展名**编码 → 传 `.webp` 即可出 webp。**零新依赖**。
- `handleThumbnail`（files.ts#L239，GET /api/files/thumbnail?url=&maxDim=&quality=）：**按需**出图，缓存 `thumb_{maxDim}x{quality}_*`，按源扩展名写（无 webp、无 `format` 参数）。
- 上传时 `tryGenerateThumbnail` 生成 256px 缩略图（原格式）。

结论：后端"按需出图"能力已有，缺 `format=webp` 与 webp 文件名后缀两条小改即可支持"按需尺寸 + webp"。

## 三、详细评判：三方案对照

| 维度 | 现状（原图直显示） | 同分辨率 WebP（docs/17） | **显示小图 + 发送原图/quality80** |
|---|---|---|---|
| 治拖拽卡顿 | ✕ 最卡 | ✕ 无效 | **✓ 有效** |
| 发送/图生图清晰 | 中（原图） | ✓ 良（同分辨率 q80） | **✓ 优（原图/同分辨率）** |
| 解码像素开销 | 最大 | 不变 | ↓ 一档 |
| 存储/网络体积 | 最高 | ↓ 30-50% | 中 |
| BE 改动 | 无 | 中（+format=webp） | 需前端收口 + 后端 format |
| 危害/风险 | 持续卡 | 治标不治本 | 改动面大但直接对痛点 |

**评判**：
- docs/17 方向（原图永存、URL 层转换、USE_WEBP 可回退）架构正确，但目标错位——把资源全花在"发送省体积"，而痛点"拖拽卡"它根本碰不到。
- 缩略图方案（朴素版）用户曾因"发送糊"反对，那是把 256px 缩略图**同时**当显示与发送源导致的；现状发送其实没用 thumbnail，糊根不在那儿。因此 **显示与发送必须解耦**，而不是"用 or 不用缩略图"二选一。

## 四、收口设计（统一入口，防第二份实现）

> 收口 = 把"显示 / 发送 / 按需出图"收敛到一个单一契约上，未来新增图片展示只走它，不各写各的 URL 处理。

### 4.1 目标契约

```text
前端唯一出口：
  resolveImageUrl(url, { scope: 'render' | 'send', maxDim?, format?, preferWebp? })
    scope='render'  → 走按需小图（maxDim 足显不糊），原图不糊小框
    scope='send'    → 原图；若 preferWebp → 同分辨率 webp quality80（省体积同清晰）
```

- 渲染一律 `resolveImageUrl(url, {scope:'render', maxDim: <节点框所需>})`；
- 发送一律 `resolveImageUrl(url, {scope:'send'})`；
- 禁组件的 `<img>` 直接写裸 URL / 禁散写 toAbsoluteFileUrl（由 4.2 做兼容收编，而非一次性大改）。

### 4.2 收编策略（兼容存量，避免大重构）

- 以 `toAbsoluteFileUrl` 为**兼容壳**：在其基础上包一层 `resolveImageUrl`，新代码用新出口，存量先指向原样行为（scope 待迁移组件逐步切到 render maxDim），保证逐步上收不破坏现有功能。
- 后端把 `handleThumbnail` 扩展 `format`（默认原扩展名，传 webp 时 `.webp` 后缀），复用其按需缓存能力——**不新增第二个缩略图端点**。

### 4.3 与其它"唯一入口"治理对齐

- 建结构/关系走既有唯一入口（同 addNode 已修复丢节点的思路）：`resizeImage` 是后端唯一出图入口、`resolveImageUrl` 是前端唯一图片出口，均已在单点收口；
- 幂等：按需缩略图以 `${maxDim}x${quality}_<format>` 文件名后缀做缓存键，重复请求不重复渲染（沿用 ensureThumbnailTarget）；
- 契约常量：URL 服务端点 / thumbnail 参数，登记到中央登记源，禁裸字面量；
- 失败可见：按需出图失败回退原图且 logger 留痕，不静默破图。

## 五、分阶段落地（建议）

1. **阶段 A（治拖拽，收益最大）**：显示链路改走按需小图。先看 `ImageNode` 等主要显示组件的 `<img>` + 前端 `resolveImageUrl(scope:'render')`，验证拖拽帧率提升。后端只需 `format` 小改（若需要 webp）。
2. **阶段 B（发送省体积）**：发送入口加可开关 `preferWebp`（同分辨率 quality80），`USE_WEBP` 开关集中管理、默认关，方便回退。这正是 docs/17 后半的真实价值落点。
3. **阶段 C（收口收尾）**：存量组件逐个切到 `resolveImageUrl('render')`，废弃直接 `toAbsoluteFileUrl` 的散用；补 `addNode` 同级别的唯一出口单测与按需出图单测。

## 六、开放问题（需复核后定）

1. 发送链路"图生图糊"真因：现发送用原图，仍糊的话更可能是**模型自身输入尺寸上限**（如 512/1024），与文件格式/缩略图无关——需一次实证定位，避免再往错误方向加方案。
2. 画布节点显示分辨率：`maxDim` 取多少既能满足节点框清晰、又不致拖拽劣化，需按最大节点框实测标定。
3. PNG 透明：webp/缩略图含透明边缘处理，阶段 C 后再判。
4. Jimp `writeAsync` 对 `.webp` 扩展名的编码映射，本地 curl 验收一次确认。

## 九、P2 实施记录（已完成：不引入 webp，2026-08-21）

> 前置裁定：Jimp 0.22 无 webp 编码器（`@jimp/types` 含 bmp/gif/jpeg/png/tiff，`@jimp/webp` 不存在）→ 若放行 `format=webp` 会在 resizeImage 失败后回退 `copyFileSync`，产出「.webp 文件名 + 原格式字节」的假 webp（不省体积 + MIME 错标）。故 P2 收紧为「不引入 webp」，专注正确性收尾。

**后端** `localTool/src/routes/files.ts`
- 新增 `SUPPORTED_THUMB_FORMATS = {png,jpg,jpeg,gif,bmp,tiff}`。
- `handleThumbnail` 的 `format` 仅白名单放行，`webp`/未知一律回落源扩展名 → 从根上杜绝假 webp。

**前端** `src/components/base/imageUrl.js` / `contracts.js`
- `buildThumbnailUrl` 仅透传白名单 format；`webp` 等不产出（前端钳制 + 后端拒绝双保险）。
- `API_ENDPOINTS.fileThumbnail` 登记注释更新为白名单语义。

**测试**
- 前端 `imageUrl.test.js`：`render` 白名单 `jpeg` 透传 / `webp` 被钳制（format 为 null）。
- 后端 `localtool.test.js` 新增「format 校验」：`format=webp` → 回落 `.png` 且绝不产出 `.webp`；`format=jpeg` → 产出 `.jpeg`。

**验证**：后端 `npm test`（tsc + node --test）139/139 通过；前端 `imageUrl.test.js` 22/22 通过。前端 `vite build` 待最终确认。

**遗留建议（非阻塞）**：发送链路目前回归「原图保真、不压缩」。若后续确认要「发送省体积」，需先升级 Jimp 1.x 或引入 `@jimp/webp` 单独评估，勿在 0.22 上硬开 webp。
