# 09 规范：节点错误降级与重试收敛策略

> 日期：2026-08-17
> 关联 TASK-056（抽统一节点错误降级 / 重试收敛策略，架构级）。
> 本文梳理「节点生成」链路上的错误处理与重试现状，标出已收敛与未收敛的部分，给出收口方案。
> 审计基线：基于 `src/**` 真实代码逐项核实（2026-08-17）。

## 一、链路全景（错误可能在哪一层发生）

```
节点 UI（PromptNode / TemplateNode / …）
  │ handleGenerate → useNodeGeneration.start()
  │   ├─ validate() 前置校验失败 → setError + 不进任务
  │   ├─ AbortController 真取消（stop）
  │   └─ run({ progress, signal })   ← 真执行器
  ▼
imageApi / videoApi.generateXxx()
  │ proxyRequest() → fetch(localTool /api/proxy)   ← 【网络层：抖动/网关未起/超时】
  │   ├─ sync ：读 SSE 流（上游失败/进度）
  │   └─ async：提交 → 轮询 GET /v1/tasks/{id}      ← 【轮询层：网关瞬断】
  ▼
上游供应商（Lovart / OpenAI …）                          ← 【上游层：限流/内容审核/任务失败】
  │ 返回 { ok, url } / { ok:false, error }
  ▼
useNodeGeneration：
   成功 → 内部 saveResultToTasks 落盘 + setNodeData + onSuccess(UI 回写)
   失败 → setError + taskCtl.fail + toast
   注册 → registerTaskRetry（手动「再来一次」）
  ▼
任务中心 / Agent generate_node（retryTask 触发同一节点 start）
```

**四层错误源**：① 节点 UI 校验 ② 网络层（前端↔localTool↔网关） ③ 轮询层 ④ 上游供应商。

## 二、现状盘点：已收敛 vs 未收敛

### ✅ 已收敛（架构级做得好，保持）

| 能力 | 落点 | 说明 |
|------|------|------|
| 节点生成统一契约 | `useNodeGeneration.js` | 收敛「提交→进度→成功（`saveResultToTasks` 内部落盘 + `setNodeData` + `onSuccess` 仅 UI 回写）/失败/中止/重试注册」。所有节点必须走它（见 `TemplateNode` 注释「生成契约」）。 |
| 成功后落盘与 UI 回写分离 | `useNodeGeneration.js:95-106` | `done` 分支：**内部**调 `saveResultToTasks`（持久化到任务中心）+ `setNodeData`（写回 `node.data` 持久 URL）；`onSuccess` 只做节点内 UI 状态回写（如 `setImageUrl`）。落盘不是散落在各节点。 |
| 手动重试注册 | `taskStore.retryRegistry`（`registerTaskRetry` / `retryTask`） | 节点挂载即注册 `start` 回调；任务中心「再来一次」、Agent `generate_node` 复用同一回调驱动重跑。 |
| 真实取消 | `AbortController` + `signal` 贯穿 `proxyRequest` | `stop()` 真中断 fetch / SSE / 轮询；`AbortError` 不报错、返回 `{aborted:true}`。 |
| 防重入 | `runningRef` 原子锁 | 双击只跑一次。 |
| 刷新恢复（结果不丢） | `taskStore.done` 广播 `agent:task-completed` + `useNodeGeneration` 监听 `onRecover` 回写 `node.data` | 覆盖存量节点 / 写回竞态丢图；节点已卸载时由 `onRecover` 兜底（节点消失重建形态差异大，由各节点实现）。 |
| 性能降级（显示层） | `useMediaDegrade` | `lodLevel≥2` 藏图、`≥3` 藏视频/音频；所有节点统一用，禁止各自写字符串判断。 |
| 编排级失败跳过 | `canvasPlanExecutor` | 依赖批仅当前置全部成功才执行；否则标 `failed` 并提示「去画布节点重试前序」（不自动重试整批）。 |
| 异步轮询网络抖动保护 | `pollTask` 机制（`imageApi.generateAsync` 内轮询） | 轮询单轮异常**直接 fail 不重试**，但提交成功后任务已在供应商侧；刷新后 `useNodeGeneration` 监听 `taskStore.done` 可恢复，不会误报 failed。 |

### ⚠️ 未收敛（需收口）

| 缺口 | 现状 | 风险 |
|------|------|------|
| **1. 网络层自动重试缺失** | `proxyRequest` / `generateSync` / `generateAsync`(提交与 SSE 阶段)遇网络错误**直接 fail**，无指数退避自动重试。`pollTask` 只保护轮询阶段，sync/提交阶段完全没有。 | 一次网关抖动 / localTool 刚启动就直接红字失败，用户只能手动重试。 |
| **2. 错误分类缺失** | API 层只返 `{ok,url,error}` 字符串，`useNodeGeneration` 不区分错误类型。网络错、上游限流、内容审核、超时、取消混为一谈。 | 无法决定「该不该自动重试」「UI 报什么」「任务中心标什么」。例如内容审核不该重试，网络抖动该重试。 |
| **3. 节点内 UI 回写 / onRecover 散落** | 落盘已统一（§二 已收敛），但 `onSuccess` 的 UI 回写（如 `setImageUrl`）和 `onRecover` 的「节点消失重建」各节点自写，不统一。 | 新建节点易漏 `onRecover`，导致刷新后结果不回填。错误文案各节点写死，体验不一致。 |
| **4. 自动重试 vs 手动重试边界未定义** | 当前只有手动重试（`retryRegistry`）。是否要自动重试、重试几次、退避多久，没有集中策略。 | 每个 API 自己拍脑袋，或干脆没有，体验分裂。 |
| **5. 重试/轮询常量硬编码** | `imageApi` 轮询间隔 `3000ms`(第147行)、`videoApi` 轮询间隔 `5000ms`(第80行)；`imageApi` 超时 `300000`(第239行)、`videoApi` 超时 `600000`(第126行)。 | 改一个间隔要翻两个文件；无统一「重试预算」概念。 |
| **6. 网络错误判断不统一 / 部分链路失效** | `imageApi.js:112,134`、`videoApi.js:67` 用 `if (/^网络错误/.test(e.message))` 区分网络错；但 `proxyRequest` 在 `!res.ok` 时抛的是 `j?.error?.message`（上游错误文案），fetch 网络失败浏览器抛 `"Failed to fetch"`/`"NetworkError"`——**这两者均不以「网络错误」开头**，故 imageApi/videoApi 这条链路的 `/^网络错误/` **实际匹配不到**，网络错被当 UNKNOWN。注意 `chatApi.js:55` 在 catch 里显式 `throw new Error('网络错误：'+e.message)`，该链路判断有效——说明判断是否生效**取决于上游/封装是否手动加「网络错误」前缀**，不可靠、不统一。 | imageApi/videoApi 的网络错被当 UNKNOWN，重试/文案策略失效；各 API 分类逻辑割裂。 |

## 三、收口方案

### 3.1 错误分类枚举（单一事实来源）→ `src/components/base/genErrors.js`（新建）

```js
// 错误类别决定「是否可自动重试」「UI 文案」「任务中心标记」
export const GenErrorType = {
  CANCELLED:  'cancelled',   // AbortError：用户主动停止，不重试
  NETWORK:    'network',     // 前端↔localTool/网关网络抖动、连接失败：可自动重试
  TIMEOUT:    'timeout',     // 轮询/请求总超时：可自动重试（限次数）
  UPSTREAM:   'upstream',    // 上游返回失败（限流/任务失败/内容审核）：不自动重试
  VALIDATION: 'validation',  // 前置校验/参数非法：不重试，提示改输入
  UNKNOWN:    'unknown',     // 兜底：可重试一次
}

// 由异常/响应推导类型（API 层统一调，node 层不自己判断）
export function classifyError(e, { httpStatus, upstreamStatus } = {}) {
  if (e?.name === 'AbortError') return GenErrorType.CANCELLED
  const msg = e?.message || ''
  // 真实浏览器 fetch 失败文案：'Failed to fetch' / 'NetworkError' / 'Load failed'
  if (/Failed to fetch|NetworkError|Load failed|ECONNREFUSED|fetch failed/i.test(msg)) return GenErrorType.NETWORK
  if (/超时|timeout/i.test(msg)) return GenErrorType.TIMEOUT
  if (httpStatus === 400 || httpStatus === 422) return GenErrorType.VALIDATION
  if (upstreamStatus === 'failed' || upstreamStatus === 'error') return GenErrorType.UPSTREAM
  return GenErrorType.UNKNOWN
}

// 是否可自动重试
export const isAutoRetryable = (type) =>
  type === GenErrorType.NETWORK || type === GenErrorType.TIMEOUT || type === GenErrorType.UNKNOWN
```

**强制规则**：所有 API 返回 `{ok:false, error, type}`（`type` 由 `classifyError` 推导）；`useNodeGeneration` 只读 `type` 决策，**节点自己不得再 `if (/网络错误/.test(msg))`**（当前 `imageApi`/`videoApi` 里散落的 `/^网络错误/` 判断一律删除，改用 `classifyError`——见缺口 6，该判断在 imageApi/videoApi 链路实际失效；`chatApi` 因手动拼前缀暂有效，统一后一并替换）。

### 3.2 自动重试策略（集中常量 + 统一封装）→ `apiBase.js` 增 `withRetry()`

```js
// 统一自动重试预算（指数退避）
export const RETRY = {
  maxAttempts: 3,          // 含首次，最多 3 次
  baseDelayMs: 800,        // 退避 = base * 2^(n-1)：800 / 1600 / 3200
  maxDelayMs: 5000,
}

const abortError = () => { const e = new Error('aborted'); e.name = 'AbortError'; return e }
const sleep = (ms, signal) =>
  new Promise((resolve, reject) => {
    if (signal?.aborted) return reject(abortError())
    const t = setTimeout(resolve, ms)
    signal?.addEventListener('abort', () => { clearTimeout(t); reject(abortError()) }, { once: true })
  })

/**
 * 包一层自动重试：仅对 isAutoRetryable 的错误重试，命中上限或不可重试直接抛出原错误。
 * 调用方（generateSync/generateAsync/proxyRequest 提交阶段）不再自己写 retry 循环。
 */
export async function withRetry(fn, { signal, attempts = RETRY.maxAttempts } = {}) {
  let lastErr
  for (let i = 1; i <= attempts; i++) {
    if (signal?.aborted) throw abortError()
    try { return await fn(i) }
    catch (e) {
      const type = e?.type || classifyError(e)
      if (!isAutoRetryable(type) || i === attempts) { lastErr = e; break }
      const delay = Math.min(RETRY.maxDelayMs, RETRY.baseDelayMs * 2 ** (i - 1))
      await sleep(delay, signal)
    }
  }
  throw lastErr
}
```

> 边界约定：**自动重试只在「网络/超时」层发力**（`proxyRequest` 提交与 SSE 包 `withRetry`）；**上游业务失败（限流/审核/任务失败）不自动重试**，交给手动「再来一次」（避免对限流猛刷导致封号）。`async` 轮询阶段已由「提交成功后供应商侧任务不受前端网络影响 + 刷新恢复」覆盖，这里 `withRetry` 只包单轮请求异常。

### 3.3 节点回写 / 文案收口 → `useNodeGeneration` 接 `type`

- 落盘（§二 已收敛）保持内部 `saveResultToTasks`，**不改动**。
- `onSuccess` 仅 UI 回写（现状正确），但要求各节点 `onSuccess` 不得再承担落盘职责（已无，明确写进契约注释）。
- 错误文案统一由 `type` 映射（网络错→「网络波动，已自动重试仍失败，请检查本地服务」；上游错→「上游生成失败：<原因>」；校验→「参数有误：<原因>」），不再各节点写死。
- `onRecover`（节点消失重建）保留各节点实现（形态差异大），但 `useNodeGeneration` 注释标明「刷新恢复必实现 onRecover」，新节点模板默认带空实现提醒。

### 3.4 编排层失败处理（保持手动，补一致性）

`canvasPlanExecutor` 现状（依赖批前序失败→标 failed、提示去节点重试）**保持不变**——多步编排不应自动重跑整批（会重复计费）。但补一条：单步失败标记统一带 `type`，任务中心据此显示「可重试」按钮。

## 五、落地步骤（建议顺序）

1. **建 `genErrors.js`**：错误枚举 + `classifyError` + `isAutoRetryable`（§3.1）。
2. **`apiBase.js` 加 `RETRY` 常量 + `withRetry()`**（§3.2，含 `sleep`/`abortError`）；`imageApi`/`videoApi` 的 `proxyRequest` 与 SSE 阶段包 `withRetry`；删除散落的 `/^网络错误/` 失效判断，改返 `{ok:false,error,type}`（修缺口 6）。
3. **`useNodeGeneration` 接 `type`**：读错误类型决策；错误文案由 `type` 映射；契约注释明确「onSuccess 仅 UI 回写、必实现 onRecover」。
4. **节点迁移**：`PromptNode` 等确认 `onSuccess` 不含落盘（已无）；`TemplateNode` 注释补「错误/重试走契约，禁止节点内自写重试」。
5. **集中常量**：轮询间隔 / 超时从硬编码提到 `RETRY` 或 `apiBase` 常量（§二 缺口 5：imageApi 3000/300000、videoApi 5000/600000）。
6. **文档/模板同步**：`BASE-CAPABILITIES.md` 登记 `genErrors.js`；节点模板默认带 `onRecover` 空实现。
