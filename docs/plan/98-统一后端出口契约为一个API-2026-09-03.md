# 统一后端出口契约为一个 API（relay/proxy 合流 · 端点层收口）

> 状态：设计。决策（你已定）：统一后端出口契约为**一个 API**，前端只打一套语义端点，不再有
> proxy / relay / generate 三套并存心智。本设计把「一个 API」的端点形态、数据流、与已实现
> relay/generate 的关系、chat/sync 并入方式、proxy 退役时序定准，作为施工蓝图。

---

## 0. 一句话

后端把所有「生成/聊天」出口收敛成**一套「提交→后端驱动→取结果」的 API**：前端只发意图拿 taskId，
后端常驻进程提交/轮询/落盘/写库，前端 GET attach 收结果（image/video 现在就能如此）。chat（文本）
并入同一契约或同一门面。proxy 后端路由不恢复、前端切完后 `check:api` 归零。

## 1. 为什么「一个 API」能成立（数据流唯一化）

现状三套端点是**三种数据流**，这正是「怎么结合」纠结的来源：
- `/api/proxy`：前端驱动（前端发起+轮询+落盘+写 result_url）→ 丢结果根因。
- `/api/relay`：后端驱动但**同步阻塞**（handleRelay await executeModelProtocol 到终态才返）。
- `/api/generate`：后端驱动**提交即返 + 可 attach**（本仓库已实现，根治丢结果）。

「一个 API」= **统一采用第三种数据流（后端驱动、句柄可 attach）作为唯一语义**，因为它同时满足：
- 丢结果根治（后端轮询+落盘+写 DB，可重启恢复）；
- 前端刷新不丢（GET attach 同一句柄）；
- 取消/进度/参考图归一全部由后端兜。

## 2. 统一端点契约（对外只一套）

```
POST /api/generate           提交（image/video/chat 意图）→ {code:0,data:{taskId}} 不等终态
GET  /api/generate/:taskId   attach 查询 → {code:0,data:{status:'running',progress}} 
                                        | {status:'completed', url?|text?} 
                                        | {status:'failed', error}
POST /api/generate/:taskId/cancel        取消 → {ok}
```

- image/video：完成后 `url` = 后端已落盘 `/files/`（backend 写 result_url 到 tasks DB）。
- chat（文本）：完成后 `text` 返回（本期 chat 走 `/api/relay` 同步；若需与 image 一致的刷新恢复，
  可让 chat 也进 `/api/generate` 后端任务化——见 §4.3，本期不做，保持同步）。
- `/api/relay`：**保留为「同步语义」薄壳**（调用方要一次性拿结果、不关心可 attach 时用；如 CLI/内部）。
  → 即 `/api/relay`(同步) 与 `/api/generate`(异步可attach) 都是「一个能力」的两种视图，不是两套生成引擎。

## 3. 后端模块归属（唯一出口纪律）

| 能力 | 唯一出口 |
|---|---|
| 协议执行（提交/轮询/取结果） | ai-relay kit（`protocol.submitModelProtocol` / `pollModelProtocolOnce`）——C0 |
| 提交即返 + 句柄管理 | `localTool/src/relay-poll.ts`（本仓库已实现） |
| 落盘 /files/ | `saveRemoteUrl`（M4-C1，不依赖 kit） |
| 写 result_url | `upsertTask`（routes/tasks.ts，本仓库已导出） |
| 对外端点 | `/api/generate*`（routes/generate.ts，本仓库已实现）+ `/api/relay`(同步薄壳) |
| provider 配置 | config/providers/<id>.json（96 号已实现）+ key 进 .env |

→ **`/api/proxy` 不再是生成出口**。它在前端未切完前仅作过渡（catch-all 透传现状）；前端全走后删。

## 4. 各模态并入方式

### 4.1 image / video —— 已就绪
`/api/generate` capability='image'|'video' 已实现后端 submit→poll→落盘→写库→GET attach。
前端 `relayProxy.relayGenerate` 已对接。缺：真机验证 + 前端 image/video 切过来 + 删 proxy 轮询段。

### 4.2 chat —— 本期走 relay 同步（不进 /api/generate）
- 端点：`POST /api/relay`（handleRelay 已实现，kit chat/streamChat）。
- 前端 `chatProxy` 改走 `/api/relay`，`stream` 用 kit `streamChat`。
- **边界**：chat 是「一次性返回文本」，无落盘/result_url 需求；刷新丢的只是「等文本的请求」而非「已产出的图」，故不必后端任务化。保持 relay 同步语义最简。
- **responses chat 形态**（GPT-5.6/gemini）：需在 relay 侧补（kit 无 responses 协议），或用前端保留的 requestModes responses 归一喂 kit 文本路径。见 §6.1。

### 4.3 sync-SSE 生图（?wait=1 平台）
全迁后**不再有前端 sync 分支**：统一在后端按 async 任务落盘（后端提交+轮询）。需在 relay 侧确认各平台
真实为 async（9004 lovart 即 async）；纯 sync 平台若存在，保留 relay 同步 generateImage 作内部快路径，
对外仍 /api/generate 语义。见 §6.2。
