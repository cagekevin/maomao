## 0. 一页速览

### 0.1 终局四条铁律（违反即返工）

1. **磁盘 `SKILL.md` 是内容的唯一真相源**。localStorage 只是缓存/索引，云端只是副本。网页改、VS Code 改、云同步拉回来的改 —— 三者最后都必须落回磁盘。
2. **一个稳定 `id`（UUID）**，写进 `SKILL.md` frontmatter，与目录名完全解耦。改名、换分类不动 id。
3. **skill 正文照旧上云、不加密**。`agent_skills` 单键含 `content`，`sync: true` —— 与现状结构一致，**零迁移**。
4. **只有一个模块、一个门面**。全部 skill 文件住 `src/components/agent/skill/`；域外调用方**只准 import `agent/skill/index.ts`**，禁引模块内其他文件（§2）。

## 1. 终局形态（唯一生效）

### 1.1 磁盘布局

```
~/.maomao-localtool/skills/                ← 单独根，**不在 uploads/ 之下**（理由见 §1.1.1）
├── 图片类/
│   └── 漫画生成/
│       ├── SKILL.md                       ← frontmatter(声明) + 正文  ＝ 内容真相源
│       ├── references/                    ← 只读资料（P4 经 skill_read_file 按需读）
│       │   ├── workflow.md
│       │   └── art-styles/manga.md
│       └── scripts/                       ← 落盘保全，**永不可被模型读取**
├── 视频类/
└── _未分类/                               ← 迁移与无分类导入的落点
```

**无 `.maomao.json`**：元数据分两块 —— 内容侧落 `SKILL.md` frontmatter，运行态侧落 localStorage。

#### 1.1.1 为什么技能库根必须独立于 `uploads/`（三条硬事实，不是洁癖）

| 事实 | 证据 | 若把 skills 放进 `uploads/skills/` 的后果 |
|---|---|---|
| `/files/**` 是静态服务 | `localTool/index.ts` 静态路由 | `scripts/**`（含可执行脚本）可经 HTTP 直接取走 |
| 素材库 rescan **递归遍历 uploadDir 每个顶层目录**并入库 | `localTool/src/routes/resources.ts:83-160` | `SKILL.md`、`references/*.md`、`scripts/*` 全变成"素材"，污染素材库 |
| uploadDir 有顶层根白名单 + 孤儿 GC | `utils/fileStore.ts:82` `UPLOAD_ROOT_ALLOW` · `utils/orphanGc.ts` | 要么往白名单塞特例（把 skill 拖进媒体域），要么被 GC 误判 |

> 结论：在 `localTool/src/db/database.ts` 新增 `getSkillsDir()`（与既有 `getUploadDir()` / `getBackupDir()` 并列，同为 `getDataDir()` 下兄弟目录）。**121 §3.6 的"facade 复用 `getUploadDir()`"作废**，以本节为准。

### 1.2 `SKILL.md` 格式

```markdown
---
id: 6f1c2a90-3b7e-4d51-9a02-8c4f5b1d7e33
name: 漫画生成
description: 根据剧本与角色设定生成分镜式漫画页，输出可直接生图的提示词
when-to-use: 用户要求"画漫画 / 出分镜 / 做条漫"时
version: 2
allowed-tools: canvas_create_node
---

# 工作流

1. 读 `references/workflow.md` 确认分镜规范
2. 按 `references/art-styles/manga.md` 的色调与网点要求撰写提示词
3. 输出 JSON 规划，等用户确认后再生成
```

| 字段 | 必填 | 谁写 | 作用 |
|---|---|---|---|
| `name` | ✅ | 用户 / 导入 | 显示名；通用规范必填 |
| `description` | ✅ | 用户 / 导入 | 用途；**清单块（块①）唯一取材处** |
| `when-to-use` | 可选 | 用户 | 触发条件（**非通用规范的扩展字段**，保留；见 §9） |
| `version` | 可选 | 用户 | 变更提示「v1→v2」 |
| `id` | 由本模块写入 | 系统 | 稳定 UUID，**一经创建永不变** |
| `allowed-tools` | 可选 | 用户 | **解析但不生效**（开关只有 `agent_skill_enabled`） |
| `user-invocable` / `disable-model-invocation` | 可选 | 用户 | **解析但不生效** |
| 其他未知字段 | — | — | **忽略但原样保留**（往返幂等 + 兼容外部 skill 包） |

**解析规则（5 条，必须全做）**：① 零依赖手写解析器；② 只解析标量，未知字段忽略但保留；③ **安全字段禁多行写法**（`allowed-tools` / `user-invocable` / `disable-model-invocation`）防伪造；④ 标签脱敏 `sanitizeSkillLabel`；⑤ **安全阀**：frontmatter 解析失败 → 整文件当正文，不报错、不丢内容。

### 1.3 存储键与同步范围

| 键 | 内容 | backend | `sync` | 说明 |

| `agent_skill_config` | `{ catalogToModel: boolean; contentLimits: {...} }` | local | ✅ true | **新增（唯一新键）**：D7/D8 开关 + D3 预算可调 |
| `agent_skill_cache` | —— | —— | —— | **不引入**（121 的双键方案已撤回） |

### 1.4 消费三层（渐进披露）

| 层 | 内容 | 何时进 system | 开关 |
|---|---|---|---|
| ① 元数据清单 | `name` + `description` + `id`（**无正文**） | `catalogToModel === true` 时**每轮** | **默认关**（D8） |
| ② 本次启用正文 | 用户本轮 chip 选中的 skill 正文（截断后） | 本轮有绑定才进 | 恒开（手动选中是主路径） |
| ③ 附属资料 | `references/**` 单文件 | 模型调 `skill_read_file` 按需读（P4） | 恒开 |

**块①（清单）措辞**（逐字用，不得改写）：

```
以下是你可用的 Skill 清单，仅表示存在，不代表本次已启用：
- 漫画生成（6f1c2a90-…）：根据剧本与角色设定生成分镜式漫画页
- …（≤24 条）

清单本身不是本次任务要求。只有当用户本次需求明确匹配某一项时，才按它执行。
```

**块②（本次启用）措辞**：

```
===== 本次启用 Skill（2 项）开始：漫画生成 =====
<正文，已按预算截断>
===== 本次启用 Skill 结束：漫画生成 =====

===== 本次启用 Skill（2 项）开始：电商详情页套图 =====
<正文>
===== 本次启用 Skill 结束：电商详情页套图 =====

```

**"AI 怎么知道本轮有没有发 skill"**：**本轮 0 绑定 → 块②完全不出现**。模型据"有无块②"判断；块①只影响它是否知道"有哪些"。两条块文本均来自用户文件（不可信数据），`SKILL_EXECUTION_RULES` 的不可信条款必须**同时覆盖块①**。

**"人怎么知道"**：P2 的 `SkillBinding` 在消息发出瞬间冻结留痕，回看/重发显示「本轮启用：xxx」。

### 1.5 编辑入口：两个门，同一份真相

**两个都做，不是二选一** —— 它们是通向同一份磁盘文件的两种手感：

| 入口 | 操作 | 底层 |
|---|---|---|
| **网页编辑**（保留现有能力） | 设置页点开 skill → 编辑器里改 → 保存 | 保存 = 经 §2.2 用例② 写盘 |
| **打开文件夹**（新增按钮） | 点卡片上的 📂 → Finder/资源管理器打开该 skill 目录 → 用任意编辑器改 `SKILL.md`、往 `references/` 丢文件 → 回猫猫点「重载」（或等焦点检测提示「文件已更新 · 点此刷新」） | 直接改盘 |

因为**磁盘是唯一内容真相源**，两个门不存在"哪边为准"的问题 —— 网页保存写盘、Finder 直接改盘，同一份文件。这正是本方案要的形态。

#### 1.5.1 普查（V2 Step 0 · 入口对照表）

**同一需求（打开某个目录）在别入口怎么满足的**：

| 入口 | 现有实现 | 已满足？ | 处置 |
|---|---|---|---|
| `GET /api/files/open?subfolder=` | `files.ts handleOpen`：`path.join(uploadDir, subfolder)` + `normalizeSubfolder` **白名单** | ❌ 开不到（`skills` 不在 `UPLOAD_ROOT_ALLOW`；加进去 = 把技能库拖进媒体域，§1.1.1 明禁） | **不复用** |
| `GET /api/files/open-dir?filepath=` | `files.ts handleOpenDir`：`path.join(uploadDir, relativePath)` | ❌ 开不到（技能库在 `getSkillsDir()`，是 uploads 的**兄弟目录**，越根） | **不复用** |
| `resource/ResourceCardActions.tsx` 的 📂 按钮 | 悬停浮现 `FolderOpen` 图标 → 调 `filesApi.openFileDir` | ✅ **UI 形态直接照抄** | **复用形态** |
| `execSync('open'/'explorer', dir)` | 两个 handler 共用的同一段 | ✅ 逻辑同款 | **复用形态** |

**结论**：形态可抄、**作用域不可复用** ⇒ 新增一个薄端点 `GET /api/skills/open-dir`（§3.4）。
它**不接受任意路径输入**，只收 `category` / `slug`（缺省 ⇒ 开技能库根）⇒ 无路径穿越面，比复用 `open-dir?filepath=` 更安全。

### 1.6 分组与批量开关

**组 = 磁盘上的分类目录**（不是新概念）。现状 UI 是硬编码两段（`SkillSettings.tsx:80` 的个人/官方），本方案把它升级为**可自建的分组树**。

| 项 | 定论 |
|---|---|
| **组清单** | `官方`（内置，只读，无磁盘目录）∪ 磁盘分类目录。`_未分类` 在 UI 显示为「未分组」 |
| **新建组** | 两条等效路径：① 侧栏「新建分组」→ `POST /api/skills/group` 建目录；② 新建/编辑技能时把「分组」字段填成新名字（目录由整包写顺带创建）。Finder 里建目录 + 重读同样可行 |
| **改组名 / 换组** | 编辑技能时的「分组」字段：与现值不同即**换组**（新位置写成功后才删旧包，id 不变、绑定不断）。只改目录名（不改技能归属）走 Finder |
| **组开关（批量）** | 点一下 ⇒ **一次读一次写**把该组内所有 skill 写进 `agent_skill_enabled`（`setSkillsEnabled`；不是新的一层状态，也不是 N 次单键写） |
| **组的显示态** | 全开 / 全关 / 部分 —— **从成员派生**，不存"组自己的状态" ⇒ **无第二个真相源**，不会出现"组显示开着但成员全关" |
| **官方组** | 只读：不能改名、不能删、不能改组（内置 skill 无磁盘目录）；开关照常可用 |
| **跨设备** | `agent_skill_enabled` 已 `sync: true` ⇒ 组开关自动跟随，**零新键、零改动** |
| **删除组** | 目前只能删**空组**（在 Finder 里删目录）；组内还有 skill 时不做"顺手递归删"（不静默删用户技能） |

**为什么不做"组自带一个开关状态"**：那会造出第二个真相源，必须再立"组状态 vs 成员状态谁赢"的优先级规则 —— 正是本仓「单一规则原则」（CLAUDE.md §5.4.9）要消灭的形态。批量写 + 派生显示态 = 一份真相、零优先级规则。

**多对多的代价（若 D11 选多对多）**：① frontmatter 加 `groups: string[]`（一个 skill 多个组）；② 必须新增一条冲突规则（"A 组关 / B 组开 ⇒ 谁赢"，且组开关不再是"批量写成员"而是"叠加一层派生状态"）；③ 组开关的显示态变成三态含义模糊（是成员显式值还是组派生值？）。⇒ 一条规则的成本，换"一个 skill 出现在两组"的便利。

> 歧义（多绑定未指明）**不猜**；缺磁盘落点/二进制/包内无此文件都**如实说清**，并回可读清单让模型自己改对。



**实际落地的形态**（与本节初版设计的差异已对齐）：
- 工具签名 = `skill_read_file({ path, skill? })`：`path` 必填（正文里写出的相对路径），`skill` 可选（本轮多个 Skill 时用**名或 id** 指明；歧义**不猜**，直接让模型用 id）。
- 授权三条件同时满足：① 该 Skill 在**本轮冻结绑定**里；② `path` 在**该 Skill 正文**的反引号/链接清单（`extractResourcePaths`）内；③ 过 `assertSafeSkillRelativePath`（拒绝对路径 / `..` / scheme / `scripts/**` / 非文本扩展名）。
- **`scripts/**` 永不读**（扩展名白名单 + 后端 `scope=content` 双保险）。
- **不做 `resourcePaths` 注入**（初版设想过）：正文里本来就写着反引号路径，再注入一份清单 = 第二份真相，且它自己还要吃预算。模型读正文即知道该读什么 —— 这也正是通用格式的做法。
- 预算**复用** `contentLimits.singleSkillChars`（不再单列 20000）：截断时回 `truncated:true`，让模型知道拿到的不是全文。
- 内置 skill 无包目录 → 明确拒绝（"不在磁盘上"），不报"文件不存在"。

**验收**：`npm run test:unit`（`skillResource.test.ts` 14 例锁边界：无绑定 / 未引用 / 路径准入 / 无落点 / 二进制 / 歧义 / 截断 / 透传后端失败）· `useCanvasAgentTools.test.ts` 锁工具注册与只读归类。

### P5 · 云 pull 后回写磁盘（✅ 已落地 2026-09-21 · D6）

**做什么**：`cloudSync.downloadConfig` 在 `restoreLocal` 成功之后、**写台账之前**调
`applyCloudSkillsToDisk({ protectIds })` —— 把刚拉下来的技能正文写回 `skills/` 磁盘。

**四个必须记住的点**（都是实现中踩出来的）：

| # | 决策 | 为什么 |
|---|---|---|
| 1 | 放在**写台账之前** | 写回会更新缓存条目（`updatedAt` 等）⇒ 台账基线必须采"写回后"的本地值，否则下次自动上传把这次写回当成"本地改过"而回推一遍 |
| 2 | `protectIds` 在 `restoreLocal` **之前**采集 | 恢复之后缓存里已是云端内容，"谁是本地改动"再也分不出来 |
| 3 | 本地磁盘改动**跳过写回 + 如实上报** | 覆盖 = 用云端版本删掉用户刚在 VS Code 写的东西。本仓红线（不静默丢用户数据）优先于"三副本一致" |
| 4 | 写盘仍只经 `saveSkillToDisk` | 本模块不自己碰磁盘/缓存，否则就成了第二个写者（ADR-0056 Q2） |

**顺带修掉一个真 bug**：`SKILL.md` 是整文件重建的，更新时**没有带过磁盘上原有的 frontmatter** ⇒
用户/外部包写的 `x-*` 未知字段会被一次"保存"（或本 P5 的写回）静默抹掉。现按
「磁盘原有（最弱）→ 调用方显式给的 → 本次事实（id/name/description）（最强）」合并，`unknown` 取并集。

**验收**：`skillCloudSync.test.ts` 8 例（一致则跳过 / 旧则写回 / 保护跳过 / id 不变 / 不连坐 / 缓存损坏 / 后端不可用 / 残缺条目）
+ `cloudSync.test.ts` 4 例接线（保护集传入 / 漂移失败仍继续 / 失败进 `partial.failed` / 保护项可见）
+ `skillPersist.test.ts` 1 例（`x-author` 不被抹掉）。

## 5. 迁移（`localStorage` → 磁盘）

前提（已实测）：114 从未落地，旧 id 只有 `skill_${now}` 一种。

1. 触发：首次 hydrate 且 `~/.maomao-localtool/skills/` 不存在或为空，且 `agent_skills` 有数据。
2. 逐条：`_未分类/<slug>/SKILL.md`，frontmatter 写 `name/description/id:<新UUID>`；`slug` 由 `name` 清洗，同分类重名加 `-2/-3`。
3. 旧 id **登记进 `aliases: string[]`**；**不改写、不删除** `agent_skill_enabled` / `agent_skill_usage` 旧键（运行时按 alias 命中）。
4. 迁移是**写文件**，不是清 localStorage；任一条失败 → 保留旧数据并告警，不静默吞。
5. **幂等**：`skills/` 非空即跳过；重复执行不产生副本。

**回滚**：删除 `~/.maomao-localtool/skills/` 即回到"纯 localStorage"老行为（`agent_skills` 一直在，未被清过）。

## 8. 边界（不做的事 · 红线）

**不做**：① `skill_search` / `skill_load` / 模型自建 skill（无 MCP 控制面）；② 第二套引用语法（不引入 `@skill{id|名}`，沿用 `/` 菜单 + chip）；③ `allowed-tools` 生效；④ `scripts/**` 的任何读取路径；⑤ 备份包含 `skills/`（后续再做）；⑥ 加密与逐用户鉴权（D5 裁定不需要）。

**红线**：① 磁盘 `SKILL.md` 是唯一内容真相源，"只改缓存不回写磁盘"即返工；② `id` 与目录名解耦，**无路径兜底**；③ 落盘失败缓存不更新；④ 技能库不得放 `uploads/` 下（§1.1.1）；⑤ 新增存储键必须 `contracts.ts` 登记 + `check:keys` 过，新增端点必须 `router.ts` + `apiRegistry` 双登记 + `check:api` 过；⑥ **域外只准 import `agent/skill/index.ts`**（§2.3）。

## 10. 为什么不另建「skill 专用」ADR（D10）· 通用条已落 ADR-0056

`scripts/adr.mjs` 的六问里，第 ③ 问是**"能不能不用 ADR 守？"**（ADR 属手段优先级 5，是孵化器不是仓库）。逐条自答：

| 铁律 | 靠什么守 | 需要 ADR 吗 |
|---|---|---|
| ① 磁盘是唯一内容真相源 | 写在保存链路内部（`skillPersist` 落盘优先），域外只能调门面 | 否 |
| ② UUID 身份、无路径兜底 | id 由模块创建时生成并写进 `SKILL.md`；映射表住模块内存 | 否 |
| ③ 正文上云不加密 | 存储键的固有属性（`agent_skills.sync`）+ 唯一写入者 + `check:keys`/`check:arch` 规则 12-b | 否 |
| ④ 域外只准走门面 | 门面唯一 import 点 + §2.3 三道守卫 | 否 |

⇒ 就**"skill 专用"这一层**而言，四条铁律全部住在模块内部或登记表里、域外无从违反 ⇒ 结构即防线，**不单独立条**。
⇒ 反过来说：若哪天出现"域外绕过门面"的**复现证据**，那时再按第 ⑤ 问补机器闸（优于补 ADR）。

> 注：这**不是**"只用一次所以不写 ADR"——⓿ 问的判据是"涉及几个面"（本方案涉及前端/后端/云同步/文档 ≥5 面，够格）。

**⚠️ 2026-09-21 修正（用户裁定）**：上表只否掉了"**skill 专用** ADR"，而**它背后的判据是通用的** ——
「新增一类用户数据时，根放哪 / 真相源是谁 / 身份怎么定 / 上不上云与加不加密」这套四问，换一个项目、换一件事
（剧本工程、素材、设置、以后任何数据域）**还会再遇到**。故判据已上升为 **`ADR-0056 · 新增一类用户数据的四问`**，
本方案（skill）降为它的**首个落地实例**。§1.1.1（技能库根独立于 uploads）与 §0.1 铁律③（正文上云不加密）
都是 `ADR-0056` 在 skill 上的取值，**冲突时以 ADR-0056 为准**。
