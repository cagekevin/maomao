## 一 · 最优解（一屏）

**要建的是一套体系，不是一次搬迁。**

| 件 | 落点 | 作用 |
|---|---|---|
| **落点** | `localTool/runtime-models/<modelId>/` | 一个模型一个目录，一个地方看全部 |
| **清单** | `<modelId>/MANIFEST.json` | 每个模型自述（文件 / 体积 / sha256 / 来源） |
| **取件** | `localTool/scripts/runtime-model.mjs` | `list` 看全部 · `init` 接管下载好的文件 · `doctor` 排查 |
| **宿主** | `/models/<modelId>/*` → `runtime-models/<modelId>/` | 浏览器按 URL 取模型文件 |
| **入口** | `POST /api/local-infer` | `backend` 类能力的统一入口（**等第一个 backend 能力落地时再建**） |
| **前端** | `localInfer('<capabilityId>', payload)` | 一次 POST，前端不知道模型在哪 |

**真相归谁**：文件事实 → 磁盘（`list` 现算）· 能力事实 → 后端枚举 · 落点规则 → `.gitignore`。

## 二 · 体系长什么样

### 2.1 落点

```
localTool/runtime-models/
  <modelId>/
    MANIFEST.json     ← 入库
    README.md         ← 入库
    …其余文件          ← 不进 git
```

**入库规则一条**（`localTool/.gitignore`）：

```gitignore
runtime-models/*/*
!runtime-models/*/MANIFEST.json
!runtime-models/*/README.md
```

**除清单与说明外，全部不进 git，无例外。** 新增模型零配置。

> **为什么全部不进**：换机一年一次，从网盘拉一次即可。为"clone 即有"而让一部分进 git，会引入"两类模型"的分支 —— 那正是"乱"的来源。

### 2.2 清单（`MANIFEST.json`）

> **本节已按实测回填**（2026-09-24 · 复检 TD-08-72）：原先写的是**目标 schema**（`modelId` / `purpose` / `path` 相对 `<modelId>/`），
> 与 `fetch-runtime-models.mjs` 实际消费的**既有 schema 不兼容** ⇒ 新模型照原稿写清单会接不上。以下为**当前真实形状**。

```jsonc
{
  "tool": "matting",                        // ★ = 目录名（即模型 id）。既有键名，非 modelId
  "runtime": "backend",                     // browser | backend | static
  "description": "AI 抠图：去背景，输出透明 PNG",   // ★ 非 purpose
  "generatedAt": "2026-09-24",
  "sourceNote": "……",                        // 可选：说明为何 source 为空
  "files": [
    {
      "path": "matting/rmbg-1.4.onnx",      // ★ 相对 localTool/runtime-models/（**含 <modelId>/ 前缀**）
      "size": 184549376,
      "sha256": "…",
      "source": "https://huggingface.co/briaai/RMBG-1.4/resolve/main/onnx/model.onnx"  // 无可直取 URL 时写 ""
    }
  ]
}
```

- **两个 id 别混**：`tool`（= 目录名 = 模型 id）与 `capabilityId`（`localInfer` 的参数）。现在一对一，多对多时靠 `META.modelId` 指向。
- **`source` 为空串** = 无可稳定直取的单文件 URL ⇒ 还原走网盘镜像（`aliyun-models.py`）。
- **sha256 不手算**：`runtime-model.mjs init <modelId>` 扫目录生成骨架，你只补 `description` 与 `source`。
  **以它生成的形状为准**（它就是上表形状）。

**为什么沿用既有键名与 path 基准（不改成原稿的目标形态）**：改成 `modelId` + 相对 `<modelId>/` 需要
① 迁移 depth-video 的 22 条 `path`、② 改 `fetch-runtime-models.mjs` 的 `path.join(ROOT, f.path)` 与镜像剥离逻辑
—— 违反 §4「depth-video 零改动」，收益只是命名更好看 ⇒ **不做**（`ADR-0016`）。此差异属**有意分缝**，见区域日志 §五。

### 2.3 获取（三条路，全部**离线优先**）

| 场景 | 命令 |
|---|---|
| 接管一个刚下载的文件 | `node localTool/scripts/runtime-model.mjs init <modelId> --from ~/Downloads/x.onnx` |
| **一次还原全部模型**（换机就这一条） | `python localTool/scripts/aliyun-models.py download all` |
| 从网盘还原单个 | `python localTool/scripts/aliyun-models.py download <modelId>` |
| 从镜像/CDN 拉（**换机期**，非运行时） | `node localTool/scripts/fetch-runtime-models.mjs <modelId>` |
| 上传网盘 | `python localTool/scripts/aliyun-models.py upload <modelId>` |

> **机制说明给人的那一份 = `localTool/runtime-models/README.md`**（AI 打开该目录即见；含"装新模型 4 步"与"一次全部同步"）。

**下载/还原后必须跑 `--check`** —— 这是"文件损坏"的唯一防线，**先验过再用**。

> **运行时零联网**（`TD-08-26` 已裁定）：加载器不得联网拉模型。缺模型 ⇒ 明确报错 + 指路，**不自动下载**。

### 2.4 后端统一入口（`backend` 类能力）

```
localTool/src/localCapability.ts       ← 能力枚举（新立）
localTool/src/routes/local/<id>.ts     ← 每能力一个 handler
POST /api/local-infer                  ← 统一入口（body.capability 分流）
GET  /api/local-infer/status           ← 各能力此刻可用性
```

**枚举机制照抄 `RelayCapability` 的优点**（但**不复用它的成员** —— 它是 relay 任务模态，判据不同）：

```ts
export const LOCAL_CAPABILITIES = ['super-res', 'matting'] as const;
export type LocalCapability = (typeof LOCAL_CAPABILITIES)[number];

// ★ 这张表才是穷尽保证：加成员不加它 = 编译报错
export const LOCAL_CAPABILITY_META: Record<LocalCapability, {
  runtime: 'browser' | 'backend' | 'static';
  modelId: string;
  timeoutMs: number;
}> = { … };
```

**前后端各一份 id 集合，由 `check-arch` 的 `CROSS_STACK_UNIONS` 对账**（**须新增一项**，否则对账不存在）。

### 2.5 前端怎么用（两行）

```ts
const { ok, data } = await localInfer('matting', { image: dataUrl });
if (ok && data?.image) onImageReplaced(data.image);
```

返回形状**与模态无关**（图 / 文本 / 音频都装得下）：

```ts
{ ok: boolean; data?: { image?: string; text?: string; audio?: string }; error?: string }
```

**前端不需要知道**：模型在哪、装没装、谁加载、超时多少、用的什么框架。
**"有哪些能力"（编译期枚举）与"此刻能不能用"（运行期 `status`）是两件事**，不许混。

### 4.1 搬迁清单（**确定动作**，非待定）

| 搬什么 | 从 | 到 | 要改的加载点 |
|---|---|---|---|
| MediaPipe 视觉（21 MB） | `public/mediapipe/` | `runtime-models/mediapipe/` | `image/lib/faceMosaic.ts:74,77` 的 `resolveAsset()` |
| 3D 模型（8.8 MB） | `public/models/` | `runtime-models/three/` | `director3d/models.tsx:83` 的 `BUILT_IN_MODEL_URL`（**修订**：原写 `models.jsx:12`，已过时） |

**已知代价（实测 · 用户已裁定接受，见 §十）**：搬走 `public/mediapipe/` 与 `public/models/` 会**破坏 Chrome 扩展形态**：
- `public/manifest.json:50-51` 把 `mediapipe/*`、`mediapipe/wasm/*` 声明为 `web_accessible_resources`（指向**扩展包内**）；

⇒ **Web 形态（dev / localTool 18080 托管）不受影响**（见 §六 处置）；扩展形态的人脸打码与内置 3D 人物在搬迁后不可用，**属有意代价**。

**顺手清理**：
- `xbot-animated.glb`（3.7 MB）—— **死文件**（50 号已证：代码零引用，注释承诺的"回退"实际走胶囊体）⇒ **不搬，删**。

**搬完的收益**：① 落点统一，一屏看全；② `dist/` 不再多一份 21 + 8.8 MB 副本；③ **关掉一个潜伏的坑** —— `public/mediapipe/vision_wasm_internal.js` 现在**已在 git 里**，哪天被改动并 `git add`，pre-commit 的 lint-staged 就会拿 eslint + prettier 解析它（搬走后整目录不进 git，坑从根上消失）。

错误透传本仓**已有完备判据**，本体系**不另立**：

| 只有网络错误才能重试 | `ADR-0018` |

**本体系只新增两条**：

### 5.1 失败分类用 HTTP status（不扩枚举）

后端 `sendError(res, message, status, code?)` 的 `code` 位复用 `GEN_ERRORS` 五值 —— 本地推理的失败**一个都套不上**（不是网络问题）⇒ **用 status 分类**：

| status | 含义 | 判定依据（**确定**） |
|---|---|---|
| `404` | 模型文件不存在 | `ENOENT` |
| `503` | 推理依赖未安装 | `ERR_MODULE_NOT_FOUND` |
| `422` | 输入不合法 | 入参校验失败 |
| `504` | 超时 | 超 `timeoutMs` |
| `500` | 推理失败 | `session.run()` 抛，**原始 message 原样透出** |

**"文件损坏"归获取阶段**（`--check` 的 sha256），不在此列；**"内存不足"归环境**，不在此列。

### 5.2 日志锚点

失败时 `console.error('[local-infer]', { capabilityId, modelId, stage, error })`，`stage` ∈ `resolve-manifest` / `load-module` / `load-model` / `run`。

走 `console.error` 而非 `logDebug`（后者默认关闭，自述是给"成功路径的细节"用的）⇒ 默认落盘 + 默认推前端日志面板。
**用户看到 `404` 知道方向，AI 看日志知道细节。**

## 六 · dev 同源问题：**已定 + 动作**（原「待实测」已消解）

**原问**：dev 模式下（vite 5180）跨源取 `runtime-models/` 的文件，MediaPipe 的 `FilesetResolver` 是否要求同源**未验证**。

**处置（确定动作）**：**不给跨源机会** —— 给 `vite.config.ts` 的 `server` 加 `/models` 与 `/depth-video` 两个 proxy 到 `127.0.0.1:18080`，使 dev 与 prod 都保持**根相对、同源**。

**理由（不是偏好，是已有实证）**：
- `depthUrls.ts:29-38` 已记载**同源铁律**：用绝对 URL 让 transformers.js 加载模型会**静默失败**（`this.processor is not a function`），改根相对即恢复。
- prod 下前端页面本身就由 localTool 18080 托管（`index.ts::handleFrontendPage` 从 `dist/` 读）⇒ `/models/*` 与页面**天然同源**，零额外配置。
- dev 下 vite 只托管 `public/`，`/models/*` 无宿主 ⇒ 若不 proxy，要么 404、要么落到 SPA 兜底返回 HTML（**假成功式的静默坏**）。
⇒ 因此 proxy 是让"dev 也同源"的**唯一不引入第二套 URL 口径**的做法；MediaPipe 是否强要求同源**无需再验证**（我们不再跨源）。

> 附带收益：`/depth-video` 一并 proxy ⇒ dev 下深度视频链路同样保持根相对，不再依赖"绝对 URL + CORS"，与生产口径一致。
