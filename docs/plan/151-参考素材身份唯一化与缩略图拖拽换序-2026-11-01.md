## 0. 结论先行

1. **拖拽对象是「参考素材缩略图条」**（`ResourceStrip.tsx`，151 行，17 处 import），不是主生成结果
   （主图框只渲染单张 `data.assetUrl`，`ImageGenerate.tsx:719-760`）。
2. **身份被拼成 5 个阶段 / 18 处**：① 诞生 ② 传递（前缀叠加 + 下标兜底）③ 持久化（id 写进
   `data.prompt`，跨会话存活）④ 判同（两套不同判据）⑤ URL 形态（dataURL → `/files/<sha1>` → 绝对 URL）。
3. **最致命不是"拼得乱"，而是"改 id 会静默弄坏存量数据"**：
   `data.prompt` 里已持久化**位置 id**（`@{img-0:…}`），而 `resolvePromptChips` 对查不到的 id
   直接 `return ''`（`promptChips.ts:298`）；`renderPromptToNodes` 却有 thumb 兜底（照常显示）
   ⇒ **界面芯片正常、发送时参考图凭空消失、零提示**。这是**已存在的 bug**，不是本计划引入的。
   ⇒ **必须先做第 0 步**（thumb 兜底），它同时是独立 bug 修复 + 后续所有 id 变更的安全网。
4. **顺序键必须是「诞生时生成、落盘后不变」的真 UUID**，不能是下标、不能是 url 哈希
   （`persistInlineOrKeep` `filesApi.ts:441` + `toAbsoluteFileUrl` `utils.ts:33` 会让 `hash(url)` 每跳都变）。
5. **「图片 N」的三套编号互不一致（既存）**，且真正决定模型看图序的是**发送数组**
   `mergeReferenceImageUrls(chipImages, upstreamImages)`（**芯片图在前**，`promptChips.ts:315` 明写「勿改」）。
   ⇒ 要让「图片 N = 缩略图第 N 个」，**必须让发送数组也按顺序表构造**，编号 = 该数组下标。
   **这是本计划唯一的语义级决策，已由用户点头（2026-11-01）**，见 §8.1。
6. **三步改五步**：第 0 步（thumb 兜底）→ 第 1 步（唯一身份原语，不碰数据结构）→
   第 2 步（物化 id）→ 第 2.5 步（复制/粘贴重开身份）→ 第 3 步（拖拽 + 指代同步）。
7. **每步可独立提交**，每步收尾都是「0 错 + 相关单测绿 + build 过」；
   全量测试只在验收时**申请后**跑（CLAUDE.md §3.0.1）。
8. **验收判据必须能真跑**：本版 §9 三条原假绿/不可满足的判据（A3/A5/A7）已修正为实测可跑的命令。

## 2. 六条硬规则（施工时对号入座）

| # | 规则 | 判据 | 违反的写法 |
| --- | --- | --- | --- |
| R1 | **生成只在诞生点，且必须落盘** | 写 `makeImageId()` 前问：这个 id 会不会进 `node.data`？不会 ⇒ 不许生成 UUID | 读取路径 `makeImageId()` |
| R2 | **身份键 = id 优先，退化键 = 内容派生，永不下标** | 任何 `id ?? \`xxx-${i}\`` / `${images.length}` | 下标、长度、遍历序号 |
| R3 | **判同只有一个实现** | 去重/建表一律走 `imageKeyOf` | 各写一套 `id ?? url` / 只按 url |
| R4 | **复制 = 新实例 ⇒ 必须重开身份** | 复制/粘贴/派生的节点，`data.images[].id` 与 `data.prompt` 里的 `@{id}` 必须重新生成 | `{...n.data}` / `deepClone(x.data)` 原样带 id（§11.4） |
| R5 | **位置指针必须按 id 重映射** | 换序后 `activeIndex` 类字段一律「取原 id → 新数组 findIndex」 | `activeIndex: merged.length - 1` 式（§11.5） |
| **R6** | **改持久化 id 之前，先证明"失配不会静默丢数据"** | 任何 id 格式变更前，必须先用 grep 证明「查不到 id 时的分支不是静默丢弃」 | 直接改 id 格式（实证：`promptChips.ts:298 return ''` + 界面照常显示） |

**R2 的退化键**：`imageKeyOf(item)` 在 id 缺失时返回 `img_<hash(url)>`（**冒号必须替换**，
否则撞坏芯片格式 `([^:]+)`）。它**不是身份**，只保证「同一 url 得同一键」。
**撞键风险（R2 新增）**：同内容两帧（抽帧静止画面）会得同一键 → `mergeRefImages` 合并成 1 张。
故退化键只允许存在于**读路径**，且必须显式接受"同内容合并"语义（见 §6.2-2-4）。

## 8. 第 3 步 · 拖拽换序 UI + 发送数组同源

### 8.1 语义决策（**用户已点头 2026-11-01**）

> **问题**：真正决定模型看图序的是发送数组
> `mergeReferenceImageUrls(chipResolved.refImages, refImages)`（`promptChips.ts:326`，**芯片图在前、上游在后**，
> `:315` 明写「顺序语义（勿改）」）；而缩略图条顺序来自 `refImages`。
> **两者天然不同**：只 @ B 时发送数组 = `[B, A, B]→[B, A]`，模型看到 `[img=图片1]`=B，
> 而缩略图第 1 个=A。**这是既存错位，与第 3 步无关。**
>
> **决策**：**发送数组改为按 `imageOrder` 顺序表构造**，`[img=图片N]` 编号 = 该数组下标。
> ⇒ 「图片 N」在缩略图、@弹层、发送数组三处**同源**。
> ⚠️ 这会**推翻** `promptChips.ts:315` 的「芯片图在前、上游图在后」，该处注释必须同步改写
> 并注明「2026-11-01 用户裁定，见 docs/plan/151 §8.1」。
