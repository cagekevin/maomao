# 素材「label 范式」改造方案（提案 · 待拍板）

> **状态**：⏸ 待用户确认后实施（本文档只是方案，未改任何代码）。
> **关联**：`daily/架构日志/02-存储-持久化-六轮-低息清偿与普查-2026-09-12.md` §8.3（架构评估）、TD-02-13/14（本方案使其**消失**而非修复）。
> **一句话**：把素材库改成和**节点**一样的身份模型——**编号是身份证（永不换），label 只是标签（随便改）**。改完后，"给素材改名/挪分类"从牵动 8 处机制，变成改一行记录。

---

## 一、为什么要改（现状的问题，用一个例子讲清）

现在上传一张图，它的"地址"里包含**文件名和目录**：

```
地址 = /files/migrated/人物/主角立绘.png
                     ↑目录    ↑名字（都会被用户改）
```

画布节点、任务列表、其他窗口，记的都是这个地址。于是当你在素材库里**改个名**：

| 步骤 | 谁在做 |
|---|---|
| 1. 磁盘文件真的改名 | 后端 `fs.renameSync` |
| 2. 扫全库把记着老地址的地方改掉（含中文编码 4 种形态） | 后端 `rewriteUrlReferences`（kv 全部 value + tasks 10 个列） |
| 3. 素材表的行删掉重建（否则收藏丢失 / 重复录入） | 后端 `applyResourceIdentityChange` |
| 4. 通知前端"地址变了" | `resource:renamed` 事件（contracts 登记 + check-events 护栏） |
| 5. 前端改当前画布/脚本箱节点里的旧地址 | `useAssetUrlRewrite`（App 订阅） |
| 6. 前端改内存任务列表里的旧地址 | `taskStore` 订阅 |
| 7. 前后端各维护一份"地址改写规则"，靠注释保证一致 | `buildUrlRewritePairs` / `replaceUrlDeep` |
| 8. 防止两个窗口互相覆盖 | 版本号 CAS——但第 2 步**忘了推版本号**（已登记 TD-02-13），且改写失败前端毫不知情（TD-02-14） |

**根因**：名字是给人看的、会经常改；但系统把名字当成了文件的"身份证号"（地址和 id 里都含名字）。于是"改个名"= 换身份证 = 所有可能记着它的人都得重新登记。

---

## 二、目标方案：照搬节点 already 跑通的范式

节点体系从来没用过"文件名当身份"，所以节点改名从来没有这些麻烦：

| | 节点（现范式，✅ 已验证） | 素材库（现状 ❌） | 素材库（改造后 ✅） |
|---|---|---|---|
| 身份（永不换） | `node.id` | `local-<目录>-<文件名>`（跟着改名变） | `local-<内容编号>`（永不换） |
| 显示名（随便改） | `data.label` | `resources.name`（改它得连磁盘一起改） | `label`（只改这一行字） |
| 文件地址（永不换） | `data.assetUrl` | `/files/<目录>/<文件名>`（含名字） | `/files/<来源目录>/<内容编号>.png` |

改造后，"改名 / 挪分类"= **改一行记录**：

```sql
UPDATE resources SET label = '女主.png', folder = '人物' WHERE id = 'local-a3f9c2e1…';
```

文件不动、地址不动 → 画布、任务、其他窗口**什么都不用做**。上表 8 步里的 **2/3/4/5/6/8 共六处机制整体删除**（不是修好，是不再需要）。

**顺带统一（你提的 label）**：节点叫 `label`、素材表叫 `name`——同一个概念两个名字。本方案统一叫 `label`，人和 AI 都少一层翻译。

## 三、改造后用户看到的变化（如实列出）

| 场景 | 改造前 | 改造后 |
|---|---|---|
| 软件里的素材名/分类 | ✅ 不变 | ✅ 不变（还是中文，还是你改的名字） |
| **下载到本地**的文件名 | 取自显示名 | ✅ 不变（仍用 label 当文件名，节点已有现成机制） |
| 右键"打开所在目录" | 打开磁盘目录 | ✅ 仍可用（地址规则没变，只是文件名变编号） |
| **磁盘文件夹里** | `migrated/人物/主角立绘.png` | `migrated/a3f9c2e1….png`（无中文名、无分类子文件夹）⚠️ |

⚠️ 这一格是**唯一的取舍**：素材的"分类"变成软件里的元数据视图，磁盘上不再有「人物/」这样的中文文件夹。**这是需要你拍板的点**（见 §七）。

## 四、实施计划（三阶段，每阶段独立提交、可单独回滚）

### 阶段一：新落盘统一用"内容编号"命名（后端一处）

- **做什么**：multipart 直传的命名从 `${时间戳}-${文件名}`（`fileStore.ts::writeUploadBuffer`）改为内容编号（sha1 前 16 位 + 扩展名）。后端**已有现成实现**：`saveBase64ToFile`（base64Externalize.ts:60，sha1 幂等去重）和稳定名落盘 `writeUploadBufferAt`——本阶段只是把三条落盘链路的命名**收敛成一条**（base64 / multipart / 远程下载统一 sha1）。
- **为什么安全**：sha1 幂等去重是既有惯例（重复内容不重复落盘）；来源目录（tasks/web/canvas/migrated/director3d）**保持不变**，符合 `UPLOAD_DIRS` "目录名一律不改，防存量 URL 破链"的既有红线。
- **验收**：同一张图传两次 → 同一地址（去重）；新落盘地址形如 `/files/tasks/<sha1>.png`；存量老地址全部照常可访问。

### 阶段二：改名/挪分类 = 纯元数据（删六处机制）

- **后端**：`handleResourcesRename` / `handleMove` 不再动磁盘，改为 `UPDATE resources SET label=?, folder=?`；id 规则改为稳定（编号文件 `local-<sha1>`；存量名字型文件维持旧 id 不动，零迁移）；返回值不再需要地址变更语义。
- **前端**：删除 `resource:renamed` 事件 + 两个订阅方（App 改写节点 / taskStore 改写任务）+ 前端那份四态改写函数；素材面板改名/拖拽移动改为直接用返回的新 `label/folder` 更新列表。
- **登记表**：EVENTS 摘除 `resource:renamed`；`check-events` / `check-node-data` 随迁。
- **验收**：改名后画布上的图**瞬间依旧正常**（地址没变）；两个窗口同时开，A 改名 B 不受任何影响；rescan 不重复录入；收藏（is_favorite）天然保留（行不再重建）。

### 阶段三（可选，默认不做）：存量文件物理归一脚本

- 旧的"名字型"文件**可以一直用下去**（地址稳定，不受影响），所以这一步**非必需**。
- 若希望磁盘也整洁，提供一个手动脚本：把存量文件改名为编号 + 一次性改写库内引用（复用现成的 `rewriteUrlReferences` + 补推版本号）。
- **推荐**：不做。让存量自然淘汰，系统里两种地址形态并存没有危害。

## 五、影响面盘点（实数，已逐一核实）

| 位置 | 改动 |
|---|---|
| `localTool/src/utils/fileStore.ts::writeUploadBuffer` | 命名改 sha1（1 处） |
| `localTool/src/routes/resources.ts`（rename/move 两 handler + `applyResourceIdentityChange`） | 大幅简化：删磁盘操作与引用改写；`resourceIdOf` 改稳定规则 |
| `localTool/src/db/database.ts::rewriteUrlReferences` | app 内不再调用；保留给阶段三可选脚本（标注"外部破坏修复用"） |
| `src/components/base/api/filesApi.ts` | 无需改（透传）；`relativePathFromUrl` 仅 2 个调用点（"打开所在目录"），地址规则未变 → 不受影响 |
| `ResourceLibrary.tsx` / `GeneratedView.tsx` / `useResourceMoveToFolder.ts` | 删 `publish('resource:renamed')`，改用返回的 `label/folder` |
| `useCanvasEventSubscriptions.ts` / `taskStore.ts` | 删订阅 |
| `contracts.ts` EVENTS | 摘除 `resource:renamed` |
| 下载命名 | 素材下载调用点改为传 `label`（机制已有） |

**不做的事**（防过度设计）：不引入"引用注册表/引用计数"；不做 `url` 代理层（`/files/id/<id>`）；不改 `UPLOAD_DIRS` 目录名。

## 六、风险与回滚

- 每阶段独立 commit；阶段一、二互不依赖先后？**有依赖**：必须先①后②（否则新文件还是"名字型"，纯元数据改名对它无效）。回滚 = revert 对应 commit，无数据迁移、无破坏性 schema 变更。
- 数据库：**列名保留 `name` 不改**（推荐），只在代码与接口层统一叫 `label`——避免一次 schema 迁移风险；若你希望连列名也统一，可加一条 `ALTER TABLE RENAME COLUMN`（sql.js 支持，但多一个迁移面）。
- 外部破坏（你绕过软件、直接在文件夹里改名/移动文件）：rescan 会重建记录，但**画布里引用的旧地址会断**——这是现状既有行为，本方案不变也不新增处理（可后续单独立项）。
- 红线遵守：不动 director3d 本体；`UPLOAD_DIRS` 目录名不改；所有 node.data 写回走既有唯一入口。

## 七、待你拍板的 3 个问题

1. **磁盘形态**：接受"磁盘里是 `migrated/a3f9c2e1….png`，中文名和分类只在软件里显示"吗？（本方案唯一的取舍）
2. **命名统一层级**：只统一到代码/接口层的 `label`（推荐，零迁移），还是连数据库列名一起改成 `label`？
3. **阶段三**：默认不做（推荐），还是要一次性物理归一脚本？
