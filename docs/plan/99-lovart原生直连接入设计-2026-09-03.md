# lovart 原生直连接入设计（relay 摆脱 9004 翻译层）

> 状态：**定稿（State 1 文件安置 + State 2 数据流契约已确认，待施工）**。方向已确认：relay 的 lovart 直连 Lovart 原生 agent 协议，摆脱 9004 的 /v1 OpenAI 兼容翻译层。
> 依据：`.codebuddy/skills/lovart/agent_skill.py`（真源协议）+ `apimart-gateway/lovart_client.py` + 既有 `localTool/src/ai-relay` 源码（`providerCatalog.ts` / `protocol/` / `httpTransport.ts` / `generate.ts`）。
> 本文把原生协议契约、与 ai-relay 引擎模型的差异、**已定的接入形态（providers/lovart 命令式 adapter + 双轨）、文件安置（State 1）、数据流契约（State 2）** 落成施工蓝图；**不改代码**。

## 0. 结论

Lovart 原生协议是 **chat-thread 型**（chat→thread_id→confirm(可选)→result.items[].artifacts[].content），
**不是** ai-relay 现成的「submit 拿 task_id → 轮询 statusPath → result.urlPath」二态模型。

**已定决策（取代原 §3 的 A/B 二选一）：建 `localTool/src/ai-relay/providers/lovart/` 命令式 adapter 包裹声明式引擎——既不硬改 kit 引擎核心（避 A 的改动面），也不绕开中央稳定传输（避 B 的"绕 kit"红线）。** adapter 复用 `httpTransport.stableRequest` 做 HMAC 传输，是 ai-relay 里首个 pre/post-flight 命令式 provider，对外只暴露单一入口，经 `index.ts createRelay` 分流。

**双轨策略**：保留 `lovart`（baseUrl=9004，走既有声明式引擎）作回退；新增 `lovart-direct`（baseUrl=`https://lgw.lovart.ai`，走本 adapter）。跑通后删 `lovart`(9004)。两轨共用同一模型清单 `manifests/lovartModelManifest.ts`（6 image / 5 video / 1 chat）。

## 1. Lovart 原生协议契约（来自 agent_skill.py）

### 1.1 鉴权（HMAC-SHA256，非 Bearer）
Header：
```
X-Access-Key: <AK>
X-Timestamp:  <unix秒>
X-Signature:  hmac_sha256(secret, "{METHOD}\n{path}\n{ts}").hexdigest()
X-Signed-Method: METHOD
X-Signed-Path: path
Content-Type: application/json
User-Agent: LovartAgentSkill/1.0   (附 Referer: https://www.lovart.ai/ 下载时)
```
base = `https://lgw.lovart.ai`（LOVART_BASE_URL），path 前缀 `/v1/openapi`。

### 1.2 端点
| 动作 | 请求 | 返回 |
|---|---|---|
| 提交 | `POST {prefix}/chat` body `{prompt, project_id, attachments?, thread_id?, mode?, tool_config:{prefer_tool_categories?, include_tools?, exclude_tools?}}` | `thread_id` |
| 状态 | `GET {prefix}/chat/status?thread_id=` | 状态（running/done/abort/pending_confirmation/...） |
| 结果 | `GET {prefix}/chat/result?thread_id=` | `{ items:[{type, text?|artifacts:[{type,content}]}] }` |
| 确认 | `POST {prefix}/chat/confirm` body `{thread_id}` | 确认高成本操作（video fast） |
| 上传 | `POST {prefix}/file/upload`（multipart） | `data.url` |
| 模式 | `POST {prefix}/mode/set|query` | — |

信封：响应顶层 `{code, message, data}`；`code==0` 成功，取 `data`。

### 1.3 状态机（final_status）
`done`（取 result） / `pending_confirmation`（先 confirm 再取） / `abort` / `timeout` / `running`。
高成本操作（如视频）在 fast 模式可能进 `pending_confirmation` → 需 confirm，然后继续轮询。

### 1.4 提交语义（关键差异）
- body **没有 model/size 字段**——模型靠 prompt 自然语言 + `tool_config.prefer_tool_categories`（如 `{"IMAGE":["generate_image_gpt_image_2"]}`），尺寸靠 prompt（target_size 文本）或网关侧归一。
- 产物是**多类型列表** `items[].artifacts[]`（可能图片+视频+文本回复混排），非单个 url。

## 2. 与 ai-relay 现有引擎模型的差异（为什么不能直接套）

ai-relay `ModelProtocol`（sync/async 二态）：
- async = `submit(拿 taskIdPath) → poll(statusPath/successValues/result.urlPath)` → 单组 url/text。
- 引擎假定「提交响应含可轮询 task_id」且「终态轮询同一 URL 得结果」。

Lovart 原生：
- 提交是 **chat**，拿的是 **thread_id**（多轮会话句柄，非一次性任务）；
- 有 **confirm** 前置门（pending_confirmation）——ai-relay 无此概念；
- 结果在 **result** 端点（与 status 不同端点），且是**多类型 artifacts 列表**；
- 状态 done 后可能需「等子 agent 起跑再复核」（agent_skill 的 5s 复核），防 video 子任务误判 done。

→ 直接硬塞进现有 `ModelProtocol` 的 statusPath/result.urlPath 会失真（无法表达 confirm / 多 artifacts / chat 多轮）。

## 3. 接入形态（已定稿：方案 C = providers/lovart 命令式 adapter）

原 A/B 二选一已收敛为 **方案 C**，理由与取舍：

| 维度 | 方案 A（引擎抽象 agent-thread） | 方案 B（relay 独立客户端） | **方案 C（providers/lovart adapter）✅ 已定** |
|---|---|---|---|
| 是否改 kit 引擎核心 | 改（增形态+confirm 门+多 artifacts 抽取） | 不改 | **不改**（引擎零改动） |
| 是否复用中央稳定传输 | 是 | 否（自写 HTTP 循环，触 C0 红线） | **是（`httpTransport.stableRequest`）** |
| HMAC 鉴权落点 | 引擎内 `resolveAuthentication` | 自写 | **`httpTransport.AuthConfig` 加 `hmac` 分支（中央可复用）** |
| pre/post-flight（project/附件/prompt 工程） | 需给引擎加钩子，改动面大 | 自由写 | **adapter 内聚，单向叶子** |
| 风险隔离 | 低（动全局） | 高（绕 kit） | **中（隔离在 provider 内，传输靠中央）** |
| 后续 chat-thread 平台复用 | 通用 | 不复用 | 复用 `providers/` 模式（非协议形态） |

**方案 C 实质**：在 `ai-relay` 顶层新增 `providers/` 目录（首个常驻实例），`lovart` 子模块把 `agent_skill.py` 原语 port 进 `lovart_client.ts`，用 `httpTransport` 发请求；`index.ts createRelay` 按 `providerId` 分流（双轨）。声明式引擎 `executeModelProtocol` 对本直连零改动——它只服务 `lovart`(9004) 那条旧轨。

> 不进引擎的根因：Lovart 直连需要 pre-flight（project 创建+缓存+失效自愈、`set_mode(fast)` 配额锁、URL/base64→字节→CDN 上传、`build_gen_prefix` 双路选模型）与 post-flight（SSE 合成、AUTO_CONFIRM、task_view 整形），而 `ModelExecutionProtocol` 是「submit→poll→result」无钩子模板，表达不了这些。给引擎加钩子改动面过大，故独立 adapter 更划算。

## 4. key 来源
直连原生需 `LOVART_ACCESS_KEY` + `LOVART_SECRET_KEY`（现仅存于 `apimart-gateway/.env`）。
localTool 侧需把这对 AK/SK 读入（新增 `LOVART_ACCESS_KEY`/`LOVART_SECRET_KEY` 到 localTool .env 或读取网关 .env），
供 HMAC 签名。key 仍只驻内存/进程内，不入库。

## 6. State 2：数据流契约（链路 / 唯一入口 / 避交叉）

### 6.1 入站链路（canvas → relay）
```
canvas/前端
  └─ relay.createRelay({ providerId:'lovart-direct', apiKey, baseUrl:'https://lgw.lovart.ai' })
       └─ relay.generateImage / generateVideo / streamChat   ← index.ts 单一分发点
            └─ [if providerId==='lovart-direct'] → providers/lovart 适配层
            └─ [else] → executeModelProtocol（既有，含 lovart@9004 旧轨）
```
**唯一入口 = `index.ts` 的 `createRelay`**。它本来就是 provider 感知边界（`config.providerId` 在此可见），在此分流最干净，不污染 `generate.ts` 模态层。

### 6.2 适配层内部链路（单向、可追溯）
```
providers/lovart/index.ts  ── 对外只暴露 3 函数 + 1 入口
   generateImageLovart({model,prompt,size,imageUrls,n,signal})
   generateVideoLovart({model,...})
   streamChatLovart({model,messages,signal}) → 返回 SSE ReadableStream

   ├─ lovart_contract.ts     normalize_body()          字段别名 + metadata 提升（§2.9.2）
   ├─ lovart_prompt.ts       buildGenPrefix() + 双路选模型（自然语言路：instruction 写模型名）
   ├─ lovart_attachments.ts  resolveAttachments()       URL/base64→字节→CDN（§2.3，失败即阻断）
   ├─ lovart_project.ts      ensureProject(accessKey)   按 AK 缓存 Map + 失效自愈重建（§2.9.1 #6）
   ├─ lovart_client.ts       set_mode(unlimited=False)  配额轴锁 fast（必显式，§2.5）
   │                  send(prompt, project_id,
   │                       tool_config={prefer_tool_categories:{IMAGE:[tool]}})   结构化路选模型 + 推理轴
   ├─ lovart_task.ts         poll(thread_id) + AUTO_CONFIRM confirm + pending_confirmation 读取
   │                  → task_view 整形（{urls}/失败 no_artifact/abort）+ 总超时（withTimeout）
   └─ lovart_errors.ts       lovart_err_response() 信封（_LOVART_ERR_TYPES，原样透传上游文案）
        └─ lovart_stream.ts（仅 chat/可选 ?wait=1）合成 OpenAI chat.completion.chunk SSE
```

### 6.3 出站到上游（复用稳定传输）
`lovart_client.ts` 所有 HTTP → **复用 `httpTransport.stableRequest`**（baseUrl 候选 / 重试 / 64MB 上限 / 可取消 / 上游文案原样透传，全现成）。
- **HMAC 头归属**：`httpTransport.AuthConfig` 加 `type:'hmac'` 分支（`buildAuthHeaders` 收 `accessKey/secretKey/method/path`），`stableRequest` 每次重试 attempt 内重算 `_sign`——把 `authHeaders` 计算移进 attempt 循环。Lovart-direct 保持薄，未来任意 HMAC provider 受益。
- 信封 `{code,data}` 剥离：**留在 `lovart_client.ts`**（忠实 port `agent_skill.py._request`），不放通用中央解析器。

### 6.4 回流到 canvas（对齐既有接口，外层零改）
- image/video（阻塞轮询）：`task_view` → `generateImageLovart` 返 `string[]`、`generateVideoLovart` 返 `{url}` —— 签名与现有 `generate.ts` 完全一致。
- chat（流式）：`lovart_stream.ts` 产 `ReadableStream`（OpenAI chunk SSE）→ 交回 `generate.ts` 的 `parseStream`(`assistantStream.ts`) → `AssistantStreamEvent[]` —— 复用既有 SSE 解析器。
- 错误：信封 → 抛带原始 message 的 `Error`/`RelayHttpError`，按 httpTransport 契约"上游显示啥就显示啥"透传，**禁翻译/静默**。

### 6.5 中央契约常量（登记，不裸字面量）
- `LOVART_DIRECT_BASE_URL = 'https://lgw.lovart.ai'` → `providerEndpoints.ts`（与 `XAI_BASE_URL` 同列）。
- provider id `'lovart-direct'` → 注册进 `providerCatalog.ts`（双轨；`lovart`@9004 保留）。
- 模型清单：`manifests/lovartModelManifest.ts` 补成 6/5/1（两轨共用，差异仅在 baseUrl+authType+协议路径）。
- 状态枚举 `completed/failed/processing/pending/abort`：沿用 `presets.ts` 注释铁律 + `protocol/presets.ts` 既有映射（§2.9.7），不新造。

### 6.6 幂等 / 去重 / 超时
- project 缓存：`lovart_project.ts` 模块级 `Map<accessKey, projectId>`（全局唯一键，单次建、失效才重建），**不在每次调用里各建各的**（§2.8 #6）。
- 轮询总超时：`lovart_task.ts` 的 poll 必须有**总 deadline**（CHAT_SYNC_TIMEOUT / 任务上限），复用 `httpTransport.withTimeout`，禁无限挂起。
- 上传失败：`attachments.ts` 任一真实上传失败即 `throw`，**阻断整条请求**，不部分成功继续（§2.3）。

## 7. 风险与红线
- **HMAC 签名**（方法/路径/时间戳）每平台不同，需独立实现，勿当 Bearer 套——落点见 §5.2 `httpTransport` 的 `hmac` 分支。
- **project_id**：Lovart 提交需 project_id（工作区）；relay 由 `lovart_project.ts` 按 AK 缓存+失效自愈持有默认 project（§5.1），不再依赖 agent_skill 的本地 state。
- **pending_confirmation**：video fast 可能触发；`lovart_task.ts` 实现 `AUTO_CONFIRM`（参考 9004 取舍，默认自动 confirm 后继续轮询）。
- **多 artifacts**：一次可能产出多图/图文混排；`generateImageLovart` 返回 `string[]` 承载多产物，`generateVideoLovart` 取视频主产物；前端单 url 节点取首元素（§6.4）。
- **能力零退化**：9004 层现有的 auto_confirm/尺寸归一/参考图透传在直连后由 `providers/lovart` 复刻（§5.1 的 `lovart_task.ts`/`lovart_prompt.ts`/`lovart_attachments.ts`），不得静默丢。
- **模型必显式（用户强约束）**：三功能（chat/image/video）均经 `tool_config.prefer_tool_categories` 显式传模型，结构化路承载 + `build_gen_prefix` 自然语言路冗余兜底，绝不裸发"用默认模型"（研究文档 §2.11）。

### 9.2 B 组：数据流断言（State 2，核心保险）
| ID | 断言 | 验证方法 |

### 9.4 D 组：测试分层建议（落地位置）

> **与仓库实际机制对齐**：localTool 是独立 Node 子项目，单测用 **Node 原生 test runner（`node --test` + tsx）**，非前端 Vitest（Vitest 只服务根 `src/` 前端）。测试落 **`localTool/test/lovart_*.test.js`**，与既有 `relay-lovart-protocol.test.js` 同目录同风格；由 `scripts/run_all_tests.cjs` 门禁统一收编（`node --test` 逐文件展开）。
> **不真打上游**：通过 DI 注入 fake transport（`LovartDirectProfile.transport`）与 fake fetch（`.fetchImpl`），断言请求体而不发真实 HTTP。

- **单测（不改上游）**：`localTool/test/` 下按模块建 `lovart_*.test.js`（node:test + 注入 fake）：
  - `lovart_client.test.js` → B2/B4/B5/B6/B7/B11/B13（fake transport 录请求体断言 HMAC 头 / tool_config / 信封）
  - `lovart_project.test.js` → B3（同 AK 单例 + 失效自愈）
  - `lovart_attachments.test.js` → B8/C2（fake fetch + fake transport：下载/上传失败阻断）
  - `lovart_task.test.js` → B9/B10/B11（fake transport 逐次返回 status；fake timer 测超时）
  - `lovart_prompt.test.js` → B6/B7/C3（纯函数，直接断言字符串）
  - `lovart_stream.test.js` → B12（消费合成 SSE 断言 chunk 形状）
  - `index.test.js` → C1（顶层入口签名 + 返回形状，注入 fake 走全链路）
- **集成 smoke（真打上游，仅直连跑通后）**：`localTool/scripts/` 下对 `lovart-direct` 跑真实 image+video+chat 各一次，验证 end-to-end；**不进单测默认执行**。
- **结构守门（CI）**：A1/A3 用 `grep`/eslint 自定义规则守；A5/A6 用 `providerCatalog`/`providerEndpoints` 单测守（frontend Vitest 域可加，或 grep）。
- **删旧时机断言**：`lovart`(9004) 删除前，需先满足 C4 + 集成 smoke 全绿；删除后 A5 退化为"仅 `lovart-direct` 存在"。
