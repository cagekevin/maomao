## B1 · 契约真源（中央端点登记表 + 静态校验）→ C1

> 根因：前端薄壳无中央端点登记表（§5.4 缺口①），`BACKEND_ROUTES`/`API_ENDPOINTS` 实为字符串占位（缺口⑨）。目标是建成「前端函数 ↔ 后端 route pattern ↔ method ↔ 信封形状」的唯一真源，并程序化互检防镜像错位。

### T1.1 新建 `apiRegistry` 结构化表
- **改动文件**：`src/components/base/contracts.js`（在 `BACKEND_ROUTES` 占位基础上**新建**结构，非升级既有字符串；`BACKEND_ROUTES` 注释已含准清单线索，缺口⑮③ 可迁移填充）
- **字段**：每条端点 = `{ fn, method, path, envelope, status }`
  - `envelope`：`ok` / `code-data` / `items` / `success-data` / `raw` / `stream` / `sse` / `probe` / `stub`（对齐缺口⑪⑭⑲㉑ 的形态分类）

## B2 · 错误信封统一（限非 SSE 域）→ C2 / C3

> 根因：`sendError` 现返 `{error:message}` 字符串、无 code（缺口⑯⑤）；前端 `extractErrorDetail` 字符串兜底当前为**必走路径**。目标是错误信封升级为 `{error:{code,message}}`，但**升级前不可移除字符串兜底**。

### T2.1 `sendError` 升级带 code
- **改动文件**：`localTool/src/utils/helpers.ts:16-18`（`sendError` 增加可选 code 形参，向下兼容：不传 code 时维持 `{error:message}`）
- **code 来源**：复用 `contracts.js` 的 `GEN_ERRORS` 5 类字符串 key（`abort|timeout|network|http|business`，缺口⑨/M5-b），**非新建数字枚举**
- **范围**：仅非流非 SSE 的具名 CRUD handler（M4-a）
- **验收**：`sendError(res, msg, status, code)` 输出 `{error:{code,message}}`；旧调用不传 code 仍 `{error:message}` 兼容；`{error:{code,message}}` 时**保留** `message` 供前端兜底。

### T2.2 前端 `extractErrorDetail` 升级
- **改动文件**：`src/components/base/httpClient.js`（第 95-97 行错误解析区）
- **改动**：
  - 抽 `extractErrorDetail(data)` 纯函数（M1-b），统一解析 `error` 字符串 / `error.code` / `error.message` / `detail` / `message`
  - **保留** `typeof data.error==='string' ? {code:'UNKNOWN',message:data.error}` 兜底（缺口⑯⑤：后端当前必返字符串，兜底不可删）
  - `HttpError.message` 只承载业务 message，**不再拼** `HTTP ${status}: ${detail}` 前缀；status 由 `HttpError.status` 单独暴露
- **验收**：`extractErrorDetail` 单一函数覆盖所有错误源；`HttpError.message` 无 `HTTP` 前缀；字符串兜底分支仍在。

### T2.3 `classifyError` 覆盖确认
- **改动文件**：`src/components/base/genErrors.js`（确认 `classifyError` 分支）
- **现状**（缺口⑮①）：`imageProxy`/`videoProxy` 在 catch 分支**已调** `classifyError`（proxyGenerate.js:147/184/271/300/301）；`chatProxy` 走 `{ok,error}` 不抛错、未调用——**不强制改**，保持契约
- **验收**：注释修正 PRD 描述为「classifyError 已覆盖 image/video，chatProxy 因 `{ok,error}` 契约未覆盖」；无行为改动。

### T2.4 SSE/探测域信封例外确认
- **不改代码**，仅确认（缺口⑦/M5-e）：`agentChat` 的 `data:{"error":"..."}`、`providers` 平铺 `{ok,error}`、`useAgentChat` 的 `parseAgentError` 三套错误解析**保留**，message 文本抽取优先级对齐 `extractErrorDetail`（不强行改造 SSE 行协议）
- **验收**：文档级确认，SSE 域无代码改动。

## B3 · 成功信封收敛（breaking · 一次性硬切，靠测试兜底）→ C2

> 根因：成功形态比 `{ok:true}` 更碎——分页包裹、`{success,data}`、`{version,hasUpdate}`、裸 null、无 ok 包裹、二进制流、stub 等（缺口⑥⑧⑩⑪⑫⑭⑲㉑）。**最高风险批次**。**策略（用户确认）：一次性硬切 + 测试兜底，不用兼容开关、不做两阶段**。

### T3.1 完整形态清单冻结
- **改动文件**：无（文档冻结）
- **冻结清单**（缺口⑧⑪⑫⑭⑮⑲㉑ 汇总）：
  - 分页：`tasks`/`resources` → `{items,total,page,pageSize,totalPages}`（缺口⑧⑭①，`totalPages` 易漏）
  - 成功含 `code`：`projects`→`{projects,lastOpened}`、`logs`/`kv-set`/`kv-delete`/`projects-save`→`{ok:true}`、`admin-import`→`{ok:true,counts:{kv,tasks,resources}}`、`admin-export`→`{kv,tasks,resources,exportedAt,version}`（无 ok）、`admin-cleanup`→`{scanned,deleted,referenced,deletedFiles}`（无 ok）
  - `success-data`：`platform` builtin/models → `{success:true,data}`（缺口⑫①）
  - 无包裹：`platform` pluginManifest → `{version,hasUpdate}`（缺口⑫②）
  - **`workflow-apps` 归 stub 豁免**：`handleWorkflowAppsByProject` 返 `{success:true, data:null, _meta:{stub:true}}`（platform.ts:33-37）——带 `_meta.stub`，且该路径前端零消费（缺口⑰③ RESERVED），**标 `stub` 豁免、不纳入 `success-data` 收敛**（此前归错）
  - providers 平铺：`{providers}`/`{providers,warning?}`/`{ok,error,stage?,detail?}`/`{image_models,...modelCount,warning?}`/`{ok:true}`（缺口⑭④）
  - official 本地：`{allowed:true,reason}`（缺口⑭⑤）
- **豁免（标类型，校验跳过）**：`stream`（files read/thumbnail）、`sse`（agentChat/proxy 流）、`raw`（kvGet 裸 null，缺口⑪）、`probe`（status，缺口㉑）、`stub`（jianying，缺口㉑）

### T3.2 一次性硬切：后端去旧字段 + 前端改 `res.data.xxx`（breaking）
- **改动文件（后端）**：涉及 CRUD 的 route 文件（tasks/resources/projects/admin/providers/platform/official）——成功返回统一为 `{code:0,data:{...}}`，**去掉**旧字段（`ok`/`deleted`/`items`/`url`/`path`/`projects`/`lastOpened` 等全部移入 `data` 内）
- **改动文件（前端）**：`localToolApi.js`/`filesApi.js`/各 store（taskStore/assetStore/kvStore/projectStore/contentStore）+ `fetchBuiltin`/`fetchPluginManifest`（platform）——所有成功消费点从 `res.xxx` 改 `res.data.xxx`
- **⚠️ 散落点收口并入本批（新断点，收口与信封收敛应一起做）**：`GeneratedView.jsx:232`(裸拼 `/api/files/mkdir`)、`AssetLibrary.jsx:209`(裸拼 `/api/files/upload`)、`:283`(裸拼 `/api/files/mkdir`) 绕过薄壳直接 `httpRequest`——**信封收敛后它们不会自动跟随 `{code:0,data}`**，会成漏改点。故本批必须**同时**把这些散落点收进薄壳（`localToolApi.createFolder`/`uploadFile`），否则硬切后这些前端消费点崩。**收口动作与信封收敛绑定，不可拆开**。
- **硬切前置（用户确认：测试兜底，非兼容开关）**：
  - 必须**先完成 B0**「后端形态冻结测试」——每一处要改的 handler 当前形态先被测试锁死
  - 冻结测试全绿 → 后端去旧字段 + 前端改 `res.data.xxx` **同版本合入** → 全部测试通过
  - **唯一可逆性保障 = 测试**：任何回归由冻结测试即时捕获，不是靠运行时开关
- **⚠️ 双端同步发布机制（新断点，必须先解）**：前端 `src/`（vite）与后端 `localTool/`（tsc）是**两套独立构建/发布**。硬切若出现"后端已改、前端未改"的窗口期 = **全崩**。必须在**同一个发布周期内前后端同版上线**，且：
  - 明确发布顺序：先同时提交后端去旧字段 + 前端改 `res.data.xxx` 的代码（同一 PR/同一次发布）
  - 严禁单独发布其中一端；验收总入口的"手动回归"必须在前端接后端联调环境跑
- **特别保护（不可破坏）**：

## B5 · 出口回收（裸 fetch 回炉）→ 可观测/契约

> 根因：`proxyGenerate.js`(4处)/`agentRuntime.js`(1处) 裸 fetch 绕过出口（§5.4 缺口②）。

### T5.1 proxyGenerate 走 `/api/proxy` 分支回炉 httpClient
- **改动文件**：`src/components/base/proxyGenerate.js`（`__proxyFetch`/`chatProxy` 走 `/api/proxy` 的裸 fetch 分支）+ `src/components/base/httpClient.js`
- **⚠️ 结构性前置（新断点，必须先解）**：`httpRequest` 默认 `timeoutMs=15000`（httpClient.js:86-91 `withTimeout(fetch, timeoutMs)`）会对**任何**请求套 15s 超时，而 `chatProxy` 是 **SSE 长连接**（流式读 `res.body`）——**直接回炉会被 15s 超时掐断**。故回炉前必须：
  - `httpRequest` 支持 SSE 模式：`timeoutMs: 0`（禁用超时）+ `retries: 0`（禁重试）+ `parseJson: false` 返回可读流
  - `chatProxy` 以该模式出站；`__proxyFetch`（同步等完整响应，生图/视频轮询）可走常规 JSON 模式
- **注意**：SSE 豁免红线**不破**（缺口⑦/M5-e），回炉的是「HTTP 语义」而非「SSE 行协议」
- **验收**：`chatProxy`/`__proxyFetch` 经 `httpRequest` 出站；SSE 流**不被 15s 超时掐断**；`{ok,error}` 契约不变。
