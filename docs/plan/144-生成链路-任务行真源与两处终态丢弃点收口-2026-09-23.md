### 1.4 本次新增的机制解释（①② 用户实测 · ③ 推导）

**① 为什么会出现「2 条 running」** —— 不是 bug，是**镜像说了真话**：
`useNodeGeneration.stop`（`:297-301`）只中止前端等待 + 关 loading；恢复侧 attach 明写 `cancelOnAbort: false`
（`pollTask.ts:75`）。于是「停掉 → 后端仍在跑 → 再提交新任务」会让**后端真的有两个任务并存**。
`reportGenerate:346-349` 删行之前，前端「假装只有一个」；删行之后，镜像与真源分叉成两条真相。

> ⚠️ **这条改动里唯一会被用户提问的地方**：改后那条后端任务**不再被镜像藏起来** ⇒ 它会留在任务中心、
> 也计入「生成中」角标，于是用户会看到「我点了停止又重新生成，怎么显示 2 个生成中」。
> **这不是角标算错，是它把「停止 ≠ 真停」这个既有缺口第一次摆到台面上**。
> 归**提交/取消层**，本批不改，只在区域日志记一句（预期提问点）。

**② 为什么「提交后刷新，任务中心里那条不见了」** —— 是**落库没成功**，不是刷新弄丢的：
前端把行落到后端只有 `persist`（`:134-142`）一条路，fire-and-forget、失败只 warn、无重试；
刷新时页面卸载会中断在途 POST ⇒ **后端从未收到该行** ⇒ 刷新后 `initTasks` 从后端拉不到它。
（这一条本次**不改**，登记为可见缺口，见 Step 6「明确不做」；与本案的"删行"是两件事，但同一个母体。）

**③ 「旧行终态会多发一次 `upstream:updated`」** —— `taskCompletionBus.ts:38-41` 的发信判据只有"`nodeId` 非空"，
与"是不是本节点最新任务"无关。P1 去掉删行后，**旧行的终态也会走完整条广播**（这正是我们要的），
于是它**也会顺发一次 `upstream:updated`**。当前 `AUTO_TRIGGER_DOWNSTREAM = false`（`config.ts:194`；
`upstreamLink.ts:36` 开关关时直接 `return undefined`，连订阅都不建）⇒ **无害**。
但开关一旦打开，同一节点会触发下游两次。⇒ 列入 P1 的**副作用登记**（本批不修，只写进区域日志与 ADR 的"违反判据"段）。

## Step 2 · 归因（孤例还是母体）

**母体**：**「镜像层的权责边界」缺失判据** —— 镜像只能**反映**真源，不能**筛除**真源。

- 症状 3 个（肉眼各自独立，实际同源）：
  ① 结果不上屏（`completeTask` 早退 → 无广播）；
  ② 任务中心缺行（`reportGenerate` 删内存 → 镜像少一行，且运行期无对账）；
  ③ 后端与前端两份真相静默分叉（DB 有、镜像无）。

## Step 4 · 定契（正确性与错误透传）

### 4.1 关键契约：镜像不得筛除（本稿的根判据）

| 层 | 允许的动作 | 禁止的动作 |
| --- | --- | --- |
| 后端 `tasks` 表 | 增/改/删行（真源） | — |
| 前端 `taskStore.tasks` | **反映**（全量拉取 + 合并且以后端为准） | **筛除**（删掉后端仍存在的行、按节点去重、按节点只留一条） |
| 节点 `node.data` | 由 `writeBackResult` 单点写（末次广播胜出） | 自判"哪条更新"（不需要） |

- 判据形态：**可机判**（"这行在后端存在吗" = 镜像刷新后仍在 ⇒ 不得删）。
- 消费方零新增判据：`TaskCenter` 只渲染镜像；`useNodeGeneration` 只按 `nodeId` 回填。

### 4.2 关键契约：区分两类"行不在"（当前被一条 `if (!cur)` 合并了）

| 事实 | 判据（可机判） | 应有处置 |
| --- | --- | --- |
| **用户主动删除**（清会话 / 删卡 / 清理全部） | 该 id 在本会话被显式删除过（`removeTask` / `clearTasksBy` / `clearAllTasks` 登记） | 保持现状：不复活、不广播（**这条语义不变**） |
| **只是没在镜像里**（未水合 / `initTasks` 失败 / 竞态） | 不在"已删除集" | **不得静默**：丢弃分支必须给**带 taskId 的 warn** 且 reason 明确，**不得伪装成"可能已被删除"** |

- 判据形态：**可机判事实**（会话内删除集），不靠猜、不靠异步查询（保持原语同步语义）。
- **为什么必须用删除集，而不是"直接把 warn 文案改诚实"就完事**：`removeTask:497-508` 不清 `stopPolling`
  ⇒ 用户删掉一个 running 任务后，poller 仍会走到终态、命中 `!cur`。若不分流，**每次"删掉一个正在跑的任务"
  都会刷一条 warn**（噪音），且把"正常删除"与"镜像缺行"混成一句（正是现状那句"可能已被删除"的失实来源）。
- **删除集是"只增不落"的会话级 Set**（与 `progressCancels` 同类；仓库对该形态有「防长会话只涨不落」的注释习惯）
  ⇒ 施工时须注一句：接受只增（存 string id，量级可忽略）。
- 失败可见（ADR-0048）：两类事实给**两种级别**（`deleted` → `debug`；`not-in-mirror` → `warn` + `reason`）。
- **本稿不补广播**：补广播需要 `nodeId`/`type`（原语签名没有）⇒ 要新增参数 = 新增面；且用户裁定②已明确
  「节点不需要」。故 P0 只做**可见化**；若 P0 上线后 `not-in-mirror` 仍有发生，再按下方备选形态补。
- 类型层（ADR-0052 第 2 级）备选（**仅当复现时启用**）：终态落地结果以判别联合表达
  `{ ok: true } | { ok: false, reason: 'not-in-mirror' | 'deleted' }`。

### 4.3 三铁律自检

- 生产者给全：后端 `upsertTask` 已给全（终态 + result_url + 证据）；**前端原语缺的是"行不在"的判据**，本方案补的是**镜像/原语层**（生产者），不在消费端拼。
- 消费者只转发：`pollTask` / `useNodeGeneration` / `TaskCenter` 保持只调原语 / 只转发 / 只渲染，**零新增判据**。
- 不越权：判据留在 `taskStore`（拥有镜像的一方），不在 `TaskCenter`、不在节点写第二份。
