## 一、用户的核心目标（务必先读，别跑偏）

用户在做一个画布型 AI 生成应用（maomao）。他要从「旧时代架构」迁移到「新时代架构」。核心目标按优先级：

### 目标 0 ·「13 个 API 厂商 = 一个平台一个 JSON，前端随便换着用」
- 后端有 **13 个（实为 14 个定义）API 厂商**（服务商），它们不是动态在设置页 CRUD 出来的，而是**每个厂商一个 JSON 配置文件**（`config/providers/<平台id>.json`）。
- **换服务商 = 换 JSON 配置 = 前端节点上换 providerId**，前端逻辑零改动。加/换厂商只加/改一个 JSON，不改代码。
- 这是用户反复强调的架构核心："换 JSON 相当于换服务商"。

### 目标 1 · 前端要有一个「新时代」设置页面（用户 2026-09-03 补充澄清）
- **核心语义（用户拍板）：「切哪个用哪个」= 用户想用哪个厂商就用哪个。既然能实现的厂商/模型都已写进 config JSON（13 个都在），用户直接选当前想用的那个即可。**
- **沿用 provider 这套机制，不重造**：用户倾向"还是这个 provider 比较好"——即保留 provider 选择模型（模型 value = providerId::modelId，节点上能选不同厂商），只是把底层从"旧时代动态 CRUD"换成"新时代：13 个厂商 JSON 都在，用户挑着用"。
- 设置页作用：**集中管理和展示所有已配置厂商（来自 config/providers JSON）**，让用户看到"我有哪些能用、分别什么模型"，并能切换/选定当前想用的。**不是**旧时代的"自由增删连接 + 选协议(openai/apimart/volcengine) + 存 providers.json"。
- 注意：**不是强制"全局唯一一个 primary 才能用"**；而是"所有已配置厂商都能用，用户灵活选当前用哪个"（具体某次生成想用哪个由用户在节点或设置里定）。是否保留"默认/主厂商"仅作为回退兜底，而非限制。

### 目标 2 · 前端所有生成请求"发意图"、数据统一、直连 relay
- 前端 5 类入口（文本节点、promote/生图节点、视频节点、剧本盒子、AI 助手）**全部收敛到 3 个门面函数**（imageApi.generateImage / videoApi.generateVideo / chatApi.chatCompletions）。
- 前端只发**统一意图** `GenIntent`（capability + providerId + model + prompt/messages/size/images + taskId），**不再塞 provider 富对象**、不碰出站细节。
- 生成链路**切到 relay**（后端驱动）：image/video → `/api/generate`（后端轮询+落盘 /files/+写 result_url），chat → `/api/relay`。**老通道 `/api/proxy` 不是目标，最终要删。**

### 目标 3 · 后端生成「一个入口、一个出口」（用户拍板：不是"合并端点"，是架构上生成只有一件事，不该有多个出口）
- **用户原话**：生成"它只有一个事情，为什么它要弄好几个出口呢？不需要前端暴露好几个出口"。
- **前端产出就 3 种：生成图片 / 生成视频 / 文字**。没别的。所以后端就该是"一个生成入口/出口"承载这 3 种 capability——capability 是入参，不是拆端点的理由。
- **原则：简单清晰、不重复；已经过时的东西（如旧 /api/proxy、旧 chat 形态、翻译网关 9004）一定要删掉**，不留僵尸代码/双轨。
- **正确架构（唯一入口 + 唯一出口）**：
  - `POST /generate`：**唯一入口**，收统一 `GenIntent`（含 capability/image|video|chat）。后端提交后**统一立即返回 `{ taskId }`**（无论 image/video/chat 都返回一个句柄，不等终态）。
  - `GET /generate/{taskId}`：**唯一查询出口**，返 `{ status: running|completed, result }`（image/video → url=/files/；chat → text）。chat 因快，几乎立刻 GET 即 completed 拿文本。
  - `POST /generate/{taskId}/cancel`：取消。
  - **不再有独立的 /api/relay 作为 chat 出口**——chat 并进同一入口/句柄模型（能力上 relay-poll 需支持 chat；后端 /api/relay 可作内部同步实现或退役）。
- **为什么 image/video/chat 用同一对入口/出口（而不是 image 一个、chat 一个）**：因为"要什么产出"(capability) 是**入参**，不是"不同的出口"。后端收到 GenIntent 后按 capability + provider 协议内部处理；前端永远只打这一对端点，不因模态区分端点。
- **为什么提交都立即返 taskId（哪怕 chat）**：这是"一个出口"能成立的关键——image/video 生成慢且要根治刷新丢结果（需句柄可 attach），chat 快也走同模型（立刻 completed）。统一为"提交→拿句柄→查结果"，前端契约单一。
- **待定（前端稳定后定）**：relay-poll 增加 chat 能力的具体接法（chat 提交也走句柄：submit→thread/task→poll→text），以及后端 /api/relay 是否退役。但**方向已明确：一对入口/出口，不按模态拆端点**。

### 目标 4 · 根治"刷新丢结果"
- result_url 写库真源从「前端一次性窗口」移到「后端常驻进程」（轮询+落盘+写库在 localTool，可 attach/重启恢复）。

### 目标 5 ·（重要）拆掉 9004 网关，relay 直连 Lovart 原生
- **9004 不是终态**（它是旧画布时代把 Lovart 原生翻译成 OpenAI 兼容 /v1/* 的一层网关，见 apimart-gateway/）。**最终要拆掉它**，让 relay 直连 Lovart 原生 agent 协议。
- Lovart 原生协议（真源：`.codebuddy/skills/lovart/agent_skill.py` + `apimart-gateway/lovart_client.py`）：
  - 鉴权 = **AK/SK HMAC-SHA256**（header `X-Access-Key/X-Timestamp/X-Signature/X-Signed-Method/X-Signed-Path`，签名=hmac(secret,"{METHOD}\n{path}\n{ts}")），**不是 Bearer**；base=`https://lgw.lovart.ai`，path 前缀 `/v1/openapi`。
  - 提交 = `POST /v1/openapi/chat`（body {prompt, project_id, attachments?, tool_config:{prefer_tool_categories,...} }）→ 拿 **thread_id**（不是 task_id）。
  - 状态 = `GET /v1/openapi/chat/status?thread_id=`；结果 = `GET /v1/openapi/chat/result?thread_id=` → `items[].artifacts[].content`（多类型产物列表）。
  - 高成本操作有 `pending_confirmation → POST /v1/openapi/chat/confirm`（auto-confirm 取舍见 9004 main.py Config.AUTO_CONFIRM）。
  - 提交**没有 model/size 字段**（模型靠 prompt + tool_config.prefer_tool_categories，如 {"IMAGE":["generate_image_gpt_image_2"]}）。
- **这是 ai-relay 现有"submit→task_id→poll status→result.urlPath"二态模型表达不了的**（是 chat-thread 型：thread_id + confirm + 多 artifacts）。接入方案二选一（详见 docs/99）：
  - 方案 A：ai-relay 抽象第三种执行形态 `mode:'agent-thread'`（守 C0、可复用）。**推荐**。
  - 方案 B：relay 侧独立 lovart 直连客户端（绕 kit，快但有违 C0）。
- 依赖 key：直连需 `LOVART_ACCESS_KEY` + `LOVART_SECRET_KEY`（现仅存于 apimart-gateway/.env），relay 侧需读入做 HMAC；仍只驻内存、不入库。
- **当前已明确为"最终要做"**（不再只是远期）；顺序上可在 lovart 经 9004 打通前端全链路稳定后，再切直连（9004 作为过渡仍保留到直连验证通过）。
- 相关设计已写在 `docs/99-lovart原生直连接入设计-2026-09-03.md`（含协议契约/差异/方案/落点/风险）。

### 目标 6 ·（远期）其它 12 个厂商的生成协议逐个补齐
- 目前后端只对 lovart 经 9004 配好了能跑通的生成协议。**其它 12 个厂商的生成协议/预设还没配**——用户明确说"最后再补"，不阻塞当前前端切 relay 打通 lovart 全链路。
- 注意：12 厂商补齐时应走"ai-relay 直连各平台原生协议"的正路（同目标 5 的思路），不依赖 9004 那种翻译网关。

## 二、关键概念澄清（用户口头确认过）

- **节点类型 ≠ 厂商**。节点类型就那 5 类（文本/promote/视频/剧本/AI助手），决定"要什么"（capability: chat/image/video）。
- **厂商（13 个）= 节点上可下拉的 providerId**，决定"用哪家"。任意节点都能换任意厂商。
- 前端选模型 value = `providerId::modelId`（providerModels.ts），`resolveProviderModel` 解出 providerId。
- chat **流式/非流式由厂商配置决定**（config/providers 里配该模型 `streaming`），不是前端传。前端 GenIntent **不传 stream**，后端按 providerId 读 JSON 决定。

## 四、下一步要做的事（按依赖排序）

### 第 1 步 · 新时代设置页（目标 1，最优先，前端）
- **语义（用户拍板）**：能实现的厂商/模型都已配进 config JSON，用户想用哪个就用哪个。保留 provider 这套选择机制，不重造；只把底层从"动态 CRUD"换成"展示 13 个 JSON 厂商、用户挑着用"。
- 把旧 `ApiSettings.tsx`/`providerStore`（动态 CRUD）换成新时代：
  - 页面展示**后端 GET /api/providers 返回的厂商列表**（来自 config/providers JSON + 内置目录），每个厂商带可用模型。
  - 用户**挑/换当前想用的厂商**，能看到并选用所有已配置厂商的模型（不是强制单 primary，而是多厂商都可用、用户灵活选）。
  - 不再是自由增删连接 + 选协议(openai/apimart/...) + 存 providers.json。
- 数据源：`/api/providers`（后端已重建，返回配置型厂商）。前端 providerStore 从"CRUD+单 primary 保存"改成"读配置型厂商列表、允许选/切当前想用的（primary 仅作回退兜底，不限制多厂商同时可用）"。

### 第 2 步 · 节点"选服务商→选模型"UI（配合目标 0/1）
- 节点（生图/文本/视频）头部从"一个大混合模型列表(ModelSelect)"改成 **两级联动：先选服务商(13 厂商) → 再选该厂商的模型**。
- 选项全部来自后端 /api/providers（JSON 配置）。换服务商即换 model 前缀(providerId)，后端随之读不同 JSON。

### 第 3 步 · 前端门面彻底直连 relay（目标 2 收尾）
- imageApi.generateImage / videoApi.generateVideo 内部直接构造 GenIntent、调 relayProxy（relayGenerate），不再经 proxyGenerate 中转（去掉 RELAY_ASYNC_SUBMIT 临时分支，或保留但统一走 relay）。
- image 的 responses/sync 形态：切 relay 后统一走 /api/generate 后端驱动；responses 形态后端协议待补，先保证 lovart(async) 主路径通。
- 全部入口只发 providerId，不塞 provider 富对象。

### 第 4 步 · chat 流式 config 驱动（目标 0 的延伸）
- config/providers/<id>.json 给该厂商 chat 模型加 `streaming` 标记。
- 后端 /api/relay（或统一 API）按 providerId 读该标记，决定走 kit `streamChat`(流式) 还是 `chat`(非流式)。
- 前端 GenIntent 不传 stream。

### 第 5 步 · 刷新恢复（R6，目标 4）
- 前端加载时从 /api/tasks 读 running 且 poll_task_id 非空 → 逐个 GET /api/generate/:id attach 后端句柄 → 完成后回填节点。替代 pollTask/initTaskRecovery 前端自轮询。

### 第 6 步 · 后端 relay/API 合并成一个（目标 3）
- 前端稳定发 GenIntent 后，后端把 /api/relay 与 /api/generate 收口成单一统一 API（前端只打一套端点语义），providerId → config/providers + preset 的翻译收口。参考 docs/98。

### 第 7 步 · 退役 proxy 老链路
- 前端零消费后：删 proxyGenerate proxy 出站段 / pollTask / taskStore ensurePolling / 前端恢复落盘；/api/proxy registry 删；check:api 归零。

### 第 8 步 · 拆 9004，relay 直连 Lovart 原生（目标 5，重要）
- 在 lovart 经 9004 打通前端全链路稳定后，做直连：在 ai-relay 抽象 `mode:'agent-thread'`（方案 A，推荐）或独立 lovart 客户端（方案 B），按 docs/99 接入 Lovart 原生（HMAC + /chat→thread_id + status/result + confirm）。
- key：读 LOVART_ACCESS_KEY/SECRET_KEY（现 apimart-gateway/.env）做 HMAC，驻内存不入库。
- 9004 作为过渡保留到直连真机验证通过，再停用/移除 apimart-gateway 依赖。

### 第 9 步 ·（远期）其它 12 厂商生成协议补齐（目标 6）
- 每个厂商补 config/providers JSON + ai-relay 预设/协议（走各平台原生直连的正路，非 9004 式翻译网关），让 13 个都能出图/文/视频。

## 五、关键红线（务必遵守）

- **provider 是配置型**：一个厂商一个 JSON（config/providers/<id>.json），key 只进 .env、不入库；换厂商 = 换 providerId = 后端读不同 JSON，**前端逻辑零改动**。
- **前端只发意图**：只发 GenIntent(providerId/model/参数)，不塞 provider 富对象、不传 stream（流式由后端 config 决定）、不碰出站细节。
- **协议执行不绕 kit**：提交/轮询/取结果一律经 ai-relay（C0），不自写 fetch/HMAC/字段抽取。
- **落盘不依赖 kit**：saveRemoteUrl；DB 写 result_url 唯一 upsertTask；node_id 归前端 taskStore 写。
- **能力零退化**：进度/取消/参考图/错误中文/刷新恢复，逐个兜住才允许切/删。
- **每步可回退**：前端改动前可 stash/分支；改完 tsc + 真机点一次。
- **过时即删、不双轨**：前端产出只有"图片/视频/文字"3 种，后端只留唯一生成入口/出口（唯一入口 POST /generate + 唯一查询 GET /generate/{id} + cancel）。旧 /api/proxy、旧 chat 形态、翻译网关 9004、前端自轮询(pollTask/ensurePolling)等**一旦被新链路替代就删干净**，不留僵尸代码。别用"双轨保留旧通道"拖延——用户明确不要重复、过时必删。

### 8.1 根治"刷新丢结果"（目标 4）——确定做法
**根因**：旧模型 result_url 写库真源在前端一次性窗口。**已根治**：relay 后端 `relay-poll.ts` 提交时落 DB 在途行(running)，轮询到终态由**后端**落盘 `/files/` 并 `upsertTask` 写 `result_url`/`status=completed`/`completed_at` 到 `tasks` 表（task_id=前端 frontTaskId），不依赖前端进程存活。
**前端刷新恢复接法**（R6，还没实现，做法确定）：
- 前端 App 启动 / 刷新后，任务中心从 `/api/tasks`（`fetchTasks`，taskStore.initTasks 已拉）得到历史任务。
- 对其中 `status ∈ (running) 且 poll_task_id 非空` 的任务：逐个 `GET /api/generate/:frontTaskId`（`relayProxy.relayPoll`）attach 到**后端同一句柄**。
- attach 返回 completed → 拿到已落盘 `/files/` url → 走既有 `taskStore.patchTask` 更新内存任务 + 前端经 `publishTaskCompleted`（`taskCompletionBus` 唯一入口）广播 → `useNodeGeneration` 里监听 `agent:task-completed` 且 `nodeId===本节点` 的 handler 自动把 resultUrl 写回 node.data（此监听**已存在**，见 useNodeGeneration 的 onRecover / recoverable 机制）。
- **替代**：删掉旧 `pollTask.ts` 的 `initTaskRecovery` / taskStore `ensurePolling` 前端自轮询恢复。
- 之所以安全：后端句柄生命周期 = localTool 进程且落库；前端刷新只是重新 GET attach，后端任务继续跑完落盘写 DB。
- 待定：具体把"attach 在途任务"放 App 启动哪个 effect（可参考原 `initTaskRecovery` 在 App.tsx 的调用时机，改成调用"relay attach"而非"前端 ensurePolling"）。
