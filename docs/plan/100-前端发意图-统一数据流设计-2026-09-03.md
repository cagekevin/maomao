# 前端「发意图」统一数据流设计（简单·无黑盒·单向清晰）

> 状态：设计定稿。方向（用户确认）：
>  - 前端有 5 类节点/入口，但**每个节点都能在 13 个服务商（= 后端 ai-relay 内置平台 / config/providers 的 <id>.json）里随便换**。
>  - 换服务商 = 换 providerId = 后端读不同 JSON，**前端零代码改动**。
>  - 前端只发"意图"（providerId + model + 模态参数）；后端按 providerId 读 config + 选 preset 出站，不信任前端塞的出站细节。
> 目标：整条「前端点一下 → 出图/文/视频」数据流每层可读、无黑盒、单向。

---

## 0. 一句话

前端任意节点选「13 个服务商之一 + 一个模型」→ 发标准意图 `GenIntent`（只要 providerId/model/参数）→
后端拿 providerId **查 config/providers/<id>.json** + 按 capability **选预设** 出站。
前端不碰出站拼装、不塞 provider 富对象；后端是出站细节真源。

## 1. 两个正交维度（别混）

- **节点类型（5）**：文本 / promote / 视频 / 剧本盒子 / AI 助手 —— 决定"要什么产出"，即 capability(image/video/chat)。
- **服务商（13）**：lovart / xai / google / ... —— 节点上可下拉的"用哪家"，即 providerId。

> 任意节点 × 任意服务商 = 前端数据流不变，只是 providerId 不同 → 后端切 JSON。这是"13 服务商随便换"的架构意义。

## 2. 前端发什么：统一意图 `GenIntent`

只含"要什么"，不含出站/UI 细节；模态差异用可选字段，各模态只填自己的：

```ts
interface GenIntent {
  capability: 'image' | 'video' | 'chat'      // 由节点类型决定
  providerId: string                          // = 13 个 config/providers/<id>.json 的 id（如 'lovart'）
  model: string                               // 该服务商模型清单里的 id
  taskId?: string                             // 贯穿任务号（前端 task_id）
  prompt?: string                             // image/video
  messages?: unknown[]                        // chat 多轮
  size?: string                               // 像素（如 '1024x1024'）
  images?: string[]                           // 参考图 url
  // signal 仅请求层，不入 GenIntent 持久化
}
```

**providerId 现成可得**：前端模型 value 是 `providerId::modelId`（providerModels.ts），节点上选的就是它 → 门面解出 provider.id 填入。

## 3. 后端接意图 → 翻译（单向、无黑盒）

```
[前端 5 类入口] → 收敛到 3 门面(imageApi/videoApi/chatApi)
   → 门面把 (节点选的 provider + model + 模态参数 + taskId) 归一成 GenIntent
   → image/video: POST /api/generate  { ...GenIntent }
   → chat:         POST /api/relay     { ...GenIntent }   (本期同步)
   → 前端拿 taskId(image/video) / text(chat)；刷新靠 GET attach

[localTool]
   POST /api/generate
     → 校验 capability/model/providerId 必填
     → providerConfig.readProvider(providerId)     ← 唯一：按 id 读 config/providers/<id>.json（13 服务商）
     → presetNameFor(capability)                    ← 唯一：capability → lovart-image/video/chat
     → relayPoll.submitGenerateTask(...) → kit 提交上游 → 落 DB 在途(running) → 返 {taskId}
   GET  /api/generate/:id  → 后端句柄轮询 → 落盘 /files/ → 写 result_url(completed) → attach 返
```

**关键**：base_url/protocol/模式/模型清单等出站细节，后端一律 `readProvider(providerId)` 自查；
**不信任**前端塞的 provider 富对象。所以换服务商只换 providerId，后端读不同 JSON 即可（96 号已建 config/providers）。

## 4. 无黑盒·唯一出口

| 层 | 唯一出口 | 禁令 |
|---|---|---|
| 前端出站 | base/api 门面(3 个) | 节点/剧本/AI 助手禁自己拼 /api/proxy、禁发 provider 富对象 |
| provider 配置 | providerConfig.readProvider(id) | 后端禁散读 config/providers |
| 预设选型 | presetNameFor(capability) | 禁按 providerId 散 if |
| 上游调用 | ai-relay kit | 禁自写 fetch/HMAC |
| 落盘 | saveRemoteUrl | 不依赖 kit |
| 写 DB | upsertTask | 禁裸 UPDATE |
| 结果抽 url | preset result.urlPath | 前端无第三份解析 |

**单向**：前端 → /api/generate → 后端；前端刷新 = GET attach 读后端已写 DB 的 result_url；不反向驱动写库。

## 5. 施工顺序（每步可验证可回退，能力零退化）

| 步 | 内容 | 验证 |
|---|---|---|
| S1 | 定 `GenIntent` 类型 + 后端 /api/generate 按它校验 | curl 用 GenIntent 形状提交通 |
| S2 | 门面层归一：imageApi/videoApi/chatApi 内部构造 GenIntent，只传 provider.id（不把 provider 富对象下传）；proxyGenerate 出站改吃 GenIntent + 后端 readProvider 查的配置 | 5 入口真机出图/文/视频 |
| S3 | image/video 切 /api/generate（后端驱动）；chat 走 /api/relay | 节点点一次出图，进度/取消/刷新恢复正常 |
| S4 | 刷新恢复 R6：前端加载读 running → GET attach | 刷新后任务续跑、节点显示 /files/ |
| S5 | 退役 proxyGenerate/pollTask/ensurePolling；/api/proxy registry 删 | check:api 归零 |

> 依赖：96 号(config/providers)已落地；relay-poll + /api/generate 已落地并真机验通(image/chat)；lovart preset 信封已固化(测试 6 例通过)。

## 6. 换服务商 = 换 JSON 的操作语义（给用户/维护者）

要在画布上用新服务商（如把某节点从 lovart 换成 google）：
1. 确保 `config/providers/google.json` 存在（或后端内置目录已含 google → GET /api/providers 已返回）；
2. 节点上把模型下拉从 `lovart::gpt-image-2-low` 换成 `google::<model>`；
3. 前端把 providerId=google 随 GenIntent 发出，后端 readProvider('google') 用 google 的 base_url/preset 出站。
→ **不改前端代码、不改节点逻辑**，只换下拉（providerId）。这就是"换 JSON=换服务商"。
