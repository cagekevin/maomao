## 二 · 根本问题：**"工程数据"没有统一的架构契约**

### 2.1 现状是"各自为政"

四类工程数据，四种形态：
- 画布 → KV，**进备份**
- 剪辑 → KV + **IndexedDB**，**不进备份**，元数据**无处可备**
- 3D → KV（双通道），**不进备份**
- 剧本盒 → 内嵌画布，随画布进备份 ✅

> **【2026-09-16 状态回改（就地，勿另开文件）】** 上表是**评估当时的实况**。此后 A-2 已落地
> （`backupStore` 新增 `kv` 段，TD-02-30 结清）⇒ **剪辑工程的 KV 部分与 3D 工程现已进备份**；
> 剪辑仅剩的缺口是「素材元数据在 IndexedDB」（A-1 未做；TD-02-31 已裁定非债）。
> **新判据**：只要在 `STORAGE_KEYS` 登记 `backend:'kv'`，就自动进备份（0 行接入）。
> 见 `daily/架构日志/02-存储-持久化-跨区-备份收全KV工程键-2026-09-16.md`。

**没有任何一条架构规则说"工程数据该存哪、要不要进备份"。**
每个域自己决定，于是漂移。

### 2.2 三个具体症状（同一根因）

**症状 A · 备份是"部分备份"，但 UI 说"完整备份"**

`backupStore.ts:6` 自述：
> 官方有"导出所有内容/导入所有内容(JSON)"——把**全局配置、项目、画布快照**完整打包下载/恢复

实际只收 `LS_KEYS` + `canvas` + `accounts`。**剪辑工程、3D 工程全都不在**。
用户导出备份 → 换机导入 → **片子和 3D 场景全丢**。

**症状 B · ~~GC 看不全引用 → 误删~~（⛔ 已裁定非债 · TD-02-31）**

> **用户裁定（2026-09-15）**：素材库是**本源（所有方）**，剪辑器只是**消费者**；用户在本源删数据 → 下游引用失效是**理所应当的因果**，不是债。为上游删除做防御（引用上报 / 副本自保 / "删前检查下游"）= **越权 + 附随复杂度**（"禁止删"三个字本身就是复杂度）。
> 原则已入**架构师心法铁律 7（数据权责单向）** + 7 步法 Step 6 自查。
> 保留的只剩**事实陈述**（GC 扫 resources+tasks+KV，IndexedDB 不在其视野——这是架构边界，非缺陷）；
> 消费者对它的正确姿势 = **不关心、不防御**（TD-02-31 已撤）。

**症状 C · UI 陈述与实际不符（假陈述）**

`StorageMonitor.tsx:856`：
> "maomao 业务数据存在 localTool，**不使用 IndexedDB**，故此处占用通常为 0"

而剪辑器**正在用 IndexedDB**（`service.ts:147`）。
`storageQuota.ts:16` 同款注释："（maomao 不写 IndexedDB，usage 通常为 0）"。

> 这是**最不能留的**：它会让下一个排查"剪辑素材为什么丢"的人
> **直接排除掉 IndexedDB 这个可能**（因为 UI 和工具都告诉他"不用 IndexedDB"）。

### 2.3 为什么这是"母体"（Step 2 判据）

| 判据 | 证据 |
| --- | --- |
| 一次修复能同时消灭 ≥3 个问题 | 若确立"工程数据统一契约" → 症状 A（备份不全）、C（假陈述）**同时消失**；且元数据入 KV 后消费者引用天然在 KV（GC 视野）——是**存放位置正确的自然结果**，非新增防御（铁律 7） |
| 是**规则层**问题 | 不是"某一行写错了"，而是**缺一条规则**：「工程数据的存储/备份归属」 |
| 会**继续产生**新问题 | 下一个工程域（如"音频工程""字幕工程"）会**再走一遍同样的弯路** |

> **母体命名**：**M7 · 工程数据无统一契约**（与 M1 结果契约缺位 / M2 唯一入口无守卫 / M3 SSOT 第二份同族）。

## 三 · 逐项取证（含此前未发现的）

### 3.1 `backupStore` 到底备了什么

```ts
// backupStore.ts:116-179 exportAll()
ls      = LS_KEYS（getLocalKeys() 过滤 backend:'local' && !pattern）
canvas  = 遍历 projects → loadCanvasState(id)      // KV 画布快照
accounts= KV yimao_accounts
```

**没备的**：
- ❌ 剪辑工程三键（`backend:'kv'` + `pattern:true` → `getLocalKeys()` 两个条件都不满足）
- ❌ 3D 导演台工程（KV，同样 pattern）
- ❌ 剪辑素材元数据（IndexedDB）
- ❌ 所有 `pattern:true` 的 KV 键 —— **`backupStore` 没有遍历动态键的能力**

> **结构性缺陷**：`backupStore` 的收集逻辑是「`LS_KEYS` 白名单 + 硬编码遍历 canvas/accounts」。
> **每个新工程域都要手工加一行**（`canvas` 就是这样硬编码的）。
> 这是 M3（手写清单必漂移）在**备份层**的又一次现身。

### 3.2 IndexedDB / OPFS 的真实范围

| 用途 | 文件:行 | 状态 |
| --- | --- | --- |
| 素材元数据 `MediaAssetData` | `service.ts:147` | ⚠️ **正在用**（T4 后二进制走了 `/files/`，但元数据留下了） |
| 素材二进制 OPFS | `service.ts:153` | ⚠️ **疑残**：T4 后 `saveMediaAsset` 不再写它，但 `deleteMediaAsset` 仍调 `remove`（`:557`） |
| 旧工程 `video-editor-projects` | `migrations/runner.ts:42` | ⚠️ **迁移遗留**（T3 后工程本体走 KV，此 adapter 只在迁移里读） |
| 旧素材 `video-editor-media-*` | `migrations/v1-to-v2.ts:49` | ⚠️ **迁移遗留** |
| 旧 timeline | `transformers/v1-to-v2.ts:246` | ⚠️ **迁移遗留** |
| sounds | `service.ts:129` | ⚠️ 收藏音效（用户数据？） |
| `video-editor-meta` | `runner.ts:34` 删除 | 一次性清理 |

**结论**：IndexedDB 里**混着三类东西** ——
① **活的**（素材元数据、saved sounds）、② **迁移遗留**（旧 projects/media/timeline）、③ **待清理**（meta 已删）。

> 这三类**不同的生命周期**混在同一载体里，本身就是"没有契约"的表现。

### 3.3 `use-local-storage.ts`（剪辑器 localStorage 裸写）

`videoEditor/hooks-cutia/storage/use-local-storage.ts:17,35` 直接读写 `localStorage`，
用于 caption 语言 / model-id / template-id。

**问题**：
- **未登记 `STORAGE_KEYS`** → 不在备份、不在云同步、不在任何清单
- 绕过 `contentStore`（违反"存储唯一入口"）
- 键名未加 `yimao:` 前缀（`storageAdapter.ts:84` 的约定）

> 这是 cutia 搬迁**带进来的**，与 `'videoeditor:seek'`（已收口进 eventBus）是同族漏网。

### 3.4 GC 的真实覆盖

`service.ts:503-505` 注释：「`runReferenceGc` 查 resources + tasks + **KV** 三处引用」。

**但**：这是**后端** GC，它扫的是**后端能看见的**（resources 表 / tasks 表 / KV 库）。
- **IndexedDB 在后端视野之外** → 剪辑素材引用**不可见**
- 同理 OPFS、浏览器 localStorage

> **这不是 bug，是架构边界**：只要"引用"存在浏览器私有存储里，
> 后端 GC 的视野就天然不含它。消费者对此**不关心、不防御**（心法铁律 7）——
> 本源何时回收磁盘，是本源的裁决；下游引用随本源删除而失效，是理所当然。

## 四 · 处置方案（三选一，需用户裁决）

> **判据（Step 5）**：这属**架构结构**（可直接定）还是**业务/契约**（须问用户）？
> —— 它同时是两者：**"工程数据存哪"是结构**，但**"要不要迁移存量 IndexedDB 数据"是业务**（用户数据）。
> 故摆选项。

### 方案 A（推荐）：**确立"工程数据契约"，统一进 KV**

**核心规则（一条）**：
> **凡"用户工程数据"（画布/剪辑/3D/未来的新工程域），一律存 localTool KV；
> 禁止使用 IndexedDB / OPFS / localStorage 裸写承载工程数据。**

**依据**：
1. **KV 已被验证可行**：画布快照、剪辑工程本体、3D 工程**都已经在 KV**
   （`contracts.ts:222 / 489 / 445`）→ 不是新机制，是**把已有的正确做法推广成规则**；
2. **KV 是后端可见的** → 消费者的引用天然可被上游 GC 视野覆盖——**无需任何防御机制**（铁律 7：消费者不约束所有方，本条只是"引用放对地方"的自然结果，不是新增约束）；
3. **KV 可被遍历**（`getKvKeyPatterns()` 已存在，`contracts.ts:512`）→ **备份能全量收集** → 症状 A 解；
4. **单点**：不用同时维护 localStorage / IndexedDB / OPFS / KV 四套适配器。

**具体动作**：

| # | 动作 | 落点 |
| --- | --- | --- |
| A-1 | **素材元数据 `MediaAssetData[]` 内联进 `TProject`** | `service.ts` `saveMediaAsset` / `loadAllMediaAssets` |
| A-2 | **`backupStore` 改为"遍历 KV 动态键"**（用 `getKvKeyPatterns`）替代硬编码 canvas | `backupStore.ts` |
| A-3 | **删除 IndexedDBAdapter / OPFSAdapter 及其迁移器**（含存量数据迁移） | `videoEditor/engine/services/storage/*` |
| A-4 | **`use-local-storage.ts` 收口进 `contentStore`** 并登记 `STORAGE_KEYS` | 剪辑器改造区 |
| A-5 | **修正 StorageMonitor / storageQuota 的假陈述** | `StorageMonitor.tsx:856` / `storageQuota.ts:16` |
| A-6 | **补一条架构闸**：`videoEditor/**` 禁 import IndexedDB / OPFS / 裸 `localStorage` | `scripts/check-arch.mjs` |

**成本**：中高 —— A-1/A-3 涉及剪辑器引擎改动 + **存量数据迁移**（用户已有的剪辑素材元数据在 IndexedDB 里）。
**收益**：一次性解决 A/B/C 三个症状 + 未来所有工程域不再走弯路。
**风险**：迁移失败 = 用户剪辑素材丢失（需**幂等 + 双写过渡**）。

### 方案 B：**保留多载体，但补齐"登记"**

**做法**：不改存储位置，但：
- 强制所有工程数据**登记进 `STORAGE_KEYS`**（哪怕后端是 indexeddb/opfs）
- `backupStore` 增加对应收集器
- GC 增加"浏览器侧引用上报"（前端把引用推给后端）

**成本**：中 —— 不用迁移存量。
**风险**：
- ⛔ **"GC 引用上报"本身就是越权**（心法铁律 7）：消费者向上游推送引用 = 消费者参与本源的回收裁决。
  素材库（本源）的 GC 扫哪几处、何时回收，**轮不到消费者插手**；
- ⚠️ **`STORAGE_KEYS` 的 `backend` 枚举要扩**（`'local'|'kv'|'native'` → 加 `'idb'|'opfs'`），
  而 `contentStore.resolveBackend` 是**全库唯一路由**，扩它影响面大；
- ⚠️ **GC 上报是"第二真相"**（前端说"我引用了它"，可能与实际不符）→ 违反 M2 精神；
- ⚠️ **备份包要能装 IndexedDB 内容**（体积、格式都要变）。
- **本质**：把复杂度**分摊到每一层**，而不是消掉它。

### 方案 C：**不动，只修 UI 陈述**

**做法**：只把 `StorageMonitor` 的"不使用 IndexedDB"改掉，其它不动。

**成本**：极低。
**风险**：**症状 A（备份丢片子）不解** —— 只是不再说谎。
**结论**：**不可接受**（用户已明确"要一次性把基础打好"）。

## 五 · 我推荐 A，但有一个必须诚实说的代价

### 5.1 为什么是 A

**A 的本质是"把已有的正确做法变成规则"**：
- 画布、剪辑工程本体、3D 工程**都已在 KV** —— 它们是对的；
- 只有**剪辑素材元数据**跑偏到 IndexedDB（`docs/134:284` 当时就标为"待决策"，施工选错了）；
- 所以 A **不是重构，是"把唯一跑偏的那个拉回来"**（+ 补规则防未来）。

### 5.2 必须诚实说的代价

**A-3 要删 IndexedDB，而里面可能有用户存量数据：**

| 数据 | 是否有存量风险 | 处置 |
| --- | --- | --- |
| 素材元数据 | ⚠️ **有**（用户已用剪辑器 → 元数据在 IndexedDB） | **必须迁移到 KV**（幂等，双写过渡期） |
| saved sounds（收藏音效） | ⚠️ 可能有 | 迁 KV 或登记 |
| 旧 projects/media/timeline | 迁移遗留，**已无人读** | 可直接删 db（但需 `grep` 确认零消费） |

> **迁移必须做对**，否则 = **用户剪辑素材丢失**（比现在的"备份丢片子"更糟，因为它发生在升级瞬间）。
> 这需要一份**独立的迁移施工书**（含幂等、回滚、验证）。

### 5.3 分期建议（不阻塞当前工作）

| 期 | 内容 | 依赖 |
| --- | --- | --- |
| **一期（本轮）** | **A-5 修正假陈述** + **A-6 补架构闸**（拦住新增 IndexedDB 用法） | 无，可立即做 |
| **二期** | **A-1 素材元数据内联进 `TProject`** + 迁移 | 需独立施工书 |
| **三期** | **A-2 备份改遍历 KV** + A-4 `use-local-storage` 收口 | 二期之后 |
| **四期** | 删 IndexedDBAdapter / OPFSAdapter / 迁移器 | 三期之后（确认零引用） |

> **一期可以立刻做**，因为它**只修正陈述 + 拦新增**，零迁移风险，
> 且它**立刻**止住"下一个工程域又用 IndexedDB"。
