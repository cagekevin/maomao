## Step 1.5 · ⚠️ 前置风险：幽灵任务（删掉取消后**唯一要担心的事** · 本批必须同时处理）

**用户提出的风险**：不能停止之后，唯一担心的是"幽灵任务一直跑、永远不结束"。
**核实结论：成立，且比预想的严重** —— 有 **5 条路径**会让任务行**永久 `running`**，
而删掉"停止"后**它们一个出口都没有了**。

### 5 条路径（全部实测）

| # | 触发条件 | 机制 | 频率 |
| --- | --- | --- | --- |
| **B** | **前端建了行，但后端从未持有它**（POST 未达/失败前用户刷新/关页面） | `reportGenerate` 建行即 `status:'running'` 并 `persist`（`taskStore.ts:359/368`，**写进后端同一个 `tasks` 表**）⇒ 后端 GET 走**回库分支**：`if (!row) return not-found`（`relay-poll.ts:910`）—— 但**行一定存在**（前端写的）⇒ 落到最后的 `return {status:'running'}`（`:942-946`）⇒ 前端 `pollTask` 永远接管、永远 running。而启动扫描的 SQL 条件（`:974-977`：`poll_task_id 非空 OR request_data LIKE '%_relayPoll%'`）**两个都不满足 ⇒ 不选中** ⇒ 后端也不给它写终态 | **高频**（刷新/关页面是常态） |
| **A1** | 有 `poll_task_id` 但 `request_data` 无 `_relayPoll` 快照 | 扫描选中后 `if (!core) continue;`（`:990`）⇒ 只跳过、**不写终态** | 中 |
| **A2** | 快照 `capability` 非法（域外值） | `if (!isRelayCapability(...)) { console.warn(...); continue; }`（`:996-1003`，**TD-08-51**）⇒ 跳过 | 低（脏数据） |
| **A3** | 快照无 `core.taskId`（脏数据，且非 `direct+pendingSubmit`） | `if (!core.taskId) continue;`（`:1036`）⇒ 跳过 | 低 |
| **A4** | 非 direct 但缺 `poll` 配置（旧/脏数据） | `if (!core.poll && !core.direct) continue;`（`:1037`）⇒ 跳过 | 低 |

### 共同根因（一句话）

**「我跟踪不了这个任务」这件事没有被写下来** —— 后端既不给终态、也不告诉前端"这不归我管"，
于是消费者（前端 `pollTask`）只能无限等。这是 **ADR-0048（失败可见）+「生产者给全」** 的双重违反。

### 为什么"删掉取消"会让它恶化

现状下用户还有一条蹩脚出口：点「停止」⇒ 前端 `taskCtl.fail('已停止')` ⇒ 行变 `failed` ⇒
（该行无 `_relayPoll` 句柄 ⇒ `hasRelayPollHandle` 为 false ⇒ **前端能写进库**）⇒ 行收敛。
**删掉停止后这条出口消失** ⇒ 幽灵行永久 `running`；而任务中心的「清理失败/未知任务」入口
只清 `failed ∪ unknown`（`isTaskNeedsAttention`）⇒ **用户彻底无出口**。

### 两处修复（**本批唯一的非删除改动**，均为后端；零新增 UI / 终态 / 判据）

| # | 修什么 | 位置 | 为什么这样修 |
| --- | --- | --- | --- |
| **D16** | 回库分支：当行**既无 `poll_task_id` 也无 `_relayPoll` 快照**时返回 **`not-found`**（而非 `running`） | `relay-poll.ts:942-946`（`getGenerateStatus` 回库分支最后那个 `return {status:'running'}`） | 语义正确：**后端从未持有它** ⇒ "我这儿没这个任务"。前端 `relayAttachUntilDone` 的 `not-found` 分支立即终态 ⇒ `pollTask` 走失败分支 ⇒ `failTask` ⇒ **收敛**。⚠️ 前面的 `completed/failed/unknown` 分支在它之前 ⇒ 历史行不受影响；`pendingSubmit` 阶段有快照 ⇒ 不受影响；`chat` 不走 attach（`pollTask` 候选已按 `type` 过滤）⇒ 无影响 |
| **D17** | 扫描的 4 条跳过路径（A1–A4）改为**写终态 `unknown`**（而非只 `continue`） | `relay-poll.ts:990`（`!core`）· `:996-1003`（capability 非法）· `:1036`（无 taskId）· `:1037`（缺 poll） | 语义正确：跳过 = "我再也跟踪不了它" + 上游**可能已生成** ⇒ 正是 **`unknown`** 的定义（TD-08-24：付费任务专属第三终态）。⇒ 行落 `unknown` ⇒ `pollTask` 不接管（候选只 `running`/`pending`）⇒ 用户用**既有**「清理失败/未知任务」处理。⚠️ 这 4 条没有 `handle`（正因如此才跳过）⇒ 需直接 `upsertTask({task_id, status:'unknown', error_msg})`，**不能**走 `upsertUnknown(handle, …)` |

**副作用与声明**

- D16 后，B 类行会被前端标 `failed` 并弹红 toast，文案来自后端 `not-found` 的 error
  （现为「后端无此任务记录（句柄与任务行都不存在）」）—— **与事实不符**（行存在，是后端不持有）
  ⇒ **同批改文案**为「后端未持有此任务（可能未提交成功），已标记失败」。
- D16/D17 都**不改** `stopHandle` 与终态写入语义，只是把"跟踪不了"这件事**写下来**。
- **不做会怎样**：幽灵行永久 `running`，任务中心永远"生成中"，且**用户无任何出口**
  （清理入口只清 `failed`/`unknown`）⇒ 本批删掉取消会让这个既有问题**恶化**。

## Step 2 · 归因

**母体**：**「不等了」被当成了「取消了」** —— 一次"我不再等这个任务"的**前端意愿**，被实现成了
一条**看起来能终止任务**的链路（按钮 → abort → cancel 请求 → 后端置 failed），
而它**从未真正终止过任何东西**（上游照跑照计费）。

母体为什么会长出来：
1. **缺"能力边界"声明**：`stopHandle` 的名字（stop）与行为（只清本地定时器）不符 ⇒ 后续每一层都按"它真能停"来写注释、写文案、加 UI。
2. **失败被吞**（`relayCancel` 恒返 `ok:true`）⇒ 后端"没做成"从未暴露 ⇒ 没人发现这条链路是空的。
3. **前后端分叉**（前端 failed / 后端 running）被当成"正常"，因为没人追它的终局。

⇒ **症状 3 个同源**：① 假成功（判据没落进代码）；② 中止后前后端分叉且结果永不回填；③ 主动停止被记成 failed（语义归属错）。
⇒ **不编第二个母体**；`upsertFailed`/`stopHandle`/`pending` 分支**都对，不动**（`stopHandle` 只改注释 D15）。

## Step 4 · 定契

### 4.1 关键契约（谁拥有什么）

| 谁 | 拥有 | 不拥有 |
| --- | --- | --- |
| **节点** | 提交一次生成 + 显示结果 | **中止**（无按钮、无出口、无 prop） |
| **任务中心** | 已提交任务的列表 + **删除** | 发起生成 · **取消**（本批确立） |
| **后端句柄** | 轮询 + 终态写入（含预算到点） | 上游任务的生命周期（`stopHandle` 只停本地轮询） |
| **上游（lovart 等）** | — | **不受任何一方控制**：无取消接口，取消后照跑照计费 |

- **"不再等待"的表达**：编排的 `pending` 分支（`generationOrchestration:199-210`，**已实现，不改**）——
  预算耗尽 ⇒ 中性提示 + `start` 的 `finally` 清 loading ⇒ 行保持 `running` ⇒ `pollTask` 续 attach。
- **"不再显示"的表达**：`taskStore.removeTask:544-556`（前端移除 + `deleteTask` 真删后端行 + `deletedIds` 处理终态晚到）。
- **本批确立的负面契约**：**生成链路不提供中止入口**（写入 ADR-0060）。

### 4.2 三铁律自检

- **生产者给全**：本批**不新增消费者**，只删消费者 ⇒ 无"要而没给"的情形。
- **消费者只转发**：节点不调中止（D2/D4）；任务中心只调 `removeTask`；**零新增转发层**。
- **不越权**：前端**不再**替后端/上游决定"任务该结束"（这正是原链路的越权）；判死权归后端。

  if (!row.poll_task_id && !readRelaySnapshot(row)) {

    await upsertTask(db as never, {

      status: 'unknown',
      error_msg: `重启后无法恢复该任务（${reason}），可能已生成，请到任务中心确认`,

## 附 C · 审计留档（146 之前六轮复核的结论，压缩）

### C.1 「取消」买不到什么（实测）

| | 点「取消」 | **什么都不做** |
| --- | --- | --- |
| 省上游算力 / 退积分 | ❌ `stopHandle`（`relay-poll.ts:256-264`）零出站；`ai-relay/**` 无取消能力 | ❌ 同样买不到 |
| 省本机轮询 | ✅ 几乎可忽略 | 继续轮询到终态 |
| **已付费的结果** | ❌ **主动丢弃**（句柄已删 ⇒ 上游 `completed` 也不再写回） | ✅ **能拿到**：`pending` → 行留 running → `pollTask` 接管 → `completed` → **广播回填节点** |
| 任务中心呈现 | ❌ 显示"失败" + 进「需处理」角标 | 正常显示结果 |

### C.2 「取消」在各阶段的实际效力

后端**提交即返回**，出站由**句柄首轮**跑（`registerHandle` 末尾 `void runOnce()`，`:775` 立即跑）。

| 阶段 | 效果 |
| --- | --- |
| 前端正在 POST | ❌ 拦不住（`relaySubmit` 的 `httpRequest` 不接 signal，`relayProxy.ts:110-117`） |
| 已入队未出站 | ⚠️ 窗口 ≈ 0 |
| **正在上传参考图 / 建任务（段①）** | ❌ **停不了且最亏**：`runDirectSubmit`（`:534-570`）无 `stopped` 检查 ⇒ 上传跑完、任务照样创建；`:713` 才 return ⇒ 不再轮询 ⇒ **钱花了 + 结果丢** |
| 上游生成中（段②） | ⚠️ 只停本地轮询 ⇒ 结果丢失 |

⇒ **没有任何时点，取消优于"什么都不做"**。
