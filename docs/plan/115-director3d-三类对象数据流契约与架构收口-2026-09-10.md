## 一、为什么是这三类对象

3D 导演台的 K 帧**全部围绕三类对象**展开，它们是系统的核心：

| 类别 | `type` 取值 | 实体类型 `entity` | 可动画通道 |
|---|---|---|---|
| **人物** | `person` | `person` | transform + action + skeleton |
| **道具** | `box`/`sphere`/`arch`/`stairs`/`table`/`model`/`depthMesh`/… | `object` | transform |
| **摄像机** | （虚拟）`__shot_camera__` | `camera` | transform + lens |

> **关键认知**：**人物是唯一被注册表完整覆盖的一类。道具和摄像机是"特例"。**
> 所以它们难排查——不是因为复杂，而是因为**没有单一位置能说明"它有什么属性、谁在写它"**。

## 二、黑洞清单（三条同源病灶）

### 黑洞 1 · 契约不在类型里（导致今日 bug）

**证据（墓碑就在代码里）**：

```415:419:src/components/director3d/Viewport.tsx
  // 【注意】这里是 onUpdateCamera 的签名：(patch) 单参数，不是 SceneObject 那个 (id, patch)。
  // 曾误按双参数写成 onUpdate(CAMERA_ID, {...})，于是 App 侧收到的是字符串 'camera'，
  // 展开后 {...current, ...'camera'} 变成 {0:'c',1:'a',...}，position 从未被写入 →
  // 拖动摄像机位置永远存不进 state，松手后被 data 回写覆盖（表现为「拖一点就弹回」）。
```

**病根**：同一概念（更新对象属性）存在**两个签名**，且到 App 后喂给两个不通用函数：

| 消费端 | 签名 | App 侧落点 | 行号 |
|---|---|---|---|
| `SceneObject.onUpdate` | `(id, patch)` | `updateObjectById`（双写 objects + objectDrafts） | `Viewport.tsx:71` / `App.tsx:2323` |
| `CameraModel.onUpdate` | `(patch)` | 内联 `setCamera`（只写 camera） | `Viewport.tsx:419` / `App.tsx:2325` |
| `Inspector.onUpdateObject` | `(patch)` | `updateSelected` → `updateObjectById` | `Inspector.tsx:83` / `App.tsx:2432` |
| `Inspector.onUpdateCamera` | `(patch)` | 内联 `setCamera` | `Inspector.tsx:84` / `App.tsx:2433` |

**为什么静默**：`{ ...current, ...'camera' }` 是**合法 JS**（字符串展开成 `{0:'c',1:'a',…}`），
`tsc` 不报（参数类型是 `Record<string, unknown>`），运行时只表现为「拖一点就弹回」。

> **AI 困境**：AI 读 `Viewport.tsx` → 看到 `onUpdate={onUpdateCamera}` → 跳 `App.tsx` 看箭头函数 →
> **它建立了正确的连接**。它唯一不知道的是：那段注释说的是「曾经犯过的错」，不是「现在的约束」。
> 因为**约束没有写在类型里**，AI 无法从代码本身判定对错。

### 黑洞 3 · 求值路径分叉

**摄像机有 3 条求值分支**（`App.tsx:474-481`）：

```ts
const animatedCamera = useMemo(() => {
  const snap = cameraPathSnapshot(currentFrame);        // 分支1：路径
  if (snap) return { ...camera, ...snap };
  return countChannelKeyframes(keyframes)
    ? cameraAtFrame(keyframes, currentFrame, camera.aspectRatio)  // 分支2：关键帧
    : camera;                                            // 分支3：基线
}, [camera, cameraPathSnapshot, currentFrame, keyframes]);
```

**道具只有 1 条入口** `objectAtFrame`，但内部 `position` 有 2 个来源
（路径 `pathPositionAtFrame` vs transform 通道），靠 `pathActive` 二选一
（`project.ts:1289-1299`）。

**AI 困境**：判断「摄像机位置谁说了算」需同时理解 3 个分支的关系；
判断「道具位置谁说了算」需理解 2 个来源的优先级。

## 三、数据流契约（本文档核心 · 定稿后代码向此对齐）

### 契约 1 · 对象标识

```
每个对象 = { id, type, entity }
  id      : string，唯一标识。摄像机固定为 CAMERA_ID = '__shot_camera__'（project.ts:116）
  type    : string，具体模型类型，决定「怎么渲染 + 默认属性」（box/arch/model/person/…）
  entity  : 'person' | 'object' | 'camera'，决定「K 帧进哪个通道体系」
```

**规则**
- C1.1 `type` 与 `entity` **解耦**。`type` 管渲染，`entity` 管通道。
- C1.2 摄像机的 `entity` 恒为 `'camera'`，`type` 恒为 `'camera'`，两者一致以便统一处理。
- C1.3 `entity` 由 `type` 经**类型注册表**查出，禁止 `objects.find(...)?.type || 'object'` 式兜底猜测
  （替换 `App.tsx:429` 的 `entityTypeFor`）。
- C1.4 禁止用通道名反推实体类型（`inferChannelEntityType`，`project.ts:811`）——保留仅作旧数据迁移兜底。

### 契约 2 · 属性登记

**唯一真相源 = `PROPERTY_REGISTRY`（`project.ts:311`）**。任何属性**必须**先登记再使用。

| layer | 语义 | 是否进通道 | 是否被关键帧覆盖 |
|---|---|---|---|
| `animatable` | 可动画的量，靠关键帧驱动 | 是（必须声明 channel） | 是 |
| `objectState` | 对象级开关，勾选即整段生效 | 否 | **否**（L2 沿基线强制覆盖） |
| `config` | 纯配置/显示，与动画无关 | 否 | 否 |

**规则**
- C2.1 新增属性 = 在注册表加一行。**禁止**在求值器/Inspector/录制函数里硬编码判断属性。
- C2.2 `animatable` 必须声明 `channel`，否则 `deriveChannels` 抛错（`project.ts:355`）——已有约束，保留。
- C2.3 所有属性**必须**有归一化规则（`normalizeCameraField` / `normalizeObjectField`，`project.ts:646,795`）。
- C2.4 **本次需补登记的字段**（详见 §4 动作 A2）：
  `visible`、`scaleAxisLocks`、`proportionalScale`、`url`、`parts`、`depthMapUrl`、`depthSettings`、`type`。

### 契约 3 · 更新写入（单入口）

```
所有属性写入统一走：  onUpdateObject(id, patch)
  · 人物：onUpdateObject(personId, patch)
  · 道具：onUpdateObject(objectId, patch)
  · 摄像机：onUpdateObject(CAMERA_ID, patch)     ← 不再是 onUpdateCamera(patch)
```

**规则**
- C3.1 **全系统只有一个更新签名**：`(id: string, patch: Partial<ProjectObject>) => void`。
- C3.2 禁止出现 `onUpdate(patch)` 形式（摄像机专属签名）。`CameraModel`、`Inspector` 的
  `onUpdateCamera` 一律收敛到 `onUpdateObject(id, patch)`。
- C3.3 `patch` 的 key **必须是注册表中该 `entity` 的合法字段**。开发期加断言，非法字段告警并附调用栈。
- C3.4 写入落点按 `entity` 分派，**对三类对象语义一致**：
  - `entity ∈ {person, object}` → 写 `objects` + `objectDrafts`（草稿层）
  - `entity === 'camera'` → 写 `camera`
  > 分派由**单一函数**完成，不是散在 App 里的内联箭头。

### 契约 4 · 求值（单入口 + 来源可判定）

```
求值统一入口：  evaluateAtFrame(object, tracks, frame, fps, path)
  · 人物：entity='person' → transform → action → skeleton → L2
  · 道具：entity='object' → transform → L2
  · 摄像机：entity='camera' → transform → lens → L2      ← 不再有独立三分支
```

**规则**
- C4.1 三类对象走**同一个** `synthesize*` 流程，通道数不同而已。
- C4.2 「路径」是**位置来源**的一个可选替换，与通道同级，**不进通道**。
  摄像机路径（`cameraPathSnapshot`）与道具路径（`pathActive`）语义对齐：**路径启用时位置唯一由路径提供**。
- C4.3 通道合成顺序 = `ENTITY_CHANNELS` 注册顺序（`project.ts:349-363`），**每字段唯一归因**。
- C4.4 `objectState` 字段在合成末端由基线强制覆盖（L2，`project.ts:1316`），**保证开关不被关键帧冻结**。

### 契约 6 · 轨道写入（唯一 op 语义）

```
所有关键帧轨写操作统一表达为 operation，经 applyTrackOperation(channels, op) 执行：
  对象轨 → writeObjectTrack(tracks, id, op)   （额外：写空自动移除条目）
  相机轨 → applyTrackOperation(channels, op)  （相机轨是裸通道结构，无条目字典）
```

**规则**
- C6.1 **禁止**在 tracks.ts 手写「先 `removeChannelFrames` 再 `upsertChannelKeys`」拼装
  ——那是重造 batch 语义，两条轨道会各自实现一份，漂移后只在一条轨道上复现。
- C6.2 需要「先删后插」时用 `{ op:'batch', steps:[...] }`（原子，M4-C5）。
- C6.3 `operation` 的 6 种 op（upsert/remove/move/interpolation/clear/batch）是**封闭集合**，
  新增写操作优先组合现有 op，而非新造。

### 契约 5 · 渲染分派

```
渲染器由 type 经类型注册表查出：renderer(type) → 组件
  person     → MixamoPersonModel
  model      → ImportedModel
  depthMesh  → DepthMeshModel
  box/arch/… → PrimitiveModel(type)
```

**规则**
- C5.1 `Viewport.tsx:258-292` 的 if/else 链**收敛为查表**。
- C5.2 新增一个道具类型 = **在类型注册表加一行**，不改 Viewport。
- C5.3 `Viewport` 只从注册表取「渲染器 + 该渲染器需要的字段」，不做类型判断。

### 🔴 重大修复 · 全屏模态层未挡住 React Flow 删除键

**事故**：在 3D 导演台（`FullscreenShell` 全屏层）里按 Delete/Backspace，

```

React Flow deleteKeyCode（App.tsx:1388）               → 无守卫，内部自挂监听    ❌
```

React Flow 在 `useKeyPress` 内**自己** `window.addEventListener`，**完全绕过** `useCanvasShortcuts`，
因此没有任何机会查询 `hasModalLayer()`。这与 modalLayer.ts 文件头记载的
「ImageEditor 里按 ⌘Z 撤掉画布节点」是**同源事故**，只是一个走查询、一个必须走订阅。

**修复**（`modalLayer.ts` + `App.tsx`）：
1. `modalLayer.ts` 新增 `subscribeModalLayer(listener)` —— 层开合时通知订阅者
2. `registerLayer` 的登记/注销处调用 `notifyLayerChange()`
3. `App.tsx` 用 `useSyncExternalStore(subscribeModalLayer, hasModalLayer)` 订阅
4. `deleteKeyCode={modalLayerOpen ? null : DELETE_KEY_CODE}` —— 全屏层开着时**从源头拆掉监听**

**为什么必须订阅而不能查询**：`deleteKeyCode` 是**声明式 props**，它的开关在渲染时就被决定了，

## 十一、第三轮：数据出入口审计（2026-09-10）

对**持久化 / 历史 / 导出 / 测试**四个此前未审的维度做了系统扫描。

### 🔴 已修复 · hydrate 竞态导致用户编辑静默丢失

**风险等级：数据丢失（不可恢复）**

**链路**（`App.tsx:646`）：
```
挂载 → 同步种子读 localStorage（显示旧内容）
     → 异步 hydrate 拉 KV（可能数百 ms ~ 秒级）
     → 完成后 applyProjectSnapshot(project) 无条件覆盖全部 state
```

**缺陷**：`applyProjectSnapshot`（`App.tsx:603`）是**无条件覆盖**，`alive` 标志
（`:647/650`）只防「组件卸载 / key 变化」，**不防「用户已编辑」**。

**后果**：用户在 hydrate 返回前动了对象/关键帧 → KV 一到 → **那批编辑被静默抹掉**。

**修复**（`App.tsx:654`）：hydrate 完成时检查历史栈，`history.past.length > 0`
即「用户已发生过可撤销编辑」→ 放弃 KV 覆盖，保留用户现场（随后由本地自动保存写回）。

**为什么判据是 `past` 而不是 `last`**：
`last` 是基线，startup 首次副作用就会设置（`App.tsx:574`），**恒非空**，
用它作判据会导致 hydrate **永远跳过**（破坏原有 KV 覆盖功能）。
`past` 有记录才是真的发生过一次用户编辑。

**验证**：`tsc` 0 error / `oxlint` 0 warning。

### ⚠️ 已定位 · 两套存储的无时间戳比较（**未修，需产品决策**）

`pickProjectSource`（`d3dPersistence.ts:215-222`）的源选择**只看存在性，不看时间戳**：

```
KV 有值        → 用 KV（无论新旧）
KV 空 + 本地有 → 用本地并写回 KV
```

**两个不一致窗口**：
1. **KV 旧、localStorage 新**（KV 写失败降级 localStorage 后）：下次 hydrate 优先返回
   **旧的 KV**，localStorage 里较新的降级副本被**判为过期而忽略** → **丢最新编辑**。
2. **启动瞬间**：`readCachedProject` 只读 localStorage（`project.ts:1136`），UI 先显示旧内容，
   直到 hydrate resolve 才切到 KV。期间用户看到/编辑的是旧数据（叠加上面已修的竞态守卫）。

**为何不现在修**：修法有多个方向（加时间戳字段 / 加版本号 / KV 失败时标记「本地更新」），
**需要产品决策选择哪种**，且涉及持久化格式变更（`PROJECT_VERSION` 可能需 +1）。
属「有明确收益但要先定方向」，不是纯代码问题。

### ✅ P2-1 · 摄像机求值三分支收口（2026-09-10 完成）

**原判断修正**：此前文档把 A3/P2-1 标为「因无法逐帧验证而搁置」。
**这个判断是错的**——逐帧验证**可以**做出来（纯函数级测试即可），护栏建好后它就是零风险重构。

**发现的关键事实**：所谓「三分支」在 App.tsx 里有**两处独立实现**，不是一处：

| 实现点 | 用途 | 原逻辑 |
|---|---|---|
| `animatedCamera`（`App.tsx:459`） | 渲染用 | 路径 → 关键帧 → 基线 |
| `setCameraAtFrame`（`App.tsx:933`） | 播放/拖帧写回 state | **又一份**路径 → 关键帧 → 基线 |

**这才是「位置谁说了算」没有唯一答案点的真正原因**：两个实现一旦漂移，
就会出现「播放时对、拖帧时不对」这类极难排查的分叉。

**收口做法**：
1. 新增 `project.ts` 的 `cameraAtFrameWithPath(camera, keyframes, path, frame, totalFrames)`
2. 两处实现点**共用**它（`animatedCamera` 与 `setCameraAtFrame` 都改为接线）
3. 删除死代码 `cameraPathSnapshot` 与两个失效导入
4. 保留 `setCameraAtFrame` 特有的 L2 处理（`targetMode`/`targetId` 恒沿基线）

**行为等价性护栏**（`tests/unit/director3d.cameraAtFrameWithPath.test.ts`，19 tests 全绿）：
- 逐字复刻「收口前三分支」为对照组 `legacyCameraAtFrame`
- **110 帧 × 2 种 targetMode × 5 个场景 = 1100 次逐帧比对**，`toEqual` 全等
- 场景覆盖：仅路径 / 仅关键帧 / 路径+关键帧 / 都无 / 路径非零起点
- 另覆盖易被合并顺序改坏的细节：
  - 路径分支用**当前基线**打底（`focalLength` 保持 85 而非 initialCamera 的 42）
  - 关键帧分支的 `aspectRatio` 来自当前 camera
  - `object` 模式下路径**不给 rotation**
  - 控制点 < 2 时回退
  - 无任何动画时**返回同一引用**（保证 memo 不误触发）

**验证**：`tsc` 0 error / `oxlint` 0 warning / vitest 19 passed。

### ✅ 契约 C6 · 轨道写入口统一（2026-09-10 完成）

**问题**：关键帧轨道写操作有**两套实现**：

| 轨道 | 收口前 |
|---|---|
| 对象轨 | 经 `writeObjectTrack(tracks, id, op)`，带完整 op 语义（upsert/remove/move/interpolation/clear/batch） |
| 相机轨 | `moveCameraFrames` / `bakeCameraPath` **各自手写** `removeChannelFrames(...)` + `upsertChannelKeys(...)` |

后两者是在**重造 batch 语义**。两份实现一旦漂移（例如某处忘了先删旧帧），
就会出现「只在相机轨留下幽灵帧、对象轨不会」这类**单轨道复现**的怪问题——
与 `onUpdateCamera` 是同构的病（同一概念两个入口），只是发生在 K 帧写入层。

**收口做法**：
1. `project.ts` 抽出 `applyTrackOperation(channels, operation)` —— op 语义的**唯一执行器**
2. `writeObjectTrack` 改为复用它（保留其特有的「写空自动移除条目」语义）
3. `tracks.ts` 相机轨 6 个函数全部改为表达成 operation 经 `applyTrackOperation` 执行
4. `bakeCameraPath` 从「循环逐个 upsert」改为**单次原子 batch**（与 `bakeObjectPath` 完全同构）
5. 删除 `tracks.ts` 里 4 个失效的底层原语导入

**护栏**（`tests/unit/director3d.trackWriteParity.test.ts`，11 tests 全绿）：
- 逐字复刻「相机轨收口前手写实现」为对照组，6 个操作逐一 `toEqual` 等价
- **对等性护栏**（最能抓漂移）：批量平移「目标帧被另一待移动帧占据」场景，
  两条轨道必须**同为 `[15, 20]`**——若某条忘了先删旧帧就会退化成 `[20]`（丢帧）
- 路径烘焙「旧路径帧不留幽灵」两条轨道同构验证
- `applyTrackOperation` 的 move/clear/batch 原子性

**验证**：`tsc` 0 error / `oxlint` 0 warning / **全量单测 1962 passed（136 files）**。

### 📝 新发现的次要问题（已记录，未修）

## 七、明确否决的方案（避免后人重提）

| 方案 | 否决理由 |
|---|---|
| **诊断面板 / 调试浮层** | 使用者是 AI 而非人。AI 排查**只有一个入口——读代码**，不能拖一下试试、不能看控制台。面板上的字 AI 看不到，对人（用户）也无人力去盯。**已明确否决**。 |
| **引入 zustand / context 替换现有 useState 群** | `App.tsx` 的状态集中虽是单一真相源，替换风险大、收益不明。真问题是「派生关系不可见」，不是「状态放哪」。 |
| **为粗模建重型注册表（OBJECT_TYPE_REGISTRY）** | 粗模是静态布景，新增频率低。为「永不变化的东西」建抽象是过度设计。**但 A4 的轻量查表不算**——它顺带治 if/else 的散落。 |

> **设计哲学（本文档的元原则）**：
> **能不让问题产生，就不要先做工具去观察它。**
> **能靠类型系统强制，就不要靠文档和纪律。**
