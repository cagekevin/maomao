# 11 - localTool 路由表重构方案

> 日期：2026-08-17
> 范围：`localTool/src/index.ts` 主路由 + 新增 `localTool/src/router.ts`
> 关联 skill：`nodejs-backend-patterns`（中间件 / 路由组织 / API 设计）

## 1. 背景与目标

### 现状
`index.ts` 的 `handleRequest` 用约 **190 行** `if (pathname === '...' && method === '...')` 逐条手写匹配（`index.ts:220-451`）。问题：

- 每加一个接口要复制粘贴 4 行样板（`if` + `return await handleXxx(...)`）。
- 注册顺序敏感（具名路由必须早于 catch-all 透传），容易踩坑。
- 无法统一挂载中间件（鉴权、请求日志、body 大小限制、错误脱敏）——
  这正是 `nodejs-backend-patterns` 强调的"框架中间件模式"。

### 目标
1. **减负**：`handleRequest` 主路由从 ~190 行收敛到 ~30 行调度逻辑。
2. **声明式**：所有路由集中在一张表，新增接口 = 加一行配置，不再碰分发逻辑。
3. **可挂中间件**：路由表支持 `middleware` 数组，为后续「统一鉴权 / 错误脱敏 / body 限制」留好接入点（本次只搭骨架，不强制实现）。
4. **零行为变更**：重构后所有端点路径、方法、响应完全不变，现有前端与测试不受影响。
5. **保留顺序语义**：精确路由 > 正则路由 > catch-all 透传 > 404，与原 `if` 链优先级一致。

### 非目标（本次不做）
- 不引入 Express/Fastify（保持零运行时依赖的设计选择）。
- 不实现具体中间件逻辑（鉴权/脱敏仅预留钩子）。
- 不改任何 `routes/*.ts` handler 的签名与实现。

## 3. 路由表数据模型

> ⚠️ **类型约束（审计修订 #1）**：现有 handler 第三参数**类型不统一**，实测有 5 种：
> - `url: URL`：`handleGatewayTask`(`system.ts:54`)、`handleWorkflowAppsByProject`(`platform.ts:27`)、`handleOfficialVipCheck`(`index.ts:360`)
> - `id: string`：`handleProviderFetchModels`(`providers.ts:464`)、`handleAgentChat`(`agentChat.ts:143`)
> - 无第三参：绝大多数 handler
>
> 因此 `Handler` **不约束第三参**，统一以 `...args: unknown[]` 透传；带参数提取的 handler 一律用 §5 闭包适配，**禁止**直接把 `string` 第三参 handler 塞进 `url: URL` 类型字段（否则 tsc 报错）。

```ts
// router.ts
import type { IncomingMessage, ServerResponse } from 'node:http';
import type { URL } from 'node:url';

// 第三参含义由具体 handler 决定，router 不约束；带参数提取者用闭包适配（见 §5）
export type Handler = (
  req: IncomingMessage,
  res: ServerResponse,
  ...args: unknown[]
) => void | Promise<void>;

export interface Route {
  method: 'GET' | 'POST' | 'PUT' | 'DELETE' | 'OPTIONS' | '*';
  // 精确字符串（全等，如 '/api/status'）、RegExp（如 /^\/api\/agent\/[^/]+\/chat$/）
  // 或 'startsWith:' 前缀（如 '/api/workflow-apps/by-project/'，见 §5）
  pattern: string | RegExp;
  handler: Handler;
  // 可选：该路由专属中间件（按顺序执行，返回 false 则中断）
  middleware?: RouteMiddleware[];
  // 可选：标记为 catch-all 透传（命中后必须复刻 if(passthrough())return; else 404，见 §6）
  catchAll?: boolean;
}

export type RouteMiddleware = (
  req: IncomingMessage,
  res: ServerResponse,
  url: URL,
) => boolean | void | Promise<boolean | void>;
```

## 4. 匹配器实现

```ts
// router.ts
export function matchRoute(
  routes: Route[],
  method: string,
  pathname: string,
): { route: Route; params?: RegExpMatchArray } | null {
  const m = method.toUpperCase();
  for (const route of routes) {
    if (route.method !== '*' && route.method !== m) continue;
    if (route.catchAll) return { route };           // catch-all 永远命中（必须放表末）
    if (typeof route.pattern === 'string') {
      if (route.pattern === pathname) return { route };   // 精确全等
      // startsWith 前缀匹配（审计修订 #7）：约定以 '/api/...' 真实前缀登记，
      // 在登记处即转成锚定正则（见 §5），这里不再特殊判断。
    } else {
      const matched = pathname.match(route.pattern);
      if (matched) return { route, params: matched };
    }
  }
  return null;
}
```

> 顺序即优先级：表中**靠前的先匹配**，因此精确路由放前、正则放中、catch-all 透传作为表中的**最后一项且标 `catchAll: true`**（其 `pattern` 用永远命中的正则 `/.*/`），404 由 `index.ts` 在 `matchRoute` 返回 null 时兜底。

```ts
// ... 其余 import 同 index.ts

  { method: 'POST', pattern: '/api/proxy', handler: handleProxy },

  // ── 正则路由（带路径参数，第三参为 url，直接透传）──
  { method: 'GET',  pattern: /^\/api\/v1\/gateway\/task\/[^/]+$/, handler: handleGatewayTask },
  { method: 'GET',  pattern: /^\/api\/agent\/[^/]+\/vip-check$/,  handler: handleOfficialVipCheck },

  // ── startsWith 前缀路由（审计修订 #7）：转锚定正则 ──
  { method: 'GET',  pattern: /^\/api\/workflow-apps\/by-project\/.*/, handler: handleWorkflowAppsByProject },

  // ── 正则路由（第三参为 string id，必须闭包适配，审计修订 #1）──
  {
    method: 'POST',
    pattern: /^\/api\/agent\/([^/]+)\/chat$/,
    handler: (req, res, ..._rest) => {                  // 第三参 router 不传，自行 match
      const m = ((req.url || '').split('?')[0]).match(/^\/api\/agent\/([^/]+)\/chat$/);
      return handleAgentChat(req, res, m ? m[1] : '');
    },
  },
  {
    method: 'POST',
    pattern: /^\/api\/providers\/([^/]+)\/fetch-models$/,
    handler: (req, res, ..._rest) => {
      const m = ((req.url || '').split('?')[0]).match(/^\/api\/providers\/([^/]+)\/fetch-models$/);
      return handleProviderFetchModels(req, res, m ? m[1] : '');
    },
  },

  // ── 双路径单 handler（审计修订 #3）：拆两个表项 ──
  { method: 'POST', pattern: '/api/assets/upload',        handler: handleUpload },
  { method: 'POST', pattern: '/api/upload/app-asset',     handler: handleUpload },

  // ── catch-all 透传（必须最后，标 catchAll，审计修订 #2）──
  { method: '*', pattern: /.*/, handler: handlePassthrough, catchAll: true },

```

> `handler` 接收 `(req, res, ...args)`。带 `string id` 第三参的 handler 在闭包内自行 `req.url` 提取参数（不依赖 router 透传 `url`，因 router 不保证字段顺序），这样 `routes/*.ts` 的 handler 签名完全不动。

## 6. index.ts 改造（目标形态）

```ts
// index.ts（改造后 handleRequest 核心段）
import { routes, matchRoute } from './router.js';

async function handleRequest(req, res): Promise<void> {
  const url = new URL(req.url || '/', `http://127.0.0.1:${PORT}`);
  const pathname = url.pathname;
  const method = (req.method || 'GET').toUpperCase();

  // ── 阶段 0：CORS + OPTIONS 预检（审计修订 #5：必须在路由匹配之前，不放路由表）──
  res.setHeader('Access-Control-Allow-Origin', '*');
  // ... 其余 CORS 头 + OPTIONS 提前 return（保留原逻辑）

  // ── 阶段 1：静态文件（保留，优先级高于路由表）──
  if (method === 'GET' && pathname.startsWith('/files/')) {
    if (handleStaticFile(req, res, pathname)) return;
  }

  if (!SILENT_LOG_PATHS.has(pathname)) {
    console.log(`[${method}] ${pathname}`);
  }

  try {
    const matched = matchRoute(routes, method, pathname);

    // ── 阶段 2：具名路由 + 中间件（按表顺序）──
    if (matched && !matched.route.catchAll) {
      for (const mw of matched.route.middleware ?? []) {
        const ok = await mw(req, res, url);
        if (ok === false) return;
      }
      await matched.route.handler(req, res, url);
      return;
    }

    // ── 阶段 3：前端页面托管（审计修订 #4：必须在 catch-all 之前）──
    if (method === 'GET' && !pathname.startsWith('/api/')
        && !pathname.startsWith('/plugin/') && !pathname.startsWith('/files/')) {
      if (handleFrontendPage(res, pathname)) return;
    }

    // ── 阶段 4：catch-all 透传（审计修订 #2：必须复刻原 if(passthrough())return; else 404）──
    if (matched?.route.catchAll) {
      if (await handlePassthrough(req, res, url)) return;   // 成功透传才 return
      sendError(res, 'Not Found', 404);                     // 失败才 404（原 index.ts:456）
      return;
    }

    // ── 阶段 5：完全未命中 → 404 ──
    sendError(res, 'Not Found', 404);
  } catch (e) {
    console.error(`[error] ${pathname}:`, e);
    sendError(res, (e as Error).message, 500); // TODO: 后续按 nodejs-backend-patterns 脱敏
  }
}
```

> **顺序铁律（审计修订 #4）**：阶段 2(具名) → 阶段 3(前端托管) → 阶段 4(catch-all) → 阶段 5(404)。
> 任何改动都不得把阶段 4 提前到阶段 3 之前，否则 `/files/x`、`/plugin/y` 未命中路径无法正确 404。
> **catch-all 红线（审计修订 #2）**：`handlePassthrough` 对 `/files/`、`/plugin/` 未命中路径返回 `false`，
> 绝不可写 `return await matched.route.handler(...)` 无脑返回，否则 404 逻辑丢失。
