# 排查：画布图片节点「发送到素材库」按钮不落盘

> 目的：供第三方审计。本文件只记录**已读代码确认的事实**与**未闭合的疑点**。
> 规则：凡未亲眼读到代码/未由用户确认的结论，一律不写。
> 用户已确认的事实只有一条：**「上传和拖拽到素材库面板」是通的（能落盘进 materials）**。
> 用户已确认的现象：**画布图片节点点「发送到素材库」按钮，不落盘到 materials 文件夹**。

---

## 一、已知的两条链路（已读代码确认）

### 链路 A：素材库面板「上传 / 拖拽」（用户确认：通）
文件：`src/components/base/AssetLibrary.jsx`

- `handleFiles`（约 199–219 行）：遍历 `File` 列表，对每个文件构造 `FormData`：
  - `fd.append('subfolder', currentFolder)`（面板在素材池时 `currentFolder === 'materials'`）
  - `fd.append('file', f, f.name)`（原始文件，multipart）
  - `httpRequest(\`${API_BASE}/api/files/upload\`, { method:'POST', body: fd, retries:0 })`
- 上传成功后 `reset(true)` 触发 rescan + 拉取。

落盘形态：**multipart 上传，subfolder=materials**。后端对应 `saveFile` 分支（localTool `files.ts`）。

### 链路 B：画布图片节点「发送到素材库」按钮（用户确认：不通）
文件：`src/components/nodes/ImageNode.jsx` → `src/components/base/assetStore.js`

- `ImageNode` 按钮 `onClick`：`sendToAssetLibrary(url, { name, type })`，其中
  `url = toAbsoluteFileUrl(data.imageUrl || data.url || '')`（约 39 行）。
- `sendToAssetLibrary`（`assetStore.js` 约 151–170 行）：
  - `folder` 默认 `'materials'`。
  - `if (url && !url.startsWith('blob:')) persistUrlToBackend(url, folder)`（约 163 行）。
  - **注意**：blob: 在此被直接跳过，不落盘。
- `persistUrlToBackend`（`assetStore.js` 约 173–195 行）：
  - `url.startsWith('data:')` → `saveInlineToLocal(url, folder)`（走 filesApi 的 multipart，subfolder=folder）。
  - 否则（http）→ `httpRequest(\`${API_BASE}/api/files/upload\`, { json: { fileUrl:url, subfolder:folder } })`（约 182–189 行，**JSON 分支**）。
  - 之后 `rescanResources()`。

落盘形态（http 分支）：**JSON `{ fileUrl, subfolder }` 上传**。后端对应 `saveRemoteUrl`（localTool `files.ts`）。

## 二、两条链路的结构性差异（已读代码确认）

| 维度 | 链路 A（面板，通） | 链路 B（发送按钮，不通） |
|---|---|---|
| 上传方式 | multipart `FormData`，字段 `file` + `subfolder` | JSON `{ fileUrl, subfolder }`，无 `file` 字段 |
| 后端入口 | 同一 `/api/files/upload`，但 `multipart` 分支（`saveFile`） | 同一 `/api/files/upload`，但 `json` 分支（`saveRemoteUrl`） |
| subfolder 来源 | 面板当前目录（materials） | `sendToAssetLibrary` 默认 `folder='materials'`，`persistUrlToBackend` 用 folder（两链路一致，均为 materials，**非疑点 1 所说的 HISTORY_LOCAL_FOLDER 硬编码**） |
| 对 blob: 处理 | 不适用（面板拿到的是真实 File） | 原第 163 行 `if (!url.startsWith('blob:'))` 直接跳过，**不落盘**（确为断点，已修复） |
| 复用 filesApi 封装 | 是（面板自己拼 FormData，但走同一后端） | data: 分支复用 `saveInlineToLocal`；http 分支是 `assetStore` 内 `httpRequest` 调同一 `/api/files/upload`（字段等价，非独立逻辑，已标注） |

**待审计确认**：两条链路的差异是否就是断点所在，需逐项核对后端对两个分支的真实处理。

## 三、后端对应实现（已读代码确认，仅列事实）

文件：`localTool/src/routes/files.ts`
- `handleUpload` 按 `Content-Type` 分流：
  - `multipart/form-data` → `saveFile`（链路 A 走这）。
  - `application/json` → `handleUploadJson` → `saveRemoteUrl`（链路 B 的 http 分支走这）。
- `saveRemoteUrl`（约 106 行起）：`new URL(fileUrl)` 取 basename；`resolveUploadTarget(subfolder, ...)` 拼 `uploadDir/materials/...`；`writeUploadBufferAt` 落盘。
  - **待审计**：`saveRemoteUrl` 对 `data:` 协议 `new URL('data:...')` 会抛异常（data: 非合法 URL），但链路 B 的 data: 分支已走 `saveInlineToLocal` 绕开，不影响。

文件：`localTool/src/utils/fileStore.ts`
- `resolveUploadTarget` / `writeUploadBufferAt` 均用 `subfolder` 拼 `uploadDir/<subfolder>/...`，逻辑确认无误。

文件：`localTool/src/routes/resources.ts`
- `rescanResources`：扫描 `uploadDir` 顶层目录 → 各子目录 → 入库，`folder` 字段取相对路径（顶层即 `materials`）。
- **待审计**：rescan 后是否有「孤儿清理」会误删刚写入、但磁盘路径暂时不可见的记录（约 172–179 行区间，需审计者逐字核对）。

## 四、审计结论（已逐字核对源码，疑点全部闭合）

| 原疑点 | 审计结论 |
|---|---|
| ① 链路 B 裸 `httpRequest` 与 `filesApi.saveRemoteUrl` 是否一致 | **已演进，二者字段等价**：`persistUrlToBackend` 调同一 `/api/files/upload`，data: 走 `saveInlineToLocal`，http 走 `fileUrl` JSON，与 `filesApi.saveResultToTasks` 范式一致。**非断点**。文档当初的"未复用 saveRemoteUrl"描述已过时（代码已演进）。 |
| ② `ImageNode` 发出的 `url` 形态 / blob 是否触发跳过 | 确证：`sendToAssetLibrary` 原第 163 行 `if (!url.startsWith('blob:'))` 对 `blob:` **静默跳过、不落盘**。正常路径（上传/压缩后写回）产生的是 `data:` 或 `http://127.0.0.1:18080/files/...`，能落盘；但任何 `blob:` 来源的节点点发送都会丢失。**这是真断点，已修复**。 |
| ③ `saveRemoteUrl` 对本站 `18080/files/...` 内部地址 | 确证：`new URL` 可解析，`fetchWithProxy` 对 `127.0.0.1` 直连本机成功下载，落 `materials/`。**非断点**。 |
| ④ 落盘成功但 rescan 未索引 / 面板未读 | rescan 把 `upload/materials/` 扫入 `resources` 表，面板读 `/api/resources` 可见。`emitAssetSent`→`onAssetSent`→`setFolder`→reset(rescan) 桥接已通。**非根因，但链路 A 上传后缺 rescan（见修复 3）已补**。 |
| ⑤ 孤儿清理误删 | **不成立**：`runReferenceGc`（orphanGc.ts 128-145）把 `resources` 表所有 url 纳入引用集，素材库里"未放画布"的图受保护；rescan 内置弱清理只删"磁盘已不存在"记录。文档第三节的担忧经验证不实。 |

**最终根因（三处）**：
1. `blob:` URL 被 `sendToAssetLibrary` 短路丢弃，不落盘（确证断点）。
2. `persistUrlToBackend` 落盘失败被 `logger.warn` 静默吞（第 194 行），用户"点了没反应"，无法感知失败。
3. **目录错配**：素材库真正读取的目录是 `migrated`，而两条链路默认 `materials`，落盘到 `materials/` 后面板（读 `migrated`）看不到，体感"不落盘"。`materials` 是误留目录，已统一删除、不存在。
4. 链路 B（节点发送）走 JSON `{fileUrl}` 分支（`saveRemoteUrl`）；链路 A（面板上传）走 multipart 分支（`saveFile`）。两链路形态不一致，排查与维护成本高。

## 五、已实施的修复（2026-08-19，最终状态）

文件：`src/components/base/assetStore.js`
- `sendToAssetLibrary`：去掉 `blob:` 短路，统一进入 `persistUrlToBackend`；默认 `folder` 由 `'materials'` → `'migrated'`。
- `persistUrlToBackend`：
  - 新增 `blob:` 分支：`fetch(blobUrl)` 取 Blob → `uploadFileToLocal`（FormData）落盘，与 data:/http 分支一致。
  - http 分支由 JSON `{fileUrl}` 改为**模仿链路 A 的 multipart 上传**（`fetch→Blob→uploadFileToLocal`），消除两链路差异。
  - 失败分支由 `logger.warn` 改为 `toastError` 透出具体原因，用户可感知。
  - 原 `logger.info('[SEND]/[PERSIST]...')` 详细排查日志改为 `logger.debug(...)`，仅 `DEBUG_ASSET` 开启时输出（默认安静）。
- `FOLDERS` 数组 `'materials'` → `'migrated'`（label「素材池」→「素材库」）；示例数据 folder 同步改 `migrated`。

文件：`src/components/base/filesApi.js`
- `uploadFileToLocal` 加 `logger.debug('[UPLOAD] 准备/完成')`（开关控制）。

文件：`src/components/base/AssetLibrary.jsx`
- `FOLDER_PILLS` `'materials'` → `'migrated'`；默认 `useState('migrated')`、上传 subfolder=migrated。
- `handleFiles` 上传成功后 `emitAssetSent(currentFolder)`，复用与链路 B 一致的"切目录 + rescan"刷新机制，修复上传后列表不刷新。

文件：`src/components/base/config.js` / `logger.js`
- 新增 `DEBUG_ASSET` 开关（`VITE_DEBUG_ASSET=1` 或 `window.__DEBUG_ASSET=true` 开启）+ `logger.debug` 级别（仅开关开启时 console 输出，不上报后端）。

**修复后验证点**：节点 `data.imageUrl` 为 data:/http/blob 任一形态，点「发送到素材库」均落盘到 `migrated/` 并实时出现在面板；任意落盘失败弹出明确错误 toast。无 `materials` 目录残留（`src/` 已全量 grep 无引用）。
