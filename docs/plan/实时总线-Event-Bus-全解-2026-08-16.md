## 〇、TL;DR

- **eventBus 是一张极简的发布/订阅表**（`Map<event, Set<fn>>`），不存状态，只广播瞬时动作。
- **共 6 个事件**，按用途分三类：

| 事件 | 发布方 | 订阅方 | 用途 | 状态 |
|---|---|---|---|---|
| `agent:task-completed` | `taskStore`、`pollTask` | `useNodeGeneration` | 任务完成→精准回填节点 | ✅ 生产使用 |
| `presets-changed` | `promptManager` | `PromptLibrary` | 预设库跨节点同步 | ✅ 生产使用 |
| `project:import` | `ProjectSelector` | `App` | 导入按钮→App 处理文件 | ✅ 生产使用 |
| `project:export` | `ProjectSelector` | `App` | 导出按钮→App 下载 | ✅ 生产使用 |
| `agent:workflow-status` | `workflowRuntime` | 暂无 subscribe 消费方 | 工作流状态广播 | ⚠️ 预留广播 |
| `agent:workflow-confirmed` | `workflowRuntime` | 暂无 subscribe 消费方 | 策划确认广播 | ⚠️ 预留广播 |

- **一条铁律**：事件只做"瞬时通知"，不做状态存储；状态归各 store（`useSyncExternalStore`）。

## 一、为什么需要它（解决的问题）

项目早期，模块间做非状态类通信时**各处硬编码 `window.dispatchEvent('xxx')`**，暴露出两个问题：

1. **只监听未发布**：订阅了某事件，但全代码库搜不到谁发布 → 死代码，维护者误以为功能存在。
2. **事件名散落**：字符串满天飞，无注册表，改一处漏一处，重名/拼错无法静态发现。

eventBus 把"发布/订阅"收拢成一个统一通道，解决：
- **解耦**：发布方不用 import 订阅方组件（如 `taskStore` 不知道哪个节点在等结果，只 `publish`，`useNodeGeneration` 按 `nodeId` 精准认领）。
- **可审计**：事件名集中，下文 §四 的注册表就是全量清单，一眼看清谁发谁收。

### 与 store 的分工（关键，别混）

| | `conversationStore` 等 store | `eventBus` |
|---|---|---|
| 管什么 | **状态**（消息/工作流/任务列表） | **事件**（瞬时动作：某步骤完成、某按钮被点） |
| 语义 | 有值、可查询、可持久化 | 一次性广播，播完即弃 |
| 订阅方式 | `useSyncExternalStore` | `subscribe(event, fn)` |
| 是否需要持久化 | 需要（落盘） | 不需要 |

一句话：**状态用 store，动作用 eventBus**，两者互补、不重复。

## 二、API 速览（`src/components/base/eventBus.js`）

```js
import { publish, subscribe, subscribeOnce, clearEvent } from './eventBus.js'

// 订阅：返回取消函数
const off = subscribe('event-name', (payload) => { ... })
off()  // 取消订阅

// 发布：同步调用所有订阅者（单订阅者抛错不影响其它订阅者）
publish('event-name', { any: 'payload' })

// 订阅一次后自动取消
subscribeOnce('event-name', (payload) => { ... })

// 清空某事件的所有订阅（测试/重置用）
clearEvent('event-name')
```

实现要点（4 个函数，全文件 52 行）：

- `listeners` 是模块级 `Map<event, Set<fn>>`，非单例、无外部状态。
- `subscribe` 守卫：事件为空或 fn 非函数时返回空函数，不抛错。
- `publish` 用 `forEach` 遍历当前订阅集合；每个订阅者包 `try/catch`，**一个订阅者崩了不拖垮其它**。
- 订阅者同步执行——**不要**在订阅回调里放长任务/重 IO，会阻塞发布方。

## 三、6 个事件逐个拆解

### 1. `agent:task-completed` —— 任务完成 → 精准回填节点

**核心链路：生成任务完成后，把结果 URL 精准写回对应节点，刷新后画布不丢图。**

- **发布方（2 个）**：
  - `taskStore.done()`（`src/components/base/taskStore.js:190`）：同步生成链路，结果**落盘 `tasks` 目录成功**后广播持久化 URL。
  - `pollTask.pollOneTask()`（`src/components/base/pollTask.js:80`）：**异步任务刷新恢复轮询**，轮询到 `status === 'completed'` 时广播。
  - payload：`{ taskId, nodeId, resultUrl, type, status: 'completed' }`，其中 `nodeId` 是**任务归属的节点**。

- **订阅方**：`useNodeGeneration`（`src/components/base/useNodeGeneration.js:147`）。
  - 只认 `d.nodeId === 本 nodeId` 的广播 → **精准**：其它在跑/不相关的节点忽略。
  - 只认 `status === 'completed'` 且有 `resultUrl` 的广播。
  - 收到后调 `onRecoverRef.current(d)`，由各节点把 `resultUrl` 写回 `node.data`（刷新后节点卡片自动恢复显示结果）。

- **为什么这么设计**：`saveResultToTasks` 落盘是异步的，若只在同步路径里写回，节点 `data.imageUrl` 存的是上游原始 URL；刷新后若该 URL 失效/是临时地址 → 画布丢图，而任务中心读的是已落盘的 `/files/tasks/` URL → **画布没图、任务中心有图的错位**。广播持久化 URL 彻底消除这个错位。

### 2. `presets-changed` —— 提示词库跨节点同步

- **发布方**：`promptManager.saveAndNotify()`（`src/components/base/promptManager.js:88`），保存预设后广播 `presets` 全量。
- **订阅方**：`PromptLibrary`（`src/components/base/PromptLibrary.jsx:40`），收到后 `setLocalPresets(presets)` 同步本地显示。

**为什么**：提示词库可在多处编辑（PromptLibrary 弹窗/别处保存），需要让已挂载的 PromptLibrary 实例感知外部改动，保持显示一致。

### 3 & 4. `project:import` / `project:export` —— 导入/导出按钮 → App 处理（UI 解耦）

- **发布方**：`ProjectSelector.jsx:99/103`，按钮 `onClick={() => publish('project:import' / 'project:export')}`。
- **订阅方**：`App.jsx:343-344`，`handleImport` / `handleExport`。
  - 导出：`exportAll()` 打包 → `backupToBlob` → 创建 `<a>` 下载 JSON → toast。
  - 导入：动态建 `<input type=file>` → `FileReader` 读 JSON → `importAll(backup)` 写回 → toast → `reload()`。

**为什么**：`ProjectSelector` 只是"菜单按钮"，不该知道"导出=打包下载 JSON、导入=读文件写回刷新"这些业务细节。它只发一个"用户点了导入/导出"的**信号**，`App` 这个"能力区"负责落地。职责分离，`ProjectSelector` 保持纯 UI。

### 5 & 6. `agent:workflow-status` / `agent:workflow-confirmed` —— 工作流生命周期广播（预留）

- **发布方**：`workflowRuntime.js`。
  - `setStatus()`（`:63`）：每次状态变化广播 `{ workflowId, conversationId, status }`。
  - `confirm()`（`:118`）：策划确认时广播 `{ workflowId, conversationId }`。
- **订阅方**：**目前没有通过 `eventBus.subscribe` 的消费方。**

**重要说明**：这两个事件目前是**"预留广播"**。工作流状态的**实际消费**走的是 `workflowRuntime` 内部机制——`onStatusChange` 回调（`createWorkflow` 注入，UI 订阅）和 `wf.subscribe(listeners)`（`workflowRuntime.js:75` 自己的订阅表）。eventBus 的 `publish` 是"对齐大雄 publish"的**对外广播预留**，供未来非 React 模块订阅。

> 若你在代码里找不到这两个事件的 subscribe 方，**不是 bug，是预留**。但使用前需想清楚：是走 `wf.subscribe`（工作流实例内聚）还是 `eventBus.subscribe('agent:workflow-status')`（全局广播）。避免两套并存造成混乱。

## 五、边界：哪些仍是原生 `window` 事件（未走 eventBus）

判断依据：**只发不收 / 只收不发 / 非事件数据格式**，不值得迁移。

| 事件/通道 | 位置 | 说明 |
|---|---|---|
| `yimao:toast` | `scriptBoxEngine.js:90`（只发） | **只发不收**（无订阅方），脚本盒内部提示，待清理或迁移 |
| `yimao:remove-edge` | `App.jsx:1078`（只收） | **只收不发**，兼容旧外部触发，无发布方 |
| `mutiwindow-nodes` / `mutiwindow-images` | `App.jsx`、`useAssetDropPaste` | 剪贴板数据格式（`type` 字段），**不是事件**，是复制/粘贴的内容载体 |
| `mutiwindow-rerun-task` | `App.jsx:144`（注释提及） | 遗留，见 §六 |

> 这些不是"遗漏"，是**判定为死代码/非事件后刻意不迁移**（见提交 `771d05a`）。若未来某事件补上了另一端（有了收或发），再迁入 eventBus。

## 六、演进历史（为什么长这样）

- **早期**：模块间用 `window.dispatchEvent('mutiwindow-task-completed')` 等原生事件，事件名无前缀、只监听未发布问题频出（`docs/11 §五.3`）。
- **Step 事件迁移（commit `771d05a`）**：
  - `mutiwindow-task-completed` → `agent:task-completed`（`taskStore`/`pollTask` 发布，`useNodeGeneration` 订阅）。
  - `yimao:presetsChanged` → `presets-changed`（`promptManager`/`PromptLibrary`）。
  - 判定死代码不迁移：`yimao:toast`（只发不收）、`yimao:remove-edge`（只收不发）、`import/export-project`（只发不收）。
- **后续**：新增 `project:import`/`project:export`（完整导入导出，commit `196b351`）、`agent:workflow-status`/`agent:workflow-confirmed`（工作流运行时预留广播，Step B）。

## 七、给维护者的 3 条守则

1. **新的事件先查 §四 注册表**，命名用 `领域:动作`，发布方/订阅方都必须存在（避免"只监听未发布"）。
2. **状态用 store，动作用 eventBus**——如果 payload 需要"存起来、可查询、可持久化"，它应该进 store 而不是广播。
3. **订阅回调别做重活**——`publish` 是同步的，回调里跑长任务会阻塞发布方；重逻辑放异步或事件驱动内部。
