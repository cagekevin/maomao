## 3. 新架构（原生方案）

### 3.1 分层

```
初始化   compressImage(url, {keepOriginalFormat:true}) → 同源 dataURL
            ↓ （画布永不被污染，toDataURL 永远安全）
编辑台   活 canvas 实时绘制（画笔/形状/文字/橡皮/吸管）
            ↓ 点「确认/保存」时一次性导出，不每帧 export
导出层   exportCanvas / canvas.toDataURL()  →  PNG 无损
            ↓
写回     onImageReplaced(dataUrl, {width,height}) → fitByRatio
```

### 3.2 核心机制

| 机制 | 做法 |
|---|---|
| 绘制源 | 一律 `compressImage` 同源 dataURL，**杜绝跨域污染** |
| 连续绘制 | 在活画布实时进行（性能），**不**每帧走 export |
| 画布变换（裁剪/扩图） | **新建游离 canvas + `drawImage`**，禁止 `getImageData` + 就地改活画布 |
| 撤销栈 | **不用全画布像素快照**（旧实现 4096² 约 67MB/步）。改用轻量方案（见 §3.3） |
| 导出 | PNG 无损；JPEG 仅在确需时，且白边场景禁止 |

### 3.3 撤销栈（新设计）

旧：`ImageData[]` 全画布像素快照 → 内存爆炸（4096² ≈ 67MB/步）。
新：**指令栈为终态，像素快照仅为过渡**，二者都建立在 §3.6 的单一数据源之上。

| 阶段 | 方案 | 说明 |
|---|---|---|
| **过渡（默认，本次）** | **方案 A**：`editorDoc` 快照，上限 10 步，超出丢最早 | 改动小；快照存 `Blob`/`ImageBitmap`（**非 dataURL 字符串**，省内存/解析）。见 §3.6 |
| **终态（未来升级）** | **方案 B**：绘制指令（矢量 ops）栈 | 内存最优，且天然兼容图层（§3.4）；与方案 A 共享同一 `editorDoc` 结构，升级不推翻 |

> 关键：无论 A/B，撤销栈操作的是 **`editorDoc` 状态**，不是画布像素。画布只是状态的投影（§3.6），因此撤销 = 切回历史 state 再重合成，**不依赖 `getImageData` 反读**。

### 3.4 图层前瞻（架构留口，现在不做）

> 未来若引入 PS 式图层，本结构应可"加层"而非"重写"。故底层从一开始按**图层模型**打底，即便当前只有一层。

**现在不实现，但必须遵守的结构约束**：

1. **图层数组**：`layers: Layer[]`，`Layer = { id, offscreen: Canvas, ops: DrawOp[], opacity?, visible? }`。
   - 当前只有 `[baseLayer]`，但所有读取/合成都走数组遍历，禁止写死"单画布"。
2. **离屏合成**：主 canvas 由 `layers.forEach(l => ctx.drawImage(l.offscreen))` 派生。
   - 这与 §3.5 的"离屏底图缓存"是**同一机制**，一次实现、性能与图层双赢。
3. **绘制落层不落屏**：每次用户绘制 → 改对应 `Layer.ops` + 重合成主 canvas，**不直接对主 canvas 命令式涂抹**。
4. **撤销栈接 ops**：方案 B 时，撤销 = 从 `editorDoc.layers[].ops` 弹出增量，天然支持逐层独立撤销。
5. **导出从合成结果取**：`exportCanvas` 的输入是"合成后的源图层"，未来加层时导出代码零改动。

### 3.4.1 与双 Tab + 自动保存方案的兼容（已论证，无冲突）

> 结论：在「涂鸦 / 画幅 双 Tab，切 Tab 或点保存即落定」的方案上叠加图层系统，**底层无需返工**。

- **自动保存 = commit 到图层，而非烙进裸位图**：切 Tab / 保存时，把当前 Tab 的编辑结果 commit 到对应 `Layer`（如涂鸦 → `contentLayer`），**禁止**把画布当单张裸位图直接 bake 死。因此图层系统未来能独立识别"这是一层涂鸦"，可单独隐藏/调透明度/删除。
- **画幅对所有图层统一生效**：裁剪 / 扩图 = 改 `editorDoc.size` + 各层 `dx,dy` 平移 + 最底垫白，`layers.forEach(drawImage)` 天然覆盖，零额外成本。
- **精度边界（可接受）**：自动保存是**粗粒度 commit**（撤销整批），图层系统是**细粒度编辑**（改单个元素）；共存无冲突，仅精度不同。日后若要"改单个标注"，再决定涂鸦留 `ops` 还是 bake，不影响当前结构。
- **一句话落地**：双 Tab 的"保存"语义必须实现为 `commit 到对应 Layer`，不能实现为"把像素烙进单张底图"——这是与未来图层系统兼容的唯一红线。

### 3.5 性能基线（验收/排期参考）

| 优化 | 做法 | 收益 |
|---|---|---|
| **离屏底图缓存** | 已完成绘制烘焙进离屏 canvas，拖拽预览只 `drawImage(底图) + 当前一笔`，不全量重绘 | 大图拖拽不卡；与 §3.4 同一机制 |
| **RAF 合帧** | `mousemove` 绘制经 `requestAnimationFrame` 合并，避免一帧多次重绘 | 消除大图卡顿主因 |
| **devicePixelRatio** | `canvas.width = 逻辑尺寸 × dpr`，避免 Retina 模糊（权衡内存） | 清晰度 |
| **异步导出** | `OffscreenCanvas` + `convertToBlob`（异步）或 `requestIdleCallback` 包裹，替代同步 `toDataURL` | 大图导出不阻塞主线程 |
| **撤销存 Blob/ImageBitmap** | 替代 dataURL 字符串快照 | 省内存/解析 |
| **超大图降级** | 超阈值（如 4096）编辑时降采样预览，导出回原尺寸（类 PS 预览分辨率） | 极端尺寸可用 |

> 前两项是**同一套离屏分层机制**，应在 §3.4 结构落地时一并实现，不重复投入。

### 3.6 ★ 单一数据源与数据流向（架构第一原则）

> 旧 `ImageEditor` 的根本弊病不是某个 bug，而是**状态散落各处 + 直接对活画布命令式涂抹**（`ctx.xxx` 满天飞），导致 state 与画布双向耦合、撤销困难、回归频发。新编辑器从根上用**单一数据源 + 单向数据流**规避。

**单一数据源（Single Source of Truth）**

```
editorDoc（唯一真源，不可变更新）
  ├─ layers: Layer[]          ← 每图层：离屏 canvas + 操作列表（见 §3.4）
  ├─ size: { w, h }           ← 画布尺寸（画幅）
  ├─ background: string       ← 底（透明/纯白 #ffffff）
  └─ view: { zoom, offset }   ← 仅视图态，不参与出图
```

- **画布是 `editorDoc` 的投影（projection），不是数据源**。
- 工具选择、选中态等 UI 瞬时态可局部存，但**任何"画了什么"必须最终落到 `layers[].ops`**。
- ❌ 禁止把画布像素当状态（即禁止 `getImageData` 当数据源）；❌ 禁止多处直接 `ctx.xxx` 改活画布当真相来源。

**单向数据流（Unidirectional）**

```
用户输入（指针/按钮）
   │  action
   ▼
更新 editorDoc ──（不可变）→ 产生新 state
   │
   ▼  派发合成（composite）
重绘主 canvas（永远由 editorDoc 派生）
   ▲
   │  撤销 = 切回 editorDoc 历史态 → 重新合成
   └─────────────────────────────
```

- 任一处变更只有一条路径：`action → editorDoc → composite → 画布`。
- 画布**不反向**驱动 state（无"从画布读像素回填状态"）。
- 视图缩放 `view` 是派生显示态，改它**不触发** `editorDoc` 变更、不重导出。

**为什么这条原则重要**：它与 §3.2「禁止就地改活画布」、§3.3「撤销栈操作状态而非像素」、§3.4「图层可加项而非重写」形成闭环——**所有具体约束都是这条总原则的体现**。

## 4. 功能实现要点

### 4.1 涂鸦类（pencil / eraser / text / line / arrow / square / circle / number / eyedropper）
- 标准 canvas 2D 操作：`lineTo/stroke/arc/fillText` 等。
- **吸管必须包 try/catch**：读 1×1 像素；旧实现是裸调，画布异常时会崩掉整个编辑器。
- 橡皮：用 `clip` + 重绘原图（沿用语义，但源改为同源 dataURL）。

### 4.2 画幅面板（裁剪 + 扩图统一）

**洞察**：裁剪 = 画布往内缩，扩图 = 画布往外扩 → 同一操作两个方向。

```
结果画布 tw × th，原图贴入 (dx, dy)
  扩图 → dx, dy ≥ 0   原图在画布内，四周留白
  裁剪 → dx, dy ≤ 0   画布在原图内，原图被外移裁切

ctx.drawImage(img, dx, dy);   // 同一行，两种结果
```

- 原图**始终 1:1 自然像素**贴入，不缩放不拉伸。
- 复用纯函数 `computeOutpaintTarget` / `computeOutpaintDrawPos` / `OUTPAINT_RATIOS`（带单测）。
- **★ `fitZoom()`**：画幅变化后必须重算缩放，否则白边在视口外看不见、拖不动（旧实现缺这步）。
- 白边**纯白 `#ffffff`**（下一步交给大模型填充，灰度过噪点会干扰识别）。

## 7. 取舍说明

### 7.1 为什么"新建 + 删旧"而不是"改造"
- 旧文件包袱：活画布生命周期 + `getImageData` 撤销栈 + 失效的裁剪/扩图 + 跨域回退污染 + 未定位根因。
- 逐个改造 = 在流沙上建房子；新建可直接套用已验证的原生模式。
- **引用只收敛在一处**（`useImageHoverActions.renderEditor`），替换成本极低、回滚只需改回 import。

### 7.2 为什么画幅合并、涂鸦不合并
- 裁剪/扩图共享同一 `drawImage(img, dx, dy)` 模型 → 合并。
- 涂鸦是连续绘制、画幅是一次性变换 → 机制不同，分属编辑台与导出层。

### 7.3 保留 `InlineImageCropper`
- 节点内"快速裁剪"已验证可用，且场景（随手裁）与大图画幅面板（精细调）不同。
- 本次不动它。
