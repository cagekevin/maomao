## 〇、动手前必读：先查调用方，不要靠猜（血泪教训）

**⚠️ 最重要的一条**：收紧任何一个函数/类型前，**必须先用工具查它的全部调用方**，
评估影响面，而不是手动 `grep` 猜。否则会像本批次一样引爆大量连锁（曾 75 处测试报错）。

### 查模块调用方：`scripts/ts-migrate.mjs refs <file>`

```bash
# 列出「import 引用方」+「字符串硬编码残留引用」（带行号），一次看清影响面
node scripts/ts-migrate.mjs refs src/components/base/api/localToolApi.ts
```

输出分两段：
- **① 模块引用 N 处**：AST 抓到的 `import` 引用方（convert 会改这些）
- **② 字符串残留引用 N 处**：文件名硬编码进字符串的位置（脚本不改，需手工同步）

## 七、API 层收窄方案（接手指引）

### 7.1 API 层通用方案（httpClient + localToolApi）

**核心矛盾**：`httpRequest<T = any>` 泛型默认 `any`；localToolApi 各函数返回 `Promise<any>`。
这些 API 返回后端 JSON，调用方众多（fetchResources / fetchTasks / kvGet 等被
PromptNode / GeneratedView / AssetLibrary / d3dPersistence / kvStore 等广泛调用），
且调用方都直接访问返回值字段（`d.items`、`data.items`、`kv.xxx`）。

**推荐做法（两选一）**：

1. **`Promise<unknown>` + 调用方断言**（改动小但调用方连锁多）：
   - `httpRequest<T = unknown>`，`httpPost` / `httpRequestLogged` 返回 `Promise<unknown>`
   - localToolApi 各函数返回 `Promise<unknown>`
   - 调用方 `await` 后对 `Record<string, unknown>` 断言访问字段
   - ⚠️ 连锁面大：几乎每个 API 调用点都要加断言，约 20+ 处

2. **为关键 API 定义精确返回接口**（改动大但一劳永逸，推荐）：
   - 例：`fetchTasks(): Promise<{ items: TaskItem[]; total: number }>`
   - `fetchResources(): Promise<{ items: ResourceItem[]; total: number; folder?: string }>`
   - `kvGet<T = unknown>(key): Promise<T | null>`（泛型化）
   - `request<T = unknown>(...)` 泛型化
   - ⚠️ 需要先摸清每个接口的后端返回结构，工作量大，但调用方全部自动类型化

**建议优先级**：`kvGet/kvSet`（泛型化收益最大）→ `fetchResources`（调用方最多）→ 其余。

### 7.2 requestModes.ts（16 处）

类型形态：`any[]` / `Record<string, any>` / `parseResponsesXxx(data: any)` / `normalizeToolCalls(source: any)`。
这些都是**协议层解析函数**（Responses API / Chat Completions 解析），本质是「未知 JSON → 结构化」。

- `buildResponsesInput` / `buildResponsesImageBody` / `buildResponsesChatBody` 的返回
  `Record<string, any>` → `Record<string, unknown>`（协议 body 是动态对象）
- `parseResponsesImage/Json/ChatJson(data: any)` → `data: unknown` + 函数内 `as Record<string, unknown>` 断言
- `normalizeToolCalls(source: any)` → `source: unknown` + 内部收窄
- `parseResponsesSSEChunk` 的 `acc.toolCalls: any[]` → `unknown[]` 或精确 ToolCall 形状
- ⚠️ 连锁：这些被 `agentCore.ts` / `agentRuntime.ts` 调用，收紧后需适配调用方

### 7.3 videoEngine.ts（10 处）

类型形态：`conversion/output: any`、`outputTarget: any`、`items/sink/source: any`。
这是 WebAudio 采样引擎内部（VideoSampleSink / AudioBufferSource / VideoSampleSource / AudioSampleSink）。

### 10.5 收尾原则（重申）

"尽量收窄" ≠ "无脑强收"。区分两类 `any`：
1. **业务代码里的宽泛 any**（`Record<string, any>` / `Promise<any>` / `: any` 参数）：必须收窄到精确接口/泛型/`unknown`+断言。本批次已清零 53 处。

## 十一、阶段五（2026-09-02，已回滚）

> 续阶段四：用户要求"unknown 也要尽量收窄，不能偷懒"。复查阶段四判为「必要保留」的 13 处。

### 11.1 本轮实际做的事 + 被否的原因

本轮只动了两处，结论如下：

1. **`base/videoEngine.ts` 的 `outputTarget` / `items` / `audioSource` —— 真可收，已保留。**
   阶段四记"mediabunny 无 TS 类型声明"是**错的**——`node_modules/mediabunny/dist/*.d.ts` 有完整类型导出
   （`Output`/`InputVideoTrack`/`InputAudioTrack`/`AudioSampleSink` 等均为 `export declare class`）。
   - `let outputTarget: any` → `Output | null`
   - `const items: any[]` → `ConcatSegment[]`（新增本地接口，元素来自 mediabunny 轨道类型）
   - `const audioSource: any` → `AudioSampleSink`
   这 3 处是**正收窄**（找对方向），保留在代码里。剩 3 处（videoSink/audioSink/source）是 mediabunny
   **运行时 API 与官方 `.d.ts` 错配**，收不紧，见 11.3。

2. **`base/toolRegistry.ts` 的 `ToolResult.data?: any` → `data?: unknown` + 测试 `rd<T>` 假断言 —— 走反方向，已回滚。**
   一度以为"改 unknown 零连锁（strict:false + 可选链），符合收窄"。但**零连锁 ≠ 真收窄**：
   - `unknown` 只是把 `any` 改名，消费方访问属性仍需断言；
   - 当时为消除测试 46 处 TS2339，引入 `rd<T> = (r) => r.data as T` 辅助——这是**无条件类型断言（cast）**，
     无运行时校验，制造"已收敛"的假象，比 `any` 更危险；
   - 真收窄应从「每个工具 execute 返回什么」源头做（`ToolResult<具体类型>` 在定义处闭环），而非在 57 个
     消费点各手抄一遍 `rd<Shape>`。
   - **用户判定：此路反向。已回滚**——`ToolResult` 恢复 `data?: any`（信封语义，与阶段三/交接注意事项口径一致），
     测试文件的 `rd<T>` 辅助与全部 `rd<...>(x).prop` 调用还原为 `x.data.prop`。回滚后 `tsc` 全绿。

### 11.2 正确的收口结论（修订阶段三/交接注意事项的"不要动"口径）

`ToolResult.data?: any` 是**信封语义的必要 any**，不在"尽量去掉"清单内：

- 约 30 个画布工具返回形状各异，消费方（useAgentChat / agentRuntime）按需读 `data` 字段，不 narrow；
- 强改 `unknown` 不产生类型安全收益（消费方要么靠可选链/推断容忍，要么被迫 `as` 断言，后者即本轮踩的坑）；
- 正方向若要做，应是「给每个工具 `execute` 标注 `ToolResult<具体类型>` 并在定义处闭环」，但那需先摸清 30 个
  工具返回形状、改动面大，属另一项独立工作，**当前不纳入**。
