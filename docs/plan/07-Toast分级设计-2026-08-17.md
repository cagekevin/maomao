## 一、现状诊断

### 1.1 两类真实 bug（核心问题）

`toastStore.js:33` 签名：

```js
export function showToast(message, { type = 'info', duration = DURATION } = {}) { ... }
```

第二参约定是**对象**，缺省时 `type` 回落默认 `info`。全量扫描确认存在**两类**会让颜色/时长失效的写法：

**Bug A — 位置字符串写法（字符串当 options 对象传入）**

```js
showToast('画布保存失败，请检查存储空间或本地服务', 'error')   // App.jsx:236
```

解构 `{ type='info', duration } = 'error'` 对字符串解构，`type` 取到 `undefined` → 回落默认 `info`。**这条本该是红色，实际渲染成 info 蓝。** 是确凿的真实 bug（仅此 1 处，在 App.jsx）。

**Bug B — 裸调（省略 type，统一变 info 蓝）**

```js
showToast('复制失败')          // 失败语义 → 变 info 蓝
showToast('GIF 生成完成')      // 成功语义 → 变 info 蓝
```

全项目裸调泛滥在节点组件与资产/拖拽类文件，把本该 error / success 的语义一律当 info。实测样本：

- 失败被吞：`VideoExtractNode.jsx:297/307/317`、`ImageNode.jsx:121/150`、`ImageBoxNode.jsx:375`、`FaceMosaicNode.jsx:118/126`、`App.jsx:588`。
- 成功无绿：`VideoProcessNode.jsx:861/945/948`、`VideoExtractNode.jsx:267/306/316`、`LoopNode.jsx:198`、`GridSplitNode.jsx:555`、`ImageBoxNode.jsx:228/232/369`、`ImageNode.jsx:140/154`、`useAssetDropPaste.js:63/75/82/109/112/126/129/184`。

> 结论：**架构不干净**有两点——① `App.jsx:236` 的位置字符串 bug（颜色错）；② 海量裸调把失败/成功渲染成 info 蓝（语义错）。修法：删位置字符串、用语义函数替代裸调。

### 1.2 语义分级边界模糊

四档 `success / error / warning / info` 没有成文契约，调用方随手写：

| 语义 | 现网乱象 |
|---|---|
| 失败 | "复制失败""上传失败""打码失败""压缩失败""截取失败""导出失败" → 大量裸调（变 info 蓝），失败语义被吞 |
| 成功 | "GIF 生成完成""音频提取完成""视频处理完成""已复制 N 张""已生成 N 个切片""已导入" → 裸调 info 蓝，但本质是成功反馈，应为 success |
| 阻断校验 | "请先上传/连接…图片""没有可用切片""请先选中节点" → 裸调 info，但属操作前置不满足，按契约应归 warning |
| 降级有损 | "未检测到人脸""图片链接已复制（直接复制图片失败）""本地引擎未连接，已保留原图" → 裸调/混合，按契约应归 warning |

> 注：对象写法集中的文件（TopNav / useNodeGeneration / App / Settings 各页 / AssetLibrary / GeneratedView / TaskCenter / AgentPanel / scriptBoxEngine 等）分级**基本正确**，说明契约清晰后调用方能写对。问题集中在裸调泛滥的节点组件与拖拽导入逻辑。

### 1.3 分级与行为脱钩

- `duration` 多数写死 3000ms（裸调走默认 `DURATION`），分级与停留时长无关。
- `scriptBoxEngine.js:107` 是唯一手动按分级设时长的：`{ type: t, duration: t === 'error' ? 5000 : undefined }`，说明已有"error 该更久"的诉求但未成规范。
- `duration: 0`（持久不消失）的语义未被任何分级引用。

## 二、分级契约（目标设计）

### 2.1 四级定义

| 分级 | 语义 | 典型场景 | 默认 duration | 配色（doc39 §3.2） |
|---|---|---|---|---|
| `success` | 操作成功完成 | 已复制/已编组/导出成功/生成完成/已导入 | 2500 | 绿 |
| `error` | 操作失败，用户需感知并处理 | 保存失败/复制失败/导入格式错/生成异常 | 4000 | 红 |
| `warning` | 执行了但有损/降级/前置不满足 | 引擎未连接已保留原图/未检测到人脸/请先选节点 | 3500 | 黄 |
| `info` | 中性提示 / 过程反馈 | 放大预览占位/手动模式提示/未接入提示 | 2500 | 蓝 |

### 2.2 消歧规则（消除 1.2 的歧义）

- **"请先连接图片""请先选中节点""没有可用切片"** 这类阻断校验 → `warning`（不是 info，因为它打断了用户预期动作）。
- **"已生成""已完成""已编组""已复制 N 个""已导入"** 这类结果反馈 → `success`（不是裸 info）。
- **含"失败"二字且非降级** → `error`。
- **降级但有损、功能仍可用** → `warning`（如"已保留原图""复制图片失败改用链接"）。
- **纯占位/过程提示**（如 `TemplateNode` 的 `showToast('放大预览')` / `showToast('下载')` / `showToast('上传处理')`、`VideoExtractNode:222` 的 `showToast('手动模式请直接在上方播放器中截取')`）→ 允许保留 `info` 裸调。

> **首要原则——「用户看不见才弹」**：是否弹 toast 的**第一判据是用户能否直接从界面感知结果**，而非操作是否"成功"。
> - 用户一眼可见结果的（粘贴图片到画布、复制节点、生成切片/下游节点、导入文件到节点、GIF/音频/视频生成完成）→ **不弹**，弹了是噪音。
> - 用户无法直接感知的（后台画布保存失败、跨域复制失败、云端推送、内联资源转换降级保留原图、编组/转换的异常）→ **必弹**，且按分级配色。
> 这条原则优先于上面的 success/info 归类：可见的成功反馈统一**不弹**，不强行标 success。

### 2.3 分级绑定默认行为

`showToast` 内按 type 给默认 duration，调用方仍可覆盖：

```js
const DEFAULT_DURATION = { success: 2500, info: 2500, warning: 3500, error: 4000 }
```

`error` 天然停留更久，符合"失败要让用户看清"。

## 三、API 收敛方案

### 3.1 语义化出口（推荐）

在 `toastStore.js` 暴露四个语义函数，调用方**不记 type 字符串也能写对**：

```js
export const toastSuccess = (m, o) => showToast(m, { ...o, type: 'success' })
export const toastError   = (m, o) => showToast(m, { ...o, type: 'error' })
export const toastWarning = (m, o) => showToast(m, { ...o, type: 'warning' })
export const toastInfo    = (m, o) => showToast(m, { ...o, type: 'info' })
```

> **⚠️ 落地顺序（防编译失败）**：必须先做第 1 步在 `toastStore.js` 导出 `toastSuccess/Error/Warning/Info`，再做第 2 步改业务调用；否则业务文件引用未定义函数会编译报错。

1. ~~`toastStore.js` 增加 `toastSuccess/Error/Warning/Info` 四个语义函数 + 分级默认 duration~~ **【已落地】**
2. 全项目批量替换（执行依据见附录 A 实测清单）：
   - `showToast(x, 'error')` 位置字符串（App.jsx:236）→ `toastError(x)`，并修复颜色 bug。
   - 裸调失败 `showToast('…失败')` / `showToast('复制失败')` 等 → `toastError(...)`。
   - 裸调成功 `showToast('…完成')` / `showToast('已生成…')` / `showToast('已导入…')` 等 → `toastSuccess(...)`。
   - 阻断校验 / 降级有损 → `toastWarning(...)`。
   - 纯占位 info（2.2 末条列举的）→ 保留裸调 `showToast(x)`。
3. 保留 `showToast` 基础出口供特殊场景（自定义 duration / duration:0 持久）使用，但业务代码优先走语义函数。
4. 灰度校验：替换后无"失败/成功/阻断/降级"语义的 `showToast(x)` 裸调残留（见验收标准）。

## 四、与存储层的关系（背景，非重点）

toast 系统本身不负责持久化。存储写入失败的反馈链路：

```
存储写入失败
  └─ storageAdapter.reportPersistFailure(key, error)
       └─ publish('persist:failed', { key, error })        [eventBus.js]
            └─ App.jsx 全局订阅（节流 5s 最多一次）
                 └─ showToast('部分数据保存失败…', { type: 'error' })   [App.jsx:423]
```

要点：

- 插件存储 / localStorage 失败 → eventBus → 节流 toast。
- KV 存储（localTool）失败 → `kvStore.storageSet` 捕获后**降级 localStorage**（只 `logger.warn`，不直接 toast）。
- 后端 loctool 落盘（`localTool/src/routes/kv.ts`）无感知 toast，错误经 HTTP 回传前端由 `kvSet` 抛异常处理。

设计意图：**能降级就降级，兜底失败才打扰用户**，故多数写入失败用户看不到 toast。
