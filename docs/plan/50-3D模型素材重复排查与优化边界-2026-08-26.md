# 3D 模型素材重复排查与优化边界

> 日期：2026-08-26
> 范围：`public/models/` 下的内置 3D 模型素材（`.glb`）
> 结论：3 个文件中 **1 个为明显错误重复的死文件可删除**，2 个为正常分工（减面版日常用 + 另一独立模型），**不应优化**。

---

## 一、素材清单（实际磁盘占用）

| 文件 | 大小 | 类型 | 实际引用 |
|------|------|------|----------|
| `public/models/xbot-animated-lod.glb` | 2.8 MB | xbot 减面版（49k→15k 三角） | ✅ 运行代码主动加载 |
| `public/models/xbot-animated.glb` | 3.6 MB | xbot 原件（未减面） | ❌ 无任何代码引用（注释声称"作回退"） |

## 二、逐项判定

### 1. `xbot-animated-lod.glb`（2.8 MB）—— ❌ 不可优化，正常在用

- 代码唯一加载入口：`src/components/director3d/models.jsx:12`
  ```js
  // 内置人物模型：使用减面版（49k→15k 三角），蒙皮/骨骼/动画全保留，降低每帧渲染成本
  const BUILT_IN_MODEL_URL = `${import.meta.env.BASE_URL}models/xbot-animated-lod.glb`
  ```
- 这是**主动减面后的生产模型**，刻意把 49k 三角降到 15k，蒙皮/骨骼/动画全部保留。
- 它本身就是"为性能而生的低模/LOD 版"，**已是当前最优形态**，没有重复、没有冗余。
- **判定：保留，不优化。**

### 2. `xbot-animated.glb`（3.6 MB）—— ✅ 明显错误重复，可删除

- 这是 `xbot-animated-lod.glb` 的**未减面原件**（同一角色、同一来源，仅精度更高）。
- `models.jsx:11` 注释写道："原件 xbot-animated.glb 保留在 public/models/ 作回退"。
- **但代码里的回退机制并没有用它**：
  - `ModelErrorBoundary`（`models.jsx:468`）的 `fallback` 是一个**程序生成的胶囊体几何体**（`capsuleGeometry`，见 `StudioPerson` 第 489 行），而非回退加载这个 glb。
  - 全局搜索 `xbot-animated.glb`（不带 `-lod`）后确认：**除那一句注释外，整个工程没有任何 import / 动态加载 / 字符串引用**指向它。
- 即：注释承诺的"回退"并未实现，该文件是**遗留死文件**，纯占 3.6 MB 磁盘（并随 `public/` 被原样复制进 `dist/` 再占 3.6 MB）。
- **判定：明确可删除。** 删除后不影响任何运行路径；若未来真要做"高精度回退"，应改为按需动态 `import()` 或条件加载，而非常驻 `public/`。

### 3. `ue-mannequin-retopology.glb`（732 KB）—— ❌ 不可优化，独立另一模型

- 文件名表明它是 **UE 人形（Mannequin）重拓扑模型**，与 xbot 是**两个不同来源/不同骨骼绑定的角色**，不是 xbot 的重复。
- 代码搜索命中仅在两处**逆向参考副本**中：
  - `scripts/1mao-scripts/scriptbox-split-snapshot/shared.js:7085`
  - `reference-1mao/httpClient-BEVPUWLI_components/shared.js:7373`
  - 这两处是 `reference-1mao/`、`scripts/1mao-scripts/` 下对"别人仓库"的逆向快照，**非本工程运行代码**，且其引用路径 `./models/ue-mannequin-retopology.glb` 指向的是**被逆向对象的资源布局**，不代表本工程运行时会加载它。
- 当前 `src/` 下无任何文件引用该模型，它大概率是为后续"UE 人形移植"预留的素材，**与 xbot 系列无重叠**。
- **判定：保留，不优化。**（若确认后续不移植 UE 人形，可另行评估删除，但那属于需求取舍而非"重复优化"。）

## 三、优化建议（只做明确正确的那一项）

| 动作 | 文件 | 收益 | 风险 |
|------|------|------|------|
| **删除** | `public/models/xbot-animated.glb` | 省 3.6 MB（含 dist 复制共约 7.2 MB） | 极低——无运行引用，回退走胶囊体 |
| 保留 | `public/models/xbot-animated-lod.glb` | — | 删除会破坏内置人物渲染 |
| 保留 | `public/models/ue-mannequin-retopology.glb` | — | 删除会丢失 UE 人形移植素材 |

> 注：若担心"将来要做高精度回退"，正确做法不是留死文件，而是：
> 1. 在 `ModelErrorBoundary` 真正接入 `xbot-animated.glb` 作为 lod 加载失败时的兜底；或
> 2. 用动态 `import()` 仅在需要时拉取高精度原件。
> 在当前回退逻辑未实现的前提下，**留着只是死重**。

## 四、与"vendor 依赖重复"的关系说明

本次排查的是 **3D 模型素材（.glb 文件）**，与之前讨论的 **npm 依赖体积（vendor-3d / vendor-media）** 是两回事：

- `vendor-3d`（three 栈）与 `vendor-media`（mediabunny 等）之间**零依赖重叠**，不存在"两套模型/底模高模兜底"的打包重复。
- `.glb` 素材走 `public/` 静态托管，**完全不参与 npm 分包**，因此体积问题只能从"删减素材文件"层面解决，无法靠改 `vite.config.js` 的 `manualChunks` 优化。

**一句话结论**：3 个素材里只有 `xbot-animated.glb` 是同一角色的高精度原件、且代码未使用，属于明确可删的错误重复；其余两个是正常分工，不应动。

## 五、three 渲染栈依赖重复排查（顺带核查）

用户额外要求核查 three 相关依赖是否存在重复/重叠。结论：**three 渲染栈内部功能有重叠，但均是合理分工，不存在需要删除的错误重复。**

### 1. three 单实例 ✅ 无重复

- `DEPENDENCIES.md:30` 明确："所有依赖在 maomao `node_modules` 下仅一份，无重复安装。"
- `three@0.185.1` 被 `fiber` / `drei` / `three-stdlib` 以 peerDependency 共享，npm dedup 后仅一份。
- **判定：正常，不优化。**

### 2. drei 与 three-stdlib 的功能重叠 ⚠️ 重叠但合理

- `drei@10.7.8` 依赖 `three-stdlib@^2.35.6`（`drei/package.json:48`），二者都提供 `GLTFLoader`、`OrbitControls` 等 three 辅助模块。
- 但 `three-stdlib` 是作为 **drei 的传递依赖**被引入，drei 在代码里被直接 import（`Viewport.jsx` 用 `OrbitControls/TransformControls/Grid/ContactShadows`，`models.jsx` 用 `useGLTF`），`three-stdlib` 不会单独再打一份 three，只是把 drei 用到的 helper 一起卷进 `vendor-3d`。
- **判定：属于"单份但 drei 偏重"而非"打了两份"**。要压体积应走"drei 按需替代"（直接从 `three/examples` 引入用到的几个 helper），而非删除——见下文建议。

### 3. `three/examples/jsm` 与 drei 的直接 vs 间接 GLTFLoader ⚠️ 看似重复，实为合理分工

- `models.jsx:5-6` 直接从 `three/examples/jsm` 引入 `GLTFLoader` 和 `SkeletonUtils`：
  ```js
  import { clone as skeletonClone } from 'three/examples/jsm/utils/SkeletonUtils.js'
  import { GLTFLoader } from 'three/examples/jsm/loaders/GLTFLoader.js'
  ```
- 而 `models.jsx:3` 又用了 drei 的 `useGLTF`（底层也是 GLTFLoader，经 three-stdlib）。
- **为什么不是错误重复**：
  - `useGLTF` 是 **React hook**，用于声明式加载内置/远程 glb（`BUILT_IN_MODEL_URL`）；
  - `three/examples` 的 `GLTFLoader` 用于 **命令式 `loader.parse(buffer)`**（`measureModelScale` 直接解析用户导入的 ArrayBuffer），hook 不适合这种场景。
  - 二者来源路径不同（`three/examples/jsm` vs `three-stdlib`），Rollup 不会合并为同一模块，但**底层都指向同一份 three 源码**，体积上只是多一份 helper 包装，不构成"同一文件打两份"。
- **判定：合理分工，保留。若想极致瘦身，可统一为只走 drei 的 `useGLTF` + 自写 parse 封装，但收益有限且改动有风险，不列为必做。**

### 4. 可优化方向（非"删除重复"，而是"按需瘦身"）

| 方向 | 做法 | 收益 | 风险 |
|------|------|------|------|
| drei 按需替代 | 把 `import { OrbitControls, Grid, ... } from '@react-three/drei'` 改为从 `three/examples/jsm` 精确引入，避免 drei 全量进场 | 省 200~400 KB | 中：需逐一替换并回归 |
| 媒体库动态加载 | `mediabunny`/`gifenc`/`@mediapipe` 走动态 `import()` | 首屏省 705 KB | 低 |
| 3D 节点懒加载 | `PanoramaNode`/`Director3DNode` 走 `React.lazy` | 首屏省 3D 相关 chunk | 低 |

> 注意：**以上均为"体积优化"而非"删除错误重复"**。本工程 three 栈没有需要删除的重复文件；唯一明确的"错误重复"仍是第四节的 `xbot-animated.glb` 死素材。
