# 129 · cutia 落地架构 · 上下两层 + 后端预留（从地基走七步法）

> **状态**：规划（基于 `125` 可移植性实测 + 本轮读码 `videoEditor/core/*` 地基现状）· **日期**：2026-09-14
> **上游**：`125`（可移植性已证：cutia 内核零 next 依赖、导出同 mediabunny、持久化浏览器原生）· `124`（能力重叠普查）
> **新约束（用户本轮口径）**：① 维持**上下两层结构**；② cutia 当前**无后端**；③ **后期要加后端**，但**第一期先不加**。
> **一句话结论**：从地基起 = 把 cutia 引擎落「下层」、保留他们的 UI 作「上层」、把**不变的基座 + 契约模型 + OpResult + 可插拔存储适配器接口**当接入口；「后端预留」不是新功能，只是把存储适配器做成**可替换实现**（一期浏览器、二期 localTool）。

---

## 〇、两层结构怎么对应（先定形，再定内容）

| 层 | 角色 | 落点 | 来源 |
| --- | --- | --- | --- |
| **地基（不变基座）** | 跨域共享 + 契约 | `base/**` · `contracts.ts` · `videoEditor/core/types.ts`(契约模型) · `videoEditor/core/result.ts`(OpResult) | 他们现有，不动 |
| **下层 · 编辑引擎** | 状态真源 + 运算 + 导出 + 持久化 | `videoEditor/engine/`（cutia core/managers/commands/renderer/storage 搬入） | **搬 cutia** |
| **桥（接进来）** | 模型互译 + 入轨/出片/持久化三桥 | `videoEditor/engine/adapters/` · `videoEditor/storage/` | 新建 |
| **上层 · UI** | 薄视图，订阅引擎状态 | `videoEditor/panels/`（他们现有 dock/timeline/ruler/preview/export-button） | 保留 + 改写订阅 |

> 依赖方向（单向，朝下）：`panels` → `engine(adapters)` → `engine(cutia)` → `core/types`+`base`。**`engine` 永不反向依赖 `panels`**；`core/types`/`result` 零 IO，可被任意层 import（与 `constants.ts` 头注释的 `check-arch` 白名单纪律一致）。

## 一、七步法落地

### Step 0 · 普查（仓库里已有什么 → 收口判定）

| 能力 | 他们 `videoEditor/core` 现状 | cutia 内核现状 | 份数 | 处置（地基视角） |
| --- | --- | --- | --- | --- |
| 时间轴数据模型 | `types.ts` `Project/Track/Clip`（无 scene，SSOT） | `TProject/TScene/TTrack/TElement`（多 scene） | 2 | **他们的作持久化契约模型**；cutia 运行时用，经 `modelAdapter` 压平 main scene（125 §八） |
| 时间轴运算 | `timelineOps.ts`+`routeClip.ts`（纯函数，248/543 行） | `lib/timeline/*` + `TimelineManager` 命令 | 2 | **收口**：cutia 引擎取代运行时运算；他们的纯函数**退休**（或仅留 `OpResult` 契约层） |
| 导出合成 | `export/composite.ts`+`pipeline.ts`（自建 mediabunny 低层） | `SceneExporter`（mediabunny 高层，同库） | 2 | **收口**：用 cutia `SceneExporter`（已验证）；他们的 `pipeline` 可留作直接通路可选实现 |
| 持久化 | `data/projectRepository.ts` + `contentStore` | `StorageService`（IndexedDB+OPFS，干净适配器接口） | 2 | **收口为可插拔适配器**（见 §四 后端预留）—— 这是关键 |
| 历史栈 | 他们的 `HistoryStack<T>`（泛型，CONTEXT §六 已收口） | cutia `CommandManager` 内建 | 2 | **复用他们的泛型**（cutia 命令接入他们的栈，不写第 6 套） |
| 共享原语 | `base/utils/timeline`(sourceTime/timeScale) · `captureFrame` · `videoEngine` · `filesApi` | 无（cutia 各自内联） | — | **保留在 `base/`**，cutia 引擎复用，不搬第二份 |

> **结论**：库内已有 ≥2 份同语义（时间轴/导出/持久化）→ 按 124 母体一次性收口，**cutia 作运行时真源，他们的纯函数退休**，契约模型（types/result）与基座（base）保留。

### Step 1 · 证伪（需求真存在？）

- **"要一个完整剪辑器"** = 真需求（用户明确要）。
- **"维持上下两层"** 证伪了 `125` 路径 C（独立全屏 cutia、放弃两层）—— 排除。
- **"全盘用 cutia 连 UI 一起替换"** 被 `125` 证伪为过度：他们的 `panels/` 已自建到 G5（128 刚拆完 dock），且须接画布节点双向桥（cutia 没有）→ **UI 必须保留/改写，不能整碗端走**。
- **"无后端"** 是事实（125 §三.1：cutia 持久化纯浏览器）→ 一期不做后端成立。

### Step 2 · 归因（母体，一次收口）

这是 **M3（SSOT 第二份）母体**：不先定共用层，搬 cutia 就会长出"第 N+1 套时间轴/导出引擎/存储通道"。一次收口动作 = **定死「下层引擎 = cutia、契约模型 = 他们的 types、存储 = 可插拔适配器」三条边界**，其余存量（他们的纯函数、cutia 的 UI）按边界归位。

### Step 3 · 定位（★重点 · 从地基）

复杂度该住哪（五问）：

1. **真源在哪**：引擎运行时真源 = cutia `EditorCore` managers；持久化契约真源 = 他们的 `core/types` + `STORAGE_KEYS`。
2. **变化速率**：cutia 引擎内部会变（升级/补功能）→ 隔离在 `engine/`；契约模型/基座几乎不变 → 留在 `core`/`base`。**快慢分居**。
3. **几种实现**：存储适配器 = 真有 2 种（浏览器/后端）→ 不是假接缝，**值得抽象接口**。
4. **改动半径**：cutia 引擎整包搬入 `engine/`，UI 只改订阅源（不动布局/交互）→ 半径最小。
5. **接口窄不窄**：存储适配器接口是 cutia 已有的窄接口（`StorageService` + `getProjectMediaAdapters`）→ 后端预留 = 换实现，零新抽象。

**物理落点（地基优先）**：
- 地基（零改动）：`base/**`、`contracts.ts`、`core/types.ts`、`core/result.ts`、`core/constants.ts`。
- 下层引擎：`videoEditor/engine/{managers,commands,renderer,storage}/`（cutia 源码搬入，去 `next/`/`i18n`/`hugeicons` 仅限其 UI，内核本就零依赖）。
- 桥：`videoEditor/engine/adapters/modelAdapter.ts`（Project↔TProject 压平）+ `videoEditor/engine/adapters/{ingest,export}Bridge.ts`。
- 存储 seam：`videoEditor/storage/{ProjectStorageAdapter.ts(接口), browserAdapter.ts(一期), localToolAdapter.ts(二期 stub)}`。
- 上层：`videoEditor/panels/`（保留，订阅改走 `useEditor()` 风格读 `EditorCore` 快照）。

### Step 4 · 定契（正确性 / 错误透传）

- **OpResult 三态贯穿跨边界**（入轨/导出/落盘）：cutia 引擎的 `export`/`insertElement` 返回须包成 `{ok}|{degraded}|{reject}`（复用 `core/result.ts`，O4 只给跨系统边界）。
- **模型桥诚实**：`modelAdapter` 只搬字段、**不解释 M2 形状**（与 `types.ts` 顶部 `unknown` 预留纪律一致）；cutia 多字段（转场/变速）在 M1 不消费 → 桥只搬运、不窄化，防静默丢数据（Step 4 禁假成功）。
- **单例 vs 多工程**：`EditorCore.getInstance()` 是进程单例 → 切工程必须 `editor.project.loadProject(id)` + `closeProject`（cutia 会 `clearAllAssets`+`clearScenes`，125 §九.2），否则跨工程串数据。
- **存储适配器接口 = 后端预留的契约**：一期 `browserAdapter`（IndexedDB/OPFS 或 contentStore+localStorage），二期 `localToolAdapter` 实现同一接口 → 换实现不碰引擎/UI。

### Step 5 · 定权（架构师定 vs 问用户）

**架构师直接定（结构）**：
- 两层结构、引擎落 `engine/`、契约模型留 `core/types`、存储可插拔接口 —— 直接定。
- `check-arch` 放宽：允许 `engine/` import `base/**` + `core/types`/`result`（参照 `timelineOps` 白名单已放宽的先例，125 §三 / `constants.ts` 头注释）。

**须交用户拍板（业务）**：
- **A/B（一期存储选型）**：A=保留 cutia IndexedDB/OPFS（零后端、但绕过 contentStore 红线）；B=一期就写 `contentStore+localStorage` 适配器（守红线、二期仅换后端目标）。**推荐 B**（红线优先、二期零成本）。
- **M1 功能范围**：只搬 timeline+export（路径 A 范围），properties/AI/素材面板延后？
- **历史栈**：cutia 命令接他们的 `HistoryStack<T>` vs 用 cutia 内建（推荐前者，CONTEXT 已收口）。

### Step 6 · 施工（分阶段，不留尾巴）

- **M0 地基契约**：定 `ProjectStorageAdapter` 接口 + `modelAdapter` 类型；`check-arch` 放宽白名单；`core/types` 标注「持久化契约模型，引擎经 adapter 读写」。
- **M1 引擎搬入 + 三桥**：搬 cutia `engine/`；写 `modelAdapter`+`ingestBridge`+`exportBridge`；`panels/` 订阅改 `useEditor()`；一期 `browserAdapter`。**他们的 `timelineOps`/`routeClip`/`normalize` 退休**（grep 零消费后再删，禁留"以防万一"）。
- **M2 后端适配器**：写 `localToolAdapter`（hit `/files/`+KV），切 `STORAGE_KEYS` 路由；引擎/UI 零改。

### Step 7 · 验证（用户本轮：**先不跑骨架验证**）

- 延后：`npm run dev` 起 `engine`+`SceneExporter` 最小骨架、验证零 next 依赖、导出出 buffer（`125` §十 提议）。
- 仍要做的静态闸：`check-arch`（白名单）、`check:keys`（存储键登记）、`OpResult` 三态单测、`modelAdapter` 往返保真测试（project→TProject→project 字段零丢）。
- 落账：决策进 `CONTEXT.md`（两层结构/引擎落点/存储适配器接口/单例 loadProject），不另开 ADR。

## 二、后端预留（一期无、二期换实现）

```
videoEditor/storage/
├── ProjectStorageAdapter.ts   ← 窄接口（cutia StorageService 同款已存在）
│     interface ProjectStorageAdapter {
│       loadProject(id): Promise<OpResult<Project>>
│       saveProject(id, p: Project): Promise<OpResult<void>>
│       loadMedia(id): Promise<OpResult<Blob>>
│       saveMedia(id, blob): Promise<OpResult<string>>  // 返回可解析 url
│     }
├── browserAdapter.ts   ← 一期：IndexedDB(工程) + OPFS(媒体) 或 contentStore+localStorage
└── localToolAdapter.ts ← 二期：saveMedia→filesApi.uploadFileToLocal；load/save→contentStore/KV
```

- **一期零后端**：`browserAdapter` 直接跑，cutia 原 `StorageService` 适配器接口即此 seam，无需新抽象。
- **二期加后端**：只新增 `localToolAdapter` 一文件 + 在挂载处切换；引擎/UI/桥全部不动。这是 Step 3「接口窄不窄」判据成立的直接收益。
- **红线对齐**：若选 Step 5 的 B，一期 `browserAdapter` 就走 `contentStore`（按 `STORAGE_KEYS.backend` 路由），二期仅把后端目标从 localStorage 换成 localTool，红线自始守住。
