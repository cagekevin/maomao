# 64-AI助手 Memory 系统架构优化方案（契约 + 工作流）

> 日期：2026-08-28
> 性质：**设计提案（未落地代码）**。本文件是 `63` 审计文档之后的目标态设计，仅定义契约与工作流；与已验事实分离，凡本文所述现有项均标注 "现状"，凡目标项标注 "提案"。
> 配套：审计事实与缺陷见 `63-AI助手memory系统审计-逻辑缺陷与数据流-2026-08-28.md`。
> 设计原则：只跑 V1；安全增量落地；契约以能落进代码注释与类型为准；优先为高频变更模块补测试。

---

## 〇、目标架构一句话

把"靠约定、有交叉、有黑盒"的 Memory 系统，重构为**"靠契约、边界清晰、行为自证"**的模型——
**两平面定职责（A=进行态 / B=稳定事实）、门禁类型化、单一语义写网关、成功信号挂真实事件、注入侧去重收口、写读全链路可观测**。

## 壹、契约（Contracts）

契约是"模块间签的书面协议"，落地后由 `service` 层导出并以单测锁死，杜绝将来再 fork。

### C0 数值契约（常量，统一收口）

| 常量 | 现值（现状） | 目标 | 说明 |
|------|------------|------|------|
| `PROJECT_MEMORY_CONTENT_LIMIT` | 500 字符 | 500（不变） | 单条记忆正文上限 |
| `PROJECT_MEMORY_LIMIT` | 60 条 | 60（不变） | 单 agentKey 条数上限 |
| `MEMORY_BLOCK_CHAR_LIMIT` | 1800 | 1800（不变） | 「记」注入块字符上限 |
| `SUMMARY_CHAR_LIMIT` | 6000 | 6000（不变） | summary 上限 |
| `RECENT_KEEP_COUNT` | 8 | 8（不变） | 压缩必要历史门槛 |
| `DEFAULT_LIMIT`(记 top-K) | 6 | 6（不变） | 注入条数 |

> 提案：另立 `memoryContracts.js` 单一常量源 + 快照单测，避免各模块漂移。

### C1 两平面职责契约（治 C3 —— 最关键）

定义"哪类事实归谁"，**从源头消除 summary 与长期记忆的语义重叠**：

- **平面 A「忆」= 任务进行时态**：只承载 *当前这个任务正在发生什么、定下了什么计划、锁定了什么风格契约*。
  - 字段：`lastPlan`、`global_contract`、`summary`（仅任务背景/未完成计划/失败原因）。
  - **不承载**用户的稳定偏好/事实/约束/决定 —— 这些一律归 B。
- **平面 B「记」= 用户稳定事实**：承载 *用户跨任务稳定的偏好/事实/约束/决定*。
- **归属判据（用一句话即可判定）**：*"关掉这个对话，下个任务还该记住吗？"* 该→B；*"只是当前任务的中间态"* 该→A。
- **去重协议**（在注入侧强制）：`buildRequestMessages` 注入 B 前，先用 A.summary 已载明的偏好/约束做交叉去重；或约定 B 不重复注入 summary 已覆盖项。**二选一并写进 `buildRequestMessages` 头部注释。**

### C2 字段所有权契约（治 C2 —— 合一）

| 字段 | 权威源（唯一） | 写者 | 注入 |
|------|----------------|------|------|
| `global_contract` | **唯一权威源** | 统一风格契约逻辑 | ✅（每步带入） |
| `lastSharedStyle` | 只读派生（从 `global_contract` 取），**禁止再独立写** | 无（删除 `conversationAiState.js` L54 独立映射） | 不再单独注入（并入 `global_contract` 块） |
| `lastPlan` | show_plan_for_confirm / execute_plan | 同上 | ✅ |
| `summary` | 压（compressToSummary 写回） | 同上 | ✅ |
| `facts`/`notes` | 提案：移交 B 平面或删除；当前为死字段 | 见 W4/落地阶段 | 未实现前不注入 |
| `artifacts` | conversationAiState | 同上 | 不走 system 注入，走 generations/执行通道（见 C6） |

> 提案：删除 `lastSharedStyle` 字段（或仅保留派生 getter），`buildRequestMessages` 只注入 `global_contract` 一份，消除 token 双写与不一致风险。

### C3 确认门禁类型化契约（治 C4）

把共享布尔位拆成**判别联合 + 单值不变量**：

```ts
// 提案：任一时刻至多存在一个待确认项
type PendingConfirm =
  | null
  | { type: 'plan' }
  | { type: 'memory'; kind: 'preference'|'fact'|'constraint'|'decision'; content: string }
  | { type: 'credit'; genCount: number /* ... */ }

// 状态派生：awaitingConfirm = pendingConfirm !== null（不再是独立布尔位）
```

- **不变量**：写 `pendingConfirm` 与写 `awaitingConfirm` 强一致（同一 write intent），不允许分别赋值。
- **路由契约**：`handleConfirmPlan` / `handleConfirmCredit` 等按 **`pendingConfirm.type`** 分发，禁止"先查 memory 再 fallback"。
- **循环契约**：`runToolCalls` 在写入 `pendingConfirm` 后**若该类型需等待用户 → `break` 工具循环**，不再用"主循环后补查"。

### C4 单一语义写网关契约（治 C7/长期防分叉）

提案：所有对 A 平面 `memory` 的语义写，**只允许经下列显式 write-intent**，禁止散落 `setCurrentMemory({...})`：

```ts
// 提案：service/memoryWriteIntents.js
applyPlanResult(memory, { plan_text, generations })   // 写 lastPlan
applyGlobalContract(memory, contract)                  // 写 global_contract（lastSharedStyle 派生）
applySummary(memory, summary)                          // 写 summary（仅压管道可调）
applyLearnedSample(pool, sample)                       // 写学样本池（仅成功事件可调）
persistProjectMemory(agentKey, { kind, content })      // 写 B 平面（确认门禁通过后唯一入口）
```

- **违反检测**：新增记忆字段必须先在 write-intent 登记，否则视为未契约字段。

### C5 成功信号契约（治 B1/C1）

提案：execute_plan **执行成功**时发出显式事件，学习只消费已证实成功的产物：

```ts
// 提案：事件 shape
//
//   onGenerationSuccess({ nodeId, mediaType:'image'|'video', prompt, url })
//   → 落进 learningPool（见 W4），`buildLearnedContext` 只从 pool 采样
```

- `.generations` 仅作**计划**（进入 A.lastPlan），不直接当"成功样本"。
- 无成功事件时，「学」返回空串（宁可少学，不可学未证实偏好）。

### C6 通道分离契约（治 C5 —— artifacts 黑盒显式化）

显式声明两条独立内存通道，禁止混用：

| 通道 | 承载 | 消费方 |
|------|------|--------|
| **上下文注入通道**（system 块） | 语义记忆：A 平面 + B 平面 + 学 | `buildRequestMessages` |
| **执行/引用通道**（不在 LLM system 上下文） | `artifacts`、`generations` 依赖、图N `direct_refs` 反查 | `execute_plan` |

> 提案：在架构图中明确把 `artifacts` 画进"执行/引用通道"，消除"图外通道"黑盒；文档与代码注释同一口径。

### C7 去重契约（治 4.1 写入侧缺口）

提案：`persistProjectMemory`（即 `saveProjectMemory` 目标态）按 **contentHash 生成稳定 id → 幂等 upsert**：

- 相同正文命中已有 id → **原地更新**（更近 updatedAt），不追加。
- 仍在 `PROJECT_MEMORY_LIMIT` 超限时淘汰最旧。
- 去重与淘汰在**落库层**收口（同时下沉 `sanitizeMemoryContent`，治 4.3），工具层不再单独脱敏。

### C8 注入顺序契约（治 4.1 注入侧 + C2）

`buildRequestMessages` system 块固定顺序（目标态，编号即执行序）：

| 序 | 块 | 说明 |
|----|-----|------|
| 1 | 画布准则 `CANVAS_AGENT_RULES` | 不变 |
| 2 | 会话 `systemPrompt` | 不变 |
| 3 | Skill 文档 + 执行规则 | 不变 |
| 4 | 忆·任务状态 | `summary`（仅任务态）+ `global_contract`（唯一风格源） |
| 5 | 图·图N 编号 | 不变 |
| 6 | 学·成功样本（只读） | 仅来自 W4 成功采样 |
| 7 | 记·长期记忆 | **注入前先按 C1 去重协议过滤**（summary 已覆盖项不重复） |

> `facts`/`notes`/`lastSharedStyle` 在未实现契约前**不注入**（告别死代码，或移交后回归）。

### C9 流式 / 非流式双模契约（告差距 + 固化）

前端 setting `agent_chat_model.streamMode` = `'stream'`（默认）| `'non-stream'`，是**唯一线源**，由 `loadAgentChatModel()` 每次请求实时读。主请求 `roundTrip` 已双模，但**压缩接口未跟随**（现状 `compressToSummary` 硬编码 `stream:true`）。契约要求全链路两模都成立：

1. **单一事实源**：`streamMode` 只在 `agentModelStore` 定义一次；所有消费方经 `loadAgentChatModel()` 读，禁止各自硬编码（现状 compression 违反——需修）。

2. **主请求 `roundTrip`（现状已满足）**：
   - `stream`：`stream:true` + SSE，`Accept: text/event-stream`。
   - `non-stream`：`stream:false` + 普通 JSON，`Accept: application/json`。

3. **压缩 `compressToSummary`（现状违反 → 提案修）**：必须跟随 `streamMode`，由统一决策函数 `resolveCompressStream(streamMode)` 输出：
   - `stream` → `stream:true`（快；慢/思考模型也及时返回）。
   - `non-stream` → `stream:false` + **更长的压缩专属超时**（`SUMMARY_NONSTREAM_TIMEOUT_MS`，独立于流式的 `SUMMARY_TIMEOUT_MS`），避免思考模型在非流式下超时挂起；超时仍按现状"保留旧摘要、不阻塞主流程"。

4. **工具能用性边界（影响门禁/学/忆）**：`roundTrip` 中 `withTools = !isNonStream || ENABLE_TOOLS_ON_NON_STREAM`。因此 **non-stream 默认不传工具**（纯对话），工具类记忆（`memory_suggest` 门禁、`show_plan_for_confirm`/`execute_plan` 产出的 `lastPlan`、进而 `lastPlan.generations` 派生的「学」）默认**不触发**；仅当开了 `ENABLE_TOOLS_ON_NON_STREAM` 开关才回归。契约据此裁能力，见下表。

**双模能力矩阵（Memory 视角）：**

| 能力 | stream | non-stream（默认无工具） | non-stream（开 `ENABLE_TOOLS_ON_NON_STREAM`） |
|------|--------|--------------------------|-----------------------------------------------|
| 主请求对话 | ✅ | ✅ | ✅ |
| 忆·summary/global_contract 注入 | ✅ | ✅ | ✅ |
| 忆·`lastPlan`（策划工具产出） | ✅ | ⚠️ 不触发 | ✅ |
| 记·`memory_suggest` 确认门禁 | ✅ | ❌ 无工具不触发 | ✅ |
| 学·成功采样（基于 execute_plan） | ✅ | ⚠️ 无样本 | ✅ |
| 压·压缩 | ✅ `stream:true` | ✅ `stream:false`+长超时 | ✅ `stream:false`+长超时 |

> 契约结论：**双模都能跑，差异只在"工具能力缺省关闭"**。纯注入路径（忆注入 + 记读取 + 学读取）与模式无关；差异集中在"写路径是否被工具触发"与"压缩的传输形态/超时"。

## 贰、工作流（Workflows）

工作流是契约的时间序实例化。以下用状态与转移表达，落地对应 `workflowState.js` / 工具 execute / service。

### W1 写工作流（A 平面）

```
[来源]                        [write-intent]      [落点]
show_plan_for_confirm ──────▶ applyPlanResult   ─▶ A.lastPlan
execute_plan(成功)      ─────▶ onGenerationSuccess ─▶ learningPool  (C5)
统一风格契约确认          ────▶ applyGlobalContract ─▶ A.global_contract
decideContextCompression ────▶ applySummary      ─▶ A.summary
```

- 规则：每个来源**只能**通过对应 write-intent，不直接 `setCurrentMemory`。

### W2 确认门禁状态机（C3）

```
idle ──(工具触发)──▶ pending {type:'plan'|'memory'|'credit'}
   ▲                      │
   │                      ├─ confirm ─▶ [执行该 type 对应动作] ─▶ idle
   │                      └─ cancel ──▶ [清该 type 暂存] ────────▶ idle
```

- `awaitingConfirm` = `pendingConfirm !== null`（派生，不单存）。
- confirm 动作按 type 路由：plan→执行策划；memory→`persistProjectMemory`；credit→补跑生成。
- 内存/resfresh 恢复：`pendingConfirm` 随 conversation 持久化（现状已含），刷新后据此恢复（恢复后再核实一次）。

### W3 读注入工作流（C8）

```
每次请求 useAgentChat
  → 组装 pieces 按 C8 顺序：
      A 水影:  getCurrentMemory() → extract 任务态块
      B:       buildProjectMemoryContextFromStore(C1 去重协议过滤)
      学:      buildLearnedContext(从 learningPool 采样)
      图:      getCurrentImageMap()
  → buildRequestMessages 按编号装配 system 块
  → fresh-task 只发本轮 user
```

### W4 学采样工作流（C5 → C8）

```
execute_plan 每步成功 ─▶ onGenerationSuccess → learningPool.push({kind,prompt,url,ts})
                                        ↓
buildLearnedContext(query)
  → inferPromptLearningKinds(query)       // 非创作意图→空
  → 按相似度+近因打分 → top-K → 脱敏 → 限字
  → 注入(只读，不改变规则/权限)
```
- 关键差异 vs 现状：**样本来自成功事件**，不再是 `lastPlan.generations`。

### W4b 写路径·模式门控（C9 双模）

```
每次调用写意图前，先判当前 streamMode 下工具能力是否可用：
  streamMode==='stream'                       → 工具全开，写入照常触发
  streamMode==='non-stream' 且 未开 ENABLE_TOOLS_ON_NON_STREAM
      → 无工具：memory_suggest / execute_plan 不触发，
        故「记·门禁」「lastPlan」「学采样」本模式不产生（走空态，不报错）
  streamMode==='non-stream' 且 开 ENABLE_TOOLS_ON_NON_STREAM → 同 stream
```
- 写入代码不得假定工具总在跑；纯对话（non-stream 无工具）下，A 平面仅 `summary`/`global_contract` 可能被写，读注入照常可用。

### W5 压工作流（含双模传输决策，C9）

```
每次请求 decideContextCompression(contextMessages, inputBudget)
  ├─ force     : 超预算 → await 压缩 → applySummary → 重装消息
  ├─ precompress: 后台节流压缩 → applySummary
  └─ none      : 直发
收尾 maybeCompressSummary(消息数 > RECENT_KEEP_COUNT 且节流间隔已过)
压缩传输形态（统一决策函数 resolveCompressStream）：
  stream     → compressToSummary({... stream:true })                    // 默认
  non-stream → compressToSummary({... stream:false, 超时=SUMMARY_NONSTREAM_TIMEOUT_MS })
```
- 双模差异点：流式用 `SUMMARY_TIMEOUT_MS`，非流式用更长 `SUMMARY_NONSTREAM_TIMEOUT_MS`；两者失败都返回 `null` + 保留旧摘要 + 记日志。
- 提案：节流阈值/预算来源写成可观测常量，日志带"本次走哪种决策 + 哪种传输形态及原因"。

### W6 去重/淘汰工作流（C7 + C0）

```
persistProjectMemory(...)
  → contentHash = stableHash(normalized content)
  → 查 hash: 命中→原地更新；未命中→新增(新 id = hash 派生)
  → 超 PROJECT_MEMORY_LIMIT → 淘汰 updatedAt 最旧
  → 更新模块缓存 + 触发持久化
```
- 顺序：sanitize → hash → upsert → 淘汰 → 缓存 → 持久化。

## 叁、落地阶段（V1 安全增量）

按"小步、每步可回滚、每步带单测"推进，**顺序即依赖顺序**。

| 阶段 | 内容 | 关联契约 | 验证 |
|------|------|----------|------|
| P0 | 立 `memoryContracts.js` 常量源 + 类型（含 `PendingConfirm` 判别联合） | C0/C3 | 常量快照单测 |
| P1 | 门禁类型化：`pendingConfirm` 替换 `awaitingConfirm` 布尔 + runToolCalls 分流 | C3 | 门禁状态机单测 |
| P2 | 字段合一：删 `lastSharedStyle` 写源，注入只留 `global_contract` | C2 | buildRequestMessages 快照单测 |
| P3 | 写网关：收拢 write-intent，记忆写仅经网关 | C4 | 网关违反检测单测 |
| P4 | 成功信号：execute_plan 发事件 + learningPool | C5 | 采样只含成功样本 |
| P5 | 落库收口：`persistProjectMemory` hash 去重 + 脱敏下沉 | C6/C7 | 去重/脱敏单测 |
| P6 | 注入去重：`buildRequestMessages` 按 C1 过滤 B 块 | C1/C8 | 重叠场景快照单测 |
| P7 | 可观测：记忆写/读事件日志（受集中开关控制） | — | 日志断言 |
| P8 | **双模收口**：`resolveCompressStream` + 压缩跟随 `streamMode` + 非流式专属超时；写路径模式门控（W4b） | C9 | 双模快照：stream/non-stream × 工具开/关 四态 |

> 依赖：P1 不依赖 P2；P5/P6 相互独立但都依赖 P3 的网关边界。P3 是全局收敛点，优先完成。P8（双模）可并行独立推进，但超时/常量的新增应并入 P0 的常量源与 P7 的可观测日志。

## 伍、验收口径

1. **不再有**"同一事实以 summary 与长期记忆双份注入"（C1/R8 生效后，快照可见仅一份）。
2. **确认卡不吞策划卡**：plan/memory/credit 任意同轮并发，路由按 type 且只生效一张。
3. **长期记忆不累积重复**：相同内容二次确认 → 原地更新而非新增。
4. **「学」只学"成功过"的产物**：无成功事件即不采样，杜绝未证实偏好。
5. **全局只有一个语义写网关**：新增记忆字段编译期/单测即被要求登记。
6. **全链路可观测**：任意一次请求的 memory 写入/读取，日志可回放"谁写、何时写、走了哪条通道"。
7. **双模等权**：`stream` 与 `non-stream` 下，纯注入路径行为一致；`non-stream` 开/关工具两态与能力矩阵一致（无工具时门禁/学/lastPlan 走空态不报错）；压缩在两种模式下都用 `resolveCompressStream` 决策、非流式用独立更长超时且失败保底旧摘要。

## 陆、方案翻车点审计（落地前必读）

本文档是"理想态设计"。逐条回源码核查后，以下翻车点决定了**落地的顺序与回滚边界**，按风险排序。

### F1 〔高·最易翻车〕C3 门禁类型化不是局部替换，是链路重写
- **证据**：`awaitingConfirm` 全仓库 **43 处引用 / 9+ 文件**，且它不止是"确认门槛"：
  - `execute_plan` 硬约束（`useCanvasAgentTools.js` L913）"未确认前拒绝执行"；
  - `send` 主循环 break（`useAgentChat.js` L581 `getAwaitingConfirm() || creditHeld`）；
  - Skill 三阶段确认态（`conversationSkillState.js`）、确认卡（`AgentPanel.jsx`/`AgentMessage.jsx`）、清空/取消收敛（`useAgentChat.js` L748/770/852）。
- **翻车**：C3 把 `awaitingConfirm` 改为 `pendingConfirm !== null` 派生，等于重写整个确认链路。**漏改任一处** → 门禁失去"未确认拒绝执行"或"send 不中断"，且 `awaitingConfirm` 有**真正的独立并列状态源**（见 F9）。
- **缓解**：P1 必须带一张"确认链路引用清单"作为改动 checklist；改完先跑"计划未确认时 execute_plan 被拒 / send 中断"两个回归。

### F2 〔高〕卡片(appendMsg) 与门禁状态粒度错配
- **证据**：确认卡是 `appendMsg` 产生的**消息级对象**（`AgentMessage.jsx` 按消息渲染），而 `awaitingConfirm` 是 **conversation 顶层布尔**——本就不是一一对应（4.2 竞态正是由此）。
- **翻车**：C3 改成单值 `pendingConfirm` 后，若卡片仍并列 append 而状态只存一张，UI 出现 2 张卡、状态只有 1 个 → `handleConfirmPlan` 按 type 路由时对不上卡，比现状更乱。
- **缓解**：`pendingConfirm` 必须**与展示的卡一一对应**（卡 id 与状态同源）；并在 C3 契约里补一条纪律"同轮只允许一种确认卡"（否则改单值就是掩耳盗铃）。

### F3 〔中高〕non-stream 下 force 压缩 = 阻塞主请求
- **证据**：`force` 分支（`useAgentChat.js` L520）`await compressToSummary`，非流式 + 思考模型 + 长超时会长时间挂起主 loop。
- **翻车**：用户点发送后"假死"，体验型回归。
- **缓解**：C9 里明确"non-stream 下 `force` 降级为后台 `precompress`（不 await），或超时内放弃；真正的强制压缩仅 stream 模式允许"。

### F4 〔中〕summary ↔ 长期记忆"交叉去重"是语义去重，难落地
- **证据**：summary 是 LLM 压缩的散文，"summary 已覆盖项"无法可靠字符串匹配。
- **翻车**：实现过重（引入 NLP 语义比较）或误删（本应保留的约束被滤掉，违反 B 平面职责）。
- **缓解**：C1/C8 去重协议别做语义比对，改为**所有权约定**（"约束/偏好默认归 B，summary 不在该区段重复承载"）+ 以 token/条数上限兜底，不追求逐条交叉去重。

### F5 〔中〕C7 hash 去重：归一化基准漂移 = 全部记忆变新增
- **证据**：content 先 normalize 再 hash 作为稳定 id。
- **翻车**：一旦 normalize 规则或措辞微调 → id 全变 → 既存全部长期记忆按"新增"重建、清空淘汰队列，甚至触发限容误删。
- **缓解**：hash 基固定且**过回归单测**；同 idea 不同措辞本就不命中（可接受）；原地更新保留 `source`（不整体覆盖）。

### F6 〔中〕C5 成功信号会造成"学"行为倒退
- **证据**：现状"学"读 `lastPlan.generations`（有计划就有内容）；提案改"仅成功事件"。
- **翻车**：若 execute_plan 成功事件覆盖不全/未埋全，「学」长期为空 → 用户感知"提词变笨"。
- **缓解**：P4 落地时给成功事件加**空池日志告警**；上线期观察"学空池率"，与现状基线对比。

### F7 〔中〕C9 压缩改跟随模式是双面对赌
- **证据**：`compressToSummary` 现状 `stream:true` 是对思考模型友好的刻意设计；改 non-stream 需更长超时，超时没配准就阻塞。
- **缓解**：`SUMMARY_NONSTREAM_TIMEOUT_MS` 先从保守上限起步并**参数可调**；压缩失败路径必须仍"保旧摘要 + 不阻塞"（已写入 W5）。

### F8 〔正面·风险低〕P3 写网关实际改动面很小
- **证据**：活跃的 `setCurrentMemory` 仅 3 处写入（`useAgentChat.js` L426/532 写 summary；`useCanvasAgentTools.js` L833/1062 写 lastPlan）。
- **注意**：`setCurrentSnapshot`（L752，clear 时）与 `conversationAiState.js`（L54/L70 直接改 `conv.memory` 的 lastSharedStyle/artifacts）是**绕过网关的盲区**，P3 收网时须一并纳入，否则契约形同虚设。

### F9 〔低·但必须先答〕存在平行 `awaitingConfirm` 死源
- **证据**：`workflowRuntime.js` L50/L68/L107/L114 有**独立**的局部 `awaitingConfirm` 与 `confirm()`，但**全仓库 0 引用**（孤儿模块）。
- **翻车**：若 P1 改 C3 前不清除/冻结该孤儿源，会被误当"还有一条活链路"而改 surface 双倍。
- **缓解**：P0/P1 前置清理该孤儿模块（删除或标注冻结），消灭并行状态源。

### F10 〔低·已知约束〕长期记忆全局不分项目
- **证据**：`PROJECT_MEMORY_LIMIT` 按 agentKey 全局、`projectId` 参数被忽略（`projectMemoryStore.js`）。
- **注意**：多项目复用一个 agentKey 会串记忆。方案沿用此约束，不引新风险，但契约应声明，避免未来误当 bug 修。

**优先级结论**：先答 **F9**（孤儿源前置清理）→ 再谨慎做 **F1/F2**（门禁链路，给足 checklist + 回归）→ **F3**（非流式 force 降级）→ **F4/F5**（去重降级为所有权约定 + hash 防漂移）→ **F6/F7**（成功信号与超时，可观测兜底）。F8 是加分项，P3 收网时顺带覆盖 `setCurrentSnapshot`/`conversationAiState` 盲区。
