## 1. 问题定义（第 1 层 State 1）

### 1.1 现象

- 给 AI 助手发一句话 → 显示"正在思考中"（流式生成中）。
- 切到设置页/多开页再切回画布 → "思考中"消失，生成已断，回不来。

### 1.2 根因（已核实代码）

- `App.jsx`：`AgentPanel` 只在 `{view === 'canvas' && (...)}` 内渲染。切到 settings/accounts 时 `view` 变 → 整个画布块（含 `AgentPanel`）被 React **卸载**。
- `AgentPanel.jsx:400`：`if (!open) return null` → `open=false` 时组件返回 null，同样卸载。
- `useAgentChat.js` 是 React hook，其**进行中运行态**（`messages`/`streaming`/`sending`/`abortRef`/`sendingRef`/`stateMachine`）全部是组件内 `useState`/`useRef`。组件卸载 → hook 销毁 → 运行态全丢。
- `useAgentChat.js:369-372`：卸载 cleanup 执行 `abortRef.current?.abort()`。
- **结论**：UI 生命周期（AgentPanel 挂载）与运行态生命周期（useAgentChat 状态）**强耦合**，违背"UI 可隐藏但运行态存活"的需求。

### 1.3 现状利好（架构先决条件）

- `agentRuntime.js` 的流式循环（`roundTrip`/`runToolCalls`）**已是依赖注入、无 React 闭包**（docs/12 §0，2026-08-18 已把"执行"从 hook 拆出）。
- 只差把流的"**状态存储**"也脱离组件——正是本次要做的。

### 1.4 核心目标

> **进行中运行态从组件（AgentPanel）解耦，上提到不随组件卸载的模块级 store。UI 可隐藏/卸载，运行态持续存活；切页回来可重新订阅到未完成流。**

### 1.5 核心原则

- 对齐项目已有范式：`conversationStore`/`taskStore` 已用「模块级 `states` + `useSyncExternalStore`」——`useAgentChat` 上提 store 是**回归既有范式**，不引入新架构。
- **独立 store，不混入 `conversationStore`**：进行中运行态 ≠ 已落盘会话，混入会让本已"上帝文件"的 `conversationStore`（见 docs/21 审计）更臃肿。
- **分阶段实施**：先做 M1+M2（运行态上提，保证切页存活），M4（持久化衔接深化）后续补。

## 2. 全局骨架（第 1 层 State 2）

### 2.1 模块列表

| # | 模块 | 一句话职责 |
|---|------|-----------|
| M1 | **运行态 Store** | 新建 `agentSessionStore.js`：持有进行中的 messages/streaming/sending/abort/stateMachine 运行态，用 `useSyncExternalStore` 范式暴露，生命周期独立于组件 |

- M3 依赖 M1 健壮性（UI 安全卸载的前提是 M1 真不依赖组件）✅
- M5 是横切关注点，随 M1-M4 同步 ✅

## 3. 翻车点（第 1 层 State 3）

| # | 陷阱 | 说明 |
|---|------|------|
| T1 | **messagesRef / 落盘一致性破坏** | messages 与 ref 强同步是历史 bug 高发区（AI 回复丢失）。上提 store 后，messages 读写必须**唯一收敛到 store**，hook 与 store 不得各持一份 |
| T2 | **agentKey 切换状态隔离断裂** | store 是模块级单例，必须自管 per-agentKey 运行态（照搬 `conversationStore` 的 `states[agentKey]`），否则切项目时旧流串进新项目 |
| T3 | **`onStream` 回调闭包仍绑 hook** | 流式增量回调目前经 hook 闭包注入。上提 store 后，这些回调必须在 store 内完成（store 持有 abortRef/appendMsg），否则组件卸载后回调链断 → 增量无人消费，"流式继续"不成立 |

## 7. 第 2 层模块细化

> 走快速通道（用户确认）完成。M1 已走完整五步法；M2-M5 基于既有深度理解（useAgentChat 结构、agentRuntime 依赖注入、AgentPanel/App 挂载、conversationStore 范式）一次性细化。

### 7.1 M1 运行态 Store 细化

**边界对齐**：M1 作为进行中运行态唯一持有者；**不含会话列表镜像**（conversations/activeId 仍在 `conversationStore`，M1 按需读取/订阅），落盘衔接归 M4。

**拆解（4 子模块）**：M1-a 状态容器 / M1-b 消息读写 / M1-c 生命周期 / M1-d 流式承接。

**陷阱**：
- M1-T1 messages state 与 internal ref 双源漂移 → 读写唯一收敛
- M1-T2 `useSyncExternalStore` snapshot 引用不稳定 → 惰性快照缓存
- M1-T3 abort 触发源（卸载不应 abort，只有 stop/切 key/切对话才 abort）
- M1-T4 模块级旧会话残留 → `disposeSession`

**约束 + 验证**：

| # | 子模块 | 约束 | 验证标准 |
|---|--------|------|---------|
| M1-C1 | a | `sessions[agentKey]` 分区 + `useSession(agentKey)` 经 `useSyncExternalStore` 订阅 | 切 agentKey 状态独立；快照引用稳定不重渲染 |
| M1-C2 | b | 消息增删改唯一收敛 store action；state 与 internal ref 同步由 action 一次完成 | 无外部直接改；`finally` 落盘不读空占位（回归现有落盘测试） |
| M1-C3 | c | abort 只由显式 action 触发（stop/切 key/切对话），**组件卸载不 abort** | 模拟卸载 streaming 继续累积；调 stop 后 abort 生效 |
| M1-C4 | c | `disposeSession(agentKey)` 清理残留，仅对话/项目切换触发 | 多次切页无堆积；切对话旧流中断 |
| M1-C5 | d | store 内承接 `onStream`，回调链不依赖组件闭包 | 卸载后注入 delta 仍写回 messages（长度增长） |

### 7.2 M2 useAgentChat 薄壳化

**边界对齐**：保持对 `AgentPanel` 的导出 API **完全不变**（messages/sending/error/model/setModel/send/sendImageMode/stop/clear/stateAction/conversations/activeConversationId/newChat/switchChat/deleteChat/refreshConversations/updateMessageByContent/executePlanDirect）。hook 只做三件事：订阅 M1 状态、订阅 conversationStore 会话、把 UI 动作转发给 M1/conversationStore。

**陷阱**：
- M2-T1 现有 `useAgentChat.hook.test.js`（784 行）依赖 hook 内 state，薄壳化后测试要随动 → 测试改为断言 store 状态
- M2-T2 re-export 契约：hook 顶部 re-export agentCore 全部导出（docs/12 §0），薄壳化**不得破坏**这条契约

**约束 + 验证**：

| # | 约束 | 验证标准 |
|---|------|---------|
| M2-C1 | hook 内不再 `useState`/`useRef` 持有运行态（error/model/stateAction 等纯展示态除外） | `useState` ≤3 个且均为展示态 |
| M2-C2 | 导出 API 签名与现有 782 行 return 完全一致 | AgentPanel 无需改动即可编译运行 |
| M2-C3 | re-export agentCore 全部导出保持 | `useAgentChat.hook.test.js` 的 agentLogic/demoPlan 用例不因 import 路径变 |
| M2-C4 | conversations/activeId 改为订阅 conversationStore（不本地镜像重复持有） | 切对话后 UI 列表随 conversationStore 更新 |

### 7.3 M3 UI 挂载策略

**边界对齐**：`AgentPanel`/`App` 调整，使面板可从 canvas 视图卸载/隐藏，但不影响运行态存活；切页回来可重新订阅未完成流。不改 `useAgentChat` 内部逻辑，只改挂载/显隐方式。

**陷阱**：
- M3-T1 `if (!open) return null`（AgentPanel:400）会卸载组件 → 改为 CSS 隐藏（display:none）或拆分"面板容器常驻 / 内容按 open 显隐"
- M3-T2 `view === 'canvas'` 条件整块卸载 → AgentPanel 需从该条件块移出，或让 ReactFlow 卸载但 AgentPanel 常驻
- M3-T3 切页时 `agentOpen` 若被重置会收起面板 → 切页应保持 agentOpen，回来仍开

**约束 + 验证**：

| # | 约束 | 验证标准 |
|---|------|---------|
| M3-C1 | 切页（`view !== 'canvas'`）不卸载 AgentPanel 的运行态宿主（用 CSS/覆盖层隐藏而非条件卸载） | 切 settings 回来，流式未断、"思考中"仍在 |
| M3-C2 | `open=false` 时用 CSS 隐藏而非 `return null`，避免 hook 卸载 | 关面板再开，同一流仍可续（如有） |
| M3-C3 | 切页保持 `agentOpen` 不被重置 | 切页回来面板仍开、消息/流式完好 |

### 7.4 M4 持久化衔接

**边界对齐**：运行态与 `conversationStore` 落盘衔接。M1 只管内存流式；M4 管"流终止/完成时经 `captureActiveConversation` 落盘""切页期间已完成数据可恢复"。**不在 M1 里落盘**。

**陷阱**：
- M4-T1 落盘时机：流进行中不应落盘（半截流写入会污染历史），仅完成/终止/切对话时落
- M4-T2 切页期间"已完成轮次"与"进行中半截"的区分：已完成落盘、进行中留在 M1，回来时合并展示

**约束 + 验证**：

| # | 约束 | 验证标准 |
|---|------|---------|
| M4-C1 | 流进行中不落盘；完成/终止/切对话时经 `captureActiveConversation` 落盘 | 切页期间无半截流写入 conversationStore |
| M4-C2 | 切页回来：已完成历史从 conversationStore 恢复，进行中半截从 M1 续 | 回来自洽，不丢不重 |
