### 五轮复核：**价值质疑 —— 「取消」该不该存在**（2026-09-23 · 用户问"停止本地等待的意义是什么，钱花出去了，我只是为了让他前端不显示？"）

**结论：用户的质疑成立，且比本方案作者理解得更彻底 —— 「取消」的净效果是负的，它不该存在（不是搬家，是取消"取消"）。**

#### 5.1 「取消」买到了什么、买不到什么

| | 取消（`relayCancel`） | **不取消**（今天已有的行为） |
| --- | --- | --- |
| 省上游算力 / 退积分 | ❌ **买不到**：`stopHandle` 无出站取消（O1）；`localTool/src/ai-relay/**` grep `cancel` 只有 `reader.cancel()`（本地流）与 `finishReason:'canceled'`（流式语义）⇒ **上游没有任何取消能力可调** | ❌ 同样买不到（本来就不花） |
| 省本机轮询开销 | ✅ 买到（`clearInterval` + `handles.delete`）—— **几乎可忽略** | 继续轮询到上游写终态 |
| 已付费的结果 | ❌ **主动丢弃**：句柄已删 ⇒ 即使上游随后 `completed`，后端**不会再写回** ⇒ 结果永久拿不到 | ✅ **能拿到**：`budgetMs` 到点 ⇒ 编排返回 `pending` ⇒ 中性提示 + `start.finally` 清 loading ⇒ 行保持 `running` ⇒ `pollTask` 补扫接管 ⇒ 上游完成 ⇒ `completeTask` ⇒ **广播回填节点**（`TASK_COMPLETED_EVENT`，`useNodeGeneration` 按 nodeId 精准回填） |
| 任务中心呈现 | ❌ 显示**"失败"** + 进**「需处理」角标**（O2） | 正常显示结果 |

⇒ **取消 = 主动放弃一个已经付过钱、而且大概率马上就能拿到的结果。** 这正是用户三次表述的物理依据。

#### 5.2 "我不想再看到这个任务"这个正当需求，已有入口

`taskStore.removeTask:544-556`（任务卡片「⋮ → 删除任务」）：前端移除 + `deleteTask(id)` **真删后端行**
+ `deletedIds.add(id)`（此后该 id 的终态晚到只 `debug`、不刷 warn，已按 ADR-0059 处理）。
⇒ **要"不显示"，用「删除任务」；不需要"取消"**。

#### 5.3 顺带发现一处语义错误（O2 的根因）

`relay-poll.ts:107` 注释把"已取消"归进 `failed`，并定义 `failed = 确定没跑（本地前置失败/上游明确报错/**已取消**）`。
⇒ **归类本身就是错的**：取消时上游**恰恰在跑**。这才是"取消的任务显示失败"的根因，不是文案问题。
`cancelled` 终态从未引入（`relay-poll.ts:121-122` 只把它当**编译期守卫的反证例子**）。

## 一、实证复原（链路逐层已核）

### 1.1 「停止」的实际链路

```
点「停止」
 └ useNodeGeneration.stop:298-301    abortRef.abort() + updateNodeRuntime(loading:false)
    └ orchestration catch:233-240     classifyError === 'abort' → taskCtl.fail('已停止')  ← 前端行 = **failed**
       └ relayProxy:360               in-flight attach 的 `cancelOnAbort: true`
          └ relayProxy:235-243        onAbort → relayCancel(frontTaskId)（失败只 warn）
             └ POST /api/generate/:id/cancel   （routes/generate.ts:195-205 → `{code:0,data:{ok}}`）
                └ relay-poll.ts:949-958      句柄在 ⇒ stopHandle + upsertFailed('已取消')
                                             句柄不在 ⇒ **return { ok:false }（什么都不做）**
```

### 1.2 三个已核实的事实

**① `relayCancel` 把后端的"没做成"吞成成功**（ADR-0048 违规）：

```172:182:src/components/generate/lib/relayProxy.ts
export async function relayCancel(frontTaskId: string): Promise<{ ok: boolean }> {
  try {
    await httpRequest(`${API_BASE}/api/generate/${encodeURIComponent(frontTaskId)}/cancel`, {
      ... retries: 0, timeoutMs: LOCAL_TOOL_PING_TIMEOUT, label: 'relayCancel',
    });
    return { ok: true };
```

后端句柄不存在时返回的是 **HTTP 200 + `{code:0,data:{ok:false}}`** ⇒ 走不到 catch；
调用点又只 `.catch()` **从不读 `ok`** ⇒ **"取消没成功"两头都没人看**。

**② 中止后前后端分叉，且结果永不再回来**：前端行置 `failed`，后端行仍 `running`
⇒ `pollTask.startRecoveryRound` 候选只含 `running`/`pending`（`pollTask.ts:142-147`）⇒ **再也不接管**。

**③ 一个动作三个词 + 归错档**：按钮「停止」· 前端行「已停止」· 后端行「已取消」，
一律落 **failed** ⇒ 主动停止 = 记一笔失败，还进「需处理」角标。
⚠️【四轮复核】**二稿没有治这一条**（见 O2）：P3 仍用 `failTask('已取消')` ⇒ `status` 还是 `failed`
⇒ `statusLabel` 显示**"失败"**、`isTaskNeedsAttention` 计入**「需处理」角标**。症状原样保留。

**④【四轮复核·新增】"取消"不停上游，只停"本地等"**：

```256:264:localTool/src/relay-poll.ts
function stopHandle(h: PollHandle): void {
  if (h.stopped) return;
  h.stopped = true;
  if (h.timer) { clearInterval(h.timer); h.timer = null; }
  if (handles.get(h.frontTaskId) === h) handles.delete(h.frontTaskId);
}
```

`stopHandle` 只清**本地轮询定时器**并从 `handles` 移除 —— **没有任何出站取消请求**。
⇒ 「取消」的真实语义 = 「**本地不再等**」：前端不再 attach、后端不再轮询、行标 failed；
**上游任务照跑、照计费**，只是结果永不再被拉回。
⇒ 这正是用户那句"我积分都花出去了，我停止他干嘛"的物理事实 —— 本批只是把按钮**换了个地方**。
⇒ **文档与 ADR 措辞必须诚实**：不许写"停后端句柄"，要写"**停止本地等待**"。

## Step 0 · 普查

### 表① 最优解（一屏以内）

> **能力**：把"中止"这件事**归位**到唯一拥有它的地方。
> - **判据**：中止 = 停后端句柄 = 管理**已提交任务** ⇒ **属于任务中心**（拥有"已提交任务"的那一方）；
>   节点只负责"提交 + 显示结果"，**不含中止**。
> - **链路**：`任务中心卡片「取消」` → `relayCancel` → `POST /api/generate/:id/cancel` → 停句柄 + 置 failed。

## Step 2 · 归因

**母体**：**「中止」被放错了所有方** —— 它被挂在**节点**上（节点只拥有"一次提交"），
而它真正的作用对象是**已提交任务**（后端句柄 + 任务行）。归属错 ⇒ 语义、文案、状态全拧。

- 症状 3 个（同源）：① `relayCancel` 假成功（M2：判据没落进代码，`{ok:false}` 无人读）；
  ② 中止后前后端分叉且结果永不回填（M4：描述层承诺与实现脱节 —— "停止"暗示任务结束了）；
  ③ 主动停止被记成 failed（语义归属错）。
- 不编第三个母体；`upsertFailed` / `stopHandle` / pending 分支都对，不动。

| **节点** | 提交一次生成 + 显示结果 | **中止**（无按钮、无出口） |
| **任务中心** | 已提交任务的列表 + **取消**（唯一入口） | 发起生成 |
| **后端** | 句柄生命周期（含预算到点写终态） | — |
| **上游（lovart 等）** | — | **不受任何一方控制**：`stopHandle` 不停它（O1）⇒ 取消后它照跑照计费 |

- 「取消」= `relayCancel` → **停「本地等待」**（前端不再 attach + 后端不再轮询）+ 行落 `failed`（文案「已取消」）；
  **成功后结果不再回填**（用户已明确放弃）。
  ⚠️【四轮复核·措辞纪律】**不许写"停后端句柄"** —— 停的是**本地轮询句柄**，不是上游任务（O1）。
  正确表述：「取消 = 本地不再等待」。ADR-0060 与本文件的措辞必须与此一致。
- 取消**失败**必须可见（ADR-0048）：`relayCancel` 读 **`res.data.ok`**（返回是信封，R12）；`ok===false` → 留痕 **且** 给用户反馈，**按原因分级**（R9）：无句柄 ⇒ 中性提示"任务可能已结束"；网络/传输错 ⇒ 可见失败。
- **【三稿·新增】取消成功的落点分工**（R10，已复核）：P3 的 `failTask` **改内存** ⇒ UI 立即显示"已取消"（`taskStore.ts:507-509`）；
  **执行态真相仍归后端**（落库被拦是应然，两边一致）。P4 只负责"**不因此误弹红 toast**"，不负责置行。
  ⇒ 分工是：**P3 落 UI，后端落真相，P4 管静音**。
- **【三稿·新增】取消入口的可见性判据** = `isTaskCancellable`（= `isTaskActive` **且** `type ∈ {image, video}`，与 `pollTask.ts:142-147` 同口径，收口在 store），**禁止**消费方内联这条判断（对齐 `isTaskActive` / `isTaskNeedsAttention` 的既有规矩）。
- ⚠️ **【二轮复核·降级】后端"预算到点必写终态"在正常路径成立**（POST 必给 `budgetMs`，缺则 fail-fast；`DEFAULT_BUDGET_MS` 是 `Record` 全覆盖）。仅**边缘分支**不成立：快照 capability 非法/损坏 ⇒ `rowBudgetMs` 为 `undefined` ⇒ 句柄超时判定可恒 false —— 即 **TD-08-51** 既有情形（后端已"留痕跳过"）。⇒ **沿用既有债，本批只声明、不修**（登记见 §7.4 债②）。

### 4.2 编排的终止分类（**【三稿·修订】abort 分支按「后端有无句柄」分级**，不再一刀切）

```
run：r.pending    → 现状（不碰任务行 + 中性提示）   ← 预算耗尽走这里，loading 由 start 的 finally 清
     r.ok===false → 【新增前置判据】命中 cancelledTaskIds ⇒ 不 fail、不 toast（R2 的 live 路径，P4）
                    否则 → 现状（fail + onFail + 红 toast）
     catch: abort → 【改·分级】① 该链路**后端有句柄** ⇒ 不 fail，只 onAbort?.() + 返回 {ok:false, aborted:true}
                              ② 该链路**无句柄** ⇒ 保留 fail（现状），否则行永不收敛（R3）
     catch: 其他 → 现状（fail + onFail + toast）
```

**分级表**（三轮复核后：可达范围内**只有第一行**，故**不新增判别字段**）：

| 情形 | 后端有句柄？ | 处置 | 可达性 |
| --- | --- | --- | --- |
| image/video abort | ✅ | **不 fail**，行保持 running，交 pollTask 收尾 | ✅ **唯一可达** —— abort 只在 attach 循环内被检测（`relaySubmit` 不接 signal ⇒ submit 不可中断），此时句柄已存在 |
| ~~submit 前 abort~~ | — | — | ❌ **已撤回**：`relayProxy.relaySubmit`（`:110-117`）的 `httpRequest` **不传 signal** ⇒ submit 阶段无法被 abort |
| text / chat abort | ❌ | 理论上**应保留 fail** | ⚠️ **当前不可达**：TextGenerate 按钮已由 D2 删；`reportGenerate` 唯一调用方是 orchestration，剧本盒只用 `type:'image'` |

⚠️ 二稿的"唯一 abort 源是 `start:247`"**成立**（三轮复核）：剧本盒虽走同一 orchestration，但其
`onStopScriptItem` **无 UI 消费者**、`withTimeout`（360s）**大于** image `budgetMs`（300s）⇒ 生产上不 abort。
⇒ 第一行是"真会执行到"的那一行，第二三行是**防回潮**（不可达但不许写错语义）。

**【二轮复核·撤回】不新增 `submitted` 字段**：可达范围内"有无句柄"恒为"有" ⇒ 该判据是**恒真分支**，
铺它 = 为不可达的消费方铺路（ADR-0053①）。改为在 abort 分支写**注释**声明这个前提：
「此处不 fail 的前提 = 后端已持有句柄；**若将来有 text/chat 或未 submit 链路走 abort，必须恢复 fail**
—— 否则行永不收敛（`routes/tasks.ts:215`）」。⇒ **零新增字段，维持二稿的删除量**（见 §7.5 闸二）。

### 4.3 三铁律自检

- 生产者给全：后端已给 `{ok}`，"前端没读"是缺的判据 ⇒ 在**传输层**补。
- 消费者只转发：节点不调中止；任务中心只调 `relayCancel`；**零新增机制**（复用既有 attach / 补扫 / pending 收敛）。
  ⚠️【三稿·自洽修正】二稿此处写"**零新增判据**"，与 §7.5 闸二"新增 2 处判据"**矛盾** —— 如实改为：
  本批**新增 2 处判据**（`cancelledTaskIds` 取消标记 · `isTaskCancellable` 可取消口径），已计入闸二。
- 不越权：中止判据归任务中心（拥有已提交任务的一方）。
