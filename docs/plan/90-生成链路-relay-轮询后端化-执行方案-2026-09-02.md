## 0. 现状与问题

**现状轮询在前端**（S2 收口）：taskStore.ensurePolling 注册表，in-flight + 恢复（刷新重扫）都在前端。刷新靠「启动扫描重新接管」。已稳定，但前端复杂。

**relay 现状**（C 步）：`/api/relay` 用 kit `executeModelProtocol` 内部**同步 await 轮询**到终态才返回。问题：前端刷新 → POST 连接断 → 无恢复、无进度（丢图/丢积分）。

**最优解**：轮询句柄从浏览器搬到 localTool，且**可 attach**——不是 kit 内部同步 await，是 localTool 提交后持有句柄、落库，前端 GET 可重新接上。

---

## 1. 目标形态（80 号 §十一 + relay 结合）

```
POST /api/generate                提交 → localTool 起轮询(句柄落库) → 立即返回 {code:0,data:{taskId}}
GET  /api/generate/:frontTaskId   查进度/结果(可重复 attach 到同一句柄)
      - running → {code:0,data:{status:'processing', progress}}
      - completed → {code:0,data:{status:'completed', url:'/files/...'}}   ← 后端已落盘 /files/
      - failed   → {code:0,data:{status:'failed', error}}
```

**关键语义**：轮询句柄生命周期 = localTool 进程（非浏览器页面）。前端刷新 → GET attach，句柄没死，任务继续跑。**前端不再需要** ensurePolling/启动扫描/恢复落盘那套（S2 前端逻辑最终可删）。

## 2. 后端落点（localTool 侧）

### 2.1 复用现有基建（别重造）
已存在：
- **tasks 表**（`localTool/src/db/database.ts`）：已落库 `task_id`/`poll_task_id`/`thread_id`/`status`/`progress`/`result_url`/`error_msg`。
- **查询能力**：`localTool/src/routes/system.ts` 的 `handleGatewayTask`（GET /api/v1/gateway/task/:id 转发 9004）+ `extractAndPersistThreadId`（提交时落库 task_id）。
- **落盘归属**：`saveRemoteUrl`（files.ts，已 export，S1 并发锁）→ tasks 目录 + `generated_<时间戳>` 命名（relay-route 已对齐）。

### 2.2 新增一个「localTool 轮询句柄管理器」（核心新代码）
放 `localTool/src/relay-poll.ts` 或并入现有路由。职责：
- `Map<frontTaskId, PollHandle>`（进程内）+ 落库（tasks 表，靠 poll_task_id/thread_id 关联）。
- 提交后注册轮询器：**复用 kit 的单轮查询**（不是 executeModelProtocol 整体 await）——即用 kit 的 `submitModelProtocol` 拿 task_id，然后 localTool 自己定时查（可查 9004 或 kit poll），到终态落盘。
- **句柄持久化**：localTool 进程重启后，从 tasks 表读 `running/pending && poll_task_id` 重新起轮询（类似前端 S2 的启动扫描，但在这后端）。这一层保障「localTool 重启也不丢」。
- 轮询间隔/总超时：对齐前端 S2 的 `GEN_POLL_INTERVAL`/`GEN_TIMEOUT`。

### 2.3 端点
- `POST /api/generate`：提交（走 relay presets + kit submit）→ 拿 task_id → 注册 poller → 返回 taskId（**不等终态**）。
- `GET /api/generate/:frontTaskId`：从 Map/库查该任务 → 返回 progress / completed(url) / failed。**已完成后结果 URL 直接回 /files/**（后端早落盘）。

> 进度如何推（可选，先低频 GET 够用）：前端要实时进度 → 前端定时 GET 拉；或 localTool SSE 推。**先用低频 GET**（executeModelProtocol 轮询进度可从网关拿）。

### 2.4 落盘归 localTool（已完成大半）
结果落盘用 `saveRemoteUrl`（relay-route 已做）。后端轮询到 completed 后**自己落盘**再存 result_url —— 前端拿到即 /files/，永不接触上游外链。

## 3. 前端落点（relayProxy）

### 3.1 relayProxy（薄壳）
前端只发意图，两态：
```ts
async function relaySubmit({providerId, capability, model, prompt, ...}) → {ok, taskId}   // POST /api/generate
async function relayPoll(taskId) → {status:'processing',progress} | {ok,url}              // GET /api/generate/:taskId
```
替换现有 generateImage 的提交+轮询。

### 3.2 刷新恢复退化为「GET attach」
前端刷新后，任务中心从 /api/tasks 载入 running 任务 → 逐个 GET /api/generate/:id attach 同一句柄 → 拿进度/结果。**不再是前端起 ensurePolling 循环**。

### 3.3 最终可删（relay 稳定后）
前端 `pollTask.ts`（整删）、`taskStore` 的 `ensurePolling/occupyOnly/startRecoveryRound`、恢复落盘补丁（后端已落盘，前端不再需要）。**分阶段删**，先双轨。

## 5. 关键决策 & 红线

- **轮询归 localTool、句柄可 attach**——这是本文唯一目标，别退回「前端 ensurePolling」也别退回「kit 同步 await 假后端轮询」。
- **双轨并行**：R1-R6 期间老链路（proxyGenerate/pollTask/useNodeGeneration 落盘）保留，新链路(image relayProxy)逐步切。别一刀切删老代码，能力退化=No-Go。
- **能力零退化**（对照 execution-plan §5.0.5）：进度条、取消(AbortSignal)、参考图归一、错误中文降级、CLI 平台、刷新恢复——逐个有人兜住才允许删/切。
- **落盘位置/命名**：`uploads/tasks` + `<sha1>_generated_<YYYYMMDD_HHMMSS>.<ext>`（对齐存量生成结果，已被生成面板 rescan 识别）。
- **并发/幂等**：结果落盘走 `saveRemoteUrl`（S1 并发锁），别另写一套。
- **contracts/check:api**：新增端点要登记 `router.ts` routes + `contracts.ts apiRegistry`（`npm run check:api`）。
- **别在长会话尾部硬铺**：R1-R7 是几个独立 commit 的大活，建议专注分段做，每步过 tsc + 测试 + 真机。
