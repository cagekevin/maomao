# 28-R5 · check-api 校验增强：fn 存在性检查（可执行）

> 配套售后计划：`docs/27-API中转层售后收口计划-2026-08-22.md`（R5）。
> 目标：让 `npm run check:api` 能发现「apiRegistry 登记了 ACTIVE、但前端代码根本没有对应函数」的**幽灵条目**（本次 platform 域三条就是因此漏检，见 §背景）。

---

## 1. 背景与动机

### 1.1 本次踩坑
apiRegistry 里 platform 域三条标了 `ACTIVE` + `fn: 'fetchBuiltin'/'Xi 拉取模型系列'/'fetchPluginManifest'`，但**前端代码里这些函数根本不存在**。`check:api` 没报错——因为它只校验「已登记条目 ↔ 后端路由」镜像匹配（后端确实有这些路由），**不校验「fn 引用的前端函数是否真实存在」**。

### 1.2 现状脚本能力（`scripts/check-api-contract.cjs`）
- `main()`（:177-221）：遍历 apiRegistry，对每条做：
  - 信封类型合法（:200）
  - path 在后端路由存在（:206-211，否则 ACTIVE→error 白实现 / RESERVED→warn）
  - method 一致（:216）
  - 信封形态（`checkEnvelope` :161，交给 `detectShapes` 静态扫描 handler）
- **缺失**：对 `entry.fn` 的前端函数存在性**零校验**。

### 1.3 收益
- 根治「幽灵 ACTIVE」：登记了却无前端实现 → 立即 warn
- 让 apiRegistry 与「前端实际代码」强一致，而非只与「后端路由」一致
- 与「代码即知识」一致：登记表的 fn 必须是真实可调用的

## 2. 实现方案

### 2.1 解析 `entry.fn` → 定位前端模块 + 函数

`apiRegistry` 的 fn 字段有 3 种形态，需分类处理：

| fn 形态 | 示例 | 处理 |
|---|---|---|
| **模块.函数** | `localToolApi.fetchTasks` | 解析出模块 `localToolApi` + 函数 `fetchTasks`，查该模块是否 export |
| **模块.对象.方法** | `localToolApi.providerApi.fetchModels` | 解析模块 + 对象 + 方法，查 export 且对象含该方法 |
| **非函数占位** | `(前端零消费)`、`proxyGenerate.__proxyFetch + chatProxy`、`logger 上报事件`、`filesApi.read (二进制流)` | **白名单豁免**（不校验，或按需解析） |

### 2.2 前端模块白名单（可解析的 ESM 文件）

扫描 `src/components/base/*.js`（及需要的子目录），建立「模块名 → 文件路径」映射：
```
localToolApi → src/components/base/localToolApi.js
filesApi     → src/components/base/filesApi.js
pollTask     → src/components/base/pollTask.js
proxyGenerate→ src/components/base/proxyGenerate.js
...
```

### 2.3 静态提取模块导出的函数名

对每个前端模块文件，正则提取导出符号：
```js
/(?:export\s+(?:async\s+)?function\s+(\w+)|export\s+const\s+(\w+)\s*[=:])/g
```
得到该模块的导出函数集合 `exports(module)`。

### 2.4 校验逻辑（新增到 `main()`，在 :221 后）

```js
// R5：前端 fn 存在性检查（防幽灵 ACTIVE）
function checkFnExists(entry) {
  const fn = entry.fn
  if (!fn || /^\(/.test(fn)) return // 占位描述（以 ( 开头）豁免
  // 解析 "module.func" 或 "module.obj.method"
  const parts = fn.split('.')
  const moduleName = parts[0]
  const file = MODULE_FILES[moduleName]
  if (!file) { add('info', `fn 模块未映射: ${fn}（需加入 MODULE_FILES 白名单）`); return }
  const exported = extractExports(file)
  if (!exported.has(parts[1])) {
    add(entry.status === 'ACTIVE' ? 'warn' : 'info',
        `${entry.status==='ACTIVE'?'幽灵ACTIVE':'fn缺失'}: ${entry.fn}（模块 ${moduleName} 无导出 ${parts[1]}）`)
  }
}
```

### 2.5 占位 fn 的白名单

以下形态**不校验**（是描述性文字，非函数引用）：
- 以 `(` 开头（`(前端零消费)`、`(别名 handler=...)`、`(前端零消费·直连官方)`）
- 含 `+`（`proxyGenerate.__proxyFetch + chatProxy`）
- 含空格但非 `.` 链（`logger 上报事件`）
- `API_ENDPOINTS.fileThumbnail`（是常量引用，非函数，可特判或豁免）

建议：**只校验「形如 `模块.符号`（无空格、无括号、无 +）的 fn`**，其余一律豁免——保守，避免误伤。

## 5. 边界与风险

### 5.1 不脆断原则
- **只对「形如 `模块.符号`」的 fn 校验**，占位/描述一律豁免 → 不会误报
- fn 缺失用 **warn 而非 error**（不是运行必崩，但应引起注意）——ACTIVE 缺失 warn，RESERVED 缺失 info
- 前端模块文件读取失败 → info（不脆断）

### 5.2 已知限制
- **不能验证「函数是否真的被调用」**，只能验证「模块是否导出该函数」——但已足够挡掉「登记了却无实现」的幽灵
- 跨模块 re-export（如 `kvStore.js` re-export `kvGet/kvSet/kvDelete`）——apiRegistry 的 fn 若写 `kvStore.kvGet`，需确保 `kvStore.js` 有该导出（它确实 re-export 了，见 kvStore.js:27）

### 5.3 与既有校验的关系
- 现有：apiRegistry ↔ 后端路由（镜像）
- 新增：apiRegistry ↔ 前端模块导出（fn 存在）
- **两层共同保证**：登记表既对后端有路由、也对前端有实现——才是真正的「唯一真源」
