# ADR-0042 · 深模块判据：窄接口＋厚实现＋被域外消费，行数不作判据

- **状态**：生效
- **结论**：深模块＝窄接口＋厚实现＋被**边界之外**消费（三条全中才算）；**粒度＝能力片（域内小能力），不是域**；文件数与行数不作判据（落盘几十文件、depthVideo 5 文件皆深模块）；达标即受保护，不因行数盲拆，拆分只认真缝隙。
- **日期**：2026-09-19
- **裁定人**：用户
- **触发**：用户裁定 2026-09-19（深模块定义：业务集中性被别的项目利用到，非文件大小；落盘/深度视频为范本）+ TD-07-3/4 巨型文件裁定欠统一判据 + DOMAIN-MODULES Stage 2 深模块化施工在即

## 背景

**旧约定（隐性，从未立条）**：大文件 = 债 = 该拆 —— TD-07-3（`director3d/project.ts` 2058 行/117 导出）、TD-07-4（`App.tsx` 2671 行）当年就是**按行数**登记的债。「窄接口+厚实现=深模块」只在 7 步法 Step 3 有一句话；`DOMAIN-MODULES.md` 有形态描述（窄门面+厚实现+唯一真源）与范本普查（agent / videoEditor / base/media），但那是**计划文档不是裁定判据**。

**用户裁定（2026-09-19）**：深模块的定义**不是**「小文件变成大文件」，而是「业务集中性会被别的项目利用到」——哪怕几十个文件的大业务也可以是一个深模块（落盘就是）；深度视频也是。

## 判据（它凭什么成立）

1. **三判据全中才算深模块**（缺一即不受本 ADR 保护）：
   - ① **接口窄**：对外出口少，消费者不必懂内部结构；物理落点 = 该模块的**门面**（域门面 `index.ts` 或域内子模块门面，ADR-0039 N5 / ADR-0044 §3）；
   - ② **实现厚**：内部复杂度（文件数/行数不限）被封装在接口之后；
   - ③ **能力被边界之外消费**：消费者必须在**该模块的边界之外** —— 跨域 **或** 跨域内子模块都算（用户 2026-09-20 裁定：域内小能力也要成块 ⇒ 原「必须跨域」过窄）。集中性的价值在于**被别人用**（ADR-0053 仍成立：fan-in=0 是幽灵预留）。
2. **粒度 ＝ 能力片，不是域**（用户 2026-09-20）：深构的对象是**域内一个个小能力**（如「下载 + 落盘」合成一块、媒体判型一块、节点写回一块），**不是把整个域变成"深域"**；域是地理边界且仍会演化，能力边界比域边界稳定。⇒ 一个域内可以有多个深模块（`image/`: 编解码 / 编辑器 / 媒体引用 各自成块）。
3. **反面 = 浅而宽**：宽接口薄实现 = 泄漏（7 步法 Step 3）。`project.ts` 的债不在 2058 行，而在 **117 个导出混 6 类职责**（接口宽）——`DOMAIN-MODULES §3.1.3.7` 同判：给它加门面也只是宽接口。
4. **深 ≠ 合并**（承 ADR-0031）：把两个判据不同的域合成一个「大模块」不叫深，是削能力。
5. **被消费必须是真的**（承 ADR-0053）：fan-in=0 不是深模块，是幽灵预留，处置是删。
6. **归属先于深浅**（承 ADR-0040）：先判它在哪（归属），再判它好不好（深浅）。

## 决议

| # | 规则 | 判据 / 范本 |
| --- | --- | --- |
| **D1** | 判模块好坏只看三条：**接口窄 · 实现厚 · 被域外消费**；全中 = 深模块 | 范本见下 |
| **D2** | **文件数/行数不作判据**；巨型文件裁定必须先量三条再谈拆不拆 | TD-07-3/4 复审口径 |
| **D3** | 拆分只认**真缝隙**：变化速率不同 / 出现第二种实现；行数不是理由 | 7 步法 Step 3 |
| **D4** | 浅而宽 ⇒ **收口出口面**（摘 export / 归并门面），不是拆文件 | `project.ts` 117 导出 |
| **D5** | 新建能力默认按深模块形态设计：窄门面 + 厚实现，先答「**谁在它的边界之外用它**」 | DOMAIN-MODULES Stage 2 |
| **D6** | **域内深构**（2026-09-20）：对象 = 能力片；识别三形态 = ①同语义多份（>1 定义处）②一入口多动词（消费者须挑动词）③杂物间（一个文件装多能力）；验收三指标 = 导出面符号数↓ · 同一能力入口数 == 1 · 消费者不必知道内部分支 | 规划 = `docs/plan/域内深构-能力片规划.md` |

**仓内范本（实证）**：
- **落盘（大而深）**：`base/api/filesApi.ts` 全站文件域单点（`saveResultToTasks` 唯一落盘出口 · `persistUrlToUploads` 判据唯一）+ 后端 `localTool/src/utils/fileStore.ts`（落盘真源）——链路 **22 个实现文件**跨前后端；filesApi 模块引用 32、非测试消费方 ≥9（DATAFLOW §十二）。
- **深度视频（小而深）**：`video/depthVideo/` 5 文件 1297 行，四分离（depthUrls 单源 / engine 纯逻辑 / loader 装载 / spawn 派生收口），双宿主跨两域（`canvas/nodes/AssetNode` · `video/nodes/VideoGenerate`）共用 `spawnDepthVideoNode`（区域 07）。
- **反例（浅而宽）**：`director3d/project.ts` —— 117 导出 × 6 类职责。

## 后果

- ✅ **收益**：巨型文件裁定有统一判据（不再按行数登记债）；新建/收口有形态目标；「复杂度放正确位置」有了正面定义。
- ⚠️ **代价 / 回潮风险**：判定要跑 refs + 数导出（取证成本）；「深」可能被误用作**拒绝拆分**的挡箭牌 —— 三条必须全查，说不出三条证据就不许说「这是深模块别动」。
- 📌 **违反时的判据**（怎么发现"又回去了"）：

```bash
# ① 以行数/文件数为拆分或登记债的理由 ⇒ 违规（三条先查）
# ② 出口面 vs 消费面：导出多而跨域消费少 ⇒ 浅而宽（反例自查）
grep -c "^export" src/components/director3d/project.ts
node scripts/mv-sync-refs.mjs refs src/components/director3d/project.ts
# ③ 自称深模块但 fan-in 只有域内/为零 ⇒ 不是深模块（ADR-0053）
```
