# ADR-0047 · 「删」的适用前提：用户能做的事不许变少

- **状态**：生效
- **结论**：「删 > 改」是结论不是前提。删须过两关：**① 用户能做的事没变少**（否则＝越权砍功能，交用户）· **② 真的没人用**（多口径一致报零；`refs` 报 0 单独不算证据）。查不清 ⇒ 不许删，改为修。
- **日期**：2026-09-20
- **裁定人**：用户
- **触发**：TD-17-27（`mv-sync-refs.mjs` 的 `move-dir` 被按「删 > 改」整条删除）

## 背景

**旧约定**：7 步法把「删」写成**首选手法**且不带前提（Step 6 标题「删比改便宜」· 心法 §③「能删 > 能收敛 > 能下沉」· 附 B「「删」比「改」便宜」）。
它当初这么定是对的 —— 本仓"为将来铺路的零消费实现"极多（ADR-0030 幽灵预留），不删就持续漂移。**问题在于这条约定没有写适用边界。**

**触发事件**：`move-dir` 有 3 处已实证损坏且是同一能力的第二份实现，据此**整条删除**；但它是一条**用户能用的命令** —— 删掉它 = 用户少一条「一条命令搬整目录 + 一键回退」= **砍功能**，用户未被问过。

## 判据

**第 0 关 · 目的关（最先过）：删了它，能解决什么问题？系统整体复杂度下降在哪一项？**

- 答不出「**解决什么问题**」或答不出「**下降在哪一项**」⇒ **不删**。
- **反例（2026-09-20 实证）**：按 ADR-0044 §3 原处方删掉 `videoEditor/engine/commands/` 下 5 处"纯中转"子门面、
  父门面改直连具体件 ⇒ 父门面暴露面**仍是 25 项**、3 个消费者实际只用 **7 项** ⇒ **接口宽度一项没变**，
  只是把列表从两处并成一处。**不产生深模块/窄接口 ⇒ 白删（已回退，ADR-0044 §3 已修正）。**
- ⇒ **目标是「深模块 + 窄接口」，不是「少一层 / 少几个文件」**。"少一个同步点"这类**次要收益**不足以单独构成删的理由。

**第一关 · 能力关：删掉它，用户能做的事变少了吗？**

| 删的对象 | 用户能做的事 | 处置 |
| --- | --- | --- |
| 死代码 · 重复实现 · 幽灵预留 · 假抽象 · 兜底 | **没变少** | ✅ 可删（删优于改） |
| **命令 · 入口 · 功能 · 能力 · 对外契约** | **变少了** | 🚫 **不许删** → 摆 A/B/C 交用户 |

**第二关 · 消费关：真的没人用吗？**（对"没变少"那一类同样适用）

- 判据 = **多口径一致报零**：模块引用（AST 图）· 字符串裸引用 · 桶与门面再导出 · 运行时字符串。
- **`refs` 报 0 单独不成立**：该工具自身修过两次盲区 —— ① `@/…` 别名 import 被静默丢弃
  ② 仓库根级件不在扫描根。**盲区下的 0 会直接诱导删活代码**（ADR-0030 的删码判据就是 fan-in）。
- ⇒ 先问：**「证明它没人用的那个工具，我验过它的盲区吗？」**

## 决议

1. 第一关不过（删的是能力）⇒ **不许删**，走 Step 5 摆 A/B/C；选项须含「加回来 / 修它 / 不做」。
2. 第一关过（删的是死代码/重复实现/幽灵预留）⇒ 仍须过第二关：**四口径查清零消费**，缺一不算查清。
3. **举证责任在"删"这一方**；两关都过才可删，过不去 ⇒ **不许删，改为修**。**默认动作是「修对」。**
4. **禁循环论证**：不得拿「规程/文档明令禁用」既当"它坏了"的证据、又当"修好也没人用"的证据。
5. **落点**：本 ADR（判据）· `.codebuddy/commands/架构师改码7步法.md` **Step 6 顶部「删的前置动作」**（动作，含四口径表）· 同文件心法 §③ / 附 B 数据结论② / 手法排行 #3（各一行指针）。

## 后果

- ✅ **收益**：把「删」从**默认**降回**有条件结论**；堵住"用一条错的约定砍掉用户能力"这条路。
- ⚠️ **代价 / 回潮风险**：门槛变高。**反风险**是把"能力"当借口保留真死代码 —— 故第二关仍要求多口径零消费。
- 📌 **违反时的判据**：
  1. 删掉的东西含**命令 / 入口 / 导出 API / 对外契约**，而 `git diff` 里没有"用户已裁定"的痕迹；
  2. 交付说明写「删了 X」却答不出「用户能做的事没变少」；
  3. 拿「规程禁止它」同时充当"它坏了"与"修了也没用"两条论据（循环论证）。
