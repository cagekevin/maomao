# ADR-0044 · 域内落点的四条边界口径

- **状态**：生效
- **结论**：①域根只留门面＋装配入口＋计划例外 ②子域门槛 ≥3 件同职责，不足并进最近子域 ③子域门面须有目录外消费者或担结构职责（纯中转必删） ④D2 优先 D3；子能力目录一级豁免；跨 ≥2 域类型集中 src/types/
- **日期**：2026-09-19
- **裁定人**：架构师
- **触发**：域籍判定第一波台账暴露的域内落点无据可依处（域根散件无出口 · D2/D3 冲突 · 子域门面被误当第二份门面 · 类型件落点）

## 背景

域内落点此前只有口头约定（"域根不该堆散件""子域要达标"），**没有判据**。2026-09-19 第一波台账（311 件）实测暴露四类无据可依：**域根散件无出口**（`image/` 两件 hook：D1 只许留门面 + 计划例外，而 D3 职责名里没有 `hooks/` ⇒ 既不能留根也无处可去）· **D2 与 D3 冲突**（`editors/cameraStudio.ts` 是纯逻辑件：按 D3 属 `lib/`，按 D2 该并进职责最近的 `cameraParams/`）· **子域门面被误当第二份门面**（计划 §A5 判 `image/editors/index.ts`「删」，实测它 6 个消费方全在域内）· **类型件落点无判据**（`src/types/*` 与各域 `types.ts` 并存）。

实证明细（含 `文件:行`）= `daily/架构日志/25-跨区-域籍判定与搬迁-2026-09-19.md §二-bis`。

## 判据（它凭什么成立 / 为什么不成立）

- **域根散件**：域根每一件都必须能指出**它靠什么成立** —— ① 门面（对外唯一出口）② 装配入口（被 `App.tsx` 直接消费 + 有「装配契约，非内部件」注释）③ 计划明写的例外。**给不出 ⇒ 它属于某个职责层 ⇒ 就有落点**（不存在"无处可去"的件，只存在"职责名表没覆盖"）。
- **D2 优先于 D3**：D2（≥3 件门槛）是**结构门槛**，防的是"为一件建一个子目录"的目录爆炸；D3（职责单一）是**命名判据**。二者冲突时 D2 优先 —— "并进职责最近的现成子目录"同时满足职责聚合与不新增目录。
- **子域门面**：ADR-0039 N5 约束的是"**域对外**出口唯一"，不约束域内层级。`image/editors/index.ts` 的 6 个消费方都在 `editors/` **目录之外**（虽仍在本域内）⇒ 它是真出口，**不构成第二份域门面**。
  ⚠️ **【2026-09-20 修正 · 原句下句已作废】** 原文续作「**唯一消费者就是父门面**的 index 是**纯中转** …… **必删**」——
  **该处方已实测证伪并作废**，理由见决议 3-b（删掉它**不收窄父门面的暴露面**，只是把列表从两层并成一层，
  **复杂度不下降** ⇒ 违 ADR-0047 第 0 关「删不解决问题就不删」）。判据的实质**不是**"有没有目录外消费者"，
  而是**"删了它，系统整体复杂度下降在哪一项"**（答案通常是"父门面暴露面收窄"，而不是"少一层"）。
- **类型件**：判据复用「被几个**业务域**消费」（与 ADR-0043 §4「经桶计域」同源）：跨 ≥2 业务域共享的契约类型集中 `src/types/`；仅单域内部使用 ⇒ 随域。
- **域存在性**：域的存在性此前只有计划约定（按产品 `cat` 维度）。实测单件域（`text/` 1 件 · `task/` 1 件 · `generate/` 1 件）确实存在且各有界面/数据落点 ⇒ **件数不是成域门槛**。

## 决议

1. **域根口径**：域根只允许 ① 门面 `index.ts` ② 装配入口（须有「装配契约，非内部件」注释）③ 计划明写的例外。**其余全部入子目录**。D3 职责名表**增 `hooks/`**（域内共享 hook）—— 解 `image/` 两件域根 hook。
2. **子域门槛**：≥3 件同职责才建子目录（D2）；不足 3 件 ⇒ **并进职责最近的现成子目录**（D2 优先于 D3）。例：`cameraStudio.ts` → `editors/cameraParams/`。
3. **门面门槛**：**域门面唯一**（对外）。子目录**不默认建门面**；仅当满足 ①**被本目录之外的代码消费**（域内其他目录也算）或 ②**承担结构性职责**（副作用自注册的唯一 import 点 / 唯一出口收口）时才建。⇒ **保留** `image/editors/index.ts`（6 个消费方在 `editors/` 外）**与** `base/media/providers/index.ts`（内置来源**副作用自注册**的唯一 import 点）；⇒ **推翻** `docs/plan/域归位-最终执行计划.md` §A5「删 `image/editors/index.ts`」（该行标 **G·描述过期**）。
3-b. **【2026-09-20 修正 · 取代原「纯中转＝删」】**"唯一消费者 = 父门面"的 index **不是靠删来处理**。
  - **实证（本条由来的翻车）**：`videoEditor/engine/commands/{media, timeline/{clipboard,element,track,transition}}/index.ts`
    5 处纯转发门面被按原处方删除、父门面改直连具体件 —— 结果**父门面 `commands/index.ts` 暴露面仍是 25 项**、
    3 个消费者实际只用 **7 项**（`use-editor-actions.ts` 4 · `veCommandRedoSnapshot.test.ts` 2 · `media.tsx` 1）
    ⇒ **接口宽度/实际用量 ≈ 3.6 倍，一项没变**。⇒ 删只搬动了列表，**不产生深模块/窄接口**（已回退）。
  - **与 §7/§8 的冲突**：§8 明定「门面导出面按**用例**定义，**不按"当前谁在用"挑符号**」；
    而"唯一消费者 = 父门面 ⇒ 删"正是**按谁在用判** ⇒ 与 §8 冲突，故以 §8 为准。
  - **正确顺序**：① 先判该子目录**是不是一个用例**（§8）⇒ 是 ⇒ 保留门面并按用例定义导出面；
    ② 不是用例且想收窄 ⇒ **改父门面**（按用例拆能力片门面，§7），而不是删子门面；
    ③ 只有当「删了它 ⇒ **父门面暴露面确实收窄**」可验证时，才删。
  - **回 ADR-0047 第 0 关**：**删不解决问题就不删**；删前必须答出"复杂度下降在哪一项"。
4. **子能力目录为一级豁免**：已被计划整体认定为"某子系统"的子目录（如 `agent/assistantTable/` 23 件）**内部不再按 D3 拆**。
5. **类型件落点**：跨 ≥2 业务域 ⇒ 集中 `src/types/`；仅单域内部 ⇒ 随域。
6. **域存在性门槛**：节点类型（`NodePalette` 的 `cat`）**即成域**，与件数解耦（单件域合法）。
7. **门面按「能力片」建；域门面不做并集转发**（2026-09-20 实证）：域门面 = **域级装配入口**（如 `settings/index.ts` 只导出 `SettingsFrame`），域内每个能力片各有自己的门面（如 `settings/store/index.ts`）。**禁止**把域内能力片并集进域门面；**横切消费者（`base/` · `src/hooks/`）只依赖能力片门面，不依赖域门面**。
8. **门面导出面按「用例」定义，不按"当前谁在用"挑符号**（2026-09-20 用户裁定「门面太随意，还不如编排」）：门面 = **用例编排入口** —— 消费者说的是"我要做**这件事**"，不是"我要这个符号"。三条判据：
   - ① **每个导出必须能归到一个具名用例**（"UI 消费供应商" · "云同步恢复后重读域状态" · "渲染设置面板" · 契约语言…）；归不进去的导出 ⇒ 摘掉；
   - ② **同一用例的多个入口必须给出差异判据**（例：`useProvidersList` 相对 `useProviders` 的唯一理由是**原子订阅防连坐重渲**，性能判据可查；给不出 ⇒ 合并成一个入口）；
   - ③ **域外消费者实测只作校验**（覆盖检查：有没有域外需求没被任何用例覆盖），**不作定义来源** —— 否则门面随消费者漂移，且必然漏（实证：本轮按"谁在用"列符号，漏掉 `useProvidersList` ⇒ tsc 红）。
   新增域外需求时：先判"是**新用例**，还是既有用例的**入口不足**"，再改门面。
   反例代价（实证）：`base/store/appSettings.ts` 只想要一个 `buildDefaults`，被域门面拉入 `SettingsFrame → sections/*` ⇒ `check:arch` 报「**会 TDZ 的循环依赖**」，并发作 `AgentPanel.test.tsx` 的 `buildDefaults is not a function`。改回"能力片门面"后：交扯指数（跨子目录未走门面直插）**10 → 4**，环消失、测试全绿。

**落点（本 ADR 的首次落实）**：`src/components/image/hooks/`（新建，第 1 条）· `src/components/agent/contract/`（新建，第 5 条）· `src/components/image/editors/cameraParams/`（第 2 条）。

## 后果

- ✅ **收益**：`image/` 域根散件 4 → 2 件（只剩门面 + 计划例外）；D2/D3 冲突有唯一解；`image/editors/index.ts` 保留（避免 6 处深路径改写或宽门面）；类型件落点可判；单件域不再被质疑。
- ⚠️ **代价 / 回潮风险**：新增 `hooks/` · `contract/` 两个职责名 = **放宽**了域内目录数量。若无人守"≥3 件门槛"，会出现"一功能一子目录"的目录爆炸（这正是 D2 原本要防的）。
- 📌 **违反时的判据（怎么发现"又回去了"）**：
  1. **域根第三类件** ⇒ `find src/components/<域> -maxdepth 1 -type f` 即可发现（第一波已机器化：`TASK-023` 起的「域根散件清单」小节逐件列）。
  2. **新建子目录只有 1–2 件**（违 D2）⇒ `ls <子域> | wc -l`。
  3. **子域门面暴露域外符号** ⇒ 对该子域门面跑 `node scripts/mv-sync-refs.mjs refs <子域门面>`，① 段出现**域外**消费方即违规。
  4. **类型件放错** ⇒ 对该文件跑 `refs` 数业务域数：≥2 却不在 `src/types/`（或反之）即违规。
  5. **纯中转子门面（本轮新增判据）** ⇒ 对每个 `index.ts` 跑 `refs`：① 段**只有父目录的 index.ts**（且该目录不承担副作用自注册）即违规。
  6. **域门面并集转发 / 横切消费者依赖域门面**（2026-09-20 判据）⇒ 对域门面跑 `refs`：① 段出现 `base/` 或 `src/hooks/` 消费者即违规（应改走**能力片门面**）；域门面导出面里同时含 UI 与 store ⇒ 违规。
     ```bash
     # 逐目录体检：件数 ≤5 且带 index 的目录 + 其"域外（目录外）消费者数"
     for idx in $(find src -name 'index.ts' | grep -v node_modules); do d=$(dirname $idx); \
       echo "$d $(find $d -maxdepth 1 -name '*.ts*' | wc -l) $(node scripts/mv-sync-refs.mjs refs $idx | awk '/① /,/② /' | grep -c '^   - ' | tr -d ' ')"; done
     ```
