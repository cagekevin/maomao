# ADR-0021 · 判别联合在-strictNullChecks-false-下的形状约束：禁-as-与-!-绕墙

- **状态**：生效
- **结论**：本仓 strict:false，boolean 判别位只在真分支/显式===false 收窄；故联合须双方各带对方键（可选undefined）或改字符串判别位，严禁用 as/! 绕墙。
- **日期**：2026-09-18
- **裁定人**：架构师
- **触发**：spec/CONTEXT.md §三 类型契约（实测矩阵 daily/架构日志/21-跨区-判别联合boolean窄化约定-2026-09-13.md）

## 背景

**旧做法：按"直觉"写判别联合，编译报错时用 `as` / `!` 压下去。**

本仓 `tsconfig.json` 实测 `strict:false` / `strictNullChecks:false`，但**判别联合的收窄行为在 `strictNullChecks:false` 下与常规认知不一致**：

```ts
// 直觉写法（会在 else / 三元假支 报 TS2339）
type R = { ok: true; value: string } | { ok: false; error: string };
if (r.ok) { r.value }        // ✅ 真分支收窄
else { r.error }             // ❌ TS2339：属性 error 不存在
!r.ok && r.error             // ❌ TS2339
r.ok ? r.value : r.error     // ❌ 假支 TS2339
```

⇒ 每写一处判别联合就撞一次 TS2339。最省力的"修复"是**加个 `as R2`** —— 类型问题消失、绿灯亮起，但那是**把编译期问题埋成运行时不诚实**（`CLAUDE.md §5.1` 的"失败不得伪装"在类型层同款）。

而旧约定的判据**从未被写下来过** —— 它只存在于一次实测里（`daily/架构日志/21-跨区-判别联合boolean窄化约定-2026-09-13.md`），新人撞上必然再走一遍"报错→加 as"的路。

## 判据（它凭什么成立）

1. **可实测**：`strictNullChecks:false` 下**只有「真分支」与「显式 `=== false`」两处会收窄** —— 这是 TS 的已知行为，不是本仓的偏好（实测矩阵见上述区域日志）。**字符串判别位与数字判别位不受影响**（`kind: 'a' | 'b'` 正常收窄）。
2. **有比"绕墙"更根本的手段**（建闸前置评审第 2 问）：改**联合的形状**即可，无需任何断言 ⇒ 手段优先级取「**类型层**」（第 2 位），远高于「机器闸」（第 6 位）。故本条**不需要闸**。
3. **`as` / `!` 的代价是可算的**：它们把"这里类型不收窄"这个**真实约束**抹掉，后人再改时拿到的是**假的类型信息** ⇒ 与 `CLAUDE.md §5.1`「失败不得伪装成空或默认值」同一病灶（把"我不知道"伪装成"我知道"）。

## 决议

**判别联合写成本仓可用的两种形状之一**（任选，`ok` 仍是判别位、语义不变）：

**① 双方各带对方的键（可选 `undefined`）** —— 推荐，改动最小：

```ts
type R = { ok: true;  url: string;  reason?: undefined }
       | { ok: false; url?: undefined; reason: string };
```

⇒ 两个分支的字段**都可直接读**，无需收窄。

**② 改用字符串 / 数字判别位**（`kind: 'a' | 'b'`） —— 不受 `strictNullChecks` 影响。

**🚫 严禁用 `as` / `!` 绕墙**。需要 boolean 分支时**按 ① 改形状**，而不是加断言。

**落点**：`src/components/base/core/degrade.ts`（`tryParseOr` 等原语的契约形状）· `spec/CONTEXT.md §三`（一行索引）· 实测矩阵 `daily/架构日志/21-跨区-判别联合boolean窄化约定-2026-09-13.md`。

## 后果

- ✅ **判别联合在本仓变得可写**：不必每个站点都撞 TS2339，也不必用断言埋雷。
- ✅ 与 ADR-0002（压平必须留痕）**配套**：那条管"消费时怎么处理失败"，本条管"契约长什么样"，两条一起才闭环。
- ⚠️ **代价 / 回潮风险**：形状 ① 的**类型声明更长**（要两遍字段）⇒ 有人会图省事直接 `as`。回潮动因 = "就一个断言，编译器又不会拦"。
- ⚠️ **与 `strict:true` 的关系**：若将来开启 `strictNullChecks`，形状 ① 仍合法（只是字段变可选），无需回改 —— 本决议**与是否开 strict 无关**，是"现在就能用"的形状。
- 📌 **违反时的判据**（怎么发现"又回去了"）：
  1. `grep -n "as unknown as"` / 双断言出现在判别联合消费处；
  2. 非空断言 `!` 出现在联合分支访问上；
  3. `npm run check:any` 报 escape hatch，或 `tsc` 被 `as` 压过的 TS2339 位置出现断言；
  4. 新增 `{ ok: true; value } | { ok: false; error }` 形状（不带对方键）而消费处用断言绕过 —— 即本 ADR 的典型违例。
