# ADR-0023 · CONTEXT 的定位：规则适用性地图（路由表＋例外），不装判据与结构

- **状态**：已取代
- **结论**：CONTEXT 只装两样：①按场景需求反查的跨模块路由表 ②规则适用性的例外与边界；判据本体归 ADR，链路与现状归 DATAFLOW，物理红线归 CLAUDE。
- **日期**：2026-09-18
- **裁定人**：用户
- **触发**：CONTEXT 与 ADR/DATAFLOW 三重重复（§二/§六B 与 DATAFLOW 同内容，§三/§五 与 ADR 同判据）

## 背景

**旧定位（`spec/CONTEXT.md:3` 自述）**：「决策地图 —— 只回答代码本身回答不了的问题：`这个功能放哪 / 该调哪个唯一入口 / 哪些红线不能碰`」。

这条自述**三个答案都有别的主人**：

| 自述要回答的 | 实际归属 | 证据 |
| --- | --- | --- |
| 这个功能放哪 | CONTEXT（**确实独有**） | 无别处承载 |
| 该调哪个唯一入口 | **DATAFLOW** | `spec/DATAFLOW.md:357` 原文已写 `**唯一入口**：node.data 写回 = useNodeData.patchNodeDataById · 节点 id = idGen.generateId · 端口真源 = contracts.NODE_HANDLE_CONTRACT` |
| 哪些红线不能碰 | **CLAUDE.md** | §5.1 四条红线 + §5.4/§5.7 契约 |

⇒ 「决策地图」是一个**没有边界的概念** —— 它把"判据、路由、现状、红线"全部收进来，于是**必然与所有其他文档重叠**。这才是三重重复的根因：不是 CONTEXT 抄了别人，而是**它的定位声明允许它抄**。

**减法实验（本次取证）**：CONTEXT 全部 16 段逐段判定归属 —— **只剩两项独有**（完整判定表见 `daily/架构日志/17-跨区-判据归位与CONTEXT定位-2026-09-18.md` §二）：

- ✅ **§五·五 director3d 子模块边界**（例外）
- ✅ **§六A 决策记录渠道**（元规则）

⇒ 其余 14 段**全部可归别处**（ADR / DATAFLOW / CLAUDE / 7步法 / daily）。

## 判据（它凭什么成立）

**判据是减法实验的结果 —— 只有两项在别处找不到承载：**

**① 按「场景需求」反查的路由表。** DATAFLOW **按链路组织**（生成 / 存储 / 画布链路），回答"这条链路怎么走"；但它**回答不了"我手上这个需求该走哪条路"**。CONTEXT 独有的正是这张**反查表**（例：跨组件共享→`store`；需持久化→`store`+`contentStore`；单组件临时→`useState`）。⇒ 这是**唯一**按"用户意图"而非"模块名"组织的内容。

**② 规则适用性的例外。** 本仓多处"规则说要 A，但这里**不适用**"：`SSE 三件套豁免 httpClient` · `时序敏感处保留手写` · `director3d 不纳入收口` · `contentStore` 的有意裸调。这些**必须与规则同址**（否则读规则的人不知道有例外），**但不能进 ADR**（ADR 是判据的**判定层**，例外是判据的**适用层** —— 判定说"该收口"，适用说"这一处不收"）。**这是第二个结构上不可替代的位置。**

**为什么合成一个定位成立**：两项的共同点 —— **它们都不是内容，而是"内容之间的关系"**。路由是"需求 ↔ 入口"的关系，例外是"规则 ↔ 场景"的关系。⇒ **CONTEXT = 关系地图**，不是内容仓库。

## 决议

**CONTEXT = 规则适用性地图。只装两样：① 按场景反查的跨模块路由表 ② 规则适用性的例外与边界。**

**四份文档的完整分工（按「回答什么问题」切）：**

| 文档 | 回答的问题 | 装什么 |
| --- | --- | --- |
| `CLAUDE.md` | **红线是什么？** | 物理契约、撬不动的红线 |
| `docs/adr/` | **凭什么这么定？被谁推翻过？** | 判据 + 由来 + 违反判据 |
| `spec/DATAFLOW.md` | **这条链路怎么走？** | 现状与拓扑（refs 实证） |
| **`spec/CONTEXT.md`** | **我这一处该走哪条路？哪条规则在这不适用？** | **路由表 + 例外** |

**保留项**（只有这 4 处）：§一A/B 路由表（核心 ①）· §五·五 director3d 边界（核心 ②）· §六A 决策记录渠道（元规则，指向 ADR-0017）· §六B 已收口清单。
其余 12 段的逐段处置见 **ADR-0024 §决议**（同一份落点表，不在此重复）。目标约 120 行（现 337 行）。

**`§六B` 为什么保留极瘦版**：DATAFLOW 的是**描述性**的（"现状是这样"），它**按构造不该承载指令**（其 §维护规矩明令"只写当前真相"，禁写结论重复）。而"**改前先认领这些唯一入口，别重复收口**"是一条**动作指令** ⇒ 必须由 CONTEXT 承担。两者不重复：DATAFLOW 说"现在是什么"，CONTEXT 说"所以你别再写一个"。

## 后果

- ✅ **CONTEXT 有了不可被替代的位置**：两条判据（按场景反查 / 例外与边界）都能通过"别处有没有"的测试。
- ✅ **篇幅与职责匹配**：337 → 约 120 行；其自述的"规范越短越不过时"（§六A 保鲜机制③）**才可能成立**。
- ✅ **新人路径变清晰**：红线看 CLAUDE → 路由看 CONTEXT → 链路看 DATAFLOW → 挑判据看 ADR。**每份文档都可被独立读完**，不再需要"那份最全的地图"。
- ⚠️ **代价 / 回潮风险**：**"决策地图"这个定位听起来更好、更全** ⇒ 未来有人会以"方便查找"为由把内容加回来。防线 = 本 ADR 的**归位问句**（见下），而不是"注意别乱加"。
- ⚠️ **执行风险**：本次删减涉及 16 段，**改动面大**。故分两轮：本轮只落 ADR + 补 7 步法维护动作；CONTEXT 的结构性删减**单独一轮**做（避免一次改太多无法回退）。
- 📌 **违反时的判据**（怎么发现"又回去了"）：
  1. CONTEXT 出现**判据正文**（能回答"凭什么成立"的段落）而 ADR 无对应条目；
  2. CONTEXT 出现**模块清单 / fan-in / 链路图**（→ 该在 DATAFLOW）；
  3. 新增段落的**组织维度是「模块名」而非「场景需求」或「例外」** ⇒ 方向已经错了；
  4. `wc -l spec/CONTEXT.md` 持续增长而其"独有内容"未增长。
- **被取代于**：ADR-0025
- **毕业去向**：合并入 ADR-0025
