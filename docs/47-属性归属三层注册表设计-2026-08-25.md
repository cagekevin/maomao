## 一、动机

当前属性生效规则散落在三处，"被关键帧覆盖"的坑（见 46）只是表象，根因是**没有单一声明**：

- 哪些字段**可被关键帧动画化** → `ENTITY_CHANNELS`（`project.js:154`，M1 已交付）
- 哪些字段**是对象级开关、应勾选即生效** → 散落在 `evaluateActionChannel` / `Inspector` / `setCameraAtFrame` 手写保留，无统一声明（47 病灶）
- 哪些字段**根本不参与动画** → 靠"恰好没写进通道"隐式保证，无显式登记

**目标**：用一个**三层注册表**集中声明每种属性的"归属层 + 通道"，今后任何属性只需登记一次，录制 / 求值 / 渲染 / UI 按层自动生效。

**边界**（顶层架构判断）：注册表只管两件事——**① 该属性是否进关键帧通道（L1 才进）；② 求值结果是否被基线覆盖（L2 强制覆盖）**。它**不接管归一化**（见 §4.4）——防御性归一化（`Boolean(...)`、clamp 等）保留在各 `normalize*Field` 里，不被"按层过滤"连带砍掉。

## 二、三层模型

| 层 | 名字 | 含义 | 关键帧行为 | 求值端行为 | 典型例子 |
|---|---|---|---|---|---|
| **L1** | `animatable` | 随时间是"量"，需打关键帧才有动画 | 录制进通道、可插值 | 关键帧值覆盖基线（无关键帧则保持基线） | `position` `rotation` `scale` `pose` `poseTime` `rigRoot` `joints` `focalLength` |
| **L2** | `objectState` | 对象/镜头级"开关/状态"，勾选即生效 | **不录制**进通道 | 永远从基线取，覆盖任何求值结果 | `continuousMotion` `footLock` `targetMode` `targetId` |
| **L3** | `config` | 纯配置/显示，根本不参与动画求值 | 不录制 | 不进求值器，仅组件消费 | `visible` `includeInExport` `bodyType` `color` `name` `aspectRatio` `loopPlayback` `showGrid` |

> **L1 vs L2**：L1 是"会变的量"（靠关键帧驱动）；L2 是"对象自身的开关状态"，一旦设置整段播放都该遵守，不该被某一帧关键帧冻结。
> **L2 vs L3**：L2 被渲染/求值消费（影响动画行为）；L3 完全在动画系统之外（显示/命名/导出开关/编辑约束）。
> **L3 内编辑约束**：`locked`（编辑期锁定）不参与动画、也不影响求值，划归 L3（见 §8 决策）。

## 四、注册表数据结构（单一声明源）

### 4.1 `PROPERTY_REGISTRY`

取代手写 `ENTITY_CHANNELS`（M1 产物），把「通道归属 + 层面」合并登记：

```js
// 属性归属注册表：集中声明每个实体类型的每个属性归哪一层、属于哪个动画通道。
// 新增属性只需在此登记一次，全链路按层自动生效（录制/求值/渲染/UI）。
// layer: 'animatable'（进通道）| 'objectState'（勾选即生效，不进通道）| 'config'（纯配置）
export const PROPERTY_REGISTRY = {
  person: {
    position:         { layer: 'animatable', channel: 'transform' },
    rotation:         { layer: 'animatable', channel: 'transform' },
    scale:            { layer: 'animatable', channel: 'transform' },
    pose:             { layer: 'animatable', channel: 'action' },
    poseTime:         { layer: 'animatable', channel: 'action' },
    rigRoot:          { layer: 'animatable', channel: 'skeleton' },
    joints:           { layer: 'animatable', channel: 'skeleton' },
    continuousMotion: { layer: 'objectState' },   // 移出 action 通道（46）
    footLock:         { layer: 'objectState' },
    bodyType:         { layer: 'config' },
    color:            { layer: 'config' },
    name:             { layer: 'config' },
    locked:           { layer: 'config' },
  },
  object: {
    position: { layer: 'animatable', channel: 'transform' },
    rotation: { layer: 'animatable', channel: 'transform' },
    scale:    { layer: 'animatable', channel: 'transform' },
    color:    { layer: 'config' },
    name:     { layer: 'config' },
    locked:   { layer: 'config' },
  },
  camera: {
    position:    { layer: 'animatable', channel: 'transform' },
    rotation:    { layer: 'animatable', channel: 'transform' },
    focalLength: { layer: 'animatable', channel: 'lens' },
    targetMode:  { layer: 'objectState' },   // 保留 setCameraAtFrame 特判（§4.5）
    targetId:    { layer: 'objectState' },
    aspectRatio: { layer: 'config' },
    name:        { layer: 'config' },
  },
}
```

### 4.2 派生 `ENTITY_CHANNELS`（保形状 + 锁序 + 校验）

保持旧名向下兼容，**派生结果必须与现有 `ENTITY_CHANNELS` 完全同构**（`{channel: [fieldName, ...]}`），否则破坏已交付的 M1–M4 契约。通道顺序由注册表**书写顺序**决定（合成器按注册顺序逐通道覆盖，[43 M2-C2](file:///Users/kevin/Documents/maomao/docs/43-对象动画通道化重构-PRD-2026-08-25.md#L92)，顺序是契约）：

```js
export const ENTITY_CHANNELS = {}
for (const [type, fields] of Object.entries(PROPERTY_REGISTRY)) {
  const channels = {}
  for (const [field, meta] of Object.entries(fields)) {
    if (meta.layer !== 'animatable') continue
    if (!meta.channel) throw new Error(`[PROPERTY_REGISTRY] ${type}.${field}: animatable 字段必须声明 channel`)
    ;(channels[meta.channel] ||= []).push(field)   // 通道顺序 = 注册表内首次出现顺序（契约）
  }
  ENTITY_CHANNELS[type] = channels
}
```

> 不使用 `Object.groupBy`（ES2024 运行时方法，esbuild 不 polyfill，是全项目唯一隐性新 API 依赖）。用普通 `for` 手写：产出是**纯字段名数组**，且对"animatable 漏写 channel"**显式抛错**，避免静默攒出 `undefined` 分组。

### 4.3 热路径：预编译 L2 字段表

`synthesizeObjectState` 每帧每对象跑，不能现场逐字段判 layer。模块初始化时预编译一次：

```js
// 模块初始化：预编译每实体 L2 字段名数组（热路径只遍历字段名，不逐字段判 layer）
const OBJECT_STATE_FIELDS = {}
for (const [type, fields] of Object.entries(PROPERTY_REGISTRY)) {
  OBJECT_STATE_FIELDS[type] = Object.keys(fields).filter(f => fields[f].layer === 'objectState')
}
export { OBJECT_STATE_FIELDS }
```

求值端 L2 强制保留（替代手写 `targetMode` 保留，但不取消相机特判）：

```js
function synthesizeObjectState(object, channels, frame, fps, path = null) {
  const result = { ...object }
  // ... L1 各通道按序覆盖 ...
  // L2：勾选即生效，永远从基线取，覆盖任何求值结果（含 action 通道的 continuousMotion）
  for (const field of OBJECT_STATE_FIELDS[object.type] || []) result[field] = object[field]
  return result
}
```

> **`continuousMotion` 的循环抑制由渲染端兜底**：`result.continuousMotion` 取基线布尔，实际循环与否由渲染端 [models.jsx:215](file:///Users/kevin/Documents/maomao/src/components/director3d/models.jsx#L214-L216) `continuousMotion && preset.loopable` 决定，与 [Inspector.jsx:41](file:///Users/kevin/Documents/maomao/src/components/director3d/panels/Inspector.jsx#L41)「非循环 pose 下禁用勾选」一致。这与 46 点修的 `基线 && poseCanLoop(pose)` 等价——46 是防御写法，机制层统一后由渲染端收敛。

### 4.4 归一化不被动摇（注册表只管通道/覆盖）

注册表只决定"是否进通道 / 求值是否覆盖基线"，**不接管归一化**。现有的 `Boolean(...)`、clamp 等防御归一化（如 [normalizePerson](file:///Users/kevin/Documents/maomao/src/components/director3d/project.js#L461-L471) 的 `footLock: Boolean(...)`、[project.js:412](file:///Users/kevin/Documents/maomao/src/components/director3d/project.js#L412) 参考图 opacity clamp）保留在各自 `normalize*Field`。切到注册表时**不得**实现成"只归一层则跳过归一化"。

### 4.5 相机不对称（targetMode/targetId 特判别删）

`person` 侧 `synthesizeObjectState(object, ...)` **自带基线** `object`，L2 覆盖有数据来源。但相机走 [cameraAtFrame(keyframes, frame, aspectRatio)](file:///Users/kevin/Documents/maomao/src/components/director3d/project.js#L881)，**签名没有基线相机**——`targetMode/targetId` 的真值在 App 层 `current` state，由 [setCameraAtFrame](file:///Users/kevin/Documents/maomao/src/components/director3d/App.jsx#L678-L685) 写回时保留。

> **因此 `setCameraAtFrame` 的两行特判必须保留**，不得删。L2 自动覆盖只服务对象侧；相机侧维持显式保留。若坚持相机也走 L2，须给 `cameraAtFrame` 加基线参数并改所有调用点——复杂度大于收益，不采纳。

## 五、实施步骤（落地时）

1. 在 `project.js` 新增 `PROPERTY_REGISTRY` + §4.2 派生 + §4.3 预编译；派生出的 `ENTITY_CHANNELS` 与现有一致（有断言比对）。**不改动既有通道形状/顺序。**
2. 把 `continuousMotion` 从 `person.action` 移到 `objectState`（改注册表一处）；`objectKeyframeFromObject` 因通道表不含它而**自然不再录制**，无需拆散「只写 animatable 字段」逻辑。
3. `synthesizeObjectState` 末尾加 L2 通用覆盖（§4.3）。`setCameraAtFrame` 的 targetMode/targetId 特判**保留**。
4. 渲染/求值侧确认 `continuousMotion` 循环抑制由渲染端 `preset.loopable` 兜底（§4.3），Inspector 禁用态天然一致。
5. 同步更新单测断言：`continuousMotion` 移出 action 通道，L2 字段求值取基线。**旧工程不计入，不做 continuousMotion 残留迁移**（46 已判定语义变更为预期结果）。
6. 回归（见 46 第五节）：先勾后打帧 / 先打帧后勾选 / 无关键帧勾选 / 非循环 pose 自动静止 / 相机始终面向对象，全部生效。

## 六、收益

- **单一入口**：加属性/开关只改 `PROPERTY_REGISTRY` 一处。
- **不再有"被关键帧覆盖"的隐性坑**：L2 由注册表语义保证，不用每个开关手写保留逻辑。
- **职责清晰**：L1 量 / L2 开关 / L3 配置边界显式，新人一看注册表就懂。
- **可审计**：文档与代码同一份真相，46 的清单可直接由注册表生成。
- **衔接既有契约**：派生 `ENTITY_CHANNELS` 与 M1 产物同构，不破坏已交付的通道结构 / 顺序。

---

## 七、副作用与规避

1. **语义变化（预期）**：`continuousMotion` 不再随关键帧变化 → 持续循环从"随段可变"变"整段恒一"。「同段循环、跨段静止」式差异策略取消。**旧工程不计入，非回归**（已决断）。
2. **派生通道潜风险**：若有人**调整字段顺序**，依赖"注册顺序覆盖"的合成行为会变。规避：文档注明通道顺序是契约；可加一条 dev 断言比对派生结果与白名单快照。
3. **animatable 漏写 channel**：旧草案用 `Object.groupBy` 会把漏标 channel 的字段静默攒进 `undefined` 组。规避：§4.2 派生处显式 `throw`。
4. **归一化被连带砍**：registries 若"按层过滤归一化"会砍掉 L2/L3 防御。规避：§4.4 明确注册表不接管归一化。
5. **相机 targetMode 退化**：删 `setCameraAtFrame` 特判会丢开关。规避：§4.5 保留特判。
6. **热路径开销**：每帧逐字段判 layer 浪费。规避：§4.3 预编译 L2 字段表。

## 八、决策记录

| 开放问题 | 决断 | 理由 |
|---|---|---|
| `locked` 归 L2 还是 L3？ | **L3** | L3 = 完全在动画系统之外；`locked` 是编辑约束，不参与渲染、也不应被求值覆盖，归 L2 只会让求值器做无意义覆盖。46 的 A 类表从"识别开关"视角分类它，与本文"数据归属"互不冲突。 |
| 全局开关（`loopPlayback` 等）是否进注册表？ | **不进 `PROPERTY_REGISTRY`** | 不在对象上，求值器/录制器都够不到；单独建 `GLOBAL_CONFIG_REGISTRY` 属过度设计，文档登记即可。 |
| 相机 `aspectRatio` 归层？ | **L3** | 被 `setCameraAtFrame` 透传、不参与插值；当前不被 `cameraAtFrame` 误覆盖，安全。 |
| 相机 L2 是否走自动覆盖？ | **否，保留特判** | `cameraAtFrame` 无基线参数，走 L2 需改签名+全调用点，复杂大于收益（§4.5）。 |
| 旧工程 `continuousMotion` 残留关键帧是否迁移？ | **不迁移** | 移出通道后 `snapshotToChannelKeys` 天然不落该字段；旧工程不计入（46 已决断语义变更为预期结果）。 |
