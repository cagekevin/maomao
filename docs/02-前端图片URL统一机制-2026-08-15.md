# 02 专题：前端图片 URL 统一机制

> 日期：2026-08-15
> 解决「前端图片反复破图 / 发送到后端丢图」的系统性问题。核心是建立**统一图片 URL 归一化模块**，让所有图片出口（渲染 / 发送 / 存储）都经过它。

## 一、问题根因

前端图片 URL 有 4 种形式，**不统一**会导致两类问题：

| 形式 | 示例 | 渲染端（前端） | 发送端（后端） |
|---|---|---|---|
| 绝对 http(s) | `http://127.0.0.1:18080/files/canvas/xxx.png` | ✅ 正常 | ✅ 网关可访问 |
| base64 | `data:image/png;base64,...` | ✅ 正常 | ✅ 网关可转 CDN |
| 相对路径 | `/files/canvas/xxx.png` | ❌ **画布环境解析成错误源 → 破图** | ❌ **网关解析成它自己的 /files/ → 丢图** |
| blob | `blob:...` | ✅ 本次会话可显示 | ❌ **浏览器临时地址，后端访问不到 → 丢图** |

**两类核心问题：**

1. **破图（渲染端）**：相对 `/files/...` 存进节点 data，渲染时 `<img src>` 在画布环境（`localhost:5180` / `chrome-extension://`）被解析成错误源（`localhost:5180/files/...`）→ 404 破图。
2. **丢图（发送端）**：把 `blob:`（浏览器临时地址）或相对 `/files/` 直接发给后端，网关/上游访问不到 → 参考图丢失，图生图/生视频垫图不齐。

## 二、统一方案：三层机制

| 层 | 统一入口 | 作用 | 保证 |
|---|---|---|---|
| **渲染端** | `normalizeImageUrl` / `toAbsoluteFileUrl` | 相对 `/files/` 补全成绝对 http | 前端不破图 |
| **发送端** | `normalizeImageUrlForSend` / `resolveRefImages` | blob→data、相对→绝对 | 后端不丢图 |
| **存储端** | `saveInlineToLocal` / `uploadFileToLocal` | base64/文件落盘成绝对 URL | 画布快照轻量、刷新可访问 |

## 三、统一模块 `src/components/base/imageUrl.js`

**所有图片 URL 归一化的唯一出口**，收敛了原本分散在各文件的 URL 处理逻辑：

| 函数 | 用途 |
|---|---|
| `toAbsoluteFileUrl(url)` | 相对 `/files/` 补全为绝对 http（渲染/存储共用） |
| `normalizeImageUrl(url)` | 渲染端归一化（等价 toAbsoluteFileUrl） |
| `blobToDataUrl(u)` | blob → data: base64 |
| `urlToDataUrl(u)` | 任意 URL（http//files/blob）→ data: base64（供只认 base64 的后端） |
| `normalizeImageUrlForSend(u, opts)` | 发送端单张归一化 |
| `normalizeImageUrlsForSend(images, opts)` | 发送端批量归一化 |

### 发送端归一化规则（`normalizeImageUrlForSend`）

**默认（走网关）**：
- `/files/` 相对 → 补全成绝对 http
- `blob:` → 转 data: base64
- `data:` / `http(s)` / 裸 base64 → 原样（网关 `resolve_attachments` 统一转 CDN）

**`preferBase64: true`（未来只认 base64 的后端）**：
- 任何形式统一转 data: base64

## 五、`refFormat: 'base64'` 能力预留（未来「只认 base64」的后端）

**背景**：有的生成服务只接受 base64，不接受 URL。虽然当前所有 provider 都走我们的网关（`apimart-gateway` 的 `resolve_attachments` 会把 URL/base64 统一转 CDN），不涉及此问题；但未来若**绕过网关直连只认 base64 的 API**，前端需要支持「URL → base64」。

**已预留的机制**（当前默认不触发，未来一行配置即生效）：

1. `normalizeImageUrlForSend(u, { preferBase64: true })` → 任何形式统一转 base64。
2. `imageApi` / `videoApi` / `chatApi` / `useAgentChat` 已读取 `provider.refFormat === 'base64'` 时传 `preferBase64: true`。
3. **未来**某个 provider 在配置里加 `refFormat: 'base64'`，参考图即自动统一转 base64 发送，无需改代码。

> 注：`urlToDataUrl` 对 `http(s)` 外网 URL 受 CORS 限制可能拉取失败；同源 localTool 绝对 URL 没问题。

## 六、统一工具收敛（消除「各写一份」）

- `filesApi.js` 的 `toAbsoluteFileUrl` → **re-export 自 `imageUrl.js`**（逻辑单一来源）。
- `refImage.js` 的 `resolveRefImages` / `resolveRefImageUrl` → **委托 `imageUrl.js`**（保持旧 API 兼容）。

## 七、规范（新增节点/面板必须遵循）

1. **渲染图片** → 一律用 `LazyImage`（内部已归一化）或 `normalizeImageUrl(url)`，不直接 `<img src={原始url}>`。
2. **发送图片给后端** → 一律走 `resolveRefImages(images, { preferBase64 })`（图生图/聊天/生视频），不绕过。
3. **存储图片到节点 data** → 用 `saveInlineToLocal` / `uploadFileToLocal` 落盘成**绝对 URL**，不存大 base64 / blob。
4. **新增 URL 处理** → 一律用 `imageUrl.js`，不各写各的。
