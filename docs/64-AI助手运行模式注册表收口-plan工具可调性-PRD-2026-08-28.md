## 0. 一句话结论

把 AI 助手运行机制整理为**三根正交轴**（三态轴 / Skill 编排轴 / 积分安全轴），每根轴各管各的、**互不进对方的分支判断**。其中「三态轴」是用户关心的主线，用**一个注册表 + 一个 `workMode` 单一枚举值**收口，做到**每个分支单一数据流**；同时**修复根因**——无 Skill 常规任务下系统提示词没引导 `show_plan_for_confirm`，导致完全自主模式 plan 工具调不了。

---

## 1. 根因诊断（代码核对，勿跳过）

### 1.1 用户反馈
「完全自主」模式下 AI 调不了 plan 工具（`show_plan_for_confirm`）；且三态关系混乱、难一眼看出问题。

### 1.2 三个事实（均已代码核对）
1. **plan 工具是注册的**：`presentPlanTool` 在 `AGENT_TOOLS` 无条件注册，schema 全量发给 LLM。→ 不是「没注册」。
2. **真正根因**：无条件注入的 `CANVAS_AGENT_RULES`（agentCore.js）**完全没有**引导 `show_plan_for_confirm`；只有启用 Skill 时 `SKILL_EXECUTION_RULES` 才讲「三阶段」。→ 无 Skill 常规任务，LLM 看到 plan 工具但无使用指引。
3. **三态散落硬编码**：`AgentPanel.jsx` / `conversationAiState.js` / `conversationState.js` / `presentPlanTool` 各自硬编码 `workMode`/`runMode` 判断，零对齐。

### 1.3 为什么「乱」——两个结构性病根
- **病根一**：一条发送链路被 `inputMode` 劈成 `send` 与 `sendImageMode` 两个入口函数，再被 `runMode` 在工具层/提示词层二次分化 → 三态底层是「2 入口 × 2 runMode」组合，判定散落 5+ 文件。
- **病根二**：`workMode`（展示层三态）是**推导结果**（`inputMode==='image' ? 'image' : (runMode... )`），不是**存储状态** → 谁要看当前模式都得自己再算一遍，算岔就乱。

## 2. 三正交轴模型（核心心智）

> 关键认知：**Skill 和积分确认本来就是和三态正交的独立轴，不是「三态的附加项」。**
> - **Skill = 只编排 AI 的思维路径**（把一次任务拆成多步 generations），与「确认粒度」完全无关。完全自主、分步确认**都能用** Skill。
> - **积分确认 = 只管真烧积分那下**，与「确认粒度」也完全无关。
> 乱的根因**不是多了这两根轴**，而是：①三态本身没收口成单一枚举值（病根二）；②`SKILL_EXECUTION_RULES` 里那句「三阶段等确认」措辞，让人误以为 Skill 会改确认粒度——其实确认粒度始终由三态决定，Skill 只是提示词里附加了一条「阶段2 等你确认」的编排指令，需要按三态自适应。

| 轴 | 决定什么 | 取值 | 独立于谁 |
|---|---|---|---|
| **三态轴**（确认粒度）| 什么时候问你、要不要先看策划 | `direct` / `step-confirm` / `auto` | 独立于 Skill、积分 |
| **Skill 编排轴** | 一次生成多少步、怎么编排 | 无 Skill / 有 Skill | 只编排思维路径，**不管确认** |
| **积分安全轴** | 真烧积分那下拦不拦 | `creditSwitch` 开/关 | 只拦扣积分，**不管确认粒度** |

### 2.1 轴间关系（必须正交，谁也不进谁分支）
- 三态轴 决定「确认粒度」，**不掺和**生成步骤数、不掺和烧积分。
- Skill 轴 决定「几步骤编排」，**不掺和**确认粒度、不掺和烧积分。确认粒度**始终由三态轴决定**（Skill 只是把任务拆成多步，不改变「要不要确认」）。
- 积分轴 决定「真生成那下拦不拦」，三态、Skill 一视同仁（现状已正交，保持）。

### 2.2 组合矩阵（四象限验证 Skill 与三态正交）
| | 无 Skill | 有 Skill |
|---|---|---|
| **分步确认** | 单步，plan 卡确认 | 多步编排，plan 卡确认 |
| **完全自主** | 单步，plan 不卡确认 | 多步编排，plan 不卡确认，真生成受积分闸兜底 |

> 关键：**Skill 是否启用，只改变「生成的步骤/编排复杂度」，不改变「确认粒度」**。确认粒度永远只看三态（step-confirm 卡、auto 不卡）。`SKILL_EXECUTION_RULES` 里「阶段2 等确认」要改成按三态自适应（见 §6.2），避免让 LLM 在完全自主 + Skill 时误等确认。

## 3. 单一数据流设计（最终方案核心）

### 3.1 核心原则：一个维度 = 一个枚举值，一个值驱动所有消费方

```
workMode ∈ { direct, step-confirm, auto }    // 单一存储值（不是推导）
```

所有消费方只读 `getWorkMode()`，禁止再各自算：
- `AgentPanel` 三态选择器 → 读/写 `workMode`
- `send` 分流 → 读 `workMode`
- `presentPlanTool` 门禁 → 读 `workMode`
- `buildRequestMessages` 提示词注入 → 读 `workMode`
- `normalizeConversation` 持久化 → 读写 `workMode`

**消除**：`inputMode × runMode` 推导、各处硬编码 `'image'`/`'step-confirm'`/`'auto'`、`runMode` 在工具层的重复判断。

### 3.2 发送入口收敛为单入口（内部第一行分流）

```
send(text, attachments):
  workMode = getWorkMode()
  if workMode === 'direct'  → 内部走「直连分支」（复用现 sendImageMode 实现，不再对外暴露独立入口）
  else                      → 走「LLM 编排分支」（工具循环 + plan/execute）
```

- 外部（AgentPanel）**永远只调 `send`**，不再自己判断调 `send` 还是 `sendImageMode`。
- `sendImageMode` 从「对外入口」**降级为 `send` 内部的一个分支**（或保留导出但 AgentPanel 不再直接调）。
- **分支只在 `send` 这一个点发生**，之后每条分支内部不再被其他正交开关劈开。

### 3.3 三条分支的单一数据流

```
workMode = getWorkMode()   // 唯一数据源

【direct 直接生图】
  send → workMode==='direct' → 直连分支 → execute_plan(auto_run)
       → 积分轴 creditSwitch（若开则挂 credit 确认，等用户点生成）
  不注入 runMode 提示词，不经 LLM，不卡 plan。

【step-confirm 分步确认】
  send → workMode==='step-confirm' → LLM 分支
       → 提示词「调 show_plan_for_confirm，等确认」
       → presentPlanTool: needConfirm=true → 卡 awaiting
       → 用户确认 → execute_plan
       → 真烧积分那下：积分轴 creditSwitch 兜底（与三态正交）

【auto 完全自主】
  send → workMode==='auto' → LLM 分支
       → 提示词「可调 show_plan_for_confirm 展示规划，不卡确认，直接 execute_plan」
       → presentPlanTool: needConfirm=false → 直接 execute_plan
       → 真烧积分那下：积分轴 creditSwitch 兜底（防积分被偷烧）
```

> 关键：direct 在 send 内部就和另外两者分开；step-confirm 与 auto 共享 LLM 分支，但由 `workMode` **一个值**决定「要不要卡确认 + 提示词怎么引导」。**没有一条分支内部再套别的正交开关。**

## 4. 注册表契约（runModeRegistry）

新增 `runtime/runModeRegistry.js`（纯常量 + 纯函数，无副作用，可单测）。

### 4.1 常量（单一事实来源）

```js
RUN_MODE_IDS = { DIRECT:'direct', STEP_CONFIRM:'step-confirm', AUTO:'auto' }
DEFAULT_WORK_MODE = 'auto'

WORK_MODE_DEFS = {
  direct:        { id, label:'直接生图',   systemPrompt: null },          // 不经 LLM，不注入提示词
  'step-confirm':{ id, label:'分步确认',   systemPrompt: stepPrompt },    // 等确认
  auto:          { id, label:'完全自主',   systemPrompt: autoPrompt },    // 可调 plan、不卡确认
}
```

### 4.2 纯函数

```js
getWorkMode()                    // 读当前 workMode（注册表 + 存储，见 §5）
setWorkMode(workMode)            // 写 workMode（同时原子同步 inputMode/runMode 兼容字段，见 §5.3）
resolveWorkMode(raw)             // 任意入参归一 → 合法 workMode（非法/旧值 → 默认）
normalizeWorkMode(workMode)      // 归一化（收敛旧值 'semi' → 'step-confirm'）
getSystemPromptForWorkMode(wm)   // workMode → 注入 LLM 的 runMode 分流指令片段（direct 返回 ''）
resolveInputMode(wm)             // workMode → 兼容字段 inputMode（image/agent）
resolveConvRunMode(wm)           // workMode → 兼容字段 runMode（step-confirm/auto；direct→auto）
isAgentWorkMode(wm)              // wm 是否走 LLM 编排（direct 为 false）
```

## 5. 存储与设置项

### 5.1 存储键（进 contracts.js 登记，禁裸字面量）

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `agent_work_mode`（**新增**）| 全局（localStorage）| `auto` | **workMode 单一存储值**，三态的单一真源 |
| `agent_input_mode` | 全局（localStorage）| `agent` | 兼容字段，由 `setWorkMode` 同步（image/agent）|
| `conv.runMode` | per-conversation | `auto` | 兼容字段，由 `setWorkMode` 同步（step-confirm/auto）|

### 5.2 为什么新增 `agent_work_mode`（方案B 定稿）
- 让「当前是哪个模式」变成**显式设置值**，而不是推导结果 → 根治病根二。
- 三态选择器 / 设置页可配、一眼可读、跨会话稳定（全局而非 per-conversation，三态是用户偏好不是对话属性）。
- `inputMode`/`runMode` 保留为**兼容字段**，仅由 `setWorkMode` 原子写入，历史代码/数据不破坏，逐步迁移。

### 5.3 写入一致性（防第三份状态不同步）
`setWorkMode(wm)` **原子写三处**（workMode + inputMode + runMode），读时**以 workMode 为唯一真源**：
- 读：一律 `getWorkMode()`（读 `agent_work_mode`）
- 写：`setWorkMode` 一次性写 workMode + 同步 inputMode/runMode
- 兜底：`normalizeWorkMode` 收敛任意非法/旧值（含 `semi`）

## 6. 提示词注入（修复 plan 可调性 + 按三态分流）

### 6.1 在 `buildRequestMessages` 注入 runMode 分流段
`buildRequestMessages` 增加第 9 参 `workMode`（或由注册表内部 `getWorkMode()` 读取，推荐后者避免改签名），在组装 system 时插入 `getSystemPromptForWorkMode(workMode)`。

- **step-confirm**：注入「调 show_plan_for_confirm 展示策划，等待用户确认后再 execute_plan」。
- **auto**：注入「可用 show_plan_for_confirm 展示规划（**不卡确认**），然后直接 execute_plan 执行」。
- **direct**：不注入（不经 LLM）。

### 6.2 与 Skill 的叠加规则（关键，防 R1）
- Skill 本来就是独立轴，**只编排思维路径、不改变确认粒度**。`SKILL_EXECUTION_RULES` 的「三阶段」里那句「阶段2 等你确认」**要按三态自适应**：确认粒度永远由三态决定。
  - 三态 = step-confirm → Skill 阶段2 等确认。
  - 三态 = auto → Skill 阶段2 **不**等确认，展示策划后直接进入阶段3 execute_plan。
- 措辞必须同时说清「**可调 plan**」与「**不卡确认**」两件事（防 R2 回归 plan 调不了）。

## 8. 翻车点（施工前必读，写进 65）

### R1 · `SKILL_EXECUTION_RULES` 里「阶段2 等确认」与三态 auto 冲突（高风险）
Skill 只编排思维路径、不决定确认粒度，但 `SKILL_EXECUTION_RULES` 现文写了「阶段2 等确认」——三态 auto 时若不改这句，LLM 会误等确认而卡住。
**对策**：`SKILL_EXECUTION_RULES` 的「阶段2 是否等确认」改为按三态自适应（§6.2）；四组合 case（Skill×auto / Skill×step-confirm / 非Skill×auto / 非Skill×step-confirm）逐条固化测试。

### R2 · 把「不卡确认」误写成「不需要 plan」（高风险，本次要修的）
三态 auto 若写成「不需要 show_plan_for_confirm」→ LLM 跳过 plan → 症状复现。
**对策**：措辞必须同时写「可调 plan 展示规划 + 不卡确认直接 execute」，不能只说一半。

### R3 · workMode 三份状态不同步（中风险）
新增 workMode 存储值后，若与 inputMode/runMode 不同步 → 回到病根二。
**对策**：`setWorkMode` 原子写三处、读以 workMode 唯一真源（§5.3），`AgentPanel.test.jsx` 固化「切换后三字段一致」。

### R4 · `semi` 历史值口径不一（中风险）
docs/61 表格写 `semi`，代码已归一 `step-confirm`。照旧文档写会回归。
**对策**：注册表只认 `step-confirm`，`normalizeWorkMode` 收敛 `semi`→`step-confirm`，施工注明勿回流 `semi`。

### R5 · 测试散写裸字面量（中风险）
现测试断言了 `runMode`/`workMode` 裸取值。注册表收口后若不同步改 import 常量 → 回归。
**对策**：测试一律 import `RUN_MODE_IDS`/`DEFAULT_WORK_MODE`，禁裸字面量。

### R6 · 完全自主 + Skill 时，批量任务可能「一步到位烧积分」（中风险）
三态 auto 下确认粒度就是「不卡确认」，与有没有 Skill 无关。Skill+auto 时 LLM 会直接 execute_plan 批量生成。若用户期望「有 Skill 就一定分步」，会意外。
**对策**：确认粒度已由三态统一（Skill 不改变它）；积分轴 creditSwitch 兜底（真生成那下拦）。用户若想要「Skill 始终分步」，应切到三态的 step-confirm，而不是给 Skill 单独加开关（保持正交，不新增 Skill 专属确认项）。

### R7 · `buildRequestMessages` 签名变更波及测试（低风险）
若给 `buildRequestMessages` 加 workMode 参数，现有单测/调用点需同步。
**对策**：优先让注册表内部 `getWorkMode()` 自读，不改签名；必须改时在 65 列出所有调用点。

### R8 · `sendImageMode` 降级为内部分支，影响外部调用方（低风险）
`executePlanDirect`（prompts 通道）/AgentPanel 若仍调 `sendImageMode`，需改为走 `send`。
**对策**：保留 `sendImageMode` 导出但 AgentPanel 不再直接调；`executePlanDirect` 是 prompts 通道，需确认其走 workMode 分流还是独立保留（见 §9）。

## 11. 决策记录（本次定稿）

1. 三正交轴：三态轴 / Skill 编排轴 / 积分安全轴，互不进分支判断（§2）。
2. 三态 = 单一枚举值 `workMode`，新增 `agent_work_mode` 存储（方案B），根治病根二（§3/§5）。

5. 完全自主下 plan 可调 = 可调 + 展示 + 不卡确认（§6/R2）。

7. `semi` 不再回流，统一 `step-confirm`（R4）。
