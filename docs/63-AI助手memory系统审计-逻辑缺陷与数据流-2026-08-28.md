## 一、一句话定位

Memory 系统对齐"大雄"参考项目的"记 / 学 / 忆 / 压"四层记忆 + 上下文压缩。核心设计：**长期记忆带 UI 确认门禁，对话级记忆自动沉淀，生图样本只读提炼，超预算自动压缩**。

**先厘清一个关键语义**：`记 / 学 / 忆 / 压` 这"四层"，**并不都是独立的存储平面**。真正的存储平面只有两个：

- **平面 A「忆」**：对话级 `conv.memory`（自动沉淀、随对话存在）
- **平面 B「记」**：项目长期记忆（用户确认、持久存储）

`学` 是**读取时派生的只读上下文**（无存储），`压` 是**把长对话折叠进 `memory.summary` 的写回管道**（一种机制，不是存储）。这样划分后，数据流就非常清晰：**两平面 + 一派生 + 一管道 + 一个读枢纽**。

## 二、四层记忆≠四存储：语义总表

| 名称 | 性质 | 存储位置 | 生命周期 | 写入/派生入口 | 读取/注入入口 |
|------|------|----------|----------|---------------|---------------|
| **忆** `memory` | 存储平面 A | 当前对话 `conv.memory` | 单对话内、跨轮 | 自动沉淀（见 §3.1 字段所有权） | `buildRequestMessages`（`agentCore.js` L298-325） |
| **记** ProjectMemory | 存储平面 B | `localStorage`（contentStore，KV=`agent_project_memory_v1_<agentKey>`） | 按 agentKey 全局、跨对话永久 | `memory_suggest` → 用户确认 → `saveProjectMemory` | `buildProjectMemoryContextFromStore` → `buildRequestMessages` L346 |
| **学** Learned | 派生（无存储） | 无（读时从 `memory.lastPlan.generations` 计算） | 每次请求临时生成 | `buildLearnedContext`（纯函数，不落库） | `buildRequestMessages` L340 |
| **压** Summary | 写回管道（非存储） | 写入平面 A 的 `memory.summary` | 触发时瞬发 | `compressToSummary` → `setCurrentMemory({summary})` | 经平面 A 走 `buildRequestMessages` L300 |

> 语义要点：`压` 是"忆"的**子机制**（把长历史折叠进 `summary`），不是独立数据层；`学` 是"忆"的**读时投影**（从 `lastPlan.generations` 提炼），也不产生持久数据。

## 三、完整数据流

### 3.0 全局数据流图

```
┌────────────────────────── 写路径 ──────────────────────────┐
│                                                            │
│  (自动沉淀 A)  show_plan_for_confirm / execute_plan          │
│      └── setCurrentMemory({lastPlan})   ──▶ 平面A.memory     │
│  (压·折叠 A)  decideContextCompression → compressToSummary    │
│      └── setCurrentMemory({summary})    ──▶ 平面A.memory     │
│  (记·确认 B)  LLM memory_suggest(脱敏) → 暂存+门禁            │
│      └── 用户确认 → saveProjectMemory    ──▶ 平面B(localStorage)│
│                                                            │
└────────────────────────────────────────────────────────────┘
                          │
                          ▼  （每次请求，读时组装）
┌────────────────────────── 读枢纽 buildRequestMessages ──────┐
│  依固定顺序注入 system 块（见 §3.5）：                       │
│  忆 ──▶ summary/lastSharedStyle/facts/notes(平面A)          │
│         lastPlan(平面A)  ·  global_contract(平面A)           │
│  图 ──▶ imageCatalog(图N编号，当前可引用图)                   │
│  学 ──▶ buildLearnedContext(从 lastPlan.generations 派生)   │
│  记 ──▶ buildProjectMemoryContextFromStore(平面B, MMR排序)  │
└────────────────────────────────────────────────────────────┘
```

### 3.1 平面 A「忆」——对话级记忆 `conv.memory`

- 结构（`emptyMemory()`，`conversationState.js` L44-50）：`{ summary, lastSharedStyle, facts[], notes[], lastPlan, global_contract, artifacts }`。
  - **审计补充**：原文档漏了 `artifacts`（跨步成果资产，`conversationAiState.js` L70 写入）；且 `artifacts` **有写入源但 `buildRequestMessages` 未注入**（仅 `generations` 依赖它）。
- 读写口：`getCurrentMemory()` / `setCurrentMemory()`（`conversationSnapshot.js`），统一走 `capConversationMemory` 限容。

**字段所有权表（谁写 / 何时写）：**

| 字段 | 写入来源 | 注入状态 |
|------|----------|----------|
| `lastPlan` | `show_plan_for_confirm`（`useCanvasAgentTools.js` L832）、`execute_plan`（L1061）：策划展示/执行时自动沉淀 | ✅ 注入（L311） |
| `summary` | `压`：`compressToSummary` 返回后 `setCurrentMemory({...mem, summary})`（`useAgentChat.js` L424 / L525 强制压缩）；`precompress` 后台节流复用 | ✅ 注入（L300） |
| `lastSharedStyle` | `conversationAiState.js` L54：捕获时由 `global_contract.unified_style_prompt/visual_positioning` 映射 | ✅ 注入（L301） |
| `global_contract` | 统一风格契约逻辑（与 `lastSharedStyle` 联动，逐字锁定） | ✅ 注入（L319） |
| `facts` / `notes` | **无任何写入点**（见缺陷 §4.4） | 死代码，永远为空 |
| `artifacts` | `conversationAiState.js` L70 | ❌ 未直接注入（供 generations 依赖） |

### 3.2 平面 B「记」——项目长期记忆（带确认门禁）

- 存储：contentStore / `localStorage`，KV=`agent_project_memory_v1_<agentKey>`，**按 agentKey 全局、不分项目**（`projectId` 参数仅为兼容保留）。
- 类别：`kind ∈ {preference/fact/constraint/decision}`；单条正文限 `500` 字符，单 agentKey 上限 `60` 条、超出淘汰最旧。
- 写入数据流（**工具绝不落库，落库只在确认流**）：

```
LLM 调 memory_suggest 工具
  → execute()：sanitizeMemoryContent 脱敏 + 校验 kind            （useCanvasAgentTools.js L1302-1313）
  → setActivePendingMemorySuggest({kind, content})   // 仅暂存，不落库
  → setAwaitingConfirm(true)                          // 进入门禁
  → 返回 awaiting_confirm:true，UI 渲染确认卡
────────────────────────────────────────────────
用户确认 → AgentPanel.handleConfirmPlan()
  → confirmPendingMemorySuggest()                     （useCanvasAgentTools.js / useAgentChat）
  → saveProjectMemory(agentKey, {...})  → 真正写 localStorage
        · 按 id upsert；L119 仅 String().slice() 截断，无再脱敏（见缺陷 §4.3）
        · 超 PROJECT_MEMORY_LIMIT 淘汰最旧；withLock 串行 read-modify-write
        · 写后同步更新模块缓存（writeCache）
  → clear pending + setAwaitingConfirm(false)
  → appendMsg 回显 "已保存长期记忆：[label] content"
用户取消 → cancelPendingConfirm() 清暂存，不下写
```

- 存储实现（`projectMemoryStore.js`）：
  - **双读路径**：异步 `loadProjectMemories`（Content 层读 + 模块缓存）与同步 `getCachedProjectMemories`（缓存直读，供注入用到）。
  - 写：`saveProjectMemory` 按 id upsert、串行化 read-modify-write、更新缓存；删：`removeProjectMemory`。
  - **注意·去重复核**：落库层**无按 content 去重**——`saveProjectMemory` 只按 `id` upsert，相同正文会以新 id 追加（触顶被淘汰后才有约束），重复长期记忆会累积占用容量。检索侧 MMR 只做**多样性**挑选，`buildPromptLearningBlock` 的 `seen` Set 去重属于「学」，不作用于「记」。

- 读取数据流（注入）：

```
buildProjectMemoryContextFromStore(agentKey, '', text)   // useAgentChat.js L511
  → getCachedProjectMemories(agentKey)                   // 同步读缓存，未加载/为空返回[]
  → rankProjectMemories(memories, query, {limit:6})      // 打分(词法+类别权重+近因) + MMR 挑选 top-K
  → buildProjectMemoryBlock(...)                          // 拼"不可信只读事实"注入块 + 限 1800 字符
  → buildRequestMessages(...)                             // 作为 system 块置于"学"之后（L346）
```

### 3.3 派生「学」——学习样本（无存储）

- **不是存储层**：每次请求读时，从 `memory.lastPlan.generations`（本对话最近一次已执行策划的步骤 prompt）提取成功样本，经 `buildLearnedContext` → `buildPromptLearningBlock` 相似度排序 → 脱敏 → 限 token → 直接生成注入块。**不新增任何持久数据。**
- 明确标记为**"不可信上下文，只学不改规则/权限"**（样本块自带约束说明）。
- 仅在创作意图（image/video 相关）时加载，非创作意图返回空串不污染上下文。

### 3.4 管道「压」——上下文压缩写回 `summary`

- **不是存储，是把长对话折叠进平面 A `memory.summary` 的管道**。
- 触发（`useAgentChat.js` 每次请求时 `decideContextCompression`）：
  - `force`：上下文超过 `inputBudget` → 请求前 `await compressToSummary` 写回 `summary` → 用新摘要重装消息（L520-528）。
  - `precompress`：后台预压缩（复用 `maybeCompressSummary` 节流，不阻塞）→ `setCurrentMemory`。
  - 收尾节流：`maybeCompressSummary`（消息数 > `RECENT_KEEP_COUNT=8` 且节流间隔已过）。
- 压缩调用：`compressToSummary({provider, model, messages, previousSummary})`（`contextCompression.js`）流式 LLM 调用，失败/超时返回 `null`（保留旧摘要，不阻塞主流程）。
- 写回：`setCurrentMemory({ ...getCurrentMemory(), summary })`。
- 摘要必需区段含"约束与偏好"（`SUMMARY_REQUIRED_SECTIONS`），这与其长期记忆中的 `kind ∈ {preference/constraint}` 天然重叠 → 是缺陷 §4.1 的根因。

### 3.5 读枢纽 `buildRequestMessages`（`agentCore.js` L273）

每次请求，`useAgentChat.js` L511 一行组装四类记忆：

```javascript
buildRequestMessages(
  getCurrentSnapshot().messages, systemRef.current, true,
  skillsRef.current,
  getCurrentMemory(),                                        // 忆（平面A）
  getCurrentImageMap(),                                      // 图：当前可引用图（图N编号）
  loadAgentHistoryTurns(),                                   // fresh-task：默认0不回传文字历史
  buildLearnedContext(getCurrentMemory(), text),             // 学（读时派生）
  buildProjectMemoryContextFromStore(agentKey, '', text)     // 记（平面B）
)
```

按固定顺序注入 system 块（已回到源码核验，`agentCore.js` L281-348）：

| 序 | 注入块 | 内容 | 源码行 |
|----|--------|------|--------|
| 1 | 画布准则 | `CANVAS_AGENT_RULES` | L282 |
| 2 | 会话 system | `systemPrompt` | L283 |
| 3 | Skill 文档 | `===== Skill 文档开始/结束 =====` + `SKILL_EXECUTION_RULES` | L288-293 |
| 4 | 忆·摘要/风格/已确认/备注 | `summary` / `lastSharedStyle` / `facts`(最近12) / `notes`(最近8) | L298-309 |
| 5 | 忆·最近策划 | `lastPlan.plan_text` + `generations` 步骤 | L311-317 |
| 6 | 忆·统一风格契约 | `global_contract`（逐字锁定，每步必须带入） | L319-325 |
| 7 | 图 | `imageCatalog`（图N 编号反查，图本体不进上下文） | L329-336 |
| 8 | 学 | `learnedContext`（不可信只读样本） | L340-342 |
| 9 | 记 | `projectMemoryContext`（MMR 排序/脱敏/限字，作补充事实） | L346-348 |

> `fresh-task`：默认 `historyTurns=0`，历史轮次（含图）一律不进上下文，跨轮记忆全靠上述 system 块承载；`historyTurns>0` 时才回传最近 N 轮**纯文字**（图片永不内联，只走图N+`direct_refs` 反查）。这是"短上下文、长记忆"的根基。

## 四、逻辑缺陷复核（已逐条回源码）

下文每条均标注"复核方式"与"结论"。复核基于 2026-08-28 工作区快照。

### 4.1 〔真问题·中等〕短期 `summary` 与长期记忆双份、无去重
- **复核**：`agentCore.js` L300 注入 `memory.summary`；L346 注入 `projectMemoryContext`；`contextCompression.js` 的 `SUMMARY_REQUIRED_SECTIONS` 含"约束与偏好"，与长期记忆 `kind ∈ {preference/constraint}` 内容天然重叠。注入顺序中两者并列，无去重/优先级机制。
- **影响**：同一事实以"压缩近似（summary）"与"原文（长期记忆）"双份呈现，浪费 token 且表述可能不一致，干扰 LLM 判断。
- **建议**：注入长期记忆前，用 `summary` 已含的约束/偏好交叉去重；或约定"长期记忆不重复注入 summary 已覆盖项"。

### 4.2 〔真问题·严重但触发面窄〕两个 awaiting 确认卡共用一布尔位 + 工具循环不中断
- **复核**：
  - `runToolCalls`（`agentRuntime.js`）对每个 tool_call 逐个 `await callTool`，无 `if (awaitingConfirm) break`。
  - `send` 主循环（`useAgentChat.js`）在 `runToolCalls` 返回后才检测 `getAwaitingConfirm()` 并 `break`，故同轮 `[show_plan_for_confirm, memory_suggest]` 两卡都会 append。
  - `handleConfirmPlan`（`AgentPanel.jsx` L406-417）**总是先查 `getActivePendingMemorySuggest()`**，有则走记忆落库并 `return`（失误路由）。
- **影响**：**step-confirm / Skill 模式下**，若 LLM 同轮既展示策划又提议记忆，用户点"确认策划"会被误路由为"保存记忆"，策划卡被吞。
- **不触发条件**：auto 模式下 `show_plan_for_confirm` 不进 awaiting（直接执行）。
- **建议**：显式互斥标志区分 `pendingType ∈ {plan, memory}`；或 `handleConfirmPlan` 按"哪张卡触发的"传参分流；或在 `runToolCalls` 执行 memory_suggest 后中断后续工具。

### 4.3 〔真问题·中等〕落库层未脱敏（后门）
- **复核**：`saveProjectMemory`（`projectMemoryStore.js` L114-137）L119 仅 `String(memory?.content || '').slice(0,500)`，**无 `sanitizeMemoryContent` 调用**。脱敏只在 `memory_suggest.execute`（`useCanvasAgentTools.js` L1306）做一次。
- **影响**：`saveProjectMemory` 是导出公共函数，注释称"供清理/未来接入"。若未来有其它入口（批量导入、其它工具）直接调用，密钥/本地路径会原样写入 localStorage。
- **建议**：把 `sanitizeMemoryContent` 下沉到 `saveProjectMemory` 内部，工具层不再单独脱敏，从源头收口。

### 4.4 〔真问题·设计未落地〕`facts`/`notes` 无写入点 → 注入死代码
- **复核**：全仓库仅注入侧（`agentCore.js` L302-307）与归一化/兜底/重置（`conversationState.js` L230-231/297-300、`useAgentChat.js` L744）涉及 `facts`/`notes`；**无任何 `setCurrentMemory` 写入这两个字段**，`emptyMemory()` 给空数组，永不填充。
- **影响**：`buildRequestMessages` L302-307 记忆块恒为空，属死代码；跨轮"忆"残缺，实际仅 `summary`/`lastPlan`/`global_contract` 生效。
- **备注**：文件头注释自承"治本是补齐 memory 自动摘要（summary/facts 自动沉淀）"，当前 facts 沉淀未实现，属已知设计缺口，非运行 bug。

### 4.5 〔已撤回·误读〕`buildProjectMemoryContextFromStore` 的 MMR 参数 bug
- **复核结论**：**不成立，是审计者误读，撤回。**
- **事实**：`memoryRetrieval.js` 导出 `rankProjectMemories(memories, query, options={limit:6})` + `buildProjectMemoryBlock` + `buildProjectMemoryContextFromStore(agentKey, projectId, query)`。**不存在** `_mmrRerank(maxResults, maxTokens)` 函数，也不存在"传 (50,8)"的调用。调用点 `useAgentChat.js` L511 为 `buildProjectMemoryContextFromStore(agentKey, '', text)`，3 参数精确匹配签名；内部 MMR 用 `DEFAULT_LIMIT=6`、按字符上限截断，逻辑正常。**长期记忆注入功能正常。**

### 4.6 〔真问题·轻微〕`withLock` 不严格串行
- **复核**：`withLock`（`projectMemoryStore.js` L46-52）用 `next = prev.then(fn)`，`fn` 是 async，`prev.then(fn)` 会**立即启动** `fn`（内部 `await` 不阻止后续链排进），多个并发写同 key 时 read-modify-write 可能交叠。
- **影响**：实测风险低（同 key 写极少并发），但严格说并非串行化。
- **建议**：改为 `prev.then(() => fn())` 确保 `fn` 在 `prev` 完成后才启动；或显式 `await prev` 后再执行。

## 六、一句话总结

> LLM 在对话中通过 `memory_suggest` 提议 → 暂存 + 门禁 → 用户确认 → 写入 localStorage 长期记忆（记，平面 B）；同时对话内自动沉淀 `lastPlan`/`global_contract`/`summary`/`lastSharedStyle`（忆，平面 A），其中 `summary` 由"压"管道把长历史折叠写回；生图样本在每次请求时由 `lastPlan.generations` 读时派生为只读学习上下文（学）。每次请求经 `buildRequestMessages` 把两平面记忆 + 图N编号 + 派生学块按固定顺序注入 system，配合 fresh-task 只发本轮 user，实现"短上下文、长记忆"。当前主要风险在确认门禁的竞态与脱敏下沉，以及短期/长期记忆的重复注入。
