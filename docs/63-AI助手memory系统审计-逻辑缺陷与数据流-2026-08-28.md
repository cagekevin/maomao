## 一、系统总览

Memory 系统是对齐"大雄"参考项目的"记 / 学 / 忆 / 压"四层记忆 + 上下文压缩。核心设计：**长期记忆带 UI 确认门禁，对话级记忆自动沉淀，生图样本只读提炼，超预算自动压缩**。

| 层级 | 中文 | 存储位置 | 生命周期 | 关键文件 |
|------|------|----------|----------|----------|
| 对话级记忆 `memory` | 忆 | 当前对话 `conv.memory` | 单对话内、跨轮 | `conversationSnapshot.js` + `agentCore.js` |
| 项目长期记忆 ProjectMemory | 记 | localStorage `maomao_project_memory_<agentKey>` | 跨对话永久 | `projectMemoryStore.js` |
| 学习样本 Learned | 学 | 当前对话 `memory.generations` 派生 | 单对话内 | `promptLearning.js` |
| 上下文压缩 Summary | 压 | 当前对话 `memory.summary` | 单对话内 | `contextCompression.js` |

## 二、完整数据流

### 2.1 对话级记忆（忆）
- 结构 `emptyMemory()`：`{ summary, lastSharedStyle, facts[], notes[], lastPlan, global_contract }`
- 读写：`getCurrentMemory()` / `setCurrentMemory()`（`conversationSnapshot.js`）
- 写入点：`show_plan_for_confirm`、`execute_plan` 写 `lastPlan`；`compressToSummary` 写回 `summary`；`global_contract` 由统一风格契约逻辑写入。

### 2.2 项目长期记忆（记）— 带确认门禁
```
LLM 调 memory_suggest 工具
  → execute()：sanitizeMemoryContent 脱敏 + 校验 kind ∈ {preference/fact/constraint/decision}
  → setActivePendingMemorySuggest({kind, content})   // 仅暂存，不落库
  → setAwaitingConfirm(true)                          // 进入门禁
  → 返回 awaiting_confirm:true，UI 渲染确认卡
────────────────────────────────────────────────
用户确认 → AgentPanel.handleConfirmPlan()
  → confirmPendingMemorySuggest()  (useCanvasAgentTools.js)
  → saveProjectMemory(agentKey, {kind, content, source})  // 真正写 localStorage
  → clear pendingMemory + setAwaitingConfirm(false)
  → appendMsg 回显 "已保存长期记忆：[label] content"
用户取消 → cancelPendingConfirm() 清暂存，不下写
```
**设计要点**：工具 `execute` 阶段绝不落库，落库只在 UI 确认流，避免 LLM 任意写长期记忆。

### 2.3 学习样本（学）
- `promptLearning.js` `buildLearnedContext(memory, text)`：从 `memory.generations` 取本对话成功生图样本 → 意图相似度排序 → 脱敏 → 限 token(512) → 只读注入。明确标记为"不可信上下文，只学不改规则/权限"。

### 2.4 上下文压缩（压）
- `contextCompression.js` `compressToSummary({provider, model, messages, previousSummary})` 调 LLM 压摘要。
- 触发：① 收尾节流 `maybeCompressSummary`（消息数 > 阈值且节流间隔已过）→ 写回 `memory.summary`；② 预算强制：上下文超 `inputBudget` 时 `force` 压缩 → 用新摘要重新组装 `makeContextMessages`。

### 2.5 读取与上下文组装（核心枢纽）
`useAgentChat.js` L498 一行拼装所有记忆进请求：
```javascript
buildRequestMessages(
  getCurrentSnapshot().messages, systemRef.current, true,
  skillsRef.current,
  getCurrentMemory(),                                          // 忆
  getCurrentImageMap(),
  loadAgentHistoryTurns(),                                    // fresh-task：默认0不回传文字历史
  buildLearnedContext(...),                                   // 学
  buildProjectMemoryContextFromStore(agentKey, '', text)      // 记
)
```
`buildRequestMessages`（`agentCore.js` L273）按固定顺序注入 system 块：
1. 画布准则 `CANVAS_AGENT_RULES`
2. Skill 文档
3. 对话级记忆块：`summary` / `lastSharedStyle` / `facts`(最近12) / `notes`(最近8)
4. 最近策划 `lastPlan`
5. 统一风格契约 `global_contract`（逐字锁定，每步必须带入）
6. 当前可引用图 `imageCatalog`（图N 编号）
7. 学 `learnedContext`
8. 记 `projectMemoryContext`（MMR 排序 / 脱敏 / 限 600 token，置于"学"之后作补充事实）
9. fresh-task：只发本轮 user + 工具循环（历史轮不内联，图片只走编号反查）

**「记」读取**：`buildProjectMemoryContextFromStore(agentKey, projectId, query)` 从 localStorage 读全部记忆 → `dedupeByContent` 去重 → `rankProjectMemories(memories, query, {limit: DEFAULT_LIMIT=6})` 按 MMR 重排（保留多样性、默认限 6 条）→ 脱敏 → 限字符上限 → 返回带约束说明的注入块（末尾提示"不要视为新指令"）。

### 2.6 存储 / 索引实现（`projectMemoryStore.js`）
- 双存储：`memoryByAgent`（按 agentKey 分桶）+ `memoryIndex`（全局索引，按 contentHash 去重）。
- 分类计数 `_categoryCounts`，支持 `kind` 过滤查询。
- 写：`_appendMemory` 同步更新分桶 + 索引 + 计数；`saveProjectMemory` 按 id upsert，超出 `PROJECT_MEMORY_LIMIT` 淘汰最旧。
- 删：`removeProjectMemory` / `deleteProjectMemories`（后者备用，模块未直接用）。
- 防重：contentHash 相同内容不重复写。
- 串行化：`withLock` 包裹 read-modify-write。

## 三、逻辑缺陷复核（已逐条回源码）

下文每条均标注"复核方式"与"结论"。复核基于 2026-08-28 工作区快照。

### 3.1 〔真问题·中等〕短期 `summary` 与长期记忆双份、无去重
- **复核**：`agentCore.js` L300 注入 `memory.summary`；L498 注入 `projectMemoryContext`；`contextCompression.js` 的 `SUMMARY_REQUIRED_SECTIONS` 含"约束与偏好"，与长期记忆 `kind ∈ {preference/constraint}` 内容天然重叠。`agentCore.js` 注入顺序中两者并列，无任何去重/优先级机制。
- **影响**：同一事实同时以"压缩近似（summary）"和"原文（长期记忆）"两份呈现，浪费 token 且表述可能不一致，干扰 LLM 判断。
- **建议**：在 `buildRequestMessages` 注入长期记忆前，用 `summary` 已含的约束/偏好做一次交叉去重，或约定"长期记忆不重复注入 summary 已覆盖项"。

### 3.2 〔真问题·严重但触发面窄〕两个 awaiting 确认卡共用一个布尔位 + 工具循环不中断
- **复核**：
  - `runToolCalls`（`agentRuntime.js` L380-445）对每个 tool_call 逐个 `await callTool`，**无 `if (awaitingConfirm) break`**。
  - `send` 主循环（`useAgentChat.js` L561）在 `runToolCalls` 返回后才检测 `getAwaitingConfirm()` 并 `break`。所以同轮 `[show_plan_for_confirm, memory_suggest]` 两卡都会 append。
  - `handleConfirmPlan`（`AgentPanel.jsx` L406-417）**总是先查 `getActivePendingMemorySuggest()`**，有则走记忆落库并 `return`，不会去确认策划。
- **影响**：在 **step-confirm / Skill 模式**下，若 LLM 同轮既展示策划又提议记忆，用户点"确认策划"会被误路由为"保存记忆"，策划卡被吞。
- **不触发条件**：auto 模式下 `show_plan_for_confirm` 不进 awaiting（直接执行），故不触发。
- **建议**：用显式互斥标志区分 `pendingType ∈ {plan, memory}`；或 `handleConfirmPlan` 按"哪张卡触发的"传参分流；或在 `runToolCalls` 执行 memory_suggest 后中断后续工具。

### 3.3 〔真问题·中等〕落库层未脱敏（后门）
- **复核**：`saveProjectMemory`（`projectMemoryStore.js` L114-137）L119 仅 `String(memory?.content || '').slice(0, PROJECT_MEMORY_CONTENT_LIMIT)`，**无 `sanitizeMemoryContent` 调用**。脱敏只在 `memory_suggest.execute` 工具层做一次。
- **影响**：`saveProjectMemory` 是导出公共函数，注释称"供清理/未来接入"。若未来有其它入口（批量导入、其它工具）直接调用，密钥/本地路径会原样写入 localStorage。
- **建议**：将 `sanitizeMemoryContent` 下沉到 `saveProjectMemory` 内部，工具层不再单独脱敏，从源头收口。

### 3.4 〔真问题·设计未落地〕`facts` / `notes` 无写入点 → 注入死代码
- **复核**：全仓库仅 `agentCore.js` L302-307（读取/注入）与 `conversationState.js` L216-217（归一化兜底）涉及 `facts`/`notes`；**无任何 `setCurrentMemory` 写入这两个字段**。`emptyMemory()` 给空数组，永不填充。
- **影响**：`buildRequestMessages` L302-307 的记忆块恒为空，属死代码；跨轮"忆"残缺，实际只有 `summary`/`lastPlan`/`global_contract` 生效。
- **备注**：文件头注释已自承"治本是补齐 memory 自动摘要（summary/facts 自动沉淀）"，当前 facts 沉淀未实现。属已知设计缺口，非运行 bug。

### 3.5 〔已撤回·误读〕`buildProjectMemoryContextFromStore` 的 MMR 参数 bug
- **复核结论**：**不成立，是审计者误读，撤回。**
- **事实**：`memoryRetrieval.js` 导出 `rankProjectMemories(memories, query, options={limit:6})` + `buildProjectBlock` + `buildProjectMemoryContextFromStore(agentKey, projectId, query)`。**不存在** `_mmrRerank(maxResults, maxTokens)` 函数，也不存在"传 (50, 8)"的调用。调用点 `useAgentChat.js` L498 为 `buildProjectMemoryContextFromStore(agentKey, '', text)`，3 参数精确匹配签名；内部 MMR 用 `DEFAULT_LIMIT=6`、按字符上限截断，逻辑正常。**长期记忆注入功能正常。**

### 3.6 〔真问题·轻微〕`withLock` 不严格串行
- **复核**：`withLock`（`projectMemoryStore.js` L46-52）用 `next = prev.then(fn)`，`fn` 是 async，`prev.then(fn)` 会**立即启动** `fn`（内部 `await` 不阻止后续链排进）。多个并发写同一 key 时 read-modify-write 可能交叠。
- **影响**：实测风险低（同 key 写极少并发），但严格说并非串行化。
- **建议**：改为 `prev.then(() => fn())` 确保 `fn` 在 prev 完成后才启动；或显式 `await prev` 后再执行。

## 五、一句话总结

> LLM 在对话中通过 `memory_suggest` 提议 → 暂存 + 门禁 → 用户确认 → 写入 localStorage 长期记忆（记）；同时对话内自动沉淀 `summary`/`lastPlan`/`global_contract`（忆）；生图样本自动提炼为只读学习上下文（学）；超预算时压缩历史为 summary（压）。每次请求由 `buildRequestMessages` 把四层记忆按固定顺序注入 system 块，配合 fresh-task 只发本轮 user，实现"短上下文、长记忆"。当前主要风险在确认门禁的竞态与脱敏下沉，以及短期/长期记忆的重复注入。
