# AI 助手架构理解文档（深度版）

> 面向开发者，目标：**读完后能安全修改 AI 助手代码**。本文基于 `src/` 源码逐行归纳，所有关键结论挂行号，标注"改这里会踩什么雷"。
>
> 为什么需要这篇文档：AI 助手是**多层嵌套**的系统（UI → 编排 → 协议 → 传输 → 工具 → 画布 → 持久化）。原单文件 `useAgentChat.js` 堆叠 7 类职责，2026-08-18 已拆成 `useAgentChat.js`（hook 编排）+ `agentCore.js`（纯函数）+ `agentRuntime.js`（运行时）三层（见 §0）。**不理解各层间的契约，任何改动都可能破坏"工具消息配对"或"undo 原子性"这类隐藏不变量。**

---

## 0. 一句话架构

`AgentPanel` 负责"长得怎么样"，`useAgentChat` 负责"怎么跑"，`conversationStore` 负责"记在哪里"，`useCanvasAgentTools` 负责"AI 对画布能做什么"，`localTool` 负责"怎么连上真模型"。

```
① UI        AgentPanel.jsx              面板 UI / 状态 / 按钮 / 附件挂载
② 编排核心  useAgentChat.js             hook 编排：send/会话/状态机/消息同步（ref 一致性）
②′ 纯函数    agentCore.js                常量+提示词+SSE/消息组装/demo/图像拆分（可单测）
②″ 运行时    agentRuntime.js            LLM通信/工具执行/演示引擎（依赖注入，无 React）
③ 会话存储  conversationStore.js        单一数据源 + 自动落盘 + AI撤销栈
④ 工具层    useCanvasAgentTools.js      ~30 个画布工具 + callTool 分发
⑤ 模型配置  agentModelStore.js          供应商 / 模型 / streamMode
⑥ 传输代理  localTool system.ts         /api/proxy 转发 + SSE 剥壳 + stream 尊重
⑦ 派生契约  deriveNodes.js + Context    建子节点+连线原子进 undo
```

> **职责模块化拆分（2026-08-18）**：原单文件 `useAgentChat.js`（1345 行）堆叠 7 类职责，已按「职责模块化」拆成三层：
> - **agentCore.js**（纯函数层）：`MAX_TOOL_ROUNDS`/`ENABLE_TOOLS_ON_NON_STREAM`/`CANVAS_AGENT_RULES`/`SKILL_EXECUTION_RULES` 常量与系统提示词，`parseSSEChunk`/`parseGenerationsFromReply`/`buildRequestMessages`/`parseAgentError`/`demoPlan`/`imageModeLooksLikePerReferenceEdit`/`buildPerReferenceGenerations`/`historyKey`/`loadHistory`。全部无副作用，可独立单测。
> - **agentRuntime.js**（运行时逻辑，依赖注入）：`roundTrip`（LLM 通信）/`runToolCalls`（工具执行）/`runDemoMode`（演示）。不持有 React 闭包，依赖经 ctx 显式注入。
> - **useAgentChat.js**（hook 编排核心）：保留 send/sendImageMode/会话/状态机/**消息同步辅助**（appendMsg/setHistory/updateLastStreaming/endStreaming/stripStreaming——与 messagesRef 强耦合、一改就崩的区域），并对 agentCore/agentRuntime 做薄封装调用。
>
> **re-export 保契约**：useAgentChat.js 顶部 `export { ... }` 重新导出 agentCore 全部导出，既有单测（agentLogic/demoPlan/imageModeSplit/useAgentChat.hook.test + scripts/test_agent_tools.cjs）import 路径不变。**改纯函数逻辑去 agentCore.js，别改 useAgentChat 的 re-export。**

## 1. 完整数据流向（端到端，10 步）

以「文本发送 + 工具调用」为例：

```
[1] AgentPanel 收集 text / attachments(model) / model
[2] send(text, attachments)                     useAgentChat:406
     · 忙判定：isAgentBusy() → 忙则进 steerQueue（:414）
     · 附件归一化：blob→data / 相对→绝对 / 只认base64的provider转base64（:433-434）
     · 参考图编号目录：refCatalog + setCurrentReferenceImages（:436-449）
[3] buildRequestMessages() 构造 LLM 消息             agentCore.js:227
     · fresh-task 只发本轮（agentCore.js:291）
     · imageCatalog「图N」注入 system（agentCore.js:280-290）
     · tool 消息配对去孤儿（agentCore.js:326-355）
     · empty tool_calls 过滤（agentCore.js:333-336）
[4] 双链路：provider → /api/proxy ；否则 → /api/agent/{key}/chat
[5] localTool system.ts 转发（尊重 stream 意图 + SSE 剥壳）
[6] roundTrip 解析：流式 parseSSEChunk + 50ms 节流 flush / 非流式 res.json()   agentRuntime.js:50
[7] 若带 tool_calls → runToolCalls()（逐个 await）     agentRuntime.js:198
[8] 无工具调用 → 结束
[9] finally 落盘：captureActiveConversation()  + workflow 终态（useAgentChat:527-557）
[10] 若 steerQueue 有下一条 → sendRef 续跑
```

## 2. 多条发送路径（5 条）

### A · 文本发送 `send`（主流，useAgentChat:406）
```
send(text, attachments)
 ├─ 忙 → 入 steerQueue（不打断）→ return
 ├─ Demo 模式（VITE_AGENT_DEMO='1'）→ runDemoMode()（本地规则引擎，不走真实 LLM）
 └─ 真实模式 → 多轮工具循环（≤ MAX_TOOL_ROUNDS）
      · planning 置位 → roundTrip()（agentRuntime.js:50）→ 工具循环 → 无工具调用结束
```

**关键细节（改这里最容易错）**：
- `MAX_TOOL_ROUNDS` 上限：走满仍不收敛时，`assistant` 被提升到循环外访问（`:470`），否则 `ReferenceError`。
- **finally 是三态落盘**（`:531`）：`!ok ? (aborted?'stopped':'failed') : 'completed'`。`AbortError`→stopped，其他异常→failed。
- **三阶段门禁**：`pausedForConfirm`（`:534`）时 workflow 置 `awaiting_confirm`，**保留 pending**（不清空），等用户确认后 `send('已确认，请按策划执行')` 重建。
- steer 队列续跑在 finally 尾部（`:550-556`），状态置 `planning` 继续。

### A' · 非流式 JSON（`roundTrip` 的 `isNonStream` 分支）
- 触发：`streamMode === 'non-stream'`。
- 请求 `stream:false`，响应完整 JSON，`res.json()` 解析 `choices[0].message.content`。
- 默认不开工具（`ENABLE_TOOLS_ON_NON_STREAM=false`）。
- ⚠️ **历史 bug**：localTool 曾把非流式完整 JSON 误当 SSE 逐行过滤 → 回复截断。已修（`system.ts` 尊重前端 `stream:false` + SSE 剥壳）。改此处必看 `system.ts` 的 `requestStream` 变量。

### B · 图像模式 `sendImageMode`（不经 LLM）
- 提示词 + 参考图 → 构造单个 generation 步骤 → 复用 `execute_plan`（canvasPlanExecutor）直连画布生图。
- 参考图按 `provider.refFormat === 'base64'` 决定是否转 base64。

### C · steer 队列续跑（`sendRef` + `workflow.steerQueue`）
- 任务进行中再发送 → 排入当前对话 `workflow.steerQueue`（per-conversation，切对话不串台）。
- 队列消息标记 `steer: true`、`statusLabel: '已排队'`（`:417`）。
- 任务结束后 finally 自动取队列下一条执行。

### D · Skill 三阶段（`runToolCalls` + 门禁）
- `show_plan_for_confirm`（策划）→ 按 `runMode` → `execute_plan`（执行）。
- **runMode 分级**（`:471-476`）：
  - `auto`（默认）：`show_plan_for_confirm` 仍输出规划/generations，但**不进入 awaiting 确认态**，LLM 直接 `execute_plan`（不弹确认）。
  - `semi`：进入 awaiting 确认态，展示确认门禁，用户确认后才 `execute_plan`。

## 3. 协议层细节（改消息构造必看）

`buildRequestMessages`（agentCore.js:227-362）是最容易踩雷的协议层，4 个隐藏不变量：

### 3.1 fresh-task：历史轮次不进上下文
- 历史 user/assistant 消息**一律不进 LLM 上下文**，只发「本轮」user + 同轮工具循环的 assistant/tool（agentCore.js:291）。
- **跨轮记忆靠 memory 注入**（摘要/统一风格/已确认信息/备注/最近策划），**跨轮改图靠执行层回退**（`execute_plan` 的 `getLastUserReferenceImages`）。
- **为什么**：彻底消除「跨轮真图堆积 + refCatalog 每轮从 1 重编撞号」→「反推图一却全反推」的 bug。

### 3.2 tool 消息配对（agentCore.js:326-355）
- OpenAI 协议要求 `role:'tool'` 消息**必须紧跟带 `tool_calls` 的 assistant 消息**，且 `tool_call_id` 能匹配。
- 实现：维护 `pendingToolIds` 集合。assistant 声明 tool_calls → 登记 id；tool 消息**需命中才保留，否则丢弃**（孤儿消息触发后端报错）。
- **改这里必看**：删消息时若破坏配对，后端会报 `messages with role "tool" must be a response to a preceeding message with "tool_calls"`。

### 3.3 empty tool_calls 过滤（agentCore.js:333-336）
- 空数组 `[]` 是 truthy，若不过滤会原样发给 LLM → 后端报 `Empty tool_calls is not supported in message`。
- 只发「非空」的 tool_calls。

### 3.4 图片目录机制（两种编号并存，容易混）
| 编号 | 位置 | 用途 |
|---|---|---|
| `图N` | imageCatalog 注入 system（agentCore.js:280-290） | 跨轮引用历史图/上一轮生成图，配 `direct_refs` |
| `参考图N` | refCatalog（useAgentChat:441-446）+ `attachment_indices`（0-based） | 本轮参考图精确引用，`attachment_indices` 指向编号 |

- **图本体不进 LLM 上下文**，执行层按编号反查原图（`setCurrentReferenceImages`）。
- 参考图附件带画布坐标 `x/y`，以文本附给 LLM 感知位置（agentCore.js:310-318）。

## 4. 工具调用层（useCanvasAgentTools）

### 4.1 runToolCalls 的 async 逐个 await（agentRuntime.js:198-257）
```js
for (let i = 0; i < toolCalls.length; i++) {
  const r = await callTool(toolCalls[i].function.name, parseArgs(...))
  // 结果按 i 回填 role:'tool' 消息
}
```
- **必须逐个 `await`**：若用同步 `forEach`，`callTool` 异步返回的 `undefined` 会被当"调用失败"误判，触发重试 → **死循环重复建节点**（历史 bug，TASK-006 修复）。
- 改这里**禁止**改回同步循环。

### 4.2 工具分组（~30 个）
读（list_nodes/read_canvas/get_node_details）｜建（create_node/batch_create_nodes）｜改（update_node/update_node_any_field）｜连（connect_nodes/batch_connect_nodes/delete_edge）｜执行（generate_node/execute_plan/show_plan_for_confirm）｜视图（fit_view/zoom_in/zoom_out/focus_node）｜管理（lock_node/group_nodes/undo_ai/move_node）。

- `AGENT_TOOLS` 数组**顺序 = 模型选择优先级**（常用在前）。
- 工具写画布走 `setNodes`/`setEdges`/`deriveNodes`，并压入 **AI 撤销栈**（`undo_ai`）。

## 5. 会话存储层（conversationStore）

- `useSyncExternalStore` 范式，模块级 `states[agentKey]`。
- **按 agentKey 隔离**：`canvas-assistant-<projectId>`（App.jsx:265），会话跟随项目走。
- **自动落盘**：所有变更走 `commit()` → 更新内存 + notify + 写 localStorage（`agent_conversations_<agentKey>`）。
- **hydrated 守卫**：挂载早期未恢复时不落盘，防空数据覆盖真实记录。
- 提供 memory / workflow（含 steerQueue、status）/ pending / **AI 撤销栈** / referenceImages / runMode 等 per-conversation 状态。
- **落盘时机**：`captureActiveConversation()` 在 send 的 finally 统一调用（useAgentChat:528-549），不是每步都落。

## 6. 传输层（localTool system.ts）

- 处理 `/api/proxy`：把 OpenAI 兼容请求转发到真实供应商。
- **尊重前端 stream 意图**：前端 `stream:false` 时，即使上游返回 `text/event-stream` 也走完整 JSON 分支（不做 SSE 逐行过滤）→ 修复回复截断。
- **SSE 剥壳**：非流式但被 SSE 包裹时，剥 `data:` 前缀还原纯 JSON。
- 协议翻译：剥 `{code, data}` 信封，前端直接拿 `data`。

### 双链路对照
| | proxy 链路 | agent 链路 |
|---|---|---|
| 触发 | 配置了 provider（如魔搭，支持 function calling） | 未配置 provider |
| URL | `POST /api/proxy` | `POST /api/agent/{agentKey}/chat` |
| body | 外层包 `{ url, providerId, method, body }` | 直接 `llmBody` |
| 上游 | `openai://chat/completions` 或 `base_url+/v1/chat/completions` | localTool `agentChat.ts` |
| 鉴权 | 无 Bearer | 可选 `Authorization: Bearer CHAT_API_KEY` |

**agent 链路的真实转发（`agentChat.ts:143`，改默认 LLM 必看）**：
- **`cfg.baseUrl` = `LLM_CHAT_BASE_URL`** env（未配 → 500 `LLM_CHAT_BASE_URL not configured`）。
- **`cfg.model` = `LLM_CHAT_MODEL` env，覆盖前端传来的 defaultModel**（agentChat.ts:201）。
- **画布操作准则 system 由前端 useAgentChat 注入**（双链路单一来源），后端仅在 `AI_CANVAS_ENHANCE='1'` 且消息无 system 时兜底，**避免双份重复**（agentChat.ts:171-179）。
- 走 `fetchWithProxy`（本机访问外部 LLM 需代理），但**SSE 会被缓冲成一次性返回**（打字机退化，功能仍正确，前端仍能解析 tool_calls）。
- **`Accept-Encoding: identity`** 主动规避 gzip（见 localTool §10.6）。

排查看 logger `via: proxy|agent` 字段。

### Provider 数据来源（决定走哪条链路的根因）

- **主供应商**：`providerStore.js` 的 `isPrimary`（`:70`）。`useCanvasAgentTools` 从主供应商读 `provider`。
- **模型分类**：provider 模型分三类 `image_models / chat_models / video_models`（localTool providers.ts:10）。**AI 助手聊天用 `chat_models`**，生图用 `image_models`。
- **KV 同步**：改主供应商时 `providerStore.js:179` 会同步写 localTool KV 的 `active_api_endpoint`（跨端读当前生效 endpoint）。
- **判定规则**：roundTrip（agentRuntime.js:50）里「provider 存在」= 主供应商存在且启用；存在 → proxy 链路，否则 → agent 链路。

## 7. 渲染层（AgentMessage.jsx，AI 消息如何呈现）

- 渲染 `conversation.messages`，按 `content`/`imageCatalog` 渲染文本 + 图片。
- **图片目录**：消息里的 `图N` 引用经 imageCatalog 反查 URL 渲染成 `<img>`；参考图附件渲染为图块。
- **正在输入态**：streaming 消息尾部有打字机光标，`endStreaming` 移除。
- **工具卡片**：工具调用/策划/执行摘要有专属渲染（`pendingGenerations`、`lastResults`）。
- **交互**：发送/停止按钮由 `sending` 状态驱动；错误消息红框展示。

## 8. 建子节点统一契约（deriveNodes）

- `buildSpawnNodes` / `applySpawnSnapshot` / `makeChildId`。
- 收敛 9 处「建子节点 + 连线」为统一快照构造，配合 `CanvasEdgesContext.record` **原子进 undo 栈**。
- **为什么原子**：`useCanvasHistory.record` 注释明确"先 setNodes 再 record 必须显式传快照"，否则 undo 丢新增节点。
- 子节点 data 构造保留在各节点（每处业务不同），统一工具只管骨架（位置/edge id/原子快照）。

## 9. 状态机（InputStateMachine）

`idle → planning → running → (awaiting_confirm | failed) → idle`

- 发送锁：`sendingRef.current = true`（`send` 开头，`:423`），finally 释放（`:548`）。
- 忙判定：`isAgentBusy()` = 发送锁 + 状态机 running（复合判定，防并发双发）。
- 停止：`AbortController.abort()` → catch `AbortError` → `setStatus('idle')` + `stripStreaming()`（`:515-526`）。
- **stripStreaming 清所有 streaming 残留占位**（循环中途出错可能残留多轮，不只最后一个）。
