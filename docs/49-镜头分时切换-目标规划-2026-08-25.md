# 49 · 镜头分时切换 + AI 直接生成工程 · 目标规划

> 日期：2026-08-25
> 状态：**目标规划（未实施）** —— 仅记录"为什么要做、最终长什么样、边界"，供后续想实施时深挖。
> 范围：`src/components/director3d/`（3D 导演台）

---

## 0. 一句话目标

让用户**用一句话描述想要的画面**（如"一个美女坐着，先切手部特写吃东西、再切脚部特写、最后拉远景全身"），AI 直接读/写我们的**工程数据**，生成一套可分镜头播放、可一键导出的成片工程，用户导入即用。

---

## 1. 背景与现状

- **单镜头独占**：工程有 `shots`（镜头列表），每镜头是**独立完整场景快照**（人物/摄像机/关键帧/参考图/路径各自独立保存）。
- 播放/编辑只认 `activeShotId`；时间轴只画该镜头；导出也只出当前镜头。
- 镜头列表可：新建/复制/删除/改名，**暂不能拖序、也没有"该镜头几秒到几秒"**。
- **工程本身是结构化 JSON**：`projectData` 序列化 / `normalizeProjectData` 反序列化（`project.js`），`objects` / `camera` / keyframes / `paths` / `shots` 一应俱全。

---

## 2. 目标形态（选镜我要切镜，不要一镜到底）

用户心理画像：喜欢**有节奏的切镜**，不喜欢一镜到底。即使人物静止，也更希望"全景 → 手部特写 → 脚部特写 → 全身"这样明确的多次切镜，而非一条机位长镜头。系统以"镜头"为单位编排时间，天然贴合。

### 2.1 多镜头分时顺播（地基）
每个镜头配一个**时间段**（镜头1=0–3s、镜头2=3–8s、镜头3=8–12s），整条时间轴依次拼接：

```
时间轴 |── 镜头1 (0–3s) ──|── 镜头2 (3–8s) ──|── 镜头3 (8–12s) ──|
```

- 播放：播放头走到几秒就加载渲染那个镜头。
- 导出：按整条时间轴把各镜头段拼成一段成片。
- 边界：初期**硬切**；过渡/交叉淡化留作后置可选。

### 2.2 一层给 AI：一句话 → 生成工程
用户给自然人语言指令，AI 产出这套 `shots` 工程（每个镜头含：人物/人物动作/机位关键帧/时长/切镜顺序），导入即用。**核心卖点：AI 直接生成数据，用户不逐镜头手搭。**

### 2.3 导出成片
工程可一键导出整段拼接的 MP4/（PNG）。这是"直接生成 + 直接导出"闭环的最后一步。

---

## 3. AI 能否直接获取现有工程数据？—— 能，靠数据通道而非 UI

工程就是一份结构化 JSON。因此"AI 拿到工程 + 生成工程"不依赖 AI 在界面里点按钮，而是**通过数据通道**。两条候选通道：

| 通道 | 做法 | 适合场景 | 成本 |
|---|---|---|---|
| **文件/导入导出（推荐起步）** | 工程存为 JSON，AI 读取→生成一份合法 `project` JSON→用户经现有导入入口加载 | "一次生成一个工程给你导入"，最不易坏，无需额外适配 | 低 |
| **MCP / 工具接口（进阶）** | 起一个 MCP server 暴露 `read_project / write_project / render_video`，AI 主动读写工程、触发导出 | "AI 持续操作、随时取最新工程+往返导出" | 中（要写 MCP 适配层） |

> 判断：对"我把描述交给 AI，AI 写好工程，我导入"这个诉求，**第 1 条（文件级生成 + 现有导入）最贴合、最稳**；MCP 更适合"AI 常驻、反复操作、自动触发导出"的深度集成。前者是第一步，后者可作为进化。
> 关键前置：无论哪条，都需要**把工程 JSON 的结构（契约）给 AI 讲清楚（schema / 示例）**，AI 才能生成可被 `normalizeProjectData` 正确加载的数据。

---

## 4. 分层依赖（为什么先做地基）

```
地基：多镜头分时顺播 + 整段导出  （docs/49 §2.1 —— 必须先有）
   ↓
中间：AI ↔ 工程数据通道（读/写 project JSON）   (§3)
   ↓
顶层：AI 一句话 → 生成多镜头工程 → 一键导出成片  (§2.2 + §2.3)
```

- 若无多镜头顺播，AI 只能生成"单镜头"，无法满足"多次切镜成一片"。
- 若无数据通道，AI 无法"直接生成工程导入"，只剩"出方案人手动搭"。
- 故**第一步是打通数据通道 + 多镜头顺播**，顶层 AI 生成是最后一层。

## 5. 实施方向的初步边界（供后续深挖，本次不展开）

- **数据**：镜头结构新增"时间起点/片段长度"；顺序 = 时间轴先后。
- **串联引擎**："按 activeShot 取工程状态" 改为 "按播放头所在镜头取状态"；导出按段拼接。
- **AI 通道**：先做"工程 JSON 生成 + 现有导入"（§3 第 1 条），并备一个 `project` 结构的 schema 给 AI 参考。
- **不做的**：不做曲线编辑器、不做机位过渡曲线、不破坏镜头独立场景。

---

## 6. 明确不做（Non-goals）

- 不做"同一人物连续演、仅换机位"的多机位共享时间轴。
- 不做 C4D 式曲线面板；不追求一镜到底式镜头美学。
- 不把镜头从"独立场景快照"改造成"共享场景只差机位"。

## 8. 要让 AI 配好一个镜头，得先喂给它哪些知识？（关键功课）

> 触发点：一次实测暴露了"AI 看着结构就能配"是不可靠的——只给逻辑/结构，AI 会把机位数值"瞎配"到根本看不到人物。结论：**结构不等于能配好**，AI 还缺一组"能让它不瞎配"的知识。以下分类列出，作为 AI 生成前的必修知识清单。

### 8.1 世界观 / 坐标与尺度（最高优先，缺了必然瞎摆）
- **坐标约定**：X 左右、Y 高度（人物脚踩 Y≈0）、Z 前后/深度。
- **默认单位尺度**：一个人物高约 1.7~1.8 单位；机位离人物多远叫特写/近景/中景/全景/远景（给"米/单位 ↔ 景别"对照表，如特写约 0.8~1.5、中景约 2.5~4、全景约 6~12）。
- **构图朝向**：人物默认朝 +Z 还是 -Z；机位的 `position` 与 `rotation` 如何配合才能"对准"人物（这是瞎配的重灾区）。

### 8.2 摄像机参数域（决定"能不能看到、取多远图"
- 摄像机 `position`（世界坐标）、`rotation`（格式见下）、`focalLength`（焦距越短视野越广）。给每项合理范围，否则会穿模/看不到。
- **`rotation` 编码**：**[pitch, yaw, roll]**，pitch=仰俯（负=俯视），yaw≈水平朝向。AI 要明白"我要看人物 → yaw 该怎么算"，最好给一个现成函数/示例 **cameraRotationToward(target)** 的计算结果作为约定，而不是让它猜。
- **`targetMode`**：`"object"` 会强制盯住目标中心（适合"始终看人"），`"manual"` 才允许自由俯仰特写（俯腿/正面必须用 manual）。这点必须在知识里点破，否则 AI 会一直用 object 导致做不出仰俯。

### 8.3 世界观数据 / 场景布局
- 当前工程里有哪些对象、位置在哪（人物 actor-lead、平台 block、台阶 step），**"人物此刻在路径哪一段、大概在世界坐标哪里"**。AI 若是"读现有工程"，需能拿到这些；若是"从零生成"，得先布局对象再配机位。
- 视野里有没有遮挡（如平台会不会挡住机位看人物）——给碰撞提示。

### 8.4 规则约束 / 硬性边界（避免生成"怪东西"）
- 机位不能进的区域（人物足底以下、穿墙、离地负数）。
- 人物 `pose` / `continuousMotion` 用哪个值（开关的层含义，见docs/46/47），别把开关当动画量打关键帧。
- 时间轴只有 360 帧（15s），关键帧 frame 必须在 [0,360] 内且递增。

### 8.5 AI 怎么"看"结果？—— 自检要分两级，别一上来就渲染

AI 必须能自我"看见大概效果"，否则光有知识也是盲配。但**真实离屏渲染很重**（项目现状截图走浏览器 canvas/monitor，UI 会话内；无 headless 渲染，见 8.5 B）。所以分两级，由轻到重：

**A · 纯数学"视锥快判"（零渲染，AI 自己就能算，做成必修）**
AI 拿到一帧的摄像机 + 对象布局后，不渲染也能判断"人物在不在画面里、大概多大、朝哪边"——这本质是几何投影，可写成纯函数让 AI 算（或给 AI 一个现成判定工具）：
- **在不在画面**：把人物包围盒（脚 Y0 → 头 Y≈1.8）的 8 角点，用相机 position/rotation/focalLength 投影到像平面，看是否落在视野(FOV)及屏幕内、是否被近平面裁剪。
- **大概多大/景别**：投影后包围盒的屏幕占比 ≈ <2% 远景 / 10~30% 中近景 / >60% 特写。AI 能据此知道自己给的镜头是"全景还是特写"，不用真看图。
- **朝没朝对**：人物中心投影应落在画面中央附近；朝向（人物正面 vs 机位方向）用点积判断"拍到的是正面/侧面/背面"。
- 优点：纯数学、快、可无环境运行；它让 AI 在**生成时**就用"视野+占比+朝向"三条硬校验自纠，把"看不到人"直接挡在生成阶段。
- 这是"AI 自检"的**默认主通道**——因为它能嵌进 AI 的推理循环，成本低。

**B · 真渲染一帧 PNG（精修才用）—— 不必新造渲染，把"导出按钮"命令化即可**
数学判定够用但不够"真"（看不出材质/构图美丑）。精修需要 AI 真看到一帧图，而**这是现成的**：
- **现状事实**：场景渲染是浏览器内 R3F，导出单帧走 [handleCaptureImage](file:///Users/kevin/Documents/maomao/src/components/director3d/App.jsx#L1195-L1243)（`canvas.toBlob` 出 PNG），产物交给宿主 `onExport` 落盘入库（project 存储）。localTool 后端只负责存图，无 headless 渲染。
- **关键洞察（用户方案）**：导出 PNG 本来就是用户在 UI 里点一下按钮做的事。把它**封装成一个"命令/工具"暴露给 AI**：AI 调用该命令 → 引擎 seek 到指定帧 → 触发 `handleCaptureImage` 渲染一帧 → PNG 落盘到 `/files/` → AI 读那张图复核构图。**已复用的就是现有渲染 + 落盘通道，不引入新渲染引擎。**
- **落地要点**：
  1. 命令参数：要的帧号（或"当前播放头 + seek 到帧N"）。
  2. 落盘到 localTool `/files/` 固定目录，返回 URL（契合"结果持久化 localTool(18080)+AI 轮询读回"的项目纪律）。
  3. AI 拿 URL 看图 → 判断构图 → 微调 position/rotation → 再渲染复核（闭环）。
  4. 前置依赖：Director 页面/UI 会话在跑（它借浏览器渲染引擎出图）。
- 定位：作为 A 判定的**复核/精修通道**，不是每次生成都跑（成本高、慢），A 选帧 B 看画面。

**联动建议**：AI 默认用 A（生成时即自纠）→ 你或 AI 挑 2~3 个代表帧 → 用 B 渲染 PNG 复核外观 → 不满意微调。这样既快又真，不依赖"一次渲染全流程"。

### 8.6 必备知识最小集（分级，别堆参数）

| 级别 | 知识 | 作用 | 缺了会怎样 |
|---|---|---|---|
| **P0 必知**（不懂就生成非法/永远不对） | project JSON schema（字段/类型/单位/`rotation` 的 [pitch,yaw,roll] 编码/`targetMode` 含义） | 能写出合法工程 | 数据导不进 / 字段错 |
| **P1 几何** | 坐标约定（X 左右/Y 高/Z 深浅）+ 人物尺寸≈1.7–1.8 单位 + 景别↔距离对照表 + 构图朝向 | 能摆对"位置 vs 画面" | 看不到人 / 画面空 |
| **P2 场景** | 当前有哪些对象及位置、人物此刻在路径哪段、有无遮挡 | 能基于现状布局 | 被平台挡 / 对着墙面 |
| **P3 约束** | 机位禁区（穿模/离地负）、开关别打关键帧、frame∈[0,360] 递增 | 不生成"怪东西" | 穿模 / 非法帧号 |
| **P4 自检闭环** | 8.5A 视锥判定数学 + (可选) 8.5B 渲染能力 | 生成时自纠、生成后复核 | 只能盲配、靠人手动修 |

> 结论：真正"必须"的是 P0–P2（结构+几何+场景），P3/P4 是"不炸 + 能自纠"。**别给 AI 堆全部字段**，给"最小能说懂 + 一张对照表（景别/朝向）+ 一个判人物在不在画面的函数"就够了；剩下的靠 8.5A 自检循环补。
