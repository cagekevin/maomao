```
现状文件 → 五轴映射：
┌─────────────────────────────────────────────────────────────┐
│ 轴1 会话轴  → conversationState.js（容器元数据）              │
```

- [ ] `updateLastStreaming`/`endStreaming`（高频热路径）→ 改 `patchCurrentMessages(next)`（Step 1A-2）。
  - ⚠️⚠️ **改 store 后必须保留的 3 个不变量（否则丢消息/LLM 报错，执行者最易简化掉）**：
    1. **`updateLastStreaming` 的 `realCalls` 空数组过滤**（`:281/:294`）：只保留 `delta.toolCalls.filter(t => t.function?.name)`，为空则**不设** `tool_calls` 字段。改成 store 后**必须原样保留**，否则空数组 tool_calls 进历史 → 后端报 `Empty tool_calls`（docs/12 §3.3）。

    3. **`endStreaming` 的时序保证**（`:307-309` 注释）：原实现"同步更新 messagesRef"是为了 finally 落盘时**读到完整 assistant 而非空 streaming 占位**。改成 store 后，`endStreaming` 必须**同步更新 store**（不是异步 setState），且 send 的 finally 落盘同步读 `getCurrentSnapshot()`——**这个"同步写→同步读"的时序链必须由 store 的同步性维持**。若 `patchCurrentMessages` 实现成异步（如放进 React 批处理），finally 会读到空占位 → **AI 回复丢失**（历史 bug 翻版）。**验证**：测试必须断言"endStreaming 后立即 getCurrentSnapshot() 读到的是完整 assistant（streaming:false）"。
- ⚠️ **保留** 8 处 `setCurrentSnapshot({messages})` 的**会话生命周期快照**（`:453/:573/:682/:710/:736/:744/:752/:766`）**原样不动**——它们携带 skills/draft/attachments 等多字段语义（clear 清 workflow/memory、switchChat 切换暂存），**不可删除**。只把它们的 `messagesRef.current` 改为"store 当前 messages"。
- **同步读法**：send 循环内 `messagesRef.current` 改为 `getCurrentSnapshot().messages`（返回浅拷贝，同步可读）。⚠️ 若热点循环性能吃紧，可在 store 加 `getActiveMessagesRef()`（返回内部引用），但**必须保证读与写指向同一份**，不得引入第二份可变数组。
- **暴露给 UI（正确做法：用 `useStoreSelector` 按字段订阅，不要整包订阅）**：返回值 `messages` 应改为只订阅 messages 字段。⚠️ **不要用 `useConversationStore()` 整包订阅**——项目已有 `src/components/base/useStoreSelector.js`（P5 范式基座，专门解决"整包订阅连坐重渲染"），应复用它：
  ```js
  import { useStoreSelector, shallowEqual } from './useStoreSelector.js'
  import { subscribe, getState } from './conversationState.js'  // conversationState 需导出 subscribe/getState（或经 conversationStore）
  const messages = useStoreSelector(subscribe, getState, (s) => {
    const cur = s.conversations.find(c => c.id === s.activeId)
    return cur?.messages ?? []
  }, shallowEqual)
  ```
  ⚠️ **为什么必须用 selector 而非 `useConversationStore()`（关键，最终审查确认）**：
    - `useConversationStore()` 返回整个 `states[agentKey]`（`{ conversations, activeId }`），是**整包订阅**——任何字段变化（含高频流式 messages）都触发所有订阅者重渲染。
    - 但阶段 1A-2 的 `patchCurrentMessages` 设计意图是"**高频更新 messages 不影响其他**"（轻量路径）。若 UI 用整包订阅，**这个意图被破坏**：messages 每 50ms 变 → 整个订阅组件每 50ms 重渲染 → 仍是"流式卡死"翻版。
    - `useStoreSelector` 只订阅 selector 选中的字段：messages 变化只触发消息订阅者，sending/编排等不连坐。**这正是 patchCurrentMessages"轻量更新"能成立的前提。**
  - ⚠️ **配套基建（硬前置）**：`conversationState` 需要导出 `subscribe`/`getState`（当前是模块内私有，`conversationState.js:73/149`）供 `useStoreSelector` 用（或经 `conversationStore` 导出）。同时**仍需**给 `getState` 的 `conversations` 维持"变更才新引用"的不可变更新（`commit` 已保证 `states[agentKey]` 每次新对象），`useStoreSelector` 的 shallowEqual 会处理引用稳定。
  - ⚠️ **消费侧验收（见 §0.5.3）**：改完后 `AgentPanel.jsx:167` 解构的其余 17 个字段语义不变；`messages` 必须在**当前对话存在时**返回非空数组（否则 `AgentPanel` 的 `messages.length`/`messages.map` 渲染会崩）。用 `tests/unit/AgentPanel.test.jsx` 或手测对话列表/消息滚动验证。**不要**把 `conversations`/`activeConversationId`/`sending` 在本次一并改成订阅（那是阶段 1D 的事），阶段 1A 只动 `messages`。
  - **验证**：新增测试：`useStoreSelector` 订阅 messages，模拟 workflow 变化（非 messages）时组件**不重渲染**；messages 变化时仅消息订阅者重渲染（可用计数器断言渲染次数）。这是"轻量更新 + 按需订阅"成立的回归锁。

## §4 回滚策略

- 每阶段**独立 commit**（1A/1B/1C/1D/2）。
- 任一步回归失败 → `git revert` 该 commit，不影响其他。

- ⚠️ **大 commit 回滚粒度**：阶段 1A（消息单源化）会**横跨多个文件**（`useAgentChat.js` + `conversationState.js`/`conversationSnapshot.js` + 可能 `AgentPanel.jsx`），**一个 revert 未必干净**。**规避**：把 1A 再拆成更小的子 commit（如：① 只加 `patchCurrentMessages` + 测试 → ② 只改 `appendMsg`/`setHistory` → ③ 只改 `updateLastStreaming`/`endStreaming` → ④ 改返回值 `messages` 为订阅）。每子 commit 独立可回滚、可回归。**若某子 commit 无法独立通过测试，说明耦合过深，停下汇报，不要强行合并。**
