## 0. 一句话结论

**把「字节内容」与「对字节的组织」这两个正交维度彻底拆开**——这是本域的本质复杂度；此前所有方案（含 A/A′）把它压平在同一个 `resource` 行里（既存 `sha1` 又存 `folder` 又存 `name` 又存 `projectId`），才不断要在 file/resource 边界打补丁。`Content`（内容维度：身份 = `<alg>:<hex>(decodedBytes)`，无 folder/project/name，全局唯一不可变，GC 真源，**唯一写入入口 `Content.put(rawBytes)` 收口一切产字节流**；`rawBytes` = 已解码原始字节，decode 由各入口在调用前完成）与 `Ref`（上下文维度：`resource` = 按项目 Ref、`asset` = 画布 Ref、`task`/生成 = 各自 Ref，记录 `{ contentId=<alg>:<hex>, context{ projectId, physBucket(不可变存储桶), folder(UI分类,可改名), name, type... } }`）。`asset` 只持稳定 `contentId`（仅内联 dataURL/blob 才用 `url`）。任何产字节动作必经 `Content.put`、按字节哈希去重——从根上消灭「重复文件」与「跨项目串味」，且改名/移动只动 `context`、永不破图。** 三条不变量：① 字节唯一真源是 `Content` 维度（身份 = `<alg>:<hex>(decodedBytes)`、无 context）；`resource`/`asset`/`task` 都是对 Content 的 Ref，可多行指向同一 Content，且不得在自己层写字节；**并发去重真保证是 DB 对 `contentId` 列加唯一约束 + 冲突回退复用**（应用层查重只是优化，防 TOCTOU 双落盘洞）；② `context` 与 `content` 正交——改名/移动/跨项目只改 Ref 的 `context`（folder/name），`physBucket` 与 `contentId` 不可变、物理 url 由二者派生，永不破图；③ 去重是维度的副产物而非机制——同字节→同 `<alg>:<hex>`→同 `Content` 是物理事实，因唯一写入入口统一算 `<alg>:<hex>(rawBytes)`、且入口不可能自带 hash 上行，跨入口/跨目录去重免费成立；**GC 孤儿判定 = 反向扫描所有 Ref 的 contentId 引用，无引用者回收物理文件**。

## 1. 需求与分层模型（你定义的「井井有条」）

你给的分层（已复述确认）：**最底层 `resource`（素材库）→ 画布层 `asset`（只引用，不另存文件）**。核对代码后做更底一层地基：当前实现把「**字节内容**」与「**对字节的组织/命名**」两个**正交维度**压平在同一个 `resource` 行里（它既存 `sha1` 又存 `folder` 又存 `name` 又存 `projectId`），导致「去重（内容维度）」与「组织（上下文维度）」互相干扰——这正是所有补丁（hash 语义、fileId/url 冗余、resourceId 易变破图）反复冒出的根。落地时应把两个维度显式拆开：

```
L0  Content（内容维度真源 / 身份 = <alg>:<hex>(decodedBytes) / 无 context）
    │  纯函数 (rawBytes)→id；全局唯一、不可变、GC 真源
    │  物理落点 = /files/<physBucket>/<<alg>:<hex>>.<ext>
    │    physBucket = Content 创建时由入口锁定的「存储桶」，之后不可变（沿用 canvas/drop、web、migrated 等现有桶，零迁移/零破链）
    │    context.folder（UI 分类）是另一独立语义，绝不作为物理路径的一部分
    │  唯一写入入口 Content.put(rawBytes)：一切产字节流必经，入参 = 已解码原始字节
    │    （base64/dataURL→bytes、远程 URL→fetch bytes、文本→utf8 bytes，由各入口在调用前完成 decode；入口不得传已编码串）
    │    内部统一算 <alg>:<hex>(rawBytes)、命中即复用，绝不二次落盘（去重免费、跨目录免费）
    │    **并发去重真保证 = DB 对 contentId 列加唯一约束 + 冲突回退复用**（应用层查重仅优化，防 TOCTOU 双落盘洞）
    │  GC 真源：定期反向扫描 resource/asset/task 的 contentId 引用，无任何引用者即回收物理文件（孤儿 Content 判定）
    ▲  被引用（contentId 稳定；可多对一：不同 resource / asset / task / 生成输出 指向同一 Content）
L1  resource（Ref · 按项目上下文）
    │  记录 = { contentId=<alg>:<hex>, physBucket(不可变物理桶,创建时锁定,持久化列), context{ projectId, folder(UI分类,可改名), name, type, size, ts } }
    │  physBucket 不可变、与 contentId 一并决定物理 url；url 由 physBucket+contentId+ext 纯派生（不冗余落库）；
    │  改名只改 context.folder/name，physBucket 与 contentId 不变 → 物理 url 不变、永不破图
    ▼  被引用
L2  asset（Ref · 画布节点 / 引用方，不持有字节、不触发落盘）
    │  data 持 contentId（稳定）；仅内联 dataURL/blob 才持 {url}（互斥）
    ▼  被引用
L3  脚本盒 / 任务中心 / 预览 / 参考图 / 生成输出（各自 Ref，均经 contentId 引用 Content）
```

**三个不变量（地基，不可被局部绕过）：**

1. **SSOT 内容**：字节的唯一真源是 `Content` 维度（身份 = `<alg>:<hex>(decodedBytes)`、无 folder/project/name）。`resource`/`asset`/`task` 都是对 Content 的 `Ref`（上下文维度），可多行指向同一 Content；**任何产字节流必须经 `Content.put(rawBytes)` 单一入口（入参=已解码原始字节），不得在 Ref 层自己写字节**；**并发去重真保证是 DB 对 contentId 列加唯一约束 + 冲突回退复用**。任何功能要展示/产出字节，先有 Content，再持其 `contentId`。
2. **context 与 content 正交**：改名/移动/跨项目只改 Ref 的 `context`（name/folder/projectId），Content 维度（含不可变 `physBucket`、`contentId`）纹丝不动；`asset` 持 `contentId`（稳定），**绝不因 context 变化而破图**——物理 url 由不可变的 `physBucket`+`contentId` 派生，与可改名的 `context.folder` 解耦。这是把「组织」从「内容」里剥离后的直接收益，无需任何改名同步 hack。
3. **去重是维度的副产物，非机制**：同字节 → 同 `<alg>:<hex>` → 同 `Content`，是物理事实；因唯一写入入口统一算 `<alg>:<hex>(rawBytes)`、且入口不可能自带 hash 上行，**跨入口/跨目录去重免费成立，无需「查 contentId 列」或「跨目录预查」等补偿机制**；**并发去重真保证是 DB 对 contentId 列加唯一约束 + 冲突回退复用**（应用层查重仅优化，防 TOCTOU 双落盘洞）。落盘文件名 `<alg>:<hex>` 仅初始命名，改名不影响查重。

### 1.5.2 心法判定：哪些隔离是对的、哪个藏了缺陷

逐文件夹套 心法 §二（溯源 / 定海 / 切割），判定**不需要动的（真缝隙）**与**唯一的真缺陷**：

- **`uploads/` vs `runtime-models/depth-video/` vs `public/` —— 分离正确（真缝隙，不动）**。三者来源与生命周期根本不同：用户生成内容 / 本机推理运行时权重 / 前端构建壳。按 Phase 3 探界，这是「变化速率与来源截然不同」的真缝隙；强行合一才造上帝类。**最合理选项 = 维持分离**，不引入统一文件服务。
- **`backups/` `providers/` 与 `uploads/` 平级 —— 正确**。备份与主库隔离（防同清）、配置与用户内容隔离，都是 Phase 2 定海「把不变式摆到正确物理位置」的正确落点。
- **`uploads/.thumbnails/` 藏于 `uploads` 内 —— 正确**。缩略图是源文件的衍生态，物理同根、GC 同回收，符合「衍生状态只读、随源生灭」。
- **❌ 唯一缺陷：双上传根白名单**（`UPLOAD_DIRS` 前端 vs `UPLOAD_ROOT_ALLOW` 后端）。两者**并非完全相同的集合**——`UPLOAD_ROOT_ALLOW` 只校验**顶层根**（`parts[0]`，fileStore.ts:57-58），`UPLOAD_DIRS` 还含嵌套 `canvas/drop`、`canvas/video-process`；真正风险是「新增顶层桶（如 `voice`）需同时改两处顶层根枚举」，违反 Phase 2 探流「绝不在多处维护同一份状态」。当前虽同步，但 `uploadDirs.ts` 注释已自承耦合（"后端白名单若实施必须显式含上述值"）——这是会漂移的隐性债。已落成真债 **TD-12-4**，非"待观察"。

### 1.5.3 对唯一缺陷的最合理决策（TD-12-4）

**收敛为单一真源 + 漂移护栏**（可逆、低代价，不造新抽象）：

1. 选定后端 `UPLOAD_ROOT_ALLOW`（fileStore.ts:39）为安全边界**真源**（路径穿越 guard 本只在后端），前端 `UPLOAD_DIRS` 退化为「消费侧枚举 / 共享导出」；
2. 加一个轻量护栏（启动或测试断言两集合顶根等价），任一侧漏改即 **fail-loud**，杜绝"一端放行、一端拒收 → 静默丢文件"。

> 不合并成"统一大入口"——那违反 §一.2 收敛前提（把简单分支合成带开关的怪物）。两处仍存，但确立「后端为源、前端派生、测试守护」的**单一真相关系**。

## 3. 目标架构（定海 + 切割）

```
请求入口                 落盘决策（唯一写入入口：Content.put(rawBytes) / 内部统一 <alg>:<hex>(rawBytes) 去重；DB contentId 唯一约束 + 冲突回退）
─────────────         ────────────────────────────────────────────────
拖文件/网页图             → uploadFileToLocal → Content.put(字节)：算 hash 查重，命中复用既有 Content/url，未命中则 hash 命名落盘
剪贴板/URL 发送素材库      → sendToResourceLibrary → Content.put 去重 + 登记 resource(context{+projectId}) + rescan
画布拖入资源             → 复用既有 resource.contentId，节点存 contentId（不落盘）
生成结果/任务中心          → saveResultToTasks → 先经 Content.put 去重，无则落盘并登记 Ref
─────────────         ────────────────────────────────────────────────
Content 物理层          /files/<physBucket>/<<alg>:<hex>>.<ext>（physBucket 创建时锁定、不可变；context.folder 不进路径；零破链）；身份=<alg>:<hex>(decodedBytes)，无 context，全局唯一，GC 回收真源；**DB 对 contentId 列加唯一约束 + 冲突回退**（并发去重真保证）
后端 files.ts            writeUploadBuffer 改 <alg>:<hex>(buffer) 命名（仅决定初始文件名，与 saveRemoteUrl/base64 对齐）
后端 resources.ts        resources 表加 project_id + contentId=<alg>:<hex> 列（加唯一约束）；GET 接 ?projectId 过滤（去重是 Content 维度全局、Ref 是 per-project）
                         删除仍只删记录 → GC 回收（沿用 docs/13，不动删盘语义）
```

> **去重归因（本质解，非 A/A′ 补丁）**：本方案不再靠「查 contentId 列」或「跨目录预查」做去重——那些是维度压平后的补偿机制。真正的机制是**维度分离 + 唯一写入入口**：`Content` 维度身份 = `<alg>:<hex>(decodedBytes)`（无 context），一切产字节流（素材/任务/生成/缩略图/base64）必须经由 `Content.put(rawBytes)`（入参=已解码原始字节），入口内部统一算 `<alg>:<hex>(rawBytes)` 并查重；**并发去重的真保证是 DB 对 contentId 列加唯一约束 + 冲突回退复用**（应用层查重仅优化、防 TOCTOU 双落盘洞）。因 `contentId` 只看解码后字节、与 folder/url/name 完全无关，**跨入口（canvas/drop、web、migrated、tasks）与跨目录去重免费成立，且入口不可能自带 hash 上行**（杜绝 A′ 仍存的「三入口 hash 语义不一致」）。物理路径 `/files/<physBucket>/<contentId>` 中 physBucket 创建时锁定不可变、`context.folder` 不进路径，零破链；`contentId` 列是 Content 真源的索引投影（非新系统）。
> **Content 维度是概念层、非新表（铁律 5）**：物理文件即磁盘 `/files/...`，已由 `resources` 表 `contentId` 列经 `rescan` 1:1 映射（resources.ts:107）。所谓「Content 维度」是把「字节内容」从 resource 行的 context 字段中**概念剥离**为去重/GC 真源，避免造新抽象（铁律 5：仅一种实现，不引入 content 表/接口）；`project_id` 与 `folder`(UI分类)/`name` 作为 `context` 加在 resource 行（#2），物理位置由不可变的 `physBucket`+`contentId` 决定，Content 维度只保留 `contentId=<alg>:<hex>`。**GC 真源机制**：Content 维度的 GC 不靠物理扫描猜，而是定期反向扫描 resource/asset/task 等所有 Ref 持有的 `contentId`，无任何引用者即标记为孤儿 Content 并回收其物理文件。
> **存储后端是 Content 维度的实现选择（B 同为同源实现）**：物理布局 `/files/<physBucket>/<contentId>` 中 `physBucket` 是 Content 创建时锁定的不可变存储桶（默认沿用 canvas/drop、web、migrated 等现有桶，**零迁移、零破链**），`context.folder` 仅作 UI 分类、绝不进物理路径。对 Content 维度而言，无论 bucket 是多个（现状/A′）还是平铺为单一 `/files/_content/<contentId>`（B），都只是「contentId→字节」的映射，上层只认 `contentId`。因此 B 不是「另一套架构」、而是同一 Content 真源的可选存储后端；若日后做存储桶收敛，只需改 `Content.put` 的物理布局实现，Ref 层与 asset 引用零改动（铁律 6 级，需单独评估迁移成本，但属内部实现替换而非架构转折）。

**关键切割**：「新建文件（`Content.put(rawBytes)`）」与「引用文件」是两个动作，永远分离。引用方（asset / 脚本盒 / 任务中心）持有 `contentId`（文件型，稳定）或 `url`（内联 dataURL/blob，**互斥**），**不允许自己 writeFile**；`asset.data` 不再存「contentId + url 双字段指向同一文件」的冗余副本。渲染时 url 由不可变的 `physBucket`+`contentId`+ext 纯派生（`context.folder` 不参与），改名只动 UI 分类、永不破图。

> **铁律 2 · 边界 guard 落点**：资源删除后的「素材已移除」不是 UI 层 `try-catch` 兜底，而是**引用解析边界**的契约失效——`asset` 渲染持 `contentId` 经 `resource`（context 派生 url）解析时若查无此 resource（或 Content 已 GC），由该边界**显式抛出/返回缺失态**（fail-loud），UI 只负责呈现，绝不静默吞错破图。改名/移动只改 resource 的 `context`，`contentId` 不变故 asset 永不感知，**无需 `rewriteUrlReferences` 跨层改写 asset 引用**（这是维度正交的直接收益）。

### 7.1 project 级操作食谱（删除 / 导出）

本框架下 `project` 是 **Ref 层可见性边界**，绝不进物理路径；因此 project 级动作一律是「**先按 `projectId` 收口 Ref 行，再对 Content 做级联**」，不是目录遍历。

**① 删除 project 里的所有图片**
1. Ref 层：`DELETE FROM resources WHERE project_id = X AND type ∈ (图片类型)`；该 project 的画布快照 `canvas-state-v1-X` 删除时，其内部 `asset` 持有的 `contentId` 引用一并消失。
2. 级联到 Content：跑 `ReferenceGC`（§4 / docs/13），**反向扫描** resource/asset/task 的所有 `contentId`，对彻底无引用者才删物理文件 `/files/<physBucket>/<contentId>`。
3. 后果：被其他 project 也引用过的字节**保留**（dedup 的正确副作用）；「删项目」删的是引用关系，非字节归属。若确需连字节一起清空，只有 GC 判定为孤儿者会被回收。

**② 导出 project 里的所有图片**
1. `SELECT contentId, physBucket, context FROM resources WHERE project_id = X AND type ∈ (图片类型)` → 得到 `{ contentId, physBucket, folder, name, type }` 集合。
2. 对每个 `contentId`，用已持久化的 `physBucket` 解析物理文件 `/files/<physBucket>/<contentId>`（含 `ext`），连同 `context` 元数据打入包。
3. 接收端经 `Content.put(rawBytes)` 重新注册（自动 dedupe）重建 resource 行。
> 要点：**project 导出 = "该 project 引用了哪些 contentId" + "这些 contentId 对应的字节" 的逻辑投影**，而非「拷贝某个目录」。`physBucket` 已随行持久化，故无需内容注册表即可稳定解析（铁律 5）。

**physBucket 持久化归属（钉死）**：因 `contentId` 全局唯一、字节由某入口**首次创建**时落桶，physBucket 本质是 Content 属性；但为不引入新表（铁律 5·仅一种实现），将其作为**列落在 `resources` 表**——创建行写入、后续引用行照搬同值、**永不改**。多项目共享同一 `contentId` 时各 Ref 行冗余持有同一 physBucket，由不变量保证一致；GC / 导出解析时读任一持有该 contentId 的 resources 行即得，无歧义。

### 7.2 完整 project 导出 / 导入 往返保真

project 在本框架是 **Ref 层过滤条件**，故「导出 project X」= 导出**所有被 X 的 Ref 触及的东西**，是**逻辑投影、非目录拷贝**。

**导出 bundle 形状**
```
project-X-bundle/
  project.json            项目元数据（id / name / 设置）
  canvas-state-v1-X.json  画布（asset 节点：文件型持 contentId，内联持 url / 参数 / 位置）
  resources.json          [{ contentId, physBucket, context{ folder, name, type, ts, is_favorite } }]
  contents/<contentId>    每个被触及 contentId 的物理字节
```
**导出范围 = 「project X 的 resources + assets 可达的所有 contentId」**，按 contentId 可达性收集，**不按文件夹、不按 physBucket**（盲区①：originally 由他项目创建、被 X 共享的字节也一并带走）。

**导入往返为何无损**
- `contentId = <alg>:<hex>(rawBytes)` 确定性 → 导入对每个字节重跑 `Content.put` 得**同一 contentId** → asset 引用的 `contentId` **无需重新接线**直接命中（根因消除）。
- `context` 原样恢复 → 素材库 folder/name/is_favorite/排序一致；canvas JSON 恢复布局与参数 → 感觉即原项目。

**4 个盲区钉死口径**
1. 导出范围按 contentId 可达性（见上），绝不按文件夹。
2. **projectId 恢复语义（导入时显式二选一，必须定死）**：
   - `restore`（同 id 恢复）：目标无同 id 项目时直接用原 projectId 落库 → 完全等同原项目（备份/换机迁移）；若已存在同 id，冲突报错或自动改名。
   - `clone`（克隆新 id）：生成新 projectId，canvas-state / resource 的 projectId 全部改写 → 内容一致、身份不同（复制一份）。
   - 默认 `restore`，冲突时 fallback `clone`。
3. **physBucket 换机导入可能变桶**（原 `canvas/drop` → 导入走 `imported`）：功能无影响（渲染按新 physBucket 解析 url），仅磁盘布局与原项目不同，可见无害。
4. **远程 / 内联 url 资产兜底**：asset 持 `{url}`（远程未下载图 / dataURL）随 canvas JSON 带走；导入后若远程 404 → 触发 Phase 3 fail-loud「素材缺失」态，不可静默破图；dataURL 自包含无此问题。

> **已知边界（Phase 3，不阻断本期收敛）**——框架已自洽，以下为跨进程/跨设备的延伸问题，需单独评估、不在本期架构口径内：
> - **跨设备 contentId 解析**：`asset.data` 只持 `contentId`，字节在本地磁盘；canvas-state 跨设备同步/导入导出时，目标设备若无该字节，引用解析边界须 fail-loud 并触发 Content 随项目打包/拉取（或显式「素材缺失」态），不可静默破图。属 Phase 3 协作分发范畴。
> - **存量迁移回填口径**：老 `saveRemoteUrl`(按 URL hash)/`saveBase64ToFile`(按 base64 hash) 的存量 `sha1` 与新增「按解码字节算 `<alg>:<hex>`」对不上——迁移回填时**存量必须重算解码字节哈希**，否则存量去重失效、且无法与新增复用。回填脚本须统一走 `Content.put(rawBytes)` 重入，禁止沿用旧 URL/base64 哈希。
