## 二、一句话结论

**编辑器与写回链路全是对的；错的是「画布快照是最后写者赢、且写者带自己内存里的整包节点」。**

只要同一项目**同时存在两个应用实例**（哪怕只是「开发端口 `localhost:5180` 的标签页」+「打包版 / `127.0.0.1:18080` 内置页面」），
后开实例做裁剪/扩图保存后，先开实例**只要发生任意一次画布变更（连平移视窗都算）**，就会把自己内存里的**旧图整包写回 KV**，
抹掉刚保存的裁剪/扩图结果。刷新后节点当然显示原图。

## 三、证据链（三组真机复现，全部可重复）

排查手段：Playwright 驱动真实应用 + 三路埋点
① 覆写 `HTMLCanvasElement.prototype.toDataURL` 记每次出图尺寸；
② 拦截 `POST /api/kv/set` **请求体**，直接看写进去的 `imageUrl`；
③ 直读后端 KV（`/api/kv/get`、`/api/admin/kv-list`）。

### 3.1 先证明「编辑器 + 写回 + 落盘」都是对的

| 观察 | 证据 |
|---|---|
| 编辑器出图正确 | 裁剪不拖拽 → `{w:320,h:240}`（400×300 的 80%）；扩图 1:1 → `{w:400,h:400}`；涂鸦 → `{w:400,h:300}` |
| 真机裁剪出图正确 | 编辑器报 `选区 960 × 717`，`toDataURL {w:960,h:717}` |
| 写回当场生效 | 保存后节点 `<img>` 立刻变 `data:image/png;base64,...`，自然尺寸 = 新尺寸 |
| 写进 KV 的内容是对的 | `[kv/set] body=1163138 img=DATA(1156822)`（是**新图**，不是旧 URL） |
| 后端把内联 base64 外置成文件 | 快照 6.3KB、`imageUrl = http://127.0.0.1:18080/files/canvas/<sha1_16>.png`（`base64Externalize.ts`，内容取哈希、幂等） |
| **单窗口全链路正常** | 裁剪保存 → 再平移画布 → 写进去的仍是新图；刷新后节点 ≈ 新图（`__probe/self-stale.mjs`） |

> 结论：**「保存不生效」不能怪编辑器**。单实例下无论是裁剪、扩图还是涂鸦，全链路都成立。

### 3.2 双实例（同源）→ 旧实例覆盖新结果


## 四、代码层为什么必然发生

### 4.1 快照是「整包 + 最后写者赢」

- 唯一写入者：`App.persistCanvas` → `saveCanvasState(projectId, nodesRef.current, edgesRef.current, viewport)`（`App.tsx:405`）。
- 触发点：① `nodes/edges` 变化后 **600ms 防抖**；② **视窗移动结束**（`handleViewportMoveEnd`，`App.tsx:440`）——**所以「只是平移一下画布」就够整包覆盖别人**。
- 写入内容 = 本实例 `nodesRef` 里的**整包节点**，没有字段级/节点级合并 → 谁旧谁就把别人写回去。

### 4.2 现有「防旧覆盖新」实际不成立

`projectStore.saveCanvasState`：

```ts
const version = now > lastSavedVersion ? now : lastSavedVersion + 1; // now = Date.now()（本实例）
const remoteVer = ...;                                                // 读 <key>_version
if (remoteVer > version) { /* 拒绝覆盖 */ }
```

两个实例各自用 `Date.now()` 当版本号，**后写的一定更大** → 旧实例的覆盖永远通过。
它防的是「同毫秒/时钟回拨」，**防不住「内容陈旧」**（真正要的是 compare-and-swap：写入前要求远端版本 == 我加载时的版本）。

### 4.3 冲突提示只在「同源 + 同浏览器 profile」有效

- `useCanvasSync` 用 `BroadcastChannel('yimao_canvas_sync')`，只置一个 `canvasConflict` 标志；
- `App.tsx:1459` 的红条文案其实就是本 bug 的自白：
  「检测到该画布在其他窗口被修改，继续保存可能会覆盖数据，强烈建议点击此处刷新页面！」
- 但 BroadcastChannel **不跨 origin、不跨浏览器、不跨打包进程**：
  `localhost:5180`（开发）↔ `127.0.0.1:18080`（打包版/内置页面）→ **红条恒不出现**（3.3 已实测 `false`），用户完全无感。

### 4.4 「涂鸦好、裁剪扩图坏」：**尚未定位，推断已撤回**

曾提出一条现象层推断（"80% 居中裁剪 + `object-cover` 看起来像原图 / 扩图原比例+0% 输出即原图"），
**已被用户明确否决**：图片有没有变用户自己看得出来，这不是解释。

现状如实记录：
- **单实例下裁剪/扩图链路已被证明正确**（§3.1：出图尺寸、写回、外部化、刷新读回全对）；
- 因此"单实例下裁剪/扩图没生效"的**真实根因仍未定位**，需要现场证据（见 §5）；
- 已知确定成立的是**多实例互相覆盖**（§3.2/3.3）——它对三个 Tab 一视同仁，不解释涂鸦/裁剪的差异。

> 处置：不再对现象做推测性解释；改为**把机制做扎实 + 补齐可观测**（见 `118`：服务端 CAS + 冲突跨源可见 + 写入审计日志），
> 让下一次复发的现场直接落在日志里（是"被 409 拒了"、"写了但刷新没读到"，还是"压根没触发保存"）。

## 六、修复方向（建议，待拍板）

按「治本 → 加固 → 体验」排序：

1. **★ 快照写入改成 compare-and-swap（治本）**
   `loadCanvasState` 时记下 `<key>_version`（loadedVersion）；`saveCanvasState` 写入前要求 `remoteVer === loadedVersion`，不等则**拒绝写入**并置冲突态。
   → 旧实例不再能覆盖新数据；代价是旧实例自己也不再落盘，必须提示用户刷新（这正是红条想做的事）。
2. **冲突检测搬到服务端（跨源也安全）**
   轮询 `<key>_version`（或复用已有轮询）→ 远端版本 > 本地 loadedVersion 即置 `canvasConflict`。
   → 打包版 / 开发口 / 不同浏览器 / 多设备都能被提示，不再依赖 BroadcastChannel。
3. **编辑器保存出口统一「先落盘再写回」（顺带解掉体积与二次写冲突）**
   现在 `handleEditorSave` 直接把 dataURL 塞进 `node.data.imageUrl`（快照里多一个 MB 级字段，靠后端外置兜底）；
   压缩/放大已经走 `saveInlineToLocal(dataUrl,'canvas')` 换成 `/files/` 持久 URL —— **裁剪/扩图/涂鸦应走同一条**，快照里只留 KB 级路径。
4. **（可选）按节点粒度做版本/时间戳合并**，把「整包最后写者赢」降级为「逐节点较新胜」，可以进一步减少多实例场景的损失面。

> 3 是低风险小改且立刻减少损失面；1+2 才是真正堵住「静默抹掉别人编辑」。建议 3 先上，1+2 一起做。

## 八、顺带发现的独立小 bug（与本问题无关，建议一并修）

`ImageGenerate.tsx`：`setAspectRatio('Auto')` 在比例本来就是 `'Auto'` 时不被 React 认作变更 → `[aspectRatio]` effect 不跑 → `editedRatioRef.current` **残留为 `true` 永不被消费** → 用户之后**第一次**切换比例时 `fitByRatio` 会被跳过一次（节点框当次不跟随）。
修法：`setImageUrl` 之后直接 `editedRatioRef` 用「一次性消费函数」或把消费点搬到 `img.onLoad` 里，不依赖 `aspectRatio` 是否真的变化。
