# 生成链路止血 · 小步可执行施工文档（2026-09-02）

> **目标**：不是把生成链路重写，而是用**最小关键路径**把系统稳住——前端锁死 `taskStore`（任务中心独占轮询/落盘/完成），后端锁死 `saveRemoteUrl`（唯一下载归属点）。小步走、每步独立验证、可停在任意一步、可独立回滚。
> **原则**：**一次只做一小步，每步能通过门禁 + 真机验证才算完，做不完安全停住，不带着半成品往前走。**
> **不覆盖**：relay-kit 重构（execution-plan）**整体冻结**，与本文主线撞车（都要动 `proxyGenerate/pollTask`），系统稳住前不评估。80号文档 §十一（localTool 独占轮询）属更远期，本文不做。

## 一、主线总览（四小步，每步独立 commit / 独立验证 / 独立回滚）

```
S1（后端，先动）  files.ts saveRemoteUrl 加 in-flight 并发去重
    ↓  独立验证：双 POST 只下一次载
S2（前端）        taskStore.ts 加轮询注册表 ensurePolling，收口双轮询
    ↓  独立验证：单次生图日志查询数不再翻倍、[恢复轮询] 消失
S3（前端）        删 PromptNode 二次落盘，落盘唯一出口 = useNodeGeneration
    ↓  独立验证：/api/files/upload 恰好 1 次
S4（前端，可做可不做）done() 改任务中心落盘（撤销 P0-C）——契约变更，需单独评估
```

> **依赖关系**：S1 → S2 → S3 是**一条因果主线**（S2 减少轮询挤压后，S1 的下载预算才真正够用；S3 消掉双落盘后，S1 的并发锁才不是空转兜底）。**每步必须在下一步前独立通过验收。**
> **S4 与 S1/S2/S3 独立**：它改 `done()` 契约、碰所有调用方，风险最高，放最后且**可选**——前三步做完系统已稳住，S4 更多是"彻底消除 P0-C 的历史妥协"，可评估后再定。

## 二、S1 —— 后端 `saveRemoteUrl` 加 in-flight 并发去重

### 为什么是第一步
收益/成本比最高：不改任何契约、不动前端、不改 `saveRemoteUrl` 的对外行为。立刻让"双落盘并发穿透幂等"失效——两个并发 `POST` 只真下载一次，第二个拿到第一个的结果。**这是稳住"下载超时"的第一刀，且是唯一能在不改前端的前提下独立见效的后端改动。**

### 改动点
文件：`localTool/src/routes/files.ts` 的 `saveRemoteUrl`（L142）。

```ts
// 进程内 in-flight 下载去重：Map<fileUrl, Promise>。
// 并发到达的同一远程 URL → 第二个不重复下载，await 第一个的 Promise 拿结果。
// 场景：前端双落盘(useNodeGeneration + PromptNode.onSuccess)发的两个并发 POST 会穿透
//       existsSync 判重（下载完成前双方都判 false）→ 都真下载。本 Map 从根上堵住。
//       fs.existsSync 幂等只防"顺序重复到达"，防不住"并发到达"，必须这层进程内锁。
// 取舍：promise 完成后从 Map 删除（不常驻，靠 sha1 文件幂等兜住更后面的重复到达）。
const inflightDownloads = new Map<string, Promise<{ url: string; path: string; thumbnailUrl?: string }>>()

async function saveRemoteUrl(subfolder: string, fileUrl: string, filename?: string): Promise<{ url: string; path: string; thumbnailUrl?: string }> {
  // 去重键：同一 URL 是否同一份，由 subfolder+fileUrl 决定；filename 不入键——
  // 双落盘两次调用 filename 相同(都 safeName('generated'))，但 URL 才是"同一内容"的判据。
  const dedupeKey = `${subfolder}\u0000${fileUrl}`
  const existing = inflightDownloads.get(dedupeKey)
  if (existing) return existing // 已有同一 URL 在下载中 → 复用其结果，不重复下

  const p = doSaveRemoteUrl(subfolder, fileUrl, filename)
  inflightDownloads.set(dedupeKey, p)
  try {
    return await p
  } finally {
    inflightDownloads.delete(dedupeKey) // 完成后移除，后续重复到达靠 existsSync 文件幂等
  }
}

// 【原 saveRemoteUrl 体改名成 doSaveRemoteUrl】—— 内容逐字不变，只加下面这段并发锁。
async function doSaveRemoteUrl(subfolder, fileUrl, filename) { /* ...原 L142-196 全量逻辑... */ }
```

### 注意点
- `saveRemoteUrl` 是 `files.ts` 内部函数，`handleUploadFormData`/`handleUploadJson` 都经它 → 只有一个入口，加锁无遗漏。
- **不改** `fetchWithProxy` 内部（P2-3 下载 abort 属另一件事，不在本步）。
- 失败时（`throw`）也要在 `finally` 里 `delete`，避免失败后死锁同 URL 后续请求。
- 缩略图生成(`tryGenerateThumbnail`)在 doSaveRemoteUrl 里，两并发共享同一 do 的结果，天然只生成一次。

### 验收
1. 门禁：`cd localTool && npm test` 全绿；`npm run build` 通过。
2. 真机：开 debug，单次生图（image async 模式）→ localTool 控制台 `[download]` 只出现 **1 次 OK**（不再 2 次）。
3. 强制并发验证：临时用脚本对同一 fileUrl 并发发 2 个 `POST /api/files/upload` → 日志 1 OK + 1 SKIP 或共享结果，**磁盘只有一份**。

### 回滚
单文件 `git revert`（仅 files.ts）。

## 三、S2 —— 前端 `taskStore.ts` 加轮询注册表，收口双轮询

### 为什么第二步
S1 消了"下载翻倍"，但**双轮询还在** → localTool 进程仍被轮询风暴挤压，S1 省下的下载预算仍可能被吃穿。S2 让"轮询权"归位到任务中心，从构造上消灭双轮询，是根治"恢复轮询刷屏 + 挤压下载"的关键。**纯前端、不动契约、不动后端。**

### 改动点
文件：`src/components/base/taskStore.ts`（新增）+ `proxyGenerate.ts`（调用方）+ `pollTask.ts`（删除主体）+ `App.tsx`（换入口）。

**taskStore.ts 新增轮询注册表**（与 `done/fail` 同层，放 store 内部）：
```ts
// ── 轮询器注册表（运行时，不持久化）──
// 核心：一个 taskId 在 Map 里只可能有一个 entry → 双重轮询在构造上不可能。
// 所有轮询(生成流程 + 启动恢复)都汇聚到 ensurePolling，不再有两套 while/setInterval。
export interface PollerHandle { promise: Promise<void>; stop: () => void }

const pollers = new Map<string, PollerHandle>() // taskId -> 句柄

/** 唯一轮询入口：taskId 已有 poller 则直接返回(不重复起)；否则按参数起一个轮询到终态。 */

  pollFn: () => Promise<void>;   // 单轮查询实现(从网关取状态并 patchTask + 终态 publish)
  intervalMs?: number;
}): void {
  if (pollers.has(taskId)) return  // 已有 poller → 双重轮询不可能发生
  const handle = { ... }
  pollers.set(taskId, handle)
  // ...定时调 pollFn，直到其返回"已达终态"或 stop() 被调，finally 里 pollers.delete(taskId)
}
```

**proxyGenerate.ts**：`pollUntilDone`(L180) 的 `while` 循环删掉，改为——提交拿 `taskId` 后调 `setTaskPollId` + 让任务的轮询改由 taskStore 的注册表驱动，自身不再起第二套循环。`imageApi`/`videoApi` 的 `onProgress` 通过 taskStore 的回调继续推。

**pollTask.ts**：删除 `runRound`/`pollOneTask`/`initTaskRecovery` 主体，只保留一个"启动扫描"函数：找出所有 `running/pending && pollTaskId` 的任务，逐个调 `ensurePolling`（与生成流程**同一个入口**）。

**App.tsx**：L489 `initTaskRecovery` 改为调新的启动扫描入口。

### 验收
1. 门禁：`npm test` + `npm run build` + `npm run check:events`（`publishTaskCompleted` 发布点收敛需同步 `contracts.ts EVENTS.from`）+ `npm run check:api`。
2. 真机（开 debug）：单次 async 生图，控制台里 `v1/tasks` + `gateway/task` 的**总查询数 ≈ 耗时/间隔**（不再两套叠加翻倍）；**`[恢复轮询]` 标签消失**。
3. 刷新回归：生成中刷新页面 → 任务继续跑 → 完成后节点与任务中心都显示 `/files/tasks/...`（非外链）。

### 回滚
P0-1(纯新增注册表) 单独 commit 可先落地观察；P0-2/P0-3 各自独立 commit，`git revert` 单阶段。

> **风险提示**：本步是前端最大的一刀，把轮询主体从 `proxyGenerate` 迁到 taskStore，需对齐 `imageApi`/`videoApi` 行为。若担心，可先只落 taskStore 的注册表(P0-1)，不切调用方，观察构建与测试；确认后再切 P0-2/P0-3。

## 四、S3 —— 删 `PromptNode` 二次落盘，落盘唯一出口

### 为什么第三步
S2 让轮询归位，但**双落盘仍在**（`useNodeGeneration.ts:245` + `PromptNode.tsx:303`）。S1 的后端并发锁此时已成"兜底"，但**结构上仍应让前端只落一次**——否则每次生成仍发两个请求、S1 的锁永远在兜底空转。S3 把落盘出口唯一化。

### 改动点
- `src/components/nodes/PromptNode.tsx`：`onSuccess`(L297) 里删掉 `saveResultToTasks` 的二次落盘(L302-309)，只保留 `setImageUrl(r.url)` + `setImgPrefs`。持久化回写交给 `resultKey:'imageUrl'` + `recoverable:true`（hook 内自动 patchData + 收 task-completed 回填），以及任务中心落盘。
- **关键前提**：删 PromptNode 的落盘前，必须确认 `useNodeGeneration.ts:245` 的主落盘**已能覆盖 PromptNode 的场景**——即上游返回外链/临时地址时，主落盘 `saveResultToTasks` 会把它落成持久 URL 并经 `resultField` 回写节点。核对 `PromptNode` 用的 hook 是否走 `useGenerateNode`（它内部就是 `useNodeGeneration`，L245 主落盘已兜住）。
- 若确认 `useGenerateNode` 已含主落盘 → PromptNode 的二次落盘是纯冗余补丁，可删。

### 验收
1. 门禁：`npm test` + `npm run build` + `npm run check:api` + `npm run check:events`。
2. 真机：单次 async 生图，日志 `POST /api/files/upload` **恰好 1 次**。
3. 刷新回归：完成刷新后节点图仍在（持久 URL 已回写 node.data）。

### 回滚
单文件 `git revert`（PromptNode.tsx）。

> ⚠️ **删之前务必先核对 `PromptNode` 是否还有别的路径需要自己落盘**（如参考图 `refUrls` 本地化、`useConnectedInputs` 等）。若某子路径只靠 PromptNode 落盘，需先迁到统一出口再删，**不能删完才发现能力丢**——这与 relay 文档 §5.0.5 的"能力零退化"同理。

## 五、S4（可选、最末）—— `done()` 改任务中心落盘（撤销 P0-C）

### 为什么可选
S1~S3 做完，前端只落一次、只轮询一次、下载不翻倍，系统已稳。S4 是把 `taskStore.done` 从"接收已落盘 URL"改回"接收原始 URL、任务中心内部落盘"（撤销 P0-C 契约）。它让"落盘权"真正归任务中心，**消除"乐观写外链 → 再落盘回写"的历史妥协**。但它是**契约变更**：`done(resultUrl)` 的语义变了，影响所有调用方，风险最高。

### 改动点
- `taskStore.ts done()`：接收 `rawUrl` → 内部调 `saveResultToTasks` → 拿持久 URL → 回填任务 + publish。
- `useNodeGeneration.ts`：删主落盘处 `saveResultToTasks`(L245)，直接 `taskCtl.done(rawUrl)`。
- 其他 `done()` 调用方（`scriptBoxEngine.ts` 等）一并核对：文本类(done 空/无URL)不适用，保持不落盘。

### 为什么放最后且要单独确认
1. 改契约 → 影响面大，需先列出全部 `done()` 调用方清单，逐个核对"传进来的是原始 URL 还是已持久 URL"。
2. S1 的后端并发锁、S3 的前端唯一落盘，已让"落盘"这条线稳了；S4 只是把落盘的**归属**从 `useNodeGeneration` 挪到 `taskStore`。若评估认为当前结构可接受，**可不做 S4**——不是缺陷，是取舍。

### 验收
同 S3，且加一条：**调用方全部改完后**，再验证节点显示、任务中心、刷新恢复三项回归。

## 七、节奏纪律（为什么这样不会翻车）

1. **每步独立 commit、独立验证**：任何一步做完即是一个可交付的稳定点，可安全停住等下次继续。
2. **验证靠真机日志，不靠"看起来对"**：下载次数、轮询次数、刷新恢复是硬指标（见各步验收），日志能直接数。
3. **每步改动面最小**：S1 只动一个函数加锁；S2 分 P0-1/2/3 三段提交；S3 只删一个 onSuccess 里的冗余；S4 明确可选。
4. **不并线**：relay-kit 重构冻结。若未来要上，也是在这条主线全部稳定、确认方向后再单独立项。
5. **失败可回滚**：每步单文件/单模块，`git revert` 即回，不带出半成品。
