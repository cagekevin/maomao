## 〇、一句话结论（与早期判断的修正）

| 早期判断（错误） | 实测事实（2026-09-14） |
| --- | --- |
| cutia 导出用 FFmpeg.wasm，你用 WebCodecs/mediabunny，路线相反 | cutia 主导出路径 `SceneExporter` 用的是 **`mediabunny`**（`CanvasSource`/`Output`/`Mp4OutputFormat`/`AudioBufferSource`），**与你 `videoEngine.ts` 同库**。`@ffmpeg/*` 在 `package.json` 里是依赖但**全 `src` 零引用**，属死重 |

## 二、cutia 编辑器内核解剖（纯 TS，可搬运）

### 2.1 EditorCore 单例 + 10 个 Manager（外部 store 模式）

`core/index.ts`：

```ts
export class EditorCore {
  static getInstance(): EditorCore { /* 单例 */ }
  public readonly command: CommandManager;
  public readonly playback: PlaybackManager;
  public readonly timeline: TimelineManager;
  public readonly scenes: ScenesManager;
  public readonly project: ProjectManager;
  public readonly media: MediaManager;
  public readonly renderer: RendererManager;
  public readonly save: SaveManager;
  public readonly audio: AudioManager;
  public readonly selection: SelectionManager;
}
```

每个 manager 自己维护 `listeners: Set<() => void>` + `subscribe/notify`（**外部 store 模式**，不是 Zustand）。组件通过 `useEditor()` 订阅：

`hooks/use-editor.ts`：

```ts
export function useEditor(): EditorCore {
  const editor = useMemo(() => EditorCore.getInstance(), []);
  // useSyncExternalStore 订阅 playback/timeline/scenes/project/media/renderer/selection 七个 manager
  return editor;
}
```

**关键**：UI 只是 `EditorCore` 的薄视图层。所有轨/片段/工程/素材状态都在 manager 里，组件只读 + 调 manager 方法。这与你 `120 §二` 的"数据编排四层 + 纯函数 timelineOps"是**同一种架构哲学**，只是实现手法不同（cutia 用命令模式 `CommandManager` + 外部 store；你用 `useReducer` + 纯函数）。

### 2.2 TimelineManager（薄命令分发器）

`core/managers/timeline-manager.ts`：每个 mutation 都包成 `Command`（`AddTrackCommand`/`InsertElementCommand`/`SplitElementsCommand`/`MoveElementCommand`/`ToggleTrackMuteCommand`…）经 `editor.command.execute` 执行，历史栈内建。`getTracks()` 实际从 `editor.scenes.getActiveScene()?.tracks` 读——**数据真源在 `ScenesManager`**。

### 2.3 数据模型形状（与你的差异点）

- cutia：`TProject { scenes: TScene[], currentSceneId, settings, ... }`，`TScene { tracks: TimelineTrack[], ... }`，元素类型 `VideoElement/ImageElement/UploadAudioElement/StickerElement/TextElement`，靠 `mediaId` 关联素材。
- 你的 `120`：`tracks` 直接挂在工程记录上，**无 scene 概念**（C2.6 明确"多序列永不"）。
- **对接**：cutia 的 `ScenesManager` 总是保证一个 `main scene`（`getMainScene`/`ensureMainScene`），你只需永远只用 main scene，忽略多场景能力即可。属"能力多给你、你不用"类差异，不是冲突。

### 2.4 这层（core+managers+commands+renderer+services/storage）全仓零 `next/` 依赖

实测：`core/`、`services/`、`lib/` 三个目录搜 `from "next/` → **0 命中**。证明编辑内核与 Next.js 解耦，可整体 import 进 Vite/任意 React 工程。

## 三、逐项耦合实测（哪些真障碍、哪些不是）

### 3.1 后端 / 数据持久化 —— **不是障碍**

`services/storage/service.ts`：`StorageService` 用 `IndexedDBAdapter`（工程元数据 + 素材元数据）和 `OPFSAdapter`（素材文件本体）。**全浏览器原生，无任何 fetch 到自有服务器、无 R2**。早期我提到的 `lib/r2/upload.ts` 是部署/landing 用的辅助，**编辑主链路不碰它**。

→ 你之前的判断"后端用我自己的替代"成立，且比想象更简单：**此版 cutia 根本没后端**，文件存 OPFS、工程存 IndexedDB。

### 3.2 导出引擎 —— **不是障碍，反而一致（重大翻转）**

`services/renderer/scene-exporter.ts`：

```ts
import { Output, Mp4OutputFormat, WebMOutputFormat, BufferTarget,
         CanvasSource, AudioBufferSource, QUALITY_* } from "mediabunny";
```

`RendererManager.exportProject` → `SceneExporter.export({ rootNode: scene })` → 返回 `ExportResult { success, buffer: ArrayBuffer }`。走的是 `CanvasSource` 逐帧合成 + mediabunny 封装输出，**与你 `base/utils/videoEngine.ts` 同库**。

搜 `@ffmpeg` 全 `src` → **0 命中**。依赖里 `@ffmpeg/ffmpeg`/`@ffmpeg/core`/`@ffmpeg/util` 存在但未在编辑器代码中使用（疑似历史残留或某 deploy helper）。**结论：无 FFmpeg 冲突，导出引擎与你一致。**

> ⚠️ 但注意版本差：cutia `package.json` 是 `mediabunny: ^1.29.1`；你钉死 `1.54.0`。两者共用 `CanvasSource`/`Output` 这类**高层 API**（相对稳定），但你 `videoEngine.ts` 用的是 `EncodedPacketSink`/`EncodedVideoPacketSource` 这类**低层 packet API**（1.54 才有）。若搬 cutia 的 `SceneExporter`，它用高层 API，与你现有低层无损导出是**两条不同路径**，可并存，但需统一维护面。

### 3.3 Next.js 壳 —— **是障碍，但只在"壳"层，你不需要它**

`next/` 真实出现在：
- `app/`（路由、`middleware.ts`、`api/*`）——整站，你不要
- `components/editor/panels/assets/views/media.tsx`：`next/image` + `@i18next-toolkit/nextjs-approuter` 的 `useTranslation`
- `lib/navigation.ts`、`middleware.ts`、`i18n.config.ts`

编辑内核（core/managers/services/renderer/lib/commands/lib/timeline）**不 import 任何 next**。

→ 你要搬的是内核 + 组件；组件里的 `next/image`→`<img>`、`@i18next-toolkit`→你的 i18n 或直写中文（`120 §五` 你本就决定编辑器直写中文），都是**机械能换**。

### 3.4 auth / 登录 —— **不是障碍（编辑器不依赖）**

`components/editor/` 搜 `@/lib/auth` / `useSession` / `better-auth` → **0 命中**。编辑器组件完全不碰 auth。`lib/auth/server.ts`（带 `next/server`）只在 landing/API 侧。README 说 auth 是 optional，实测成立：**编辑器可纯前端裸跑**。

### 3.5 i18n —— **机械能换**

全组件用 `useTranslation()` + `t(...)`（`@i18next-toolkit/nextjs-approuter`）。换你是两件机械事：要么保留 i18next（去掉 nextjs-approuter 适配器，用原生 i18next）、要么按 `120 §五` 直写中文。工作量大但无架构风险。

### 3.6 UI 原语 / 图标 —— **机械能换**

- `components/ui/*`：shadcn 式 Radix 封装（`button`/`dialog`/`tooltip`/`context-menu`/`dropdown-menu`/`input`）。搬时需带这些或换成你的。
- 图标：`@hugeicons/react` + `@hugeicons/core-free-icons`；你用 `lucide-react`（`120 §五` 已定）。逐图标替换。
- 样式：`tailwind` + `cn()`（clsx+tailwind-merge），与你的工程一致。

### 3.7 Zustand —— **不是障碍**

`stores/*` 是 Zustand，但只放 **UI 状态**（agent-store / assets-panel-store / media-preview-store / keybindings）。**时间轴数据不在 Zustand**（在 EditorCore managers）。Zustand 框架无关，Vite 里照跑。你可保留，或把 UI 状态并入你的 store 体系。

## 四、素材入口桥（画布节点 → cutia）—— **cutia 已有现成钩子**

`components/editor/panels/assets/views/media.tsx` 的入轨流程：

1. 文件选择：`useFileUpload` → `processMediaAssets({files})` → 产出 `MediaAsset { file: File, url, type, name, duration, width, height, thumbnailUrl }`
2. URL 导入：`fetchRemoteMediaAsFile({ url })`（`@/lib/media/url-import`）→ 远程 URL **fetch 成 File** → 走同一条 `processFiles`
3. `editor.media.addMediaAsset({ projectId, asset })` → `MediaManager` → `storageService.saveMediaAsset`（写 OPFS + IndexedDB）
4. 拖/点到时间轴：`editor.timeline.insertElement({ element, placement:{mode:"auto"} })`，element 由 `buildVideoElement/buildImageElement/buildUploadAudioElement({ mediaId })` 造

**→ 你的画布节点 URL（`/files/canvas/...`）对接 cutia = 它的 "From URL" 路径**：直接复用 `fetchRemoteMediaAsFile` 把画布 URL fetch 成 File，再走 3–4。或者更省事：改 `MediaManager.addMediaAsset` 接受"URL-only 资产"（不存 OPFS，直接 `url` + `thumbnailUrl`），因为你素材本就在 `localTool /files/` 已落盘、无需再存一份 OPFS。

**对应你 `120` 的 C11（点选即入轨）**：你的"在画布点选节点 → 落轨尾"只需在节点 click handler 里调 `editor.media.addMediaAsset` + `editor.timeline.insertElement`，比 cutia 的拖拽/面板入口更简单。

## 五、出片桥（cutia 导出 → 你的画布节点）—— **改一个文件**

`components/editor/export-button.tsx`：

```ts
const result = await editor.project.export({ options }); // → ExportResult { buffer }
const url = URL.createObjectURL(blob);                    // 当前：下载到本地
// 你的桥：把 buffer/blob 落盘并回写画布节点
```

导出结果是一个 `ArrayBuffer`/`Blob`。**唯一消费点就是 `export-button.tsx`**。

→ 你只需把这段替换成：`uploadFileToLocal(blob, UPLOAD_DIRS.videoEditor, name)` 拿 `/files/` URL，再 `deriveNodes.spawnAndCommit` 生成新视频节点（对应你 `120` C4.1 "导出新建节点不覆盖源" + C4.8 节点 data 契约）。约 10 行改动，**无架构风险**。

## 六、持久化桥（IndexedDB/OPFS → 你的 contentStore）—— **政策选择，非技术阻塞**

cutia 的 `storageService` 是浏览器原生 IndexedDB + OPFS，**在 Vite 里能原样跑**。所以技术上你可以：
- **方案 A（最小改动）**：直接保留 cutia 的 `storageService`，工程存 IndexedDB、素材存 OPFS。编辑完全自洽。代价：违反你 `120` 红线"唯一存储通道 = contentStore"（`STORAGE_KEYS` 登记）。
- **方案 B（守你的红线）**：把 `storageService` 的 `IndexedDBAdapter`/`OPFSAdapter` 换成你的 `contentStore` + `localTool /files/`。`getProjectMediaAdapters` 那两处适配器是干净的接口边界，替换成本低。

→ 这是**政策决策**（守不守 contentStore 红线），不是技术难点。若你接受 cutia 自带存储，桥几乎为零。

## 九、风险与未决项

1. **mediabunny 版本差（1.29 vs 你 1.54）**：搬 `SceneExporter` 用高层 API 应兼容，但需实跑回归。你已钉 `1.54.0`（D4 债），若引入 cutia 的 `SceneExporter` 可能想统一到 1.54——需验证高层 API 在 1.54 签名未变。
2. **单例 vs 多实例**：`EditorCore.getInstance()` 是进程级单例。你若同一页面多个剪辑上下文（多 project 切换）靠 `loadProject` 切换状态，需确认切换时无残留（cutia 的 `closeProject` 会 `clearAllAssets`+`clearScenes`，基本干净）。
3. **UI 壳机械替换量**：`next/image` + `@i18next-toolkit` + `@hugeicons` + Radix 在组件里散布广，机械但费时。建议只搬 `timeline/` + `preview/` + `export-button`，其余面板（assets/properties）用你自己的。
4. **CSS/设计 token**：cutia 用自己 tailwind token（`bg-accent/30` 等），与你 `tailwind.config.ts` 语义 token 需对齐类名或改 config。
5. **场景概念压平**：cutia 多 scene，你单 timeline，适配层需固定 main scene。

## 十、推荐路径（三选一，给你拍板）

- **路径 A（推荐·省最多）**：搬 cutia 的 `core+managers+commands+renderer+storage` 内核作为你 `videoEditor/core` 引擎（直接替代你 G0–G5 自建的 `core/`），UI 层只搬 `timeline/`+`preview/`+`export-button` 并去 next/i18n/图标，写三座桥。保留你画布联动（入轨/出片/对账）。**最大省时，代价是放弃你已建 core（但 cutia 的更完整）**。
- **路径 B（最稳·局部借）**：不搬内核，只把你 `120` G5 遗留项（走带出声/多选框选/右键集/工程参数）对照 cutia 的 `timeline/` 实现抄到你的 `videoEditor/`。**最小风险，但省时有限**。
- **路径 C（独立全屏）**：直接用 cutia 当主编辑器，放弃画布联动（你 `120` 形态定稿的反面）。**不推荐**，除非你改主意要纯剪辑 App。

> 我的判断：你已建到 G5 的 `core/` 与 cutia 内核**高度同质**，继续自写 = 重复造一个 cutia 已经验证的轮子。**路径 A 最值**，且因为导出引擎同库、素材有 URL 钩子、持久化是浏览器原生，实际阻力远小于两轮前我说的。要不要我下一步**实测跑通"路径 A 的最小骨架"**——把 `core/managers` + `SceneExporter` 在 Vite 里 import 起来，验证零 next 依赖、导出能出 buffer？这样能把"能搬"变成"跑通"。
