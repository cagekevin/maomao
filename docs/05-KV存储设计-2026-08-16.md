# 05 专题：KV 存储设计（localTool SQLite 键值存储）

> 日期：2026-08-16
> 本文梳理项目 **KV 存储** 的现状设计（已实现）、当前实际用到的键、排查发现的脏数据，以及**后续还需要用到 KV 的场景**。
> 核心：KV 是 localTool 的跨端共享键值存储，**区别于浏览器 localStorage**；两者靠 key 前缀自动分流（`kvStore.js`）。

---

## 〇、一句话结论

**KV = localTool（:18080）SQLite 里的 `kv` 表**，服务"需要被多端（同一 localTool 实例）共享的结构化数据"。前端经 `kvStore.js` 统一封装，**只有 `canvas-state-v1-` 前缀的键 + 显式 `kvSet` 才走 KV**，其余（项目/账号/设置/预设等）走浏览器 localStorage。**文本/抽屉落盘正是靠 KV（画布快照）实现刷新不丢的。**

---

## 一、两套存储：必须分清（最容易混淆）

| 维度 | A. localTool KV | B. 浏览器 localStorage |
|---|---|---|
| 所在 | 独立 localTool 服务（Node:18080） | 浏览器扩展/网页 `localStorage`（storageAdapter 加 `yimao:` 前缀） |
| 后端实现 | sql.js（SQLite WASM），文件 `~/.maomao-localtool/localtool.db` | 浏览器内置 |
| 访问 | `GET/POST /api/kv/{get,set,delete}` | JS 直接 `localStorage`（同步） |
| 跨端共享 | **同一 localTool 实例 ⇒ 共享** | 仅同源/同扩展 |
| 典型键 | `canvas-state-v1-<id>`、`active_api_endpoint` | `projects`、`app_settings`、`presetPrompts`、`users` 等 |
| 同步/冲突 | 仅最新值，覆盖写；**无云同步、无冲突合并** | 无 |

**前端统一存储抽象（`kvStore.js`）自动分流**：
```
key.startsWith('canvas-state-v1-')  → 走 KV（storageGet/storageSet/storageDelete 转发 kvGet/kvSet/kvDelete）
否则                                → 走 localStorage（sGet/sSet/sRemove）
```

> ⚠️ **防误判**：`api_configs` / `localToolBaseUrl` / `transitResources` / `app_settings` 等**都不走 KV `kv` 表**（官方 18 文档 §0 也强调）。"前端调用了存储"≠"走 KV"，看 key 前缀。
> **`projects` 特例**：它**走后端 `projects` 表**（`/api/projects`，SQLite 权威源，跨端共享）+ localStorage 兜底，**不是 KV `kv` 表，也不是纯 localStorage**（详见 §4.1）。"项目要存服务端"已满足。

## 二、KV 接口契约（真实实现，`localTool/src/routes/kv.ts`）

| 接口 | key 位置 | 成功响应 | 不存在时 | 错误 |
|---|---|---|---|---|
| `GET /api/kv/get?key=` | query | 解析后的值（无包裹） | `null` | `{error:英文}` |
| `POST /api/kv/set` | body `{key,value}` | `{ok:true}` | — | `{error:英文}` |
| `POST /api/kv/delete?key=` | query | `{ok:true}`（恒真） | 仍 `{ok:true}` | `{error:英文}` |

- 表结构：`kv(key TEXT PRIMARY KEY, value TEXT, updated_at INTEGER)`。`value` 仅存字符串，对象由调用方 `JSON.stringify`。
- **落盘**：sql.js 内存库，`debouncedSaveDb()` 500ms 防抖写盘。
- **写 base64 自动外置**：`handleKvSet` 前会 `externalizeBase64InValue`，把 value 里 base64 图片落盘成 `/files/`，避免 KV 库被撑大（docs/41）。
- **无批量/前缀列举**：只有单 key 的 get/set/delete。

## 三、当前实际使用 KV 的键（活跃，已实现）

| 键 | 写入方 | 用途 | 关联 |
|---|---|---|---|
| `canvas-state-v1-<projectId>` | `projectStore.saveCanvasState` | 画布快照（nodes/edges），600ms 防抖自动保存 | **文字/抽屉落盘的基础**（`03/04` 相关） |
| `canvas-state-v1-<projectId>_version` | `projectStore.saveCanvasState` | 版本号（`Date.now()`），多端冲突检测 | 防旧覆盖新 |
| `active_api_endpoint` | `providerStore.save` | 当前生效 API endpoint（主供应商信息），跨端读取 | API 设置 |

**删除项目时**：`projectStore` 会 `storageDelete('canvas-state-v1-<id>')` + `storageDelete('<id>_version')`。

## 四、排查发现：KV 表里的脏数据（历史遗留，当前不走 KV 读）

用 `cd localTool && node scripts/db-query.mjs --kv ""` 排查 KV 表，发现**除了上述活跃键，还有一批历史遗留键**：

| 残留键 | 当前 src/ 实际存储 | 判定 |
|---|---|---|
| `lastOpenedProject` | localStorage（projectStore `LAST_OPENED_KEY`） | **脏数据**（应走 localStorage） |
| `auth_token` | — | 业务数据，localTool admin 明确"不碰"（`admin.ts` L50/74） |
| `membership` | — | 脏数据（官方兼容残留） |
| `projects` | **localTool `projects` 表**（`/api/projects`，权威源）+ localStorage 兜底 | **KV 表里是旧版残留**；当前项目系统走后端 `projects` 表，不存 KV `kv` 表（见 §四.1） |
| `users` | localStorage | 脏数据 |
| `api_configs` | localStorage（`api_configs`，官方 Ar 枚举） | **脏数据**（官方 18 文档明确排除） |
| `presetPrompts` | localStorage（`yimao_preset_prompts`） | 脏数据 |
| `customNodeTemplates` | localStorage | 脏数据 |
| `cloud_storage_config` | — | 脏数据（云端配置未实现） |
| `app_settings` | localStorage（`appSettings.js`） | 脏数据 |

**结论**：这些键**本不该出现在 KV 表**（按 `kvStore.js` 分流规则应走 localStorage 或后端业务表），是**早期原型/官方兼容测试直接写 KV 留下的**。当前 src/ 前端**不通过 KV 读它们**，属历史脏数据。

> ⚠️ **风险**：这些脏数据虽然当前不影响功能（前端读 localStorage 的 `yimao:` 前缀键），但**污染 KV 表、语义混乱**。后续可清理（删除非活跃的残留键），但**动 `auth_token` / `canvas-state-v1-*` 要谨慎**（admin.ts 明确不碰）。

### 4.1 项目（projects）到底存哪？—— 澄清

**项目系统已走后端 `projects` 表（localTool SQLite），不是单纯 localStorage，也不走 KV 的 `kv` 表。**

```
项目列表（projects 元数据）
  ├─ localTool /api/projects → projects 表   ← 权威源（跨端共享，刷新/换浏览器不丢）
  ├─ localStorage（兜底，localTool 断开也能用）
画布快照（每个项目的内容）
  └─ KV 的 kv 表 canvas-state-v1-<id>         ← 跨端共享
```

- **为什么项目列表不走 KV 的 `kv` 表**：它是**结构化业务表**（`projects(id, name, is_last_opened, created_at)`，有主键/排序/lastOpened 标记），用专门的 `projects` 表比塞进 KV `kv` 表更合适——KV 是无结构键值，不适合做需要查询/排序的业务表。
- **KV 表里那个 `projects` 残留**是旧版直接写 KV 留下的脏数据，**不代表当前项目存 KV**。
- **用户视角的"项目要存 KV（服务端持久化）"已经满足**：项目走后端 `projects` 表（localTool SQLite），跨端共享已实现，不是只存浏览器 localStorage。

> **判断原则**：需要"结构化查询/排序"的业务数据（项目列表、任务）→ 走后端业务表（`projects` 表 / `tasks` 表）；需要"按 key 存取的结构化共享数据"（画布快照）→ 走 KV `kv` 表；纯本机单端 → localStorage。

## 五、后续还需要用到 KV 存储的场景（建议）

按"该不该走 KV"判断（**跨端共享 / 体积不大 / 需要刷新恢复** → KV；纯本机单端 → localStorage）：

### 5.1 推荐走 KV（跨端共享或需恢复）

| 场景 | 键 | 为什么走 KV | 状态 |
|---|---|---|---|
| **节点输入/配置落盘**（提示词、文本、抽屉开合） | 已复用画布快照 `canvas-state-v1-<id>`（写 node.data） | 刷新恢复，跨窗口同步 | ✅ 已做（04 相关） |
| **任务恢复轮询状态** | tasks 表（非 KV，`tasks.ts`） | 用 `poll_task_id` 查网关 | ✅ 已做（走 tasks 表而非 KV） |
| **当前生效 API endpoint** | `active_api_endpoint` | 跨端读当前主供应商 | ✅ 已做 |
| **节点/脚本盒历史**（未来） | `canvas-state-v1-<id>` 内扩展 | 随画布快照存 | 规划 |
| **跨窗口同步的临时状态** | 业务前缀 | 多窗口共享 | 按需 |

### 5.2 不走 KV 的 `kv` 表（走后端业务表或 localStorage）

- `projects` → 走 localTool **`projects` 表**（`/api/projects`，权威源跨端共享）+ localStorage 兜底（见 §4.1）。**不是存 KV `kv` 表**，但已经是"服务端持久化"。
- `tasks` → 走 localTool **`tasks` 表**（`/api/tasks`），任务中心用。
- `app_settings` / `presetPrompts` / `users` / `customNodeTemplates` → localStorage（本机单端足够）
- `pinnedTools` → `app_settings.pinnedTools`（localStorage）
- `agent_history_*` → localStorage（聊天记录）

> **判断原则**：需要"结构化查询/排序"→ 后端业务表（projects/tasks）；需要"按 key 存取的跨端共享"→ KV `kv` 表；纯本机单端 → localStorage。能 localStorage 就不上 KV（避免 KV 表膨胀 + 跨端串扰）。
