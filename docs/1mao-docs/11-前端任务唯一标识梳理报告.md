## 0. 结论速览

| 问题 | 结论 |
|------|------|
| 前端任务对象是否同时有 `id` 和 `taskId`？ | **是**，但两者语义在不同 store 中不一致（见 §1） |
| 哪个是「稳定唯一标识」？ | **`taskId`** 才是与后端 `task_id` 对应的业务唯一键；`id` 是前端别名，有时等于 `nodeId`、有时等于 `taskId`，**不是稳定唯一键** |
| `id` / `taskId` 在哪里生成？ | `taskId` 来自「发起运行」接口（`/run`）返回，前端原样赋值（21227）；`id` 在全局任务 store 中被设成与 `taskId` 同值，在画布 store 中被设成 `nodeId` |
| `batch-save` 请求体里 `id` 和 `taskId` 分别是什么？ | 全局任务的请求体里 `id === taskId === o`（run 接口返回的 taskId）；但后端 `taskToRow` 会把两者都映射到 `task_id`，且后者覆盖前者 |
| 重复记录根因？ | 前端无统一主键；后端 GET 只回 `taskId` 不回 `id`；`taskToRow` 对 `id`/`taskId` 双写 `task_id` 且按迭代顺序 last-wins；重载后 `id` 基准的 diff 无法命中已有记录，导致重新插入 |

**重要更正（与任务书假设不符）**：任务书假设 `database.ts` 同时存在 `id INTEGER PRIMARY KEY` 和 `task_id`。实际建表语句只有 `task_id TEXT PRIMARY KEY`，**没有 `id` 列**（见 §3 证据 A）。`id` 完全是前端概念，后端通过 `CAMEL_TO_SNAKE['id']='task_id'` 把它硬塞进 `task_id`。

## 1. Q1：前端任务对象是否同时有 `id` 和 `taskId`？

**是。** 但「`id` 等于什么」在三个位置各不相同，这是混乱的根源。

### 1.1 全局任务 store（任务中心的数据源）—— `id` 与 `taskId` 同值

发起一次运行、拿到 `taskId` 后，前端构造全局任务对象（`output.js:21244-21264`）：

```js
21227:  let o = String(a?.taskId || a?.task_id || ``)
21244:  ;(c.updateGlobalTasks?.((t) => {
21252:    {
21253:      id: o,           // ← id = 运行接口返回的 taskId
21254:      taskId: o,       // ← taskId = 同一个值
21255:      nodeId: e,
21256:      type: `rhWebapp`,
21259:      createdAt: Date.now(),
...
21264:    }
```

即在此 store 中 **`id` 是 `taskId` 的别名**，二者恒等。该 store 经 `updateGlobalTasks: I` 维护（`output.js:45809`），并以 `globalTasks` 为 key 持久化到本地工具 KV（`GLOBAL_TASKS`，`output.js:2044` / `45808`）。

### 1.2 画布/节点任务 store —— `id` 等于 `nodeId`

`mutiwindow-task-completed` 事件处理器按 `id` 匹配节点（`output.js:45981-45984`）：

```js
45981:  let { nodeId: t, resultUrl: n, type: r, status: i, errorMsg: a } = e.detail
45984:  if (e.id === t) {            // ← 这里的 id 是 nodeId
```

视频生成 store 中也以 `id === nodeId` 为基准回填 `taskId`（`output.js:48650`）：

```js
48650:  ;(I && I((e) => e.map((e) => (e.id === N ? { ...e, taskId: L } : e))),
```

> 注：`I` 在不同组件作用域内被复用，此处 `I` 指画布/视频节点的局部任务 store，与 §1.1 的全局 `I` 不是同一个变量。

### 1.3 小结

| store | `id` 的值 | `taskId` 的值 |
|-------|-----------|---------------|
| 全局任务（任务中心） | run 接口 `taskId`（`o`） | `o`（同 `id`） |
| 画布/节点任务 | `nodeId` | 运行开始后回填的 `o` |

**前端根本没有一处「始终稳定、全局唯一的任务主键」**。`id` 在不同 store 含义漂移，只有 `taskId` 是前后端共识的业务键。

## 2. Q2：`id` / `taskId` 在哪里生成？

- **`taskId` 的生成方是后端运行接口**，不是前端本地随机生成。
  - 发起运行：`POST /run` → 响应 `a.taskId || a.task_id`（`output.js:21227`）。
  - 赋值给任务对象：`r(e, { taskId: o, status: 'RUNNING' })`（`21231`）；全局任务构造时 `taskId: o`（`21254`）。
  - 完成后回填：`{ ...e, taskId: L }`（`48650`、`49045`、`49585`）。
- **`id` 没有独立生成逻辑**，它只是被「拷贝」成 `taskId` 同值（全局 store）或「借用」`nodeId`（画布 store）。
- 前端仅在 `createdAt: Date.now()`（`21259`）和预设项 `id: Date.now().toString()`（`52894`、`54606`）使用 `Date.now()`，**任务 `id`/`taskId` 本身不是 `Date.now()` 生成**（除非运行接口返回的 `taskId` 本身是时间戳形态——这要看 `/run` 服务实现，见 daily/09 中关于 `task_id=Date.now()` 的记录）。

> 待核实：运行接口（`/run`）返回的 `taskId` 的构成。若它就是 `Date.now()` 一类「每次运行都变」的值，那么「同一节点多次运行」天然会产生不同 `taskId`，这是重复记录的直接燃料之一。

## 3. Q3：`batch-save` 请求体里 `id` / `taskId` 是什么？

`batchSaveTasks`（`output.js:1480-1492`）：

```js
1480:  async function ar(e) {
1484:    await fetch(`${Mn()}/api/tasks/batch-save`, {
1488:      body: JSON.stringify({ tasks: e }),   // ← 直接序列化整个任务数组
```

请求体结构：`{ tasks: [ taskObj, ... ] }`，`taskObj` 即 §1.1 中的全局任务对象（含 `id`、`taskId`、`nodeId`、`type`、`status`、`prompt`、`createdAt`、`requestData` 等）。

后端接收与落库（`localTool/src/routes/tasks.ts`）：

```ts
46:  function taskToRow(task) {
47:    const row = {};
48:    for (const [key, value] of Object.entries(task)) {
49:      const snakeKey = CAMEL_TO_SNAKE[key] || key;     // id→task_id, taskId→task_id
...
57:  function upsertTask(db, row) {
61:    run(db, `DELETE FROM tasks WHERE task_id = ?`, [row.task_id]);
62:    run(db, `INSERT INTO tasks (...) VALUES (...)`, vals);
```

**关键歧义点**：`CAMEL_TO_SNAKE` 同时把 `id` 和 `taskId` 映射到 `task_id`（`tasks.ts:18,20`）：

```ts
9:   const SNAKE_TO_CAMEL = { task_id: 'taskId', node_id: 'nodeId', ... };
17:  const CAMEL_TO_SNAKE = {};
18:  for (const [k, v] of Object.entries(SNAKE_TO_CAMEL)) CAMEL_TO_SNAKE[v] = k; // taskId → task_id
20:  CAMEL_TO_SNAKE['id'] = 'task_id';                                          // id     → task_id
```

由于 `taskToRow` 遍历 `Object.entries(task)`，**谁在对象里后出现，谁就决定最终的 `task_id`**。在全局任务对象 `{ id: o, taskId: o, ... }` 中两者同值，故 `task_id = o`（一致）；但若某个任务对象里 `id`（=nodeId）与 `taskId`（=o）不一致（例如画布 store 直接拿去保存），则落库的 `task_id` 取决于字段顺序，结果不可预期。

证据 A —— 表结构（`localTool/src/db/database.ts:107`）：

```ts
107: db.run(`CREATE TABLE IF NOT EXISTS tasks (
        task_id TEXT PRIMARY KEY, node_id TEXT, prompt TEXT, ... )`);
```

**只有 `task_id TEXT PRIMARY KEY`，没有 `id` 整型列。** 因此：
- 后端主键永远是 `task_id`；
- `id` 在前端是「影子字段」，落到数据库时被合并进 `task_id`；
- 不存在任务书假设的「`id` 整型自增主键 + `task_id` 业务键」双层结构。

## 4. Q4：重复记录的根本原因（链路）

把以上证据串成链路：

1. **前端无统一主键**：全局 store 用 `id(=taskId)`，画布 store 用 `id(=nodeId)`，`diffAndPersistTasks` 又以 `e.id` 作为 diff 基准键（`output.js:1535` 区域：`n`/`r` 均以 `e.id` 建 map）。
2. **后端 GET 只回 `taskId`、不回 `id`**（`rowToTask`，`tasks.ts:26-35`）：`task_id → taskId`，对象里没有 `id`。重载后拿到的历史记录没有 `id`。
3. **diff 基准缺失 → 全部判为「新增」**：`dr(e, t)` 中旧集（来自 GET，无 `id`）按 `e.id` 建 map 全为 `undefined`，新集（内存，有 `id`）全部匹配不到 → 整组被当作「已变更」重新保存（`output.js:1546` 分支 `o.push(ar(i))`）。
4. **`taskToRow` 双写 `task_id` 且 last-wins**：若保存对象里 `id` 与 `taskId` 不一致，落库的 `task_id` 取决于字段顺序；即使一致（都=`o`），只要 `o` 在每次运行/重载时重新取值（见 §2 待核实），就会生成新的 `task_id`。
5. **upsert 是按 `task_id` 删除再插入**（`tasks.ts:61-62`）：`task_id` 一旦变化，旧行不被删、新行被插入 → **任务中心出现重复记录**。

> 补充观察（本构建）：`diffAndPersistTasks`（`dr`）/`serializeTaskWrites`（`ur`，导出别名为 `un`，`output.js:181`）在 `httpClient` 产物中**只有定义、无调用点**；`batchSaveTasks`（`ar`）/`saveTask`（`ir`）仅被 `dr` 内部调用。也就是说，在当前 `dist` 构建里，`/api/tasks/batch-save` 的自动同步路径疑似为**死代码**，全局任务主要靠 `globalTasks` KV（`updateGlobalTasks`）持久化。若任务中心读取的是 `/api/tasks` 表，则需确认是谁在真正写入该表——这条链路建议进一步核对（可能是更早构建或另一条未反混淆出的路径）。此观察不影响上述「`id`/`taskId` 语义混乱」结论，但影响「修复应从哪条路径入手」。

## 5. 修复建议（方向，供评审）

1. **确立唯一键为 `taskId`**：前端所有任务对象统一以 `taskId` 为主键，`id` 仅作为 `taskId` 的只读别名（或干脆删除 `id`）。
2. **后端 GET 同时返回 `id`**：在 `rowToTask` 中补充 `task.id = task.taskId`，使前端 reload 后 `id` 基准的 diff 能命中已有记录（治标）。
3. **消除 `taskToRow` 的双写歧义**：明确 `task_id` 只取 `taskId`，`id` 不再参与映射（删掉 `CAMEL_TO_SNAKE['id']='task_id'`，或在 `taskToRow` 中优先采用 `taskId` 并忽略 `id`）。
4. **统一前端 store 的 `id` 语义**：全局 store 与画布 store 的 `id` 含义必须一致，避免「`id=nodeId`」与「`id=taskId`」混用。
5. **去重保障**：`updateGlobalTasks` 追加任务时已有 `nodeId` 过滤（`output.js:21245-21250`），但只过滤 running；建议以 `taskId` 去重，确保同一运行不会重复入列。
6. **核实 `/run` 返回的 `taskId` 稳定性**：若为每次运行都变的时间戳，需评估「同节点多次运行 = 多条记录」是否符合产品预期。
