# 20 · 官方权益接口转发层方案（思路 A：localTool 中转 + 缓存）

> 起草：2026-08-01
> 背景：当前自研链路由 localTool(:18080) → apimart-gateway(:9004) → Lovart 承载生图/生视/聊天；但**账号/权益/会员类接口仍直接打官方 1mao（闭源、非自研）**，存在散乱裸连、来源判定混乱、无降级兜底等问题。本方案在 localTool 侧加一层"官方权益接口转发层"，统一入口、官方做权威源、本地做中转 + 短缓存。

---

## 一、现状核实（源码实证，含混淆反查可信度标注）

> 可信度说明：涉及 `localTool/src` 的论断为 ✅ 高可信；涉及 `dist/assets` 混淆变量的 base 映射为 ⚠️ 强推断（已逐字定位调用点，但实例 base 绑定行未全逐字定位，详见 §7.1）。凡 ⚠️ 论断均已在 §3.3/§7.1 标注前提。

### 1.1 前端三处权益接口的实际去向
在 `dist/assets` 中定位到的真实调用（混淆变量已反查）：

| 端点 | 前端调用形态 | 实际 base | 当前落点 |
|---|---|---|---|
| `/user/info` | `ut("/user/info")` + `_t.get("/user/info")` | `ut`(`gn as ut`)/`_t`(`i as _t`) 的 base 均来自 `Wn=Nn()`（`Nn`=endpointConfig 的 active endpoint 取值器）。**`active_api_endpoint` 默认值即 `http://127.0.0.1:18080`（localTool），官方三地址（`1mao.cc` 等）仅作为候选列表、需用户/配置切换才生效**（源码实证：endpointConfig `function n()` 默认返回 `127.0.0.1:18080`） | 默认**落 localTool:18080**（因 `active_api_endpoint` 默认即 18080）；但 localTool 当前无权益路由（grep=0），故实际 **404/兜底**。仅当用户在 UI 把接入点切到官方候选时才真去官方 |
| `/user/model-entitlements` | `fetch(`${r2}/user/model-entitlements`)`，`r2` 来自 active endpoint 取值器 | `active_api_endpoint`（**默认 18080**，非固定官方） | 默认落 **localTool:18080**；无路由 → 404/兜底 |
| `/agent/{id}/vip-check` | `fetch(`${Je}${st}/agent/.../vip-check`)`，`Je`=active endpoint 取值器 | `active_api_endpoint`（**默认 18080**） | 默认落 **localTool:18080**；无路由 → 404/兜底 |

> 佐证：`localTool/src` 全仓 grep `/user/`、`/agent/`、`/auth/`、`model-entitlements`、`vip-check` = 0 命中（**当前态**），证明 localTool 当前**完全不拦截**权益接口；本方案 §3.1 即在 localTool 中**新增**这些路由（与 `docs/12` §1.1 第 51/54 行规划一致，非"永远不会有"）。
> 补充：官方接入点清单见 `dist/assets/endpointConfig-Bt85xi8d.js`：`https://www.1mao.cc` / `https://1mao.16iai.com` / `http://154.219.102.152:3012`，但它们是"候选接入点列表"（函数 `s()`），**默认生效的是 `active_api_endpoint` 取值器 `function n()` 返回的 `http://127.0.0.1:18080`（localTool）**，而非官方。最终值由 `sessionStorage → KV → 默认 18080` 决定（注意：此前文档写"默认官方"系误述，已据 endpointConfig 源码更正）。

### 1.2 关键事实
- 会员校验 100% 在官方远程服务器，前端只展示 + 提前拦截（详见 `docs/15`）。
- `modelApiTokenKey`（真实调用凭据）由 `/user/info` 下发，本地改不出真权限。
- 因此本方案**只做中转与缓存，不取代官方判定**；grok/GK 能否用仍由官方账号等级决定。

---

## 二、方案目标（奥卡姆剃刀：只做必要的事）

1. **统一入口**：让所有官方权益请求经 localTool，符合"唯一入口"铁律，来源判定清晰。
2. **中转 + 缓存**：官方做权威源，localTool 转发并缓存短 TTL，官方抖动时降级不白屏。
3. **最小前端改动**：沿用现有 `ut()` 与 endpoint 取值机制。注意（精确化自 §3.3）：JSON 权益接口直连官方、不进 `/api/proxy`，故"KV 重定向自然生效、零改动"不成立——若走 KV 路径须先在 localTool 新增 §3.1 路由（`docs/12` §1.1 支持"前端黑盒可不动"，但 localTool 侧须补路由）；最可控路径是改 `src/bundle/` 把三调用指向 localTool 新端点后 `npm run build` 回灌 `dist/`。属"最小改动"而非"零改动"。
4. **不触碰官方鉴权**：透传 `Authorization: Bearer <token>`，本地不解析会员语义。

---

## 三、落地设计

### 3.1 新增 localTool 路由（透明转发）
在 `localTool/src/index.ts` 注册一组"官方代理"路由，统一指向官方接入点（值取自 `active_api_endpoint` KV，回退默认 `http://127.0.0.1:18080`——即 endpointConfig 取值器的默认值，而非官方地址）：

| 路由（localTool 侧） | 转发目标（官方） | 方法 |
|---|---|---|
| `GET /api/user/info` | `${OFFICIAL}/user/info` | GET |
| `GET /api/user/model-entitlements` | `${OFFICIAL}/user/model-entitlements` | GET |
| `GET /api/agent/:id/vip-check` | `${OFFICIAL}/agent/:id/vip-check` | GET |

- 实现复用现有 `handleProxy` 思路（原样 fetch 转发、透传 Bearer、超时、错误透传），但**独立函数**（不混进 `/api/proxy`，便于单独加缓存与日志）。
- 请求头：`Authorization` 从前端传入的 Bearer 原样透传；`x-official-base` 可选覆盖。

### 3.2 缓存策略（短 TTL 降级）
- 缓存键：`user:info` / `entitlements:<token-hash>`（按 token 隔离，避免串号）。
- TTL：`/user/info` 60s，`model-entitlements` 300s（权益变化不频繁）。
- 命中：官方 5xx / 超时 / 网络错 → 返回上一次缓存 + `x-cache: hit-stale`；无缓存则透传官方错误（不伪造权限）。
- 不缓存：`vip-check`（实时性要求高，按需透传，失败即失败）。

### 3.3 重定向机制（路径澄清：KV 重定向有效，但非"零改动"）
> **重要澄清（2026-08-01，依据 `docs/12` §1.1 与 `docs/15` §9.1–9.3 交叉核实）**：`/user/info`、`/user/model-entitlements`、`/agent/.../vip-check` 均为 **JSON body 请求**。`httpClient` 的 `Bl(e2,t2)` 仅当 body 为 FormData/Blob 时才走 `/api/proxy`；JSON 请求走 `else` 分支 `fetch(e2)`（见 `docs/15` 结论 1/2）。据此精确厘清两条路径：
> - **KV 重定向路径（对 JSON 有效，但需补路由）**：若 `active_api_endpoint` 经 `POST /api/kv/set` 改为 `http://127.0.0.1:18080`（`docs/12` §1.1 第 37/54 行明确支持"无需改前端"），则 `fetch(`${Je}/agent/.../vip-check`)` 会**直接打到 localTool 的 18080 端口**（作为普通 HTTP server，非 `/api/proxy`）。localTool 若**新增 `/api/agent/{id}/vip-check` 等路由**即可响应——这正是 `docs/12` 第 51-54 行的规划。**KV 重定向并非"技术上无效"**，而是：`docs/15` §9.3 否认的是"localTool 已自动接管 JSON 逻辑"，并非否认"Je 可改 18080"。原文档"KV 重定向对 JSON 无效"的表述不精确，更正为"KV 重定向能让 JSON 请求落 localTool 端口，但 localTool 需补对应路由，而非自动接管"。
> - **改 `src/bundle/` 路径（最可控）**：在 `src/bundle/`（打包前对应 `httpClient`/`App` 的源码）中把三处权益调用的 base 直接指向 localTool 新增 GET 端点（即 §3.1 路由），再 `npm run build` 回灌 `dist/`。不依赖全局 `active_api_endpoint` 副作用（避免影响 A1 画布助手 chat 等其它 `Je` 消费点，见 §7.6）。
> - **原文档误区（已修正）**：早期"零前端改动 / KV 重定向自然生效、localTool 已接住"的设想，混淆了"`Je` 重定向让请求落 localTool"与"localTool 已具备接管逻辑"两层（`docs/15` §9.3 修正表已驳斥"只需加路由映射接管"）。若走 KV 路径，必须**显式在 localTool 新增 §3.1 三组路由**；若走改 `src/bundle/` 路径，指向新端点后 build 回灌。两条都需 localTool 补路由，无"免费午餐"。
> - 无论哪条路径，`docs/12` 第 39 行的"⚠️ 待运行时确认"必须继承：先实测 `POST /api/kv/set active_api_endpoint=127.0.0.1:18080` 后用 DevTools 观察三请求是否真落 18080（若不命中说明实际优先级与推断不同，需改前端而非只写 KV）。

- `/user/info`：`ut()` 调用走 `Kn(e2)`，`e2`=active endpoint；但如前所述 JSON 直连官方，补 localTool 路由**不会自动生效**，需在 `src/bundle/` 层把该调用指向 localTool 新端点后 `npm run build` 回灌 `dist/`（或在 `src/bundle/` 把 active endpoint 改本地，但后者对 JSON 无效，仅影响 FormData/Blob 类）。
- `model-entitlements` / `vip-check`：base 取自 `active_api_endpoint`，但 JSON 直连特性同上——**KV 重定向无效**。唯一可行路径是改 `src/bundle/` 显式指向 localTool 新 GET 端点后 build 回灌。
- ⚠️ 联动：`active_api_endpoint` 同时影响 A1 画布助手 chat 等 JSON 专属调用（见 §7.6 / `docs/15` §9.1 清单）；这些调用的"标记官方专属"兜底逻辑与权益接口无关，改 `src/bundle/` 时须逐一确认落点，避免误改。

### 3.4 日志与可观测
- 沿用 `system.ts` 的 `[proxy]` 日志格式，新增 `[official]` 前缀，便于与 Lovart 链路区分来源。

## 四、收益与边界

### 收益
- **来源统一与可观测**：把散乱在多处（ut/_t/r2/Je）的官方权益调用收敛到一个可审计入口，报错来源清晰可溯（注意：官方 base 当前本就可直连，CORS/证书非阻断点，见 §7.5，故本收益是"可观测/统一"而非"解决连不通"）。
- 官方抖动时凭缓存降级，画布不白屏、不误弹"无权限"。
- 为后续"部分接口本地化"（如模型清单改本地返回）留跳板（类比现有 `/public/platform/*`）。
- 统一日志，权益类报错来源清晰可溯。

### 边界（硬限制，不解决）
- **账号/付费状态仍由官方判定**：本地只能中转/缓存，不能自研会员体系。grok/GK 能否用取决于官方账号等级，本地改不了。
- **需官方登录态**：转发须带官方 token；无账号仍不可用。
- **非真替换**：官方是权威源，本层是中转层。

## 五、实施步骤（建议顺序）

> **路径定调（修正自 §3.3）**：两条路径均可落地，但语义不同：
> - **主路径（推荐，最可控）：改 `src/bundle/` 指向新端点**——在 `src/bundle/`（打包前对应 `httpClient`/`App` 源码）把三处权益调用的 base 直接指向 localTool 新增 GET 端点（§3.1），再 `npm run build` 回灌 `dist/`。注：此前文档称此路径是为"避免污染 A1 画布助手 chat 等其它 `Je` 消费点"，但源码实证表明 `active_api_endpoint` 默认值本就是 `18080`（聊天/生图/视频内置模型默认全走 localTool），故"KV 改 18080 会污染其它链路"的担忧**不成立**（详见 §7.6 勘误）。改 `src/bundle/` 路径的真正价值是"显式、可控、不依赖全局 KV 切换"，且遵守 `dist/` 禁止手改的规程。
> - **可选灰度路径：KV 重定向 + 补路由**——`POST /api/kv/set active_api_endpoint=http://127.0.0.1:18080`（`docs/12` §1.1 支持"无需改前端"）。注意：**`active_api_endpoint` 默认值本就已是 `18080`**，故 KV 设为 18080 通常不改变默认态（除非此前 sessionStorage/KV 被切到官方候选）。JSON 请求本就打到 18080；**但必须先在 localTool 新增 §3.1 三组路由**，否则 404（这正是早期"零改动"设想的误区：KV 改了 ≠ localTool 自动接管）。该路径好处是前端黑盒可不动，且因默认即 18080，**无"污染其它链路"的副作用**（详见 §7.6 勘误）；唯一需注意的场景是用户已在 UI 把接入点切到官方候选时，KV 重定向会把它拉回 18080。

**硬性前置（必须最先做，否则后续全错）**：
0. **运行时验证 `active_api_endpoint`（`Je`/`r2`/`e2`）的真实值**：`docs/12` §1.1 已标注此优先级系"对混淆 bundle 逆向解读、全仓源码 0 印证、待运行时确认"。先抓包/DevTools 实测三请求的真实 base 与是否直连官方（预期：直连官方，与 `docs/15` §9.1 一致）。**未确认前不进入步骤 1。**
0.5 **枚举 JSON 直连接口全量清单**：直接采用 `docs/15` §9.1 清单（`/user/info`、`/user/model-entitlements`、`/agent/canvas-assistant/vip-check`、`/agent/canvas-assistant/chat`、`/auth/login-*`），补齐 A1 画布助手专属落点，形成"受影响接口清单"，避免 §7.6 重复造轮子。

1. localTool 新增 `routes/official.ts`：`handleOfficialUser`、`handleOfficialEntitlements`、`handleOfficialVipCheck`，**独立 GET 端点**（不复用 `/api/proxy` 路由，因其仅 POST，见 §7.3），复用 `handleProxy` 的 fetch/超时/错误逻辑，加内存缓存（见 §7.4 修正）。
2. `index.ts` 注册三个 GET 路由（注意前缀与现 `index.ts` 路由风格一致，不与 `/api/proxy`、`/public/platform/*` 冲突）。
3. **选路径落地**：
   - 走主路径：在 `src/bundle/` 改三处权益调用 base 指向 localTool 新端点，再 `npm run build` 回灌 `dist/`。
   - 走 KV 灰度：执行 `POST /api/kv/set active_api_endpoint=http://127.0.0.1:18080`（步骤 1/2 的路由已就绪为前提），DevTools 验证三请求落 18080 而非官方；若不命中说明实际优先级与 `docs/12` 推断不同，退回主路径改 `src/bundle/`。
4. 验证：DevTools 观察三请求 base 是否变为 `127.0.0.1:18080/api/...` 且官方不可达时走 stale 缓存。
5. 缓存 TTL 调参，观察官方不可达时的降级表现（stale 提示见 §7.7/9.3-2）。
6. 更新 `CLAUDE.md` §二，把"官方权益转发层"列为 localTool 职责之一（编号以 `CLAUDE.md` 现职责条数为准，§五.5 的"第 8 类"待核）。

## 六、风险与注意
- **KV 冲突**：`admin/import` 会清空全部 KV（见 `docs/12` §2.3-补充），权益缓存已改内存（§7.4 修正），但若仍用 KV 存配置须用 `POST /api/kv/set` 单键写入。
- **token 安全**：缓存键按 token hash 隔离，避免不同账号权益串号。
- **不要把缓存当真相**：降级返回 stale 时前端可能短暂显示过期权益，属可接受的体验降级，绝不可伪造 `allowed:true`。
- **JSON 直连前提**：`active_api_endpoint` KV 重定向**对 JSON 有效但需补路由**（JSON 走 `fetch(e2)` 直连 `e2` 指向的端口，若 `e2`=18080 则落 localTool，但 localTool 须已注册 §3.1 路由，否则 404）。勿误以为"KV 一设即自动接管"（`docs/15` §9.3 已驳斥）。

## 七、审计补充：源码二次核实后的盲点与修正（2026-08-01）

> **复核声明（2026-08-01 二次核实）**：本章首次写入时部分前端反查结论有误（见 7.1 勘误）。以下结论均来自对 `dist/assets/*.js` 与 `localTool/src` 的核对，但**混淆变量反查存在局限**，凡涉及"前端变量 → base 映射"的论断均标注可信度，不再声称"非推测"。配套审计结论见 `docs/20` 末尾"独立审计结论（用户）"一节。

### 7.1 【降级·勘误】`/user/info` 确有两处调用，但其 base 归属首版误判
首版（2026-08-01 早些时候）称"`ut`=localTool 客户端、`_t`=官方 base 客户端"，**经二次反查证伪**，特此勘误。

二次反查结果（`App-BX6o9fW5.js` + `httpClient-BknZwXjG.js`）：
- 行 5：`ut("/user/info")` —— `ut` 来自 `gn as ut`（httpClient 导出名 `gn`）；
- 行 9：`_t.get("/user/info")` —— `_t` 来自 `i as _t`（httpClient 导出名 `i`）；
- httpClient 内 `var Wn=Nn();` 且 `Nn` 来自 `endpointConfig`（= `active_api_endpoint` 取值器），即 **`Wn` 就是 active endpoint**；`Kn()` 把 base 拼 `/api`（`Gn="/api"`）。

**修正后的结论**：
1. `ut` 与 `_t` 的 base 都源于 `active_api_endpoint`（即 `Wn`），**并非"一条 localTool、一条官方"**。二者 base 同源。
2. 因此"双链"的真实含义是：**默认（KV 未改 / sessionStorage 未设）两条 `/user/info` 都走 `active_api_endpoint` 的默认值 `http://127.0.0.1:18080`（localTool）**——因为 `endpointConfig` 的 `function n()` 默认即返回 `18080`，而非官方。只有用户在 UI 把接入点切换到官方候选（`1mao.cc` 等）后，两条才会改走官方。原 §1.1 早期写"默认官方裸连"**与 endpointConfig 源码不符，已更正**。
3. 方案落地含义：采用"新增 localTool 端点 + 改 `src/bundle/` 指向"或"KV 重定向 + 补 §3.1 路由"两条路径，因 base 同源（`Wn`），权益请求默认都已打到 18080，**缺的只是 localTool 侧的 §3.1 权益路由**（当前 grep=0 → 404/兜底）**。两条调用点（`ut` 与 `_t`）都受同源 `Wn` 影响，补路由后一并接管，无需逐处改 `src/bundle/`。

> 可信度：双链存在（✅ 已逐字定位 App 行5/行9）；base 同源自 `Wn=Nn()`（⚠️ 强推断，`gn`/`i` 实例的具体 base 绑定行未逐字定位，但 `Wn`=active endpoint 已证实）。

### 7.2 【修正】`vip-check` 并非"未对齐"，其 base 已走 active endpoint + `/public/platform`
原 §2.1 把 `vip-check` 与 `user/info`、`model-entitlements` 并列视为"形态不一致、需对齐"。源码核实（`App-BX6o9fW5.js` 行 7）：
```js
fetch(`${Je}${st}/agent/${e2}/vip-check`, { headers: { Authorization: `Bearer ${t2}` } })
```
- `Je` = 官方 active endpoint（与 `model-entitlements` 的 `r2` 同源，均来自 `active_api_endpoint` 取值器）；
- `${st}` = `/public/platform`；
- 带 `Bearer`，**实时透传、未缓存**。

即 `vip-check` 当前已是「active endpoint + `/public/platform` + Bearer」形态，且能工作。原方案把三件套"对齐"的提法不准确：**`vip-check` 实际最规整**，`model-entitlements` 走 `/user/`（非 `/public/platform`），`/user/info` 走 `ut`（base 同源于 active endpoint，非固定 localTool）。三者形态本就不一致，需分别处理，而非统一"对齐到 localTool"。

### 7.3 【盲点】`handleProxy` 不支持 GET 转发，原 §4「复用 /api/proxy」与协议不兼容
原 §3.1 / §五.1 称"复用 `handleProxy` 思路"。源码核实（`localTool/src/routes/system.ts:60-76`）：`/api/proxy` 仅接受两种形态——
1. `X-Proxy-Url` 头 + FormData/Blob（形态①）；
2. `Content-Type: application/json` + body `{url, method, headers, body}`（形态② `handleProxyJson`）。

二者**均为 POST**，且 JSON 形态强制要求 body 含 `url` 字段。**没有 GET + query 转发的形态**。而前端权益接口是 `GET + Bearer`。若直接复用 `/api/proxy` 路由，前端必须从 GET 改为 POST 并打包 body/头 —— 与原 §2 目标"零前端改动"矛盾。
**修正 / 补丁**：§3.1 已说"独立函数"，但未点明"**不能复用 `/api/proxy` 路由本身**"（协议不兼容）。应明确：新增独立 GET 端点（如 `GET /api/user/info`），复制 `handleProxy` 的 fetch/超时/错误透传逻辑，而非挂载到 `/api/proxy`。

### 7.4 【盲点】localTool 无现成 API 响应缓存，缓存需从零写且会叠加前端内存缓存
原 §3.2 / §五.1 把"加缓存"描述得轻量。源码核实：`localTool/src` 全仓仅有**静态文件**的 `Cache-Control`（`index.ts:111/134`），**API 层无任何响应缓存中间件/封装**；KV（`/api/kv/*`）仅用于配置存储（如 `active_api_endpoint`），非响应缓存。
此外，前端 `model-entitlements`（`Ui` 函数，`httpClient` 行 6）已自带内存缓存 `Fi` + `cache:"default"`。新增 localTool 缓存是**第二层**，若 TTL 设置不当（如 300s + 前端内存 300s），权益变更后最长 **2×TTL** 才生效。
**补丁**：①明确缓存走 KV 自建（键入 §3.2 设计）；②TTL 需与前端内存缓存错开/缩短；③权益变更（升级/降级）应提供主动失效接口（如 `POST /api/kv/delete` 清 `entitlements:<token-hash>`），不能只依赖 TTL 自然过期。

> **修正（2026-08-01 第三轮核实）**：经读 `docs/18-KV存储键读写面梳理.md` 确认，localTool KV 用 sql.js 落盘 `~/.maomao-localtool/localtool.db`，且 `admin/import` 会 `DELETE FROM kv` 清空全库（docs/12 §2.3）。**若把权益缓存落 KV，会被 import 误清**，与 §六 KV 冲突同源。故建议改为**进程内内存缓存**（如 `Map<tokenHash, {data,exp}>`，TTL 300s），主动失效用内存 delete 而非 `/api/kv/delete`。这与你（用户）审计"三.4"完全一致。

### 7.5 【重大盲点】本地中转层引入可用性/部署耦合，原方案"减少 CORS"收益论证不足
原 §四把"消除 CORS/证书裸连"作为核心收益。但源码与 `docs/15` 表明：用户能登录、能生图、能拿 `modelApiTokenKey`，说明**官方 base（含 `0.1mao.cc`/`1mao.16iai.com`）当前在国内本就可直连**（否则整套产品不可用）。即 CORS/证书并非当前阻断点。
反而新增 localTool 中转层引入：
- **部署耦合**：localTool 必须与前端同机/可达，且其出网需能访问官方（若 localTool 跑在内网/仅代理 Lovart 的环境，官方请求会连不上）；
- **单点故障**：localTool 挂 → 权益接口全挂 → 可能连带拖累同走 `active_api_endpoint` 的链路（见 7.6）；
- **延迟叠加**：多一跳转发。
**补丁**：§四应补"前置条件——localTool 出网可达官方"与"localTool 可用性 SLO"，并重新论证收益（主要价值应是**可观测/降级兜底/来源统一**，而非"解决连不通"）。

### 7.6 【盲点·已实证闭环】`active_api_endpoint` 影响面（聊天/生图/视频默认即落 localTool）
原 §3.3 曾担忧"改 `active_api_endpoint` 设成本地会污染聊天/生图/视频等其它链路"。源码实证结论（2026-08-01）：

- `endpointConfig` 的 `active_api_endpoint` 取值器 `function n()` **默认返回 `http://127.0.0.1:18080`**（localTool），官方三地址（`1mao.cc` 等）仅为候选列表 `s()`，需用户/配置切换才生效。
- 聊天 `Bl(\`${n4}/v1/chat/completions\`)`、生图 `${V2}/v1/draw/completions`、视频 `${e3}/v1/videos` 的 base 均来自 `Mn()`（= `active_api_endpoint` 取值器），**默认即 18080**。词频佐证：`Mn()` 在 httpClient 出现 28 次、`proxyMode` 14 次——即聊天/生图/视频（内置模型）默认全走 localTool:18080。
- 第三方 API（用户自填 endpoint）走任务对象的 `e3.apiUrl`（如 `sd2VideoApiUrl`/`videoApiUrl`）直连，**不经过本地 `Mn()`**，与本地聊天/生图路径并存。

**结论（推翻原担忧）**：把 `active_api_endpoint` 经 KV 设为 `18080` **无副作用**——它本就默认 18080，聊天/生图/视频（内置）本就该走 localTool。原 §7.6「会全链路崩」的风险不成立，应撤销。
**真实风险只剩一个**：用户若在 UI 把接入点从默认（18080）切到官方候选（`1mao.cc`），权益请求才会真去官方，此时仍需 §3.1 路由让 localTool 接管。实施前应枚举 `Mn()`/`Je`/`r2` 的全部消费点形成清单（此动作保留，但目的从"防污染"改为"确认默认态 + 识别 UI 切换场景"）。

### 7.7 【盲点】中转层错误语义未定义，前端两处 catch 行为不一致
原方案未规定 localTool 新端点在官方返回 401/403/5xx 时的**响应形态**。源码核实前端两处容错逻辑不同：
- `model-entitlements`（`Ui`）：失败则 `Ni=[]`、`Fi=undefined`，**静默回退**（权益列表空，不弹错）；
- `vip-check`（`ar`）：失败返回 `{allowed:false, message:"VIP 校验失败"}`，**硬性拦截**。
若 localTool 统一返回 `502`/`504` 或 `{success:false}`，两处 catch 行为不同：权益侧会"永远空列表"，会员侧会"永远 allowed:false"。属**静默降级**，用户无感知根因。
**补丁**：规定中转层错误时**透传官方原始状态码与 body**（不要包成 502），或统一返回 `{success:false, code, message}` 与前端两处 catch 对齐；并在 §3.4 日志里区分官方错误 vs 本地错误。

### 7.8 【安全盲点】Bearer 不得进日志/落库（现状已较安全，须保持纪律）
原 §3.4 仅说"沿用 `[proxy]` 日志格式 + `[official]` 前缀"。经独立审计核实（`system.ts` 第 184/329 行的 `[proxy]` 日志）:现有日志**只记 `method + targetUrl + status + 耗时`,未记录请求头/Authorization**;且存在 `SILENT_LOG_PATHS` 静默机制。即**现状代码并不泄露 Bearer**,原 7.8"可能被记入"属合理前置防御但措辞略夸大。
**修正补丁**:official 端点日志**沿用现有不记 header 的纪律**,明确"只记 `method + path + status + 耗时 + token 前缀(前4位)`,绝不记完整 Bearer、绝不落库"。重点不是"新增脱敏",而是"保持与 `handleProxy` 一致的 header 零记录纪律,勿在新增 official 端点时破例"。

### 7.9 【盲点】`vip-check` 是否需要迁移需单独论证，不宜默认"三件套一起迁"
结合 7.2：`vip-check` 当前已走 active endpoint + `/public/platform` + Bearer 且工作正常。原 §3.1 把它列入"迁到 localTool 新端点"，但迁移收益不明确、且会改动一条本就正常的链路（增加回归风险）。
**补丁**：在 §五 实施前，先回答"vip-check 迁移动机是什么"——若仅为"统一入口"，优先级应低于 `model-entitlements`（后者确实裸连、收益最大）。建议实施顺序调整为：①先迁 `model-entitlements`（裸连 → 中转+缓存，收益最大）；②补 `/user/info`（覆盖 `ut` 与 `_t` 双链，见 7.1）；③`vip-check` 视统一入口需求再定，不强制首轮迁移。

### 7.10 核实小结（哪些原论断被源码支持）
- ✅ 支持：`localTool/src` grep 权益接口 = 0 命中（确实无拦截）；`model-entitlements` / `vip-check` 走官方 base；`active_api_endpoint` 由 KV 决定；`/public/platform/*` 在 localTool 不存在（README 已确认）。
- ⚠️ 需修正：`/user/info` 双链（7.1，已勘误 base 归属）；`vip-check` 已规整（7.2）；`handleProxy` 协议不兼容 GET（7.3）。
