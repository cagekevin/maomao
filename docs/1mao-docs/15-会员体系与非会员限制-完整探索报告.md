## 1. 会员数据模型

### 1.1 会员等级枚举

来源 `dist/assets/httpClient-BknZwXjG.js` @ 427119：

```js
function Bs(e2){ return e2==="VIP" || e2==="SVIP" || e2==="UNLIMITED"; }
```

这是**全局唯一**的等级判定函数。`FREE` 不在白名单内 → 被拒。

### 1.2 会员对象结构

前端 state（`App-BX6o9fW5.js`，变量 `_i`，setter `vi`）：

```js
{
  type:   "FREE" | "VIP" | "SVIP" | "UNLIMITED",
  expiry: <毫秒时间戳>,
  code:   <会员码>
}
```

默认值出现在 3 处，均为 `{type:"FREE", expiry:0}`。

### 1.3 用户对象（`/user/info` 返回）

```js
{
  userId, username, phone, nickname, avatar,
  membershipType,          // ← 等级
  membershipExpiryDate,    // ← 到期毫秒
  hasUnlimitedMembership,  // ← 无限会员布尔位
  balance,                 // ← 特惠币余额
  modelApiTokenKey,        // ← 服务端下发的真实 API Key
  hasPassword
}
```

> **关键**：`modelApiTokenKey` 是**服务端根据会员等级下发的真实调用凭据**（与下方 §1.4.1 的 token 同源，均由 `/user/info` 提供）。这就是为什么"改前端解锁"无效——没有有效 key，请求到不了模型。

### 1.3.1 四个等级 + `hasUnlimitedMembership` 的实际差异（原文未澄清）

文档 §1.1 列出 `FREE/VIP/SVIP/UNLIMITED`，但**没说它们到底差在哪、以及 `hasUnlimitedMembership` 布尔位参与哪条判定**。静态分析补充如下（基于混淆代码中的使用点，非官方文档）：

- **`FREE`**：`Bs()` 白名单外 → 被拒。所有付费能力入口关闭；模型权益走 `Vi()` 兜底 `denied`。
- **`VIP` / `SVIP`**：进入白名单，解锁 AI 应用节点与 AI 助手面板；模型权益按 `/user/model-entitlements` 下发的**逐模型 `access` + `callLimit`** 精细化放行（§2 限制③）。`callLimit` 与 `usedCount` 决定 `quota_exceeded`。
- **`UNLIMITED`**：等级白名单内；语义上"全模型无配额"，但**是否真的跳过 `callLimit` 取决于服务端下发的数据**——前端 `Vi()` 只读 `Ni`（远程权益表），本地并不为 `UNLIMITED` 写死"全部 allowed"。即：**`UNLIMITED` 的"无限制"是服务端赋予的，不是前端等级名自带的光环**。
- **`hasUnlimitedMembership`（布尔位）**：这是**独立于 `membershipType` 字段**的另一把钥匙。它出现在 `/user/info` 返回体与会员渲染逻辑中，用于"无限会员"标签展示与部分**全局免配额**判断（例如某些原本按 `callLimit` 计数的能力，在该位为 `true` 时跳过计数）。但**它同样不绕过 §4.3 的服务端墙**——它的真假由 `/user/info` 下发，前端伪造不了。
  - ⚠️ 模糊点保留：混淆产物中 `hasUnlimitedMembership` 与 `membershipType:"UNLIMITED"` 是否为同一事实的两种表达（冗余双写），还是存在"类型=SVIP 但无限位=true"的组合，静态分析**无法 100% 确认**，需抓包 `/user/info` 真实响应才能定论。

> 📌 结论补充：**前端没有任何一处把 `type==="UNLIMITED" || hasUnlimitedMembership` 当"全放行"硬编码**；所有放行都回溯到远程 `Ni` 表或远程 vip-check。这与 §4.1 结论一致——"前端改不出真权限"。

### 1.4 本地缓存

`localforage` key = `membership`（常量 `B.MEMBERSHIP`），另有 `old_membership` 备份位。

加载逻辑（`App-BX6o9fW5.js`）：

```js

  if(e3){
    let t3=Date.now();
    e3.expiry>t3 ? vi(e3) : (vi({type:"FREE",expiry:0}), z.remove(B.MEMBERSHIP));

```

**离线兜底**：`/user/info` 连续失败时，保留缓存会员（只要 `expiry > now`）：


> ⚠️ 这是**唯一一个不需要改代码的软肋**：直接往 localforage 写一条 `{type:"UNLIMITED", expiry:<远期>}`，在断网时前端会认它。但联网后 `/user/info` 一返回就被覆盖，且不影响服务端鉴权。

### 1.4.1 鉴权 Token 的来源 / 存储 / 刷新频率（原文盲点，影响"断网兜底能撑多久"）

拦截②（`ar()` 远程 vip-check）和权益拉取（`Ui()`）都依赖 `We()` 取出的 token。补充机制：

- **来源**：token 由 `0.1mao.cc` 的 `/auth/login-phone` / `/auth/login-password` 登录后下发（Bearer 凭据）；其登录态与 `modelApiTokenKey` 同由 `/user/info` 一并返回（字段结构见 §1.3），前端存于 localforage / 内存 state。
- **存储**：与 `membership` 类似走本地 KV（`localforage`），但** token 与会员态是两个独立字段**——token 过期 ≠ 会员过期；`modelApiTokenKey` 与 `membership` 同为 `/user/info` 下发的独立字段（见 §1.3）。
- **刷新触发**：`We()` 取的是当前有效 token；`/user/info` 的拉取挂在 `refreshCounter`（§4.3①）上。静态分析**未定位 `refreshCounter` 的具体自增周期**（是定时 `setInterval`、路由切换、还是手动触发），因此：
  - **断网兜底的"安全窗口"无法精确量化**——它取决于"两次 `/user/info` 成功调用之间的最大间隔"。若 `refreshCounter` 仅在用户主动操作/切页时自增，则断网期间本地会员态可一直保留；若是固定 `setInterval`（如每 N 秒），则窗口约为一个周期。
  - 抓包或定位 `refreshCounter` 的赋值点才能给出确切数字。本报告将其标记为**待补盲点**，不臆测数值。

> 📌 实务含义：想在"不改 `src/bundle/`"前提下用离线兜底，必须**长期断网 + 不触发任何会重拉 `/user/info` 的操作**，且会员的**真实业务能力仍受 token 有效性约束**（token 过期则 vip-check / 权益接口全失败，前端即便认了本地会员也调不动模型）。

**⚠️ 此处链路的澄清（原文盲点）**：限制①的"前端拦截"明确在 `httpClient` 内 `return`（不发请求），这点清楚。但"服务端二次校验"那段（`i3.ok` / 402 / 403）**到底是谁在返回 402/403，原文没说清**，补充如下：

- 根据 `CLAUDE.md` 的分层铁律，**画布业务请求的唯一出口是 `localTool :18080 /api/proxy` → 网关 `:9004` → Lovart**（需 VPN）。AI 应用节点（rhWebappNode）的真实生图/生视请求**也走这条链路**，而非前端直连 `0.1mao.cc`。
- 然而 §3 / §5 已用 grep 证明 **`localTool` 与 `apimart-gateway` 源码中 0 处会员代码**，所以 402/403 **不是自研后端返回的**。
- 由此推断：402/403 要么（a）来自请求经 `localTool` 代理后**仍命中官方服务器**（例如任务提交接口本质上由 `0.1mao.cc` 侧的 `/workflow-apps` 等承接，localTool 只是透传），要么（b）由 Lovart 侧按携带的 `modelApiTokenKey` 鉴权后回绝。
- **静态分析无法 100% 区分 (a)/(b)**：要定论必须抓包"AI 应用节点提交任务时的真实 Host"。本报告保留"402/403 是真正的墙、且不受前端控制"的结论，但**撤回任何"该请求一定直连 0.1mao.cc"的隐含假设**——它与 CLAUDE.md 的"唯一入口"铁律并不矛盾，因为 `0.1mao.cc` 与 Lovart 在该功能上可能是同一后端的不同暴露面。

**位置**：`dist/assets/App-BX6o9fW5.js`

|---|---|
| 校验中 | `"校验会员状态..."`（脉冲动画） |
| `enabled===false` | `"VIP 专属功能"` + `"AI 助手为 VIP/SVIP 会员专属功能"` + **「开通会员」按钮** |
| `allowed && enabled!==false` | 正常渲染聊天界面 |

「开通会员」按钮跳转：

```js

```

> 📌 这是**纯远程判定**，前端没有任何本地兜底。`ar()` 返回什么就信什么。

**⚠️ 补充澄清（原文盲点，已静态核实）**：AI 助手**不是纯前端功能，它强依赖后端 agent 能力**。仅把面板显示出来 ≠ 能用。

1. **它是什么**：`canvas-assistant` 是一个挂在画布上的"智能体/Agent"，前端常量 `var fr="canvas-assistant"`，工具集 `var sr={'canvas-assistant':or}`。它的工具（`or`）能直接操作画布：`list_nodes` / `list_edges` / `get_node_details` / `create_node` / `update_node`——即能读画布、建节点、改节点参数，是"会动手"的助手，而非纯问答。

2. **聊天请求打到官方后端（非自研）**：面板聊天由 `xr` 组件内的 `dr()` hook 发起，真正发请求的是 `dr` 里的 `v2()`：
   ```js
   fetch(`${Je}${st}/agent/${encodeURIComponent(t2)}/chat`, {  // t2 = "canvas-assistant"
     method: "POST",
     headers: { Authorization:`Bearer ${i3}` },               // i3 = 登录 token
     body: JSON.stringify({ model:f2, messages:[...],
                           tools:cr(t2), tool_choice:"auto",
                           stream:true, temperature:0.6 })
   })
   ```
   请求 URL 即 `https://0.1mao.cc/agent/canvas-assistant/chat`（SSE 流式）。**这个接口在 `0.1mao.cc` 上，本项目的 `localTool` / `apimart-gateway` 源码中 0 处 agent/chat 代码**（§3 grep 已证），所以它是**官方 SaaS 能力，不在自研范围内**，且与生图/生视的 `localTool→Lovart` 链路是**两条完全不同的后端**。

3. **当前 dist 中面板 `open` 被硬编码为 `false`**：画布主组件里以 `<xr agentKey="canvas-assistant" ... open={false} .../>` 渲染，且传给画布的 context 也是字面量 `agentPanelOpen:false`。即：面板组件存在、`ar()` 仍每 30 秒轮询一次 vip-check，但**可见入口被写死关闭**——普通用户界面上看不到可点开的 AI 助手面板。

4. **"打开"也救不了**：即使绕过 `open:false` 把面板显示出来，它仍会先调 `/agent/canvas-assistant/vip-check`（非 VIP 直接显示"VIP/SVIP 专属"）；即便 vip-check 通过，聊天还要调 `/agent/canvas-assistant/chat`——该接口由官方提供，自研后端并未实现，**没有它面板就是空壳，发消息必失败/401**。

> 📌 结论：AI 助手是**官方账号体系下的 SaaS Agent 能力**（vip-check + chat 双接口都在 `0.1mao.cc`），自研后端既不提供也不参与。想"用上"需官方 VIP/SVIP 账号 + 官方服务可用；想"自研等价物"才是在 `localTool` 侧新写 agent 服务（符合 §5 推荐路线），而非撬开官方面板。

```js
/审核|违规|敏感|涉黄|涉政|安全|拦截|blocked|moderation|safety|content[_ ]?policy|policy violation|prohibited|nsfw|sensitive/
```

用于把服务端错误归类成"计费类 / 权益类 / 审核类"，决定是否重试、是否切模型。**改它没用**，它只读不判。

> 📌 **审核类链路的澄清（原文盲点）**：第三组正则（`/审核|违规|涉黄|涉政|...|moderation|safety|nsfw|sensitive/`）说明服务端**确实存在内容审核**，但这是**业务执行层（Lovart 侧）的返回**，不是会员体系的一部分，也**不经过 `0.1mao.cc` 的会员判定**。
> - 走自研后端（`localTool → Lovart`）的请求同样可能收到审核类错误——因为**审核发生在 Lovart 执行端**，与"你是否是会员"无关。
> - 因此"审核类错误"**不受会员状态影响，也不受本报告的任何前端改动影响**；它属于另一套独立的内容安全机制，文档此前把它和会员限制并列易产生"审核也是会员墙"的误读，特此澄清。

## 4. 要"通过所有会员设置"，改哪里？

### 4.1 前置结论（必须先看）

> **前端改动只能骗过 UI，骗不过服务器。**

## 9. 补充核查：localTool `/api/proxy` 是否过手官方请求（2026-08-01）

> 本节纠正一份早期口头推断（"localTool 的 `/api/proxy` 已具备代理任意官方请求的能力，官方请求已进 localTool 只是没接管"）。**该推断不成立**，核查后结论如下。

### 9.1 确凿结论（静态分析已验证）

**结论 1：X-Proxy-Url 通道仅对「带文件上传」的请求触发。**

`dist/assets/httpClient-BknZwXjG.js` 中统一请求函数 `Bl(e2,t2)` 的实测逻辑：

```js
async function Bl(e2,t2){
  let n2 = t2.body instanceof FormData;   // 仅当 body 是 FormData
  let r2 = t2.body instanceof Blob;       // 或 Blob
  if(proxyMode==="local-tool" && (localPort||localToolBaseUrl)){
    let i3 = localToolBaseUrl;
    if(!e2.startsWith("http")&&!e2.startsWith("data:")&&!e2.startsWith("blob:")){
      return fetch(`${i3}/api/files/read?path=...`);   // 本地文件 → files/read
    }
    try{
      let a3;
      if(n2||r2){   // ★ 关键：只有带文件上传才走 localTool 代理
        let n3=new Headers();
        n3.set("X-Proxy-Url", e2);
        n3.set("X-Proxy-Method", t2.method||"POST");
        a3 = await fetch(`${i3}/api/proxy`, {headers:{X-Proxy-Url:e2,...}});
      } else {
        a3 = await fetch(e2, {...});   // ★ 否则直接 fetch 原始 URL（直连官方）
      }
    }
  }
}
```

**结论 2：普通 JSON 类官方请求在 local-tool 模式下直连官方，不经过 localTool。**

以下请求均为 JSON body（非 FormData/Blob），因此走 `else` 分支直接 `fetch(e2)`：
- `/agent/canvas-assistant/vip-check`（拦截②，`ar()` 函数）
- `/agent/canvas-assistant/chat`（AI 助手聊天）
- `/user/info`（会员态刷新）
- `/user/model-entitlements`（模型权益，拦截③）
- `/auth/login-*`（登录）

**结论 3：`0.1mao.cc` 仅作为默认基址字符串出现一次。**

`dist/assets/App-BX6o9fW5.js`：`let Dn2="https://0.1mao.cc";` 且 `kn2(l2.url)` 会从配置（sync/default 或设置）覆盖。`0.1mao.cc` 全仓库仅此 1 处硬编码字面量。

### 9.2 不确定项（静态分析无法 100% 定论，已诚实标注）

- `${Je}${st}/agent/...` 中的 `Je` 基址运行时值：追踪链 `Je→ct→m→Nt→oe(vendor-Z)`，vendor 内 `oe` 无显式 `=` 赋值、也无 `0.1mao.cc` 字面量，混淆层层重命名无法静态定论其最终值。两种可能：(a) 运行时 = `0.1mao.cc`（默认/配置下发）；(b) 运行时 = localTool 地址（若配置把 base 改本地）。
- **但无论 `Je` 指向谁，因结论 1，JSON 请求是 `fetch(e2)` 直连，不经过 `/api/proxy` 接管逻辑**——所以 `Je` 的值不影响"localTool 是否过手 JSON 官方请求"这一结论。

### 9.3 对"迁移到自研 localTool"方案的影响（修正）

| 早期口头推断 | 修正后 |
|---|---|
| "官方请求已进 localTool，只需加路由映射接管" | ❌ 错误。JSON 类官方请求直连官方，localTool 只接 FormData/Blob 上传类 |
| "localTool 已具备接管能力" | ⚠️ 仅对**带文件上传**的请求成立（如 AI应用节点若用 FormData 提交，确实经 `/api/proxy`） |
| AI应用节点能否不经改 `src/bundle/` 就被 localTool 接管 | **取决于其提交 body 类型**：FormData/Blob → 经 localTool（可接管）；纯 JSON → 直连官方（localTool 碰不到，必须改 `src/bundle/` 让那些请求也走 localTool 才能改指向） |

**修正后的前提**：要让 localTool 接管官方 JSON 能力，要么改 `src/bundle/` 让那些请求也走 `/api/proxy`（需先补 localTool 路由），要么在 localTool 侧新增对应端点并改前端指向（同样需改 `src/bundle/`）。不能假设 localTool 已经过手所有官方请求。

### 9.4 待补盲点（下一步核查项）
