## 一、问题现状（已确认）

官方 1mao 平台有「🎬视频去字幕」功能卡片，前端展示为「系列 / 1 个模型 / 权益不够」。三个事实：

1. **功能卡片能显示** → 前端功能系列列表是从官方接口动态拉取的（经 localTool 透传 `passthrough`/官方权益层），不是前端硬编码。链路通。
2. **"权益不够"** → 来自官方 `model-entitlements` / `vip-check` 判定（后端权威源）。localTool 只做透传，不伪造权限。
3. **localTool 自研兜底清单 `BUILTIN_MODELS` / `BUILTIN_MODEL_SERIES` 里没有"视频去字幕"**（见 `localTool/src/routes/platform.ts`），但那是"调不通官方时"的兜底，正常情况下前端走官方透传，不读这份清单。

> 📌 **补充（澄清模糊点）**：此处需精确化两点——
> - 该兜底清单（`/public/platform/builtin`、`/public/platform/models`）**目前只登记图像/视频/特惠视频的内置模型 id**（如 `gpt-image-2`、`seedance-2`、`kling-v3-omni`），**根本不含任何"智能体/去字幕"类条目**。所以"没有视频去字幕"不是漏登记，而是该清单的设计范围就只覆盖生图/生视频模型，与"功能卡片"是两套数据（详见 §一第1点：卡片来自官方 `passthrough` 透传，而非这份本地清单）。
> - 这份清单**仅在"自托管模式、前端 base 指向 18080 且官方不可达"时**才被前端读取（见 `localTool/src/routes/platform.ts` 文件头注释）。在正常 `proxyMode=local-tool` 但官方可达时，前端功能系列列表来自官方透传，**这份本地清单不参与渲染**。故 §二的 `platform.ts` 登记动作（条目 3）属"增强项"，且只在自托管路径下有意义。

**结论**：这是一个"官方有、本地未接管、且被官方权益拦截"的功能。B 方案的核心是——**在 localTool 本地实现去字幕能力，并让前端把这个功能当成"本地支持"来渲染与调用，绕过官方权益层**。

## 四、本地去字幕能力实现（videoSubtitle.ts）

去字幕本质是「去掉视频里的硬编码/软字幕」。**只看功能可用性（用户诉求），不追求 100% 完美**：

### 方案 A（推荐，硬字幕压制）—— 适用于"烧录"在画面上的字幕
用 `ffmpeg` 对视频做**模糊/裁剪遮罩**覆盖字幕区域：
- 底部条状模糊：`ffmpeg -i in.mp4 -vf "delogo=x=W*0.1:y=H*0.88:w=W*0.8:h=H*0.1:show=0"` 或 `gblur`/`boxblur` 局部模糊；
- 或黑条覆盖（简单粗暴但稳）：`drawbox` 把字幕区涂黑。
- 输出回灌到约定的结果格式（对齐 `apimart-gateway` 的 `videos[].url` / 画布读 `t.data[0].url` 契约，见 `docs/16`）。

> ⚠️ **审计批注（命令参数有误 + 用语自相矛盾）**：
> - 本段标题/正文说"**模糊**字幕区域"，但给出的命令是 `delogo`。`delogo` 的作用是**插值消除**（基于周围像素重建）而非"模糊"——这是两类完全不同的视觉处理。若意图是"模糊"，应使用 `gblur`/`boxblur` 的裁剪区域（`crop`+`gblur` 或 `sendcmd` 局部模糊），而不是 `delogo`。文档把二者混为一谈会造成实现歧义。
> - `delogo` 的 `show` 参数取值为 `0/1/2`（0=不显示边框、1=显示边框、2=仅处理首帧并显示），**`show` 不是坐标/模糊强度**；文档用 `show=0` 仅表示"不画线框"，可保留，但需说明语义。
> - 命令中 `x=W*0.1` 等写法：`delogo` 的 `x/y/w/h` 必须用**整数像素**（或 `iw/ih` 表达式），`W*0.1` 这种浮点乘积在多数 ffmpeg 版本里需要写成 `iw*0.1` 并经 `floor`/`trunc` 取整（如 `x='trunc(iw*0.1)'`），否则部分版本报错。建议改用明确整数或 `iw/ih` 表达式。
> - 结论：方案 A 应明确"模糊派（`gblur`/`boxblur` 局部）"与"消除派（`delogo`）"二选一并给正确命令，不要同时写"模糊"又给 `delogo`。
>
> ✅ **排查结论（2026-08-06）**：批注全部成立。落地时应二选一并给出正确命令：
> - **模糊派（推荐用于"去字幕"，视觉为涂花字幕区）**：底部条状模糊用 `ffmpeg -i in.mp4 -vf "crop=iw:ih*0.12:0:ih*0.88,gblur=sigma=20" ...`（注意 crop 后需先缩放回原尺寸或直接 `drawbox`+`gblur` 组合；最稳的是 `sendcmd`/`geq` 局部处理，但复杂度高）。简单稳做法：`drawbox` 黑色遮罩。
> - **消除派（`delogo` 插值重建）**：`delogo` 用 `x/y/w/h` 整数像素，示例 `delogo=x=trunc(iw*0.1):y=trunc(ih*0.88):w=trunc(iw*0.8):h=trunc(ih*0.1):show=0`。`show=0` 仅表示不显示诊断线框。
> - 若追求"真消除"，`delogo` 对纯色背景的台标/字幕有效，但对复杂动态画面下的字幕可能留下残影——应以实际测试为准。文档应明确实现时二选一，不再混写。

### 方案 B（软字幕轨剥离）—— 适用于外挂/内嵌文字轨（SRT/MOV_TEXT）
`ffmpeg -i in.mp4 -sn -c copy out.mp4` 直接丢弃字幕流，无损快。
→ **优先检测**：若视频含软字幕轨，直接走 B（秒级）；否则降级到 A（模糊）。

## 五、权益层放行（official.ts 改法）

仿 `handleOfficialVipCheck` 中 `canvas-assistant` 的处理（`official.ts` L288-297）：

```ts
// 本地放行「视频去字幕」智能体：不依赖官方会员判定，属自研能力
if (agentId === 'video-subtitle-remover' && process.env.VIDEO_SUBTITLE_LOCAL !== '0') {
  res.writeHead(200, { 'Content-Type': 'application/json' });
  res.end(JSON.stringify({ allowed: true, reason: 'local video subtitle remover' }));
  console.log(`[official] ${ts} | GET ${url.pathname} | 200 | LOCAL allow (video-subtitle-remover)`);
  return;
}
```

> 注：`model-entitlements` 是 GET 全量权益清单，**不建议伪造**（会影响其他官方功能判定、且前端可能按列表渲染）。只放行 `vip-check`（单点、实时、不缓存）即可让"点击时"通过，符合"重点能用上、权益判断不重要"的诉求。

> ⚠️ **审计批注（代码错误 + 引用精度）**：
> - **`ts` 变量未声明（运行期 ReferenceError）**：L111 `console.log(\`[official] ${ts} | ...\`)` 引用了 `ts`，但本段代码块内**从未声明 `ts`**（原版 `canvas-assistant` 分支在 `official.ts` L288-297 也没有 `ts` 变量，日志里用的是内联 `new Date().toISOString().replace(...)`）。直接复制本片段会导致 `ts is not defined`。修正：把日志改成内联时间，或在该 `if` 块顶部加 `const ts = new Date().toISOString().replace(/[-:]/g, '').slice(0, 14);`（注意：本方案 §四/§五开头"仿写"片段里出现过 `const ts` 声明，但此处未带，需二选一保持一致）。
> - **L288-297 段归属正确**：实测 `official.ts` L288-297 确为 `canvas-assistant` 分支（L288 `if (agentId === 'canvas-assistant')`、L295 构造 `data`、L296 `return res.json(...)`），"仿写"指向无误。但需指出：原版返回体是 `{ allowed, reason, data:{ allowed, remain, total, timestamp, signature } }`（经 `res.json`），而本片段改用 `res.writeHead(200)+res.end(JSON.stringify({allowed:true,reason:...}))`——**返回结构与原版 `canvas-assistant` 不一致**。前端 `vip-check` 是否只认 `{allowed:true}` 还是要求 `data.allowed`，需对齐 `official.ts` 里正常 `vip-check` 成功分支的字段，否则前端可能仍判定"不可用"。
> - **返回结构 vs 开头承诺不符**：文档第二行说"仿 `canvas-assistant` 的处理"，但给出的代码既改了返回方式（writeHead/end 而非 res.json），又去掉了 `data`/`signature` 字段，又用了未定义的 `ts`。建议实现时严格对齐 `official.ts` L288-297 原版的返回形状，仅把 `agentId` 条件扩展为 `|| 'video-subtitle-remover'`。
>
> ✅ **排查结论（2026-08-06，已实证定论）**：
> - **`ts` 未声明问题：属实**。`official.ts` L295 实际用内联 `new Date().toISOString().replace('T',' ').slice(0,19)`，无 `ts` 变量。文档 §五示例代码 L111 引用未声明的 `ts` 会报 ReferenceError，必须修正（改为内联时间或声明 `const ts`）。
> - **返回体结构断言：需纠正（原批注判断有误）**。批注称"原版返回体是 `{ allowed, reason, data:{...} }`"，但实测 `official.ts` L292-297 的 `canvas-assistant` 分支**实际返回就是 `{ allowed: true, reason: 'local canvas assistant' }`**（`res.writeHead(200)` + `res.end(JSON.stringify(...))`），**没有 `data`/`signature` 字段**。`docs/27` §3.4 方案二（L358）的本地放行也是同一返回 `{ allowed:true, reason:'local canvas assistant' }`。`docs/15` §2限制② 显示的 vip-check 返回结构是 `{ allowed, enabled, membershipType, displayName, message }`，同样**无 `data:{allowed,...}`**。
>   - 因此：文档 §五示例代码的 `res.writeHead(200)+res.end(JSON.stringify({allowed:true, reason:'local video subtitle remover'}))` **结构与 canvas-assistant 实际实现完全一致**，可直接套用。批注"返回结构与原版 canvas-assistant 不一致"**不成立**。
>   - 但 `docs/27` §10.1 盲点 A 提示：chat 入口只依赖登录态、**不读 vip-check 的 `allowed`**，故 vip-check 放行属"可选优化"而非"必需前置"。对视频去字幕同样需实测其点击入口是否真读 vip-check，避免把放行当作硬前提。
> - **实施建议**：`ts` 改为内联时间；`if` 条件 `agentId === 'video-subtitle-remover'` 扩展为 `|| agentId === 'video-subtitle-remover'`；返回体保持 `{ allowed:true, reason:'local video subtitle remover' }` 即可，与 canvas-assistant 一致，无需补 `data`/`signature`。
