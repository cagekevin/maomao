### 2.1 流水线很慢，必须"后台 detached"跑
`run.cjs` 会对 3 个 DEEP chunk 跑 webcrack（每个几十秒到 1 分钟），整条流水线**总耗时约 5~8 分钟**，**远超交互式命令的 300s 超时**，会被中途杀掉导致 `output/project/src` 为空或残缺。
正确姿势（PowerShell）：
```powershell

Stop-Process -Name node -Force -ErrorAction SilentlyContinue
Start-Sleep -Seconds 2
cd 本文件夹/scripts
Start-Process -FilePath "node" -ArgumentList "run.cjs" `
  -WorkingDirectory "本文件夹/scripts" `
  -RedirectStandardOutput "..\pipe.log" -RedirectStandardError "..\pipe.err" -NoNewWindow
# 然后另开轮询（每次最多 sleep 280s 就回头查，别一次 sleep 超过 300s）：
Start-Sleep -Seconds 280
Get-Process -Name node   # 还有进程 = 仍在跑
Test-Path output/project/src   # 存在 = 已组装完
```
查进度/报错：直接读 `pipe.log` / `pipe.err`（不要用 `Select-String` 把旧缓冲区糊一脸，用 `read_file` 工具看文件最干净）。

关键坑（脚本里已经处理，但你改脚本时要注意）：
- 默认 headless 模式**扩展根本不加载**，必须 `--headless=new` + `--allow-extensions-in-headless-mode`。
- `--load-extension` 的路径必须用**正斜杠**，且**不能是中文路径**（Chrome 静默忽略）。用 junction 到 ASCII 路径最稳。
- `context.serviceWorkers()` 里的 `sw.url` 不是普通字符串，要用 `String(sw.url)` 再正则取 `chrome-extension://xxxx`。
- Playwright 没有 `context.waitForTimeout`，用 `await new Promise(r=>setTimeout(r,ms))`；脚本里有 90s watchdog 防止挂死。
- webcrack/构建是 async 的，脚本里任何一处 `await` 卡住都会挂，watchdog 是保命符。

## 4. 助手踩过的坑（仅供参考，不是方法，别照抄）
1. **别信静态检查当裁判**：用静态脚本判"通过"，结果 9 个产物都绿了却真机全打不开。真机加载结果才是唯一真相。
2. **悬空引用是已知翻车点**：真机报 `X.forwardRef is not a function`、`Oi is not defined`。
   根因（前一任定位）：拆分脚本 `02_split.cjs` 旧版用 `innerPath.scope.hasBinding(name)` 判断依赖，把"模块级 import（如 `Z` 来自 vendor-Z）"误判为"已绑定"而**丢掉**了应有的 `import`，导致组件运行时引用 `undefined`。
   旧版还把每个组件的依赖都漏斗式塞进 `shared.js` 再 `import { Z } from './shared.js'`，形成 `shared.js → 组件 → shared.js` 的**循环依赖**，eval 顺序错就会 `is not defined`。
3. **最小化的"别名 import"被吃掉了**：构建报 `"We" is not exported by vendor-Z-adA07W.js`。
   根因：源码是压缩别名 `import { REALNAME as We } from './vendor-Z'`，旧 split 只存了 local 名 `We` 并生成 `import { We }`，但 vendor-Z 导出的是 `REALNAME`。**所有别名 import 都要保留 `imported as local`**。
4. **import 来源被 webcrack 改写**：webcrack 还原后，有些 import 来源被改成了 `./vendor-Z-...` 但实际原始 chunk 里是 `./rolldown-runtime-...`，而 vendor-Z 并不导出那个符号 → 构建报 "not exported"。
   根因/修法：构建 import 映射要以**原始(未 webcrack) chunk** 为准（`run.cjs` 已把原始 chunk 作为 `argv[4]` 传给 `02_split.cjs`），webcracked 文件只作回退，且**原始必须覆盖**（顺序：先建 webcracked 再覆盖原始，反了就会用错来源）。
5. **保留字当变量名**：报 `Unexpected keyword 'in'`，因为压缩器生成了 `import { _Component0 as in }`，`in` 是保留字不能做 binding。
   修法：`02_split.cjs` 里加 `RESERVED` 集合 + `sanitizeName()`，遇到保留字/数字开头就加 `_` 前缀，并重写组件内所有 `Identifier`/`JSXIdentifier` 引用（脚本已在 `renames` 里实现）。
6. **流水线自带的 `verify-split.mjs` / `verify-dist.mjs` / `fix-build.mjs` 会假绿**，别当裁判。
7. **我曾把某一种修法当成唯一正解写进任务书，害 10 个 AI 全走同一条路——这是我的失误。** 特此更正：**达到目标的方法完全不限**，你可以改流水线任意环节、用任意思路。
8. **React 版本要对齐**：`vendor-Z` 里是 React 19；构建用 Vite `jsx:'automatic'` 会从 node_modules 拉 `react/jsx-runtime`。旧 `run.cjs` 写的是 `^18.3.1`，与 vendor 内 React 19 不一致有风险。前一任已把 `package.json` 改成 `react/react-dom ^19.0.0` + `@types/react ^19`。

# 踩坑与经验汇总（整合 AI01~AI10，按类归档，供参考）

> 以下全部来自 AI01~AI10 十家 AI 的真实记录。按主题分类，每条标注「现象 / 根因 / 已验证可行的修法（来自哪家）」。
> 这是「作业笔记」，不是方法约束，也不构成执行步骤。达到目标的方法完全不限。

## 一、流水线 / 构建期基础设施坑（与代码无关，最容易卡住）

- **webcrack 伪迹 `function X() { [native code] }` 破坏语法**
  - 现象：16 个文件 babel 解析失败（`02_split`/`04_unicode` 抛错）。
  - 根因：webcrack 把方法调用/构造方法替换成原生函数 `.toString()` 文本插进文件，形如 `.function NAME() { [native code] }` 或 `function NAME() { [native code] }(args)`；`NAME==='Object'` 要映射成 `constructor`。
  - 已验证修法（AI06 §6.2）：`scripts/00_sanitize.cjs` 用通用正则清理（覆盖任意 NAME，不只 Object）；`scripts/clean_project.cjs` 在组装完成后再递归终检。验证标准：跑完 grep `function\s+[A-Za-z_$][\w$]*\(\)\s*\{\s*\[native code\]` 应为 0。

- **esbuild `config.esbuild: "loader" must be a string`**
  - 根因：在 `vite.config` 里写 `esbuild: { loader: { '.js':'jsx' } }`，loader 不能传对象 map。
  - 已验证修法（AI06 §6.3）：删掉 loader 对象，改 `esbuild: { jsx: 'automatic' }` + 插件 `force-jsx-for-js`（用 `transformWithEsbuild` 对 `.js` 且非 node_modules 的文件强制 jsx loader）。

- **`.js` 文件里的 JSX 不被编译**
  - 现象：Vite 默认只把 `.jsx`/`.tsx` 当 JSX，`.js` 里的尖括号 JSX 被 import-analysis 拒绝。
  - 已验证修法（AI06 §6.4）：两条路——①用上面的 `force-jsx-for-js` 插件（本项目采用）；②或把含 JSX 的文件改名 `.jsx`。本项目约定「`.js` 用 `X.jsx(...)` 调用式而非尖括号」。

- **`Could not resolve entry "index.html"` / npm 用了父目录 package.json**
  - 双根因：①`run.cjs` 开头 `fs.rmSync(OUTPUT,{recursive,force})` 每次清空 `output/project/node_modules`；②cmd 中文代码页下 `cd /d` 到中文路径静默失败，npm 落在父目录执行。
  - 已验证修法（AI06 §6.9）：用 `scripts/build_project.cjs`，Node 里 `path.resolve(__dirname,'..','output','project')` 定位工程目录再 `execSync('npm install',{cwd})`，绕开 `cd`。习惯：所有 npm/node 命令都用 `cwd`，不 `cd`。

- **Babel 克隆节点作用域错乱 `getBlockParent` 崩溃**
  - 根因：`t.cloneNode` 后直接在原 path 上 `traverse`，作用域路径缓存错乱。
  - 已验证修法（AI06 §6.8）：`emitProgram()` 先 `generate` 成代码字符串，再重新 `parser.parse` 成干净 AST，然后才跑 `renameInAst`。不要直接克隆后 traverse。

- **流水线真实阶段顺序**
  - 已验证顺序（AI06 §6.1）：`⓪ webcrack → ① 01_expand → ①b 00_sanitize → ② 02_split → ③ 03_facade → ④ 04_unicode → ⑤ assemble → clean_project 终检`。关键：①b 必须在 ① 后 ② 前（expand 会重新引入 webcrack 伪迹）；⑤ 后还要再跑一次 `clean_project` 兜底（拆分会再触发 babel 失败）。

- **中文路径在 PowerShell/cmd 参数乱码**
  - 现象：`node run.cjs` 路径含中文时参数被 GBK/UTF-8 错解，报 "Cannot find module"。
  - 已验证修法（AI07 §5.1）：写 ASCII 探测脚本定位目录，或把整个工作区 `Copy-Item` 到 ASCII 路径再跑（node_modules 很大，可只拷 scripts+input+已生成 output）。

- **执行工具 300s 超时 + 杀后台 detached 进程**
  - 现象：webcrack 慢（单 chunk 60~120s），`run.cjs` 超 300s 被杀；用 `Start-Process` 后台分离时，新命令一启动就把后台 `node.exe` 杀掉，日志停在"某 chunk 拆分中"无报错。
  - 已验证修法（AI07 §5.1）：给 `run.cjs` 加 webcrack 展开结果缓存 `.wc_cache`（key=文件名，命中条件 `源 mtime <= 缓存 mtime`），首次种缓存后跳过 webcrack，单次压到 <300s 可前台跑完。

- **真机验证的"假阴性"风险（headless 不暴露 extension target）**
  - 现象：headless Chrome 不暴露 extension target，HTTP 服务 `dist/` + 注入 `chrome` 全局 stub 兜底可能掩盖部分真实 extension API 报错。
  - 记录（AI07 §5.1）："verify 报零错"不等于 `chrome://extensions` 真机零错，最终仍建议人工真机加载确认。

## 二、拆分悬空引用类（核心翻车点）

- **根因：依赖分析用 `scope.hasBinding` 误杀模块级绑定**
  - 现象：真机 `Z.forwardRef is not a function` / `Oi is not defined`；生成 134 个 `.jsx` 文件零 import。
  - 根因：`02_split` 用 `innerPath.scope.hasBinding(name)` 比对原始单文件作用域，任何在原始顶层声明过的标识符（React 别名 `Z`、组件名 `Oi` 等）都被误判"已绑定"→ 不生成 import；拆成多模块后这些绑定消失 → 悬空引用。
  - 已验证修法（AI01 B1 / AI05 §4.1 / AI07 §5.2.1）：重写为完整 free-variable 分析——沿作用域链走到 `programScope` 判断是否为本地绑定，非本地才入依赖；按"其它组件(默认 import) / shared.js 模块绑定(具名 import) / 未解析(TODO)"三类注入。

- **别名 import 被吞 `"We" is not exported by vendor-Z`**
  - 根因：压缩源码 `import { REALNAME as We }`，旧 split 只记 local 名生成 `import { We }`，但 vendor 导出的是 `REALNAME`。
  - 已验证修法（AI01 B2）：`importMap` 同时存 `imported`（真实导出名）与 `local`，生成 `import { REALNAME as We }`，JSX 引用走同一套。

- **import 来源被 webcrack 改写（rolldown → vendor-Z）**
  - 根因：webcrack 把部分 `from './rolldown-runtime'` 改写成 `from './vendor-Z'`，vendor-Z 不导出那个符号。
  - 已验证修法（AI01 B3）：`run.cjs` 把**原始 chunk** 作为 `argv[4]` 传给 `02_split.cjs`；`buildImportMap` 先建 webcracked 再被原始覆盖（顺序很重要）。

- **保留字当变量名 `Unexpected keyword 'in'`**
  - 根因：压缩器产出 `import { _Component0 as in }`。
  - 已验证修法（AI01 B4）：`RESERVED` 集合 + `sanitizeName()`（加 `_` 前缀），生成前用 `traverse` 把组件内所有 `Identifier`/`JSXIdentifier` 引用一并改名。

- **JSX 标签名是 `JSXIdentifier`，普通 `Identifier` visitor 不遍历**
  - 现象：真机 `Oi is not defined`（`Oi` 是 `<Oi/>` 组件引用，出现在 `Jo.jsx/bo.jsx/_o.jsx/Zo.jsx`）。
  - 根因：依赖收集只挂 `Identifier` visitor，JSX 标签名是 `JSXIdentifier` 节点，Babel 默认不把它当归 `Identifier` 遍历 → 漏收集。
  - 已验证修法（AI05 §4.1 / AI07 §5.2.2）：加 `JSXOpeningElement` visitor 收集 JSX 标签名与 `JSXMemberExpression` 根名，维护 `INTRINSICS` 集合（HTML/SVG 标签）确保永不视作 import。

- **反向悬空引用 `Oi.displayName`（shared 引用已拆组件）+ 扫描循环漏掉 shared.js**
  - 现象：真机 `ReferenceError: Oi is not defined`（at `httpClient-Bqba_SHR.js`）；`shared.js` 残留 `Oi.displayName='ResizableTextarea'`。
  - 根因：`fix_refs` 只补 react 与 `./shared.js` 的 import，从不补兄弟 `.jsx` 组件；且扫描循环 `f!=='shared.js'` 把 shared.js 排除，反向引用永远扫不到。
  - 已验证修法（AI03 §6 / AI07 §5.2.4）：读 `component_map.json` 得到「原始名→安全文件名」；对每个 free 标识符若命中 component_map 则加 `import X from './X.jsx'`（默认导入）；**去掉** `f!=='shared.js'` 排除让 shared.js 参与扫描。AI03 实测 81+ 文件获得兄弟组件 import。

- **默认导出组件 `import { Qn }` 应为 `import Qn`**
  - 现象：真机 `Qn is not defined`（暴露 JSX 组件引用 + 默认导出组件两大坑）。
  - 根因：`export default function Qn` 没有命名导出，写 `import { Qn }` 拿到 `undefined`。
  - 已验证修法（AI05 §4.1）：导出表区分 `kind: 'named' | 'default'`，默认导出组件生成 `import Qn from './Qn.jsx'`。

- **跨 chunk 同名别名串味（`Z`/`V`/`Rr` 在不同 chunk 意思不同）**
  - 现象：`Oi.jsx` 本该拿 httpClient 的 `Z`（React），`findDefiner` 因别名碰撞解析到 src chunk 的 `Z`（一个 element 工厂）→ `Z.forwardRef is not a function`。
  - 已验证修法（AI04 §9.4）：`findDefiner(name, fromFile)` 优先在同 chunk（`_components` 目录名）内解析，同 chunk 找不到才去别的 chunk。

- **shared.js 顶层声明没导出**
  - 根因：即使想从本地 shared.js `import { Z }`，若 shared.js 没 `export { Z }` 也导不进来。
  - 已验证修法（AI04 §9.5）：把 shared.js 的 `topLevelDeclared`（非 import 进来的）全部 `export` 出去。

- **GLOBALS 漏浏览器/JS 全局被当悬空引用误报**
  - 现象：`AudioBuffer`/`VideoDecoder`/`EncodedAudioChunk`/`Request`/`Headers`/`Uint8ClampedArray`/`WeakRef`/`FinalizationRegistry` 等被当成悬空引用。
  - 已验证修法（AI04 §9.6）：扩 `GLOBALS` 集合（AI04/AI05 的 fixer 顶部已含较全的清单）。

- **babel `errorRecovery` 偶发误报**
  - 现象：`e19`/`t4`/`i3` 这类是 babel 恢复错误语法时偶尔没绑定的局部变量，属 false positive，真机不会报。
  - 记录（AI04 §9.7）：别被吓到，以真机为准。

- **具名导出收集误把嵌套函数参数当导出名**
  - 现象：Babel 报 `Export 'e2' is not defined` / `has already been exported`。
  - 根因：用 `isBindingIdentifier` 收集时会把 `function tc(e2,t2){}` 的参数 `e2/t2` 收进去；且 `export const X` 形式会重复补 `export { X }`。
  - 已验证修法（AI07 §5.2.5）：按语句类型只收顶层声明名（`VariableDeclaration` 的 declarator id / `FunctionDeclaration`/`ClassDeclaration` 的 id / `export const` 的 declarator id）；`FunctionDeclaration`/`ClassDeclaration` 从 `sharedExportNames` 剔除；`export const X` 不再补 `export { X }`。

- **import 是只读绑定，对导入的 var 做 `++` 崩**
  - 现象：`this._workerTrackId = Wf++` / `Ts++` 运行期报错（import 来的绑定只读，赋值/自增非法）。
  - 已验证修法（AI07 §5.2.6）：`fix-mutators.cjs` 在 shared.js 暴露 `__nextWorkerTrackId()`/`__nextAge()` 等 mutator 函数，调用方改为函数调用并去掉对 `Wf`/`Ts` 的 import。

- **跨模块绑定错配 `_Component32`（move pass 搬走后 shared 仍 export）**
  - 现象：构建报 `Exported variable "_Component32" is not defined in shared.js, but imported by Fn.jsx`。
  - 根因：模块级 `var _Component32 = V.memo(kn)` 被 move pass 搬进 `kn.jsx`，但 shared.js 仍留 `export { _Component32 }` 自身不再定义。
  - 已验证修法（AI07 §5.2.4）：move pass 把"引用了被抽走组件"的语句分两类——成员赋值（`X.displayName`/`.propTypes`）搬进 `X.jsx` 不导出；新建绑定（`var Y=V.memo(X)`）搬进 `X.jsx` 并由 `X.jsx` 具名导出 `Y`，依赖 `Y` 的其它组件改为从 `X.jsx` 具名 import。

- **门面按本地名取用但 shared 导出别名 → `L_ is not exported`**
  - 现象：`03_facade` 生成 `export { L_ as d } from './shared.jsx'`，但 shared.jsx 实际导出的是别名 `d` 不是 `L_`。
  - 已验证修法（AI02 坑1）：`02_split` 生成 shared.jsx 时丢弃所有导出别名 `export { LOCAL as ALIAS }` → `export { LOCAL }`，门面自己负责重新 `as ALIAS`。

- **同一本地名被多个别名复用 → 重复 export**
  - 现象：`Identifier 'L_' has already been declared`。
  - 根因：原 chunk 里 `L_` 被 `export { L_ as d }`/`export { L_ as e }` 复用，剥掉别名后变两条 `export { L_ }`。
  - 已验证修法（AI02 坑2）：跨导出语句做全局去重（`globalSeen` 集合），同一 `local.name` 只保留一条。

- **全局函数被误当模块引用 → `decodeURIComponent is not exported`**
  - 现象：`Vn.jsx` 报 `shared.jsx does not provide an export named 'decodeURIComponent'` 等。
  - 根因：`collectFreeNames` 把 `decodeURIComponent`/`escape`/`encodeURIComponent` 等内置全局误判成自由引用去 import。
  - 已验证修法（AI02 坑3）：`GLOBALS` 集合补全整套 decode/encode/escape/unescape/setImmediate/clearImmediate（注意与已有集合去重）。

- **小写 JSX 标签被当组件 → `div is not exported`**
  - 现象：`Vn.jsx` 报 `shared.jsx does not provide an export named 'div'`。
  - 根因：`collectFreeNames` 的 `JSXIdentifier` 收集对 JSX 标签名一视同仁，`<div>`/`<mesh>`/`<boxGeometry>` 是内置元素不是用户组件。
  - 已验证修法（AI02 坑4）：`JSXOpeningElement` 分支加首字母判断，小写直接 `return`。

- **组件需 shared 的 import 绑定（如 `import Z from 'react'`）→ `Z is not exported`**
  - 现象：组件里 `import { Z } from './shared.jsx'`，但 shared.jsx 只把 import 当本地声明保留没 re-export。
  - 已验证修法（AI02 坑5）：shared.jsx 生成末尾把自身所有 import 的本地绑定追加一条 `export` 兜底（default import 的本地名注意别进命名 `export {}`）。

- **`renameInAst` 误改 import 标识符 → `X is not exported by vendor`**
  - 现象：`✗ "_cmp_Fn" is not exported by vendor-Z-adA07W.js`。
  - 根因：`renameInAst` 把从兄弟 chunk（vendor 导出的 `Fn`）import 进来的名字也重命名成 `_cmp_Fn`，破坏 import 绑定。
  - 已验证修法（AI06 §6.6）：`renameInAst` 遍历时跳过所有 import/export 声明里的标识符（`ImportSpecifier`/`ExportSpecifier`/`ImportDefaultSpecifier`/`ImportNamespaceSpecifier`/`ImportDeclaration`/`ExportNamedDeclaration`/`ExportDefaultDeclaration`）。

- **`Z has already been exported`（shared.js 重复导出）**
  - 现象：打包报 `Z has already been exported`（常出在 httpClient 的 shared.js）。
  - 根因：`02_split` 生成组件后，shared.js 的 re-export 语句和原声明里的 `export` 撞同名。
  - 已验证修法（AI06 §6.7）：用 `originalExported` Set 跟踪所有已导出的 `exported` 名，最后生成 `export {}` 时过滤掉已导出过的。

## 三、React 命名空间 / 实例类

- **`X.forwardRef is not a function`（react 命名空间别名没 import）**
  - 现象：运行时 React 命名空间是 `undefined`。
  - 已验证修法（AI01 / AI05 §4.1 / AI07 §5.2.1）：把 react 命名空间别名补 `import * as X from 'react'`（见下一类 `fiximports` 逻辑）。

- **`d.forwardRef is not a function`（`C` 来自 vendor 是 number 不是 React）**
  - 现象：修到上一步后新报错 `d.forwardRef is not a function`，`d = C as d`（httpClient 的 `shared.js` 里 `import { C as d }`）。
  - 根因：node 实测 vendor 的 `C` 导出是 **number**，只有 `Rr` 是 React 工厂。原始混淆代码里某个模块把 `C` 当成 React 命名空间，拆分时被错误映射到 vendor 的 `C` 导出（而 `C` 不是 React）。
  - 记录与方向（AI04 §10）：定位源码里哪些 `_components/*.jsx`/`shared.js` 出现 `C.`/`d.` 后跟 `forwardRef|useState|createElement|memo|Fragment|useEffect` 等 React API，统一重定向到真正的 React（`Rr` + interop，或本 chunk 的 `Z`）。vendor 内 React 是单例内联，`Rr` 是工厂，`interop(Rr(),1)` 才是 React 实例，`C`/`Fr`/`Ir`/`Dr` 都不是 React。

- **多 React 实例 / Invalid hook call（`H` 为 null，dispatcher）**
  - 现象：页面渲染 `Cannot read properties of null (reading 'useState')` / dispatcher `H` 为 null。
  - 根因：原始混淆产物把**自己的一份 React** 打包进 httpClient chunk（含 `react_production`/`ReactSharedInternals`），拆分后的组件走 npm react 19 → 两份实例，renderer 设的 dispatcher 在组件用的那份上是 null。
  - 已验证修法（AI05 §4.4，两步缺一不可）：①`vite.config.ts` 加 `resolve.dedupe:['react','react-dom']` + `manualChunks` 把 `node_modules/(react|react-dom|react-dom-client|scheduler)` 强制并入单一 `react-vendor` chunk；②改写两个入口文件（`src/bundle/main-1TOrc0Z5.js`、`share-CymbjOw4.js`）的 bootstrap，把混淆 react-dom（`Ir`/`Fr` from vendor-Z）换成 npm 的 `react-dom/client`、`react/jsx-runtime`、`react`。验证：`ReactSharedInternals` 在整份 dist 里应只出现一次（在 react-vendor）。

- **react 命名空间自动识别，但 `document.createElement` 被误抓**
  - 现象：扫描 `MemberExpression` 时 `document.createElement` 的 `createElement` 命中 `REACT_APIS`，生成 `import * as document from 'react'`，把真全局 `document` 覆盖，真实 DOM 操作崩溃。
  - 已验证修法（AI05 §4.2）：`REACT_APIS` 集合（`forwardRef,useRef,useState,useEffect,useMemo,useCallback,useImperativeHandle,useContext,useReducer,useLayoutEffect,createElement,createContext,Fragment,memo,lazy,Suspense,StrictMode,cloneElement,isValidElement,Children,Component,PureComponent,version`…）配合 `GLOBALS` 白名单（`document/window/self/globalThis` 等）跳过；import 注入插在最后一个已有 import 声明之后避免 TDZ。

- **React 19 升级**
  - 已验证修法（AI05 §4.5 / AI06 §6.12）：`package.json` 锁 `react:^19`/`react-dom:^19`/`@types/react:^19`；`vite.config` 用 `jsx:'automatic'`。`forwardRef` 在 19 仍可用（deprecated 不报错）。React 是单例内联在 vendor 里（无 `from 'react'`），运行时已是 vendor 自带 React 19。

## 四、压缩 / 构建碰撞类

- **esbuild 压缩重命名碰撞 `n.getElementById is not a function`**
  - 现象：源里明明 `document.getElementById`，压缩后 esbuild 把全局 `document` 重命名为 `n`，而 `n` 恰好又是某导出 `U_ as n`（`U_` 是 GET 函数）→ `n` 指向函数 → "is not a function"。
  - 根因：纯构建期产物，源是正确的。
  - 已验证修法（AI05 §4.3）：`vite.config.ts` 里 **`minify: false`** 彻底消除碰撞。代价是产物体积变大，但不违反拆分约束。

- **`fixdom.cjs` 是错误方向（已废弃）**
  - 现象：想扫 `MemberExpression` 把 DOM 别名 `LOCAL as X` 替换成 `document as X`，结果误伤 `window/self`（真全局），且抓不到 `n`（源里是 `document.getElementById` 字面量，压缩产物里才出现 `n.getElementById`）。
  - 记录（AI05 §4.5）：遇到压缩碰撞直接按上一条关 minify，别走这条路。

## 五、真机验证类（唯一真相）

- **静态脚本假绿**
  - 记录（AI01/AI04/AI06）：流水线自带的 `verify-split.mjs`/`verify-dist.mjs`/`fix-build.mjs`、任何"数文件数/grep import"的脚本都会假绿，9 个产物绿了真机全挂。**唯一真相是真机 Chromium 加载 + 捕获 console + pageerror + service-worker 异常**。

  - 现象：`EXT_ID=(none)`，扩展根本加载不到。

- **分析器 `unresolved` 列表 90% 是误报**
  - 记录（AI03 §4.7）：JSX 属性名（`active`/`open`）、对象字面量 key（`HTMLImageElement`）、WebCodecs `VideoFrame` 属性（`codedWidth`）等被当成未定义自由标识符，从没断过构建。**只有确实出现在真机运行期调用栈里的符号才需要修**。

## 关键脚本：`C:\Users\xinye\Downloads\yimaomao\A21\pipeline\fix_esm.cjs`

对 `output/project` 递归后处理（排除 node_modules/dist/.git），一次性根治真机/构建期五类坑：

- **A. `cleanArtifacts`** — 清 webcrack 伪迹 `function NAME() { [native code] }` → `NAME`（兼容空格/内嵌，如 `new Date(x).toLocaleString()`）。
- **B. `fixConstructorArtifact`** — webcrack 把 `constructor(...){super(...)}` 错写成 `Object(...){super(...)}`，还原为 `constructor`（babel `errorRecovery` 解析）。
- **C. `fixImportAssignments`** — `import { X }` 后对 `X` 赋值/自增是 ESM 非法（"Cl is an import"）；改写为 `import * as _shared` + `_shared.X = r2`。
- **D. `exportSync`** — `shared.js` 顶层声明与导出不同步时，从 body 重算导出列表（彻底杜绝 `X is not exported`）。
- **E. `fixExtractedComponentRefs` + `fixDanglingImports`**（最终版，三处关键修正）：
  - `fixExtractedComponentRefs` 读**同级 `component_map.json`**（原始名→文件名，如 `"I_": "I__1"`），把父文件里对原始名 `X` 的引用（`X` 与文件名可能不同）改写为 `_cmp_<FILE>` 并补 `import _cmp_<FILE> from './<FILE>.jsx'`，同时剔除 dangling 误加的 `import { X } from './shared.js'`。覆盖 `<X/>`、`<X.Member>`（如 Context 的 `<_r.Provider>`）、函数调用三种形态。
  - `fixDanglingImports` 补「未绑定且确属同级 `shared.js` 导出」的标识符 import，并**额外收集 JSX 成员表达式对象位置**（`<_r.Provider>` 的 `_r`），且跳过 `component_map` 里的原始名（避免与 E 冲突）。
