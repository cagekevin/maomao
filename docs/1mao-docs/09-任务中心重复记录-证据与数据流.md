# 任务中心「历史记录重复」现象 —— 证据与数据流记录

> 目的：把截至 2026-07-31 已确认的事实、真实数据、代码调用链如实记录，供后续排查。
> 本文**只陈述证据，不提修复方案**。所有「推测」均已明确标注。

---

## 一、现象（用户描述 + 实测）

- 用户现象：每次打开画布时，任务中心（点时钟图标按钮打开）里「最新的历史记录」会变成很多条重复项。
- Playwright 实测任务中心界面：显示 `20 / 126`，列表里每条都是同一条文本聊天记录（"你好"），时间完全相同（`2026/7/31 09:58:45`）。
- 用户补充：
  - 「资源里的生成」只有 1 个（正常）。
  - 「日志（任务中心）」里显示多条，每条图片/内容都一样。
  - 新任务（正在生成的）正常，一旦进入历史就重复。
  - 改成同步模式（异步同步改造）后，所有历史都会出现此问题。

## 二、后端真实数据（Node 原生 fetch 直连 `127.0.0.1:18080` 获取，非浏览器）

### 1. `GET /api/tasks?page=1&pageSize=200`
- `total = 126`
- `items` 实际返回 **126 条**记录
- 每条关键字段：
  - `taskId`：形如 `1785471739121`、`1785471642618`（13 位毫秒时间戳，每条不同）
  - `nodeId`：**全部相同** = `promptNode-1785470157337-xxwpv`
  - `type`：全部为 `chat`
  - `prompt`：全部为 `你好`
  - `status`：全部为 `completed`
  - `createdAt`：每条不同（对应不同时刻）
- 结论（已确认）：**SQL 任务库里确实存了 126 条记录，且每条 taskId 都唯一**，它们来自同一个 nodeId、同一条 prompt。

### 2. `GET /api/kv/get?key=globalTasks`
- 返回 `null`（空）
- 结论（已确认）：任务中心**不读** `globalTasks` 这个 KV。

### 3. KV key 列表
- 未找到任何含 `task`/`history`/`log`/`gener` 的 KV key。
- 结论（已确认）：任务中心列表数据**不是**来自前端 KV 持久化，而是直接来自 SQL `/api/tasks`。

## 三、与「资源里只有 1 个」的矛盾解释（推测，待确认）

- 用户说「资源里的生成只有 1 个」，但 SQL 有 126 条同 nodeId 记录。
- 推测：资源界面按 `nodeId`（或 `result_url`）去重后只展示 1 个；任务中心按 `taskId` 全量列出，于是出现 126 条。
- 此推测**尚未通过代码核实**，仅用于解释表面矛盾。

## 四、代码调用链（写入路径）

### 后端（localTool，TypeScript）
| 位置 | 函数 | 作用 |
|------|------|------|
| `localTool/src/routes/tasks.ts:57` | `upsertTask` | 按 `task_id` 去重：`DELETE FROM tasks WHERE task_id=?` 然后 `INSERT`。**去重键 = task_id** |
| `localTool/src/routes/tasks.ts:725` | `handleTasksBatchSave` | 接收 `POST /api/tasks/batch-save`，遍历调用 `upsertTask` |
| `localTool/src/routes/tasks.ts:780` | `handleTasksSave` | 接收 `POST /api/tasks/save`（单条） |
| `localTool/src/routes/tasks.ts:380` 附近 | `handleTasksGet` | 返回 SQL 任务列表（`total` + `items`） |

> 注意：`upsertTask` 的去重逻辑本身没问题——它按 `task_id` 删了再插。问题在**传入的 `task_id` 每次都是新的**，导致去重永远不命中，每次都变成 INSERT 新行。

### 前端（dist 混淆代码，已用 `script/format.js` 格式化为 `script/output.js`）
| 格式化后位置（对应 `dist/assets/App-BX6o9fW5.js`） | 内容 |
|------|------|
| `output.js:1484` | `fetch(`${Mn()}/api/tasks/batch-save`, POST)`，即批量写入入口 `batchSaveTasks` |
| `output.js:1535` | `diffAndPersistTasks`（变量名 `dr`）：用 `new Map(e.map(e => [e.id, e]))` 按 `e.id`（=taskId）做新旧 diff，只把「变化的或新增的 id」push 进待保存数组，再调用 batch-save |

- `batch-save` 的**实际调用点**在 `dist/assets/httpClient-BknZwXjG.js`（该文件内 `api/tasks/batch-save` 出现 1 次）。App.js 里只有定义、没有调用。
- 监听 `mutiwindow-task-completed` 的 `addEventListener` 也在 `httpClient-BknZwXjG.js`（约字符偏移 891009 处，格式化后约 `output.js:46007`），其处理函数对该事件做的是 **`map` 更新已有任务**（按 `nodeId` 匹配改字段），不是 `push` 追加。

## 七、小结（仅事实，无结论）

后端 SQL 库中存在 **126 条同 nodeId、同 prompt、但 taskId 各不相同的 completed 记录**。这些记录由前端经 `batch-save` 写入，后端按 `task_id` 去重但因 taskId 每次都新而失效。任务中心直接展示 SQL 全部记录 → 出现大量重复；资源界面可能另有去重 → 显示正常。

根因定位还差最后一步：**找到前端生成 taskId 并触发 `batch-save` 的具体代码位置**，确认它是「每次打开重新生成 taskId」还是「同步逻辑 bug 导致重复调用」。
