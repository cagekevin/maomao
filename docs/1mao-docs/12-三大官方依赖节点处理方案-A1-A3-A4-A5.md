## 1. A1 画布助手（canvas-assistant）

### 1.1 调用证据
- 默认 agent id：`ar(e=\`canvas-assistant\`)`（前端 `App-BX6o9fW5.js`）。
- 聊天函数 `v`（onGenerateAgentChat）：
  - 组装 `messages`（system=`g.current`，用户消息带 `image_url` 附件）+ `tools: cr(t)`（画布工具：`list_nodes` 等）+ `tool_choice:'auto'` + `stream:true`。
  - 请求：`POST ${Je}${st}/agent/${id}/chat`，头 `Authorization: Bearer <token>`、`Accept: text/event-stream`（**SSE 流式**）。
  - 响应按 SSE 解析，处理 `tool_calls` 并继续多轮。
- 权限校验：`ar()` → `GET ${Je}${st}/agent/${id}/vip-check`，返回 `{allowed, message}`。
- 基础地址：`Je` = `ct as Je`，来自 `endpointConfig`（官方接入点，如 `https://www.1mao.cc` 或 `154.219.102.152:3012`）；`st = '/api'`。即 **请求命中官方服务器**。

> **`Je` 重定向机制澄清（关键）**：`endpointConfig` 中真正给 Agent 用的 base 是「active api endpoint 取值器」（`g()`/`r()`），它**不是写死的**，而是按 `sessionStorage('active_api_endpoint')` → `KV('active_api_endpoint')` → 默认官方地址 的优先级取。也就是说，`Je` 的最终值由 **KV `active_api_endpoint`** 决定。因此在 `proxyMode=local-tool` 下让 A1/A4 这类专属调用回落 localTool，**无需改前端**：只需 `POST /api/kv/set` 把 `active_api_endpoint` 设为 `http://127.0.0.1:18080`（或在非扩展模式下，endpointConfig 会把 `127.0.0.1` 自动替换成 `window.location.hostname`）。这与「前端黑盒无法改」不矛盾，原「手动把 `Je` 指向 18080」的说法不准确。

> ⚠️ **待运行时确认**：上述 `Je` 取值优先级（sessionStorage→KV→默认）、`canvas-assistant` 默认 agent、以及 `vip-check` / `agent/{id}/chat` 路径，均来自对混淆 `dist/assets/App-BX6o9fW5.js` 的逆向解读；在可读源码 `script/`（及 localTool 源码）中**全仓搜索 `canvas-assistant|active_api_endpoint|vip-check|canvas/state` = 0 命中**，即无任何源码印证。落地前务必实测：先 `POST /api/kv/set active_api_endpoint=http://127.0.0.1:18080`，再用 DevTools 观察 Agent 请求是否真落到 `127.0.0.1:18080`；若不命中，说明实际优先级与本文推断不同，需改前端而非只写 KV。

### 1.2 难点分析
画布助手是官方「服务端 Agent」：
1. 需要 LLM（函数调用）决定画布操作；
2. 需要**在服务端执行画布工具**（list_nodes、增删节点等）——但画布状态在**客户端**，服务端无法直接改客户端画布，官方是靠一套「画布状态同步 API」实现。
3. 还有 `vip-check`（会员/VIP 校验）。

因此**完整自托管 = 重造官方 Agent 服务 + 画布操作后端**，工作量极大。

### 1.3 处理决策
- **方案 R（推荐，中等工作量）— 本地轻量 Agent**：
  - localTool 新增路由 `/api/agent/{id}/vip-check`：返回 `{allowed:true}`（可结合 `membership` KV 做真实校验）。
  - localTool 新增 `/api/agent/{id}/chat`（SSE）：接收 `messages+tools`，转发到网关 `/v1/chat/completions` 跑 LLM；对**只读类**画布工具（如 `list_nodes`）通过画布状态接口返回；对**修改类**工具返回「该操作需官方环境」提示。
  - 效果：自研下画布助手可「对话 / 查画布结构」，但不执行破坏性修改。
  - 路由指向：见 1.1 的 `Je` 重定向机制澄清——**不需要手动改 `Je`**。只要 KV `active_api_endpoint` = localTool 地址，agent 的 `/api/agent/*` 请求自然落到 localTool。localTool 只需暴露 `/api/agent/*` 即可。

> **方案 R 的两处待补细节（已细化，落地前必须完成）**：
> - **① 工具清单 `cr(t)` 如何抓取**：`cr(t)` 是前端在 `onGenerateAgentChat` 里构造 `tools` 数组的函数，藏在 `dist/assets/App-BX6o9fW5.js`。抓取步骤：在 bundle 中搜索 `canvas-assistant` 的 chat 函数（文中 `v`/`onGenerateAgentChat`），定位其把 `cr(t)` 的结果赋给 `tools:` 的位置，把返回值（一组 `{type:'function', function:{name, description, parameters}}`）dump 出来，逐项标注 `readonly`（如 `list_nodes`、`get_node`、`read_canvas`）/ `mutate`（如 `add_node`、`delete_node`、`update_node`）。**注意**：因前端混淆，函数名 `cr` 可能已被二次改名，须以「`tools:` 的实参」为锚点反查，而非死找 `cr` 字样。标注结果决定分流：readonly → 走画布状态接口（见下）；mutate → 返回「需官方环境」提示。
> - **② 「画布状态接口」的真实障碍（关键，原稿一笔带过）**：localTool 是**服务端**，画布节点图在**客户端浏览器内存**中，二者默认不通。所以「新增 `GET /api/canvas/state`」路由本身好写，但**它没有数据来源**——除非满足以下任一前提，否则 `list_nodes` 等只读工具仍无数据可回：
>   - (a) 前端已存在「画布变更 → 推送到某 KV」的同步通道（实现前需抓包确认是否有 `canvas_state`/`nodes` 类 KV 被写入；当前 `index.ts` 未发现此类路由，故**大概率不存在**）；
>   - (b) agent 的 `/chat` 请求体里前端已附带当前画布快照（需核对 `messages`/`extra` 字段——本文未确认）；
>   - (c) 在 front-end 黑盒无法改的前提下，只能由用户在打开画布助手前手动 `POST /api/kv/set canvas_state <JSON>` 注入快照（笨但可行）。
>   **结论**：方案 R 对 A1 不是「中等工作量」，而是**被「服务端看不到客户端画布」卡住**。除非抓包证明 (a) 或 (b) 已存在，否则本地 Agent 只能「对话 + 识别工具意图」，但只读工具也回不了真实画布数据。落地前务必先抓包确认 (a)/(b)。
- **方案 F（最小，标记官方专属）**：保持走官方，自研模式下该节点明确不可用，在 UI/文档标注「画布助手为官方功能」。
- **建议**：先 F 过渡，R 作为后续增强。

## 2. A3 工作流节点（workflow-apps）

### 2.1 调用证据
前端用 `ut()`（= `Me`，即 **localTool 客户端**，base `http://127.0.0.1:18080/api`）发起：
- `ut('/workflow-apps/licenses/mine')` — 我的授权列表
- `ut('/workflow-apps')` — 工作流列表（筛 `isOwner` 取 `appId/appName`）
- `ut('/workflow-apps/${appId}')` — 单个工作流定义（取 `access.canRun`、`appName`、`description`、`visibility`）

### 2.2 难点分析
- localTool **当前确实缺绝大多数** `/api/workflow-apps*` 路由。需修正：代码里已有一个 stub——`GET /api/workflow-apps/by-project/:id`（`handleWorkflowAppsByProject`，实际固定返回 `{success:true,data:null,_meta:{stub:true}}`，并非 400），但**列表 `GET /api/workflow-apps`、单条 `GET /api/workflow-apps/:appId`、授权 `GET /api/workflow-apps/licenses/mine` 这三条都还没有** → 列表/打开必报错（前端 `catch` 后提示「加载失败」）。这才是「自研下打不开」的根因。
- 工作流「执行」（跑节点图）需要工作流引擎，属官方 app-store 能力，难以完整复制。

### 2.3-补充：数据「怎么进 KV」
- **导入入口已确认（校正原稿「需新增解析」的说法）**：localTool 的 `POST /api/admin/import`（`localTool/src/routes/admin.ts` 的 `handleAdminImport`）接收 `{ data: { kv:[{key,value,updated_at}], tasks:[...], resources:[...] }, confirm:true }`，**直接把 `kv` 数组逐条写进 KV 表**。因此 `workflow_apps`（以及 A4 的 `app_assets`）**无需任何特殊解析**——只要官方导出的数据以 KV 形式存在（key=`workflow_apps`），随 `kv` 数组一起导入即自动落库。推荐做法：用户从官方导出工作流 JSON 后，把它包成上面的 `kv` 数组（或单独 `POST /api/kv/set` 写 `workflow_apps`）提交即可。

> ⚠️ **`admin/import` 两点限制（已核对 `admin.ts`）**：
> 1. **`tasks`、`resources` 也是必填**：`handleAdminImport` 校验 `!src.kv || !src.tasks || !src.resources` 才放行（line 107），只传 `kv` 会直接 400；可为空数组 `[]`。
> 2. **导入会清空全部已有 KV（破坏性）**：导入前先 `DELETE FROM kv`（line 113），再逐条插入本次 `kv` 数组。若此前已用 `POST /api/kv/set active_api_endpoint`（A1 回落机制）或设想的 `sd2_video_base`（A5 方案 K）写入 KV，**一次导入会把它们一并删掉**。
> 因此 A3 数据导入**主路径应改用 `POST /api/kv/set` 单键写入**（不会清空），`admin/import` 仅适合「整机重置式」导入并事先备份全部 KV。

**原稿说的「增加对 `workflow_apps` 类型的解析」是多余的**，替代方案「新增 `POST /api/workflow-apps` 带鉴权写 KV」也不是必须。无论哪种，前端「我的工作流」读的是 `GET /api/workflow-apps` + `licenses/mine`，与写入端解耦。

### 2.3 处理决策
- **方案 R（推荐，低-中工作量）— 本地工作流库**：
  - localTool 新增：
    - `GET /api/workflow-apps` — 读 KV `workflow_apps`，返回数组。
    - `GET /api/workflow-apps/:appId` - 读单条定义。
    - `GET /api/workflow-apps/licenses/mine` - 返回 `[]` 或本地授权记录。
  - 数据来源：用户从官方导出的工作流 JSON 存入 KV `workflow_apps`，作为「我的工作流」。
  - 效果：节点能列出并打开用户自己保存的工作流。
  - 执行：若无引擎，运行时提示「工作流执行需官方环境」。
- **方案 F**：标记不支持。
- **建议**：直接做 R（路由很轻，KV 即可），先做「能打开/能看」，执行后续再说。

## 3. A4 资产节点（app-asset）

### 3.1 调用证据（部分已确认）
- 前端 `ut('/...')` 调用清单**只有** workflow-apps 与 `/user/info`，**未发现** `ut('/app-asset')` 或 `asset` 类 API 调用。
- 结合原断点总表（A4 = app-asset，官方 app store 资产），推断资产节点**走官方 base（同 A1 模式）**，经 `Je`（官方）而非 localTool。
- 前端无 `assetNode`/`appAsset` 字面量，UI 文案可能非「资产」二字。
- **局部已确认（利好）**：资产「上传」路径 localTool 其实**已经接住了**——`localTool/src/index.ts` 已注册 `POST /api/upload/app-asset` 与别名 `POST /api/assets/upload`（均走 `handleUpload`）。所以资产上传大概率已可用/兜底；真正悬而未决的是资产**列表 / 打开**端点（读 `app_assets` KV 的那条），目前谁也说不清真实路径。

### 3.1-补充：抓包确认方法（落地可执行）
打开资产节点面板时，在浏览器 DevTools → Network 过滤以下关键字，记录真实请求路径与响应形状：
- 路径候选：`/api/app-asset`、`/api/app-assets`、`/api/assets`、`/api/my-assets`、`/api/user/assets`；
- 同时观察该请求的 `base`：若 base = localTool（18080）则只需补读 KV 路由；若 base = 官方（走 `Je`），则还需走 1.1 的 `active_api_endpoint` KV 重定向（同 A1）。
抓到真实路径后，仿 A3 在 localTool 加 `GET` 对应路由读 `app_assets` KV 即可。

### 3.2 处理决策
- **先抓包确认**：打开资产节点面板，在 DevTools → Network 记录真实请求路径与 base（候选见 3.1-补充）。
- **确认后同 A3 落地**：在 localTool 加 `GET /api/app-asset`（或抓到的真实路径），读 KV `app_assets`，**建议返回形状**（对齐 A3 工作流字段风格，便于前端复用同一套渲染）：
  ```json
  { "success": true, "data": [ { "id": "...", "name": "...", "type": "...", "url": "...", "thumbnail": "...", "updatedAt": 0 } ] }
  ```
  单条 `GET /api/app-asset/:id` 返回对应对象；让节点至少能列出/打开本地资产；执行/运行类能力标记官方专属。
- **base 归属决定重定向方式**：抓包时同时看该请求的 base——若为 localTool（18080），补读 KV 路由即可；**若为官方 base（走 `Je`）**，则直接复用 A1 的 `active_api_endpoint` KV 重定向机制（把 `active_api_endpoint` 设成本地），无需新机制。鉴于 3.1 已推断 A4 走官方 base，大概率走后者，故 A4 的落地关键其实是「确认真实路径 + 复用 `Je` 重定向」，而非另起炉灶。

## 4. A5 sd2Video 节点（直连 kkidc）

### 4.1 调用证据（httpClient-BknZwXjG.js，已按源码逐行核对）

> **注意**：原稿把素材转换写成「按类型调 `/Image`、`/Video`、`/Audio`」是**错的**，且把两种凭证混为「SD2 素材库 Token」一种也**不准**。以下为核对后准确版。

sd2Video 有**两处** kkidc 直连，且涉及**两组不同凭证**：

1. **素材转换** `Cr()`（把素材 URL → kkidc 素材 ID）：
   - base：`let i = d || 'https://ai.kkidc.com'`（`d` = 可配置 base，来自「SD2 素材库」配置；若含 `ai-api.kkidc.com` 自动规整为 `ai.kkidc.com`）。
   - **实际调用**：`POST ${i}/api/assets/upload`（**不是** `/Image`、`/Video`、`/Audio` 三个端点）。
   - 请求头：`Authorization: <W>`（**W =「SD2 素材库 Token」，原始 token，无 Bearer 前缀**），`Content-Type: application/json`。
   - 请求体：`{ url: <素材URL>, asset_type: 'Image'|'Video'|'Audio', name: <文件名> }`。
   - 响应取素材 ID：`res.data.Id || res.Id || res.id`，最终前端拿到 `asset://<Id>`。
2. **视频生成提交**：
   - base：`let C = (d || 'https://ai-api.kkidc.com').replace(/\/$/,'')`。
   - **提交**：`POST ${C}/v1/video/generations`，头 `Authorization: Bearer <f>`（**f =「SD2 视频大模型 API Key」，带 Bearer 前缀，与上面的 W 不是同一凭证**）。
   - 请求体：`{ model: 'seed-2'(默认), prompt: <文本>, metadata: { reference_images, reference_videos, reference_audios, generate_audio, ratio, duration, watermark:false } }`。
   - 响应取任务 id：`res.task_id || res.id`（前端记为 `L`）。
3. **轮询**（前端自行轮询，注意与网关方案的关系见 4.3）：
   - `GET ${C}/v1/video/generations/${L}`，头 `Authorization: Bearer <f>`、`Accept: */*`。
   - 响应形状（**关键，后端必须原样返回给前端**）：`{ code:'success', data: { status, data:{ content:{ video_url } }, fail_reason } }`，其中 `status ∈ {SUCCESS/succeeded, IN_PROGRESS/running, FAILED/failed}`；成功时取 `data.data.content.video_url`。

> 即 sd2Video base **默认兜底为 kkidc 双地址**（`script/output.js:48553` `C=(d||'https://ai-api.kkidc.com')`、`:48366` `i=d||'https://ai.kkidc.com'`）+ 两组凭证，仅在 kkidc 可达时工作；kkidc 不可达即挂。
>
> **⚠️ 已核实的传输路径（修正「绕过中继」旧论）**：在默认 `local-tool` 代理模式下，sd2Video 的 `Bl(T, {... ...Ee})` 调用（`script/output.js:48613,48622`）会把 `proxyMode` 等经 `...Ee` 传入；`Bl`（`script/output.js:27473`）判定 `proxyMode==='local-tool'`（默认，`:45822`）且存在 `localPort/localToolBaseUrl` 时，将请求改发到 `localTool/api/proxy`；`localTool/src/routes/system.ts:141` 的 `handleProxy` 对 `X-Proxy-Url`（即 kkidc 地址）**原样 `fetch` 转发、不做协议转换**。因此：浏览器**不再直连** kkidc（走了 localTool 中继），但中继的上游**仍是 kkidc 外部服务**——sd2Video 能跑通的前提是 **kkidc 从 localTool 侧可达**，响应仍是 kkidc 协议形状；它**并未统一到自托管 Lovart 网关**。这与 `docs/13`「已改道」方向一致，但 `docs/13`「不命中 kkidc」措辞不准——kkidc 仍被命中（由 localTool 代发）。详见 4.3 冲突定论。

### 4.2 网关现状（关键）
`apimart-gateway/main.py` **已有** sd2Video 的兼容路由：
- `POST /v1/video/generations` → `_submit_generation(VIDEO)`（代码注释明确「兼容画布 sd2Video 节点（单数 video）」）
- `GET /v1/video/generations/{gen_id}` → `get_task`（轮询，注释「G2: sd2Video 节点轮询」）

**但**：这两条路由内部按 **Lovart 协议**处理（按模型名路由到 `generate_video_*`，用 Lovart token）。而 sd2Video 发送的是 **kkidc 协议**（素材 ID、模型 `seed-2`）。因此**若把 sd2Video 的 base 改为指向网关（而非 kkidc），网关会按 Lovart 协议返回，与前端期望的 kkidc 形状不匹配而解析失败**——必须让网关真正「说 kkidc 话」。
>
> 注：当前默认路径是「base=kkidc（经 localTool 代理透传）」，前端拿到 kkidc 形状响应，故**当前是可用的**；上述「协议不匹配」只发生在「把 base 改指网关」的设想下，也正是 方案 R/K 要解决的问题（把 kkidc 收口进网关）。

### 4.3 处理决策
- **方案 R（推荐，架构正确，中工作量）— 网关接 kkidc 协议**：
  - 在网关 `/v1/video/generations`（及 poll 路由）内加 kkidc 适配器：当模型为 kkidc 系（`seed-2`/`seedance`）或请求带 kkidc token 时，**整条走 kkidc，不走 Lovart 分支**：
    1. 用素材库 Token（W，原始值、无 Bearer）调 `ai.kkidc.com/api/assets/upload` 做「素材 URL → ID」转换（对应前端 `Cr`）；
    2. 用视频 Key（f，`Bearer`）调 `ai-api.kkidc.com/v1/video/generations` 提交，取 `task_id`；
    3. 网关内部轮询 `ai-api.kkidc.com/v1/video/generations/{id}`；
    4. **把结果按前端期望的 kkidc 形状返回（见 4.1 第 3 点）**：提交返回 `{ task_id: <kkidcId> }`（或 `{ id }`，前端读 `task_id||id`）；轮询返回 `{ code:'success', data:{ status, data:{content:{video_url}}, fail_reason } }`。**不要用 Lovart task 结构**——原稿「包成 Lovart 兼容结构复用 get_task」是**错的**：sd2Video 前端自己轮询并只认 kkidc 形状，喂 Lovart 形状会导致解析失败。
  - 把 sd2Video 的 base 在 `api_configs` 配成网关 `http://127.0.0.1:9004`（即写死 kkidc 双地址的那两处 base，改为指向网关；前端会照原协议把请求打到网关，由网关转 kkidc）。
  - 收益：「一切走中继」成立，token/重试/兜底统一管控，且 kkidc 不可达时网关可返回明确错误而非前端超时。
  - 注意：Lovart 系视频（非 seedance）仍走原 Lovart 分支，互不影响（按模型分流）。
- **方案 K（最小改动，先落地）— 参数化 base（前置已核对，结论见下）**：
  - **前置已核对 `apiConfigs.baseline.json`**：该文件是「按 provider 列出模型」的结构（`apiConfigs[].models[]`），**不是扁平 key/value 配置**，所以 `sd2_video_base` 这类字段本就不该直接塞进 baseline.json。原稿「确认 api_configs 已暴露」不成立；但 sd2Video 读取 base 的位置也**尚未定位**——4.1 提到 base 来自「SD2 素材库配置」，这个配置点在前端哪里（KV key？apiConfigs 某 provider 字段？）需**抓包或搜 bundle 确认**，与 A4 同一类问题。
  - **落地方式（推荐，绕开 baseline.json）**：若 sd2Video 的 base/token 是从 KV（类似 `active_api_endpoint` 机制）读取，则直接用 `POST /api/kv/set` 写入以下 KV 键即可重定向，无需改 baseline.json：
    - `sd2_video_base` = `https://ai-api.kkidc.com`（视频生成/轮询 base `C`）
    - `sd2_asset_base` = `https://ai.kkidc.com`（素材转换 base `i`）
    - `sd2_asset_token`（W，原始值无 Bearer）、`sd2_video_key`（f，带 Bearer）
    - 若前端不读 KV 而只读 apiConfigs，则需在 baseline.json 对应 provider 下加 `config` 子对象承载这些键，但仍需先确认前端读取路径。
  - **✅ 与 `docs/13` 的冲突（已核实定论，非「粒度不同」）**：本文此前称「两文档不矛盾，只是粒度不同」是**误读**；经核对源码，**两文档各错一半，现可定论**：
    - `docs/13` 第 30、35 行：A5「✅ 已改道」、commit `2db5171` 把 `video/generations` 移出 `?wait=1` 同步注入改异步+轮询、代理模式「经 `localTool/api/proxy`→**不命中 kkidc**…**通**」。其中「已改道/通」方向正确，「不命中 kkidc」措辞**不准**。
    - 本文 4.1/4.2 旧论「sd2Video 默认绕过中继直连 kkidc、协议不匹配必失败」也**不准**：它其实走了本地中继，并未直连；当前默认可用，并非必失败。
    - **核实后的真实链路**（`script/output.js` + `localTool/src/routes/system.ts`）：① sd2Video 提交 `Bl(T,{... ...Ee})`（`:48613,48622`）把 `proxyMode` 等经 `...Ee` 传入；② `Bl`（`:27473`）在 `proxyMode==='local-tool'`（默认 `:45822`）且存在 `localPort/localToolBaseUrl` 时，将请求改发到 `localTool/api/proxy`；③ `handleProxy`（`system.ts:141`）对 `X-Proxy-Url`（即 kkidc 地址）**原样 `fetch` 转发、不做协议转换**。即：**浏览器 → localTool 中继 → 原样转发到 kkidc**。
    - **结论（统一口径）**：sd2Video 在默认代理模式下**经 localTool 中继透传 kkidc**——浏览器不直接连 kkidc，但中继上游仍是 kkidc 外部付费服务；localTool 只做透传，不映射到 Lovart 网关。故：
      1. **当前可用**：只要 kkidc 从 localTool 侧可达，sd2Video 即可跑通（与 `docs/13`「通」一致）；
      2. **仍未真正统一**：它依赖外部 kkidc，未收口到自托管 Lovart 网关——这才是 方案 R/K 要解决的真问题（而非「会失败」）；
      3. `docs/13` 应把「不命中 kkidc」改为「经中继透传 kkidc」；本文旧论「绕过中继/必失败」已删除（见 4.1）。
    - **对方案的真实含义**：方案 R/K 的价值是「把外部 kkidc 收口进网关（网关侧说 kkidc 话 + 统一 token/重试/兜底）」，而不是「修一个会失败的 bug」。若仅想让 sd2Video 在当前环境跑通，**默认代理透传 kkidc 已可用，无需改**。docs/13 已同步修正 A5 行。
  - 文档声明：sd2Video 依赖 kkidc 可达（kkidc 本身是外部付费服务，本就不可自托管，直连在「可配置」前提下可接受）。
  - 局限：未收敛到统一中继，kkidc 挂则挂。
- **建议**：赶时间先 K（确保 base 可配置而非写死）；随后补 R，让视频全链路真正统一中继。

## 6. 风险与注意
- **前端黑盒**：无法改前端，所有方案只能「后端补路由 + 配置指本地」。逐节点确认 base 来源时，A1/A4 的 `Je` 已确认是 KV 驱动的 active endpoint（见 1.1），重定向用 `active_api_endpoint` KV 即可，无需改 `src/bundle/`；其余节点（如 A5 的 sd2Video 双地址）需靠 `api_configs` 参数化 base 或 hosts/代理。
- **`Je` 全局 base 问题（已澄清）**：A1/A4 走官方 base `Je`，但 `Je` 的最终值在 local-tool 模式下可由 `active_api_endpoint` KV 决定（endpointConfig 的 active endpoint 取值器按 sessionStorage→KV→默认官方 取）。因此「local-tool 下专属调用回落 localTool」**已实现路径**，不再阻塞，详见 1.1 澄清。
- **执行类能力**：工作流/资产的「运行/执行」依赖官方引擎，本地兜底只能做到「列出/打开」，执行需标记为官方专属。
- **与本仓库其他缺口的关系**：本文只解决「官方依赖节点兜底」。云端同步（见 `docs/10-*`）、听音 501、剪映发送 stub、安全 CORS/`0.0.0.0` 等不构成此文档范围，但同为「不完美」清单项。
