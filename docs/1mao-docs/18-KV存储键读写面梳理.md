# 18-KV存储键读写面梳理

> 本文档基于仓库当前真实源码梳理 KV 存储能力。
> 核实来源（`localTool` 为后端源码，`dist` 为已打包前端，变量名压缩）：
> - 后端路由：`localTool/src/routes/kv.ts`
> - 后端数据库：`localTool/src/db/database.ts`
> - HTTP 工具：`localTool/src/utils/helpers.ts`
> - 路由注册：`localTool/src/index.ts`
> - 前端存储抽象：`dist/assets/httpClient-*.js`（`Kr`/`Fr` 存储层、`Ar` 键枚举、`jr()` 画布 key 构造）
> - 前端调用：`dist/assets/endpointConfig-*.js`、`dist/background.js`

---

## 0. ⚠️ 最重要：本项目存在「两套完全独立的存储」，必须先分清

AI 阅读本项目时**最容易犯的错误**就是把下面两套存储混为一谈，或误以为 `api_configs` 也走 KV。请务必先读完本节再往下看。

### 0.1 两套存储对比表

| 维度 | A. localTool KV（本文档主角） | B. 前端浏览器存储（localStorage 体系） |
|------|------------------------------|------------------------------------------|
| 所在进程 | 独立的 localTool 服务（Node，端口 18080） | 浏览器扩展 / 网页的 `localStorage` |
| 后端实现 | sql.js（SQLite WASM），文件落盘 `~/.maomao-localtool/localtool.db` | 浏览器内置 `localStorage`（或 `chrome.storage.local`） |
| 访问方式 | HTTP：`GET/POST /api/kv/{get,set,delete}` | 浏览器 JS 直接 `localStorage.getItem/setItem` |
| 跨端共享 | 同一 localTool 实例 ⇒ 共享 | 仅同源/同扩展内，不跨设备 |
| 能否被前端统一封装 | 是（通过 `Kr`/`Fr` 自动路由） | 是（通过 `Kr`/`Fr` 自动路由） |
| 典型 key | `active_api_endpoint`、`canvas-state-<projectId>`、`canvas_pinned_tools` | `api_configs`、`app_settings`、`users`、`projects`、`membership`、`transitResources`（注意！）等 |
| 是否云端同步 | 否 | 否 |

### 0.2 防误判清单（给后续 AI 的硬约束）

1. **`api_configs` 不走 KV。** 它是前端 `Ar` 键枚举里的 `localStorage` 键（`httpClient` 中 `API_CONFIGS:"api_configs"`），由 `Wr` 存储层（`get/set/remove` 底层 `localStorage`）读写。文档旧版曾把它列为 KV 键，是错误。
2. **`localToolBaseUrl` 不走 KV。** 它存于浏览器扩展 `chrome.storage.local`（`dist/background.js` 的 `getLocalToolBaseUrl`），用于前端找到 localTool 服务的地址。它甚至不是数据，而是「服务地址配置」。
3. **`transitResources` 也不走 KV。** 它属于前端 `Ar.TRANSIT_RESOURCES`（localStorage 键），前端 `Kr` 存储层里明确把 `transitResources` 路由到 localStorage，而非 KV。
4. **前端有一个统一存储抽象 `Kr`/`Fr`**（`httpClient` 中），它根据 key 自动分流：
   - key 形如 `canvas-state-*` 或 `transitResources` 的**部分画布数据** → 走 localTool KV；
   - 其余（`projects`/`users`/`app_settings`/`api_configs` 等）→ 走 `localStorage`。
   所以"前端调用了存储"≠"走的是 KV"，要看 key 前缀与路由分支。
5. **KV 的 key 在 HTTP 层没有前缀**；前端 `Kr` 写入 KV 时会自动给画布类 key 加上前缀（如 `canvas-state-`）。即 SQLite 里看到的 key 是带前缀的，**接口入参也要带前缀**。
6. **KV 没有 `success/data` 外层包裹、没有 `message` 字段、错误文案是英文**——见第 2 节。凡是文档里出现 `{success:true,data:null}`、`{message:...}`、中文错误文案，都是旧版编造，一律以第 2 节为准。
7. 不要凭"函数名 kvGet/kvSet/kvDelete/createKVTable"去 `database.ts` 找——这些函数在当前 `localTool` 源码中**不存在**，是旧文档虚构。真实函数见第 2 节源码片段（`handleKvGet`/`handleKvSet`/`handleKvDelete`，位于 `routes/kv.ts`）。

## 1. localTool KV 的定位与边界（真实实现）

`localTool` 的 KV 是一套**极简本地键值存储**，只服务于「需要被多端（同一 localTool 实例）共享的少量结构化数据」，典型如画布状态、当前生效的 API endpoint。

- **存储引擎**：[sql.js](https://github.com/sql-js/sql.js)（SQLite 纯 WASM 移植，**无需编译原生模块**，跨平台）。数据库文件：
  - 默认：`~/.maomao-localtool/localtool.db`
  - 可用环境变量 `MAOMAO_DATA_DIR` 覆盖（`database.ts` 的 `getDataDir`）
- **表结构**（`initTables` 中建表）：
  ```sql
  CREATE TABLE IF NOT EXISTS kv (
    key        TEXT PRIMARY KEY,
    value      TEXT NOT NULL,
    updated_at INTEGER NOT NULL DEFAULT (unixepoch())
  );
  ```
  - `updated_at` 是 **整数 Unix 时间戳（秒）**，由 `unixepoch()` 默认填充，不是文本。
  - `value` 为 `TEXT NOT NULL`，仅存字符串；对象由调用方/写入兜底 `JSON.stringify`。
- **落盘机制**：sql.js 是内存库，写操作经 `debouncedSaveDb()` 做 **500ms 防抖落盘**。非优雅退出最多丢 500ms；进程收到 `SIGINT/SIGTERM` 时 `closeDb()` 强制 `saveDb()`。
- **跨进程共享**：是——只要多个端连**同一个 localTool 实例**（同一 18080、同一 SQLite 文件），读写同一 key 即共享。
- **多端自动同步**：**否**（无云端、无增量同步、无冲突合并）。
- **历史快照 / 审计**：**否**（仅最新值，set 为覆盖写）。
- **批量 / 前缀列举**：**否**（只有单 key 的 get / set / delete，无 `keys(prefix)`）。
- **鉴权**：**否**。三个接口均无 API Key / Token。服务绑定 `127.0.0.1:18080`（CORS 全开 `*`，但 loopback 绑定，外部默认不可达）。

## 2. 读写面（接口）详表 —— 真实实现

> 路由注册（`index.ts` 主路由 `handleRequest`）：
> - `GET  /api/kv/get`    → `handleKvGet`
> - `POST /api/kv/set`    → `handleKvSet`
> - `POST /api/kv/delete` → `handleKvDelete`（⚠️ key 来自 query，非 body）
>
> 静默日志：`SILENT_LOG_PATHS` 含 `/api/kv/get`、`/api/kv/set`；**不含** `/api/kv/delete`（会打印）。
>
> 错误响应统一结构 `{ "error": "<英文 message>" }`（由 `sendError(res, message, status)` 返回）。

### 2.1 `GET /api/kv/get?key=<key>`

- **参数**：`key` 经 **query 参数 `key`** 传递，必填。
- **成功响应**（HTTP 200）：
  - key 不存在：响应体即 **JSON `null`**（不是 `{success,data}`）。
    ```json
    null
    ```
  - key 存在：后端先 `JSON.parse(row.value)`；成功则返回**解析后的对象/数组/数字**，失败则原样返回**字符串**。
    ```json
    { "url": "https://www.1mao.cc" }
    ```
  ⚠️ **无 `success`/`data` 包裹**。"是否存在"靠「响应体是否为 `null`」或 HTTP 状态判断。前端 `endpointConfig` 用 `e.ok ? await e.json() : null` 再递归 `JSON.parse` 兼容二次字符串化。
- **错误响应**：
  - `key` 缺失/空：`{ "error": "Missing key parameter" }`（HTTP 400）。
  - 数据库异常：catch 返回 `{ "error": "<异常信息>" }`（HTTP 500）。

  真实源码（`kv.ts`）：
  ```ts
  const key = url.searchParams.get('key');
  if (!key) return sendError(res, 'Missing key parameter', 400);

  const db = await getDb();
  const row = queryOne(db, 'SELECT value FROM kv WHERE key = ?', [key]);

  if (!row) return json(res, null);

  try { return json(res, JSON.parse(row.value)); }
  catch { return json(res, row.value); }
  ```

### 2.2 `POST /api/kv/set`

- **请求体**（JSON）：
  ```json
  { "key": "<键名>", "value": "<字符串 / 对象 / 数字均可>" }
  ```
  - `key` 必填且为 string（非 string → 400）。
  - `value`：
    - 字符串 → 直接存。
    - 对象/数组/数字（非字符串）→ 后端 `JSON.stringify(body.value)` 后存（**不会报 400**）。
    - ⚠️ 传 `undefined` 会被 `JSON.stringify` 成字符串 `"undefined"`，调用方应避免。
- **成功响应**（HTTP 200）：
  ```json
  { "ok": true }
  ```
  ⚠️ 是 `ok` 不是 `success`。
- **错误响应**：
  - `key` 缺失或非 string：`{ "error": "Missing key field" }`（HTTP 400）。
  - 数据库异常：`{ "error": "<异常信息>" }`（HTTP 500）。

  真实源码（`kv.ts`）：
  ```ts
  const body = await parseJsonBody(res, req);
  if (!body || typeof body.key !== 'string')
    return sendError(res, 'Missing key field', 400);

  const db = await getDb();
  const value = typeof body.value === 'string'
    ? body.value
    : JSON.stringify(body.value);

  run(db, 'DELETE FROM kv WHERE key = ?', [body.key]);
  run(db, 'INSERT INTO kv (key, value, updated_at) VALUES (?, ?, unixepoch())',
      [body.key, value]);

  return json(res, { ok: true });
  ```
  ⚠️ sql.js 不支持 `ON CONFLICT`，此处用 `DELETE` + `INSERT` 模拟覆盖写（不是 UPSERT 语法）。

### 2.3 `POST /api/kv/delete`

- **参数**：`key` 经 **query 参数 `key`** 传递（**非 body**），必填。
  ```http
  POST /api/kv/delete?key=canvas-state-abc123
  ```
- **成功响应**（HTTP 200）：**恒为**
  ```json
  { "ok": true }
  ```
  ⚠️ 删不存在的 key 也返回 `{ ok: true }`，**不返回「未找到」、无 `message` 分支**。
- **错误响应**：
  - `key` 缺失/空：`{ "error": "Missing key parameter" }`（HTTP 400）。
  - 数据库异常：`{ "error": "<异常信息>" }`（HTTP 500）。

  真实源码（`kv.ts`）：
  ```ts
  const key = url.searchParams.get('key');
  if (!key) return sendError(res, 'Missing key parameter', 400);

  const db = await getDb();
  run(db, 'DELETE FROM kv WHERE key = ?', [key]);

  return json(res, { ok: true });
  ```

### 2.4 三个接口的「易踩坑」速查

| 接口 | key 位置 | 成功响应 | 不存在时 | 错误文案语言 |
|------|----------|----------|----------|--------------|
| get  | query `key` | `null` 或 解析后的值（无包裹） | 返回 `null` | 英文 |
| set  | body `{key,value}` | `{ ok: true }` | — | 英文 |
| delete | query `key` | `{ ok: true }`（恒真） | 仍 `{ ok: true }` | 英文 |

## 3. 目前实际落地的 KV key（按用途分类）

> 这些 key 是代码里**真实出现并读写**的。注意：前端经 `Kr`/`Fr` 写入 KV 时会**自动加前缀**，所以 SQLite 中存的 key 带前缀，接口调用也要带前缀。

### 3.1 `active_api_endpoint`（endpointConfig 模块）
- **用途**：当前生效的 API endpoint 配置（如 `{"url":"https://..."}`）。
- **读写**：
  - 读：`GET /api/kv/get?key=active_api_endpoint`
  - 写：`POST /api/kv/set` + body `{ "key": "active_api_endpoint", "value": {...} }`
- **来源**：`endpointConfig-Bt85xi8d.js` 中变量 `a = "active_api_endpoint"`，拼接 `/api/kv/get?key=` 与 `/api/kv/set`。
- 这是**唯一在 endpointConfig 模块中显式使用 KV 的 key**。

### 3.2 `canvas-state-<projectId>`（画布状态，经 `Kr`/`Fr` 路由）
- **用途**：保存画布节点数据（`nodes`、`transitResources`、`completedNodes`、`nodeExecOrder` 等运行态）。
- **key 构造**：前端 `jr(e2)` 返回 `` `${Ar.CANVAS_STATE_PREFIX}${e2}` ``（前缀常量 `Ar.CANVAS_STATE_PREFIX`，形如 `canvas-state-`）。
- **读写**：经统一存储层 `Kr`/`Fr` 自动分流到 KV（代码中 `e2.startsWith(Ar.CANVAS_STATE_PREFIX)` 的分支走 `Fr.set`/KV）。
- **注意**：这是 KV 中数据量最大的 key 类型，value 为 JSON 序列化后的画布对象。

### 3.3 `canvas_pinned_tools`（画布固定工具栏）
- **用途**：画布中固定（pin）的工具列表。
- **读写**：前端 `Ce2.getKV("canvas_pinned_tools")` / `Ce2.saveKV("canvas_pinned_tools", ...)`，直接走 `/api/kv/get` / `/api/kv/set`。

### 3.4 不在 KV 中的「易混淆」键（明确排除）

| key | 实际存储 | 说明 |
|-----|----------|------|
| `api_configs` | 前端 `localStorage`（`Ar.API_CONFIGS`） | 旧文档误列为 KV，错误 |
| `localToolBaseUrl` | 扩展 `chrome.storage.local` | 服务地址配置，非数据 |
| `transitResources` | 前端 `localStorage`（`Ar.TRANSIT_RESOURCES`） | `Kr` 存储层把它路由到 localStorage |
| `app_settings` / `users` / `projects` / `membership` / `customNodeTemplates` 等 | 前端 `localStorage` | 均属 `Ar` 枚举，走 `Wr` 层 |

## 4. 给后续 AI 的总结性提示

- 改 KV 相关逻辑时，**接口契约以第 2 节真实源码为准**：get 返回裸值或 `null`、set/delete 返回 `{ok:true}`、错误是 `{error:英文}`、delete 用 query。
- 不要把 `api_configs` / `localToolBaseUrl` / `transitResources` 当成 KV key 去调 `/api/kv/*`。
- 前端「存储」是双后端（`Kr`/`Fr` 路由），要定位某 key 到底存哪，去 `httpClient` 看 `jr()`/`startsWith`/`Wr`/`Fr` 分支，而不是搜 `/api/kv`。
- 旧版文档里 `{success:true,data:...}`、`{message:...}`、中文错误、`kvGet/kvSet/kvDelete/createKVTable` 函数名，均为虚构，**不可信**。
