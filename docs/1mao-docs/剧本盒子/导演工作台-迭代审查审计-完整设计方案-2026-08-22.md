# 剧本盒子 · 导演工作台（分阶段闸门·迭代·审查·审计）完整设计方案

> 日期：2026-08-22 ｜ 阶段：**定契约**（定契约 → 构思测试 → 定数据流与施工，本文件只到契约 + 数据流设计，不含可执行业务代码）
> 目的：把剧本盒子从「一次性生成 + 整镜重生成」升级为**分阶段闸门管线**：每一段产出（故事→资产清单→多角度资产→分镜→提示词→定稿）都必须经过**用户确认门**才流向下一段，且每一段内部都可**反复迭代沟通**，全程**可审计**。
> 关键升级：故事创作、角色/资产定义不再是"自动一次给定"，而是**先出草案 → 用户确认 → 才进入下一段**。
> 对比基准：`src/components/base/scriptBoxSchema.js`、`scriptBoxEngine.js`、`useScriptBoxEngine.js`、`scriptBoxPrompts.js`、`nodes/ScriptBoxNode.jsx`、`scriptbox/{StepShots,StepAssets,StepPrompt}.jsx`、`docs/剧本盒子/*.md`。

---

## 0. 一句话结论

> **把"一次性生成"改成"分阶段闸门管线"**：故事、资产清单、多角度资产、分镜、提示词每一段都先产出草案，经用户确认门（可多轮迭代）后才流向下一段；现状里最值钱的能力（`@资产`、多角度资产模板、引擎注入、并发安全）全部保留，新增**闸门/确认/审查/审计**四层数据契约。三 skill 对号入座各审一段。

---

## 1. 用户视角：这是一个什么样的操作体验

**像导演拿着分场表逐场确认，而不是点一次"生成"就等待最终成品。** 每一步都"先给你看、你点头才继续"。

### 1.1 完整走查（第一次使用）

> 用一个贯穿例子：给品牌写一支 30s 的萌宠广告片。

**① 故事创作（可多轮）** — 输入一句话命题 + 风格。点「起草故事」→ 引擎给一版完整故事梗概。用户不满意 → 输入意见「调成更有悬念的开场、结尾落到产品」→ 「按此精修」再造一版。直到满意 → 「确认故事」→ 故事门通过，才解锁下一段。

**② 资产清单确认（新增，重点）** — 引擎按故事自动列出一张角色/场景/道具清单（每项只有名称+描述，**还没生成图**）。用户核对：删掉不用的、补上漏的、改掉名字。确认无误 → 「确认清单」→ 清单门通过。

**③ 生成多角度资产** — 才真正批量生成参考图（角色四视图/场景四格/道具六视图）。这一步是**用户想落资产表的地方**（模型全球通用，无需适配）。生成后每张图可审可重生成（LIRA 维度意见落资产卡）。→ 「确认资产」→ 资产门通过。

**④ 生成分镜（三维度审查迭代）** — 逐镜产出。每一镜卡上：**导演（机位/运镜/光影）／表演（动作/走位）／表演连续性／美术（参考图）** 三个维度可分别写意见、标通过/待改。通过的维度 `locked`，被否维度意见汇成 `feedback` → 定向精修该镜。全部通过 → 「确认分镜」→ 分镜门通过。

**⑤ 合成提示词（定向精修）** — 每镜的生图/生视频提示词，双击可改；带意见可定向重生成（复用 `onGenerateShotPrompts(id, feedback)`）。确认 → 提示词门通过。

**⑥ 定稿连线** — 整份剧本/资产/提示词定稿，才开始连线生图/生视频。定稿写进审计。

**⑦ 随时审计** — 「改动历史」侧栏：每一段在哪个门通过、哪一版改成哪一版、每镜每资产每维度的意见与处理、依据哪条 feedback。**用户能回答"这镜头为什么从 A 变成 B"。**

### 1.2 与现状的用户感知差异

| 现状 | 升级后 |
|---|---|
| 故事一次性生成 | 故事可多轮迭代，满意才确认入口 |
| 角色/资产自动全给定 | 先出清单 → 用户核对增删改 → 才生成图 |
| 资产图一次性生成 | 每资产可审、可重生成（LIRA） |
| 分镜只能整镜重生成 | 分镜按三维度定向精修，通过维度锁定 |
| 没有"第几轮/哪段过了" | 每一段有确认门 + 轮次记录，可回溯 |
| 改了啥、为什么，全凭记忆 | 全程 `auditLog`，可答"何时、为何改" |
| 三 skill 无从挂载 | 导演/表演/美术对号入座各审一段 |

## 3. 数据契约（全落在 `node.data`，经归一化）

> 纪律不变：任何新字段先在 `scriptBoxSchema.js` 登记默认值。

### 3.1 顶层新增：闸门层 + 迭代层 + 审计层

```js
// 扩展 defaultScriptBoxTop()
{
  ...原有,

  // ── 分阶段闸门层（每段一个确认门）──
  gates: {
    story:   'draft',   // draft | reviewing | approved
    roster:  'draft',   // 资产清单确认门
    assets:  'draft',   // 多角度资产生成确认门
    shots:   'draft',   // 分镜（三维度审查）门
    prompts: 'draft',   // 提示词门
    final:   'draft',   // 定稿门
  },
  gateOrder: ['story','roster','assets','shots','prompts','final'], // 单向推进，前面的门未过则后面锁定
  // 导航即 gateOrder：UI 的「步骤/阶段条」直接渲染 gateOrder（§9a），不维护独立的 step 数字——彻底去掉「固定三步」

  // ── 迭代层 ──
  directive: { intent:'', director:'', acting:'', art:'' }, // 导演意图（故事确认锚点）
  rounds: [],          // Round[]
  storyDraft: '',      // 当前故事草案（多轮迭代产物）

  // ── 审计层 ──
  auditConfig: { enabled:true },
  auditLog: []         // AuditEntry[]
}
```

```js
// Round —— 一次迭代/审查单元（每段每轮各一条）
{ id, round, gate:'story'|'roster'|'assets'|'shots'|'prompts'|'final',
  ts, intent, focusShotIds:[], status:'draft'|'generated'|'reviewing'|'approved'|'rejected' }

// GatePass —— 门通过记录（进审计，节点内可不存，审计推导）
{ gate, ts, round, summary }
```

#### 3.2.a shot 子字段新增（审查层 — 补 ACTING 引用 + LIRA 图内编辑 lane）

```js
// 扩展 defaultShotFields()
{
  ...原有,
  actingRef:'',        // ACTING：该镜引用哪份「表演大师档案」assetId，按本镜场景改写；无档案则 ''
  // LIRA：图内编辑 lane（针对本镜参考图/分镜帧做「编辑」而非「重生成」，保留身份一致性）

```

#### 3.2.b asset 子字段新增（补 ACTING 持久档案 + LIRA 类型路由）

```js
// 扩展 defaultAssetFields()
{
  ...原有,
  // ACTING「永久双档案」：写一次，贯穿全片；写进资产卡使其可跨镜复用（G1）
  actingProfile:'',    // 表演大师档案 ~150-220 词（Objective/Obstacle&stakes/Tactics/Beats/掩膜与裂纹/眼活/步态/软化目标）
  voicePrompt:'',      // 固定声音身份，台词出现时逐字粘贴到 voice 字段；静默则省略
  // LIRA 资产类型 -> 构建法路由：决定该资产用哪套组装模板（G6）
  assetKind:'character'/* |location|prop */, // 由 roster/清单项驱动：character→three-panel sheet、location→camera anchor、prop→product framing
  productionHint:'',   // LIRA 材质/光/色板锚点（技术光、具体材质+finish、60/30/10 色板），跨镜一致的资产基调
}
```

> **点名 @资产 + 表演档案的联动**：每镜 `actingRef` 指向一份 `asset.actingProfile`；下游生视频提示词合成时，取该档案按本镜状态改写为一段（ACTING §8「重写不照搬」），`voicePrompt` 则原样落到 audio 字段。

### 3.4a 审查用「结构化检查清单」契约（G2）

三维度意见不再是纯自由文本，而是**「清单勾选 + 定向意见」生成**。每个维度一份契约级 `checklist` 模板，审查时逐项判 through/未过，未过项+意见结构化进 `ReviewNote`（作为 `buildRefineFeedback` 的输入），自由文本仅作补充。清单来源即三 skill 的 Pre-send / 自检清单。

```js
// REVIEW_CHECKS —— 契约常量，UI 渲染勾选、引擎收集
REVIEW_CHECKS = {
  acting: [ // 源自 ACTING §14 清单
    'objective:动词且指向场内具体对方', 'obstacle&stakes成本真实',
    '2-4个visible beat', '反应先于对方台词结束', 'eye life显式',
    'subtext存在', 'states-not-transitions', 'scale>=4', '声线档案一致'],
  director: [ // 源自 CINEDANCE 自检
    'first-frame非空且含关键角色', 'spatial blocking具体(无near/around)',
    'gaze line明确', 'landmark距离锚定', '镜头按内容选FOV',
    '防flat正光', '无陈旧@tag', '多镜连续性(同向/同光/同服装)'],
  art: [ // 源自 LIRA Pre-send
    '技术光而非情绪光', '具体材质+finish', '60/30/10色板源于材料',
    'positive>negative', '长度<=1500-2000字符', '身份由Soul ID/档案而非纯prose'],
}
```

> 待确认（进 §8）：清单项是**默认全量**还是一段只取子集；勾选结果是否直接驱动「精修反馈」还是仅作评分。

### 3.4b 提示词产物「文档 schema」契约（G3）+ 上下文隔离纪律（G4）

**提示词文档 schema** —— 引擎合成/定向精修每镜生视频提示词时，必须产出结构化段落（不止一段文本），以保证审计能做段级 diff、且能按 skill 规则定向修正：

```js
// 生视频提示词文档（对应 CINEDANCE 段落序；缺省项可省略）
shot.videoPromptDoc = {
  sections: [ // 顺序固定：sceneContext→activeRefs→locationMap→firstFrame→optics→camera→actionTiming→physics→lighting→audio→posConstraints
    { key:'sceneContext', ... },
    { key:'activeRefs',   // 只含本镜 active @tag，引用 asset 现在的 @资产
    { key:'locationMap'|'firstFrame'|'optics'|'camera'|'actionTiming'|'physics'|'lighting'|'audio'|'posConstraints', ... },
  ],
  outputSettings:'',  // 属平台 UI，一般不进提示词（duration/aspect/fps等）
  negative:'',        // 默认空，仅局地 no-X 锁，不设整大负向块
  // ACTING 合成段
  actingParagraph:'', // 由 asset.actingProfile 按本镜改写（states-not-transitions）合成
  voice:'',           // asset.voicePrompt 原样；无台词则空
  // 资产引用（供 @资产 动态收集）
  refs:{ [assetId]: 'active'|empty },  // 只列本镜确实出现者
}
```

**上下文隔离纪律（G4，写进数据流行为契约）**：每镜每提示词是**密封的当镜文档**。多轮分阶段/定向精修时，合成器必须剥离陈旧引用——只带本镜 active 角色/场景/道具的 `@资产`，丢弃上一轮带入的其他 tag、不含未上场角色、不含场景号/脚本头/`same as before` 等上下文泄漏词。精修 = 在当镜 sealed 文档上局部替换，不允许把旧提示词整段顺延。

### 3.4 契约锁定的决策（含待确认）

- 审查形态：每镜打三标（导演/表演/美术）——已确认方向。
- **闸门推进**：默认**硬闸门**——前面的门未 `approved`，后面的门锁定不可操作（避免跳过确认）；可在设置关。待确认。
- **审计落点**：推荐 `node.data.auditLog` 随画布快照；备选独立 KV。方案默认推荐，抽 `auditBackend` 留演进口。待确认。

## 4. 数据流（分阶段闸门管线）

```
① 故事 story ──[故事门 多轮迭代至通过]──▶
② 资产清单 roster（先出名单，未生图）──[清单门 核对增删改]──▶
③ 生成多角度资产 assets（四视图/四格/六视图）──[资产门 每资产可审/精修]──▶
④ 生成分镜 shots（三维度审查迭代）──[分镜门]──▶
⑤ 合成提示词 prompts（定向精修）──[提示词门]──▶
⑥ 定稿 final ──▶ 连线生图/生视频（始启动下游生成）

每一段内部都是"草案 → 用户意见 → 精修 → 再审"的局部环；
只有用户「确认」该段，门才通过，才解锁下一段。
全程 auditLog：draft / edit / review / regenerate / approve / 门通过 逐条落库。
```

**纪律不变**：读 `getData→normalizeScriptBoxData`；写仅 `updateData` 两条通道；纯函数 `appendAudit`/`markReview`/`buildRefineFeedback`/`nextGate` 放纯函数层可单测；依赖方向 UI→引擎→纯函数。

**契约化的三处升级（把 skill 能力落到数据流）**：
1. **@资产 → 密封引用（G4）**：每镜到「提示词门」时，合成器在**当镜 sealed 文档**上从 `asset` 动态收集 `@资产`，只带 active 引用；多轮精修在密封文档上局部替换，剥离陈旧 tag。沿用现状 `@资产` 机制，不重构，仅新增「剥离陈旧引用」这一行为纪律。
2. **意见 → 三 skill 检查清单（G2）**：审查意见默认由 `REVIEW_CHECKS` 勾选 + 自由文本生成，引擎据此构建结构化 feedback（`buildRefineFeedback`），比纯手写更可判、更贴近三 skill 的自检标准。
3. **修正 → 重生成 或 图内编辑 lane（G5）**：资产/参考图修正不只有「重生成」，凡涉局部改动（换表情、改道具握持、改一处材质）走**图内编辑 lane**（LIRA 外科手术编辑：极简 CHANGE + 穷尽 PRESERVE，模型默认 Banana NBP lane），保留身份一致性；只有整体重做才走「重生成（Soul 模型）」。

三条升级均属**增量**：不新增 AI 调用种类——“重生成”与“图内编辑”共用既有人像/生图回调，只加 `{mode:'edit'|'rebuild'}` 这类可选参数；不重构 §2 的 N1–N8。

## 5. 三个 skill 的嵌入

| Skill | 维度 | 主要落在哪一段 | 承载点 | 流向 |
|---|---|---|---|---|
| CINEDANCE | 导演（机位/运镜/光影/镜头-FOV/连续性） | ④ 分镜 | `shot.review.dim='director'` + `REVIEW_CHECKS.director` | 勾选+意见→feedback→按提示词文档段定向精修 |
| ACTING | 表演/连续性（表演档案/声线/眼活/走位） | ② 资产(档案) + ④ 分镜 | `asset.actingProfile`+`voicePrompt`；`shot.actingRef` + `dim='acting'` + `REVIEW_CHECKS.acting` | 档案跨镜重写→actingParagraph/voice 合成；意见→feedback |
| LIRA | 美术（参考图/光/材质/色板/类型路由/图内编辑） | ②③ 资产 + ④ 分镜 | `asset.assetKind`+`productionHint`+`actingProfile外的前置`；`asset.review`+`dim='art'`+`REVIEW_CHECKS.art`+`shot.edit` | 类型→组装模板；意见→重生成或图内编辑 lane |

三项能力锚点（对应 §4 契约化升级）：
- **ACTING 持久档案**（G1）：`asset.actingProfile`/`voicePrompt` 在②资产段写入，④分镜合成时经 `actingRef` 引用并按本镜改写，`voice` 原样落 audio——这是跨镜表演一致性的根基。
- **CINEDANCE 提示词文档**（G3）：`shot.videoPromptDoc` 结构化段输出，审查意见能落到**具体段**做定向修正，而非整段重写。
- **LIRA 图内编辑 lane**（G5）：`shot.edit`/资产编辑走外科手术编辑（CHANGE 一动、PRESERVE 尽锁），只有整体重做才 `rebuild`。

此外 story 段可让三者在"叙事/调度/风格基调"三视角给出故事审查初稿，作为用户修正的起点（待 §8 确认是否开放"AI 预审初稿"）。

## 8. 仍需用户确认的契约点

1. **闸门推进方式**：硬闸门（前面未通过则后面锁定，Default）vs 软闸门（只提示不锁）。

4. **意见来源**：默认「三 skill 检查清单勾选 + 自由文本」（已定为默认）；是否额外开放「三个 skill 各自预审出初稿，用户改后采纳」。

## 9. 架构决策：闸门导航 / 目录自包含 / 真全屏

> 进入施工前必须锁定的三条结构决策，与 §3 数据契约并行。落地时都体现在增量阶段 §10。

### 9a 导航 = 实际分阶段闸门流程，不是固定「三步」

**决策**：废弃硬编码的 `step:1|2|3`（`StepNav` 圆环 + `ScriptBoxNode` 里 `step===1/2/3` 的 `StepShots/StepAssets/StepPrompt` 三选一切换）。导航条改为**直接渲染 `gateOrder`**（story→roster→assets→shots→prompts→final）的阶段闸门条：

- 数据层面不再有独立的 step 数字——「当前在哪一段」= `gates` 状态机的推导（前序 `approved` 的最后一个门之后，即当前段）。`node.data.step` 字段删除（或归一化时兼容忽略）。
- 每段渲染一个**阶段闸门 Step**（`GateStory/GateRoster/GateAssets/GateShots/GatePrompts/GateFinal`），内部是「草案 → 用户意见 → 精修 → 确认」局部环；闸门条上未 `approved` 的门锁定、当前段高亮、已过段显示打勾。
- `gateOrder` 是**可配置**的（段名增减时导航条随之增减，不写死），未来若扩展段数，UI 与引擎自动跟随。

### 9b 目录自包含：所有剧本盒子专属代码收进 `scriptbox/`

**决策**：剧本盒子是**自包含**子系统，所有专属代码统一放 `src/components/scriptbox/`，**不再往 `base/` 新增**；现状散落在 `base/` 的专属模块**迁移收口**进来。这样未来改动剧本盒子只要打开一个目录。

**现状到目标的迁移清单**（`base/` → `scriptbox/`，纯搬移 + 改 import 路径，逻辑不动）：

| 现状 | 迁移目标 | 说明 |
|---|---|---|
| `base/scriptBoxSchema.js` | `scriptbox/schema.js` | 数据契约 + 归一化 |
| `base/scriptBoxEngine.js` | `scriptbox/engine.js` | 生成/连线引擎 |
| `base/scriptBoxPrompts.js` | `scriptbox/prompts.js` | `@资产` 匹配 + 提示词合成（纯函数） |
| `base/useScriptBoxEngine.js` | `scriptbox/useScriptBoxEngine.js` | 引擎注入 hook |
| `scriptbox/StepShots.jsx` | `scriptbox/gate/GateShots.jsx` | 按分镜闸门重组 |
| `scriptbox/StepAssets.jsx` | `scriptbox/gate/GateAssets.jsx` | —— |
| `scriptbox/StepPrompt.jsx` | `scriptbox/gate/GatePrompts.jsx` | —— |
| `scriptbox/ScriptBoxModal.jsx` | `scriptbox/ui/ScriptBoxModal.jsx` | 保留（节点内小弹层） |
| `scriptbox/GearSettings.jsx` | `scriptbox/ui/GearSettings.jsx` | 保留 |
| — | `scriptbox/gate/GateStory.jsx` | 新增：故事段闸门 |
| — | `scriptbox/gate/GateRoster.jsx` | 新增：清单段闸门 |
| — | `scriptbox/gate/GateFinal.jsx` | 新增：定稿段闸门 |
| — | `scriptbox/meta/REVIEW_CHECKS.js` | 三 skill 检查清单契约常量（§3.4a） |
| — | `scriptbox/meta/ASSET_TEMPLATES.js` | 多角度资产模板（自 `ScriptBoxNode` 或 `schema` 收口） |
| — | `scriptbox/audit.js` | `appendAudit`/纯函数（§3.3） |
| — | `scriptbox/refine.js` | `buildRefineFeedback`/`nextGate`/上下隔离开尔（§3.4b/§4） |

**归属铁律**：凡是 `ScriptBoxNode`、`useScriptBoxEngine`、剧本盒子 Step/引擎/prompt schema 之间互相引用的模块，都算剧本盒子专属，一律住 `scriptbox/`。只有真正被其他节点强复用的通用件才留在 `base/`（本设计未引入此类需求，故不回base）。

**入口文件**：`scriptbox/index.js` 收口本子系统对外的依赖面——`ScriptBoxNode.jsx`（nodes）、`useScriptBoxEngine` 等通过它引用 `scriptbox/`，外部不直接 `import` 内部实现；降低耦合、方便整体替换。

### 9d 提示词后台化：主流程 UI 不展示任何提示词

**纪律**：所有生成提示词（起草故事 / 分镜 / 生图生视频 / 资产）一律**收进齿轮设置**（GearSettings）内配置，**主流程创作面板不展示、不暴露提示词内容**。

- 现状已符合：GearSettings 的「剧本/分镜/生图类型/资产」Tab 各自放了 `SCRIPT_WRITER_SYSTEM` / `SHOT_DIRECTOR_SYSTEM` / `IMAGE_GEN_TYPES` / `ASSET_TEMPLATES` 等提示词编辑框。
- 分阶段后：每个闸门段的生成提示词（story→bespoke 剧本提示词、roster→清单抽取提示词等）也在 GearSettings 加对应项，同样后台化。
- 主面板（Gate*）只承载**交互**（命题/草案编辑/意见/按钮/进度），不显示提示词文本、不做提示词编辑入口。

> 这是对 §9b 自包含的补充：UI 与提示词配置彻底分离——创作在面板、规则在设置。

### 9c UI 全屏 = 真全屏（铺满视口），不是放大弹窗

**现状**：全屏复用 `base/FullscreenModal`，初始仅 80% × 80% 且可缩放、带圆角边框——是「放大的居中弹窗」，不是真全屏。

**决策**：剧本盒子的「全屏工作台」改为**真正铺满视口**：
- 移除居中留边、圆角卡片、右下缩放手柄；容器 `fixed inset-0`（或 `100vw × 100vh`）**无填充占满全屏**，标题栏 + 闸门导航条 + 当前段内容 `flex-1` 自适应。
- 保留 Esc / 关闭按钮 / 点空白关闭；全屏内复用节点内的闸门条与各 `Gate*` 组件（同一份渲染，小窗/全屏共用）。
- 不再依赖 `base/FullscreenModal`（或在其上内置 `full` 模式）：剧本盒子全屏要么自实现 `scriptbox/ui/Fullscreen.jsx`，要么给 `base/FullscreenModal` 加 `fullscreen`（无留边全覆盖）开关。倾向**自实现**以保自包含（§9b），`base/FullscreenModal` 保持通用给其他节点用。
