## 2. 实测：导出 JSON（323MB）

### 2.1 结构
```json
{
  "localforage": { "canvas-state-v1-default": {...}, "canvas-state-v1-proj-1785550656491": {...}, "..._migration_backup": {...}, ... },  // 242.66MB
  "kvStore":     { "users":..., "projects":..., "canvas-state-v1-proj-1785550656491":{...}, ... }                                           // 78.48MB
}
```
- **结论 2**：导出=浏览器存储快照，不含 localTool sql.js KV。
- 源码 `Vr.jsx:2645-2682`：`localforage` 块=`At.default.keys()`+`getItem`（IndexedDB）；`kvStore` 块=`z.getObject`（localStorage）的 users/projects/app_settings 等 + 每项目画布 `He(id)`。
- **⚠️ 补充（外部 AI 审计发现，2026-08-13 修正）**：`Vr.jsx:2659` 导出 localforage 时有过滤 `if (!n.startsWith('img_') && n !== 'transitResources')`，即**导出文件已排除所有 `img_` 前缀键（含 `img_orig_*`/`img_thumb_*`）**。这解释了为何导出文件里 `img_orig_*` 数量为 0（见 §3.1：localTool KV 里有 `img_orig_*`，但浏览器导出文件不含它）。导出文件中的 base64 全部来自**画布节点内嵌**（`canvas-state-*` 的节点 `data.imageUrl`），不是 `img_*` 键。

## 4. 源码证据：base64 如何进入 localTool KV

### 4.1 前端外置 base64（`H_.jsx:726-734`）
```js
let r = t.data.imageUrl;
if (r && r.startsWith('data:image')) {        // H_.jsx:727
  let e = `img_orig_${t.id}_${Date.now()}`;    // H_.jsx:732
  console.log(`[Canvas] 存储原图 key=${e} ...`);
  await Kr.setObject(e, r);                    // H_.jsx:734  → 外置原图 base64
  // 缩略图：await Kr.setObject(`img_thumb_...`, thumbBase64)  → H_.jsx:745
}
```
- 画布状态本身也经 `Kr.setObject('canvas-state-v1-...', 画布对象)` 入库（节点 `data.imageUrl` 含 base64）。
- **结论 7**：前端确有外置机制，但存的是 **KV**（非磁盘 `/files/`）。

### 4.2 存储路由（`shared.js`）
- `Kr.setObject`（shared.js:1147）→ `Fr.setObject`（:1178）。
- `Fr.setObject`（shared.js:803）→ `window.localTool.saveKV(e, t)`。
- `saveKV`（shared.js:6328）：
  ```js
  let e = typeof n == 'string' ? n : JSON.stringify(n);
  await fetch(`${Mn()}/api/kv/set`, { body: JSON.stringify({ key: t, value: e }) });
  ```

### 4.3 入库（`localTool/src/routes/kv.ts:22-35`）
```ts
const value = typeof body.value === 'string' ? body.value : JSON.stringify(body.value);
run(db, 'DELETE FROM kv WHERE key = ?', [body.key]);
run(db, 'INSERT INTO kv (key, value, updated_at) VALUES (?, ?, unixepoch())', [body.key, value]);
debouncedSaveDb();
```
- **结论 8**：所有 base64（画布内嵌 + img_orig/img_thumb）最终经 `/api/kv/set` 的 `value` 原样写进 sql.js `kv` 表，`handleKvSet` 是唯一收口点。
- localTool 落盘：`database.ts` `saveDb()` 全量 `_db.export()` 原子写；`VACUUM_THRESHOLD=50MB`。

### 6.2 死机机制补充（2026-08-13，基于用户反馈 + 源码）

- **真实痛点**：数据库膨胀 → 电脑卡死/死机，非单纯磁盘占用。
- **机制**：`saveDb()`（database.ts:102-126）= `_db.export()`（全量 WASM 序列化）+ `Buffer.from`（复制）+ `fs.writeFileSync`（同步阻塞）。配合 tasks/resources/kv 三路由每次写都调 `debouncedSaveDb()`（database.ts:286，500ms 防抖），前端频繁写入 → 每 500ms 全量 export 79MB+，内存峰值 + 同步阻塞事件循环。
- **方案②对死机的效果**：把库 79MB→几 MB，export 峰值和写盘耗时降 90%+，**直接消除卡顿根因**。
- **注意**：`fs.writeFileSync` 会阻塞 Node 事件循环（服务卡顿），但单进程不太会导致 Windows 系统级死机；系统级卡顿更可能来自 sql.js WASM 内存峰值（corrupt 达 354MB 时单次 export 内存可达 600MB+）。
- **saveDb 异步化（`writeFileSync`→`writeFile`）**：只解决"写盘那一下阻塞"，但瓶颈在 `_db.export()` 同步序列化，异步化收益有限；**瘦库（方案②）才是釜底抽薪**。可作低成本加固，非关键。
