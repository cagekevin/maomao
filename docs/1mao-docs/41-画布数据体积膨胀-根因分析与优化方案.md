# 41-画布数据体积膨胀：根因分析与优化方案（终版，真实代码核实）

> 目标唯一：**让系统数据不要这么大**。
> 本文档全部依据**真实源码 + 实测数据**，不瞎编。关键结论均标注「源码位置」或「实测值」。优化方向按收益/成本/风险排序，最终给出最优落地路径。

## 0. 真实数据全景（实测，非推断）

数据分布在**三处**，全部实测确认：

| # | 存储 | 位置 | 实测大小 | 内容 |
|---|------|------|----------|------|
| A | localTool KV（sql.js） | `~/.maomao-localtool/localtool.db` | **79 MB**（当前库） | KV 表 `canvas-state-*` 78.44MB + `img_orig_*` 0 |
| A' | localTool KV 备份 | `backups/localtool.db.20260813_090938.bak` | **203 MB** | KV `canvas-state-*` 78.47MB + **`img_orig_*` 52.42MB** + tasks 49 行 + resources 574 行 |
| B | localforage（IndexedDB） | 浏览器 | 242 MB（导出文件 localforage 块） | `canvas-state-v1-*` 画布（节点内 base64） |

- `img_orig_*` 只在 8/13 备份里出现（52MB），当前库为 0 —— **时有时无**（会被清理或重写覆盖）。
- 两者相加 130.91MB ≈ 8/13 备份 KV value 合计 130.91MB，即 **KV 膨胀 = `canvas-state-*` + `img_orig_*` 两个前缀包圆**。
- `tasks`（49 行）/`resources`（574 行）**不是主因**。

## 1. 数据流根因（真实代码链路）

前端「保存画布」把 base64 图片写入 localTool KV 的**完整链路**（已逐行核实）：

```
H_.jsx 保存画布（打包产物）
  ├─ Kr.setObject('canvas-state-v1-<id>', 画布对象)        // 节点 data.imageUrl 含 base64
  ├─ Kr.setObject('img_orig_<nodeId>_<ts>', base64原图)    // 外置原图
  └─ Kr.setObject('img_thumb_<nodeId>_<ts>', thumbBase64)  // 外置缩略图
        ↓
shared.js  Kr.setObject → Fr.setObject → window.localTool.saveKV(key, obj)
        ↓
shared.js  saveKV（useLocalTool）:
            value = typeof obj == 'string' ? obj : JSON.stringify(obj)
            POST /api/kv/set  body: { key, value }          // shared.js:6328-6343
        ↓
localTool/src/routes/kv.ts  handleKvSet:
            value = body.value（字符串）
            DELETE + INSERT INTO kv (key, value, updated_at)   // kv.ts:22-35
        ↓
localTool sql.js kv 表 → 库膨胀 → saveDb() 全量 export 落盘
```

**结论**：所有 base64（画布内嵌 + img_orig/img_thumb）最终都经 `POST /api/kv/set` 的 `value` 原样写进 sql.js `kv` 表。**`handleKvSet` 是唯一收口点。**

`localTool/src/routes/kv.ts`（当前实现，唯一需要改的地方）：
```ts
export async function handleKvSet(req, res) {
  const body = (await parseJsonBody(req)) as { key?: string; value?: string } | null;
  const value = typeof body.value === 'string' ? body.value : JSON.stringify(body.value);
  run(db, 'DELETE FROM kv WHERE key = ?', [body.key]);
  run(db, 'INSERT INTO kv (key, value, updated_at) VALUES (?, ?, unixepoch())', [body.key, value]);
  debouncedSaveDb();
  return json(res, { ok: true });
}
```

## 2. 最优解（推荐）：localTool 在 `handleKvSet` 把 base64 外置为磁盘文件

### 2.1 思路（不改前端任何代码）

`handleKvSet` 收到 value 后，在入库前做一次「base64 → 磁盘文件」变换：
1. 尝试 `JSON.parse(value)`（画布状态是 JSON 对象；`img_orig_*` 是裸 base64 字符串）。
2. 深度遍历对象，找出所有以 `data:image/` / `data:video/` 开头的字符串字段。
3. 解码二进制 → 写入 `~/.maomao-localtool/uploads/`（复用 files.ts 落盘逻辑），用 sha1 内容哈希命名（幂等去重）。
4. 用 `http://127.0.0.1:18080/files/...` URL **替换**该字段。
5. 把替换后的对象 `JSON.stringify` 后入库。
6. 若是裸 base64 的 `img_orig_*`，同样解码落盘，存 URL。

### 2.2 为什么这是最优解（针对本项目）

- **唯一收口点**：所有 base64 必经 `handleKvSet`，一处改动覆盖画布内嵌、img_orig、img_thumb 全部来源。不需要逆向前端打包产物。
- **前端零改动、零回归风险**：前端 `getKV` 读回的是 `/files/` URL，渲染时 localTool `/files/` 静态服务（`index.ts handleStaticFile`）已能返回文件 → 前端无感知。
- **复用现成能力**：localTool 已有 `saveFile`/`writeUploadBuffer`（files.ts:84）、`/files/` 静态服务（index.ts:99）、`tryGenerateThumbnail` 真实缩略图（files.ts:119）、`fileStore.ts` 的 `resizeImage`/`ensureThumbnailTarget`。**不引新依赖**。
- **同步根治三处**：localTool KV 里的 base64 被剪掉后，库不再膨胀（当前 79MB→预计几 MB）；整库备份（203MB）随之变小；若浏览器侧从 KV 回填 base64 的路径也被 URL 替代，IndexedDB/localStorage 不再累积。

### 2.3 落地要点（真实代码为依据）

- 改动文件：`localTool/src/routes/kv.ts`（`handleKvSet`），新增一个 `externalizeBase64(value: string): string` 辅助。
- 复用：把 `files.ts` 的 `saveFile` / `writeUploadBuffer` 提升为可导入（当前是模块私有），或在其上加一个 `saveBase64ToUpload(dataUri: string): Promise<string>`（返回 `/files/` URL）供 kv.ts 调用。
- 幂等/去重：文件名用 `sha1(base64内容)` 前 16 位 → 同一 base64 永远同文件，重复写入不落重复盘（对齐 `saveRemoteUrl` 的 sha1 去重惯例，files.ts:97）。
- 失败回退：解码/落盘失败则**保留原 base64**，保证不丢数据（不破坏 `handleKvSet` 现有行为契约 `{ok:true}`）。
- 写入触发 `debouncedSaveDb()`（不变），磁盘文件不影响库的防抖语义。

### 2.4 收益预估（基于实测）

| 项 | 现状 | 方案②后（预估） |
|----|------|------------------|
| localTool 当前库 | 79 MB | ~几 MB（KV 只剩 URL） |
| 整库备份 | 203 MB | ~几 MB |
| 前端导出文件（B+C base64） | 302 MB | 画布节点内嵌 base64 部分可下降；`img_*` 本就不导出（`Vr.jsx:2659`），收益保守估计 |
| 落盘速度 | 全量 export 79MB+ | 显著加快 |

### 2.5 注意事项

- `img_orig_*` 当前为 0，但 8/13 曾达 52MB：方案②需覆盖「裸 base64 字符串」形态（非 JSON 对象），不能只处理 JSON。
- **缓存前缀细节（外部 AI 审计修正，2026-08-13）**：`getKV` 读取时对**三组前缀**走内存缓存（`Hr`，shared.js:844；`zr=['img_','img_thumb_','video_thumb_']`，shared.js:834），TTL **10 分钟**（`Rr=600000`，shared.js:833），`Ir`/`Lr` 双 Map 缓存。方案②把值替换成 `/files/` URL 后，缓存的是 URL，无副作用。**注意**：前缀含 `video_thumb_`（文档早期漏提），且是 10 分钟非无限期缓存。
- **导出过滤影响（外部 AI 审计修正）**：前端导出 `Vr.jsx:2659` 已排除 `img_` 前缀键，故 `img_orig_*` **不进浏览器导出文件**。方案②对浏览器导出（localforage/kvStore）的收益，主要来自**画布节点内嵌 base64**（`canvas-state-*` 的 `data.imageUrl`），`img_*` 键本就不导出，需**保守估计**导出层面的降幅。

### 2.6 兼容性验证：前端读 `/files/` URL（✅ 已验证，2026-08-13）

> 此前文档将「前端读回 URL 的兼容性」列为 ⚠️ 未验证假设。**现已逐行核实源码确认安全，方案②可行**。证据如下：

**① 渲染层直接支持 `/files/` URL，不要求 base64**
- `Kl_1.jsx:120`：`<Component1735 src={t.imageUrl}>` 直接把 `imageUrl` 作为 `<img>` src 渲染，无 base64 强制校验。
- `Co.jsx:132`：收集节点图片时接受 `e.data.imageUrl.startsWith('http') || startsWith('data:')`，`/files/` URL（`http://127.0.0.1:18080/files/...`）符合 `http` 前缀，正常纳入。

**② URL 透传函数 `An` 不破坏 `/files/` 地址**
- `An` = endpointConfig 的 `i(e)`（endpointConfig-Bt85xi8d.js:15-19）：仅当从非本机页面访问时，把 URL 里的 `127.0.0.1` 替换为 `window.location.hostname`；chrome 扩展环境直接原样返回。**不改协议、不校验、不转换 base64**，`/files/` URL 安全通过。

**③ `/files/` 是系统一等公民（已有专门识别）**
- `H_.jsx:3345`：`e.startsWith('data:') || e.startsWith('blob:') || /:\d+\/files\//.test(e)` → 把 `/files/` 识别为本地素材（`fetch(e).blob()` 处理，3365 行）。
- `H_.jsx:3415` / `H_.jsx:4108`：同样把 `/:\d+\/files\//` 排除出"需远程下载"集合，即 `/files/` 视为已本地持有。

**④ 不回写 base64（方案②不埋雷的关键）**
- `H_.jsx:726-727`：只有 `imageUrl.startsWith('data:image')` 才触发"外置 base64"逻辑。方案②把 base64 换成 `/files/` URL 后，此 if 不成立 → 前端**不会重新外置、不会回写 base64、不会报错**。
- localTool `/files/` 静态服务（index.ts:99）已存在，前端渲染时能取到图片 → **读取闭环成立**。

**结论**：方案②把 localTool KV 里的 base64 换成 `/files/` URL 后，前端渲染正常、不会回写、不报错。**方案②由"推断"升级为"已验证可行"。**

### 2.7 实现前置硬缺口（进入实现前必须补齐）

> 以下由外部 AI 审计补充，是方案②落地前**必须**解决的配套项，否则方案②会制造新问题。

**① 磁盘孤儿文件 GC（必做，否则问题换地方继续存在）**

- **现状缺口**：`/api/admin/cleanup`（admin.ts:86-122）只扫 `resources` 与 `tasks` 表里的 URL 引用，**不扫 KV 表**。方案②把 base64 落盘成 `/files/` 文件后，节点删除/画布重置时，KV 里的 URL 引用消失，但**磁盘文件不会被清理** → 磁盘孤儿文件无限累积，膨胀从「KV 库」转移到「uploads 目录」。
- **必须配套的 GC**：新增一个「KV 引用 ↔ 磁盘文件」对照 GC，挂在 `/api/admin/cleanup` 或独立定时任务：
  1. 遍历 KV 表所有 `value`（重点 `canvas-state-*`、`img_orig_*`、`img_thumb_*`），用正则 `/\/files\/([^"'\s)]+)/` 提取所有 `/files/` 相对路径，构成**被引用集合**。
  2. 递归扫描 `uploads/` 目录下所有文件（跳过 `.thumbnails/`，因为缩略图按名配对、随原图处理），构成**磁盘文件集合**。
  3. 删除「磁盘有、但不在被引用集合」的文件。
  4. **安全约束**：只删 `uploads/` 目录内文件；保留 `.thumbnails/`（缩略图按需重新生成）；新增 GC 前先 dry-run 统计，避免误删。
- **注意**：现有 `deleteLocalFile`（database.ts:258）只检查 tasks/resources 引用，同样不含 KV，需同步扩展或由新 GC 统一处理。

**② 裸 base64 字符串形态（已覆盖，需确保分支不丢）**

- `img_orig_*`/`img_thumb_*` 是**裸 base64 字符串**（非 JSON 对象，审计 §3.1 确认）。`externalizeBase64(value)` 的 `JSON.parse` **失败时**必须按「整串是裸 base64」处理（直接解码落盘、存 URL），不能因 parse 失败而放弃外置。
- 方案 §2.1 第 6 步已声明此分支，实现时**勿漏**。

**③ 失败回退的精细 try/catch（单字段失败不拖垮整条）**

- `externalizeBase64` 必须**逐字段** try/catch：单个 base64 解码/落盘失败时，**该字段保留原 base64**，其余字段照常外置，整条 value 仍成功入库。
- 失败字段保留 base64 会继续撑大库，属**可接受降级**，但必须：
  - 在日志打 **WARN**（含 key 与失败原因），便于观察；
  - 不破坏 `handleKvSet` 的 `{ok:true}` 契约（外置失败≠写库失败）。

## 3. 备选方案（按需叠加）

### 方案③：localTool 整库备份瘦身（快、独立）
- `backupDb()` 是全库文件拷贝（database.ts:174），会包含 KV 里所有 base64 → 203MB。方案②落地后自动变小。
- 可另加：备份前排除 `img_orig_*`/`img_thumb_*` 前缀（这些是缓存性质，可重建）。当前 `exportDataJson` 已只导轻量字段，无需改。

### 方案④：清理 `_migration_backup` 残留（浏览器端）
- localforage 里 4 个 `_migration_backup` 键，几乎整份重复（实测 ~125MB）。属迁移残留，可在前端导出/恢复时跳过，或提供一次性清理。
- 独立于方案②，收益在**浏览器导出文件**层面（323MB→~200MB）。

### 方案①（长期治本）：前端图片直接落盘为 `/files/` 引用
- 前端在生成/保存图片时直接调 `POST /api/files/upload`，`data.imageUrl` 存 URL 而非 base64。**根治，但需改前端打包产物（H_.jsx/shared.js），风险高**。
- 方案②是它的后端等价实现，收益相同、风险更低，因此**短期不必做方案①**；若未来能安全改前端，可把方案②逻辑前移，进一步省掉 KV 里的 URL 中转。

## 4. 推荐落地路径

| 顺序 | 动作 | 改动 | 风险 | 收益 |
|------|------|------|------|------|
| **P0（本轮）** | **方案②：`handleKvSet` 外置 base64 为 `/files/` 磁盘文件** | `kv.ts` + 复用 `files.ts` 落盘 | 低（不碰前端） | localTool 库 79MB→几MB，整库备份 203MB→几MB，落盘提速 |
| **P0（本轮）** | **GC：KV 引用 ↔ uploads 磁盘孤儿文件清理**（§2.7①，方案②必配） | `admin.ts`/新路由 + `database.ts` | 低 | 防止 uploads 目录孤儿文件累积，避免膨胀转移 |
| P1 | 方案③：备份瘦身（方案②自动带来，可选补 `img_*` 排除） | `database.ts` | 极低 | 备份文件进一步变小 |
| P2 | 方案④：清理 `_migration_backup` | 前端导出/恢复 | 中 | 浏览器导出 323MB→~200MB |
| P3（长期） | 方案①：前端图片落盘 | 前端打包产物 | 高 | 彻底根治 |

> **一句话**：最优先做 **方案② + 配套 GC**——在 localTool `kv.ts` 的 `handleKvSet` 里把 base64 外置为磁盘文件（唯一收口点、前端零改动），同时新增「KV 引用 ↔ uploads 文件」对照 GC 清理孤儿文件（§2.7①），两者一起做，避免膨胀从 KV 转移到 uploads 目录。GC 与方案②必须**同批上线**，缺一不可。方案①只在未来能安全改前端时再考虑。

## 5. 给后续实现者的硬约束（基于真实代码）

- **不要逆向前端打包产物**去改 base64 生成点：`data:image` 产生自 `H_.jsx` / `shared.js` 多处（如 2884、5584 行的 `data:image/png;base64,${e.b64_json}`），改动面大、易回归。
- **最优改动点是 `localTool/src/routes/kv.ts` 的 `handleKvSet`**：它是所有 base64 的唯一入库收口，改一处覆盖全部来源。
- 复用 `files.ts` 的 `saveFile`/`writeUploadBuffer`/`tryGenerateThumbnail` 与 `fileStore.ts` 的 `resizeImage`，**零新依赖**。
- 文件名用内容 sha1 去重（对齐 `saveRemoteUrl` files.ts:97 惯例）。
- 失败必须回退保留原 base64，**逐字段** try/catch（单个失败不拖垮整条），失败字段打 WARN 日志，不破坏 `handleKvSet` 的 `{ok:true}` 契约与前端读回逻辑（§2.7③）。
- **GC 是方案②的必配项**（§2.7①）：扫描 KV 全部 value 提取 `/files/` 引用 ↔ uploads 实际文件对照，删孤儿；只删 uploads 目录内、保留 `.thumbnails/`、先 dry-run 再删。不做 GC 则膨胀从 KV 转移到 uploads 目录，方案②未闭环。
- 参考：`docs/18-KV存储键读写面梳理.md`（三处存储拓扑）、`docs/35-缩略图实现机制探索.md`（落盘/缩略图链路）、`localTool/src/routes/kv.ts`、`localTool/src/routes/files.ts`、`localTool/src/db/database.ts`。
