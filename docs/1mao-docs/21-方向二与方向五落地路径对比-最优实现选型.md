# 21 · 方向二 vs 方向五 落地路径对比 —— 最优实现选型

> 日期：2026-08-01
> 关联：`docs/01 长期目标-未来适配方向.md`（方向二 = 特惠视频支持第三方；方向五 = 内置模型平台接口走 localTool）、`docs/16`（特惠视频探究）、`docs/20`（权益转发层方案）
> 目的：在两条"待改 `src/bundle/`"的方向中，判断**哪一条实现起来最优**（改动最小、风险最低、收益最大），给出推荐执行顺序。
> 结论先行：**方向五显著优于方向二，应优先做方向五**；且方向五可与方向一合并为**同一次 `src/bundle/` base 改造**（`npm run build` 回灌 `dist/`），边际成本趋近于零。

---

## 一、两个方向的本质差异

| | 方向二 特惠视频支持第三方 | 方向五 内置模型平台接口 |
|---|---|---|
| 改造性质 | **改业务逻辑**（数据源、下拉组件、计费通道） | **改一个 base 地址**（请求指向） |
| 触及层面 | `src/bundle/` 组件树 + 状态 + 请求拼装 + 响应适配 | 仅 `src/bundle/` 网络层 base，改后 build 回灌 |
| 后端准备度 | 无（localTool 未参与特惠链路） | ✅ 已就绪（`platform.ts` 静态清单已实现并注册） |
| 是否牵涉钱 | ✅ 牵涉计费/额度，存在财务漏洞风险 | ❌ 纯清单展示，不涉计费 |
| 能否与方向一合并 | ❌ 不能（改点完全不同） | ✅ **完全可以**（同一条 base 链） |
| 可回滚性 | 弱（逻辑改动分散） | 强（改回原 base 即恢复） |

## 三、方向二：改动点盘点（证据）

### 3.1 硬隔离是设计而非 Bug

`docs/16` 已确认特惠链路与 `apiConfigs` 下拉**完全解耦**：

| 维度 | 普通视频节点 | 特惠视频节点 |
|---|---|---|
| 模型来源 | `apiConfigs` 合并清单 | 硬编码 `discountVideoModel`（`\n` 拆文本，混淆 `Ur`） |
| API 地址 | 选中 apiConfig 的 `.apiUrl` | 固定 `discountVideoApiUrl`（闭包常量 `u2`） |
| 鉴权 | 选中 apiConfig 的 `.apiKey` | 固定 `discountVideoApiKey`（闭包常量 `d2`） |
| 可切换 | 是 | 否（面板无下拉入口） |

### 3.2 需要改的东西（至少五类）

1. **上游来源**：`u2` / `d2` 由闭包常量改为 `apiConfigs.find(选中ID)` 驱动。
2. **UI 组件挂载**：把普通节点的"API 配置"下拉挂到特惠面板（组件存在，但未挂载 → 涉及组件树改动）。
3. **模型下拉数据源**：`Ur`（硬编码文本）切到"选中 apiConfig 的模型清单"渲染分支。
4. **路径模板兼容**：下游拼 `/v1/gateway/task/...`，第三方基址未必兼容，需约定或加适配。
5. **响应结构兼容**：轮询状态码（`3` / `"success"` / `"completed"`）第三方可能不一致，需适配层。

### 3.3 额外的非技术成本

- **计费漏洞（阻断级）**：官方锁死 url/key 就是为了强制走特惠计费通道；放开即绕过特惠计费。`docs/16` §6.2 建议白名单（`allowInDiscount`），这本身又是一套新机制（配置项 + UI + 校验）。
- **业务决策前置**：见 `docs/01` 方向二"前提辨析" —— 若全面自研接管，「特惠」概念本身消解，此时正确做法是**删除特惠节点的特殊性**而非给它加第三方支持。**决策未定，改造方向就未定。**

## 五、结论与推荐执行顺序

### 结论
**方向五是最优实现路径**，理由三条：

1. **边际成本近乎为零** —— 它与方向一是同一条 base 链，方向一迟早要改；改的时候方向五**自动生效**，等于"顺手完成"。
2. **后端零改动** —— `platform.ts` 两个 handler 与契约字段已完全就位，改完 base 即可验证。
3. **零财务风险** —— 只是模型清单展示，不触碰任何计费通道。

**方向二不建议现在做**：它的技术改造面是方向五的数倍，且真正的阻塞点不是技术而是**业务决策**（是否放弃官方特惠计费）。在决策明确前动手，很可能做完发现路线选错、整体推倒。

### 推荐顺序

```
第 0 步（前置，必做）：localTool 补 catch-all 兜底透传
        └─ 在 index.ts 404 之前插一层：未命中本地路由的请求原样转发官方
        └─ 目的：让 base 改造后「未接管的请求也不会 404」，而是经 localTool 转发出去

第 1 步（合并执行）：方向一 + 方向五 + 方向六
        └─ 一次 src/bundle base 改造：g() 链默认值 → http://127.0.0.1:18080，改后 npm run build 回灌 dist/
        └─ 一次改动同时点亮：权益转发层 / 内置模型清单 / A1 助手重定向
        └─ 有第 0 步兜底，无需逐条核对"哪些请求必须直连官方"

第 2 步：验证
        └─ 三类请求落 18080；官方不可达时权益走 stale 缓存（x-cache: hit-stale）
        └─ 模型下拉显示本地静态清单（seedance / kling / gpt-image / nano-banana）
        └─ 登录/支付等未接管请求经 catch-all 透传后功能不变

第 3 步：补数据
        └─ 填 BUILTIN_MODELS 的 discountVideoSpecs / power / unit / descriptions 空字段

第 4 步（可选、需决策）：方向二
        └─ 先定路线 A（保留官方特惠 + 白名单）还是路线 B（自研接管、删除特惠特殊性）
        └─ 若选 B，实为"做减法"：特惠节点并入普通视频节点
```

### 一个重要副作用（值得注意）
做完第 1 步后，**方向二的紧迫性会进一步下降**：因为内置模型清单已由 localTool 提供，`discountVideo` 字段与普通 `video` 字段本就返回**同一套 Lovart 模型**（`platform.ts:58` 注释明确"特惠视频与普通视频共享同一套 Lovart 模型"）。届时特惠节点与普通节点在**模型层面已无差别**，只剩 url/key 的通道差异 —— 这正是路线 B「特惠概念消解」的实证。

## 六、执行前置：localTool 全量接管（第 0 步详述）

### 原则（2026-08-01 确立）
**不再区分"哪些请求该直连官方、哪些该走 localTool"—— 全部走 localTool，即使最终目的地仍是官方，也必须经 localTool 转发。**

localTool 从"白名单路由服务"升级为"**唯一出口网关**"：

```
前端所有请求 → localTool 18080
   ├─ 命中本地路由（权益 / 模型 / 文件 / 任务 / 资源 …）→ 本地处理
   └─ 未命中 → catch-all 兜底透传 → 官方 1mao（原样回传）
```

### 为什么这一步是硬前置
当前 `localTool/src/index.ts` 是**逐条 `pathname === '...'` 精确匹配**，末尾兜底只处理静态页，其余一律 404：

```ts
// index.ts:326-331
if (method === 'GET' && !pathname.startsWith('/api/') && !pathname.startsWith('/plugin/') && !pathname.startsWith('/files/')) {
  if (handleFrontendPage(res, pathname)) return;
}
sendError(res, 'Not Found', 404);
```

⇒ 若**先改 base、后补透传**，则所有未注册的 `/api/*`（登录、支付、上传凭证等）会直接 **404，功能立刻损坏**。因此必须**先补 catch-all，再改 base**。

### catch-all 透传实现要点
| 要点 | 说明 |
|---|---|
| 插入位置 | `index.ts` 所有具名路由之后、404 之前 |
| 目标地址 | 复用 `official.ts:89-106` 的 `readOfficialBase()`（`x-official-base` 头 → KV `active_api_endpoint` → 默认 `https://www.1mao.cc`） |
| 转发内容 | 原样保留 method / path / query / body / 请求头（**尤其 `Authorization: Bearer`**） |
| 响应处理 | 原样回传状态码 / 响应头 / body，**不改写、不缓存** |
| 流式支持 | 必须支持 SSE 透传（A1 `/agent/*/chat` 依赖流式） |
| 可观测 | 统一 `[proxy]` 日志前缀，token 脱敏；便于统计"还有哪些接口在连官方" |
| 排除项 | 静态页托管（`handleFrontendPage`）与 `/files/` 本地文件仍走本地，不进透传 |

### 收益
1. **改 base 零风险** —— 未接管请求行为不变，只多绕一跳。
2. **免除白名单核对** —— 不需要再逐条排查 `docs/20` §9.1 直连清单哪些能改哪些不能。
3. **后续接管零前端成本** —— 想本地化任何接口，只在 localTool 加一条路由即可，**dist 一行都不用再动**。
4. **全链路可观测** —— 所有出站流量集中一处，日志可见。

#### ⚠️ 重验证中发现并修复的既有 Bug（权益转发层路径缺 `/api` 前缀）

复验时发现 `/api/user/info` 返回的是 **HTML 而非 JSON**，追查为 `official.ts` 的**既有缺陷**（非本次透传层引入）。

官方同名路径存在**两套路由**，实测对照：

| 官方 URL | 状态 | Content-Type | 性质 |
|---|---|---|---|
| `https://www.1mao.cc/api/user/info` | 401 | `application/json` | ✅ 真接口 |
| `https://www.1mao.cc/user/info` | 200 | `text/html` | ❌ 前端页面路由 |

而 `official.ts` 原先转发目标写作 `${base}/user/info`（**漏了 `/api`**），于是：
1. 打到官方**前端页面**，拿回 200 HTML 登录页；
2. 因 `fetchRes.ok === true`，HTML 被当作合法权益数据**缓存 60s**（复验时实测 `x-cache: hit`）；
3. 前端若已改 base，会读到一坨 HTML 而非权益 JSON —— **属会静默污染缓存的隐性故障**。

修复（两处）：
- **路径修正**：三个端点转发目标补 `/api` 前缀 —— `/api/user/info`、`/api/user/model-entitlements`、`/api/agent/:id/vip-check`。
- **类型防线**：`forwardGet` 写缓存前增判 `content-type` 含 `json`；非 JSON 的 2xx 一律**透传但不缓存**，并打 `[official] 跳过缓存` 警告。防止未来再次「打错路由却静默缓存」。

修复后四个端点均正确返回官方 401 JSON（`{"error":"无效或过期的认证令牌"}`），与直连官方行为一致。

> 教训：**localTool 转发官方时，路径必须与官方接口完全一致（含 `/api` 前缀）**；`fetchRes.ok` 不足以判定「拿到的是业务数据」，还需校验 Content-Type。
