## 二、P0 修复（阻塞一切生成/对话，最高优先，三处同在 `/api/proxy`）

`system.ts` 的 `handleProxy`（`system.ts:24-39`）是画布唯一出口，三缺陷连带让所有生成/对话失败。**P0 是解锁一切的前提，建议最先动手。**

### P0-1 解除 15s 硬超时 `[未实施]`
- **问题**：`handleProxyFormData`（`system.ts:68`）与 `handleProxyJson`（`system.ts:132`）均 `setTimeout(() => controller.abort(), 15000)`，超时返 504。视频提交、流式对话等长任务必然被掐断。
- **修复**：超时改为可配置，读 `process.env.PROXY_TIMEOUT`（默认 `300000` 即 300s）；两处 `setTimeout` 统一替换为环境变量值。
- **验证**：提交一个 >15s 的视频任务，`[proxy] ... | TIMEOUT` 日志消失（日志位置 `system.ts:81`/`system.ts:145`）。
- **风险**：低。仅放宽超时；不影响转发逻辑。**边界**：默认 300s 上限在"异步提交 + 短轮询"模式下通常足够（轮询请求本身 <1s）；但若单请求真超 5 分钟（如超长视频同步生成），仍会被掐——此时应依赖高-1 的异步提交模式而非拉长超时。

### P0-2 转发 SSE 流式 `[未实施]`
- **问题**：`handleProxyFormData`（`system.ts:80` 缓冲 + `:92-93` 一次性 `writeHead/end`）与 `handleProxyJson`（`system.ts:144` 缓冲 + `:155-156` `writeHead/end`）均整段 `Buffer.from(await fetchRes.arrayBuffer())` 后回写，**不转发流**；`chat/completions` 带 `stream:true` 收不到增量 → 对话假死。
- **修复**：当下游响应 `Content-Type` 含 `text/event-stream`（或请求体 `stream:true`）时进入流式路径：
  1. **绝不可设置 `Content-Length`**，由 Node 自动 `Transfer-Encoding: chunked`；
  2. 透传 `Content-Type: text/event-stream` 与 `Cache-Control: no-cache`；
  3. **`content-encoding` 必须显式处理（致命坑）**：现有 `skipHeaders`（`system.ts:85`/`:148`）会把 `content-encoding` 剔除——若下游返回 gzip/br 压缩流，剥离该头后把原始压缩字节直接 pipe 给前端 → 前端收到无法解码的乱码。**修复时二选一**：(a) 转发前本地 `decompress`（`zlib`/`undici` 的 `decompressed()`）再 pipe 纯文本流；或 (b) **保留** `content-encoding` 头随压缩字节一并透传，由前端按头解码。**推荐 (a)，避免前端解码依赖**。
  4. `res.writeHead(fetchRes.status, cleanHeaders)` 后 `Readable.fromWeb(fetchRes.body).pipe(res)`；非流式仍走原缓冲路径。
- **验证**：调试面板「请求日志」里 `chat/completions` 出现持续流入的分块响应（非一次性 200）；压缩响应下前端能正常渲染（非乱码）。
- **风险**：中。需正确处理流式头 + `content-encoding`（见上坑），避免双重缓冲与乱码。

### P0-3 协议翻译层 `[未实施·架构决策见下]`
- **问题**：`handleProxy`（`system.ts:24-39`）纯透传 header+body，网关返回 `{code,data}` 信封若与前端解析预期不符 → 白收到。
- **架构决策（消除与高-1 双重翻译）**：**网关只 alias/透传 Lovart 原生响应，所有字段映射集中在 P0-3 翻译层**。即 `main.py` 侧 G1/G2/G3 仅做路由别名与必要透传（不拆 `{code,data}`、不做前端形状映射），P0-3 统一负责"识别 `body.code`/`body.data` 信封 → 映射成前端形状"。这样高-1 不会产出前端形状（不会让 P0-3 变死代码），翻译职责唯一。
- **修复**：在转发返回处加轻量适配——识别 `body.code`/`body.data` 信封，按端点映射成前端形状（见 S5）；未知结构原样透传降级。
- **严重度说明**：标"阻塞一切"指"无翻译层则前端拿不到可用数据"。**前端取字段实证已部分完成**（已读 `dist/` 打包产物）：G2 期望 `status==="succeeded"`+`results[0].url`（httpClient:561）、S5 draw 期望 `data[0].task_id`（配合 `main.py:117` 的 `{code:200,data:[...]}` 信封）。其余端点映射规则仍建议联调时固化。
- **验证**：生图/对话返回能被前端正常解析（结合 P0-2 流式 + S5 联调）。
- **风险**：中。映射规则需与前端取字段一致，建议先联调再固化。

## 八、安全操作与回退（防改错 / 审计可追溯）

> **状态**：本工作区已 `git init`（`035ed2c` 基线快照「改动前可跑版本」）。所有修复均可在改错后 `git checkout -- <文件>` 秒回。localTool 为 TypeScript 源码（`build = tsc`），改 `src/*.ts` 须 `npm run build` 生成 `dist/index.js`；网关 `main.py` 为单文件 Python，改完直接重启 uvicorn。

### 8.1 版本管理（回退保险）
- 已建 git 仓库；每次改完**一个断点**就 `git add -A && git commit -m "fix: xxx"`，形成可回退节点链。
- 改错回退：`git checkout -- localTool/src/routes/system.ts`（单文件回到上次提交）；或 `git revert <commit>` 回退整次改动。
- 未建 git 兜底：改前 `cp <file> <file>.bak`，恢复时 `.bak` 覆盖回去再 build/重启。

### 8.2 单点修改协议
1. **一次只改一个函数/一个断点**（如只动 `system.ts:68` 超时），不攒一堆一起改。
2. 改完先 `npm run build`（tsc 类型检查）——语法/类型错在此拦下，且 **build 没成功不会覆盖 `dist/`，原服务不受影响**。
3. localTool 改 `src/*.ts` → `npm run build` → 重启 `node dist/index.js`（或 `start.sh`）；扩展在 `chrome://extensions` 点「重新加载」。
4. 立刻跑端点探针（🔍 → ▶ 探针）确认这一改没把别的搞坏。

### 8.3 救援清单
| 症状 | 原因 | 救法 |
|---|---|---|
| `tsc` 报错 | 类型/语法错 | 按红字改；未 build 成功不覆盖 dist，原服务仍跑 |
| build 过但功能坏 | 运行期逻辑错 | `git checkout` 还原 `src` → 重新 `npm run build` → 重启 |
| 网关启动报错 | `main.py` 逻辑错 | 还原 `main.py` → 重启 uvicorn |
| 扩展面板异常 | `background.js`/`debug-panel.js` 写错 | 调试基建坏了不影响主功能；还原备份或 reload 旧版 |
| 全乱了 | 多处改崩 | 所有 `src`+`main.py` 还原基线 → `npm run build` → 重启 → 回到可跑状态 |
