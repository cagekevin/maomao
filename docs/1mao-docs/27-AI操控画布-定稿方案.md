## 0. 结论

**1mao 官方 A1 画布助手前端黑盒已内置完整的「AI 操控画布」闭环**（30 个画布工具 + Agent 多轮循环 ≤8 轮 + 浏览器端实时执行器 `lr()`，直接操作 React Flow 内存画布）。**真正缺的只有后端**：一个支持 `tools`/`tool_calls` 的 LLM 中转端点。

```
浏览器（官方 A1 黑盒，前端闭环已齐）
   │  POST http://127.0.0.1:18080/api/agent/{id}/chat   (SSE, 标准 OpenAI 格式)
   ▼
localTool 新增 POST /api/agent/:id/chat   ← 本次实施的核心
   │  透传 messages+tools 到「支持 function calling 的 LLM」
   │  返回 SSE (含 tool_calls) 原样透传
   ▼
浏览器 → tool_calls → lr() 实时执行画布操作 → 回填 role:'tool' → 下一轮（前端自动）
```

**⚠️ 关键前提（必须满足）**：现有网关 `apimart-gateway /v1/chat/completions` 是 **Lovart 纯中转**（只拼 prompt 对话，**忽略 `tools`、不返回 `tool_calls`**），**无法驱动 A1 工具循环**。因此必须接入一个**支持 function calling（tools）的 OpenAI 兼容 LLM**，见 §4。

## 1. 官方 30 个画布工具（完整 schema，直接抄给 LLM）

## 2. 前端 A1 的请求/响应协议（已逆向 100% 确认）

### 2.1 请求体（前端 `v` 函数组装，`shared.js:2555-2627`）
```json
{
  "model": "gpt-4o-mini",                    // 组件 defaultModel，可由后端忽略/覆盖
  "messages": [
    { "role": "system", "content": "<前端拼的 system prompt>" },
    { "role": "user", "content": "..." },
    ...多轮...
    { "role": "assistant", "content": "...", "tool_calls": [ {...} ] },   // 每轮回填
    { "role": "tool", "tool_call_id": "call_...", "content": "{\"ok\":true,...}" }
  ],
  "tools": [ {30个工具 schema} ],            // 前端 cr(t) 传入
  "tool_choice": "auto",
  "stream": true,
  "temperature": 0.6
}
```
**要点**：后端必须**保留多轮 `messages` 上下文**（每轮前端会带全量历史+tool 结果），不能只转第一轮。

### 2.2 请求地址
- `POST ${Je}${st}/agent/${id}/chat`，`Je = g() = u() || l()`，`g()` 默认回退 `http://127.0.0.1:18080`。`st` 为前端导入的混淆变量，源码中未直接定位到字面量 `st = '/api'`，但 `Je` 与 `st` 拼接后形成 `/api/agent/:id/chat` 路径（见 `shared.js:2629` 的 `fetch(`${Je}${st}/agent/.../chat`)`），故路径后缀确为 `/api/agent/:id/chat`。
- 头：`Authorization: Bearer <token>`（`We()` 登录态）+ `Accept: text/event-stream` + `Content-Type: application/json`。
- **结论：默认已到 localTool 18080**（sessionStorage 未设官方地址时）。

### 2.3 SSE 响应格式（前端按 `data:` 前缀解析）
```json
data: {"choices":[{"delta":{"content":"你好"}}]}
data: {"choices":[{"delta":{"reasoning":"...","reasoning_content":"..."}}]}
data: {"choices":[{"delta":{"tool_calls":[{"index":0,"id":"call_abc","type":"function",
      "function":{"name":"create_node","arguments":"{\"type\":\"promptNode\"}"}}]}}]}
data: [DONE]
```
- **`tool_calls` delta 按 `index` 增量拼接**：`id`/`name`/`arguments` 都可能分片出现，前端用工具调用累积器类（混淆名 `Hd`，`shared.js:2659` 实例化，2660-2673 累积合并同 `index`）——文档此前写的 `ToolCallAccumulator` 为虚构类名，实际源码无此名。
- `arguments` 是 **JSON 字符串**，可能被拆成多个 delta 片段，前端拼完整后 `JSON.parse`。
- 前端读完 `[DONE]` 后 `clearTimeout`，关闭流。
- 支持 `content`（正常回答）、`reasoning`/`reasoning_content`（思考）、`tool_calls` 三类 delta。

### 2.4 多轮循环（前端 `send`，`shared.js:2786-2895`）
```
do {
  POST /agent/:id/chat {messages(含历史+tool), tools, stream}
  for each SSE delta: 累积 content/reasoning/tool_calls
  若 tool_calls.length > 0:
     for each tool_call:  r = lr(name, args, canvasHandleRef)
       push {role:'tool', content:r, tool_call_id}
     push {role:'assistant', content, tool_calls}
     继续下一轮（最多 ur=8 轮）
  else break
} while(...)
```
- **执行器在浏览器端**：后端完全不需要理解画布，只负责「LLM 理解 tools 并返回 tool_calls」。

### 2.5 借鉴无限画布（infinite-canvas）增强本地 Agent（高价值）

无限画布 `canvas-agent` 的工具协议（`canvas_get_state`/`canvas_apply_ops`/`config` 节点）与官方 A1 的 30 工具（`list_nodes`/`create_node`/`trigger_generation`）**是两套不同协议，工具本身不能直接搬**。但它的**「提示词写作范式」和「工具描述文案」质量极高，可直接复用**来增强官方 A1 的本地 Agent。

#### 2.5.1 可直接复用的「行为准则提示词」（`agent-instructions.md` 改编）

官方前端会在 `messages[0]` 带自己的 system prompt。为增强其画布操控能力，可在 localTool 的 `handleAgentChat` 里**给 system message 追加**（或替换）以下准则——由无限画布范式改写为官方 30 工具：

```text
你是 1mao 画布助手，正在帮助用户操作当前打开的画布。

【基本原则】
- 用户要求操作画布时，默认目标就是当前已打开的画布。先调用 list_nodes 了解现有节点，
  再执行任务；不要臆造节点 id，不要假设画布为空。
- 不要模拟鼠标点击，不要要求用户手动复制 JSON。直接用工具完成画布操作。

【读取】
- 操作前先 list_nodes（获取全部节点 id/type/标题/坐标）。
- 需要看节点内容时用 get_node_details；需要连线结构用 list_edges。

【创建】
- 新建节点用 create_node，type 枚举：textNode（文本）、promptNode（提示词/生成配置）、
  discountVideoNode（视频）、imageNode（图片）。
- 提示词/生成配置节点务必填 prompt；图片节点填 label 作说明。
- 批量创建多个同类节点用 batch_create_nodes；多个并行连线用 batch_connect_nodes。

【修改与生成】
- 改节点用 update_node（白名单字段 prompt/label/selectedModel/aspectRatio/resolution/seconds/text）。
- 改任意原始字段才用 update_node_raw，且只改必要字段，不要抹掉其他 data。
- 用户要求生成内容时，用 trigger_generation 触发已有节点（先确保该节点有提示词），
  或 create_node(promptNode, prompt=...) 后 trigger_generation。
- 生成任务提交后应说明「已在画布开始生成」，不要在没有结果时声称「已生成」。

【组织】
- 相关节点用 connect_nodes 连线表达数据流（source→target）。
- 调整布局用 move_node；删除用 delete_node（会连带删线）。
- 放大/缩小视口用 zoom_in/zoom_out；定位节点用 focus_node。
```

> 这套准则把「先读再改」「批量用 batch」「生成前先建带提示词节点」「不声称未发生的事」等关键行为固化进 prompt，是无限画布已验证有效的范式。

#### 2.5.2 可复用的「工具描述」文案（从无限画布 toolDescriptions 改写）

无限画布的中文工具描述写得很好（如 `canvas_create_config_node` 的「创建生成配置节点，可指定模式和生成参数，可选择立即触发」）。可仿此给官方工具补齐**中文描述**（前端 `or` 数组里的 description 往往是英文或简略），让 LLM 更懂每个工具。示例：

| 官方工具 | 建议中文描述（仿无限画布风格） |
|---|---|
| `create_node` | 在当前画布创建节点。type：textNode(文本)、promptNode(提示词/生成配置)、discountVideoNode(视频)、imageNode(图片)。提示词/视频节点填 prompt，图片节点填 label。 |
| `trigger_generation` | 触发指定节点的生成任务。调用前确保该节点已有提示词（用 update_node 或 create_node 设置）。生成为异步过程，提交后返回状态。 |
| `batch_create_nodes` | 批量创建多个节点，适合一次搭建整条生成流程（提示词→配置→视频/图片）。 |
| `connect_nodes` | 连接两个节点表示数据流（source 的输出流向 target）。 |
| `get_node_details` | 读取节点完整 data（提示词、模型、尺寸、生成结果 URL），用于了解生成配置。 |
| `update_node_raw` | 直接更新节点的任意原始 data 字段（高级）。仅改必要字段，避免覆盖其他数据。 |

#### 2.5.3 具体落地位置

- **准则提示词**：⚠️ 注意前端数据流——`shared.js:2586-2591` 在本地组装请求时，用 `g.current` 作为唯一 system，并**把传入 `messages` 里所有 `role:'system'` 过滤掉，不会发到后端**。因此后端收到的 `messages` **不含任何 system**。落地时：后端 `messages` 中 `findIndex(m => m.role === 'system')` 恒为 -1，应直接 `messages.unshift({ role:'system', content: rules })` 插入一条本地准则 system（不要写"追加到官方 system"，因为官方 system 不在后端收到的消息里）。可做成可配置开关 `AI_CANVAS_SYSTEM_PROMPT_FILE`（或 `AI_CANVAS_ENHANCE !== '0'` 控制，见 §3.2）。
- **工具描述**：通常前端已传完整 `tools`，无需后端补；若前端 `or` 的描述过简，可在转发前对 `tools[].function.description` 做替换/补充。

#### 2.5.4 提醒：工具协议别混淆

- 无限画布是 `canvas_get_state`/`canvas_apply_ops`/`config` 节点——**不能用于官方 A1**。
- 官方 A1 是 `list_nodes`/`create_node`/`trigger_generation`——用它自己的 30 工具。
- 增强只发生在「提示词/描述文案」层面，工具协议必须用官方 A1 那套。

### 3.2 核心处理器（新建 `localTool/src/routes/agentChat.ts`）

```ts
import type { IncomingMessage, ServerResponse } from 'node:http';

// LLM 渠道配置（支持 function calling 的 OpenAI 兼容端点，见 §4）
// 注意：现有 localTool 直接用 process.env 读取配置，无 env/logger 封装模块，故此处直读。
const LLM_BASE = process.env.LLM_CHAT_BASE_URL || 'http://127.0.0.1:9004/v1/chat/completions';
const LLM_KEY  = process.env.LLM_CHAT_API_KEY  || '';
const ENHANCE_ON = process.env.AI_CANVAS_ENHANCE !== '0';   // 默认开启
const LLM_TIMEOUT_MS = 120_000;                              // 与 §6 一致

export async function handleAgentChat(req, res, agentId) {
  // 1. 鉴权（可选）：与 vip-check 对齐，校验 Bearer token
  //    需自行实现 getAuthToken / checkToken（参考 official.ts 的 tokenPrefix 鉴权写法）
  const token = getAuthToken(req);
  if (token && !(await checkToken(token))) {
    res.writeHead(401, { 'Content-Type': 'application/json' });
    res.end(JSON.stringify({ error: 'unauthorized' })); return;
  }

  // 2. 读 body（同时保留前端 AbortSignal 以便透传，见 §6）
  const frontSignal = (req as any).signal as AbortSignal | undefined;
  let body = '';
  for await (const chunk of req) body += chunk;
  let payload;
  try { payload = JSON.parse(body); }
  catch { res.writeHead(400, { 'Content-Type': 'application/json' });
          res.end(JSON.stringify({ error: 'invalid json' })); return; }

  const { model, messages, tools, tool_choice, stream = true, temperature = 0.6 } = payload;
  if (!Array.isArray(messages) || messages.length === 0) {
    res.writeHead(400, { 'Content-Type': 'application/json' });
    res.end(JSON.stringify({ error: 'messages required' })); return;
  }

  // 2.5 增强：插入「画布操作准则」system message（见 §2.5.3）
  // 注意：前端已把入参里的 system 过滤掉（shared.js:2586-2591），
  // 后端收到的 messages 不含 system，故直接 unshift 一条即可，不要写"追加"。
  if (ENHANCE_ON) {
    const rules = loadCanvasAgentRules();   // 需自行实现：读取 §2.5.1 的准则文本（文件或常量）
    messages.unshift({ role: 'system', content: rules });
  }

  // 3. 转发到支持 function calling 的 LLM（透传 messages + tools），带超时与前端 signal
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), LLM_TIMEOUT_MS);
  if (frontSignal) frontSignal.addEventListener('abort', () => controller.abort());
  let upstream;
  try {
    upstream = await fetch(LLM_BASE, {
      method: 'POST',
      signal: controller.signal,
      headers: {
        'Content-Type': 'application/json',
        'Accept-Encoding': 'identity',   // 避免上游返回 gzip，见下方注意
        ...(LLM_KEY ? { Authorization: `Bearer ${LLM_KEY}` } : {}),
      },
      body: JSON.stringify({
        model: model || 'gpt-4o-mini',
        messages,
        ...(tools && tools.length ? { tools, tool_choice: tool_choice || 'auto' } : {}),
        stream: true,
        temperature: temperature ?? 0.6,
      }),
    });
  } catch (e) {
    clearTimeout(timer);
    res.writeHead(502, { 'Content-Type': 'application/json' });
    res.end(JSON.stringify({ error: `upstream error: ${e.message}` })); return;
  } finally {
    clearTimeout(timer);
  }

  // 4. SSE 透传
  res.writeHead(200, {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache',
    Connection: 'keep-alive',
    'X-Accel-Buffering': 'no',
    'Access-Control-Allow-Origin': '*',
    'Access-Control-Allow-Headers': 'Content-Type, Authorization',
  });
  res.flushHeaders?.();

  // 用 existing SSE passthrough helper（如已有）或手动透传：
  try {
    if (upstream.body) {
      // 直接透传字节流（网关/LLM 已输出标准 SSE data: 行）
      const reader = upstream.body.getReader();
      const decoder = new TextDecoder();
      while (true) {
        const { done, value } = await reader.read();
        if (done) break;
        res.write(decoder.decode(value, { stream: true }));
      }
    }
  } catch (e) {
    res.write(`data: {"error":"${String(e?.message || e).replace(/"/g, '\\"')}"}\n\n`);
  } finally {
    res.end();
  }
}
```

> **注意**：若 LLM 返回 gzip，需解压后再透传；建议在 `fetch` 时设 `Accept-Encoding: identity` 或处理 gzip（复用 `system.ts` 的 `gunzip` helper）。若上游不支持流式（返回非 SSE），需把它包装成 SSE 行。

### 3.3 CORS 与 OPTIONS

### 3.4 vip-check 放行

## 4. LLM 后端：必须支持 function calling（**本方案核心难点**）

### 4.1 为什么现有网关不行
`apimart-gateway/main.py:614+` 的 `/v1/chat/completions`：
- 是 **Lovart 中转**：把 `messages` 拼成纯文本 prompt 发去 Lovart 对话（628-650）。
- **不解析 `tools`、不返回 `tool_calls`**（`apimart-gateway/main.py` 内搜 OpenAI 格式的 `tool_calls`/`tools` 零结果；注意：`lovart_client.py`/`agent_skill.py` 里的 `include_tools`/`exclude_tools` 是 Lovart Agent 自己的工具开关参数，不是 OpenAI 的 `tools`/`tool_calls`，勿混淆）。
- → 前端收不到 `tool_calls` → 永远不调 `lr()` → 画布不被操作，只回纯文本。

### 4.2 两个可实施选项（已确认 AB 均可）

**选项 A：接入支持 function calling 的 OpenAI 兼容服务（推荐，最直接）**
- 在 localTool 配置 `LLM_CHAT_BASE_URL` + `LLM_CHAT_API_KEY`，指向一个支持 `tools` 的端点（DeepSeek / 通义千问 dashscope / 真实 OpenAI / 或任何 OpenAI 兼容 function-calling 服务）。
- 例如 DeepSeek：`https://api.deepseek.com/v1/chat/completions`，模型 `deepseek-chat` 支持 function calling。
- localTool `handleAgentChat` 直接转发（§3.2 的 `LLM_BASE` 设成该地址）。
- **优点**：零改造网关，配置即用。**注意**：需确认所选模型的 `tool_calls` 返回格式兼容 OpenAI delta（绝大多数 OpenAI 兼容服务都一致）。
- **⚠️ 配置提醒**：§3.2 中 `LLM_BASE` 的**默认值** `http://127.0.0.1:9004/v1/chat/completions` 是 apimart-gateway（纯 Lovart 中转，**不支持 tools**，见 §4.1）。选 A 时**必须显式设置 `LLM_CHAT_BASE_URL`** 指向支持 function calling 的端点，否则会落到 9004 网关、前端收不到 `tool_calls`。

**选项 B：扩展现有网关支持工具调用**
- 改 `apimart-gateway/main.py`：`/v1/chat/completions` 支持透传 `tools` 并解析 `tool_calls`。
- **前提**：Lovart 底层模型是否支持 function calling —— **需验证**。若 Lovart 只回纯文本，则 B 无法落地，只能走 A。
- **做法**：若底层支持，则把 `tools` + `messages` 完整透传给 Lovart 的 chat 接口，解析其返回的 `tool_calls`，包装成 OpenAI SSE delta 输出。

### 4.3 推荐组合
- **先做 A**（接一个支持 function calling 的 OpenAI 兼容服务），快速让 A1 画布助手本地跑通、验证全链路。
- **B 作为可选优化**：若后续想纯用 Lovart 且验证其支持 tools，再扩展网关。
- 两者共用 localTool 的 `handleAgentChat`（A 直接转发；B 转发到本地网关，网关再透传 Lovart）。

## 6. 边界与错误处理

| 场景 | 处理 |
|---|---|
| `messages` 为空 | 400 返回 `{error:'messages required'}` |
| LLM 上游连接失败 | 502 返回 `{error:'upstream error: ...'}` |
| LLM 超时 | 透传层 `AbortController` 超时（建议 120s），断流 |
| 前端取消（`AbortSignal`） | 转发请求带前端 signal，取消时 `res.end()` 清理 |
| LLM 返回 gzip | **优先在请求头声明 `Accept-Encoding: identity` 规避**（见 §3.2）；若上游仍返回 gzip，再用 `system.ts` 的 `gunzip` 兜底解压后透传 |
| LLM 返回非 SSE（如 JSON 错误体） | ⚠️ §3.2 当前代码**仅透传 `upstream.body`，未实现「按行包成 `data:`」分支**。若上游返回非 SSE（如 `{"error":...}`），前端因缺 `data:` 前缀会解析失败。需在 §3.2 补：`if (!upstream.headers.get('content-type')?.includes('text/event-stream'))` 时把 body 读成文本、包成 `data: {json}\n\n` 再写回 |
| `tool_calls` arguments 分片 | 前端自己累积（Hd 类，shared.js:2659），后端无需处理 |
| 多轮上下文 | 前端每轮带全量 messages，后端无状态即可（透传） |
| token 鉴权失败 | 401（可选，与现有体系对齐） |
| 8 轮耗尽 | 前端自动断（`ur=8`），后端无需管 |

## 10. 盲点与模糊地带（已查证，实施前必读）

以下为逐条比对 `localTool/src`、`src/bundle` 前端打包代码后发现的**盲点（文档未覆盖、实施后必踩）**与**模糊地带（描述含糊、易误读）**。均为工具实测证据，未改动上文已验证正确的结论。

### 10.1 盲点 A（致命）：vip-check 是否真为 chat 前置闸门 —— 文档假设未证实

- 文档 §3.4 方案二断言："放行 vip-check 后前端才会正常发起 chat"。
- **实测**：chat 发送函数 `v`（`shared.js:2579`）的前置校验只有 `We()`（取登录 token，失败抛"请先登录"），**并未调用 vip-check 函数 `ar()`**（`ar()` 定义于 `shared.js:1248`，全仓仅约 3 处调用，需进一步确认是否含 chat 入口闸门）。
- **结论**：chat 入口目前**只依赖登录态，不读 vip-check 的 `allowed` 返回值**。§3.4"否则前端不会发起 chat"的因果链**未被代码证实**。实施前务必实测：`ar()` 到底在哪被调用、是否真的闸住 chat 按钮；若不影响 chat 发起，则 §3.4 的 vip-check 放行是**可选优化**而非**必需前置**，文档说法需据此修正。

### 10.2 盲点 B（致命）：工具执行依赖「画布句柄 `r.current`」—— 文档完全未提

- 前端多轮循环执行工具时（`shared.js:2861`）：`let i = r.current; for (let t of n.tool_calls) { ... lr(t.function.name, n, i) : 返回 {ok:false, error:"画布句柄未就绪"} }`。
- 即 `lr()`（工具执行器，`shared.js:1896`）的第三个参数 `i` 必须是非空的**画布句柄**（`r` 是从 vendor chunk 导入的 ref，`Rr as r`），否则**所有工具调用一律返回"画布句柄未就绪"**。
- **结论**：即使 §3.2 chat 路由打通、LLM 正常返回 `tool_calls`，只要本地引擎模式下 `r.current` 未被正确初始化，画布节点一个都不会变。文档 §2.4 对 `lr()` 执行工具的这个前置依赖**零提及**，是实施后最易踩的坑。实施前需确认：`r.current`（画布句柄）在 localTool 18080 托管的前端运行时里由谁、何时赋值、本地引擎模式下是否正常。

### 10.3 盲点 C（已澄清，非问题）：passthrough 兜底不会 404 chat

- `passthrough.ts:81`：`LOCAL_ONLY_PREFIXES = ['/files/', '/plugin/']`，**不含 `/api/agent/`**。
- 若 chat 未注册具名路由，请求会落入 `handlePassthrough` 透传官方（而非 404）；但 `passthrough.ts:195` 注释明确：A1 助手 `/agent/*/chat` 依赖流式，缓冲会导致打字机效果失效。
- **结论**：§3.1"先注册具名路由"方向正确，与本实测一致，无需改动。

### 10.4 盲点 D（模糊）：8 轮上限 `ur=8` 是前端硬编码，不可配置

- `shared.js:2536`：`var ur = 8`；循环 `shared.js:2807`：`for (let t = 0; t < ur; t++)`。
- **结论**：多轮工具链超过 8 轮会被前端硬截断。文档 §2.4/§6 提到 `ur=8` 但未说明"硬编码、非配置项"。若业务工具链可能超 8 轮，需评估前端改 `ur` 或拆任务。

### 10.5 盲点 E（模糊）：`lr`（执行器）与 `cr`（schema）相邻易混，但文档均正确

- `cr`：`shared.js:1893`，生成 `tools` schema（请求体 `tools: cr(t)`）。
- `lr`：`shared.js:1896`，工具执行器（前端多轮循环调用）。
- **结论**：两者都在 `shared.js` 且相邻，文档 §1/§2.4 的行号标注均准确，无需修正（此处澄清以防误读）。

### 10.6 模糊 F/G：§6 表格已就地对齐（见上表）

- gzip：§3.2 已用 `Accept-Encoding: identity` 主动规避，gunzip 仅兜底。
- 非 SSE：§3.2 当前**未实现**"按行包成 data:"分支，§6 已标注需在 §3.2 补该分支，否则上游 JSON 错误体直透会导致前端解析失败。
