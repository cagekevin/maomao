在 `main.py` 顶部（`import time` / `import uuid` / `import os` 已存在，见 16-19 行，**不要**新增 `import time as _time`）：

```python
# main.py 顶部，app 定义之前（time/uuid/os 已 import，直接复用）
GATEWAY_LOG_LEVEL = (os.getenv("LOG_LEVEL") or "info").lower()

def _log(msg: str, level: str = "info") -> None:
    # level 控制粒度；GATEWAY_LOG_LEVEL=debug 时连 debug 行也输出
```

### 3.2 `upsertTask` 伪 upsert 抹库 —— **真根因，必须修**（P0）

**现象**：`tasks` 表 `request_data` 列存在（`database.ts:107`），但前端视频任务的 `request_data` 实测为 **None**。v4 误归因于"前端黑盒不填"——**不准确**：前端（httpClient `output.js`）实际在 `diffAndPersistTasks` 里写了 `requestData`（含 `reference_videos` 等），但据 `docs/11` 第 150 行核查，当前 `dist` 构建中 `diffAndPersistTasks`/`batch-save` 自动同步路径**仅有定义、无调用点，疑似死代码**，真正写入 `tasks` 表的路径未反混淆出。因此 `request_data` **不是"前端不写"，而是"前端写了但持久化函数没被调用"**——根因在链路而非字段本身。**无论前端走哪条路径，最终完整请求体只在网关 9004 收口**，故 §2.1 的网关级 `ref_videos_raw` 打点才是唯一可靠取证点。而即使落库通路被修通，`upsertTask` 伪 upsert 仍会在每次部分字段 PATCH 时抹掉 `request_data`，故以下修复仍必须做：

```63:69:localTool/src/routes/tasks.ts
function upsertTask(db: any, row: Record<string, unknown>) {
  const keys = Object.keys(row);
  const vals = Object.values(row);
  const placeholders = keys.map(() => '?').join(', ');
  run(db, `DELETE FROM tasks WHERE task_id = ?`, [row.task_id]);
  run(db, `INSERT INTO tasks (${keys.join(', ')}) VALUES (${placeholders})`, vals);
}
```

这是 **DELETE + INSERT 伪 upsert**，不是真 UPSERT。后果：**任何一次只带部分字段的保存**（如前端轮询只 PATCH `progress`），都会先把整行 DELETE 再 INSERT 部分字段，已落库的 `request_data`/`response_data`/`error_msg` **全部丢失**。

**修复（真 UPSERT，用 INSERT ... ON CONFLICT 兜底已有列）**：

```ts
function upsertTask(db: any, row: Record<string, unknown>) {
  // 1) 先按主键取出现有行（保留历史诊断字段）
  const existing = queryOne(db, `SELECT * FROM tasks WHERE task_id = ?`, [row.task_id]);
  const merged = existing ? { ...existing, ...row } : row;
  const keys = Object.keys(merged);
  const vals = keys.map(k => merged[k]);
  const placeholders = keys.map(() => '?').join(', ');
  const cols = keys.join(', ');
  const updates = keys.map(k => `${k} = excluded.${k}`).join(', ');
  run(db,
    `INSERT INTO tasks (${cols}) VALUES (${placeholders})
     ON CONFLICT(task_id) DO UPDATE SET ${updates}`,
    vals);
}
```

> 这样部分字段保存不再抹掉 `request_data`/`response_data`。修复后，前端多次 PATCH 进度也能保住首次提交时写入的请求体。**这是"字段有了却查不到"的真正修复点，优先级高于 §3.1 的 proxy 摘要。**

### 3.4 审计澄清与补充（第四轮，基于 v6 复核）

> 第四轮审计多数指控针对**更早版本**（前端改一半、`get_status` 二元组、`_log` 当成既有能力、第二章整章改前端、localTool 需 PATCH 路由）——这些在 **v6 已修正或本就不存在**（v6 第 3/15/297 行已明确"前端黑盒改不得、不列入"；第 17 行已声明网关零日志设施需从零建；第 112 行已注明 `get_status` 返回单值 dict）。故以下仅记录**对 v6 仍成立的补充项**。

**补充 1（成立）：后台 watcher 路径无 HTTP 上下文，tid 取源说明。**
`_check_and_fire_task`（831 行）除被提交链路调用外，还会被 `_background_webhook_watcher`（685 行，822 行 `asyncio.create_task` 触发）在**无 HTTP Request** 的上下文中调用。此时 `tid` 无法从 header 取，只能从 `_TASK_META[task_id]['tid']` 回取（v6 §2.1-A 已把 `tid` 写入 meta，§2.2 用 `meta.get('tid','-')` 兜底——**已正确**，此处仅补明确注记：后台路径 traceId 来自 meta，非 header，设计上可接受）。

**补充 2（成立）：网关侧 header 大小写。**
§2.1-A 用 `request.headers.get("X-Trace-Id")`。FastAPI/Starlette 的 `request.headers` 对外键名大小写不敏感（内部归一化），故 `X-Trace-Id` 可取到入站头；但若将来改从原始 `scope["headers"]` 字节读取则需小写 `x-trace-id`。localTool 侧 §3.1 从 **JSON body 的 `body.headers`** 读（前端经 `/api/proxy` 把 headers 内联进 body），非入站 HTTP header，同样不受大小写限制。无需改代码，仅此注记。

**补充 3（成立，已并入 §3.2）：`diffAndPersistTasks` 死代码。**

## 七、验收标准

- 一次视频提交，网关日志必出现 `[submit]`（各路 ref 计数 + traceId）+ `[submit:parse]`（attachments 计数）+ 后续 `[poll]`（traceId/lovart_raw/effective/poll）。
- `[submit]` 与 `[poll]` 的 `traceId` 一致，并发提交可区分。
- 若 `reference_videos`/`reference_audios` 被静默丢弃，§2.1-B 修复后 `videos_raw`/`audios` 不再为 0。
- 若参考图结构不兼容，`attachments=0` 暴露，按 §2.3 最小 diff 修复。
- 修复 §3.2 后，前端多次 PATCH 进度不再抹掉 `request_data`/`response_data`；SQL 可稳定回看。
- 修复 §3.3 后，错误任务能正确写入 `error_msg`（或 `error_message` 列），不被静默丢弃。
- Lovart 卡住时，从 `lovart_raw` + `effective` + `[poll:confirm]` 直接可知：生成中 / 等确认（已自动确认未）/ 失败 / 超时，无需前端配合。
