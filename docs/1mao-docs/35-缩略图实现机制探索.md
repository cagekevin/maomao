# 35-缩略图实现机制探索（概览）

> 本文档**仅做概览性探索**，梳理缩略图从「生成 → 存储 → 访问 → 前端消费」的完整链路与关键代码位置，标注出值得深挖的点，供后续深入实现/优化时直接取用。核对时间：2026-08-07。
>
> 相关代码（localTool 后端 TS 为主，前端为打包产物）：
> - `localTool/src/utils/fileStore.ts`（缩略图路径/URL 计算的唯一收口）
> - `localTool/src/routes/files.ts`（`tryGenerateThumbnail` / `handleThumbnail`）
> - `localTool/src/index.ts`（路由挂载）
> - 前端 `src/bundle/App-BX6o9fW5_components/Vr.jsx`、`shared.js`（`useThumbnail` 开关、thumbnailUrl 消费）

---

## 0. 一句话结论

缩略图机制**原为"很弱"状态**：此前"生成"只是**把原图原样复制**到 `.thumbnails/thumb_<名>`（不真正压缩尺寸），缩略图与原图大小相同，**没有走图像缩放/裁剪**；真正的"按尺寸生成"接口 `/api/files/thumbnail` 虽支持 `maxDim`/`quality`，但也只是复制、未做实际压缩。**现已于 2026-08-07 落地修复**：引入 `jimp` 做真实缩放+压缩，`maxDim`/`quality` 真正生效，保留复制兜底（详见 §6.3/§6.5）。优化收益主要在**前端解码内存/CPU**（本服务为 localhost，带宽非瓶颈，见 §6.1）。

## 1. 缩略图的完整链路

```
[生成] 文件落盘时自动触发
   POST /api/files/upload (handleUploadFormData / saveRemoteUrl)
        └─ tryGenerateThumbnail(filePath, urlPath)     files.ts:119
              └─ ensureThumbnailTarget(filePath)       fileStore.ts:68
                    → 在 <文件所在目录>/.thumbnails/thumb_<basename> 复制一份原图
        └─ 返回体带 thumbnailUrl: http://127.0.0.1:18080/files/.../.thumbnails/thumb_xxx.png

[按需生成/访问]
   GET /api/files/thumbnail?url=...&maxDim=200&quality=80   files.ts:214 handleThumbnail
        └─ ensureThumbnailTarget(filePath, `${maxDim}x${quality}_`)   → 同样只是 copyFileSync
        └─ 返回 { thumbnailUrl }

[前端消费]
   任务列表/节点等通过 task.thumbnailUrl / resource 等字段引用缩略图地址
   useThumbnail 开关 (Vr.jsx / Ln.jsx / jn.jsx 等透传) 决定是否用缩略图渲染
```

## 2. 关键代码逐一说明

### 2.1 `fileStore.ts` — `ensureThumbnailTarget`（缩略图路径的唯一收口）

```ts
// fileStore.ts:68
export function ensureThumbnailTarget(filePath: string, suffix = '') {
  const thumbDir = path.join(path.dirname(filePath), '.thumbnails');
  ensureDir(thumbDir);
  const thumbPath = path.join(thumbDir, `thumb_${suffix}${path.basename(filePath)}`);
  const thumbUrl = `/files/${path.relative(getUploadDir(), thumbDir).replace(/\\/g, '/')}/${path.basename(thumbPath)}`;
  return { thumbDir, thumbPath, thumbUrl };
}
```

要点：
- 缩略图统一放在**原文件同目录的 `.thumbnails/`** 下，命名 `thumb_<suffix><原文件名>`。
- `suffix` 用于区分不同尺寸（如 `200x80_`），同名文件多尺寸互不覆盖。
- 这是唯一收口函数，`files.ts` 的 `tryGenerateThumbnail` 与 `handleThumbnail` 都复用它。
- **注意**：`.thumbnails` 目录在 `resources.ts` rescan 时会被显式跳过（`e.name !== '.thumbnails'`），避免缩略图被当作素材入库。

### 2.2 `files.ts` — `tryGenerateThumbnail`（落盘后自动生成）

```ts
// files.ts:119
async function tryGenerateThumbnail(filePath: string, _urlPath: string): Promise<string | null> {
  const ext = path.extname(filePath).toLowerCase();
  const imageExts = ['.png', '.jpg', '.jpeg', '.webp', '.gif', '.bmp', '.svg'];
  if (!imageExts.includes(ext)) return null;   // 只对图片生成
  const { thumbPath, thumbUrl } = ensureThumbnailTarget(filePath);
  try {
    if (!fs.existsSync(thumbPath)) fs.copyFileSync(filePath, thumbPath);  // ⚠️ 纯复制，不压缩
    return thumbUrl;
  } catch { return null; }
}
```

**关键观察（值得深挖）**：
- 只处理图片扩展名，视频/音频无缩略图（视频没有抽帧）。
- `copyFileSync` **原样复制** → 缩略图与原图同尺寸同大小，**并未真正缩小**，只是"多一份副本"。这是性能优化的核心待改点。
- 无 sharp 等图像处理库（可从 `package.json` dependencies 仅 `sql.js` 佐证），所以只能复制，不能缩放。

### 2.3 `files.ts` — `handleThumbnail`（按需尺寸接口）

```ts
// files.ts:214
export async function handleThumbnail(req, res, url) {
  const sourceUrl = url.searchParams.get('url');       // /files/subfolder/filename
  const maxDim = parseInt(url.searchParams.get('maxDim') || '200', 10);
  const quality = parseInt(url.searchParams.get('quality') || '80', 10);
  const relativePath = sourceUrl.replace(/^\/files\//, '');
  const filePath = path.join(getUploadDir(), relativePath);
  if (!fs.existsSync(filePath)) return sendError(res, 'File not found', 404);
  const { thumbPath, thumbUrl } = ensureThumbnailTarget(filePath, `${maxDim}x${quality}_`);
  if (!fs.existsSync(thumbPath)) fs.copyFileSync(filePath, thumbPath);   // ⚠️ 仍只是复制
  return json(res, { thumbnailUrl: `${BASE_URL}${thumbUrl}` });
}
```

**关键观察（值得深挖）**：
- 虽接受 `maxDim`/`quality`，但**只是把它拼进文件名后缀**，没有用它们做真实缩放/压缩（`quality` 参数实际未参与图像处理）。
- 意味着请求 `maxDim=200` 得到的仍是原图尺寸的副本，仅文件名带 `200x80_` 前缀——**功能形同虚设**，是个明显的"半成品"点。
- 路由挂在 `index.ts:234`（`/api/files/thumbnail`，GET）。

### 2.4 路由挂载 `index.ts`

```ts
// index.ts:234
if (pathname === '/api/files/thumbnail' && method === 'GET') {
  return await handleThumbnail(req, res, url);
}
```
其它文件路由见 `index.ts:490-494` 的启动打印。

## 3. 前端消费侧（打包产物）

- **`useThumbnail` 开关**：由 `Vr.jsx` 的 state（`Xr`）控制，经 props 传给 `Ln.jsx`（任务列表）、`jn.jsx`（任务卡片）等，决定渲染时是否优先用缩略图地址。
- **thumbnailUrl 字段**：任务对象 `thumbnailUrl`（来自后端 `tasks` 表的 `thumbnail_url` 列 / `shared.js` 归一化 `v.thumbnail_url || v.cover_url || v.thumbnail`），图片走 `upload`/`localize` 链路后带 `thumbnailUrl`。
- 资源/素材侧：`resources` 表无缩略图列，素材卡默认直接渲染原图 url（`transitResources` 的 `url`），**素材列表没走缩略图**——这也是"资源面板加载大量图"潜在性能点之一。

## 4. 值得深挖/优化的点（供后续 AI 聚焦）

| # | 点 | 现状 | 深挖方向 |
|---|---|---|---|
| 1 | **缩略图未真正压缩尺寸** | `copyFileSync` 原样复制，缩略图=原图 | 引入 sharp/jimp 做真实 resize + quality 压缩；`.thumbnails` 下生成小尺寸图 |
| 2 | **`handleThumbnail` 的 maxDim/quality 形同虚设** | 只进文件名后缀，未参与图像处理 | 接入真实缩放；`quality` 用于 JPEG/WebP 压缩 |
| 3 | **视频/音频无缩略图** | `tryGenerateThumbnail` 只认图片扩展名 | 视频抽帧生成封面（需 ffmpeg，仓库已有 ffmpeg 依赖，见 docs/19） |
| 4 | **素材列表不走缩略图** | `resources` 无缩略图字段，素材卡直接渲染原图 | 资源面板/导入弹窗大量图时考虑缩略图，减少加载体积 |
| 5 | **缩略图生成时机** | 上传时同步复制；失败仅返回 null 不重试 | 是否异步生成、失败重试、缺失时兜底 |
| 6 | **`.thumbnails` 与 rescan 的隔离** | 已跳过，但磁盘会累积 | 清理策略、孤儿缩略图回收 |

## 5. 一句话给后续探索者

缩略图链路已闭环（生成→存`.thumbnails`→`/api/files/thumbnail`按需取→前端`useThumbnail`开关），但**当前只是"原图多复制一份"，没有真实图像压缩**，`maxDim`/`quality` 参数未真正生效。若目标是降低资源/任务列表的加载体积，需引入图像处理库做真实 resize，并给素材（resources）也补缩略图路径。

> ⚠️ **选型修订（2026-08-07）**：原文档建议引入 **`sharp`**。经利弊评估（见 §6），**本项目最优解是引入 `jimp`（纯 JS 零原生依赖）**，而非 `sharp`——诊断正确，但 `sharp` 这剂药对 localhost 轻量服务偏重。详见 §6。

## 6. 技术选型评估与最优方案（2026-08-07 补充）

> 本节对"引入图像处理库做真缩放"这一方向做选型利弊评估，并给出**明确的最优解**。
> 适用范围：`tryGenerateThumbnail`（files.ts:119）与 `handleThumbnail`（files.ts:214）两处 `copyFileSync` 的替换，以及 §4 优化点 1/2。

### 6.1 先厘清一个前提：优化收益在哪

- 本服务所有文件与缩略图均从 `127.0.0.1:18080` 经 localTool 提供（uploads 在 `~/.maomao-localtool/uploads`），前端 `mi()` 走 `${Mn()}/api/files/thumbnail` 拉取，且前端已有 300s 内存缓存 + 并发去重（`pi=300000`、`di`/`fi` Map）。
- 因此**网络带宽不是瓶颈**（loopback 链路）。真缩放的收益主要在：
  1. **前端解码内存/CPU**：大量大图同时渲染时，缩略图能显著降低 `new Image()`/canvas 的解码内存与绘制开销；
  2. **磁盘占用**：`.thumbnails/` 不再与原图等大；
  3. **后续云端迁移友好**：若未来缩略图改走对象存储/CDN，小尺寸才有真实省带宽意义。
- 结论：优化**有价值但属"质量/体感"提升，非硬性能修复**。改造须控制风险、不引入回归（承接 docs/19 §六-1 的遗留优化项，且 docs/19 已明确"真缩放应走图像库，与 ffmpeg 无关"）。

### 6.2 候选方案利弊对比

| 方案 | 原理 | 利 | 弊 | 结论 |
|---|---|---|---|---|
| **A. sharp**（原文档建议） | libvips 原生二进制 | 性能最强（多线程/GPU），resize 质量最高，功能全（转格式/裁剪/旋转） | **依赖重**：`@img/sharp-*` 各平台预编译二进制，安装体积大，Node 版本/平台不匹配易装包失败；与项目"仅 sql.js 单依赖、零原生依赖"极简取向冲突；localhost 场景性能过剩 | **不采用**（对轻量服务偏重） |
| **B. jimp** ✅ | 纯 JS 像素处理 | **零原生依赖**，跨平台无装包风险；`resize`+`quality` 完全满足缩略图需求；符合项目轻量取向 | 性能弱于 sharp（纯 JS），但 localhost 生成 ≤200px 缩略图毫秒级足够；超大图/GIF 略慢 | **最优解（推荐）** |
| **C. 前端 canvas 缩略图** | 浏览器 canvas downscale 后回传 | 复用前端已有 canvas 管线；可顺带解决视频抽帧 | 需"下载原图→canvas 缩放→再上传"，多一次往返；**破坏 `ensureThumbnailTarget` 唯一收口架构**（单一职责）；触及打包产物、改动面大 | 不采用（架构相悖、改动大） |
| **D. 纯 Node 手写降采样** | 不引库 | 零依赖 | Node 无内置图像缩放，手写降采样质量差、代码量大、维护成本高 | **不可取** |

### 6.3 推荐最优方案（jimp 主 + 最小改动）

> ✅ **已实施（2026-08-07）**：按本方案落地完成，构建/运行验证通过，详见 §6.5 实施记录。

**方案 B：引入 `jimp`，替换两处 `copyFileSync` 为真实 resize，并保留复制兜底。**

核心要点（实施已按此路径落地）：
1. **依赖**：`localTool/package.json` dependencies 增加 `jimp`（纯 JS，`npm install` 无原生编译风险）。
2. **文件级改动**：
   - `localTool/src/utils/fileStore.ts`：新增/下沉一个"图像缩放"辅助（如 `resizeImage(src, dst, { maxDim, quality })`，内部用 jimp），`ensureThumbnailTarget` 保持不变（仍是路径收口）。
   - `localTool/src/routes/files.ts`：
     - `tryGenerateThumbnail`（:119）：把 `fs.copyFileSync` 改为调 resize 辅助，`maxDim` 用默认值（如 256），只对图片走缩放；**保留** copyFileSync 作 jimp 不可用/异常时的兜底（承接 docs/19 约束 3"兜底保留"）。
     - `handleThumbnail`（:214）：把 `maxDim`/`quality` 从"仅拼文件名后缀"改为**真正参与缩放/压缩**，让 `200x80_` 这类缓存文件名与实际产出一致。
   - `localTool/src/index.ts`：路由挂载不动（`/api/files/thumbnail` 已存在）。
3. **行为契约**：返回 JSON 仍为 `{ thumbnailUrl }`，前端无感知，**打包产物零改动**；`.thumbnails/` 仍被 `resources.ts` rescan 跳过，不需额外处理。
4. **验收标准**：
   - `maxDim=200&quality=80` 请求后，`thumb_200x80_*.png` 的实际像素最长边 ≤200，文件体积显著小于原图；
   - 默认上传自动生成的 `thumb_*.png` 也真缩放过；
   - jimp 异常时回退到原 copyFileSync 行为，功能不回归；
   - 前端 `useThumbnail` 开关、任务列表/素材渲染无可见变化。

### 6.4 不建议本批做（保持为后续独立深挖，同 §4）

- 视频/音频抽帧缩略图（§4-3）：需 ffmpeg/前端 canvas，超出"引入图像库"范围，且 docs/19 已定前端视频管线纯前端。
- 素材（resources）列表接入缩略图（§4-4）：涉及前端打包产物与 `resources` 表结构，改动面大，应单独排期。
- 生成时机异步化/失败重试（§4-5）、孤儿缩略图清理（§4-6）：与选型无关，可单独评估。

> **一句话给后续实现者**：诊断维持 §0-§5 结论；**落地时用 `jimp` 而非 `sharp`**，在 `tryGenerateThumbnail` 与 `handleThumbnail` 两处把 `copyFileSync` 换成真实 resize + 兜底，`maxDim`/`quality` 真正生效，前端零改动。
