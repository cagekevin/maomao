> 目的：把为「快速排查断点」而打下的 4 项调试地基完整记录下来——含 Chrome 扩展调试模式（请求日志 + 端点探针）、proxy 结构化日志、`.env` 凭据启动警告、stub 端点统一标记。
> 范围：逐条回到 `dist/`（`background.js` / `index.html` / `debug-panel.js`）与 `localTool/src`（`index.ts` / `routes/system.ts` / `routes/platform.ts`）源码实证。
> 状态图例：`[已落地]` = 已实现并经源码坐实；`[需配合]` = 功能已加，但生效依赖外部环境（如本地引擎已启动）。
> 本文只讲「加了什么调试能力、怎么用、对应哪些断点」，不含修复方案（修复见 `02-断点三域梳理.md`）。

## 一、Chrome 扩展调试模式（请求日志 + 端点探针）

> 形态：侧边栏（`side_panel`）左下角浮层，独立 IIFE 脚本，不侵入 React 业务代码。
> 状态：`chrome.storage.local` 存 `debugMode`（`background.js:145`），重载扩展后保留上次开关。

### 1.1 唤出与开关 `[已落地]`

- **快捷键 `Ctrl+Shift+D`**：在侧边栏页面内按，浮层显隐切换（`debug-panel.js` 内 `keydown` 监听）。
- 面板右上 `✕` 收起、`清空` 清日志、`▶ 探针` 跑全量探测。
- 浮层固定底部 `position:fixed; bottom:0`，`z-index:2147483646`，不挡画布主区。

### 1.2 请求日志 Tab（fetch + XHR 拦截） `[已落地·需配合]`

- 拦截 `window.fetch` 与 `XMLHttpRequest.prototype.open/send`，记录 `方法 / URL / 状态码 / 耗时ms`。
- 仅记录命中白名单的 URL：`/(localhost|127\.0\.0\.1|18080|1mao|kkidc|lovart|0\.1mao)/i`（`debug-panel.js` 内 `shouldLog` 正则）。
- 每条日志按状态码着色：`ok`(绿) / `warn`(橙) / `fail`(红)；面板顶部徽标显示总数与失败数。
- 用途：直接看到「画布发起的请求到底有没有到 localTool `:18080`、返回 2xx 还是 4xx/5xx、耗时多少」——对应排查 B 域 proxy 与三域连通性。

### 1.3 端点探针 Tab（16 端点一键探测） `[已落地·需配合]`

- 点 `▶ 探针` → 面板发 `chrome.runtime.sendMessage({action:'debug.runProbe'})`（`debug-panel.js:runProbe`）→ `background.js:runProbe` 异步逐个 `fetch` 16 个端点。
- 每个端点实时回 `probe.progress`，跑完回 `probe.done`（含 4 类汇总），侧边栏渲染（`background.js:216/223`）。
- **探针清单**（对应 `02-断点三域梳理.md`）：

| key | 域 | 端点 | 对应断点 |
|---|---|---|---|
| status | B | `GET /api/status` | 健康入口 |
| sync-default | B | `GET /api/sync/default` | A2 / L4（404 已知缺口 → warn） |
| files-upload | B | `POST /api/files/upload` | S1 |
| tasks-list | B | `GET /api/tasks`（注：早期文档写 `/api/tasks/list`，实际路由为 `/api/tasks`，见 `index.ts:163`） | S3 |
| kv-get / kv-set / kv-delete | B | KV 三件套 | L1（kv-delete 404 → warn） |
| upload-app-asset | B | `POST /api/upload/app-asset` | A4 / L5（404 → warn） |
| workflow-by-proj | B | `GET /api/workflow-apps/by-project` | A3（stub 标记 → stub） |
| jianying-send | B | `POST /api/jianying/send` | 剪映发送（stub 标记 → stub） |
| plugin-manifest | B | `GET /plugin/manifest.json` | L3 |
| gw-status / gw-images-draw / gw-videos-submit / gw-videos-poll / gw-chat | C | 经 `/api/proxy` 透传的网关端点（共 5 个） | G1/G2/G3、聊天、伪覆盖诊断 |

- **verdict 语义（4 色）**：
  - `✅ ok`（绿）：2xx 且非 stub —— 端点真的通。
  - `📌 stub`（蓝）：响应含 `_meta.stub` —— 端点存在但**功能未实现**（已规划，非故障）。
  - `⚠️ warn`（橙）：已知缺口型 404（如 `sync-default`/`kv-delete`/`upload-app-asset`）或网关提交非 200。
  - `❌ fail`（红）：超时 / 网络错误 / 5xx / 其他 4xx —— 真故障。
- **判定逻辑**（`background.js:196-212`）：`TIMEOUT/NET_ERR` 或 `>=500` → fail；`>=400` 时已知缺口键 → warn 否则 fail；2xx 且 `body._meta.stub` → stub。
- 用途：把 `02-断点三域梳理.md` 的静态断点表，变成「一键验证当前环境到底哪些端点活着」的活探针。

### 1.4 修复记录：内联脚本违反 MV3 CSP `[已落地]`

- 现象：调试脚本起初写在 `index.html` 的 `<body>` 内联 `<script>`，Chrome 报 `Executing inline script violates the following Content Security Policy directive 'script-src 'self' 'wasm-unsafe-eval''`（同一段脚本被两种 CSP 各拦一次，hash 相同可证）。
- 修复：抽成独立文件 `dist/debug-panel.js`，`index.html:19` 改为 `<script src="./debug-panel.js"></script>`。外部同源脚本在 `script-src 'self'` 下合法，两种 CSP 均放行。
- 加载顺序：该经典脚本位于 `<body>` 末尾，先于 `<head>` 里被 defer 的 React 模块执行，故 fetch/XHR 拦截器在 App 发请求前已挂好。
- 相关无害警告：`manifest.json` 的 `changelog` / `localToolChanged` 报 "Unrecognized manifest key" —— 二者被 App 真实消费（`App-BX6o9fW5.js` 内 `p.changelog`、`localToolChanged:!!p?.localToolChanged`），属有用字段，警告无害、可忽略，勿删。

## 二、proxy 结构化日志 `[已落地]`

> 落点：`localTool/src/routes/system.ts` 的 `handleProxyFormData` 与 `handleProxyJson` 两条转发路径。

### 2.1 成功路径日志 `system.ts:81` / `:145` `[已落地]`

- 每条成功转发打印一行：
  ```
  [proxy] YYYY-MM-DD HH:mm:ss | {METHOD} {targetUrl} | {status} | {elapsed}ms
  ```
  - `:81` 对应 FormData 路径（`handleProxyFormData`），`targetUrl` 取自 `X-Proxy-Url` 头。
  - `:145` 对应 JSON 路径（`handleProxyJson`），`body.url` + `body.method`。
- 用途：localTool 控制台直接看到「哪次请求、打到哪个真实后端、回了什么状态码、花了多久」，对应 B 域 P0（超时/非流式/无翻译）的现场取证。

### 2.2 失败路径日志 `system.ts:97` / `:160` `[已落地]`

- 异常时 `console.error` 并标记 `TIMEOUT`（AbortError）或 `ERR`，附 `err.message`：
  ```
  [proxy] ... | {METHOD} {targetUrl} | TIMEOUT | {elapsed}ms | {message}
  ```
- 用途：15s 超时被掐（`system.ts` 原 `setTimeout(...15000)`）时控制台即刻可见，定位「请求被谁掐断」。

> 所有日志前缀 `[proxy]` 统一，便于在 localTool 终端用 `grep '[proxy]'` 单独捞转发记录。

## 三、`.env` 凭据启动警告 `[已落地]`

> 落点：`localTool/src/index.ts:255-289`（在 `main()` 的 `await getDb()` 之后执行）。

### 3.1 行为 `[已落地]`

- 按 3 种路径尝试读 `apimart-gateway/.env`（`index.ts:256-260`：localTool/dist→根、localTool→根、cwd→根）。
- 正则取出 `LOVART_ACCESS_KEY` / `LOVART_SECRET_KEY`（`index.ts:265-266`），去引号后检测是否含 `xxxx` 或 `REPLACE`（`index.ts:270`）。
- 命中占位符 → 打印醒目 `⚠️` 块：
  ```
  ⚠️  LOVART 凭据为占位符！生图/对话将不会真正生效。
  ⚠️  请在 apimart-gateway/.env 中填入真实 AK/SK。
  ```
- 未找到 `.env` 文件 → 打印 `ℹ️` 提示（可能网关未部署）（`index.ts:286-289`）。

### 3.2 对应痛点 `[已落地]`

- 直接解决 `02-断点三域梳理.md`「七、6」的硬前置：`.env` 是 `ak_xxxx_REPLACE_ME` / `sk_xxxx_REPLACE_ME` 占位符时，`OPEN_RELAY=true` 下网关调 Lovart 必然失败，但画布侧**静默无提示**。此警告把「生图为什么没反应」在启动即暴露。

## 四、stub 端点统一标记 `[已落地]`

> 语义：端点**路由存在、返回 200**，但功能尚未实现。响应体附 `_meta: { stub: true, message }`，供探针精准标记为 `📌 stub`（区别于「实现了但返回空数据」与「404 未实现」）。

### 4.1 已标记端点 `[已落地]`

| 端点 | 文件:行 | message |
|---|---|---|
| `POST /api/jianying/send`（批量形态） | `system.ts:187` | 剪映发送功能尚未实现，当前仅记录请求（后续补） |
| `POST /api/jianying/send`（单文件形态） | `system.ts:203` | 同上 |

### 4.2 探针如何消费 `[已落地]`

- 探针判定（`background.js:206-207`）：2xx 且 `body._meta.stub` 为真 → `verdict='stub'`，面板渲染为蓝色 `📌`。
- 用途：把「剪映发送」「工作流应用市场」这类**已规划未实现**的端点，与「真故障 404」明确分开，避免排障时被误判为「连不通」。

## 五、使用流程（排障 SOP）

1. **启动本地引擎**（localTool `:18080` + 网关 `:9004`，见启动脚本 `run_local.sh`/`启动网关.command`）与画布（方式一/方式二）。
2. 打开 Chrome `chrome://extensions` → 本扩展「重新加载」（改过 `manifest.json`/`background.js`/`debug-panel.js`/`index.html` 后必做）。
3. 打开侧边栏，按 `Ctrl+Shift+D` 唤出调试浮层。
4. **先看「端点探针」点 `▶ 探针`**：
   - `✅ ok` 多 = 基础连通正常；
   - `📌 stub` = 已规划未实现（剪映发送 / 工作流市场），非故障；
   - `⚠️ warn` = 已知缺口（sync-default / kv-delete / upload-app-asset，对应 A2/L1/A4/L5）；
   - `❌ fail` = 当前真故障，逐条对照 `02-断点三域梳理.md` 总表。
5. **再切「请求日志」复现操作**：看画布发起的具体请求命中白名单没、状态码与耗时，定位卡在浏览器侧还是 localTool/proxy 侧。
6. **看 localTool 终端**：`grep '[proxy]'` 捞转发明细，确认 proxy 超时/非流式/无翻译（B 域 P0）现场。
7. **看启动日志**：若生图无反应，先确认有无 `⚠️ LOVART 凭据为占位符` 警告（第三节）。
