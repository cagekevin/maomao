## 0. 为什么要做这份海关审计

前端是**混淆压缩产物（黑盒）**，后端（`apimart-gateway` / `localTool`）是我们**自研源码（白盒）**。两者之间没有任何 schema / OpenAPI / 类型契约文件兜底，全部靠"字段名巧合 + 网关盲转 + 行号硬编码消费"对齐。

**核心风险不是安全，而是认知错位**：后端改一个字段名、前端混淆代码里那行 `output.js:49040` 不会报错，只是静默拿不到值；等发现时已是线上事故。

> **关于文中行号（如 `output.js:49040`）的读法**：`output.js` 是混淆打包工具（如 esbuild/Rollup）在 `dist/assets/App-BX6o9fW5.js` 单文件内对某个内部模块的命名，**并非独立文件**。文档引用的行号是「该单文件内的行偏移」。⚠️ **这些行号随每次打包（版本号、代码变更）漂移**，本文档基于 `App-BX6o9fW5.js`（v1.4.2 产物）快照，仅作当下定位；后续版本须以字段名/上下文重新 grep，不可直接信赖行号。

本审计把所有**字段**当作「报关单」逐项核验：前端实际发出/消费的字段 vs 后端实际接收/返回的字段，逐一对账，标注 ✅ 对得上 / ⚠️ 靠翻译 / ❌ 错位。

> **关于模型名**：前端模型名（如 `seedance_2_fast`，来自 `discountVideoModel` 硬编码文本）与后端 Lovart 接受的模型名是两套，中间由 `resolve_prefer_models` 翻译。**此翻译属实现细节、不稳定也不致命（模型名错了至多生成用错模型），因此本文不展开映射表，仅标注"后端有翻译层"。**

## 1. 配置类报关单：`apiConfigs` 对象

### 1.1 前端配置对象真实字段（`App-BX6o9fW5.js`）

```js
// 新建配置时的对象字面量
{ id: Date.now().toString(), name:"", url:"", key:"", showKey:false, readonly:false }
```

| 字段 | 类型 | 前端语义 | 后端是否认领 |
|------|------|---------|------------|
| `id` | string | 配置唯一 ID，存于 `localStorage["apiConfigId_<类型>"]` | 网关不认；localTool 不存配置 |
| `name` | string | 下拉展示名 | 不认 |
| `url` | string | **配置基址**（注意：是 `url`，不是 `apiUrl`） | 见 1.2 错位 |
| `key` | string | **API Key**（注意：是 `key`，不是 `apiKey`） | 见 1.2 错位 |
| `showKey` | bool | 面板是否明文显示 key | 不认 |
| `readonly` | bool | `true`=系统内置、`false`=用户自建（见文档 15 第 2 节合并排序） | 不认（仅前端排序用） |

### 1.2 ⚠️ 关键错位：配置字段 `url`/`key` ↔ 节点消费字段 `apiUrl`/`apiKey`

- 前端配置对象存的是 **`url` / `key`**（见 1.1）。
- 但节点**调用时**消费的是 **`e3.apiUrl` / `e3.apiKey`**（见混淆产物：`m3=${(e3.apiUrl||o2)...}`，其中 `e3` 为节点运行时对象、`o2` 为兜底基址）。
- 两者之间的映射在混淆产物中**未直接 grep 到显式赋值**（如 `apiUrl: cfg.url`）。据静态分析，该映射**极可能发生在两个地方之一**：
  1. **打包前的未混淆源码**（本仓库 `dist/` 只提供混淆产物，未提供前端源码，故无法在此审计中直接定位）；
  2. 节点初始化 / `Ti()` 合并逻辑里，把「配置对象」的 `url/key` 规整为「节点运行态」的 `apiUrl/apiKey`（混淆后函数名不可读，无法 100% 确认）。
- **为什么这是高风险**：配置层字段名（`url/key`）与节点层字段名（`apiUrl/apiKey`）是两套命名，中间唯一的转换点"说不清"在哪。若将来任一方改了命名（例如节点端误写成 `apiURL`），不会编译报错，只会在运行时静默拿不到 key/url，导致请求打到兜底地址或直接 401。
- **判定：⚠️ 两级命名（配置层 `url/key` ↔ 节点层 `apiUrl/apiKey`），映射点未明文，属「说不清」高风险项。**
- **如何验证/固化（落地动作）**：
  - 在**前端未混淆源码**中搜索 `apiUrl\s*[:=]|apiKey\s*[:=]`，定位赋值语句，确认其来源是 `cfg.url` / `cfg.key`；
  - 在该赋值处加一行注释：`// 配置字段 url/key → 节点字段 apiUrl/apiKey（海关映射点）`；
  - 若映射确实发生在 `Ti()` 合并，则在合并函数内补同样注释。完成后此 ⚠️ 可降级为 ✅。

### 1.3 各节点「当前选中配置 ID」的 localStorage 键

```
apiConfigId_video / apiConfigId_sd / apiConfigId_image /
apiConfigId_text / apiConfigId_audio / apiConfigId_discountVideo
```

后端**完全不读这些键**——纯前端自管。网关只认 `Authorization` header（见第 3 节）。

## 2. 网关请求报关单：`/v1/gateway/generate`

### 2.1 前端实际发出的字段（特惠节点路径）

特惠节点请求构造（`App-BX6o9fW5.js`，已核对）：
```
m3 = `${(u2||"").replace(/[`\s]/g,"").replace(/\/$/,"")}/v1/gateway/task/${g3}`
Authorization: Bearer ${d2}
```
其中 `u2 = discountVideoApiUrl`（固定字段，非 apiConfigs）、`d2 = discountVideoApiKey`。

**⚠️ 重要发现**：特惠节点的 `discountVideoApiUrl` / `discountVideoApiKey` 是**独立于 `apiConfigs` 的私货字段**（文档 15 已详述），直接拼网关地址打过去。所谓"私货"指：普通节点通过 1.1 节的 `apiConfigs` 配置对象（字段 `url`/`key`）+ 1.3 节的 `localStorage` 选中键来管理地址与密钥；而特惠节点**不走这套配置体系**，而是把地址/密钥存在节点自身专属字段 `discountVideoApiUrl`/`discountVideoApiKey` 里，等于两套平行的凭据来源。后端网关 `main.py` 的 `/v1/gateway/*` 是**统一前缀盲转**，并不知道"这是特惠来的"——它只认 `Authorization` token（见第 3 节），因此这两套凭据在网关层被归一为同一种"Bearer token 直打"。这也意味着特惠节点与第三方节点在网关侧**无语义区分**，是 3 节所述计费风险的根因。

### 2.2 后端 `_submit_generation` 实际读取的字段（`main.py:712-774`）

后端在 `_submit_generation` 入口做了**显式字段翻译（即你说的海关）**：

```python
# 字段兼容映射：画布视频节点字段名 → 网关标准字段名
if "metadata" in body and isinstance(body["metadata"], dict):
    meta = body.pop("metadata")
    for key in ("reference_images","reference_videos","reference_audios",
                "ratio","duration","watermark","generate_audio"):
        if key in meta and key not in body:
            body[key] = meta[key]
if "ratio" in body and "aspect_ratio" not in body:
    body["aspect_ratio"] = body.pop("ratio")          # ratio → aspect_ratio
if "seconds" in body and "duration" not in body:
    body["duration"] = body.pop("seconds")            # seconds → duration
if "input_reference" in body and "reference_images" not in body:
    body["reference_images"] = body.pop("input_reference")
if "input_video" in body and "videos" not in body:

```

随后 `_do_submit`（`main.py:759+`）读取：

| 后端读取字段 | 来源链路（前端→后端） | 判定 |
|-------------|---------------------|------|
| `prompt` / `input` | 前端 prompt 字段 → 直接 | ✅ |
| `model` | 前端 model → `resolve_prefer_models` 翻译 | ⚠️ 翻译层（模型名，见 0 节略） |

> **`metadata` 提升字段的消费现状（避免误读"提升=已用"）**：

| `ratio` → `aspect_ratio` | 前端 `ratio` 字段 | ⚠️ 别名翻译 |
| `seconds` → `duration` | 前端 `seconds` 字段 | ⚠️ 别名翻译 |
| `input_reference` → `reference_images` | 前端 `input_reference` | ⚠️ 别名翻译 |

| `videos` / `reference_videos` | 视频类多候选名，`_extract_raw_urls(body.get("videos") or body.get("reference_videos"))`（`_do_submit:773`） | ⚠️ **多别名合并**（仅视频） |
| `audios` / `reference_audios` | 音频类多候选名，`_extract_raw_urls(body.get("audios") or body.get("reference_audios"))`（`_do_submit:774`） | ⚠️ **多别名合并**（仅音频） |

> - 图片：`image_urls` / `images` / `attachments` / `reference_images`（最后一项还可经 `metadata` 提升或 `input_reference` 别名进入）
> - 视频：`videos` / `reference_videos`（后者可经 `metadata` 提升或 `input_video` 别名进入）
> - 音频：`audios` / `reference_audios`（后者可经 `metadata` 提升进入）

> **字段翻译执行顺序（避免误读）**：`_submit_generation` 先执行「`metadata` 提升」（712-726 行），再执行「顶层别名映射」（727-734 行）。因此 `ratio` 等字段若已在 `metadata` 内被提升到顶层，则其后的 `ratio → aspect_ratio` 仍能正常命中；二者**不冲突**，但顺序敏感——若将来有人把别名映射移到 `metadata` 提升之前，需要先提升再别名的字段会漏翻译。
| `webhook` | 前端可选 | ✅ |
| `wait`（query `?wait=1`） | localTool FormData 路径拼 query | ✅ |
| `mode`（fast/unlimited） | 前端可选 | ✅ |

### 2.3 判定

**`/v1/gateway/generate` 是前后端错位最严重的端点**：前端用 `metadata` 包裹 + `ratio`/`seconds`/`input_reference` 等旧字段名，后端被迫写一整段"翻译代码"把它们归一化。这份翻译逻辑**就是事实上的海关**，但它：
1. 只存在后端代码注释里，前端黑盒无从知晓；
2. 若前端新增一个字段名变体而没同步后端翻译，会**静默丢失**。历史上 `reference_videos` / `reference_audios` 就曾因 `_do_submit` 只读了 `videos`/`audios` 而被**静默丢弃**——该问题已在 `main.py:765-774` 通过 `videos or reference_videos`、`audios or reference_audios` 的短路合并**修复（当前代码已为修复后状态，非遗留缺陷）**。这说明「别名翻译缺失」不是理论风险，而是已经发生过的线上事故类型，值得用 7.3 的映射表固化以防回归。

### 5.4 localTool 与前端错位点

> **已核实（代码为准，修正此前误判）**：前端在 `httpClient` 混淆产物内 `fetch` `${baseURL}/public/platform/builtin`（≈`function jr`/`fetchBuiltin`）与 `/public/platform/models`（≈`function Xi`），baseURL 经 `VITE_API_BASE_URL` 替换为 `127.0.0.1:PORT`，即打到 localTool。

> - 此前"前端未调用 / localTool 无此路由"的断言系 grep 误判（混淆产物变量名与 `App-*.js` 文件命中失败），**以本段代码核实结论为准**。

| 端点 | 前端期望 | localTool 实际 | 判定 |

## 7. 建议：建立「软海关」的最小集（呼应文档 15 的奥卡姆思路）

目标是**消除前后端认知模糊**，不引入重框架。按性价比排序：

### 7.1 必做：写一份「前后端契约清单」（本审计即初稿）
把第 1–5 节的字段对账表固化成仓库常驻文档（`docs/16`），每次前后端改动时同步。成本≈0，收益=消除"说不清"。

### 7.2 必做：把 `url/key ↔ apiUrl/apiKey` 映射点明文化
前端配置对象用 `url`/`key`，节点消费用 `apiUrl`/`apiKey`，中间映射应在源码（打包前）有**一行注释或常量**标明。否则混淆后无人能追溯。

**现状**：因前端源码不在本仓库，映射点无法在代码中直接标记。已在 `contract.py` 文件头部注释中固化此信息（含验证步骤），作为给前端源码持有者的"待办标记"。

### 7.3 建议：网关层把"翻译逻辑"外提为显式映射表 ✅ 已落地
当前 `_submit_generation` 的字段翻译是**散落在 if 里的硬编码**（720-734 行）。建议抽成一份可读的 `FIELD_ALIASES` 映射表（前端旧字段名 → 网关标准字段名），让"海关规则"人能一眼审，而不是埋在代码里。

**✅ 已落地为 `apimart-gateway/contract.py`**（见下文雏形对照实际代码）。`main.py` 已改为调用 `normalize_body(body)` 替代原有散落 if。

**具体雏形（对照 2.2 节真实代码）**：

```python
# 前端字段名（旧/别名） → 网关标准字段名
FIELD_ALIASES = {
    "ratio":           "aspect_ratio",   # 仅当 aspect_ratio 不存在时生效
    "seconds":         "duration",       # 仅当 duration 不存在时生效
    "input_reference": "reference_images",
    "input_video":     "videos",
}
# metadata 子对象提升字段（仅当顶层不存在时生效）
METADATA_LIFT_KEYS = (
    "reference_images", "reference_videos", "reference_audios",
    "ratio", "duration", "watermark", "generate_audio",
)
# 多候选合并（or 短路，按图片/视频/音频分组）
URL_MERGE_GROUPS = {
    "image": ["image_urls", "images", "attachments", "reference_images"],
    "video": ["videos", "reference_videos"],
    "audio": ["audios", "reference_audios"],
}
```

> 抽表后，`_submit_generation` 改为「先 `METADATA_LIFT_KEYS` 提升、再 `FIELD_ALIASES` 别名、最后 `URL_MERGE_GROUPS` 合并」三段式，顺序与 2.2 节注明的执行顺序一致。新增字段名变体时，只需在对应表里加一行，无需改逻辑，也便于在 code review 中一眼发现「前端新增了候选名但没登记」。

### 7.4 可选：网关加"报关单回显"日志 ✅ 已落地
`/v1/gateway/generate` 已打 `[submit]` 日志（744 行），建议**额外记录"本次命中了哪些别名翻译"**，使前后端字段错位时能在日志里看见"前端发了 X，网关翻译成 Y"。

**✅ 已落地**：`normalize_body` 返回命中列表后，`_submit_generation` 打 `[submit:alias] hits=[...]` 日志（格式如 `["metadata.ratio→ratio","ratio→aspect_ratio"]`）。localTool 同步补了 `[taskToRow:dropped]` 日志（`tasks.ts`），记录被白名单过滤的字段名。

### 7.5 不建：全局强 schema 校验
当前前端是混淆产物，强 schema 难落地、且会拖慢迭代。**软海关（文档 + 映射表 + 日志）足够**，待前端源码化后再考虑强校验。
