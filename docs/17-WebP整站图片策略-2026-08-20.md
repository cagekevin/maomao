## 0. 为什么是 WebP（用户诉求，最高优先）

> 用户原话：「我不喜欢用『所有图』。图生图如果用『所有图』，缩得太狠，发过去图就糊了，所以我不要用『所有图』。WebP 反而是我能接受的方案。」
> 「所有图」= 现有/官方的「缩略图缩放尺寸」（最长边 ≤256px，`resizeImage` 的 `maxDim`）。缩得太狠 → 图生图发送时糊。

**核心认知**：
- ❌ **不要**「缩略图缩放尺寸」——256px 缩略图会糊，图生图/发送不能用。
- ✅ **要**「同分辨率 WebP 重编码」——**不缩小尺寸**，只用 `quality` 压缩 + 换 `.webp` 扩展名。清晰度保留、体积小 30-50%。
- 一旦引入，**整站统一用**（不是只图生图）——渲染、发送、存储、显示全部走 WebP 策略。
- **转码范围：JPG + PNG 全部转 WebP**（用户已确认）。

## 1. 目标与原则

### 1.1 目标
1. 整站图片统一用 WebP，体积小、加载快。
2. **图生图/发送参考图不糊**：发送用「质量 80 的 WebP」（**不缩放**，同分辨率）。
3. 前端改动**收口在唯一出口**（`imageUrl.js`），一处改整站生效，不散落各处。
4. **架构简单 + 可回退**：不做复杂机制；哪天不想用 WebP，前端一个开关即可改回原图。

### 1.2 原则（决策铁律）
| 原则 | 说明 |
|---|---|
| **不缩放尺寸，只重编码** | WebP 是"同分辨率压缩"，不是"缩略图"。任何场景都**不能**为了省体积把图缩到 256px。 |
| **发送优先高清** | 图生图/发送参考图用**质量 80 的 WebP**（不缩放），**绝不**用 256 缩略图。 |
| **唯一出口** | 所有图片 URL 出口（渲染/发送/存储）都经 `imageUrl.js`。WebP 转换逻辑放这里，一处改整站。 |
| **原图永存，URL 层转换** | 后端**只存一份原图**（不删、不生成双份）。WebP 由后端**按需动态生成**（`/api/files/thumbnail?format=webp`），前端 `imageUrl.js` 统一请求。 |
| **可回退** | 原图始终在磁盘，前端 `imageUrl.js` 一个开关把 URL 改回原图即整体回退。**不删除任何原图 = 永不"改不回来"。** |
| **架构简单优先** | 不为"处理链二次编辑"引入原图/中间态标记机制。原图永存，任何二次处理都从原图重新转，天然避免"多次转码累积糊"。 |
| **渐进接入** | 分步实施，每步测试；核心上传/发送链路谨慎，避免回归。 |

### 1.3 用户拍板的参数（定稿）
- **发送参考图 quality：80**（清晰够用、省体积；2K/1K 图转 WebP 损失可接受）。
- **转码范围：JPG + PNG 全部转 WebP**。
- **成品图（生成/粘贴/素材）：直接用 WebP，不纠结保留原图**。
- **架构：简单优先**——后端保原图，前端 URL 层转换，可回退。

## 2. 什么时候转 WebP（接入时机 = 用到才转，纯动态 + 缓存）

> **决策（用户拍板）**：选「纯动态 + 缓存」，不选「上传即转存两份」。理由：逻辑更简单、磁盘不翻倍、可回退；代价仅是首次显示 100 张大图有渐进延迟（可接受，之后全走缓存）。

**转 WebP 的唯一时机 = 用户**第一次显示或发送**某张图的那一下**，由后端 `/api/files/thumbnail?format=webp` 动态生成并缓存。**上传时不做任何转码**（原图照存一份）。

| 接入时机 | 做什么 | 为什么 |
|---|---|---|
| **上传落盘时**（`/api/files/upload`） | **不转**。只存一份原图。 | 磁盘不翻倍、上传不卡；符合"简单 + 可回退"。 |
| **第一次显示**（前端 `normalizeImageUrl`） | 请求 `/api/files/thumbnail?format=webp`，后端**此刻**转 WebP 并缓存 | 显示瘦身、加载快 |
| **之后每次显示/发送** | 直接读缓存（文件名按 maxDim/quality/format 区分） | 缓存命中 = 0ms，不重复转 |
| **发送参考图**（前端 `normalizeImageUrlForSend`） | 用「同分辨率 WebP，quality 80」 | 图糊根因修复点 |
| **压缩/导出**（`imageCompress.js`） | 默认 `format` 改 `image/webp` | 单图压缩统一 WebP |

### 2.1 动态生成的时间线（示例：粘贴 2K 图 cat.jpg）
```
1. 上传      → 后端存原图 cat.jpg（只此一份，不转）
2. 第一次显示 → 前端请求 /api/files/thumbnail?url=cat.jpg&format=webp&maxDim=2K&quality=80
             → 后端此刻用 Jimp 转成 .webp，存 .thumbnails/ 缓存，返回 webp URL
3. 再显示/发送 → 同一 webp URL → 缓存命中，直接返回，不再转
```

### 2.2 动态生成有多快（性能）
| 场景 | 耗时 |
|---|---|
| 单张首次转 WebP（1K） | 约 50-150ms |
| 单张首次转 WebP（2K） | 约 150-400ms |
| **缓存命中**（平时操作/二次打开） | **0ms**（等同读原图文件） |
| **首次打开 100 张大图画布** | 浏览器并发约 6 个连接，排队转，约几秒~十几秒，**图逐张渐进出现** |

**结论**：日常操作（缓存命中）够快；仅首次全量加载 100 张大图有渐进延迟，可接受。若以后嫌慢，因原图永存，随时可升级为"上传即转一份 webp"（存两份），不锁死。

## 3. 现状（已具备的基础）

### 3.1 后端已具备的能力（localTool）
`localTool/src/utils/fileStore.ts` + `routes/files.ts` 已有：
- `resizeImage(src, dst, { maxDim, quality })`：用 **Jimp**（`^0.22.12`，纯 JS 无原生依赖）缩放+压缩。`quality()` 对 JPEG/PNG/WebP 生效。

- `/api/files/thumbnail?url=&maxDim=&quality=`：**动态按需**生成任意尺寸缩略图（`handleThumbnail`），maxDim/quality 真正参与缩放压缩。

> **关键洞察**：`resizeImage` 的 `scale = Math.min(1, maxDim/长边)`。只要 `maxDim ≥ 原图长边`，`scale=1` **不缩放**，只保留 `quality` 压缩；把输出 `dst` 扩展名改成 `.webp`，即得「同分辨率 WebP」。**后端转 WebP 零新增依赖。**

- `useNodeGeneration.js`：生成结果落盘 + 写 `imageUrl/thumbnailUrl`。
- `useConnectedInputs.js`：图生图上游取参考图。

## 4. 方案设计（最简 + 可回退）

> **一句话架构**：后端**只存一份原图**，永不删除；前端 `imageUrl.js` 在**渲染/发送时按需把原图 URL 转成 WebP**（请求后端动态生成）。要回退 = 前端一个开关，原图一直在。

### 4.1 后端改造（localTool，极小改动）

**A. `resizeImage` 支持「仅转码不缩放」+ WebP 输出**
```ts
// 新增选项 format：'jpeg' | 'webp'（缺省 'jpeg'，保持现有缩略图行为不变）
resizeImage(src, dst, { maxDim, quality, format?: 'jpeg' | 'webp' })
```
- `format='webp'`：`maxDim` 传原图长边即 `scale=1` 不缩放，`dst` 后缀强制 `.webp`，`quality` 生效。
- 复用 Jimp，无新依赖。

**B. `/api/files/thumbnail`：加 `format=webp` 参数（唯一后端新增点）**
- 现有接口默认仍是 JPEG 缩略图（**不改现有行为**）。
- 新增：`?format=webp` → 输出 `.webp`（`maxDim` 可传原图长边 = 不缩放，即"同分辨率 WebP"）。
- 缓存沿用 `ensureThumbnailTarget(filePath, "${maxDim}x${quality}_")`，文件名后缀带 `.webp` 区分，同图转一次缓存复用。
- **`/api/files/upload` 不改**：仍只存一份原图、仍返回 `thumbnailUrl`（256px JPEG 缩略图仅供列表小图用，不参与发送）。

> 为什么后端只加 `thumbnail?format=webp`、不改 upload：
> - 原图**始终只有一份**，磁盘不翻倍。
> - 前端任何显示/发送尺寸都能按需生成 WebP，不预先猜尺寸。
> - 彻底回退：前端开关关掉，后端原图 URL 原样返回，WebP 能力闲置但无害。

### 4.2 前端改造（imageUrl.js 唯一出口 + 回退开关）

**A. 新增回退开关**
```js
// config.js 或 imageUrl.js 顶部：整站 WebP 开关，false = 整体回退原图
export const USE_WEBP = true
```

**B. 新增 `toWebpUrl(url, width?)`**
- `/files/` 图片 → 拼 `/api/files/thumbnail?url=...&maxDim=W&quality=80&format=webp`。
  - `width` 缺省 = 原图长边（不缩放，仅重编码，quality 80）。
- 非 `/files/`（外网 http/blob/data）→ 原样返回。
- `USE_WEBP=false` → 直接返回原 `url`（整体回退）。

**C. `normalizeImageUrl`（渲染）**
- `/files/` 图片 → `USE_WEBP ? toWebpUrl(url, 显示宽) : url`。
- `<img onerror>` 回退原 URL（WebP 生成失败/兼容）。

**D. `normalizeImageUrlForSend`（发送，核心修复点）**
- **绝不用 256px 缩略图**（当前 `thumbnailUrl` 会糊）。
- `/files/` 图 → `USE_WEBP ? toWebpUrl(url, 原图宽 /* 不缩放, quality 80 */) : toAbsoluteFileUrl(url)`。
- blob/data → 保持现有 base64 逻辑不变。

**E. `imageCompress.js`**
- `compressImage` 默认 `format` 改 `image/webp`（quality 0.8），保留 `image/jpeg` 作回退。

### 4.2.1 显示时为什么"自动"就转 WebP（核心机制，讲透）

> 用户疑问："前端显示的时候呢？只要一显示它就自动的？" —— 对，就是自动的，机制如下。

**原理**：前端所有 `<img>` 显示图片前，都先经过 `normalizeImageUrl`（`imageUrl.js`）。这是**唯一的图片显示闸门**。只要在 `normalizeImageUrl` 里加一步"转 WebP"，**所有显示图片的组件，显示的那一刻就自动请求 WebP，无需各处改动、用户无感**。

```
所有 <img src={...}> 
   ↓ 统一经
normalizeImageUrl(data.imageUrl)     ← 这一个函数，改这里 = 整站显示全变 WebP
   ↓
USE_WEBP ? toWebpUrl(url, 显示宽) : url
   ↓
/api/files/thumbnail?format=webp&maxDim=显示宽&quality=80   ← 显示那一瞬间动态生成+缓存
```

**三个关键点**：
1. **唯一闸门**：`normalizeImageUrl` 是所有图片显示的共同出口。改一处 = 整站生效（这正是"收口"的意义）。
2. **`onerror` 兜底**：`<img onerror>` 在 WebP 生成失败/浏览器不支持时回退原图，永远不破图。
3. **不侵入业务代码**：显示组件只需保证 `src` 走 `normalizeImageUrl`（多数已如此），不需知道 WebP 细节。

**所以"显示"正是 WebP 一半的价值**：体积小 → 加载快、内存省、画布不卡。另一半价值在"发送"（quality 80 同分辨率不糊）。显示和发送都收口在 `imageUrl.js`，整站自动。

### 4.3 显示组件
- `LazyImage` / `ImageNode` / `TaskCenter` 等的 `<img>`：`src` 经 `normalizeImageUrl`（自动 webp），`onerror` → 原 `imageUrl`。

### 4.4 发送/图生图链路（你的痛点）
- `useConnectedInputs` / `PromptNode` / 图生图节点：参考图经 `normalizeImageUrlForSend`（**质量 80 同分辨率 WebP，不缩放**）。
- **禁用 256 缩略图作为发送参考图**；排查并修正所有误用 `thumbnailUrl` 发图的地方。

## 5. 风险与权衡

| 风险 | 应对 |
|---|---|
| **PNG 透明边缘**：WebP 有损丢透明/边缘糊 | JPG 已白底；PNG 透明图可保留原图显示（`onerror` 回退），或 WebP `alphaQuality`。用户已接受 2K 转 WebP 损失，默认不特殊处理。 |
| **WebP 浏览器兼容** | 现代浏览器全支持；`<img>` `onerror` 回退原 URL。 |
| **后端动态转码 CPU** | 按需 + 文件名缓存（`ensureThumbnailTarget` 已存在），同图转一次缓存复用，可忽略。 |
| **核心发送链路回归** | 分步：先加后端 `format=webp`（不影响现有默认），再接前端显示，最后改发送；每步跑测试。 |
| **可回退性** | `USE_WEBP=false` 一开关整体回退原图；后端原图永存，**不会"改不回来"**。 |
| **磁盘** | 只存一份原图，不翻倍。 |

## 6. 分步实施（评审通过后执行）

### 阶段 1：后端 `format=webp`（零前端影响，可独立上线）
1. `resizeImage`：**几乎不用改**——它已用 `img.quality(quality)`（对 WebP 生效）+ `writeAsync(dst)`（按 dst 扩展名编码）。只需调用方传 `.webp` 结尾的 dst 即可出 WebP。
2. `/api/files/thumbnail` 加 `format=webp` 参数（默认仍 jpeg，不改现有缩略图行为）：
   - **⚠️ 关键实现细节（已验证）**：输出文件**必须以 `.webp` 结尾**，否则 Jimp 按原扩展名(jpg/png)编码而非 WebP。不能复用 `ensureThumbnailTarget` 的默认 basename（会带 .jpg）。
   - 做法：webp 分支在 `.thumbnails/` 目录下拼 `thumb_<maxDim>x<quality>_webp_<原名去扩展名>.webp`，`resizeImage(filePath, 该.webp路径, { maxDim, quality })`。
   - 缓存：文件名带 `webp` 与尺寸/质量后缀区分，同图同参数转一次缓存复用；`resizeImage` 失败回退 `copyFileSync`（兜底，此时前端 onerror 回退原图）。
- 验收：curl `/api/files/thumbnail?url=原图&format=webp&maxDim=原图长边&quality=80` → 返回 `.webp`，浏览器打开、体积变小、尺寸不变。

### 阶段 2：前端 imageUrl.js 统一出口
3. 加 `USE_WEBP` 开关 + `toWebpUrl`。
4. `normalizeImageUrl` 渲染用 webp + onerror 回退。
5. `imageCompress` 默认 webp。
- 验收：全站图片显示变 webp，体积下降，刷新/各节点正常。

### 阶段 3：发送/图生图链路（痛点修复）
6. `normalizeImageUrlForSend` 用「质量 80 同分辨率 WebP」，**禁用 256 缩略图**。
7. 排查并修正所有把 `thumbnailUrl` 当发送参考图的地方。
- 验收：图生图发送后结果清晰不糊，体积小。

### 阶段 4：专项验证
8. PNG 透明、GIF、SVG、外网图、视频封面各场景不破。
9. 大图、粘贴、拖入、素材库、AI 生成全链路。
10. **回退验证**：`USE_WEBP=false` 后整站回退原图正常。
