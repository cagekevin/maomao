
## 模块 1：协议适配层（可执行规格）

### 目标
协议从 2 种扩展到 8 种，`resolveProviderTarget`/`buildTargetUrl` 只查注册表。

### 交付文件
- 后端：`localTool/src/routes/protocolAdapters.ts`（改造，已有 openai/apimart）
- 后端：`localTool/src/routes/providers.ts`（`resolveProviderTarget` 委托适配器）
- 前端：`src/components/base/providerProtocols.js`（扩展适配器）

### 数据结构

> **类型单一真相（审计修正 #4）**：`ProviderProtocol` 类型只在 `protocolAdapters.ts` 定义并导出，`providers.ts` 从它 import 复用，**禁止两处重复定义**（避免 TS 不一致）。

```ts
// protocolAdapters.ts
export type ProviderProtocol =
  | 'openai' | 'apimart'      // HTTP 远程（现有）
  | 'gemini' | 'volcengine' | 'runninghub'  // HTTP 远程（新增）
  | 'jimeng' | 'codex' | 'gemini-cli';      // CLI 本地（新增）

export interface ResolvedTarget {
  url: string;
  authHeader?: string;
  protocol: ProviderProtocol;
  providerId?: string;
}

export interface ResolveCtx {
  rawUrl: string;
  providerId: string;
  baseUrl: string;
  providerKey?: string;
  provider: ApiProvider;
}

interface ProviderAdapter {
  protocol: ProviderProtocol;
  matches: (provider: ApiProvider) => boolean;
  resolve: (ctx: ResolveCtx) => ResolvedTarget;
}
```

### 适配器清单

| 协议 | 类型 | resolve 行为 |
|------|------|-------------|
| openai | HTTP | `openai://<path>` → `${base}/v1/<path>` + Bearer key（已有） |
| apimart | HTTP | base 重拼 + 前缀吸收，不注入 key（已有） |
| gemini | HTTP | models 端点 `/v1beta/models`；请求走 `/v1beta/...` |
| volcengine | HTTP | models 端点 `/api/v3/models`；key 用 `ARK_API_KEY` |
| runninghub | HTTP | models 端点 `/openapi/v2/models`；请求走 OpenAPI |
| jimeng | CLI | **非 proxy 协议**：返回原始 URL + `protocol: 'jimeng'`，不注入 key |
| codex | CLI | **非 proxy 协议**：返回原始 URL + `protocol: 'codex'`，不注入 key |
| gemini-cli | CLI | **非 proxy 协议**：返回原始 URL + `protocol: 'gemini-cli'`，不注入 key |

> **审计修正 #2（CLI 设计）**：CLI 协议**不抛错**。真实链路中 CLI 平台无 base_url、不走 `/api/proxy`（前端走专用通道）。`resolveProviderTarget` 遇到 CLI 协议**返回原始 URL + 协议标记**，让调用方识别为"非 proxy"后走 CLI 专用分支。**抛错会导致代理链路崩溃**。

> **审计修正 #1（域名嗅探决策）**：`is_apimart_provider` **只认 `protocol` 字段，不引入域名嗅探**（维持 C2 单一真相）。
> 依据：APM 这类"protocol=openai + base_url 含 apimart.ai"的站，前端 `buildTargetUrl` 已按 `protocol` 走 openai 伪协议 → 后端按 protocol 解析正确，**无需嗅探**。
> 注：参考实现 Infinite-Canvas 保留嗅探（PRD A2），但我们已用 protocol 字段 + 前端 buildTargetUrl 一致性绕开该需求，故不引入嗅探。

## 模块 2：请求形态层（可执行规格）

### 目标
让 `image_request_mode` 4 形态**真正驱动**生图端点/格式（消灭死字段）；聊天新增形态（chat/completions vs responses）解决 gpt-5.6 工具调用。

### 交付文件
- 后端：`localTool/src/routes/providers.ts`（`effective_image_request_mode` / 生图形态分派）
- 后端：`localTool/src/routes/` 新增 `requestModes.ts`（形态分派 + responses 请求/响应适配）
- 前端：`src/components/base/imageApi.js` / `videoApi.js` / `proxyGenerate.js`（按形态走不同端点）
- 前端：`src/components/base/chatApi.js` / `agentRuntime.js`（聊天形态选择）

### 数据结构

```ts
// requestModes.ts
export type ImageRequestMode =
  | 'openai' | 'openai-json' | 'openai-video-proxy' | 'openai-responses';

export type ChatRequestMode = 'chat' | 'responses';  // 聊天形态

export const SUPPORTED_IMAGE_REQUEST_MODES = ['openai', 'openai-json', 'openai-video-proxy', 'openai-responses'];
```

### 生图形态分派（M2-1）

| image_request_mode | 端点 | 请求 body 要点 | 响应提取 |
|---|---|---|---|
| openai | `${base}/v1/images/generations` | `{model, prompt, size, n, ...}` | `data[].url` |
| openai-json | 同 openai | + `extra_body.response_format:url`；图生图 `extra_body.image` | 同 |
| openai-video-proxy | `${base}/v1/videos` | `{model, prompt, aspect_ratio}`，参考图 multipart | `data[].url` |
| openai-responses | `${base}/v1/responses` | `{model, input:[{role,content:[input_text/input_image]}], tools:[{type:image_generation}], tool_choice}` | `output[]` 的 `image_generation_call` |

**responses 生图实现要点（M2-3，含 H1/H2 兜底）：**
- 请求体：`input` 数组，文本用 `{type:'input_text', text}`，参考图用 `{type:'input_image', image_url}`。
- 响应解析（非流式）：遍历 `output[]`，取 `type==='image_generation_call'` 且 `status==='completed'` 的 `result`。
- **兜底解析（H2）**：若没有 image_generation_call，解析 `output_text` 里的 markdown 图片链接 `![...](url)` 或裸 URL。
- **流式解析（H1）**：处理 `response.completed`/`response.incomplete`/`response.failed`/`error` 事件；**流被掐断时用最后一张收到的图兜底**（`partial_image_b64`/`image_b64`/`result`/`image_url`）。

### 聊天形态分派（M2-2）

| ChatRequestMode | 端点 | 工具格式 |
|---|---|---|
| chat（默认） | `${base}/v1/chat/completions` | `tools:[{type:function,...}]`，响应 `message.tool_calls` |
| responses | `${base}/v1/responses` | `tools:[{type:function, name,...}]`，响应 `output[]` 的 `function_call` |

**responses 聊天实现要点（M2-2/M2-3/M2-4）：**
- **请求构造**：`{model, input:[...messages], tools:[{type:'function', name, description, parameters}], tool_choice:'auto'}`。
  - 注意：responses 的 tool 要求 `name` **直接在 tools 元素**（不是 function 嵌套），实测 APM 报 `Missing required parameter: 'tools[0].name'`。
- **非流式响应解析**：`output[]` 里 `type==='message'` 取 `content[].text`；`type==='function_call'` 取 `name`/`arguments`。
- **流式响应解析**：`response.output_text.delta` 拼文本；`response.function_call_arguments.delta` 拼工具参数；`response.completed` 结束。
- **工具循环兼容（M2-4）**：`agentRuntime.js` 的工具循环需同时识别两种格式——chat/completions 的 `message.tool_calls` 和 responses 的 `output[].function_call`，归一成统一的 `tool_calls` 结构供现有循环消费。

### 形态选择优先级（M2-5）

```
手动指定 image_request_mode（provider 字段）> 自动探测 detect_image_request_mode > 默认 openai
```
- `detect_image_request_mode(base_url, models)`：按 base_url 域名/models 前缀猜（如 agnes 域名→openai-json），**未命中返回空 → 走默认 openai**（保守，不误判）。
- 聊天形态默认 `chat`；gpt-5.6 系模型 → 配置为 `responses`（或在 ProviderForm 加聊天形态下拉）。

### 错误降级提示（G1）

新增 `friendlyRequestError(text, model, provider)`，把上游原始错误翻译成中文可操作提示：
- 含 `reasoning_effort` → "该模型不支持在 chat/completions 用工具，建议改用 responses 端点或换模型"
- 401/unauthorized → "API Key 无效或已过期"
- 429/rate limit → "请求过于频繁，稍后再试"
- 方舟模型不存在 → "改用 ep- 接入点"
集成到 `agentRuntime.js` / `imageApi.js` / `videoApi.js` 的错误分支。

```ts
// providers.ts
const PER_MODEL_PROTOCOL_OPTIONS = ['openai', 'gemini'];  // 只允许 openai/gemini
const FIXED_PROTOCOL_PROVIDER_IDS = ['modelscope', 'volcengine', 'jimeng', 'runninghub'];

export function effectiveProtocol(provider: ApiProvider, model = ''): ProviderProtocol {
  const base = provider.protocol;
  if (FIXED_PROTOCOL_PROVIDER_IDS.includes(provider.id)) return base;  // 锁死平台不支持覆盖
  const overrides = provider.model_protocols || {};
  const val = (overrides[model] || '').toLowerCase();
  if (PER_MODEL_PROTOCOL_OPTIONS.includes(val)) return val as ProviderProtocol;
  return base;
}
```

```ts
// 校验 image_generation_endpoint / image_edit_endpoint
function normalizeEndpointOverride(value: string, label: string): string {
  const e = (value || '').trim();
  if (!e) return '';
  if (e.length > 300 || /\s/.test(e)) throw new Error(`${label} 不合法`);
  if (/^https?:\/\//i.test(e)) return e.replace(/\/$/, '');
  if (!e.startsWith('/')) throw new Error(`${label} 需以 /v1/... 开头`);
  return e;
}
```

### 关键实现

**1. 协议下拉 8 项（M5-1）**
`ProviderForm.jsx` 的 `PROTOCOLS` 从 `['apimart','openai']` 扩为 8 项，与后端 `protocolAdapters` 的 protocol 集合一致（C3）。**下拉选项由同源常量驱动**，避免加协议时前后端漏改。

**2. 生图形态下拉（M2-1/M5-1）**

**3. 聊天形态选择（M2-2，新增）**

**4. 单模型协议选择器（G2/M3-2）**
`ModelSection.jsx` 每个 image/chat 模型加协议选择下拉：
- 只对 image/chat 显示（video 不显示）
- 只有非锁死平台能选（`FIXED_PROTOCOL_PROVIDER_IDS` 内不可选）
- 选项：默认 / openai / gemini
- 选非 openai/gemini → 删除该键

```jsx
// ModelSection.jsx
function modelProtocolSelect(catKey, model, item) {
  if (catKey === 'video_models' || FIXED_PROTOCOL_PROVIDER_IDS.has(item.id)) return null
  const val = (item.model_protocols?.[model] || '')
  return <select value={val} onChange={...}>
    <option value="">默认</option>
    <option value="openai">OpenAI</option>
    <option value="gemini">Gemini</option>
  </select>
}
```

**5. 模型数据一致性（G3/G4，新增）**

**6. 平台专属面板（M5-2）**

**7. 自动探测反馈（M5-3，含 D 系列）**

- 显示探测到的协议/生图形态（D1/D2）

- 跳转/HTML 探测提示（D3）："请填 API Base URL 不是网页"
- 方舟兜底提示（D4）

**8. 默认平台不可删（G7）**
`ApiSettings.jsx`：modelscope/volcengine/runninghub 等内置平台 readonly，只可改不可删。

**9. 密钥输入（M5-4）**
password 型 + 清 key 按钮（已有 ProviderForm），保持。
