# 平台配置声明化 · 目标与文件位置（设计稿）

> 范围：仅描述目标、文件位置与**写代码前已核实的平台契约**，**不含具体实施方案**。
> 契约均从源码核实（`providerProtocols.js` / `protocolAdapters.ts` / `providers.ts` 的 `normalizeProvider`、前端 `ProviderForm.jsx` / `providerStore.js`），非仅依赖文档。

---

## 一、目标

把"每个平台长什么样"从散落在前后端多处的硬编码逻辑，收敛为**每个平台一个独立的 JSON 声明文件**。

具体目标：

1. **一个平台 = 一个 JSON 文件**，彼此独立、互不干扰，改坏一个不影响其他平台。
2. 平台 JSON 只描述**元数据 + 默认配置骨架**：`label`（中文名）、`tab`（通用/专属归类）、`locked`（是否锁协议 id）、`default_protocol`（用哪个协议）、以及一组**默认值字段**（含平台专属字段的默认值）。**不描述表单字段/渲染**——因为前端已改为纯 JSON 编辑框，无表单渲染层。
3. **前端编辑面板形态重构**：去掉现有连接配置类手写表单（协议下拉、请求地址、密钥、volcengine/modelscope 专属字段、LoRA 面板等），改为极简三块式——
   - **上方：一个 JSON 配置项**（纯文本编辑框），用户直接编辑该平台的连接配置 JSON；
   - **中间：保留「测试连接（fetch）」与「拉取模型」两个按钮**（行为不变）；
   - **下方：保留 `ModelSection` 模型清单编辑区**（拉取模型后弹窗勾选写回此处，也可手动增删 chat/image/video 模型）。
   
   即：连接配置表单移除、改走"直接填 JSON"；模型管理区因用户"拉取后勾选"诉求予以保留。由此消除 `ProviderForm.jsx` 里针对 `volcengine` / `modelscope` 等的全部 `if` 分支。JSON 编辑框与 `ModelSection` 的同步规则见 3.2。
4. 后端字段归一与同步白名单可由同一份平台 JSON 推导，消除 `providers.ts` 里手写的逐项搬运与 `CONFIG_SYNC_FIELDS` 静态白名单。
5. **协议拼装 / 鉴权注入逻辑不动**：继续复用现有 `protocolAdapters.ts` 的 adapter 体系（那是"协议"层，已做对）。平台 JSON 与 adapter 是解耦的两层。
6. **存储格式兼容**：现有 `providers[]` 存储结构、KV 回写、后端契约保持不变，仅编辑/渲染层改用 JSON 驱动。
7. 加新平台 = 新增 1 个平台 JSON（+ 必要时 1 个 adapter），前端零代码改动。

## 二、写代码前已核实的平台契约（源码事实）

> 以下均从实际运行代码核实，是平台 JSON 设计的事实依据。

### 2.1 协议层（URL 拼装 + key 注入方式）
来源：`src/components/base/providerProtocols.js:91-123`（前端 `buildTargetUrl`）、`localTool/src/routes/protocolAdapters.ts:81-151`（后端实际拼装）。

| 协议 | 类型 | URL 拼装规则（path 自动追加） | key 注入 | base_url 必填 |
|------|------|------|------|------|
| `openai` | HTTP | 伪协议 `openai://<path>`，后端再拼 `base/v1/<path>` | Bearer ✅ | ✅ |
| `apimart` | HTTP | `base/v1/<path>`（含前缀吸收） | 不注入（用 apimart 自身 key） | ✅ |
| `gemini` | HTTP | `base/v1beta/<path>` | Bearer ✅ | ✅ |
| `volcengine` | HTTP | `base/api/v3/<path>` | Bearer ✅ | ✅ |
| `runninghub` | HTTP | `base/openapi/v2/<path>` | Bearer ✅ | ✅ |
| `jimeng` | CLI | `cli://jimeng/<path>`（不走 /api/proxy） | 不注入 | ❌ |
| `codex` | CLI | `cli://codex/<path>`（不走 /api/proxy） | 不注入 | ❌ |
| `gemini-cli` | CLI | `cli://gemini-cli/<path>`（不走 /api/proxy） | 不注入 | ❌ |

> `base_url` 必填列含义：CLI 协议在 `normalizeProvider`（providers.ts:399-423）**不强制 base_url**，可空。HTTP 协议若无 base_url 则 proxy 拼装会缺 host，实际必填。前端 JSON 编辑框下，CLI 平台可留空 base_url（仅填 protocol 即可）。

- `CLI_PROTOCOLS = ['jimeng','codex','gemini-cli']`（`providerProtocols.js:37`）：不走 `/api/proxy`，调用方经 `isProxyProtocol` 识别走 CLI 通道。
- `GENERAL_PROTOCOLS = ['openai','apimart','gemini']` 与 `SPECIAL_PROTOCOLS = ['volcengine','runninghub','jimeng','codex','gemini-cli']`（`providerProtocols.js:26-29`）：决定前端的"通用/专属"归类。
- **这些数组的消费点（迁 JSON 时必须一并处理）**：
  - `ProviderForm.jsx:99` `protocolOptions = tab==='general' ? GENERAL_PROTOCOLS : SPECIAL_PROTOCOLS`（协议下拉选项）
  - `ApiSettings.jsx:4` 导入 `GENERAL_PROTOCOLS/SPECIAL_PROTOCOLS/isGeneralProtocol`（设置页分类渲染）
  - `ModelSection.jsx:36` `FIXED_PROTOCOL_PROVIDER_IDS.includes(p.id)`（锁协议判定）
  - `providerStore.js:241` 保存时 `if (p.protocol==='volcengine')` 补字段（契约 2.2 专属字段由 JSON 默认值替代）

### 2.2 平台专属字段（铁律默认值，来自 `normalizeProvider`）
来源：`localTool/src/routes/providers.ts:414-423`。

| 字段 | 默认值 | 仅哪个平台（按 id，非 protocol）使用 |
|------|--------|------|
| `volcengine_project_name` | `'default'` | id=volcengine（protocol=volcengine） |
| `volcengine_region` | `'cn-beijing'` | id=volcengine（protocol=volcengine） |
| `ms_loras` | `[]` | id=modelscope（**protocol=openai**，非 modelscope 协议） |
| `ms_defaults_version` | `0` | id=modelscope（protocol=openai） |
| `rh_apps` | `[]` | id=runninghub（protocol=runninghub） |
| `rh_workflows` | `[]` | id=runninghub（protocol=runninghub） |
| `image_generation_endpoint` | `''` | 通用「覆盖端点」覆盖项 |
| `image_edit_endpoint` | `''` | 通用「覆盖端点」覆盖项 |
| `model_protocols` | `{}` | 单模型协议覆盖 |
| `model_names` | `{}` | 单模型协议覆盖 |

> 注意：
> - 字段归属按 **provider id** 判断（见 2.3 锁协议），不是按 `protocol`。尤其 `ms_loras` 等属于 id=modelscope 但其 protocol 是 openai——写代码时**不能用 protocol 来决定是否带这些字段**。
> - `image_generation_endpoint` / `image_edit_endpoint` / `model_protocols` / `model_names` 非某平台专属，是「通用覆盖端点」能力，任何平台都可能带。

### 2.3 锁协议平台（前后端双份定义，已埋漂移雷）
- 前端：`FIXED_PROTOCOL_PROVIDER_IDS = ['modelscope','volcengine','jimeng','runninghub']`（`providerProtocols.js:52`）
- 后端：`PROTOCOL_BY_FIXED_ID`（providers.ts:350-356）映射 `modelscope→openai` / `volcengine→volcengine` / `jimeng→jimeng` / `runninghub→runninghub`
- **两处必须保持一致**，是声明化要消除的重复源之一。

### 2.4 通用字段（所有平台共享）
`name` / `base_url` / `protocol` / `image_request_mode`(openai|openai-json|openai-video-proxy|openai-responses) / `image_mode`(sync|async) / `chat_request_mode`(chat|responses) / `chat_models[]` / `image_models[]` / `video_models[]` / `enabled` / `primary`。

> `image_request_mode` 仅 `openai` 协议在 `buildImagePayload` 内消费（providerStore.js:163）；`image_mode` 后端 `buildImagePayload` 拼 `?(sync)` 后缀（protocolAdapters.ts:106-113）。其余协议不消费这两个字段。

## 三、建议文件位置

### 平台声明文件（新增，每个平台一个）
```
localTool/data/platforms/
  openai.json        # 协议，也是 modelscope 的底层协议
  apimart.json       # 协议
  gemini.json        # 协议
  volcengine.json    # 协议
  runninghub.json    # 协议
  jimeng.json        # 协议（CLI）
  codex.json         # 协议（CLI）
  gemini-cli.json    # 协议（CLI）
  modelscope.json    # ⚠️ 非协议：锁 id 平台，其 protocol 实际为 openai（见 2.3）
```
> 单文件、纯声明式。前端可 fetch 汇总，后端可复用做字段归一。
>
> **两份 JSON 的区别（写代码前必读）**：
> - `localTool/data/platforms/<id>.json` = **默认骨架**（平台有哪些字段、默认值），用于初始化/重置。
> - 前端编辑框里用户填的 JSON = **实例**（= `providers[]` 里那条 `ApiProvider`），结构与骨架一致，只是填了实际值。
> - 两者都是同一份 `ApiProvider` 结构，不是两种结构。

### 现有涉及、将被收敛的文件（仅标注，不改结构）
| 文件 | 现状角色 | 收敛方向 |
|------|---------|---------|
| `src/components/base/settings/sections/ProviderForm.jsx` | 协议下拉 + volcengine/modelscope 硬分支 + LoRA 面板 | 整个手写表单移除，改为「上方 JSON 编辑框 + 下方 fetch/拉取模型按钮」两块式 |
| `src/components/base/providerProtocols.js` | 协议白名单 / 中文标签 / 锁 id 静态数组 | 标签与归类迁至平台 JSON |

| `src/components/base/settings/providerStore.js` | 保存时 `if volcengine` 补字段 | 由平台 JSON 默认值驱动 |

### 保持不变的核心层
```
localTool/src/routes/protocolAdapters.ts   # 协议→URL 拼装 / key 注入，保持原样
```

## 三、审计发现（写代码前必读的风险点）

> 第三轮审计（逐行比对文档与 `providerStore.js` / `providers.ts` 真实调用链）发现以下事实，实现时必须处理。

### 3.1 专属字段保存依赖 `prev` 回填，首次创建必须有默认骨架
- `normalizeProvider(item, prev)`（providers.ts:481）传入 `prev` = 磁盘旧值。
- 专属字段（L414-423）每个都是 `input.x ?? prev.x ?? 默认值`：前端**没发**则回退到 `prev`，`prev` 也没有才用铁律默认值。
- 推论：**编辑已有 provider 时，前端 JSON 只填通用字段不会丢专属字段**；但**首次创建**（无 prev）必须靠平台 JSON 默认骨架提供专属字段值，否则落空。→ 平台 JSON 的 `default_*` 骨架在"新建"路径上不可省略。

### 3.2 `ModelSection` 保留（已定方案 B）
- `ProviderForm.jsx:204` `<ModelSection p={p} onUpdate={onUpdate} />` 渲染在表单**最底部**，是**手动增删 chat/image/video 三类模型**的编辑区（`ModelSection.jsx` 全文核实）。
- `fetchModels` 按钮（L187）把拉取结果弹窗勾选，勾选后写回 `p.chat_models/image_models/video_models`；`ModelSection` 的增删改也写回同一字段。**两者同读写 `p` 的模型数组，天然同一数据源，无本质冲突**。
- **用户已定：保留 `ModelSection`**（拉取后勾选进这个手动编辑区，也可手敲）。最终面板形态：
  - 上方：JSON 编辑框（连接配置 / 协议 / 专属字段）
  - 中间：`测试连接(fetch)` + `拉取模型` 两个按钮
  - 下方：保留 `ModelSection`（模型清单手动编辑区）
- **JSON 编辑框与 ModelSection 的同步风险（写代码必处理）**：
  - JSON 编辑框绑定 `p` 整体 JSON，ModelSection 绑定 `p` 的模型数组。若 JSON 编辑框也展示 `chat_models` 等，用户在两端手改会**互相覆盖**。
  - 处理口径：**JSON 编辑框只覆盖"连接配置类"字段**（name/base_url/protocol/image_request_mode/image_mode/专属字段等），保存时**merge 而非 replace** 整个 `p`——即 JSON 编辑框写回的字段覆盖 `p` 对应键，但不触碰 `chat_models/image_models/video_models/model_protocols/model_names`（这些只由 ModelSection 管）。或：JSON 编辑框的"保存"只对 `p` 做浅合并（`{ ...p, ...parsedJson }` 后再剔除模型四类键），杜绝覆盖。
- 由此，`ModelSection` 是前端唯一保留的"表单残留"，符合用户"拉取后勾选"的交互诉求。

### 3.3 `test()` 只发 4 字段，JSON 实例必须含
- `providerStore.js:143` test payload = `{ id, base_url, key, protocol }`。
- 推论：JSON 编辑框的实例**必须含这 4 个字段**，否则测试连接按钮失效。这 4 个均在 2.4 通用字段内，✅ 一致。

### 3.4 `fetchModels()` 只发 id，安全
- `providerStore.js:173` 仅发 `id`，后端自己读 provider → 不依赖前端 JSON 内容，✅ 无风险。

### 3.5 save 时前端 `cleaned` 不挑专属字段，但后端 merge 兜底
- `providerStore.js:224-236` save payload 仅挑通用字段（未挑 volcengine_*/ms_*/rh_*）。
- 但后端 `normalizeProvider` 用 `prev` 回填（见 3.1）→ **实际不丢**。前端 `cleaned` 不挑专属字段是安全的，勿误以为需补。

## 四、非目标（明确不做）

- 不改 `providers[]` 的存储契约与 KV 回写机制。
- 不重写 `protocolAdapters.ts` 的 adapter 拼装逻辑。
- 不把"怎么拼 URL / 怎么注入 key"塞进平台 JSON（那属于协议层）。
- 不合并成单个大 JSON 文件（按本稿，单平台单文件，最安全）。
- 不涉及 `localTool/data/apiConfigs.baseline.json`：那是 apimart 网关级的"第三方 API 接入点 + 模型清单"配置，与 `providers[]` 平台契约是两套体系，不在本次声明化范围。

## 五、验收口径（目标侧）

- 改/加任一平台配置，只需编辑对应 `localTool/data/platforms/<id>.json`，无需改动任何 `.jsx` / `.ts` 表单代码。
- `ProviderForm.jsx` 中不存在针对具体平台 id / protocol 的 `if` 分支（手写表单已整体移除，仅保留 JSON 编辑框 + fetch/拉取模型按钮）。
- 前端编辑面板无手写表单字段；平台配置完全通过上方 JSON 文本项编辑、下方按钮触发动作完成。
- 前后端对"某平台有哪些字段"的定义来源唯一（平台 JSON），不再双份维护。
