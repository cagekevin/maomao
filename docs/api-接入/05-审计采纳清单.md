# 审计采纳清单（一堆 AI 交叉核对后的取舍）

> **定位**：记录外部 AI 审计 Infinite-Canvas 多供应商地基文档后，哪些意见**采纳**、哪些**否掉及理由**。仅文档，不改代码。
> **前提**：IC 后端**确实**有多供应商（`generate_ai_image`(10482)/`get_api_provider`(1381)/`normalize_provider`(1254)/`GET·PUT /api/providers`(12457·12461)/`data/api_providers.json` 3311 行），这是亲自读源码验证过的铁证，不因任何审计意见推翻。

## 一、采纳（4 条，补进地基）

### 采纳 1 · 前端照抄"逻辑"，不照抄"jQuery 写法"
- **审计意见**：IC 的 `api-settings.js`(200KB) 是全局 `document.getElementById` + 全局函数（`applyCliProtocolDefaults` 直接改 `baseInput.value`），别原样搬进 React。
- **采纳方式**：`ProviderSettings.jsx` 抄**数据结构 + 业务逻辑**（RECOMMENDED_APIS / CLI_PROTOCOLS / applyCliProtocolDefaults 的默认模型逻辑 / 测试连接 / 拉取模型），但用**受控组件 + store** 重写，不搬全局 DOM 引用。配色用我们原型暗色。

### 采纳 2 · 字段命名要拍板，避免两套冲突
- **审计意见**：你们 `apiConfigs.baseline.json` 用 `url/key/provider:"自托管"/models[]`；IC 契约用 `base_url/protocol/image_request_mode`。字段名不一致，文档说"一字不差照抄 IC"会跟现有前端冲突。
- **采纳方式**：**保留现有 `apiConfigs` 命名**（`url/key/models` 向后兼容，现有 13 个模型节点不破），**新增字段** `protocol`/`image_request_mode`（对齐 IC 语义）。不推翻现有字段，只加。见 `02-provider字段契约.md` 的"兼容映射"待补充节。

### 采纳 3 · `provider_id` 从前端到网关的传输要闭环
- **审计意见**：IC 的 `provider_id` 是后端函数参数（单进程），但你们跨进程（前端→localTool `/api/proxy`→9004），文档没交代放哪。
- **采纳方式**：前端节点 `data` 加 `providerId` → localTool `/api/proxy` 转发时注入 **`X-Provider-Id` 头**（复用现有 `X-Proxy-*` 机制）→ 9004 路由按头/body 取 `provider_id` 分派。跨进程用 header 完全合理，不等同 IC 的单进程函数参数。
- **注意**：这是"待实现"，不是"已有"。`system.ts` 现在没有 `X-Provider-Id` 注入逻辑。

### 采纳 4 · 裁剪死代码
- **审计意见**：`merge_default_api_providers`(841) 里 modelscope/runninghub/volcengine 三个强制平台分支（约 869-923 行）对你们是死代码（你们默认只有 9004 Lovart）。
- **采纳方式**：抄 `merge_default` 时**只保留"默认 Lovart 缺失则 inject"**，其余 3 平台分支不抄（减少实现量与审计面）。

## 二、否掉（4 条，及理由）

### 否掉 1 · "IC 后端没有多供应商 / generate_ai_image 不存在"
- **审计断言**：`generate_ai_image` 全仓库 0 命中，IC 后端只有单 Lovart。
- **否掉理由**：亲自读 `/Users/kevin/Documents/画布/Infinite-Canvas/main.py`，`generate_ai_image`(10482) 存在且是多供应商分派器（modelscope→codex→gemini-cli→jimeng→runninghub→gemini→volcengine→openai 分支）。审计 AI 多半只看了 IC 的 `apimart-gateway/` 子目录（单上游翻译层），没看主 `main.py`。

### 否掉 2 · "api_providers.json 只在前端，后端不读"
- **审计断言**：IC 的 `api_providers.json` 只存在于 `static/runninghub/` 前端，后端 gateway 不读。
- **否掉理由**：主 `main.py` 的 `get_api_provider`(1381)/`load_api_providers`(1313)/`normalize_provider`(1254) 都读后端 `DATA_DIR/api_providers.json`。后端确实读。

### 否掉 3 · "provider_id 必须用 body 字段，不能用 header"
- **审计断言**：应以请求 body 的 `provider_id` 字段做分派键，不能 header。
- **否掉理由**：IC 用函数参数是因为它单进程。你们跨进程，`X-Provider-Id` 头完全合理，与 IC 设计不矛盾（IC 前端也用 header/query 传 `provider_id`）。

### 否掉 4 · "Lovart 协议名要跟通用 apimart 区分"
- **审计顾虑**：Lovart 用 `protocol:apimart` 会跟以后接通用 apimart 站撞。
- **否掉理由**：**协议名统一用 `apimart` 更好**——apimart = "异步任务 + task_id 轮询"形态，Lovart 对外正是这个形态；区分站靠 `provider_id`（lovart / exellome / ...）不靠协议名。同一 `protocol:apimart` 下可挂多个 provider，分派器按 `provider_id` 选不同 client（`provider_id=="lovart"` 走现有 `LovartClient` HMAC，`provider_id=="exellome"` 走 `openai_client` Bearer）。**一个协议名，多个 provider，正是 IC 的设计。**
