## 一、问题本质（先对齐认知）

两条都不是错误，是 Chrome 的性能提示（Long Task / 强制重排）。它们**成对出现**时，几乎必然指向同一个根因：

> 在一次拖拽/缩放操作中，**每一帧都发生了一次"全画布规模"的 React 重渲染 + 对所有可见节点的 DOM 测量**，导致单帧工作量远超 16ms，且读布局→写样式→再读布局形成同步重排。

- `rAF handler took 81ms`：说明**某个 rAF 回调**里做了太多同步工作（初版写的"React 调度器"是猜的，见下方复核 C——本项目里真正的 rAF 载体是业务代码，不是 React 调度器）。

- `Forced reflow took 35ms`：JS 读了布局属性（`getBoundingClientRect` / `offsetHeight` 等）后立刻写回 DOM/CSS，浏览器被迫当场重排。

> **【审计】reflow 归因修正（原链路不成立）**
>
> 初版称「React Flow 在 commit 后对**每个**可见节点调用 `getBoundingClientRect` 更新 `nodeLookup.measured`
> → 强制重排 ×N = 35ms」。**这条不成立**：React Flow v12 的节点测量由**一个共享 ResizeObserver** 驱动
> （`dist/esm/index.mjs:2137-2162`），且 `updateNodeInternals` 只在**尺寸真的变化**时才读 rect：
>
> ```js
> // @xyflow/system/dist/esm/index.mjs:1848-1852
> const doUpdate = !!(dimensions.width && dimensions.height &&
>     (dimensionChanged || !node.internals.handleBounds || update.force));
> if (doUpdate) {
>     const nodeBounds = update.nodeElement.getBoundingClientRect();
> ```
>
> 拖拽只改 `position`、不改尺寸 → RO 不触发 → **不存在「每帧测量所有可见节点」**。
> 35ms 的真实来源需重新抓，候选：内容自适应节点的 RO 读 `offsetHeight`、`CustomHandle` 的 mousemove rect
> （已 rAF 合帧）、App 级重渲染中的布局读。**第五节验收标准已据此修正。**
>
> **【复核 D】Forced reflow 候选排序（第二轮补）**：按「读布局→写样式」的模式逐个排查，
> 全项目明确的"读后立即写"只有 4 处，排序如下（建议按此顺序在 Performance 面板对调用栈取样）：
>
> | # | 位置                                            | 模式                                                                              | 触发时机           | 评估                                                                                   |
> | - | --------------------------------------------- | ------------------------------------------------------------------------------- | -------------- | ------------------------------------------------------------------------------------ |
> | 1 | `CustomHandle.tsx:43-51` mousemove rAF        | `getBoundingClientRect()` → 立即 `style.setProperty('--cust-shift-x/y')`          | 鼠标 hover 端口时每帧 | **教科书级 forced reflow**。若同帧 React 刚写过 DOM，必触发同步重排。单个只几 ms，但 rAF 内执行会与 React commit 抢帧 |
> | 2 | `uiHooks.ts:327/342` 内容自适应 RO 回调              | RO 回调读 `el.offsetHeight`（`syncWidth:true` 时再读 `offsetWidth`）→ 下一帧 `setNodes` 写回 | 4 类节点内容变化      | RO 回调本身在布局后执行，若同帧有 style 写入即触发同步重排；`syncWidth:true` 读两个属性，风险更高                       |
> | 3 | `system/index.mjs:1852` `updateNodeInternals` | 批量 `getBoundingClientRect` + 每个 handle 一次                                       | 尺寸真变时          | 一次 `setNodes` 会让 N 个更新**集中**执行（这正是 §四 P2「峰值 reflow 更尖」风险的直接证据）                       |
> | 4 | `App.tsx:1068-1076` `visibleNodes` useMemo    | 有折叠 group 时每帧 O(N) `filter`+`map` 出新数组                                          | 每帧             | **不读布局，不算 reflow**，但是每帧 CPU 开销；且新数组会让 `StoreUpdater` 每帧都走 `setNodes`                 |
>
> 注：`NodeShell.tsx:259` 根 div 上的 `contain: layout style` 已经把重排范围限制在节点内部，
> 这是**已有的有利条件**，不要把 `contain` 一起删掉（P3 方案 B 若动主容器 class 时要保住它）。

> **【审计】补充：一次拖拽 = 两遍 React 渲染（结构性成因）**
>
> 受控模式下每帧有两条渲染链：① `onNodesChange` → `useNodesState` 的 `applyNodeChanges` → App setState（第 1 遍）；
> ② `StoreUpdater` 的 effect → `store.setState({ nodes })` → 所有 `useStore` 订阅者（第 2 遍）。
> 单帧工作量因此**翻倍**，是 81ms 的结构性成因之一，也是所有"每帧放大器"的收益乘数。
>
> **【复核 B】修正：每帧其实是 ≥2 次** **`store.setState`，不是 1 次（第二轮补）**
>
> `StoreUpdater`（`react/index.mjs:271-319`）的 effect deps 是 `fieldsToTrack.map(f => props[f])`，
> `fieldsToTrack` 里包含 **`fitViewOptions`**（`:216`）。而 `App.tsx:1179` 传的是**内联字面量**：
>
> ```jsx
> fitViewOptions={{ padding: 0.2, maxZoom: 1, minZoom: 0.05 }}   // ← 每次 App 渲染都是新对象
> ```
>
> → App 每渲染一次，effect 就重跑一次，多出 `store.setState({ fitViewOptions })`
> → **全画布所有** **`useStore`** **订阅者的 selector 又重跑一轮**。
>
> 所以每帧 selector 调用次数是 `订阅数 × setState 次数`，且 `setState 次数 ≥ 2`（拖拽时）；
> §四 P0 里「订阅数 N×1 → N×2」的实际算式是 `2N → 4N`（不是 `N → 2N`）。
> 结论不变（返回原始值的 selector 单次开销极低，净收益仍为正），但**顺手修掉它等于白捡一轮**：
> 见 §四 **P0-C**（1 行改动，零风险）。
>
> 另：`deleteKeyCode={['Backspace','Delete']}`（`App.tsx:1167`）虽**不在** `fieldsToTrack`，
> 但它是内联数组，会破坏 `memo(FlowRenderer)`（`react/index.mjs:2117`）。一并提为模块常量。

## 二、根因定位（代码级证据）

### P0（核心放大器）— `useNodeSize` 返回新对象导致"单点更新被放大成全画布重渲"

`src/components/base/ui/NodeShell.tsx:49-59`：

```ts
function useNodeSize(id) {
  return useStore((s) => {
    const lookup = s?.nodeLookup
    if (!lookup || !id) return { width: undefined, height: undefined }
    const n = lookup.get(id)
    if (!n) return { width: undefined, height: undefined }
    const w = n.width ?? n.style?.width
    const h = n.height ?? n.style?.height
    return { width: w, height: h }   // ← 每次都返回「新对象字面量」
  })
}
```

**为什么这是放大器**：`@xyflow/react` 的 `useStore` 默认以 `Object.is` 比较 selector 结果。`useNodeSize` 每次都返回**新对象引用**，所以 `Object.is` 永远为 `false` → **只要 React Flow 内部 store 变化一次，每个调用** **`useNodeSize`** **的** **`NodeShell`** **都会重渲染**。

而拖拽节点 / 缩放画布时，React Flow 内部 store **每帧**变化（拖拽改 `position`、缩放改 `transform`）。结果：

- 拖拽/缩放 1 个节点 → **画布上所有可见节点**的 `NodeShell` 全部重渲染（即使它们的尺寸根本没变）；

- 一帧内同步完成"全节点 diff + DOM 写"，且叠加两遍渲染（见 §一）→ rAF 81ms 掉帧。

> **【审计】已删除的错误链路**：原「React Flow 在 commit 后对每个可见节点调用 `getBoundingClientRect`
> → 强制重排 ×N」不成立（见 §一）。**reflow 35ms 与本放大器无直接因果**，需单独定位，
> 不能指望修 P0 让它下降到 1 次。

> **【复核 A】React Flow 自己没有这个放大器——全画布重渲 100% 是我们的订阅造成的**
>
> 这条决定了"P0 + P0-B 是不是全部"。逐层核对源码，结论是**是的**：
>
> | 层              | 源码                                                                                                                                                                                          | 结论                                                                    |
> | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
> | `NodeRenderer` | `react/index.mjs:2401` `memo(NodeRendererComponent)`；节点 id 列表由 `useVisibleNodeIds` 用 **`shallow`** 比较（`:2132`）                                                                              | 可见集合不变 → **不重渲**                                                      |
> | `NodeWrapper`  | `react/index.mjs:2358` `memo(NodeWrapper)`；`:2218-2226` 的 selector 返回 `{node, internals, isParent}` 并用 **`shallow`** 比较                                                                     | 只要 `node` 对象引用不变 → **不重渲**                                            |
> | `nodeLookup`   | `system/index.mjs:1635` `if (checkEquality && userNode === internalNode?.internals.userNode) { nodeLookup.set(id, internalNode) }`，且 `react/index.mjs:3406-3412` 调用时传 `checkEquality: true` | `applyNodeChanges` 只替换**被拖节点**，其余节点在 lookup 里**保持同一对象** → `node` 引用不变 |
>
> 也就是说：**拖 1 个节点时，React Flow 只会重渲那 1 个** **`NodeWrapper`**。我们看到的"全画布重渲"，
> 全部来自 `NodeShell` 的 `useNodeSize`（P0）和 14 类节点的 `useConnectedInputs`（P0-B）自订阅触发。
> **不存在"库内第三个放大器"**，不要再去 React Flow 内部找。
>
> 顺带两个"看着像放大器其实不是"的点，别误改：
>
> - `useVisibleNodeIds` 的 selector 每次 store 变化都跑 `getNodesInside`（O(N)，`react/index.mjs:2119-2123`）
>   → 是每帧 **CPU** 开销，但结果用 `shallow` 比较，**不产生重渲染**。
>
> - `useReactFlow()`（`react/index.mjs:1042-1046`）只订阅 `s.viewportInitialized`（原始值）
>   → `useSizeSync` / `useContentHeightSync` 里的 `getNode/setNodes` **不会**因此每帧重渲。

store 每帧变化的完整链路（已核对源码）：
`XYDrag.on('drag')` → `updateNodePositions(dragItems, true)` → `triggerNodeChanges`
→ 受控模式 `onNodesChange` → `useNodesState` 的 `applyNodeChanges` 产生**新 nodes 数组**
→ `StoreUpdater` → `store.setState({ nodes })` → 新快照 → **所有订阅者的 selector 全部重跑**。

`NodeShell` 被 **16 个**节点类型复用，所以这个放大器覆盖全画布。

> **【复核 G】数字修正 19 → 16**：`src/components/nodes/` 下 18 个文件，其中 `useImageHoverActions.tsx`
> 不是节点；17 个节点组件里 `GhostTargetNode.tsx` 只渲染一个透明 `<Handle>`、不用 `NodeShell`。
> 真正复用 `NodeShell` 的是 **16 个**：VideoProcess / VideoExtract / Text / Template / ScriptBox /
> Prompt / Panorama / Loop / Image / ImageBox / GroupNode / GridSplit / GridMerge / FaceMosaic /
> DiscountVideo / Director3D。
> 另：`App.tsx:1190` 的 `onlyRenderVisibleElements={nodes.length > 20}` 已开启虚拟化，
> 所以"全画布"实际是"**全部可见节点**"——节点数 >20 时按视口裁剪（这是有利条件，别关）。

### 【审计新增】P0-B（与 P0 同级的放大器）— `useConnectedInputs` 订阅整个 `nodes`/`edges` 数组

**这是初版完全遗漏的一项，且它比 P0 更重。**

`src/hooks/useConnectedInputs.ts:196-206`：

```ts
export function useConnectedInputs(nodeId?: string): NodeOutputGroup {
  const nodes = useStore((s) => s.nodes)   // ← 订阅整个数组引用
  const edges = useStore((s) => s.edges)   // ← 订阅整个数组引用
  return useMemo(() => {
    const out: NodeOutputGroup = { images: [], texts: [], videos: [], audios: [] }
    if (!nodeId) return out
    const nodeById = new Map(nodes.map((n) => [n.id, n]))          // ← O(N) 建索引
    edges.filter((e) => e.target === nodeId).forEach((e) => { ... }) // ← O(E) 遍历
```

**为什么它是放大器**：`useNodesState` 每帧 `applyNodeChanges` 都产生**新数组引用** → `Object.is` 为 `false`
→ **14 个节点组件全部重渲染 +** **`useMemo`** **全部重算**：
VideoProcess / VideoExtract / Text / Template / ScriptBox / Prompt / Panorama / Loop / ImageBox /
GridSplit / GridMerge / FaceMosaic / DiscountVideo / Director3D。

每个节点每帧的成本：`new Map(nodes.map(...))`（O(N)）+ `edges.filter/forEach`（O(E)）+ 每个产出项
`.map()` 出新对象（大量临时对象 → GC 压力）。合计 **O(N × (N+E)) / 帧**。

> **⚠️ 关键结论：只修 P0，这 14 类节点在拖拽时依然每帧全量重渲染，`rAF handler`** **不会降到 16ms 以下。**
> 初版「P0 单独就能消除 rAF 81ms」的判断**不成立**，第七节的分支决策已据此改写。
>
> 同理，`React.memo(NodeShell)`（`NodeShell.tsx:312`）目前是**无效 memo**——props 里的
> `children` / `icon` / `style` 每次父渲染都是新引用。不先解决 P0-B，memo 与 P0 都会被父级重渲染冲掉。

### P1（次要，跨阈值才发生）— `LodContext` 的 `lodLevel` 变化触发全消费重渲

`src/components/base/canvas/lod.tsx:77-88`：缩放跨阈值（≤0.5 / ≤0.3 / ≤0.2）时 `setLodLevel` 改变 `LodContext` 值 → 所有 `useLod` 消费者重渲染。
**注意**：它只在"跨阈值"那一刻发生（不是每帧），且已用 `lastRef` 防重复。所以它**不是** rAF 81ms/reflow 35ms 的持续成因，而是"缩放时偶尔卡一下"的次要来源。

> **【审计】消费端数量修正**：初版写「`ConnectionLine`、`ImageNode`/`DiscountVideoNode`/`PromptNode` 经 `useMediaDegrade`」。
> 实际 `useMediaDegrade` 有 **10 个**消费节点：VideoProcess / VideoExtract / Template / Prompt / Image /
> ImageBox / GridSplit / GridMerge / FaceMosaic / DiscountVideo；另有 `ConnectionLine` 直接用 `useLod()`。

### P2（内容自适应节点）— `useContentHeightSync` 的 ResizeObserver 读/写模式

`src/components/base/core/uiHooks.ts:315-361`：**4 类节点**（VideoExtract / ScriptBox / GridSplit / GridMerge）用 ResizeObserver 监听内容高度，变化时读 `offsetHeight` 再 `setNodes` 写回 node 尺寸。现状已用 `disconnect + rAF` 防循环，但**多个节点各自排队 rAF、各自读+各自写**，N 个内容变化 = N 次 `setNodes` + N 次测量，且读/写交错。

> **【审计】节点数修正**：初版写「5 类（含 Template）」。实际 `TemplateNode` **只在注释里引用**
> （`TemplateNode.tsx:528` 是文档示例），并未真正调用 `useContentHeightSync`，故是 **4 类**。
> §四 P2 的收益预估需按 4 类重算。

### P3（死规则）— `lod-3` 的 `.node-content` 隐藏未生效

`index.css:649-651` 有 `.react-flow.lod-3 .react-flow__node .node-content { display:none }`，但 `NodeShell` 主容器（`NodeShell.tsx:244` 的 `mainShellClassName`）没有 `node-content` 类（见 `CANVAS_PERFORMANCE.md` 已标注），缩到极小仍渲染全部节点内容。

> **【审计】风险修正：初版标为「零回归，顺手做」是危险的误判。** 直接给主容器加 `node-content`
> 至少有三个实质副作用：
>
> 1. **端口消失 / 边可能报 code-008**：`CustomHandle`（含 `<Handle>`）就渲染在这个 div 内部
>    （`NodeShell.tsx:295-300`）。`display:none` → 端口 rect 归零 → 触发 `updateNodeInternals`
>    → `getHandleBounds` 读到空 rect → `handleBounds` 被清掉，连到这些节点的边可能消失或错位；
>    放大回来还要重新测量（一次批量 reflow）。
> 2. **内容自适应节点的尺寸会被写坏并持久化**：ScriptBox / GridSplit / GridMerge / VideoExtract 用
>    `useContentHeightSync` 监听这个容器。塌成只剩标题栏后 RO 触发 → 把 `node.height` **写回成极小值
>    并落进项目快照**。此后「缩到 ≤0.2 再放大」就会改动用户数据。
> 3. 与 `lod-2` 的 `img { visibility:hidden }`、lod-3 的 `input/textarea/button { visibility:hidden }`
>    叠加后，节点视觉上等于被清空，可能超出预期。
>
> **结论：不是零回归。** §四 P3 的方案已改为「首选删死 CSS」，见该节。

## 三、为什么这是"最优解"（论证）

最优解 = **用最小改动、零行为回归，消除最大杠杆的放大器；其余按收益/成本取舍，不盲目堆优化**。

| 候选方案                                                         | 杠杆                                                                           | 成本/风险                                                                                         | 结论                    |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | --------------------- |
| 【P0】修 `useNodeSize` 返回原始值                                    | 消除 `NodeShell` 层的全画布重渲放大器                                                    | 1 文件、行为等价、零回归                                                                                 | ✅ **必做**              |
| **【P0-B】收窄** **`useConnectedInputs`** **订阅粒度**（审计新增）         | **消除 14 类节点每帧重渲染 + O(N²) 重算，比 P0 更重**                                        | 1 文件；改数据订阅语义，需 PoC + 14 节点回归                                                                  | ✅ **必做，与 P0 同批**      |

**关键判断（审计后修订）**：

rAF 81ms 是**每帧持续**的。能解释"每帧全画布重渲"的有 **两个**放大器，不是初版说的一个：

1. **P0**（`useNodeSize` 返回新对象）→ 所有 `NodeShell` 重渲；
2. **P0-B**（`useConnectedInputs` 订阅整个 `nodes`/`edges` 数组）→ **14 类节点组件重渲 + O(N²) 重算，比 P0 更重**。

> **两者必须同批修。** 只修 P0，父级节点组件仍每帧重渲并带着新的 `children` 进来，
> P0 的收益会被完全掩盖（`React.memo(NodeShell)` 挡不住新 `children` 引用）。

**【复核 C】但"放大器"不等于"载体"——rAF 81ms 的直接载体是业务里的 rAF 回调（第二轮最重要的一条）**

P0 / P0-B 决定的是**每帧有多重**；而 `[Violation] 'requestAnimationFrame' handler took 81ms`
要求这段工作**发生在一个 rAF 回调里**。React 调度器本身不用 rAF（走 MessageChannel），
所以初版"来源是 React 调度器的 rAF"是猜的。本项目里真正的 rAF 载体是：

```ts
// src/App.tsx:262-269
const viewportRaf = React.useRef(null)
if (viewportRaf.current == null) {
  viewportRaf.current = createRafBatch((zoom) => setZoomPercent(Math.round((zoom || 1) * 100)))
}
const onViewportChange = React.useCallback((v) => {
  viewportRef.current = v || null
  viewportRaf.current?.(v?.zoom || 1)
}, [])
```

`createRafBatch`（`utils.ts:300-312`）把 `fn` 放在 **rAF 回调里同步执行**。于是**缩放时每一帧**：

```
滚轮 → d3-zoom → onViewportChange → rAF 回调 → setZoomPercent → App 全量 setState
      → App 重渲（ReactFlow + 16 类节点 × NodeShell，被 P0/P0-B 放大成全画布）
      → React commit + DOM 写 → 全部耗时记在这个 rAF handler 上 → [Violation] 81ms
```

这同时解释了**两条告警为什么成对出现**：缩放是最容易同时命中
「rAF 回调内全量重渲（81ms）」+「重渲过程中的布局读（35ms reflow）」的操作。

> ⚠️ **纯拖拽节点时** **`onViewportChange`** **不触发**，所以拖拽场景的 81ms 另有载体。
> 候选：`useContentHeightSync` 的 rAF 内 `setNodes`（`uiHooks.ts:334`）、`CustomHandle` 的 rAF。
> **必须先录基线确认载体再动手**（§五新增第 7 步），不要把 P0/P0-B 的成败绑在 rAF 数字上。

**结论：修 P0/P0-B 是"减重"，修 P0-C 是"换载体"。两者缺一不可**——
只减重不换载体，rAF 回调里那次 App 重渲依然存在（只是从 81ms 变成比如 30ms，仍可能超 50ms 阈值）；
只换载体不减重，拖拽场景依然掉帧。

reflow 35ms **不是**由 P0 / P0-B 直接导致（见 §一归因修正 + 复核 D 候选表），需单独定位。
P1 / P2 / P3 均为局部或间歇项，且经审计后风险均高于初版评估。

### 【P0 · 必做】修复 `useNodeSize`：拆成两个返回原始值的 selector

**文件**：`src/components/base/ui/NodeShell.tsx`（仅 `useNodeSize` + 其调用点）

**原理**：拖拽/缩放时 store 每帧变 → 每个 `NodeShell` 的 selector 仍会重跑（zustand 对所有订阅者重算），但 selector 返回**原始 number/string/undefined**，`Object.is` 相等 → React **跳过该节点重渲染**。只有尺寸真变的节点（拖 resize 手柄、比例变化、内容自适应写回）才重渲自己。

**目标代码**：

```ts
// 拆成两个独立 selector，各自返回原始值（Object.is 安全，零对象分配）
function useNodeWidth(id: string): number | string | undefined {
  return useStore((s) => {
    const n = s?.nodeLookup?.get(id)
    return n?.width ?? n?.style?.width
  })
}
function useNodeHeight(id: string): number | string | undefined {
  return useStore((s) => {
    const n = s?.nodeLookup?.get(id)
    return n?.height ?? n?.style?.height
  })
}
```

`NodeShell` 组件内把 `const { width, height } = useNodeSize(id)` 改为：

```ts
const width = useNodeWidth(id)
const height = useNodeHeight(id)
```

> 无需改 `style={{ width, height }}` 的渲染逻辑——原代码已对 `undefined` 做了 fallback 兜底。
> **【审计】行号修正**：初版写的「`NodeShell` 注释 L100-103」是 `style` prop 说明，不是尺寸 fallback；
> fallback 实际在 **`NodeShell.tsx:248-253`**（`fallbackW` / `inlineW` / `inlineH`）。结论不变：无需改渲染逻辑。
> 不推荐 `useShallow` 方案：它每次仍分配新对象（selector 返回字面量），大画布下每帧几百次对象分配有 GC 压力；返回原始值才是真最优。

**等价性已核对**：原实现在 `!lookup` / `!n` / `!id` 三种情况下返回 `{width: undefined, height: undefined}`，
新实现 `s?.nodeLookup?.get(id)` 在这三种情况下同样得到 `undefined` → **行为完全等价**。

**已知副作用（可接受）**：拆成两个 selector 后订阅者数从 N×1 变 N×2，大画布下 `store.setState` 时
selector 调用次数翻倍。但因返回原始值、单次开销极低，**净收益仍为正**。

**验收**：见第五节。无回归风险（尺寸跟随行为完全等价，仅"不该重渲的不再重渲"）。

> **⚠️ 必须与 P0-B 同批落地**，否则父级节点组件仍每帧重渲并传入新的 `children`，
> 本项收益会被完全掩盖（见 §三关键判断）。

### 【P0-B · 必做，与 P0 同批】收窄 `useConnectedInputs` 的订阅粒度

**文件**：`src/hooks/useConnectedInputs.ts`（仅 `useConnectedInputs` 本体，L196-237）

**问题**：现状订阅 `s.nodes` / `s.edges` 整个数组引用 → 拖拽每帧数组重建 → \*\*14 类节点组件全体重渲染

- `useMemo` O(N×(N+E)) 重算\*\*（见 §二 P0-B）。这项比 P0 更重，且初版完全遗漏。

**思路**：把"订阅整个 `nodes`/`edges` 数组"改成"只订阅与本节点相关的最小切片"。

> **【复核 E】从"需先 PoC"收敛为可落地设计（第二轮补——初版和第一轮审计都只给了方向，没给方案）**
>
> 三条源码事实决定了方案长什么样（都已核对）：
>
> 1. **`s.edges`** **与** **`connectionLookup`** **在拖拽期间引用稳定。**
>    `connectionLookup` 只在 `setEdges` 时重建（`react/index.mjs:3428-3432` → `system/index.mjs:1947`）。
>    而 `App.tsx` 的 `onNodesChangeForEdges` 在 `selectionMap` 为空时**第 1010 行就 return**，
>    拖拽只产生 `position` change → **`setEdges`** **根本不被调用**。
> 2. **上游节点对象在** **`nodeLookup`** **里引用稳定**（`adoptUserNodes` 的 `checkEquality`，`system/index.mjs:1635`），
>    因此 `node.data` 引用也随之稳定。
> 3. **"按** **`data`** **引用判等"是这个库自己的标准做法**——React Flow 内置的
>    `useNodesData`（`react/index.mjs:4309-4327`）就用 `shallowNodeData`
>    逐项比较 `Object.is(a.data, b.data)`（`system/index.mjs:1961-1976`）。我们照抄同一范式即可，
>    不需要自创。另外 `useStore(selector, equalityFn)` 第二参数是官方 API
>    （`react/index.mjs:38-44` → `useStoreWithEqualityFn`），**不算 hack**。
>
> **落地设计（三段式，`useConnectedInputs`** **内部改造，调用方零改动）**：
>
> ```ts
> // ① 入边：以 edges 数组为 key 做 WeakMap 缓存，只在 edges 引用变化时重建 O(E)
> //    → 拖拽每帧返回「同一个数组对象」，Object.is 相等 → 不重渲染
> const EMPTY_IN: IncomingEdge[] = []
> const incomingCache = new WeakMap<Edge[], Map<string, IncomingEdge[]>>()
> function incomingOf(edges: Edge[], nodeId: string): IncomingEdge[] {
>   let idx = incomingCache.get(edges)
>   if (!idx) { idx = buildIncomingIndex(edges); incomingCache.set(edges, idx) }
>   return idx.get(nodeId) ?? EMPTY_IN
> }
>
> // ② 上游：返回 [{ node, sourceHandle }...]，用自定义 equalityFn 逐项比 node 引用 + handle 字符串
> //    group 上游用 s.parentLookup 展开为「非 hidden 子节点」
> const upstream = useStore(
>   useCallback((s) => collectUpstream(s, incoming), [incoming]),
>   upstreamEqual   // (a,b) => 长度相等 && 每项 node 引用相等 && sourceHandle 相等
> )
>
> // ③ 聚合：复用现有 getNodeOutput，签名与返回值完全不变
> return useMemo(() => aggregate(upstream), [upstream])
> ```
>
> ⚠️ **`parentLookup`** **有个坑**：`adoptUserNodes` 每次 `setNodes` 都会 `parentLookup.clear()`
> 再 `new Map([...])` 重建（`system/index.mjs:1632` / `:1680`）→
> **不能把** **`parentLookup.get(id)`** **这个 Map 直接当 selector 返回值**（引用每帧都变）。
> 必须 `Array.from(map.values())` 后按**元素引用** shallow 比较。

**⚠️ 副作用与前置验证（必须先做，否则勿动）**

- **最大风险：上游** **`data`** **深层变化不再触发下游更新**（表现为"上游重新生成了，下游还是旧图"）。
  这正是本 hook 存在的核心语义（其注释 L34-36 明确写了"用 `useStore` 订阅数据本身"）。

- **回归面**：14 个节点组件的"读上游"行为全量回归，重点
  `TextNode` / `TemplateNode` / `ScriptBoxNode` / `ImageBoxNode`（多图与编组出口逻辑最复杂）。

- **退回方案**：若 shallow 比较仍有每帧抖动（例如某上游每帧重建 `data`），则保留数组订阅，
  但把 `useMemo` 的计算改为**按节点 id 索引的增量缓存**（只重算入边发生变化的下游节点），
  至少把 O(N×(N+E)) 降到 O(N+E)。注意：这条路**只降 CPU，不降重渲染**，是次选。

**验收**：见第五节（新增"拖拽时只有被拖节点重渲染"这一条）。

### 【P2】`useContentHeightSync` 的读/写批处理（审计后下调为观察项）

**文件**：`src/components/base/core/uiHooks.ts`；新增 `src/components/base/canvas/resizeBatch.ts`

**设计**：把"每节点独立 RO + 独立 rAF + 各自读各自写"改为"全局批处理调度器"，遵循 FastDOM 的 **先批量读、再批量写** 模式，消灭读/写交错重排：

1. 新增 `resizeBatch.ts`，维护一个 `Map<id, el>` 待重测队列 + 单个全局 rAF：

   - RO 回调只做"登记 id 到队列 + 标记脏"，**不读布局、不写 store**；

   - 下一帧统一遍历队列：`el.offsetHeight`/`el.offsetWidth` 全部读完（批量读，浏览器只重排一次）；

   - 用**一次** `setNodes` 把多个变化节点的新尺寸合并写回（批量写）。
2. `useContentHeightSync` 改为调用 `scheduleNodeResize(id, el, opts)`，复用 `createRafBatch`（`utils.ts:300`）的"last-args-wins + flush"语义保证松手位置不丢帧。
3. 4px 阈值判定保留（基于 `lastWrittenH`，已是自上次写回值比较，非滞后 `getNode`）。

**收益（审计后下调）**：初版称"把 N 个内容变化压成 1 次 setNodes + 1 次测量，消除重排堆叠"。经审计，该收益**存疑**：

> **【审计】P2 的三条反效果风险**
>
> 1. **RO loop 告警很可能复发（高）**：现状的 `disconnect → rAF 写回 → 下一帧 re-observe`
>    （`uiHooks.ts:322-353`）是**专门为消除** **`ResizeObserver loop completed with undelivered notifications`**
>    而做的（该 hook 注释 L257-267 有明确记载）。改成全局批处理后，per-node 的
>    disconnect/re-observe 时机丢失 → 多节点同帧写回 → 仍在观察的 RO 同帧再次触发 → **已根治过的告警回归**。
> 2. **峰值 reflow 可能更尖（中）**：一次 `setNodes` 会让 `updateNodeInternals` 一次性收到 N 个更新
>    → 集中执行 N 次 `getBoundingClientRect` + 每个 handle 一次（`system/index.mjs:1852` / `:898`）。
>    现状是错峰在多个 rAF 里，改后反而集中成单帧尖峰。
> 3. **`lastWrittenH`** **与实际高度可能不同步（中）**：批量写回改变了每个节点的写回时序。
>
> **结论：P2 从"✅ 做"下调为"⚠️ 观察项"。** 若确要做，必须：
> ① 保留 disconnect / re-observe；② 限制每帧批量写回的节点数（如 ≤3）；
> ③ 把「`ResizeObserver loop` 告警不复现」写入验收。
>
> 另注意：初版写"5 类节点"，实际是 **4 类**（见 §二 P2），收益预估需按 4 类重算。

**验收（修订）**：同时调整 4 个内容自适应节点的 resize 手柄 / 批量粘贴图片，观察：
① 控制台**不出现** `ResizeObserver loop completed with undelivered notifications`；
② 尺寸跟随正确；③ Forced reflow **峰值不高于改动前**。
（初版的"从 N 次降为 1 次"基于错误归因，已作废——见 §一。）

### 【P1 · 边际】lod 媒体隐藏改为纯 CSS 驱动（P0 验证后视情况）

**文件**：`src/components/base/canvas/lod.tsx`、`useMediaDegrade.ts`、各媒体节点

**思路**：媒体隐藏已通过 `index.css` 的 `lod-1/2/3` class 实现（`CANVAS_PERFORMANCE.md §二`），`LodProvider` 已做 `classList` 切换。可让 `useMediaDegrade` 不再**条件渲染** `<img>/<video>`，而是始终渲染、仅用 CSS 隐藏，使 `lodLevel` 变化时媒体节点**无需 React 重渲染**（只靠已有的 classList 切换）。

> **【审计】方案不可直接落地，取舍理由需重写**
>
> 1. **消费端是 10 个节点，不是初版说的 3 个**（VideoProcess / VideoExtract / Template / Prompt /
>    Image / ImageBox / GridSplit / GridMerge / FaceMosaic / DiscountVideo），另有 `ConnectionLine`
>    直接用 `useLod()`。改动面远大于初版评估。
> 2. **CSS 只能隐藏标签级** **`img`** **/** **`video`**。像 `ImageBoxNode` 的多图网格、`TemplateNode` 的生成结果
>    容器这类**媒体包在 div 里**的场景，CSS 选择器够不到 → 改成"始终渲染 + CSS 隐藏"后
>    **既不减少渲染，还多占了内存**。
> 3. `display:none` / `visibility:hidden` 的媒体仍占内存与解码资源（初版这点是对的）。
>
> **结论**：本项从"P0 后视情况投入"进一步下调为\*\*"默认不做"**。
> 若缩放跨阈值确实仍偶发卡顿，正确做法是**逐个节点排查\*\*（哪个节点的 `useMediaDegrade` 分支最重），
> 而不是整批改渲染结构。

**取舍**：跨阈值才发生一次，非持续卡顿主因；上述 3 点使收益/成本比进一步恶化。**默认不做。**

### 【P3 · 高风险，方案已改】`lod-3` 死规则处理

**文件**：`index.css`（首选）/ `src/components/base/ui/NodeShell.tsx` + `index.css`（次选）

> **【审计】初版「零回归，顺手做」是误判**，三条副作用见 §二 P3（端口消失 / 边 code-008、
> 内容自适应节点尺寸被写坏并持久化、跨 0.2 阈值批量 reflow）。方案改为二选一：

**方案 A（首选）：直接删死规则。** 删除 `index.css:649-651` 的
`.react-flow.lod-3 .react-flow__node .node-content { display:none }`。

- 理由：该规则复制自官方 `V_.jsx:14-26`，但原型的节点结构里**没有一个不含端口的"纯内容容器"**，
  强行造一个就会伤到端口与尺寸写回。承认这条官方规则在原型不适用，成本最低、收益为正（消除误导）。

- 回归：仅影响 zoom ≤ 0.2 时的视觉（少一层隐藏）。零风险。

**方案 B（次选，仅当确实需要在极小缩放下降渲染量时）：把** **`node-content`** **加在业务内容的内层容器上。**

- 必须满足：该容器**不包含** **`CustomHandle`**（端口在 `NodeShell.tsx:295-300`，位于主容器内）；

- 必须满足：4 个内容自适应节点（ScriptBox / GridSplit / GridMerge / VideoExtract）的
  `useContentHeightSync` **测量目标不受影响**，否则 `display:none` 会把极小高度写回并持久化；

- 必须回归：① zoom 跨 0.2 来回切换后，边是否还在、是否报 code-008；
  ② 来回切换后节点 `width`/`height` **是否被改动**（对比切换前后的项目快照）。

## 五、验证方法（量化验收，必须过）

用 Chrome DevTools 实测前后对比，目标：

| 指标                                       | 优化前                  | 优化后目标                           |
| ---------------------------------------- | -------------------- | ------------------------------- |
| `rAF handler` 时长                         | 53–81ms（有 Violation） | < 16ms（无 Violation）             |
| 拖拽 1 节点时重渲染的组件数                          | 全画布节点                | **仅被拖节点**（需 P0 + P0-B **同时**生效） |
| **缩放时重渲染的组件数**（复核新增）                     | App 全量 + 全画布节点       | **仅 zoom% 叶子组件 + LodProvider**  |
| **每帧** **`store.setState`** **次数**（复核新增） | ≥ 2                  | **1**                           |
| `Forced reflow`                          | 35ms（来源待重新定位）        | **不高于改动前**（不能设"降为 1 次"，见 §一）    |
| 拖拽 / 缩放节点 FPS                            | 掉帧                   | ≥ 55fps                         |

> **【审计】reflow 一行已修正**：初版写"从多次/35ms 降为仅被拖单节点 1 次、< 5ms"。
> 该目标建立在「React Flow 每帧测量所有可见节点」这一**已被证伪**的前提上（见 §一），已作废。
> 正确做法：先录基线，改完对比，**只要峰值不升高**即视为通过；若 reflow 未改善，
> 说明它是独立问题（另立主题排查），**不要据此判定 P0/P0-B 失败**。

**步骤**：

1. **React DevTools → Profiler**：勾选高亮重渲染，录制"拖拽 1 个节点 2 秒"。

   - **P0 + P0-B 联合验收关键**：画布上**只有被拖节点**重渲染，其它节点颜色不变。
     ⚠️ 初版只写「`NodeShell` 不再重渲染」——**不够**：只做 P0 时，14 类使用
     `useConnectedInputs` 的节点组件仍会每帧重渲染。必须 P0 与 P0-B **都做完**再验收这一条。
2. **Performance 面板**：录制"拖拽 2 秒 + 缩放 2 秒"，看 Summary 的 Long Tasks 数量与最大耗时、
   以及 `Forced reflow` 标记，与改动前基线对比。
3. 控制台不再出现 `[Violation] 'requestAnimationFrame' handler took …`。
4. **回归：14 个** **`useConnectedInputs`** **消费节点的"读上游"行为**（P0-B 的主要风险面）——
   上游改 data、增删连线、编组内子节点变化，下游均能拿到最新产出。
5. **回归：`ResizeObserver loop completed with undelivered notifications`** **不出现**（P2 相关，
   改动 `useContentHeightSync` 时必须验）。
6. 边界回归：拖 resize 手柄改尺寸、改比例（`useSizeSync`）、粘贴图片后高度自适应、缩放跨阈值——
   节点尺寸均正确跟随（行为等价不变）。

> **【复核 H】第二轮新增的 3 条验收（必须补，否则前 6 步会漏判）**
>
> 1. **先定位 rAF 载体再动手**：Performance 面板录制，在 `[Violation] 'requestAnimationFrame' handler took …`
>    上右键看**调用栈归属**——确认是 `viewportRaf`（缩放场景）还是 `useContentHeightSync` 的 rAF /
>    `CustomHandle` 的 rAF（拖拽场景）。**载体会影响验收口径**：
>
>    - 若 81ms 只出现在**缩放** → P0-C 的 C3 是关键项，P0/P0-B 是减重项；
>
>    - 若**拖拽**也报 → 需先解决另一个 rAF 内的 setState，P0/P0-B 只能降低数值、不能换载体。
> 2. **缩放与拖拽必须分别录基线**（两者触发链不同，见复核 C）。只录拖拽会漏掉

> 3. **每帧** **`store.setState`** **次数**：在 `StoreUpdater`（`react/index.mjs:283`）临时打点计数，
>    或接 zustand devtools 看 action 流。P0-C 的目标值就是这一条（≥2 → 1）。

                                                               ├─ 同批落地 → 浏览器验证
③ P0（NodeShell 单文件，行为等价）──────────────────────────────┘   （Profiler：是否只剩被拖节点重渲）

**必须同步做的一件事**（不是性能，是防止埋雷）：
把「**写** **`node.data`** **必须用不可变更新，禁止原地 mutation**」写进
`src/components/base/ui/NodeShell.tsx` 的 §5 数据状态注释。P0-B 落地后，
原地 mutation 会从「性能差」升级为「下游静默不更新」（复核 F1），这条约束必须显性化。

> **一句话总结（第二轮审计后修订）**：
> **每帧全画布重渲有两个放大器，不是初版说的一个——`useNodeSize`** **的对象选择器（P0）和
> `useConnectedInputs`** **订阅整个数组（P0-B，更重，初版遗漏）。经复核 A 确认，React Flow 自己
> 已做到「只重渲变化的节点」，`memo(NodeWrapper)`** **+** **`shallow`** **+** **`adoptUserNodes(checkEquality)`
> 三层都在挡——所以这两个订阅就是全部，不必再去库里找第三个放大器。两者必须同批修。**
> **但"减重"不等于"换载体"**（复核 C）：`[Violation] 'requestAnimationFrame' handler took 81ms`
> 要求这段工作发生在 rAF 回调里，而本项目把它放进去的是 `App.tsx:264` 的 `viewportRaf`
> （缩放时每帧在 rAF 内 `setZoomPercent` → App 全量重渲）。**P0/P0-B 减重，P0-C 换载体，缺一不可。**
> **`Forced reflow 35ms`** **与它们无直接因果**（原归因已证伪），候选已排好序（复核 D），需独立定位，
> 不要拿它判断 P0/P0-B 成败。
> **P1 / P2 / P3 经审计后风险均高于初版评估**：P2 可能让已根治的 RO loop 告警复发，
> P3 的"零回归顺手做"是误判（会伤端口并把错误尺寸写进快照），P1 的 CSS 驱动方案在原型不可直接落地。
