## 一句话结论

**一个能力 = 一个入口 = 一处实现。** 裁剪只用「就地裁剪」，标记只用「涂鸦编辑器」，扩图用新的原生面板；`ImageEditor` 里**失效且与节点入口重复的裁剪/扩图按钮直接删除**——不去修它，绕开。

---

## 1. 现状问题（为什么必须收敛）

| 能力 | 当前入口 | 问题 |
|---|---|---|
| 裁剪 | ① hover 栏「裁剪」→ `InlineImageCropper`<br>② `ImageEditor` 内「裁剪」按钮 | **两套并存，按钮重复**；且 ② **实测保存无效** |
| 扩图 | 仅 `ImageEditor` 内「扩图」 | 与裁剪共用失效的画布写回链路，同样不可靠 |
| 标记/涂鸦 | `ImageEditor`（pencil 等） | ✅ 可用，但编辑器里混着上面两个坏按钮 |

核心矛盾：**同一个能力有两个入口，其中一个还是坏的**。用户明确反馈"不需要那么多裁剪按钮"。

---

## 2. 终态架构

```
节点 hover 栏
  ├─ 裁剪  →  InlineImageCropper（就地，已验证可用）   ← 节点内「快速裁剪」，保留
  ├─ 标记  →  ImageEditor（仅涂鸦工具，见 §3）          ← 涂鸦唯一实现
  └─ 画幅  →  CanvasSizePanel（新增，见 §4）            ← 大图内「裁剪 + 扩图」统一面板

三者统一出口：
  onImageReplaced(dataUrl, {width,height})  →  fitByRatio  →  节点框跟随
                                            （78 号文档已通，不改）
```

**裁剪为何仍是两个入口（非重复）**：
| 入口 | 场景 | 定位 |
|---|---|---|
| `InlineImageCropper` | 节点上随手裁 | 快速、就地、不离开画布 |
| `CanvasSizePanel` 内裁剪 | 双击大图后调画幅 | 精细、可配合扩图/原图重定位 |

二者**语义不同、不冲突**，且 `ImageEditor` 内那个失效的裁剪已删除 —— 用户不再会遇到"点了没反应"的按钮。

## 3. ImageEditor 改造（只留涂鸦）

### 3.1 删除的工具
- `crop`（裁剪）、`expand`（扩图）—— 从 `ALL_TOOLS` 与工具栏按钮中移除。
  - 理由：裁剪已有节点上的就地裁剪（可用）；扩图由新面板承担。**不去修 `applyCrop`**，绕开未定位的根因。
  - 影响：用户若想"涂鸦后裁剪" → 保存涂鸦 → 再点节点「裁剪」，流程无损。

### 3.2 保留的工具
`pencil` / `eraser` / `text` / `line` / `arrow` / `square` / `circle` / `number` / `eyedropper`

### 3.3 必须同步修的两处（低成本、高收益）
1. **初始绘制源改同源 dataURL**（防画布污染）
   现状 `tryLoad(true)` 失败会回退**无 CORS 加载** → 画布被污染 → `toDataURL` 抛 `SecurityError`。
   改为统一走 `compressImage(url, {keepOriginalFormat:true})` 拿同源 dataURL 作绘制源，**永不污染**，`toDataURL` 永远安全。
2. **吸管取色补 try/catch**
   `ctx.getImageData(...)` 当前是**裸调**（无 try/catch），画布一旦污染会直接抛错崩掉整个编辑器。补 try/catch + 失败提示。

### 3.4 保存出口（"绘制完再 export"，已成立）
绘制全程在活画布实时进行（性能），**点保存时一次性** `canvas.toDataURL()` 导出——这与现状 `handleSave` 一致，且实测可用，不改。

## 4. 画幅面板 `CanvasSizePanel`（新增，裁剪 + 扩图统一）

### 4.1 核心洞察：裁剪与扩图是同一操作的两个方向

- **裁剪** = 画布往**内**缩（丢掉边缘）
- **扩图** = 画布往**外**扩（补白边）

因此**无需两套工具**，只需一个"调整画幅"的交互：**拖边往内即裁、往外即扩**。

### 4.2 统一模型（一个 `drawImage` 覆盖两种情形）

```
结果画布：tw × th
原图贴入位置：(dx, dy)
  扩图 → dx, dy ≥ 0  （原图在画布内，四周留白）
  裁剪 → dx, dy ≤ 0  （画布在原图内，原图被外移裁切）
```

导出统一为：

```ts
exportCanvas(url, { w: tw, h: th }, (ctx, img) => {
  if (非透明) { ctx.fillStyle = '#ffffff'; ctx.fillRect(0, 0, tw, th); }
  ctx.drawImage(img, dx, dy);   // 同一行代码，同时支持裁剪与扩图
});
```

**原图始终 1:1 自然像素贴入，不缩放不拉伸** —— 变的只有画布尺寸与原图在其中的位置，画质零劣化。

### 4.3 交互

```
      ┌─ ── ── ── ── ── ── ──┐
      │  斜线纹 = 新画幅区域    │   往外拖→扩(白边)；往内拖→裁
      │    ┌───────────┐      │
   ◄──┤    │  原图可拖动  │      ├─►   四边/四角手柄
      │    └───────────┘      │
      │              1920×1080 │   实时显示目标尺寸
      └─ ── ── ── ── ── ── ──┘
```

| 元素 | 做法 |
|---|---|
| 画幅 | 4 边 + 4 角拖拽手柄，往内/往外双向 |
| 预设 | `1:1 / 4:3 / 16:9 / 9:16 / 原比例` 胶囊 |
| 尺寸反馈 | 拖动中实时显示 `1920×1080` |
| 原图定位 | 自由拖；**居中吸附 + 三分线**（决定 AI 往哪延伸，是核心功能） |
| 白区视觉 | 斜线纹 / 浅灰底，明确"留给 AI 填" |
| 缩放 | 画幅一变即 `fitZoom()`（见 109 §2.3，当前缺失的关键一步） |

**不做**：扩展滑块（拖边已替代）、shimmer、A/B 对比、重新生成 —— 本步只产出"留白图"，填充由下一步大模型完成。

### 4.4 技术复用与约束

- **复用**：`computeOutpaintTarget` / `computeOutpaintDrawPos` / `OUTPAINT_RATIOS`（纯函数，带单测）；导出走 `exportCanvas`（109 §2.1）。
- **约束**：白边**纯白 `#ffffff`**，输出 **PNG 无损**（JPEG 噪点干扰下一步 AI 识别待填区）。
- **入口**：双击大图内加「画幅」（需拖放空间，节点内放不下）。

## 5. 施工顺序（低风险优先，每步可独立验收）

1. **删 `ImageEditor` 的 `crop` / `expand`**（止血 + 去重，改动最小，立即消除坏按钮与重复入口）。
2. **`ImageEditor` 初始源改同源 dataURL** + **吸管补 try/catch**（防污染/防崩溃）。
3. **新增 `CanvasSizePanel`（§4）**：统一画幅（裁剪 + 扩图），双击大图内入口；含 `fitZoom`。
4. 跑 `tsc` + 构建 + 相关单测；人工验收能力各点一遍。

> 第 1、2 步是**纯删减与防护**，风险极低，可先行；第 3 步是新增，独立不影响存量。
> `InlineImageCropper`（节点内快速裁剪）**全程不动**。

## 7. 取舍说明（为什么不修 `applyCrop`）

- `applyCrop` 的真实根因**未定位**（坐标映射？`sw` 被钳成 1？），jsdom 单测无法复现真机布局时序。
- 已有**可用替代**（`InlineImageCropper`），修它的唯一收益只是"能在全屏编辑器里裁剪"，而用户可在保存后回到节点裁剪，**功能无损**。
- 因此选择**删按钮绕开**，而非继续投入定位根因。
- 若日后确实需要全屏内裁剪，路径见 109 §2.1：改用「新建游离 canvas + `drawImage(主画布, 选区)`」绕开 `getImageData`——但这属于可选增强，**不在本方案范围**。

## 8. 遗留（记账，不急）

1. **撤销栈内存**：`pushHistory` 存 `getImageData` 全画布快照，4096×4096 RGBA ≈ 67MB/步。当前小图无碍；若未来有大图编辑反馈，需单独方案（折中：改存 dataURL 快照；彻底：改存绘制指令重放）。
2. **出图体积**：PNG 无损 + 扩图后面积增大 → base64 体积上升（见 `72` 号文档）。靠 `OUTPAINT_ZOOM_MIN/MAX` 限制扩图上下限来控制，**不牺牲 PNG 无损**。
3. **`ImageEditor` 与 `InlineImageCropper` 两套画布模型并存**：本方案通过"能力互斥"规避冲突（裁剪归就地、涂鸦归全屏），无需统一到一套，代价可控。
