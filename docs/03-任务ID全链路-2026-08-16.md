# 03 功能：任务 ID 全链路（前端可见 ID → Lovart thread_id → 查询状态/结果）

> 日期：2026-08-16
> 本文档解释「任务 ID」这一机制为什么这样设计、背后逻辑、能达到什么效果，并把完整链路讲透。
> **读者是后续 AI**：看完应能理解「用户/前端看到的任务 ID 是怎么贯穿到 Lovart 的、每一步改哪里、为什么这么改」，并在此基础上安全修改。

---

## ⚡ 速读（TL;DR · 30 秒抓住核心，改代码前先看这段）

**这条链路解决一件事：让"用户在任务中心看到的那个 ID"能查到"这个任务在 Lovart 里跑得怎么样了、返回了什么"。**

链路上一共有 **3 个 ID**，别搞混：

| ID | 是谁的 | 长什么样 | 干什么 |
|---|---|---|---|
| **前端 task_id** | 前端自造 | `task_msuk85sh_...` | 任务中心主键，**用户能看到的就是它** |
| **网关 task_id** | 网关用 Lovart 返回拼的 | `task_82b545c6-...` | 网关统一查询入口的 ID |
| **thread_id** | Lovart 上游真实 ID | `82b545c6-...` | 拿它直接问 Lovart"任务好了没/结果是什么" |

> 关系：网关 task_id = `"task_" + thread_id`。前端 task_id 和它们不是一回事，靠 localTool 关联。

**完整链路一句话：**
```
前端把前端 task_id 带给 localTool → localTool 转发网关拿到 thread_id → localTool 把两者关联落库
→ 拿前端 task_id 用 db-query.mjs 能查到 thread_id → 再拿 thread_id 直接问 Lovart 状态/结果
```

**后续 AI 要记住的 3 条铁律（详见 §五）：**
1. **关联必须发生在 localTool**（它同时能看到前端 ID 和 Lovart ID；网关不落盘、Lovart 不回显前端 ID）。
2. **前端 task_id 靠模块级变量传**（`getCurrentTaskId/setCurrentTaskId`），只覆盖走 `useNodeGeneration` 的路径。
3. **连 Lovart 必须走代理**（脚本已内置 CONNECT 隧道 + 探测端口）。

> 本文还包含另一层能力：**「刷新网页后异步任务不丢」（§四）**——生图/视频任务刷新后靠 `poll_task_id` 自动恢复轮询，把网关还在跑的结果补回任务中心。文本/同步任务无 task_id，刷新断即断（对齐官方，不恢复）。

---

## 〇、一句话结论

**前端任务中心显示的那个 `task_xxx` ID，是整条链路的「贯穿主 ID」。** 前端在发请求时把它带给 localTool，localTool 转发网关、网关拿到 Lovart 的 `thread_id` 后，localTool 把「前端 task_id ↔ thread_id」关联落库。于是拿用户能看到的前端 ID，就能一步步查到关联的 Lovart thread_id，进而直接向 Lovart 查任务状态（`/chat/status`）和结果（`/chat/result`）。

```
前端任务中心显示的 task_id（用户可见）
   ↓ 前端 proxyRequest 带 payload.taskId
localTool /api/proxy（读 body.taskId）
   ↓ 透传网关，网关返回 Lovart thread_id（= 网关 task_id 去掉 task_）
localTool persistThreadId：把「前端 task_id ↔ thread_id」关联落库（tasks.thread_id）
   ↓
db-query.mjs --lifecycle <前端task_id>   → 得到 thread_id + 全链路记录
   ↓
db-query.mjs --lovart-status / --lovart-result <thread_id>  → 直查 Lovart 状态/结果
```

**在此基础上，又加了一层「刷新恢复轮询」（详见 §四）：** 异步任务（生图/视频）提交时把网关返回的 task_id 存进任务记录 `poll_task_id`；前端网页刷新后，靠它重新查 `GET /api/v1/gateway/task/{id}`（localTool 统一入口，不绑死具体 API），把还在网关后台跑的任务状态/结果补回任务中心，实现「刷新后任务继续跑直到返回」。文本/生图 sync 同步无 task_id，不恢复（官方同此）。

## 一、为什么这样设计

### 1.1 痛点：用户需要「一个能对上号的 ID」

- 用户生成一个任务后，任务中心会显示一个 ID（前端自造的 `task_msuk85sh_...`）。**用户能看到的只有它**，这是用户与后台对话的"身份证"。
- 但 Lovart 上游根本不认识这个前端 ID，它只返回自己的 `thread_id`（如 `82b545c6-...`，UUID）。这两个 ID 不是一回事。
- 如果两者不关联，用户拿前端 ID 去问"我这个任务好了没"，谁都不知道这个 ID 对应 Lovart 的哪个任务——链路就断了。

### 1.2 设计原则（为什么不在网关/Lovart 侧直接做）

- **网关（9004）不直接落盘**（CLAUDE.md §四.2：唯一文件入口是 localTool `/files/`）。所以"存 ID"必须归 localTool，不能靠网关写文件。
- **Lovart 不会回显前端 ID**（它只返回自己的 thread_id）。所以"前端 ID ↔ thread_id"的关联**不能靠 Lovart 那一端完成**，必须在**中间的中转方**建立。
- **localTool（18080）是前端 → 网关 → Lovart 的唯一中转**：它既能"看到"前端发来的前端 task_id（请求里带），也能"看到"网关返回的 Lovart thread_id（响应里带）。**localTool 是天然的关联点**——在这做关联，改一端（localTool）就能打通，不需要改网关、更不需要改 Lovart。

> 一句话：**关联必须发生在"既能看到前端 ID、又能看到 Lovart ID"的节点上，这个节点就是 localTool。**

## 二、背后逻辑（每一步为什么这么写）

### 2.1 前端：把 task_id 带给链路

- 前端 `taskStore.reportGenerate()` 用 `genId()` 生成前端 task_id（`'task_' + base36时间戳 + 随机`），作为任务中心主键。
- 关键：这个 ID 以前**从不发给后端**，只存任务中心。导致后端完全没有它。
- 修复：`imageApi.js` / `videoApi.js` 的 `proxyRequest()` 通过模块级变量 `getCurrentTaskId()` 读到"当前正在生成的前端 task_id"，塞进请求体 `payload.taskId`。
  - 为什么用模块级变量：`proxyRequest` 是独立函数，拿不到 `reportGenerate` 的作用域。用 `useNodeGeneration` 在 `reportGenerate` 后 `setCurrentTaskId(taskCtl.taskId)`，`proxyRequest` 再 `getCurrentTaskId()`，避免改每个节点的传参链路。
  - 为什么塞 body 的 `taskId` 字段而不是 header：前端 JSON 形态的 `/api/proxy` 本来就是 `{url, method, body, providerId}` 结构，加 `taskId` 字段最一致；FormData 形态则走 `x-task-id` header（见 2.2）。

### 2.2 localTool：读 taskId + 透传 + 关联落库

- `handleProxyJson`：body 类型加 `taskId?: string`，读 `frontTaskId`；转发网关时加 `X-Task-Id` header（网关可不读，但透传无害、便于网关日志关联）。
- 响应回来后，`extractAndPersistThreadId(resBody, frontTaskId)`：
  - 从网关异步提交响应解析 `task_id`（图片：`data[0].task_id`；视频：`data.task_id`）。
  - 去掉 `task_` 前缀得到 Lovart `thread_id`。
  - 调 `persistThreadId(threadId, taskId, {}, frontTaskId)` 落库。
- `persistThreadId`（`tasks.ts`）做**两件事**：
  1. 以网关 `task_id` 为主键落一行（`thread_id` 作关联键）。
  2. 若前端 `task_id`（frontTaskId）已有记录（前端 `/api/tasks/save` 写过），`UPDATE` 补上 `thread_id`；没有则 `upsert` 建一行。
  - **必须 `await getDb()`**：`getDb` 是 async（sql.js 首次需异步初始化），早期没 await 拿到 Promise 导致 `upsertTask` 静默失败——这是踩过的坑。
- FormData 形态：从 `req.headers['x-task-id']` 读前端 taskId，同样走 `extractAndPersistThreadId`。

### 2.3 数据库：tasks 表新增 thread_id 列

- `database.ts` 建表语句 + 迁移各加 `thread_id TEXT`。
- `tasks.ts` 的 `ALLOWED_TASK_COLUMNS` 加 `thread_id`、`SNAKE_TO_CAMEL` 加 `thread_id → threadId`，保证它能被写入/读出。

### 2.4 查询脚本：db-query.mjs 三步走

- `--lifecycle <id>`：自动判定 id 是 `task_id` / `thread_id` / `node_id`。用 `thread_id` 或 `task_id` 时转 `task_id="task_"+id` 查库 + 双键 grep 日志（`[poll]` 记 `thread=xxx`、`[submit]` 记 `task_id=task_xxx`）。
- `--lovart-status <thread_id>`：直接向 Lovart 发 `GET /v1/openapi/chat/status?thread_id=xxx`，HMAC-SHA256 签名（对齐 `lovart_client.py`），**自动走代理**（原生 fetch 不走系统代理，需 CONNECT 隧道：`HTTPS_PROXY` 等环境变量 + 探测 7897/7890/1087/1080/8888/8118）。
- `--lovart-result <thread_id>`：同上连 `/chat/result`，返回任务结果（出图 URL / 生成文本）。

## 三、能达到什么效果

1. **用户可见 ID 贯穿到底**：拿任务中心显示的 `task_xxx`，就能查到关联的 Lovart `thread_id` 和全链路（数据库记录 + 网关/前端日志）。
2. **直查 Lovart 状态/结果**：拿 thread_id，不用经过前端，直接问 Lovart"任务好了没 / 结果是什么"。
3. **事后可追溯**：所有任务的前端 ID ↔ thread_id 关联都落库，重启不丢（区别于网关内存 TaskManager）。
4. **不改网关、不改 Lovart**：改动收敛在前端（传 taskId）+ localTool（关联落库）+ 查询脚本，架构侵入最小。
5. **刷新后异步任务不断**：生图/视频任务刷新网页后，靠 `poll_task_id` 自动轮询恢复，任务中心继续显示并最终拿到结果（§四）。文本/生图 sync 同步任务刷新断即断（官方同此），不在恢复范围。

## 四、任务刷新恢复轮询（异步任务：网页刷新不丢）

> 这是在上文「任务 ID 全链路」之上新增的一层能力：**前端网页刷新 ≠ 网关重启**，异步任务在网关/Lovart 里还在跑，前端靠已落库的 `poll_task_id` 重新发起查询，把状态/结果补回任务记录，实现「刷新后任务继续跑直到返回」。

**整体时序（先看这张，再读下文细节）：**
```
1) 用户点生成 → 前端 reportGenerate 造 task_id（任务记录 running）
2) 前端 imageApi/videoApi 提交 → 网关返回 task_id（=task_<thread_id>）
   → setTaskPollId 把网关 task_id 存进任务记录 poll_task_id（落库）
   → 前端继续自己轮询 /v1/tasks/{id} 等结果
        │
        │ 【用户此时刷新网页】
        ▼
3) 前端重建 → initTaskRecovery() 启动恢复轮询
   → 扫到 running 且有 poll_task_id 的任务 → GET /api/v1/gateway/task/{poll_task_id}
   → 网关查还在跑的 Lovart 任务 → 返回 processing/completed/failed
   → patchTask 更新任务记录（进度/结果）→ 任务中心看到结果
```
**关键：2) 不刷新时是正常同步等结果；3) 是刷新后补的回退路径。同步任务（文本/sync）没有 2) 里的 task_id，所以走不到 3)，刷新断即断（官方同此）。**

### 4.1 为什么需要（痛点）

- 异步任务（生图 async 模式 / 视频）提交后，任务在**网关/Lovart 后台继续跑**，但前端是**同步等结果**的请求（fetch 挂着）。
- 用户**刷新网页** → 请求断开 → 前端刷新后**不知道这个任务还在跑**，更不知道结果在哪 → 任务在任务中心卡住/或前端把断开的请求误判成 `failed`（`Failed to fetch`）。
- 核心矛盾：**任务没丢（网关还在跑），但前端丢了"继续等它"的能力**。

### 4.2 核心思路：能查的才查，不能查的不查

```
异步任务（生图async / 视频）          文本 / 生图 sync(SSE)
  提交时拿到网关 task_id                 同步阻塞，无 task_id
  存进任务记录 poll_task_id              （刷新断即断，不恢复）
  刷新后靠 poll_task_id 查状态恢复 ✓
```

- **可查询（有 poll_task_id）**：生图 async 模式、视频。提交即拿到网关 `task_id`，能按它查 `GET /api/v1/gateway/task/{id}`。
- **不可查询（无 task_id）**：文本 `chat_completions`、生图 sync(SSE)。同步阻塞、一次请求到完成，刷新断就断。**官方（reference-1mao shared.js `Pt` hook）也只对视频异步任务做刷新轮询，对文本/同步直接提示"仅支持刷新视频任务状态"。** 故对齐官方，不强行恢复。

> **同步任务不刷新时怎么正常返回？** 同步请求（文本/生图 sync）在前端 `useNodeGeneration` 里是**一次 fetch 挂着直到返回**（网关内部 `run_and_get()` 轮询 Lovart 到 done 才给响应）。只要**不刷新**，前端就会同步拿到结果并 `patchTask` 完成。**只有刷新**才会断——而它没 task_id 可查，所以不恢复。这就是"能查的才查、不能查的不查"里的"不能查"。

> **为什么不做文本恢复（方案B）**：文本目前是网关同步轮询（`chat_completions` 内部 `run_and_get()` 到 done 才返回），前端拿不到 task_id。要恢复文本需网关 chat 也「提交返回 task_id」+ 前端轮询，工作量大且要动网关，本期不做。若后续需要，在网关 `chat_completions` 加异步分支 + `pollTask.js` 放开 type 限制即可（代码注释已标）。

### 4.3 落库：任务记录新增 poll_task_id

- 前端 task 记录新增 `pollTaskId` 字段（存网关返回的 task_id，`task_<thread_id>`）。
- 后端 `tasks` 表新增 `poll_task_id` 列（`database.ts` 建表 + 迁移）。
- `tasks.ts` 的 `ALLOWED_TASK_COLUMNS` 加 `poll_task_id`、`SNAKE_TO_CAMEL` 加 `poll_task_id → pollTaskId`，保证写入/读出。
- 落库时机：`imageApi.js`/`videoApi.js` 的 `generateAsync` 提交拿 `taskId = submitted.task_id`（网关异步提交响应解析，图片 `data[0].task_id`、视频 `data.task_id`，见 §2.2 的 `extractAndPersistThreadId`）后，调 `setTaskPollId(getCurrentTaskId(), taskId)` 写回当前任务记录。
- **注意这是"第二个 task_id"**：任务记录里已有 `id`（前端自造主键）和 `threadId`（Lovart 关联键），`pollTaskId` 存的是**网关返回的可查询 task_id**，三者不同：前端 `id` 是任务中心主键、`threadId` 是 Lovart 上游 ID、`pollTaskId` 是网关统一任务查询入口用的 ID。

### 4.4 轮询恢复：pollTask.js

新模块 `src/components/base/pollTask.js`：

- `initTaskRecovery()`：App 挂载后启动，`setInterval` 每 2s 检查 + 5s 节流，扫描任务列表。
- 筛选条件：`status === 'running' || 'pending'` **且** `pollTaskId` 存在。
- 每轮最多查 `MAX_PER_ROUND=5` 个（防止一次刷新几十个任务打爆网关），超出下轮再查。
- `pollOneTask(task)`：`GET ${API_BASE}/api/v1/gateway/task/${pollTaskId}`（**localTool 统一入口，见 4.5**），解析：
  - `status === 'completed'` → 按类型提取结果 URL（图片 `result.images[0].url`、视频 `data.video_url`）→ `patchTask` 更新 + **广播 `mutiwindow-task-completed`**。
  - `status === 'failed'/'error'` → `patchTask` 置 failed + errorMsg。
  - 还在跑 → `patchTask` 更新 progress。
  - **网络异常不误判失败**：`fetch` 失败 `catch` 后保持 running，下轮再试（避免刷新后误报 `Failed to fetch`）。
- 节流用 `lastRun` 时间戳 + `MAX_PER_ROUND`，避免高频轮询。

### 4.5 为什么走 localTool `/api/v1/gateway/task`（统一入口，不绑死 API）

- 该入口是 localTool `system.ts handleGatewayTask` 统一转发到网关 9004 的**固定查询端点**，按 task_id 查，**不依赖具体 provider 的 base_url**。
- 关键好处：**换底层 API 也有效**。不管现在是 Lovart 还是将来换成别的，只要网关能按 task_id 查状态，前端和 localTool 就不用动。这避免了「和某一个 API（如 Lovart thread_id）强耦合」——task_id 由网关自产、前端只管用，跟具体上游无关。

### 4.6 任务中心：手动刷新状态按钮

- `TaskCenter.jsx` 的 TaskCard：对**非进行中且有 `pollTaskId`** 的任务显示「刷新状态」按钮（对齐官方 jn.jsx 的刷新按钮）。
- 点击调 `pollOneTask(task)` 手动查一次，立即更新状态。
- 文本/生图 sync 任务无 `pollTaskId`，不显示该按钮（官方同此）。

### 4.7 节点自动回填结果（已实现）

- `pollTask.js` 已完成时**广播** `mutiwindow-task-completed`（detail 带 `nodeId/resultUrl/type`）。
- **精准监听**：`useNodeGeneration.js`（所有生成节点共用的统一契约）加了一个 `useEffect` 监听该事件，只处理 `detail.nodeId === 本节点` 且 `status === 'completed'` 且 `resultUrl` 存在的广播，其余**直接忽略** → 只有任务归属的那个节点响应，其他节点零成本。
- 匹配后调节点传入的 `onRecover(detail)` 回调，把 `resultUrl` 写回 `node.data`：
  - `PromptNode.jsx`（生图）：`setImageUrl(resultUrl)` + `patchData({ imageUrl: resultUrl })`
  - `DiscountVideoNode.jsx`（视频）：`setVideoUrl(resultUrl)` + `patchData({ videoUrl: resultUrl })`
- 效果：刷新后节点卡片自动恢复显示生成的图/视频，无需手动重生成。
- 同步任务（文本/生图 sync）刷新断不恢复，无广播，节点不会收到 → 天然不会误回填。

| **网关不直接落盘** | CLAUDE.md §四.2：唯一文件入口是 localTool `/files/`，Python 网关不写文件。ID 落库一律归 localTool。 |
| **关联点必须在 localTool** | 前端 ID 和 Lovart ID 只在 localTool 中转时能同时看到；别在网关/Lovart 侧做关联。 |
| **`getDb()` 是 async** | `persistThreadId` 必须 `await getDb()`，否则拿到 Promise 无法 upsert（踩过坑）。 |
| **前端 task_id 靠模块级变量传递** | `getCurrentTaskId()` / `setCurrentTaskId()`；只覆盖走 `useNodeGeneration` 的路径。不走该路径的提交不会带前端 task_id。 |
| **chat 任务无 thread_id** | chat 走 `/v1/chat/completions` 同步返回，无异步 thread，结果在提交响应的 `choices[0].message.content`，不落 thread_id。 |
| **连 Lovart 必须走代理** | 直连超时；脚本用 CONNECT 隧道 + 环境变量/探测端口。网关走的是同款代理策略。 |
| **网关响应 task_id 形态** | 图片 `data:[{task_id}]`，视频 `data:{task_id}`；`extractAndPersistThreadId` 兼容数组/对象两种。 |
| **刷新恢复只覆盖异步任务** | 只对有 `poll_task_id` 的生图(async)/视频做轮询恢复；文本/生图 sync 同步无 task_id，刷新断即断（官方同此），不强行恢复。 |
| **恢复轮询走 localTool 统一入口** | `GET /api/v1/gateway/task/{id}`（`handleGatewayTask`），按 task_id 查、不依赖具体 provider → 换 API 也有效，不绑死 Lovart。 |
| **轮询网络异常不误判失败** | `pollOneTask` 里 `fetch` 失败 `catch` 后保持 running、下轮再试；绝不把断开误报成 `failed`（修复 `Failed to fetch` 误标）。 |
| **每轮有上限** | `pollTask.js` `MAX_PER_ROUND=5` + 5s 节流，防止一次刷新几十个任务打爆网关。 |
| **节点回填（已实现）** | `useNodeGeneration` 统一监听 `mutiwindow-task-completed`，仅 nodeId 匹配的节点响应（精准）；PromptNode/DiscountVideoNode 传 `onRecover` 写回 `node.data`，刷新后节点自动恢复显示结果。 |
