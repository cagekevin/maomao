# 42-文件生命周期：单一引用感知 GC 方案（问题2 图片404 的最优解）

> 目标唯一：**根治「删任务/资源时误删画布仍在引用的文件」导致的图片 404，让文件删除决策权收归一处。**
> 本文档全部依据**真实源码**（`localTool/src/**` 与 `src/components/base/filesApi.js`）核对，行号为核对时点，供后续实现者定位。
> 相关背景：落盘机制见 docs/34（素材/落盘/rescan 专题）、文件外置见 docs/41 §2（base64 外置 + §2.7① 配套 GC）。

---

## 0. 一句话结论

**删除记录绝不删盘，删盘只由 GC 决定。** 所有「删除任务 / 删除资源 / 清空任务 / 清空资源」的入口一律只删数据库记录，把「要不要删磁盘文件」这件事交给唯一的「引用感知 GC」去裁决——GC 扫描**全库引用**（tasks + resources + 画布 KV），磁盘上无任何引用才删文件。

---

## 1. 问题回溯：图片 404 的真实根因

### 1.1 现象
控制台出现两个生成图 404：

- `efeaf79f54ee2e84_generated_20260817_151515.png`
- `75a8d3ed9e00a0a9_generated_20260817_151220.png`

排查（docs/41 会话已确认）：
- **排除网络问题**：日志显示两文件都落盘成功（`[download] ... OK`）；
- **排除偶发问题**：同日期其它文件都在，唯独这两张消失；
- **定位为代码逻辑问题**：文件被「清空任务」（clear all tasks）误删了。

### 1.2 根因链

```
用户在任务中心点了「清空所有任务」
    ↓
localTool/src/routes/tasks.ts  handleTasksClear
    ↓  取出所有 result_url/thumbnail_url → DELETE FROM tasks
    ↓  逐 URL 调 deleteLocalFile(db, url)      ←【这里删盘】
        ↓
database.ts  deleteLocalFile
    ↓  只检查 tasks 表 + resources 表是否还引用
    ↓  （两表已无引用 → 判定"可删" → fs.unlinkSync 删盘）
        ↓
但这两张图仍被 画布 KV（canvas-state-*）引用！
    ↓
画布下次打开 → <img src="/files/..."> → 404 破图
```

**核心缺陷**：`deleteLocalFile` 的引用检查**只覆盖 tasks 与 resources 两张表，不包含画布 KV**（`canvas-state-*`）。而文件生命周期中最重要的一类引用恰恰是「画布节点里存的图片 URL」——任务中心清空任务后，画布可能仍在使用这些图。

## 2. 现状审计：分散的删盘逻辑（真实代码）

### 2.1 tasks 删除入口 —— 三处都在删盘

`localTool/src/routes/tasks.ts`：

| 接口 | 位置 | 删盘调用 |
|---|---|---|
| `handleTasksDelete` | tasks.ts:139-140 | `deleteLocalFile(db, task.result_url / thumbnail_url)` |
| `handleTasksBatchDelete` | tasks.ts:155-156 | 同上（去重后逐个删） |
| `handleTasksClear` | tasks.ts:168-169 | 同上（全量清空时逐个删） |

### 2.2 resources 删除入口 —— 删盘更狠

`localTool/src/routes/resources.ts`：

| 接口 | 位置 | 删盘调用 |
|---|---|---|
| `handleResourcesDelete` | resources.ts:284 | `deleteLocalFile(db, row.url)` |
| `handleResourcesClear`（按文件夹） | resources.ts:297 | `fs.rmSync(folderPath, { recursive: true, force: true })` —— **整目录递归删** |
| `handleResourcesClear`（全量+deleteFiles） | resources.ts:308-309 | 遍历目录 `fs.unlinkSync(...)` 逐个删 |

`rmSync(recursive)` 是**最危险的删盘**：它不看任何引用，按文件夹一刀切，画布/其它文件夹引用的文件也会被连带删除。

### 2.3 deleteLocalFile 的引用检查盲区

`localTool/src/db/database.ts:258-279`：

```ts
export function deleteLocalFile(db: any, dbUrl: string): boolean {
  if (!dbUrl.startsWith(LOCAL_FILE_BASE)) return false;
  const relativePath = dbUrl.slice(LOCAL_FILE_BASE.length);
  const diskPath = path.join(getUploadDir(), relativePath);
  if (!fs.existsSync(diskPath)) return false;

  // 只检查 tasks 表 + resources 表引用
  const taskRefs = queryOne(db, 'SELECT COUNT(*) ... FROM tasks WHERE result_url = ? OR thumbnail_url = ?', ...);
  const resRefs  = queryOne(db, 'SELECT COUNT(*) ... FROM resources WHERE url = ?', ...);
  if ((taskRefs?.cnt ?? 0) > 0 || (resRefs?.cnt ?? 0) > 0) return false;  // ← 不含画布 KV

  fs.unlinkSync(diskPath);   // ← 误删点
  return true;
}
```

盲区：**不检查 `kv` 表 `canvas-state-*` 里的 `/files/` 引用**。这是问题 2 的直接原因。

### 2.4 现有 GC 的现状（已经具备骨架）

`localTool/src/utils/orphanGc.ts` 已有 `runOrphanGc`：
- 遍历 **KV 表全部 value**，用 `extractFilesUrls` 提取被引用的 uploads 相对路径（**已覆盖画布 KV**）；
- 合并 `extraRefs`（tasks/resources 的 URL，完整 URL 转相对路径）；
- 递归扫描 `uploads/`（跳过 `.thumbnails/`），删除「磁盘有、但不在引用集合」的孤儿文件；
- 支持 `dryRun` 只统计不删除。

触发点：`localTool/src/routes/admin.ts:87-114` `handleAdminCleanup` → 挂载在 `router.ts:192` `POST /api/admin/cleanup`。

> **结论**：GC 需要的「全库引用收集」能力已经存在且**已含 KV**，只是目前只被手动接口调用、且各删除入口仍在各自删盘，GC 没有成为唯一裁决者。

## 3. 方案核心原则

1. **删记录绝不删盘**：所有删除接口只做 DB 记录删除，绝不直接 `unlinkSync` / `rmSync`。
2. **删盘只由 GC 决定**：GC 是文件生命周期的唯一裁决者，扫描全库引用（tasks + resources + 画布 KV），磁盘文件无任何引用才删除。
3. **先 dry-run 再执行**：GC 上线默认 dry-run，验证误删为零后再开自动执行。
4. **幂等下载 + 原子写**：下载落盘前检查 `existsSync`（已有），落盘用「写 .tmp → rename」原子写，避免半截文件。
5. **GC 的 `extraRefs` 必须包含 `resources` 表全部 url**：不仅画布 KV、tasks 表，素材库 `resources` 表里的 url 也是合法引用。用户"存进素材库但没放进画布"的图只存在于 `resources` 表，若漏传会造成新的素材丢失（详见 §3.5）。

## 3.5 与 rescan 的关系（关键补遗：方案不冲突，但职责边界必须写清）

> 本节回应"已有 rescan，本方案是否多余 / 会否冲突"的质疑。结论：**不冲突，且 rescan 是 GC 的天然补位**；但两者对"什么是引用"的口径不同，必须显式分工，否则后人改 rescan 时会引入风险。

### 3.5.1 rescan 不删盘，不是 404 的来源

`resources.ts:168-178` 的孤儿清理**只删 `resources` 表记录，无任何 `fs.unlinkSync` / `rmSync`**：

```ts
const localRows = queryAll(db, `SELECT id, folder, name, type FROM resources WHERE source = 'local-tool'`);
for (const row of localRows) {
  const diskPath = path.join(uploadDir, row.folder, row.name);
  if (!fs.existsSync(diskPath)) {
    run(db, `DELETE FROM resources WHERE id = ?`, [row.id]);  // 仅删表记录
  }
}
```

所以 rescan **永远不会造成图片 404**。它只做"磁盘↔resources 表"的元数据同步：磁盘有则补记录，磁盘无则删记录。

### 3.5.2 rescan 与 GC 的口径差异（真正的问题不在删盘，在"引用真相"）

| 维度 | rescan（resources.ts） | GC（orphanGc.ts） |
|---|---|---|
| 引用来源 | 只看**磁盘上有什么文件** | 看 **KV(画布) + tasks + extraRefs(resources 等)** |
| 输出 | 把磁盘文件登记进 `resources` 表；删"磁盘已无"的表记录 | 删"磁盘有、但全库无引用"的文件 |
| 是否删盘 | **否** | 是（仅 GC 删盘） |
| 是否看画布 KV | 否 | 是 |

关键事实：**AI 资产（`ci`/`hi` 落盘，docs/34 §4.2/§6.1⑤）只写磁盘、不写 `resources` 表、不触发 rescan**。因此一份被画布 KV 引用的图，可能处于"磁盘有、resources 表无"状态。此时：

- GC：画布 KV 引用 → **不删盘** ✅（GC 正确）
- rescan：扫到磁盘有这文件 → **补建一条 `resources` 记录** → GC 的 `extraRefs` 也由此看到它 → 更稳 ✅

**结论：在"摘掉删除入口删盘、只靠 GC 回收"的方案下，rescan 不但不打架，反而是 GC 的补位**——它把"磁盘有、表无"的画布引用文件登记进 `resources`，确保 GC 的 `extraRefs` 不漏。文档原稿未述及此点，特此补全。

### 3.5.3 GC 的 `extraRefs` 必含 `resources` 表（最高优先护栏）

`handleAdminCleanup`（admin.ts:87-106）**已实现正确收集**：

```ts
const refUrls = new Set<string>();
const resUrls = queryAll(db, 'SELECT url FROM resources');        // ← resources 表全部 url
for (const r of resUrls) refUrls.add(r.url);
const taskUrls = queryAll(db, 'SELECT result_url, thumbnail_url FROM tasks'); // ← tasks 表
// ...
const gc = runOrphanGc(kvValueStrings, uploadDir, refUrls, false);  // extraRefs = resources + tasks
```

- `resources` 表里的素材**不必然出现在画布 KV**（用户存着以后用、暂未放入画布）。若某次实现漏把 `resources` 表 url 放进 `extraRefs`，GC 会把这类素材当孤儿删掉 → **新的素材丢失**。这是当前方案最危险的隐蔽点。
- **护栏**：任何重写 GC 引用收集的代码，必须 `SELECT url FROM resources` 全量并入 `extraRefs`（现状 admin.ts 已做到，文档 §4 步骤 2 描述"把收集收敛进 GC 内部"与现状不符——实际由调用方收集，GC 只消费 `extraRefs` 参数，见 §4 步骤 2 修正）。

### 3.5.4 显式职责边界（写死，防止后人误改）

1. **rescan 职责**：仅"磁盘文件 ↔ resources 表"元数据同步；孤儿清理**只删表记录、永不得扩展为删盘**。
2. **GC 职责**：全库引用（KV + tasks + resources）扫描 → 孤儿文件回收；GC 是**唯一**的删盘裁决者。
3. **两者不冲突**：rescan 让"磁盘有、表无"的引用显性化（补进 resources），GC 据此保命；GC 删盘后，下一次 rescan 的孤儿清理会因"磁盘已无"而自然删掉对应 resources 记录，形成闭环。
4. **竞态**：rescan 与 GC 都只读库/删表/删盘，均为幂等。建议 GC 自动调度与 rescan 手动触发错峰；极端并发下最多多算/少算一条引用，**不会误删盘**（因两者都不存在"先删盘再校验"的路径）。

## 4. 实施步骤（具体执行）

### 步骤 1：摘除各删除入口的删盘逻辑（只删记录）

1. `tasks.ts`：
   - `handleTasksDelete`：删除 `deleteLocalFile(db, task.result_url)` / `thumbnail_url` 两行（tasks.ts:139-140），只保留 `DELETE FROM tasks`。
   - `handleTasksBatchDelete`：删除 seen 去重删盘循环（tasks.ts:153-157），只保留逐条 DELETE。
   - `handleTasksClear`：删除删盘循环（tasks.ts:166-170），只保留 `DELETE FROM tasks`。
2. `resources.ts`：
   - `handleResourcesDelete`：删除 `if (row?.url) deleteLocalFile(db, row.url)`（resources.ts:284），只保留 `DELETE FROM resources`。
   - `handleResourcesClear`：删除 `fs.rmSync(...)`（resources.ts:297）与 `fs.unlinkSync(...)` 循环（resources.ts:308-309）。`deleteFiles` 参数改为「提示将在下次 GC 回收」或不传该参数。
3. `database.ts`：`deleteLocalFile` 不再被路由调用后，可**降级为仅供 GC/迁移工具内部复用**（其引用检查改由 GC 统一接管），或直接移除对外暴露。

> 删盘行为消失后，磁盘上可能出现「短期的临时孤儿」，这正是下一步 GC 自动触发的理由——文件由 GC 在引用消失后的下一个周期回收。

### 步骤 2：GC 成为唯一删盘裁决者

扩展现有 `runOrphanGc`（orphanGc.ts）为「引用感知 GC」的正式入口，明确契约：

```
输入：
  - kv 表全部 value（画布节点图片 /files/ 引用）
  - tasks 表 result_url、thumbnail_url
  - resources 表 url
  -（可选）临时目录排除规则
输出：deletedFiles 列表 + 统计（scanned/deleted/skipped/referenced/dryRun）
安全边界：
  - 只删 getUploadDir() 目录内文件
  - 跳过 .thumbnails/（缩略图按需重新生成）
  - 跳过隐藏文件/目录
  - dryRun=true 只统计不删除
```

要求：引用收集**当前由调用方 `handleAdminCleanup`（admin.ts:91-106）负责**（查 `resources` 全表 url + `tasks` 的 `result_url`/`thumbnail_url`，合并为 `extraRefs` 传入 `runOrphanGc`）。GC 自身只消费 `extraRefs` 参数，**不主动查库**。此分工保持不变即可——关键是保证 `extraRefs` 必含 `resources` 表全部 url（见 §3.5.3）。若未来想让 GC 单点收口，需把 admin.ts 的收集逻辑移入 `runOrphanGc` 并在函数内 `getDb()`，并确保 `resources` 表 url 不漏。

### 步骤 3：GC 自动化触发

**最优触发方式：删除入口尾部同步触发**（比定时更优——"引用消失 → 文件回收"窗口趋近于零，无需等日/小时级定时）。

1. **删除入口尾部调用**（已实现，2026-08-18）：
   - `tasks.ts`：`handleTasksDelete` / `handleTasksBatchDelete` / `handleTasksClear` 删完记录后 `await runReferenceGc(false)`。
   - `resources.ts`：`handleResourcesDelete` / `handleResourcesClear` 删完记录后 `await runReferenceGc(false)`。
   - 统一入口：`orphanGc.ts` 新增 `runReferenceGc(dryRun)`，内部收集**resources 表 url + tasks 表 url + KV 全部 value** 后调 `runOrphanGc`，引用收集口径唯一（§3.5.3）。
2. **服务启动后**：`dryRun` 跑一次，打印统计（不删）。
3. **保留手动入口**：`POST /api/admin/cleanup` 继续可用（已改为复用 `runReferenceGc`），支持 `dryRun=1` 参数便于人工核查。
4. **可选定时兜底**：若担心删除入口之外的孤儿（如 `ci`/`hi` 落盘后画布节点删除、但从未经过删除接口），可加 `startGcSchedule()` 定时兜底；**首次上线前 N 次只 dry-run**，确认 `deleted` 不含仍被引用文件后，切到真实执行。

### 步骤 4：文件下载原子写（防半截文件）

现状（files.ts:117-134 `saveRemoteUrl`）：`existsSync` 幂等跳过已有 + `writeUploadBufferAt` 直接 `writeFileSync`（fileStore.ts:54-63）。

改进：落盘改为「写 `xxx.png.tmp` → `fs.renameSync` 到正式名」（对齐 `saveDb` 的原子写做法，database.ts:121-126）。这样即使进程在写盘中崩溃，正式文件名下永远是「完整文件或不存在」，GC 扫描时不会把半截文件当成合法文件保留，也不会让前端读到坏图。

### 步骤 5：dry-run 先验证再执行 + 回归测试

1. **验证流程**：
   - 备份 `localtool.db` 与 `uploads/`（可用现有 `/api/admin/export` + 文件拷贝）。
   - 调 `POST /api/admin/cleanup`（dryRun=1）→ 核对 `deletedFiles` 全部为「确认无引用」的文件。
   - 抽查几个被删文件是否在画布 KV / tasks / resources 中仍有引用（应无）。
   - 打开画布，确认此前 404 的两张图场景不再误删。
2. **回归测试**（localTool 测试目录）：
   - `deleteLocalFile` 移除后，任务/资源删除接口不再删盘（断言磁盘文件仍在）。
   - `runOrphanGc` 覆盖三种引用来源（KV / tasks / resources），构造「KV 引用但 tasks 无引用」用例，断言**不删**。
   - 自动 GC 调度函数可被 `unref`、不阻塞进程退出。

## 5. 解决的问题

1. **根治图片 404（问题2）**：任务中心「清空所有任务」不再误删画布 KV 仍在引用的文件，画布打开不再破图。
2. **统一文件生命周期决策权**：删除入口不再各自判断「能不能删」，删盘逻辑从 N 处收敛为 GC 一处，杜绝「一个入口漏查一类引用」这类 bug 复现。
3. **消除最危险的整目录删除**：`handleResourcesClear` 的 `rmSync(recursive)` 一刀切行为被摘除，文件夹删除也走引用感知，不会连带删掉画布引用。
4. **防半截文件污染**：原子写保证磁盘上不残留「写了一半」的文件，GC 与前端读到的都是完整文件。
5. **孤儿文件自动回收**：GC 自动化后，「删记录留下的磁盘文件」会在引用消失后的周期被回收，不无限膨胀（补全 docs/41 §2.7① 的配套闭环）。

## 6. 配套护栏与风险

| 风险 | 缓解 |
|---|---|
| GC 误删（引用收集漏项） | 默认 dry-run 上线；只删 uploads 目录内；`.thumbnails/` 永不删（可重新生成）；删前全库引用扫描 |
| 自动 GC 与用户操作竞态 | GC 用防抖/串行执行，避免与写库并发；可先只做「启动 + 手动」再逐步放开定时 |
| 摘除删盘后磁盘临时膨胀 | 说明这是正常状态：临时文件由 GC 在下个周期回收；可给 GC 配置阈值告警 |
| 引用格式不一（绝对 http URL vs 相对 /files/ 路径） | GC 内统一做「完整 URL → 相对路径」归一（orphanGc.ts 已实现 decodeURIComponent + 去前缀） |
| 旧版本库无 KV 引用迁移 | GC 扫描 KV 全部 value（含 canvas-state-*），不依赖特定 key 前缀，天然兼容 |
