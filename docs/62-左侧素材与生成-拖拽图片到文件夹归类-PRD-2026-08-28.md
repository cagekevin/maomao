## 1. 一句话目标

在左侧「素材」tab（`AssetLibrary.jsx`）和「生成」tab（`GeneratedView.jsx`）中，用户能通过**卡片上的「⋯」下拉菜单 → 「移动到文件夹」**，把文件物理移动到目标目录完成归类，完成后列表自动刷新。

## 2. 交互决策（2026-08-28 已定，采纳「按钮 → 下拉」方案）

> **结论**：**不做「拖拽到文件夹」**，改为**「⋯ 下拉菜单 → 移动到文件夹」**。
>
> 理由（用户决策留档）：移动/归类不是常见高频操作，拖拽交互成本高（要区分「拖到画布」与「拖到文件夹」两种语义，风险高）；而**现有的四个平铺操作按钮（打开目录 / 复制 / 重命名 / 删除）占满卡片**，正好可以收进一个「⋯」下拉，菜单里再加「移动到文件夹」一项，视觉更干净、入口统一。

### 2.1 采纳的 UI 形态

- **卡片右上角**：现有一排四个小按钮（打开目录 / 复制 / 重命名 / 删除）→ 收敛为**单个「⋯」图标按钮**。
- 点击「⋯」→ 弹出下拉菜单，包含：
  1. 打开所在目录
  2. 复制链接
  3. 重命名
  4. 移动到文件夹（**本次新增**）
  5. 删除
- 选择「移动到文件夹」→ 弹出**目标文件夹选择器**（当前目录下的文件夹列表 + 可新建文件夹）→ 确认后执行移动。

> 顶部「⋯」菜单（打开本地目录 / 新建文件夹）已存在，卡片右上角的「⋯」是**新加的另一个**，与顶部菜单互不冲突，注意不要共用同一个 `menuOpen` 状态。

## 4. 利弊分析（供决策留档）

### 采纳「⋯ 下拉」方案的优点

1. **交互简单可靠**：不做拖拽，天然避开「拖到画布 vs 拖到文件夹」两种拖拽语义冲突，风险最低。
2. **入口统一、视觉干净**：四个平铺小按钮收进 ⋯ 下拉，卡片不再被按钮挤满；菜单后续加新操作也容易扩展。
3. 移动是低频操作，放菜单层级合理，不占用高频操作的视觉位。
4. 后端 `move` + `rescan` 孤儿清理已就绪，**服务端零改动**，前端只做接线。

### 缺点 / 风险

1. **多一步点击**：相比拖拽，移动文件要「⋯ → 移动到文件夹 → 选目标」三步。因是低频操作可接受。
2. **移动是物理 `fs.renameSync`**：跨目录移动会改变 `id/url`（resources 记录由 rescan 重建）。若画布节点/任务引用了旧 URL，移动后引用失效（孤儿 GC 可能清理缩略图）。需在 toast 明确提示「已移动到 xxx」；是否深层引用处理不在本期范围。
3. 仅支持 `source='local-tool'` 的本地文件型资源；远程/收藏类资源不应进入移动逻辑（移动无意义或报错）。
4. 下拉菜单需与顶部「⋯」菜单状态区分，避免共用状态互相干扰。

## 5. 交互设计（两 tab 统一）

### 5.1 移动流程

1. 悬停任意**非文件夹**素材卡片 → 右上角出现「⋯」按钮。
2. 点击「⋯」→ 下拉菜单（打开所在目录 / 复制链接 / 重命名 / **移动到文件夹** / 删除）。
3. 选「移动到文件夹」→ 弹出**目标文件夹选择器**：
   - 列出当前所在目录下的**文件夹卡片**（可进入/多级选择）。
   - 提供「新建文件夹」入口（复用现有 `createFolder`）。
   - 底部确认/取消。
4. 确认 → `moveFile` → 成功 toast「已移动到「{文件夹名}」」→ `reset(true)` 刷新；失败 toast 报错。

### 5.2 边界处理

- 源为文件夹 → 不提供移动入口（或禁用）。
- 源非 `local-tool`（远程/收藏）→ 不提供移动入口。
- 目标文件夹与源文件同目录 → 忽略（可 toast 提示「已在目标目录」）。
- 目标文件夹选择器内不能选择文件，只能选文件夹。
- 移动失败 → 保持原状，toast 报错。

### 5.3 复用与抽离（两 tab 一致性保障）

- 两 tab 都要，建议把「卡片 ⋯ 下拉 + 移动到文件夹选择器 + 移动执行」抽成**共享组件/hook**（如 `AssetCardMenu` + `useMoveAssetToFolder`），两个组件共用，避免逻辑漂移。这符合仓库「唯一收敛点」的一贯原则。
- 若抽离成本过高，退而求其次：至少抽一个纯函数 `moveAssetToFolder(assetUrl, targetFolder)` 两处共用，UI 层各自实现但逻辑复用。

## 6. 改动点（两 tab 一起落地）

### 6.1 `localToolApi.js` 新增 move 封装

```js
// POST /api/files/move { src, dst } → { code:0, data:{ ok:true } }
export async function moveFile(src, dst) {
  return httpRequest(`${API_BASE}/api/files/move`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ src, dst }),
    retries: 0, // 移动是即时操作，不重试
    label: 'moveFile',
  })
}
```

> `src` / `dst` 为**磁盘绝对路径**。前端从素材项拿到的是 `url`（`http://127.0.0.1:18080/files/...`），需先转成磁盘路径。参考：`files.ts` `relativePathFromUrl`（去 `/files/` 前缀）只是相对路径；磁盘绝对路径 = `getUploadDir()` + 相对路径。前端侧需约定从 url 得到相对路径，再由后端 move 拼 uploadDir（或前端直接把相对路径传给后端，由后端统一拼根目录）。
>
> **执行时需确认**：`handleMove` 目前接收的是绝对路径（`body.src/dst`）。若前端拿不到 uploadDir 绝对路径，建议后端把 `handleMove` 改为「收相对路径 + 内部拼 `getUploadDir()`」，与 `mkdir`（收相对 `folder`）一致。这一处是**唯一可能需要的小后端改动**，落地时优先核实。

### 6.2 `AssetLibrary.jsx`（素材 tab）——核心逻辑

- **卡片按钮收敛**：`AssetLibrary.jsx` 现卡片右上角四个平铺按钮（`handleOpenFileDir` / `handleCopy` / `handleRename` / `handleDelete`，见文件 464-478 行）→ 收敛为单个「⋯」图标，点击弹出下拉（上述 5 项）。
- 新增「移动到文件夹」菜单项 + 目标文件夹选择器 UI。
- 新增 `moveItem(item, targetFolder)`：
  1. 解析 `item.url` → 相对路径（复用 `relativePathFromUrl`）。
  2. 由相对路径拼出 `src`（绝对）与目标 `dst`（绝对，`<targetFolder>/<basename>`）。
  3. 判边界（同目录 / 非 local-tool / 是文件夹 → return）。
  4. `await moveFile(src, dst)` → 成功则 `showToast` + `reset(true)`；失败 toast 报错。
- 顶部「⋯」菜单与卡片「⋯」菜单**用不同状态**（如 `menuOpen` 顶部 / `cardMenuId` 卡片）。

### 6.3 `GeneratedView.jsx`（生成 tab）——**同一套逻辑**

- 复用 6.2 相同的「⋯ 下拉 + 移动到文件夹 + `moveItem`」。
- 注意生成 tab 当前目录根是 `tasks`，文件夹进入路径前缀不同（`tasks/<name>` vs `migrated/<name>`），`dst` 拼接要按各自 `folder` 状态一致。
