## 一、架构总览（已确认）

```
用户输入 → AgentPanel → useAgentChat（多轮工具循环 ≤8 轮）
                       ├─ Demo 模式：demoPlan 本地规则引擎
                       └─ 真实 LLM：/api/proxy(多provider) 或 /api/agent/:id/chat(localTool→外部LLM)
                            ↓ 工具调用
                       useCanvasAgentTools（24 个工具）↔ ReactFlow 内存画布
                       └─ execute_plan → canvasPlanExecutor（多步编排出图）
状态：InputStateMachine(#7) + conversationStore(多对话隔离) + skillStore
```

链路贯通、职责清晰。后端 `handleAgentChat` 已在 `index.ts` 正确注册为 `POST /api/agent/:id/chat`，无路由缺口。

---

## 二、亮点（做得对）

- **工具层统一**：24 个画布工具集中注册、统一信封 `{ ok, data | error }`、写操作「不可变局部更新」（引用不变→不重渲染）。
- **AI 撤回与用户撤销隔离**：`aiUndoStack` 分组事务快照，`execute_plan` 一次编排整体入栈，`undo_ai` 可整体回退，不污染 Ctrl+Z。
- **并发双发防护**：`sendingRef` + `sendRef` 自调用处理 steer 队列，避免快速双击双发。
- **刷新恢复**：`pending` 机制在刷新后自动重发未完成任务。
- **准则注入单一来源**：前端 `useAgentChat` 注入，避免后方 `agentChat.ts` 在默认路径（走 proxy）下成死代码——`agentChat.ts` 注释已如实记录此次修正。
- **后端 SSE 鲁棒性**：gzip/deflate/br 自动解压、非 SSE 错误体包成 `data:` 行、超时覆盖整条透传、前端取消信号联动 abort。
- **异步安全·节点消失兜底重建**：`PromptNode.jsx` 的 `onRecover` 在异步完成广播时若原节点已消失则用结果重建（复用原 id），避免「任务中心有图、画布没图」错位。

## 三、发现的问题（按严重度）

### 🔴 高

**1. `present_plan` 三阶段「等待确认」态缺失（人机确认可被绕过）**
- 位置：`useAgentChat.js:616-621` + `useCanvasAgentTools.js:500-502`（`setPendingGenerations`）。
- 现象：阶段1 `present_plan` 把策划显示为一条 assistant 消息「确认后我会按此开始生成」，但**没有任何状态标记进入"等待确认"态**。阶段3 `execute_plan` 执行时（`useCanvasAgentTools.js:537-539`）只要 `getPendingGenerations()` 取到暂存 generations 就直接跑，`clearPendingGenerations()` 立即清空。
- 风险：用户尚未确认时，若 LLM 下一轮直接调 `execute_plan`（例如用户说「先不，改一下」后被模型误判），会**立刻真实出图**，违背"确认后执行"的人机对齐预期。`SKILL_EXECUTION_RULES`（`useAgentChat.js:114-118`）明确写了阶段2"停止工具调用、等确认"，但代码层**没有硬约束**——纯靠 LLM 自觉。
- 建议：在 `present_plan` 成功后由 `conversationStore`/状态机置 `awaitingConfirm:true`；`execute_plan` 入口校验该态，未确认则拒绝并提示「请先确认策划」；用户确认动作（前端按钮或"确认"语义消息）才翻转该态。

**2. 会话刷新/恢复后待确认态丢失**
- 位置：`useCanvasAgentTools.js:36` `pendingGenerations` 是**模块级变量**。
- 现象：`present_plan` 暂存的 generations 仅存在内存模块变量，不进 `conversationStore`/`skillStore` 持久化。刷新页面或跨窗口后该变量归零。
- 风险：用户看到策划→刷新→确认，此时 `execute_plan` 的 `getPendingGenerations()` 返回 null；若用户没在确认消息里重传 generations，执行会丢 generations 直接失败或退化为单步。且多对话隔离下模块级变量会**串话**（A 对话的 pending 被 B 对话的 execute_plan 误用）。
- 建议：把 `pendingGenerations` 移入 `conversationStore` 的 per-conversation 快照（随 `captureActiveConversation` 落盘），与 `setCurrentSnapshot` 走同一持久化通道；`useCanvasAgentTools` 改为从当前 conversation 读取。

### 🟠 中

**3. 视觉模型校验仅前端拦截，直连模式易绕过**
- 位置：`AgentPanel.jsx` 上传前校验 `VISION_MODELS`。
- 现象：图片上传在原型以 `dataURL` 直传（`blob→dataURL`），校验依赖前端模型列表。直连 OpenAI 兼容端点时若用户手填非视觉模型，前端校验可能因模型名不在内置 `VISION_MODELS` 而放行，把图喂给不支持视觉的模型导致静默降级。
- 建议：校验改为「不在视觉名单且不在 chat_models 视觉白名单推断」时统一拦截；或在 `roundTrip` 前加一次模型能力探测兜底。

**4. Demo 模式与真实链路工具集不完全对齐**
- 现象：`demoPlan()` 规则引擎只覆盖「创建/连接/删除/查看/适配」有限意图，且走的是固定映射，不经过 `execute_plan`/`present_plan` 三阶段。开发者在 Demo 下验证"Skill 批量生图"流程会**误以为通了**，实际上真实 LLM 路径才触发三阶段。
- 建议：文档或 Demo 入口明确标注「Skill 三阶段仅在真实 LLM 模式可见」；或在 Demo 中加入对 `present_plan`/`execute_plan` 关键词的最小映射以便联调。

**5. `undo_ai` 多步事务在多对话下快照可能错乱**
- 位置：`useCanvasAgentTools.js:110-124` 的 `aiUndoStack`（模块级 `MAX_AI_UNDO` 栈）。
- 现象：与 `pendingGenerations` 同类问题——`aiUndoStack` 是模块级，多对话切换时撤销目标会串。当前面板 UI 仅单面板，但 `conversationStore` 已支持多对话，隐患存在。
- 建议：将 `aiUndoStack` 也下沉到 per-conversation 状态，与 `conversationStore` 对齐。

### 🟡 低

**6. `execute_plan` 失败回滚不彻底**
- 现象：`canvasPlanExecutor` 在建节点/连线/触发生成的多步过程中，若中间某步失败（如节点未注册生成契约），已建的节点不会自动回滚，`undo_ai` 只能撤到整体入栈前——但部分成功节点已可见。
- 建议：对 `execute_plan` 增加「全有或全无」事务语义，或在文档明示「部分失败需用户手动 undo_ai」。

**7. 错误态 message 残留的边界小概率**
- 现象：`useAgentChat.js:642-646` 在 catch 中 `filter((m) => !m.streaming)` 清理流式占位（已核对代码，位置准确）；若 LLM 在最后一条 assistant 已 `streaming:false` 但内容为空时出错，会留下一条空 assistant 气泡。
- 建议：catch 清理时顺带剔除空内容 `assistant` 消息。
