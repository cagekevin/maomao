# AI 助手「工作流运行时」根本重构计划

> **目标**：从根上解决 08 地基 5 步审计暴露的散乱问题，**不靠打补丁**。
> **核心思想**：引入一个**统一的任务生命周期管理器（Workflow Runtime）**，让"任务如何开始/并行/停止/回滚/确认/归属"有唯一权威实现，各模块不再各自为政。
> **状态**：完整计划（含风险与回滚），**未实施**。确认后分步落地。
> **日期**：2026-08-16
> **关联**：`11-08地基五步落地审计`（问题清单）、`10-状态重构方案`（会话隔离，已 P0 完成）。

---

## 〇、为什么必须做根本重构（而不补丁）

### 现有 5 个问题，实为**同一根因**

| 问题 | 表面 | 本质 |
|------|------|------|
| `stop()` 不中断请求 | 只清 loading | **没有"可取消任务"的抽象** |
| Wave1 串行 | for 循环 await | **没有"并发执行器"基础设施** |
| aiUndoStack/pendingGenerations 模块级 | 全局变量 | **临时状态没有归属**（不绑定 conversation） |
| 三阶段无确认态 | 纯靠 LLM 自觉 | **工作流没有阶段状态机** |
| 事件系统空转 | 只监听未发布 | **没有统一的状态分发** |

**共同根因**：整个 AI 助手缺少一个**「统一的任务/工作流生命周期管理器」**。每个模块自己管自己的生命周期（loading boolean、模块级变量、手动 await），导致状态散落、语义不一致、无法协作。

**补丁 vs 根本**：
- 补丁 = 给 stop 加 AbortController、把 for 改 Promise.all、把变量下沉……每个都修一个点，但**没有统一抽象，下一处还会再犯**。
- 根本 = 引入 `workflowRuntime`，把"任务生命周期"这个**横切关注点**收拢成一份权威实现，所有模块复用。

### 借鉴大雄（已核实）
大雄的 `stopAgentWorkflow`（canvas-agent.js:7978）本质就是：
```js
agentActiveWorkflow.status='stopping';
await Promise.all(nodeIds.map(id => host.cancelNodeRun(id)));  // 真取消
agentActiveWorkflow.status='stopped';
```
它有一个**统一 workflow 对象**（含 status/nodeIds/steerQueue），stop 时遍历取消所有节点任务。这正是我们缺的。

## 一、根本方案：引入 `workflowRuntime.js`

### 1.1 它是什么

一个**纯逻辑、无 React 依赖**的运行时，管理"一个 AI 工作流"的完整生命周期。对齐大雄 `agentActiveWorkflow` 但更完整、可测试、可取消、可回滚。

```
┌────────────────────────────────────────────────────────┐
│  workflowRuntime.js（唯一权威：任务如何跑）              │
│                                                        │
│  Workflow = {                                          │
│    id, conversationId, status,                         │
│    nodeIds: [],       // 本次工作流建的节点             │
│    cancelTokens: [],  // 每个运行中任务的取消句柄        │
│    steerQueue: [],    // 补充指令队列                   │
│    awaitingConfirm,   // Skill 阶段2 确认态             │
│    aiUndoStack: [],   // AI 撤销栈（绑定本工作流）       │
│    logs: [],          // 执行日志                       │
│  }                                                    │
│                                                        │
│  API：                                                 │
│  - start(opts) → workflow                              │
│  - steer(text)   → 入队列（不打断）                     │
│  - cancel()      → 遍历 cancelTokens 真取消            │
│  - confirm()     → awaitingConfirm=false              │
│  - awaitNode(id, signal) → 真 await 拿结果，可取消      │
│  - runParallel(list, fn) → 并发执行（Promise.all）      │
│  - rollback()    → 清理本次建的节点                     │
│  - pushUndo/popUndo → AI 撤销栈（绑定本工作流）         │
└────────────────────────────────────────────────────────┘
```

### 1.2 它如何根本解决 5 个问题

| 问题 | workflowRuntime 的解法 |
|------|----------------------|
| stop 不中断 | `cancel()` 遍历 `cancelTokens` 真取消（对齐大雄 cancelNodeRun）；每个 `awaitNode` 接受 signal |
| Wave1 串行 | `runParallel(list, fn)` 用 `Promise.all` 并发 |
| 状态归属 | Workflow 对象绑定 `conversationId`，`aiUndoStack`/`pendingGenerations`/`awaitingConfirm` 挂到 Workflow 上，随 conversation 持久化 |
| 无确认态 | `awaitingConfirm` 字段，`execute_plan` 入口校验，`confirm()` 翻转 |
| 事件空转 | Workflow status 变化 → 通过 conversationStore 订阅广播（对齐 useSyncExternalStore） |

### 1.3 依赖关系（谁用谁）

```
useAgentChat ── 驱动 ──→ workflowRuntime（一次对话 = 一个 Workflow）
    │                      │  管理生成任务
    │                      ▼
useCanvasAgentTools ── 工具 ──→ runNodeGeneration（可取消）
    │  execute_plan/present_plan/undo_ai 都走 runtime
    ▼
canvasPlanExecutor ── 用 ──→ runtime.runParallel/awaitNode/rollback
    │
    ▼
useNodeGeneration ── 提供可取消的 start（AbortSignal）
```

## 二、关键设计决策（防踩坑）

### 2.1 可取消的底层：`useNodeGeneration.start` 接受 AbortSignal
- **现状**：`start()` 内部 `runRef.current()` 不接受 signal，`stop()` 只清 loading。
- **改法**：`useNodeGeneration` 的 `start` 内部持有 `abortControllerRef`；`stop()` 调 `abortControllerRef.current?.abort()`。`run` 执行器（各节点传入的 `generateImage`）需接受 AbortSignal（`imageApi` 已有部分支持）。
- **风险**：部分执行器（`generateImage`）可能未支持 signal → 需逐个确认，这是主要工作量。

### 2.2 Workflow 归属 conversation，持久化经 conversationStore
- Workflow 对象（含 aiUndoStack/awaitingConfirm/pendingGenerations）作为 conversation 的一个字段存。
- **不再有模块级 `aiUndoStack`/`pendingGenerations`**。
- conversationStore（已重构订阅式）自动落盘。

### 2.3 确认态：仅前端按钮翻转（沿用 10 方案 §2.4 结论）
- `awaitingConfirm=true` → `execute_plan` 拒绝（无论是否带 generations）。
- 仅 `confirm()` 按钮翻转。不做语义消息识别。

### 2.4 Wave 并行与依赖
- Wave1（独立批）→ `runParallel` 并发。
- Wave2（依赖批）→ 等 Wave1 全部成功后，`awaitNode` 逐个（依赖必须串行）。

## 三、风险与缓解

### 风险 1：可取消链路深，改动大（高）
`stop()` 要真中断，需要 `useNodeGeneration → run → generateImage → imageApi` 整条链路支持 AbortSignal。
- **缓解**：分两层。
  - L1（低风险）：`useNodeGeneration` 内部加 AbortController，`stop()` abort 内部请求；对**已支持 signal 的执行器**立即生效。
  - L2（后续）：逐个执行器补 signal。
- **回滚**：L1 不改执行器，只加 abort 逻辑，可单独回滚。

### 风险 2：Workflow Runtime 引入后，工具层契约变化（中）
`execute_plan`/`present_plan`/`undo_ai` 从"读模块级变量"改为"经 runtime 操作当前 workflow"。
- **缓解**：runtime 提供**与现有一致的 API**（`setPendingGenerations`→`runtime.setPending`，`aiUndoStack.push`→`runtime.pushUndo`），工具层内部改调用点，对外工具信封不变（LLM 无感知）。
- **回滚**：工具信封不变，回归面可控。

### 风险 3：并行执行与画布写冲突（中）
Wave1 并发 `addNodes`/`setNodes` 可能冲突（ReactFlow 批量更新）。
- **缓解**：`runParallel` 内部对画布写做**串行队列**（建节点串行，`await` 生成并行），即"建节点串行、跑图并行"。避免并发 setNodes 竞态。
- **验证**：`npm run test:smoke` + 真机批量出图。

### 风险 4：会话隔离 + 工作流状态（中）
多对话切换时，Workflow 要随 conversation 切换。
- **缓解**：Workflow 挂 conversation，`switchConversation` 时 runtime 重建为当前对话的 Workflow（conversationStore 已支持）。切换时 `cancel()` 旧对话仍在跑的任务？——**设计**：后台对话任务继续跑（引用独立 runtime 实例），切换只切"当前 UI 绑定的 Workflow 视图"。

### 风险 5：重构回归（整体）
- **缓解**：渐进式分步（见 §四），每步独立可验证、可回滚；`git` 每步提交 checkpoint。

## 四、分步实施（每步独立可验证 + 可回滚）

### Step 1：`useNodeGeneration` 支持可取消（解 stop 不中断）
- `start` 内部持 AbortController；`stop()` 调 `abort()`。
- 执行器 `run` 支持 signal 的立即生效；不支持的先不强行（记录待补清单）。
- **验证**：点停止 → 请求真中断。
- **风险**：低-中。
- **回滚**：单文件。

### Step 2：新建 `workflowRuntime.js`（纯逻辑，核心抽象）
- 定义 Workflow 对象 + API（start/cancel/awaitNode/runParallel/confirm/pushUndo）。
- **纯逻辑，不接 UI**，可单测。
- **验证**：单测（node 脚本）+ 不接入现有代码，零风险。
- **回滚**：删除文件即可。

### Step 3：接入 `execute_plan`/`present_plan`/`undo_ai`（状态归属）
- 把模块级 `pendingGenerations`/`aiUndoStack` 改为经 runtime（绑定 Workflow/conversation）。
- `execute_plan` 校验 `awaitingConfirm`。
- **验证**：Skill 三阶段走通；多对话撤销不串话；刷新不丢策划。
- **风险**：中。
- **回滚**：工具信封不变，可切回。

### Step 4：执行器并行化（Wave1 并发）
- `canvasPlanExecutor` Wave1 用 `runtime.runParallel`；Wave2 依赖批用 `awaitNode`。
- 建节点串行、跑图并行（见 §3 风险 3）。
- **验证**：批量出图效率提升 + 无画布竞态。
- **风险**：中。
- **回滚**：可切回串行。

### Step 5：确认态 + 事件广播（收尾）
- Workflow status 变化经 conversationStore 订阅广播；`awaitingConfirm` 前端按钮。
- **验证**：未确认不出图；UI 状态实时更新。
- **风险**：低。

## 五、验收标准

1. **stop 真中断**：点停止，网络请求 + 节点任务真正取消，不再后台跑。
2. **并行**：Wave1 独立批并行生成，明显提速；画布无竞态错乱。
3. **状态归属**：多对话切换，撤销栈/策划不串话；刷新不丢。
4. **确认态**：present_plan 后未确认，execute_plan 拒绝；刷新后仍待确认。
5. **可回滚**：每一步独立 checkpoint，出问题可回退到上一步。
6. **回归**：原有画布工具、生图、Skill 批量出图全部通过。

## 六、最终架构（目标态）

```
useAgentChat（对话引擎，复用）
   │
   ▼
workflowRuntime（唯一任务生命周期管理）  ← 新增核心
   │  start/cancel/awaitNode/runParallel/confirm/rollback/pushUndo
   │
   ├── conversationStore（Workflow 归属 + 持久化，已 P0 订阅化）
   ├── useCanvasAgentTools（工具层，经 runtime 操作）
   ├── canvasPlanExecutor（执行器，用 runtime 并行/依赖/回滚）
   └── useNodeGeneration（可取消底层）

所有状态收敛：Workflow 挂 conversation，conversationStore 单一数据源自动落盘。
不再有模块级 aiUndoStack/pendingGenerations。stop 真正可取消。执行可并行可回滚。
```

---

## 七、明确不做（避免过度设计）

- **不做完整事务 begin/commit/rollback**：`rollback()` 只清理"本次工作流建的节点"，不做全量画布快照回滚（快照回滚过度设计，且与用户 Ctrl+Z 冲突风险高）。
- **不做 host 画布适配层**（08 第6步长期重构，另立项目）。
- **不做事件系统重构**：Workflow status 变化用 conversationStore 订阅广播即可，不引入独立事件总线。
- **不重写 useAgentChat 核心循环**：08 文档明确"复用对话引擎"，runtime 是引擎的底层支撑，不推翻引擎。
