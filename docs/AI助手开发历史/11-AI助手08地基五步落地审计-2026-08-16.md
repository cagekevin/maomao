## 一、第 1 步 异步执行器（useNodeGeneration / taskStore.runNodeGeneration）

### 做对的
- `start()` 返回 `{ ok, resultUrl }`，生成完成即落盘 `uploads/tasks/`，url 稳定可复用（`useNodeGeneration.js:84-88`）。
- `trigger_generation` 改为 async，await 拿 resultUrl，供前序依赖/多图编排复用。
- 比大雄"轮询 output pending"更可靠（start 完成即知 url，无需额外轮询）。

### 问题
- 🟠 **`stop()` 不真正中断请求**（`useNodeGeneration.js:104`）：`stop = () => setLoading(false)`，只清 loading，**不 abort 网络请求**。文档注释自认"待接真引擎时用 AbortSignal 实现"。对 AI 编排影响：用户点停止后请求仍在跑，可能继续改画布/任务中心，**UI 状态与真实请求脱节**。
- 🟡 **并发防护靠 React state**（`:61 if (loading) return false`）：React state 异步更新，快速双击可能读到旧 `loading=false` → 并发双发。缺 ref 级同步锁（useAgentChat 的 `sendingRef` 已有此范式，此处未用）。

## 二、第 2 步 前序依赖 + generations 执行器（canvasPlanExecutor）

### 做对的
- Wave1（独立批）/ Wave2（依赖批）分批逻辑正确（`:73-74`）。
- 前序依赖用**连线**（`:163`），下游 `useConnectedInputs` 自动读前序图当参考图，无需注入 data.images——比大雄更简洁。
- `autoRun=false` 只建节点不跑（ready 态）。
- 参数优先级对齐大雄 resolveFinalGenParams（`:87` 每步字段 > 面板 defaults）。

### 问题
- 🟠 **失败回滚不彻底**（审计 09 §三.6）：Wave1 建了节点但某步失败，已建节点不自动回滚，用户要手动删/undo_ai。
- 🟡 **Wave1 串行非并行**（`:129-145`）：`for` 循环 `await runNode` 逐个跑，不是大雄的 `Promise.all`。独立批内部本可并行，串行拖慢整体生成时间。
- 🟡 **`waitForNodeReady` 5s 轮询**（`:105`）：依赖 React 渲染时序，超时可能误判失败。

## 三、第 3 步 分组事务 + 模型锁定（aiUndoStack / genParams）

### 做对的
- `aiUndoStack` 快照栈（上限 20 步），`execute_plan` 整体入栈，`undo_ai` 整体撤回（对齐大雄 beginTransaction/rollback）。
- 写工具统一 wrap（MUTATING_TOOLS），push 改前快照，集中一处。
- 生图参数区（模型/档位/比例）用 genParams，无数量（对齐 resolveFinalGenCount）。

### 问题
- 🟠 **aiUndoStack 模块级**（`useCanvasAgentTools.js:129`）：多对话切换时撤销目标会串（A 对话的操作被 B 对话撤销）。方案 P1 已规划下沉到 per-conversation。
- 🟡 **手动快照非真事务**：只存 nodes/edges 快照，没有 begin/commit/rollback 语义。部分失败时快照栈状态复杂，不如大雄的 transaction 整体回滚清晰。

## 六、两个贯穿性架构问题（最重要）

### 1. 「状态与真实请求脱节」
多处的 UI/状态机 status 与实际网络请求不同步：
- `stop()` 不 abort 请求 → status 置 idle，但请求仍在跑（第1步）。
- 状态机 status 是"声明"，但真实生成进度靠回调回填，二者可能短暂不一致。

**影响**：用户点停止/重试时，底层行为与界面显示脱节，AI 编排时尤其明显。

**建议**：stop 需真正 AbortController 中断；状态机 status 与请求生命周期用 ref 同步（对齐 useAgentChat 的 sendingRef）。

### 2. 「模块级可变状态跨会话串话」
- `aiUndoStack`（第3步）、`pendingGenerations`（第4步）、`genParams`（模型锁定）都是模块级。
- 多对话隔离下，这些全局可变状态会跨会话串话。

**影响**：A 对话的撤销栈/策划被 B 对话误用。

**建议**：方案 P1 已规划下沉到 per-conversation（conversationStore 已具备承载能力）。

## 八、修复优先级建议（按「必修/可修/不修」）

**🟠 可修（架构完整性，建议推进）**
1. `stop()` 真中断（AbortController）——解"状态与请求脱节"。
2. Wave1 真并行（Promise.all）——提升生成效率。
3. aiUndoStack / pendingGenerations 下沉 per-conversation——解跨会话串话（方案 P1）。
4. Skill 三阶段确认态（awaitingConfirm）——解未确认出图（方案 P2）。

**🟡 低优先 / 可不修**
5. 并发 ref 锁（useNodeGeneration）——边缘，可后置。
6. 事件系统真正用起来——预留即可，非硬伤。
7. Skill 完整编辑——08 自认未做，可后补。

**⚪ 不修**
8. 手动快照 vs 真事务——当前够用，过度设计。

> 注：以上优先级遵循既定「必修排前、可修排后、一次就懂的不做」原则。必修项（数据丢失/产品逻辑缺陷）已在 P0/P2 覆盖；本审计列出的多为「可修」的架构完善项。
