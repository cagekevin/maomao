# lovart 原生直连接入设计（relay 摆脱 9004 翻译层）

> 状态：设计（方向已确认：relay 的 lovart 直连 Lovart 原生 agent 协议，不再依赖 9004 的 /v1 OpenAI 兼容翻译层）。
> 依据：`.codebuddy/skills/lovart/agent_skill.py`（真源协议）+ `apimart-gateway/lovart_client.py`。
> 本文把原生协议契约、与 ai-relay 引擎模型的差异、接入形态落成蓝图；**不改代码**，供施工前对齐。

---

## 0. 结论

Lovart 原生协议是 **chat-thread 型**（chat→thread_id→confirm(可选)→result.items[].artifacts[].content），
**不是** ai-relay 现成的「submit 拿 task_id → 轮询 statusPath → result.urlPath」二态模型。要直连，需在
ai-relay 抽象出**第三种执行形态（agent-thread）**，或为 lovart 单独建一个直连客户端接入 relay，二者择一。

## 1. Lovart 原生协议契约（来自 agent_skill.py）

### 1.1 鉴权（HMAC-SHA256，非 Bearer）
Header：
```
X-Access-Key: <AK>
X-Timestamp:  <unix秒>
X-Signature:  hmac_sha256(secret, "{METHOD}\n{path}\n{ts}").hexdigest()
X-Signed-Method: METHOD
X-Signed-Path: path
Content-Type: application/json
User-Agent: LovartAgentSkill/1.0   (附 Referer: https://www.lovart.ai/ 下载时)
```
base = `https://lgw.lovart.ai`（LOVART_BASE_URL），path 前缀 `/v1/openapi`。

### 1.2 端点
| 动作 | 请求 | 返回 |
|---|---|---|
| 提交 | `POST {prefix}/chat` body `{prompt, project_id, attachments?, thread_id?, mode?, tool_config:{prefer_tool_categories?, include_tools?, exclude_tools?}}` | `thread_id` |
| 状态 | `GET {prefix}/chat/status?thread_id=` | 状态（running/done/abort/pending_confirmation/...） |
| 结果 | `GET {prefix}/chat/result?thread_id=` | `{ items:[{type, text?|artifacts:[{type,content}]}] }` |
| 确认 | `POST {prefix}/chat/confirm` body `{thread_id}` | 确认高成本操作（video fast） |
| 上传 | `POST {prefix}/file/upload`（multipart） | `data.url` |
| 模式 | `POST {prefix}/mode/set|query` | — |

信封：响应顶层 `{code, message, data}`；`code==0` 成功，取 `data`。

### 1.3 状态机（final_status）
`done`（取 result） / `pending_confirmation`（先 confirm 再取） / `abort` / `timeout` / `running`。
高成本操作（如视频）在 fast 模式可能进 `pending_confirmation` → 需 confirm，然后继续轮询。

### 1.4 提交语义（关键差异）
- body **没有 model/size 字段**——模型靠 prompt 自然语言 + `tool_config.prefer_tool_categories`（如 `{"IMAGE":["generate_image_gpt_image_2"]}`），尺寸靠 prompt（target_size 文本）或网关侧归一。
- 产物是**多类型列表** `items[].artifacts[]`（可能图片+视频+文本回复混排），非单个 url。

## 2. 与 ai-relay 现有引擎模型的差异（为什么不能直接套）

ai-relay `ModelProtocol`（sync/async 二态）：
- async = `submit(拿 taskIdPath) → poll(statusPath/successValues/result.urlPath)` → 单组 url/text。
- 引擎假定「提交响应含可轮询 task_id」且「终态轮询同一 URL 得结果」。

Lovart 原生：
- 提交是 **chat**，拿的是 **thread_id**（多轮会话句柄，非一次性任务）；
- 有 **confirm** 前置门（pending_confirmation）——ai-relay 无此概念；
- 结果在 **result** 端点（与 status 不同端点），且是**多类型 artifacts 列表**；
- 状态 done 后可能需「等子 agent 起跑再复核」（agent_skill 的 5s 复核），防 video 子任务误判 done。

→ 直接硬塞进现有 `ModelProtocol` 的 statusPath/result.urlPath 会失真（无法表达 confirm / 多 artifacts / chat 多轮）。

## 3. 接入形态二选一（需确认）

### 方案 A：ai-relay 抽象第三种协议形态 `mode:'agent-thread'`
在 `ModelProtocol`/engine 增加 `mode:'agent-thread'`：`submit→thread_id`、可选 `confirmGate`、
`pollStatus(endpoint=status)`、`pollResult(endpoint=result)`、结果抽取 = 遍历 `items[].artifacts[]` 取 url/text。
- 优点：进统一引擎，后续其他 chat-thread 型平台可复用；与 docs/91「加平台=加协议数据」一致。
- 代价：改 kit 引擎（增形态、状态机含 pending_confirmation）、preset 声明扩展。

### 方案 B：relay 侧独立 lovart 直连客户端（不进 kit 声明式引擎）
在 `relay.ts`/`relay-poll.ts` 旁新增 `lovartDirect.ts`（自实现 HMAC + /chat + poll/confirm/result），
走统一 `/api/generate`(后端驱动) 语义但内部直连 Lovart。
- 优点：不碰 kit 引擎，落地快、风险隔离。
- 代价：绕开 kit（违反 docs/91 C0「协议执行不绕 kit」红线）；自写 HMAC/状态机。

> 建议：**优先方案 A**（守 C0 + 可复用）；若工期紧可先 B 后 A。需你拍板。

## 4. key 来源
直连原生需 `LOVART_ACCESS_KEY` + `LOVART_SECRET_KEY`（现仅存于 `apimart-gateway/.env`）。
localTool 侧需把这对 AK/SK 读入（新增 `LOVART_ACCESS_KEY`/`LOVART_SECRET_KEY` 到 localTool .env 或读取网关 .env），
供 HMAC 签名。key 仍只驻内存/进程内，不入库。

## 5. 落点草案（方案 A）
- `ai-relay/types.ts`：`ModelProtocol` mode 增 `'agent-thread'`；新增 `ModelAgentThreadConfig`（submit/confirm/status/result 路径 + artifacts 抽取）。
- `ai-relay/protocol/engine.ts`：`executeModelProtocol` 分支处理 agent-thread。
- `ai-relay/protocol/poll.ts`：支持「status→(confirm?)→result」两段轮询 + `items[].artifacts[]` 归一到 `urls/text`。
- `ai-relay/protocol/presets.ts`：`lovart-agent` preset（chat-thread + HMAC auth + default project）。
- `relay.ts`/`relay-poll.ts`：image/video/chat 经统一 `/api/generate`（后端驱动）改走 lovart-agent。
- `providerConfig`：lovart 平台补 HMAC AK/SK 读取（.env）。

## 6. 风险与红线
- **HMAC 签名**（方法/路径/时间戳）每平台不同，需独立实现，勿当 Bearer 套。
- **project_id**：Lovart 提交需 project_id（工作区）；relay 需维护/注入一个默认 project_id（agent_skill 用本地 state 持久，relay 需服务端持有）。
- **pending_confirmation**：video fast 可能触发；relay 后端 pollWorker 需 auto-confirm 或透传待确认态给前端（参考 9004 的 AUTO_CONFIRM 取舍）。
- **多 artifacts**：一次可能产出多图/图文混排；`result_url` 落库需取主产物，或前端多产物语义需另行（当前节点单 url 模型）。
- **能力零退化**：9004 层现有的 auto_confirm/尺寸归一/参考图透传在直连后要么由 relay 复刻，要么显式放弃；不得静默丢。
