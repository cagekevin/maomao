### 核心诊断：为什么"数据流契约不放心"

AI 助手存在**两套状态系统并存**：

- **持久层（干净）**：`conversationState.js` 已是 `states[agentKey]` 单一数据源 + `useSyncExternalStore` 订阅 + 自动落盘，`normalizeConversation` 已把 messages/skills/attachments/workflow/pending/memory/runMode/undoStack/pendingGenerations/awaitingConfirm/referenceImages 全部归一。**这一层契约是干净的。**
- **运行时层（混乱）**：`useAgentChat` 的 `messages`/`sending`/`error`/`model`/`stateAction`/`activeConversationId`/`conversations` + refs 全是 hook 内状态。**其中 `messages` 与持久层的 `conv.messages` 双源**，靠 finally 手动 `setCurrentSnapshot` 同步——不同步就漂移，中断/切页就丢。

**收口方向**：把运行时层也收敛到 `conversationState`（它已是单源+订阅+落盘），删掉 hook 里的 `messages` useState/ref 双源，让整个 AI 助手只剩一个状态源。

## 1. 目标形态

```
┌─────────────────────────────────────────────────────────────┐
│ 唯一状态源：conversationState.js（states[agentKey]）          │
│   · 会话数据：messages/skills/attachments/workflow/pending/  │
│     memory/runMode/undoStack/awaitingConfirm/refImages       │
│   · useSyncExternalStore 订阅 + 自动落盘 + per-agentKey 隔离  │
│                                                             │
│  useConversationStore()  ──订阅──►  useAgentChat（纯薄壳）    │
│                                     · 只读状态（不再 useState）│
│                                     · 转发动作（send/stop/..）│
│                                     · 编排循环（依赖 callTool）│
│                                                │            │
│  AgentPanel ◄──订阅──┘                          │调用        │
│     · 只渲染 UI                               agentRuntime   │
└─────────────────────────────────────────────────────────────┘
```

### 核心原则

1. **唯一状态源** = `conversationState.js`。`useAgentChat` 不再用 `useState`/`useRef` 持有 messages/conversations/activeId 等（会话数据在 store）；**仅保留纯展示/瞬时态**（error/model/stateAction/sending）在 hook 内——它们不进持久层，且由 Step 3 的 CSS 隐藏保证组件不卸载时自然存活。
2. **messages 单源**：删掉 hook 里 `messages` useState + `messagesRef`，直接读写 `conversationState.conv.messages`（经 `setCurrentSnapshot`/`getCurrentSnapshot`）。**彻底消灭双源。**
3. **切页不中断**：移除卸载 cleanup 的 `abortRef.current?.abort()`；`AgentPanel` 改 CSS 隐藏不卸载。
4. **不新增独立 agentSessionStore**（docs/22 的 M1 方案作废）——因为 `conversationState` 已经是单源+订阅+落盘，再建一个 store 反而制造第三套状态。**收敛进既有单源，而非叠新层。**

### Step 1：useAgentChat 的 `messages` 单源化（消灭双源，核心）

> 目标：hook 不再自持 `messages` useState + `messagesRef`，改为订阅/读写 `conversationState.conv.messages`。

> ⚠️ **交接必读（重要修正）**：原文档曾断言"finally 那处 `setCurrentSnapshot({messages})` 可删除"。**此断言错误。** 实测 `useAgentChat` 内 `setCurrentSnapshot({ messages })` 共 **8 处**（`:453/:573/:682/:710/:736/:744/:752/:766`），它们不只是"落盘"：
> - **携带多字段语义**：多数同时写 `skills`/`draft`/`attachments`；`:710`（clear）还清空 `workflow/pending/memory/pendingGenerations/awaitingConfirm`；`:744`（switchChat）依赖切换前暂存。
> - **因此"每次 append 已落盘"不能替代这 8 处**——它们承担的是"会话切换/清空/终态"时的**完整快照语义**，不是"落盘增量"。
>
> **正确做法**：保留这 8 处 `setCurrentSnapshot` 调用（及其多字段语义）**原样不动**，只把它们的 `messagesRef.current` 替换为"store 当前 messages"（见下"同步读法"）。**不要删除任何一处。** 若删除，会破坏 skills/draft 同步或 clear/switchChat 语义。

- [ ] **读**：删除 `const [messages, setMessages] = useState([])` 与 `messagesRef`（含 255 行的 `useEffect(() => { messagesRef.current = messages })` 同步）。
- [ ] **写辅助改走 store（只改这 5 个消息动作）**：`appendMsg`/`setHistory`/`updateLastStreaming`/`endStreaming`/`stripStreaming` 不再 `setMessages`/`messagesRef.current = ...`，改为 `setCurrentSnapshot({ messages: next })`（只传 messages，不动其他字段）。**这 5 个是"消息内容变化"的唯一入口，与上述 8 处"会话生命周期快照"职责不同，不得混删。**
  - ⚠️ **高频增量风险（交接必读，最容易做错）**：`updateLastStreaming`（流式增量）/`endStreaming`（收尾）在**热路径**（每 50ms 节流 flush 一次增量，见 docs/12 §6.1）。若直接改为 `setCurrentSnapshot`（内部 `commit` → 全量 notify 所有订阅者 + 节流落盘），会**每 50ms 触发一次全量订阅通知**——这正是 docs/12 明确记载的"每片 setState 导致大回复卡死"历史 bug 的翻版。
  - **正确做法（二选一，必须选一个并写测试）**：
    - **方案 ①（推荐）**：`updateLastStreaming`/`endStreaming` 走 store 内一个**轻量更新函数**（如 `patchCurrentMessages(messages)`），它**只更新消息数组并 notify，但跳过或极低频落盘**（流式中间态不该落盘，docs/12 §5.1 明确"流进行中不落盘"）。新增该函数到 `conversationState.js` 或 `conversationSnapshot.js`。
    - **方案 ②**：保留高频增量在 send 作用域内的本地引用，**循环末尾统一 flush 一次**到 store（避免每片 commit）。
  - **无论选哪种**：`appendMsg`/`setHistory`/`stripStreaming`（低频，非流式热路径）可安全用 `setCurrentSnapshot`；但**流式热路径（updateLastStreaming/endStreaming）不得用全量 commit**。这是整个 Step 1 风险最高处，必须用测试锁定（模拟 50ms 高频增量，断言订阅通知次数不爆炸 / 落盘不产生中间态）。
- [ ] **同步读法（关键取舍）**：send/sendImageMode 循环内所有 `messagesRef.current`（同步读最新消息）改为读 store 当前 messages。**推荐用 `getCurrentSnapshot().messages`**（conversationSnapshot.js:18 返回浅拷贝，同步可读）。⚠️ 注意性能与引用：`getCurrentSnapshot()` **每次返回新数组**，若在热点循环（多轮工具 + 每轮 append）高频调用会有拷贝开销；必要时改为"在 store 内提供返回内部引用的同步读函数（如 `getActiveMessagesRef()`）"或"在 send 作用域内缓存一份本地引用、循环末尾统一 flush 到 store"。**文档不强制具体实现，但必须保证：① 读与写都指向同一份 store 状态；② 不得重新引入第二份可变数组。**
- [ ] **暴露给 UI**：`useAgentChat` 返回值 `messages` 改为订阅 `useConversationStore()` 的结果，从中取当前对话消息。⚠️ **注意**：`useConversationStore()` 返回的是整个 `states[agentKey]`，结构为 **`{ conversations: [], activeId: '' }`**（conversationState.js:77-79），**没有 `currentConv` 字段**。取当前消息需执行者自己推导：`const store = useConversationStore(); const cur = store.conversations.find(c => c.id === store.activeId); return cur?.messages ?? []`（或用 `getActiveConv()`/`getCurrentSnapshot()` 辅助）。文档不强制实现方式，但**必须保证返回的是 store 单一来源的消息数组**（不再用本地 useState）。
- **验证**：`useAgentChat.hook.test.js` 全绿（需同步改断言：由"内部 state"改为"store 状态"）；新增用例：append 后 `getCurrentSnapshot().messages` 同步增长；`grep -c "messagesRef" useAgentChat.js` = 0；**回归确认 `switchChat`/`clear`/`newChat` 的多字段快照语义不变**（`useAgentChat.hook.test.js` 的"多对话隔离"用例覆盖）。

## 3. 风险清单与规避

| 风险 | 规避 |
|---|---|
| **messages 双源改动破坏落盘**（历史 bug：AI 回复丢失） | Step 0 先建 conversationState.test 安全网；每步跑 `useAgentChat.hook.test.js` 回归；messages 读写严格收敛到 `setCurrentSnapshot` |
