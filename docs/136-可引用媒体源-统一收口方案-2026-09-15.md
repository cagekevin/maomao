## 三 · Step 2 归因 —— 孤例还是母体？

**结论：这是一个母体的正面建设，不是修一堆症状。**

母体表述：

> **M4 · 「可引用内容」没有统一视图** ——
> 每个消费方各自去"能拿到的地方"捞数据，导致：
> ① 谁能被引用，取决于**消费方碰巧能访问什么**（剪辑器碰不到 `nodes` 就完全引用不了画布）；
> ② 同一个来源被 N 个消费方各映射一遍（将来 `@素材库` 就是第 2 份）；
> ③ 新增来源要改 N 个消费方。

**判据（某修复能同时消灭 ≥3 个问题 → 母体）**：
- 症状 1：剪辑器看不到素材库 ✅
- 症状 2：剪辑器看不到画布（且**结构上不可能**） ✅
- 症状 3：未来的 `@提及` 需重写同一套映射 ✅
- 症状 4：未来「3D 定妆照 / 剧本资产」等新来源需改 N 处 ✅

**M4 与既有三大母体的关系**：M4 属 **M3（SSOT 第二份）** 的一个新切面 ——
"有哪些可引用内容"这条真相，目前被**每个消费方各持一份**。

## 五 · Step 4 定契 —— 正确性与失败语义

### 5.1 统一形状 `MediaRef`

```ts
/** 一条「可引用媒体」——所有来源归一后的唯一形状。 */
export interface MediaRef {
  /** 全局唯一标识：`${source}:${id}`。用于去重 / React key / 芯片序列化。 */
  ref: string;
  /** 来源标识（决定它从哪来，消费方一般不需要关心） */
  source: MediaRefSource;
  /** 显示名（用户看到的） */
  name: string;
  /** 媒体类型 */
  type: MediaRefType;
  /** 可渲染地址（**已归一为绝对 URL**，可直接给 <img>/<video>） */
  url: string;
  /** 缩略图（可选；消费方缺省回退 url） */
  thumbnailUrl?: string;
  /**
   * 稳定内容身份（文件型才有）。
   * 用途：导入剪辑器时**避免重复上传**（与后端 resources.sha1 同源）。
   * ⚠️ 剪辑器 `addMediaAsset` 目前**无条件重传**，本字段是将来修那处的依据。
   */
  contentId?: string;
  /** 归属项目（legacy 无归属 = 全项目可见，沿用 resourcesOfProject 语义） */
  projectId?: string;
  /** 来源私有附加信息（尺寸/时长/目录等）。**不进核心契约**，消费方不该依赖。 */
  meta?: Record<string, unknown>;
}

export type MediaRefType = 'image' | 'video' | 'audio';

/** 来源枚举 —— 新增来源只在这里加一项 + 注册一个 provider。 */
export type MediaRefSource = 'canvas' | 'library';
```

**三条契约铁律**：

1. **`url` 恒为绝对 URL**（provider 内已过 `toAbsoluteFileUrl`）。
   理由：消费方可能是非 React / 非画布环境（剪辑器在 `ve-scope` 里），不该各自补前缀。
2. **`ref` 前缀是跨模块契约**（同 `SHOT_HANDLE_PREFIX` 的量级）。
   消费方**禁止**自己拼 `${source}:${id}` —— 必须用 `makeMediaRef()` / `parseMediaRef()`（成对提供）。
   理由：与 `contracts.ts` 里 `shotHandleId`/`parseShotHandle` 同一个教训 —— 写侧改前缀而读侧没改，
   **失败是静默的**。
3. **`meta` 是出口，不是契约**。消费方依赖 `meta` 里的字段 = 自建第二份耦合。

### 5.2 注册表契约

```ts
/** 查询条件（各 provider 按需消费，不必全用）。 */
export interface MediaRefQuery {
  /** 项目 id（素材库按项目隔离用） */
  projectId?: string;
  /** 关键词（按 name 模糊匹配；空则不过滤） */
  keyword?: string;
  /** 只要这些类型 */
  types?: MediaRefType[];
}

/** 一个来源：能列出条目。**异步**（素材库要请求后端）。 */
export interface MediaRefProvider {
  source: MediaRefSource;
  /** Tab 显示名（消费方直接用，不自己写映射） */
  label: string;
  /**
   * 列出条目。
   * 契约：
   *  - 必须**自己处理失败**：失败时抛错（不返回空数组冒充"没有"）。
   *  - 返回的 `url` 必须已是绝对 URL。
   *  - 必须已按 query 过滤（本层不做二次过滤）。
   */
  list: (query?: MediaRefQuery) => Promise<MediaRef[]>;
}
```

**对外 5 个函数**：

```ts
registerMediaRefSource(p: MediaRefProvider): void      // 唯一写入口
listMediaRefSources(): MediaRefProvider[]               // 消费方生成 Tab 用
hasMediaRefSource(source): boolean
queryMediaRefs(source, query?): Promise<MediaRef[]>     // 单来源（Tab 切换用）
searchMediaRefs(keyword, query?): Promise<MediaRef[]>   // 跨来源（@提及用）
```

### 5.3 失败语义（诚实契约）

| 场景 | 现在的设计 | 为什么 |
| --- | --- | --- |
| **未注册的来源被 query** | **抛错**（fail-fast） | 静默返回 `[]` 会把"代码写错了"伪装成"这个来源是空的"（同 `contentStore.checkRegistered` 的哲学） |
| **重复注册同一 source** | **抛错** | 两个 provider 抢同一个 `source` = 第二份真相，必然漂移 |
| **provider.list 内部失败** | **原样上抛**，由消费方处理 | 消费方可能是"Tab 里显示错误态"（持续状态）或"toast"（瞬时），**本层不该替它决定**。这与 `media.tsx:376` 已有的 `PanelState tone="error"` 错误态一致 |
| **provider 返回了非绝对 URL** | dev 下 `logger.warn`（不抛） | 属 provider 实现瑕疵，不该炸掉整个面板；但必须留痕 |
| **`searchMediaRefs` 某个来源失败** | **部分成功语义**：返回成功的 + 记录失败的 | 这是唯一允许"降级"的地方：跨来源搜索里，一个来源挂了不该让整个 `@` 框不可用。**但必须把失败暴露在返回值里**（见下） |

```ts
export interface MediaRefSearchResult {
  items: MediaRef[];
  /** 失败的来源与原因（消费方可显示"素材库暂时不可用"） */
  failures: Array<{ source: MediaRefSource; message: string }>;
}
```

> **为什么 `searchMediaRefs` 单独一个返回形状**：它是**唯一**跨来源的操作，
> 而跨来源必然面对"部分失败"。把它塞进 `MediaRef[]` 就会掩盖失败（= 静默吞）。
> 这是 §五禁令「禁静默吞」与本层"诚实契约"的落点。
> **注意**：`queryMediaRefs`（单来源）**不加**这个信封 —— 单来源失败了就该抛，
> 包一层 `{items, failures}` 反而让消费方多写一次判空（形态要匹配语义，不是统一就好）。

### 5.4 画布 bridge 契约

```ts
setCanvasNodesSnapshot(nodes: Node[]): void    // App 调用（唯一写入口）
getCanvasNodesSnapshot(): Node[]               // 非 React 读
subscribeCanvasNodes(fn: () => void): () => void  // React 订阅式读
```

**语义约束（写进文件头）**：

- 它是**投影**，不是状态。真源**永远是** `App` 的 `nodes`。
- **单向**：只有 App 写，其他模块只读。禁止任何模块拿它当"能改画布"的通道。
- **不做持久化**（同 `editorSession.ts`：不 import `contentStore`/`localStorage`），
  并**照 `editorSession.test.ts:64` 的先例加源码级断言**锁死这一点。
- **引用相等优先**：`setCanvasNodesSnapshot` 收到同一引用时**不通知**
  （`nodes` 每次 `setNodes` 都是新数组，但 effect 里可能拿到相同引用；防无谓重渲染）。

### 5.5 两个内置 provider

**`providers/canvasSource.ts`**（`source='canvas'`）

- 输入：`getCanvasNodesSnapshot()`
- 映射：**复用 `getNodeMedia(node)`** 取 `{type, url}`，**复用 `resolveAssetDisplayUrl`** 解析
  `contentId → resource.url`（三形态互斥一次收口）
- `ref` = `canvas:${node.id}`
- `name` = `data.label ?? data.name ?? '节点'`
- `contentId` = `data.contentId`
- **过滤**：`type` 为空（`''`）的节点**不收录**（= 该节点没有媒体）

> ⚠️ **一处必须注意的实现细节**：`getNodeMedia`（`nodeMedia.ts:49`）**只返回主媒体一个 URL**。
> 而 `imageBoxNode` 可能有**多张图**（`data.images[]`）。
> **本轮裁决**：**沿用 `getNodeMedia` 语义（只取主媒体）**，因为
> ① 它与 AgentPanel 待发送区**口径一致**（用户不会困惑"为什么两边数量不同"）；
> ② 展开多图是**行为扩展**（Step 5 业务决策），不该在收口层擅自决定。
> **登记为后续可选扩展**：若将来要展开，应在 `nodeMedia.ts` 加 `getNodeMediaList(node): MediaRefItem[]`
> （**扩展真源，而不是在 provider 里旁路一份**）。

**`providers/librarySource.ts`**（`source='library'`）

- 输入：`fetchResources({ projectId })`（后端真相）
- 映射：`ResourceItem → MediaRef`，**复用 `detectAssetType`** 判型
- `ref` = `library:${item.id}`
- `url` = `toAbsoluteFileUrl(item.url)`
- `contentId` = `item.contentId`
- **过滤**：`type` 为 `text` / 未知的**不收录**（剪辑器只吃图/视频/音频）

> ⚠️ **分页问题（必须诚实面对）**：`fetchResources` 是**分页**接口。
> 本轮实现**取第一页（页大小由 provider 内部常量定，如 100）**，并在 `meta` 里带
> `{ page, pageSize, hasMore }`。
> **不实现**无限滚动/全量拉取 —— 那是 UI 层的事（消费方拿 `hasMore` 决定要不要"加载更多"）。
> **登记为约束**：若消费方需要全量，应加一个 `fetchAllResources` **在 provider 内循环拉取**，
> 而不是让每个消费方自己写分页循环。

## 九 · 消费侧设计（剪辑器怎么"引用"）—— **本轮只设计，不施工**

> 用户要求："到时候那个视频编辑器里面怎么引用，你也先想好。"
> 本节是**消费侧契约**，与 §一–§七 的**地基**分开：地基不依赖本节，本节依赖地基。

### 9.1 先取证：剪辑器的"引用"到底受什么约束？

**三个硬事实（全部读到源码确认）**：

| # | 事实 | 出处 | 后果 |
| --- | --- | --- | --- |
| **F1** | 拖拽载荷只带 `mediaId` | `types/drag.ts:6-9` `MediaDragData { id, type:'media', mediaType }` | 时间轴**不认识 URL** |
| **F2** | 时间轴按 `mediaId` 去工程素材里查 | `media.tsx:149` `createElementFromMedia({asset:...})` → `buildVideoElement({mediaId})` | **素材必须在 `editor.media.getAssets()` 里** |
| **F3** | 拖入源判断只看 `dataTransfer.types` 有无内部 MIME | `drag-data.ts:69` `hasDragData` | 不能"外部 URL 直接拖上轨" |

**结论（这是本节最重要的一句）**：

> **剪辑器的"引用"不可能绕过"先落成工程素材"这一步。**
> 外部 URL 必须先经 `addMediaAsset()` 落盘 + 登记元数据，才能被拖上时间轴。
> 所以"引用画布/素材库的图" = **导入**，不是"链接"。

这与参考项目 `AI-Canvas-tauri` 的 `@{}` 芯片**本质不同**：
它的引用是**文本芯片**（生成时由 `nodeReferenceService` 反解成 URL 塞给 AI），
剪辑器的引用是**二进制素材**（要真的进视频）。**两者不该共用一套语义。**

### 9.2 关键裁决（2026-09-15 与用户确认）：**引用，不复制；只删引用，不删实体**

> **用户原话**："那如果让编辑器只删，不删那个实体文件不就好了吗？那不就更干净吗？"
> **用户确认**："我们的 resource 本来就是不会被删除的，除非用户哪天自己想去删它而已。"
>
> **本节是 §9 的定论**，取代此前"复制进工程"的设计。

#### 先看现在的语义是"混"的

| 层 | 真相 | `deleteMediaAsset` 现在干什么 | 应不应该 |
| --- | --- | --- | --- |
| 磁盘实体 | `uploads/` 里的文件 | 不直接删（后端 `delete-file` 只删无引用文件） | ✅ 正确 |
| **resources 表行** | 文件的**全局登记** | **删**（`:511-541` `releaseResourceRefs`） | ❌ **越界** |
| 工程元数据 | `mediaMetadataAdapter` 那行 | 删 | ✅ 正确（这是剪辑器自己的） |
| 工程素材数组 | `editor.media.getAssets()` | 删 | ✅ 正确（这是剪辑器自己的） |

**病灶在第二行**：resources 行是**全库共享的"这个文件存在过"的登记**，
素材库面板（`ResourceLibrary`）正在读它。剪辑器删一个"指向它的引用"，
**凭什么把别人的登记也删掉？** —— 这是**归属越界**。

#### 裁决

> **剪辑器只删自己那两行（工程元数据 + 工程素材数组），不碰 resources 行、不碰磁盘文件。**

推论（三条，同时成立）：

| # | 推论 | 说明 |
| --- | --- | --- |
| **A1** | **素材直接引用原 URL，不复制二进制** | 消费者持**引用态**（轻量、随本源持久共享），不为自保持副本（铁律 7：副本自保 = 越权防御）→ **磁盘不再翻倍** |
| **A2** | **R3（重复上传）问题直接消失** | ✅ **见 §十 P0-2 的修正**：不用改**上传逻辑**（该路径不再需要上传），但 `saveMediaAsset` **必须新增"已有 url"分支**（否则纯引用走不通 —— 它会去上传一个不存在的 `File`） |
| **A3** | **删掉 `releaseResourceRefs` 对剪辑器素材的调用** | **职责本分**（心法铁律 7）：消费者删除 = 只删自己的引用态；上游的登记行（resources）与磁盘实体**不归消费者管** |

**A3 的依据（用户裁定 2026-09-15）**：素材库是**本源（所有方）**，剪辑器只是消费者。
消费者删素材时越界去删 resources 行（`releaseResourceRefs`），就是"消费者管到上一层"——
不管上游 GC 怎么裁决磁盘，都与消费者无关。删掉它不是"回归纪律"，是**职责归位**。

> ⚠️ **一个必须同时处理的隐患**：`releaseResourceRefs` 被 `deleteProjectMedia`（`:560`）也调用。
> 删**整个工程**时同样不该动 resource 行（用户没说"销毁这些素材"）。
> 故两处一起改，**不留一半**（留一半 = "删单个素材不删库、删整个工程却删库"的语义分裂）。

#### 代价（唯一一条，必须说清）

素材库会**保留**剪辑器用过的素材（哪怕已无人引用）。

**判断：这不是脏数据，这是正确行为。**
- 用户在剪辑器里用过的图**本来就是素材**（从画布/素材库来的）；删片子不该把原始素材也删掉；
- 真正的清理归**引用感知 GC**（"全库无引用才回收"才是正确判据）；
- 素材库面板本身有**删除**按钮 —— 用户想清就显式删（正是用户说的"除非自己想去删"）。

> **一句话**：**"剪辑器删素材" = 从我的工程里移除它，不是"销毁这个文件"。**
> 这两件事本来就该分开，是先前的实现把它们混在了一起。

#### 关于"源被删 → 素材失效"（用户裁定：正常结果，非缺陷）

**源文件被用户显式删除 → 工程里的素材失效 —— 这是消费上游数据的理所当然**，不是要防的场景（铁律 7）。

现状（`service.ts:434-435`）：

```ts
if (!metadata.url) return null;
...
const res = await fetch(metadata.url);
if (!res.ok) return null;      // ← 静默 return null
```

`loadMediaAsset` 拉不回时**静默 `return null`** → `loadAllMediaAssets` 把它**直接跳过** →
用户看到的是**素材凭空消失**（零提示），这与 `media.tsx:376` 已有的 `PanelState tone="error"` 错误态**不一致**。

**说明**：失效本身**不防御、不补偿**（铁律 7）。唯一遗留的是**展示诚实性**：
`loadMediaAsset` 静默 `return null` → 素材凭空消失（零提示）。这由**既有 TD-22-43② 原则**覆盖
（"加载失败要给面板错误态，不静默消失"——该债早已确立，非本轮新增）。
实现 3-a 时顺手对齐该原则即可，**不立新债、不设"必做"**。

### 9.3 消费侧接口设计：**"引用 → 工程素材"的唯一适配器**

按 §9.2 的裁决，"引用"**不再需要上传/下载** —— 素材已在 `/files/`，
只需在**当前剪辑工程**里登记一条指向它的元数据。
按本仓惯例（唯一入口），应在**剪辑器改造区**新增一个适配器（不在地基里 —— 它依赖引擎）：

```
videoEditor/ui/editor/panels/assets/linkMediaRefs.ts   （新建，下一轮）
```

```ts
/**
 * 把一批 MediaRef 登记为「当前剪辑工程的素材」（唯一入口）。
 *
 * 【语义】登记引用，**不复制文件、不上传**（§9.2 裁决）——
 * 素材二进制已在 /files/，这里只写工程侧元数据 + 内存态。
 */
export async function linkMediaRefsToProject({
  items, projectId,
}: { items: MediaRef[]; projectId: string }): Promise<LinkMediaRefsOutcome>;

export type LinkMediaRefsOutcome = {
  ok: true;
  linked: MediaAsset[];   // 已登记（可直接拖上时间轴）
  skipped: MediaRef[];    // 已存在（按 contentId/url 去重），无需重复登记
} | {
  ok: false;
  linked: MediaAsset[];   // 部分成功（部分成功不丢）
  failures: Array<{ ref: string; message: string }>;
};
```

**三个设计点**：

1. **动词是"登记引用"（link），不是"导入"（import）** —— 命名即契约。
   叫 `import` 会让人以为在复制文件，而复制正是 §9.2 刚刚裁决要**避免**的。
2. **仍需 `File` 对象怎么办？** `MediaAsset` 类型要求 `file: File`（`types/assets.ts:31-34`），
   而 `MediaRef` 只有 URL。
   **取 File 的方式**：`await fetch(ref.url).then(r => r.blob())` 再 `new File(...)`
   —— 这是**同源请求**（`/files/` 就是 localTool），无 CORS 问题。
   **但它只是为了让类型满足**，**不上传、不落盘**。
   > ⚠️ 值得注意：这里存在一次性全部 fetch 的内存压力（大视频）。
   > **优化方向（下一轮按需）**：给 `MediaAsset.file` 改成**惰性取**，或让工程素材
   > 支持"无 file、只有 url"的形态。**本轮不改引擎**，先用 fetch 满足类型。
3. **去重判据 = 双轨**（⚠️ **见 §十 P0-3 的修正**）：
   - `contentId` **两者都有**时 → 按它去重（都是 `sha1:<hex>`）；
   - 否则按 **归一化后的 `url`** 去重。
   > **`contentId` 缺失是常态**（`useAssetDropPaste.ts:224` 只在非 dataURL 时才算；
   > `ImageGenerate` 产出写 `data.assetUrl` 但未必有 `contentId`）→
   > **不能只按 `contentId` 去重**，否则多数情况静默重复登记。
   > **`url` 归一化必须做**：画布侧可能是 `http://127.0.0.1:18080/files/a.png`，
   > 素材库侧是 `/files/a.png` —— 不归一化就是两个字符串，去重失效。

**为什么返回"部分成功"而不是首错即抛**：
用户多选 10 张图，其中 1 张挂了 —— 另外 9 张应该**照常进工程并可见**。
「整体失败」会让用户重来一遍。这与 §5.3 `searchMediaRefs` 的**部分失败**同族。

**为什么放在剪辑器而不是 `base/media/`**：
它依赖 `editor.media`（引擎）→ 属**业务适配**，不是地基能力。
放进 `base/media/` 会让地基反向依赖 `videoEditor`（**违反 `check-arch` 规则 2**）。
> 这是本节最容易摆错的一处，**必须记住**：**地基只回答"有什么"，不回答"怎么用"。**

### 9.4 UI 设计：三来源 Tab（**结构照搬现有，不新造卡片组件**）

**落地位置**：`ui/editor/panels/assets/views/media.tsx`（改造，不是新建面板）

**方案：在现有「素材」面板内部加一排来源切换**（不是加 `TabBar` 图标）

理由（三条）：
1. **用户心智是"找素材"一件事**，不是"三个面板"。切 Tab 图标会让"工程素材"和"画布素材"看起来是两个功能；
2. `TabBar`（`tabbar.tsx:79`）的图标列**已有一层渐隐 + 滚动**，再加图标会挤压；
3. 参考文献 `MentionPicker` 用的就是**面板内 tabs**（`MentionPicker.tsx:80-96`）。

**结构**：

```
┌ 素材 ────────────────────── [排序] [切视图] [导入] ┐
│  [本工程] [画布] [素材库]        ← 新增一行来源切换  │
├─────────────────────────────────────────────────┤
│  <GridView />  ← 完全复用现有卡片网格与 DraggableItem │
└─────────────────────────────────────────────────┘
```

**三个来源的语义**（关键：**"本工程"不是 `MediaRefSource`**）：

| Tab | 数据来源 | 说明 |
| --- | --- | --- |
| **本工程** | `editor.media.getAssets()`（**既有，不动**） | 已是 `MediaAsset`，可直接拖拽 |
| **画布** | `queryMediaRefs('canvas', { projectId })` | 点击 → `linkMediaRefsToProject` 登记引用 |
| **素材库** | `queryMediaRefs('library', { projectId })` | 同上 |

> ⚠️ **"本工程"刻意不做成 provider**：它的返回值是 `MediaAsset[]`（含 `File` 对象），
> 而 `MediaRef` 是**轻量投影**（无二进制）。
> 硬塞进 provider 会逼着 `MediaRef` 带上 `File` → 破坏"轻量"契约。
> **这是"判据重复 ≠ 探测重复"的又一实例**（7 步法 Step 3）：两者**看似同一件事**（列出素材），
> 但**层级不同**（一个是引擎内存态，一个是外部只读视图）。**不可合并。**

**交互（关键决策：点击行为）**：

| 动作 | 行为 | 为什么 |
| --- | --- | --- |
| 单击卡片 | **选中/预览**（与"本工程"一致） | 三来源**交互同构**，用户不用重新学 |
| 悬停「+」 | **登记引用 → 直接上时间轴**（`onAddToTimeline`） | 复用现有 `DraggableItem` 的加号语义 |
| 拖拽 | **仅"本工程"可拖** | 见下方 |

**拖拽的时序约束（必须设计清楚，否则会出 bug）**：

现有拖拽是**同步** `setDragData`（`draggable-item.tsx:89-100`：`onDragStart` 里同步写 `dataTransfer`）；
而 `linkMediaRefsToProject` 是**异步**的（要 fetch 取 File）。
若在 `onDragStart` 里 `await` → 拖拽手势会被浏览器取消。

**设计**：**"拖拽"只对"本工程"启用**；画布/素材库来源的卡片**先登记再拖**：
- 卡片显示「+」按钮 → 点击 = `linkMediaRefsToProject` + **立即上轨**（等同登记后自动加）；
- 登记完成后该卡片**自动切到"本工程"Tab 并高亮**（复用已有的 `requestRevealMedia` /
  `useRevealItem`，`assets-panel-store.tsx:104-105` + `use-reveal-item`），用户接着拖就是本工程素材。
- **不实现**"跨 Tab 拖拽"（异步登记 + 拖拽手势的时序在浏览器里不可靠）。

> 这个裁决可能让用户觉得"少了点顺滑"，但**它换来的是"不会静默失败"**。
> 若用户实测后要求"拖拽直上"，再评估用 `DataTransfer` 的 `setData` 延迟填充方案 ——
> **登记为待用户实测反馈项**。

### 🔴 P0-2 · `saveMediaAsset` 用 `uploadFileToLocal` 处理 **URL 源** —— 纯引用后**根本不该走它**

**取证**：`service.ts:386-393`，第 4 参 `canvasProjectId ?? undefined`；函数体 `filesApi.ts:340`。

`uploadFileToLocal(file, subfolder, name, projectId)` 的签名是 **File 源**。
纯引用方案下，`linkMediaRefsToProject` 拿到的素材**已在 `/files/`**，
**不需要上传** —— 但 `saveMediaAsset` 这条路径**只有"上传"一个分支**（除 `ephemeral`）。

**两条路**：
- **A（推荐）**：新增"**已有 url**"分支 —— `saveMediaAsset` 接受 `{ url }` 时跳过上传，
  直接写 `MediaAssetData.url`。**但要小心**：`mediaAsset.file.size`（`:409-410`）
  在"只有 url"时从哪来？→ 需从 `fetch` 回的 blob 拿，或标 `0`。
- **B**：`linkMediaRefsToProject` 不调 `saveMediaAsset`，**自己写** `mediaMetadataAdapter`
  → **违反唯一入口**（存储写入旁路），**不可取**。

**结论**：**必须走 A**（改引擎，`saveMediaAsset` 加一个显式的"已落盘"入参）。
**这修正了 §9.2 推论 A2 的说法** —— A2 说"R3 问题直接消失、不用改原语"，
**只说对了一半**：不用改**上传逻辑**，但**必须加一条分支**让 URL 源绕过上传。
否则纯引用根本走不通（会去上传一个不存在的 `File`）。

### 🔴 P0-3 · `contentId` 在**导入侧拿不到**（画布图往往没有）

**取证**：
- `MediaRef.contentId` 来源：画布侧 `data.contentId`（`AssetNode.tsx:82` 从 `getResources()` 反查）；
- 但**画布上很多图没有 `contentId`** —— `useAssetDropPaste.ts:224` 只在"非 dataURL"时才算；
  `ImageGenerate` 的产出写 `data.assetUrl`，**未必有 `contentId`**；
- `MediaRef` 的 `contentId` 是**可选**的，`undefined` 是常态。

**后果**：**§9.3 说的"按 `contentId` 去重"在多数情况下失效** → 同一张图从画布和素材库各导入一次，
**会登记两条**（`contentId` 都是 `undefined`，去重判据落空）。

**必须的处置**：去重判据必须是**双轨**：
1. `contentId` 相同 → 去重（两者都有时）；
2. 否则**按归一化后的 `url`** 去重（`/files/xxx` 相对路径，**去掉 `API_BASE` 前缀与 query**）。

> **这修正了 §9.3 设计点 3 的说法**（原写"`contentId` 优先，`url` 兜底"是对的，
> 但**没说清 `contentId` 缺失是常态**，容易被实现成"只按 contentId"→ 静默重复登记）。
> 且 url 去重**必须归一化**：画布侧可能是 `http://127.0.0.1:18080/files/a.png`，
> 素材库侧是 `/files/a.png` —— 不归一化就是两个不同字符串，去重失效。

`:178` `item.file.size`）→ **改类型波及面大**，需单独评估。

### 🟠 P1-2 · 画布 bridge 是"全量节点数组"→ 每帧复制，性能红线

**取证**：`App.tsx:415-422` 现有 `nodesRef` 用 `useEffect` 同步（**引用赋值，零成本**）。
若 `setCanvasNodesSnapshot(nodes)` 也**存引用**，那没问题；
但 `canvasSource` 每次 `list()` 都**遍历全部节点**（`nodes.map(...)`）。

**后果**：
- 画布 1000+ 节点时，每次切到"画布"Tab 都全量遍历 + 全量 `resolveAssetDisplayUrl`；
- 若 bridge 在 `nodes` 每次变化都通知订阅者 → 拖动节点时**每帧通知**（`editorSession.ts` 同族风险）。

**处置**：
1. bridge 必须**引用相等短路**（§5.4 已写：同引用不通知）——**这条是性能红线，不是优化**；
2. `canvasSource.list()` 应**只遍历一次**并把结果缓存到"签名"（复用 `nodeMedia.ts:127`
   `selectedAssetSig` 的**同款思路**：签名不含坐标 → 拖动不算变化）；
3. **不得**在 bridge 里做映射（bridge 只存引用；映射留给 provider，按需调用）。

### 🟠 P1-3 · `searchMediaRefs` 跨来源关键词搜索 = **N 个来源都拉全量**

**取证**：`librarySource` 只取第一页（§5.5）；`canvasSource` 全量但本地。
关键词过滤在**客户端**做（`MediaRefQuery.keyword`）。

**后果**：用户输入 `@猫` → 素材库只搜到**第一页 100 条**里的猫，
第 2 页的猫**搜不到** → 用户报"我的图明明在库里，为什么搜不到"。

**处置（必须诚实标注）**：
- 素材库有 `keyword` 参数吗？需查 `fetchResources` 是否支持 —— **若不支持**，
  则 `@` 搜索**只能搜到已加载的部分**，**必须在 UI 上诚实体现**（如"仅搜索了最近 100 条"）；
- 或：`librarySource` 支持"搜索时全量拉取"（分页循环），**但要有上限与进度**。
> **禁止**：假装搜了全部（静默不完整 = 最坏的失败形态）。

### 🟡 P2-1 · "本工程"Tab 与"画布/素材库"Tab 的素材**可能重复显示同一张图**

### 🟡 P2-2 · 多窗口同开画布时，bridge 只反映**本窗口**的 nodes

**后果**：多窗口场景下，剪辑器"画布"Tab 可能显示**过期**的节点列表。

**但要在 `canvasNodesBridge.ts` 文件头写明**，免得后人当 bug 修。

**处置**：本轮**不改**（改名有存量 URL 破链风险，`uploadDirs.ts:7-8` 明令"一律不改名"）。
**但要在注释里补充说明**（它是"剪辑器直接拖入的素材"，不是"剪辑器引用的素材"）。
