## 一、生成节点「真相源契约」合规审计

### 1.1 范围与方法
- grep `useNodeGeneration` 命中 11 个文件，其中**直接声明 config 的生成节点 4 处**（4 个运行时/蓝本），其余为驱动层（`NodeShell` / `useCanvasAgentTools` / `canvasPlanExecutor` / `taskStore` / `eventBus` / `contracts`），不声明 config。
- `ImageNode` 等其余节点**未调用** `useNodeGeneration`，属"上传/编辑/素材"类，不纳入生成契约（但其字段命名见 1.3）。

### 1.2 合规判定表

| 节点 | onSuccess 写回 data | 结果字段 | onRecover | 合规 | 备注（行号） |
|---|---|---|---|---|---|
| **TextNode** | 是（`data.text`） | `text` | 否（契约③文本例外，正确） | ✅ | `onSuccess` L181–221 走 `setTextPersist`+`patchData({text})`；结果本体在 `data.text`，刷新随画布快照恢复 |
| **PromptNode** | 是 | `imageUrl` | 是（含"节点消失重建"兜底） | ✅ | `onSuccess` L205–221；`onRecover` L224–247；另 L132–148 挂载时 `fetchTasks` 存量回填。契约样板 |
| **DiscountVideoNode** | 是 | `videoUrl` | 是 | ✅ | `onSuccess` L169–177（本次已补 `patchData({videoUrl})`）；`onRecover` L180–183 |
| **TemplateNode**（蓝本） | 是 | `imageUrl` | 是 | ✅ | L211–214 / L219–222。未注册进 `nodeTypes`，但作为"新建节点权威蓝本"，其写法即规范基线 |
| **ImageNode** | N/A | `imageUrl`+`url` | N/A | ⚪ 非生成节点 | 无 `useNodeGeneration`，结果来自上传/编辑 |

### 1.3 结果字段命名
- 生成节点命名**一致无混乱**：生图 `imageUrl`、视频 `videoUrl`、文本 `data.text`（例外条款）。
- **唯一冗余**：`ImageNode` 内部同时存 `data.imageUrl` 与 `data.url` 双字段（L39/L70/L108/L113/L150），`getNodeImageUrl` 已做兼容（L201–217）。建议后续收敛为单一 `imageUrl`。

### 1.4 需注意的"准缺口"（非硬违反）
1. **Template/DiscountVideo 的 `onRecover` 缺"节点消失重建"兜底**：PromptNode 在节点被删时会 `addNodes` 重建，另两者只做 `set+patchData`，异步任务完成时原节点已删会静默丢结果。属样板间行为不一致，建议统一。
2. **ImageNode 双字段冗余**（见 1.3）。

> **结论**：已落地生成节点全部合规。剩余项均为样板间兜底差异与历史双字段，**不构成契约违反，但应纳入自查清单**。

## 二、数据一致性路径梳理（画布 ↔ 任务中心 ↔ 磁盘）

### 2.1 三条落盘 / 恢复路径（各管什么）

| 路径 | 链路 | 管什么 | 真相级别 |
|---|---|---|---|
| **A. 任务中心落盘** | `taskStore.js` → `POST /api/tasks/save` → 18080 SQLite（`localtool.db`，`tasks` 表） | 任务记录、`resultUrl`、状态机、`poll_task_id` | 结果**权威源** |
| **B. 文本落盘** | `TextNode.saveTextToTasks` → `POST /api/files/upload` → `uploads/tasks/*.txt` | 文本结果文件（供"生成"面板扫描收录） | 文件级，与 A 独立 |
| **C. 画布落盘** | `App.jsx` 600ms 防抖 autoSave → `saveCanvasState` → 18080 KV（`canvas-state-v1-{projectId}`） | `node.data` 副本（含 `imageUrl`/`videoUrl`/`text`）、节点拓扑 | 渲染**缓存副本** |

### 2.2 刷新时序仲裁现状（谁覆盖谁）
- 刷新两条恢复链并发：① 画布快照先恢复旧 `node.data` 副本渲染（路径 C）；② 任务中心 `initTasks` + 延迟 500ms `initTaskRecovery` 轮询 → `publish('agent:task-completed')` → `useNodeGeneration` 订阅回写 `onRecover`（路径 A）。
- **仲裁结果**：任务中心回填晚到、用新持久 `resultUrl` **覆盖**画布旧副本 → 正确。文本节点无 `onRecover`，完全依赖 `data.text` 随画布快照恢复。
- `canvasLoaded` 门控确保首帧 KV 读回不被立即 autoSave 覆盖。

### 2.3 localTool 未连时的降级
- 任务中心：`persist` 失败仅 warn、不阻断；`initTasks` 加载失败静默（任务列表空）。**未连时结果只落内存 + `node.data` 副本，不写 `/api/tasks`、不落 `uploads/tasks/`**。
- 画布：KV 不可用 → `storageSet` 降级 localStorage 并标 `degraded`。
- 文本：`saveTextToTasks` 同依赖 localTool，未连仅 warning，但 `data.text` 仍在画布内存快照。

### 2.4 潜在不一致风险清单（带文件:行号）

| # | 风险 | 位置 | 严重度 |
|---|---|---|---|
| 1 | 离线态结果只存 `node.data`，重连后不补登任务中心（内存任务记录刷新即清，无重放日志） | `taskStore.js:47,51-53`；`kvStore.js:42-50` | P1 |
| 2 | 文本结果纯靠 600ms autoSave 窗口，窗口内刷新即丢 | `useNodeGeneration.js:33-35`；`TextNode.jsx:218-219`；`App.jsx:281` | P1 |
| 3 | sync 生图无 `pollTaskId`、无 `agent:task-completed` 广播，刷新恢复全靠 `data.imageUrl` 副本；若副本是外链/临时地址则丢图 | `pollTask.js:13-14`；`taskStore.js:205-208` | P1 |
| 4 | 多端/多窗口：画布 KV 有 `_version` 冲突保护但只"拒绝覆盖"，两窗口各自看到旧/新；`BroadcastChannel` 只广播事件不传数据 | `projectStore.js:152-163`；`App.jsx:263-266` | P2 |
| 5 | `blob:`/`data:` 地址永不落盘，两端都丢 | `filesApi.js:133`；`taskStore.js:199` | P1 |
| 6 | 节点被删后 PromptNode 重建"孤儿节点"（位置写死、无撤销栈） | `PromptNode.jsx:227-243` | P2 |
| 7 | KV 降级 localStorage 后，重连不会回灌 KV，双源分裂 | `kvStore.js:42-50` | P2 |

### 2.5 架构师建议方向（不改代码）
1. 确立"任务中心/磁盘为真相源，画布 `data` 仅作缓存"；刷新后**以任务中心回填为权威**，画布旧副本只占位不回写。
2. 离线补登队列：localTool 未连期间把写操作记入内存 pending + 持久化 localStorage，重连后幂等重放（`saveTask` 已是 upsert）。
3. 文本纳入回填链路（带 `text` 或 `resultUrl` 指向 txt），与图/视频同权。
4. 多窗口协同：BroadcastChannel 携带增量或触发对方 reload；冲突用"最后写入者胜出 + 版本号"而非静默丢弃。
5. 把"结果 URL 归一化为稳定 `127.0.0.1:18080/files/...`"前移到生成成功那一刻（`useNodeGeneration` 已做），从根消除错位。
6. 降级层提供 `flushDegraded()` 回灌 KV。

## 三、节点组件单一职责分析

### 3.1 范式对照
理想范式：节点只声明 `useNodeGeneration` 的 `validate/run/onSuccess/onRecover` + 渲染 UI；生成、进度、恢复、落盘、偏好、供应商样板全收敛进 hook。
**实测：17 个节点里仅 4 个接入 `useNodeGeneration`，13 个绕开自写生成逻辑。**

### 3.2 已接 hook 节点的职责混淆
- **每个节点重复写同构 `onSuccess`/`onRecover`/`patchData` 样板**（PromptNode L205–221、DiscountVideoNode L169–177、TemplateNode L211–214 等）。
- **`patchData` 逐字相同实现 4+ 处**（DiscountVideoNode:65–70、PromptNode:95–97、TemplateNode:126–128、TextNode:68）→ 应下沉为共享 `useNodeData(id)`。
- **结果落盘重复（最严重）**：`useNodeGeneration.js:114-118` 已统一 `saveResultToTasks`；但 `PromptNode.jsx:211-218` 又重复调一次，且 L132–148 挂载时再 `fetchTasks` 主动拉——三处做同一件事，双落盘有竞态。
- **供应商加载 + 默认模型 effect 跨节点重复 3+ 处**（DiscountVideoNode:130–144、PromptNode:165–179、TemplateNode:189–192）。
- **防抖写回 `debouncedPatch` 同款 3 处** → 随 `patchData` 下沉。

### 3.3 越界职责（应属画布/任务中心）
- `PromptNode.onRecover` 内 `addNodes` 重建自身（L224–247）：节点在恢复回调里直接读写画布，属编排职责。
- 13 个未接 hook 节点自写 `reportGenerate`/`taskCtl`/retry 散落各组件（典型 `VideoProcessNode.jsx:357-977` 整段手写）。
- `VideoExtractNode` **未写回 `node.data`，刷新即丢结果**，违反真相源契约。

### 3.4 "声明式 config 范式"目标形态
```jsx
function XxxNode({ id, data }) {
  const { patchData } = useNodeData(id)        // 共享 hook 一次拿到，消除 4+ 处拷贝
  const { loading, error, start, stop } = useNodeGeneration({
    nodeId: id, type: { type: 'image', prompt, modelName },
    resultKey: 'imageUrl',                     // ← 新增：hook 自动 patchData({[resultKey]: r.url})
    validate: () => (prompt.trim() ? '' : '请输入提示词'),
    run: async ({ progress, signal }) => generateXxx(...),
    onSuccess: (r) => setImageUrl(r.url),       // 只更新 UI state，落盘+写 data 交给 hook
    recoverable: true,                          // hook 自动订阅广播回填 resultKey
  })
}
```
hook 侧应补强：`resultKey` 自动写回 + 自动落盘 + 自动回填；`patchData`/`debouncedPatch`/供应商 effect 抽到 `useNodeData`；"节点消失重建"移出节点下沉到恢复层。

### 3.5 老节点回改优先级
| 节点 | 优先级 | 理由 |
|---|---|---|
| PromptNode | P0 | 重复落盘 + 重复拉取 + 越界 addNodes |
| VideoExtractNode | P0 | 未接 hook、未写回 data、刷新丢结果 |
| ImageNode / VideoProcessNode / GridSplit / Loop 等 13 个 | P1 | 整体未接入统一契约，工作量最大收益最高 |
| DiscountVideoNode / TemplateNode / TextNode | P2 | 已接 hook，只消除样板 + `resultKey` 自动回填，改动小 |

> **回改策略**：先改 hook（加 `resultKey` + 抽 `useNodeData`）→ 回改 P0 两个验证 → 批量收口 P1。**切勿先改节点、hook 没跟上导致二次返工。**

## 四、localTool 网关职责边界

### 4.1 关键澄清：两个进程不要混淆
| 进程 | 端口 | 真实职责 |
|---|---|---|
| **localTool**（TS，`localTool/src/`） | **18080** | 代理转发 + 文件落盘 + 任务中心落库 + KV/资源/项目。**唯一出口网关** |
| **apimart-gateway**（Python，`apimart-gateway/`） | **9004** | **纯中转站**：把图片/视频/聊天翻译成 Lovart 协议转发，**不落盘、不存任务中心** |

"既代理又落盘又任务中心"的是 **18080**，不是 9004。9004 的文件 `main.py:8-11` 自声明纯中转站；其 `TaskManager` 是进程内存字典，重启即丢，不进任务中心 UI。

### 4.2 18080 三层职责（路由表 `router.ts:116-207`）
- **A. 代理转发**：`/api/proxy`、`/api/v1/gateway/task/{id}`（转 9004 + 协议翻译）、catch-all 透传官方。
- **B. 文件落盘**：`/api/files/upload` → `~/.maomao-localtool/uploads/`；`/files/*` 静态读。
- **C. 任务中心**：`/api/tasks/*` → SQLite `localtool.db` 的 `tasks` 表；含引用感知 GC。

### 4.3 任务中心数据存哪 / 落盘谁负责
- **任务中心真源 = 18080 SQLite**；前端 `taskStore.tasks` 仅是易失 UI 缓存，每次增删改 fire-and-forget 调 `/api/tasks/*`，刷新靠 `initTasks()` + `pollTask.js` 恢复。
- **落盘 100% 由 18080 负责**：前端 `filesApi.saveResultToTasks` → `POST /api/files/upload`，无前端直写磁盘。

### 4.4 越界风险检查结论
- ✅ **前端所有写操作都经 `API_BASE`（18080 `/api/*`）**，无任何 `fetch`/`fs` 直写 `127.0.0.1:18080/files/` 的越界（grep 命中的明文地址全是常量定义/注释/只读 URL）。
- ⚠️ catch-all 透传是"最大职责面"（设计目标，但建议建"本地化接管清单"逐步缩小）。
- ⚠️ `/files/*` 仅只读静态出口，无鉴权，上云需补访问控制。

### 4.5 边界红线建议（固化进 spec/）
1. 前端所有写必须经 `API_BASE`（`/api/*`），禁止直接 `fs`/`fetch` 写本地盘。
2. `/files/*` 仅只读静态出口；任何写必须走 `/api/files/upload`。
3. 文档/架构图明确分层 9004（无状态中继）vs 18080（本地唯一出口网关）。
4. 建立 catch-all 本地化接管清单，定期 review `[passthrough]` 日志缩小透传面。
5. 前端 `taskStore.tasks` 只作缓存，勿直接改又不调 `persist()`（当前已守）。

## 六、给架构师的一句话
你已把最痛的"真相源"钉住；但**一致性**和**单一职责**是两条不同战线——一致性靠"规则 + 自查清单 + 红线"（纪律问题，写进 CONTEXT 即防），单一职责靠"结构收敛 + 新节点样板"（演进问题，靠冻结老节点、规范新节点，不靠一次大改）。**最危险的误区是想一次性把 13 个老节点重构成纯声明式**——那会触发你 CLAUDE.md 自写的"改节点跑 regression"风险，且非当下急需。顶级做法是：冻结老节点、规范新节点、文档锁红线。
