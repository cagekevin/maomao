## 一、官方账号数据结构（对照/校验）

### 为什么做
本项目 `accountsStore` 的环境对象必须与官方字段一致，否则激活/cookie 同步可能漏字段。

### 官方代码
`Zr.jsx` L2171-2178：
```js
let e = {
  id: Date.now().toString(),
  name: i,            // 环境名
  siteName: t,        // 站点名（'手动添加' / tab title 前5字）
  siteUrl: a,         // 站点 URL
  avatar: o,          // 头像
  cookies: s          // cookie 数组
};
```
Cookie 字段（`shared.js` / `chrome.cookies.set` 用）：`{ name, value, domain, path, secure, httpOnly, expirationDate, sameSite, storeId }`。

### 本项目对应
`accountsStore.js` 的 `newEnv` 结构应包含以上字段。**核对**：`id`（本项目用 `generateId('env')`，官方用 `Date.now().toString()`，可保持本项目）、`name/siteName/siteUrl/avatar/cookies` 需与官方一致。

### 验收标准
1. `accountsStore` 保存的环境对象含 `id/name/siteName/siteUrl/avatar/cookies` 六字段。
2. cookie 元素含 `name/value` 且可选含 `domain/path/secure/httpOnly/expirationDate/sameSite/storeId`。

## 二、存储：账号走 localTool KV + 空值保护

### 为什么做（本项目丢数据的核心根因）
- 官方账号存 **localTool KV**（`window.localTool.saveKV`）→ 磁盘持久化，关闭插件重开、跨设备不丢。
- 官方 `setObject` **拒绝空值**（null/空数组/空对象/空串）→ 从根上防"读不到写空覆盖"。
- 本项目 `accountsStore.load()` 读不到时 `contentSet(STORAGE_KEY, [])` 写空覆盖 → 关闭插件重开账号丢失。

### 官方代码
`shared.js` `B.setObject`（L1193-1234）：
```js
if (Lr()) { Rr.set(e, t); return true; }   // disableLocalTool 时走内存
if (t == null) { warn; return false; }     // 拒绝 null/undefined
if (typeof t === 'object') {
  if (Object.keys(t).length === 0) warn;   // 拒绝空对象
  if (Array.isArray(t) && t.length === 0) warn;  // 拒绝空数组
}
if (typeof t === 'string' && t.trim() === '') { warn; return false; }  // 拒绝空串
let n = await Br.setObject(e, t);          // 正常：写 localTool KV
```
`localToolEngine.saveKV`（L836-860）：`window.localTool.saveKV(key, value)`。

### 本项目改动（由 docs/30 S3 落地，此处列出多开相关部分）
1. `contracts.js`：`yimao_accounts` backend → `kv`。
2. `accountsStore.js` `load()`：改异步读 KV，**删除** `contentSet([], [])` 写空覆盖。
3. `accountsStore.js` `persist()`/`saveEnvs()`：改 `await contentSetAsync`（落盘完成才算保存）。

### 验收标准
1. `accountsStore` 保存环境后，`contentGetAsync('yimao_accounts')` 能读回（KV 落盘）。
2. `load()` 读不到数据**不**触发写空覆盖（本地/后端无空数组被写入）。
3. 关闭插件重开 → 账号仍能读到（KV 持久化，非浏览器内存）。

## 三、保存/新建环境

### 为什么做
对齐官方"手动粘贴 / 抓当前标签页"两种新建路径，确保 cookie 抓取、站点信息正确。

### 官方代码
`Zr.jsx` L2059-2180：
1. `name = 表单名` → tab title → `'新建环境'`。
2. 若填 cookie 串：`parseCookies` 解析 → `siteName='手动添加'`、`siteUrl ||= 'https://example.com'`、`avatar = favIconUrl || dicebear(name)`；失败 `alert('Cookie 格式错误...')`。
3. 否则（扩展端）抓当前标签页：`siteUrl=tab.url`、`avatar=favIconUrl || google favicon`、`cookies=chrome.cookies.getAll({url})`、`siteName=title?.substring(0,5)`。
4. 空 cookie → `confirm`。
5. 组装对象 → 保存。

### 本项目对应
`accountsStore.js` `saveEnvironment()`。**核对**：cookie 解析、抓取、降级逻辑是否与官方一致。本项目已有 `parseCookies`/`fetchActiveTab`，应已覆盖。

### 验收标准
1. 手动粘贴合法 cookie → 保存成功，对象含 `siteName:'手动添加'`。
2. 扩展端抓取当前页 cookie → 保存成功，对象含 tab 的 siteUrl/avatar。
3. cookie 格式错误 → 返回 `{ ok:false, error:'Cookie 格式错误...' }`。

## 四、激活/切换环境（cookie 注入 + 跳转）

### 为什么做
官方激活 = 先同步 cookie（清多余 + 设环境 cookie），再跳转到 siteUrl。本项目 `activateEnv` 需对齐，确保 cookie 真正注入生效。

### 官方代码
- `xa`（Zr.jsx L1942-1954）：`await va(env)` → 若 `siteUrl` → `chrome.tabs.update(url)`。
- `va`（L1806-1882）cookie 同步：
  1. 取激活 tab，url 须 `http` 开头。
  2. `current = chrome.cookies.getAll({url})`。
  3. 清多余：`current` 中不在 `env.cookies` 名字集合的 → `chrome.cookies.remove({url, name, storeId})`。
  4. 设环境：`env.cookies` 逐个 `chrome.cookies.set({url, name, value, domain?, path?, secure?, httpOnly?, expirationDate?, storeId?, sameSite?})`（字段存在才传）。

### 本项目对应
`accountsStore.js` `activateEnv()` + `syncCookies()`。**核对**：`syncCookies` 是否与官方 `va` 一致（清多余 + 逐 set + 字段条件传）。

### 验收标准
1. 激活后：当前页多余 cookie 被清除，环境 cookie 被设置。
2. 激活后：若有 siteUrl → 跳转该 URL。
3. 非扩展环境 → 激活静默（不崩溃）。

## 五、清除 cookie

### 为什么做
对齐官方"清登录态白名单 / 清全部"两种模式 + 清后 reload。

### 官方代码
- `ba`（Zr.jsx L1884-1941）：白名单 `ya`（`sid_tt/sid_guard/uid_tt/ttwid/n_mh/odin_tt/has_biz_token/is_staff_user/user_spaces_idc`）。`all=false` 只清白名单，`all=true` 全清。清后 `chrome.tabs.reload`。空 cookie → toast。
- 注意：官方 `e.cookies = []` 仅改内存对象，**无持久化副作用**（本项目可对齐：不做 envs 更新/落盘）。

### 本项目对应
`accountsStore.js` `clearCookies()` + `LOGIN_COOKIE_WHITELIST`。**核对**：白名单一致、reload 行为、空 cookie toast。

### 验收标准
1. `all=false` 只清白名单 cookie；`all=true` 全清。
2. 清后当前标签页 reload。
3. 无 cookie → 返回对应信息（不崩）。

## 六、本项目差异与收口总表

| 项 | 官方 | 本项目当前 | 收口动作（归属文档） |
|---|---|---|---|
| 存储位置 | localTool KV | localStorage | docs/30 S3（改 kv） |
| 空值保护 | 拒绝 null/空数组 | `load()` 写空覆盖 | docs/30 S3（删写空） |
| 保存落盘 | `setObject`（异步） | 同步 fire-and-forget | docs/30 S3（改 async） |
| 数据结构 | `{id,name,siteName,siteUrl,avatar,cookies}` | 基本一致 | 校验字段（本文第一节） |
| cookie 白名单 | `ya` | `LOGIN_COOKIE_WHITELIST` | 已对齐 |
| 激活 | 同步 cookie + 跳转 | `activateEnv` 同逻辑 | 已对齐 |
| 清除 cookie | 白名单/全部 + reload | `clearCookies` 同逻辑 | 已对齐 |

**结论**：多开逻辑本身（数据结构/cookie 同步/激活/清除）与官方基本对齐，**核心差异在存储层**。按 docs/30 S2/S3 收口存储层后，多开即可对齐官方、关闭重开不丢。
