## 1. 现状机制（还原）

`check-api-contract.cjs` 全程**以登记表为出发点**，3 条校验方向：

| 方向 | 校验内容 | 失败级别 |
|---|---|---|
| registry → 后端路由 | path 存在 / method 一致 | 白实现 / 方法不符 = error |
| registry → 后端 handler | 信封形态（`detectShapes`） | 明显不符 = error；判不了 = info |
| registry → 前端模块导出（R5） | fn 指向的模块是否导出该符号 | ACTIVE 缺失 warn / RESERVED info |
| 后端路由 → registry | 未登记的响应 | 一律 info（不分类） |

R5 的 `MODULE_FILES` 白名单 = 手工维护 5 项模块映射：
`localToolApi / filesApi / pollTask / relayProxy / agentRuntime`（`check-api-contract.cjs:43-49`）。

**实测基线**（2026-09-04 跑 `node scripts/check-api-contract.cjs`）：登记 **55 条**，后端路由 61 条（catch-all 1 豁免），结果 **error 0 / warn 0 / info 13**。
> ⚠️ 文档口径出入：`CLAUDE.md` 声称 apiRegistry 57 条——实测 55。差 2 条疑为 L3 收口删登记后未同步 `CLAUDE.md`，需要核对（本文件按实测 55 为准）。

## 2. 盲区实证（每条都有活例，可按图索骥）

### ① fn 夹描述后缀 = 整体豁免（E5 同款洞仍在）
`FN_CHAIN_RE = /^[\w$]+(\.[\w$]+)+$/`（`check-api-contract.cjs:55`）——fn 里出现空格/括号/描述就**跳过该校验**。

- **活例**：`fileRead: { fn: 'filesApi.read (二进制流)', status: 'ACTIVE' }`（`contracts.ts:639`）。实测 `filesApi.ts` **无 `read` 导出**（该文件只打 `/api/files/upload`，见文件头注释），因 fn 含" (二进制流)"→ R5 豁免 → **ACTIVE 幽灵无人报**。
- 对照组：`filesApi.list`（`contracts.ts:642`，RESERVED）没加描述，被查出缺导出 → 现 info。**同是真缺失，一个报一个不报，全看 fn 脏不脏。**
- 溯源：E5（L3 裁定文档）证实的 relayProxy 曾踩同类豁免——洞在机制上从未补，只是该条目后来改对了。

### ② 多段链只校验第一层导出
`localToolApi.providerApi.getProviders` → `parts[1] = 'providerApi'`，只查 `export const providerApi` 存在（`checkFnExists` 只取 `parts[1]`，见 :225）。**方法名拼错（getProviders→getProvider）永不发现**。registry 内 6 条 `模块.对象.方法`（providerApi×6）全部只有第一层被验。

### ③ MODULE_FILES 白名单含死映射 + 未映射静默降级
- `agentRuntime` 在白名单内（:48），但 55 条登记 **0 条**以它开头（agent/runtime 已零直连 HTTP）→ **死映射**。
- 未映射模块的 fn → `info 'fn 模块未映射'` 不失败（:215）→ 新增消费模块忘登记 = **永久静默**，机制不提醒。

### ④ 登记 fn ≠ 真实消费入口（最深的一层错位）
- `relayProxy` 三条 ACTIVE（`contracts.ts:658-660`）登记的是**底层传输原语**；但 `base/api/index.ts`（薄入口 re-export 清单 :17-21）**根本不导出 relayProxy**——外部真实入口是 `generate.ts` 门面（`generateImage/generateVideo/chatCompletions/chatStream`，消费 `relayChat/relayChatStream`）。
- `generate.ts` 整文件不在任何登记 fn 里。它改名/换实现/弃用 relayProxy，registry **零感知**。
- 含义：R5 校验"relaySubmit 导出存在" ≠ "前端仍走它"。消费链验证与登记对象脱节，是 ① 之外第二个结构性假阳性来源。

### ⑤ 执行顺序：后端无路由则连 fn 都不验
`main()` 中 `!samePath.length` → error/warn 后 `continue`（`check-api-contract.cjs:266-270`），**跳过 R5 fn 校验**。理论上一条 ACTIVE 同时"后端无路由 + 前端无导出"只报前半段。

## 3. 「全量扫描」可行性验证与量级预判

对提议范围逐文件实测（39 处 `httpRequest/API_BASE` 调用点全部对账）：

1. **base/api 内部去重端点 ≈ registry ACTIVE 端点，基本自洽**（registry 本就是照这些函数抄的）。tasks×6 / projects×2 / resources×5 / files×7 / kv×3 / providers×5 / generate×3 全部已登记 → **此范围扫不出爆炸性失配**。
2. **agent/runtime 零直连 HTTP**：全目录仅 `contextCompression.ts:14`、`agentRuntime.ts:29` 两处 import，且都走 `base/api` 门面 → 扫它只值一个**负向断言**（防未来有人绕门面裸拼 fetch）。
3. **真正"后端有、前端未登记"仅 5 条**：`logs/stream`、`v1/gateway/task/{id}`、`local-patch/{crop,merge,fingerprint}`。其中 `local-patch` 在 `src/` **零引用**、gateway 协议分支已删（`pollTask.ts` 头注释确认）→ 属"应标 RESERVED 或死路由"，非路径漂移。
4. **登记表外的散落调用点**（约 10 处：`imageUrl.ts`/`imageCompress.ts`/`assetStore.ts`/`App.tsx`/hooks/`VideoProcessNode` 等）绝大多数是**对任意 URL 的原始流下载**（`parseJson:false` + `blob()`），非 localTool 业务端点，**不该进登记表**——全量扫描需此口径过滤，否则全是噪音。

**结论**：一次性暴露的将是"登记语义错位 + 幽灵映射 + 豁免洞"（黄/灰级），**红色级路径失配已被 L3 收口清掉**——可安全实施，无需先修历史再上闸。

## 4. 演进方案（建议，按价值排序）

> 目标：把「登记表声明了什么才查什么」改成「源码实际打了什么才准」，两端收口。

### 4.1 废除 MODULE_FILES 手工白名单 → 目录自动发现
扫 `base/api/*.ts` + 全仓所有出现 `httpRequest` 的文件建立「模块名 → 路径」映射；顺带删 `agentRuntime` 死映射。
风险：模块名解析要兼容 `import * as` / 默认导入，避免误映射同名模块。

### 4.2 从数据形态消灭豁免洞（先做，独立 commit）
- fn 字段**禁止夹描述**（`filesApi.read (二进制流)` → 拆 `read` + `note` 字段）。
- ACTIVE 条目 fn 不合 `模块.符号[.符号]` 形态 → **error** 而非静默豁免。
- `checkFnExists` 支持两层：`模块.对象.方法` 时同时验 `export const 对象` 存在 **且** 对象字面量含该方法名（正则提取对象体内键即可）。
- 顺手修两处假登记：`fileRead`（filesApi 无 read）、`filesList`（无 list）。

### 4.3 新增反向方向 D：源码调用点 → 登记表差集
静态提取全 `src/` 中 `httpRequest/httpPost` 字面量（复用现成 `patternToTemplate` 思路把 `encodeURIComponent(x)` 当 `{x}`）→ 得 `(method, urlTemplate)` 集合 → 与 registry 求差：
- 调用点真实存在且未登记 → **error**（真漂移，新增端点漏登记）；
- 后端有路由、前端零调用 → info 保持现口径（可人工标 RESERVED）；
- `parseJson:false` 的任意 URL 下载（`s.url`/`clip.url`/`u` 等非 `API_BASE` 前缀）→ 豁免。

### 4.4 登记 fn 对齐真实消费链
relayProxy 三条 ACTIVE 建议改标 `generate.generateImage / generateVideo / chatCompletions / chatStream`（消费真源），或条目加 `consumer` 字段——避免"校验原语、漏掉门面"。

### 影响面 / 验证
- 改动集中在 `scripts/check-api-contract.cjs` + `contracts.ts`（registry 注释与 fn 清洗）+ 可能 1-2 处前端导出修正。
- 预期新告警 ≈ 0 error（§3 结论），info 数变化来自 `fileRead/filesList` 假登记修正。
- 验证：`npm run check:api` + 人为注入假 ACTIVE / 漏登记端点，应分别报 warn / error；收尾 `npm run check:health`。
