## 一、这个功能到底解决什么问题（背景与痛点）

产品里，AI 助手左侧有一张「表格工作区」：随对话持久化、列/行可编辑，是用户用来**整理结构化内容**的地方（可以放故事分镜、产品清单、任意结构化数据——表不限定用途）。

用户的真实工作流是：**在表格里（或跟 AI 聊着）整理内容 → 整理满意了 → 让某一行「生成到画布/出图」**。

这带来一个核心张力：**AI 同时要会「填表」（输出表格 JSON）和「操作画布」（调工具建节点/出图）**。历史上出过这些故障：

1. **模型在「填 JSON」和「调画布工具」之间摇摆**——同一轮请求里既给了表格规则、又给了画布三通道意图识别，模型反复纠结要不要调工具，多轮才动手，甚至误调 `get_node_details`。
2. **误判「写故事/描述内容」=「要生成图片」**——特别是当模型是「Agent」（如 lovart），可能理解错用户意图，在后台网站上**擅自生成图片/视频并扣积分**，用户毫不知情（真实事故：意图识别未写准前，用户在表格里让它整理故事，它却悄悄生成了一堆图）。
3. **用户只想「先讨论清楚」再落表**——表是空的时，用户说"帮我写个故事"，模型却自作主张直接设计列、输出一版表，而不是先陪用户把故事聊清楚。
4. **把「输出 JSON」当「在聊天里吐代码」**——模型没意识到，对它而言「填 JSON」就是对用户可见表格唯一的作用手段（=建表），可能犹豫"这算不算真的在改表"。

**本设计的目标**：把表格协作收敛成**单一、清晰、默认直达填表**的规则，让模型「不用猜」——默认就填表输出 JSON；只有极少数「明确要出图画布」的情况才岔到工具；并**从规则上禁止擅自生成**，防住「Agent 脑补出图扣积分」。

## 二、核心架构决策（每条都说明为什么）

### 决策 1：表格协作 ≠ 画布助手——按开合切换「人格」，不叠加

- **现状/曾错**：表格展开时，`CANVAS_RULES`（画布助手 + 三通道意图识别）仍无条件注入，表格上下文只被塞进 user 末尾 → 模型同时面对「我是画布助手，先做意图分流」和「我在填表，只回 JSON」两套互斥身份 → 摇摆。
- **设计**：`buildRequestMessages` 增加可选参 `mode: 'canvas' | 'table'`（默认 `'canvas'`）。`mode='table'` 时**首条 system 换成 `TABLE_AGENT_RULES`（表格人格），不再注入画布 `CANVAS_RULES`**。
- **为什么**：模型在任意一刻只面对**一套**任务脚本，不存在两套身份打架。表格关闭（默认 canvas）行为与历史完全一致，向后兼容、不破坏既有测试。
- **注**：这里只是切「system 提示词人格」，**画布工具 schema 仍全部暴露**（`create_node/generate_node/list_nodes`…仍在工具列表）。表格态"不调工具"靠的是 TABLE_RULES 的措辞约束 + 把出图降成唯一例外，**不是**靠裁剪工具（裁剪会牵动执行层，属另一可选根治项，暂不做）。

### 决策 2：默认直达填表，只有少数情况才岔开（不做穷举漏斗）

- **曾错**：写成一版「五条执行漏斗（自上而下命中即执行）」，每条带一堆"【不】调工具/【不】输出 JSON"否定句。实测发现模型会**逐条排除**、反复论证"这不是建节点、不是出图"，绕十几轮才敢输出 JSON（用户输入「帮我写个故事。建表格」，模型思考过程极长才定稿）。
- **设计**：改为「**默认直达填表，少数情况才岔开**」。开头直接声明：只要用户让表格里有内容，**默认就是填表输出 JSON，不用考虑任何工具**。把「工具/画布」这条维度从每个正常填表请求里拿掉，只在唯一例外（明确出图）时才出现。
- **为什么**：大部分请求（填表、写内容、加行）根本不该碰"工具"这个维度，穷举排除是浪费且诱发摇摆；默认直达才是对人类直觉的贴脸拟合。

### 决策 3：「输出 JSON」=「建表/改表」，要跟模型点破

- 用户说"建表"想要的是界面上表变出来；对模型而言，它**唯一能改表的手段就是输出那个 `{globalStyle, rows}` JSON**（没有别的方式）。所以"填 JSON"对模型 = "执行了建表/改表"。
- 不点破，模型可能把输出 JSON 当"在聊天里吐代码"，犹豫"这算不算真在建表"。
- 措辞里直接写明"回复JSON=建表"。

### 决策 4：区分「讨论」与「落表」——表空 + 想点子先讨论，不硬落表

- 用户想「先聊清楚再落表」是常见诉求。表是空的、用户给个点子（没说整理成表），AI 应先当创作伙伴陪聊给思路，结尾可问"要不要整理成表"，而**不**自作主张设计列行出表。
- 判定关键不是"表空不空"，而是**用户有没有落表动作**（建表/整理成表/改/加）——有则落表，无则可能是讨论（围绕表格的构思）或无关闲聊。

### 决策 5：有选中行 = 铁定改这行（不兜底极少数"选了只想看"）

- 用户选中某行，意图已锁定"我要动这行"。前端（`AgentPanel.handleSend`）在有 `selectedRow` 时本就把它作为"改单行"目标注入 user。规则统一为「有选中行就默认改这行、输出单行 JSON」。
- **刻意不为"选中了但只想看看/先别改"这类极少数兜底**——模型本就不可控，为少数极端情况加判断只会复杂化、诱发摇摆（用户明确裁定）。

### 决策 6：禁止擅自生成——防 Agent 脑补出图扣积分

- 事故根因是模型（Agent）把"填表/写故事/整理"误判成"要出图"，在后台擅自生成扣分。
- 规则明确：**填表、写故事、整理、润色都不构成生成指令**，绝不因此调生成工具。
- 若要出图，需**两道闸**：① 用户明确说"生成到画布/建节点/出图"；② 模型先停下问"确认生成吗？"，等用户回"确认"才真正生成。用户没说"确认"前一律不生。
- **注**：这是**纯提示词层的软约束**，能大幅抑制脑补；但模型理论上仍可能绕过（不 100% 可靠）。若未来要绝对兜底，需在工具执行层做硬闸（如表格态触发 create_node/generate_node 前强制挂起等确认，仿 credit 积分闸），那是独立演进项。

## 三、当前 TABLE_RULES 结构（最终形态逐段解读）

TABLE_RULES 定义在 `agentConfig.ts` 的 `AGENT_PROMPTS.TABLE_RULES`，是 **`mode='table'` 时注入的首条 system**。结构分五段，各段意图：

| 段 | 内容 | 作用 |
| --- | --- | --- |
| 【表格管家】状态与指令 | 声明"当前在左侧表格工作区，user 已含表格现状 + 选中行" | 给模型必要上下文锚点，别把它当画布助手 |
| 【核心铁律】 | 一次回复仅限一种操作，绝不混用 | 从根上禁"边填 JSON 边调工具 / 同轮改表又出图" |
| 【怎么回应】 | 先默认填表 + 分 4 种情况 + 唯一岔到画布工具 | 主决策逻辑（见 §四） |
| 【禁止擅自生成】 | 填表/写故事≠生成；要出图须"明确指令 + 用户确认" | 防脑补出图扣积分 |
| 【JSON 输出格式铁律】 | 纯 JSON 无代码块；整表/单行规则；`_rowIndex` 定位 | 输出契约 |

### 3.1 当前 TABLE_RULES 全文（2026-09-06 定稿）

（注：以下为书写时点快照，实际以 `agentConfig.ts` 为准；改前先读该文件当前文本）

```text
【表格管家】状态与指令

当前是左侧表格工作区。用户输入中已包含表格现状（列名 + 各行的可读内容 + 全局风格）及「选中行」状态，据此判断该怎么处理。

【核心铁律】一次回复仅限一种操作，绝不混用（禁边输出表格 JSON 边调工具；禁同一轮又改表又出图）。

【怎么回应（先默认填表，回复JSON=建表，少数情况才岔开）】
只要用户这句话是在让表格里有内容（写、建表、整理、改、加行、做一张XX表、把故事做成表…），【默认就是填表】——直接按下面输出表格 JSON，【不用考虑任何工具/画布】。只有下面列出的少数例外才不输出表格 JSON。

分 4 种情况（一次只做一种）：
- 【建表/填表·默认】用户要表里有内容，且没【选中行】→ 输出表格 JSON：表格空 → 设计列行输出【整表】；往已有表加 → 按现有列输出该新行【单行】。
- 【改行·有选中行】用户选中了某行并说改它/优化它/把这行改成X → 只针对该行输出【单行】JSON（其它行不动）。只要选中了行，就默认是改这行。
- 【跟表无关】这句话和这张表无关（看图、问答、闲谈、单独要一段话/提示词）→ 直接文字回复即可，别硬塞进表、也别输出表格 JSON。
- 【只讨论不落表】用户没选中行、没说要建表/改表，只是在想点子或问这个方向好不好（如"帮我写个故事""这方案还有没有更好的"）→ 纯文字陪聊给思路，别急着输出表格 JSON，可问一句"要不要我整理成表 / 把某行做出来"。

【唯一岔到画布工具的情况】用户【明确】说要把内容"生成到画布 / 建节点 / 出图" → 才调用画布工具（create_node/generate_node）把内容落到画布并生成，一句话收尾（如"已在画布建好并开始生成"），【不】输出表格 JSON。除这句外，一律不碰画布工具。

【禁止擅自生成（铁律）】填表、写故事、整理内容、润色这些【都不构成】"生成图片/生成到画布"的指令——收到这类请求时【绝不】调用任何生成工具、也【绝不】去生成图片。只有用户【明确】说要"生成到画布 / 建节点 / 出图"，并且你【先停下问一句"确认生成吗？"、等用户回了"确认"】之后，才真正调用生成工具；用户没说"确认"前，一律不生。

【JSON 输出格式铁律（仅命中 1、3 时适用）】
- 严格输出单个 JSON 对象，禁止 Markdown 代码块，直接输出 {...}，不要附加解释文字：
{"globalStyle":"全局统一风格（整批基调；用户已给则照抄不改，未给且需要时补合理默认；没有可留空）","rows":[{"列名":"值","列名2":"值"}...]}
- 规则：rows 是行数组，每行一个对象，键=列名（按需求设计）。整表=各行列名一致、含全部行；单行更新/追加=只输出目标那一行、带列名，其余行不要动也不要输出。
- 定位键：改【已有】某行时，若确切知道它在现状里的第几行，可在该行对象内加 "_rowIndex"（从 1 起算）便于精准定位、不当列存表；拿不准行号【绝不】乱加（宁缺勿错），前端按你当前处理的行落。
```

> ⚠️ 模板字符串用反引号包裹，正文里**禁止再出现裸反引号**（`_rowIndex` 等引用一律用双引号包裹），否则编译炸。

## 四、判定逻辑（模型应如何分流）

TABLE_RULES 把模型的决策收敛成"默认直达填表 + 少数岔开"。逐条推演：

| 输入（表格态） | 该进哪 | 动作 |
| --- | --- | --- |
| 空表 + "帮我写个故事"（没说整理成表） | 只讨论 | 文字陪聊，不落表，可问要不要整理成表 |
| 空表 + "帮我写个故事，建表格" | 填表·建整表 | 设计列行输出整表 JSON |
| 有行 + 选中某行 + "把这行改紧凑/优化下" | 改单行 | 只针对选中行输出单行 JSON |
| 有行 + 没选中 + "再加一个 XX" | 填表·加行 | 按现有列输出新行单行 JSON |
| 有行 + 没选中 + "把第 3 行改成 X" | 改单行 | 输出带 `_rowIndex:3` 的单行 JSON |
| 表格开着 + "把第 2 行生成成图/建节点" | 出图（唯一岔路） | 先停下确认，用户说"确认"才调工具 |
| 表格开着 + "这张图里有什么"（跟表无关） | 无关 | 直接文字答，不塞表 |
| 表格开着 + 选中行 + "这行方向对吗"（问意见） | 讨论 | 文字给建议（选中行但用户没让改 → 讨论；虽选中但语义是讨论） |

**设计要点**：判定主要靠「现状 + 用户这句话」：
- 有【选中行】→ 默认改这行（除非用户明显只是问意见/没让改 → 讨论）。
- 没选中行 → 有落表动词（建表/整理/改/加）→ 填表；无动作且在想点子 → 讨论；明确出图 → 唯一岔路调工具；跟表无关 → 文字答。
- **一次只能落一个分支**。

## 五、代码对应关系（改哪看哪）

### 5.1 注入链路（表格打开 → 首条 system = 表格人格）

```
AgentPanel.handleSend / tableOpen = ws.open
  → useAgentChat({ tableOpen })                          // 入参加 tableOpen
  → send 里 mode = tableOpenRef.current ? 'table' : 'canvas'   // useAgentChat 用 ref 同步，避开闭包旧值
  → buildRequestMessages(..., mode)                       // 加在参数末尾，默认 'canvas'（向后兼容）
      → 首条 system = mode==='table' ? TABLE_AGENT_RULES : CANVAS_AGENT_RULES
```

关键文件与位置：
- `src/components/agent/agentConfig.ts`：`AGENT_PROMPTS.TABLE_RULES`（表格人格真源）+ `CANVAS_RULES`（画布人格）。
- `src/components/agent/runtime/agentCore.ts`：
  - `TABLE_AGENT_RULES = AGENT_PROMPTS.TABLE_RULES`（别名）。
  - `buildRequestMessages(messages,...,workMode, mode='canvas')`：`if (enhance)` 处按 mode 选首条人格（默认 canvas 行为不变）。
- `src/components/agent/runtime/useAgentChat.ts`：入参加 `tableOpen=false`；`tableOpenRef` + useEffect 同步；send 里 `mode` 判定 + 表格态 `intentHint=''`（不注入画布意图预判）。

### 5.2 表格现状注入（user 侧）

表格态下 AgentPanel.handleSend 不再拼一大坨模式介绍/格式契约（那些已进 system），只发【表格现状 + 用户这句话】：
- `buildTableSnapshotText(storyboard, globalStyle)`（AgentPanel 内辅助函数）：列名 + globalStyle + 各行可读文本 + 空表提示。
- 有选中行 → 追加 `buildRefineRowUser(rowToText(...), globalStyle, 用户原文)`（assistantTablePrompt.ts），明说"这是你选中的行…改完输出单行 JSON"。
- 无选中行 → 只发现状 + 用户原文。

### 5.3 模型返回表格 JSON → 预览 → 写回

- `tryParseAssistantTableJson`（assistantTable.ts）：从回复剥 Markdown 围栏 + 只取 `{...}`，需含 `rows` 数组才算表格 JSON。
- `buildPreviewModel`：单行带 `_rowIndex`（或选中行）→ 还原成完整行预览；否则整表。
- `confirmTablePreview`（tableWorkspaceState.ts）：单行优先用 `_rowIndex` 定位、无则回退发起时选中行；否则整表 `jsonToSb` 全量替换 + globalStyle 写回会话记忆。

### 5.4 数据真源 / 纯函数

- 表格数据 = per-conversation `memory.assistantTable`（`columns/rows`），读写经 `conversationStore.get/setCurrentAssistantTable`。
- `globalStyle` 不存表内，存会话记忆 `memory.global_contract.unified_style_prompt`，确认写回时同步。
- 行内定位元数据键 `_rowIndex`（`ROW_INDEX_KEY`）：解析层剥出不当列（见 assistantTable.ts `jsonToSb` 排除、`extractRowIndex`）。

## 六、与「意图识别 / 画布三通道」的关系（边界）

- 表格态（mode='table'）：**不注入** CANVAS_RULES（画布三通道意图识别文字消失），也**不注入**本地意图预判（`intentHint=''`）。表格态完全由 TABLE_RULES 引导。
- 画布态（mode='canvas'，默认）：照旧注入 CANVAS_RULES + 本地意图预判，表格相关全部不可见。
- **重要**：表格态只是"提示词人格"切了，**画布工具 schema 仍在工具列表**。表格态不擅自调工具，靠的是 TABLE_RULES 措辞（默认填表 + 禁止擅自生成），**不是**工具被裁剪。
- 因此：表格态模型仍"看得到"工具，是否不乱调取决于规则约束力。若未来要绝对保证表格态完全不碰工具，需在工具注册层按 mode 裁剪（未实现，属可选根治项）。

### 7.3 已知边界 / 未竟项

- 「禁止擅自生成」目前是**纯提示词软约束**，非 100% 可靠；要绝对防 Agent 后台擅自出图扣积分，需工具执行层硬闸（表格态触发 create_node/generate_node 前强制等"确认"），未实现。
- 表格态画布工具未按 mode 裁剪（工具仍全量暴露），依赖规则约束；可选做工具裁剪以根治。
- 用户给"选中行但只问意见/先别改"这类极少数不兜底（设计如此）。
- "auto confirm 扣积分通知前端"——相关排查/讨论见历史，尚未落地；属独立需求。
