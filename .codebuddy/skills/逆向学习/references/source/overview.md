# 逆向学习 AI 应用项目 SOP

> **适用场景**：你有一个目标项目（通常是 Python/FastAPI 后端的 AI 应用），想快速挖透它的完整架构，产出可用于复刻的参考资料。本 SOP 用 9 个 Phase + 15 个交叉视角 + 元数据规范 + 可执行验收标准，确保不遗漏核心链路，且交付物可被信任。
>
> **技术栈适配**：本文命令与示例默认 Python/FastAPI + PowerShell。**方法（探测、分桶、视角、验收）与技术栈无关**；换栈时替换检索命令即可（`references/source/commands.md` 附 bash/rg 等价命令）。

---

## 定位与使用边界（先看这条）

本 SOP 的定位是**个人学习 / 复刻研究**，不是生产级交付。在这个前提下：

- **读源码、复现 prompt、抄写实现、记笔记、本地跑通**——都是正常的学习手段，**可以抄，放心抄**，不需要犹豫。
- 产出物默认是**私有学习笔记**：自己看、自己改、自己练手。
- 唯一的边界是"离开个人学习范围"那一步——**对外分发 / 商用 / 公开发布**。只要不跨这一步，抄多细都没问题。
- 抄的时候**顺手标来源**（repo + 文件 + commit）：不是负担，既方便自己回溯，也让笔记更可信。

> 一句话：**学习复刻 = 可以抄；只把它当私有笔记，别当成品对外发。**

## 核心原则（必须先记住）

| 原则 | 说明 | 违反后果 |
|---|---|---|
| **口径统一** | 每个分类用「唯一键」计数（文件名/函数名/表名），不靠行数/关键词出现次数 | 宣称"已覆盖"但实际有遗漏，数字对不上 |
| **分层推进** | 先粗后细：文件列表 → service 入口 → 核心函数 → 逐行细读 | 上来就逐行读，迷失在细节里 |
| **边界优先** | 先搞清楚"系统能做什么 + 参数边界是什么"，再深入内部实现 | 复刻时因参数超限被上游拒绝 |
| **多视角交叉** | 单一视角一定看漏（只看 AI 能力会忽略状态机和并发模型） | 架构有盲区，复刻时才发现 race condition |
| **业务优先** | 先提炼领域规则，再抄 prompt 文本；规则是"为什么"，prompt 是"怎么写" | 只抄了文本，换模型/场景就失效 |
| **验证驱动** | "复刻对不对"靠 golden sample 对比，不靠肉眼"差不多" | 交付一堆文档却无法证明一致性 |
| **元数据可追溯** | 每个产出标覆盖度/置信度/版本，别把推测当事实 | 交付物无法被信任，按错信息施工 |
| **及时交付** | 每挖完一个桶就落盘（Write 文档），不要攒 | 上下文丢失后忘了之前挖了什么 |

## 执行约定（三条铁律，全程适用）

1. **预算与停止**：每个 Phase 有建议预算（见各 Phase 标题）。**超预算不无限深挖**——把剩余项写进 `00-进度台账.md`，转入下一 Phase，之后再回补。
2. **拿不到运行时数据**：若目标项目跑不起来（缺密钥/算力/数据），所有依赖运行时的结论一律标 `[待验证]` + 写明验证方法。**禁止用推测冒充确证**。
3. **大项目并行**：项目 > 约 50 个 service 文件、或跨多个模块时，**按桶用子代理并行挖掘**，主上下文只收结论（见 `references/source/templates.md` 采样策略）。

## Phase -1 · 启动（探测 + 定界）

**目标**：确认"逆向什么、挖到什么程度"，并把目录与台账先建起来。

**关键动作**：
1. **确认输入**：目标项目路径（或仓库地址）；**能否本地运行**（决定 Phase 2/6 能否拿运行时数据）。
2. **探测结构**：定位后端根、service 目录、API 目录、DB 文件、配置文件。
   - 不要假设一定叫 `backend/services/`——找不到就按实际结构调整（`src/` / `app/` / monorepo 子包…），**把实际路径写进台账**。
3. **定界**：与用户确认本次范围（整个项目 / 某几个桶 / 某条链路）。**范围之外明确写"本次不挖"**。
4. **建目录与台账**：创建 `docs/`，按 `references/source/templates.md` 建 `00-进度台账.md` 骨架，列出待挖桶清单。
5. **确认技术栈**：Python/Node/Go… 决定用哪套检索命令。

**落盘**：`00-进度台账.md`

**验收标准（可执行）**：
- ✅ 台账含：目标项目路径 + commit + 逆向日期
- ✅ 台账含：实际探测到的 service / api / db / config 路径
- ✅ 台账含：本次范围声明（含"本次不挖"清单）
- ✅ 台账含：待挖桶清单（每项初始状态 = 未挖）

---

## Phase 0 · 全局扫描（预算 15 分钟）

**目标**：搞清楚项目有哪些模块，哪些是核心，哪些可以跳过

**关键动作**：
1. 列出所有 service 文件并按行数排序（命令见 `commands.md`）
2. 按行数分层：>5000 核心 Skill / 1000-5000 重要模块 / 200-1000 辅助 / <200 工具类
3. 扫 API 入口，建立 `api 文件 ↔ service 文件` 的对应关系
4. **扫依赖闭包**：`utils/` / `core/` / `middleware/` 是零件，漏了复刻缺胳膊少腿
5. 标记纯运维/配置类（log / watermark / sensitive_word）为"可跳过"

**落盘**：`01-全局扫描.md`

**验收标准（可执行）**：
- ✅ 文档含一张 service 清单表（列：文件 / 行数 / 分层 / 核心? / 跳过?），**行数 = 实际 service 文件总数**
- ✅ 文档含依赖闭包清单（utils / core / middleware 文件）
- ✅ 每个"跳过"项都写了原因
- ✅ 文档里明确写出"最重要的 5 个 service"

## Phase 1 · 能力分桶

**目标**：为**当前项目**推导出互斥的 AI 能力桶（**不要照搬示例项目的桶**）

**关键动作**：
1. 扫所有可能调用 AI API 的文件
2. 读核心文件头部（前 50 行）确认定位
3. **按 `references/source/buckets.md` 的「校准方法」三步推导本项目桶**，每桶记录：覆盖范围、文件列表、行数
4. 校验互斥 + 完备 + 依赖方向

**落盘**：`02-能力分桶.md`

**验收标准（可执行）**：
- ✅ 文档含桶定义表（每桶：覆盖范围 / 文件列表 / 行数）
- ✅ **Σ 各桶内文件数 = service 文件总数**（口径统一，用文件数核对）
- ✅ 无 >1000 行文件落在桶外
- ✅ 明确标出基础层桶（基础设施 / 契约层）

---

## Phase 2 · 逐桶深挖（核心工作）

**目标**：挖透每个核心桶的 service 实现——**精确到源码行号 + LLM 参数 + DB 落库 + 并发防重**

**关键动作**（对桶内每个核心 service）：
1. 读文件头 docstring → 搞清高层定位
2. 扫 function/class 定义 → 列出入口函数
3. 逐个入口函数读实现，重点抓六件事：
   - Prompt 组装（system / user message 各是什么）
   - LLM 参数（max_tokens / timeout / temperature / task_type）
   - DB 读写（哪张表？INSERT/UPDATE？条件？）
   - 并发控制（BEGIN IMMEDIATE / CAS / hash 比对）
   - 错误处理（哪些重试、哪些不重试）
   - 后处理（清洗 / 规整 / 回填）
4. 追跨文件调用链：`API → service 入口 → 私有函数 → LLMService/ImageService/VideoService`
5. **能用运行时日志核对的就核对**；核对不了 → 标 `[待验证]`（见执行约定 2）
6. 每挖完一个桶立即落盘

**落盘**：`03-人类版.md`（AI 协议版 `04` 可后置）

**验收标准（可执行）**：
- ✅ 每个核心 skill 一节，含：入口函数签名 / prompt 结构 / LLM 参数 / DB 表与操作 / 并发设计
- ✅ 每条 prompt 结论带 `[确证]`（+行号）或 `[待验证]`（+方法）
- ✅ 文档中**无未标注置信度的裸结论**

---

## Phase 3 · 契约补齐（配置层 + 边界表）

**目标**：Phase 2 挖"怎么调用"，Phase 3 补"调用边界是什么"

**关键动作**：
1. **模型预设**：读模型配置文件 → 模型能力边界表（max_tokens / context_window / temperature）
2. **视频/图像模型能力**：读能力表文件 → 时长/素材上限 + provider 兼容
3. **凭证来源**：读 token/sync 服务 → API key 优先级链
4. **全局设置**：读 settings 服务的 `KEY_` 常量 → 业务开关清单
5. **Provider 凭证矩阵**：每个 provider 要什么凭证、来源、复刻要不要实现
6. **Prompt-模型耦合矩阵**：每个 Skill 依赖哪个模型能力（长上下文/多模态/JSON 模式），换模型会不会坏
7. **环境可复现性**：扫环境变量/配置 → `.env` 清单（含默认值 + 必需项）

**落盘**：`05-配置契约层.md`

**验收标准（可执行）**：
- ✅ 含模型能力边界表（每模型一行）
- ✅ 含凭证来源清单 + Provider 凭证矩阵
- ✅ 含 app_settings key 清单
- ✅ 含 `.env` 清单（变量 / 默认值 / 必需?）
- ✅ 含 Prompt-模型耦合矩阵

## Phase 4 · 多视角交叉验证（15 个视角）

**目标**：用 15 个视角交叉验证，补单一视角的盲区

**关键动作**：
1. **先做 P0 五个视角**（必做）：状态机 + 数据模型关系 + 异步边界 + **长任务生命周期** + **失败降级链路**
2. P1 / P2 视角按需挖——**判据**：只要该视角能回答的架构问题对"复刻"有影响，就必须挖；纯运维细节可跳过（并把跳过项写进台账）
3. 完整清单与「怎么挖」见 `references/source/views.md`

**落盘**：`06-架构视角.md`（**独立文件，不追加到 `03`**）

**验收标准（可执行）**：
- ✅ `06` 里 P0 五个视角各占一节，缺一不可
- ✅ 状态机：每个核心实体一张状态转换表
- ✅ 异步边界：每个 skill 标注 同步 / 队列 / background
- ✅ 含长任务时间轴 + 降级路径图
- ✅ 含锁 / 竞争点清单

---

## Phase 5 · 领域规则提炼（业务维度）

**目标**：Phase 2 抄的是 prompt 文本，本 Phase 提炼的是 prompt 背后的**业务规则**——这是"复刻得像不像"的关键。规则换个模型/场景依然成立，prompt 文本不行。

**关键动作**：
1. **拆分 prompt 三要素**：固定模板 / 可变注入 / 业务规则
2. **区分硬约束 vs 软约束**：代码 `if/raise` 的是硬约束；prompt 里"建议/尽量"的是软约束
3. **建术语表**：领域专有名词统一口径
4. **画 prompt 继承树**：base prompt + 各 skill 增量
5. **每条规则标源码行号**

> 若不确定某句是"业务规则"还是"措辞"，判据：**换个模型/换个题材后它是否仍需成立**？需要成立 = 规则。

**落盘**：`07-领域规则.md`

**验收标准（可执行）**：
- ✅ 每个 skill 的 prompt 被拆成 模板 / 注入 / 规则 三部分
- ✅ 规则表含"硬/软"列 + 来源行号
- ✅ 含术语表
- ✅ 含 prompt 继承树

---

## Phase 6 · 验证闭环（复刻正确性）

**目标**：定义"复刻对了没有"的判据，而不是凭肉眼说"差不多"

**关键动作**：
1. **找现成测试**：扫 `tests/` / `pytest` / mock 策略，复用原项目的判据
2. **收集 golden sample**：真实输入 + 真实输出（JSON/图片/视频/日志）
3. **定义可复现性**：同参数同 seed 是否稳定？`temperature=0` 是否确定？
4. **定义对比方法**：结构对比（字段/数量/长度）+ 语义对比（人工抽样）
5. **区分噪声与错误**：哪些差异是 LLM 可接受噪声，哪些是复刻错了
6. **拿不到真实输出时**：用例标 `[待验证]` + 写明获取方法（见执行约定 2）

**落盘**：`08-验证用例.md`

**验收标准（可执行）**：
- ✅ 每个核心 skill 至少一条用例（输入 / 期望输出或判据 / 容忍度）
- ✅ 标注哪些 skill 非确定（不能要求逐字一致）
- ✅ 拿不到真实输出的用例已标 `[待验证]` + 方法

## 产出物元数据规范（交付物可信度）

每个产出文档头必带 4 项：

- **覆盖度声明**：挖了多少、刻意跳过了什么（`覆盖 X/Y；跳过：<清单+原因>`）
- **置信度分级**：每条结论标 `[确证]`（附行号）/ `[推断]` / `[待验证]`
- **版本锚定**：目标项目 + commit + 逆向日期
- **进度台账**：`00-进度台账.md`（桶 / 状态 / 断点 / 下一步）

> 填充模板见 `references/source/templates.md`。

## 复刻实施顺序（MVP 切片）

**目标**：逆向产出一堆文档后，按什么顺序搭才不返工。

| 顺序 | 做什么 | 依赖 |
|---|---|---|
| 1 | 基础设施桶 + 契约层（模型表 / 凭证） | 无 |
| 2 | 数据模型 + 状态机（DDL + 状态流转） | 1 |
| 3 | 一个最小闭环 skill（文本类，最易验证） | 1,2 |
| 4 | 异步 / 长任务框架（队列 + 进度 + 取消 + 恢复） | 1,2 |
| 5 | 图片 / 视频 / 语音桶 | 1,2,4 |
| 6 | 编排 + 批量 + 特化 skill | 3,5 |
| 7 | 验证闭环 + 可观测性 | 全 |

**原则**：先搭"能跑通一条链路"的最小集，再横向铺能力。**不要按桶编号顺序平铺**。

## 常见坑 & 反模式

> 完整清单见 `references/source/antipatterns.md`。最高频的三个：
> 1. **照搬示例桶**——桶必须按当前项目重新推导（`buckets.md`）
> 2. **把推测当事实**——每条结论标置信度
> 3. **口径漂移**——用唯一键计数，不用行数/关键词
