> **效力边界**：与心法冲突以心法为准（`CLAUDE.md` 物理红线 > 心法 > 本步骤）。

## 🚫 第一条禁令：只读，不改一行代码

> 本流程**禁止修改任何代码**——包括"顺手改一下"、抽 helper、删死代码、修注释、补守卫。
>
> **为什么**：债很可能有**共性**（同一条规则/契约/机制生出来的）。现在逐条就地改，极可能**改错、改重、改出新重复**——因为你还看不到全局。
> **正确做法**：本流程只**登记**；等区域（乃至全仓）审完后，**交给最后那位"统一决策的架构师"**，由他纵览全部债、按母体**一次性做决策 + 收口**。
>
> **本流程的唯一产出 = 账本 + 覆盖度表 + DATAFLOW 的灯。发现债 → 登记；不修。**

## 工具（唯一实证工具 = `mv-sync-refs.mjs`，别自己翻库）

> 查**数据流 / 依赖方向 / 谁引用谁 / 改动影响面 / 是不是死代码** → 一律用它。
> **不要为搞清楚链路启动子代理全库乱搜**（CLAUDE §5.4.8）。

```bash
# ① 查引用（本流程主力）：谁 import 它（fan-in）+ 字符串残留引用；可一次传多个文件
node scripts/mv-sync-refs.mjs refs <file> [<file2> ...]

# ② 找孤儿 / 仅被测试引用的文件（启发式，删前人工核实）
node scripts/mv-sync-refs.mjs find-dead [<dir>] [--strict]
```

- `refs` 一屏给出 **① 谁 import 它（消费者）+ ② 字符串残留引用**（含注释/字符串，需人工剔除，别被误导）。
- 三个惯用场景：trace 一条链路 / 问"改这处会被谁影响" / 判某文件是不是死代码（**0 引用且非入口 = 死**）。
- 全库链路图维护在 `spec/DATAFLOW.md`：**先看它，再用 `refs` 单点验证**。
- ⚠️ 本流程**只读**：`move` / `rename` / `move-dir` 虽然也是这个脚本提供的，但**属"改"的阶段**（CLAUDE §5.4.8），本流程不用。

## 覆盖度账（"不重复查"的唯一机制）

> 审计最怕两件事：**① 同一批文件被反复查（浪费）；② 以为查过、其实没查（自欺）。**
> 治法是给每个区域建一张**覆盖度表**——它就是"查过什么、还剩什么"的账。**开审前先查它，收尾必更新它。**

**覆盖度表（真源 = 区域文件，每轮追加/更新）**：

| 文件 | 层 | 覆盖状态 | 灯 | 轮次/日期 | 证据(refs/行号) | 债/裁定 |
| --- | --- | --- | --- | --- | --- | --- |
| `base/core/contracts.ts` | L0 类型/契约 | 深审 | 🟢 | 二轮 09-12 | `refs` 实测 12 fan-in | 无债 |
| `base/store/projectStore.ts` | L2 store | 有债待还 | 🔴 | 六轮 09-12 | L130 双真相 | TD-02-23 |
| `hooks/useAssetDropPaste.ts` | L3 hook | 未审 | ⚪ | — | — | — |

**覆盖状态只允许这 5 个**：

| 状态 | 含义 | 还会不会再查 |
| --- | --- | --- |
| `未审` | 没碰过 | **会**（下轮优先） |
| `抽审` | 只看过一眼 / 浅判 | **会**（欠一轮深审） |
| `深审` | 逐行 / 逐契约看过 | 只有**代码变了**才 `回查` |
| `已裁定非债` | 查过、判非债（留痕） | **不会**（禁再当 bug 补） |
| `有债待还(TD-xx)` | 有债没还 | 还债时按 TD ID 回查 |

**三条铁律**：

1. **开审前先读覆盖度表**：只把 `未审` / `抽审` / `回查` 纳入本轮；`深审` 的不重查（除非本区代码自上次审计后被改过 → 标 `回查`）。
2. **`已还清` 区 ≠ 覆盖完备**（区域 04 的真实教训）：状态词只说"已发现的债还了"，**覆盖度由本表单独说话**——表里还有 `未审` 行，就**不许**写"该区审完"。
3. **收尾必报覆盖账**：本轮审了 M 个 / 本区共 N 个 / 未审 K 个（**逐个列名**），K 行必须有理由（不属本区 / 低价值 / 下轮）。

## 数据流覆盖地图（在 `spec/DATAFLOW.md` 上**打灯**，别塞明细）

> **为什么画在 DATAFLOW**：它是全库链路的唯一真源。节点旁挂一盏灯，**一眼看全仓哪块干净、哪块没碰**——这就是渐进式优化的进度地图，每审一格推进一格。
> **只打灯，不写字**：DATAFLOW **禁止**写债明细 / 日期 / 说明——**一旦写详情立刻臃肿**。灯 = 一个颜色，详情永远在区域文件。

**四种灯**（图例**只在 DATAFLOW 头部写一次**，节点旁只放一个灯字符）：

| 灯 | 含义 | 对应覆盖表状态 |
| --- | --- | --- |
| 🟢 | 已审、无债 | `深审`（无债）/ `已裁定非债` |
| 🟡 | 已审、有持平 / 待裁定 | `深审` + 持平债 |
| 🔴 | 有债待还 | `有债待还(TD-xx)` |
| ⚪ | 未审 / 抽审（欠深审） | `未审` / `抽审` |

用法 —— 节点后**只放一个灯，不写别的**：

```
类型地基：contracts.ts 🟢
生成链路：... → contentStore.ts 🔴 → ...
3D 模块：rig/xxx.ts ⚪
```

- 灯**变的唯一时机 = Step 5 收口**；就地改灯，**禁删旧链路**。
- **真源规则**：灯只是**区域文件覆盖度表的投影**；冲突时以区域文件为准，修 DATAFLOW。
- 已被改动过的 🟢 节点 → 打回 ⚪（覆盖表标 `回查`），等重审。
- 不愿用 emoji 可用文字灯：`[绿]` / `[黄]` / `[红]` / `[未审]`——**任选一种，全仓统一**。

# Step 1 · 定起点 —— 审哪个区，从哪个"最底层文件"开始？

**要回答**：这一轮登记哪个区、起手第一个文件是什么、**哪些文件这轮不用审**？

**动作**：
1. 读 `daily/架构日志/index.md`，取状态为 `待审计` / `审计中` 的区（都没有 → 按「层（底→顶）」列选最靠底的一个）。
2. **先读 `spec/DATAFLOW.md`**（数据流唯一真源）该区链路 + 链路上的**灯**（🔴⚪ 优先看）。
3. 找出该区的**最底层文件**——类型定义 / 契约表 / 常量登记表 / 纯函数。
4. 列出该区文件清单（**按层从底到顶排序**），并**对照覆盖度表**筛出本轮要审的（`未审`/`抽审`/`回查`）；本轮不审的写明原因。

**产出**：文件清单（底→顶 + 覆盖状态 + 灯），第一个文件就是本轮起点。

**不过关怎么办**：找不出"底层文件" → 说明区域边界还没定清，**先把边界写清楚再开始**，别硬审。

**真实对照**：区域 02 从 `contracts.ts`（`STORAGE_KEYS` 红线登记表）起手，而不是从 `contentStore.ts` 的 catch 兜底点切入——切入口选错，结论必错（八轮日志已实证）。

# Step 2 · 取证 —— 别信描述，跑 refs 看真实数据流

**要回答**：这条链路真实长什么样？DATAFLOW 过期了吗？

**动作**：
1. 对起点文件跑 **`node scripts/mv-sync-refs.mjs refs <file>`**（可把 Step 1 的文件清单一次传多个），看 **fan-in**（谁 import 它）。
2. 读它的真实代码：**类型 / 契约 / 不变式 / 唯一入口**在哪。
3. 沿 fan-in **逐级向上**，一级一级核实"谁产生 → 经过谁 → 谁消费 → 落哪"，随手标出 DATAFLOW 与实际不符处。
4. 疑似死代码 → 用 `find-dead` + `refs` 双证（0 引用且非入口）。

**产出**：真实链路快照（贴 `refs` 输出 / 链路图）+ **覆盖证据**（每个文件挂了什么 refs/行号）。

**不过关怎么办**：拿不出 `refs` 证据 → **这不叫取证，别下结论**。

> ⚠️ **自证式审计 = 没审**：结论只有自己能复述、别人照着复现不出来，就是走过场。
> 证据（refs 输出 / 文件:行号）必须落进区域文件，供下轮与他人**独立复核**。

# Step 3 · 找债 —— 先归因，再五问，最后标归属（**只登记，不动手**）

**要回答**：这些问题是孤例还是母体？是债还是有意设计？归到哪一类？

## 3.1 先归因：孤例，还是母体？（**别急着修，先看根**）

1. **按"它为什么会产生"归堆**（**不要**按症状表面分类）：它们共享哪一条**规则 / 契约 / 机制**？
2. **判据：某个修复能同时消灭 ≥3 个债 → 它就是母体。** 母体几乎总在**契约层 / 规则层 / 机制层**，不在"某一行代码"。
3. **查规则层的三问**：是不是**某条规则**出问题了？是不是**缺一条机器守卫**（红线只写在注释里 → 必回潮）？是不是**同一真相被抄成了多份**？
4. **产出**：`母体` → 登记为**一个母体债**（一收全消），把共享它的症状全挂它名下；`孤例` → 老实登记为独立债；`症状群但无母体` → 登记 N 个债（**不要编造母体**）。
   - **注意**：归因只用于**组织账本**，**不用于现在动刀**——修复统一交给最后那位决策架构师（见开头禁令）。

## 3.2 再五问：每层只问这 5 句

1. **同一真相是否被抄成 ≥2 份？**（SSOT 第二份，最高频母体）
2. **有没有绕过唯一入口？**（旁路直调底层）
3. **错误被静默吞了吗？**（`catch(() => {})` 零日志 / 失败伪装成功）
4. **有没有死代码 / 死参数 / 假护栏 / 假收窄（`as` 掩盖）？**（死代码须 `refs` 0 引用 + `find-dead` 双证）
5. **注释与实现一致吗？**（描述漂移）

**判据表（是债 vs 不是债）**：

| 是债 | 不是债 |
| --- | --- |
| 同一真相多处维护、靠"约定"同步 | 有意设计（有理由，且注释已固化） |
| 绕过唯一入口、假护栏（守卫恒真） | 为一致性而改（功能不变、收益为 0） |
| 静默吞错、失败伪装成功、假收窄 | 已经在正确位置的复杂业务逻辑 |
| 死代码 / 死参数 / 注释与实现矛盾 | 真缝隙上只有 1 种实现（还没到，不是债） |

## 3.3 最后标归属（**只标注，不决定谁改、更不现在改**）

6. **这是结构债还是业务债？**（只决定**登记到哪一类**）
   - 结构债（删重复 / 抽 helper / 补守卫 / 死代码 / 注释漂移）→ 登记为 `结构债`；
   - 业务债（删需求 / 砍功能 / 改交互 / **改对外契约与持久化格式** / 引重依赖）→ 登记为 `业务债 · 待用户拍板`，并摆 A/B/C 选项（见 Step 4）。
   - **两类都**不**在本流程施工**（见开头禁令）——归属只影响**将来谁决策**（结构债由决策架构师统一收口，业务债需用户拍板）。
7. **这条"不能动"是真红线还是假习惯？**
   - 拿不出 `CLAUDE.md` 级红线证据（端口 `18080` / `{code,data}` 契约 / 存储键登记表）→ **假习惯**，债成立，登记里注明"现被认为是硬约束，实为假习惯"；
   - 拿得出 → 债照样登记，备注"红线约束 + 依据"（红线只影响**将来怎么改**，**不影响登记**）。

> **证据闸（防"走过场"的硬闸）**：每笔债、每个"非债"结论，**都必须挂 `refs` 输出或 `文件:行号`**。
> **挂不出证据 = 无效结论**，不许写进账本。

**产出**：债候选清单（一笔一行）+ 归因（母体 / 孤例）+ 归属（结构债 / 业务债 / 红线备注）。

**不过关怎么办**：判成"**不是债**"也必须**留痕**（写进区域文件 + `债务.md` 标 `[已裁定 <日期>·非债]`），禁止默默略过——否则下一个 AI 还会当 bug 补。

**典型翻车**：TD-05-11「错误态无独立 UI，是债」→ 复核后**非债**（刷新后空白是诚实结果）；TD-06-8「现无实害」→ 实测**有实害**。**两例都是没取证就下结论。**

# Step 4 · 登记 —— 明细进区域文件，摘要进索引，覆盖表同步

## 4.1 明细（真源）

写进 `daily/架构日志/<NN>-<区域>-<日期>.md` 的**「探债」段**（同区多轮各写新日期文件，**不覆盖旧档**）：

| TD-ID | 决策点 / 问题点 | 归类 | 归属 | 爆炸半径 | 利息率 | 根因 | 偿还计划 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| TD-02-23 | projectStore 与 cache 两份内存真相 | 增债 | 结构债 | 2 处存储层 | 中 | 母体 M3（SSOT 第二份） | 契约钉死唯一写路径 | 待还 |

- **ID 规则**：`TD-<NN>-<n>`（NN=区域号，n=区内序号，如 `TD-02-23`）。**绑定首次发现的区域，永久固定**；跨区引用只写 `@见 TD-xx`，**不搬运明细**。
- **归类三选一**：`还债` / `持平` / `增债`。
- **归属**：`结构债` / `业务债`（业务债状态写 `待用户拍板`，**必须附 A/B/C 选项 + 推荐项**，缺任一项 = 未登记）。
- **利息率**：核心链路 = 高 / 边缘 = 中 / 内部 = 低。
- **根因**：填 §3.1 的归因（母体 `M?` / 孤例）；母体债把同源症状全列它名下。
- **偿还计划**：写"**将来怎么改**"（触发条件或具体动作），**本流程不执行**——留给决策架构师。
- 已还清 → 该行状态改 `已解决 <日期>`（**禁删，保留决策价值**）。

> **一票打回**：① `增债` 却没写**偿还计划**；② `业务债` 却没写 **A/B/C 选项**；③ 任何一笔挂不出**证据** → 打回重写。

## 4.2 摘要（索引）

在 `daily/架构日志/债务.md` **追加一行**（一行一债，**不写叙述**）：

```
| TD-02-23 | 02 存储/持久化 | projectStore 与 cache 两份真相 | 增债 | 中 | 待还 | [02-...md](./02-...md) |
```

**落盘纪律**：只追加、不覆盖、不删旧行。

## 4.3 覆盖度表（同区域文件，**别漏**）

按 §覆盖度账 的表格更新本区每个文件的状态 + 灯（`未审/抽审/深审/已裁定非债/有债待还`），并把**本轮判定为"非债"的文件也标进去**——否则下次还会被重审。

# Step 5 · 收口 —— 四份档案逐一收口，再进下一区

**动作 —— 对照上面「档案」表逐份收口**：
1. `daily/架构日志/index.md`：该区状态（`已验证(无债)` / `已验证(有债待还)` / `待翻新` / `已还清`）+ 「日志」列补本轮新文件链接。
2. **区域文件 `<NN>-<区域>-<日期>.md`**：六段（链路快照 / 溯源 / 定海 / 切割 / 探债 / 结论）写全 + **覆盖度表已更新**（依 `_template.md`）。
3. **覆盖度表 → 同步 `spec/DATAFLOW.md` 的灯**（**只改灯，不写字**）：
   - 本区链路漂移了 → **就地追加** `更新(<日期>, refs实证): ...`（**禁静默删旧链路**）；
   - 按覆盖度表把节点灯改成 🟢 / 🟡 / 🔴 / ⚪（未审的留 ⚪）；
   - 没漂也要在区域文件里写明「**已对账一致**」。
4. `daily/架构日志/债务.md`：确认本区新增/变更的债行**都已追加**。
5. **报覆盖账**：本轮审了 M / 本区共 N / 未审 K（列名 + 理由）。**K 行必须逐个列出，不许含混**。
6. 进入下一区：按「层」**从底到顶**取下一个 `待审计`。

**产出**：四份文件口径一致；该区"审到哪、剩什么"**一眼可读**；DATAFLOW 上多几盏灯。

**不过关怎么办**：DATAFLOW 没改灯 / 覆盖账没报 = 本轮**没闭环**，别开下一区。

# 附：索引用词速查

| 状态 | 含义 |
| --- | --- |
| 待审计 | 还没开 |
| 审计中 | 正在登记 |
| 已验证(无债) | 审过、无债 |
| 已验证(有债待还) | 审过、有债没还 |
| 待翻新（转架构5步法） | 需重构但**不算债**，**不进 `债务.md`** |
| 已还清 | 债已还 |
| 已退役 | 代码已删（编号不回收） |

> **待翻新 ≠ 债**：`债务.md` 只收「确是债、且现在不能动」的项。
> **已还清 ≠ 覆盖完备**：覆盖率看覆盖度表，不看这个状态词。

# 附：退回机制

| 在做什么 | 发现 | 退回 |
| --- | --- | --- |
| **任何一步** | **我想改这几行代码** | **停**：只登记，修复交给最后统一决策的架构师 |
| Step 2 取证 | refs 说不清链路 | 回 Step 1 重新定底层起点 |
| Step 3 找债 | 多个债共享同一规则 / 机制 | 回 §3.1 按**母体**挂账（一收全消），**别现在动刀** |
| Step 3 找债 | 分不清"债"还是"有意设计" | 回 Step 2，把该层代码 / 契约读完再判 |
| Step 3 找债 | 涉及业务能力变化 | 标 `业务债 · 待用户拍板` + 摆 A/B/C 选项 |
| Step 4 登记 | 增债写不出偿还计划 | 回 Step 3 重判——**多半它其实不是债，是偷懒** |
| Step 5 收口 | 覆盖表还有 `未审` 行却想写"审完" | 状态改「部分覆盖」+ 列出未审清单 |
| 任何一步 | 发现"债"根本不存在 | 改判非债 + 留痕，**结束**（这是最常见也最该退的一步） |

# 附：一句话总纲

> **读 DATAFLOW 看灯定起点（自底向上 + 看覆盖表）→ `refs` 取证 → 先归因再五问再标归属 → 明细进区域、摘要进索引、覆盖表更新 → 收口四份档案（DATAFLOW 只改灯）→ 下一区。**
>
> **全程只读不改码**：债的共性要等最后那位决策架构师统一收口，现在动刀必错。
>
> 三个最容易跳过、代价最大的地方：
> **① Step 2 取证**——不取证就登记，等于把上一轮的错抄进账本；
> **② 覆盖账**——不记"审了几个 / 剩几个"，这块区域必然被反复重审或假装审完；
> **③ 归因**——不把债挂到母体上，最后那位也收不了口。
