# 债务登记 5 步法（低脑力 SOP）

> **一句话总结**：读 index 看灯定起点（自底向上 + 看覆盖表）→ refs 取证 → 先归因再五问再标归属 → 明细进轮次文件、摘要进账本、覆盖表增量更新 → 收口「1 份必改 + 1 按需 + 2 自动」→ 下一区。

---

## 零、核心准则与边界

### 1. 基础定位

只管一件事：把一笔债登记下来，并让这块区域越审越清楚、不被反复重审。

- **触发**：用户说「审计 `<区域>` / 排查架构 / 维护架构日志 / 数据流过期了 / 登记债务」
- **分工（别混）**：
  - `本文件` = 审（发现 + 登记，只读）
  - `架构师改码7步法.md` = 改（施工还债）
  - `系统治理5步法.md` = 旁路复检
- **效力边界**：`CLAUDE.md` 物理红线 > `架构师心法.md` > 本步骤
- **精简留痕**：2026-09-16 删去论证 / 沿革 / 案例（原文见 git 历史），只留可执行步骤

### 2. 审查方向：从最底层出发

```
类型 / 契约 / 定义 → 纯函数 utils → store / core → hook 编排 → 节点 / UI → 后端
```

> 从 UI / 功能往下钻只能看到症状；债的根几乎总在更底层。**底层一条债，抵上层十条。**

### 3. 三大铁律与禁令

> 🚫 **禁令：只读，不改一行代码**
> 为什么：债往往同源（同一条规则 / 契约生出来的），逐条就地改易改错 / 改重 → 统一交决策架构师一次收口。

> 🚫 **禁令：禁止跑测试**
> 原则：审计 / 登记债时，不准跑任何测试（`npm test` / `vitest` / `playwright` / `*.test.*` 等）。能通过的代码一定都能通过测试，测试不是本流程的验收门槛，债只靠 `refs` / `文件:行号` 取证。碰测试命令即违规。
> 例外（仅限两处）：① 写代码施工还债（走改码7步法）；② 当场修工具债（`scripts/**` / `.codebuddy/commands/**` / `package.json scripts`）—— 修完可测作回归。

> **动作限制**：审计时手只准碰 `refs` / `debt.mjs` / 轮次文件 / `DATAFLOW`。本流程唯一产出 = 轮次文件（探债 + 覆盖度表）+ 账本一行。

> 🔒 **铁律：任何"描述"都只是线索，不是结论**
> 债登记、注释、issue、上一轮结论、覆盖表里的"深审"都可能是错的。动手前必须重新取证（`refs` + 读真实代码）。把描述当"去哪儿看"，不当"是什么"。

## 一、工具库与文件规范

### 1. 工具箱（严禁手写，统一使用命令）

| 用途 | 命令 |
| --- | --- |
| 查引用 / 数据流 / 死代码（主力） | `node scripts/mv-sync-refs.mjs refs <file> [<file2> …]` |
| 找孤儿文件（启发式，须人工核实） | `node scripts/mv-sync-refs.mjs find-dead [<dir>] [--strict]` |
| 取债 / 查历史 | `node scripts/debt.mjs list [--area NN] [--status 待还] [--all]` · `area NN` · `search "<词>"` · `show TD-xx` |
| 登记 / 改状态 / 归档 | `node scripts/debt.mjs add …` · `resolve TD-xx --note "…"` · `archive` |
| 架构日志进度表 | `node scripts/arch-index.mjs --write`（重生成）· 不带参数 = 校验 |

> **提示**：`refs` 一屏给 ① 谁 import 它 + ② 字符串残留引用（后者含注释，需人工剔除）；0 引用且非入口 = 死。查链路先看 `spec/DATAFLOW.md`，再用 `refs` 单点验证。禁手写 `债务.md` 表格行，禁 ReadFile 全量账本（读写唯一入口 = `debt.mjs`）。本流程只读，禁用 move/rename 类写操作。

### 2. 落点规范（每个文件只干一件事）

| 文件 | 唯一定位 | 本流程怎么动 |
| --- | --- | --- |
| `daily/架构日志/<NN>-<区域>-<日期>.md`（跨区 → `<触发区NN>-跨区-<主题>-<日期>.md` 一份） | 结论与证据（探债+覆盖度）—— 唯一人工落盘 | Step 4 写「探债」段 + 「覆盖度表」 |
| `spec/DATAFLOW.md` | 数据流现状（链路图 + 关键边）；不放灯 | Step 1 先读；Step 5 仅链路漂移时改现状图 |
| `daily/架构日志/index.md` | 区域清单 + 审计进度；机器生成不手改 | 跑 `arch-index.mjs --write` |
| `daily/架构日志/债务.md` | 债摘要索引（一行一债） | Step 4 跑 `debt.mjs add` / `resolve` |
| `daily/架构日志/债务-归档.md` | 已完成（自动维护） | `debt.mjs archive`，不手改 |
| `spec/TECH-DEBT.md` | 已废弃（只读，禁追加） | 不动 |

> **注意**：`spec/DATAFLOW.md` 的维护规矩唯一出口 = 它自己的 §维护规矩，禁在别处另立清单。

## 二、前置准备：覆盖度账与灯图

> "不重复查"的唯一机制。开审前，须在轮次文件里按本表登记每个文件的覆盖状态。

### 1. Step 0 · 维护覆盖度表

| 文件层 | 覆盖状态灯 | 轮次/日期 | 证据(refs/行号) | 债/裁定 |
| --- | --- | --- | --- | --- |

**5 种合法状态**：未审（会再查）、抽审（欠一轮深审）、深审（只有代码变了才回查）、已裁定非债（禁再当 bug 补）、有债待还(TD-xx)。

- **开审规则**：只审 未审 / 抽审 / 回查；深审 不重查（除非代码被改过 → 标 回查）。
- **完备性判定**：表里还有 未审 行，就不许写"该区审完"（已还清 ≠ 覆盖完备）。
- **增量账原则**：只登记本轮新纳入 / 状态变化的行，未变的原样保留、不重抄。

### 2. 数据流覆盖地图（灯的定义）

> 细粒度（文件→灯）写在轮次文件的覆盖度表里；粗粒度（区域→灯）由 `index.md` 自动派生。

| 灯 | 含义 | 对应覆盖状态 |
| --- | --- | --- |
| 🟢 | 已审、无债 | 深审（无债）/ 已裁定非债 |
| 🟡 | 已审、有持平 / 待裁定 | 深审 + 持平债 |
| 🔴 | 有债待还 | 有债待还(TD-xx) |
| ⚪ | 未审 / 抽审（欠深审） | 未审 / 抽审 |

**读起点的两步**：先看 `index.md` 的灯选"该动哪个区" → 再看该区最新轮次文件的覆盖度表选"该动哪个文件"。已被改动过的 🟢 文件 → 在覆盖度表里标 回查。

## 三、标准审计 5 步法

### Step 1 · 定起点

**目标**：确定登记哪个区、起手第一个文件，以及本轮不审哪些。

- 读 `daily/架构日志/index.md` 取 待审计/审计中 的区（如无，按「层」自底向上选）。
- 先读 `spec/DATAFLOW.md` 该区链路。
- 细粒度进度看该区最新轮次文件的覆盖度表（🔴⚪ 优先）。
- 找出该区最底层文件（类型定义/契约表/常量登记表/纯函数）。
- 按层从底到顶列出文件清单，对照覆盖度表筛出本轮要审的（不审的写明原因）。
- 查历史旧债：`debt.mjs area <NN>` 及 `search "<词>"`。防重审、看是否复发（复发=没治根）。

> **不过关**：找不出"底层文件" → 边界没定清，先定边界再开审。

### Step 2 · 取证

**目标**：确定链路真实面貌，验证 DATAFLOW 是否过期。

- 对起点文件跑 `refs`，看 fan-in（谁 import 它）。
- 读真实代码：找出类型 / 契约 / 不变式 / 唯一入口。
- 沿 fan-in 逐级向上核实，标出 DATAFLOW 与实际不符处。
- 疑似死代码 → `find-dead` + `refs` 双证（0 引用且非入口）。

> **不过关**：拿不出 `refs` 证据 → 自证式审计 = 没审（必须能让别人独立复现）。

### Step 3 · 找债（只读分析，不动手）

**目标**：定性孤例还是母体？是债还是设计？属于哪类？

#### 3.1 归因判定

- **判据**：某个修复能同时消灭 ≥3 个债 → 它是母体（多在契约层/规则层）。
- **三问**：是否某条规则出错？缺机器守卫（红线只在注释）？同一真相被抄多份？
- **产出**：母体 登记一债全消，症状挂其名下；无母体不强行编造，独立登记 N 个债。

#### 3.2 找债速查表（基于本仓历史形态，先 grep 扫一遍）

> 高频形态先用 grep 扫一遍，再进五问，比逐行读快一个量级！(数据源自 2026-09-16 的 278 条历史快照)

| 形态 | 条数 | 检出信号（照着 grep） |
| --- | --- | --- |
| 注释/文档漂移（最高频） | 41 | 将注释里提到的符号名/文件名/路径逐个 grep，查是否已改名/删改。 |
| 静默吞/失败伪装成功 | 29 | grep 空 `catch {}` · `.catch(() =>` · `?? <默认值>` · `return null`；再问是否通知了调用方。 |
| 死代码/幽灵预留 | 27 | `refs <file>` 看 0 引用；grep `将来\|预留\|暂不\|备用\|后续用`；对称 API 常有无用的。 |
| 绕过唯一入口 | 26 | 跑闸：`check:arch` 的红点 = 现成清单（裸 setNodes/裸 localStorage/直读 cache/深路径 import）。 |
| SSOT 第二份 | 24 | 抓字面量（端口 18080/键名等）全库 grep，≥2 处定义 = 第二份；同语义常量表亦是。 |
| 口径错位 | 15 | grep 某判断的所有比较点（大小写/是否剥 ?query/边界取值），逐一对齐。 |
| 假护栏/假守卫 | 8 | grep 恒为 true 的守卫、空 Set/数组判据、`if (true`。 |
| 复发/回潮 | 6 | `debt.mjs` 查是否有同类解法再次出现（复发=缺闸）。 |

#### 3.3 五层叩问（结合 3.2 扫出的候选进行判定）

1. 同一真相是否被抄成 ≥2 份？（最高频母体）
2. 有没有绕过唯一入口？
3. 错误被静默吞了吗？
4. 有没有死代码 / 死参数 / 假护栏 / 假收窄？
5. 注释与实现一致吗？

> 判定区分表：若是为一致性而改、处于正确位置的复杂逻辑、缝隙上的唯一实现，则不是债。

#### 3.4 标定归属与证据闸

- 分类为 **结构债**（删重复/补守卫等） 或 **业务债**（改功能/改对外契约等 → 必须标 待用户拍板 并摆 A/B/C 选项）。两者均不在本流程施工。
- **真假红线判定**：拿不出 `CLAUDE.md` 级证据（端口/存储键等）即为假习惯，债成立。
- **证据闸**：每笔债、每个非债结论必须挂 `refs` 或 `文件:行号`。

> **不过关**：判"不是债"也必须留痕（账本标 `[已裁定 非债]`），防被 AI 反复重审。

### Step 4 · 登记

#### 4.1 明细入轮次文件（「探债」段）

**格式**：

```
| ID | 决策点/问题点 | 归类 | 归属 | 爆炸半径 | 利息率 | 根因 | 偿还计划 | 状态 |
```

**一票打回**：① 增债 没写偿还计划；② 业务债 没写 A/B/C；③ 挂不出证据。

**ID 规则**：跨区只写 `@见 TD-xx`；已还清状态改 `已解决`（禁删）。

#### 4.2 摘要入账（跑命令，禁手写）

```bash
node scripts/debt.mjs add --area 02 --summary "…" --class 增债 --rate 中 --anchor <轮次文件名>
node scripts/debt.mjs resolve TD-02-23 --note "…"
```

**字段白名单强校验**：归类(还债/持平/增债)，利息(高/中/低)，归属(结构/业务)。摘要 ≤1 行且去竖线 `|`。就地改状态，不追行。

#### 4.3 更新覆盖度表

按 Step 0 更新状态，必须包含本轮判非债的文件。

### Step 5 · 收口（1份必改 + 1处按需 + 2处自动）

| 动作 | 源文件/操作规则 | 要求 |
| --- | --- | --- |
| **必改** | 本轮次文件 | 补全六段（快照/溯源/定海/切割/探债/结论）+ 覆盖度表。报覆盖账：本轮审 M / 共 N / 未审 K（逐个列名+理由）。 |
| **按需** | `spec/DATAFLOW.md` | 仅链路漂移时改现状图；没漂移就在轮次文件写「已对账一致」。禁追加更新叙事段。 |
| **自动** | 刷新进度与账本 | 跑 `arch-index.mjs --write` 更新 index；跑 `debt.mjs` 处理摘要及归档。 |
| **收尾** | 进入下一区 | 选取下一个 待审计。 |

> **不过关**：轮次文件 §七 没写状态行 / 没报覆盖账 = 没闭环，禁止开下一区。

## 四、区域治理与异常处理

### 1. 架构师自主裁量的治理规则

- **增/拆/并/退役**：区域清单变更在 `arch-index.mjs` 中修改，编号顺延不回收。跨区影响通过 `@见` 和指向新编号记录。
- **跨区定点**：一轮命中多区根因只开一份轮次文件（绑根因区）。
- **状态维护**：已还清被打回则重开文件并回退状态；"待翻新"不属于"债务"（不进 `债务.md`）。
- **单区膨胀**应按子关注点拆分。
- **当场清偿**：工具债（脚本/文档/package）不延后，当场修。

### 2. 卡住时怎么办（退回机制）

| 现象 | 退回动作 |
| --- | --- |
| refs 说不清链路 | 回 Step 1 重定底层起点 |
| 分不清"债"还是"有意设计" | 回 Step 2，把该层代码/契约读完再判 |
| 增债 写不出偿还计划 | 回 Step 3 重判（多半它不是债，是偷懒） |
| 覆盖表还有 未审 却想写"审完" | 状态改「部分覆盖」+ 列出未审清单 |
| 发现"债"根本不存在 | 改判非债 + 留痕，结束（最常见，最该退的一步） |

## 五、收尾自检清单（打不了勾就严禁写"审完"）

- [ ] `src/**` / `localTool/**` 一行都没改（哪怕是"顺手"）？
- [ ] 命中的工具债当场修了（没留成待还债）？
- [ ] 结论只写在轮次文件？轮次文件 §七 有状态行？
- [ ] 跨区发现只开了一份文件？
- [ ] 从类型 / 契约地基起手（而非从 UI 往下钻）？
- [ ] 覆盖账报全（共 N / 审 M / 未审 K + 逐个列名 + 理由）？
- [ ] 每笔债 / 每个非债结论都挂了 `refs` 或 `文件:行号`？
- [ ] 判定了孤例还是母体（未编造母体）？
- [ ] 标了 结构债 / 业务债，且业务债提供了 A/B/C 选项？
- [ ] 没有把假习惯当红线？没重抄旧结论？没重审 深审 / 已裁定非债 的文件？
- [ ] 全程没跑任何测试（测试执行次数 = 0）？

> **最容易踩坑、代价最大的三处**：① 不取证（直接把上轮的错抄进账本）。② 不计覆盖账（不写审了几个/剩几个，必定反复重审或假装审完）。③ 不归因（不找母体，最后负责修复的人收不了口）。
