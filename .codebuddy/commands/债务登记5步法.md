# 债务登记 5 步法（低脑力 SOP）

> **一句话总结**：读 index 看灯定起点（自底向上 + 看覆盖表）→ refs 取证 → 先归因再五问再标归属 → 明细进轮次文件、摘要进账本、覆盖表增量更新 → 收口「1 份必改 + 1 按需 + 2 自动」→ 下一区。

---

## 零、核心准则与边界

### 1. 基础定位

只管一件事：把一笔债登记下来，并让这块区域越审越清楚、不被反复重审。

- **触发**：用户说「审计 `<区域>` / 排查架构 / 维护架构日志 / 数据流过期了 / 登记债务」
- **分工（别混）**：
  - `本文件` = 审（发现 + 登记，只读）
  - `架构师改码7步法.md` = 改（施工还债）
  - `系统治理5步法.md` = 旁路复检
- **效力边界**：`CLAUDE.md` 物理红线 > `架构师心法.md` > 本步骤
- **精简留痕**：2026-09-16 删去论证 / 沿革 / 案例（原文见 git 历史），只留可执行步骤

### 2. 审查方向：从最底层出发

```
类型 / 契约 / 定义 → 纯函数 utils → store / core → hook 编排 → 节点 / UI → 后端
```

> 从 UI / 功能往下钻只能看到症状；债的根几乎总在更底层。**底层一条债，抵上层十条。**

### 3. 三大铁律与禁令

> 🚫 **禁令：只读，不改一行代码**
> 为什么：债往往同源（同一条规则 / 契约生出来的），逐条就地改易改错 / 改重 → 统一交决策架构师一次收口。

> 🚫 **禁令：禁止跑测试**
> 原则：审计 / 登记债时，不准跑任何测试（`npm test` / `vitest` / `playwright` / `*.test.*` 等）。能通过的代码一定都能通过测试，测试不是本流程的验收门槛，债只靠 `refs` / `文件:行号` 取证。碰测试命令即违规。
> 例外（仅限两处）：① 写代码施工还债（走改码7步法）；② 当场修工具债（`scripts/**` / `.codebuddy/commands/**` / `package.json scripts`）—— 修完可测作回归。

> **动作限制**：审计时手只准碰 `refs` / `debt.mjs` / 轮次文件 / `DATAFLOW`。本流程唯一产出 = 轮次文件（探债 + 覆盖度表）+ 账本一行。

> 🔒 **铁律：任何"描述"都只是线索，不是结论**
> 债登记、注释、issue、上一轮结论、覆盖表里的"深审"都可能是错的。动手前必须重新取证（`refs` + 读真实代码）。把描述当"去哪儿看"，不当"是什么"。

> 🔒 **铁律：诚实优先，禁止静默兜底（兜底必留痕）**
> 任何失败 / 降级 / 取不到值 / 走到异常分支的情况，**必须显式留痕**（抛错、打日志/告警、或在账本显式标记），绝不允许静默兜底——即：`catch {}` 吞掉、`return null` 假装成功、`.catch(() => …)` 静默化、`?? <默认值>` 无条件兜默认值、`未来再说` 式跳过。
> **为什么**：静默兜底让债「看不见」，是本项目头号伪装型债（见 §3.2「静默吞 / 失败伪装成功」29 例）。看不见 = 没人还 = 越滚越大，比明面债更贵。
> **兜底也须留痕**：若因客观限制（上游不可用 / 必须降级容错）确要兜底，必须在该处**显式记录**——打日志 + 行内标注 `兜底` + 写明原因与责任方，**并据此登记一债**（归类 增债 / 利息高）。**任何「无任何痕迹的兜底」= 违约，审计发现即登记一债。**
> **错误必须当场抛，不许转嫁（本流程只揪不改）**：失败应在**发生点**抛出，不该靠一个不相干的总线 / 下游 / 外层去"顺便吸收"。凡把错误甩给一个**本不负责此事**的通道去兜底（如：借别的事件总线静默消化、依赖下游容错掩盖上游错），**审计时即登记为一笔债**：标「转嫁兜底」、归属到真正的责任域（发生点所在模块）、挂 `文件:行号` 证据，并在偿还计划里写明"应在发生点正确抛出 / 处理，而非转嫁"。**"拆掉转嫁、做对"是「架构师改码7步法」的活——本流程（只读）只负责把它揪出来、指归属、记下来。**
> 审计动作：对每个捕获点 / 默认值点读上下文，问"失败时调用方知情吗？有痕迹吗？"；无痕迹即债，记「静默兜底」并指出该补上抛 / 告警 / 标记。
>
> **一句话内核**：**「一段代码失败了、却没任何人知道，那就是债。」** 判定不看严重程度，只看"失败是否可见"。可见（抛错/告警/标记/日志）就不算债；不可见，就是债——无论它当下"看起来没出事"。

> 🔒 **铁律：首判为债、复核翻非债 = 它仍是债（横跳即证据）**
> 找债时，**第一次判断是债、第二次"复核盘"又改成非债**的情况，直接以「债」定论，不许顺手把复杂度合理化掉。
> **为什么**：一个真正"处于正确位置"的复杂逻辑（见 §3.3 判定区分表），判断是**稳定**的，不会让人反复横跳。能让人从"债"改判到"非债"，恰恰说明**复杂度没放对位置**——它本该在契约层 / 规则层被一次性消化，却散落成让人纠结的"似债非债"。**横跳本身 = 错位的证据，故判债。**
> **动作**：判债后若要"复核推翻"，必须先能说清"复杂度在哪、为何位置正确"；说不清就保留债，账本标 `[首判债·复核疑非债→维持债]`。**禁止仅凭"感觉没那么严重 / 想简化掉"就翻案。**

## 二、前置准备：覆盖度账与灯图

> "不重复查"的唯一机制。开审前，须在轮次文件里按本表登记每个文件的覆盖状态。

### 1. Step 0 · 维护覆盖度表

| 文件层 | 覆盖状态灯 | 轮次/日期 | 证据(refs/行号) | 债/裁定 |
| --- | --- | --- | --- | --- |

**5 种合法状态**：未审（会再查）、抽审（欠一轮深审）、深审（只有代码变了才回查）、已裁定非债（禁再当 bug 补）、有债待还(TD-xx)。

- **开审规则**：只审 未审 / 抽审 / 回查；深审 不重查（除非代码被改过 → 标 回查）。
- **完备性判定**：表里还有 未审 行，就不许写"该区审完"（已还清 ≠ 覆盖完备）。
- **增量账原则**：只登记本轮新纳入 / 状态变化的行，未变的原样保留、不重抄。

### 2. 数据流覆盖地图（灯的定义）

> 细粒度（文件→灯）写在轮次文件的覆盖度表里；粗粒度（区域→灯）由 `index.md` 自动派生。

| 灯 | 含义 | 对应覆盖状态 |
| --- | --- | --- |
| 🟢 | 已审、无债 | 深审（无债）/ 已裁定非债 |
| 🟡 | 已审、有持平 / 待裁定 | 深审 + 持平债 |
| 🔴 | 有债待还 | 有债待还(TD-xx) |
| ⚪ | 未审 / 抽审（欠深审） | 未审 / 抽审 |

**读起点的两步**：先看 `index.md` 的灯选"该动哪个区" → 再看该区最新轮次文件的覆盖度表选"该动哪个文件"。已被改动过的 🟢 文件 → 在覆盖度表里标 回查。

## 三、标准审计 5 步法

### Step 1 · 定起点

**目标**：确定登记哪个区、起手第一个文件，以及本轮不审哪些。

- 读 `daily/架构日志/index.md` 取 待审计/审计中 的区（如无，按「层」自底向上选）。
- 先读 `spec/DATAFLOW.md` 该区链路。
- 细粒度进度看该区最新轮次文件的覆盖度表（🔴⚪ 优先）。
- 找出该区最底层文件（类型定义/契约表/常量登记表/纯函数）。
- 按层从底到顶列出文件清单，对照覆盖度表筛出本轮要审的（不审的写明原因）。
- 查历史旧债：`debt.mjs area <NN>` 及 `search "<词>"`。防重审、看是否复发（复发=没治根）。

> **不过关**：找不出"底层文件" → 边界没定清，先定边界再开审。

### Step 2 · 取证

**目标**：确定链路真实面貌，验证 DATAFLOW 是否过期。

- 对起点文件跑 `refs`，看 fan-in（谁 import 它）。
- 读真实代码：找出类型 / 契约 / 不变式 / 唯一入口。
- 沿 fan-in 逐级向上核实，标出 DATAFLOW 与实际不符处。
- 疑似死代码 → `find-dead` + `refs` 双证（0 引用且非入口）。

> **不过关**：拿不出 `refs` 证据 → 自证式审计 = 没审（必须能让别人独立复现）。

### Step 3 · 找债（只读分析，不动手）

**目标**：定性孤例还是母体？是债还是设计？属于哪类？

#### 3.1 归因判定

- **判据**：某个修复能同时消灭 ≥3 个债 → 它是母体（多在契约层/规则层）。
- **三问**：是否某条规则出错？缺机器守卫（红线只在注释）？同一真相被抄多份？
- **产出**：母体 登记一债全消，症状挂其名下；无母体不强行编造，独立登记 N 个债。

#### 3.2 找债速查表（基于本仓历史形态，先 grep 扫一遍）

> 高频形态先用 grep 扫一遍，再进五问，比逐行读快一个量级！(数据源自 2026-09-16 的 278 条历史快照)
>
> ⚠ **计数≠重要性**："条数"只是历史里被**捞到**的数量。凡是 grep 抓不到的（需语义推断 / 跨轮比对），计数必偏低，但**越难查的形态越是母体根因、价值越高**。AI 不能只信这张表的数字——下表"AI 怎么挖"列是硬动作，必须逐条执行，尤其难检项要主动深挖。

| 形态 | 条数 | 快扫（grep） | AI 怎么挖（硬动作） |
| --- | --- | --- | --- |
| 注释/文档漂移（最高频） | 41 | grep 注释里提到的符号名/文件名/路径，查是否已改名/删改。 | 抽取本文件注释中所有引用的符号/路径 → 逐个 `refs`/grep 验证存在 → 不存在即漂移。 |
| 静默吞/失败伪装成功 | 29 | grep 空 `catch {}` · `.catch(() =>` · `?? <默认值>` · `return null`。 | 对每个捕获点读上下文：失败是否被吞、调用方是否知情、是否该上抛/告警。 |
| 死代码/幽灵预留 | 27 | `refs <file>` 看 0 引用；grep `将来\|预留\|暂不\|备用\|后续用`。 | `refs` 双证 0 引用且非入口；对称 API 只实现一半的判定为幽灵。 |
| 绕过唯一入口（高价值·重点项） | 26 | 跑闸 `check:arch` 红点（裸 setNodes/裸 localStorage/直读 cache/深路径 import）。 | 列全仓"写状态"点，逐点核是否走唯一入口；非入口直写 = 违约。 |
| SSOT 第二份 | 24 | 抓字面量（端口 18080/键名等）全库 grep，≥2 处定义 = 第二份。 | 取每个常量/配置键名全仓 grep，出现 ≥2 处定义或同语义不同名 → 第二份。 |
| 口径错位（高价值） | 15 | grep 某判断的所有比较点（大小写/是否剥 ?query/边界取值）。 | 同一个判断在 N 处出现，逐点对比取值/归一化方式是否一致。 |
| 假护栏/假守卫（难检·高价值） | 8 | grep 守卫骨架：`if (` · `assert` · `require` · `validate` · `guard` · `ensure` · `check`。 | **逐条读判据**：是否恒真（常量/`process.env` 定值/`if(true`）、空 `Set`/数组判据、依赖从不变化的外界态；再问"这条守卫真挡得住吗"。 |
| 复发/回潮（难检·高价值） | 6 | `debt.mjs list --all` 取历史债主题词。 | **跨轮比对**：每个新债先 `debt.mjs search "<主题词>"` 看是否已有同类；同类再现 = 上次没治根（缺闸），记回潮并指向母体。 |

> 🔴 **重点项 · 绕过唯一入口**：架构级母体债。凡查到一处绕过，必顺藤摸瓜列全仓"写状态"点逐一核对——它养出的下游症状（口径错位 / SSOT 第二份 / 静默吞）往往比它本身更显眼，但**根在这**。审计中遇到即优先深挖并挂母体，不要只修它暴露出来的表面症状。

##### 3.2.1 难检两项：越难越要挖

这两类 grep 数字最低，却最该被 AI 主动捞——它们是"母体没治干净"的直接证据。

**假护栏/假守卫（8）**：grep 只抓得到 `if (true` 这种蠢货。真正的假护栏是**语义级**的——守卫判据在现实路径上永远为真、或依赖一个"理论上会变、实际从不改"的开关。AI 必须：**①** 枚举全仓守卫骨架；**②** 对每一条追溯判据能否为假；**③** 凡"挡不住"却让人以为安全的，记一债。

**复发/回潮（6）**：这根本不是代码 grep 能发现的，它要求**横向对照 `debt.mjs` 历史**。AI 必须：开审先 `debt.mjs list --all` 拿到旧债主题词；每发现一个债先 `search` 一遍；若同类已存在 = 复发，说明上次只修了表面、缺了根上的闸，必须挂回母体并重开根因。

#### 3.3 五层叩问（结合 3.2 扫出的候选进行判定）

1. 同一真相是否被抄成 ≥2 份？（最高频母体）
2. 有没有绕过唯一入口？
3. 错误被静默吞了吗？
4. 有没有死代码 / 死参数 / 假护栏 / 假收窄？
5. 注释与实现一致吗？

> 判定区分表：若是为一致性而改、处于正确位置的复杂逻辑、缝隙上的唯一实现，则不是债。

#### 3.4 标定归属与证据闸

- 分类为 **结构债**（删重复/补守卫等） 或 **业务债**（改功能/改对外契约等 → 必须标 待用户拍板 并摆 A/B/C 选项）。两者均不在本流程施工。
- **真假红线判定**：拿不出 `CLAUDE.md` 级证据（端口/存储键等）即为假习惯，债成立。
- **证据闸**：每笔债、每个非债结论必须挂 `refs` 或 `文件:行号`。

> **不过关**：判"不是债"也必须留痕（账本标 `[已裁定 非债]`），防被 AI 反复重审。

### Step 4 · 登记

#### 4.1 明细入轮次文件（「探债」段）

**格式**：

```
| ID | 决策点/问题点 | 归类 | 归属 | 爆炸半径 | 利息率 | 根因 | 偿还计划 | 状态 |
```

**一票打回**：① 增债 没写偿还计划；② 业务债 没写 A/B/C；③ 挂不出证据。

**ID 规则**：跨区只写 `@见 TD-xx`；已还清状态改 `已解决`（禁删）。

#### 4.2 摘要入账（跑命令，禁手写）

```bash
node scripts/debt.mjs add --area 02 --summary "…" --class 增债 --rate 中 --anchor <轮次文件名>
node scripts/debt.mjs resolve TD-02-23 --note "…"
```

**字段白名单强校验**：归类(还债/持平/增债)，利息(高/中/低)，归属(结构/业务)。摘要 ≤1 行且去竖线 `|`。就地改状态，不追行。

#### 4.3 更新覆盖度表

按 Step 0 更新状态，必须包含本轮判非债的文件。

# TS+React 异常&容错代码禁止项
原则：禁止静默吞异常、隐藏失败状态；失败与正常数据必须在类型上区分；所有异常必须可观测（日志/监控）

1. Promise相关
❌ 禁止空catch：.catch(()=>{}) / .catch(e=>{})，捕获错误必须写日志或上报。
❌ 禁止裸fetch不校验 !res.ok，必须手动throw HTTP错误。
❌ 禁止直接调用async函数不捕获异常（useEffect、onClick、setTimeout里），产生unhandledRejection。
❌ 禁止Promise.allSettled不判断status直接读取value。
❌ 禁止在.finally回调内抛出未捕获异常。

2. 同步容错工具 tryParse / tryRun / safeStringify / safeDecode
❌ 禁止捕获异常后直接return null / 默认值 / 空字符串，不记录错误。
❌ 禁止返回 T|null 单一类型；必须返回带success标识的联合类型 {success, data?, error?}。
❌ 禁止仅使用 as T 做类型转换，缺少zod/守卫函数运行时校验。
❌ 禁止调用tryParse/tryRun后不判断success，直接读取data。

3. Hooks与副作用
❌ useEffect异步请求必须使用AbortController，禁止竞态请求覆盖state。
❌ 禁止组件卸载后执行setState。
❌ useEffect清理函数内异常必须try/catch，禁止裸抛。
❌ useMemo/useCallback内危险计算，禁止不捕获异常直接向上抛出。

4. 类型断言与空值兜底
❌ 禁止双重类型断言 as unknown as T。
❌ 禁止滥用非空断言 !。
❌ 禁止使用 ?? / || 强行填充默认值掩盖缺失字段，无法区分空值和数据缺失。

5. 定时器、DOM事件回调
❌ setTimeout / setInterval 内async回调必须try/catch。
❌ DOM事件回调禁止空catch吞掉异常。

6. 接口与错误边界
❌ HTTP 200时，禁止跳过业务错误码判断直接使用返回数据。
❌ ErrorBoundary不能设置fallback=null；捕获组件错误必须上报监控，禁止静默隐藏。

审计规则：任意一条命中 → BUG，写明原因；全部满足 → PASSED
