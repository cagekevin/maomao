## 二、需求演化史（重要，帮助接手者理解用户到底想要什么）

用户在本次会话中反复调整，核心诉求最终收敛为（后半段）：

1. **初始担忧（性能）**：做交互增强要**性能最好、bug 最少、不引入外部库/复杂度**。
2. **行操作**：觉得右侧一整排图标（复制/上移/下移/删除/发送）占用空间且不常用；想"像正常表格那样通过序号选择"。后又提出：**行首拖拽符号做排序**、右键只留"复制 / 删除 / 插入空行 / 发送到画布"，`⋯` 三点放行尾。→ **因高风险（拖拽与 textarea/滚动冲突）被建议暂缓，最终未做。**
3. **列宽**：想让**长文本列真正按内容自适应铺开**，不要被压成窄条疯狂换行。→ 末尾在 css 用 `max-content` 试了一版（见第〇节），未验证。
4. **"从单元格本身看更舒适"** + **"你能不能做到自适应"**：用户希望单元格展示舒适。曾尝试给 `.cell` 限高（`max-height` + 格内滚动），用户反馈：内容看不全、格内也有滚动条、加上整表滚动条，**双重滚动很难受**。→ 撤销该限高，改为让内容完整自然撑开（当前 css 里 `.cell` 已是 `overflow:hidden` 自然撑高，无格内滚动）。
5. **最终明确需求（用户最后拍板的方向）**：
   > **默认折叠态**：几乎能看全全局（不纠结细节）；
   > **点「展开」**：切换为占满的大表视图，能看到所有长文本细节。
   > 接受"点一下（多一次点击）才进入编辑"，要**性能最好、bug 最少**。

   即：**一个"概览(compact) / 展开(full)"双态表格 + 点选才编辑**。→ **本次未实现**，是最大遗留任务。

## 三、为什么这些大功能被叫停（给接手者的决策背景）

用户反复强调、也是最终叫停的核心原则：**不能为实现功能引入 bug，宁可为不出 bug 牺牲功能。** 在此原则下，以下方案被评估为高风险 / 不合适：

| 想做的事 | 评估结论 |
|---|---|
| 行拖拽排序（行首拖拽换位） | 与 textarea 编辑、滚动容器、指针事件冲突面大，跨浏览器/触屏差异大，**易出诡异 bug → 明确不做** |
| 列宽拖拽调宽 | 实时拖宽 + 持久化边界多，风险偏高 → 暂缓 |
| 单元格限高 + 格内滚动 | 用户实测体验差（双重滚动、内容看不全）→ 已撤销 |
| HTML5 DnD 类方案 | 用户点名"不用 HDMI 5（HTML5 DnD）这类，可能有 bug" |

**关键认知**：把一张"多列（分镜：镜头编号/场景标题/场景描述/动作/对白/情绪/视觉要点）+ 每格长文本"的表，硬塞进左侧 ~600px 窄栏，**物理上就不可能舒适**。任何纯 CSS 微调都救不了"列数多 + 栏窄 + 每格文本长"的根矛盾。**真正解法是"展开成大表/全屏看细节"这种双态视图**——但改动大，需谨慎分步、低风险实现。

## 四、遗留大任务（下一步建议）

### 任务 A（用户已明确要、但未做）：概览 / 展开 双态表格
- 默认：左侧窄栏里表格**紧凑可概览**（一屏看到全局行，不纠结每格细节）。
