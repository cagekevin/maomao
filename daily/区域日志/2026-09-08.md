## 一、需求与最终方案

用户痛点：文本生成节点 hover 工具栏第三个按钮是「展开输入框」，一点就展开，有时不想展开很烦。最终拍板：**默认加锁，点一下解锁才能展开**。后续追加：锁住时单击节点主体直接进文字编辑（省去双击），解锁时维持原有双击编辑习惯。

实现要点（全部在 `TextGenerate.tsx`，约 15 + 8 行，无新文件）：

1. **新增 `inputLocked` 本地 state**：默认 `true`（加锁）。落盘到 `node.data.inputLocked`，复用既有 `patchData` + `useEffect` 链路（与 `expanded`/`autoSplit` 同款）。存量节点无该字段 → 走 `?? true` 默认加锁；锁只挡「展开」动作。
   - ⚠️ 后续修正（用户反馈）：**点锁加锁时，若面板当前是展开的，要一并把抽屉收起**（加锁 = 合上抽屉）。实现在 hover 锁按钮 `onClick` 内：`const next = !inputLocked; setInputLocked(next); if (next) setExpanded(false);`。故存量已展开节点在「首次点锁加锁」时会被收起，而非保持展开。
2. **hover 第三个按钮由「展开切换」改为「锁」按钮**：锁着显示 🔒（title「输入已锁定，点击解锁」），解锁显示 🔓（title「输入已解锁，点击锁定」），点击仅切锁状态，不再直接展开。
3. **`toggleExpanded` 加锁守卫**：`inputLocked === true` 时只许 `setExpanded(false)`（收起）、拒绝展开；`false` 时行为同前。
4. **新增 `enterEditing` 集中入口**：抽离「进编辑 + 聚焦」逻辑，避免重复。`onDoubleClick` 与「锁住时单击」都走它。
5. **节点主体 `onClick` 分支**：
   - `inputLocked` 为真 → 单击 `enterEditing()` 后 `return`（不切抽屉，满足「锁住时只想安静改字」）；
   - 否则 → 原行为 `toggleExpanded()`（切抽屉）。
6. `onDoubleClick` 复用 `enterEditing()`（解锁时双击编辑、锁住时双击也能编辑，无害）。

### 副作用（透明）
- 唯一副作用：`inputLocked` 随画布快照落盘。存量文本节点默认加锁；**加锁动作会连带收起展开的面板**（见上条修正），解锁不会自动展开；一旦某节点解锁，刷新后仍保持解锁（记忆意图）。
- 未触动其他节点、未改既有 `expanded`/`autoSplit` 逻辑、无新文件、无新全局契约。

全量 `npm run test:unit` 在本机**大量 `.tsx` 测试随机报 `document is not defined`**，根因已定位：

- vitest 默认环境是 `node`（无 DOM）。`.tsx` 组件测试需 jsdom。
- 配置靠 `environmentMatchGlobs` 按 `.test.tsx` 后缀自动路由到 jsdom，但**全量并发下该 glob 路由抖动**，部分 `.tsx` 被错分到 node 环境 → render() 崩。

- **纯 `.ts` 逻辑测试全过**；所有失败均为同一类 `document is not defined`，与业务逻辑无关。

给缺注解的 `.tsx` 补一行文件头 `// @vitest-environment jsdom`（配置注释本身也写明这是本意），即可消除抖动；或把 vitest 默认 `environment` 改为 `jsdom`（代价：纯逻辑 `.ts` 测试也走 jsdom，略重）。**加注解不会变慢**，反而省去随机失败重跑。

## 一、为什么会有"水合"（背景，30 秒版）

会话键 `agent_conversations_{agentKey}` / `agent_active_conversation_id_{agentKey}` 已登记为 `backend:'kv'`，**读必异步**（同步 `contentGet` 对 KV 键缓存未命中返回 undefined）。

于是必然存在一段**空窗期**：

```
setAgentKey(key) → 放空壳（同步读不崩，但读不到真数据） → 异步读 KV/迁存量 → 写全 states[key] → 放行
```

要防的只有一件事：**空窗期把"空壳"落盘，覆盖 KV 里的真数据**。其余都是为此服务的。

---

## 二、原实现虽然"正确"，但藏着 3 个洞（本次审计发现）

| # | 问题 | 后果 |
|---|---|---|
| 1 | 三套账记同一生命周期：`hydratedSet` + `hydrationInFlight` + `hydrationWaiters`，还要 `resolveHydration` 手动放行 | 认知负担重，漏一处就挂 |
| 2 | `hydrateAsync` 抛错 → `resolveHydration` 不执行 | `waitHydrated` **永久悬挂**（只靠调用方 `withTimeout` 兜），且 `hydratedSet[k]` 恒 false → **落盘永久闸死** |
| 3 | 失败后 `inFlight` 已清、`hydrated` 未置 → 每个 `getState()` 重新发起水化 | `requireActiveConv` 一次调两次 `getState`（热路径）→ KV 挂掉就是**读风暴** |
| 4 | 调用方 `withTimeout(waitHydrated, 8s)` | 超时后建的空对话会被随后到达的真数据整体覆盖 → 正是它想防的"刷新丢记录"观感 |

---

## 三、改后的机制（**记住这 4 句就够了**）

1. **`hydration: Map<key, Promise<void>>`** —— 每 key 只水化一次。缓存即幂等，**同时**充当"在途去重 + 等待者"（原 2 个结构 → 1 个）。
2. **`hydrated: Set<key>`** —— 唯一的同步闸。**不在里面就一律不落盘**（`commit` 不排期、`persist`/`flushPersist` 直接 no-op）。
3. **`hydrate()` 永不 reject** —— `.catch` 记日志 + `.finally` 置 `hydrated`。失败也放行落盘，否则等待者悬挂、落盘永久闸死（比"读到空态"更糟）。
4. **空窗期的写入会被水化结果整体覆盖** —— 这是既定语义（原样保留），所以**任何写入方必须先 `await waitHydrated(key)`**。

核心代码（`conversationState.ts`，第 ~200 行）：

```ts
const hydration = new Map<string, Promise<void>>(); // 每 key 的水化任务，只此一份
const hydrated = new Set<string>();                 // 同步闸：未水化 → 不落盘

function hydrate(k: string): Promise<void> {
  const cached = hydration.get(k);
  if (cached) return cached;
  const p = hydrateAsync(k)
    .catch((e) => logger.warn('AI助手', '会话水化失败，按空态继续（下次进入会重新读取）', {...}))
    .finally(() => { hydrated.add(k); });   // 无论成败都放行落盘
  hydration.set(k, p);
  return p;
}
export function waitHydrated(k?: string): Promise<void> { return hydrate(k || currentAgentKey); }
```

顺带：`hydrateAsync` 里两次 KV 读改为**并行**（最坏耗时 16s → 8s）；`ensureState` 只剩"放空壳 + `void hydrate(k)`"。

## 四、故障速查（**碰到问题先看这张表**）

| 症状 | 根因判断 | 立刻怎么解 |
|---|---|---|
| 刷新后聊天记录没了 / 首屏空白 | KV 里有数据但 UI 读到空壳：**某处在 `waitHydrated` 之前就读了，或自己 new 了空对话** | 全局搜 `ensureActiveConversation` / `applyConversation` / `newConversation`，确认调用链上都 `await waitHydrated(key)` 了 |
| 改了会话，KV 一直没写进去 | 99% 是 `hydrated` 没置上（落盘闸没开） | ① 确认 `setAgentKey(key)` 被调用过；② 确认 `waitHydrated(key)` 已 resolve；③ 注意 **`flushPersist()` 在 unhydrated 时同样是 no-op** |
| 启动期刷 `写「xxx」未生效：当前无有效对话` | 空窗期 `conversations` 为空 → `requireActiveConv` 必然返回 null（已限频 5s/条） | 在 `requireActiveConv` 里加一行静默：`if (!conv && !hydrated.has(currentAgentKey)) return null;`（已知时序，非缺陷） |
| 控制台 `会话水化失败，按空态继续（下次进入会重新读取）` | KV 读失败/超时，本次按空态跑，**会话内不自动重试** | 想让它重试：在 `hydrate` 的 `.catch` 里加 `hydration.delete(k)`。**慎用** —— 会退化成"每个 `getState()` 重试一次"，即上文漏洞 #3 的 KV 风暴 |
| 切项目后读到别的项目的会话 | `waitHydrated` 用的 key 与当前 `currentAgentKey` 不一致 | 务必 `setAgentKey(newKey)` **之后再** `waitHydrated(newKey)`；**别用无参 `waitHydrated()`**（它跟 `currentAgentKey`，可能还是旧值） |
| 怀疑"空壳覆盖真数据" | 只有 `hydrated` 为真才可能落盘 | 查是否有绕过 `commit` 直接 `contentSet` 会话键的地方；再查 `markHydrated()` 是否被过早调用（`applyConversation` / `importLegacy` 里有，它们会提前开闸） |
| 会话保存失败 toast / `会话落盘失败` | 与本次改动无关，是 KV 写入本身失败 + 降级上报 | 看 `reportDegrade` 与 `persistFailureBus`，别往水化方向查 |
