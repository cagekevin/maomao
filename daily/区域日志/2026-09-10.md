## 一、根因（看懂这个才懂为什么改）

咨询 Lovart AI 后明确其真实契约：

- **模型选择器 = `tool_hint`**，取值只有基础工具名：`generate_image_gpt_image_2_5_sunburst` / `generate_image_gpt_image_2_5_flare`（**不带质量后缀**）；`generate_image_gpt_image_2`。
- **质量 = `quality`**，是独立档位，6 档：auto / low / medium / high / xhigh / max（xhigh、max 仅 2.5 有效）。
- Lovart 解析我们 prompt 里的自然语言（如"用 GPT Image 2.5 Sunburst，质量 max"）自行拆出 `tool_hint` + `quality`。**`tool_hint`/`quality` 是 Lovart 内部解析结果，不是我们要发的结构化字段**——我们要做的只是把 prompt 写成它给的例句格式。
- **image-2 与 image-2.5 机制一模一样**：质量都不烤进工具名，工具名都是基础名、质量独立下发（之前误以为 image-2 工具名带 `_low` 后缀是真工具，已纠正）。

我们之前的实现有 3 处错位：

1. 下发带质量后缀的**假工具名**（`generate_image_gpt_image_2_5_sunburst_low` 等），上游并不真实存在。
2. **quality 从未传过**——全 `providers/lovart` 没有把质量写进请求，prompt 可读名还把 Low/Medium 烤进模型名。
3. 把"模型 × 质量"拆成 4 个假模型 id，质量未作为独立轴。

## 二、最终方案（用户拍板）

**模型 id 作单一数据源**，prompt 与 tool_config 都从它派生，不新增模型、不拆 quality 轴。

- 新增 `LOVART_QUALITY_MODELS: Record<模型id, { base, quality }>`。命中即：prompt 用 `base`（去后缀基础名）+ 单独质量子句；tool_config 发基础工具名（去后缀）。
- 未命中质量模型的（nano / 无质量模型）走原 `LOVART_PROMPT_MODEL_NAMES` 逻辑，不变。
- image-2（low/medium/high）与 2.5（当前仅 low/medium，按用户"用不了那么多"保留）同套逻辑。

### prompt 输出格式（以 `gpt-image-2.5-sunburst-medium` 为例）
```text
target_size: 1024x1024
用 GPT Image 2.5 Sunburst，质量 medium。
Generate exactly ONE image using the GPT Image 2.5 Sunburst model, quality medium.
<user_prompt>
{用户原文}
</user_prompt>
以上为用户提示词原文，直接使用，请勿修改
```
中文句给 Lovart 解析器、英文句作双保险硬约束；有参考图时首句前插 `Reference image attached. `（避免误走 edit_media 改图）。

### tool_config（全部去后缀，发基础工具名）
| 模型 id | 工具名 |
|---|---|
| `gpt-image-2-low/medium/high` | `generate_image_gpt_image_2` |
| `gpt-image-2.5-sunburst-low/medium` | `generate_image_gpt_image_2_5_sunburst` |
| `gpt-image-2.5-flare-low/medium` | `generate_image_gpt_image_2_5_flare` |

> 注释里已写明 **image 2.5 支持的全部能力**：2 基础模型 + 6 档质量；当前仅收 low/medium，要暴露 high/xhigh/max 只需在 `LOVART_QUALITY_MODELS` 追加对应 id 行（并在 manifest 加模型条目）。

## 一、三个同源黑洞（根因）

| 黑洞 | 表现 | 根因 |

| **1 契约不在类型里** | 摄像机拖不动，静默失败 | 同类对象两个更新签名：`onUpdate(id,patch)` vs `onUpdateCamera(patch)`；`{...current, ...'camera'}` 是**合法 JS**，`tsc` 不报 |

## 二、🔴 两个**真实事故**修复（最要紧）

### A. React Flow `deleteKeyCode` 绕过全屏模态层

**现象**：在 3D 导演台（`FullscreenShell` 全屏层）按 Delete，**删掉的是画布节点**。

**根因**：画布有**两条键盘路径**，只有一条接了守卫：

```
useCanvasShortcuts（hooks/useCanvasShortcuts.ts:77）→ 有 hasModalLayer() 守卫  ✅
React Flow deleteKeyCode（App.tsx:1388）            → 内部 useKeyPress 自挂 window，绕过守卫  ❌
```

与 `modalLayer.ts` 文件头记载的「ImageEditor 里按 ⌘Z 撤掉画布节点」是**同源事故**——
只是一个走查询、一个必须走订阅。

**修法**：
- `modalLayer.ts` 新增 `subscribeModalLayer(listener)`，层开合时通知
- `registerLayer` 登记/注销处调 `notifyLayerChange()`
- `App.tsx` 用 `useSyncExternalStore(subscribeModalLayer, hasModalLayer)` 订阅
- `deleteKeyCode={modalLayerOpen ? null : DELETE_KEY_CODE}` —— **从源头拆掉监听**

> **为什么必须订阅**：`deleteKeyCode` 是**声明式 props**，开关在渲染时就定了，
> 没有"执行前再问一次"的时机，查询式守卫对它无效。

**影响面**：对所有全屏层生效（导演台 / 全景漫游 / 图片编辑 / 剧本盒…），不止导演台。

### B. hydrate 竞态导致用户编辑静默丢失

**现象**（预演场景）：打开导演台 → KV 还没回来 → 用户动了几下 → KV 一到 → **那批编辑没了**。

**根因**：`applyProjectSnapshot` 是**无条件覆盖**，`alive` 标志只防「卸载 / key 变化」，
**不防「用户已编辑」**。

**修法**（`App.tsx` hydrate 的 `.then` 内）：检查 `history.past.length > 0` 即放弃覆盖。

> **判据为什么是 `past` 不是 `last`**：`last` 是基线，startup 首次副作用就设置（**恒非空**），
> 用它作判据会让 hydrate **永远跳过**，等于破坏原有 KV 覆盖功能。这个坑我踩了一次才想对。

## 四、护栏（这是本次最有价值的产出）

改了求值/写入路径，**必须有逐帧等价护栏**，否则就是裸奔。

| 护栏文件 | 锁住什么 |
|---|---|
| `tests/unit/director3d.cameraAtFrameWithPath.test.ts`（19 tests） | 逐字复刻「收口前三分支」为对照组，**110 帧 × 2 种 targetMode × 5 场景 = 1100 次逐帧比对** |
| `tests/unit/director3d.trackWriteParity.test.ts`（11 tests） | 相机轨 6 个操作与旧手写实现等价；**两条轨道语义对等** |

**对等性护栏最能抓漂移**：批量平移「目标帧被另一待移动帧占据」场景，
两条轨道必须**同为 `[15, 20]`**；若某条忘了先删旧帧就退化成 `[20]`（丢帧）。

护栏还专门盯住几个**光读代码发现不了**的点：
- 路径分支用**当前基线**打底（误用 `initialCamera` 会让焦距 85 突变成 42）
- `object` 模式下路径**不给 rotation**
- 无动画时**返回同一引用**（返回新对象会让 memo 失效、整个视口每帧重渲染）

## 五、明确的元原则（写进文档了）

1. **能不让问题产生，就不要先做工具去观察它。**
2. **能靠类型系统强制，就不要靠文档和纪律。**
3. **没有护栏就不要动高风险路径**（求值/写入）。
4. **让 AI 只读代码就能确定对错** —— 使用者是 AI 不是人。

> **据此否决了「诊断面板」方案**：用户明确表示自己不会诊断、都是 AI 诊断，
> 而 AI 排查**只有一个入口——读代码**，看不到运行时面板。
