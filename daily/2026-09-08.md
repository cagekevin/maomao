## 一、需求与最终方案

用户痛点：文本生成节点 hover 工具栏第三个按钮是「展开输入框」，一点就展开，有时不想展开很烦。最终拍板：**默认加锁，点一下解锁才能展开**。后续追加：锁住时单击节点主体直接进文字编辑（省去双击），解锁时维持原有双击编辑习惯。

实现要点（全部在 `TextGenerate.tsx`，约 15 + 8 行，无新文件）：

1. **新增 `inputLocked` 本地 state**：默认 `true`（加锁）。落盘到 `node.data.inputLocked`，复用既有 `patchData` + `useEffect` 链路（与 `expanded`/`autoSplit` 同款）。存量节点无该字段 → 走 `?? true` 默认加锁；锁只挡「展开」动作、**不强制收起已展开的面板**。
2. **hover 第三个按钮由「展开切换」改为「锁」按钮**：锁着显示 🔒（title「输入已锁定，点击解锁」），解锁显示 🔓（title「输入已解锁，点击锁定」），点击仅切锁状态，不再直接展开。
3. **`toggleExpanded` 加锁守卫**：`inputLocked === true` 时只许 `setExpanded(false)`（收起）、拒绝展开；`false` 时行为同前。
4. **新增 `enterEditing` 集中入口**：抽离「进编辑 + 聚焦」逻辑，避免重复。`onDoubleClick` 与「锁住时单击」都走它。
5. **节点主体 `onClick` 分支**：
   - `inputLocked` 为真 → 单击 `enterEditing()` 后 `return`（不切抽屉，满足「锁住时只想安静改字」）；
   - 否则 → 原行为 `toggleExpanded()`（切抽屉）。
6. `onDoubleClick` 复用 `enterEditing()`（解锁时双击编辑、锁住时双击也能编辑，无害）。

### 副作用（透明）
- 唯一副作用：`inputLocked` 随画布快照落盘。存量文本节点默认加锁，但**原本已展开者保持展开**（锁只挡展开不强制收起）；一旦某节点解锁，刷新后仍保持解锁（记忆意图）。
- 未触动其他节点、未改既有 `expanded`/`autoSplit` 逻辑、无新文件、无新全局契约。

## 二、如何回退（用户重点关注，写得清楚点）

改动高度局部、无架构变化，回退分两种粒度：

### 回退 A：去掉「锁」功能，恢复「第三个按钮=展开切换」
- 删除 `TextGenerateData` 接口里的 `inputLocked?: boolean;`；
- 删除 `inputLocked` state 及对应的 `useEffect(patchData({ inputLocked }))`；
- 将 hover 第三个按钮改回原样：
  ```tsx
  { key: 'toggle',
    icon: expanded ? <ChevronUp .../> : <ChevronDown .../>,
    title: expanded ? '收起输入' : '展开输入',
    onClick: toggleExpanded }
  ```
- 把 `toggleExpanded` 还原为无守卫版本：`const toggleExpanded = useCallback(() => setExpanded((v) => !v), []);`
- 此时 `inputLocked` 引用全部消失即可。

### 回退 B：保留锁，但「锁住时也别单击进编辑」，恢复成全部双击编辑
- 仅改节点主体 `onClick`：删掉 `if (inputLocked) { if (!editingText) enterEditing(); return; }` 整段，恢复为：
  ```tsx
  if (!editingText) toggleExpanded();
  ```
- `enterEditing` 与 `onDoubleClick` 可保留不动（双击仍走它，无副作用）。

### 回退 C：想「所有情况都单击编辑」（不止锁住时）
- 把 `onClick` 里的 `if (inputLocked) { ... return; }` 改成直接 `if (!editingText) { enterEditing(); return; }`（去掉锁判断），即解锁后单击也进编辑。

> 三种回退都只动 `TextGenerate.tsx` 内几行，不影响其他文件；改完跑 `npm run dev` 验证即可。

## 三、测试环境注意事项（重要，避免误判失败）

全量 `npm run test:unit` 在本机**大量 `.tsx` 测试随机报 `document is not defined`**，根因已定位：

- vitest 默认环境是 `node`（无 DOM）。`.tsx` 组件测试需 jsdom。
- 配置靠 `environmentMatchGlobs` 按 `.test.tsx` 后缀自动路由到 jsdom，但**全量并发下该 glob 路由抖动**，部分 `.tsx` 被错分到 node 环境 → render() 崩。
- 文件顶部带 `// @vitest-environment jsdom` 注解的 `.tsx` 不受 glob 影响，稳定通过；缺注解者才会随机中招（已用 `git stash` 掉本次改动后单跑 `LazyImage.test.tsx` 仍稳定失败，证明确属预存在环境故障，与本次锁改动无关）。
- **纯 `.ts` 逻辑测试全过**；所有失败均为同一类 `document is not defined`，与业务逻辑无关。

### 根治建议（独立任务，本期未做）
给缺注解的 `.tsx` 补一行文件头 `// @vitest-environment jsdom`（配置注释本身也写明这是本意），即可消除抖动；或把 vitest 默认 `environment` 改为 `jsdom`（代价：纯逻辑 `.ts` 测试也走 jsdom，略重）。**加注解不会变慢**，反而省去随机失败重跑。

> 因此本期「锁改动」未能在本机用 DOM 测试验证（环境故障），仅 lint 通过；验证依赖本地预览手动点按。
