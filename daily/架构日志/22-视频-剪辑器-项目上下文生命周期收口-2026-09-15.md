## 二、Step 1 · 证伪：哪些「债」经取证其实不存在？

> 铁律：「任何描述都是线索，不是结论」。本轮复核 4 笔，**2 笔改判**。

### 2.1 TD-22-25（`[待还]·高`：redo 缺省=execute → redo 后 undo 失效、元素永久丢失）→ **改判非债**

- **描述**：快照式命令在 `execute()` 内重存 `savedState`，`redo()` 缺省 = `execute()` ⇒ 重做会用「重做后的状态」覆盖快照 ⇒ 元素永久丢失。
- **取证（行为测试，非读代码猜）**：新增 `tests/unit/veCommandRedoSnapshot.test.ts`，跑真实链路 `deleteElements → undo → redo → undo`——
  结果**第一次就通过**：第二次 undo 与第一次 undo 结果一致（`['e1','e2']`）。
- **真相**：栈语义保证 redo 的前置状态 = 首次 execute 前状态（undo 已完整恢复），因此 **redo 重捕得到的快照与首次完全相同**，重捕无害。
  26 处命令（`grep 'this.savedState = '` 实测 26 处）+ `BatchCommand.redo()` 委托 `execute()` 均同此理，无实害。
- **反向验证（防自证式测试）**：注入「undo 也重捕快照」→ 测试精确变红（§七 探针 E）→ 证明该用例确实在测快照正确性，而非自说自话。
- **处置**：状态改 `已裁定非债`；**保留该用例**锁住「execute→undo→redo→undo 一致」契约（防未来有人改成「redo 不重捕」或加自定义 redo 而打破一致性）。
- **latent（登记不立债）**：`BatchCommand.redo()` 调子命令 `execute()` 而非 `redo()` —— 当前全库 0 命令自定义 `redo()`，故无差异；若未来有命令自定义 redo 会被忽略。

### 2.2 TD-22-41（`scenes` 状态双源：命令不同步 `ProjectManager.active.scenes`）→ **改判非债（描述失真）**

- **描述**：`ScenesManager.list/active` 与 `ProjectManager.active.scenes` 并存，scene 命令「从不调 `setActiveProject` 同步」→ 双源漂移。
- **取证**：`ScenesManager.setScenes()`（`scenes-manager.ts:215-235`）**内部自己就调** `this.editor.project.setActiveProject({ project: {...active, scenes} })`。
  `CreateSceneCommand` / `DeleteSceneCommand` / `RenameSceneCommand` / `ToggleBookmark*` **全部**经 `editor.scenes.setScenes()` 提交 ⇒ 同步确实发生 —— 「从不同步」不成立。
- **真相**：`ScenesManager.list/active` 是 `ProjectManager.active.scenes` 的**派生镜像缓存**（为 O(1) 读 + 订阅粒度），且**所有写路径单点同步**（`setScenes` / `updateSceneTracks` / `switchToScene` / `initializeScenes`）。
  唯一不同步的 `clearScenes()` 现由 `releaseProjectContext()` 与 `clearActive()` **成对调用**，一致性保持。
- **处置**：改判非债；描述修正写入本文件（**不回改**旧轮次文件的历史描述 —— 那是当时的取证记录；本文件为最新真相，`index` 指向本文件）。

## 三、Step 2 · 归因：母体（1 条母体覆盖 4 债）

**母体 M-D：引擎单例的「项目上下文生命周期」没有拥有者。**

`EditorCore` 是**长驻单例**（`getInstance()` 首次构造，`reset()` 仅测试用），而「切换 / 关闭 / 新建项目」只清了 `media` + `scenes` 两格 ——
**命令栈 / 选择 / 音频 / 播放 / 渲染树没人清**，因为**没有一个人负责这件事**：谁调用的谁就得记全 10 项，于是必然漏。

| 子债 | 症状（用户可见） | 根因（同一母体） |
| --- | --- | --- |
| **TD-22-45**（高） | 切作品后按 Ctrl+Z，**弹出上一作品的命令**，其 `undo()` 把 A 的 tracks 快照写回 B | 命令栈跨项目存活，无清栈 |
| **TD-22-46**（高） | 切项目后选择残留旧 `trackId/elementId` → 属性面板错乱 + **误删**；旧项目音频继续调度；缩略图缓存残留 | selection/audio/thumbnail 的清理 API **存在却从未被切项目调用** |
| **TD-22-32**（高） | 切场景后 Ctrl+Z 把 **A 场景快照写回 B 场景** | 切场景不清命令栈（同一根因的另一维度） |
| **TD-22-22**（中） | 空时间轴按播放 → 时间码狂奔、raf 永续 | 播放态无上下文边界（同族：播放上下文没有拥有者） |

**母体判据**：一次收口同时消灭 ≥3 个债 → 命中（4 笔）。

**触发面（实证必然可达，非边缘）**：`App.tsx:1572` 的 `<EditorShell key={activeProjectId} …/>` —— 切画布项目时 React key 变化 ⇒ EditorShell **卸载重挂**，走的是 `EditorProvider` unmount cleanup，**不经过** `exitEditorToCanvas`。
即：切项目时**必然**复用同一个 `EditorCore` 单例而不释放（卸载路径原只 `clearEditorContext()`）。

## 四、Step 3 / 4 · 定位与契约

**位置（五问）**：
1. 真源 = 状态本身（各 manager 私有字段）；2. 变化速率 = 随项目切换而变；3. 实现份数 = 4 份散写（§一）；4. 改动半径 = 收口到 1 处后，未来新增 manager 只需加一行；5. 接口 = 窄（无参、无返回）厚实现。

⇒ **收口点 = `EditorCore.releaseProjectContext()`** —— 唯一能看见全部 manager 的位置。

**契约（Step 4 四问）**：
- **语义诚实**：命名区分**重置**（`reset` / `releaseProjectContext`，实例可复用）与**销毁**（`dispose`，实例终结）。原 `AudioManager.dispose()` 被当成"清理"用是错位（它会解订阅 + 关 AudioContext，在切项目时调用会让音频永久失效）。
- **顺序**：先停"会产生副作用的"（播放 → 音频在途调度），再清缓存、栈与项目本体。
- **`AudioManager.reset()` 必须 `playbackSessionId++`**：`startPlayback` 是 async，重置瞬间可能有在途 await；递增让它们醒来后 fail-fast，防旧项目 clips 写回新上下文。
- **失败可见性**：不适用（本方法无 IO）。

**定权（Step 5）**：架构判断（结构、行为不变）→ 架构师直接定，未打断用户。
**判据**：改完用户能做的事**没减少** —— 切项目后"不能撤销上一项目的操作"不是能力削减，而是**消除错误能力**（那个撤销本就把 A 的数据写进 B）。
