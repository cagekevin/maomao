## 二 · 溯源（症状 vs 病根）

**症状（用户可感知）**：
- 工程里明明有 10 个素材，打开后媒体面板**空了**（其实 KV 里 `video_editor_media_meta_*` 形状异常被静默当 `{}`）；
- 工程库列表**整个消失**（KV `video_editor_projects_*` 形状异常被静默当 `[]`）；
- `/files/` 临时不可达 → 部分素材**悄悄不显示**，没有报错、没有 toast；
- 收藏音效按钮显示「未收藏」，其实**已收藏**（读失败被当 `false`）。

**病根（母体）**：storage 服务层对「读失败 / 形状异常」的兜底策略**不统一**，且**缺「读失败必须可见」的统一契约**：
- 已修的（TD-02-35）：`loadSavedSounds` 读失败**上抛**、`saveSoundEffect`/`removeSavedSound` catch **throw+log**、`loadSavedSounds` 形状异常 `logger.warn`+空（不是零日志）；
- 未修的（本轮）：`readMediaMetaMap`/`readProjectList` 形状异常 → **静默 `{}`/`[]` 零日志**；`loadMediaAsset` fetch 失败 → **null 零日志**；`loadAllMediaAssets` **静默丢弃**；`isSoundSaved` → **`false`**。
⇒ 同文件两种口径，说明收口（TD-02-35）是**按点修的、没横向铺到读路径全集**，且缺机器守卫（"读失败不得静默当空/当否"）。

**为什么现在才看见**：上轮（16 区）扫的是 `catch → return 默认值` 形态 + 平行轮扫的是「成功信号」与「零调用」；**「读到的存量形状异常 → 静默当空」** 是第三种静默面，恰好落在 videoEditor 自己的 storage 层，两轮的扫描器都没覆盖到（一个扫 `catch`，一个扫 `toast`）。

## 三 · 定海（不变式 / 唯一真相源）

1. **读到的存量 ≠ 空**：`contentGetAsync` 返回 `null/undefined` = 「确实没有」；返回**形状异常值** = 「损坏/迁移失配」。**二者必须区分** —— 后者至少要 `logger.warn`（对齐 `loadSavedSounds:583`），绝不能零日志当空。
2. **读失败不得被聚合成「更少的结果」**：`loadAllMediaAssets` 返回 `MediaAsset[]` 却静默丢弃失败项 = 调用方无法区分「3 个媒体」与「5 个里 2 个坏了」⇒ 失败可见性缺失（同 TD-22-43 母体）。
3. **同层读路径契约一致**：`loadSavedSounds`/`saveSoundEffect`/`removeSavedSound` 已立「读失败 throw + log」范式 ⇒ `isSoundSaved` 必须对齐（不得 `catch → false`）。
4. **正面范式（复用，不新造）**：`storage/service.ts:575-590` `loadSavedSounds` 区分「无值 vs 形状异常」，异常 `logger.warn`；`video-cache:249` `initializeSink` 失败 `logger.error + throw`（失败上抛）；`transcription/worker.ts` 全部错误走 `init-error`/`transcribe-error` 消息协议。
