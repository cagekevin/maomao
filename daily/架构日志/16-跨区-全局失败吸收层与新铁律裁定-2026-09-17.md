## 二 · 溯源（Phase 1：症状 vs 病根）

**症状**（用户/排查者能感知的）：
- 持久化连续失败，只弹一次「部分数据保存失败」，后续静默（用户以为好了）。
- 高频降级（如 KV 反复失败）只 logger，用户全程无感。
- 控制台 `ResizeObserver loop` 类告警被全局监听吃掉，连排查线索都无。
- 单个节点渲染崩，静默变成「该节点渲染出错」占位，崩溃根因被掩盖。

**病根（母体）**：**失败吸收层**——app 级 / 全局把失败就地吸收，使失败对「用户」与「调用方」双不可见。
与逐点静默（TD-16-22）同源不同层：逐点是「函数内 catch 把失败换算成默认值」；本文件是「跨函数/跨模块的全局吸收通道」。两者根因都是「失败必须可见」红线只写在注释里、缺针对「全局层」的机器守卫。

**为什么现在才看见**：TD-16-22 的扫描器与闸只认「空 catch / catch 内 return 默认值」的**逐点形态**；`persist:failed` 总线、`reportDegrade` 节流、`main.tsx` 全局监听是**架构级通道**，不在逐点判据面内。逐点票据修完，全局层仍原样吸收。

### 8.1 ②回改原文：`reportDegrade` 的病不在「留痕」，在「谁决定呈现」

**取证（先说清原文错在哪）**：`degrade.ts` 里 `logger.warn` 写在**节流判断之前**、且 toast 判空 —— 即
**每一次降级都 100% 留痕**，「降级未留痕」不成立 ⇒ §五「建议改判非债」的**判据只覆盖了留痕**。

**但按用户原则看，真病是**：该模块在**顶层**持一个 `const throttle = { key, ts }` —— 一个**模块级可变全局单槽**；也就是说**转发原语自己替所有生产者决定「这条失败要不要让用户看见」**。这与刚删掉的 `persist:failed` 总线是**同一形态**（全局吸收层），只因粒度小（只并「同文案」）没被 §四 的清单抓到。⇒ **不是非债，是漏判的越权债**。

**施工（判据/状态归位，行为不变）**：

| # | 落点 | 改动 |
| --- | --- | --- |
| 1 | `core/toastStore.ts` | `showToast` 新增 `coalesceMs`（同文案合并窗口）+ 导出 `TOAST_COALESCED`；**窗口状态由展示层持有**（`lastShownAt: Map<'type\0message', ts>`），并写明「有界性 = 只有声明窗口的调用方写它，全仓即 reportDegrade 一族，文案有限」 |
| 2 | `core/toastStore.ts::clearToasts` | 连合并窗口一起清 —— 否则「清空提示」后同文案再也弹不出来 = 用清屏造出新的静默 |
| 3 | `core/degrade.ts` | **删掉模块级 `throttle` 单槽**；`reportDegrade` 变成**纯转发**（logger + `showToast(toast,{type:'warning',coalesceMs:throttleMs})`），自身不留任何窗口状态 |

**行为等价性**：合并键 = `文案 + type`、窗口默认仍 `THROTTLE_MS`(5s)、未声明 `coalesceMs` 的调用方（全仓其余 toast）**从不合并** ⇒ **用户能看到的提示不多不少、不早不晚**（属结构收口，非业务变更）。

### 8.2 ③`main.tsx` 残留：过滤已不静默，但**计数没有出口**

`main.tsx` 现版已按本债治过（注释即 TD-16-33④）：无害告警**首次 `logger.warn`**、节流只限**日志频率**、被压次数经 `suppressedInWindow` 带出 —— 这两点合规。**残留**：`_harmlessSeen`（累计计数）**只写不读**（全仓 3 处引用全是它自己：声明 + 自增两行）⇒ 「累计次数」只活在内存里、任何人读不到 = 「过滤」在第二层退化成「静默丢」。**已改**：首次 + **每 100 次**各留一条（`{ message, seen }`），计数有出口且日志频率受控。

### 8.3 ④`ErrorBoundary`：**不越权**，维持不拆

- 它不是「消费者替生产者定行为」：React 的错误边界是**框架规定的唯一合法承载者**（owner），节点级降级是工程必需兜底；
- 按铁律第 4 条「确需兜底必须留痕」：`componentDidCatch` 已 `logger.error`（含 `componentStack`）✅。
- **仅记一处小瑕疵（本轮未改，属 UI 行为，另立）**：`handleReload` 只把 `hasError` 清回 false、不重置子树任何状态 ⇒ 同一个**必然再抛**的子组件会立即再次崩溃，用户观感是「点了重新载入没反应」。

## 九 · TD-16-37 施工轮（同日）—— ErrorBoundary「重新载入」：先把机制测准，再决定补什么

### Step 1/2 取证：债文的**机制描述不成立**（探针实测）

债文：「`handleReload` 只把 `hasError` 清回 false、**不重置子树任何状态** ⇒ 同一个必然再抛的子组件会立即再次崩溃」。

实测（临时探针，跑完即删）：子组件持内部 state（点击计数），先点到 `1` → 打开 boom 开关让其自身重渲染抛错 →
边界捕获 → 清错误位重载后读回：**`n` 回到 `0`**，且组件体**重新执行**（mount 计数增加）。
⇒ React 在边界进入 fallback 时**卸载了出错子树**，清 `hasError` 后是**重新挂载**，子树内部 state 随之归零。
**「不重置子树任何状态」证伪** —— 机制不是缺陷所在。

### 真实缺陷（收窄后）

重试**失败时界面零信息**：根因在子树之外（store／父级数据／props／环境）时，重新挂载必然立刻再抛 ⇒
用户看到的是**与首次崩溃一模一样的一张图**，无法区分「按钮没反应」与「重试了、又失败了」。
且按钮文案承诺"重新载入"，而它实际只**重置出错子树**（不是重载页面）—— 承诺与实现在文案层面也不吻合。

### 施工（Step 6）

- `state.retryCount` + `handleReload` 自增：把"重试过"变成**可计数状态**，而非无痕动作。
- **失败可见**：两个粒度各自升级文案 —— node：「已重试 N 次仍出错」；full：
  「已重试 N 次仍出错。「重新载入」只重置出错的界面子树；仍失败说明问题来自画布数据或运行环境，请用下方「强制刷新」。」
- **日志**：`componentDidCatch` 在 `retryCount > 0` 时事件名改为「重试后再次崩溃」并带 `retryCount`
  ⇒ 崩溃循环在日志侧可直接识别（不必靠用户口述"点了好几次"）。
- 文件头 JSDoc 写清「重新载入」到底是做什么的（含本次实测结论），防后来者照旧债文再"修"一遍。

### 合同变更 / 新增用例（`tests/unit/errorBoundary.test.tsx` 4 → 7）

1. 「重试仍失败必须可见：明说『已重试 N 次仍出错』」（node 粒度，连点两次验 1→2）；
2. 「full 粒度重试仍失败：给出根因说明 + 引导『强制刷新』」；
3. **「『重新载入』= 重挂载出错子树（实测锁定：子树内部 state 归零）」** —— 锁的是按钮**承诺**的兑现方式：
   若将来有人改成"保留子树实例"，坏状态会复活、重试就真成"没反应"；
4. 既有恢复用例补断言：重试**成功**时不得出现「已重试」提示（不许乱喊）。

### 追加修正（同日 · 用户裁定「只有生产者才有权呈现错误」）

本节施工里我**越权**了：给 full 崩溃页写了「…仍失败说明问题来自画布数据或运行环境，请用下方「强制刷新」。」

- **错在哪**：`ErrorBoundary` 是**转发者 / 承载容器**，而那句话是个**因果结论** —— 没有任何生产者提供它；
  它还与组件自己的知识矛盾（渲染里**必然**抛的 bug 同样"重试必败"，与数据/环境无关）。后果是用户与后来的
  开发者**按错误方向排查**，且它把真原因盖住（真原因在「错误详情」里由抛错方给出）。
- **已撤除**：边界现在只陈述**它自己生产的事实** —— `已重试 N 次仍出错。`；"下一步做什么"交既有按钮承担，
  不再自造指导语。
- **已立红线**：`CLAUDE.md §5.1` 新增「**只有生产者才有权呈现错误**」（判据：写用户可见失败文案前先问
  「这句话断言的事实是谁生产的？」；三条禁止；两条实证 —— 本节 与 §八 全局降级窗口越权）。
- **用例随之改向**：`tests/unit/errorBoundary.test.tsx` 该条从"断言有引导语"改为**锁"不许解释原因"**
  （`queryByText(/问题来自|说明问题|根因|原因是/)` 必须为 null）。
