## 一、Step 1 · 证伪（重新取证）

**症状确认**：`contracts.ts:93-98` 的 `agent:credit-gate` 条目 `from: []` / `to: []`（虚假标死）。

**真实站点（grep 常量名，非事件名字面量）**：
- `useCanvasAgentTools.ts:1464` `publish(CREDIT_GATE_EVENT, { pending: true })`
- `useCanvasAgentTools.ts:1550` `publish(CREDIT_GATE_EVENT, { pending: false })`
- `AgentPanel.tsx:577` `subscribe(CREDIT_GATE_EVENT, ...)`

**结论**：真债。登记表**声称无发布无订阅**，实际 2 发布 + 1 订阅。

---

## 二、Step 2 · 归因（母体 —— 这是本轮核心）

**不是孤例**。追问"为什么登记表能长期虚假而闸不报"→ 读 `check-events.mjs`：

> 反向校验的事件名正则 `LITERAL_EVENT_RE` **只匹配字面量** `fn('event:name'`。
> 凡事件名经 `const` 常量引用（`publish(CREDIT_GATE_EVENT, ...)`）的站点，**全部落在守卫盲区**。

`contracts.ts:97` 的 note 自白：「经常量 `CREDIT_GATE_EVENT` 引用（P1-D），**非字面量故反向校验跳过**」—— 盲区的**书面证据**。

> **母体 M2 变体**：「唯一入口/唯一真源**有守卫，但守卫有盲区**」—— 守卫形同虚设比无守卫更危险（它给出"已校验"的错觉）。
> 只填 `from/to` 而不补盲区 → 下一个常量引用事件必再漂移（"没有机器守卫必回潮"）。

## 三、Step 3 · 定位（五问）

| 问 | 答 |
| --- | --- |
| ① 真源在哪 | 事件名字面量（`const X = 'a:b'` 的右值）；事件名常量是**唯一间接层** |
| ② 变化速率 | 事件名/站点随代码变；守卫须随代码重新取证（非缓存） |
| ③ 几种实现 | 守卫 1 处（`check-events.mjs`）；只在字面量路径+常量路径各一份解析 |
| ④ 改动半径 | **2 文件**（contracts.ts 填站 + check-events.mjs 补盲区） |
| ⑤ 接口窄不窄 | 常量解析 = 一个前置 map + 主循环复用同一 `pushLoc`/`isRegistered` → 窄 |

**动作**：① 数据修正（填真实站点）；② **收敛守卫**（消除常量盲区，一次堵死同型回潮）。

## 八、方法论沉淀

1. **母体往往藏在"守卫自己"里**：症状是"登记表虚假"，根因是"闸有盲区"。只修数据（填站点）是治标；补闸才是治本。
2. **守卫有盲区比无守卫更危险**：`check:events` 的存在让维护者以为"表已被校验"，实际常量引用全程失守 —— 登记表的 note 甚至把盲区写成"设计"（"非字面量故跳过"）。**盲区的自白就是母体的地址**。
3. **双探针证守卫**：一个探针证明"能看见"（滞后）、一个证明"fail-loud"（未登记），才算真守住。
