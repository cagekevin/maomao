# 区域 03 · 三轮 · 底层正确性与「兜底掩盖错误」专项审计

> 日期：2026-09-12 ｜ 方法：从最底层 `fileStore`/`base64Externalize`/`mime` 上钻，逐层验证正确性、复杂度、兜底是否掩盖了真实错误。
> 范围：`filesApi`(前端桥) → `httpClient` → `files.ts`(路由) → `fileStore`(落盘原语) → `base64Externalize`(JSON 分支) → `mime`(映射) → `parseMultipart`(事实核验) → `database.ts`(约束核验)。
> **本轮只落盘结论，不触生产代码。**

---

## 一、已验证的正确性强项（先记正面，避免只报忧）

- **路径穿越已闭合**：`sanitizeFilename`（fileStore.ts:36）把 `/ \` 都换成 `_`，`normalizeSubfolder`（fileStore.ts:58）拒绝 `.`/`..`/绝对形式，`resolveUploadFile`（fileStore.ts:104）对既有路径再 `path.relative` 校验仍在 uploads 内。filename 里的 `..` 经 sanitize 变字面 `..foo`，非路径段，安全。
- **contentId 跨入口一致**：multipart(`writeUploadDedup` fileStore.ts:213)、远程(`doSaveRemoteUrl` files.ts:281)、base64(`saveBase64ToFile` base64Externalize.ts:69) 三者均按 **`sha1(decodeBytes)`** 算 contentId，去重权威统一。这是前几轮 TD-03-1/2/3 的根因修复成果，已坐实。
- **并发下载只真下一份**：`inflightDownloads` Map（files.ts:69）+ 文件级 `fs.existsSync` 幂等配合得当，注释语义自洽。

## 二、正确性缺陷（实证）

### TD-03-7｜缩略图失败回退 `copyFileSync` 产出「假缩略图」（错误被兜底成错误结果）

`resizeImage`（fileStore.ts:255）失败时 `catch → return false`。两处调用方据此做了**回退复制原图**：

- `tryGenerateThumbnail`（files.ts:321）：`const ok = await resizeImage(...); if (!ok) fs.copyFileSync(filePath, thumbPath);`
- `handleThumbnail`（files.ts:406-407）：同构。

**后果**：jimp 因格式不支持 / 解码异常 / 资源紧张失败时，代码把**全尺寸原图**复制一份当缩略图返回。前端拿到 `/files/.../thumb_...` 却是一张未缩小的原图——缩略图机制在「失败时」产出与其语义相反的结果，且 `ok` 被吞掉、无日志可查。这是教科书级「用兜底掩盖错误、且产出错误输出」。注释引 docs/35§6、docs/19「兜底保留」为据，但「保留功能」不应以「返回非缩略图」为代价。

**建议方向（不代改）**：`resizeImage` 失败应返回 `null` 缩略图而非伪造一张。属于正确性 > 兼容性的取舍。

### TD-03-8｜multipart 上传丢弃 `mimeType`，无扩展名 Blob 落盘成「无扩展名文件」

`parseMultipart`（helpers.ts:137）已逐 part 解析出 `mimeType`（缺省 `application/octet-stream`），但 `handleUploadFormData`（files.ts:98-104）只用 `filename` 推扩展名：

```98:104:localTool/src/routes/files.ts
const saveName = filename || fileData.filename;
const db = await getDb();
const dedup = await writeUploadDedup({
  subfolder,
  ext: path.extname(saveName),   // ← 仅从文件名取 ext，fileData.mimeType 完全没用
  data: fileData.data,
  ...
```

`writeUploadDedup` → `contentHashName(hash, ext)`（fileStore.ts:129）在 ext='' 时返回**纯哈希无扩展名**文件。于是：

- `uploadFileToLocal(file)` 的两参默认调用（`filename` 未传）+ 一个无 `.name` 的 `Blob`（典型如 `canvas.toBlob`、程序生成的 `Blob`）→ `saveName = (file as File).name || 'upload'`（filesApi.ts:207）→ `'upload'`（无 ext）→ **落盘文件无扩展名**。
- 后续 `handleRead`（files.ts:348）`extToMime('')` → `application/octet-stream`，浏览器按二进制处理，**图片/视频可能无法正确渲染**。
- `tryGenerateThumbnail`（files.ts:315）`imageExts.includes('')` 为假 → **跳过缩略图**，`thumbnailUrl` 为空。

**根因**：扩展名**只**从文件名推断，手边的 `fileData.mimeType` / 下载态 `response.headers content-type` 都未作为 ext 回退来源。远程分支 `doSaveRemoteUrl`（files.ts:278-279）`ext = needsExt ? mimeToExt(mime) || '' : ...` 同理——未知 MIME 且无 URL 后缀时 ext='' → 同样无扩展名落盘（同族缺陷）。

**影响面**：`uploadFileToLocal` 被 depthVideo / videoEngine / director3d / 拖放上传共用，`canvas` 系生成物最易踩中。属潜在正确性回归。

### TD-03-9｜base64Externalize 物理命名与 canonical 命名不一致（被 contentId 去重掩盖的复杂度）

- canonical 落盘命名：`contentHashName(sha1(bytes))`（fileStore.ts:129），全 40 位 hex + 扩展名。
- `saveBase64ToFile`（base64Externalize.ts:76）：`const hash = crypto.createHash('sha1').update(base64Data).digest('hex').slice(0, 16);` —— 用的是 **`sha1(base64 *文本*)` 前 16 位**，而非字节哈希。

同一字节内容，经 multipart 上传落 `…/<sha1bytes>.png`，经 KV 外置落 `…/<sha1b64text16>.png`，**物理文件名不同**。当前仅因 `saveBase64ToFile`（base64Externalize.ts:68-73）先按 contentId 查 `resources` 命中既有的 `…/<sha1bytes>.png` 行并返回其 url，才没出现两份文件——即该 16 位命名实质上只充当「本地 `fs.existsSync` 幂等键」，去重权威已被 contentId 接管。这是**遗留冗余 + 注释称"保持 URL 契约/测试不变"但与全局命名规范背离**，属维护期复杂度/一致性隐患（非运行时 bug，但易误导后续改者）。

### TD-03-10｜fileStore 注释声称的「DB contentId 唯一约束」根本不存在（doc 与实现矛盾）

- fileStore.ts:14-16 注释：「并发去重真保证 = DB 对 contentId 列加唯一约束 + 冲突回退」。
- 但 `database.ts:330` 显式 `DROP INDEX IF EXISTS idx_resources_sha1`，并声明（database.ts:326-329）：「不再依赖 DB UNIQUE 约束兜底——该约束会在『同内容被不同路径引用』时误杀合法复用（撞约束→500）」。

实际并发去重保证来自 **content-hash 文件名幂等**（`fs.writeFileSync` 同字节覆盖同名文件）+ `inflightDownloads` 同进程并发锁，与注释所述机制不符。注释是 stale 的，会误导审阅者以为有 DB 约束兜底。

## 三、「用过多兜底掩盖错误」的结构性观察（设计层）

### TD-03-11｜`httpClient` 吞掉非 JSON 错误体

`httpClient.ts:198`：`const data = await res.json().catch(() => ({}));`。当后端返回非 JSON 的 4xx/5xx（崩溃页、代理错误、nginx 兜底），`res.json()` 抛错被吞成 `{}`，随即 `extractErrorDetail({})` → `{ code:'UNKNOWN', message:'' }`。**真实错误报文在此被清空**，上游只拿到一个空 message 的 `HttpError`。filesApi 各函数再 `catch → null + warn`，错误语义彻底丢失。files 路由的 `sendError` 走 JSON 故常规路径 OK，但「后端异常态」下不可见。

### TD-03-12｜`httpRequest` 把任意 `TypeError` 当成可重试网络错误并重抛为 `NetworkError`

`httpClient.ts:235`：`const retryable = e instanceof NetworkError || isTimeoutError(e) || err?.name === 'TypeError';`。任何 `TypeError`（含**代码 bug**，如调用未定义函数、属性访问越界）都会被判定为「网络失败」并重试最多 3 次；耗尽后 `httpClient.ts:242` 又把它 `throw new NetworkError(...)` 重分类。结果：真实编码错误被伪装成网络错误，类别被篡改、排障被引偏。

### TD-03-13｜filesApi 全函数「失败返回 null 不抛 + warn」—— 持久化失败系统性无用户信号

`filesApi` 8 个落盘/访问函数一律 `catch → return null` + `logger.warn`，调用方「降级保持原 URL/内联」。其中 `resolveNodeAssetUrl`（filesApi.ts:254-256）/ `persistInlineOrKeep`（filesApi.ts:270-272）在内层还**二次兜底回退内联**——即「上传失败」连 warn 之外的任何信号都没有，节点数据静默保留 base64（虽由 `base64Externalize` 在下次 kvSet 重新外置，最终一致，但用户/会话内无错误可见）。

这是区域 03 内**兜底密度最高、最易掩盖错误**的位置：本地后端挂掉时，每一次图片入节点都静默退化为内联，无报错、无重试提示。属**有意为之的设计权衡**（落盘是「优化非前提」），但符合用户所问「在合适的位置是否过多兜底掩盖错误」——答案是：**技术正确性无破坏，但可观测性/故障可见性在此被刻意弱化**，应作为已知权衡登记，而非默认「健康」。

---

## 四、结论

- **正确性硬伤 2 条**：TD-03-7（假缩略图，错误→错误结果）、TD-03-8（无扩展名 Blob/未知 MIME 落盘，octet-stream + 无缩略图）。两者都是「兜底回退」直接产出了**语义相反的输出**。
- **复杂度/一致性 2 条**：TD-03-9（base64 命名分歧）、TD-03-10（注释与 DB 实现矛盾，stale 约束声称）。
- **错误掩盖结构性 3 条**：TD-03-11（吞错误体）、TD-03-12（TypeError 伪装网络错误）、TD-03-13（持久化失败全局静默）。
- **正面**：路径穿越闭合、contentId 跨入口统一、并发下载锁自洽——前几轮去重根因修复已坐实。
