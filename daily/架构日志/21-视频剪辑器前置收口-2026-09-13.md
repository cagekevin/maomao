| 原语默认 | `captureFrame.ts:192-193` → `if (waitForLoad === false) begin(); else video.addEventListener('loadeddata', begin, { once: true })` → 默认**等 `loadeddata`** |
| **原 hook 的真实语义** | 原实现用 `v.onloadeddata = () => { v.currentTime = 0.05 }` —— **它本来就等 `loadeddata`**。→ **② 的就绪度判据未被改动**（"原 hook 不等待"只成立于 ⑤，不成立于 ②） |
| 归属结论 | `waitForLoad` 不是"原语的判据"，是**宿主就绪度判据的参数化**（②①③ 自建元素→等；⑤ 宿主自备元素→不等，两者相反故必须显式）。故此前报告"判据全部留在宿主"应精确为：**帧语义判据**（时刻 0.05 / 原尺寸 / jpeg 0.7 / 失败静默回退 / cleanup）全留宿主；**就绪度判据**由宿主经 `waitForLoad` 声明。 |

**问：那处异常差异（`currentTime` 抛异常）的实际走向？**

**答：分两支，取决于当时尺寸；两处都已用测试锁住。**（`captureFrame.ts:182-186`：`try { video.currentTime = target } catch { draw() }`）

| 支 | 触发条件 | 走到哪一步 | 与"原 hook 静默 `''`"的关系 |
| --- | --- | --- | --- |
| A | 抛异常 **且** `videoWidth/Height > 0` | `draw()` → 尺寸检查过 → `canvas.toBlob/toDataURL` → **产出封面** | **差异成立**（原 hook 此时为 `''`）→ 就是"更可用"的那支 |
| B | 抛异常 **且** 尺寸为 0 | `draw()` → `fail(dimensions)` → reject → 宿主静默 catch → `''` | **与原 hook 观测等价**（都是 `''`）→ **这不是新差异，而是 ④① 指出的缺口**（原语无"就绪但 0 尺寸"防御） |

- **达到该路径的前提**：`waitForLoad=true` ⇒ `begin()` 在 `loadeddata` 之后跑 ⇒ 尺寸应 > 0 ⇒ 设 `currentTime` 一般**不抛**（能抛的场景：不可 seek 的媒体 / `readyState` 异常的实现差异）→ **该差异属窄条件**，故必须用测试锁（否则会漂）。
- **新增 3 例差异锁**（改坏 `catch { draw() }` → **3 例精确红**）：
  1. 原语级：抛异常 + 尺寸可用 → 仍绘制（`expect(lastCanvas.drawImageArgs).toHaveLength(1)`）
  2. 原语级：抛异常 + 尺寸为 0 → `rejects.toThrow('captureFrame: zero dimensions')`（**缺口证据**）
  3. 宿主级：`useVideoPoster` 抛异常 → `expect(result.current).toMatch(/^data:image/)`（**锁定②的差异**）

### 8.3 未结项（状态 = **待证据 → 待审核拍板**）

| 它是**帧基** | `contentWidth = totalFrames * pxPerFrame`（:128）· `clientX / pxPerFrame`（:234/:250/:304）· `frame * pxPerFrame`（:227/:419/:440/:466/:554）；标尺 `rulerStep` 也以**帧**为单位（:155-162） |
| `fps` 是**刻意未用**的 | 组件签名 `fps: _fps`（:100）—— 它按设计就是帧原生，其 store（关键帧）亦以 `frame` 为键 |
| 框选不是矩形相交 | 命中判定是**一维邻近**：`Math.abs(x - item.frame * pxPerFrame) < radius`（:227/:309）；`.timeline-marquee` 只是**视觉盒子**（min/abs，非相交判据）→ `rectsIntersect` 在 3D 域**没有重复实现**可收 |
| 无测试覆盖 | `tests/unit/` 仅 `director3d.cameraAtFrameWithPath` / `trackByWriteParity`，与本组件换算无关 |

**结论（Step 1 证伪 + Step 3 五问）**：本域与共用层之间**没有「同一算法的两份实现」**——
`x = t * pps`（秒基）与 `x = frame * pxPerFrame`（帧基）是一次乘法的**单位换算**，不是可漂移的算法。
强行迁入需把 `fps` 穿透进一个刻意不用它的组件、并在 6+ 处加换算层 ⇒ **改动半径变大、复杂度上升、收益 0**
（Step 3 判据：*「若半径没变小，我只搬了家」*），且无测试可保证行为不变。
⇒ 按 *「判据/宿主不同 → 保留分层」* **不迁**；共用层仍服务 `nodes/` + `videoEditor/` **两域**（非假接缝）。
