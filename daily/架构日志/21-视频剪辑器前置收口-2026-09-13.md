| 原语默认 | `captureFrame.ts:192-193` → `if (waitForLoad === false) begin(); else video.addEventListener('loadeddata', begin, { once: true })` → 默认**等 `loadeddata`** |
| **原 hook 的真实语义** | 原实现用 `v.onloadeddata = () => { v.currentTime = 0.05 }` —— **它本来就等 `loadeddata`**。→ **② 的就绪度判据未被改动**（"原 hook 不等待"只成立于 ⑤，不成立于 ②） |
| 归属结论 | `waitForLoad` 不是"原语的判据"，是**宿主就绪度判据的参数化**（②①③ 自建元素→等；⑤ 宿主自备元素→不等，两者相反故必须显式）。故此前报告"判据全部留在宿主"应精确为：**帧语义判据**（时刻 0.05 / 原尺寸 / jpeg 0.7 / 失败静默回退 / cleanup）全留宿主；**就绪度判据**由宿主经 `waitForLoad` 声明。 |

**问：那处异常差异（`currentTime` 抛异常）的实际走向？**

**答：分两支，取决于当时尺寸；两处都已用测试锁住。**（`captureFrame.ts:182-186`：`try { video.currentTime = target } catch { draw() }`）

| 支 | 触发条件 | 走到哪一步 | 与"原 hook 静默 `''`"的关系 |
| --- | --- | --- | --- |
| A | 抛异常 **且** `videoWidth/Height > 0` | `draw()` → 尺寸检查过 → `canvas.toBlob/toDataURL` → **产出封面** | **差异成立**（原 hook 此时为 `''`）→ 就是"更可用"的那支 |
| B | 抛异常 **且** 尺寸为 0 | `draw()` → `fail(dimensions)` → reject → 宿主静默 catch → `''` | **与原 hook 观测等价**（都是 `''`）→ **这不是新差异，而是 ④① 指出的缺口**（原语无"就绪但 0 尺寸"防御） |

- **达到该路径的前提**：`waitForLoad=true` ⇒ `begin()` 在 `loadeddata` 之后跑 ⇒ 尺寸应 > 0 ⇒ 设 `currentTime` 一般**不抛**（能抛的场景：不可 seek 的媒体 / `readyState` 异常的实现差异）→ **该差异属窄条件**，故必须用测试锁（否则会漂）。
- **新增 3 例差异锁**（改坏 `catch { draw() }` → **3 例精确红**）：
  1. 原语级：抛异常 + 尺寸可用 → 仍绘制（`expect(lastCanvas.drawImageArgs).toHaveLength(1)`）
  2. 原语级：抛异常 + 尺寸为 0 → `rejects.toThrow('captureFrame: zero dimensions')`（**缺口证据**）
  3. 宿主级：`useVideoPoster` 抛异常 → `expect(result.current).toMatch(/^data:image/)`（**锁定②的差异**）

### 8.3 未结项（状态 = **待证据 → 待审核拍板**）

| 它是**帧基** | `contentWidth = totalFrames * pxPerFrame`（:128）· `clientX / pxPerFrame`（:234/:250/:304）· `frame * pxPerFrame`（:227/:419/:440/:466/:554）；标尺 `rulerStep` 也以**帧**为单位（:155-162） |
| `fps` 是**刻意未用**的 | 组件签名 `fps: _fps`（:100）—— 它按设计就是帧原生，其 store（关键帧）亦以 `frame` 为键 |
| 框选不是矩形相交 | 命中判定是**一维邻近**：`Math.abs(x - item.frame * pxPerFrame) < radius`（:227/:309）；`.timeline-marquee` 只是**视觉盒子**（min/abs，非相交判据）→ `rectsIntersect` 在 3D 域**没有重复实现**可收 |
| 无测试覆盖 | `tests/unit/` 仅 `director3d.cameraAtFrameWithPath` / `trackByWriteParity`，与本组件换算无关 |

**结论（Step 1 证伪 + Step 3 五问）**：本域与共用层之间**没有「同一算法的两份实现」**——
`x = t * pps`（秒基）与 `x = frame * pxPerFrame`（帧基）是一次乘法的**单位换算**，不是可漂移的算法。
强行迁入需把 `fps` 穿透进一个刻意不用它的组件、并在 6+ 处加换算层 ⇒ **改动半径变大、复杂度上升、收益 0**
（Step 3 判据：*「若半径没变小，我只搬了家」*），且无测试可保证行为不变。
⇒ 按 *「判据/宿主不同 → 保留分层」* **不迁**；共用层仍服务 `nodes/` + `videoEditor/` **两域**（非假接缝）。

| # | 缺陷 | 说明 |
| --- | --- | --- |
| 1 | **「哪些是新选中」有两个真源** | 旧写法同时读 `useStore` 的**渲染期快照**（`selectedSig`）与 effect 里 `flow.getNodes()` 的**实时值**。两者在一次提交内可以不一致（快照落后于 store），于是「上次没处理过 n1」成立了**两次** |
| 2 | **入轨 effect 每次渲染都跑** | 依赖里有 `enqueue`，而它依赖 `store` —— 而 `useEditorProject` **每次渲染都返回新的 store 对象** ⇒ `enqueue` 每次换身份 ⇒ effect 每次渲染重跑。这是缺陷 1 的**放大器**（把「有机会不一致」变成「每帧都在比较」） |

**修法（结构解，不是补丁）**

1. **单一真源**：该不该入轨**只看签名之间的差**（`selectedNodeIdsOfSig`）—— 不在签名里的 id **永远不会**被入轨；节点详情只按签名已声明过的 id 取用。第二次读被彻底删掉。
2. **把「上一个签名」换成「已处理集合」**（`handledRef: Set<nodeId>`）：`fresh = 本次签名里的 id − 已处理集合` 是**幂等**的 —— effect 多跑几次也只会入一次。
3. **依赖收敛**：flow / store 经 ref 传入（只求「最新值」，不求「参与依赖」），`enqueue` 依赖空数组 ⇒ effect 依赖只剩 `[selectedSig, open]`，**运行次数与语义对上**。
4. **签名的逆运算住在产生它的模块里**（`base/canvas/nodeMedia.ts::selectedNodeIdsOfSig`，紧邻 `selectedAssetSig`）：格式知识不留两份 —— 解析端写在消费者那儿，格式一改必静默算错 id。

**先红后绿（实证）**

| 步骤 | 结果 |
| --- | --- |
| 先写复现测试 `tests/unit/videoEditor/dockEnqueue.test.tsx`（按真机时序：快照落后 = 第 1 次提交 `getNodes()` 已看到选中、快照仍空） | **红**（修复前）：`expected "spy" to be called 1 times, but got 2 times` —— 与用户现象一致 |
| 应用修法 1–4 | **绿**：3 例全过（含「取消后再点 = 再得一条」C11.4 的另一半、以及折叠态不动作 C11.5） |
| `tests/unit/nodeMedia.test.ts` 补 `selectedNodeIdsOfSig` 4 例 | **绿**（往返一致 / 空签名 / url 里的 `:` / 重复条目只算一个） |

**门禁**：`check:arch/dead-code/any/catch/strict-src/keys/upload-dirs/events` ✅ · `type-check` ✅ · `eslint` ✅ · **全量单测 209 文件 / 2706 例** ✅。

**度量**

| --- | --- | --- |

### 17.2 关键判断（结构 · 自行拍）

| # | 判断 | 依据 |
| --- | --- | --- |
| 1 | **`buildFilmstrip` 落 `captureFrame.ts`**（该文件自述「消费方：时间线胶片条抽缩略图；视频剪辑器可直接复用」） | 它不是「某域怎么显示缩略图」，而是**抽帧能力的第二种输出形态**（拼成一条）。放这里，`drawVideoFrame` 仍是「seek + drawImage」的唯一实现，本函数只是它的组合用法 —— 不新建平行模块 |
| 2 | **一个 `<video>` 抽 N 帧**（而非 N 次 `captureFrame`） | `captureFrame` 每次调用都**新建元素 + 重新加载整条素材**；N 帧 = N 次加载。复用同一元素只反复 seek ⇒ 一次加载。这正是既有 ⑤ 的模式（`waitForLoad` 首帧 true、其后 false） |
| 3 | **`duration` 必传**（不从元素现读） | 调用方本来就知道它（它就是「这个片段有多长」的同一件事实）。让本函数再读一次 = 同一事实第二个来源 |
| 4 | **缓存 Blob（会话级），对象 URL 按挂载生命周期** —— 刻意**不用** `previewUrls` | `App` 在**切项目**时会 `previewUrls.clear()`（`App.tsx:515/531`）→ 会 revoke 掉所有对象 URL。而本缓存是**跨工程**的（同一份 `/files/` 素材不因换工程而变），一旦被 revoke 就是死链且**不回滚**。两者生命周期不同，不能共用一个管理器 |
| 5 | **缓存键含帧高** | 换了行高（C7.5）必须重抽，否则把按 24px 拼的图拉成 40px —— **不报错的错** |
| 6 | **抽不到就留空，不填占位图案** | C11.7b 原话：「用固定图案冒充波形会被读成真实音量，属于撒谎」。同理，给视频填假缩略图会被读成「这一镜就是这个画面」 |
| 7 | **映射的时长用 `max(0, sourceEnd − sourceStart)`**（与 `core/timelineOps.clipDuration` **同一公式**） | 片段盒子宽度 = `clipDuration × pps`；映射若自行夹取（如把负入点夹到 0 再算），两处时长分歧 ⇒ **图片与盒子对不上且不报错** |
| 8 | 图片片段显示**素材本体**（`contain`），不抽帧 | 图片没有时间维度，抽它是白费；`contain` 而非 `cover` —— C11.10 明确「`object-cover` 会把关键内容裁掉」 |
