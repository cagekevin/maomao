## 二、溯源（Phase 1：症状 vs 病根）

- **底层是否承载**：ai-relay/protocol 是从 AI-Canvas-tauri 整体搬迁的声明式协议引擎，本区域承接后无病态扩展——协议校验把「不可信输入」在**进入点**（validation.ts）洗净，下游（request/engine/poll）只消费已校验数据。这是标准的**源头收敛**（Phase 1 正例），不是末端补丁。
- **中上层症状**：`resolveBaseUrl` 在 generateEngine.ts 与 relay-poll.ts **各写一份**（逐字近似）；`resolveApiKey` 一处是函数、一处是内联表达式。同语义两处实现 = 单一规则原则（CLAUDE §5.4.9）违反——虽暂未漂移，但两文件一旦各自演化（如一个加配置兜底、一个不加）必然重现「modelscope 未配置接口地址」式回归（2026-09-03 已发生过一次）。这是**症状**，根因 = baseUrl/key 解析该归属 provider 配置域（providerConfigStore）而未归属。
- **退役残留**：`persistThreadId`（/api/proxy 时代 0 调用者）与 `deleteLocalFile`（生产 0 引用）未被 docs/105 退役手册（2026-09-05）实际执行删除；`/api/proxy` 退役后 index.ts 横幅/注释、resolveLocalImages.ts 头注释、generateEngine.ts gzip 注释仍指旧链路。属「退役未闭环」症状。

## 三、定海（Phase 2：不变式 / 唯一真相源）

- **SSOT 唯一**：tasks 表是任务真相（upsertTask 唯一写库，relay-poll 全部经它，禁裸 UPDATE）；request_data._relayPoll 快照是轮询句柄持久态，DB 持久态即真相、不依赖内存。✓
- **key 只驻内存**：apiKey 不入库（resolveProviderApiKey 从 .env 按 `API_PROVIDER_{ID}_KEY` 读），重启按 providerId 重读。✓
- **边界 Guard**：协议层 validation.ts 全量校验（白名单变量/同源/Header/数值边界），错误按 `{code,data}` 信封或上游原文透传（不翻译、不掩盖）。✓
- **超时铁律**：relayGenerate 10min 总超时（makeTimeoutSignal）、relay-poll DEFAULT_TOTAL_TIMEOUT_MS 10min + DIRECT_SUBMIT_TIMEOUT_MS 180s + MAX_CONSECUTIVE_POLL_ERRORS 30，失败可见不静默挂起。✓

## 四、切割（Phase 3：深模块 / 真缝隙 / 收敛口）

- **深模块**：ai-relay/protocol 窄接口（protocol/index 8 组导出）× 厚实现（validation 584 行/engine/poll），是真深模块。relay-poll 句柄管理器同理（窄的 submit/status/cancel 三入口）。
- **第二份真相（本次修复）**：`resolveBaseUrl` ×2 + `resolveApiKey` 内联/函数双形态 = 同语义两处实现。**抽唯一实现到 providerConfigStore.ts**（provider 配置唯一读写入口，职责匹配）：`resolveProviderBaseUrl`（override → 配置文件 base_url → 内置目录 defaultBaseUrl，含 2026-09-03 modelscope 修复语义）+ `resolveProviderApiKey`（override → `API_PROVIDER_{ID}_KEY`）。generateEngine / relay-poll 全部委托。
