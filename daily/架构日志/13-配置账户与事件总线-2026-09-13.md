## 一、链路快照（refs 实证，非凭文件名猜）

本域不是单一「产生→落盘」链路，而是**三组横切契约 + 各自 store**：

```
① 横切契约地基（contracts.ts）
   EVENTS         —— 事件总线注册表（eventBus 的单一事实来源）
   STORAGE_KEYS   —— 存储键登记表（红线：新增键先登记，禁散字面量）
   NODE_TYPES / NODE_HANDLE_CONTRACT / SHOT_HANDLE_PREFIX / apiRegistry / GEN_ERRORS
   ⇅ settingRegistry.ts（设置声明表，app_settings 默认值/UI/云同步三派生 SSOT）

② 配置/账户 store 层（均「模块级 state + useSyncExternalStore」，经 contentStore 落盘）
   appSettings.ts      ← AgentChatSettings/ApiSettings/OtherSettings（KEY=app_settings, backend:local）
   accountsStore.ts    ← AccountsPanel（KEY=yimao_accounts, backend:kv，仍进云同步）
   providerStore.ts    21 处 fan-in（AgentChatSettings/ApiSettings/GearSettings/useScriptBoxEngine/useGenerateNode…）
                         写盘后额外 contentSetAsync('active_api_endpoint') 回写 KV（backend:kv，供后端 official.ts/passthrough.ts 路由）
   agentModelStore.ts  ← AgentPanel（agent_chat_model / agent_history_turns，backend:local）
   skillStore.ts       ← SkillSettings/AgentPanel（agent_skills / agent_skill_usage / agent_skill_enabled）
   nodeRuntimeStore.ts ← 各节点（纯内存瞬态 map，不落盘）

③ 通信层
   eventBus.ts（subscribe/publish 唯一通道）<—— contracts.EVENTS 登记
```

DATAFLOW.md 现状：① 的 EVENTS/STORAGE_KEYS 仅在 contracts.ts 内联，**DATAFLOW.md 无独立「配置/账户/事件总线」段**——本域此前不在这张进度地图上（漏绘，非漂移）。② 的 store 零散出现在各业务段（如 providerStore 在「生成链路」、accountsStore 在「云同步」）。③ eventBus 全仓仅 1 处注释引用、无 DATAFLOW 节点。

## 二、溯源（Phase 1：症状 vs 病根）

- 三组契约（EVENTS / STORAGE_KEYS / settingRegistry）设计意图健康：均收口为「静态声明表 + 派生」，明确「新增先并表，禁另起新表」（contracts.ts:1-5、settingRegistry.ts:1-5）。
- 但**登记表本身的「准确性」依赖人工维护 file:line**，eventBus 铁律已自承「行号靠人工维护会漂移、可能滞后于代码」（contracts.ts:54-60）。这导致「登记表说无引用」与「代码实测有引用」可冲突——正是本轮 TD-13-1 的病根，不在业务代码，而在**契约登记机制缺机器守卫**。
- 账户域 `yimao_accounts` 明文 Cookie 进云同步是**产品决策（docs/73 已裁定保留）**，非代码 bug，但属未登记的隐私债（TD-13-3）。

## 三、定海（Phase 2：不变式 / 唯一真相源）

- EVENTS 的「发布/订阅须成对」是不变量，但**登记表不强制校验**：`from/to` 可填 `[]`（=「跳过/未知」），与「死事件（真无引用）」语义混用，无机器区分（TD-13-1）。
- STORAGE_KEYS 红线（禁裸字面量键）较健康：`active_api_endpoint`/`yimao_accounts`/`agent_chat_model` 等**均已登记**（refs 实证），未发现绕过登记表的裸键。
- `active_api_endpoint` 是 primary provider 信息的**派生缓存**（前端写、后端 official.ts/passthrough.ts 读做路由）：属跨端派生，非「第二真相冲突」——KV 写失败仅 `logger.warn` 降级，下次 save 自愈。判为**设计权衡，非债**（留痕，防误改）。

## 四、切割（Phase 3：深模块 / 真缝隙 / 收敛口）

- 无上帝类；各 store 单一职责清晰（providerStore 215 行但职责边界清晰，未达 TD-01-7「拆子模块仅为美化」阈值）。
- 真缝隙 = **契约登记机制**（EVENTS/STORAGE_KEYS）无机器对账发布/订阅配对与键引用：这是 TD-13-1 与潜在未来漂移的母体，收敛口 = 给 `check:events`/新增 `check:registry` 加「EVENTS.from/to 每项须有真实 publish/subscribe 站点」校验（仿 `check:arch` 防回潮）。
