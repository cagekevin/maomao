## 二、真债与修法（4 条）

### ① `handleMkdir` 缺越根守卫（**安全级 · 唯一缺守卫的目录写入口**）

- **取证**：`path.join(uploadDir, body.folder)` 直拼，不拒 `..`、无顶层根白名单 → `{"folder":"../../x"}` 可把目录建到 uploads 之外。
  对照：`handleOpen` / `handleList` / 落盘早已共用 `normalizeSubfolder`；只有 mkdir 漏了。
- **修**：复用既有原语 `resolveUploadFile`（拒空 / `.` / `..`，且 resolve 后必须仍在 uploadDir 内）。
  **刻意不收紧为顶层白名单** —— mkdir 只建空目录（落盘仍受 `normalizeSubfolder` 白名单约束，那份判据只该住在落盘处），
  收紧会改动既有 mkdir 契约（首版收紧即打红既有用例 `Files·mkdir 创建目录`，已回退为最小守卫）。

### ② `rescan` 读不到 uploads 目录 → 报 `ok:true, count:0`（假成功）

- **后果**：权限/磁盘/目录被删时，面板显示成"空库"，发送链路以为没事 —— **真实故障被掩盖成正常态**。
- **修**：明确 `500`（`console.error` 留痕）。前端 `reset` 的 catch 分支留痕；`sendToResourceLibrary` 的 `rescanUploads` 只 warn、**不改写落盘结论**（TD-12-2 禁重分类仍成立）。

### ③ `saveBase64ToFile` 两类失败同返 `null` → handler 一律报 `400 Invalid dataUri`（错误归因）

- **后果**：磁盘满/权限问题被报成"格式不对"，排查被引偏（与 TD-03-12「代码 bug 被当网络错误重试」同族）。
- **修**：**非法输入 → `null`（400）**；**写盘系统故障 → 抛出（500 `Failed to persist dataUri`）**。
  降级型调用方（KV 外置：`externalizeObject` / `externalizeBase64InValue`）补 `try/catch` 保留原 base64
  —— 顺带把 `externalizeObject` 头注释里"逐字段 try/catch"从**谎报**变成事实（此前只有 null 判断，没有 catch）。

### ④ `handleResourcesBatchSave` 静默跳过无 id 项

- **修**：返 `{ok:true, saved, skipped}`（不再"我说存了"却不告诉调用方跳了几条）。低优先，但一行成本。

## 三、排除清单（**判为非债 · 防后人当 bug 补**）

| 候选 | 为什么不是债 |
| --- | --- |
| `probePort` → `null` | "无代理可用"是**答案**，不是失败 |
| `normalizeSubfolder` / `resolveUploadFile` → `null` | **守卫判定**（非法输入），调用方必须显式拒绝或回退 —— 这是正确的 fail-closed |
| `tryGenerateThumbnail` → `null` | 缩略图是**优化非前提**，且有 `console.warn` 留痕（TD-03-7 的既定语义） |
| `toUploadRelPath` catch → 原样返回 | 安全偏向：宁可少删盘（GC 宁可漏回收不误删） |
| `deleteProviderConfigFile` → `false` | bool 契约明确，调用方判值 |
| `handleResourcesDelete` 恒 `ok:true` | **幂等删除**（"确保不存在"）是 REST 惯例；前端不依赖 changes |
| `handleResourcesRename` 同名 → `ok:true` | 幂等（改名到同名 = 已是目标态） |
| `backupDb` 双语义 `null` | 失败**有 `console.error` 留痕**（:218），调用方不看返回值 → 可接受（登记注意：若将来要判"今天备了没"需拆分） |
| `contentSha1` → `null` | rescan 惰性回填的既定设计（缺列下次补） |
| `orphanGc` unlink 失败计 `skipped` | 有计数（可见）；GC 属清理类，不阻断 |
