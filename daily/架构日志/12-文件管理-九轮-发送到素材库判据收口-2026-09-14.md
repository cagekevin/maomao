## 三、Step 3/4 · 定位与定契

**三段顺序 = 真相顺序**（`sendToResourceLibrary`）：

```
① 落盘（必要时） persistUrlToUploads(url,{folder,name,type,projectId}) → {ok,url,source}
     · data: → saveInlineToLocal（后端校验+内容寻址）
     · 已是本机 /files/ → 'already-local'（**不重传**）
     · blob: → 前端 fetch → multipart（后端拿不到 blob:）
     · http(s) → 后端唯一「下载归属点」uploadRemoteFile（免 CORS/大文件不进前端内存）
     · 其它 → unsupported（明确失败，不猜）
② rescanUploads()  行由后端建（失败只留痕，**不改写落盘结论**）
③ relocateToFolder(url, folder)  context-only 改 resource 行 folder（复用 filesApi.moveFile）
     · 同目录 → 幂等短路；行不存在 → 404 → **relocate-failed**（不宣告成功、不留本地假行）
④ 登记（仅为本地缓存投影）+ emitResourceSent(folder) —— 此刻「文件 + 行 + 目录」三件齐备
```

**契约**：`PersistOutcome`（判别联合，`reason ∈ empty|unsupported|upload-failed|exception|relocate-failed`）
**定义在 filesApi**（拥有真相的层），resourceStore 仅 `export type { PersistOutcome }` → 消费方零改动。

## 八、结论

- 本区域状态：**有待还债**（TD-12-10/12-13 已结清 + 本轮收口；TD-12-11/12-12 待裁决）。
- 「发送到素材库」现在只有一份分流判据、一个结果契约、一条顺序（落盘→归位→广播）；
  过程里的复杂度落回了它该在的层：**判据 → 文件域（filesApi）**，**用例编排 → store**，**显示 → 面板**。
- 用户报障的「点了却库里没有」在本轮收口后由**三处**同时堵住：① 本机文件不再重传（避免撞去重、行留旧目录）；
  ② 落盘后必**归位**到目标目录；③ 「全部」pill 改前缀语义（子目录素材不再被过滤掉）。
- **重测须知（诚实提示）**：素材库里的**显示名仍是内容寻址哈希名**（`c12ae61…png`），因 TD-12-12（后端
  `recordUploadedFileRow` 用磁盘名当行 name）尚未裁决 → 素材确实入库了，但**认不出是哪张**。
  这条直接决定"用户觉得成没成功"，建议优先裁决。
