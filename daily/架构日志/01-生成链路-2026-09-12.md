## 一、链路快照（refs 实证）

DATAFLOW「生成链路（★主链路）」段（§10-48）**总体准确**，本轮 refs 实证两条支线均真：

**主范式（经 useGenerateNode 委托）**
```
nodes/{ImageGenerate,TextGenerate,VideoGenerate}
  → hooks/useGenerateNode（provider/模型 + useSyncNodeData + 委托）
      → hooks/useNodeGeneration（契约：reportGenerate → progress → run → 成败 → retry + 落盘 + 回填）
          → base/api/generate.ts（单门面：generateImage/generateVideo/chatCompletions/chatStream）
              → base/api/relayProxy.ts（relaySubmit → relayAttachUntilDone 低频 GET attach）
                  → POST :18080 /api/generate
  → store/taskStore.reportGenerate / progress / done / fail（任务中心权威源）
  → 落盘唯一出口 filesApi.saveResultToTasks（useNodeGeneration 单点调）
  → 刷新恢复 base/api/pollTask.ts ─→ relayAttachUntilDone（只 attach 不 cancel）
      → taskStore.patchTask + taskCompletionBus.publishTaskCompleted（唯一发布入口）
          → 广播 agent:task-completed → useNodeGeneration 精准回填（detail.nodeId===本节点）
```

**第二入口（剧本盒，不经过 useGenerateNode）**
```
scriptbox/scriptBoxEngine.ts（ScriptBoxNode 经 hooks/useScriptBoxEngine 注入 15 个 onXxx 到 node.data）
  ① asset 生图：generateImage → reportGenerate(伪 nodeId `nodeId-asset-<assetId>`) → 回填 data.assets[].imageUrl
      → resourceStore.localizeAndStoreToResourceLibrary（migrated/）+ saveResultToTasks 副本
  ② 文本类 chatCompletions（写剧本/分镜提示词/审计/合并视频提示词）→ 直接回填 data.shots[]，**不经任务中心**
```

**DATAFLOW 漂移（本轮已就地更正，见 §六）**：原写 `assetStore.localizeAndStoreToLibrary（migrated/ 目录）`，实测为 **`resourceStore.localizeAndStoreToResourceLibrary` + `resourceFolderOf`**（asset*→resource* 重命名后未同步）。

**refs 实证关键点**：`generate.ts` ← 4 生成节点（经 useGenerateNode）+ scriptBoxEngine + agentRuntime + contextCompression；`relayProxy` ← generate.ts / pollTask.ts（无节点/agent/scriptBox 直连，门面收口）；`taskStore` 被 useNodeGeneration / useScriptBoxEngine / pollTask / TaskCenter 消费。

## 二、溯源（Phase 1：症状 vs 病根）

- **主范式健康**：「任务中心为结果权威源、node.data 为渲染缓存副本」的红线落地清晰——单向（写只走契约、刷新靠任务中心回填）、落盘单点（`saveResultToTasks`）、广播单入口（`publishTaskCompleted` 带校验）、精准回填（`nodeId` 过滤）。这是本区**做得对**的地方。
- **病根 1 · 第二入口未接入契约的全部边**：剧本盒「对齐」了主范式的**上报**（`reportGenerate` + 伪 nodeId 防互顶），但**未对齐 retry 注册**——而任务中心对任何任务都显示「再来一次」（`TaskCenter` 无 `isNodeRegistered` 门控），于是剧本盒资产任务的「再来一次」必失败（TD-01-1）。病根 = **契约是「面的集合」，第二入口只挑了部分面复用，没有机器对账「第二入口须覆盖哪些面」**。
- **病根 2 · 失败语义在 transport 层被压平**：`relayPoll` 把网络/HTTP 错误统一吞成 `{status:'running'}`（本意"下轮续查"），而 attach 循环只看 `status` 不看 `error` → 真实错误在提交后掉线场景**无出口**，最终统一报「生成超时」（TD-01-2）。病根 = **失败分类在到达 UI 前被丢弃**（与区域 02 的 M1「失败语义无分类」同源）。

## 四、切割（Phase 3：深模块 / 真缝隙 / 收敛口）

- **`taskStore`（750 行）判「合格深模块」**：内存态唯一源 + 后端同步 + 轮询注册表 + 互斥锁 + retry 注册表集中一处，接口窄（reportGenerate/patchTask/claimNodeRun/ensurePolling…），不切。
- **`relayProxy`（367 行）判「合格」**：submit/attach/cancel/chat/stream 五个原语，attach 循环被 in-flight 与恢复复用，正是「唯一查询协议」的收敛点，不切。
- **`scriptBoxEngine`（2171 行）观察**：15 个 onXxx 回调工厂 + 内部编排（滑动窗口/补丁合并/槽位分配）。UI 只调 `d.onXxx`、职责边界清晰，但**单文件体量已大**，是否按「生图域 / 文本域 / 连线域 / 尾帧域」拆子模块待裁定（TD-01-7）。
- **真缝隙**：剧本盒与主范式「节点生成契约的面」无对账清单 → 收敛口 = 把「第二入口须覆盖的契约面（上报/进度/落盘/retry/回填）」写成一张**可测清单**（新增面漏接即红）。这是 TD-01-1 的根治方向。
