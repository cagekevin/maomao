## 二、★ 最重要的发现：两道「孤儿闸」（不在册 = 从没跑过）

用户要「应拆尽拆」，但**真正的病不是"闸太多"，是"有些闸根本没接上"**：

```
scripts/check-token-mirror.mjs   → 不在 gates.manifest.json 的 build/push/health 任何一层
scripts/check-css-globals.mjs    → 同上；且 scripts/css-globals-baseline.json 【不存在】
mockup/scripts/check-css-globals.mjs → 同名第三份，内容与上面那份不同
```

**实测各自状态**：

```
check-token-mirror   ❌ 副本一致性未通过：1 条
    ✗ mockup/image-editor-tabs-mockup.html 引用 --mao-gold 在 kit / 真源里都不存在
      （空引用 ⇒ 颜色静默失效）

check-css-globals    ❌ 基线不存在：scripts/css-globals-baseline.json
   门禁未就位 = 无闸必回潮
```

⇒ 这是 **形态①（不跑）＋形态④（基线不存在）的教科书案例**。`token-mirror` 有一条**真实的、用户可见的**违规（颜色静默失效）躺在那里无人知晓；`css-globals` 连基线都没生成过，**等于空壳**。

**它们守的是什么**：`mockup/` 设计样稿目录（`MOCKUP-REFACTOR-PLAN.md` §2–§5）。而 `mockup/` 本身在 `TD-23-5` 里已裁定为「设计样稿工作目录，本就该入库」—— 但**样稿目录不代表需要闸**。

**处置**：**删**（用户裁定「剩下的没用的直接删」）。理由：留着比删掉**更有害** —— 它们假装有门禁，且 `MOCKUP-REFACTOR-PLAN.md` 的头部还**明确宣称**这两闸「挂 push 层、整仓生效」（**与实况相反**）。

## 三、元层闸的自我暴露（两处）

**① `check-gate-vitals` 自己报的 `catch` 残留**：

```
⚠️ catch: GATES 登记表里有，但闸清单已无此闸（可能已退役，请删登记行）
```

`check-silent-catch.mjs` 2026-09-17 已按用户裁定退役，但本登记表**漏删** ⇒ 元层闸长期背一条**假警告**。警告疲劳正是形态②（跑了但没人看）的成因。已删（并在原位留痕「删闸时必须同时删本表登记行」）。

**② `check-gate-vitals` 自己的设计留痕，就是本轮要的答案**：

它头部写着第一版设计**是错的**——「跑所有在册闸抓扫描基数，0 就判红」，实测 **8.9 秒**（全仓最慢），因为它把整个 push 阶段又跑了一遍。改成**静态度量**后 **<0.1 秒**（降 99%）。

> **它的判据直接可用**：**"跑一遍"往往只是拿执行换一个"本来是静态的信息"** —— 优化前先问「这个信息真的需要跑吗」。

**③ 顺带修好一个检测器缺陷**：`gate-vitals` 对 `dead-code` 误报「无集合判 0」，因为它的正则只认 `.length|.size === 0`，而 `dead-code` 写的是 `raw.trim().length === 0`（两段式）与 `parsed === 0`（裸计数）。已放宽正则，并**先用负例验证能红**（改 `process.exit(1)`→`(0)` 后正确报「fail-loud: 无」），再确认正例 0 警告。

## 四、重叠排查：全部用**负例探针**实测，不靠读代码

**① `check-arch` 规则 15 vs `check-storage-keys` —— 实测互补，都留**

| 注入 | storage-keys | arch 规则 15 |
| --- | --- | --- |
| `contentGet('未登记键')` | ✅ 抓（报裸键未登记） | 不抓 |
| `contentGet('projects')`（**已登记键**的裸字面量） | 不抓 | ✅ 抓（报应引用命名 const） |

两个方向各管一半。**这是本轮"别凭直觉拆"的最好例证** —— 单看代码，两者的函数集高度重合（9 vs 19），极易误判为重复。

**② `check-node-types` —— 有重叠，但当前不可替代（记债，非拆）**

它扫 `useNodePrefs('xxxNode', …)` 字面量首参是否在 `NODE_TYPES` 登记。**能替代它的正道是类型层**，但实测：

```ts
// src/components/base/canvas/nodePrefs.ts:143
export function useNodePrefs(type: string, defaults: NodePrefsMap = {}) { … }
```

`type` 是 **`string`** —— tsc **拦不住**。要改成 `keyof typeof NODE_TYPES` 才等价，那是**改业务代码**、且 `NODE_TYPES` 与 `nodePrefs` 分处不同层（会引循环依赖风险）。当前调用点仅 3 节点 + 1 模板，且**都是多行写法**（`useNodePrefs(\n  'imageGenerateNode',`）——好在闸的正则 `fn\s*\(\s*(['"])` **允许空白符**，能覆盖多行，**不是靠运气**。

⇒ **保留闸**，把「能否升为类型层」留作后续（未登记新债，同 TD-09-1 族）。

**③ `node-handles` vs `node-data` —— 零重叠**：一个守**端口渲染**（漏口 = 边静默不渲染），一个守 **data 字段对账**（写侧产出 vs 读侧认识）。

## 五、提速：knip 真提速，strict-src 无法提速（留痕防重走）

### 5.1 knip：`--cache` —— 官方方案，**10.2s → 6.0s（省 41%）**

**官方依据**（knip.dev/reference/cli「--cache」节）：缓存**文件分析（AST 遍历）结果**，连续运行提速 **10–40%**；策略保守，以「文件 mtime + size」判缓存有效。

**本仓实测**：

```
无 cache        ~9100ms
有 cache（建）   ~9137ms（同无 cache）
有 cache（命中） ~7500ms   ← 首次实测
接入闸后         6019ms    ← 闸内实测（含 Node 启动开销）
```

**结果一致性（关键，必验）**：带/不带 cache 的 `--reporter json` 输出**逐字节相同**（`JSON.stringify` 全等，47 issues 全同）。

**cache 不掩盖新违规（关键，必验）**：注入 `src/components/base/utils/__probe_dead.ts`（无人引用的新文件）→ 闸仍 **❌ 新增死代码 1 条** 精确抓出。探针已清。

**官方已知限制（写进闸头）**：新增的 `.gitignore` 条目**不会**被自动感知，变化时需清 `node_modules/.cache/knip`（该目录在 node_modules 下，不入库）。

### 5.2 strict-src：**三种提速写法全部实测否决**（这才是本轮的诚实产出）

用户要求「看看怎么能优化速度，可以去他们官网查查」。查了、试了、**结论是没有便宜的提速**：

**① `incremental` / `tsBuildInfoFile` —— 无效（TypeScript 已知限制）**

发现过程（值得记）：
1. 先看到 `tsconfig.json` 已写 `"incremental": true`，且根目录**已有** `tsconfig.tsbuildinfo`（567KB）—— 却仍 10.5s
2. **决定性观测**：那个文件的 **mtime 长期冻结**（13:47 之后再没变）⇒ **缓存根本没被复用**
3. 读 `tsbuildinfo` 内容：`affectedFilesPendingEmit` 恒含 **841** 项、`options.noEmit === undefined`
4. 试显式 `--tsBuildInfoFile`（能落盘了）→ 第二次**仍 ~10.5s**
5. 试 `--incremental --noEmit` → 仍是 ~10.5s

⇒ **`tsc --noEmit` 与 `--incremental` 组合下增量短路不生效** —— 这是 **TypeScript 的限制**，不是配置写错。已把三种写法与数字钉进闸头，**防后人重走**。

**② 按白名单收窄 `include` —— 更快但会引伪错误，否决**

做法：按 `strict-src-whitelist.json` 生成只含 18 个白名单目录的子配置（285/589 文件）。

```
全量   ~11400ms
窄面   ~10500ms   ← 只省 0.9s
```

**但窄面引入伪错误**：`src/components/base/utils/videoEngine.ts:34` 报 `TS7016 gifenc 无声明文件`，而**全量下不报**（`grep -c gifenc` = **0**）。原因：收窄 `include` 会改变 tsc 的 program 组成（外部 `.d.ts` 的加载与可见性随之变化）。

⇒ **为 0.9s 去换「可能红在别处」= 破坏闸的诚实性，不做。**（这条正是 `probe.mjs` 头部说的「红的不是那点」—— 探针最怕的失败模式。若当时不查这个错误、只看"变快了"，就会把一个会误报的闸推上线。）

**③ `--skipLibCheck` —— 已开**（tsconfig 内），无可再省。

### 5.3 顺带澄清：`type-check` 与 `strict-src` **确实不同，不可合并**（实测）

manifest `_design.tsc` 段原有判断「标志会改变推断、不可合并」。本轮**实测证实成立**：

| tsconfig `noImplicitAny` | `type-check`（无 CLI flag） | `strict-src`（带 `--noImplicitAny`） |
| --- | --- | --- |
| **false**（临时改） | **93 错** | **0 错** |
| **true**（现状） | 0 错 | 0 错 |

⇒ **CLI flag 会覆盖 tsconfig**，`strict-src` 的覆盖面独立存在。
**⚠️ 但也要知道**：当前 tsconfig 已写死 `noImplicitAny: true`，故此刻两闸输出**逐行相同**。`strict-src` 的价值在于「**即使有人把 tsconfig 的 noImplicitAny 改成 false，白名单目录仍被守住**」—— 它是防「悄悄放松 tsconfig」的二道锁。**这条理由必须留着**，否则后人会因"看起来重复"而删掉它。

## 九 · 弯路留痕

### 弯路 1：差点把「不在册」当「在册」审计

第一遍读 `gates.manifest.json` 得出「16 条在册」，然后用 `ls scripts/check-*.mjs` 比对**才**发现两个孤儿脚本。**若只读 manifest，会得出"闸体系很干净"的相反结论**（因为坏闸根本没进清单）。

⇒ 教训：**审计"某集合的成员"时，必须独立枚举"物理存在的成员"再与"登记成员"求差** —— 登记表天然看不见"该登记而未登记"的东西。这与本仓 `check-gate-vitals` 的 `missing`/`stale` 双向对账是同一判据，**我当时没用上它**（它就是专门为此写的）。

### 弯路 2：`tsc --noEmit` 的增量无效，绕了三圈才确认

先改 tsconfig 加 `tsBuildInfoFile`（能落盘了，**以为修好了**）→ 实测**还是 10.5s** → 才去读 `tsbuildinfo` 内容 → 看到 `affectedFilesPendingEmit: 841` + `noEmit: undefined` → 才确认是 TS 限制。

⇒ 教训：**"文件生成了"不等于"机制生效了"**。判"缓存是否真的命中"，要看**它的 mtime 有没有变**（本次的决定性观测），而不是看文件存不存在。**同族**：`check-gate-vitals` 治的「扫 0 却绿灯」—— **产物存在 ≠ 产物被消费**。

### 弯路 3：窄面 `include` 的诱人陷阱

窄面配置测得 **10.5s vs 11.4s**，第一反应是"省了 0.9s"。**差点直接换上去**。多看了一眼输出里的 **2 个错误**（`Cannot read tmp/tsconfig.json` + `No inputs found`）才发现是路径问题 → 移到根目录重测 → **才看到那个真的伪错误**（`gifenc TS7016`，全量下 0 命中）。

⇒ 教训：**"变快了"不是全部结论，必须逐项比对"结果有没有变"**。若当时把 `tmp/` 下那两个路径错误当成"无关噪声"跳过，就会把一个**会误报的闸**推上线。这正是 `probe.mjs` 头部的 `--expect-not-out`（防「红在别处」）想防的事 —— **验证提速时，等价性检查要比速度检查更严格。**
