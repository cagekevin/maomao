## 二、溯源（Phase 1）：症状 vs 根因

- **症状**：「KV 4xx 业务拒收被误报成引擎不可用」「画布工程偶发本地 stale 副本写回 KV」。
- **根因（非症状）**：**「KV 失败分类」这个复杂度被复制成两套不一致实现**——写族正确收口，读族漏接。需求消失后这段代码仍有意义（它是真地基缺陷），故不是喂症状。

## 三、定海（Phase 2）：契约与不变式

- **不变式**：`STORAGE_KEYS` 是存储键路由的**唯一真相源**；`isEngineUnavailable`（L281）是失败分类的**唯一实现**。下游承诺：4xx=业务结论原样上抛，引擎不可用才降级。
- **地基现状**：`StorageKeyMeta` 定型完整（好）。但**分类的应用点**只覆盖写族，读族与契约承诺背离——地基（分类函数）在，但**应用边界**缺了一侧。

## 四、切割（Phase 3）：收敛关卡该守在哪

> ⚠️ **核心结构判词**：失败分类 / 错误可见性 这两个复杂度，必须收口到 **contentStore 唯一边界**，且读/写族对称共用同一套分类语义（单一事实源）。当前它们：
> - 写族：正确（`writeKvWithFallback` L324 `if (!isEngineUnavailable(e)) throw e;`）✅
> - 读族：漏接（`readKvWithFallback` L297 / `contentGetKvWithFallback` L516 任何 catch 都 `reportDegrade` + 回退本地 + 标 `from:'local'`）❌
>
> 这违反 §一.2（同一复杂度应压到唯一物理位置）+ 铁律 2（4xx 根因在 read 处被伪装成引擎故障）+ §二 Phase 3（收敛关卡没守在读/写统一边界）。**复杂度被「藏」进读族且藏错位置**。

**正确位置（修复方向，未实施）**：把「读 KV → 失败分类 → 4xx 上抛 / 引擎不可用降级回本地 → 信号(reportDegrade/logger)」抽成**一个受守卫的读辅助**（与 `writeKvWithFallback` 对称，如 `readKvOrFallback`），读族两函数统一调用。修复后：分类逻辑一处、读/写对称、下游 `from` 信号诚实。

## 五、探债（Phase 4）：债本

### TD-02-15（深化 + 画布侧实证，利息率由「中」上调为「中高」）

- **原判定（七轮）**：读族 `readKvWithFallback`/`contentGetKvWithFallback` 缺 `isEngineUnavailable` 守卫，4xx 误报引擎不可用 + 静默回退本地副本。
- **本轮画布侧实证（核心增量）**：`d3dPersistence.hydrateProject` (L254) 经 `contentGetKvWithFallback` 加载 3D 画布工程，该函数**任何 catch 都返回 `from:'local'`**（L516-521，含 4xx）。d3d 据 `from==='local'` 触发 `local→KV 迁移写回`（L257-265）。当 KV 返回 **4xx（如 403 无权限 / 404 键业务不存在）** 时：
  1. `reportDegrade` 弹**假** toast「本地引擎存储暂不可用」（真实是业务拒收）；
  2. 回读本地 stale 副本并标 `from:'local'`；
  3. d3d 据此把本地 stale 副本**错误写回 KV** —— 恰好是 contentStore 自己注释警告的「两窗口各写一份本地副本 → 静默分叉」数据陷阱（L531）。
  → **从「toast 文案假」升级为「画布工程数据可能静默分叉」的可观测危害**。
- **复杂度位置判词**：分类逻辑应**收口到唯一受守卫读辅助**，与写族对称；不应散落在两个读函数各自 blanket catch。
- **曾评估被否决的替代方案**：
  - ✗ 仅改 toast 文案 → 不解决 `from:'local'` 污染导致的迁移写回（假信号仍驱动数据写回），是装饰性修复，否决。
  - ✗ 在读族也加 `isEngineUnavailable` 但保留"4xx 也回退本地" → 写回陷阱仍在，否决。必须 4xx **上抛**、不污染 `from`。
- **偿还计划**：抽 `readKvOrFallback`（受 `isEngineUnavailable` 守卫），`readKvWithFallback`/`contentGetKvWithFallback` 统一调用；4xx 上抛、仅引擎不可用降级、`from` 仅表示"KV 真空/引擎降级"语义。@见 TD-02-19（信号语义契约）。

### TD-02-19（新增 · 信号语义契约不诚实，利息率「中」）

- **现象**：`contentGetKvWithFallback` 返回的 `from` 字段语义不诚实——4xx 失败也被标 `from:'local'` 并触发回退，下游（d3d `hydrateProject`）无法区分「KV 真空/引擎不可用（真·需迁移）」vs「KV 4xx 拒收（应上抛，不该迁移）」。这是铁律 2「边界诚实」的第二维度：**不仅错误要炸开，成功信号的语义也必须诚实**。
- **归类**：增债（根因 = 信号语义契约未定义；非偷懒，因 `from` 本为迁移判定设计，但读族失败时未区分失败类型）。
- **爆炸半径**：1 处（d3d 画布加载直接消费 `from`），但危害为数据写回。
- **偿还计划**：与 TD-02-15 同一次修复——`from` 仅在"KV 真空/引擎降级"时返回 `'local'`，4xx 失败不返回 `from`（或显式区分），下游据诚实信号行动。

### TD-02-16（深化 · 口径冲突实证，利息率维持「低」）

- **原判定（七轮）**：fire-and-forget 落库/删除被 `.catch(()=>{})` 完全静默（零日志）。
- **本轮实证（refs + grep）**：5 处确证——
  - `taskStore.ts:336` `deleteTask(id).catch(()=>{})` // 后端删除
  - `taskStore.ts:686` `batchDeleteTasks(...).catch(()=>{})` // fire-and-forget 后端删除
  - `taskStore.ts:693` `clearAllTasksApi().catch(()=>{})` // fire-and-forget 后端清空
  - `resourceStore.ts:530` `rescanResources().catch(()=>{})`
  - `projectStore.ts:598` `contentDeleteAsync(CANVAS_STATE_PREFIX+id).catch(()=>{})` // fire-and-forget KV 删除
- **口径冲突实证**：同链路 `useNodeGeneration.ts:281`、`scriptBoxEngine.ts:580`、`TextGenerate.tsx:279`、`conversationState.ts:158` 均 `reportDegrade` 留痕（注释明写「落盘失败不得静默吞」）。这 5 处是**反向口径**——错误在根因处被消音，违反铁律 2（根因炸开）+ §二 Phase 3（收敛关卡漏到三公里外 store 末端）。
- **复杂度位置判词**：错误可见性（`reportDegrade`/`logger.warn`）应**收口到 contentStore 边界**（已有 `reportDegrade` 单一入口），而非散落到各 store 末端各自吞。
- **曾评估被否决的替代方案**：✗ 直接删这些 fire-and-forget（属于业务性删除，架构师无权，须交决策者，见 §零.5）→ 否决，仅登记为「最低纲领改 logger.warn 与同链路对齐」。
- **偿还计划**：最低纲领：5 处 `.catch(()=>{})` 改 `.catch(logger.warn)` 与同链路对齐；理想纲领：这些 fire-and-forget 经 contentStore 边界统一 `reportDegrade`。

### TD-02-17（深化 · 契约层哲学矛盾，利息率维持「低」）

- **原判定（七轮）**：`findPatternEntry`/`isKvPatternKey` 的 `catch { 忽略 }` 静默吞坏正则，键路由退化为启发式兜底（L217 `isKvPatternKey(key) ? 'kv' : 'local'`）。
- **本轮深化（哲学矛盾实证）**：同文件 `checkRegistered`（L179-185）对「dev 环境未登记字面量键」**直接 throw**（fail-loud），却对「登记表正则模板坏了」在热路径 `catch { 忽略 }`（L143-144 / L230-231）静默吞。**两套哲学自相矛盾**：登记表的「键名漏登记」在开发期炸开，登记表的「正则坏了」却在运行期静默退化。
- **复杂度位置判词**：脏契约（坏正则）应在**契约加载源头** fail-loud（`STORAGE_KEYS` 初始化时一次性校验所有 `pattern` 正则合法性），而非在每次热路径匹配时静默吞。热路径本不该承担「正则可能坏」的防御——那属于契约层责任。这是把复杂度从「热路径静默兜底」**前移**到「源头拦截」（§二 Phase 3 探口：脏数据在边界炸死）。
- **曾评估被否决的替代方案**：✗ 在 `findPatternEntry` 内 `throw` → 会把「单个坏正则」变成「全量路由崩溃」，爆炸半径过大，否决；正确位置是**初始化期**集中校验（坏一个 fail-loud 且定位精确）。
- **偿还计划**：`STORAGE_KEYS` 初始化时遍历 `pattern:true` 项 `compilePatternRegex` 校验，坏正则直接 throw（带键名）；热路径 `catch` 改 `logger.warn`（防御性兜底，正常不触发）。

## 六、结论

- **本轮增量**：把七轮的「catch 兜底点扫描」升级为「自底向上 + 复杂度位置」的结构判词。核心贡献 = **证明 02 区读族分类漏接直接毒化画布加载（d3d `from` 信号污染 → stale 副本写回 KV 的数据分叉陷阱）**，并把 TD-02-15 利息率上调、补 TD-02-19（信号语义契约）。
- **根因一句话**：「KV 失败分类 / 错误可见性」这两个复杂度，本应收口到 contentStore 唯一边界且读/写对称，当前散落在读族 blanket catch + 各 store 末端 `.catch(()=>{})`，且契约层坏正则在热路径静默吞——复杂度放错了位置。
