## 二 · 本轮交付：测试网（`tests/unit/vePropertiesCommit.test.tsx` · 3 例）

**锁的契约**（不是"函数被调用"，是可观察的提交语义）：

| 用例 | 锁什么 |
| --- | --- |
| 字号 · Input 路径 | 编辑中两次 `change` 全部 `pushHistory:false`、**零次落历史**；`blur` 时调用序 = `[v1,false] → [v2,false] → [initial,false] → [v2,true]` |
| 字号 · Slider 路径 | 同上（且与 Input **共用同一个 initial ref** ⇒ 还原值必须等于字段初始值） |
| 每次提交只产生**一次**历史 | 预览 5 次 ⇒ `pushHistory:true` 恰好 1 次 |

**测试基础设施（决定了这套网能不能长期用）**：

- `useEditor` 打桩，只关心 `timeline.updateElements` 的**调用序**；
- `Slider` **用真实实现** —— 它是原生 `<input type="range">`（无 Radix，见其文件头注释）⇒
  `fireEvent.change` 触发 `onValueChange`、`fireEvent.pointerUp` 触发 `onValueCommit`，**不需要 mock**；
- 打桩的 `updateElements` **真的把更新应用回 fixture 并 `rerender`** —— 模拟真实环境的
  「写库 → 数据回流 → 面板重渲染」。

## 三 · 弯路留痕（强制 · 与结论同等对待）

### 弯路 1：受控 `<Slider>` 的 DOM value 是**测试环境假象**（差点误判成组件缺陷）

首跑时 Slider 用例红：`onValueCommit` 报出的值是**旧的**（15），而不是刚拖到的 19。
第一反应是"组件的两段提交写错了"—— **错**。真因：

`Slider` 是**受控**的（`value={[element.fontSize]}`），而 `onValueCommit` 报的是
**元素当前值**（`commit()` 读 `element.value`，见 `slider.tsx:63`）。
测试里 fixture 不随打桩的 `updateElements` 更新 ⇒ 重渲染后 `value` 仍是被重置的旧值
⇒ 报出的自然还是旧值。**真实环境下游数据会回流，控件拿到新值，行为正确。**

⇒ 让打桩**真的应用更新 + rerender** 后转绿。

**教训**：受控组件的"读 DOM 值"行为，**必须在数据会回流的条件下测**；
否则测的是"测试环境里控件被卡住"的假象 —— 与组件质量无关。
（同族教训：`TD-21-23` 那次是"抖动没传导到被测代码"，这次是"数据没回流到被测控件"——
**两次都是"我的条件没真的成立"，而第一次看见的都是红色。**）

### 弯路 2：按 role 取控件不唯一

面板里有多个 `input[type=number]` / `input[type=range]`（不透明度 / 位置 / 缩放 / 旋转…）
⇒ `getByRole('spinbutton')` 直接抛 "Found multiple elements"。
改用**标签定位**（`PropertyItem` 是 `label + value` 的兄弟结构）：先 `getByText('字号')`，再在其 `parentElement` 内取控件。

# 追加 · 组②（text 的非数字字段：②a 文本/颜色 + ②b 背景四项）已迁移 · 2026-09-16 同日

## 一、交付（7 个字段）

| 字段 | 入口形态 | hook 用法 |
| --- | --- | --- |
| `content` | Textarea | **draft 路径**（`onFocus`/`onChange`/`onBlur`），与组① 的 Input 完全同形 |
| `color`（文字颜色） | ColorPicker `onChange`/`onChangeEnd` | **值直传** + 调用方补 `#` |
| `backgroundColor` | ColorPicker（同上） | 值直传 + 调用方补 `#`（并保留"记住最后实色"的副作用） |
| `backgroundOpacity` | Slider（percent 域） | 值直传 + 调用方 `/100` |
| `backgroundBorderRadius` | Slider | 值直传 |
| `backgroundPaddingY` | Slider | 值直传 |
| `backgroundPaddingX` | Slider | 值直传 |

**结论：不需要"第二种 hook"**。上一轮把这一组预判为"需新变体"，取证后发现：
组① 里那两个方法（`onSliderChange`/`onSliderCommit`）本身就是**通用的"值直传"入口** ——
ColorPicker 的 `onChange`/`onChangeEnd`、Slider 的 `onValueChange`/`onValueCommit` 都是它的实例，
**值域换算（`#` 前缀、`/100`）由调用方做**。

⇒ 一个 hook、三种入口（draft 输入框 / 值直传 / 纯滑杆），而不是三个 hook。

**附带收益**：迁移后 `text-properties.tsx` 里的 `forceRender` **零消费者** ⇒ 连同 `useReducer` import 一并删除
（整文件不再需要手动触发重渲染）。

## 二、一处**有意保留的行为差异**（不属"零变化"，如实登记）

`content` 的旧实现在 **`onFocus` 里就播种 `initial`**；hook 只在**首次 `onChange`** 播种。差异只在一种路径上显现：

> 聚焦后**一个字都不改**直接失焦 ⇒ 旧实现会 `commit(initial, false)` + `commit(当前值, true)`
> ⇒ **撤销栈里多一条"什么都没变"的记录**；hook 不提交。

判定：旧行为是**缺陷**（用户视角：撤销一次，画面没有任何变化），hook 的行为更正确 ⇒ **按 hook 保留**。
本次的 15 例**没有覆盖这条路径**（它们都先 `change` 再 `blur`），所以 §三 的等价性验证**不会**暴露该差异 ——
这一点如实写明，避免后人误以为"15 例全绿 = 逐路径等价"。

## 四、弯路留痕（强制）

### 弯路 1：以为 ColorPicker 没法在 jsdom 里测（其实它是原生控件）

### 弯路 3：手抄默认值 ⇒ 4 例红

## 四、本轮最贵的两条经验（跨 4 组累计）

1. **"同一个字段" / "同一个对象"才是实例化单位，不是控件**。
   - 组①：同一字段的 Slider 与 Input 必须共享一个 initial（拖完滑杆接着输入框微调 ⇒ 撤销**一次**回起点）；
   - 组②c：`stroke` / `shadow` 是**对象**，它的多个入口（颜色 / 宽度 / X / Y / 模糊）也属同一次会话。
   - 两者是**同一条判据**，只是单位从"字段"上升到"对象"。按控件实例化会得到 2~4 个互相不知道的 initial。
2. **`git stash push -- src/` 是"等价性"的强证据**：新测试写完先跑**旧实现** ——
   全绿才说明"我锁的行为 == 原来的行为"；若红，先假定**我的测试改错了契约**再谈别的。
   这比单向探针强：它同时证明了"测试测的是真契约"与"迁移没改行为"。
   （四组各跑一次，**32 例全程双绿**。）
