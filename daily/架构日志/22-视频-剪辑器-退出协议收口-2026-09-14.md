# 22 · 视频剪辑器 · 退出协议收口 · 2026-09-14

## 用户报 bug（原话）

「在 video editor 里边，我点返回画布，它一直卡在那个。正在退出中。」
用户随后明确要求：**不要猜 bug 成因，按"正确的退出应该长什么样"重新设计，先收口再改对。**

## Step 0/1 取证（不猜，全 grep）

| 退出入口 | 现状 | 后果 |
| --- | --- | --- |
| ① 右上角 X（`EditorShell.tsx`，title「关闭编辑器（返回画布）」） | `onClose` = `setSetting('videoEditorOpen', false)` 直接卸载 | 卸载前无善后（不 flush / 不 closeProject） |
| ② header 菜单「退出项目」（`editor-header.tsx` `handleExit`） | `prepareExit()` → `closeProject()` → **到此为止**（原 cutia 是 `router.push` 跳走；搬入时注释写「退出目标由宿主控制」但**从未接宿主**，断头） | `closeProject` → `notify` → Provider 渲染 `!activeProject` 分支「正在退出工程…」→ 无人接力关层 → **永久卡死**（用户实测症状） |
| （重复实现证据） | `handleExit` 的 catch 里还有一次 `closeProject()`，finally 又一次 —— 同一善后被调 2 次 | 断头实现的伴生混乱 |

机制取证：`useEditor()` 经 `useSyncExternalStore` 订阅 `editor.project.subscribe`（`hooks-cutia/use-editor.ts:19`），故 `closeProject()` 的 notify 直接触发 Provider 重渲染——卡死画面渲染路径闭环确认。

## 设计（如果重来，退出长什么样）

```
exitEditorToCanvas（唯一协议，EditorShell.tsx）：
  ① prepareExit()   — flush 落盘（内部已 catch 留痕，失败不阻断退出；退出是用户意志）
  ② closeProject()  — 清引擎内存态
  ③ onExit()        — 宿主关层 → 卸载（unmount cleanup 清存储上下文）
```

两条铁律（写进实现注释）：
- **退出必然以卸载结束**——closeProject 之后下一步永远是卸载，不存在「退出了还挂着」的停留态；
- **退出入口不允许自带实现**——入口只触发，善后与卸载收口为一份（防重入 `isExiting` 也收在函数内，判据 1 份）。

## 施工（2+1 文件）

| 文件 | 改动 |
| --- | --- |
| `EditorShell.tsx` | 新增唯一退出函数 `exitEditorToCanvas`；X 按钮走它；`onExit` 经 `EditorLayout` 下传 |
| `ui/editor/editor-header.tsx` | 删除断头 `handleExit`（含重复 closeProject、`isExiting` state、单用途 `logger` import）；「退出项目」只触发宿主回调；`onExit` 缺省**不渲染该入口**（从根上消灭断头退出） |
| `ui/providers/editor-provider.tsx` | 「正在退出工程…」分支收口（见下） |

## 第二处收口：Provider 的「正在退出工程…」分支（用户质疑：防御性代码不就是死代码？）

先取证再答（不靠推断）：
- **退出路径**：收口后 closeProject 与宿主 setSetting 同一事件处理器同步发生，React 18 同批提交 → 不可达 → 在这条路径上它**就是死代码**（用户判断正确）；
- **切换/新建作品路径**：`closeProject → loadProject` 之间 active 为空，此分支挡住 children 半初始化渲染（否则 header `getActive()` 抛错）——**可达且必要**。

结论：不是"防御 vs 死代码"二选一，它是**说谎的活代码**（切换时也显示"正在退出工程…"），且与 `isLoading` 分支是同一占位的两份渲染。
修法：两分支收口为一个 `if (isLoading || !activeProject)` → 同一「正在加载工程…」占位，说谎文案删除。
