## 一 · 弯路留痕（强制 · 与结论同等对待）

### 弯路 1（**上一轮留下、本轮翻案**）：把"测试挂死"误诊为"环境不可用"，并据此立了一条假硬约束

**当时（09-15）**：vitest 启动后只落盘 `RUN v2.1.9` 一行，四种启动方式（`npx vitest run` /
`node vitest.mjs run` / `Start-Process -Wait` / 后台分离）**同样被截断**，且残留进程持续占 CPU。
⇒ 结论写成「**vitest 不可执行** ⇒ 测试类债在本环境无法闭环」，**回退了 TD-21-2 的全部代码**。

**为什么错**：那四种方式的共同点是「**都在等前台输出**」。当测试进入无限渲染循环时，
**vitest 本来就不会产出任何后续输出** —— 现象与"输出被会话收走"**完全一致**，但成因相反：
一个是"有结果拿不到"，一个是"**压根没有结果**"。

**本轮怎么分清的**：把 stdout **重定向到文件**（绕开任何输出管道）⇒ 文件里**仍然只有 `RUN` 一行**
⇒ 排除"输出被吞"，锁定"**真的没跑完**"；再看进程 ⇒ 3 个 vitest worker 分别烧了 46s/22s/24s CPU ⇒ 实锤。

**后果（严重）**：那条假硬约束写进了区域日志且标了"后续必读"，**会持续劝退后续所有测试类债**
（日志里它已顺手把 `TD-09-2` 也划进"本环境无法闭环"）。

**教训**：「拿不到输出」= 「输出被吞」∪「真的没输出」—— **必须用重定向/落盘把两者分开**，
不能因为四种前台方式都失败就断定是环境。**"多种方式都一样"只说明触发条件相同，不说明原因相同。**

### 弯路 2：写用例前没先审 mock 的"语义保真度"

我为了触发抽帧 effect，直接复用了 `_nodeMocks.mjs` 的 `useReactFlow`，**没先问它是否忠于真实实现**。
它把整个方法对象写在 `useReactFlow()` **内部** ⇒ 每次调用新对象新函数，而 `@xyflow/react` 真实实现是
**引用稳定**的。这个不保真的 mock 顺手伪造了"上游每渲染都变"的触发条件，把组件的脆弱点放大成挂死。

**教训**：用共享 mock 构造新触发路径前，先核一眼**该 mock 是否保真于真实库的引用语义**
（尤其是 hook 返回对象/函数 —— 稳定性是真库的契约之一，mock 里最容易丢）。

### 弯路 3：第一反应是"跟着上一轮的结论走"

看到命令返回空 + "monitoring for 10 seconds"，我的第一反应是"**这正是上一轮记录的同一现象（输出被收走）**"，
差点直接接受。是"先重定向读文件"这个动作把结论翻了过来。
**教训**：读到前人留下的"硬约束"时，**先当成待验证假设**，不要当成前提。

## 三 · Step 3/4 定位（二分）

| 实验 | 结果 |
| --- | --- |
| 既有 10 例 | ✅ 通过（130ms） |
| 单跑**反例**（有源、无元数据） | ✅ 通过（70ms） |
| 单跑**正例**（有源 + 有元数据 ⇒ 触发抽帧） | ⛔ **挂死**（10s 无输出，worker CPU 空转） |

**根因链（读码确认）**：

1. `_nodeMocks.mjs` 的 `useReactFlow: () => ({ setNodes, getNodes, … })` ⇒ **每次渲染返回新函数**；
2. ⇒ `VideoProcessNode.tsx:345` 的 `ne`（依赖 `getNodes`）与 `:374` 的 `sources` **每次渲染重算**（新数组）；
3. ⇒ `:380` 的 `tracks` useMemo（依赖 `sources`）重算；其中 `:428-448`「把有元数据的未用源自动补进视频轨」
   用 **`makeId('clip')`** 生成片段 id ⇒ **每次重算都得到一批新 id**；
4. ⇒ `:628` 的 effect 发现 `selectedClipId`（旧 id）已不在 `tracks` 里 ⇒ `setSelectedClipId(新id)` ⇒ 渲染 ⇒ 回到 2。

**为什么"有元数据"才是触发条件**：第 3 步的自动补片段**只对 `duration > 0` 的源生效**
⇒ 无元数据时 `tracks` 里没有随机 id，循环链断在起点（反例因此通过）。

**责任划分（重要）**：
- 测试侧 —— mock **不保真**（真实 `@xyflow/react` 返回引用稳定的对象）⇒ **本轮修**；
- 组件侧 —— `useMemo` 里派生**含随机 id 的对象**（同输入不同输出，违反 useMemo 语义）⇒ **真实脆弱点**，
  另立 `TD-21-23`（本轮不动组件，见 §七）。
