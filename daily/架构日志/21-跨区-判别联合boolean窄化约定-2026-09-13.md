# 跨区 · 判别联合在 `boolean` 判别位下不窄化 —— 约束取证与编码约定（2026-09-13）

> **触发**：TD-12-2 收口时把 `persistUrlToBackend` 的返回改为判别联合 `{ok:true;url} | {ok:false;reason}` →
> tsc 报 `Property 'reason' does not exist on type 'PersistOutcome'`。用户同意把该约束**落成编码约定**（非仅记在单处日志）。
> **性质**：语言/配置层约束（本仓 `tsconfig`），非某区业务债。**无代码行为变更**。

---

## 一、Step 1 取证 —— 边界实测（先证伪"这是我的代码写错了"）

起初以为是自己写法问题，做**工程内最小对照**（`src/__scratch_*.ts`，用完即删）逐一验证：

| 判别位形态 / 访问位置 | 窄化 | 证据 |
| - | - | - |
| `if (x.ok) { x.成功字段 }`（boolean · **真分支**） | ✅ 正常 | 无报错 |
| `x.ok && x.成功字段`（boolean · 真分支短路） | ✅ 正常 | `StorageOpResult` 现行消费式即此形态 |
| `if (x.ok === false) { x.失败字段 }`（**显式等式**） | ✅ 正常 | 无报错 |
| `else { x.失败字段 }` / `if (!x.ok) { x.失败字段 }` / 三元假支 | ❌ **TS2339** | 三处精确报错 |
| `{kind:'a'} \| {kind:'b'}`（字符串判别位，含假分支） | ✅ 正常 | 无报错 |
| `{code:1} \| {code:2}`（数字判别位） | ✅ 正常 | 无报错 |
| 双方各带对方的键（可选 `undefined`） | ✅ 正常 | 无报错 |

> **两轮取证的自我修正**：首轮只测 `if…else` 一个形态，得出「**不对 `boolean` 判别位做收窄**」——**过于笼统**。
> 二轮补测分支形态后修正为准确表述：**真分支与显式 `=== false` 能窄化；假分支（`else` / `!x.ok` / 三元假支）不能**。
> 同名形态在工程外以 `--strict` 编译**通过** → 差异来自本仓配置。

**根因**：`tsconfig.json` 的 `"strict": false` / **`"strictNullChecks": false`**（既有演进项，非本轮引入）。

## 二、落地（约定，做在"会发现的地方"）

1. **决策层**：`spec/CONTEXT.md` §三 新增一条——
   *「类型契约：判别联合的写法（`strictNullChecks:false` 约束）」*：给出两种合规形态（① 双方带键 ② 改字符串/数字判别位），并**明禁 `as` / `!` 绕墙**。
2. **困惑发生地**：`tsconfig.json` 的 `strict`/`strictNullChecks` 处加指针注释（说明后果 + 指回 CONTEXT §三）。

**为什么不做机器闸（诚实交代）**：
> 这堵墙**本身 fail-loud**（写错就 tsc 报错），不存在"静默放过"的漏洞 → 做闸的低价值。
> 真正的风险是**被绕墙**（用 `as` 消掉报错，把编译期问题埋成运行时）——那才是需要在约定里明禁的。
> 另：`tsconfig` 若日后缩紧 strict，本约定自动失效（注释已写成条件式，不会误导）。

## 三·五、顺带收口：`StorageOpResult` 的失败分支**从未接线**（@见 区域 02 / TD-02-24）

沿 TD-02-24 的契约类型继续查，发现它**类型过宽、与现实不符**：

| 证据 | 结果 |
| - | - |
| `ok:false` 两支（`error:'engine-unavailable' \| 'rejected'`）构造点 | **全仓 0** —— 4xx 与引擎不可用耗尽都走 **throw**（`kvReadOp`/`kvWriteOp` 内 `if (!isEngineUnavailable(e)) throw e`）；`contentGetKvWithFallback` 那处 `{ok:false,error:'rejected'}` 属 `KvFallbackReadResult`（**另一个类型**，其 rejected 分支是**真接线**的） |
| `ok` 字段 | 恒 `true` ⇒ **5 处 `res.ok && …` 守卫全是死代码** |
| `degraded` / `error` / `status` | **零读取**（`source:'local'` 已等价表达「降级」） |
| 该类型自身 | **已在死代码基线内**（未用导出）→ 仅被 2 个私有函数签名引用 |
| 文档头旧述「4xx 拒收返回 `{ok:false,error:'rejected'}`」 | 与实现（throw）**不一致** → 陈旧表述 |

**处置**（结构类 · 架构师自决）：
- `StorageOpResult<T>`（4 支，导出）→ **私有 `KvOpOutcome<T> = { value: T; source: 'kv' | 'local' }`**（判别位改**字符串** `source`，本仓窄化正常）；
- 删 **5 处恒真 `res.ok` 守卫**（`loadFromKv` ×2 / `writeKvWithFallback` / `contentGetKvWithFallback` ×2）；
- 更正文档头第 9 条 + 两处内核注释（4xx = throw，不是返回信封）；
- 死代码基线 **140 → 139**（`--update-baseline` 修剪）。

**有意未做**：把 4xx 从 **throw 改成返回** `{ok:false}` —— 那是**行为/对外契约变更**（改变 `contentGetAsync` 族 4xx 语义），不属"结构怎么摆"。

**验证**：`tsc` 0 错 · contentStore 及其消费方 **201 例绿** · `lint` 0 · 死代码闸 **139/139** 绿。

## 五、诚实边界

1. **未做闸**：理由见 §二（fail-loud，闸低价值）。若日后希望通过"编译期强制"根除，正解是**缩紧 `strictNullChecks`**（既有演进项，代价另评），不是加正则闸。
2. **2 处存量点已收敛**（见 §三）：`StorageOpResult` / `ImportResult` 改互带键形态，测试端 `as` 绕墙一并去除。它们**改前本就无 tsc 报错**（潜在陷阱）⇒ 属**面向未来**的收敛，**不是**修现行 bug。若日后再遇同类，按 §三 形态改即可。
3. **顺带发现（独立问题，本处不动）**：`StorageOpResult` 的 `ok:false` 成员**当前无构造点**（降级族一律 throw；"4xx 拒收"的诚实返回实际由 `contentGetKvWithFallback` 的 `KvFallbackReadResult`（单接口可选字段）承载）→ 该类型有 2 个**从未被生产**的成员。仅登记，未处置（属契约准确性问题，需另立判断）。
4. **约定本身的失效条件**：`tsconfig` 缩紧 strict 后，本约定即不再需要（注释已写成条件式）。
