## 二、溯源（Phase 1：待裁定项深挖 → 症状 vs 病根）

### 2.1 TD-01-5 三重防重：深挖定论 = `runningRef` 是死冗余（已可还债）

`useNodeGeneration.start` 入口三道并发关（line 199–212）：

```
202  const claim = claimNodeRun(nodeId);          // taskStore 同步 Map 锁（nodeRunning）
203  if (!claim.ok) { … return { ok:false, inFlight:true }; }   // ← 同节点并发重入先被此处拦截
208  if (loading || runningRef.current) {            // ← runningRef 的唯一判点
209    releaseNodeRun(nodeId); return false;
210  }
212  runningRef.current = true;                       // ← R4 同步防重位
```

`claimNodeRun`（`taskStore.ts:388-404`）= `nodeRunning = new Map<string,boolean>()`，**同步、store 级、跨实例全局**。
- 同实例同步双击：第一次 `claimNodeRun` 同步置位（398）；第二次进入 `start` 在 **202 行即命中** `nodeRunning.has(nodeId)` → 返回 `inFlight`，**根本到不了 208 行的 `runningRef` 判点**。
- 跨实例（Agent 与用户节点）：`nodeRunning` 是全局 Map，同样在 202 先行拦截。
- **唯一能到 208 的情形**：`claimNodeRun` 已返回 ok（即本实例刚 claim 成功、未释放）。此时 `runningRef` 与 `loading` 才被读——但这一情形只在「claim 成功后、finally 释放前」的**同一调用内**重入才触发，而 claim 成功已保证独占，再判 `runningRef` 纯属冗余。

**定论**：`runningRef`（R4）与 `loading`（line 208 守卫）在 `claimNodeRun`（P1-E）落定后**语义完全重叠、且永不单独决断**。`runningRef` 是历史修复（R4 防闭包 stale loading）叠加 P1-E 跨实例锁后的**残余死机制**。

> 注：R4 引入时 `claimNodeRun` 可能尚未存在（顺序：先 R4 同实例防重 → 后 P1-E 跨实例锁）。P1-E 落地后 R4 被完全覆盖，但未回收。属 §零.2「能删就删：债务靠结构消灭」。

### 2.2 TD-01-6 双形态返回值：补 caller 证据（维持持平待裁定）

`runNodeGeneration`（`taskStore.ts:423`）返回 `boolean | NodeGenerationRunResult`；`start` 同态。4 个调用方实证：

boolean 旧路径仅由 `retryRegistry` 旧回调（`() => boolean` 兼容签名）存活，文件头已注「勿简化」。**待裁定升级动作**：全量审计 `retryRegistry` 当前注册方——若已无 React 旧版 `useNodeGeneration` 之外的注册者，`boolean` 路径即死缝，可收口为单一 `NodeGenerationRunResult`。本轮**不擅自收口**（属契约形态变更，爆炸半径跨 Agent 工具层）。

### 2.3 TD-01-7 / 新根因：生成契约物理位置错配（★本轮最深发现）

**现象**：第二入口 `scriptBoxEngine.ts`（102KB）手写重复了主范式的契约序列：

```
scriptBoxEngine L502-617（资产生图，逐一对照 useNodeGeneration.start）：
  reportGenerate(taskNodeId,'image',prompt,{modelName})   ← 复用主范式①上报
  taskCtl.progress(5,…)                                    ← 复用主范式②进度
  generateImage(...)                                       ← 复用主范式③执行（门面）
  saveResultToTasks(assetUrl,'image').catch(reportDegrade)← 复用主范式④落盘（已修 TD-01-3）
  taskCtl.done(assetUrl) / taskCtl.fail(...)               ← 复用主范式⑤成败
  （缺失：retry 注册 / 刷新 recover / resultKey 自动回填）
```

此外**第三种合约形态**（文本类，L770-819）：`chatCompletions` → `enqueuePatch` 直接写 `shots[].prompt`，**完全不经任务中心**（无 reportGenerate/done）。

**病根（Phase 1 溯源）**：把「生成契约」（report→progress→run→save→done/fail→recover）**嵌进了 React hook `useNodeGeneration`**。React hook 必须挂在组件实例上、自带 `useNodeRuntime` 瞬态与 `useEffect` 订阅。非 React 的第二入口（`scriptBoxEngine` 是纯 TS 编排引擎，由 `useScriptBoxEngine` 注入 15 个 `onXxx` 回调驱动）**无法复用该 hook**，于是被迫手写重复序列 + 第三种形态。
→ 这不是「剧情盒业务特殊」，而是**契约的物理位置选错了**：它应属于协议/模型层（framework-agnostic），而非 React 表现层。

**对照架构师心法**：这是「末端收敛」反模式——复杂度没在源头（合约层）收口，而是在第二入口手写补丁。正确动作 = **空间收敛法则·源头收敛**：把合约抽成与框架无关的纯执行器，两入口（hook / 引擎）都来消费。

## 四、切割（Phase 3：深模块 / 真缝隙 / 收敛口）

### 4.1 真缝隙 = 「生成合约执行器」（framework-agnostic）

把 `useNodeGeneration.start` 中**与 React 无关**的合约序列抽为纯函数（建议落 `components/base/generation/runGenerationContract.ts`，不入 hook）：

```
runGenerationContract(opts: {
  nodeId: string;                // 支持伪 nodeId（剧本盒 `nodeId-asset-<id>`）
  type: string; prompt?: string; modelName?: string;
  run: (args:{progress,signal,taskId}) => Promise<GenerationResult>;
  resultKey?: string;            // 成功自动 patchData({[resultKey]:url})（主范式 P0-2-b）
  taskCenter?: boolean;          // 默认 true；文本类传 false（不经任务中心）
  recoverable?: boolean;         // 刷新回填（主范式；第二入口伪 nodeId 传 false）
  retryable?: boolean;           // 是否 registerTaskRetry（主范式 true；第二入口 false，TD-01-1 已裁）
  onSuccess?: …; onRecover?: …;  // 业务回写
}): Promise<NodeGenerationStartResult>
```

内部固化：`reportGenerate → progress → run → (patchData[resultKey] + saveResultToTasks + done) | fail → classifyError + toast`，失败可见（对齐 TD-01-2/3）。

**收敛后两入口**：
- `useNodeGeneration`（hook）= 薄壳：持有 `useNodeRuntime` 瞬态 + `agent:task-completed` 的 `useEffect` 订阅 + `AbortController` ref → 调 `runGenerationContract({taskCenter:true, recoverable:true, retryable:true, …})`。
- `scriptBoxEngine` 资产生图 = `runGenerationContract({ nodeId: 伪, taskCenter:true, recoverable:false, retryable:false, run: ()=>generateImage(...) })`（约 15 行，替代现 L502-617 约 115 行）。
- `scriptBoxEngine` 文本类 = `runGenerationContract({ taskCenter:false, run: ()=>chatCompletions(...) })`（run 内自写 `enqueuePatch` 业务回填）。

**度量（§零.3，收敛前→后）**：
- 改动半径：改「done→save 顺序 / 失败留痕策略」须触 2 文件（useNodeGeneration + scriptBoxEngine）→ **1 文件**（执行器）。
- 真相集中度：合约真源 2 份发散（hook 内 + 引擎手写）→ **1 份**（执行器）。
- 跨层跳跃：2 入口各重实现一套序列 → 2 入口同调 1 执行器。
- 认知单元：3 种合约形态（全契约 / 资产部分 / 文本裸 patch）→ **1 形态 + 3 个布尔开关**。

### 4.2 `relayProxy` / `generate` / `taskStore` 判「合格深模块」

三层均窄接口厚实现、无重复、无上帝类，本轮无新增债。`taskStore` 的 `claimNodeRun` 作为并发唯一权威成立（见 2.1）。

### 4.3 `scriptBoxEngine` 体量（TD-01-7 原「拆子模块」待裁定 → 重判）

首轮把 TD-01-7 标为「是否拆生图/文本/连线/尾帧子模块」。本轮深挖后**重判**：拆子模块只是把 102KB 切成几块，并未消除「合约序列重复」这一根因（每块仍各自手写 report→save→done）。**正确动作不是拆文件，是抽合约执行器（4.1）**——拆文件是下游可选美化，非根因。故 TD-01-7 维持「持平待裁定（拆文件）」，另立 **TD-01-8** 承载根因收敛（待翻新/待裁定，因是设计+重构、P0 爆炸半径）。
