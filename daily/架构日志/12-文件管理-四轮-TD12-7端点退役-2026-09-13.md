# 12 区 · 四轮 — TD-12-7 端点退役（`POST /api/resources/save`）

> 日期：2026-09-13 ｜ 触发：**用户裁定「都没用了为什么不删」**（选 B 退役，非 A 改造）｜ 方法：按 `架构师改码7步法.md`。

---

## Step 0 · 这是什么（先把话说明白）

后端有个**特例端点** `POST /api/resources/save`（`handleResourcesSave`）：专收「前端从剪贴板粘贴的 base64 图」→ 解码 → 落盘 → 建资源行。

它的落盘**直调 `writeUploadBuffer`**、**不经过 `writeUploadDedup`**（内容寻址 + 按 contentId 去重的标准编排）——这就是债登记里说的「**第二落盘入口**」：同字节内容可能落成两份物理文件，DB 侧只靠 rescan 的 contentId 查重跳过建行，遗留「无 row 的孤儿文件」等 GC。

而它**前端零生产调用**：`saveResource()` 只被 `contracts.ts` 登记 + 1 个单测引用，没有任何业务流程发这个请求。

## Step 1 · 证伪（真的是死端点吗）

| 检查 | 结果 |
| - | - |
| `grep saveResource` 全 src | 仅 `localToolApi.ts` 定义 + `contracts.ts` 登记 → **0 生产调用** ✅ |
| `grep handleResourcesSave` 全仓 | 仅 `router.ts` 注册 + 后端测试 → **0 内部复用** ✅ |

→ 「零消费的死端点」成立；**顺带**：`/api/resources/batch-save` 早已是「前端零消费 / RESERVED」，本次只处理 save。

## Step 6 · 施工（B 方案 = 退役）

**前端**：
- 删 `localToolApi.saveResource()`；
- 删 `contracts.ts` 的 `saveResource` 登记；
- 删 `tests/unit/resourcesApi.test.ts` 的 `describe('saveResource')` 两个用例。

**后端**：
- `router.ts`：删路由注册 + import；
- `routes/resources.ts`：删 `handleResourcesSave` + 其**专属**的 `decodeDataUrl`；连带删已无用的 import（`writeUploadBuffer` / `mimeToExt`）；
- `index.ts`：启动提示去掉该端点。

**后端测试（关键连带 —— 它原被当「造资源行」的 seed 用）**：
`localtool.test.js` 有 **11 处** + `seedResource()` 走这个 handler 来造数据。处理：
- **`insertResourceRow` 泛化**：支持文件型 `('migrated/a.png')` 与自定义行 `({id,url,folder,name,sha1})` 两种用法；
- `seedResource` 降为该函数的**薄封装**；
- 11 处调用全部改走纯 SQL seed；
- **删 2 个端点多用例**（「缺少 id → 400」「dataURL → 自动落盘」）——能力随端点一起退役（后者本就是被删掉的绕过落盘路径）。

> **顺带收益**：seed 不再经 handler 内部 `debouncedSaveDb` 的 500ms 计时器 —— 正是注释里记的 **T4/T8 假绿陷阱**的入口（该坑当初就是为绕开它才引入 `insertResourceRow`）。
