## 一、链路快照（已读代码取证，非凭文件名猜）

```
节点 UI 按钮（AssetNode / ImageGenerate / VideoGenerate / TextGenerate「发送」）
  └→ 同步调用 sendToResourceLibrary(url, {name,type})
        └→ addResources(...)                // 前端 localStorage 占位（同步，立即可见）
        └→ emitResourceSent(folder)         // 同步广播「已发送」→ 面板 setFolder → reset(true) 重新 rescan

  └→ 紧接着同步 showToast('已发送到素材库', {type:'success'})   // ★ 此时落盘还没开始
```

## 二、溯源（Phase 1：症状 vs 病根）

- 业务能跑，但「发送是否真成功」这件事的**责任归属是错的**：UI 按钮（拿不到异步结果）承担了「宣告成功」的职责；落盘层（拿着成败真相）却选择沉默，理由是「别和已发送提示矛盾」。
- 这不是某个 if 写错，而是**反馈信号的归属位置**错了——复杂度（"到底落没落盘"）没有被放在它唯一能被正确回答的地方（落盘完成的边界），而被放在了它必然答错的地方（UI 发起处）。

## 三、定海（Phase 2：不变式 / 唯一真相源）

- 「素材库 SSOT」= `resourceStore`，但**成功反馈并不归它所有**：UI 直接 `showToast` 成功，绕过了 `resourceStore` 的异步结果。SSOT 只管数据，不管"用户该看到什么结果"，而结果恰恰应是它的产出。
- 边界处无 Guard：`filesApi` 落盘失败归一为 `null`，错误语义在边界被销毁；上层 `persistUrlToBackend` 拿到 `null` 只能"猜失败"，再为"护短"而吞掉——脏数据（假成功）被洗进了 UI。

## 四、切割（Phase 3：深模块 / 真缝隙 / 收敛口）

- `filesApi` 是"全站文件域单点"，却把**失败**也单点吞成 `null`（无判别联合、无错误透传）——它既是落盘单点，也是"失败信息黑洞"单点。
- `sendToResourceLibrary` 的签名 `: Resource[]`（返回前端占位），**不返回也不 await 落盘结果**；调用方因此无法据真相连 toast。这是「反馈权与真相权分离」的结构根。
- 与本仓已落地的同母体对照：**区域 02「诚实结果契约」**要求失败分类唯一实现、fail-closed；**TD-22-2** 已把视频上传 `uploadResult` 的「失败伪造 blob: / 静默」改为「返 null + 消费方显式报错」。**同母体，本链路（发送素材库）未落地。**
