## 一、最优解（Step 0 第 0 步）

**这个能力的正确形态**：localTool 作为唯一出站口，把请求体里所有本机 `/files/` 媒体**在出站前统一内联成
`data:` URL** —— 图片压 ≤1920、视频/音频直读原字节；下游（lovart adapter 等）拿到 data: 后解码上传 CDN。

- **入口**：`utils/resolveLocalImages.ts#resolveLocalImages`（唯一）。
- **链路**：`/files/` → 读盘（图片 Jimp 压缩 / 视频音频原样）→ `data:{mime};base64` → adapter 解码 → 传 CDN。**2 环节，无回环 HTTP**。
- **判据在哪层**：形态 = 唯一一种（base64），无分流判据。
- **真相归谁**：本机文件内容归 `resolveLocalImages`（唯一出站口）。
- **它取代/复用了什么**：取代原「lovart 走回环 URL 交 adapter 自取」妥协路径；复用 `mime.ts#extToKind/extToMime`（不新建表）。

**「换个人来做会写成什么样？」** —— 一个平台为了省一趟 encode/decode 而给自己开一条「请求自己」的回环路，
换个人**不会**这么写：用户 2026-09-20 原话「**所有的网站都是直接内联 base64 的，就这么简单**」。
本案就是把这个妥协**拆掉**（不是修它）。

## 二、根因（Step 2/3）

段① = 从点击到交出 thread_id。改前 lovart 参考图走：
`出站补回环 URL` → `adapter 用 fetchImpl(u) HTTP 请求自己下载`（**无超时**）→ `传 CDN`。
- **无超时**的 HTTP 回环是 249s 级长尾最可能的来源（`lovart_attachments.ts:157` 原 `await fetchImpl(u)`）；
- 且**串行**（逐张 `for + await`）、**未压缩**（对比 base64 路径压 ≤1920 → 上传大图）。

**判据归属**：这是**本地代码可控**（`文件头自检句`：「如果这个妥协明天被去掉，我盖的楼还剩什么？」答案 = 什么都不剩）
⇒ 按债的闭环判据走「**偿债**」，不是「关债」。**见 §七 弯路留痕：我前几轮一度判成「纯网络 → 关债」，是错的。**

## 七、弯路留痕（强制）

1. **第一版（错）**：把「后发先完成」归因为「段①长尾是**网络**、不可控 → 应**就地关债**」。
   - 推理链：段① max 249s，看来像网络；债务闭环判据写「纯网络 → 关债」。
   - 为什么错：段①里 lovart 参考图那条路是**本仓代码**（回环 URL 是**我们自己产的**，`fetchImpl(u)` 下载是**我们写的**且**无超时**），
     属债务明文列出的「本地代码可控（参考图串行同步下载+上传）」那支；且它导致**用户可感知的顺序不可控**（提交顺序被打乱）。
   - 是否完整回退：是（结论已改为「偿债」，代码按此落地）。

2. **用户纠偏原话（当轮最贵的一手证据）**：「顺序不重要，如果真的是后面生成的生成速度快，我认，但是 [段① median 4.8s max 249s]」
   —— 指出要治的是**段①本身的长尾**，不是解释顺序现象。随后用户裁定「在 A 的基础上加视频」= 选定
   「统一 base64 + 视频直读」方案。

## 八、决策留痕（ADR-0050 骨架）

- **用户裁定（2026-10-09）**：cdn 回环妥协退役，本机媒体统一内联 base64；视频/音频一并直读内联（能力不减）。
- **被推翻的既有约定**：2026-09-20「lovart 分支保持原样（就地给回环 URL）」—— 该处置的前提（省 encode/decode）
  被成本证据推翻（换来一次无超时回环 HTTP + 未压缩上传）。落 ADR：`docs/adr/`（见 `adr.mjs add` 当轮）。
- **能力边界**：视频/音频「原样传」与注释里说的「将来抽帧转图」是两件事；本轮只做「原样传」（与改前 cdn 行为一致），不碰抽帧。
