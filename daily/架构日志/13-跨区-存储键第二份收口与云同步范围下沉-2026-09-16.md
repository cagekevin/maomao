### 3.3 云同步范围下沉（TD-13-9 · 用户裁定后的方案）

**用户裁定（原话）**：「云同步他就只负责云同步，他就不要管他要不要去拿个云同步了」+「就是默认不同步嘛，跟现在一样。你把我现在数据要同步那些改成'要同步'不就行了吗？」

落地 = 把「要不要同步」变成**键的字段**（与 `backend` / `fallback` / `timeout` 同类）：

```ts
interface StorageKeyMeta {
  ...
  sync?: boolean;   // ← 新增：缺省 = 不同步（红线）
  label?: string;   // ← 新增：可读名（原 SYNC_LABELS）
}
```

- `contracts.ts` 新增派生入口：`getSyncKeys()`（= `getLocalKeys()` ∩ `sync === true`）· `getKeyLabel()`（查 `label`，缺省回退键名）。
- `cloudSync.ts` **删掉两份清单**，改 `const LS_KEYS = getSyncKeys();` + `syncLabel = getKeyLabel`。

**功能不变得证**（行为断言，见 §四）：派生结果 = **7 个键**，与旧 `SYNC_ALLOW` 逐字相同。

### 3.4 机器闸（防回潮 · 本轮的核心止损）

`check-arch.mjs` 新增两条**反向判据**规则：

| 规则 | 判据 | 治什么 |
| --- | --- | --- |
| **15** | src 全域内，**已登记固定键的字面量**直接传 contentGet/Set/Delete(+Async)/Subscribe/ReadThrough → 违规 | 既有 `check:keys` 只校验"登记没登记"，对"已登记又被抄第二份"完全无感（M2 母体：红线只在注释里） |
| **12-b** | `cloudSync.ts` 内出现任何**已登记固定键字面量** → 违规 | 同步范围第二份清单回潮 |

两条均**照 STORAGE_KEYS 推导**（新增键自动纳入，无需改闸）+ `assertScanned` 基数自检（0 扫描 = 红灯）。

**规则 12 的注释同步更新**：原写「云同步范围真源 = cloudSync 的 SYNC_ALLOW」→ 改为「= 登记表 `sync` 字段」。

## 五 · 弯路（必须留痕）

### 弯路 ①：把「SYNC_ALLOW 是独立关注点」当结论写进注释（**已被用户推翻，注释已回改**）

- **当时的推理链**：`SYNC_ALLOW` / `SYNC_LABELS` 不是"键名定义"，是"哪些键进云/怎么显示"的清单 → 判为**独立关注点**（比照 TD-16-12「`EXT_BY_TYPE` 是独立关注点」的先例）→ 故我在 contracts 注释里写「保留自身清单结构，只把键名字面量换成引用常量」。
- **为什么是错的**：TD-16-12 的 `EXT_BY_TYPE` 是"**每类首选输出扩展名**"（与 ext→kind 方向不同、值集也不同，是真独立关注点）；而 `SYNC_ALLOW` 里的每个元素**就是 STORAGE_KEYS 的键本身**——它不是"另一件事"，它是**键的属性**（与 `backend`/`fallback`/`timeout` 完全同类）。判"独立关注点"判错了。
- **用户裁定**：「云同步他就只负责云同步，他就不要管他要不要去拿个云同步了」+「就是默认不同步嘛…把我现在数据要同步那些改成'要同步'」。
- **是否已完整回退**：是。contracts 那两段注释（「唯一例外」「独立关注点」）已**回改原文**为「该判断已被推翻 + 现均已下沉为字段」，不是只记在本文件里。

### 弯路 ②：收口收过头 —— 把**非存储条目**的显示名一起删了（**既有测试当场红暴露**）

- **现象**：`cloudSync.test.ts` 2 条红 —— `expected [ 'providers' ] to include 'API 供应商配置'`。
- **根因**：`SYNC_LABELS` 里有两项**不是** `STORAGE_KEYS` 的键：`providers`（走 localTool `/api/providers`）与 `accounts`（只是 `yimao_accounts` 的**短名**）。我改派生后 `getKeyLabel` 查不到 → 回退裸键名。
- **修法**：`accounts` 调用点改传**真键** `KEY_YIMAO_ACCOUNTS`（label 本就在登记表内）；`providers` 是真异类 → 在 contracts 加**极小**的 `NON_STORAGE_SYNC_LABELS`（唯一成员 `providers`，非第二份清单：`sync`/`label` 判据仍在登记表）。
- **教训**：7 步法 7.2 —— **收口后既有测试变红 → 先假定"我的收口越界了"**，事实正是。

### 弯路 ③：把前缀常量写窄（**既有测试当场红暴露**）

- **现象**：`d3dPersistence.test.ts` 1 条红 —— `expected false to be true`。
- **根因**：我把常量写成 `'director3d-project-'`（带尾横线），但既有契约是 **`'director3d-project'` 本身也算工程键**（`isProjectPersistenceKey('director3d-project') === true`）。
- **修法**：常量恢复为**不带尾横线**的 `DIRECTOR3D_PROJECT_PREFIX = 'director3d-project'`，`KEY_DIRECTOR3D_PROJECT = DIRECTOR3D_PROJECT_PREFIX`；动态键处补 `-${nodeId}`。
- **教训**：同上 —— 既有测试锁的是**行为契约**，我在收口时把语义改窄了。

> 弯路 ②③ 都是**同一类**：收口时只盯着"消除第二份"，没有逐项核对该能力的**既有语义边界**。

### 弯路 ④：跑了一堆无关验证（用户点名）

用户原话：「跑的这些东西有一半都是多余的」「禁止连续跑全量测试，你这样会让我电脑卡死的」。
- 多余项：3 个探针各跑两遍（复验那次多余）· `check-storage-keys`/`check-silent-catch`/`check-dead-code`（我没碰 catch / 死代码）· 把 6 个测试文件拆开单独跑（`cloudSync`+`d3dPersistence` 那两个文件已覆盖）。
- **今后口径**：只跑「受影响的测试文件 + tsc + 我改动的闸 + 每个新规则**一次**探针」。全量测试禁连续跑。
