## 二、溯源（Phase 1：症状 vs 病根）

- 视频引擎 `videoEngine.ts` 是「领域无关的媒体操作」层（trim/concat/gif/metadata + 落盘），与领域模型解耦良好（composite.ts:13 注释明言渲染合成器不进本文件）。这是对的。
- 真问题不在引擎算法，而在**引擎与上层之间的两个契约边界**：① 跨源读取策略（谁决定 crossOrigin）；② 落盘结果「持久 vs 临时」的判别。两者都因「模块各自就近处理」而生出第二份真相/不一致。

## 三、定海（Phase 2：不变式 / 唯一真相源）

- `uploadResult` 的返回形状是**失败语义不诚实**的典型：成功与「降级兜底」共用 `{ url }` 单字段，无判别位。调用方无法区分 `url` 是 `/files/xxx.mp4`（持久）还是 `blob:xxx`（刷新即失效）。这与本模块 `AudioOutcome` 判别联合（lines 119–131）「禁止用 boolean+嗅 reason 字符串」的自陈哲学**自相矛盾** —— 模块内部一边立规矩一边破规矩。
- 跨源读取策略的唯一真源在 `captureFrame.ts::setCrossOriginForReadable`，但 `useVideoPoster` 未复用，另立一套相反逻辑。同一条「同源/video 是否跨源」规则出现第二份实现。

## 四、切割（Phase 3：深模块 / 真缝隙 / 收敛口）

- `videoEngine.ts` 941 行但职责内聚（纯媒体操作），不拆。
- 真缝隙在**边界**：`uploadResult` 返回值应带持久性判别；跨源策略应单一收口。
- 无上帝类 / 无过度抽象。

6. **原型兜底 ≠ 生产路径**：健康模块把原型兜底隔离或显式报错，绝不静默兜底当主路径。

### 二、债的共性根因（4 笔债 ≠ 4 个问题，是 2 个家族）
- **家族 A：URL/IO 生命周期未类型化（TD-22-1 / TD-22-2 / TD-22-5 同源）**
  - 证据链：
    - `uploadResult` 返回 `{ url: string }`（videoEngine.ts:919-924）—— **裸 string，无持久性标记**；落盘失败仍返 `URL.createObjectURL(blob)` 瞬态 blob:，类型上**不可区分**。
    - 全节点 `assetUrl?/url?/videoUrl?: string` 全是裸 string（grep 命中 45+ 处），持久化时不区分 `/files/`（持久）vs `blob:/data:`（瞬态、刷新即死）。
    - `classifyAssetUrlKind`（assetType.ts）只分类**媒体类型**（image/video/audio/text），**不分类生命周期** —— 团队已建"URL 分类单一真值源"能力（EXT_KIND 表、"禁止就地手写正则"），但**维度不全**。
    - `resolveAssetUrl`（assetUrl.ts:175）是图片"唯一出口"但只管缩略图/scope 策略，**不裁决"可否 canvas 读回 / 可否持久化"**。
  - 三债同源映射：
    - **TD-22-2**：返回裸 string + 静默 blob 兜底 → 被当持久节点源，刷新失效。
    - **TD-22-1**：crossOrigin 读回正确性依赖 URL 种类（blob:/data: 不需 CORS、/files/ 需 CORS 头），但无单一"是否可读回"裁决 → 3 处散写（captureFrame.setCrossOriginForReadable / videoEngine.loadVideoElement / VideoExtractNode）。
    - **TD-22-5**：GIF blob 产物未升级为持久 URL（同"瞬态→持久"漏升级家族）。
- **家族 B：契约腐化 / 死字段（TD-22-3 poster）**
  - 正交小类：定义了字段 + 读取分支但零写入，持久化封面契约未兑现。与生命周期无关，单独处理（删字段 or 写回）。

### 三、底层共性结论
- **最深根因 = "媒体 URL 的生命周期/持久性语义不是一等类型（裸 string 散落全树）+ 原型兜底静默化为生产路径"**。
- 这恰是健康 DNA 第 2/3/6 条的**反面实例**：若有 `MediaUrl` 判别联合（persistent|transient）+ 单一 `resolveAssetUrl(url,{scope,persist})` 裁决点，TD-22-1/2/5 会在**类型/单点层**被消除。
- **健康模块已在各自 reinvent 同一护栏**（证明模式可行、只是未共享）：
  - `Director3DNode.handleExit`：blob: → fetch → uploadFileToLocal 升级为 /files/。
  - `d3dPersistence.externalizeProjectImages`：data: → saveInlineToLocal 升级。
  - `sourceResolver.ClipSource`：源地址判别联合（按来源而非生命周期，但示范了 union 手法）。
  - `filesApi.uploadFileToLocal`：失败返 null 强制显式处理（反 `uploadResult` 静默 blob）。

### 四、统一收口行动（4 债归并为 2 工程）
**工程甲："媒体 URL 语义统一"，吸收 TD-22-1 + TD-22-2 + TD-22-5**
1. 引入 `MediaUrl` 判别联合（补**生命周期维度**）：
   ```ts
   type MediaUrl =
     | { persistent: true; scheme: 'files' | 'http'; url: string }
     | { transient: true; scheme: 'blob' | 'data'; url: string };
   ```
2. `assetType` 增 `classifyUrlLifetime(url)`（blob:/data:=transient；/files//http(s)=persistent），复用 EXT_KIND 同款"单一真值源"纪律。
3. `resolveAssetUrl` 升级为唯一裁决点：据 lifetime 自动决定 crossOrigin（TD-22-1，复用 setCrossOriginForReadable）、据 persist 标志拒绝/升级瞬态 URL（TD-22-2/5）。
4. `uploadResult` 弃用静默 blob 兜底 → 改 `uploadFileToLocal`（null 显式报错），与 Director3DNode/director3d 同款；videoEditor 两消费点据 null 显式 toast。
5. 对齐既有权威：sourceResolver 单出口、assetType 单表、docs/123 类型化铁律。

**工程乙："poster 契约兑现/删"（TD-22-3 单独）**：二选一，与工程甲正交、可并行。

→ 4 笔债 → 实际 **2 个工程**（"媒体 URL 语义统一" + "poster 契约"），工作量与风险显著低于"4 笔独立债"；且工程甲与已登记的健康 DNA（判别联合/单点裁决/不静默/原型兜底隔离）完全同向，是"顺手还债"而非"推倒重来"。

### 全量视频域最终账（再更新）
7 子域 / 审 ~40 文件分组：待还债 **4 笔**，但可归并为 **2 工程**（家族 A「媒体 URL 语义统一」吸收 TD-22-1/2/5 + 家族 B「poster 契约」吸收 TD-22-3）；健康 ~30；director3d 集成实证为家族 A 的正确样板；无漏审。

## 十三、第七轮·真底层共性（2026-09-13 续）

> 触发：用户"往底层去找，还是视频领域的底层"。前六轮在模块层/共性层打转；本轮凿到视频域**真底层三件套**（传输 `httpClient` / IO 基座 `filesApi` / 媒体原语 `captureFrame`），追问"债是不是因为底层缺能力"。结论发生反转。

### 一、真底层三件套（视频域全部坐在它们之上）
1. **`httpClient.ts`（传输）**：单一 fetch 入口；无默认超时（15s 会掐断上传，见文件头）；`isFetchNetworkTypeError`（L35-44）把"fetch 网络失败 TypeError"与"我方代码 bug TypeError"**区分开**（TD-03-12），避免代码 bug 被伪装成网络错误重试 3 次；错误分类 Timeout/Network/Http/Abort；仅网络/超时重试，业务 4xx/5xx 不重试；`silentSuccess` 仅限高频可还原写。✅ 零债。
2. **`filesApi.ts`（IO 基座 = `blob/file → 持久 /files/ URL` 的唯一正确实现）**：
   - `uploadFileToLocal`（L246-281）：`try{ httpRequest multipart }catch{ logger.warn; return null }` → 成功返 `http://127.0.0.1:18080/files/...`，**失败诚实返 null（绝不伪造 blob:）**。
   - `saveResultToTasks`（L434-468）：**显式拒绝 blob：** `if (url.startsWith('blob:')) return null`（L435）—— 它知道 blob: 瞬态、**拒绝"持久化"它**；并对已本地 URL `if (isLocalFileUrl(url)) return url`（L438）防双落盘。
   - `resolveNodeAssetUrl`（L324-334）：File→`uploadFileToLocal`→失败→`fileToDataUrl` 兜底→失败→null；落盘失败经 `notifyLocalServiceDegrade`（TD-03-13）**一次可见 toast**（"本地服务未启动，素材已临时保存"），不再静默。
   - `persistInlineOrKeep`/`showThenPersistInline`：图像入节点**唯一统一落盘策略**（"落盘只是刷新不丢的优化，不是显示前提"），调用方禁止再写第二套降级。
   - 全模块"全站文件域单点"（候选 C 收口），`moveFile`/`resolveMovePaths` 已修正"url 是唯一磁盘真源"纠正 folder/name 漂移（TD-12-8）。✅ 零债，且自带"降级可见"纪律。
3. **`captureFrame.ts`（媒体原语 = `seek+drawImage` + crossOrigin 唯一裁决）**：
   - `setCrossOriginForReadable(video,url)`（L86-89）：**crossOrigin 唯一正确裁决点**——`sameOriginUrl(url)` 为真（`/`、`blob:`、`data:`、同 origin 绝对）**不设** crossOrigin（避免网关不对 `/files/*` 回 ACAO → canvas 变 opaque → `toBlob null` 静默失败）；真跨源才设 `anonymous`。注释 L77-84 精确解释这是"旧实现恒设 crossOrigin"在同源部署下的错误修正。
   - `drawVideoFrame`（L154-222）：底层探测原语，`addEventListener`+结算 `removeEventListener`（不占 `onxxx`），`<1ms 直接绘制` 守卫防 seek 永久挂起。
   - 文件头"同机制清单"：4 处同机制已收口到 1 实现，5 处**异类显式登记不合并**（含 clipboard.ts 用 3 条语义不可通约判据拒绝并入）—— 这是"Step 3 先分重复种类再统一"的方法论文档化。✅ 零债，且自带"明确不覆盖/已知边界"纪律（L50-71）。

### 二、🔑 深层反转：债不是"底层缺能力"，而是"消费者绕过已存在的单点原语"
前几轮把共性归因为"URL 生命周期未类型化（裸 string）"。凿到底层后发现**更精确的共性**：

> **视频域的真底层三件套（`filesApi`/`captureFrame.setCrossOriginForReadable`/`httpClient`）已经成熟、正确、零债；4 笔债（尤其 TD-22-1/2/5）全部是"消费者绕过这些既有单点原语、自己另写一套会静默失败的 ad-hoc 逻辑"。**

逐债对号入座（证据）：
- **TD-22-2**：`uploadResult`（videoEngine.ts:921-940）**成功路径其实已 delegate 给 `uploadFileToLocal`**（L932），但**失败分支**自作主张 `return { url: URL.createObjectURL(blob) }`（L935/938）——伪造瞬态 blob: 当成功。而同层 `saveResultToTasks` 在同样失败处**老實 `return null`**（L435/467）。即：债 = "失败分支没复用 `saveResultToTasks`/`uploadFileToLocal` 的 null 纪律"，不是缺能力。→ **修复 = 把 `uploadResult` 失败分支改成返 null（或 delegate 给 `saveResultToTasks`），3 行即可，无需新原语**。
- **TD-22-1**：`VideoExtractNode:290` / `videoEngine.loadVideoElement:799` 要么恒设、要么不设在 crossOrigin，而**正确的单点 `setCrossOriginForReadable` 已存在且正确**（captureFrame.ts:86）。债 = "没复用 `setCrossOriginForReadable`"。→ **修复 = 这 2 处改调 `setCrossOriginForReadable(url)`，与 `buildFilmstrip`/`captureFrame` 同款**。
- **TD-22-5**：GIF blob 产物未走 `filesApi` 落盘（同"绕过 IO 基座"家族）。债 = "GIF 产出没 delegate 给 `filesApi.uploadFileToLocal` 换 /files/"。

### 三、最深的底层共性（方法论层）
- **健康 DNA 第 3 条"单点裁决"在底层被严格执行**（`httpClient`/`filesApi`/`captureFrame` 都是单点），而债全部发生在"上层消费者没遵守单点、另起炉灶"——这是**单点裁决纪律的越界 violation**，不是能力缺口。
- 代码库已有"防越界"的方法论文档：`captureFrame.ts` 头的"同机制清单 / 异类登记 / 明确不覆盖"，正是为防"有人以为原语没覆盖一切、于是另写一套"。TD-22-1/2/5 恰是该方法论在 `uploadResult`/`VideoExtractNode`/`videoToGif` 三处**未被执行**的实例。
- 因此"URL 生命周期未类型化"是**表象**，真正根是"上层绕过底层已存在的持久化/crossOrigin 单点原语"。`MediaUrl` 判别联合（第十二节工程甲）的价值，从"补能力"修正为"**类型级护栏，让'绕过单点原语'在编译期不可写**"（transient URL 不可传入持久化写函数）。

### 四、对还债的修正结论（更省、更低风险）
- **工程甲「媒体 URL 语义统一」工作量被高估**：底层原语（`filesApi`/`setCrossOriginForReadable`）已就绪，**无需从零建 `MediaUrl` 即可先消除 3 笔债**——
  - TD-22-2：改 `uploadResult` 失败分支返 null（3 行）+ 2 消费方据 null 显式 toast。
  - TD-22-1：2 处改调 `setCrossOriginForReadable`。
  - TD-22-5：GIF 产物 delegate `filesApi.uploadFileToLocal`。
  - 以上均为"接回既有单点原语"，**风险极低、可局部验证**，不必等大重构。
- `MediaUrl` 判别联合降级为**收尾护栏**（防回归），而非还债前置。
- **底层三件套零债**这一事实，意味着整个视频域的修复面集中在"上层 3-4 处绕过点"，不是地基问题 → 还债信心大幅提升。

### 全量视频域最终账（再更新）
7 子域 / 审 ~43 文件分组：待还债 **4 笔** = 2 工程；其中 **TD-22-1/2/5 的根因从"底层缺能力"修正为"上层绕过已存在的 `filesApi`/`setCrossOriginForReadable` 单点原语"** → 修复可先局部接回单点（低风险），`MediaUrl` 类型护栏降级为收尾；**底层三件套 `httpClient`/`filesApi`/`captureFrame` 经审零债**。
