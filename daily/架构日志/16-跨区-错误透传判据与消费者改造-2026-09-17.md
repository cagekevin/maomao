# 16-跨区 · 错误透传判据与消费者改造（2026-09-17）

**触发**：用户裁定「**错误必须由产生它的那层以判别联合透传（含可展示信息）；消费者只转发、禁止自己显示/加工！**」

## 〇 · 判据（本轮唯一真源）

1. **产生失败的那层**负责把失败**定型**：判别联合（`{ok:true,…} | {ok:false, message, error?}`），
   **并给全"可展示信息"（人话）** —— 因为只有它知道真相。
2. **消费者只转发**：不改写、不翻译、不拼接、不自造判词、**不自己决定"该不该提示"**。
3. `message === ''` ＝ 生产者声明"这次失败**不必打扰用户**"（如"内容里根本没有 JSON"＝正常结论）。
4. 消费者仍可**留痕给开发者**（`logger`）与**选择展示时机**（如"表格协作没打开就不打扰"）——
   但**判词与文案必来自生产者**。

### 6.2 代价（写明）+ 回潮风险（登记）

**代价**：
1. **"禁静默吞"从机器闸降级为判据 + 人审**（写在 `架构师改码7步法` 禁令表 + 本文件）。

**回潮风险**：同类形态**可能回涨**（它此前正是靠闸压着的）。
**但不能靠"再加一道闸"解决** —— 新闸若"合法通过成本"仍低于"绕行成本"，会重蹈同一个坑。
真正的替代是**三件非闸手段**：① 生产者判别联合（类型层，写错**编译不过**）② 消费者只转发（评审判据）③ 对账测试（行为断言）。

## 七 · 施工：`filesApi` 判据落地（第 1 批 / 共 3 批）

**为什么从它开始**：`filesApi` **自己有正确范式** —— `SaveTasksOutcome` 的注释就写着

## 十 · 第 4 批：`audio.ts` 音频解析链（**产物受损**级）

**病根**：3 个私有原语 `catch { logger.warn; return null }` ⇒ `null` 只让**开发者**看到失败，
而上层 `collectAudioElements` 拿到 `null` 就 **`if (!buffer) return null` 静默跳过该元素**
⇒ 用户在**导出的成品**里才发现"这段音频没了"，零提示、事后无从回查。
**比"播放时没声音"更严重** —— 那是**产物受损**（导出的视频/字幕用的音频缺了几段）。

| 层 | 改前 | 改后 |
| --- | --- | --- |
| `resolveVideoAudioBuffer` | `Promise<AudioBuffer ｜ null>` + `logger.warn` | `AudioResolveOutcome = {ok:true,buffer} ｜ {ok:false,message}` |
| `resolveAudioBufferForElement` | 同；且"素材缺失／不含音轨／解码失败"**三者都压成同一个 `null`** | 同；**三种失败各自给判词**（可判别） |
