### 3.4 TD-04-58 · 改判非债（**用户质疑触发实测** —— 本轮最重的一条）

**用户质疑原话**：「加载期需要那么久吗，如果是这样，你还不如不优化」⇒ 按铁律 3，审计的「489.79 kB 下载期空白 ⇒ 用户可感知退化」是**描述**，必须重新取证。

**实测（真实 Chromium 冷缓存 ×3，探针 `tmp/_m1probe/measure-editor-chunk2.mjs`）**

| 量 | 值 |
| --- | --- |
| chunk 网络耗时 | **3.4 / 8.9 / 16.5 ms**（本地服务 127.0.0.1:18080，transfer 496301 B，未压缩） |
| 首次打开剪辑器总空白 | **58.4 / 58.8 / 117.4 ms** |
| 之后每次打开 | **0.3 ms**（模块已在内存） |
| 首屏收益（1B） | gzip **728.65 → 586.81 kB（−19.5%）**；`index.html` 的 modulepreload 列表**不含** EditorShell ⇒ 确为按需拉取 |

**实测输出（机器产 · 方法：Playwright 真实 Chromium，每个样本**全新 context** 冷缓存，`goto` 后 `waitForTimeout(800)` 等首页 CPU 稳定，再 `page.evaluate(() => import(chunk))` 计时）**

```
run1: 冷 import=58.4ms ｜ 其中网络=3.4ms ｜ transfer=496301B
run2: 冷 import=58.8ms ｜ 其中网络=8.9ms ｜ transfer=496301B
run3: 冷 import=117.4ms ｜ 其中网络=16.5ms ｜ transfer=496301B
热缓存 import(): 0.3ms      （模块已在内存）
```
> `transfer=496301B ≈ decodedBodySize` ⇒ 本地服务**未压缩**发送（即用户实际拉的是 484 kB 原始体积，不是 gzip 141.85 kB）；即便如此，loopback 下也只有 3–17 ms。

**判据**：空白期的绝大部分（≈50–100 ms）**不是下载**，而是编辑器自身 JS 的**解析 + 执行** —— 这部分成本 1B 只是**搬家**（启动期 → 首次打开），**不是新增**。撤销 1B 不会消灭它，只会把它挪回启动期，并让**每个**用户首屏多付 gzip **+141.85 kB**（含从不打开剪辑器的人）。
⇒ **保留 1B + 保留 `fallback={null}`**：60–120 ms 的懒加载挂 spinner 会「闪一下」，反而不如不显示（这也是快速懒加载场景的通行做法）。
**已按 A7 回改原文**（见 §七）。若用户仍要加载反馈，改动是 1 处 fallback（本裁定不含该改动）。
