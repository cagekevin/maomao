## 一 · 弯路留痕（强制 · 与结论同等对待）

### 弯路 1：把「为老用户保留」当成了一个正经备选（用户当场改判，并升级为项目约定）

**当时的推理链**：我按"三个方案 + 推荐 A"汇报 —— A 保留迁移器/OPFS 清理（推荐，理由"删它的唯一收益是代码短一点，
风险是不可逆地放弃存量"）、B 删除、C 部分保留。**我把"存量用户"当成了一个真实的成本项来权衡。**

**为什么错**：这条**本来就不是本项目的取舍维度** —— 用户裁定「**不管老用户死活，只管正确性**」。
我把一个"项目已明确不接受的约束"重新摆上桌，等于**把已定的判据又退化成问答题**（正是 7 步法 A3 的翻车形态）。
**处置（超出本轮的收口）**：该约定已写进 **`架构师改码7步法.md` 开头「项目约定」**（管全程）
+ **Step 4「取舍顺序」把"兼容性"明列为恒排最后**，并附本轮实证（13 个文件 = 多余工作）。
—— 否则下一个 AI 会**重走这一步**（弯路的思路"有理有据"，所以必须留痕）。

### 弯路 2：删 `getMigrationState()` 前**没 grep**（靠推理删，被 tsc 兜住）

**当时的推理链**：迁移器整层删了 ⇒ `migrationState` 没有数据来源 ⇒ 连同 `getMigrationState()` 一起删。
**我直接下了"全库零调用"的结论，但没有跑 grep。**

**为什么错**：`src/.../managers/save-manager.ts:138` 真的在用它（`if (…getMigrationState().isMigrating) return { ok:false, reason:'migrating' }`）。
`tsc` 报出 TS2339 才暴露。**"推理出来的零消费"不是零消费**（铁律：任何判断都要取证，包括"没人用它"）。
**正确处置**：删掉该守卫（迁移器没了 ⇒ 分支恒不成立 ⇒ **死守卫**）+ 连带删 `SAVE_FAIL_REASONS` 里的死枚举值 `'migrating'`。

### 弯路 3：幽灵 API 的第一反应是"改实现"，不是"删"

**当时的行为**：`getStorageInfo` / `getProjectStorageInfo` / `getDetailedStorageStats` 三个 API，我**先按新载体把它们重写了**；
写完自查才想起来问"**谁在用**" → grep 全库**零消费者** ⇒ 改为**整个删除**。

**为什么错**：对"零消费者 + 语义描述已消失的形态（`isOPFSSupported`/`isIndexedDBSupported`）"，
第一反应应是 M6（幽灵预留 → 直接删）；"把它迁移到新载体"是**为不存在的人维护代码**。
**判据**：改之前先问一句「**改完谁会用到它？**」——答不出就是该删，不是该改。

## 三 · Step 1 证伪（债描述 vs 取证）

| 债描述 | 取证真相 |
| --- | --- |
| 「IndexedDB **迁移遗留** … 零生产写入」 | 迁移器**本身是活路径**（`loadProject`/`loadAllProjectsMetadata` 每次都会跑 `ensureMigrations()`），只是它的**产出无消费者**：它把 `video-editor-projects` 表里的旧工程做 schema 升级后**写回同一张 IDB 表**，而 `loadProject` 只读 **KV** —— 即**每次开工程真跑一遍 I/O，结果没人看** |
| 「OPFSAdapter **半死残留**」 | 对：T4 后无写入，只剩 `deleteMediaAsset`/`deleteProjectMedia` 的 `remove`/`clear`（清用户机器上的旧二进制） |
| 「删 IndexedDB 适配器」（四期方案） | **做不到**：`IndexedDBAdapter` 是素材元数据的**活载体**，不是遗留 |

⇒ **真债成立**，但**形态与描述不同**（不是"清残留"，是"载体未统一"）。

## 四 · Step 2 归因（母体）

- **M7（工程数据无统一契约）** 的最后一笔：剪辑器四类数据散在**四种载体**，素材元数据独留 IndexedDB
  ⇒ 不进备份（backupStore 只覆盖 local 键 + KV）· 不跨端 · 与工程本体不同生命周期。
- **M6（幽灵预留）**：6 个零消费者 API + 1 套产出无消费者的迁移器。
- **M3（同一件事两个入口）**：迁移编排在 `StorageService` 与 `ProjectManager` 各有一套。

⇒ 一次收口可同时消灭三类症状 ⇒ 母体成立，一次做净（不拆多轮）。

## 五 · Step 3 定位置（为什么这么定）

| 决策 | 判据 | 结论 |
| --- | --- | --- |
| 素材元数据放哪 | 它属**工程本体的一部分**（按 projectId 隔离、需跨端）⇒ 按载体两分法归 **KV** | `video_editor_media_meta_{projectId}`（`backend:'kv'`，登记即自动进备份） |
| **不内联进 `TProject`** | docs/133 §2.3 的"分键"决策是为了**避免大 payload 互相拖累**（列表/本体/活跃 id 分键）；元数据内联会让"改一个素材 = 重写整个工程"并触发无谓 CAS 冲突 | **独立键、整表一键**（与工程本体同粒度） |
| 每素材一键？（更细粒度） | 本表只是**元数据索引**（几十条 × 数百字节）；拆键会引入"列键 + N 次读"，复杂度不换收益 | 否决，整表一键 |
| 要不要 CAS | 原 IDB 表是 last-write-wins；本轮目标是**载体收口**，不是并发升级（升级会改变调用方失败语义，409 需 UI 消费） | **沿用等价语义**（注释已写明升级路径） |
| OPFS / 迁移器 / 幽灵 API | 「留这个是为了谁？」→ 答案是"老用户的旧数据" ⇒ 按**项目约定**直接删 | 全删 |
