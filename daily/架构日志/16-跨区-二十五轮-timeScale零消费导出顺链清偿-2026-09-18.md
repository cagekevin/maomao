## 二 · 弯路（与结论同等重要）—— 我犯了闸头**明确警告过**的错

1. **第一版只删了 3 条"链尾"**（`fitZoom`／`dropIndexAt`／`rectsIntersect`）—— 跑闸**当场红**：
   ```
   ❌ 新增死代码 1 条（基线外）：
      + src/components/base/utils/timeline/timeScale.ts::exports::clampZoom
   ```
2. **为什么**：`clampZoom` 原本**被同文件的 `fitZoom` 内部调用** ⇒ knip 不把它算"死"；删掉 `fitZoom` 后它才露出来。
   这正是 `check-dead-code.mjs` 文件头第 37-41 行写的原话：
   > **只删链尾（无人 import 的那层）会让死代码上移一层**（knip 转而报中游）= 打地鼠，
   > 且下次跑闸反而变红 → 人会觉得"删代码不如塞基线"，**正是成本倒挂的入口**。
   > 正确动作：`node scripts/mv-sync-refs.mjs refs <file>` **顺消费者查到底**，一次清干净。
3. **顺链查到底的结果**：这一族实际是 **6 个导出 + 2 个类型 + 2 个常量** ——
   `clampZoom` 同样零生产消费；两个缩放上下限常量（`MIN/MAX_PIXELS_PER_SECOND`）唯一的"消费者"就是 `clampZoom`。
   - ⚠️ **取证坑**：`ImageEditor.tsx:299` 有个**同名局部** `clampZoom`（`useCallback`）—— 那是**巧合撞名，不是消费**
     （`grep clampZoom` 会把它一并捞出来，**别误判**；要以 import 关系为准）。
4. **一次清干净后复跑**：`✅ 无新增死代码`，且闸精确报出那 3 条基线项消失 ⇒ 链上再无残留。

> **为什么这条弯路值钱**：闸的报错（"新增 1 条"）**没有**直接告诉我该删谁 —— 它把我按在"顺链查到底"这一步上，
> 而这一步的产物比"我本来想删的 3 条"多出一倍。**这是闸在生产正确行为，不是在拦我**（成本守恒律的正例）。
