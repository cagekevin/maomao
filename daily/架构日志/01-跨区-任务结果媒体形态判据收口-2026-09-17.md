## §一 · 症状与只读取证

**症状（用户）**：每次生图，localTool 终端出现 3 条

```
[passthrough] 2026-09-17 07:33:31 | GET /%E6%88%91%E6%B3%A8%E6%84%8F… | -> lgw.lovart.ai | ERR | 10581ms | fetch failed
```

路径是 **URL 编码的中文正文**（AI 助手的历史回复），每条白等 ~10.5s 才失败；**图本身生成成功**（`contract·success` + `/files/tasks/*.png`）。

**取证链（全程只读）**：

| 步骤 | 手段 | 结论 |
| --- | --- | --- |
| ① 谁发起的 | 透传层入口加诊断（`referer` / `sec-fetch-*`） | `dest=image mode=no-cors referer=http://127.0.0.1:18080/` → **`<img>`**（fetch/XHR 为 `cors`） |
| ② 数据是什么 | `task-inspect.mjs --sql` 查 tasks 表 | **正好 3 行**：`type='text' status='completed'`，`result_url` = 正文（821／206／101 字节），`node_id` 全是 `textNode-*` |
| ③ 出口在哪 | 读 `TaskCenter.tsx` | `:353` 缩略图 `type==='video' ? <VideoThumbnail> : <img src={render(task.resultUrl)}>` —— **非 video 一律当图片** |
| ④ 为何每次作图都复发 | 读 `taskStore.ts` | `reportGenerate()` 首句 `openTaskCenter()` → 生成即自动展开任务中心 → 三条文本任务重新挂载 `<img>` |
| ⑤ 写入侧是否还在生产 | 全库检索 `ok: true, url:` ／ `url: r.content` | **0 命中** → 当前代码不会再把文本写进 `result_url`；那 3 行是 8 月存量脏数据 |

**值得记下的对照**：TD-01-11 当年已裁定「文本类任务无 resultUrl（`publishTaskCompleted` 硬校验空 URL 不广播）」，
但**消费端从未按这条契约分流** —— 契约定了、渲染端仍 fail-open，正文便顺着 `resultUrl` 字段一路走到 `<img src>`。

## §二 · 正确形态（先写下来，再动手）

**能力：任务中心的「结果展示」（缩略图／预览／下载）**

- **入口**：`Task`（`taskStore` 内存态 + 后端持久行）。
- **链路**：`task.type` →（唯一判据）→ 媒体形态 → 三个出口各自决定渲染。
- **判据放哪层**：`type` 是 `Task` 的字段，判据属 `Task` 的展示语义 → 与既有 `typeLabel`／`statusLabel`／`statusDotClass` **同层**（`taskStore.ts`）。
- **真相归谁**：只有**显式登记为媒体**的 type 才有媒体结果；其余（text／audio／未知）**无媒体**。
- **失败诚实**：未知 type 不得被猜成任何形态（fail-safe）—— 宁可不渲染，也不制造一次请求。

## §五 · 施工

### 5.1 判据收口 —— `src/components/base/store/taskStore.ts`

新增唯一原语（与 `typeLabel` 同层）：

```ts
export type TaskMediaKind = 'image' | 'video' | 'none';
const VIDEO_TASK_TYPES = new Set(['video', 'sd2Video', 'discountVideo']);
export function taskMediaKind(type?: string): TaskMediaKind {
  if (type === 'image') return 'image';
  if (type && VIDEO_TASK_TYPES.has(type)) return 'video';
  return 'none'; // fail-safe：不为未知类型制造媒体请求
}
```

## §七 · 弯路留痕（强制）

**弯路 ①：先按「谁的代码会发请求」找，跳过「让请求自报家门」——连错两次。**

- 推理链：见 3 条 `GET /<正文>` → 猜「某个 fetch／media provider 把文本当 URL」（先翻 `media/providers/*`、
  `assetUrl.normalizeAssetUrlForSend`，又去看未提交的 git diff 想找回归）→ 全部落空；
  再猜「后端为防失败先探活一次」→ 也不成立（探活不会把正文编码进路径，且失败与生成结果无依赖）。
- 为什么错：**请求形态本身就是最强线索**（`dest=image` 一次就能定性），我却先去读"像会发请求的代码"。
  正确顺序是**先让请求自报家门**（入口记 `sec-fetch-dest`／`referer`），再顺藤摸瓜。
- 已完整回退：诊断日志**按用户要求保留**（只对可疑路径打印，正常转发零噪音）；其余无代码残留。

**弯路 ②：把「生成链路里没有」说成了「前端没有」。**

- 用户据此反问「那它是从哪发出来的」——对的质问。准确表述应是「**链路代码里没有**；
  页面渲染出口可以在零链路代码参与的情况下发起请求」。

**弯路 ③：一度把 `GET` 的耗时差异（10.5s vs 211ms）当成线索。**

- 那是上游网络差异，与判据无关。**耗时不是证据。**
