## 〇 · 一句话

> 全仓对「静默吞」的机器守卫**只认识「空 catch」**；而现实里最常见的静默形态是**在 catch 里兜底返回一个默认值**（`return null / undefined / '' / [] / false / 0`）。
> 于是 `check:catch` 判绿（0 违规），但按它**自己的判据口径**（catch 内仅 return 空值、块内零留痕零抛出）重扫，实测 **41 处**。
> ⇒ **闸绿是假绿**；`TD-02-45` 的「改判非债」正是建立在这条假绿上（其 §② 明写「实测 = 0 处」）。
> 另在兜底链上抓到 2 处**功能级**静默：`canvasSource` 静默漏「只持 contentId 的文件型节点」、发送归一化静默丢参考图。

## 二 · 溯源（Phase 1：症状 vs 病根）

**症状**（用户/排查者能感知的）：
- 「导入弹窗里选了画布的图，但它自己不出现在画布来源里」（无声，无日志）；
- 「明明挂了 3 张参考图，模型只看到 2 张」（无声，且日志还说 3 张）；
- 「会话体积治理没生效 / 素材列表莫名空了」（无声，因为判据被兜底成了 0 / null）。

**病根（母体）**：本仓已建了「失败必须可见」的红线（`catchOk.ts` 头注释 · `spec/CONTEXT.md §三`）与一道闸，但**闸的判据面只覆盖「空 body」**。
一旦失败被**换算成默认值**（哪怕只是一行 `return null`），它就同时满足了「有语句」（闸不判）与「无留痕」（无人知）——**恰好落在两者之间**。
⇒ 这不是 41 个孤例，是**一条判据面缺口**在 41 个点上显形（母体 M-静默吞的**未收口面**）。

**为什么现在才看见**：上一轮审计用的是**同一个窄判据**去扫，于是「扫出 0 处」被当成「不存在」，并据以改判非债（TD-02-45）。
本轮的差别只有一个：**用「catch 体内仅 return 默认值」这一更宽（也更贴现实）的口径重扫**。

## 三 · 定海（Phase 2：不变式 / 唯一真相源）

1. **闸自身的判据**（`scripts/check-silent-catch.mjs:111-118 / 142-174`）是唯一有权定义「什么算静默」的地方 —— 它一旦窄，全仓的「失败可见性」就只窄到那里为止。
2. **同层正面对照（本仓已有正确范式，不是没有标准）**：
   - `librarySource.ts:57-60`：资源行缺 url → **抛错**（注释明写「后端契约违约，拒绝静默跳过」）；
   - `mediaRefRegistry.ts:52-55`：未注册来源 → **抛错**；`searchMediaRefs` 部分成功 → `failures` 进返回值；
   - `pagedList.ts:89-96`：响应缺 `items/total/totalPages` → **抛错**（「拒绝假装完整」）。
   ⇒ 同一层里，「数据违约不许静默」已经是**成文标准**；`canvasSource` 是它唯一的破口。
3. **兜底返回默认值本身不都是债**：谓词函数里 `catch → false`（"不是这种 JSON"）语义上是对的。
   所以本轮的债**不是「41 处都该改」**，而是「**41 处无法区分**」——缺的是**分类**（哪些是结构性豁免、哪些是真吞），分类的载体就是闸的判据面 + 原语/标记。

## 九 · 施工轮（2026-09-17 · TD-16-23：`canvasSource` 顺序倒置 + 恒假守卫）

> **触发**：§五 里 TD-16-23 已带完整偿还计划（①②③④），本节按计划逐条施工。

### 9.1 病根复核（比原描述更准：是**顺序**问题，不是"少了个判断"）

`canvasSource.list()` 原顺序 = ① `getNodeMedia(node)` → ② `if (!media.type) continue` → ③ 才 `resolveAssetDisplayUrl(...)`。
而**「只持 contentId 的文件型节点」**（`App.handleImportPick` contentId 优先建的节点）的 `assetType/url/assetUrl` **全空**
⇒ `getNodeMedia` 返回 `{type:'', url:''}` ⇒ **在解析入口之前就被 `continue` 掉，且零日志**。
即：本文件头写明的「用显示解析入口兜底文件型节点」这条契约，被**它自己的执行顺序**架空了。

### 9.2 施工（计划 ①②③）

| # | 改动 |
| --- | --- |
| ① | **把 `resolveAssetDisplayUrl` 提到类型判断之前**：先拿 url，再判类型（`if (!media.type && resolved.kind !== 'ok') continue`） |
| ② | **删恒假守卫** `if (!rawUrl)`：走到该处必是 `media.type` 非空或 `resolved.ok` 成立 —— 前者由 `nodeMedia` 不变量（type 非空 ⟺ url 非空）保证 url 非空，后者 url 即解析结果 ⇒ 那条守卫及其"必须留痕"日志**永不触发**（假护栏 + 死日志）。**留痕职责改由真判据承担**（下一条） |
| ③ | **留痕判据改真**：把「无媒体」拆成两种 —— 真·非媒体节点（文本/生成态，**静默**跳过＝正常状态）／**媒体节点但解析不出地址**（有 `contentId` 却解析不出，典型=引用的 resource 已删，画布上已 fail-loud 显示「素材已移除」）→ `logger.warn` 带 `nodeId/contentId/kind` |
| ③′ | **类型来源收口**：类型 = 节点自报/嗅探（`getNodeMedia`）优先，否则由**唯一判型入口** `assetType.classifyAssetUrlKind` 按解析出的 url 判（与 `nodeMedia` 同源，不新写扩展名嗅探）；**判不出不猜**（留痕 + 跳过） |

### 9.6 取舍留痕（为什么类型走 url 判型而不是查 resource 行）

更好的类型真源本是 **resource 行自己的 `type`**（素材库登记），但 `buildContentUrlResolver` 只回 url；要拿 type 就得再建一份 `contentId→resource` 索引 = **第二份真源**（M3）。`classifyAssetUrlKind` 是仓内**唯一判型入口**（`nodeMedia` 同款），且落盘 url 带扩展名（`contentHashName(hash, ext)`）⇒ 判得出。**若线上出现"判不出类型"的留痕**，说明素材库 url 无扩展名假设不成立 —— 那时再谈扩 `buildContentUrlResolver`，**不预先为假设付成本**。
