> 前 10 轮均从**复杂度**透镜审计（心法 §零 唯一目标）。用户要求最后一轮从**正确性**透镜做最终审计。

## 一、正确性核心故障：读失败被混标为"本地副本"，触发无条件写回 KV

### 1.1 信号混淆点（contentStore L505-521）

`contentGetKvWithFallback` 的 `from` 字段在**两种语义完全不同**的情形下都返回 `'local'`：

| 情形 | KV 实际状态 | 当前返回值 | 是否应触发迁移写回 |
| --- | --- | --- | --- |
| KV 键为空 / 未创建（value == null，L513 不 return） | 真空 | `{value, from:'local'}` | ✅ 应迁移（本地副本是权威来源） |
| KV 抛错（4xx / 5xx / 超时 / 网络，L515-517） | **未知** | `{value: 本地副本, from:'local'}` | ❌ **绝不应**（KV 状态未知，写回=clobber） |

→ `from:'local'` 同时表达"KV 真空"与"KV 读取失败"两个互斥语义。**这是正确性故障的根**。当前实现（L519-521）对两者一视同仁地回读本地副本并标 `'local'`，调用方无法区分。

### 1.2 故障链：从混淆到数据损坏（d3dPersistence L254-265 + L207-241）

1. `hydrateProject`（L254）读 `contentGetKvWithFallback` 得 `{value, from}`。
2. L257 `if (from === 'local' && value != null)` → 调 `writeProject(key, value)`（L259）。
3. `writeProject`（L229）走 **`contentSetKvWithFallback`（降级族，无 CAS、无条件写）**。

**当 KV 因读失败（而非真空）被标 `from:'local'` 时**：把本地 stale 副本**无条件写回 KV**，覆盖 KV 实际状态：
- 若另一窗口/设备已在 KV 写入更新 → **丢失更新（lost update）**，他人工作被静默覆盖；
- 若 KV 该键本应存在但本次读失败 → 用 stale 副本覆盖真值。

这**直接违反 `contentStore.ts` 自己 L531 的警告**："失败一律上抛……否则两窗口各写一份本地副本 → 静默分叉……数据陷阱"。降级族的读侧回退，恰好在 d3d 消费侧变成一次**写回**，踩中它自己警示的陷阱。

### 1.3 正确性规则（应然）

| KV 状态 | 正确行为 |
| --- | --- |
| KV 可用、键空 | 用本地副本 + **迁移写回**（合理，一次性） |
| KV 不可用（错误/超时） | 用本地副本 **但不迁移**（KV 恢复后才是真值，写回会 clobber） |
| KV 拒收（4xx） | **上抛错误**，不服务本地副本、不迁移 |

当前实现把三者全归为"from:'local' + 迁移"，违反第 2、3 行。

## 二、正确性故障的第二个子类：已删除数据复活

`contentStore.deleteKvWithFallback`（L346-352）的语义（注释 L342-344 明确）：KV 删除**成功即 return，不清本地降级副本**；只有 KV 失败才 `sRemove` 本地。即 director3d 这类 `keepFallback=true` 的键，**KV 删除成功后本地副本仍保留**。

随后若 `hydrateProject` 重新读取该键：
1. KV 已删除 → `kvGet` 返回 null/空 → `contentGetKvWithFallback` 标 `from:'local'`；
2. L257 触发 `writeProject` 写回本地副本 → **已删除的工程被复活**。

→ 这是明确的**数据正确性故障**：用户删除操作被后续 hydrate 静默撤销。根因同源（"读失败/空"混标 `from:'local'` + 降级键保留本地副本）。

## 三、正确性故障的第三个子类：cache 第二真相导致跨设备/跨窗口读到 stale

`loadFromKv`（L266）把 `readKvWithFallback` 的结果（可能为 local 降级副本）**无标记**写入 `cache`；`contentGet` 命中即返回（TD-02-20 已立）。叠加 cache 无失效机制（L246-249 仅修了"未就绪"子类）：一次 KV 瞬时失败缓存的 local 副本，**会话内永久返回 stale 值**。跨设备同步的数据在本地读侧不可见 → 同步正确性失效。

## 六、结论（最终审计）

- 前 10 轮从复杂度透镜得出 TD-02-15/19/20/24 等，正确但**低估了严重性**：它们不是"可降复杂度"的优化点，而是**数据正确性故障**——降级信号混淆使 stale 数据被写回 KV（lost update / 已删复活），且违反 contentStore 自身 L531 的警示。
- 根因仍是 **TD-02-24（缺诚实结果契约类型）**：`from` 字段一个字符串同时承载"真空"与"失败"两种互斥语义，下游无法正确分支。修复 `StorageOpResult` 判别联合，使"真空/失败/拒收"成为互斥分支，TD-02-15/19/20/23/25 一并收口。
- 偿还档位建议：TD-02-24/25 为**正确性最高优先**，应先于任何低息复杂度债偿还；TD-02-22/21/17 等复杂度债可排后。

DATAFLOW 无需刷新（本轮未改链路形态，仅从正确性透镜重判既有链路的故障严重度）。
