## 二、溯源（Phase 1：症状 vs 病根）

- 三条「问题」本质是**地基缺陷**，非功能需求：重复文件 = 落盘命名无内容去重（fileStore.ts:118 Date.now() 前缀）；文件不跟 project = resources 表无 project_id（resources.ts:275）；双注册表 = 前端随机 id 与后端路径 id 两套空间。撤掉任何单一业务诉求，这些代码结构仍是有害的——是病根，不是症状。
- 未把「兼容乱象」推到末端写 if-else：正确做法是源头收敛（命名统一 sha1、表加 project_id），非策略模式兜底。符合心法 Phase 1。

## 三、定海（Phase 2：不变式 / 唯一真相源）

三条不变量（地基，不可局部绕过），详 `docs/122` §1：
1. **SSOT 文件**：物理文件唯一 owner = `resource`；`asset` 是引用非副本。
2. **project 跟随**：`resource.projectId` 绑定当前项目（对齐 `projectStore` 既有 `canvas-state-v1-${projectId}` 隔离）。
3. **内容寻址去重**：落盘文件名 = `sha1(content)`，同字节 → 同 url（物理事实，非比对）。

> 铁律 2 类型诚实：新增 `asset.data = {resourceId, url}` 的 `resourceId` 必须在**引用解析边界**做运行时校验（查无则 fail-loud），不在消费端 `as` 谎称完整。

## 四、切割（Phase 3：深模块 / 真缝隙 / 收敛口）

- **源头收敛**（首选）：命名去重 sha1 落在落盘边界（fileStore），project 隔离落在 DB 契约边界（resources 表），均非末端补丁。
- **收敛口（choke-point）**：`resourceStore.addResources` 成为唯一「新建文件」通道；`saveResultToTasks`/`downloadRemoteToLocal` 先经它去重（docs/122 §3）。引用方只持 `resourceId`，禁止自写 writeFile。
- 无过度抽象 / 上帝类；`{resourceId,url}` 由真实需求（引用化 + project 隔离）驱动，非 YAGNI 假接缝（铁律 5 通过）。
