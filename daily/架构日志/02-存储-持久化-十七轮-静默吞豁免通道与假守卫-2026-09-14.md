## 二、溯源（Phase 1：症状 vs 病根）

- 症状（用户可见）：禁静默 catch 后出现**假守卫**（`if (isSafe(x)) { doRisky(x) }` 恒真/恒假）+ 真守卫写起来极贵。
- 病根不在业务 catch 点，在 **十三轮立下的豁免通道设计**：
  > 十三轮原文：**「不用白名单（白名单=假护栏）…而用显式标记 `// catch-ok: <理由>`：标记本身是代码（可查），理由另说。」**
  「理由另说」= 判定权留在写代码那一轮 + **理由从不被验证** → 闸只守"标记存在"，守不住"失败是否可见"。
- 该设计**只堵不放**：禁掉静默 catch，却未给"运行时可预期失败"一条更便宜的合法出口 → 成本上移到守卫侧 → 规避迁跃（假守卫）是理性反应，不是 AI 偷懒。

## 三、定海（Phase 2：不变式 / 唯一真相源）

- **失败可见性真值源**已在位且唯一：`core/degrade.ts`（`reportDegrade`）+ `core/logger.ts`（87 fan-in 唯一日志出口）。机制层无缺口。
- 缺口在**判定层**：`catch-ok` 是**自由文本**（无限面），不是登记表项（有限面）。本仓其余全部同类判据都走「单一真源登记表 + 双向校验」（`STORAGE_KEYS`/`EVENTS`/`NODE_TYPES`/`apiRegistry`/`NODE_HANDLE_CONTRACT`），**唯 `catch-ok` 游离**。
- 后果可量化（见 §五）：**标记量 ≠ 豁免量**（99 处标记里 ≥7 处贴给**非空** catch）→ 任何"按标记数做账本/基线"的方案口径从根上不可信。

## 四、切割（Phase 3：深模块 / 真缝隙 / 收敛口）

- 真缝隙 = **豁免通道**：应把"允许吞"从"逐处写自由文本"收敛为**极少数收口原语（代码符号）**——一次写好处处调，闸只守符号白名单。符号可被 `tsc`/引用数/测试三重约束，自由文本不可。
- 职责边界缺口：全仓无成文"守卫 vs catch"分工（守卫 = 契约违约、fail-fast；catch = 运行时意外、必须留痕）→ 压力必然外溢到守卫侧。
