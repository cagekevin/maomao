## 三、Step 3 定位 —— **不拆**

- **五问⑤（接口窄不窄）是关键否决项**：15 个 `onXxx` 是**共享同一份 engine 状态的闭包**（`shots` / `assets` / `loading` 标志 / `deps` 等），因此它们**天然拥有窄接口**（只需 engine 内部作用域）。
- 若把它们抽成独立模块/文件，则**必须把状态与依赖全量透出**（或改造为传参）→ **接口由窄变宽 → 反「深模块」**（宽接口 + 薄实现 = 泄漏）。这正是方法 Step 3 五问⑤ 要防的形态。
- **fan-in 证据**：11 个消费方**全部是「用整个 engine」**（`useScriptBoxEngine` / `ScriptBoxNode` / schema / workflows / promptResolver / contracts / config / filesApi / generate / generationContract / assistantTable），**无一对「某个 onXxx」** → 无「按回调拆分以复用」的真实需求。
- ⇒ **不拆**。拆分的唯一收益是「文件看起来小」，代价是接口变宽 —— **只美化、不降复杂度**。
