## 二、复杂度错位清单（本轮核心）

> 读法：`M# 错位现象` → **复杂度被搬去了哪儿** → 违反哪条心法 → **正确物理位置**。

### M1 「失败语义」没有分类，两类异质复杂度被压进同一个 `catch`
- 现象：`writeKvWithFallback` 的 catch 把任何 KV 失败都当「引擎不可用」→ 写本地副本 + 弹「存储暂不可用」。
- 复杂度被搬去哪：**把「协议结论」（4xx，如 CAS 409 版本冲突）伪装成「可用性故障」**。信息在 L2 被抹掉 → 需要该信息的 L3（画布快照 fail-closed）无法用 L2 表达自己的语义 → 只能绕过去。
- 违反：§五 静默自检「防腐」（万能的 catch 是耻辱）+ 铁律 2（错误必须在根因发生地炸开）。
- 正确位置：**错误分类是 L2 的一等职责**（一处实现，两族共用）。
- ⚠️ 这条纠正了一个流行误判：TD-02-1 的根因**不是「L3 不守规矩」**，而是「L2 的接口丢失了一个语义维度」。

### M2 入口接口面缺「协议原语」→ 抽象泄漏，消费者下钻
- 现象：KV 后端的协议面是 `get / set / delete / version / 条件写` 五件事；`contentStore` 只暴露前三件。
- 复杂度被搬去哪：**抽象不完整 → 泄漏**。需要版本语义的唯一消费者（画布快照）只好 import transport。
- 违反：§一.2 空间收敛法则（复杂度应压在唯一入口，而非复制到消费端）。
- 正确位置：L2 暴露与后端能力对齐的**最小协议面**（版本读 / CAS 写），**不含业务编排**（基线、单飞、冲突提示仍留 L3）。

### M3 同一份数据（画布快照）在同一个模块里走了三套口径
- 现象：`projectStore` 对 `canvas-state-v1-*` —— 写 `kvSet`、读 `contentGetAsync`、删 `contentDeleteAsync`。
- 复杂度被搬去哪：一个数据的「策略身份」分裂成三个答案 → 认知单元数 3（本应 1）。
- 违反：CLAUDE §5.4·9（同一语义只准一条实现路径）。
- 正确位置：同键三操作同族同口径（M1+M2 的合成症状，随其一并消除）。

### M4 `contentStore.cache` 把「未加载」与「不存在」写成同一个值，且不可失效
- 现象：`loadFromLocal` 在底层读不到时 `cache.set(key, undefined)`；此后 `contentGet` 命中 `cache.has` 恒返回 `undefined`（粘性）。
- 复杂度被搬去哪：**信息丢失 → 复杂度守恒律兑现**：被抹掉的「就绪度」信息，在别处重新出现为**一条隐式时序契约**（「任何模块级读都必须发生在 `initStorage()` 完成之后」），它没有类型、没有守卫、没有名字，只活在 `main.tsx` 第 12 行与 ESM 求值顺序里。
- 违反：§二 Phase 2（契约必须有物理位置）+ 铁律 2（诚实：`undefined` 声称「不存在」，实际可能是「还没读到」）。
- 正确位置：**就绪度是一等状态**（L1 暴露 `isStorageReady()`；L2 未就绪时不写入假真相）；**eager 读从模块作用域移出**（让启动顺序不再承载正确性）。
- 注：症状是否在扩展运行态复现**不影响本债成立**——「同一格承载两种世界状态 + 契约无物理位置」本身就是附随复杂度。

### M5 画布快照 schema（「什么字段会被持久化」）没有单一真相源 ← 本轮新发现，跨区根因
- 现象：`scripts/check-node-data.mjs` 头注释自述 node.data 形状由 **五处各自表述**（① palette `data:{}` ② 各节点本地 interface ③ `NODE_OUTPUTS`/genericOutput ④ `nodeDefaults` ⑤ `projectStore.sanitizeNodes`）；另有 `NODE_KEEP`/`EDGE_KEEP` 两份**保留白名单**写死在 `projectStore`；`CANVAS_SCHEMA_VERSION` 又在 `contracts`。
- 复杂度被搬去哪：**同一条知识（持久化契约）散落 ≥6 处、互不对账** → 每次加字段都要「记得改所有地方」，漏一处就是静默丢数据。**这正是区域 04 的 TD-04-15/16/17/19 反复围绕 `width/height/style/selected/label` 打架的同一根因**（写侧加了、白名单没加 → 刷新丢字段；或白名单加了、写回没走入口 → 静态闸盲区）。
- 违反：§一.2 空间收敛法则 + 铁律 5 注（契约/类型模型/SSOT 属地基，该一次到位）。
- 正确位置：**一个快照 schema 模块 = 唯一真源**；白名单、默认值、节点 interface、`NODE_OUTPUTS`、对账脚本全部**派生**它（而非各自表述）。
- 归属：根因属「持久化语义（哪些字段进快照）」→ **归区域 02**，`@见区域 04`。

### M6「假护栏」与「死抽象」
- 现象 A：`d3dPersistence.getChannel()` 守卫写反（初值 `null` 比 `!== undefined`）→ 通道恒不建立；更糟的是**用类型（`null | undefined` 联合 + 恒真比较）为这个 bug 背书**，注释还要求「保持行为不变」。
  - 判读：**护栏存在但不生效，比没有更糟**（给人「已防护」的错觉）。违反铁律 2 + Phase 4 风控（假护栏）。
- 现象 B：`storageQuota.analyzeAgentConversationPressure()` 恒返回 `null`（已弃用却保留 API）；`resourceStore.loadResources()` 定义完整但 src 零调用。
  - 判读：YAGNI 反向验收——「明天删掉它，有真实调用方受影响吗？」没有 → 是复杂度，不是架构。
- 正确位置：假护栏要么修（改守卫 + 补测），要么删（删掉整段失效机制）；死抽象直接删。

### M7 同一条知识有两处写点
- `backupStore.getCurrentProjectId()`（从存储重推导当前项目）vs `projectStore.getCurrentProject()`（内存真相）；
- `orphanGc.collectReferencedRelPaths()` vs `runReferenceGc()`（「全库被引用文件集合」两份同构实现，注释自承同口径）；
- `nodePrefs.useNodePrefs.set`：每个节点实例持本地副本、写时覆盖共享整表 → 同类型两节点 = 同一条知识的两个写点（末写胜）。
- 正确位置：一处实现，其余委托；写共享表一律「以最新为准合并」。

### M8 红线只有注释、没有机器
- 现象：「所有存储读写必须走 contentStore」写在 CLAUDE.md 与文件头，但 `check:arch` 只有 node/edge 与工具层规则，**没有存储层规则**。
- 判读：**契约无守卫 = 无契约**。TD-02-1 能长期存活就是制度缺口的实证。
- 正确位置：把红线降为 AST 规则（与既有 5 条同族），旁路即红。

## 三、目标结构（把复杂度放回正确位置）

```
L1 物理层
  storageAdapter       local/native 物理读写 + 【就绪度一等状态 isStorageReady()】
  localToolApi.kv*     KV 协议：get / set / delete / version

L2 存储域 = contentStore（唯一入口：窄接口 + 厚实现）
  ├ 尽力而为族（配置类）：contentSet / Get / Delete (+Async)   —— 失败 → 降级本地 + 提示，不阻断
  ├ 严格族  （用户主数据）：contentKvGetVersion / contentKvSetCas —— 失败 → fail-closed 上抛，绝不写副本
  ├ 双通道原语（d3d 类）：contentSet/GetKvWithFallback（per-key fallback/timeout 驱动）
  └ 共享内核：resolveBackend · cache · notify · createDebouncedPersist
              · 【失败分类唯一实现 isEngineUnavailable】（4xx=请求被拒 / 其余=引擎不可用）

L3 领域仓储（store）—— 只写业务编排，✗ 永不 import L1
  projectStore    : CAS 基线 + 单飞队列 + 冲突提示 + sanitize（消费严格族）
  d3dPersistence  : 双通道 + 一次性迁移（消费双通道原语）
  backupStore     : 备份清单 + 导入导出（消费 contentSet/Get）
  …（其余 store 一律消费尽力而为族）
```

**真分叉在哪**：存储只有一条「后端分叉」（local/native/kv），那不是缝隙；**真正的缝隙是「失败语义」**——配置类可降级、主数据必须 fail-closed。此前没把这条缝画出来，才逼出了 M1/M2/M3 的泄漏。**收敛 ≠ 强行大一统**：两族共存是「真分叉」，把两族合成一个带开关的万能入口才是过度设计。

**附**：备份导入（整页 reload，全量重建）与云同步下载（定向 `rehydrateStoresAfterCloudPull`，只动配置域）**语义不同、刻意分叉，非债**——前者恢复的是含 assetStore/taskStore/会话 KV 在内的全量，reload 是正确选择；强行「统一」会造出部分 rehydrate 不完整的新洞。

**增债理由 + 曾评估但被否决的替代方案**（§七.3 要求，仅 增债 项需列）

- **TD-02-2（增债·历史）**
  - *增债理由（客观约束，非偷懒）*：Chrome MV3 `chrome.storage` **无同步 API**，而本仓存储接口是**同步**的 → 只能靠「异步预填内存 cache」模拟同步；预填与模块级 eager 读之间存在**未声明**的先后依赖。dev（非扩展）走 `localStorage` 同步径天然掩盖该依赖 → 长期不可见。属运行时物理约束。
  - *曾评估但被否决的替代*：① 「`sGet` 加同步 fallback 直读 `chrome.storage`」→ **否决**：MV3 无同步 API，物理不可行。② 「`initStorage` 回调里 `contentClearCache()` 清假真相」→ **否决**：会让已渲染组件的 `useSyncExternalStore` 快照瞬间变 `undefined`（抖动/白屏），是更危险的末端补丁。故取「未就绪不写缓存 + eager 读惰性化」的温和方案。
