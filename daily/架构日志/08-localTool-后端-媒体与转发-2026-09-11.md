## 二、溯源（Phase 1：症状 vs 病根）

- **症状**：MIME↔ext 映射在 localTool 内散落 **6 处**（ext→mime：index.ts handleStaticFile / handleDepthResource / FRONTEND_MIME + files.ts handleRead / handleThumbnail；mime→ext：files.ts MIME_TO_EXT / resources.ts MIME_TO_EXT / base64Externalize.extFromMime），且**已出现漂移**：files 表无点前缀（`'jpg'`）、resources 表带点（`'.png'`）、base64 表默认 `.${m}` 兜底——正是 CLAUDE §5.4.9「媒体判型曾 5 处各写一份漂出不一致」的后端镜像。**病根** = 媒体判型缺后端唯一真值源（前端已有 mediaType.ts，localTool 是独立包无法直接复用）。
- **退役残留（重复首轮 TD-08-4 的模式）**：`files.ts handleRead` 仍支持 `x-proxy-url/x-proxy-method/x-proxy-headers/x-proxy-cookie` 整套代理读——CLAUDE §5.7 明令该机制已随 2026-09-03 收口退役、前端 0 调用。**退役未闭环**。
- **同语义小重复**：`isRecord` ×3（protocol/shared 唯一导出，但 body.ts / connection.ts 各内联一份）；`ai-relay/generate.ts` 的 chat() 与 chatWithTools() 前半段（body 构造 + 错误透传）逐字重复。

## 三、定海（Phase 2：不变式 / 唯一真相源）

- **SSOT 唯一**：转发目标 base 唯一决策点 = official.readOfficialBase（passthrough 复用，注释明示「转发给谁只有一个决策点」）；relayHeaders（maskToken/logTs/HOP_BY_HOP）已收口；fetchTimeout 已收口（fetch-timeout-seam）。✓
- **媒体判型（本轮修复）**：新增 `utils/mime.ts` 为后端唯一真值源（EXT_TO_MIME + extToMime + mimeToExt），4 处消费方全部委托；域专用表（handleDepthResource 的 wasm/onnx、FRONTEND_MIME 的 woff2/ico）保留不并入（真缝隙，变化速率不同）。
- **错误透传**：relayHeaders / passthrough / lovart_client 均「上游文案原样透传不翻译」；saveRemoteUrl 下载失败回退原 URL 不抛 500。✓
- **超时**：passthrough 30s、relayGenerate 10min、pollTask maxDuration 全有总超时。✓

## 四、切割（Phase 3：深模块 / 真缝隙 / 收敛口）

- **收口（本轮）**：
  - `utils/mime.ts`：ext↔MIME 唯一实现（单规则原则 §5.4.9）。files.ts / resources.ts / base64Externalize.ts / index.ts 全部委托。
  - `isRecord`：body.ts / connection.ts 改为 import protocol/shared 的唯一实现。
  - `ai-relay/generate.ts`：chat / chatWithTools 抽公共 `postChatRaw`（body 构造 + 错误透传一份，两公开 API 只差响应解析）。
  - `files.ts`：删除 x-proxy-* 代理读死分支（handleRead 直连 + handleReadProxy 整段删除，留痕注释指向 CLAUDE §5.7）。
- **真缝隙（不合并，记录理由）**：
  - `uploadLovartFile` 内联 code≠0 检查 vs `parseEnvelope`：错误分类不同（UPLOAD_FAILED vs UPSTREAM），合并会丢失分类语义。
  - `handleDepthResource` / `FRONTEND_MIME` 表：域专用（推理运行时 / 前端资源），变化速率与通用媒体不同。
  - `routes/providers.ts readEnvKey`：.env 文件兜底热加载（运行期新增凭证不重启），与 process.env 唯一读取 resolveProviderApiKey 是不同行为。
