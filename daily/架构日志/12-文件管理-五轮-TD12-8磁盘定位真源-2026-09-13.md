## 二、Step 2 · 归因（母体）

三症状**不是三个 bug**，共享**一条规则**：

> **母体 M-12-2**：context/content 解耦后，「磁盘路径真源」未随之从**可变的 `folder`/`name`** 迁到**不可变的 `url`**。

**判据**：一处修复（磁盘定位统一由 url 派生）能同时消灭 3 症状 → **母体成立**（≥3 症状）。
真源其实一直在 `url` → 修复是**真源替换**（1 处原语），非逐个打补丁。

## 三、Step 3 · 定位（五问）

| 问 | 答 |
| --- | --- |
| ① 真源在哪 | 磁盘 rel = `url` 派生；`url` rescan 写入后**永不改**（`folder`/`name` 是 UI 层，可变） |
| ② 变化速率 | `url`/`contentId` 静止；`folder`/`name` 频繁变 → **不可用于磁盘定位** |
| ③ 几种实现 | 磁盘定位本应 1 处（`resolveUploadTarget` 落点真源）；现存 **2 份**（+ `resources.ts:229` 手拼）→ 收口 |
| ④ 改动半径 | 后端 2 处 + 前端 1 处原语 + payload 1 字段；**≤5 文件**（小改动大收益） |
| ⑤ 接口窄不窄 | `relativePathFromUrl` 已是纯函数 → 直接复用作收口点 |

**动作：收敛（收口探测原语）+ 正确性（无 row 不假成功）**。

> ⚠️ **探测重复 vs 判据重复（TD-04-21 教训）**：`url→rel` 是**探测**（怎么读数据）→ **可收口**为单一原语；
> 「移动是否放行」是**判据**（要不要做动作）→ **保留**不变。本轮只收口探测，未动判据。

## 四、Step 4 · 定契（正确性 / 错误透传）

- **成功信号诚实**：`applyResourceContextMove` 无 row 时**不再回 `{url:null, ok:true}`** → 抛 `HttpStatusError(404)`。
- **错误在根因处炸开**：`handleMove`（API 边界）catch → `sendError(res, message, status)` → 前端 `useResourceMoveToFolder` catch → toast。
- **失败可见性读者正确**：用户 → toast「资源未同步，请刷新后重试」。
- **权属（Step 5）**：此点**改用户可见行为**（成功→失败）→ **交用户拍板**；用户裁定**「返回失败 + 明确提示」**。

## 八、方法论沉淀

1. **一处真源替换 > 三处补丁**：TD-12-8 三症状的根不是"三处各写错"，而是**真源没跟着换**。改 5 处、清 3 症状。
2. **收口前先分探测/判据**：`url→rel` 是探测（收口）；「是否放行移动」是判据（保留）。只收探测，未越界。
3. **反向探针的价值**：收紧共享原语时既有测试当场红 → **先假定自己越界** → 取证两消费方确认「旧行为只是把错误推迟」→ 才改测试（并注明是 characterization test）。
4. **先红要精确命中**：probe1 只红 2 条（rescan 保留）、probe2 只红 3 条（url 派生）——**精确命中所修点**，非整片红。
