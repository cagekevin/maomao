## 二 · Step 1 证伪（三问 + 描述精化）

1. **① 硬证据（比债描述更精确）**：债文写"前端 120s 小于后端默认 180s" —— 取证后**真正的病灶不是"两个数字不同"，而是「预算根本没传过去」**：
   - `generateEngine.ts:260` `relayChatStream` **接受** `timeoutMs`；
   - `routes/generate.ts:48-58` chat 分支**只传** providerId/model/messages/tools/baseUrl —— **不读 `body.timeoutMs`、也不传**；
   - `relayProxy.ts:319` 那个 `timeoutMs` **只喂给本层 `httpRequest`**（掐自己），**body 里没有它**。
   ⇒ 前端 120s 断自己的连接，后端对上游仍按**默认 180s** 跑 ⇒ **上游白跑** ✅ 真债。
2. **② 替代方案**：生成任务（image/video）**已有** `frontTaskId` + attach + 终态 + cancel 的完整链路 —— 但那是**另一套机制**（异步任务），chat 是流式，不能照搬；**可复用的是"预算贯通"这一条**。✅
3. **③ 致命拷问**：用户不"多做"事；变的是**前端放弃的时刻 = 后端掐上游的时刻**（不再白跑）。→ 正确性修复。
4. **⚠️ 描述精化（A7）**：债文"口径错位：前端 120s 小于后端默认 180s"**不是**准确的病灶描述（真正的病灶是**传递链断了一环**）；"chat 又无句柄无 unknown 无恢复"部分**成立但属加能力**（见 §六）。

## 三 · Step 3 定位

- **判据归属**：「本次请求的预算」的真相在**发起方（前端）** ⇒ 预算由前端定义并**写进请求体**；后端只**转发**（三铁律②）。
  ⚠️ 这**不是**"让后端也记一个 120s" —— 那会造出**第二份真相**（正是本债的成因）。
- **改动半径**：前端 2 文件（`config` / `relayProxy`）+ 1（`agentRuntime` 引用收口）；后端 2 文件（`routes/generate` 转发 / `generateEngine` 加注）。

## 四 · Step 4 定契

```ts
// config.ts —— 两段预算的唯一真源
export const CHAT_TIMEOUT = 120000;                    // 「等上游响应」
export const CHAT_TOTAL_TIMEOUT = CHAT_TIMEOUT + 60000; // 「等响应 + 响应体读取/解析/落盘」= 总闸
export const SCRIPT_TEXT_TIMEOUT = CHAT_TOTAL_TIMEOUT;  // 同源（不再各写 +60000）

// 前端：生产者给全 —— 把本次预算写进请求体
relayChat:       body.timeoutMs = opts.timeoutMs ?? CHAT_TIMEOUT
relayChatStream: body.timeoutMs = CHAT_TOTAL_TIMEOUT

// 后端：消费者只转发 —— 读 body.timeoutMs（非法/缺失 → undefined，**不自己编数**）→ 交给上游
```

- 它**不改变用户能做的事**（断连仍不可恢复）⇒ 不是业务性；
