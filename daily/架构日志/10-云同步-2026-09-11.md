## 二、溯源（Phase 1：症状 vs 病根）

- **结构能否承载业务**：cloudSync 定位为「编排层」正确——它不持有真相，真相在各域 store / contentStore。但历史上被写成「尽力而为 ad-hoc 同步」：读/写失败=可忽略，埋下静默吞错根因。
- **末端补丁 vs 源头收敛**：原 `restoreLocal` 4 处 `catch{ignore}` + `collectLocalData` 2 处静默跳过，是「在末端把错误压掉」而非「源头保证数据齐」——典型的末端补丁思维。projectStore 的「根因修复」注释（`projectStore.ts:177-202,244-249`）已证明同类 `saveProjects` 静默失败是反复踩的坑，cloudSync 原样重演。
- **projects 第二真相源**：`projects` 既有跨端真通道（`projectStore` → localTool `/api/projects` backend + KV 画布快照），又被云同步经 localStorage 直读、再经 `saveProjects` 写回 backend——同一实体造了两套真相。这是「特例用通用 LS 循环兜底」的收敛错位，非业务必需。

## 三、定海（Phase 2：不变式 / 唯一真相源）

- **SSOT**：修复前 `projects` 双真相（projectStore 内存态 + cloudSync LS 快照 + backend 写回三方博弈）。[F-云B] 后 `projects` 从源头移出云同步（`SYNC_EXCLUDE`），跨端真通道只剩 projectStore 一条 → SSOT 唯一。
- **边界 Guard**：`contracts.ts` 已把 `projects` 登记 `store:'projectStore.js'` 作为权威读写方，但 cloudSync 原绕过它裸写 LS/backend。修复后云同步对「有独立 backend 真相源的领域实体」一律不碰，收敛点回到领域 store 边界。
- **错误洁净**：原 `ok:true` 掩盖部分失败（用户误信"恢复成功"但数据没回来）。[F-云A] 后 `restoreLocal` 返回 `{written, failed}`，`downloadConfig` 的 `ok` 必须 = "全部目标写成功"，任一失败即 `ok:false` 带 `failed` 明细。

## 四、切割（Phase 3：深模块 / 真缝隙 / 收敛口）

- **第二份真相**：`projects` 的 `getCurrentProjectId` + `saveProjects(ls.projects)` 死路径 = 在 sync 层长出的第二份真相。已删除（[F-云B]）。
- **真缝隙**：云同步应区分「纯存储键（无内存态，如 app_settings，sync 层直碰 contentStore 可辩护，backupStore 同模式）」与「领域实体（有独立 store + backend，如 projects/providers/accounts）」。前者可通用循环，后者须走领域出口。原代码把 projects 当纯存储键处理，是缝隙填错。
- **上帝类/跨层**：`CloudSyncEngine` 承担 URL 校验 + 重入锁 + fetch + 解析 + 错误归一，属合理单职责引擎；`isSyncing` 模块级可变锁为已知反模式（autoSync 注释已论证现有门控够用，持平不修）。
