## 二、溯源（Phase 1：症状 vs 病根）

- 画布编排地基**结构总体健康**：注册表（NodePalette）、结构默认（nodeDefaults）、参数记忆（nodePrefs）、编组（groupNodes）、派生（deriveNodes）、历史（historyStack）各自职责单一且收口清楚，「节点怎么上画布」的骨架没有长出上帝类。
- **病根 1（端口契约漂移）**：节点端口（target/source handle）的**真源**是各节点文件的 `NodeShell targetHandleId/sourceHandleId` prop（`check-node-handles.mjs` 已强制「固定一进一出必须走声明式」）。但 `App.tsx` 又手写了两张 `TARGET_/SOURCE_HANDLE_BY_NODE_TYPE` 表，`lazyNode.tsx` 又有一张 `LAZY_NODE_HANDLE_CONTRACT` 表——**同一语义三处维护**。这不是「为兼容乱象打补丁」，而是「单源信息被复制了两份却没同步」的典型第二真相源。
- **病根 2（第二新建入口）**：节点创建的主入口是 `App.addNode`（注入记忆 + 结构默认 + 历史记录 + 建边）。但 `AssetNode`/`ImageGenerate`（相机工作室）/`useScriptBoxEngine`（剧本盒子）**各自内联建节点**，仅补 `injectNodePrefs`，绕过 `addNode` 的结构默认补齐与 history.record。这是「同语义多条实现路径」的隐患（详见切割段）。

- **影响诚实评估（不夸大）**：漂移的表项对应的目标节点**当前都只有单个 target/source 口**（gridSplit/gridMerge/imageBox/videoProcess 均为单口），React Flow 在 `targetHandle=null/undefined` 时会回退取「第一个 target 口」，故**当前未见建边失败**。真正的风险是**潜伏性**：一旦某节点改为多 target 口（如 GridMerge 未来加第二个入口），漏登记的表就会让存量边补不正 handle → 静默不渲染线 / code-008。故利息率定 **中**（非高），属「已漂移的第二真相源 + 无静态闸」的维护债，非 live bug。
- **边界 Guard**：`check-node-handles.mjs` 拦「手写 CustomHandle 失控」，`check-node-types.mjs` 拦「裸 useNodePrefs 命名空间」——但**无任何脚本守护上述三张 handle 表与节点真源的一致性**（表漏登记不会变红）。

## 四、切割（Phase 3：深模块 / 真缝隙 / 收敛口）

- **收敛口缺失（端口契约）**：handle 契约的正解应是**单一派生**——由节点文件声明（或一张集中清单）派生，供 App 补边、lazyNode 占位骨架共同消费。现状是「信息源（节点 prop）+ 两张手工复制表」，属于「同一语义 ≥2 可写点且已漂移一次」——按 CLAUDE §5.4·9「单一规则原则」**必须收口**。
  - 候选收口位：`nodeDefaults.ts`（已是「节点结构契约」归位处）或 `contracts.ts`（已是跨模块契约登记表）——三处 `import` 同一份 `NODE_HANDLE_CONTRACT`，`check:arch` 或新静态闸对账「节点文件声明 ⊆ 契约表」。
- **第二新建入口（deriveNodes 收口已覆盖一部分）**：`deriveNodes.spawnAndCommit` 已把「建子节点+连线+record」三连收口（9 处调用方）。但 `App.addNode` 与三处内联建节点（AssetNode/ImageGenerate/useScriptBoxEngine）仍是**四条独立建节点路径**：`addNode` 走 `applyNodeTypeDefaults` + `history.record`，另三处**不走**。语义缝隙真实存在（三处均为「节点内自建子节点」而非「画布空白建节点」），但「结构默认补齐 + 进 undo 栈」两件事应对所有路径成立，属可收口项。
- 无上帝类 / 无过度抽象：`NodePalette` 单文件 298 行（数据表性质，合理）；`lod.tsx` 已把原三碎片合并为深模块（正向）。
