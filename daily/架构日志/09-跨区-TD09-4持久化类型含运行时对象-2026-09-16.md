## 二、Step 0 普查 —— 真形态：**回调函数住在被持久化的 `node.data` 里**

债描述指向 `store/types`，但**真正的病灶在别处**。普查「谁把运行时对象写进了持久化容器」：

| 能力 | 现有实现（文件:行） | 份数 | 问题 |
| --- | --- | --- | --- |
| 快照落盘白名单 | `canvasSnapshotSchema.ts:41` `NODE_KEEP` 含 **`data` 整包透传**（注释明写「不做字段级过滤」） | 1 | 落盘容器 = 整个 `data` |
| 落盘写入 | `projectStore.ts:421` `sanitizeSnapshotNodes(nodes)` → `contentStore` → `JSON.stringify` | 1 | 只裁 node 级字段，**不裁 `data` 内部** |
| **运行时回调注入** | `useScriptBoxEngine.ts:148` `patchNodeDataById(setNodes, nodeId, callbacks)` —— 把**14 个函数**写进 `node.data.onXxx` | **1** | **函数进了持久化容器** |
| 回调类型契约 | `ScriptBoxNodeData extends Partial<ScriptBoxTop>, ScriptBoxCallbacks`（`ScriptBoxNode.tsx:31`）→ **持久化类型物理声明了 14 个函数字段** | 1 | **正是债描述的「类型层诚实性」缺口** |

**关键证据**：`ScriptBoxCallbacks`（`scriptBoxSchema.ts:92-120`）14 个字段全部是 `() => void` / `(id) => void` 形态 —— 而 `ScriptBoxNodeData` 是该节点 `data` 的类型，`data` 又是 `NODE_KEEP` 整包落盘的对象。**类型层宣称「data 里可以有函数」= 宣称了一件序列化会静默吃掉的事。**

> 这就是债描述「持久化类型物理禁含运行时对象」的**真形态**：不是 `store/types` 缺守卫，而是**回调与持久化数据物理同居**。

## 三、Step 1 证伪 —— 真债成立（有实害），但危害形态与描述不同

**三问**：

### ① 根因证据：有可复现的失败（只读实测）

```text
JSON.stringify({step:1, onGenerateScript:()=>{}, onConnectShot:()=>{}})  → {"step":1}          // 函数静默消失
JSON.stringify({step:1, ctl:new AbortController()})                       → {"step":1,"ctl":{}} // 静默变空对象
JSON.stringify({m:new Map([['a',1]])})                                    → {"m":{}}            // 静默丢数据
```

⇒ **实害**：任何「写进 `data` 的运行时对象」在落盘时**静默丢失/腐蚀**，刷新后无声无息。剧本盒的回调**当前能工作**，仅因它们在 `useEffect` 挂载时被**重新注入**（`useScriptBoxEngine.ts:148`）—— 即：**每次落盘都在丢弃、每次挂载都在补**。这是「靠重注入掩盖序列化丢数据」的兜底形态（心法 A6：兜底数量 = 地基体温计）。

### ② 替代方案：现状**没有**守卫，且 `Record<string,unknown>` 边界抹掉类型

- 编译期：`node.data` 在持久化边界（`saveCanvasState`）是 `Record<string, unknown>[]` —— **类型在边界已被擦除**，故债提议的「在 store/types 加判别联合」**够不着真实边界**（且 store/types 不存在）。
- TS 无法对 `Record<string, unknown>` 做「深层条件映射排除函数」而不引入巨型泛型（过度抽象）。
  ⇒ **债提议的修法（编译期守卫）不可行**；正解在**结构层**。

### ③ 决策者的选择

- 把回调移出 `data` = **用户能做的事不变**（复制/分享节点后回调仍工作的语义要保留）→ 属**架构师可直接定**（Step 5）。
- 但**改动半径** ≥6 文件（`ScriptBoxNode` / `scriptbox/*` 5 个消费方 + `useScriptBoxEngine` + schema），需按 Step 3/6 设计，不是本轮一句话可清。

### 致命一问

> **「我加了这个，用户/系统能多做哪一件原来做不到的事？」**
> **答**：**用户不多做，但系统从「静默丢数据靠重注入掩盖」变为「落盘容器与运行时对象物理分离」** —— 消除「任何未来往 data 写的函数/对象都会静默消失」这一**地基级隐患**（复活 M5 失败不可见）。**真债成立。**

## 四、Step 3 定位 —— 正解是「把回调搬出持久化容器」，而非「加编译期守卫」

**六问定位置**：

1. **职责归属**：回调（`onGenerateScript`…）是**引擎与 UI 的会话契约**，不是**画布数据**。会话契约不该住进随快照持久化的 `data`。
2. **真源在哪**：回调的产生方 = `useScriptBoxEngine`（宿主 hook）；消费方 = `scriptbox/*` UI。**双方都不在 `data`** —— `data` 只是「传话的信箱」。
3. **变化速率**：回调每挂载重建（快）；`data` 内容随用户编辑（慢）。**快慢同居 = 假缝隙**（正是问题源）。
4. **有几种实现**：回调注入 **1 份**（`useScriptBoxEngine.ts:148`）→ 收口成本低。
5. **改动半径**：消费方 6 文件（均只读 `d.onXxx` / `callbacks.onXxx`）→ 若改为经 React props/context 传递，消费方签名**基本不变**（仍是 `callbacks` 对象）。
6. **接口窄不窄**：`ScriptBoxCallbacks`（14 方法）= 窄接口 + 厚实现 → **保留该接口**，只换**传递通道**（data → props/context）。

**正解形态（一屏内）**：
> **`ScriptBoxCallbacks` 仍由 `useScriptBoxEngine` 产生，但经 React 通道（`ScriptBoxNode` 内 `callbacks={engine}` 直接传给 `ScriptBoxFullscreen`/三步组件）下发，不再 `patchNodeDataById` 写进 `node.data`。**
> `ScriptBoxNodeData extends ScriptBoxCallbacks` 一并删除 → **持久化类型不再声明任何函数**。

**为什么这不是权宜之计**：它同时消灭 ①类型不诚实 ②落盘静默丢函数 ③「靠挂载重注入掩盖」的兜底 ④复制节点后回调的错觉来源（复制时回调本就被 drop，重注入才是真保障）。

> ⚠️ **待验证**：`ScriptBoxNode` 的 `callbacks: { ...d, onDisconnectUpstream }`（`:183`）说明 `onDisconnectUpstream` 是节点本地追加项 —— 搬迁时需确认这两条通道（引擎注入 9 个 + 节点补 1 个）合并后语义不变。

### ⚠️ 途中发现的真 bug（签名收口意外暴露 · 已修）

施工中把 `ScriptBoxCallbacks` 与引擎签名对照，暴露**一处潜在静默 bug**：
- `Shot.id` 真源是 `string | number`（`scriptBoxPrompts.ts:442`），且 `createNewShot` 产出 **`Number`**（`:334`）；
- 引擎按 `s.id === shotId` **严格相等**匹配（`scriptBoxEngine.ts:875`）；
- 原契约写 `string | number`，引擎写 `string` —— **契约与产出方不一致**。

**弯路（必须记）**：我第一版为"对齐"把 UI 侧调用点全部 `String(s.id ?? '')` 归一 —— **这是错的**：
number id 经 `String()` 后与 `s.id`（number）严格比较**永不相等** → **生成/连线下游静默无反应**。
- 为什么错：**把"类型对齐"当成了"语义对齐"**，用 `String()` 掩盖了「id 身份必须同型透传」这条契约。
- 回退：`git checkout` 完整回退两文件（`StepPrompt.tsx`/`StepShots.tsx`，探针式确认零残留）。
- 正解：**放宽引擎入参为 `string | number`**（保严格相等匹配），并在契约注释写明「不得 `String()` 归一，否则 number id 匹配不到」。
