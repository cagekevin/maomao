## 二、行为变更（诚实登记）

1. **`useNodePrefs` 不再把 defaults 落盘**（TD-02-5 附带）：存储只记「用户真正改过的字段」，defaults 由读取/新建注入时补。好处：**改代码默认值对新节点立即生效**（原会被历史固化的默认值掩盖 —— 这是一处潜在功能 bug，不只是写法问题）。
2. **导出/备份的「当前项目」以内存真相为准**（TD-02-4）：切项目后立即导出，不再出现"刚切到的项目画布没进备份"。
3. **跨窗口覆盖提示真的会出现**（TD-02-3）：此前功能静默失效，修复后同 key 被其他窗口更晚保存时，保存前会有一次红色 toast + 日志（仅提示一次，防刷屏；同 tab 多实例仍按 `tabId` 忽略，不会自扰）。
4. **KV 删除后版本归零**（TD-02-10）：删除后重建的 CAS 基线重置（这是修复目标，非副作用）。

三条均已在对应测试中固化（不是"跑一下看起来没事"）。

## 八、追加复查（用户问答触发，2026-09-12）：「素材改名/移动」前后端分工与残留缺口

用户问：「存储持久化目前是完美的么？比如前端文件改名、移动位置这些，主要是后端做是吗，前端只负责发信号？」——按此逐链路只读复查，结论如下（**先纠正一处"看似债但不是"**，再报 2 条真缺口）。

### 8.1 事实核对（分工确实如此，且比"只发信号"多一层）

- **物理文件操作 100% 在后端**（浏览器无 fs）：改名 `POST /api/resources/rename`、移动 `POST /api/files/move`，两侧最终落到**同一个** `applyResourceIdentityChange()`（`localTool/src/routes/resources.ts`，注释明确"二者本质同一件事、必须收口成一个"，并记录此前两份实现抄漏了三步的教训）。
- 该入口一次调用做完五件事：① 路径安全解析（拒 `..` 逃逸 → 400）；② 目标已存在 → **409**（禁静默覆盖；注释解释了为何覆盖比 404 更隐蔽：引用还在 → GC 判"有人引用"不回收 → 全库引用静默指向另一张图）；③ `fs.renameSync`；④ resources 表行**迁移**（保 `is_favorite`/`page_url`/`timestamp`）或按 rescan 的 id 规则补建（`local-${folder}-${name}`，防 rescan 重复录入）；⑤ **`rewriteUrlReferences`** 改写库内旧引用（`kv` 全部 value + `tasks` 10 个 url 承载列；每处 4 形态：绝对/相对 × 原样/encodeURI）。
- **前端不只是"发信号"**，它负责「同一会话的内存态」三件事（有意分工，契约写在 `contracts.EVENTS['resource:renamed']`）：① 就地更新自己的列表项 + 清 `textCache`；② `publish('resource:renamed', {oldUrl,newUrl})` → 两个订阅方 `useAssetUrlRewrite`（App：改写画布/脚本箱节点 data 里的旧 url 并触发持久化）与 `taskStore`（改写内存任务 `resultUrl`）；③ 前后端共用同一份改写纯函数（`buildUrlRewritePairs`/`replaceUrlDeep`），四态对账。**必须前端也做**的原因：库里的快照被后端改好了，但前端内存是另一份真相，不改内存则同一会话内节点仍指旧路径 → 图生图 404，刷新才恢复。
- **"看着像债但不是"**：`EVENTS['resource:renamed'].from` 里的 `:NN` 行号已漂移（记 `ResourceLibrary.tsx:300` 等，实际在其后 ~22 行）。`scripts/check-events.mjs` 明确**只做文件级匹配、行号仅作审计参考**（注释已写"行号漂移不逐行硬匹配"的根因）→ 被容忍的已知取舍，**不登记为债**。

### 8.2 新登记债（2 条）

| TD-ID | 现象 | 利息率 | 偿还方案 |
| - | - | - | - |
| **TD-02-13**（新） | **「同 key 内容变更 ⇒ version 必须推进」协议被绕过**：`database.ts::rewriteUrlReferences` 直改 `kv.value`（`UPDATE kv SET value=?`）而**不推进 `<key>_version`** —— 而 `projectStore.saveCanvasState` 注释明写"版本所有权移交服务端"，即**任何**该 key 的内容变更都该走 `handleKvSet` 的版本推进。后果：**其他窗口**的 `loadedVersion` 仍"有效" → 其自动保存（CAS 旧基线）被接受 → 用**内存里的旧 url** 覆盖后端刚改好的内容（陈旧覆盖、破图复发），且 `useCanvasSync` 的 3s 轮询**发现不了**（版本没动）。同窗口路径靠 `resource:renamed` 订阅兜住，故只在**多窗口 / 后端直接发起改名（脚本、`/api/admin`）**时暴露 | 中 | **必须成对改**：① 后端 `rewriteUrlReferences` 对**被改的 key** 推进 `_version = max(Date.now(), cur+1)`（与 `handleKvSet` 同规则）；② 前端处理 `resource:renamed` 时**刷新自身 CAS 基线**（`contentKvGetVersion` → 更新 `loadedVersion`），否则**改名那个窗口自己**的下一次自动保存会 409 自撞。附带白拿：其他窗口 3s 轮询会立刻亮冲突红条（= 正确语义"你的内存已落后于库"）。需用户拍板（多窗口会多一次冲突提示） |
| **TD-02-14**（新） | **改写失败不可见**：`applyResourceIdentityChange` 里 `rewriteUrlReferences` 失败只 `console.error` 且不阻断（注释自称"不影响变更本身"）。实际后果**不是**丢文件（resources 新行已建 → GC 不会误删，此处已验证），而是**画布/任务侧仍指旧 url → 404 破图，且前端拿不到任何信号**（返回值无改写结果/失败计数，UI 无法提示"建议刷新"） | 低 | 返回值带 `rewritesApplied` / `rewriteFailed`（或失败即回滚 rename：先 rename 回原路径）；前端失败时提示"部分引用未同步，建议刷新"。**架构评估见 §8.3：推荐 A 先行 + B1 终局** |

### 8.3 架构评估（TD-02-13/14 的最优解）：「引用稳定性」应由标识不可变保证，而非改写协议保证

> **→ 已按用户意向整理成正式提案：`docs/121-素材label化改造方案-2026-09-12.md`（对齐节点 label 范式，待拍板后实施）**

**复杂度账（现状）**：一次"素材改名/移动"牵动 **8 个机制**——① 后端 `applyResourceIdentityChange`（安全解析/409 判重/renameSync/表行重建迁移/引用改写/落盘）② 后端 `rewriteUrlReferences`（kv 全部 value + tasks 10 列 × **4 形态**）③ `resource:renamed` 事件 + EVENTS 登记 + check-events 护栏 ④ 前端两个订阅方（改画布/脚本箱节点、改内存任务）⑤ 前后端**各一份**四态改写纯函数（严格对账注释）⑥ `resourceIdOf` 单一来源 + T11 护栏（防 rescan 重复录入）⑦ `useResourceMoveToFolder`（拖拽双 MIME 协调）⑧ 版本/CAS 语义的隐性依赖（不推进 = TD-02-13）。

**根因（一句话）**：**可变的展示属性（文件名/目录）被当成了不可变身份（url、id）**——
`url = /files/<folder>/<name>`、`id = local-${folder}-${name}`，两者都随改名/移动而变 →
"用户改个名字"= 身份变更 = 后端库 3 处 + 前端内存 N 处 × M 窗口全部追着改。复杂度守恒：信息抹掉了，复杂度变成 8 机制 + 2 条新债。

**事实核查（决定方案可行性）**：① 后端**已有内容寻址落盘**——`saveBase64ToFile` 文件名 = `sha1(base64) 前16位 + ext`，幂等去重（`base64Externalize.ts:60`；remote 下载同为 sha1 去重惯例）；但 **multipart 直传是另一套**：`writeUploadBuffer` 用 `${Date.now()}-${filename}`（`fileStore.ts:118`）→ 同域两套命名口径。② 稳定名落盘原语 `writeUploadBufferAt` **已存在**。③ 用户归类确实是**物理目录**（`migrated/人物`、`migrated/脚本/尾帧变体`，`fileStore.ts:35` 注释承认动态目录）。④ 前端从 url 反推路径的调用点仅 **2 处**（`relativePathFromUrl`：ResourceLibrary/GeneratedView 的"打开所在目录"）→ 改造面小。

**四个档位**：

| 方案 | 做法 | 收益 | 代价 | 判定 |
| - | - | - | - | - |
| **A 加固现状** | TD-02-13 成对修（后端推版本+前端刷基线）+ 02-14 失败可见 + 机器不变量（改 kv 内容必推版本） | 现方案自洽、多窗口不再陈旧覆盖 | 8 机制全保留；以后每加一个"存 url 的地方"仍要人工进改写清单（继续计息） | **立即做**（止血；且"推版本"在 B1 懒迁移里仍要用） |
| **B0 纯逻辑改名** | 改名/移动只 UPDATE `resources.name/folder`，磁盘与 url 不动 | 改写链整体消失 | 磁盘文件名 ≠ 显示名（rescan 以磁盘为准 → "所见即所得"被破坏） | ❌ 太激进，磁盘一致性是真实诉求 |
| **B1 内容寻址 + 元数据分离** ★ | 物理路径 = `<来源目录>/<sha1>.<ext>`（来源目录语义不可变：tasks/web/canvas/migrated/director3d）；**展示名与归类 = resources 纯元数据**；资源 id 改稳定（`local-<sha1>`） | 改名/移动退化为 `UPDATE … SET name=?,folder=?` 一条 SQL；**①②③④⑤⑧ 六个机制整体删除**（不是修好，是不再需要）；引用永久稳定 | ① multipart 改 sha1 命名（后端一处，`writeUploadBufferAt` 现成）② 前端反推路径 2 处改从元数据取 ③ **用户目录不再映射磁盘目录**（产品拍板）④ rescan 的目录→folder 映射调整 ⑤ 存量懒迁移（被改名/移动的文件才一次性迁移为 sha1 名，此时一次 url 变更由 A 的推版本机制兜住） | ★ **终局推荐**：净删 6 机制，复杂度实质下降 |
| **B2 url 间接化**（`/files/id/<assetId>` 代理读取） | url 用稳定 id，后端按 id 查当前物理路径返回文件 | 磁盘布局完全自由 | 每次读取多一跳 + 代理层（缩略图/range/缓存头）+ 直链语义变化 | ❌ 为保留磁盘目录付常驻运行时成本，不值 |

**推荐路线（分阶段、可逆）**：**A 立即（1~2h，含测试）→ B1 分三步**：① 新落盘统一内容寻址（后端一处 + 幂等测试）→ ② 改名/移动改纯元数据（**删**改写链 + 事件 + 两个订阅方 + 四态函数之一）→ ③ 存量懒迁移脚本。每步独立可回滚。
**明确不做**：不引入"引用注册表/引用计数"（把 O(N) 追着改变成 O(N) 登记，复杂度只增不减）；不选 B2。
**判据一句话**：现状 = 引用稳定性由**所有副本共同维护**（最贵）；B1 = 由**标识本身**保证（零成本）。分工最清晰的结构，是让"改 url"这个动作从系统里消失。
