## 三、根因：为什么「原图还是没有被替换」

**不是没写，是写了读不到。**

| 环节 | 事实 |
| --- | --- |
| 读侧优先级 | `resolveAssetDisplayUrl`（`base/utils/media/assetUrl.ts:282-292`）：**`contentId` > `url` > `assetUrl`** |
| 写侧 | `replaceNodeImage` **只写 `assetUrl`**（最末优先级）；且 `patchNodeDataById` 是**浅合并**（旧字段不丢） |
| 旧身份来源 | 素材库拖入（`useAssetDropPaste:284-288`）/ 拖文件（`App.tsx:1104-1109`）建的节点带 `contentId`（**那张 JPG 的 sha1**） |
| ⇒ 结果 | 抠图后透明 PNG 写进了 `assetUrl`，但旧 `contentId` 仍命中第一优先级 → 经 resource 解析出**那张 JPG 的 url** → 界面纹丝不动 |

⇒ **用户观察到的「JPG 换成 PNG 后还是显 JPG」正是此因**（contentId 解析出的就是那张 JPG）。

⚠️ **不是抠图独有**：`replaceImage` 被裁剪/压缩/放大/抠图共用 ⇒ **同一 bug 影响全部图片编辑动作**，且 6 处绕过**全都缺这一步**。

### 11.1 Step 0 第 0 步 · 表① 最优解（一屏）

**能力**：节点「主媒体字段」的**读**与**写** —— 一份媒体以什么身份存在节点上、按什么优先级取回、写新内容要维持什么不变式。

| 项 | 正确形态 |
| --- | --- |
| 真相 | 节点 `data` = 唯一真源；`resource` 表 = `contentId → url` 的 url 真源（内容寻址 ⇒ 构造上稳定，改名/移动不改它） |
| 唯一读 | `resolveAssetDisplayUrl(data, resolveContentUrl)` → `{kind:'ok',url} ／ {kind:'missing'}` |
| 唯一写 | `replaceNodeImage`（写新图）／`clearNodeMainImage`（清主图） |
| 住哪 | **三件同址** `base/utils/media/`（横切层；且**读写的判据本来就是同一份**） |
| 链路·写 | 产出 → 写 `assetUrl`，**同时让旧身份失效**（清 `contentId` · `url`） |
| 链路·读 | `contentId →(resolver)→ url` ＞ `assetUrl` ＞ `url` |
| 判据只许一份 | 「哪几个字段代表当前媒体 + 优先级」= **同一个不变式的两个方向**（写侧清旧身份，正因为读侧按优先级认身份） |

**换个人来做会写成什么样**：他会发现「从节点取主媒体地址」只有一个问题、答案只该一份 ⇒ 字段优先级只写一处、读写都看它；并把读写放一起 —— 因为**写侧要"让读侧认不出旧内容"，不看着读侧写就必漏**（本轮实证：`contentId` 漏过、`url` 也漏过）。
