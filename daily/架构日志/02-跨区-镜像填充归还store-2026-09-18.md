## 二 · Step 1 证伪（债成立，但危害已降级为结构债）

1. **① 硬证据**：`librarySource.list()` 里 `mergeResourcesFromBackend(items)` —— 纯查询写全局状态；
   且镜像填充的调用点**全在消费方**（3 处），store 本身**没有**刷新入口 ⇒ 「镜像完不完整」由 UI 打开顺序决定。
2. **② 替代方案**：store 自取（本轮）。**关键取证**：`App.handleImportPick:1037-1054` 自 TD-02-55 起
   **同时写 `assetUrl` 与 `contentId`**，`resolveAssetDisplayUrl` 在镜像缺行时**自动回落 `assetUrl`**
   ⇒ 删掉 provider 的写入**没有渲染回归**（债文的"随时序静默失效"这半，用户可见后果已被上一轮修复消掉）。
3. **③ 致命拷问**：用户不"多做"事；变的是**镜像完整性不再取决于用户开过哪个界面**（结构修复）。
4. **④ 补强证据（红线级）**：`spec/DATAFLOW.md:205` 早就写明 `base/media/` **本层不持久化、不广播** ——
   而 `mergeResourcesFromBackend` → `notify()` → `persistDebounced` → **会落盘** ⇒ 该写入**违反了本层自己声明的红线**
   （`check:arch` 规则 2/6 拦不住它：resourceStore 属 base 目录、且不是"直调 contentStore 底层"）。
   ⇒ 本轮的修复不是"改风格"，是**让代码回到它声明的边界**。

## 三 · Step 3 定位

- **所有方判定**：「后端有哪些资源」的**前端镜像**的持有者是 `resourceStore`（它自己声明：`contentId → url` 解析的真相）。
  ⇒ 「填充镜像」这个动作**归它**；`base/media/**`（契约/映射层）**只读不写**（provider 的契约原文就是"只做映射，不重实现"）。
- **触发点**：镜像的完整性是 `contentId → url` 解析的**前提**，故必须有一个**与会话绑定的确定时点** ——
  `onStorageReady`（已就绪则**同步立即回调**，见 `storageAdapter:144-151`）＝ 与 `taskStore.initTasks` 同性质的"启动把后端真相拉进内存"。
- **改动半径**：源 2 + 测试 1；**不动** `buildContentUrlResolver` 的任何消费方（见 §六-1）。

## 四 · Step 4 定契

```ts
// resourceStore —— 镜像填充的唯一自有入口（契约层不再写 store）
export async function refreshFromBackend(): Promise<void> {
  try {
    const items = await fetchAllResourcePages({});   // 全量（分页唯一实现；不抄上限）
    mergeResourcesFromBackend(items);                // 并入（既有机制，语义不改）
  } catch (e) {
    // 【不是静默吞】运行时可预期失败（网络/引擎不可用）⇒ 按 Step 4 规定 catch + logger.warn 留痕；
    // 镜像刷新是**后台动作**，用户侧的可见失败由各面板自己的错误态负责。
    logger.warn('resourceStore', '从后端刷新素材索引失败（镜像可能不完整）', ...);
  }
}

// 触发：onStorageReady(() => { reloadFromStorage(); void refreshFromBackend(); });
// 契约层：librarySource.list **不再**写 store（provider = 纯映射）
```

## 六 · 弯路留痕

1. **源日志 §8.7 记的顾虑（"会牵动 `buildContentUrlResolver` 的全部消费方"）已被上一轮消掉** ——
   我差点按那条顾虑去改 `AssetNode` / `canvasSource` / `useConnectedInputs`（无收益的大改）。
   回读 `App.handleImportPick` 才发现 **TD-02-55 起画布节点同时持 `assetUrl` + `contentId`**，
   镜像缺行自动回落 ⇒ **本债只剩结构债，没有用户可见后果** ⇒ 改动半径从"3 个消费方"缩到"2 个文件"。
   **教训：债文里记的"改动半径"是当时的估值，引用前必须重新取证**（同 A2）。
2. **刷新时点的三选一（留痕，防后人重纠结）**：
   - ① 每次 app 启动全量拉 —— 成本：大库 N 页；收益：**确定**（不依赖 UI）；
   - ② 只由面板/选择器拉 —— 成本 0；收益：**仍与 UI 耦合**（就是本债的病根）；
   - ③ 只在入库动作后顺带刷 —— 成本低；但覆盖不到"上次会话之后的新增"。
   ⇒ **选 ①**：镜像完整性是 `contentId → url` 解析的前提，而 store 本来就把行持久化进 localStorage
   （**不冷启动**，①只补"上次会话之后的新增"）。**若将来实测启动拉取成本过高，可退化为"就绪后延迟拉"，契约不变。**
3. **strict 闸当场抓到我新写测试里的类型问题**：桩写成 `vi.fn(async () => [])`，在 `--noImplicitAny` 下推成 `never[]`
   ⇒ 喂数据即 `TS2322`（普通 `tsc` 不带该标志看不出来）。**这是闸在生产它该生产的信号**（我写测试只顾运行时通过）。
   已补显式返回类型 `Promise<ResourceItem[]>`，并在测试里**写明为什么**（防后人删掉类型注解）。

## 九 · 未做（诚实边界）

1. **面板 / 剧本盒选择器的 2 处 `mergeResourcesFromBackend` 有意保留**：它们是「**读即同步**」
   （把自己已经拉到的分片并入**同一公开入口**，不绕过所有方改内部状态），且**效率上正确**
   （用已有的数据，不额外发请求）。若一并拆除，需把"面板的分页读"与"store 的全量读"合并 = 另一层重构，
   且会引入**重复请求**。**留痕：这不是漏改，是选择** —— 它们的并入**不再是镜像完整性的唯一来源**（本债病根已消）。
2. **增量刷新未做**：现在只有"启动一次 + 面板并入"。若将来出现"跨设备新增后本会话看不到"，
   可在 `resource:sent` / 云同步回流时补一次刷新（属独立需求，本轮不预设）。
3. **不立 ADR**：本轮判据（「纯查询不许有副作用」＋「镜像填充归其所有方」）分别落在
   结构（provider 无写入）与**唯一入口**（store 的 `refreshFromBackend`）上，已被既有约定与测试承载，
   未推翻任何既有 ADR，故不占现行 ADR 名额。
