## 一、链路快照

`taskStore`（`TaskStatus` 集合的拥有者 = 真相源）→ `TaskCenter`（展示端，消费方）：

```
taskStore
  ├→ taskStatusVisual(status)   → TaskCenter 圆点 / 状态文字 / 错误块底 / 错误块文字（4 用途，一处判据 4 个派生）
  ├→ isTaskNeedsAttention(t)    → computeTaskCounts.failed 档 · 「清理失败/未知」谓词 · 错误块显示条件
  └→ statusLabel / isTaskActive / computeTaskCounts / typeLabel / taskMediaKind（既有原语族，本轮未动）
LeftPanel 角标：只消费 computeTaskCounts 的**数字**，不碰颜色/谓词 ⇒ 非本判据载体。
```

DATAFLOW §一「展示：task/TaskCenter」仍准确，**链路未变**（只把判据从消费方搬回真相源）⇒ 本文件不需改。

## 二、溯源（症状 vs 病根）

- **症状**：同一判据散在消费方 —— 状态→色 4 份（`taskStore.statusDotClass` + `TaskCenter:260/344/348`）、
  `failed ∪ unknown` 3 份（`taskStore:832` + `TaskCenter:95/342`，后一处登记表**漏登**），靠 `:90` 注释同步。
- **病根不是"某处写错"**：是**判据留在了 UI 层**（TaskCenter），而状态集合的真相在 store。
  ⇒ 修症状（在 TaskCenter 抽本地 helper）会留下"store 一份 + UI 一份"两份判据；正解是**判据回 store**。

## 三、定海（不变式）

- `TaskStatus` 是**封闭 5 值联合**（`pending｜running｜completed｜failed｜unknown`）—— 由 `taskStore` 拥有
  ⇒ 「每个状态长什么样」「哪些状态需用户处理」也归它。收口后 **TaskCenter 零状态判据**，只渲染。
- 不变式（TD-08-24）：`unknown`（提交结果未知·可能已在生成）**不得与 `completed` 同色** —— 未知染成功色 = 失败伪装成成功。

## 四、切割

- 本判据属**「该走真源却没走」**（非探测重复）⇒ 处置 = 建真源 + 逐个销副本（ADR-0057 第 2 动作）。
- `config.ts::CHAT_TIMEOUT`（120s「等上游响应」段值）已被 143 · S5′ 由 `CHAT_TOTAL_TIMEOUT`（总预算）取代，
  属**替换动作的过渡产物**（ADR-0053）⇒ 清剿；引用它的 4 处注释同步回改（防描述层脱节）。

**零炸三问**：

1. **哪些行为被改了？** ① 状态→视觉 4 处改为派生自 store 单点（**用户可见结果不变**：completed 绿 / failed 红 / unknown 琥珀 / running·pending 蓝，逐一对照原映射）；
   ② `failed ∪ unknown` 三处（计数 / 清理 / 错误块）改为同一谓词（**结果不变**）；
   ③ 删除零消费导出 `CHAT_TIMEOUT`（**无调用方，用户不可见**）+ 4 处引用它的注释改为描述式（信息不丢失）。
2. **改前能走的路径改后仍能走吗？** 是 —— 49 tests 全绿（含 `TaskCenter` 各状态卡片渲染、清理菜单、错误块、预览、下载）；`check:arch`／`type-check` 绿。
3. **改前会失败的改后仍失败吗？** 是 —— `check:dead-code` 的 `config.ts::CHAT_TIMEOUT` 系 143 过渡残留（**非本轮引入**，`git diff` 证明本轮未碰 `config.ts`），按"不顺手改好"先登记；经用户裁定后本轮**同批清偿**（属 ADR-0053「过渡态只许存在于本次施工内，落账前清干净」）。

**用户可感知的行为变化（显式声明）**：状态文字色的**表外值兜底**由 `text-emerald-400`（成功色）改为 `text-blue-400`（进行中色）。
`TaskStatus` 为封闭 5 值联合 ⇒ 该分支**不可达**（仅运行时脏数据），故用户可感知变化 = **无**；此改动是**有意的语义修正**（未知状态不得染成功色）。
