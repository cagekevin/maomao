## 一、它原本是干嘛的

`element.trimEnd` = **源素材右侧还剩多少没用**：

```
源素材:  [-------][================][---------]
          trimStart   duration×速度    trimEnd
          (左边裁掉)   (实际用到)      (右边没用上)

素材总长 = trimStart + duration × playbackRate + trimEnd
```

它**不是**"派生字段"（体检轮描述如此），而是"素材总长"在 element 上的一份**冗余副本**。
真源是 media asset 的 `duration` —— 上传时读视频/音频元数据得到（`processing.ts:227-244`
走 `getVideoInfo().duration` / `getMediaDuration()`，**是真实值、不是空的**）。

## 二、零损失的取证（两条决定性证据 + 一张读者表）

**① 真读者只有 1 处**（逐处核实，不是数出现次数）：

| 位置 | 读法 | 能否替代 |
| --- | --- | --- |
| `use-element-resize.ts:148/217` | 反推 `sourceDuration` 算拖拽边界 | ✅ **等价可换 `media.duration`** |
| `use-element-resize.ts:246` | `maxTrimEnd`（右侧最多裁到哪） | ✅ 同上 |
| `audio.ts` 3 处 | 打包进 `AudioMixSource`/`AudioClipSource` | ❌ **无消费者**：`mixAudioChannels` 只解构 `trimStart` + `duration×rate`（纯搬运） |
| `scene-builder.ts` 3 处 → `VisualNodeParams` | 传进渲染节点 | ❌ **`visual-node.ts` 声明后零使用**（纯搬运） |
| `mediabunny.ts:133` | `const trimEnd = source.trimStart + sourceDuration` | ❌ **同名局部变量**，与字段无关 |

**② 它的边界作用可被 `media.duration` 完全覆盖**：
`canExtendElementDuration()` 只对 `text`/`image` 返回 true ⇒ 视频/音频右侧拖拽**永远**受
`maxTrimEnd` 约束，而
`maxTrimEnd = 素材总长 − trimStart − 最短时长×速度` —— 用 media 的 duration 表达**完全等价**。

**③ 唯一的边界情况**：素材在 media 里找不到（断链）→ 退回"当前已用长度"（不允许再裁出源范围）。
断链片段本就播不了，**不是新增损失**（保守边界比错误边界安全）。

**④ 兼容**：旧工程存档里的该字段成为未知字段，反序列化时被忽略 —— **无人读 → 无行为变化**。

## 三、额外发现：这个字段**本身就自相矛盾**

`split-elements.ts` 的原注释声称不变式是 `trimEnd = trimStart + duration × rate`（当成"源出点"），
而真正读它的 `use-element-resize.ts:148` 是按 `素材总长 = trimStart + duration×rate + trimEnd` 反推的
（当成"尾部剩余"）—— **同一个字段，两处两种互不相容的语义**。`split` 当年就按"源出点"写，
于是把值写成了 `trimStart + 左半源长`，直接喂给 resize 的公式就是错的。

→ **一字段两义 + 冗余副本 = 边缘处必然算错**。删掉它，两个矛盾一起消失。

## 五、顺带修掉一个**真功能缺陷**（用户可感知）

原 `updateElementTrim` **只提交 `trimStart` / `trimEnd`，从不提交 `duration`**：

```ts
// 旧：duration 未传 → 命令里 `this.duration ?? element.duration` 保持原值
new UpdateElementTrimCommand(elementId, trimStart, trimEnd);
```

而右侧拖拽改的**恰恰是长度**（`duration`）—— 于是**「拖右边缘改时长」在松手后完全不落库**
（UI 预览弹回，用户以为拖拽坏了）。这条缺陷一直被 `trimEnd` 的存在掩盖着：
写进去的值没人读，读它的人又拿不到新 `duration`。

现在提交 `duration`，拖拽结果才真正落到元素上（并由命令栈支持撤销）。

## 七、弯路留痕（强制）

**① 差点误删 `leftSourceDuration` —— 它不是只为 `trimEnd` 服务的。**

它同时是**右半段的源入点**：`trimStart: element.trimStart + leftSourceDuration`（split 的两处分支）。
我按"它只喂 trimEnd"的判断删掉了定义，`type-check` 立刻报 3 处 `Cannot find name`。
→ **教训**：删字段时，与它相关的**派生变量**必须逐个确认是否还有别的用途；类型检查是这里唯一的守门人。

**② `replace_all` 是子串匹配，会跨缩进命中。**

用 8 空格缩进模式批量删 `v1-to-v2.ts` 时，它把 10 空格缩进的行也匹配走了（`        trimEnd…`
是 `          trimEnd…` 的子串），后续那条 10 空格的 replace 反而报"未找到"。
→ 批量删除时，**缩进要当作模式的一部分**；事后用 `grep` 复核残余比"再补一次 replace"可靠。

**③ `scene-builder.ts` 的 12 空格缩进漏了一处**，类型检查报 `trimEnd does not exist in StickerNodeParams` 才补上。
→ 同一文件的**同一字段可能出现在多个缩进层级**，一处 `replace_all` 不代表清完。
