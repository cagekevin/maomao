### 描述修正（Step 1 §「任何描述都是线索」）

- **TD-22-33 被低估**：原描述只说「`flush()` 在 `isSaving` 时空转」。取证发现**两层**：
  1. `flush()` → `saveNow()` 撞 `if (this.isSaving) return` → 不等待；
  2. **更致命**：`saveCurrentProject()` 的 `catch` **吞掉非 409 失败且不 rethrow** → `await saveNow()` 无论如何都「成功」→ `hasPendingSave` 被清成 `false` = **宣告「脏数据已保存」**。
  叠加 `prepareExit()` 把 flush 写在 `if (didUpdateThumbnail)` 里 → **退出时若无缩略图更新，队列里的最后变更根本不落盘**。
  → 修法据此扩为「三层一起收」（判别返回 + 保持 dirty + 无条件 flush）。
- **TD-22-38② 的形态比描述更「假」**：不只是「宽松」，而是**实现已是判别联合、类型却宽松** —— 即类型在给一个**不存在的自由度**背书。

## 三、定海（Step 3 定位 + Step 4 定契）

### 正确形态（一屏）

- **入口**：任何会改持久状态的引擎操作（保存 / 素材写入 / 媒体加载 / 导出）。
- **链路**：调用方 `await` → 拿到**能判别成败的结果** → 按结果决定 UI 与后续动作。
- **判据在哪层**：成败由**执行 IO 的那一层**（`storageService` / `uploadFileToLocal`）如实回答，不吞不伪造。
- **真相归谁**：结果真相归**操作执行者**（manager 方法）；调用方只消费，**禁止二次探测**。
- **失败可见性**：开发者 → `logger`；用户 → toast（瞬时动作）/ **面板错误态**（持续状态）。

### 复杂度落点（五问）

- 真源 = 「操作执行者」；形态定义放 **`types/`**（最底层，不反向依赖 engine —— 顺带不加重 TD-22-31 的层位倒置）。
- 变化速率：失败**原因词表**各域不同（导出有 `cancelled`、保存有 `conflict`）→ **词表分域保留**；只有**判别位形态**统一（`ok`）。
- 份数：统一形态将被 4 处使用（非 1 处）→ **不是假接缝，允许抽**。
- 改动半径：新增 1 个类型文件 + 就地收窄 3 个域类型 + 4 个 manager + 5 个消费点。

### 定契（四条禁令逐条对齐）

| 禁令 | 本条怎么落地 |
| --- | --- |
| 禁静默吞 | `saveCurrentProject` 不再吞（如实返回 `conflict`/`save-failed`）；`saveNow` 失败保持 dirty + 唯一读者给 toast；`loadProjectMedia` 置 `loadError`；`removeMediaAsset` 失败补 toast |
| 禁假成功 | `addMediaAsset` 失败返 `{ok:false}`（不再返幽灵 id）；TTS 拿 `!ok` 时 revoke + **中止**（不再插断链片段） |
| 禁错误→错误结果 | 导出失败不再可能「`success:true` 但无 buffer」——该组合**在类型上不存在** |
| 禁重分类 | `flush` 的 `paused`/`loading`/`migrating`/`no-project` 如实分类（原来全部静默 `return`） |

## 七、弯路留痕（强制）

1. **`AddMediaAssetOutcome` 成功支第一版只带 `id`**（不同 `asset`）→ 写消费方时发现 drag-drop 仍要回数组里找对象拿 `duration/type/name`（就是原「二次探测」的第二半成因）。**改为成功支带 `asset` 本体**。
   → 记下来防后人「精简」掉它：那会把探测重新引回消费端。
2. **测试第一版 6 例中 2 例红**：`expected 'loading' to be 'save-failed'`。不是实现错，是**测试 fixture 缺「就绪」前置** —— `ProjectManager.isLoading` 初值 `true`，真实链路靠 `EditorProvider` 挂载时 `loadAllProjects()` 落到 `false`；不先走这一步，`SaveManager` 的前置守卫直接返回 `loading`，**测不到保存本身**。
   → 抽 `bootEditor()` 显式造「已就绪」上下文并写明理由（否则后人会以为实现有 bug）。
3. **`while (this.inflight) await this.inflight` 用了 `while` 而非 `if`**：等待期间可能又有新的保存被触发，`if` 只等一次会留下同样的窗口。
4. **探针曾想把「`runSave` 单飞复用」当注入点** → 推演发现它不会让测试红（`flush` 的 `while` 已把 inflight 等空）→ 改为注入 `flush` 的等待块本身。**「注入点选错 = 探针假红/假绿」**，与 7.1「先红没红就要重写」同源。
