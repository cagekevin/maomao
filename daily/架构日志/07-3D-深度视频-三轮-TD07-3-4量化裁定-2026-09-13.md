## 三、Step 3 定位 —— 复杂度该落哪？

### TD-07-3 → **不拆**

- **内容性质**：2058 行是**同一领域（3D 工程数据模型）的分层**：类型/常量（L27–299）→ 通道/轨道（L361–780）→ 归一化（L782–1270）→ 求值/插值（L1270–1675）→ 路径（L1676–2050）→ IO（L1989–2058）。**非跨领域混杂**；债说的「6 类职责」实为**一域内的层**。
- **拆分收益判据**：拆成 `project/{types,tracks,normalize,evaluate,path,io}.ts` + 桶文件 `re-export` → **消费方零改动**（fan-in 本就 1）⇒ **改动半径不变 = 只搬家**。方法 Step 3 明示「若半径没变小，我只搬了家」→ **不做**。
- **唯一真缝隙**（判据：变化速率不同）：尾部 DOM IO `referenceImageFromFile` / `referenceCanvasForExport`（依赖 `File` / `canvas`）与纯数据模型**变化速率/依赖层不同** —— 但仅 **2 函数 ~70 行**，抽出收益 < churn 成本 → **一并登记为观察项**。

### TD-07-4 → **不拆（登记真缝隙地图）**

- **真缝隙存在**（状态成簇，非同质堆砌）：
  ① **工程数据**：`shots` / `activeShotId` / `objects` / `camera` / `lighting` / `reference` / `channelTracks` / `objectTracks` / `paths`；
  ② 选择/工具栏：`selectedKeyframe` / `keyframeClipboard` / `pathContextMenu` / 变换模式三态；
  ③ 面板可见性：多个布尔；
  ④ 导出/缩略图：两个 canvas + 计数 + 标志位。
- **已有前置收口**：持久化/历史**已抽出**（`d3dPersistence.ts` / `history.ts`）→ ① 簇若抽出，形态是 `useDirectorProject`（窄接口：state + actions），属**深模块**方向（合法）。
- **但不做（Step 1 判）**：致命问「拆了用户/系统能多做哪件原来做不到的事？」→ **答不出**；且 **拿不出根因证据**（无由上帝组件引发的可复现故障）。**决定性阻碍：0 组件级测试** —— 18 个 director3d 测试**全部测 `project.ts` 纯函数**，`App.tsx` 无任何组件/行为断言。对 2672 行、46 state 的编排做重构而**无测试护栏** = 方法 Step 1「拿不出证据→不做」。
- **留痕**：把 ①–④ 缝隙地图写入台账，供**将来有组件测试护栏时**再拆（届时只需抽 ① 簇）。
