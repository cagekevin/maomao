## 二、溯源（Phase 1：症状 vs 病根）

- **类型地基层（最底）已定位并收口**：`NodePalette` 注册表零类型 → 下游假收窄（TD-04-6，本轮已修）。
- **新发现病根（连接渲染层）**：`CustomEdge` 的删边路径与 App 注释声明不符（TD-04-8）——App 专门建了 `window 'yimao:remove-edge'` 监听并注释「CustomEdge ✕ 经它触发」，但 `CustomEdge` 实际走 `deleteElements`，**从未 dispatch 该事件**。全项目 0 发布方 → 死事件 + 死监听。
- **新发现病根（id 契约层）**：画布边 id 有 **4 套格式**，缺统一的「一对节点一条边」去重契约（TD-04-9）。

## 三、定海（Phase 2：不变式 / 唯一真相源）

- **node.data 写回唯一入口 = `patchNodeDataById`（useNodeData）** ✅ 唯一；F1 约束（不可变更新，禁原地 mutation）已在注释固化，全项目 0 处原地 mutation（`useConnectedInputs` 头注实证）。
- **节点 id 唯一入口 = `idGen.generateId`** ✅ 唯一。
- **边 id = ❌ 4 套格式无统一契约**（TD-04-9）；但每套内部唯一，**当前未观测到实际碰撞**（target 端多为新节点 id）。
- **事件通道 SSOT**：`yimao:remove-edge` 为孤儿（只有 window 监听、无 dispatch）——**已删**（TD-04-8）。

## 四、切割（Phase 3：深模块 / 真缝隙 / 收敛口）

- **`useNodeData` / `CustomHandle` / `useSyncNodeData` = 合格深模块**（窄接口厚实现，注释含 P0 reflow 决策与 F1 约束）。**不切**。
- **连接渲染层无上帝类**：`CustomEdge`（渲染 + 删边）、`CustomHandle`（端口 + mousemove）、`ConnectionLine`（拖拽临时线）职责清晰。
- **id 契约缺收敛口**：4 套边 id 应归一为单一策略（TD-04-9）。

### 纠正记录（2026-09-11 用户质问后复核）

初版把「同对多边」笼统当缺陷并提议加 `isValidConnection` 拦截——**方向判错**。用户指出：**一节点多输入、一节点多输出到多个节点，本就合理**。复核后确认：

- **一节点多输入**（多 source → 一 target）：✅ 现支持（每对 pair 一条边，多个上游各成一条）。
- **一节点多输出到多个节点**（一 source → 多 target）：✅ 现支持（shot-1→图A、shot-2→图B，target 不同=pair 不同）。
- **唯一真缺陷**：**同一对 (source,target)** 用**不同端口**连多条（如 shot-1→图A 与 shot-2→图A）→ 原 `onConnect` id（`xy-edge__${source}_${target}`）**不含 handle** → 撞车。**已修**（id 纳入 handle + `generateId` 兜底）。
- **代码库事实上不变量 = 「一对节点一条边」**：Agent `connect`（`useCanvasAgentTools.ts:745`）明确 `already` 拒绝同对、节点自连去重（TextGenerate/ImageGenerate/VideoGenerate/ScriptBoxNode `e.source===..&&e.target===..`）、`upstreamLink` 均只看 pair 忽略 handle。故「同对多边」是否应支持 = **产品语义决策**，非我单方可定。
