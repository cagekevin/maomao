## 二 · 溯源（症状 vs 病根）

**症状**（用户可感知）：
- 「导入弹窗选了图 → 提示"已导入 N 个素材" → **画布上什么都没有**」（本轮报障；已修）；
- 「删了素材，刷新它又回来了」（假删除）；
- 「备份导入提示成功，实际丢了一部分工程」；
- 「素材列表莫名少几张 / 少几项」（`loadAllMediaAssets` 逐条静默丢）；
- 「发到画布提示已发送，目标节点并不存在」。

**病根（母体）**：本仓把"失败可见"写成了红线与闸，但**"成功"这一侧没有对应的判据契约**：
- 成功可以只凭**输入**（选了 3 张就报 3 张）或**"没抛错"**（`res.ok` 恒真、`!skipped`、`writeFileSync` 返回值丢弃）宣告；
- 而"已写好的失败处理"若挂在**零调用**的方法上，等于**修复从未生效**（比没修更坏：注释与账本都显示"已修"）；
- 死代码闸因 `entry` 含 `tests/**` 而**系统性看不见**"仅测试引用"，于是"零调用"长期无法被机器发现。

**为什么现在才看见**：上一轮（TD-16-22）用的是"闸自己的窄判据"扫静默；本轮**换了三个视角**——① 成功文案的**数值来源**（输入 vs 结果）；② 导出符号的**生产引用点份数**；③ **闸的 entry 面**（而非判据面）。三者各扫出独立面，说明这不是零散疏漏，而是**"信号诚实性"缺少成体系的守卫**。

## 三 · 定海（不变式 / 唯一真相源）

1. **成功判据的唯一合法来源 = 结果对象**（`linked.length` / `created.length` / `run().changes` / `savedPath` / `dedup.savedPath`），**不是**输入长度、不是"没抛错"、不是 `!skipped`。
2. **失败处理的宿主必须可达** —— 写在零调用方法里的修复 = 0 收益；`knip` 基线 0 **不能作为"无死代码"的证据**（entry 含 tests 时它是假绿）。
3. **同层已有正面范式**（本轮复用，不新造标准）：`link-media-refs.ts:158-168` 按 `linked.length` 分流 · `media.tsx:145-158` 0 新增改 info · `App.tsx:1044-1056` 按 `addNode` 返回 id 判定 · `librarySource.ts:57-60` 缺 url 抛错 · `pagedList.ts:89-96` 缺字段抛错。
4. **互斥不变量仍成立**：`contentId` / `url` / `assetUrl` 三形态互斥（docs/122 #4）—— 本轮结论**不得**以"再加一个字段"绕过。
