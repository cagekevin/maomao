## 一、Step 0 · 普查：清理选择这件事有几份？

grep `clearSelection()` / `setSelectedElements()`（`src/components/videoEditor` 全量）：

**A. 「删除导致选择失效」的路径**（本该清而各写各的）：

| 路径 | 是否清选择 | 证据 |
| --- | --- | --- |
| 删元素（UI 主路径 `delete-selected`） | ✅ 清 —— **但写在 UI action 里** | `actions/use-editor-actions.ts:229` |
| 素材连带删除（`RemoveMediaAssetCommand` → `deleteElements`） | ❌ 不清 | `commands/media/remove-media-asset.ts:48` |
| 删轨道（`RemoveTrackCommand`） | ❌ 不清 | `commands/timeline/track/remove-track.ts` |
| 删场景（`DeleteSceneCommand`） | ❌ 不清 | `commands/scenes/*` |

**B. 「用户意图」清选择**（应当保留，与失效无关）：点击空白 `use-preview-interaction:137` · 点时间轴 `use-timeline-seek:165/179` · 切场景 `scenes-manager:80` · 退出/切项目 `core/index.ts:83`。

**判据（红线）命中**：同一件事（"选择要跟着元素消失而失效"）被写成 **1 份（UI 层）+ 3 处漏**，且 4 条路径分布在 4 个不同层（UI action / media 命令 / track 命令 / scene 命令）——**典型"谁记得谁清"**，必然漏。
另注：`split` / `duplicate` / `paste` / `detach-audio` 四个命令都各自手写 `previousSelection` 捕获 + undo 还原（TD-22-26 未提到的同族）：**同一件事 4 份手抄**。

## 三、Step 2 · 母体

> **「选择必须指向存在的元素」这条不变量没有拥有者。**

选择是 `{trackId, elementId}` **引用**集合，其有效性完全由当前场景的 tracks 决定 —— 真相在 tracks，判据却散在调用方。
只要它是"调用方的责任"，路径增加一条就漏一条，且 undo 恢复还得每个命令各抄一遍。

---

## 四、Step 3 / 4 · 定位与契约

**Step 3 三选一**：

| 方案 | 内容 | 判定 |
| --- | --- | --- |
| A | 在 4 条删除路径各补一次清理 | ❌ 仍是"清单"，新增路径照漏（母体未治） |
| B | 抽一个 `pruneSelection` 原语，4 条路径各调一次 | ⚠️ 判据单点，但**调用清单**仍在 |
| C | **把不变量做进读取侧**：`getSelectedElements()` 返回「选择意图 ∩ 当前 tracks 存在的元素」 | ✅ **采纳**：任何删除路径自动失效、撤销后自动恢复、调用方零记忆 |

**采纳 C 的关键约束（Step 4 契约）**：

1. **引用必须稳定**：UI 经 `useSyncExternalStore` 读它（`selection-overlay` / `use-preview-interaction` / `use-element-selection` **3 处**），该 API 要求 `getSnapshot()` 在状态未变时返回**同一引用** —— 否则 React 判定"每次都变了"→ 无限重渲染。
   ⇒ 派生结果缓存在 `visibleElements`，**只在内容真变时**才换引用（`isSameRefs` 按内容比较）。
2. **失效要能立刻广播**：`SelectionManager` 构造时订阅 `timeline` + `scenes`（两者任一变化都意味着元素集合可能变），重算后内容有变才 `notify()`。
   订阅的时机安全性：`EditorCore` 构造顺序里 `selection` 最后构造，`timeline`/`scenes` 已就绪 ✔。
3. **无活跃场景 = 无有效选择**：派生走新增的 `ScenesManager.getActiveSceneOrNull()`（与 `ProjectManager.getActiveOrNull()` 同惯例），**不复用会抛错的 `getActiveScene()`**。
4. **连带效果（免费获得）**：`split`/`duplicate`/`paste`/`detach` 手抄的 `previousSelection` 还原变得冗余（撤销后元素回来、选择自动可见），但**本轮不删** —— 它们各自还还原"选中新建的右半/副本"等意图，不是同一件事，删了会改变行为（Step 6：不为一致性而改）。

**定权（Step 5）**：结构 + 不变量，用户可见行为**只有正确方向的变化**（幽灵消失、且"部分删除"时不再一刀切全清）→ 架构师直接定。

### 6.3 ⚠️ 既有测试被新不变量打破（本轮最值得记的一件事）

第一次全量跑出 **4 failed**（此前稳定 3 failed）——多出的一例是**我上一轮自己写的** `veProjectContextRelease.test.ts`：

- 失败断言：`expect(selection.getSelectedElements()).toHaveLength(1)` → 得到 `[]`。
- **根因**：该 fixture 写的是 `{ trackId: 't1', elementId: 'e1' }`，而 `trackOf('t1', …)` 生成的元素 id 是 **`t1-e1`** —— 这个引用**从一开始就指向不存在的元素**（幽灵引用）。旧实现不校验，所以测试"通过"；不变量落地后它立刻暴露。
- **处置 = 修 fixture，不是迎合实现**：把两处 fixture 改成真实 id（并在注释里写明"该 id 原写错，被选择有效性不变量揪出"），另有"切场景"用例顺带加了"切之前选择确实有效"的前置断言（断言更强）。
- **教训**：**派生式不变量的落地成本会体现在测试上** —— 旧测试里所有"用假数据构造的通过"都会现形。这是好事（假引用本来就是隐患），但必须逐条判断"是 fixture 假、还是我把收口做过头了"（本题为前者，因为断言的对象本就该存在于 tracks）。

## 七、结论与遗留

- **结清 TD-22-26**，且把它的边界从"一条路径"扩到"四条路径 + `previousSelection` 手抄"——**一并消除**。
- 交付物是**不变量**而非守卫：`SelectionManager.getSelectedElements()` 即"选择意图 ∩ 现有元素"，从此新增任何删除入口都不需要记得清选择（删不掉的正确性）。
- 代价与约束已写进类注释：**引用稳定性**（`useSyncExternalStore`）+ **订阅失效广播**（timeline/scenes）。
- **遗留**：
  1. `split`/`duplicate`/`paste`/`detach` 的 `previousSelection` 捕获未删（它们同时还原"选中新建元素"的意图，非冗余；若未来要削，须先证明"撤销后选中新建元素"不必要）。
  2. `RemoveMediaAssetCommand` 的存储删除在 jsdom 下报 `indexedDB is not defined`（如实记录、已 catch）—— 属测试环境无持久层，非债；已在测试文件注明，免后人误判。
- **下一轮建议**：**M-A 手抄形状族**（TD-22-28/30/35/36/39，5 笔低息、机械但成片），或 TD-22-19（宿主 6 处 window 键盘无编辑器门，用户可感知的误删风险）。
