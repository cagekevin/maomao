# 02 区 · 十轮深化 — 根因层：缺"诚实结果契约"，复杂度从声称的单一内核漏进散落 catch

> 重读 `架构师心法` 后，把"复杂度落点图谱（九轮）"再往下打一层：九轮只判了**复杂度该落在 contentStore 内核**，但没回答**内核为什么收不住**。本轮用 Phase 1 探因（症状 vs 根因）+ 铁律 5（假接缝复核）+ §五 真相（SSOT 双真）三探针，追到根因层。
> 实证工具：`node scripts/mv-sync-refs.mjs refs <file>`；源码定位见 `src/components/base/core/contentStore.ts` / `contracts.ts` / `store/projectStore.ts`。
> 本轮**只登记不修**，所有债进入 `债务.md`。

## 一、§二 Phase 1 探因：TD-02-15/19/20 是症状，根因是"地基缺诚实结果契约"

### 1.1 文件头已自陈设计意图，但实现漂移（文档 ≠ 代码）

`contentStore.ts` 文件头 L16-19 明确写道：

> 策略两族：尽力而为族（降级，失败不阻断）与严格族（CAS，失败 fail-closed 绝不写副本）。**两族共用路由/缓存/订阅内核；真分叉在「失败语义」，不在「后端」**。

以及 L13-14：

> 失败分类唯一实现 = `isEngineUnavailable`；降级只服务前者。

**但实现与自陈漂移（这是本轮最硬的发现）：**

| 函数 | L 行 | 是否接入 `isEngineUnavailable` | 与文件头声明 |
| --- | --- | --- | --- |
| `writeKvWithFallback` | 322-324 | ✅ `if (!isEngineUnavailable(e)) throw e` | 符合 |
| `readKvWithFallback` | 297-301 | ❌ **catch 直接 `sGet` 回退本地副本 return**，无守卫 | **违反"唯一实现"声明** |
| `contentGetKvWithFallback` | 505-521 | ❌ 借 `readKvWithFallback`，`from` 标 `'local'` 含 4xx | 违反 |

→ 读族把"失败分类"这个复杂度**漏到了散落的 ad-hoc catch**，而不是收在文件头声称的"唯一实现"内核里。九轮我建议"给读族补 `isEngineUnavailable`"，那是**给症状打补丁**——用户点我"研究得不够深"，正是指这点：补一个 catch 拦不住根因复发。

### 1.2 真正的根因：地基没有"存储操作结果的诚实契约类型"

把 5 个核心函数的返回形状并列（均来自 `contentStore.ts`）：

| 函数 | 返回形状 | 调用方能否区分"KV 真值 / 降级副本 / 4xx 拒收 / 引擎挂" |
| --- | --- | --- |
| `readKvWithFallback` | `Promise<unknown>` | ❌ 全混（降级副本与真值同为 `unknown`） |
| `writeKvWithFallback` | `'kv' \| 'local'` | ⚠️ 粗（local=降级，但 4xx 已上抛不可见） |
| `contentGetKvWithFallback` | `{ value, from: 'kv'\|'local' }` | ❌ `from:'local'` 在 4xx 时也是谎 |
| `contentKvSetCas` | `{ landed: 'kv', version? }` | ⚠️ 严格族靠"抛"表达失败，无定型 |
| `deleteKvWithFallback` | `void` | ❌ 失败完全无信号 |

**根因判词（§二 Phase 2 探底）：** 失败分类只做到了"一个 `isEngineUnavailable` 布尔 helper"，但**"一次存储操作的结果"从未在契约层定型**。于是每个函数各自发明信号（`from` / `landed` / `'kv'|'local'` / `void`），调用方必须重新推导"成没成功、降没降级、真源是哪"——复杂度被迫散落。这正是"声称单一内核、实际散落 catch"的病根。

### 1.3 根因修复（统摄 TD-02-15/19/20，不再逐个打补丁）

在 `contracts.ts` / `contentStore` 类型层引入**诚实判别联合**（地基一次到位，符合铁律 5「地基该一次到位」+ §二 Phase 2）：

```ts
type StorageOpResult<T> =
  | { ok: true; value: T; source: 'kv' }
  | { ok: true; value: T; source: 'local'; degraded: true }   // 仅引擎不可用才出现
  | { ok: false; error: 'engine-unavailable' }                // 网络/超时/5xx
  | { ok: false; error: 'rejected'; status: number };         // 4xx，必须上抛

// 两族只是"容许的分支"不同，共用同一内核：
//   降级族：返回 degraded / engine-unavailable 分支
//   严格族：非 { ok, source:'kv' } 一律 throw
```

这样 `readKvWithFallback` / `writeKvWithFallback` / `contentGetKvWithFallback` 的差异**由判别联合自然表达**，散落 catch 消失，"真分叉在失败语义"才真正成立且共用单一内核。TD-02-15（读族漏接守卫）、TD-02-19（`from` 语义造假）、TD-02-20（cache 无来源标记）均被此根因修复**统摄**——不再三个独立补丁。

> **铁律 2 第二维度收口**：`source` 仅在 `{ok,source:'kv'}` 或 `{ok,source:'local',degraded:true}` 时存在；4xx 拒收**不携带** `source`，下游据诚实分支行动（d3d 不再误把 4xx 当降级写回 KV）。

## 二、铁律 5（YAGNI / 假接缝）复核：backend 不是缝、失败语义是真缝，但内核样板三重复用

### 2.1 复核结论：真分叉判词正确，无需推翻

`resolveBackend` 单一路由（L210，14 处调用）+ 文件头 L18"勿按 local/kv 划族"，确认**backend(kv/local) 不是真缝隙**（若按后端拆族就是假接缝，已被正确否决）。降级族 vs 严格族的拆分**是**真缝隙——用户主数据（CAS）fail-closed、配置类 fail-soft，失败语义确实不同。九轮/本轮不推翻此判词。

### 2.2 但"表达真分叉"时，共用内核被字面复制（附随复杂度）

KV op 的样板 `resolveMeta/resolveBackend/timeout?withTimeout/keepFallback?sRemove` 在 **4 处字面子重复**（非假抽象，是冗余表达）：

- `readKvWithFallback`：L292-294 / L296 / —（无 sRemove，因读不删副本）
- `writeKvWithFallback`：L312-314 / L317 / L320（`if (!keepFallback) sRemove(key)`）
- `contentKvSetCas`：L566-568 / L570 / L571（`if (!keepFallback) sRemove(key)`）
- `contentGetKvWithFallback`：L509-510 / L513

→ **TD-02-22（新·内核样板三重复用）**：抽 `withKvOp(key, op)` helper（被 4 处调用 = 真复用，符合 §一.2 收敛、非铁律 5 假抽象），把 `meta.timeout/withTimeout/keepFallback/sRemove` 收口到一处。配合 §一.1 复杂度守恒：删 4 份样板 = 认知单元下降、改动半径下降。

## 三、§五 真相（SSOT）：store 层存在"双真"，靠约定而非结构同步

### 3.1 同一键有两份内存真相

`projectStore.ts` 自持 **module 级可变态**（L130 `projects`、L145-147 `projectVersion = ...; projects = merged`）。`contentStore` 另有独立 `cache`（L266 `cache.set`）。对 `PROJECTS_KEY` 同时存在：

- **真相 A**：`projectStore` module 态（权威编辑态，selector 直接读 `projects` 变量）
- **真相 B**：`contentStore.cache`（其他消费者走 `contentGet` 读此处）
- **真相 C**：后端 `/api/projects`（L179 `saveProjects`）

同步靠"projectStore 每次变更必 `contentSet(PROJECTS_KEY, projects)`"（L174）+ `saveProjects` 的**约定**，无任何结构保证。若任一路径绕过 `contentSet` 直改 module 态、或直读 `contentGet` 未刷新 cache，即分叉。

### 3.2 与 TD-02-20 同源

这正是 §五 真相自检"偷偷创建数据副本而不做同步"的**第二处**（第一处是 contentStore 内部 cache 降级副本无标记，TD-02-20）。架构师曾在 L246-249 修过"未就绪≠不存在"的 cache 污染（TD-02-2），证明他**应用过一次 §五 真相**，但只修了"未就绪"子类，**漏了"降级副本"子类**——典型的"症状级修补、根因级遗漏"，与 1.1 漂移同一病根。

→ **TD-02-23（新·SSOT 双真）**：不是要删 store 态（那是业务能力，架构师无权自删，§零.5），而是用契约钉死"谁是唯一真相源"——store module 态 = 权威编辑态，contentStore.cache = 只读派生态，且**必须只由唯一写路径（`contentSet`）实时刷新**（把"同步约定"升级为结构保证，如 contentSet 后强制 cache 与订阅同源于一处）。根因同源：缺单一诚实状态/结果契约。

## 五、结论（十轮 vs 九轮）

- **九轮**只判"复杂度该落 contentStore 内核"（落点图谱）；
- **十轮**追到根因：内核收不住，是因为**地基缺诚实结果契约类型**——单一个 `isEngineUnavailable` 布尔 helper 不足以表达"操作结果"，于是 5 函数各发明信号、散落 catch 重现。
- 修复从"给读族补守卫（症状补丁）"升级为"引入 `StorageOpResult` 判别联合（根因收敛）"，统摄 TD-02-15/19/20。
- 另立 TD-02-22（内核样板三重复用，铁律 5 邻接）、TD-02-23（SSOT 双真，§五 真相第二处）。
- 复核确认：backend 不是假接缝、降级/严格是真分叉（九轮判词成立，不推翻）；只是"表达真分叉"时内核样板被冗余复制（TD-02-22）。
