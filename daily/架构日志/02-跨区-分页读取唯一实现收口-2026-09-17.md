## §一 · 本轮范围（Step 0 普查 → Step 1 证伪）

用户报的是"导入面板生成只显示 100 条"。**Step 1 证伪：需求为真**（硬证据：`librarySource.ts` 写死
`PAGE_SIZE=100 / PAGE=1` + 后端 `helpers.ts::parsePagination` 把 pageSize 硬性 cap 到 100）。

**但 Step 2 归因发现：这不是"某个面板的上限"，而是一条母体在 7 处各写一份。**

## §三 · 母体判定（Step 2）

**母体 = `读列表` 这条能力既没有唯一实现，也没有唯一契约。**
分页参数、取页策略、"后端上限是多少"三种知识散在 7 处，各自演化。一次生产 5 类症状：

**① 静默不完整（4 处）** —— ③④⑤⑥ 全都"只给一部分且不告知还有更多"。

**② 失败不可见（M5）** —— `ResourceLibrary.tsx` 下一页失败被 `catch { /* 忽略 */ }` 吞掉（**零日志**，
而同文件 `reset` 的 catch 有 `logger.warn` = 同文件内双标）⇒ 用户把"加载失败"读成"已经到底"。

**③ 已算出真相却零消费** —— provider 诚实地算了 `meta.hasMore`，全库 grep：**无任何消费方读它**；
注释却写着"消费方拿 hasMore 决定要不要加载更多"（M4 描述与代码脱节）。

**④ 契约描述与实现脱节（M4）** —— `librarySource.ts` 注释称"`fetchResources` 不支持 keyword 参数"，
**描述不实**：后端 `parsePagination:226` 一直在读 `search` 并做多列 LIKE，缺的只是前端封装没暴露该参数。

**⑤ 顺带挖出独立 bug（两端参数名不匹配）** —— 前端 `fetchTasks` 发 `keyword`（`localToolApi.ts:97`），
后端读 `search` ⇒ **任务搜索永久静默失效**（不报错，只是不过滤）。
诚实边界：当前两个调用点都未传该参数 ⇒ **无用户可见症状**，属契约级潜伏缺陷。

## §四 · 定契（Step 3/4）：复杂度落在哪

**真相所有方 = 后端** `/api/resources` `/api/tasks`（决定 `total` 与**实际**页大小）。
故新增 `src/components/base/api/pagedList.ts` 作为分页读取的**唯一实现**，关键设计：

1. **不抄任何上限数字** —— 收敛一律按响应里的 `totalPages`；后端把 cap 从 100 改 200，本层与全部消费方**零改动**。
   `FETCH_PAGE_SIZE=100` 只是"每次要多少"的**性能参数**，不参与正确性判断（被 cap 到更小时 `totalPages` 变大，循环照样取齐）。
2. **两条能力各自唯一**：`fetchXPage`/`hasMoreOf`（读一页，UI 自己翻页时用）· `fetchAllXPages`（取全量，语义上就要全部时用）。
3. **不吞错、不假装完整**：任何一页失败原样上抛；响应缺 `items/total/totalPages` → **抛错**
   （缺了就无法诚实判断"是否已取齐"，给默认值 = 假成功）。
4. **快照语义**：循环上界取第 1 页的 `totalPages`，翻页期间新增不保证包含 —— 保证循环必然终止（不对移动靶追逐）。
5. **能精确查的不用全量代替查询**：⑤ 改用后端 `filters` 等值（`nodeId` → `node_id = ?`），
   这才是"正确形态是查询而不是拉全量再筛"。

**不动**（判据属于各 UI，合并会削能力）：各面板的页大小（20）与呈现方式（无限滚动 / 点击翻页）。

## §六 · 弯路留痕（必须记）

### 弯路 ① 我轻信了注释，把"前端封装漏参数"当成"后端不支持"（A1/A2 同款）

**当时推理链**：读 `librarySource.ts` 注释「`fetchResources` **不支持 keyword 参数** → 关键词只能在
已加载的第一页内过滤」→ 直接采信为事实，在方案里把它当成"后端能力缺失"这一**约束**来设计（甚至考虑过
"要不要请后端加搜索端点"）。

**为什么错**：注释是**描述层**，不是真相。取证 `localTool/src/utils/helpers.ts:226` 发现：
`const search = url.searchParams.get('search')` —— **后端一直在读 search 并做多列 LIKE**，
`buildPaginatedQuery` 也早就支持。缺的只是前端 `fetchResources` 没暴露这个参数。
⇒ 所谓"只能搜已加载页"的妥协（连 `meta.keywordScope:'loaded-page-only'` 都标好了）**根本不必存在**。
这正是本仓 M4 母体的活标本：**描述与代码脱节，而读描述的人（我）差点照它设计**。

**是否完整回退**：无需回退（结论方向未变），但**决策依据已改正**为"读后端实现，不读注释"；
并把这两处描述**回改**（`librarySource.ts` 文件头 + `mediaRefTypes.keyword` 注释），防下一个人再踩。

### 弯路 ② 我靠推理断定"8 个测试会因 mock 缺失导出而报错"，实测证明是错的

**当时推理链**：`vi.mock('.../localToolApi.ts', () => ({ fetchTasks }))` 是**部分 mock**；而
`pagedList` 现在同时 import `fetchResources` 与 `fetchTasks` → 我推断"缺失的具名导出会让 vitest 抛错"，
于是准备去改 8 个测试文件（ImageGenerate ×4 / VideoGenerate / TextGenerate / TemplateNode / ensurePolling）的 mock。

**为什么错**：**没实测就动手**。实跑一批后：`ImageGenerate.upstream` / `taskStore` / `GeneratedView.refresh`
**全绿**（vitest 对缺失具名导出宽容，返回 undefined，不抛）。真正红的只有 `mediaRef.test.ts` 2 例，
且红因是**我新加的 fail-fast**（它的 mock 响应缺 `total`，本就不是合法后端响应）。
⇒ 若照推理动手，会在 8 个无关文件里加 8 行"防一个不存在的问题"的兜底 —— 正是本仓最痛的那种债。

**是否完整回退**：✅ 未改那 8 个文件（本来就不需要改）。`mediaRef.test.ts` 的修法是**让 mock 更真**
（mock 目标上移到 `pagedList`，贴住消费方契约），**不是**放宽 `toSlice` 的检查 —— 测试红的方向是"mock 不完整"，
不是"契约太严"。

### 弯路 ③ 同一个 `tsc` 命令，三种口径给出两种结论（假红）

**当时推理链**：① 先跑 `npx tsc --noEmit 2>&1 | Select-Object -First 30` → 输出**空** ⇒ 判定"0 错"并写进本文件。
② 收尾复跑 `npx tsc --noEmit`（无管道）→ 报出 `videoEditor/.../transition-node.ts` **2 个 TS2339**
（`clearRect` 不在 `WebGLRenderingContext` 上）⇒ 一度以为本轮改坏了类型。

**为什么错**：两种口径都不可靠 ——
- `| Select-Object -First 30` 会在读满 30 行前关闭管道，**上游 `npx` 被提前终止**，输出被吞 ⇒ **假绿**；
- 无管道的增量模式会**复报 `tsconfig.tsbuildinfo` 里记录的陈旧错误**（该文件与 `HEAD` 逐字节一致、
  本轮从未改动，已由 `git diff --stat HEAD` 取证）⇒ **假红**。

**定案口径**：`Remove-Item tsconfig.tsbuildinfo` 后跑 `npx tsc --noEmit` ⇒ **0 错**（真实状态）。
⇒ 教训：**类型检查这类"全量结论"必须用干净全量口径取**，且**注入/清缓存都要走受控命令**；
被管道截断的输出不能当作"通过"（与 `assertScanned` "扫到 0 ≠ 干净" 同一条哲学）。

**是否完整回退**：✅ 无需回退（本轮未改任何 videoEditor 文件；`git diff` 已证实该文件与 HEAD 一致）。
仅删除构建缓存 `tsconfig.tsbuildinfo`（可再生产物，非源码）。
