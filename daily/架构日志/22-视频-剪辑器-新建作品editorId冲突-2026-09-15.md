# 22 · 视频（剪辑器）· 「新建作品」失败（editorId 冲突）· 2026-09-15

> **触发**：用户报「新建作品失败：`[StorageService] 工程本体写入 editorId 冲突：上下文=10b1c5b2-…，project.metadata.id=72bab2c2-…`」（video editor 内）。
> **开工口径**（7 步法「用户报症状」节）：**不找那个 bug，去找这段设计正确时该长什么样，然后照着重写。**
> 症状不是要修的对象，是"这段设计错了"的报信人。

## 一、链路快照（读代码取证，非凭名猜）

报错点唯一 —— `engine/services/storage/service.ts` 的 `resolveEditorIdFor`：

```ts
if (ctx.editorId !== projectMetadataId) {
  throw new Error('[StorageService] 工程本体写入 editorId 冲突：上下文=…，project.metadata.id=…');
}
```

「新建作品」编排点：`ui/editor/editor-header.tsx` `handleCreateProject`
→ `engine/core/managers/project-manager.ts:79` `createNewProject`（`generateUUID()` → **立刻** `storageService.saveProject`）。
→ `saveProject` → `resolveEditorIdFor(project.metadata.id)`。

**冲突成因（纯时序）**：`createNewProject` 生成的是**新 uuid**，必然 ≠ `editorContext.editorId`
（此时仍是**上一部**片子 —— 头部的 `saveActiveEditorId` 要等 `createNewProject` 返回后才执行）。
即：**新工程的 id 还没机会进上下文，守卫已经在 `saveProject` 里抛了。**

---

## 二、Step 0 · 普查：写盘槽位 `(canvasProjectId, editorId)` 的 editorId 从哪来？（4 份实现）

| # | 实现 | 位置 | editorId 取值 |
| - | ---- | ---- | ------------- |
| 1 | `saveProject` | `service.ts`（原 `:222`） | `resolveEditorIdFor(project.metadata.id)` —— **上下文优先 + 冲突抛错** |
| 2 | `loadProject` | `service.ts` | 调用方传的 `id`（实参） |
| 3 | `deleteProject` | `service.ts` | 调用方给的 `id`（实参） |
| 4 | `clearAllData` | `service.ts` | `item.id`（列表项**自带**） |

**份数 = 4**，其中 **3 份直接用"实体自带 id"**，只有第 1 份引入了"模块上下文"这个**第二真相源**
（grep 全 `service.ts`：`editorContext.editorId` **仅**出现在 `resolveEditorIdFor` 内 —— 这一格只为喂这条守卫而存在）。

→ 漂移必发生在它身上。

---

## 三、Step 1 · 证伪：这条守卫真的在防什么吗？

三问（缺一不可）：

1. **根因证据**：行为测试**先红**（见 §八）—— 新建作品 / 一次落多部，都被它拦下。
2. **替代方案**：键 = `(canvasProjectId, project.metadata.id)`。写到哪个槽位**由实体自己决定**，天然无歧义；
   上下文那一格在删掉守卫后**零消费者**（上节 grep 实证）。
3. **致命一问**：「加了这条守卫，用户/系统能多做哪件原来做不到的事？」—— **答不出**。

**裁定：假守卫（假需求）**。它拦的是**合法操作**。删。

> 与 `docs/134` T3 原设计的关系：原文只让 `setEditorContext` 注入 `(canvasProjectId, editorId)`，
> 守卫是执行期自加的"保护"。它保护的不是真相，而是它自己造出来的第二份真相。

## 四、Step 2 · 归因：母体还是孤例？

**母体 = M3「同一真相被抄成多份」**：`project.metadata.id`（实体自带）与 `editorContext.editorId`（模块缓存），
并用一条守卫强制两者一致。

同一母体的症状（≥3，母体判据成立）：

| # | 症状 | 性质 |
| - | ---- | ---- |
| 1 | **「新建作品」必抛**（用户报） | 用户可见 |
| 2 | `duplicateProjects` 一次落 N 个新 id → 必抛 | **潜伏**（该 API 当前无 UI 调用点，`grep duplicateProjects` 仅定义处 1 命中）——但**结构上根本表达不了** |
| 3 | `saveActiveEditorId` 被迫兼职"改上下文"（写 active 键与切上下文耦合） | 结构耦合 |

> 症状 2 是**决定性论据**：它证明"在每个调用点补上下文"这条路**架构上不可行**（见 §五）。

## 五、Step 3 · 定位：判据该落回"拥有真相的那一层"

五问：真源 = `ProjectManager.createNewProject` 生成、住在 `TProject.metadata.id`；变化速率 = 每新建一部就变
（不属于"编辑器会话"这个慢变量层）；实现份数 = 1（**不需要抽象**）；改动半径 = `service.ts` + 2 个 UI 调用点；
接口 = 上下文只剩 1 个字段（**更窄**）。

| 真相 | 谁拥有 | 落哪 |
| ---- | ------ | ---- |
| `canvasProjectId` | 引擎**不携带**（`TProject` 里没有它）；只有"编辑器挂在哪个画布项目上"这层知道 | 模块上下文（外部注入） |
| `editorId` | **工程实体自带**（= `TProject.metadata.id`，docs/133 §2.1 M-4） | 取自实体，**不进上下文** |

**为什么"在每个新建/切换调用点补 `setEditorContext`"是错的（本节的关键排除）**：

- `duplicateProjects` 一次落 **N** 个新 id，而上下文只有**一格** ⇒ 该方案在这条路径上**结构上无法成立**，
  只能退化成"每次写盘前轮番改全局态"（比守卫更脆弱）；
- 且调用点是**手写清单**（挂载 / 新建 / 复制 / 未来入口…）—— 手写清单本身就是附录 A4 的母体（必漂移）。

## 九、弯路与教训（强制留痕，7 步法）

1. **本轮排除掉的那条弯路（必须记，它看起来完全合理）**：
   第一反应是「**在每个新建/切换调用点补 `setEditorContext`**」—— 不动 storage 层、改动更小，
   而且守卫自己的注释就是这么建议的（"注入上下文必然发生在 save 之后"）。
   **它是错的，且错因是结构性的**：`duplicateProjects` 一次落 N 个 id、上下文只有一格 ⇒ 这条路走不通（§五）。
   → 教训：**"在调用点补一步"永远是可疑的修法**；先问"这条判据落在拥有真相的层了吗"。
   （本轮**未实际改码**即排除，故无需回退。）

2. **顺带回改一处失实注释**：`editor-header.tsx` 原文称"`saveActiveEditorId` 必须在 `loadProject` 之前，
   否则 loadProject 仍按旧 editorId 组键，读回的还是上一部"。
   取证：`loadProject({id})` **从未读过**上下文 editorId（它一直按传入实参组键）——
   该注释描述了一个**不存在的机制**（附录 A2）。已就地写明"该机制不存在"而非直接删除（保留推理链）。

3. **`docs/134` 的修正落在原文**（T3 + E.1 U-1 就地改），未另开"修正表"——否则就是亲手造 SSOT 第二份（附录 A7）。
