## 一 · 需求澄清（弯路留痕 · 强制）

**弯路：把「任务中心」误当成一个导入来源。**
- **当时推理**：用户列举"1 侧边栏任务中心 2 生成 3 素材 4 画布"，我当成 4 个 providers。
- **用户纠正**：「任务中心只是跟你说的是位置而已，那又不是图片」「我只是要它的**交合规范**（视觉/交互范式），
  并不是让他作为导入来源」。
- **教训（值得留痕）**：用户列举里的条目**未必是同质项** —— 有的指"数据来源"，有的只是**指位置/借范式**。
  我按"并列枚举 = 同类"处理，把参照物当成了数据源。**判据**：列举项要逐条问"它是被读的数据，还是被借的形态"。
- **处置**：任务中心**不进弹窗**；creative **只借交互规范**（复用其 CSS 类），不是数据源。

**另一处修正：把「生成」误判为「与素材库同源、应合并」。**
- **当时推理**：两者都调 `fetchResources` → 我判定可合并为一个 tab。
- **用户纠正**：「生成里面的图和视频也是可以导的呀，因为生成里边和画布里面的图未必是同一个」。
- **取证确认（成立）**：`GeneratedView.tsx:176` 硬编码 `folder:'tasks'`；素材库读用户目录 → **不同目录、不同一批**。
- **处置**：拆成 `generated` 与 `library` 两个来源（provider 层**委托复用**同一映射，只差一个 folder 参数）。

### 4.3 死代码闸抓到的真实问题（当场修，非抑制）

**闸报 4 条**：`base/media/index.ts`（0 消费）+ `providers/index.ts` + `generatedSource.ts` + `hasMediaRefSource`。
- **取证**（`mv-sync-refs refs`）：`base/media/index.ts` **模块引用 0 处** —— 弹窗当时直接 import 了 `mediaRefRegistry`。
- **判据**：这不是假阳性。`@public` 通道要求"真实消费者路径 + 该文件真含符号名"，**不适用**（确无消费者）。
- **修法（按闸的裁决路径，不宽基线）**：
  ① 弹窗改**经唯一出口** `../media/index.ts` 消费（这本来就是契约：漏走它会静默少来源）；
  ② `hasMediaRefSource` **删**（与 `listMediaRefSources` 是同一真相的两种问法 + 零消费者 = M6 幽灵预留）；
  ③ 出口**只导真实被消费的符号**（`listMediaRefSources` / `queryMediaRefs`），其余按需直取 `mediaRefTypes`/`mediaRefRegistry`。
- **复跑**：`当前 0 条` ✅。

## 五 · 路线 A 的代价与后续（用户裁定 2026-09-17）

**用户选择路线 A**（`fetch(ref.url)` → blob → `new File()`，**不上传**），并同意架构师建议的三步走：

| 步 | 内容 | 状态 |
| --- | --- | --- |
| 1 | 路线 A + **大小保护**（`LINK_MAX_BYTES = 100MB`，超限进 failures 不 OOM） | ✅ **本轮已做** |
| 2 | 实测：导入大视频是否真卡/OOM | ⬜ 待实测 |
| 3 | 若实测证明需要 → 路线 B（`MediaAsset.file` 惰性取 / 允许"无 file 只有 url"） | ⬜ 待实测决定 |

**为什么不当场做 B**：A 与 B 在"不复制、不落盘"这个**正确性判据上等价** —— B 是**性能优化**（省内存），
不是正确性修正；而 B 要动 `MediaAsset.file` 公共类型（波及 `media.tsx:127/178`、`processing.ts:186` 等）。
**不为假设的痛点付真实成本**（`docs/136` §五 同一精神）。先例：`service.ts::loadMediaAsset` 已用同款 A 做法。
