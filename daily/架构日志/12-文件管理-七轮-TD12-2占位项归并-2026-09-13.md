## 一、Step 1 · TD-12-2 证伪（原债「同一素材两行」不成立）

原债：「前端 `resourceStore` 双注册表未合并（随机 id vs 后端路径 id）…… → **同一素材两行**」。

逐条核验：

| 声称 | 实测 | 判定 |
| - | - | - |
| 双 id 空间并存 | `buildResourceRecord:269` `id: item.id \|\| genId()`（`resource-xxx` 随机）vs 后端 `resources.ts:84 resourceIdOf` = `local-${folder}-${name}`（**磁盘文件名派生**） | ✅ **成立** |
| 实害「同一素材两行」 | ① `useResources`（store 列表 hook）**生产零消费** —— 全仓仅 2 处**测试** mock，且它本身已在**死代码基线**（`resourceStore.ts::exports::useResources`）；② 素材库面板渲染**后端 items**（`ResourceLibrary:524 items.map`），不渲染 store 列表；③ `getResources` 唯一生产消费方 `AssetNode:83` 按 **contentId** 查，而占位项**无 contentId** → 永不匹配 | ❌ **不可观测**（无 UI 路径） |
| 残留（**结构**，非实害） | 占位项**永不回收**：`mergeResourcesFromBackend` 只按 `id` 归并，随机 id 与后端路径 id 永不相交 → 本地项常驻（`persistDebounced → contentSet(STORAGE_KEY, resources)` 落 localStorage）。**量化实测**：典型占位项 **202 B/条**（`/files` 绝对 URL）→ 撑满 5MB 配额需 **~2.6 万次**发送；`data:` 200KB 边界态 **273 KB/条**（20 次触限，但其**触达频率未举证**） | ⚠️ **结构性重复**（**无用户可见实害**；**无已证实的体积实害**） |

> **结论**：债描述的方向对（双 id 空间并存），但**声称的用户可见症状不成立**（列表无人渲染；`AssetNode` 按 contentId 查，占位项无 contentId → 永不匹配）。**量化后体积论据亦不成立**（典型 202 B/条，可忽略）。
> ⇒ 本项**降级为「结构小修」**：目标只是「同一素材不要在 store 里留两份登记」，**不是**修用户可见 bug，**不是**修体积问题。

## 三、Step 6 · 施工（`resourceStore.ts`，两处）

1. **`persistUrlToBackend` 改返回 `Promise<string|null>`**：三个落盘分支（data / blob / http）各自捕获 `saveInlineToLocal`/`uploadFileToLocal` 的返回 url，成功后统一返回（失败/跳过 → null）。
2. **`sendToResourceLibrary` 落盘成功后校正占位项**：`.then(localizedUrl => patchResource(placeholderId, { url: localizedUrl }))`（新增模块内 `patchResource`）。两个调用方（`AssetNode:337` / `ImageGenerate:571`）**均忽略返回值** → 安全。
3. **`mergeResourcesFromBackend` 归并身份加 `url`**：`kept = resources.filter(r => !incoming.has(r.id) && !(r.url && incomingUrls.has(r.url)))`。

> `localizeAndStoreToResourceLibrary` 路径**无需改**：它登记时 url 已是后端持久 url → 直接被 url 归并命中。

4. **（追加 · 用户裁定）落盘结果契约 + 禁重分类**：`persistUrlToBackend` 的返回由 `string|null` 改为**判别联合 `PersistOutcome`**（`ok` 判别位 + `reason:'upload-failed'|'exception'` 原因码）；并把 `rescanResources()` 从「落盘 try」中**移出** —— 此前 rescan 抛错会被外层 catch 归为「落盘失败」，把**已到手的持久 url 一起丢掉**（违反 Step 4「禁重分类」）。

   - **Step 3 分辨**：未显式做「**探测重复 vs 判据重复**」分辨（本次是单一数据归并规则、非分层判据，结果无碍，但流程漏了）。
   - **Step 4 形态**：~~`persistUrlToBackend` 返回 `string|null`（把「失败」与「跳过」压成一个 null），未用判别联合~~ → **已按用户裁定修正**（见 §三.4）：改判别联合 `PersistOutcome`，并把 `rescan` 移出落盘 try（消除「rescan 失败被重分类成落盘失败 → 丢掉已到手 url」）。**先红后绿**：恢复旧语义 → 该用例精确红（`expected 'data:…' to be 'http://…'`）。
   - **顺带发现的工程约束（重要）**：本仓 `tsconfig` 为 `strict:false` / **`strictNullChecks:false`** → TS 对 `boolean` 判别位**只在「真分支 / 显式 `=== false`」收窄**，`else` / `!x.ok` / 三元假支读失败分支字段报 **TS2339**（工程内最小对照实测；两轮取证修正，字符串/数字判别位不受影响）。故判别联合须写成「**双方各带对方的键（可选 `undefined`）**」；`ok` 仍为判别位、语义不变。**已落成编码约定**（`spec/CONTEXT.md` §三 + `tsconfig` 指针注释），**并顺手收敛 2 处存量点**（`StorageOpResult` / `ImportResult`，含去掉测试端 `as Extract` 绕墙）→ 见 [21-跨区-判别联合boolean窄化约定](./21-跨区-判别联合boolean窄化约定-2026-09-13.md)。
   - **Step 7.1 反向探针偏薄**：改前 `resourceStore.test.ts` 对 merge **零覆盖** → 既有测试 85 例绿只能证明「没弄坏别处」，**不能**证明合并判据未越界。


1. **未做 #7 投影化**（有意）：store 列表生产零消费，投影化无收益；本轮只在**合并点**收敛身份。若日后有 UI 真消费 store 列表，再评估 #7。
2. **离线窗口**：落盘失败时占位项保留原始 url（不校正），此时不与后端归并 —— 符合「离线仍可见」意图；下次落盘成功会自动归并。
3. **历史存量**：既往已累积的占位项（原始 data:/http url）不会被本轮追溯归并（url 对不上）。属低息存量，随 localStorage 清理或后续 GC 自然消退。
4. **DATAFLOW 无需改**：本轮不新增/删除链路（同一条 发送→落盘→合并 链，只改归并口径）。
