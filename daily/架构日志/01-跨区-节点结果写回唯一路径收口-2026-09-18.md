## 二 · Step 1 证伪（债描述精化）

债文写「写回路径**五条并存**（settle、onPersisted、resultKey、recoverable、onRecover）」。**逐条回读后精化**：

| 债文所称 | 取证结果 | 定性 |
| --- | --- | --- |
| `settle` / `onPersisted` | 是 `runGenerationContract` 的**两个时点回调**（R3 顺序固化），不是并列的"路径" | **非重复**（契约时点），保留 |
| `resultKey` / `recoverable` | 两个声明；但 `recoverable` 在**全部 3 个生产消费方恒为 true**、第 4 个（TextGenerate）两个都不传 ⇒ **else 分支零消费** | **冗余开关（幽灵预留 M6）→ 删** |
| `onRecover` | 承担**非 data 副作用**（ImageGenerate 的「节点被删→用结果重建」、VideoGenerate 的本地 state） | **不可删**，收窄职责 |
| 真正的问题 | hook 内**同判据 3 份** + 节点侧**一条书面许可**允许第二份写回 + `resultField`/`resultKey` 两名 | **真债**（M3 SSOT 第二份 + M4 描述层无对账） |

① **硬证据**：JSDoc 原文背书「并存时幂等双写（无害）」；`useNodeGeneration` 内 3 处 `patchData({ [resultKey]: … })` 各写一遍判据。
② **替代方案**：`resultKey` 声明式已覆盖全部三个时点，`recoverable`/回调写回均无增量能力。
③ **致命拷问**：用户不"多做"事；变的是**写回只有一个入口**（排查"结果没回填"时不再需要同时怀疑 hook 与 4 个节点的回调）。

## 三 · Step 3 定位

- **判据归属**：「写不写 `data[resultKey]`」的真相在**声明它的那一层**（`useNodeGeneration`，写回真相方）⇒
  判据定义在那里并**导出为唯一原语**；消费方（节点回调）**不再持第二份写回**（三铁律③）。
- **改动半径**：源 7 文件 + 测试 5 文件；**对外签名只增不减语义**（`run` 由可选→必填 = 编译期收窄，4 个消费方本就都传）。
- **真假接缝判别**：
  - 写回判据 = 同域**运算重复** ⇒ **强制收口**；
  - `onSuccess`/`onRecover` = **判据/宿主不同的回调**（各节点做各自的 UI 副作用）⇒ **保留分层、只收窄职责**，**不合并**。

## 四 · Step 4 定契

```ts
// useNodeGeneration —— 唯一写回原语（成功首写 / 落盘后覆盖 / 广播恢复三处共用）
const writeBackResult = useCallback((url: string | undefined) => {
  const key = resultKeyRef.current;
  if (key && url) patchData({ [key]: url });   // 判据只此一条：声明了就写、没声明就不写
}, [patchData]);

// 契约：
//  resultKey      = data 写回的唯一声明（不再有 recoverable 开关）
//  onSuccess / onRecover = 只做非 data 副作用；禁止再 patchData 同字段
//  run            = 必填（缺它是调用方漏传，编译期即拒）
```

## 六 · 弯路留痕

1. **先按债面意思找"5 个重复实现"，读完发现 5 个里有 2 个不是"路径"**：`settle`/`onPersisted` 是 `runGenerationContract` 的**时序回调**（R3 固化），
   真正的重复是它们**各自内联同一判据**。⇒ **债描述的"五条"是描述层的近似，不是结构事实**（铁律 3 / A2）。
2. **一度打算删掉 `onSuccess`/`onRecover`**（"既然声明式能写回，回调就多余了"）—— 回读节点发现回调承担**非 data 副作用**：
   ImageGenerate 的「节点已被删 → 用结果重建」（`commitNewNodes`）、VideoGenerate 的本地 state、TextGenerate 的「自动拆分建多个文本节点」。
   ⇒ **不能删**。正解是**收窄职责**（只做非 data 副作用），不是砍掉回调。**这是本轮最重要的弯路**（若照初判动手，会砸掉节点重建能力）。
3. **`recoverable` 判冗余的方式**：把 4 个消费方**逐个读完**（3 个恒 true、1 个不传），确认 else 分支零消费 —— **没有靠"看起来冗余"下判断**（附 A6 反滥用：两边都要取证）。

## 九 · 诚实标注（唯一行为差异）

1. **`onPersisted` 不再用空串清空字段**：旧实现 `if (resultKey) patchData({[key]: persistedUrl})`（**不校验非空**）——
   若落盘返回空 URL，会把已显示的 URL **覆盖成空**；新实现经 `writeBackResult` 要求 `url` 非空 ⇒ 空 URL 时**保持不变**。
   取证：`generationContract` 仅在 `outcome.ok && !outcome.skipped && outcome.url !== url` 时调 `onPersisted`，正常路径 `outcome.url` 非空；
   旧行为只在异常边角触发，且**旧行为是错的**（拿空串抹掉好数据）。
2. **未改可见能力**：写回时机、写回值、恢复行为对全部 4 个节点**逐字节一致**；`run` 可选→必填只影响编译期。
