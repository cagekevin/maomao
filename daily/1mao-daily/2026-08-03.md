## 一、React 双实例 / vendor 死重修复（方案 S1）真机验证闭环

**现象（历史）**：真机打开带 Three.js 的画布页崩溃：
```
THREE.WARNING: Multiple instances of Three.js being imported.
TypeError: Cannot read properties of null (reading 'useMemo')
    at e.useMemo (vendor-Z-adA07W2.js:1:7323)
    at lg (App-BX6o9fW5.js:31:54230)
    at fi (vendor-Z-adA07W.js:8:48278)
    ...
```

**根因（§2.2 机制 + 本次确认）**：
- 源 `index.html` / `share/index.html` / `public/share/index.html` 各有一行 `<link rel="modulepreload" ... vendor-Z-adA07W.js>`。
- 该 preload 把 `vendor-Z-adA07W.js` 变成 **entry 身份**，占用输出名 `vendor-Z-adA07W`；`vite.config.ts:79` 的 `manualChunks` 又对同名源文件强制命名 `vendor-Z-adA07W` → Rollup 命名冲突 → 被 import 的副本被迫追加 `2` 后缀 → 产出 `vendor-Z-adA07W2.js`。
- 于是 `main-CYvt_zul.js` 用**无2版 vendor** 的 react-dom 渲染 App，而 App 的 hooks（经 `_react_shim`）静态改写后解析到 **`adA07W2` 的 React** → 运行时双 React 实例、dispatcher 为 null → `useMemo` 崩溃。

**修复（方案 S1，已实施）**：删除三处 HTML 的 vendor `modulepreload` 行（各删 1 行，共 3 行）：
- `index.html`
- `share/index.html`
- `public/share/index.html`

**静态验证（通过）**：`npm run build` 干净重建后 `dist/assets/` 只剩 **1 个** `vendor-Z-adA07W.js`，`adA07W2` 消失；全部 8 个业务模块（`main`/`share`/`App`/`ShareAppPage`/`_react_shim`/`_jsx_runtime`/`httpClient`/`mediabunny`）React 符号 100% 指向同一份 vendor；`npm run test:smoke` **ALL PASS**（含 `dist 重复 chunk  PASS`）。

**真机验收（✅ 通过）**：打开带 Three.js 的画布页，`useMemo` 崩溃**消失**、`Multiple instances of Three.js` 警告**消失**。真机报错栈消失，闭环达成。

**登记**：`docs/22-React双实例与vendor死重排查报告.md` 顶部新增「✅ 修复已真机验证闭环（2026-08-03）」状态块；§九 新增「试错 #3 · 成功」；旧「试错 #1」S1 失败结论标注已被复测推翻。

## 二、遗留 Bug B 说明（非本次修复范围，另立跟踪）

**Bug B 是什么**：`dist/share/index.html` 同时注入 `main-CYvt_zul.js` 与 `share-CyPsaet6.js` 两个入口脚本。

**成因**：`main` 与 `share` 两个 entry 各自源码都定义了同名的 `__vite__mapDeps` 辅助函数，Rollup 在构建期将其提取为共享代码、归属到 `main`，再让 `share` 反向 `import main` → 分享页把主画布应用和分享页两个入口**同时挂载到同一个 `#root`**。已实测 `main-CYvt_zul.js` 与 `share-CyPsaet6.js` 各含 1 处 `createRoot`，即分享页会跑**两次 `createRoot`**。

**影响**：双 `createRoot` 并发渲染同一 `#root` 会互相打断渲染阶段，属独立于 React 双实例的第二个潜在崩溃源（docs/22 §2.6 Bug B / 方向 C）。

**✅ 已于同日修复并真机验证通过**（见下文「三、Bug B 修复」）。

## 五、修复：文字节点自动拆分成功后任务中心一直 running（真实 bug）

**现象（用户报告）**：文字节点勾选「自动拆分」后，画布上拆分节点已正常生成，但任务中心对应任务**一直等待结束**（永远 `running`）。**不勾选自动拆分则正常**。

**根因**：文本生成函数 `Lr`（`src/bundle/httpClient-BknZwXjG_components/H_.jsx`）在自动拆分成功分支里**提前 `return`**（返回 `{splitNodes,clonedNodes,newEdges}`），跳过了函数尾部把任务标记为 `completed` 的 `if(I){...status:'completed'...}` 逻辑。画布节点已生成（`K`/`q` 更新了节点与连线），但任务记录从未被收尾 → 任务中心永远停在 running。

**修复（改 `src/bundle/` 后 `npm run build` 回灌 `dist/`）**：在自动拆分成功分支的 `k("已自动拆分为 N 个节点并复制后续节点")` 之后、`return` 之前，补齐与函数尾部同款的任务收尾逻辑（按 `e.id===C || e.taskId===C` 标记 `status:'completed', progress:100, resultUrl:E`）。

**验证**：`npm test:smoke` ALL PASS（契约/React 单实例/chunk 完整）→ `npm run build` 回灌 dist 成功 → 无 lint 错误。

## 六、修复：图生图侧边栏请求日志为空（真实 bug）

**现象（用户报告）**：图片节点——文生图侧边栏能正常显示请求日志（`{model,prompt,n,image_size,quality,size}`）；**图生图侧边栏有一条日志但请求内容为空**。

**根因**：图生图因需上传参考图，请求体 `B` 走 **FormData** 分支（`B.append('image', blob)`），而非普通对象。任务记录 `requestData: B` 原样存 FormData；侧边栏日志组件 `jn.jsx:539` 调 `Dn(requestData)`（`shared.js:865-866`）对非字符串执行 `JSON.stringify(e)`，而 **`JSON.stringify(FormData)` 恒为 `{}`**（FormData 无自有可枚举属性）→ 日志显示空对象。文生图 `B` 是普通对象，JSON 正常，故不受影响。

**修复（改 `src/bundle/` 后 `npm run build` 回灌 `dist/`）**：任务记录 `requestData: B` 改为 `requestData: re ? Object.fromEntries(Array.from(B.entries()).map(([k,v]) => [k, v instanceof Blob ? `[${k}:${v.type||'file'}:${v.name||'blob'}]` : v])) : B` —— 仅当 `re`（FormData）时转普通可序列化对象，Blob/File 参考图字段转可读占位符；非 FormData（文生图）行为不变。**不影响实际请求发送**（发送仍用原始 `B` FormData）。

**验证**：`npm test:smoke` ALL PASS（契约/React 单实例/chunk 完整）→ `npm run build` 回灌 dist 成功 → 无新增 lint 错误。

**登记**：`docs/01 长期目标-未来适配方向.md` 四.2 变更登记新增 **变更 #10**。
