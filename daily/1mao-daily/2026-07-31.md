## P0-2：SSE 流式转发（3 次迭代）

### v1：SSE 管道直传 + zlib 解压
- **文件**：`system.ts` `handleProxyFormData` 和 `handleProxyJson`
- **新增 import**：`Readable`(stream)、`createGunzip/createInflate/createBrotliDecompress`(zlib)
- **逻辑**：检测下游 `Content-Type: text/event-stream` → `writeHead` → `Readable.fromWeb(fetchRes.body)` → zlib 解压 → `pipe(res)`
- **问题**：`skipHeaders` 去掉 `content-encoding` 但没本地解压（v1 补了 zlib 解压后 pipe）

### v2：过滤 `: heartbeat` + 保留 `data:` 前缀
- **问题发现**：网关返回 `: heartbeat\n\n` 行，直接 pipe 给前端 → 前端 `JSON.parse(": heartbeat")` 报 `Unexpected token ':'`
- **前端解析代码**（`httpClient-BknZwXjG.js` 位置 951968）：
  ```javascript
  for(let e of s) {
      let t = e.trim()
      if(!t || !t.startsWith('data:')) continue  // ← 关键！
      let n = t.slice(5).trim()                   // 去 "data:" 取 JSON
      JSON.parse(n) → choices[0].delta.content
  }
  ```
- **第一次尝试**（错误）：`createSSEParserTransform()` 剥离 `data:` 前缀，输出裸 JSON → 前端全部跳过
- **修正**：保留 `data: ` 前缀，只过滤 `: heartbeat` 注释行
- **Content-Type**：`text/event-stream`（前端据此判断流式模式）

### v3：非流式 chat 请求强制 `stream:false`
- **问题发现**：文本节点聊天用 `await T.json()` 解析响应（不支持流），网关 `chat/completions` 默认 `stream=true` 返回 SSE → 前端 `JSON.parse` SSE 失败
- **前端代码**（`httpClient-BknZwXjG.js` 位置 965457）：
  ```javascript
  let T = await Bl(v, {...body:JSON.stringify({model:..., messages:_, ...})})
  let E = (await T.json()).choices?.[0]?.message?.content || ''
  ```
- **修复**（`system.ts` `handleProxyJson`）：
  ```typescript
  if (body.url?.includes('/chat/completions') && !fetchBody.includes('"stream"')) {
      const p = JSON.parse(fetchBody);
      p.stream = false;   // 网关默认 true，前端用 T.json() 不支持
      fetchBody = JSON.stringify(p);
  }
  ```
- **验证**：curl 不带 `stream` → 返回纯 JSON `{"choices":[{...}]}` ✅

## P0-3：协议翻译层 + Content-Length 修复

### 信封剥离
- **文件**：`system.ts` `handleProxyFormData` 和 `handleProxyJson`
- **逻辑**：网关用 `ok(data)` → `{code:200, data}`。检测 `code` + `data` 字段 → 仅返回 `data`
- **安全降级**：非 JSON、无 `code` 字段、含 `error` → 原样透传

### Content-Length 不匹配（关键 bug！）
- **问题发现**：P0-3 改 body 后 Content-Length 仍是网关原值 → 浏览器等缺失字节 → `failed to fetch`
- **实测**：网关 `{code:200,data:[{task_id:...}]}` 98 字节，剥信封后 74 字节，差 24
- **修复**（4 处）：`skipHeaders` 加 `content-length`，`writeHead` 移到 P0-3 翻译之后
  ```typescript
  const skipHeaders = new Set(['transfer-encoding', 'connection', 'keep-alive', 
                                'content-encoding', 'content-length']);  // ← 新增 content-length
  // P0-3 翻译 ...
  res.writeHead(fetchRes.status, resHeaders);  // ← 移到翻译之后
  res.end(finalBody);
  // Node 自动用 Transfer-Encoding: chunked，不设固定 Content-Length
  ```
- **验证**：curl -i → `Transfer-Encoding: chunked`，无 `content-length` 头

## 后续排查（2026-07-31 下午）

### 一、502 bad_gateway：Win 连不上 Lovart
- **现象**：localTool 代理返回 `502`，`error:"All connection attempts failed"`（连接 Lovart 失败）
- **根因**：Win 这台机器**未开 VPN**，连不上 `lgw.lovart.ai:443`。这是**纯网络层建连失败**，非鉴权/代码问题。Mac 一直开 VPN 所以正常。
- **网关 `.env` 配置正确**：AK/SK 已填、`LOVART_BASE_URL=https://lgw.lovart.ai`、`OPEN_RELAY=true`
- **诊断（Win）**：DNS 解析 / 代理变量 / TCP 443 探测均指向网络不可达
- **修复**：开 VPN 后恢复正常
- **待确认建议**：在 `launch-all.ps1` 加启动前连通性自检——连不上 `lgw.lovart.ai:443` 就倒数提示「请先开 VPN」再退出，避免再次静默卡住。

### 二、图片请求数据侧边栏显示 `{}`
- **现象**：画板侧边栏日志「请求数据」对图片任务显示 `{}`，但**文生图正常**
- **取数链路**：侧边栏 `Dn(e.requestData)` 读任务记录的 `requestData` 字段；localTool `tasks.ts` 仅透传落库，不修改
- **根因**：画布 `dist/assets/httpClient-BknZwXjG.js` 图片生成函数，在**带参考图的图生图/编辑**分支走 FormData：
  - `v.length===0`（纯文生图）→ `B = {model,prompt,...}` 普通对象 → 序列化正常 → 显示正常
  - `v.length>0`（带参考图）→ `re=!0`、`B=new FormData()`，任务写 `requestData:B`；而 `JSON.stringify(FormData)` **恒为 `{}`** → 显示 `{}`
- **与 P0-4（异步转同步）无关**：`re`/`B` 的构造是画布前端逻辑，P0-4 只动了 `localTool/src/routes/system.ts` 的 `handleAsyncPoll`，未触碰此路径。之前 Mac「正常」是测文生图，这次 Win 看到 `{}` 是测带参考图编辑。
- **修复方向（待拍板，未改）**：
  - **A（最稳）**：在画布**源码仓库**的图片任务创建处，把 `requestData:B` 改为 FormData 时存可序列化摘要（如 `{model, prompt, imageCount, _form:'FormData'}`）
  - **B（临时）**：直接 patch `dist/assets/httpClient-BknZwXjG.js` 混淆包；脆弱、下次构建会被覆盖
  - **约束**：localTool 后端救不回（`{}` 在画布 `JSON.stringify` 任务时即已定型）

### 三、任务中心（日志）重复记录：根因 + 修复

- **现象**：每次打开画布 / 任务中心，「日志」面板的历史记录重复累加（实测 20/126 条，每条文本 / 图片相同）；而「资源」界面按 `nodeId` 去重只显示 1 个。新任务运行时正常，一旦成为「历史」再次打开就重复。
- **实测数据**（Node 直连后端）：
  - SQL `/api/tasks` 共 **126 条**，每条 `taskId` 都是不同时间戳、`nodeId` 全相同（`promptNode-...xxwpv`）、`prompt` 全相同 → 后端确实存了 126 条，非前端渲染重复。
  - KV `globalTasks` 为 `null` → 任务中心直接读 SQL，不读 KV。
- **根因（前后端去重契约不一致）**：
  - 前端 `httpClient` 的 `diffAndPersistTasks` 以任务对象的 **`id`** 字段作为去重 / diff 基准键（按 `e.id` 建 map）。
  - 但后端 `GET /api/tasks` 的 `rowToTask`（`tasks.ts:26`）只把 `task_id` 映射成 `taskId` 返回，**没有回传 `id`**。
  - 于是前端重新打开、拉取历史后记录没有 `id` → 去重键缺失 → diff map 全部 miss → 整组被当作「新增」重新写回 → 越攒越多（20/126）。
  - 一句话：前端用 `id` 判重，后端不提供 `id`，契约不匹配。
- **修复**：`localTool/src/routes/tasks.ts` 的 `rowToTask` 返回前补 `task.id = taskId`，并附注释说明原因（见源码 34 行附近）：
  ```typescript
  task.id = taskId;   // 补齐前端去重所需的 id，避免 reload 后判重失效、重复写入
  return task;
  ```
  - **生效条件**：localTool 跑的是编译产物 `dist/index.js`，改 `src` 后需 `cd localTool && npx tsc` 重新构建。
- **关联文档**：根因由子 AI 梳理确认，见 `daily/10-梳理任务书-前端任务唯一标识.md` 与 `daily/11-前端任务唯一标识梳理报告.md`。
- **未做**：历史已累积的 126 条脏数据本次**未清理**（修复只防以后再重复）；如需清理可另按 `node_id` 保留最新一条、删除其余。

### 五、全链路可观测性落地（打通日志与落库）

> 方案文档：`docs/14-全链路可观测性方案-打通日志与落库.md`（v6 审计修订版）
> 改动范围：`apimart-gateway/main.py`（P0-1~4）、`localTool/src/routes/tasks.ts`（P0-5）
> 核心目标：视频卡 running 时从网关日志直接定位 Lovart 真实状态 / 参考图是否进 Lovart / 确认是否执行 / 超时点，不依赖前端。

#### P0-1：网关日志原语 `_log`（`main.py` 28-38 行）
- **事实**：网关此前无任何日志设施（无 `print`/`logging`/`_log`），不打此底所有后续打点代码都会 `NameError`。
- **新增**：`GATEWAY_LOG_LEVEL`（环境变量 `LOG_LEVEL`，默认 `info`）+ `_log(msg, level)` 函数（`print(..., flush=True)`）。
- `level="debug"` 受 `GATEWAY_LOG_LEVEL` 控制，`flush=True` 适配 launch-all 重定向 `.log` 文件不丢尾。

#### P0-2：修复 `reference_videos` / `reference_audios` 静默丢弃（`main.py` 765-772 行）
- **根因**：711 行 metadata 提升已把 `reference_videos`/`reference_audios` 提到顶层，但 741-745 行 `_extract_raw_urls` 只读了 `videos`/`audios` → 视频/音频参考被静默丢弃。
- **修复**：`videos or reference_videos`、`audios or reference_audios`（最小 diff，`or` 短路覆盖不存在 / `[]` / 单 dict 三种形态）。

#### P0-3：提交入口打点 + tid 全链路透传（`main.py` 736-822 行）
- `_submit_generation`：生成 `tid = X-Trace-Id or uuid`，打 `[submit]` 日志（各路 ref 原始计数 + model + prompt 截断）。
- `_do_submit` 签名加 `tid=None` 参数，调用处传 `tid`。
- `_TASK_META[task_id]` 写入 `"tid": tid`，使后续 `[poll]` 可回读 traceId 关联 `[submit]`。
- `_resolve_attachments` 后打 `[submit:parse]`（raw_urls / attachments 计数，复用已有变量不重复调用 `_extract_raw_urls`）。

#### P0-4：轮询打点 + 两处 AUTO_CONFIRM 日志 + 同步超时（`main.py` 885-954 行）
- `[poll]`：同时打 `lovart_raw`（Lovart 原始状态）和 `effective`（网关改写后），区分 done 防抖 / 真卡住 / pending_confirmation。
- `[poll:confirm]`（status 路径，917-924 行）：第一处 AUTO_CONFIRM triggered + FAILED。
- `[poll:confirm2]`（get_result 路径，944-952 行）：第二处 AUTO_CONFIRM（更常命中），避免假阴性。
- `[submit:sync-timeout]`（838 行）：同步 wait 504 超时埋点。

#### P0-5：修复 `upsertTask` 伪 upsert 抹库（`tasks.ts` 63-76 行）
- **根因**：`DELETE FROM tasks WHERE task_id=?` + `INSERT INTO tasks (...)` 是伪 upsert，任何部分字段 PATCH（如前端只 PATCH progress）都会先把整行删掉再插，已落库的 `request_data`/`response_data`/`error_msg` 全部丢失。
- **修复**：先 `SELECT *` 取历史行合并 → `INSERT ... ON CONFLICT(task_id) DO UPDATE SET`（真 UPSERT），部分字段保存不再抹掉诊断字段。

#### 跳过的项
- §3.3 `error_message` 列不存在：已不适用，`database.ts:107` 建表已含 `error_message TEXT`，119 行有 ALTER 兜底。
- §2.3 `_extract_raw_urls` 扩 dict key：P0-条件，待日志验证 `ref_images_raw>0 && attachments=0` 后再决定。

#### 验收标准
一次视频提交后网关日志应出现：
```
[submit] traceId=... ref_images_raw=N ref_videos_raw=N ...
[submit:parse] traceId=... raw_urls=N attachments=N
[poll] traceId=... lovart_raw=... effective=... poll=N ...
```
所有 `[submit]` 与 `[poll]` 通过 `traceId` 关联，并发可区分。
`lovart_raw=done, effective=running` → done 防抖窗口（5s），正常；`lovart_raw=running` 持续 → Lovart 真卡住。
