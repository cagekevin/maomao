### 一.2.1 数据源与分区权限（SSOT：每种数据各归其最简唯一来源）

**裁决**：**不做物理统一的数据库**。4 个策划分区与「我的提示词」是**来源迥异的两种数据**（前者团队策划、随包发布、运行时不可变；后者用户私有、浏览器内可变），按 §一.2 收敛法则属**真分叉**——强行塞进同一个 `IndexedDB` 是「强行大一统」，会造出种子化 / 迁移 / 异步读 / 合并等附随复杂度，违反本仓降复杂度第一性原理。故各归其最简来源，每种数据仍只有唯一真相源（SSOT 成立）。

| 分区 | 数据性质 | 唯一来源（SSOT） | 运行时可写 | 机制 |
| --- | --- | --- | --- | --- |
| 风格 / 滤镜 / 运镜 / MJ（4 类） | 策划目录，随包发布、只读 | 打包 `src/.../creative/data/*.json`（经 `creativeCatalog.ts` 归一化） | 否（UI 不暴露增删） | 静态 `import`，同步、零持久化代码 |
| 「我的提示词」 | 用户私有、可增删 | 浏览器本地 `promptManager`（`STORAGE_KEY` 本地库，复用既有实现） | 是 | `localStorage`，同步、已存在 |

- **新增提示词** = 直接写 `promptManager`（与 mockup 加号同路），不碰打包 JSON、不 rebuild、不注册。
- **两种来源 ≠ 违反 SSOT**：catalog 只在其 JSON 有一份、提示词只在其本地库有一份，互不复制；统一胶囊插入靠 **`cp_<kind>-<n>` 命名空间**对齐（见 TD-23-6 收口），不需要统一存储。
- **跨用户共享提示词？** 把 `promptManager` 后端从 `localStorage` 换成 API+DB（接口不变），**仅影响第 5 分区**，不动 4 类 catalog 的静态导入。

**对 TD-23-6 的收口**：5 分区共用 `cp_<kind>-<n>` 命名空间；「我的提示词」在 `promptManager` 内以 `cp_prompt-<id>` 归一，**消除 `pp_*` / `cp_*` 双命名空间碰撞**，插入胶囊与字典解析走同一套 `cp_*` 键。

### 一.3 选中态的唯一载体 = 富文本胶囊

**裁决**：唯一真源是 `prompt` 正文里的胶囊；**不设** `data.creativePresets[slot]` 那套 slot 结构（那是 AIFISHER 的，与「胶囊即正文」重复）。

| 项 | 定义 | 锚点 | 状态 | 验证 |
| --- | --- | --- | --- | --- |
| 胶囊序列化 | `@{cp_style-643:暖阳赛璐璐CG}` | `promptChips.ts:51` | 已有 | 复用现有正则，**零改动** |
| id 命名空间 | 用**下划线前缀**而非冒号 | 本文裁定 | — | 见下方「为什么不用冒号」 |
| 芯片渲染 | 走既有 `buildChipEl`，`kind='preset'` 新增一档 | `promptChips.ts:158` | 待建 | `tests/unit/prompt/chips.test.ts`（已有文件，追加用例） |
| 字典 | `data.creativePresets: Record<id, {kind,name,prompt}>`（`kind` 含 `'prompt'`；catalog 仅前 4 类，prompt 条目由 `promptManager` 插入时写入，见 §1.2.1） | `nodeDataSchema.ts:93` | 待建 | `npm run check:node-data` |

> **`creativePresets` 登记是三段动作，不是加一行**（G4 施工注意）：
> ① 三个节点（生图 `imageGenerateNode` / 生视频 `videoGenerateNode` / 文本 `textGenerateNode`）的本地 `interface XxxData` 各加 `creativePresets?: Record<id, {kind,name,prompt}>`；
> ② `NODE_DATA_DEFAULTS` 三个节点项各登记默认值 `creativePresets: {}`；
> ③ `npm run check:node-data --strict` 对账（interface 字段名必须与 defaults 键名一致）。

**为什么 id 用 `cp_` 前缀而不是 `style:643`**
现有正则 group1 是 `[^:]+`（**禁冒号**）：`promptChips.ts:51`。若把命名空间写成 `style:643`，会被解析成 `id='style'` + `label='643:暖阳…'`，显示即错。改正则 = 动字符串契约（序列化格式），要同步 `serializeDOM` / `renderPromptToNodes` / `resolvePromptChips` 三处并重跑旧数据回归。改用下划线前缀，**三处零改动**。

**字典与胶囊的一致性（唯一易漏点）**

> 风险：用户删掉胶囊后，字典里留下孤儿条目并随快照落盘。

| 契约 | 内容 | 落点 | 状态 |
| --- | --- | --- | --- |
| `syncCreativePresets(prompt, dict)` | 扫 `prompt` 里 `cp_*` id 集合，返回只含被引用项的字典（**纯函数**） | `creativePresets.ts` | 待建 |
| 调用时机 | 任何写 `prompt` 的路径（节点 patchData / Agent `update_node_any_field`） | 节点内 + 快照裁剪 | 待建 |

**验证**：`tests/unit/creative/gc.test.ts`（待建）—— 输入「删胶囊后的 prompt + 旧字典」，断言输出键数 = 胶囊数。

### 一.4 合成原语

```
resolvePromptChips(rawPrompt, refImages, refTexts, presets?) → { text, refImages }
```

| 项 | 定义 | 锚点 | 状态 |
| --- | --- | --- | --- |
| 签名扩展 | 第 4 参 `presets`（`Record<id, {prompt}>`），缺省 = 行为与今天完全一致 | `promptChips.ts:249` | 已有 |
| 新分支 | id 以 `cp_` 开头 → 命中 presets → 替换为该条 `prompt`；未命中 → **替换为空**，但须在生成结果留可见标记（⚠ + 缺失预设名）并打红日志（禁静默吞，见 I2） | `promptChips.ts:262` | 待建 |
| 替换语义 | **原文照搬**：`prompt` 字段一字不改替换胶囊，**不 trim、不压换行、不剥标签头**（`视觉风格：`/`影像处理：`/`运镜要求：` 与 `\n` 均为原文一部分，原样保留） | 本文裁定 | — |
| 顺序 | **胶囊在正文中的位置决定片段插入位置**（不同于 AIFISHER 的「统一拼在尾部」） | 本文裁定 | — |
| 与摄影参数的关系 | `applyCameraSettingsToPrompt` 仍**最后追加**，现行为不变 | `cameraPrompt.ts:71` | 已有 |

**为什么不照抄 AIFISHER 的 `composeCreativePrompt`**
它的顺序是「所有 prefix → 正文 → 所有片段」（`CreativeLibrary.tsx` 侧），因为它的 tag 不在正文里、只存在于 `creativePresets`。我们的胶囊在正文里，若再统一拼尾，用户把胶囊挪到句首就无效——**位置即语义**，这是选胶囊方案的必然结果。

**验证**：`tests/unit/prompt/chips.test.ts` 追加 3 例：① 命中替换 ② 未命中置空 ③ 三参调用（老签名）输出逐字节不变。

### 二.4 素材分发裁决（待 G0 定，数据已备）

> **✅ 已裁决（2026-09-15 · 用户拍板）**：**A 全量打包 = 终局**。理由：**本项目素材为作者本人自用**，不存在分发场景 ——
> 无"用户下载体积"、无 CDN/带宽成本、无商店审核；git 收录反而带来「换机器 clone 即全」的收益。
> 故 B/C 的性能/成本换算在此场景**均不成立**（懒加载会把"体积成本"从自身磁盘换成自身带宽 + 断网不可用，净亏）。
> **素材保持 `public/` + 进 git，不做 gitignore、不清历史**。本节 A/B/C 保留为「若将来改为对外分发」的备查。
> 债登记：TD-05-17（已结清，改判非债 —— 前提"107MB 是问题"在自用场景不成立）。详见 `daily/架构日志/05-提示词-创作库落地审计-2026-09-15.md` §十一。

| 目录 | 文件数 | 体积 |
| --- | --- | --- |
| `creative-presets/`（风格 217 + 滤镜 17 图 + 运镜 51 封面 + 51 mp4） | 336 | **77 MB** |

**素材构成实测（补齐原「待补」项）**：mp4 **48 MB**（51 个，运镜动态预览）；webp/jpg/png **70 MB**（1271 个）。→ mp4 占 **44%**。

**运行形态约束**：本仓是 Chrome 扩展（MV3，`public/manifest.json`），体积影响安装与更新体感 —— **但仅对「对外分发」成立**；自用场景不适用（见上裁决）。

| 路线 | 做法 | 代价 | 自用场景判定 |
| --- | --- | --- | --- |
| **A 全量打包** ✅ | 110 MB 进 `public/` | 扩展包体翻一个量级；商店审核与更新变慢 | **终局**（无分发 = 无此代价） |
| **B 目录打包 + 预览远程** | 两个 JSON（几百 KB）打包；图/视频走 CDN + 本地缓存 | 需图床/CDN；离线不可用 | 不采用（自建服务器成本，纯亏） |
| **C 目录 + 样图打包，其余懒加载** | 每类带少量样图（mockup 现在就是这个：223 文件 / 16.9 MB） | 实现最复杂；首屏与离线兼顾 | 不采用（"省包体"换来"花带宽 + 断网破图"，净亏） |

> **原「倾向 C / 阈值 <40MB 改 A」作废**：该判据的前提是「包体要发给别人」。自用场景下判据改为 —— **素材是否对外分发？否 → A**。
